# Bugfix: v1.4.5 — eso-ldap-directory Vault policy missing keycloak/* paths

**Branch:** `k3d-manager-v1.4.5`
**Files:** `scripts/etc/ldap/vars.sh`

---

## Problem

`keycloak-secrets` and `keycloak-client-secrets` ExternalSecrets in namespace `identity`
remain in `SecretSyncedError` state after the `vault-kv-store` SecretStore fix. Keycloak
and postgres pods cannot start.

**Root cause:** The `eso-ldap-directory` Vault policy (created by `ldap.sh` via
`_vault_configure_secret_reader_role`) only grants read access to `ldap/*` paths.
`LDAP_VAULT_POLICY_PREFIX` defaults to `"ldap"` in `scripts/etc/ldap/vars.sh`.
The Keycloak ExternalSecrets use the same `vault-kv-store` SecretStore (which authenticates
via the `eso-ldap-directory` Kubernetes role), but Vault rejects reads to `keycloak/*`
because the policy has no rule for those paths.

---

## Reproduction

```bash
# Confirm policy is missing keycloak paths:
curl -sf -H "X-Vault-Token: $(kubectl get secret vault-root -n secrets \
  --context k3d-k3d-cluster -o jsonpath='{.data.root_token}' | base64 -d)" \
  "http://localhost:18200/v1/sys/policies/acl/eso-ldap-directory" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['data']['policy'])"
# Actual: only ldap/* paths — no keycloak/* paths

kubectl get externalsecret keycloak-secrets -n identity --context k3d-k3d-cluster \
  -o jsonpath='{.status.conditions[0].message}'
# Actual: "could not get secret data from provider"
```

---

## Fix

### Part A — Live cluster: extend Vault policy

Obtain the Vault root token:
```bash
_vault_token=$(kubectl get secret vault-root -n secrets \
  --context k3d-k3d-cluster -o jsonpath='{.data.root_token}' | base64 -d)
```

Apply the updated policy via Vault API (Vault is reachable at `localhost:18200`
via the existing port-forward):

```bash
_new_policy='path "secret/data/ldap"           { capabilities = ["read"] }
path "secret/data/ldap/*"          { capabilities = ["read"] }
path "secret/metadata/ldap"        { capabilities = ["read", "list"] }
path "secret/metadata/ldap/*"      { capabilities = ["read", "list"] }
path "secret/data/keycloak"        { capabilities = ["read"] }
path "secret/data/keycloak/*"      { capabilities = ["read"] }
path "secret/metadata/keycloak"    { capabilities = ["read", "list"] }
path "secret/metadata/keycloak/*"  { capabilities = ["read", "list"] }'

curl -sf -X PUT \
  -H "X-Vault-Token: ${_vault_token}" \
  -H "Content-Type: application/json" \
  "http://localhost:18200/v1/sys/policies/acl/eso-ldap-directory" \
  -d "{\"policy\": $(echo "$_new_policy" | python3 -c 'import sys,json; print(json.dumps(sys.stdin.read()))')}"
```

Verify:
```bash
curl -sf -H "X-Vault-Token: ${_vault_token}" \
  "http://localhost:18200/v1/sys/policies/acl/eso-ldap-directory" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['data']['policy'])"
# Expected: policy includes keycloak/* paths
```

Force ESO to re-sync:
```bash
kubectl annotate externalsecret keycloak-secrets -n identity --context k3d-k3d-cluster \
  force-sync="$(date +%s)" --overwrite
kubectl annotate externalsecret keycloak-client-secrets -n identity --context k3d-k3d-cluster \
  force-sync="$(date +%s)" --overwrite
```

Confirm secrets sync:
```bash
kubectl get externalsecret -n identity --context k3d-k3d-cluster
# Expected: keycloak-secrets and keycloak-client-secrets both show SecretSynced / True
kubectl get pods -n identity --context k3d-k3d-cluster
# Expected: postgres-keycloak and keycloak pods reach Running
```

---

### Part B — Code fix: `scripts/etc/ldap/vars.sh` line 79

**Exact old line:**
```bash
export LDAP_VAULT_POLICY_PREFIX="${LDAP_VAULT_POLICY_PREFIX:-ldap}"
```

**Exact new line:**
```bash
export LDAP_VAULT_POLICY_PREFIX="${LDAP_VAULT_POLICY_PREFIX:-ldap,keycloak}"
```

This ensures that on the next `make up` (or any call to `ldap_provision`),
`_vault_configure_secret_reader_role` generates a policy covering both `ldap/*`
and `keycloak/*` paths so the cluster state matches the code.

## Recurrence 2026-09-26 — `vectordb/postgres` (v1.39.0 WS1)

Third occurrence of this class. `LDAP_VAULT_POLICY_PREFIX` had grown to
`ldap,keycloak,observability,platform-ops`; the WS1 vector-store ExternalSecret reads
`vectordb/postgres`, which was not on it, so `vectordb-postgres` sat `SecretSyncedError` and
`pod/vectordb-0` stayed `CreateContainerConfigError`.

Fixed by adding `vectordb` to the list in `scripts/etc/ldap/vars.sh:79`.

### The misleading part, again

The ExternalSecret condition message is `could not get secret data from provider` — exactly as
recorded above for keycloak. That message is identical whether the Vault path is **absent** or
the policy **denies** it, and the condition is the only thing `kubectl get externalsecret`
shows. It led to a wrong diagnosis here: the state was read as "the Vault path does not exist
yet", and writing the secret was reported as the single remaining blocker. It was not — the ESO
controller log had been printing `Code: 403 ... permission denied` on
`GET /v1/secret/data/vectordb/postgres` all along, before any write.

**Read the ESO controller log, not the ExternalSecret condition**, when a secret will not sync:

```
kubectl --context k3d-k3d-cluster -n secrets logs deploy/external-secrets --tail=300 \
  | grep '<name>'
```

A `403 permission denied` means this bug — the policy prefix. A `404` means the path genuinely
does not exist. The condition message cannot distinguish them.

### Why a new prefix keeps getting missed

The grant lives in `scripts/etc/ldap/vars.sh`, far from the ExternalSecret manifest that depends
on it, and nothing connects the two. Any new Vault prefix silently fails until someone reads the
controller log.

A gate now ties them together for `vectordb` (`scripts/tests/plugins/argocd_vectordb.bats`,
"the ESO Vault policy grants the prefix the vectordb ExternalSecret reads"), mutation-checked.
That is per-component, so it does not prevent the next recurrence for a different component. The
general fix would be a gate that enumerates every `remoteRef.key` prefix across all
`scripts/etc/argocd/**` ExternalSecret manifests and asserts each is covered by
`LDAP_VAULT_POLICY_PREFIX` or `VAULT_ESO_APPS_PREFIXES`. Not written yet — it needs a decision
about app-cluster manifests, whose ExternalSecrets authenticate through different roles.

### Applying it live

The policy is written by `_vault_configure_secret_reader_role`, called from `deploy_ldap`
(`scripts/plugins/ldap.sh:1136`). Editing `vars.sh` alone changes nothing on a running hub —
the policy in Vault keeps the old path list until that code path runs again. This is the same
inertness as the ApplicationSet values-branch pin: committed, CI green, no effect.
