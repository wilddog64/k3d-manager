## Correction (2026-07-10) — the original premise was wrong

This bug originally opened with *"The current machine does not have a local `ubuntu-k3s` kube context"* and framed the problem as **post-migration drift** — dead references left behind by the Hostinger migration. Both halves were wrong.

**The context did exist**, bound to `https://52.37.60.119:6443` and not answering. And it was not migration drift.

`ubuntu-k3s` is the **ACG AWS sandbox context**. An ACG sandbox lives **4 hours, extendable once to 8 hours** — it cannot stay up. Each provider merges its context into `~/.kube/config` on `up` (`k3s-gcp.sh:138-152 _gcp_merge_kubeconfig`) and deletes it on teardown (`k3s-gcp.sh:143`, `k3s-az.sh:143`, `k3s-hostinger.sh:101`, `acg.sh:687`). A stale context is what you get when the sandbox **expires on its own clock** instead of going through `cluster-down`, so teardown never runs.

That reframes the fix:

- The context being absent is the **normal steady state**, not a bug. It is present for at most 8 hours of any day.
- Hardcoding `ubuntu-k3s` is still wrong, but the failure mode is a **hang against a dead endpoint**, not a clean "context not found".
- The durable fix is a **reachability preflight** plus provider-keyed context resolution — not a find-replace, and not a one-time cleanup.

**Cleanup performed 2026-07-10.** Backed up `~/.kube/config`, then removed the expired-sandbox contexts (`ubuntu-k3s`, `ubuntu-azure`, `ubuntu-gcp`), the orphaned `k3s-gcp` context, and the orphaned `default` / `k3d-automation` clusters and users. Survivors: `k3d-k3d-cluster` and `ubuntu-hostinger`, both reachable. Selecting a deleted context now fails in ~0.03s with `context was not found` instead of hanging. All three sandbox contexts are regenerated by the next `cluster-up`, so this is safe and repeatable — but it will recur every time a sandbox expires untorn-down.
