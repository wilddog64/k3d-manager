## Symptom and live evidence

Follow-up live check on 2026-10-21: in the thread containing `cluster-status` job `76933b92`, the operator sent `logs 76933b92` and received an “unknown or records expired” error, then sent `status 76933b92` and observed no bot reply. The queued `cluster-status` message and status report were visible in the same thread. This proves the explicit-target experience is not yet live-verified; it does not prove whether the first ID was mistyped. The missing reply to the second command is the actionable regression.

Source review found that the explicit-target path switches notification delivery from the parent thread anchor to the target job directory. The parent context has the Slack channel ID, while status workers persist the target job's thread timestamp but do not persist its channel ID. `_notify_job()` requires channel/thread context to post a bot-thread reply. Follow-up spec: `docs/issues/2026-10-21-slack-explicit-target-reply-context-spec.md`.

## Root cause — source-confirmed ambiguity

On `k3d-manager-v1.43.5`, `bin/k3dm-webhook`:

1. `/slack/events` resolves any reply's parent `thread_ts` with `_find_job_by_thread_ts()` (around line 2223), before dispatching the text.
2. `_find_job_by_thread_ts()` (around lines 634–654) scans `JOB_DIR/*/thread_ts`, skips `ask` and `ask-docs` subjobs, sorts candidate directories by modification time, and prefers the most recently modified non-anchor entry. Several unrelated jobs can therefore compete for the same parent thread. Directory mtime is not an immutable measure of command intent, job creation or completion.
3. `_handle_thread_command`'s `cluster-status` branch (around lines 920–935) spawns a new independent job and deliberately passes through the parent `thread_ts`. Notification delivery via `_notify_job` preserves that shared thread.
4. Bare `logs` calls `_resolve_thread_log_job()`, which **again** chooses `_find_job_by_thread_ts(thread_ts)` (around lines 659–681). Meanwhile `status`, `diagnosis`, and `kill` act upon the initial implicitly selected `job_id`; they do not offer the same explicit target contract. The first selection and the subsequent logs selection can differ if job metadata changes between them.

Consequences: an implicit diagnostic can read the wrong job's status/output, report absent output for a different job, or, more seriously, direct `kill` at a different running job within the same thread. This is a **code-path risk**, not a claim of observed wrong-job termination.

## Expected behavior

Allow conversational Slack threads to contain many operations while making the job target of every job-scoped command unambiguous and auditable. Preserve the existing correct explicit `logs <job-id>` behavior, thread/channel authorization, stable output redaction, command-role gates, and normal threaded `cluster-status` delivery. Never silently substitute a different job for an explicitly selected ID.

## Fix / investigation requirements

1. Define documented target-selection semantics for job-scoped thread commands (`logs`, `status`, `diagnosis`, `kill`). Prefer explicit `<job-id>` for mutations such as `kill`; reject ambiguous implicit targets or ask for an ID rather than guessing. If shorthand remains, define a deterministic last-command-in-thread contract with durable mapping keyed by channel, parent thread, user/command, and job ID as appropriate.
2. Stop using mutable directory modification time as the sole authoritative correlation signal. Persist explicit command-to-job references and immutable creation/request identifiers; ensure results and acknowledgments name their own job ID.
3. Resolve target ID once per command under safe concurrency semantics; prevent divergence between event routing and later `logs` resolution. Keep authorization scoped to the original channel/thread and required role. Do not permit arbitrary cross-thread job access.
4. Diagnose `No log found for job 3ec129d0` by distinguishing no output yet, no persisted output, expired log, invalid ID, and wrong mapping; do not mark missing logs as proven from Slack alone.
5. Examine bare `check` and `echo` as separate inputs. Establish whether they are recognized commands, ignored messages, or merely adjacent to an asynchronous status report; avoid assuming causal delivery from temporal proximity.
6. Avoid duplicating or reopening the live-verified explicit-ID bug (2026-10-13); update any shared selector carefully and preserve its tests.

## Acceptance criteria

- [ ] Two or more overlapping `fix-list`, `cluster-status`, and lifecycle jobs can share a parent thread without misbinding a job-scoped query or control action.
- [ ] Every job-scoped reply identifies the exact target job ID and distinguishes pending/no output from missing/unavailable logs.
- [ ] Explicit `logs <job-id>` keeps its live-verified exact-ID behavior; no substitution of a different ID.
- [ ] Ambiguous bare `logs`, `status`, `diagnosis`, or `kill` is deterministic and documented, or safely rejected with usage guidance.
- [ ] `kill` cannot terminate the wrong job due to thread collisions, directory mtime changes, or races.
- [ ] Concurrent event replay, changed directory mtimes, multiple matching job dirs, expired anchor, unknown thread, mismatched channel, unauthorized role, and two users in one thread are covered with isolated tests.
- [ ] `cluster-status` thread replies continue in their requested parent thread; independent top-level requests retain their own thread.
- [ ] Tests make no real Slack, host, cluster, AWS, or lifecycle mutations; perform live verification only with operator approval.
