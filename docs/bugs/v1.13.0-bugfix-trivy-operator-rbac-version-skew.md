# Bugfix: v1.13.0 — trivy-operator CrashLoopBackOff from chart/image RBAC skew

**Branch:** `k3d-manager-v1.13.0`
**Files:** `scripts/etc/argocd/applicationsets/observability.yaml`, `scripts/etc/argocd/applicationsets/observability-acg.yaml`

---

## Problem

`trivy-operator` (infra cluster `k3d-k3d-cluster`) and `acg-trivy-operator` (app cluster
`ubuntu-hostinger`) are stuck in `CrashLoopBackOff` — 197 restarts in ~22h. The operator
aborts on startup with:

```
unable to run trivy operator: starting controllers manager: failed to wait for
configmap caches to sync kind source: *v1.ConfigMap: timed out waiting for cache to be synced
```

**Root cause:** chart/image version skew. The ApplicationSets pin the Aqua `trivy-operator`
Helm chart to `0.24.1` (whose RBAC ClusterRole matches app ~0.22.0), but
`trivy-operator-values.yaml` overrides the *image* to `0.31.2`. The 0.31.2 operator starts
`PersistentVolume` and `PersistentVolumeClaim` informers, which chart 0.24.1's ClusterRole
does not grant. The PV/PVC informers fail with `persistentvolumeclaims is forbidden` /
`persistentvolumes is forbidden`; when one `WaitForCacheSync` fails, controller-runtime tears
down the whole manager and reports "cache did not sync" timeouts for every other informer
(ConfigMap, ClusterRbacAssessmentReport, …). **The ConfigMap timeout is the cascade symptom,
not the cause.**

> This supersedes `docs/issues/2026-07-04-trivy-operator-crashloop-cache-sync-timeout.md`,
> which attributed the crash to CPU throttling at `cpu: 100m`. That diagnosis is wrong: the
> live operator container runs with `resources: {}` (no CPU limit), the node is idle (CPU
> 0–2%), and only 107 ConfigMaps exist cluster-wide. The head of the log (not the shutdown
> tail) shows the real trigger is missing PV/PVC RBAC.

---

## Reproduction

```
kubectl -n trivy-system logs -l app.kubernetes.io/name=trivy-operator --tail=-1 \
  | grep -iE "is forbidden"
# persistentvolumeclaims is forbidden
# persistentvolumes is forbidden

kubectl auth can-i list persistentvolumeclaims \
  --as=system:serviceaccount:trivy-system:trivy-operator     # -> no
```

Expected: operator reaches `1/1 Running`. Actual: `CrashLoopBackOff`.

---

## Fix

Align the chart pin with the 0.31.2 image. Chart `0.33.2` ships `appVersion: 0.31.2` and its
ClusterRole includes `persistentvolumes` + `persistentvolumeclaims` (verified via
`helm template … --version 0.33.2` against the existing values file — renders clean, no
values-schema errors). Keep the existing image/registry override in
`trivy-operator-values.yaml` (the `mirror.gcr.io` mirror is intentional).

### Change 1 — `scripts/etc/argocd/applicationsets/observability.yaml`: bump trivy chart pin

**Exact old block:**

```yaml
            chart: trivy-operator
            repoURL: https://aquasecurity.github.io/helm-charts
            targetRevision: 0.24.1
```

**Exact new block:**

```yaml
            chart: trivy-operator
            repoURL: https://aquasecurity.github.io/helm-charts
            targetRevision: 0.33.2
```

### Change 2 — `scripts/etc/argocd/applicationsets/observability-acg.yaml`: bump trivy chart pin

**Exact old block:**

```yaml
            chart: trivy-operator
            repoURL: https://aquasecurity.github.io/helm-charts
            targetRevision: 0.24.1
```

**Exact new block:**

```yaml
            chart: trivy-operator
            repoURL: https://aquasecurity.github.io/helm-charts
            targetRevision: 0.33.2
```

## Interim live remediation (already applied on infra cluster)

Because both ApplicationSets have `selfHeal: true`, patching the chart-owned ClusterRole
directly would be reverted. A standalone additive ClusterRole + ClusterRoleBinding
(`trivy-operator-pv-pvc-fix`) granting `get,list,watch` on `persistentvolumes` +
`persistentvolumeclaims` to the `trivy-operator` SA was applied to unblock the infra cluster
now. Operator recovered to `1/1 Running`.

- The **app cluster** (`ubuntu-hostinger`, SA `acg-trivy-operator`) still needs the same
  interim ClusterRole/binding until the chart bump is synced.
- After chart `0.33.2` syncs (its own ClusterRole covers PV/PVC), delete the interim
  `trivy-operator-pv-pvc-fix` ClusterRole + ClusterRoleBinding on both clusters.
