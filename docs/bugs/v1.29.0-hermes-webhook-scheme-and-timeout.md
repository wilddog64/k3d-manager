# Bug — Hermes webhook sensors blinded by `https://` scheme + 10s timeout

**Filed:** 2026-09-05
**Branch:** `k3d-manager-v1.29.0`
**Severity:** high (two of five sensors permanently `unknown` in production)
**Found:** during live activation of the Hermes Phase-1 agent (WS0 posture verification).

## Symptom

With all four read-only credentials provisioned and the webhook healthy on
`127.0.0.1:7443`, the two webhook-derived Hermes sensors (`eso`, `node_pressure`)
would never report real status — they would always fall through to `unknown`
("status source unavailable"). Because `unknown` sensors never count toward an
incident by design, Hermes would silently observe **nothing** from the webhook: no
false alarms, but no coverage of ESO sync health or node/data-layer pressure either.

## Root cause

Two independent defects, both on the webhook fetch path:

1. **Wrong scheme.** `bin/k3dm-hermes` (`webhook_fetch`) and
   `scripts/lib/hermes/sensors.py` (`_webhook_services`) build **`https://`** URLs
   for the webhook. The webhook (`bin/k3dm-webhook`) is a plain-HTTP
   `http.server.ThreadingHTTPServer` bound to `127.0.0.1:7443` — TLS is terminated at
   the Cloudflare edge, and the loopback listener is HTTP by design (see
   `docs/architecture/cloudflare-slack-relay.md`, `docs/architecture/webhook-server.md`,
   and every other caller: `v1.6.0`/`v1.6.2`/`v1.8.0`/`v1.28.0` specs use `http://`).
   A `https://` request against it fails the TLS handshake (`WRONG_VERSION_NUMBER`),
   the fetch raises, and the sensor returns `unknown`.

   The WS1/WS2 spec (`docs/plans/v1.29.0-hermes-ws1-ws2-sensors-correlator.md:29`)
   wrongly specified `https://<webhook-host>:7443` — the implementation faithfully
   followed a wrong spec.

2. **Timeout too short.** `_http_json` in `bin/k3dm-hermes` hard-codes `timeout=10`.
   The **authenticated** `GET /api/v1/health` runs the full cluster smoke test
   (`_smoke_test_services`) and legitimately takes ~46s on a degraded cluster (measured
   2026-09-05: 46.5s, with Keycloak/Grafana 502 and ESO 1/20 not synced). Even with the
   scheme fixed, the webhook fetch would time out at 10s and the sensor would return
   `unknown`. (The unauthenticated 401 path returns instantly, which masked this in
   ad-hoc probing.)

## Fix

- `bin/k3dm-hermes` `webhook_fetch`: `https://{webhook_host}` → `http://{webhook_host}`.
  **Leave `github_fetch` on `https://api.github.com`** — the GitHub API is genuinely TLS.
- `scripts/lib/hermes/sensors.py` `_webhook_services`: `https://{provider}` → `http://{provider}`
  (latent path — the agent calls the webhook sensors without `provider`, but keep it
  consistent so a future caller that passes `provider` is not re-bitten).
- `bin/k3dm-hermes` `_http_json`: make the timeout env-overridable via
  `K3DM_HERMES_HTTP_TIMEOUT`, default **90s** (comfortably above the observed ~46s
  degraded-cluster latency; the agent must tolerate a slow health check precisely when
  the cluster is degraded — that is when it most needs the signal).

## Verification (DoD)

- [x] `bin/k3dm-hermes` run once against the live webhook: `eso` and `node_pressure`
      records show real status derived from the payload — not `unknown` (2026-09-05:
      eso → "1/20 not synced: cosign-public-key", node_pressure → "webhook failures:
      Keycloak, Grafana, ESO ExternalSecrets"; both fetches ~40s, well within the 90s timeout).
- [x] `grep -n "https://" bin/k3dm-hermes` shows only the `api.github.com` line.
- [x] `scripts/lib/hermes/sensors.py` webhook URL is `http://`.
- [x] pytest suite green (`scripts/tests/hermes/` — 8 passed).
- [x] `docs/guides/hermes.md` config table documents `K3DM_HERMES_HTTP_TIMEOUT`.

## What NOT to do

- Do NOT make the webhook serve TLS on loopback — the established contract is
  plain HTTP on `127.0.0.1`, TLS-terminated at the Cloudflare edge. Changing it would
  break every existing webhook client.
- Do NOT change `github_fetch` off `https://`.
- Do NOT lower the timeout below the observed authenticated-health latency.
