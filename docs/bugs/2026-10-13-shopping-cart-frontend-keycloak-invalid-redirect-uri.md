## Symptom

When attempting shopping-cart frontend login, the browser reaches `https://keycloak.3ai-talk.org` and displays:

> SHOPPING-CART — We are sorry... Invalid redirect uri

The authorization request is rejected **before** the credential prompt or callback. This indicates an OIDC client redirect-URI validation failure, not necessarily a frontend rendering failure or Keycloak outage.

## Expected / actual

- Expected: Selecting Sign In on `https://frontend.3ai-talk.org` starts OIDC authorization and successfully returns to the frontend's registered callback.
- Actual: Keycloak returns `Invalid redirect uri`, preventing login.

## Likely causes (hypotheses — not yet verified)

1. The frontend's actual OIDC authorization request contains a `redirect_uri` not accepted by the effective Keycloak client configuration (wrong host, scheme, port, path, or slash). The intended public callback in earlier repository records is `https://frontend.3ai-talk.org/callback`.
2. The Keycloak `frontend` client was recreated or reconciled from stale realm configuration following hub recovery, changing `Valid redirect URIs` or `Web origins`.
3. A changed frontend origin, reverse-proxy routing, or frontend build configuration generated a different callback URL than expected.

Do **not** add permissive wildcard redirect URIs or disable redirect validation to work around the error.

## Reproduce / collect evidence

1. Open `https://frontend.3ai-talk.org` in a private browser window and select Sign In.
2. In browser DevTools Network, capture the Keycloak `/realms/shopping-cart/protocol/openid-connect/auth` request; record **only** `client_id`, `redirect_uri`, and the relevant public origin (do not publish `state`, `nonce`, codes, cookies, or tokens).
3. Through an authenticated, read-only Keycloak admin query, find the client by that `client_id` in realm `shopping-cart`. Compare its effective `redirectUris`, `rootUrl`, `baseUrl`, and `webOrigins` with the requested URI. Confirm realm/client existence first.
4. Inspect the deployed frontend image/configuration (`VITE_KEYCLOAK_URL`, OIDC client ID, callback routing) and the desired realm/client manifest in the shopping-cart infrastructure repo. Compare with **live** client settings to detect drift.
5. Determine whether a recent hub restore, Keycloak reconciliation, frontend rebuild, or Cloudflare/public origin change preceded this failure.

## Fix / regression prevention

- Reconcile the `frontend` client **declaratively and idempotently** with the exact legitimate callback URI(s) generated by the deployed frontend; preserve valid existing settings and enforce HTTPS on public origins.
- Fix incorrect frontend callback/origin configuration if that is what generates the unexpected URI.
- Add a negative and positive OIDC redirect contract test (expected public callback accepted; unapproved origin rejected).
- Add a real browser login smoke/E2E test for public frontend -> Keycloak -> frontend callback, and verify it after reconciliation and hub recovery. A Keycloak HTTP health check alone is insufficient.

## Investigation 2026-10-15 (Claude, read-only, operator-approved)

No credentials were used and nothing was changed. Every request was an anonymous public GET.

**What the frontend sends.** The deployed bundle (`/assets/index-DiHAdjCP.js`) configures
oidc-client-ts with:

- authority `https://keycloak.3ai-talk.org/realms/shopping-cart`, `client_id` `frontend`;
- `redirect_uri` = `${window.location.origin}/callback`;
- `post_logout_redirect_uri` = `window.location.origin`, i.e. `https://frontend.3ai-talk.org`, with
  no path.

**Login is fine.** These are the results of the authorize endpoint:

| Request | Result |
|---|---|
| `redirect_uri=https://frontend.3ai-talk.org/callback` with PKCE S256 | 200, "Sign in to shopping-cart" form |
| the same without PKCE | 302 back to `/callback?error=invalid_request` (PKCE required; the real client sends it) |
| `https://evil.example/callback`, `https://www.3ai-talk.org/callback`, `https://shop.3ai-talk.org/callback`, `http://frontend.3ai-talk.org/callback` | 400 "Invalid parameter: redirect_uri" (correctly rejected) |

**Logout fails, and it shows the exact text in the report.** These are the results of the logout
endpoint:

| `post_logout_redirect_uri` | Result |
|---|---|
| `https://frontend.3ai-talk.org` (what the frontend sends) | **400 "Invalid redirect uri"** |
| `https://frontend.3ai-talk.org/callback` | 302 (accepted) |

Keycloak words an invalid login redirect as "Invalid parameter: redirect_uri". It uses "Invalid
redirect uri" for an invalid **post-logout** redirect. So the screenshot came from signing out (or
from a login started right after a failed sign-out), not from a rejected login.

**Cause.** In `shopping-cart-infra/identity/keycloak/realm-shopping-cart.json`, the `frontend` client
has `redirectUris` containing only the exact `https://frontend.3ai-talk.org/callback` for the public
host. It has no `post.logout.redirect.uris` attribute. Keycloak's default for post-logout URIs is
the client's redirect URIs, so the bare origin the frontend sends is not allowed. The live realm
matches git: the file last changed on 2026-09-12 (#96), the `/callback` URI was added 2026-06-01
(#82), and the hub Keycloak pod has run since 2026-10-03. Nothing drifted. The logout path has most
likely never worked on the public host. Hub recovery is not the cause (hypothesis 2 above is ruled
out).

**Fix options for the plan, not started.** Either of these is exact, with no wildcard:

1. Realm: add `"post.logout.redirect.uris": "https://frontend.3ai-talk.org"` to the `frontend` client's
   `attributes` in `shopping-cart-infra`. Before choosing this, find out how the realm reaches the
   live Keycloak. If the realm is imported once at startup with `IGNORE_EXISTING`, a JSON change will
   not update the live client, and an idempotent `kcadm` update is needed too.
2. Frontend: send `post_logout_redirect_uri = ${origin}/callback`, which is already allowed, and treat
   a `/callback` that has no `code` as "signed out". This is a code change in `shopping-cart-frontend`.

Option 1 matches the intended behaviour (return to the home page) and needs no frontend release.
Regression test: a public logout request with the frontend's own `post_logout_redirect_uri` must not
return 400, and an unlisted origin must still be rejected.

**Priority.** Login works. Logout does not end the Keycloak session, because the request is rejected
before the session is cleared, so a user cannot sign out except by clearing cookies. That may be P2
rather than P1. Operator set P2 on 2026-10-15.

**Possibly related:** `2026-10-13-shopping-cart-cart-lost-after-logout-login.md`. That report
involves the same logout step, which errors here. Check it after this fix.

**How the fix reaches the live Keycloak (checked 2026-10-15).** `identity/keycloak/keycloak-reconcile-hook-job.yaml`
in `shopping-cart-infra` is an Argo CD **PostSync** hook. It runs `kcadm.sh create partialImport -s ifResourceExists=OVERWRITE`
with the realm JSON. So once option 1 is merged, the next sync rewrites the live `frontend` client, and
no manual `kcadm` step is needed. One catch: the hook only warns when `partialImport` exits non-zero,
so a failed import would still look like a green sync. Prove the fix with the public logout probe,
not with sync status.

```markdown

```
