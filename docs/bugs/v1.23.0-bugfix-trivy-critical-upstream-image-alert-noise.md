# Bugfix: v1.23.0 — TrivyCritical alert noise from non-remediable upstream images

**Branch:** `k3d-manager-v1.23.0`
**Files:** `scripts/etc/argocd/platform-ops/prometheusrule.yaml`, `scripts/etc/argocd/platform-ops/alertmanager-config.yaml`, `bin/k3dm-webhook`

---

## Problem

`TrivyCriticalVulnerabilityDetected` keeps paging Slack. Live query (2026-08-09 hub):
**39 alerts firing, only 1 is ours** (`wilddog64/shopping-cart-payment`). The other **38 are
third-party upstream images** (`hashicorp/vault`, `grafana/grafana`, `istio/pilot`,
`library/postgres`, `keycloak/keycloak`, `prometheus/*`, `argoproj/argocd`, …) that the
`app-cve-scan` auto-patch loop **cannot rebuild** — it only rebuilds `wilddog64/*` images.

Every firing alert carries `remediation: cve-auto-patch` and routes to **both** the
`k3dm-cve-remediate` and `k3dm-analyze` webhooks, so all 38 non-actionable alerts trigger a
(failing) analysis call, flooding Slack.

**Root causes:**
1. The alert rule does not distinguish images we can remediate (`wilddog64/*`) from
   upstream/third-party images we cannot — all get `remediation: cve-auto-patch`.
2. Third-party alerts have no dedicated route, so they fall through to the parent
   `k3dm-analyze` receiver.
3. `bin/k3dm-webhook:_run_analyze` renders the Slack title from `labels["name"]`, which Trivy
   alerts do not have → title arrives as `TrivyCriticalVulnerabilityDetected — ``` (empty).

**NOT the fix:** excluding namespaces. All 39 alerts (including payment) report
`namespace: platform-ops` — the exporter attributes everything there — so a namespace
exclusion would suppress the one legitimate remediable alert. The correct discriminator is the
**`image_repository` prefix**.

---

## Reproduction

```
kubectl exec -n monitoring sts/prometheus-kube-prometheus-stack-prometheus -c prometheus -- \
  wget -qO- localhost:9090/api/v1/alerts
# → 39 firing TrivyCriticalVulnerabilityDetected, 38 third-party, all ns=platform-ops
```

---

## Fix

### Change 1 — `prometheusrule.yaml`: split the alert by image ownership

Replace the single `TrivyCriticalVulnerabilityDetected` rule with two rules sharing the same
`alertname` (so Alertmanager matchers and the existing inhibit rule still apply), differing
only in the `image_repository` selector and `remediation`/`tier`/`severity` labels:

- **ours** (`image_repository=~"wilddog64/.*"`): keeps `severity: critical`,
  `remediation: cve-auto-patch`, `app: "{{ $labels.image_repository }}"`.
- **upstream** (`image_repository!="", image_repository!~"wilddog64/.*"`): `severity: warning`,
  `remediation: none`, `tier: upstream`, `app: "{{ $labels.image_repository }}"`, and an
  annotation noting it is not auto-remediable and lives on the CVE inventory dashboard.

### Change 2 — `alertmanager-config.yaml`: route upstream alerts to a blackhole

Add a sub-route **before** the parent fall-through that matches
`alertname=TrivyCriticalVulnerabilityDetected, tier=upstream` and sends to a new
`k3dm-quiet` receiver (no `webhookConfigs` → dropped). `groupWait`/`repeatInterval` widened.
Add the `k3dm-quiet` receiver (name only). Ours-alerts (`remediation=cve-auto-patch`) still
match the existing remediate + analyze sub-routes; ArgoCD/scan-job alerts still fall to the
parent `k3dm-analyze` receiver.

### Change 3 — `bin/k3dm-webhook` `_run_analyze`: title label fallback

`labels.get("name")` → keep the ArgoCD app name for `kubectl describe application`, but derive
a display name `argocd_app or labels.get("app") or labels.get("image_repository") or "unknown"`
for the log line, prompt, and Slack title.
