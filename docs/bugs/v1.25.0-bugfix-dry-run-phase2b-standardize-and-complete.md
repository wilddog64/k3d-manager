## Problem (two defects, one root cause)

There are **two** dry-run mechanisms that do not talk to each other:

- **`DRY_RUN`** → `_dry_run_active()` (active `scripts/lib/system.sh:1717` → `[[ "${DRY_RUN:-0}" == "1" ]]`).
  This is what Phase 2's new guards check.
- **`K3DM_DEPLOY_DRY_RUN`** → the `_run_command` override in `scripts/lib/system_overrides.sh:30`, plus direct
  checks in `scripts/plugins/vault.sh` (×3), `scripts/plugins/jenkins.sh`, and the dispatcher’s `--dry-run`
  flag (`scripts/k3d-manager:530`). This is the *pre-existing* dry-run.

Because the two are unbridged **and** `system_overrides.sh` is sourced only by the dispatcher
(`scripts/k3d-manager:75`) — never by `bin/cluster-up` / `bin/cluster-down` — a `DRY_RUN=1 make up`:

1. Fires the new `_dry_run_active` guards (good), but
2. Leaves every `_run_command` call in the raw lib-foundation state (no dry-run awareness on the bin path at
   all), and
3. Never reaches most of `bin/cluster-up` anyway because its guards stop at line 364 — the entire macOS access
   layer (browser listeners, loopback alias, named tunnel: 17 `_run_command --interactive-sudo/--prefer-sudo`
   ops) and the inline `kubectl apply`/`kubectl patch`/`launchctl` provisioning are ungated.

**Net effect:** `DRY_RUN=1 make up` can run `sudo security add-trusted-cert` (system keychain),
`sudo launchctl bootstrap system`, `sudo ifconfig lo0 alias`, and `kubectl apply` against a live hub — i.e. it
mutates while claiming to preview.

**Decision (owner, 2026-08-14):** standardize everything on **`DRY_RUN`** as the single canonical variable;
`K3DM_DEPLOY_DRY_RUN` becomes a still-honored deprecated alias. For `make up`, a true dry-run cannot configure
a cluster it never created, so after the provisioning core it prints a plan summary and **exits 0**
(guard-core + plan-and-exit). `make down` gets full per-op guards.

> `{ … }` block: keep the existing preview logic verbatim, and replace the closing `;;` + `esac` of the old
> `case` with a closing `}`. Net: same preview output, but gated on `_dry_run_active` (both vars) instead of

## Part B — `bin/cluster-up`: guard-core + plan-and-exit

Codex already guards the provisioning core (deploy_cluster/tunnel/hub/deploy_vault/ldap/argocd/bootstrap,
lines ≤333). A true dry-run has no cluster, so the inline configuration that follows (Vault port-forward,
istio gateways, Keycloak realm, browser listeners, port-forwards, named tunnel) must not run. Insert a
plan-and-exit **immediately before** the Step 4 Vault port-forward section.

**Exact anchor (line 338, unchanged):**
```bash
_info "[acg-up] Step 4/12 — Starting Vault port-forward (k3d → localhost:${_vault_local_port})..."
```

**Insert immediately BEFORE that line:**
```bash
if _dry_run_active; then
  _info "[acg-up] DRY_RUN: provisioning plan complete — the cluster was not created, so the"
  _info "[acg-up] DRY_RUN: remaining configuration is skipped (would run against a live cluster):"
  _info "[acg-up]   • Vault port-forward + LaunchAgent"
  _info "[acg-up]   • Cloudflare tunnel credential sync + istio gateways + CoreDNS"
  _info "[acg-up]   • Keycloak realm import + browser HTTPS/HTTP listeners"
  _info "[acg-up]   • ArgoCD / Keycloak / frontend / Grafana / Pushgateway port-forwards"
  _info "[acg-up]   • loopback alias + named Cloudflare tunnel"
  _info "[acg-up] DRY_RUN: no changes were made."
  exit 0
fi
```

> This makes `DRY_RUN=1 make up` deterministic and side-effect-free regardless of whether a hub already
> exists. Part A’s `_run_command` bridge remains a belt-and-suspenders safety net for the ops after this
> point (never reached in dry mode, but safe if the exit is ever moved).

## Part C — `bin/cluster-down`: split the coarse launchd guard into per-op

Replace the single coarse guard (`if _dry_run_active; then _info "DRY_RUN: would unload local launchd agents
and remove their state"; else <whole _is_mac block> fi`, ~lines 162–278) so each teardown prints its own
accurate plan line and still touches nothing. Two rules:

- **`_run_command`-routed ops** (keycloak-browser / argocd-browser / cf-tunnel / frontend-browser bootout+rm)
  need **no** explicit guard once Part A lands — `_run_command` now prints `[dry-run] …` and skips. Remove the
  coarse wrapper around them.
- **Direct (non-`_run_command`) ops** inside that block — the user-level `launchctl unload` + `rm -f` for
  Pushgateway, Alertmanager, AM-auth-proxy, and Keycloak port-forwards, and `rm -f "${_cf_tunnel_plist}"` —
  get per-op guards in the established pattern already used for the Vault PF earlier in the file:

```bash
if launchctl list "${_pgw_pf_label}" >/dev/null 2>&1; then
  if _dry_run_active; then
    _info "DRY_RUN: would unload Pushgateway port-forward LaunchAgent"
  else
    launchctl unload "${_pgw_pf_plist}" 2>/dev/null || true
  fi
fi
_dry_guard "remove Pushgateway port-forward plist" rm -f "${_pgw_pf_plist}"
```

Apply the same shape to Alertmanager, AM-auth-proxy, Keycloak PF (`rm -f "${_kc_pf_plist}" "${_kc_pf_wrapper}"`),
and the cf-tunnel plist rm. Keep every `launchctl list` probe unguarded (read-only). Net: the vague one-liner
becomes an itemized, accurate plan; real mode is byte-for-byte unchanged.
