# Bugfix: v1.23.0 — Grafana rotator `rollout status` blocked by RBAC (missing deployments list/watch)

**Branch:** `k3d-manager-v1.23.0`
**Files:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`
**Status:** DONE — applied + live-verified end-to-end 2026-08-08 (rotation Job `Complete`; login 200 with the newly-rotated secret).
**Severity:** high — 4th and final latent blocker; with openssl fixed, the rotator got as far as `rollout status` and then spun on a forbidden-list error until the 5m timeout, so the DB-apply never ran.

---

## Problem

With the `runAsNonRoot` (`a66463e1`) and `openssl` (`4557cdeb`) blockers fixed, the rotator pod
finally reached line 122:

```bash
kubectl rollout status deployment/kube-prometheus-stack-grafana -n monitoring --timeout=5m
```

and looped on:

```
deployments.apps "kube-prometheus-stack-grafana" is forbidden:
User "system:serviceaccount:monitoring:grafana-credential-rotator" cannot list resource
"deployments" in API group "apps" in the namespace "monitoring"
```

`kubectl rollout status` uses a **ListWatch informer**, so it needs `list` + `watch` on
`deployments` at *collection* scope. The rotator Role granted `deployments` only `get`/`patch`, and
that rule is restricted with `resourceNames: ["kube-prometheus-stack-grafana"]`.

**Root cause + the RBAC subtlety:** Kubernetes RBAC **ignores `resourceNames` for the collection
verbs** (`list`, `watch`, `create`, `deletecollection`). You therefore cannot grant a name-scoped
`list`/`watch`; those verbs only work in a rule *without* `resourceNames`. Adding `list`/`watch` to
the existing name-scoped rule would still be denied. `rollout restart` (line 121) worked because it
uses `get`+`patch` (both name-scopeable), which is why the deployment actually rolled out while
`rollout status` was still failing.

---

## Fix — a separate, verbs-only list/watch rule (least privilege preserved)

**File:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`

Keep the existing name-scoped `get`/`patch` rule. Add a **second** `deployments` rule with only
`list`/`watch` (which are inherently collection-scoped and cannot carry `resourceNames`). All grants
stay **namespace-scoped to `monitoring`** (Role, not ClusterRole).

**Exact old block (after the deployments get/patch rule):**

```yaml
  - apiGroups: ["apps"]
    resources: ["deployments"]
    resourceNames: ["kube-prometheus-stack-grafana"]
    verbs: ["get", "patch"]
  - apiGroups: [""]
    resources: ["pods"]
```

**Exact new block:**

```yaml
  - apiGroups: ["apps"]
    resources: ["deployments"]
    resourceNames: ["kube-prometheus-stack-grafana"]
    verbs: ["get", "patch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["list", "watch"]
  - apiGroups: [""]
    resources: ["pods"]
```

Justification (least privilege): `list`/`watch` cannot be name-scoped in RBAC, so a verbs-only rule
is the minimal grant that lets `rollout status` observe the rollout. `get`/`patch` remain restricted
to the single `kube-prometheus-stack-grafana` deployment; the read-only `list`/`watch` widening is
confined to the `monitoring` namespace.
