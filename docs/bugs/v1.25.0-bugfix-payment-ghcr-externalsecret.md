# Bugfix: v1.25.0 — payment ghcr pull secret is imperative + on the wrong SA → pruned under GitOps

**Driving release:** v1.25.0 workstream G / Tier 2 e2e (`docs/plans/v1.25.0-e2e-harness-tier2-sandbox.md`)
**Work repo:** `shopping-cart-payment` (multi-repo — spec lives in k3d-manager, code change lands in the service repo)
**Branch (shopping-cart-payment):** `fix/payment-ghcr-eso-pull-secret`
**Files:** `k8s/base/externalsecret-ghcr.yaml` (new), `k8s/base/serviceaccount.yaml`, `k8s/base/kustomization.yaml`

---

## Problem

On the Tier 2 self-contained sandbox (in-sandbox ArgoCD + the four appsets), the full shopping-cart stack
came up **7/8 apps Healthy — only `payment` lagged**, unable to pull its image. This blocks the Stripe live
E2E (workstream G): no payment pod → no checkout.

**Root cause — two independent defects that only bite under GitOps `prune: true`:**

1. **The `ghcr-pull-secret` is created imperatively, not in git.** `shopping_cart_create_ghcr_pull_secret`
   (`k3d-manager/scripts/plugins/shopping_cart.sh:349–388`) runs `kubectl create secret docker-registry
   ghcr-pull-secret …` at bring-up Step 5/12. Because that Secret is **not** a git-tracked resource, the
   `services-git` ArgoCD Application (which runs with **`prune: true`**) treats it as extraneous in the
   namespace it manages and prunes it. The image pull then fails.

2. **The imperative bring-up patches the wrong ServiceAccount.** The same function patches only the
   **`default`** SA in each namespace (`shopping_cart.sh:383–387`), but the payment Deployment runs as
   **`serviceAccountName: payment-service`** (`shopping-cart-payment/k8s/base/deployment.yaml:38`), which has
   **no `imagePullSecrets`** (`serviceaccount.yaml`). So even before pruning, `payment-service` never
   referenced the pull secret — payment survived earlier only incidentally (cached image / a manual copy).

**Durable fix (this spec):** make the pull secret **git/ESO-owned and correctly referenced**, entirely inside
the `shopping-cart-payment` base — a dockerconfigjson **ExternalSecret** (ESO templates it from the Vault
ghcr PAT; `creationPolicy: Owner` + ArgoCD `IgnoreExtraneous` → not pruned), plus an `imagePullSecrets`
reference on the **`payment-service`** SA that actually runs the pod.

## Reproduction

On a Tier 2 sandbox (or any cluster where `services-git` syncs with `prune: true`):

```
kubectl -n shopping-cart-payment get externalsecret,secret | grep ghcr        # → nothing (pruned)
kubectl -n shopping-cart-payment get pods -l app.kubernetes.io/name=payment-service
# → ImagePullBackOff / ErrImagePull on ghcr.io/wilddog64/shopping-cart-payment
kubectl -n shopping-cart-payment get sa payment-service -o jsonpath='{.imagePullSecrets}'  # → empty
```

Expected after fix: `ghcr-pull-secret` present and ESO-owned; `payment-service` SA lists it; pod pulls.

## Preconditions (verify before implementing)

- **ESO store reach (A01/A02 — least privilege):** the `vault-backend` **ClusterSecretStore** must be able to
  read Vault path `secret/data/github/pat` (property `token`). This is the same PAT the imperative path reads
  (`shopping_cart_load_ghcr_pat_from_vault`, `shopping_cart.sh:262`). If the store's Vault policy does not
  already grant `read` on `secret/data/github/pat`, add exactly that one path (read-only) — do **not** widen
  to `secret/data/*`.
- Vault `secret/data/github/pat` holds only `token` (no `username`) — confirmed from the writer paths
  (`shopping_cart.sh:302/322`). The docker username is therefore supplied as a literal in the template. The
  GitHub owner `wilddog64` is **public** (repo owner) — this is not a secret and does not violate A02; the
  credential (the PAT) still comes only from Vault.

## Fix

### Change 1 — NEW `k8s/base/externalsecret-ghcr.yaml`

Mirrors the in-repo ESO pattern (`shopping-cart-product-catalog/k8s/base/externalsecret.yaml`): ESO
`external-secrets.io/v1`, `vault-backend` ClusterSecretStore, `creationPolicy: Owner`, `sync-wave: "-1"` so
the secret exists before the Deployment reconciles. The `template.type` makes it a
`kubernetes.io/dockerconfigjson` pull secret.

```yaml
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: ghcr-pull-secret
  namespace: shopping-cart-payment
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
  labels:
    app.kubernetes.io/instance: ghcr-pull-secret
    app.kubernetes.io/component: credentials
spec:
  refreshInterval: 24h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: ghcr-pull-secret
    creationPolicy: Owner
    template:
      type: kubernetes.io/dockerconfigjson
      metadata:
        annotations:
          argocd.argoproj.io/compare-options: IgnoreExtraneous
      data:
        .dockerconfigjson: |
          {"auths":{"ghcr.io":{"username":"wilddog64","password":"{{ .token }}","auth":"{{ printf "wilddog64:%s" .token | b64enc }}"}}}
  data:
    - secretKey: token
      remoteRef:
        key: secret/data/github/pat
        property: token
```

### Change 2 — `k8s/base/serviceaccount.yaml`: reference the pull secret on the SA that runs the pod

**Exact old block:**

```yaml
    pci-scope: "true"
automountServiceAccountToken: false
```

**Exact new block:**

```yaml
    pci-scope: "true"
automountServiceAccountToken: false
imagePullSecrets:
  - name: ghcr-pull-secret
```

### Change 3 — `k8s/base/kustomization.yaml`: track the new ExternalSecret

**Exact old block:**

```yaml
resources:
- serviceaccount.yaml
- configmap.yaml
- deployment.yaml
- service.yaml
- networkpolicy.yaml
```

**Exact new block:**

```yaml
resources:
- serviceaccount.yaml
- configmap.yaml
- deployment.yaml
- service.yaml
- networkpolicy.yaml
- externalsecret-ghcr.yaml
```

> The kustomization comment forbids listing **Secret** manifests (ESO owns those). An **ExternalSecret** is a
> CR, not a Secret, and is already listed in the product-catalog base — so this is consistent with the
> established pattern, not a violation of that note.
