## Problem

The same DRY_RUN footgun Phases 1–3 close for the CLI is still open over Slack: the operator has no
way to preview a `cluster-up` / `cluster-down` from Slack. Once Phase 2 lands, `DRY_RUN=1` produces an
accurate, side-effect-free plan on the CLI — Slack operators should get the same preview so they can
sanity-check a teardown before running it for real.

**Root cause (feature gap, not a defect):** `_run_cluster` (`bin/k3dm-webhook:610`) always spawns
`make up`/`make down` in real mode — there is no path to set `DRY_RUN=1` in the child environment, and
the Slack dispatch handlers (`cluster-up` @1026, `cluster-down` @1004) parse only an optional provider
token, never a dry-run flag.

---

## Design (why env-injection, not a make arg)

`bin/cluster-up` / `bin/cluster-down` read `DRY_RUN` **from the environment** (`[[ "${DRY_RUN:-0}" == "1" ]]`).
`make` exports its own inherited environment to recipe commands, so setting `DRY_RUN=1` in the environment
of the spawned `make` process flows through to the `bin/cluster-*` recipe unchanged. `_posix_spawn_job`
already accepts `env=` (`bin/k3dm-webhook:579`) and passes it to `os.posix_spawn`. So the entire wiring is:
parse a dry-run token → thread a `dry_run` bool into `_run_cluster` → inject `DRY_RUN=1` into the spawn env
→ skip the post-provision side effects (which assume a real cluster) → label the Slack messages.

No change to `bin/cluster-up` / `bin/cluster-down` / the Makefile is required or permitted here.

---

## Slack syntax (decided defaults — adjustable)

- `cluster-up [provider] [dry-run]`
- `cluster-down [provider] [dry-run]`

The dry-run token is any of `dry`, `dry-run`, `--dry-run`, `dryrun` (case-insensitive), in **any**
position among the args. Provider detection also becomes position-independent (scan args for a known
provider token) so `cluster-down dry` and `cluster-down hostinger dry` and `cluster-down dry aws` all work.
Role gate is unchanged — `cluster-up` / `cluster-down` stay **admin-only** (`_THREAD_COMMAND_MIN_ROLE`,
lines 288/290); a dry-run still spawns the lifecycle script and reads live cluster state.

## Part A — Slack DRY_RUN wiring (`bin/k3dm-webhook`)

### Change 1 — `bin/k3dm-webhook`: add a dry-run parser helper

Add near the other small command helpers (place above `_run_cluster`, ~line 609):

```python
_DRY_RUN_TOKENS = {"dry", "dry-run", "--dry-run", "dryrun"}
_PROVIDER_TOKENS = {"aws", "gcp", "az", "hostinger"}


def _parse_cluster_args(command):
    """Return (provider, dry_run) from a cluster-up/down Slack command.

    Provider and dry-run tokens may appear in any order after the command word.
    Provider defaults to 'hostinger' (matches the existing dispatch default).
    """
    parts = command.strip().split()[1:]
    dry_run = any(p.lower() in _DRY_RUN_TOKENS for p in parts)
    provider = next((p.lower() for p in parts if p.lower() in _PROVIDER_TOKENS), "hostinger")
    return provider, dry_run
```

## Part B — Phase 3b (test-only): strengthen the `*)` bridge regression guard

**Context.** Phase 3 (`469a3427`) added `source "${REPO_ROOT}/scripts/lib/system_overrides.sh"` to the
`*)` branch of `bin/cluster-down` (Change 2 there) so `DRY_RUN=1` on a local provider previews the
`_run_command`-only teardown ops instead of firing real `sudo`. That fix is **correct and shipped**, but
its regression test — `acg-down dry-run local provider bridges launchd bootouts` (currently
`scripts/tests/bin/cluster_down.bats:34`) — is **vacuous**: it asserts on the `launchctl-mutation-called`
sentinel, and every `launchctl bootout` in `bin/cluster-down` sits behind the headless-skip guard
(`if ! sudo -n true 2>/dev/null && ! [[ -t 0 && -t 1 ]]`, lines ~187/212/254) **or** an already-`_dry_run_active`
branch. So the sentinel never fires whether or not the `*)` source is present — reverting the Phase 3
`*)` source leaves the whole suite green.

**The fix (verified).** Target a **non-tty-gated** op that relies purely on the `_run_command` bridge:
the unconditional `_run_command --prefer-sudo --soft -- rm -f "${_keycloak_browser_plist}" …` at
`bin/cluster-down:198`. Its plist path is env-overridable via `KEYCLOAK_BROWSER_LISTENER_PLIST`. Point it
at a sentinel file and assert the sentinel **survives** under `DRY_RUN=1`: with the `*)` source present the
bridge previews the `rm`; without it the base `_run_command` (`scripts/lib/system.sh:128`, no dry-run
awareness) really `rm`s the sentinel.

> Mutation-verified before writing this spec: the new test **passes** on the current tree and **fails**
> (`[ -e "${_sentinel}" ]`) when the Phase 3 `*)` source line is removed.

### Change 7 — `scripts/tests/bin/cluster_down.bats`: replace the vacuous `*)` bridge test

**Exact old block (lines 34–39):**

```bash
@test "acg-down dry-run local provider bridges launchd bootouts" {
  run env DRY_RUN=1 CLUSTER_PROVIDER=orbstack bash -c 'bin/cluster-down --confirm --keep-hub 2>&1'
  [ "$status" -eq 0 ]
  [[ "$output" == *"Stopping ArgoCD browser HTTPS listener launchd daemon"* ]]
  [ ! -e "${BATS_TEST_TMPDIR}/launchctl-mutation-called" ]
}
```

**Exact new block:**

```bash
@test "acg-down dry-run *) path previews _run_command rm -f without executing it" {
  cat > "${BATS_TEST_TMPDIR}/bin/uname" <<'STUB'
#!/usr/bin/env bash
if [[ "${1:-}" == "-s" ]]; then printf 'Darwin\n'; else /usr/bin/uname "$@"; fi
STUB
  chmod +x "${BATS_TEST_TMPDIR}/bin/uname"

  _sentinel="${BATS_TEST_TMPDIR}/keycloak-browser.plist"
  : > "${_sentinel}"

  run env DRY_RUN=1 CLUSTER_PROVIDER=orbstack \
    KEYCLOAK_BROWSER_LISTENER_PLIST="${_sentinel}" \
    bash -c 'bin/cluster-down --confirm --keep-hub 2>&1'

  [ "$status" -eq 0 ]
  [ -e "${_sentinel}" ]
}
```

**Why this shape:**
- `CLUSTER_PROVIDER=orbstack` routes through the `*)` branch — the exact path Phase 3 Change 2 fixed.
- The local `uname` → `Darwin` stub forces `_is_mac` true so the keycloak-plist `rm` block (line ~198) runs.
- `--keep-hub` skips the k3d hub delete; the sentinel assertion is the mutation-sensitive check.
- Do **not** keep the old `launchctl-mutation-called` assertion — it is what made the test vacuous.
