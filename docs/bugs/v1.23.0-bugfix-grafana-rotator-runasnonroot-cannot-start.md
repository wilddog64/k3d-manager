## Problem

The `grafana-credential-rotator` CronJob pod fails to start with:

```
Error: container has runAsNonRoot and image will run as root
(container: rotate) — CreateContainerConfigError
```

The pod `securityContext` sets `runAsNonRoot: true` but supplies **no `runAsUser`**, and the
image `docker.io/alpine/k8s:1.31.4` runs as **root** by default. The kubelet refuses to start a
root-running container under `runAsNonRoot: true`, so the pod never leaves
`CreateContainerConfigError`.

**Root cause:** `runAsNonRoot: true` with no `runAsUser` + a root-default image. Present since the
rotator was first created (`5b418dd7`) — only two commits have ever touched this file, so the
rotator **has never successfully run**.

**Impact — this makes the `816835fd` DB-apply step inert.** The reset-admin-password step added in
`816835fd` (Fix 1 of the bundled Grafana bugfix) is correct, but it is wired into a CronJob whose
pod cannot start. Until this blocker is fixed, the rotator neither rotates nor applies the password
to Grafana's DB. (The false-red status smoke — Fix 2 of `816835fd` — is unaffected and is already
live-verified GREEN.)

> This also reframes the original "401 after rotation" symptom: no scheduled rotation ever ran.
> The 401 came from DB drift introduced when `5b418dd7` first wired Vault-sourcing (Grafana's DB
> kept its bootstrap password while Vault/ESO/secret got a new one). The stopgap reset already
> repaired the live DB; this fix makes the rotator able to run so future rotations self-heal.

## Live findings & mechanism verification (2026-08-08)

- A throwaway Job cloned from the rotator with `runAsUser: 65534` + `runAsGroup: 65534` added to
  the pod `securityContext` **started cleanly** (uid=65534), ran `kubectl` in-cluster (SA token is
  world-readable), `kubectl exec`'d into the Grafana pod, and ran
  `grafana cli … admin reset-admin-password --password-from-stdin` → **rc 0**,
  `Admin password changed successfully ✔`. Login at `https://grafana.3ai-talk.org` stayed **200**
  (the exec was idempotent to the current stored password).
- `65534` matches the non-root UID already used by the `vulnerability-inventory-exporter` in the
  same namespace group — a proven pattern for `alpine`-based images here.
- The rotator does **not** read the k8s secret (it reads the old password from **Vault**, generates
  `$new` via `openssl rand`), so the SA's lack of `secrets get` is irrelevant; `$new` is always
  populated and the `--password-from-stdin` read succeeds.

## Fix — give the pod a non-root `runAsUser`

**File:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`

Keep `runAsNonRoot: true` (do **not** drop the hardening); add an explicit non-root UID/GID so the
kubelet admits the root-default `alpine/k8s` image running as UID 65534.

**Exact old block (lines 90–93):**

```yaml
          securityContext:
            runAsNonRoot: true
            seccompProfile:
              type: RuntimeDefault
```

**Exact new block:**

```yaml
          securityContext:
            runAsNonRoot: true
            runAsUser: 65534
            runAsGroup: 65534
            seccompProfile:
              type: RuntimeDefault
```
