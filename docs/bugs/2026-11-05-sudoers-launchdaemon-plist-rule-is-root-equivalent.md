# Bug: LaunchDaemon and exec wildcard sudoers rules are root-equivalent

**Status:** OPEN. D1 failed its pf test on 2026-11-05 (`lo0` is skipped). D3 (launchd socket relay) is proposed and awaits the operator's go plus its own spike. Nothing has been dispatched.
**Priority:** P1
**Severity:** high — local privilege escalation through rules that headless `acg-up` currently relies on.
**Filed:** 2026-11-05
**Detected by:** `docs/issues/2026-11-02-acg-phase-c-privileged-inventory.md` (Terra Phase C worktree), confirmed by Claude against `bin/install-sudoers.sh` at `7c9927e9`.
**Branch:** `k3d-manager-v1.43.14`
**Approval:** operator, 2026-11-05: "go with your recommendation" (B plus C). Claude has since found that B is insufficient (see the finding below). Operator, 2026-11-05: "let dispatch D1". Part 1 dispatches after the pf test (S1) passes on the M4.
**Related:** `docs/bugs/2026-11-05-sudoers-passwordless-rules-grant-root-escalation.md` (narrow fix, dispatched first)

## Evidence

- `NOPASSWD: /usr/bin/install -m 644 * /Library/LaunchDaemons/com.k3d-manager.*.plist` together with `NOPASSWD: /bin/launchctl bootstrap system /Library/LaunchDaemons/com.k3d-manager.*.plist`.
  The caller writes the plist, chooses its `ProgramArguments`, and bootstraps it as a root daemon.
  Headless callers: `bin/cluster-up:906,1573,1748,1813` and `scripts/lib/providers/k3s-hostinger.sh:730`.
- `NOPASSWD: /bin/rm -f /Library/LaunchDaemons/com.k3d-manager.*.plist *`: the trailing `*` lets the caller delete any file as root.
- `NOPASSWD: /usr/local/bin/k3s *`, `/usr/bin/systemctl *`, `/usr/bin/apt-get *`, `dnf *`, `yum *` and `microdnf *` are each root-equivalent wherever the binary exists (for example `apt-get -o APT::Update::Pre-Invoke::=...`).
  They are harmless on macOS only while those paths stay absent.

## Design options (for the operator)

- **A.** A root-owned plist installer: `/usr/local/bin/k3d-manager-install-daemon <label> <port>...`. It renders each plist from a fixed template in a root-owned directory and accepts only allowlisted labels and numeric ports. The sudoers file would then allow only this helper.
- **B.** Drop passwordless plist install entirely. The listeners are installed once with a password by a `make browser-listeners` target, and headless runs only `bootstrap`/`bootout` the existing root-owned plists.
- **C.** Split the sudoers file per OS so the Linux wildcards never appear on macOS, and the reverse.

Recommendation: B plus C. They are the smallest change and need no new privileged code, which is the lesson from `2026-11-02-acg-up-stalls-at-system-keychain-trust`.

## Finding: option B is insufficient (Claude, M4, 2026-11-05)

The root daemons run user-writable code, so a user-level process gets root **without any sudoers rule**:
- All four browser-listener daemons run as root: no `UserName` key, with `KeepAlive` true. Their `ProgramArguments` is `/bin/bash <wrapper>`, and every wrapper is owned by the user:
  - `~/.local/share/k3d-manager/k3s-aws/bin/{argocd-browser-https,keycloak-browser-http,frontend-browser-http}.sh`
  - `~/.local/share/k3d-manager/bin/frontend-browser-http.sh`
  - All are `cliang:staff`, generated by `bin/cluster-up` (for example `_argocd_write_browser_https_wrapper`, around line 859).
- The wrappers run Homebrew's `socat` and `curl` as root. `/opt/homebrew/bin/socat` is also owned by the user.
- Editing a wrapper (or `socat`) runs the edit as root at the next `KeepAlive` respawn. The remaining passwordless `launchctl bootout`/`bootstrap` rules make that respawn immediate.
- Moving the listeners off root is not possible as-is. A non-root bind of `127.0.0.1:81` and of `127.0.0.1:444` fails with `PermissionError: [Errno 13]`, because macOS exempts only wildcard binds from the privileged-port check.

The fix must therefore stop root from executing anything user-writable, not only remove sudoers rules. The candidate designs are pending the operator's choice:
- **D1. pf redirect.** A one-time, password-gated pf anchor redirects `127.0.0.x:443/80` to user high ports. The listeners become user LaunchAgents, so there is no root daemon. The LaunchDaemon sudoers rules and the system plists are removed. Needs a spike: pf `rdr` on `lo0` for local traffic is unverified here.
- **D2. Root-owned runtime.** A one-time, password-gated install puts static wrappers, plus pinned copies of `socat` and `curl`, in a root-owned directory (`/usr/local/libexec/k3d-manager`, `root:wheel` 0755). Per-sandbox values (ports, cert paths) come from a data file that the wrapper validates strictly and never sources. Headless runs only `bootout`/`bootstrap`. This keeps a root process that parses user data.
- C (split sudoers per OS) applies to either.

## Finding: D1 is not viable (pf tests S1 and S2, M4, 2026-11-05)

- **S1.** The rule loaded into `com.apple/k3dm-pf-spike`, but `curl 127.0.0.3:81` returned nothing.
- **S2 (diagnostic).**
  - The main ruleset does reference `rdr-anchor "com.apple/*"`, and the anchor rules are listed.
  - The `127.0.0.1:81` rule shows `Evaluations: 14  Packets: 0`.
  - `pfctl -s Interfaces -i lo0` shows **`lo0 (skip)`**, with `References: Rules: 1`.
  - pf has been enabled for 11 days by another owner (the system), and its main ruleset carries `set skip on lo0`.
- **Conclusion.** pf never filters or translates loopback traffic on this Mac. `set skip` is a main-ruleset option and cannot be set or cleared from an anchor.
- D1 would therefore mean replacing Apple's main ruleset, which Part 1's N3 forbids. Apple or another tool could also reload that ruleset at any time.
- D1 is dropped.

## Proposed D3: launchd socket relay (pending operator go + relay spike)

- launchd itself, which is already root, binds the low port from a static plist `Sockets` entry.
- For each connection it starts `/usr/bin/nc 127.0.0.1 <high>` as **`UserName nobody`**, through `inetdCompatibility`.
- `/usr/bin/nc` is a SIP-protected system binary, and every argument is a literal.
- The real listeners move to user LaunchAgents on high ports, as in D1 Part 2.
- So no root process runs any user-writable code, and the only root-run binary is launchd.
- Homebrew `socat` as root was rejected, because it links `/opt/homebrew/opt/openssl@3` dylibs, which are user-writable.
- **Relay spike** (operator-run, M4): a temporary system job on `127.0.0.1:81` and `127.0.0.3:81` relays to a user listener on 18081. It is removed on exit.
- **Open check:** binding `127.0.0.2/.3` needs the loopback aliases to exist first. The spike shows whether launchd tolerates that ordering.

### S1: pf test (operator, M4, before any dispatch)

The script is in Claude's session scratchpad; its full path is in the operator message. It does the following:
- Starts a user-owned HTTP listener on `127.0.0.1:18081`.
- Loads `rdr pass on lo0 inet proto tcp from any to 127.0.0.3 port 81 -> 127.0.0.1 port 18081` into anchor `com.apple/k3dm-pf-spike`. The stock `/etc/pf.conf` already has `rdr-anchor "com.apple/*"`.
- Enables pf with a reference token, then curls `127.0.0.3:81`.
- Flushes the anchor and releases the token on exit.

PASS means D1 is viable. FAIL means fall back to D2.

### Part 1: redirect infrastructure (dispatch 1)

1. `scripts/etc/pf/k3dm-browser-redirects.conf`: the four `rdr pass on lo0` rules from the table, and nothing else.
2. `bin/install-browser-redirects.sh` (`make install-browser-redirects`). It is operator-run and installs everything through `_run_command --interactive-sudo`:
   - the rules as `/etc/pf.anchors/k3dm-browser-redirects` (`root:wheel` 0644)
   - LaunchDaemon `com.k3d-manager.pf-redirects`, which runs only `/sbin/pfctl -a com.apple/k3dm-browser-redirects -f /etc/pf.anchors/k3dm-browser-redirects` and `/sbin/pfctl -E` at boot. Fixed root-owned args; no user path anywhere in the plist.
   - `--dry-run` prints both files and runs `pfctl -n -f` syntax validation. `--uninstall` removes both and flushes the anchor.
3. Does **not** touch the existing listeners or sudoers. With Part 1 alone, the redirects are inert, because nothing listens on the high ports yet.

### Part 2: migrate the listeners and drop the rules (dispatch 2, filed after Part 1 lands)

1. In `bin/cluster-up` and `scripts/lib/providers/k3s-hostinger.sh`, the four listeners become user LaunchAgents (`gui/$UID`) on the high ports. No `/Library/LaunchDaemons`, no sudo.
2. Migration: on the first run after Part 2, the `bootout` and removal of the old system daemons need a password once. Headless runs skip it with a warning, as they do today.
3. `bin/install-sudoers.sh` removes the LaunchDaemon `install`, `bootstrap`, `bootout` and `rm` rules. It applies C: the Linux wildcards (`k3s`, `systemctl`, `apt-get`, `dnf`, `yum`, `microdnf`) are written only on Linux, and macOS gets only `true` plus `ifconfig lo0 alias/-alias`.
4. The loopback-alias daemons (`/sbin/ifconfig lo0 alias 127.0.0.x`, static root args) move into the Part 1 installer, so they are installed once with a password.
