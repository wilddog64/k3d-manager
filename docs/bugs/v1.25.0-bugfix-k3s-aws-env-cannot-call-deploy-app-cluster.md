# Bugfix: v1.25.0 — k3s-aws provisioning: `env` cannot invoke the `deploy_app_cluster` shell function

**Branch:** `k3d-manager-v1.25.0`
**Files:** `scripts/lib/providers/k3s-aws.sh`

---

## Problem

Fresh `k3s-aws` provisioning (`deploy_cluster --provider k3s-aws --confirm`, and therefore
`bin/cluster-up` / `make up CLUSTER_PROVIDER=k3s-aws`) fails to install k3s. The CloudFormation
stack and 3 EC2 nodes come up, tunnel mode is selected, then the k3s-install step dies with:

```
env: 'deploy_app_cluster': No such file or directory
```

and `_provider_k3s_aws_deploy_cluster` returns 1. The `ubuntu-k3s` kube context is never
re-merged (stays pointed at the previous/dead sandbox IP), so the cluster is unreachable.

**Root cause:** `scripts/lib/providers/k3s-aws.sh:178` invokes the installer as
`env UBUNTU_K3S_AGENT_HOSTS=… K3S_AMBIENT_MESH=… deploy_app_cluster --confirm`.
`deploy_app_cluster` is a **shell function** (`scripts/plugins/shopping_cart.sh:1109`), but
`env NAME=val CMD` execs `CMD` as a **binary from `PATH`** — it cannot call a shell function.
The bash idiom `NAME=val func …` sets the environment for a function call; prefixing it with
`env` breaks it. This line is reached on every fresh provision (nodes not yet Ready), before the
SSM/SSH branch, so both tunnel modes are affected.

Proof:
```
$ myfunc() { echo "var=$MYVAR"; }
$ MYVAR=hello myfunc          # → var=hello        (works)
$ env MYVAR=hello myfunc      # → env: 'myfunc': No such file or directory
```

---

## Reproduction

```bash
# fresh ACG sandbox (no Ready k3s nodes yet)
./scripts/k3d-manager deploy_cluster --provider k3s-aws --confirm
# ... "Installing k3s server + joining agents..."
# env: 'deploy_app_cluster': No such file or directory   → exit 1
```

Expected: k3s installs on the server, agents join, `ubuntu-k3s` context merged and Ready.
Actual: install step aborts; cluster never provisioned.

---

## Fix

### Change 1 — `scripts/lib/providers/k3s-aws.sh`: drop `env`, use the bash var-prefix idiom

**Exact old block (line 178):**

```bash
    _dry_guard "deploy application cluster" env UBUNTU_K3S_AGENT_HOSTS="ubuntu-1,ubuntu-2" K3S_AMBIENT_MESH="${_ambient_mesh}" deploy_app_cluster --confirm || return 1
```

**Exact new block:**

```bash
    _dry_guard "deploy application cluster" UBUNTU_K3S_AGENT_HOSTS="ubuntu-1,ubuntu-2" K3S_AMBIENT_MESH="${_ambient_mesh}" deploy_app_cluster --confirm || return 1
```

> Note: verify `_dry_guard` forwards a leading `NAME=val` word to the invoked function with the
> assignment intact. If `_dry_guard` word-splits its command such that the `NAME=val` tokens are
> not applied to `deploy_app_cluster`'s environment, instead export the two vars immediately
> before the call and unset them after, e.g.:
> ```bash
> local _prev_hosts="${UBUNTU_K3S_AGENT_HOSTS:-}" _prev_mesh="${K3S_AMBIENT_MESH:-}"
> export UBUNTU_K3S_AGENT_HOSTS="ubuntu-1,ubuntu-2" K3S_AMBIENT_MESH="${_ambient_mesh}"
> _dry_guard "deploy application cluster" deploy_app_cluster --confirm || return 1
> ```
> Codex: pick whichever matches `_dry_guard`'s actual argument handling (read its definition in
> `scripts/lib/system.sh`/`core.sh` first) and note which you used.
