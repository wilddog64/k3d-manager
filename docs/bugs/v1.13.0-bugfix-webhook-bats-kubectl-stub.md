# Bugfix: v1.13.0 — deterministic cluster-idle wait (+ kubectl stub) in webhook.bats

**Branch:** `k3d-manager-v1.13.0`
**Files:** `scripts/tests/lib/webhook.bats`

---

## Problem

Three `webhook.bats` tests fail in CI (`lint` job → "Run lib unit BATS"), all with
`[[ "$output" == *'"status":"queued"'* ]]` failing:

- `POST /cluster with unknown provider defaults to aws (202)` (line 185)
- `POST /cluster with action=up returns 202 and job_id` (line 409)
- `POST /cluster with action=down returns 202 and job_id` (line 420)

They pass locally (macOS) and in the full-file run locally, but fail on the GitHub
`ubuntu-latest` runner.

**Root cause:** the `POST /api/v1/cluster` handler marks a job `"running"` synchronously
before returning `202 queued` (`bin/k3dm-webhook:2756`), and the background `_run_cluster`
thread only clears that status in `_finish` **after** the `up` success path calls
`_record_acg_state` (`bin/k3dm-webhook:467`), which runs `kubectl create configmap … |
kubectl apply -f -` via `_posix_spawn_capture(timeout=15)`. That `_posix_spawn_capture`
poll has a 0.5s floor, so every successful `up` job holds `"running"` for ~0.5–1s after
`make` returns. The `make` stub added earlier this release made the `up` path *succeed*
(previously it failed fast and never ran `_record_acg_state`), which is why the tests
regressed. On the fast GitHub Linux runner, consecutive `/cluster` tests fire within that
window, so the next POST hits `_running_cluster_job()` (`:2746`) and gets `409 cluster job
already running` instead of `202 queued`. The failing tests are each immediately preceded
by another cluster-queue test (gcp-up → unknown-up, up → down). Locally the inter-test gap
is larger than the hold, so the collision never surfaces.

**Fix (two parts):**
1. **Deterministic** — a per-test `setup()` waits (`_wait_cluster_idle`) until no cluster
   up/down job is still `"running"` in `JOB_DIR` before the test runs. bats is serial, so
   once idle nothing else queues before the test's POST; `_running_cluster_job()` then
   returns `None` and the 409 path is unreachable. This closes the collision regardless of
   how long the `up` success path takes.
2. **Isolation** — stub `kubectl` in `setup_file` alongside the existing `make` /
   `K3DM_GEMINI_BIN` stubs so the queued `up` success path's `_record_acg_state` cannot run
   real `kubectl … apply` against a live cluster during tests (it would otherwise write an
   `acg-state` ConfigMap into `platform-ops` on a dev machine that has a cluster).

---

## Reproduction

On a host with `kubectl` installed but no reachable cluster (or with `KUBECONFIG` pointing at
a dead endpoint), run:

```bash
bats scripts/tests/lib/webhook.bats
```

Expected: all cluster POST tests queue (`"status":"queued"`).
Actual: consecutive `/cluster` up/down tests return `409 cluster job already running`.

---

## Fix

### Change 1 — `scripts/tests/lib/webhook.bats`: stub `kubectl` alongside `make`

Add a no-op `kubectl` stub to the existing `_BATS_STUB_BIN` dir so the `up` success path's
`_record_acg_state` / `_run_post_provision_check` kubectl calls cannot touch a live cluster.

Inside `setup_file`, after the `make` stub and before `export PATH=…`:

```bash
    printf '#!/bin/sh\nexit 0\n' > "${_BATS_STUB_BIN}/kubectl"
    chmod +x "${_BATS_STUB_BIN}/kubectl"
```

### Change 2 — `scripts/tests/lib/webhook.bats`: per-test cluster-idle wait

Add a `_wait_cluster_idle` helper and a `setup()` that calls it, so no test runs while a
prior cluster up/down job is still `"running"`:

```bash
_wait_cluster_idle() {
    local i=0 s
    while (( i < 100 )); do
        local running=0
        for s in "${K3DM_JOB_DIR}"/*/status; do
            [[ -f "$s" ]] || continue
            if [[ "$(cat "$s" 2>/dev/null)" == "running" && -f "${s%/status}/action" ]]; then
                running=1
                break
            fi
        done
        (( running == 0 )) && return 0
        sleep 0.1
        (( i++ )) || true
    done
    return 0
}

setup() {
    _wait_cluster_idle
}
```
