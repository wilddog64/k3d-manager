## Problem

Deploying the `k3s-aws` cluster to an ACG (A Cloud Guru / Pluralsight) AWS sandbox
has two coupled failure modes, and there is no automatic path between them:

1. **SSH tunnelling is fragile on ACG.** The `k3s-aws` provider defaults to an
   autossh SSH tunnel (`tunnel_start`, `scripts/lib/providers/k3s-aws.sh:86-87`),
   which needs inbound TCP 22 open in the security group from your *current* IP
   plus a stable public IP. On sandboxes, `ACG_ALLOWED_CIDR` drift (home NAT /
   CGNAT / VPN) or account-level ingress guardrails cause the tunnel to flap and
   the kube-apiserver at `localhost:6443` to become unreachable.

2. **The SSM alternative can't even provision on IAM-restricted sandboxes.** The
   CloudFormation template (`scripts/etc/acg-cluster.yaml:64-83`) *unconditionally*
   creates `SSMInstanceRole` (`AWS::IAM::Role`) + `SSMInstanceProfile` and attaches
   the profile to all three instances (`:114`, `:133`, `:152`). ACG sandboxes
   routinely deny `iam:CreateRole`, so the stack fails creating the role and
   **rolls back the entire cluster** — you get nothing, regardless of tunnel choice.

The user must know in advance whether their specific sandbox permits IAM role
creation, then hand-set `K3S_AWS_SSM_ENABLED` (`k3s-aws.sh:80`). Get it wrong and
provisioning either silently rolls back (SSM path on IAM-restricted sandbox) or
the cluster comes up but is unreachable (SSH path when ingress is blocked).

**Root cause:** the SSM IAM resources are hard-wired into the template (no way to
deploy without `iam:CreateRole`), and tunnel-mode selection is a static env var
with no detection of what the sandbox actually allows.

---

## Reproduction

**Rollback case (IAM-restricted sandbox):**
1. Use ACG sandbox creds where `iam:CreateRole` is denied.
2. `CLUSTER_PROVIDER=k3s-aws ./scripts/k3d-manager deploy_cluster`
3. CloudFormation fails on `SSMInstanceRole`; stack enters `ROLLBACK_COMPLETE`;
   no cluster. Expected: stack deploys (without the IAM role) and falls back to SSH.

**Unreachable case (SSH tunnel on restricted ingress):**
1. Sandbox where `iam:CreateRole` *is* permitted but inbound 22 is unstable/blocked.
2. Deploy with the default (SSH) tunnel. Cluster provisions but
   `kubectl --context ubuntu-k3s get nodes` times out via `localhost:6443`.
   Expected: provider detects IAM is permitted, enables SSM, and tunnels over SSM
   (no inbound SSH needed).

---

## Fix

Make the SSM IAM resources **conditional** (default off, so the stack always
deploys — safe on IAM-restricted sandboxes), then have the provider **probe
`iam:CreateRole`** and auto-select:

- **permitted** → flip the existing stack's `EnableSsm` parameter to `true` via
  `update-stack --use-previous-template` (attaches the instance profile with no
  interruption; no AMI re-derivation), wait for the SSM agent to register, use
  SSM port-forwarding (`ssm_tunnel`) — no inbound SSH.
- **not permitted / undetectable** → leave the stack as deployed (no IAM role),
  use the autossh SSH tunnel (`tunnel_start`).

An explicitly set `K3S_AWS_SSM_ENABLED` always wins (auto-detect is skipped).

### Change 5 — `scripts/lib/providers/k3s-aws.sh`: add detection + auto-select helpers

Insert these four functions **immediately after** the `source .../ssm.sh` line
(after line 18, before `function _provider_k3s_aws_deploy_cluster()` on line 20).

**Exact new block:**

```bash
# Probe whether the current caller may create IAM roles (side-effect-free).
# Returns 0 only when iam:CreateRole is explicitly allowed; any denial, error,
# or inability to evaluate (e.g. iam:SimulatePrincipalPolicy itself denied)
# returns non-zero so the caller falls back to the SSH tunnel.
_provider_k3s_aws_ssm_permitted() {
  local region="${ACG_REGION:-us-west-2}"
  local caller_arn source_arn decision acct role_name
  caller_arn=$(_run_command --soft -- aws sts get-caller-identity \
    --region "${region}" --query 'Arn' --output text 2>/dev/null) || return 1
  case "${caller_arn}" in
    *:assumed-role/*)
      acct=$(printf '%s' "${caller_arn}" | cut -d: -f5)
      role_name=$(printf '%s' "${caller_arn}" | sed -E 's#.*:assumed-role/([^/]+)/.*#\1#')
      source_arn="arn:aws:iam::${acct}:role/${role_name}"
      ;;
    *)
      source_arn="${caller_arn}"
      ;;
  esac
  decision=$(_run_command --soft -- aws iam simulate-principal-policy \
    --region "${region}" \
    --policy-source-arn "${source_arn}" \
    --action-names iam:CreateRole \
    --query 'EvaluationResults[0].EvalDecision' --output text 2>/dev/null) || return 1
  [[ "${decision}" == "allowed" ]]
}

# Flip the already-deployed stack to EnableSsm=true (attaches the SSM instance
# profile to running nodes with no interruption). Uses --use-previous-template
# and UsePreviousValue so no AMI/key re-derivation is needed. Idempotent: if the
# stack already has EnableSsm=true, returns 0 without an update.
_provider_k3s_aws_enable_ssm_stack() {
  local region="${ACG_REGION:-us-west-2}" current
  current=$(_run_command --soft -- aws cloudformation describe-stacks \
    --region "${region}" --stack-name "${_ACG_CF_STACK_NAME}" \
    --query "Stacks[0].Parameters[?ParameterKey=='EnableSsm'].ParameterValue" \
    --output text 2>/dev/null)
  if [[ "${current}" == "true" ]]; then
    _info "[k3s-aws] Stack already has EnableSsm=true — SSM profile present"
    return 0
  fi
  _info "[k3s-aws] Updating stack ${_ACG_CF_STACK_NAME} with EnableSsm=true..."
  _run_command --soft -- aws cloudformation update-stack \
    --region "${region}" \
    --stack-name "${_ACG_CF_STACK_NAME}" \
    --use-previous-template \
    --capabilities CAPABILITY_NAMED_IAM \
    --parameters \
      ParameterKey=EnableSsm,ParameterValue=true \
      ParameterKey=KeyName,UsePreviousValue=true \
      ParameterKey=AllowedCidr,UsePreviousValue=true \
      ParameterKey=InstanceType,UsePreviousValue=true \
      ParameterKey=AmiId,UsePreviousValue=true >/dev/null 2>&1 || return 1
  _run_command --soft -- aws cloudformation wait stack-update-complete \
    --region "${region}" --stack-name "${_ACG_CF_STACK_NAME}" || return 1
}

# Block until the SSM agent registers the instance (PingStatus Online), so the
# subsequent ssm_tunnel does not race the profile attachment. Times out at 150s.
_provider_k3s_aws_wait_ssm_registered() {
  local instance_id="$1" region="${ACG_REGION:-us-west-2}" attempts=0
  _info "[k3s-aws] Waiting for SSM agent to register ${instance_id}..."
  until [[ "$(_run_command --soft -- aws ssm describe-instance-information \
      --region "${region}" \
      --filters "Key=InstanceIds,Values=${instance_id}" \
      --query 'InstanceInformationList[0].PingStatus' --output text 2>/dev/null)" == "Online" ]]; do
    (( attempts++ ))
    if (( attempts >= 30 )); then
      _err "[k3s-aws] SSM agent did not register ${instance_id} within 150s"
      return 1
    fi
    sleep 5
  done
  _info "[k3s-aws] SSM agent online for ${instance_id}"
}

# Decide tunnel mode once, after the stack exists. Honors an explicit
# K3S_AWS_SSM_ENABLED; otherwise probes iam:CreateRole and, when permitted,
# enables SSM on the stack. Any failure degrades to the SSH tunnel.
_provider_k3s_aws_autoselect_tunnel_mode() {
  if [[ -n "${K3S_AWS_SSM_ENABLED:-}" ]]; then
    _info "[k3s-aws] Tunnel mode explicitly set (K3S_AWS_SSM_ENABLED=${K3S_AWS_SSM_ENABLED}) — skipping auto-detect"
    return 0
  fi
  _info "[k3s-aws] Auto-detecting tunnel mode (probing iam:CreateRole)..."
  if _provider_k3s_aws_ssm_permitted && _provider_k3s_aws_enable_ssm_stack; then
    export K3S_AWS_SSM_ENABLED=true
    _info "[k3s-aws] iam:CreateRole permitted + SSM profile attached — using SSM port-forwarding (no inbound SSH)"
  else
    export K3S_AWS_SSM_ENABLED=false
    _info "[k3s-aws] SSM unavailable (iam:CreateRole denied/undetectable or stack update failed) — using SSH tunnel (autossh)"
  fi
}
```

## Known Limitations / Notes (do not "fix" beyond scope)

- **SSM agent must be present on the AMI.** Recent Canonical Ubuntu AMIs ship
  `amazon-ssm-agent` (snap) preinstalled; if a future AMI filter drops it, SSM
  registration will time out and `_wait_ssm_registered` returns 1. That is the
  correct loud failure — do not silently swallow it here.
- **`simulate-principal-policy` may itself be denied** on locked-down sandboxes.
  That is treated as "not permitted" → SSH fallback. This can leave SSM unused
  even where `CreateRole` would actually succeed; the safe default is intended.
- **Vault reverse bridge is not supported in SSM mode** (pre-existing note at
  `k3s-aws.sh:42`) — unchanged by this fix.
