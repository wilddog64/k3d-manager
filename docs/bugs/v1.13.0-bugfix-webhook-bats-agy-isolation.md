# Bugfix: v1.13.0 — webhook bats suite launches real `agy`/Chrome

**Branch:** `k3d-manager-v1.13.0`
**Files:** `scripts/tests/lib/webhook.bats`, `bin/smoke-test-webhook`

---

## Problem

Running the webhook bats suite (`bats scripts/tests/lib/webhook.bats`) pops a Chrome
window on the dev box every run. The `POST /api/v1/analyze` and `POST /api/v1/diagnostics`
tests return `202` immediately, but the handler queues a **background daemon thread** that
runs the real analysis pipeline — `_call_gemini()` shells out to the `agy` (Antigravity)
CLI, which drives Chrome via ACG browser automation. The tests assert only on the `202`
and never wait for the job, so the job runs `agy` against the developer's machine unnoticed.

**Root cause:** `setup_file()` in `webhook.bats` does not stub `K3DM_GEMINI_BIN`, so
`_call_gemini()` (`bin/k3dm-webhook:911`) resolves the real `agy` binary
(`/Users/cliang/.local/bin/agy`) and launches it — and thus Chrome — from the queued job.

> This is a pre-existing test-isolation defect, unrelated to the auth-slice refactor
> (`5ee301bd`, `b32d0cec`), which moved only `_get_token` / `_verify_slack_signature` /
> `_spawn_capture_text` and never touched `_call_gemini`. On CI the `agy` binary is absent,
> so `_call_gemini` short-circuits ("agy CLI not found") and no browser launches — which is
> why this only reproduces on the dev box.

---

## Reproduction

```bash
bats scripts/tests/lib/webhook.bats
```

- **Expected:** all tests pass with no GUI side effects.
- **Actual:** all tests pass, but a Chrome window opens (from the `agy` job spawned by the
  `/analyze` and `/diagnostics` 202-returning tests).

---

## Fix

Point `K3DM_GEMINI_BIN` at a harmless no-op (`/usr/bin/true`) in both harnesses. `_call_gemini`
resolves it, spawns it (it ignores `--model`/`--prompt` and exits 0), and returns
"agy returned no output" — the job path is still exercised, just without launching `agy`/Chrome.
`/usr/bin/true` exists on both macOS and Linux/CI.

### Change 1 — `scripts/tests/lib/webhook.bats`: stub the analysis binary before booting the server

**Exact old block (lines 15–22):**

```bash
setup_file() {
    export K3DM_WEBHOOK_TOKEN
    K3DM_WEBHOOK_TOKEN="$(python3 -c 'import secrets; print(secrets.token_hex(16))')"
    export K3DM_WEBHOOK_PORT="${_WEBHOOK_PORT}"

    REPO_ROOT="$(cd "${BATS_TEST_DIRNAME}/../../.." && pwd)"
    python3 "${REPO_ROOT}/bin/k3dm-webhook" &
    export _BATS_WEBHOOK_PID=$!
```

**Exact new block:**

```bash
setup_file() {
    export K3DM_WEBHOOK_TOKEN
    K3DM_WEBHOOK_TOKEN="$(python3 -c 'import secrets; print(secrets.token_hex(16))')"
    export K3DM_WEBHOOK_PORT="${_WEBHOOK_PORT}"

    # Stub the analysis binary so queued /analyze and /diagnostics jobs cannot
    # spawn the real agy CLI (which launches Chrome via ACG browser automation).
    export K3DM_GEMINI_BIN="/usr/bin/true"

    REPO_ROOT="$(cd "${BATS_TEST_DIRNAME}/../../.." && pwd)"
    python3 "${REPO_ROOT}/bin/k3dm-webhook" &
    export _BATS_WEBHOOK_PID=$!
```

### Change 2 — `bin/smoke-test-webhook`: stub the analysis binary defensively on boot

The smoke test only hits `/api/v1/health` (no `agy` path today), but it boots a full
webhook instance; add the stub so any future health-adjacent job path can never launch a browser.

**Exact old block (lines 55–59):**

```bash
K3DM_WEBHOOK_TOKEN="${TOKEN}" \
K3DM_WEBHOOK_PORT="${PORT}" \
K3DM_JOB_DIR="${TMP_DIR}/jobs" \
K3DM_RUN_DIR="${TMP_DIR}/run" \
  python3 "${REPO_ROOT}/bin/k3dm-webhook" >"${SERVER_LOG}" 2>&1 &
```

**Exact new block:**

```bash
K3DM_WEBHOOK_TOKEN="${TOKEN}" \
K3DM_WEBHOOK_PORT="${PORT}" \
K3DM_JOB_DIR="${TMP_DIR}/jobs" \
K3DM_RUN_DIR="${TMP_DIR}/run" \
K3DM_GEMINI_BIN="/usr/bin/true" \
  python3 "${REPO_ROOT}/bin/k3dm-webhook" >"${SERVER_LOG}" 2>&1 &
```

## Follow-up (out of scope — do NOT implement here)

The bats suite boots the real server and queues **real jobs** — `POST /cluster action=up`
queues `_run_upgrade` → `make up`, and it also does not isolate `K3DM_JOB_DIR`/`K3DM_RUN_DIR`
(so its `_clear_stale_jobs()` mutates the live `:7443` instance's job dir). This contradicts
CLAUDE.md's "`scripts/tests/` — pure logic only, no cluster mocks." File a separate bugfix
to (a) isolate `K3DM_JOB_DIR`/`K3DM_RUN_DIR` in `setup_file()` and (b) neutralize the
live `make up`/`make down` job side effects. Not part of this Chrome fix.
