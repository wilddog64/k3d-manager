# Bugfix: v1.23.0 — Grafana admin-password rotation never reaches the DB (+ status false-green)

**Branch:** `k3d-manager-v1.23.0`
**Files:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`, `scripts/plugins/observability.sh`, `bin/k3dm-webhook`
**Status:** QUEUED — needs design decision on the DB-apply mechanism + live-verify. NOT yet handed to an agent.
**Severity:** high — locks the stored admin credential out of Grafana on every monthly rotation; `make status` hides it.

---

## Problem

`make show-service-passwords` displays the Grafana admin password from Vault
(`secret/observability/grafana`), but that value returns **HTTP 401 "Invalid username or
password"** at `https://grafana.3ai-talk.org` — even byte-for-byte (not a copy-paste error).
Meanwhile `make status` reports **"Grafana login: HTTP 200"**, so the breakage is invisible.

**Root cause (two independent defects):**

1. **Rotation never updates Grafana's DB.** The kube-prometheus-stack Grafana applies
   `admin_password` from `existingSecret` **only at first DB provisioning**. The monthly rotator
   `grafana-credential-rotator` rotates Vault → ESO → k8s secret `grafana-admin-credentials`, but
   **never changes the password in Grafana's sqlite DB** (`/var/lib/grafana/grafana.db`). Vault and
   the k8s secret stay in sync with each other (verified: identical SHA-256) but both drift away
   from what Grafana's DB actually accepts.

2. **The hub Grafana smoke reads the wrong secret → false-green.** In `bin/k3dm-webhook`,
   `grafana_base` is hardcoded to the hub URL `https://grafana.3ai-talk.org` (line 1674), but the
   login smoke reads its password from `acg-kube-prometheus-stack-grafana` in the **app-cluster**
   context (lines ~1758–1762) — a secret that **does not exist on the hub**. So the check either
   silently uses `K3DM_SMOKE_GRAFANA_PASS` or tests a different cluster's credential, and reports
   green while the hub login is broken. (This is the exact failure class flagged in
   `project_status_login_verification` — health smoke false-greens.)

Other services were audited and are fine: ArgoCD (`argocd-initial-admin-secret`), Prometheus and
Alertmanager basic-auth all authenticate HTTP 200 with their displayed passwords. Only Grafana
drifts, because only Grafana keeps its own credential store (DB) separate from the k8s secret.

---

## Stopgap already applied (2026-08-07, live only — NOT in git)

Reset Grafana's DB password back to the stored secret value so login works now:

```
PW=$(kubectl --context k3d-k3d-cluster get secret grafana-admin-credentials -n monitoring \
      -o jsonpath='{.data.admin-password}' | base64 -d)
printf '%s' "$PW" | kubectl --context k3d-k3d-cluster exec -i -n monitoring \
  <grafana-pod> -c grafana -- \
  grafana cli --homepath /usr/share/grafana --config /etc/grafana/grafana.ini \
  admin reset-admin-password --password-from-stdin
```

Verified: `POST /login` with the stored secret → HTTP 200. **This will re-break at the next
monthly rotation (`0 0 1 * *`)** until Fix 1 lands.

## Fix

### Fix 1 (durable) — rotator + initial deploy must APPLY the new password to Grafana's DB — DESIGN NEEDED

After writing the new value to Vault and force-syncing ESO, the rotator must change Grafana's own
admin password. Two candidate mechanisms — pick one during implementation:

- **(a) exec + CLI (recommended):** `kubectl exec` into the Grafana pod and run
  `grafana cli admin reset-admin-password --password-from-stdin` with the new value on stdin.
  Requires adding `pods` + `pods/exec` (verbs: `get`, `create`) on namespace `monitoring` to the
  `grafana-credential-rotator` Role. Justification for the RBAC widening: the rotator owns the
  credential lifecycle and must apply it to Grafana's internal store; namespace-scoped, not
  cluster-wide. No password on argv (stdin only).
- **(b) admin API:** `PUT /api/admin/users/1/password` authenticated with the *current* password.
  Fragile — needs the pre-rotation password to authenticate, and breaks if the DB already drifted.

The same DB-apply step must also run once in `observability.sh` (`deploy_observability`) so a fresh
deploy converges the DB to the secret, not only first-provision.

**Do NOT pin exact YAML here** — the exec/RBAC wiring is LIVE-VERIFY (confirm the rotator SA can
exec, confirm `--password-from-stdin` on the pinned Grafana image, confirm idempotency).

### Fix 2 (clean) — hub Grafana smoke must read the hub secret

**File:** `bin/k3dm-webhook` (~lines 1758–1762).

**Exact old block:**

```python
    graf_user = (os.environ.get("K3DM_SMOKE_GRAFANA_USER")
                 or _smoke_secret("monitoring", "admin-user",
                                  "acg-kube-prometheus-stack-grafana", context=app_context)
                 or "admin")
    graf_pass = os.environ.get("K3DM_SMOKE_GRAFANA_PASS") or _smoke_secret(
        "monitoring", "admin-password", "acg-kube-prometheus-stack-grafana", context=app_context)
```

**Proposed new block** (verify first that this function is not shared with an app-cluster status
path; `grafana_base` is hub-hardcoded, so the credential must be the hub's):

```python
    graf_user = (os.environ.get("K3DM_SMOKE_GRAFANA_USER")
                 or _smoke_secret("monitoring", "admin-user",
                                  "grafana-admin-credentials")
                 or "admin")
    graf_pass = os.environ.get("K3DM_SMOKE_GRAFANA_PASS") or _smoke_secret(
        "monitoring", "admin-password", "grafana-admin-credentials")
```

After this, `make status` goes RED whenever the DB drifts from the secret — i.e. it will catch a
future Fix-1 regression instead of hiding it. Requires `make restart-webhook` after the change.
