# Bugfix: v1.23.0 — Grafana admin-password rotation never reaches the DB (+ status false-red)

**Branch:** `k3d-manager-v1.23.0`
**Files:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`, `bin/k3dm-webhook`
**Status:** READY FOR HANDOFF — mechanism live-verified 2026-08-08 (Grafana 11.4.0; deployment-form exec exit 0; login 200). Bundled per user decision (Fix 1 + Fix 2 in one commit).
**Severity:** high — locks the stored admin credential out of Grafana on every monthly rotation; `make status` mis-reports it.

---

## Problem

`make show-service-passwords` displays the Grafana admin password from Vault
(`secret/observability/grafana`), which — after a monthly rotation — returns **HTTP 401 "Invalid
username or password"** at `https://grafana.3ai-talk.org` even byte-for-byte. Separately, the
`make status` smoke currently reports **"Grafana login: HTTP 401" (false-red)** — the hub login
actually works, but the smoke checks the wrong cluster's credential.

**Root cause (two independent defects):**

1. **Rotation never updates Grafana's DB.** kube-prometheus-stack Grafana applies `admin_password`
   from `GF_SECURITY_ADMIN_PASSWORD` (the `existingSecret`) **only at first DB provisioning**. The
   monthly rotator `grafana-credential-rotator` rotates Vault → ESO → k8s secret
   `grafana-admin-credentials` and then does `kubectl rollout restart` (lines 113–114) — but a
   restart does **not** rewrite Grafana's sqlite DB (`/var/lib/grafana/grafana.db`). The DB keeps
   the old password while Vault + the k8s secret hold the new one, so the stored credential 401s.

2. **The hub Grafana smoke reads the wrong secret → false status.** In `bin/k3dm-webhook`,
   `grafana_base` is hardcoded to the hub URL `https://grafana.3ai-talk.org` (line 1684), but the
   login smoke reads its password from `acg-kube-prometheus-stack-grafana` in the **app-cluster**
   (`ubuntu-hostinger`) context (lines 1769–1774) — the hostinger Grafana's credential, a different
   password against the hub's Grafana. Verified 2026-08-08: hub login with `grafana-admin-credentials`
   → **200**; the smoke's hostinger-sourced password → **401**. Today this false-**reds**; after a
   rotation with Fix 1 in place it would flip to false-**green** — either way the smoke must read
   the hub secret to reflect reality. (Same failure class as `project_status_login_verification`.)

Other services were audited and are fine: ArgoCD (`argocd-initial-admin-secret`), Prometheus and
Alertmanager basic-auth all authenticate HTTP 200 with their displayed passwords. Only Grafana
drifts, because only Grafana keeps its own credential store (DB) separate from the k8s secret.

## Live findings & mechanism verification (2026-08-08)

- Hub Grafana pod: `kube-prometheus-stack-grafana-*` in ns `monitoring`, context `k3d-k3d-cluster`,
  **Grafana v11.4.0**. Binary `/usr/share/grafana/bin/grafana`; config `/etc/grafana/grafana.ini`;
  DB `/var/lib/grafana/grafana.db` (owned by `grafana` uid 472 — the container's runtime user).
- The DB-apply command below was run live (idempotently, to the current value) via **both** the
  explicit-pod and the `deployment/…` exec forms — **exit 0**, `Admin password changed successfully ✔`,
  and `POST https://grafana.3ai-talk.org/login` returned **200** afterward. This is the exact form
  Fix 1 wires into the rotator.
- `_smoke_secret(namespace, key, secret_name, context=None)` with `context=None` omits `--context`
  and uses the webhook's current kubectl context, which is the hub — so Fix 2 just drops the
  `acg-…`/`app_context` args.

## Fix

### Fix 1 — rotator applies the new password to Grafana's DB (exec + `grafana cli`)

**File:** `scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`

**1a — widen the namespace-scoped Role** so the rotator SA can resolve + exec the Grafana pod.
Insert these two rules into the existing `Role` (`grafana-credential-rotator`), immediately after
the `deployments`/`patch` rule (after current line 22), before the `---` at line 23:

**Exact new block:**

```yaml
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
```

Justification for the RBAC widening: the rotator owns the credential lifecycle and must apply the
new password to Grafana's internal store; both verbs stay **namespace-scoped to `monitoring`**
(Role, not ClusterRole). `pods` get/list is needed for `kubectl exec deployment/…` to resolve the
backing pod; `pods/exec` create is the exec itself.

**1b — add the DB-apply step** to the CronJob script. Insert immediately AFTER the `rollout status`
line (current line 114) and BEFORE the `slack_url=` line (current line 115) — i.e. still inside the
`trap restore EXIT` region, so a failure rolls the Vault value back. Indent to match the surrounding
script (18 spaces).

**Exact old block (lines 113–115):**

```bash
                  kubectl rollout restart deployment/kube-prometheus-stack-grafana -n monitoring >/dev/null
                  kubectl rollout status deployment/kube-prometheus-stack-grafana -n monitoring --timeout=5m >/dev/null
                  slack_url="$(kubectl get secret platform-ops-notifications -n platform-ops -o jsonpath='{.data.slack-incoming-webhook-url}' 2>/dev/null | base64 -d || true)"
```

**Exact new block:**

```bash
                  kubectl rollout restart deployment/kube-prometheus-stack-grafana -n monitoring >/dev/null
                  kubectl rollout status deployment/kube-prometheus-stack-grafana -n monitoring --timeout=5m >/dev/null
                  printf '%s' "$new" | kubectl exec -i -n monitoring deployment/kube-prometheus-stack-grafana -c grafana -- \
                    grafana cli --homepath /usr/share/grafana --config /etc/grafana/grafana.ini admin reset-admin-password --password-from-stdin >/dev/null
                  slack_url="$(kubectl get secret platform-ops-notifications -n platform-ops -o jsonpath='{.data.slack-incoming-webhook-url}' 2>/dev/null | base64 -d || true)"
```

Notes:
- `$new` (the freshly rotated password) is fed on **stdin only** — never on argv (satisfies the
  secret-hygiene rule; consistent with the LDAP rotator).
- Runs against the freshly-restarted, Ready pod. `set -eu` is already in force, so a non-zero exit
  aborts the job and fires the existing `restore` trap.
- Do NOT remove the `rollout restart`/`status` lines — they keep the new pod's env in sync for the
  first-provision path; the diff is purely additive.

### Fix 2 — hub Grafana smoke must read the hub secret

**File:** `bin/k3dm-webhook` (lines 1769–1774).

**Exact old block:**

```python
    graf_user = (os.environ.get("K3DM_SMOKE_GRAFANA_USER")
                 or _smoke_secret("monitoring", "admin-user",
                                  "acg-kube-prometheus-stack-grafana", context=app_context)
                 or "admin")
    graf_pass = os.environ.get("K3DM_SMOKE_GRAFANA_PASS") or _smoke_secret(
        "monitoring", "admin-password", "acg-kube-prometheus-stack-grafana", context=app_context)
```

**Exact new block:**

```python
    graf_user = (os.environ.get("K3DM_SMOKE_GRAFANA_USER")
                 or _smoke_secret("monitoring", "admin-user",
                                  "grafana-admin-credentials")
                 or "admin")
    graf_pass = os.environ.get("K3DM_SMOKE_GRAFANA_PASS") or _smoke_secret(
        "monitoring", "admin-password", "grafana-admin-credentials")
```

`grafana_base` is hub-hardcoded, so the credential must be the hub's `grafana-admin-credentials`
(default/current context = hub). After this, `make status` reflects reality — GREEN when the DB
matches the secret, RED if a future rotation regresses (i.e. it will catch a Fix-1 failure instead
of masking it). Requires `make restart-webhook` after the change.
