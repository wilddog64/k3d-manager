# Retrospective — v1.21.0

**Date:** 2026-08-03
**Milestone:** Harden the k3dm webhook auth surface
**PR:** [#110](https://github.com/wilddog64/k3d-manager/pull/110) — merged to main (`f68bdee1`)
**Participants:** Claude, Codex, Copilot

## What Went Well

- **Defense-in-depth landed cleanly.** The internet-facing webhook (Cloudflare Worker → tunnel → `127.0.0.1:7443`) went from "bearer token is the only boundary and it grants full admin" to a layered posture: Slack path enforces the same RBAC as HTTP, roles fail **closed**, the `/ask` bash sandbox blocks interpreters/nested shells/redirection, plus a 429 rate limiter, guarded JSON parse, bounded event-id cache, and a `TOKEN_FILE` permission check.
- **Live verification, not just green CI.** Restarted the `:7443` instance and exercised the real matrix — health 200, no-token → 401, invalid role → 403 fail-closed to reader, malformed JSON → 400, sustained GETs trip the 429 — and `bin/smoke-test-webhook` (13/13) with 49/49 BATS. The security claims are demonstrated, not asserted.
- **Copilot findings resolved with evidence.** Two real fixes (`base64 -d` → `--decode`; removed the vestigial pytest gate from the spec) and one **evidence-based decline** (the "flaky real kubectl" finding — already PATH-stubbed via `_BATS_STUB_BIN`, documented in the issue log rather than making a no-op change).
- **The hidden stacked release was surfaced, not blindly merged.** Discovered v1.22.0 (and v1.23.0) sat unmerged *beneath* the branch we were about to PR; stopped and let the user choose sequential vs blended. Chose sequential — two clean release stories, two tags.

## What Went Wrong

- **Misreported CI as green on the first pass.** A backgrounded `gh run watch … ; gh run view` returned exit 0 from the final `gh run view`, not from the CI conclusion — CI had actually FAILED lint. Caught by reading the authoritative `conclusion` field. **Lesson: never trust the shell exit code of a chained watch/view; read `gh run view --json conclusion`.**
- **A latent CI regression detonated mid-release.** `stale_test_refs.bats` hard-codes historical fixture SHAs; the v1.20.0 branch cleanup orphaned them, so a fresh CI clone (even `fetch-depth: 0`) couldn't reach them and `check-stale-test-refs.sh` silently exited 0 via `|| true` on the bad revision. Not caused by this milestone's changes — environmental — but it blocked the PR until guarded.
- **base64 short-flag convention drift.** The v1.17.0 `base64 --decode` portability convention wasn't carried into the `21cf3a38` make-passwords change; Copilot re-caught it. Convention decisions need to propagate to *new* code, not just the code that established them.

## Process Rules Added

| Rule | Where | Why |
|------|-------|-----|
| Read `gh run view --json conclusion` as authoritative; a chained watch/view's exit code is the *view's* status, not CI's | Session lesson (verification protocol) | Prevented a false "CI green" report from recurring |
| `stale_test_refs.bats` fixtures must be commit-reachability guarded (`skip` when the SHA is orphaned) — durable fix is a self-contained in-test fixture | `docs/issues/2026-08-03-stale-test-refs-fixture-orphaned-by-branch-cleanup.md` | Fresh CI clones stay green after branch cleanup orphans historical SHAs |

## Decisions Made

- **Release theme split (2026-08-03):** v1.21.0 stays scoped to webhook security hardening (1 plan doc — a *theme-coherence* split, not a 5-plan-doc-cap split). The openldap `bitnamilegacy` → maintained-image migration is its own release **v1.22.0** — a heavy cross-subsystem infra migration doesn't belong in an internet-facing-webhook theme.
- **Sequential stacked merge:** v1.21.0 → main first (this milestone), then rebase v1.22.0 onto the new main and PR it, then v1.23.0. Two release stories, two tags — not one blended PR.
- **`K3DM_SLACK_ROLE_MAP` is a deploy prerequisite:** without it populated (env or Keychain `k3dm-slack-role-map`), every Slack user is treated as reader-only. Documented in the release notes as an owner deploy note.

## Theme

v1.21.0 is a security-hardening milestone with a single tight scope: the internet-facing k3dm webhook. A review found the whole auth boundary was one bearer token that granted full admin — and the Slack command path didn't even enforce the RBAC the HTTP path did. This release makes a leaked token, an unmapped Slack user, or a crafted `/ask` payload much less useful to an attacker: RBAC on both paths, roles that fail closed, a hardened bash sandbox, and server-level guards (rate limit, JSON parse guard, bounded cache, token-file perms). It shipped verified live, not just CI-green. The milestone also flushed out two process lessons the hard way — a false "CI green" from trusting a shell exit code, and a latent fixture-orphaning CI regression from the previous release's branch cleanup — and surfaced a hidden stacked release (v1.22.0/v1.23.0 sitting underneath), which the user chose to unwind sequentially rather than blend.
