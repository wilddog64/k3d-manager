## What Went Well

- **Phase 2 crossed the read-only → write boundary cleanly.** Hermes' first-ever mutation path is a *closed, code-defined allowlist* (R1 restart-webhook, R2 kick zombie port-forward, R3 refresh Hostinger edge, R4 rerun transient CI). The poll cycle only **proposes**; execution happens only through `bin/k3dm-hermes approve <action-id>`, which re-validates the precondition and re-samples after. No auto-execution path exists in code (grep-proven, invariant-1).
- **Least-privilege held.** R1–R3 use local levers (make target, `launchctl`, a lib-foundation function) and add **no** new cluster/cloud credential. Only R4 gained a remote scope (`actions:write`), and it still holds no `contents:write`, no branch-protection, no PR/merge.
- **R4 write-scope verified end-to-end through the real code path**, not an ad-hoc token — the business-logic-403 distinction (`"This workflow run cannot be retried"` = authorized; `"Resource not accessible by personal access token"` = missing scope) confirmed the `k3dm-hermes-gh-token` PAT holds write.
- **Copilot review was high-signal: 11 findings across 5 rounds, all legitimate, 0 false positives, all fixed**, with CI green on every head and 0 unresolved threads throughout. The fix→push→(reply+resolve) discipline held every round.
- **Codex-authored code was independently verified before commit** (Codex hit its usual sandbox `.git` lock; Claude committed after gates). Claude caught a fabricated-data defect (R2 port-forward labels for services that don't exist) and grounded the map to the one real match.

## What Went Wrong

- **R4 token scoping is manual and error-prone.** GitHub has no API to mint or re-scope a fine-grained PAT, so granting `actions:write` was a hand-operation the user had to perform in the UI. User: *"why can't we automate this? this is really not a very good way to manage tokens."* Filed as a follow-up (GitHub App installation-token auth).
- **A smoke-script verdict heuristic misfired** on GitHub's 403 wording, briefly reporting the token lacked write. The raw API response was authoritative and corrected it — a reminder not to trust a hand-rolled classifier over the source response.
- **Claude stopped at the merge gate with `enforce_admins` still enabled**, so the user (who self-merges) couldn't merge. User: *"you didn't enable admin override for me to merge. you need to update your memory so that will be executed every time PR created."* Corrected: disabling admin override is now a proactive step at every PR merge-ready.
- **Two Copilot findings were about mistakes in the PR's own framing** (e.g. the R4 403 misclassification that the PR text itself described) — the review caught what the author's prose had glossed over.

## Process Rules Added

| Rule | Where | Why |
|------|-------|-----|
| Disable `enforce_admins` proactively at every PR merge-ready (not "if needed") | auto-memory `feedback_notify_pr_review_before_merge` | User self-merges and needs admin override on; leaving it enabled blocks the merge. `/post-merge` re-enables it. Never-auto-merge unchanged. |
| R4 must refuse (skip) rather than fall back to ambient `gh` auth when the Hermes Keychain token is absent | `scripts/lib/hermes/repairs.py` `approve()` | Empty `GH_TOKEN` would let `gh` use the laptop's ambient OAuth — a least-privilege / no-ambient-auth violation. |
| Missing-scope detection keys on `"resource not accessible"` only, not any `403` | `scripts/lib/hermes/repairs.py` | Business-logic 403s (`"cannot be retried"`) are authorized and must fall through to `failed`, not be misreported as missing scope. |
| Proposal `action_id` must be stable (sha1 of key+command, no timestamp) | `scripts/lib/hermes/repairs.py` `propose()` | A per-cycle-changing id grows `pending_repairs` unboundedly and breaks idempotency. |

## Decisions Made

- **Ship v1.30.0 with the PAT auth now; migrate to a GitHub App later.** The manual `actions:write` PAT is the accepted v1.30.0 posture. The auto-scoped, short-lived alternative is scoped as a *follow-up*, not a v1.30.0 blocker.
- **GitHub App installation-token auth is filed as `docs/plans/v1.31.0-hermes-r4-github-app-auth.md`** — an auth-swap only (RS256 JWT → installation token, ~1h TTL, auto-scoped), retaining a PAT fallback, with Phase 2 repair logic unchanged, plus a DI-testable `k3dm-hermes preflight` scope check.
- **Phase 3 (cooldowns, daily budgets, durable audit, automatic post-repair verification) remains deferred** and requires its own scope document. Phase 2 carries only the minimum: proposal/approval/outcome to state + Slack, a one-incident guard, and a single post-repair re-sample.

## Theme

v1.30.0 is the release where Hermes stopped only watching and started — carefully — repairing. The whole design is an argument that a monitoring agent can be given a write capability without becoming a liability: the set of things it can touch is a closed list in code, every action is human-approved at the operator's own shell, preconditions are re-checked at execution time, and three of the four repairs need no new privilege at all. The one repair that does (R4's `actions:write`) exposed the real friction — hand-scoped PATs are a poor way to manage credentials — which turned into the next milestone's first task. Alongside the feature work, the release hardened the merge workflow itself: admin override is now enabled proactively so the human who owns the merge decision isn't blocked by the machinery meant to protect it.
