# Retrospective — v1.43.0

**Date:** 2026-10-11
**Milestone:** v1.43.0 — daily hub data export (scheduled, encrypted, verified, retained); split from the wider hub-restore scope into v1.43.1
**PR:** #139 — merged to main (`edfc9a5c`), tag `v1.43.0`, GitHub release `v1.43.0`
**Participants:** Claude, Codex, Gemini, Copilot

## What Went Well

- The daily export shipped as code with tests: 72 BATS cases across hub_data, dr_drill and publish, shellcheck, and 78 manifests validated. Mutation checks went red for both Codex and Claude. (`CHANGELOG.md` `[1.43.0]`, `scripts/tests/plugins/hub_data.bats`)
- The live launchd path was proven, not just the manual run. The operator kickstarted the LaunchAgent on the M4; export `20261011T120849Z` pushed, remote verify and prune passed, and the Pushgateway reported `last_run_success 1`. (`docs/bugs/2026-10-11-hub-data-export-fails-under-launchd-and-dr-alerts-never-deployed.md`)
- Copilot left one comment on PR #139, and it pointed at a real defect (`rg` in a BATS suite). The thread was resolved with a fix, and CI run `38141089074` was green on `e2b457de`. (`docs/issues/2026-10-11-copilot-pr139-review-findings.md`)
- The release gate was honoured: `enforce_admins` was disabled only for the merge window and re-enabled afterwards, and `required_approving_review_count` was never lowered. (`memory-bank/activeContext.md`)

## What Went Wrong

- PR #139 went red in CI three times in a row, each time for something the M4 could not show:
  1. `hermes_alert_rules.bats` called `rg`. CI does not install ripgrep, so the call exited 127 (`BW01 ... Command not found`). The M4 has `rg`, so the test passed locally.
  2. `precommit_bug_priority.bats` inherited CI's `K3DM_ENABLE_AI=1`. The pre-commit hook then ran the AI lint reviewer, which fails on the runner. The two "accepted" tests failed; the two rejection tests exited earlier and passed. The suite pinned the bypass switches it knew about, not every switch the hook reads.
  3. `scripts/bug-tally.py` had an unused `collections.defaultdict` import (Ruff F401). Ruff is not installed on the M4, so `make lint-python` refused to run there and this was never checked before the PR.
- The first scheduled export failed at 03:30 on 2026-10-11. launchd starts jobs in `/`, and `hub_data.sh` built the age-recipient path from `${REPO_ROOT:-.}`, which resolves wrongly under launchd. Manual runs from the repo root and the tests (which set the recipient explicitly) both hid it. The data repo's drill-freshness workflow also failed (exit 127) on a `k3d-manager` path. (`docs/bugs/2026-10-11-hub-data-export-fails-under-launchd-and-dr-alerts-never-deployed.md`)
- The `HubDataExport*` and `DRDrill*` alert rules were never on the hub. `prometheusrule.yaml` is applied by `make platform-ops`, not by ArgoCD sync. An earlier note that said the alerts auto-synced via `hub-platform-ops` was wrong.
- A manual run had been counted as proof that the schedule worked. It was not, until the LaunchAgent itself was kicked.

## Process Rules Added

| Rule | Where | Why |
|---|---|---|
| A test that runs `.githooks/pre-commit` must pin every switch the hook reads (`K3DM_ENABLE_AI`, `K3DM_SKIP_DOC_LINKS`, `K3DM_SKIP_ROOT_DEBRIS`), not only the ones it is testing around. | `docs/issues/2026-10-11-copilot-pr139-review-findings.md` (process note) | CI sets `K3DM_ENABLE_AI=1`; a developer shell usually does not. |
| Before a PR, run any new suite once in `ubuntu:24.04` with the CI lint job's env, and run `make lint-python` with the pinned Ruff (`ruff==0.15.8`). | `docs/issues/2026-10-11-copilot-pr139-review-findings.md` (process note) | Neither `rg` nor Ruff is present on the M4, so both defects were invisible locally. |
| A scheduled job is not proven by a manual run. End setup with `launchctl kickstart` so the job runs the way the schedule will. | `docs/bugs/2026-10-11-hub-data-export-fails-under-launchd-and-dr-alerts-never-deployed.md` (Lesson) | The manual run used the repo root as cwd; launchd uses `/`. |
| Alert rules are not live until they are confirmed on the hub. Check the rules API and `ALERTS{}` after applying a PrometheusRule. | `docs/bugs/2026-10-11-hub-data-export-fails-under-launchd-and-dr-alerts-never-deployed.md` | `dr.alerts` was never loaded on the hub. |

## Decisions Made

- **Split v1.43.0 into v1.43.0 and v1.43.1.** The hub-restore work (`hub_data_recover`, one-command restore) and the DR clean-room checks moved to `docs/plans/v1.43.1-hub-data-recover.md` and `docs/plans/v1.43.1-dr-clean-room-checks.md`, so v1.43.0 would ship only the daily export. Reason: the operator made the daily export a P1 to implement right away and left the split to Claude; the restore scope was moved so v1.43.0 would stop growing (`docs/roadmap.md`, v1.43.1 entry).
- **v1.43.1 branches from the merged v1.43.0.** Branch `k3d-manager-v1.43.1` was created at `edfc9a5c`, and the post-merge memory-bank commit was carried onto it.
- **The release branch stays the values ref for ApplicationSets.** Reapply on each release is a required step.

## Theme

Make the scheduled path, not the manual path, the thing that gets proven. The export worked when run by hand from the repo root for hours and failed on its first scheduled run; the CI reds were the same gap in the other direction, where the M4 passed what CI could not.
