## What Went Well

- **The spec → implement → independently-verify loop held on every task.** Five Codex tasks landed this milestone (`843e643a`, `cdeebfa6`, `647b4181`, `950998aa`, `2a55f0be`) and every one was checked against the spec byte-for-byte, with gates re-run on this machine and the SHA confirmed on `origin/<branch>` — never on Codex's word. Nothing had to be reverted.
- **Reviewing Codex's *plan* before he touched code caught nothing this time — and that is the point.** Both plans were faithful, which is the expected outcome when the spec carries exact old/new blocks. The cost of the review is low and it is the gate that has previously caught wrong-file and wrong-spec starts.
- **Running the thing live found the bug the spec could not.** Spec 5 was implemented exactly as written and still produced a red smoke. Only executing `keycloak_seed_smoke_user` against a real cluster surfaced `invalid_grant "Account is not fully set up"`. Two of the five tasks this milestone (`950998aa`, `2a55f0be`) exist *only* because live verification was treated as mandatory rather than optional.
- **Disproving an assumption beat implementing it.** The Frontend ⚪ was documented as a designed limitation ("smoke-client token not scoped for frontend audience"). Testing it took one `curl` and showed the frontend returns HTTP 200 with that token — the ⚪ was discarding real coverage. The check is now genuinely green.
- **Copilot's finding was verified, not obeyed.** Its `base64` remedy would have broken Linux (see below). Measuring both implementations before editing turned a would-be regression into a correct fix.

## What Went Wrong

- **Pre-flight caught two gaps that should never have reached PR time.** The CHANGELOG `[Unreleased]` section was completely empty despite five landed code commits, and the new public `keycloak_seed_smoke_user` was registered in neither `docs/api/functions.md` nor the README plugins table. Both are mechanical and both were invisible until `/create-pr` ran its checklist.
- **A merge-blocking check was mis-reported as green.** The `/create-pr` Phase 1 subagent reported "CI: success" based on the CI *workflow* run, while a separate `GitGuardian Security Checks` was red. It also invented line numbers (1558/1612/1631) for the flagged secrets that pointed at ordinary code. Delegated status reports need independent confirmation before they gate a decision.
- **`.gitguardian.yaml` gave false confidence.** Local `ggshield` reported `0 secrets detected` while the PR check reported `3 secrets uncovered`. `ignored_matches` silence only the local CLI — the server-side incidents stay OPEN. This was learned once earlier in the milestone (incident 35144224) and then re-encountered on three more, because the two-step nature was never written down.
- **Milestone scope crept past the stated limit.** Seven `docs/bugs/` specs shipped in one release branch. They are exempt from the max-5-*plan* rule, but seven unplanned fixes in a single milestone is a signal the theme was discovered rather than planned.
- **A one-line fix touched four lines it did not have to.** Normalizing all 7 `base64` sites (vs the 3 the PR introduced) was a deliberate, owner-approved call to avoid a mixed convention — but it is scope creep on a release PR and worth naming as such.

## Process Rules Added

| Rule | Where | Why |
|---|---|---|
| `base64 --decode` is the house form; never `-D` or `--decode \|\| -D` | `.github/copilot-instructions.md` → Platform Detection | `-D` is invalid under GNU coreutils, and the `\|\|` arm is unsound in a pipeline (no stdin). Stops the same bad suggestion recurring. |
| Keycloak plugin + `keycloak_seed_smoke_user` documented, incl. the required User Profile attributes | `.github/copilot-instructions.md` → Architecture | The v1.17.0 seed contract was undocumented for reviewers; the User Profile requirement is the non-obvious part that cost a live debugging cycle. |
| Health-smoke login grading contract (2xx→pass, smoke-client 401/403→skip, else→fail) | `.github/copilot-instructions.md` → Architecture | Encodes *why* a ⚪ is legitimate, so a future change does not collapse it back to an unconditional skip. |
| `k3s` provider added; `k3s-oci` marked **DE-SCOPED** | `memory-bank/projectbrief.md` | The table claimed OCI was Active and omitted bare-metal `k3s` entirely. |

## Decisions Made

- **k3d-manager owns its own smoke identity.** Rather than depend on app-owned Keycloak client configuration, the project seeds `k3dm-smoke` (client + user + Secret). This keeps the smoke working regardless of how the application team configures `frontend`, at the cost of a documented limitation: an app-owned realm reconcile can wipe the user, and the fix is to re-run the idempotent seed.
- **Frontend login is graded, not skipped.** A smoke-client `401`/`403` degrades to ⚪ rather than ❌, so the check stays honest if the frontend is later hardened to enforce `aud`. Today it passes because the frontend authenticates the bearer without checking audience — recorded as a dev-only observation, not silently relied upon.
- **v1.17.0 was stamped as a release** rather than merged as an incremental PR, matching the v1.16.0 convention (stamp → PR → merge → tag).
- **OCI stays de-scoped.** Reaffirmed while auditing standing docs; the provider code remains but earns no further effort.

## Theme

This milestone is about the difference between a green dashboard and a working system. `make status` had been reporting healthy logins for a long time while only ever fetching health pages — and a Keycloak stale-session page answers HTTP 200 just as cheerfully as a working one. Closing that gap meant the smoke had to actually log in, which immediately ran into the reason nobody had done it: the application's own Keycloak client cannot do password grants at all. So k3d-manager started seeding its own identity.

What is worth remembering is that the specs were implemented correctly and the feature still did not work. A fresh cluster produced `Account is not fully set up`, because Keycloak 24 requires profile attributes nobody had thought to set. Then the frontend check turned out to be skipping itself based on an assumption that a single `curl` disproved. Neither was findable by reading the diff — both required running it against a real cluster and being willing to distrust the comment explaining why something was grey. The same instinct paid off at review time, when the one automated finding on the PR came with a fix that would have broken every Linux run.

The recurring lesson, in three different costumes: verify the claim, especially when the claim is reassuring.
