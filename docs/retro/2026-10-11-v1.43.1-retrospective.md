# Retrospective — v1.43.1

**Date:** 2026-10-11
**Milestone:** v1.43.1 — recover a real hub from its export (`make hub-data-recover`, `make hub-recover-all`) and keep the DR drill out of the host's credentials
**PR:** #140 — merged to main (`38fbf3ab`), tag `v1.43.1`, GitHub release `v1.43.1`
**Participants:** Claude, Codex, Copilot

## What Went Well

- The recovery path was rehearsed live before the PR, not just unit-tested. The M2 rehearsal (run `20261011T184927Z` on `k3d-dr-drill`) passed steps 1–9 and found four bugs that the stubbed BATS could not see. Each was fixed with a test that goes red under mutation.
- The drill's Keychain guard proved what it was built for. The audit drill at `84b26ca2` listed five `credentials_unexpected` entries: the drill was overwriting the M2's own Vault unseal cache. That became `docs/bugs/2026-10-11-dr-drill-overwrites-host-vault-unseal-cache.md` and was fixed before the guard default flipped to `enforce`.
- The final enforce drill (`20261012T001215Z.json`) passed with V0–V7 and V9 true and `credentials_unexpected: []`, using default policy with no override.
- The release stayed at two plans, as split from v1.43.0. Bug docs filed during the milestone went to v1.43.2 or later releases, not into this PR.

## What Went Wrong

- Codex's spec 1 needed three rounds:
  - Round 1 (`949df1a9`) ignored step failures, inverted the ArgoCD read-back and never produced a format-2 export.
  - Round 2 (`8df73a62`) had a dead resume (`jq` without `-s`), restored the latest export instead of the approved one, and left grep-only tests.
  - Round 3 was accepted with Claude fixes.

  Grep-only tests and `!` no-ops let both rejected rounds report green.
- The first live export of the new format failed ("could not record the inventory"). The Vault metadata walk treated the JSON listing as one key, and the stub returned a version for any path, so the tests hid it.
- PR #140's first CI run failed on Linux only. A `dr_drill.bats` test asserted a `security` call, but `_secret_load_data` uses `secret-tool` off macOS. This is the same class as v1.43.0's `rg` failure: a test written on the M4 that assumes the M4's tools.
- Copilot's review summary said the `hub_data.sh` recovery code was not in its diff, although the PR changes it by about 630 lines. A clean Copilot review on a large PR is not evidence that the largest file was reviewed.
- The enforce drill's RTO was 1294 s against 744 s for the audit run, with no explanation recorded.

## Decisions Made

- The drill uses its own unseal cache service `k3dm-vault-unseal-drill`, purged at teardown. The host cache is never touched.
- The drill's Keychain guard defaults to `enforce`; audit is opt-in.
- The M2 hub Vault was retired (helm release, PVC and its cache entries removed); `external-secrets` there is undecided.
- A scheduled unattended drill is planned for v1.46.0 (`docs/plans/v1.46.0-scheduled-dr-drill.md`), now that enforce and the isolated cache remove the two original blockers.
- Hub kine compaction died again on 2026-10-08, the third time. The remedy is a planned `make hub-recover-all` rebuild, never a k3s restart. The missing alert is v1.43.2 P2 (`docs/bugs/2026-10-11-hermes-kine-sensor-misses-dead-compaction.md`), including an end-to-end test that the alert fires and reaches `platform-warning`.

## Theme

v1.43.0 made the hub's data leave the machine every night; v1.43.1 made it come back. The real work was not the restore steps but the guard rails around them: an approval-first flow that resumes, a drill that cannot touch the host's credentials, and an audit that showed it could before the switch to enforce. The milestone shipped green, and the same day showed the next gap. The hub's datastore had quietly stopped compacting three days earlier and nothing alerted, so the first live use of `hub-recover-all` may come sooner than planned.
