# Retrospective — v1.23.0

**Date:** 2026-08-09
**Milestone:** CVE remediation observability + self-verification (workstreams B + C, plus a pulled-forward Grafana credential-rotation slice from E)
**PR:** [#112](https://github.com/wilddog64/k3d-manager/pull/112) — merged to main (`7253ece4`)
**Participants:** Claude, Codex, Gemini, Copilot

## What Went Well

- **v1.20.0 made the auto-patch loop run; v1.23.0 made it trustworthy.** The remediation verifier now confirms the Deployment-pinned spec digest + readiness instead of the pod's runtime `imageID`, and looks in each service's real namespace. End-to-end live-verified on the hub: matching-digest payment events flip `promotion_requested → applied`, and Alertmanager suppresses the paired TrivyCritical during an in-flight remediation and lifts it on completion.
- **Live-cluster verification caught real bugs that green CI and BATS could not.** The `image_repository` host-qualification mismatch (`ghcr.io/` vs bare `org/repo`) that silently no-op'd the inhibit-rule join was found only by a live `equal:` join check — not by any unit test. Same for the alert-noise root cause (39 firing / 1 remediable).
- **The multi-arch index-digest false-negative was correctly root-caused, not patched-over.** containerd aliases a multi-arch pod's `imageID` to whichever OCI *index* digest it first cached the platform child under — so a byte-identical patched image string-compared as a `ready_pod_digest_mismatch`. Fixed by comparing the deploy-pinned spec digest, and captured as a durable reference memory so the next occurrence isn't re-debugged from scratch.
- **A wrong auto-diagnosis was caught before implementation.** The handed-in "exclude infra namespaces (platform-ops/secrets/trivy-system)" fix for the alert flood would have suppressed the one legitimately remediable alert — the exporter attributes *every* image to `namespace=platform-ops`. Surfaced to the user, then fixed with the correct discriminator (`image_repository=~"wilddog64/.*"`) instead.
- **Copilot's 3 PR findings were all real and all fixed** (Vault token off `curl` argv → mktemp header file; exporter writable `/tmp` for ro-rootfs; `printf %q` quoting of `mount_path` across the `sh -lc` boundary), threads replied + resolved, re-review of the folded-in commit came back clean.

## What Went Wrong

- **Config committed to a branch is inert until deployed — this bit twice this release.** The platform-ops files (prometheusrule / alertmanager-config / exporter / verify-script CM) are applied by `deploy_argocd_platform_ops` reading the working tree, NOT by ArgoCD — so the alert-noise fix was green in CI and merged for hours while the live hub kept flooding, until the post-merge `deploy_argocd_platform_ops` ran. Same class as the standing ApplicationSet `$values`-branch-freeze trap.
- **The webhook Slack-title bug (`labels["name"]` → empty for Trivy alerts) shipped the empty `` `` title for as long as it did** because the webhook is a host launchd process, not in-cluster — the merged `bin/k3dm-webhook` change is inert until `make restart-webhook`. Two separate "merged ≠ live" surfaces in one release (in-cluster apply + host webhook restart).
- **One follow-up is knowingly deferred:** the surviving ours-alert still triggers `_call_gemini` headless, which hits a tool needing a command permission it can't prompt for → posts *"no output produced — command permission auto-denied"* to Slack. The routing fix reduced the flood to ≤1/12h, so this is now low-volume, but it's still broken. Deferred to v1.24.0 (needs an agy no-tools / allowlist / `--dangerously-skip-permissions` decision).
- **Order remediation is still unresolved (task #18).** The promoter live-patches the ArgoCD Application (ephemeral, not git) and order's override is empty — it never resolved a clean immutable `sha-*` candidate (bare-tag / `IfNotPresent`). Carried to a design decision, not a code fix.

## Process Rules Added

| Rule | Where | Why |
|------|-------|-----|
| namespace is NOT a usable CVE-alert discriminator — the vulnerability-inventory-exporter attributes every image to `platform-ops`; split by `image_repository` prefix instead | auto-memory `reference_trivy_critical_upstream_image_noise` | A namespace exclusion suppresses the one real remediable alert |
| Verifier must compare the **Deployment-pinned spec digest**, never the pod runtime `imageID`, for multi-arch images | auto-memory `reference_containerd_index_digest_aliasing_verifier` (reinforced) | containerd index-digest aliasing produces false `ready_pod_digest_mismatch` |
| `image_repository` label convention differs across metrics (`cve_remediation_state` host-qualified vs `trivy_vulnerability_inventory` bare) — normalize with `label_replace` before any join/inhibit | auto-memory `reference_trivy_vs_remediation_image_repository_label_mismatch` | `equal:` joins silently match nothing otherwise |

## Decisions Made

- **CVE inventory dashboard shipped as Codex 1:1** (4-table view, `06a0416e`) — the user preferred it over the "by image" regroup; dashboard parts (b)+(c) (CVE-ID panel + KSM job-target labeling) are superseded and must be re-scoped against the Codex dashboard before ever executing.
- **Grafana admin credential rotation (E slice) was pulled forward** into v1.23.0 after a leaked admin password. v1.24.0 must **SKIP** the Grafana slice — remaining E = recurring rotation automation for ArgoCD / Prometheus / Alertmanager (only LDAP + Grafana are automated so far).
- **Upstream (third-party) critical CVEs stay visible on the Grafana inventory dashboard but do not page** — routed to a `k3dm-quiet` blackhole receiver rather than dropped, so they remain auditable without noise. Only `wilddog64/*` images (which the app-cve-scan loop can actually rebuild) keep `remediation: cve-auto-patch`.

## Theme

This release turned a CVE auto-patch loop that *ran* into one you can *trust*. The headline features — an inventory dashboard, a vulnerability exporter, and a remediation verifier — are really one idea: stop guessing from runtime signals (pod `imageID`, all-time stale event rows, un-normalized labels) and instead confirm ground truth (the Deployment-pinned digest, GC'd terminal events, `label_replace`-normalized joins). The recurring lesson, paid twice this release, is that **merged config is not live config**: the platform-ops files and the host webhook both needed an explicit post-merge apply/restart to take effect, and the live hub kept misbehaving until they ran. The sharpest save was refusing a plausible-but-wrong auto-diagnosis (exclude infra namespaces) that would have silenced the one alert that actually mattered — a reminder that the fix which *looks* obviously correct is exactly the one to check against live data before shipping.
