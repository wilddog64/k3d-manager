# Retrospective — v1.43.3

**Date:** 2026-10-16
**Milestone:** v1.43.3 — PR checks dashboard, lib-foundation bug tracking, fixed-in release attribution, dispatch cost panels, and the first live-proof cycle for the 2026-10-15 hub rebuild fixes
**PR:** #144 — merged to main (`881bb921`), tag `v1.43.3`, GitHub release `v1.43.3`
**Participants:** Claude, Codex, Copilot

## What Went Well

- Three of the five v1.43.3 items landed as specs with mutation evidence: fixed-in release attribution from tag ancestry, the PR checks dashboard, and lib-foundation bug tracking. Each new test was run against the pre-fix source and went red, and the spec mutations were run and went red.
- Copilot left 0 findings on PR #144, so the review loop closed without a code round.
- The v1.43.2 Bug Tracking dashboard work carried over. Live checks on the hub showed `pr_checks` scrape_success=1 for both repos, lib-foundation `bug_info`=26, and the per-spec dispatch and fixed-in series present.
- Live proof came in for two v1.43.2 items during this cycle: the e2e abort fix `c92c4311` ("aborted at <phase>" in Failure causes) and the checkout load-test dashboard leaving the hub.
- The lib-foundation v0.5.3 release shipped the `_secret_store_data` fix (no secret on the `security` argv, failed Keychain writes reported), and the subtree pull on `k3d-manager-v1.43.3` matched the tag tree.

## What Went Wrong

- PR #144's CI lint failed once on ruff F541 (a placeholder-less f-string in `scripts/tests/hermes/test_pr_checks.py`). `ruff` is not installed on the local machine, so `make lint-python` cannot run here. The failure only showed in CI. Fixed in `4072343c`.
- The Bug Tracking table lost its Verified, Live-verified and Fixed in columns when the selected release had only open bugs. The labels were emitted only for fixed bugs, and the Grafana panel builds its columns from the labels present. Fixed in `099b0586` by emitting a `-` placeholder for unfixed bugs. Mutation-proven: 3 pytest and 2 BATS reds on the pre-fix code.
- Live `make up` failed at Step 10d.5: the hub's LDAP rejects the `openldap-admin` password (err=49) while Keycloak binds fine. Filed as a P1 for v1.43.4. The cause is still open and needs an operator hash comparison.
- `make e2e-sandbox` failed at configuring-vault (`vault` CLI missing, rc 127). Tier 2 rebuilds what the hub already deploys, so the sandbox run and the hub fight over the same workloads. The operator chose design (a′): a label-switched hub overlay, recorded in `888a878f`. The spec moves to v1.43.4.
- The e2e-sandbox Argo CD CRD ownership conflict recurred on a fresh sandbox. The bug doc now records the recurrence. The fix (reuse the `cicd` Argo CD that `cluster-up` installs) landed as `e809f9c5` and needs a live run to prove it.

## Process Rules Added

| Rule | Where |

| A new test is only evidence once it has been run against the pre-fix source and gone red | memory `reference_new_test_passing_does_not_mean_it_can_fail` |

## Decisions Made

- The e2e-sandbox design is option (a′), the label-switched hub overlay, not (c). (c) was checked live and is not viable. The spec is queued for v1.43.4.
- The `cluster-up` LDAP admin-bind failure is a P1 for v1.43.4. It blocks a clean `make up` and is not fixed in this release.
- The e2e-sandbox Argo CD CRD fix was moved from v1.43.4 into v1.43.3 at operator request and shipped in this release.
- Bug Tracking defaults to the current release, not "all" (P3, v1.43.4, operator-approved).
- The v1.43.3 release is not a multiple-of-5 milestone, so no branch cleanup was done for it.

## Theme

v1.43.3 made the dashboards tell the full story: which bugs are fixed and in which release, what each PR's CI looks like, and what the dispatch agents cost. The release also surfaced the gaps the live runs expose. A column that disappears when a release has no fixed bugs, an e2e sandbox that rebuilds what the hub already runs, and a hub LDAP admin bind that fails are the three that carry into v1.43.4. Live proof for most of this release still needs the operator's `make appsets-reapply` and `make platform-ops`.
