# Retrospective — v1.22.0

**Date:** 2026-08-07  
**Milestone:** OpenLDAP bitnami→Symas migration  
**PR:** #111 — merged to main (`1bbb74b0`)  
**Participants:** Claude, Codex, Copilot

## What Went Well

- **Chart research rigor.** When the initial Symas migration spec targeted `jp-gouin/openldap` (a stale 2.0.4 chart), Codex's execution plan review included a direct `helm template` validation of the target chart. This caught the critical error in time and established a practice: always render and verify Helm chart contracts before writing infrastructure code.

- **Consumer reconciliation completeness.** Every stateful consumer touching the directory service — Keycloak LDAP federation, Jenkins LDAP auth, password-rotator credentials, bootstrap schema — was systematically re-tested and reconciled. No lingering Bitnami references survived to production. Service name pinned (`openldap.identity.svc:389`) for transparent cutover across the board.

- **Delimiter-safe password generation.** The migration exposed a template-corruption vulnerability in the Symas chart's `sed`-based value rewriting. Admin/config passwords are now hex-encoded (delimiter-safe), preventing accidental breakage when the chart's templating engine processes them. This hardening applies forward to all password-dependent migrations.

- **Durable bootstrap semantics.** Vault-seeded platform users (admin/developer/operator) survive the OpenLDAP chart swap. Bootstrap changed from one-shot to durable (the ConfigMap-based LDIF import is now idempotent and safe to re-run). The Vault integration persists across rebuilds.

- **Live verification confidence.** Developer login through Keycloak, Jenkins LDAP auth, and pod-side password validation all passed live acceptance testing. No "ghost feature" risk — the replacement chart genuinely works end-to-end.

## What Went Wrong

- **Stale mount-path defaults carried forward.** The LDIF import helper checked the old Bitnami mount path (`/ldif_import`) when the Symas chart uses `/ldifs`. Because `LDAP_LDIF_ENABLED` defaults to `true`, the guard silently failed post-deploy, meaning the idempotent re-import and subsequent password-reset helper (essential for chart rotation) were skipped entirely. Only the container-startup bootstrap saved the release from data loss. Copilot's review caught this live and verified it against the pod. **Process fix:** When swapping a Helm chart in a spec, explicitly re-verify every hardcoded in-pod path, mount default, and environment variable name against the new chart's `helm template` output. Don't rely on naming conventions.

- **Slack-notify RBAC initial proposal lacked deployment-order justification.** Copilot flagged the notifier ClusterRole as over-privileged when a namespace-scoped Role would suffice. The initial reasoning was absent. Investigation revealed a hard ordering dependency: `platform-ops` namespace is created by a separate argocd entrypoint with no guaranteed ordering relative to LDAP deployment. Justification was added and the ClusterRole kept, but the spec should have included this trade-off upfront.

## Process Rules Added

None this milestone. (The mount-path and ordering trade-off notes are incorporated as comments in the CLAUDE.md security rules and the code review findings doc, not as new standing process rules.)

## Decisions Made

1. **Chart swap entails full path audit.** When migrating to a new Helm chart, the spec must include a rendered `helm template` validation and explicit re-verification of every in-pod path, mount, and default against the new chart. This is now recorded in `docs/issues/2026-08-07-copilot-pr111-review-findings.md` Finding 3 root-cause section.

2. **Namespace-ordered dependencies documented in RBAC trade-offs.** When a RBAC resource must be cluster-scoped due to namespace creation ordering, the spec records the ordering dependency and the marginal over-privilege trade-off explicitly (see Finding 2 justification).

3. **mount-path defaults to vendor-specific Symas layout.** Hardcoded defaults now assume the `jp-gouin/openldap-stack-ha` chart contract: `/ldifs` for LDIF mounts, `openldap` for service name, `openldap-stack-ha` for container name. Future drift from this chart requires explicit local overrides, not silent failures.

## Theme

Migrate OpenLDAP off the retired `bitnamilegacy` image (66 CVSS-critical vulnerabilities, frozen namespace, no CVE patches post-August-2025) to the maintained `jp-gouin/openldap-stack-ha` 4.3.3 chart running `jpgouin/openldap:2.6.9-fix` image. The migration is transparent to all consumers: the service stays pinned at `openldap.identity.svc:389`, admin/developer/operator users survive via durable Vault-seeded bootstrap, and Keycloak's LDAP federation plus Jenkins LDAP auth are reconciled without service interruption. Passwords are generated delimiter-safe (hex) so the Symas chart's `sed`-based templating can't corrupt them. The release was split out from a larger 142-commit integration branch (archived at `origin/archive/k3d-manager-v1.22.0-integration`) into four focused v1.22.0/v1.23.0/v1.24.0/v1.25.0 milestones. Live verification confirmed the Symas chart is running, `developer` login succeeds through Keycloak, and Jenkins LDAP auth is fully reconciled. All shell code passes pure-logic BATS validation (ldap_chart_passwords 2/2 green; shellcheck clean on all changed shell).
