## Problem

`bin/k3dm-codex-dispatch` only works on k3d-manager. It takes the repo root from its own checkout,
requires a `k3d-manager-vX.Y.Z` branch, makes the task worktree from that repo, and lands by
fast-forwarding the k3d-manager release branch. Fixes in `shopping-cart-*`, `lib-foundation` and the
other repos therefore go through a bare `codex exec`, which writes no ledger event. The `k3dm Agent
Dispatch` dashboard then shows nothing for that work.

On 2026-10-18 every Codex run went through bare `codex exec`: two k3d-manager bugs, two in
`shopping-cart-infra` and one in `shopping-cart-frontend`. The dashboard showed "Time since last
dispatch 21.4 hours" and "Running 0". From 2026-10-01 to 2026-10-17, at least 43 headless Codex sessions
ran outside k3d-manager (see `v1.43.6-dispatch-codex-solo-activity.md`). The operator uses this data
for research. Lost lifecycle events (start, Codex exit, verifier lines, wait, land or refusal) cannot
be rebuilt afterwards.

`v1.43.6-dispatch-codex-solo-activity.md` counts unledgered sessions from Codex's session files. It
does not record verification, landing or rework. This plan is the other half: work in another repo
goes through the dispatcher, so it gets the full lifecycle.

## Design

The spec stays in k3d-manager, which is tracked and pushed on the release branch as today. The code
change happens in a **work repo**, on a **target branch** that Claude creates and pushes before the
dispatch (for example `fix/<slug>` from `origin/main`). The dispatcher never creates, pushes or merges
to `main`.

New `start` options, used together (each requires the other):

- `--repo PATH`: a git checkout other than k3d-manager. It must be a git toplevel, have a GitHub
  `origin`, and must not be k3d-manager itself.
- `--branch NAME`: the target branch. It must exist on the work repo's `origin`, and must not be
  `main` or `master`.

When both are given:

1. The version still comes from the k3d-manager release branch, so the task is filed under the release
   that holds the spec.
2. The checks on the spec (exists, tracked, unchanged, HEAD pushed, `## Files` not empty) still run
   against k3d-manager.
3. `git -C <repo> fetch origin <branch>:refs/remotes/origin/<branch>`, then
   `git -C <repo> worktree add -b task/<version>/<slug> <worktree> origin/<branch>`. The same
   checks as today for an existing local or remote task branch run against the work repo.
4. The run folder records `repo` (absolute path), `target` (branch name), `base` (the work repo's
   `origin/<branch>` SHA), `spec` (the spec path) and `spec-base` (the k3d-manager HEAD SHA). It also
   holds `spec.md`, a copy of the spec at `spec-base`.
5. The prompt names the absolute path of `$run/spec.md` instead of a path inside the worktree, and
   `--add-dir` covers the run folder, so Codex can read it.
6. The `start` ledger event carries `repo` = the work repo's `origin` repository name (for example
   `shopping-cart-frontend`). Every later event for the task (`codex_exit`, `land`, `land_refused`,
   `resume`, `abandon`) carries the same `repo`, read from the run folder. k3d-manager tasks carry
   `repo: "k3d-manager"`.

`status`, `land`, `resume` and `abandon` read `repo` and `target` from the run folder. If those files
are missing, the task is a k3d-manager task, which keeps today's behaviour for tasks started before
this change.

- **`land` in a work repo:**
  - The operator's checkout of the work repo (`repo`) must be on `target` and clean.
  - Rebase onto `target`, run the test command in the task worktree, then `merge --ff-only` into
    `target` in that checkout.
  - Print `push: git -C <repo> push origin <target>`.
  - The scope check reads the `## Files` patterns from `$run/spec.md`. They are paths in the work repo.
    `memory-bank/**` is refused there too.
- **Target-movement check on `land` (both kinds of task):** before the rebase, `land` fetches
  `origin/<target>` (for a k3d-manager task, `origin/<release branch>`) and compares three SHAs: the
  recorded `base`, the current `origin/<target>`, and the local `<target>` in the operator's checkout.
  - Local `<target>` must equal `origin/<target>`. A local branch that is ahead (unpushed commits) or
    behind is refused with reason `target_diverged`.
  - If `origin/<target>` equals `base`, the branch has not moved.
  - If `base` is an ancestor of `origin/<target>`, the branch moved forward. `land` prints
    `target moved: +N commits since dispatch (<base>..<new>)`, rebases and continues. The `land` event
    records `target_moved_commits: N` (0 when unmoved).
  - If `base` is not an ancestor of `origin/<target>` (force-push, reset or rebase of the target),
    refuse with reason `target_rewritten`. No `--allow-*` flag overrides this. The operator abandons
    and re-dispatches.
  - After the tests pass and immediately before `merge --ff-only`, `land` re-reads the local
    `<target>`. If it differs from the SHA it rebased onto, it refuses with `target_moved_during_land`.
  - Each refusal writes a `land_refused` event with that reason and leaves the task worktree as it was.
- **`status` with no SLUG:** lists the tasks of every repo under the version, with a `repo:` line for
  each.
- **Task worktree removal after land:** `git -C <repo> worktree remove` and branch delete, in the work
  repo.

**Metrics.** `bin/k3dm-dispatch-metrics` adds a `repo` label to the per-task series
(`k3dm_dispatch_task_*`) only. The aggregate series keep their current labels, so the existing panels
and alerts are unchanged. The label must match `^[A-Za-z0-9._-]{1,64}$`. A missing or invalid `repo`
on an older event becomes `k3d-manager`. The 50-task cap per window stays. The dashboard's per-spec
table gets a Repo column.

**Make.** `codex-dispatch` passes `REPO` and `BRANCH` through when set:
`make codex-dispatch SPEC=docs/bugs/<file>.md REPO=~/src/gitrepo/personal/shopping-carts/<repo> BRANCH=fix/<slug>`.
Bug specs in `docs/bugs/` are valid specs, as today.
