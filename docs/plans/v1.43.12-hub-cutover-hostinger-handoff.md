## Problem

`make hub-new` passed every stage on the M5 on 2026-10-31. A read-only comparison with the M4 found three gaps:

1. **The M5 ArgoCD has no Hostinger registration.** The M4 has the cluster Secret `cicd/cluster-ubuntu-hostinger` (label `k3d-manager/role=app-cluster`) and the kube context `ubuntu-hostinger`, built from `~/.kube/hostinger.config`. The M5 has neither file nor context nor Secret. So the M5 runs 13 Applications where the M4 runs 33: the 15 `ubuntu-hostinger-*` Applications plus `shopping-cart-apps` and `shopping-cart-networking` are missing. `bin/hub-cutover` moves only the launchd singletons. Once the M4 cluster stops after cutover, nothing manages Hostinger.
2. **The ExternalSecret `cicd/argocd-oidc-secret` is missing on the M5.** `_hub_recovery_ensure_identity_bootstrap` (`scripts/plugins/hub_recovery.sh:147`) applies it from `../../shopping-carts/shopping-cart-infra/argocd/config/argocd-secret.yaml`. That repo is not cloned on the M5, because `scripts/etc/machine/repos.list:38` gives it role `worker` only. The reconcile only warned, and hub-new's verify did not notice, because it checks that the ExternalSecrets present are synced, not that this one exists. ArgoCD's Keycloak login would break after cutover.
3. **`cve-remediation-verify` fails every 15 minutes on the M5** with `secrets "cluster-ubuntu-hostinger" not found`. This has the same cause as 1.

**Why the registration cannot simply be added to hub-new.** Registering Hostinger on the M5 while the M4 ArgoCD still manages it would give one cluster two application controllers, both with automated sync, prune and selfHeal, applying the same Applications. So the handoff belongs inside the cutover, with a single invariant: **at every point, at most one hub's `argocd-application-controller` has replicas above zero while both hubs register Hostinger.**

**Why rollback must not delete a registration.** Deleting a registration Secret makes the ApplicationSets delete their generated Applications, and the hub's ESO goes with them (memory `reference_hub_app_cluster_registration_is_load_bearing_for_eso`). Rollback therefore moves the active controller back by scaling. It never deletes the M5's registration.

## Design

### 1. `refresh_registration` merges a saved kubeconfig when the context is missing

`_provider_k3s_hostinger_refresh_registration` (`scripts/lib/providers/k3s-hostinger.sh:1130`) calls `_hostinger_register_cluster`, which reads the server and CA from the `ubuntu-hostinger` context. Today it fails when that context is absent. Change it so that before registering:

- if `kubectl config get-contexts "${_HOSTINGER_KUBE_CONTEXT}"` fails and `${_HOSTINGER_KUBECONFIG}` exists, it calls `_hostinger_merge_kubeconfig`;
- if the context is absent and the file is missing, it fails with: `[k3s-hostinger] no ${_HOSTINGER_KUBE_CONTEXT} context and ${_HOSTINGER_KUBECONFIG} missing — copy it from the old hub first`.

When the context already exists, nothing else changes; the additive-only guard stays.

### 2. `bin/hub-cutover` hands over the application controller

Add these steps to the cutover. The existing singleton steps are unchanged. Run every remote kubectl through `ssh "$OLD_HOST"` with `PATH=/opt/homebrew/bin:$HOME/.local/bin:$PATH` set in the remote command, because a non-login SSH shell does not find kubectl. Context `k3d-k3d-cluster` on both Macs (override `HUB_CUTOVER_CONTEXT`); namespace `cicd` (override `HUB_CUTOVER_ARGOCD_NS`).

**Before the singleton bootout**, while still read-only:
- **H0. Read the M4 state.** Read the M4 controller's `.spec.replicas` (`statefulset/argocd-application-controller`). Check that `~/.kube/hostinger.config` exists on the M4, unless the M5 already has the `ubuntu-hostinger` context or `~/.kube/hostinger.config`. Refuse with a clear message if either read fails. `DRY_RUN=1` prints both results plus the handoff plan lines, and exits 0 without changing anything.

**After the "old host is quiet" check passes, and before loading any M5 singleton:**
- **H1. Stop the M4 controller.** Record the M4 replica count in `$STATE_DIR/old-argocd-controller-replicas`. Scale the M4 statefulset to 0. Wait until it reports `readyReplicas` 0 or absent and no pod matches `app.kubernetes.io/name=argocd-application-controller` (timeout `HUB_CUTOVER_CONTROLLER_WAIT_S`, default 180). On timeout, append report `old-controller-not-stopped` and exit non-zero without registering anything.
- **H2. Copy the Hostinger kubeconfig.** If `~/.kube/hostinger.config` is missing on the M5, `scp` it from the M4 to `~/.kube/hostinger.config`, then `chmod 600`. Never print its contents.
- **H3. Register Hostinger on the M5.** Run `CLUSTER_PROVIDER=k3s-hostinger ./scripts/k3d-manager refresh_registration`. On failure, append report `registration-failed` and exit non-zero, telling the operator to run `make hub-cutover-rollback`.
- **H4. Make sure the M5 controller is running.** If the M5 controller statefulset has replicas 0, which a previous rollback leaves behind, scale it to 1.

Then load the singletons as today.

**`verify_cutover` additions**, inside the existing retry loop:
- `cicd/cluster-ubuntu-hostinger` exists on the M5 with label `k3d-manager/role=app-cluster`. Check the label with a `-l` selector on `kubectl get secret`, never with `-o jsonpath` or a go-template on the Secret.
- The Application `ubuntu-hostinger-eso` exists on the M5 and is Synced and Healthy.
- The M4 controller still has replicas 0.

### 3. Rollback moves the controller back

`rollback()` gets these steps, before the existing singleton steps:
- **R1. Stop the M5 controller.** Scale it to 0 and wait as in H1.
- **R2. Restart the M4 controller.** Scale it back to the count in `$STATE_DIR/old-argocd-controller-replicas`. If the file is missing, rollback still proceeds with the singleton steps, but warns that the M4 controller was not restored and prints the command to scale it to 1.

Rollback never deletes `cluster-ubuntu-hostinger` or any other Secret, Application or ApplicationSet, on either hub.

### 4. hub-new catches the missing OIDC ExternalSecret

- **`scripts/etc/machine/repos.list:38`:** change the roles of `shopping-cart-infra` from `worker` to `hub,worker`.
- **`bin/hub-new` preflight:** fail when `${HUB_RECOVERY_INFRA_ROOT:-$HOME/src/gitrepo/personal/shopping-carts/shopping-cart-infra}/argocd/config/argocd-secret.yaml` is missing. The fix to print is `run make machine-setup ROLE=hub, or clone shopping-cart-infra beside k3d-manager`.
- **`bin/hub-new` verify:** fail when ExternalSecret `cicd/argocd-oidc-secret` is absent, with the message `ArgoCD OIDC ExternalSecret cicd/argocd-oidc-secret is missing` and the next step `clone shopping-cart-infra, then HUB_NEW_FROM=reconcile make hub-new`.

### 5. Docs

`docs/howto/m5-hub-migration.md`:
- the cutover step now says it hands the Hostinger app cluster to the new hub's ArgoCD, and stops the old controller first;
- rollback moves the controller back;
- add an operator check after cutover: `kubectl -n cicd get applications | grep ubuntu-hostinger` shows the apps Synced.

## What NOT to do

- Do not run `make hub-cutover`, `make hub-new`, ssh, scp, kubectl, `launchctl` or `refresh_registration` for real. Tests stub them on `PATH`, record calls in order, and use `$BATS_TEST_TMPDIR` for `HOME`, `HUB_CUTOVER_STATE_DIR` and `HUB_NEW_STATE_DIR`. Each fixture first asserts that HOME is the scratch directory.
- Never delete a Secret, Application, ApplicationSet, plist or cluster, in code or tests.
- Never `cat`, print or `-o jsonpath`/go-template a Secret or the kubeconfig.
- Do not change the singleton order, the 24h report gate or the typed confirmation.
- Do not modify `scripts/lib/foundation/` or `scripts/lib/acg/`.
- Do not create a PR, commit to `main`, or skip hooks with `--no-verify`.
- Write the must_not tests first, and show them red against a temp copy with the guard removed (never mutate the tree under test).
