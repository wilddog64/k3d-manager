## Problem

The old design had the operator's own `bin/k3dm-hub-promote` evaluate and push after an `approval consume` call, with test switches in the
environment. Under O2 the evaluation and the push must run in the authority principal. This part is that code: a Python module that, given a
validated approval record, evaluates the same policy the shell promoter enforces today, then moves `deploy/hub` and records the tag in one
atomic push. It is a port, not a redesign of the policy, with the review's three-way result discipline.

Findings fixed here:

- (R1) the mover is constructed with its repo URL, API object and ssh command; production code (`main` in Part 2c) passes only constants and a curl-backed API, tests pass a local bare repository and a fake API. There is no environment or sentinel path.
- (R4) a rerun after a successful move is `ok`, proven by a remote tag naming the approval, not by local state.
- (R5) every lookup returns `ok`, `refused` or `unknown`; a failed lookup is never a refusal and never consumes; the tag name is checked before the push; a push-succeeded flag decides what a later failure may report.
- (Fable) branch selection filters by the exact regex before version sorting (a git glob is looser than the regex); an absolute git with a scrubbed environment; the 20-commit walk fixture; a non-equivalent mutant set; secrets never in argv.
- (Astra) green status and the release tip are re-checked immediately before the push, not on the first snapshot; the repository is one value used for both API and push.

## Behaviour

**A. Construction and isolation**

1. Module `scripts/lib/promote_mover.py`; installed by Part 2c as `/usr/local/libexec/k3dm-promote/promote_mover.py`. Imports: `json`, `os`, `re`, `subprocess`, `tempfile`, `time`, `urllib.parse`. It reads no environment variable (`os.environ`, `os.getenv` absent; a test greps) and no file other than the paths given.
2. `Mover(repo_url, repo_slug, api, ssh_command, workdir, clock)`. `repo_url` is whatever `git` accepts (production: the `git@github.com:...git` of `promote.conf`; tests: a path to a local bare repository). `api` is an object with `get(path) -> (status:int, body:str)`; production passes `CurlApi(token_path)`, tests pass a scripted fake. `ssh_command` becomes `GIT_SSH_COMMAND` (production: `/usr/bin/ssh -F /dev/null -i /var/db/k3dm-promote/deploy_key -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=/var/db/k3dm-promote/known_hosts -o BatchMode=yes`). `workdir` holds the bare mirror.
3. `CurlApi.get`: runs `/usr/bin/curl` with `-sS --max-time 20 -K -`; the config on stdin holds `url = "https://api.github.com<path>"`, the `Authorization: Bearer` header read from the root-only token file at call time, and `Accept: application/vnd.github+json`. No token in argv or environment. A timeout, a non-2xx status, an unparseable body or a curl failure returns `(0, "")` or the status, and callers map it to `unknown`.
4. Git is always `/usr/bin/git` with `-c core.hooksPath=/dev/null` and an environment built from scratch: `PATH=/usr/bin:/bin`, `HOME=<workdir>`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `GIT_SSH_COMMAND=<ssh_command>`; the parent's environment is not inherited. Each git call has a 60-second timeout (`unknown/deadline`). The mirror is `git init --bare` in `workdir` on first use.

**B. Three-way results**

5. Every helper returns exactly one of `("ok", data)`, `("refused", code, message)` or `("unknown", code, message)`; callers propagate. Mapping, fixed: an exit status or HTTP status that means "the thing is absent or false" is `refused` only where Behaviour C says so; every network error, timeout, 5xx, 403/429, malformed body, or git failure that is not a definite answer is `unknown`. `unknown` never changes the approval and never consumes.

**C. `move(id, sha, branch)` and its order (the contract)**

All refusals keep the approval (Part 2a B and D); only step 12's observed move consumes (the daemon calls `commit_moved`).

1. Validate `id`, a full-length lowercase hex `sha` (40 or 64) and `branch` against `^k3d-manager-v[0-9]+\.[0-9]+\.[0-9]+$` (refused `bad_input`).
2. Fetch: `git fetch --prune origin '+refs/heads/*:refs/remotes/origin/*' '+refs/tags/hub-promote/*:refs/tags/hub-promote/*'` (failure: `unknown/lookup_failed`).
3. Newest release branch: list every `refs/remotes/origin/*`, keep only names matching the regex above (done in Python, never with a git glob such as `k3d-manager-v*`, which also matches `k3d-manager-vX` and `k3d-manager-v1.45.0-evil`), sort by the integer tuple (so `v1.43.15` is newer than `v1.43.9`), take the last. `branch` not equal to it: refused `not_newest_branch`. No branch matches: refused `not_newest_branch`.
4. Old: `git ls-remote origin refs/heads/deploy/hub` (failure: `unknown`; absent: refused `deploy_moved` with the message that the first promote is the manual bootstrap in `docs/howto/hub-promote.md`).
5. Rerun and already-current (R4): when old equals `sha`, search the fetched `hub-promote/*` tags for one whose message has the lines `approval: <id>` and `new: <sha>` (full sha). Found: ok `{"outcome":"already","old":..., "new": sha, "tag": ...}` (the daemon commits it if the record is still approved, or serves it from `rerun_view` if consumed). Not found: refused `deploy_moved` ("deploy/hub is at that commit but not by this approval").
6. Spent witness: any `hub-promote/*` tag with `approval: <id>` and a `new:` other than `sha`, or the same `new` but `old` is not the current old: refused `already_spent`. This also covers local state loss (Part 2a E.11).
7. Containment, ported from `bin/k3dm-hub-promote:22` (`merged_pr_contains`) and `:39` (`uncontained_commits`): `git cherry <sha> <old>`, the `+` lines are the candidates; when any, accept only if the API says (`/repos/<slug>/commits/<old>/pulls`) a merged PR whose head sha equals `git ls-remote origin refs/pull/<n>/head`, whose merge commit exists and is an ancestor of `sha`, and whose head contains `old`. A candidate list that is not empty after that: refused `not_contained` listing at most five short shas; an API or ls-remote failure while evidence was needed: `unknown`.
8. Green walk: `git rev-list --first-parent -n 20 origin/<branch>`; for each commit in order, fetch `/repos/<slug>/commits/<c>/check-runs` (paginated) and classify like `bin/k3dm-hub-promote:93` (`classify_check_runs`): no runs is "none" (3), any run not `completed` is pending, any conclusion outside success, neutral, skipped is failed, otherwise green (0); a lookup failure is `unknown` immediately; pending, failed and none continue to the next commit. The first green is `g`. None green within 20: refused `not_green`. `sha != g`: refused `not_newest_green` naming `g`.
9. Atomic move (the stated instant): re-run `git ls-remote origin refs/heads/<branch>` and the check-runs of `sha`; the tip must equal the fetched tip and `sha` must still be green, else refused `release_moved`; any failure `unknown`. Re-run `git ls-remote origin refs/heads/deploy/hub`: not equal to old: refused `deploy_moved`.
10. Tag pre-flight (R5): `tag = hub-promote/<UTC stamp %Y%m%dT%H%M%SZ>` from the injected clock; `git ls-remote --tags origin refs/tags/<tag>` non-empty: refused `tag_exists` (approval kept, retry takes the next second); failure: `unknown`. A local tag of that name is deleted first.
11. Create the annotated tag in the mirror at `sha` with `-c user.name=k3dm-promote -c user.email=k3dm-promote@localhost` and the message `action: promote`, `old: <old>`, `new: <sha>`, `REF: <sha>`, `approval: <id>` (extra lines are tolerated by readers: `bin/k3dm-hub-promote:154` already appends `reason:`; the rollback reader takes `old:` and `new:` by `sed -n` pattern, `:228-229`, so order is irrelevant).
12. Push: `git push --atomic --force-with-lease=refs/heads/deploy/hub:<old> origin <sha>:refs/heads/deploy/hub refs/tags/<tag>`. Then observe with `git ls-remote origin refs/heads/deploy/hub refs/tags/<tag>`: branch equals `sha` and the tag exists: ok `{"outcome":"moved","old","new","tag"}` and set the push-succeeded flag. After a non-zero push: observation shows branch equal `old` and no tag is "definitely unmoved" and returns `unknown/push_unknown` (a transient or credential failure, retry is safe, the lease binds `old`); branch equal `sha` with the tag is the moved case (the push really succeeded); branch changed to something else: refused `deploy_moved`; a failed observation: `unknown/push_unknown`. After a zero push, a failed observation is `unknown/push_unknown` with the message "the push succeeded; rerun with the same approval" and never a refusal. `--atomic` is required: if the capture in Proof owed shows GitHub does not support it the worker stops and asks.

**D. The daemon glue, tested here with the real Engine**

13. `promote(engine, mover, id, sha)` in the same module (the daemon calls it): `engine.begin_promote(id, sha)` (Part 2a F.17; a consumed record goes to `rerun_view` then `witness`); the record's `branch` is passed to `mover.move`; on ok `outcome moved` or `already` it calls `engine.commit_moved(id, old, new, tag)` and returns the data; on `Refused` from the mover it calls `engine.note_refusal(id, code)` and re-raises; on `Unknown` it re-raises untouched. If `commit_moved` itself fails after a moved push, the result is `unknown/push_unknown` (the rerun finishes it through step 5). The mover never calls the engine and the engine never calls git.

## Worker definition of done

1. Every must_not has a test with its positive control and is shown red against a stub mover that returns success and ignores its arguments; the mutants below are non-equivalent (a reorder of the tag message lines is equivalent for the readers and is not a mutant): drop the `new:` line, wrong `old:`, skip the tag pre-flight, skip the second green check, consume before observing, take a plain-string branch sort, drop the `--atomic`, drop the lease.
2. Fixtures assert their target first: a temporary bare repository path, a scripted fake API object, a `FileClock` file; no network, no real HOME, no `/usr/local`.
3. The walk fixture has 21 first-parent commits, commit 21 (the oldest) is the only green one in the not-found case, and the side-parent green is distinguishable from a first-parent walk.
4. Synthesized fixtures (green check-runs, pulls rows) carry a comment saying so until proof owed 2 and 3 are captured.
5. `make lint-python` and `make test-pytest` pass.

## What NOT to do

- No daemon, socket, TOTP or approval logic here; no calls to the engine inside the mover.
- No environment reads, no test mode, no flag that skips checks.
- Do not edit `bin/k3dm-hub-promote`; the policy is ported, not moved.

## Open questions for the operator

1. **Atomic push.** Recommendation: require `git push --atomic` and stop and ask if the GitHub capture rejects it; the fallback (branch then tag, as the shell promoter does) leaves a window where the branch moved without its witness tag, which the rerun path would then refuse as `deploy_moved`.
2. **`not_newest_green` strictness.** A promote of an older green commit while a newer green exists is refused. Recommendation: keep; it is the umbrella's stated rule and shrinks what a same-user attacker could request.
