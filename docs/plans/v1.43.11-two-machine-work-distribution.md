## Problem

Today all work runs on one Mac. Dispatches write `ledger.jsonl` under that Mac's worktree root, and
the metric producers push to the hub through `127.0.0.1` port-forwards (Pushgateway `:19094`, Loki,
Prometheus, Vault `:18200`) that exist only on the hub Mac.

With the M5 as the hub and the M4 as the worker, the operator may take **either** laptop out:

- **M4 away:** it can still run Codex and tests (both need only GitHub and the model APIs), but it
  cannot reach the hub's port-forwards. Today its ledger events and metrics would be lost or would
  fail.
- **M5 away:** the hub cluster travels with it. It keeps running, and its outbound paths (Cloudflare
  tunnel, ArgoCD to Hostinger and ACG) do not depend on the home network. If the lid closes, the hub
  sleeps (memory `reference_clamshell_sleep_ignores_caffeinate`). The M4 at home loses every hub path.
- **Both on the same network:** a LAN path exists, but it is a fast path only. Nothing may depend on it.

## Design

### D1. Transport: git is the queue, the LAN is optional

**Decided 2026-10-25 (operator):** "git queue sounds good". A mesh VPN is a possible backup only, not part of this plan.
Tailscale's Personal plan was free for personal use as of Claude's knowledge; check current pricing before adopting it.

**Recommended:** every hand-off between machines goes through GitHub, the one service both laptops
reach from any network. This reuses the cloud-request pattern: a `work-queue` branch holds job,
claim and result files. No inbound port, tunnel or new public path is opened, and nothing new needs
a secret beyond each machine's own `gh` login.

**Alternative:** a private mesh VPN (e.g. Tailscale) lets the machines reach each other's
`127.0.0.1` services from anywhere. It is lower-latency, but it adds a third-party control plane and
a standing network path into the hub. That is the operator's top security concern
(`project_webhook_server_security_audit`, `project_secure_vault_remote_access`). It can be layered
on later as a fast path, without changing the queue contract.

### D2. Jobs carry their requirements; machines claim only what they can run

A job is a small JSON file on `work-queue`: id, kind, release, slug, `needs` and `created_at`.
It holds no secrets, prompts or logs.

| `needs` | Runs on | Examples |
|---|---|---|
| `offline` | either machine | Codex dispatch, `make test`, pytest, spec drafting |
| `hub` | the hub machine only | read-only kubectl, live checks, `make platform-ops`, appsets reapply |
| `acg` | one machine at a time (lease) | sandbox up, ACG e2e |
| `pin:<host>` | that machine only | anything the operator pins |

Each machine runs a `work-queue` poller (LaunchAgent, about every 60 s). The poller:

1. pulls `work-queue`;
2. picks the oldest job it can run;
3. **claims it with a git push**, writing a claim file that holds the host, `lease_expires_at` and
   a heartbeat.

GitHub rejects a non-fast-forward push, so two machines cannot claim the same job. The loser
re-pulls and moves on.

`make codex-dispatch` gains `HOST=auto|local|m4|m5|m2`. The default is `local` and behaves exactly as
today. `auto` enqueues the job.

### D2b. Resource-aware claiming (operator, 2026-10-25: "should also consider resources across two laptops. If needed maybe lighter work can go to m2")

Every job also carries a `weight`, with a default per kind:

| Weight | Examples | Budget it needs |
|---|---|---|
| `light` | doc-link checks, single BATS or pytest files, bug and plan scans, spec lint, `machine-check` | about 1 core, under 2 GB |
| `medium` | one Codex dispatch, a targeted test set | about 2 cores, 4 GB |
| `heavy` | the full `make test` run (about 15 minutes), parallel dispatches, ACG e2e, Playwright | 4+ cores, 8 GB |

Before a claim, the poller reads its own machine's state:

- free memory (`vm_stat`);
- 5-minute load per core;
- free disk;
- whether it is on battery (`pmset -g batt`);
- on the hub only, the memory the cluster is currently using.

It claims a job only if the job fits:

- **Per-host config** in `scripts/etc/machine/hosts.conf` sets:
  - `max_weight`: M5 `heavy`, M4 `heavy`, M2 `light`;
  - `max_concurrent`: M5 1, M4 2, M2 1;
  - `reserve_gb`: the memory kept free for the hub cluster on the M5 (default 12 GB) and for the
    operator's browser on the M2 (default 6 GB).
- **On battery,** a machine claims `light` jobs only. The M5 hub keeps running the cluster but stops
  taking `heavy` jobs.
- **Preference order:** a job goes to the least-loaded eligible machine.
  - The M4 is preferred for `heavy` jobs, so the hub keeps headroom.
  - The M2 takes `light` jobs only when the M5 or M4 is over its budget or away.
- **The M2 is opt-in** (`ROLE=console` plus `light-worker: true` in `hosts.conf`). It never takes
  `hub`, `acg`, `medium` or `heavy` jobs, and it never lands.
- Each poller publishes its headroom (free GB, load, battery, `max_weight`) in its heartbeat. Hub
  dashboards show per-host headroom next to per-host work. No hostname or username is included.

### D3. Leases, heartbeats and a machine that disappears

- A running job's claim heartbeats every 5 minutes. A lid close or a network drop stops the heartbeat.
- After 20 minutes without a heartbeat the job is `stale`.
- **`offline` jobs** start from a fresh worktree branch, so they may be re-claimed **once**, by
  either machine. The second attempt uses a new worktree branch name, so the two attempts never push
  to the same ref.
- **`hub` and `acg` jobs are never re-run automatically.** They become `needs-operator`, because a
  half-run live action may have changed the cluster or the sandbox.
- A machine that comes back finds its lease taken. It stops its run, keeps its worktree and logs
  locally, and marks its attempt `superseded`.

### D4. Single-writer rules stay single-writer

- **Landing** (`make codex-land`) takes a git lock ref, `refs/k3dm/locks/land-<release>`, created
  with an atomic compare-and-swap: `git push --force-with-lease=<ref>: …`, where the empty expected
  value means the ref must not exist. A plain push is not a lock, because it accepts a fast-forward
  over the holder's claim. Release and hand-off use `--force-with-lease=<ref>:<oid read>`. The claim
  commit is a fencing token that the holder re-checks before each step. Only one machine lands at a
  time, and the lock carries the same lease rules as a job claim. Job claims on the `work-queue`
  branch also push with the expected old tip, never `--force`.
- **The ACG sandbox** follows the same rule with the `acg` lease. One owner at a time, as the
  existing memory rule requires.
- Release-branch pushes happen only inside a land, never from a queued job.

### D5. Ledger and metrics store-and-forward

- Every ledger event gains `host` (`m4` or `m5`, a short alias from config; never a username or
  hostname), plus a per-host sequence number.
- Each machine keeps its own `ledger.jsonl`. When the hub's Pushgateway port-forward is not local,
  events are spooled and periodically pushed to a `work-queue` path (`ledger/<host>/<date>.jsonl`).
- On the hub, `k3dm-dispatch-metrics` merges the local ledger and the shipped per-host files,
  deduplicating on `(host, seq)`. The hub is the only producer that pushes to the Pushgateway.
- A host that has not shipped for over 24 hours shows on the agent dispatch dashboard as
  `worker silent`, not as zero work. A new `host` label lets the panels split work by machine.
- `codex.log` and run logs never leave the machine (standing rule). Only ledger events and the
  `agent_usage` numbers ship.

### D6. What each absence looks like

| Situation | Offline jobs | Hub jobs | ACG | Dashboards |
|---|---|---|---|---|
| Both home | either machine | M5 | lease holder | live |
| M4 away | M4 or M5 | M5 | lease holder | M4 data arrives when it ships |
| M5 away, lid open | either (via GitHub) | M5, from where it is | lease holder | live via the hub's own paths |
| M5 lid closed | M4 | queued, `waiting-for-hub` | M4 if leased | hub down; nothing is lost, it ships later |

### D7. The vector store: one writer on the hub, local read copies elsewhere

Operator agreed 2026-10-25 ("sounds good"). The pgvector store (`vectordb` namespace, hub only, see
`docs/guides/vector-store.md`) is reached by `kubectl exec` with the hub context. Another machine
cannot reach it reliably: the hub's Kubernetes API is local to the M5, and either laptop may be away.

- **Single writer.** Only the hub runs `make index-docs`, including Hermes's automatic re-index. All
  machines share one Gemini embeddings quota, and two indexers could prune each other's rows.
  `make index-docs` refuses on any host whose role in `hosts.conf` is not `hub`, and the queue never
  routes an index job anywhere but the hub (`needs: hub`).
- **The store stays on the hub only.** The `vectordb` ApplicationSet keeps its single-element `list`
  generator and never selects by `role` or `env`.
- **Reads on the M4 and M2 use a local copy of the embedding cache.**
  - After each successful index run, while the target is reachable on the LAN, the hub pushes
    `~/.cache/k3dm/embeddings.sqlite` to the M4 (and to the M2 if it is an opted-in `light-worker`).
    This uses the existing `make embed-cache-backup DEST=<host>:…`, which is atomic and retries. A
    failed push leaves the previous copy intact, and the hub retries on the next heartbeat that
    sees the host.
  - `make find-similar-docs` on a host without the hub's context searches that local copy: cosine
    similarity over about 1,700 × 768 vectors, in memory. The only quota used is one Gemini call to
    embed the query.
  - The copy carries the doc set it covers, the git commit it was built from and its build time.
    Results say "index as of <time>". Docs added or changed since that commit are searched with
    the TF-IDF lexical scorer, the control from the v1.40.0 evaluation, and labelled `lexical`.
  - It stays advisory: it always exits 0. A missing copy, a missing key or no network prints a
    reason and exits 0.
- **Vectors never travel through git.** The `work-queue` branch carries jobs, claims and ledger
  events only.
- **Credential:** query embedding on the M4 uses the existing resolution order
  (`docs/guides/vector-store.md`). The worker role's secret list includes `gemini-cli-api-key`,
  checked for presence only.
- **The M5 cut-over** runs `make embed-cache-restore` before its first `make index-docs`, so the
  rebuilt store costs no embeddings quota.

### Out of scope

- Moving the hub between machines (snapshot and restore, operator-run).
- Running anything but opt-in `light` jobs on the M2 console.
- Running Claude sessions on two machines against the same branch at once.

## What NOT to Do

- Do not open a port, tunnel or VPN, or rely on the LAN.
- Do not ship logs, prompts or secrets through the queue.
- Do not let a queued job land, push a release branch, or run a live action twice.
- Do not change `HOST=local` behaviour; it is the default and the fallback.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
