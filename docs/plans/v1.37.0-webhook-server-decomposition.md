# v1.37.0 — Decompose the webhook server

**Status:** QUEUED for v1.37.0. Do not implement during v1.36.0.
**Filed:** 2026-09-22
**Target:** `bin/k3dm-webhook` → `scripts/lib/webhook/`

---

## Why

`bin/k3dm-webhook` is **4,009 lines / 180KB**, with ~110 module-level functions,
19 routes and one `_Handler` class. Extraction into `scripts/lib/webhook/` was
started and stalled at 412 lines across 5 modules (`config`, `auth`, `render`,
`proc`, `make_targets`) — the easy leaves came out and the hard 90% did not.

Measured concern clusters still inside the entrypoint:

| Lines | Concern |
|---|---|
| 1233 | cluster lifecycle (`_run_cluster*`, `_run_hostinger*`, `_run_upgrade`, `_run_make_target`, …) |
| 483 | smoke-SSO client (`_smoke_*`, `_SmokeLoginFormParser`, `_SmokeNoRedirect`) |
| 450 | ask/agent invoker (`_call_gemini`, `_run_cluster_ask`, fix-mode policy) |
| 362 | Slack thread commands and formatting |
| 153 | failure analysis (`_analyze_stall`, `_analyze_failure`, `_collect_cluster_state`) |
| 149 | authz/policy (`_role_allows`, `_action_policy`, `_audit_remote_action`, `_rate_limited`) |
| 100 | metrics push |
| 50 | secret redaction |
| **2980** | **grouped total** |

Two of these have no business being in an HTTP server at all: the smoke cluster
is a **browser-emulating SSO test client** (it subclasses `HTMLParser` and walks
an OAuth authorization-code flow), and the agent cluster **invokes an AI agent
with a mutate-the-cluster "fix mode"**.

### The actual defect is adjacency, not size

`do_POST` spans lines 3515–3942 (**428 lines**). Within it:

- line **3642** — the role resolution for `/api/v1/make`
- line **3880** — the handler for `/api/v1/make` that spawns the job

The authorization decision and the privileged execution for the same route are
**238 lines apart inside one method**. Nothing is wrong with either block today;
the problem is that no reviewer can hold both in view at once, and this is the
component the operator has repeatedly identified as their top security worry
(see `docs/architecture/webhook-server.md` and the F1/F3/F2 fixes in v1.32.0).

Line count is the symptom. Reviewability of the auth→exec path is the defect.

Note the three `webhook_*.py` files are **`unittest.TestCase`, not pytest**, and

### The critical mechanical constraint

All four Python suites load the entrypoint **wholesale** via
`SourceFileLoader("k3dm_webhook", "bin/k3dm-webhook")` and then reach into
private module attributes:

```python
wh._REDACT_VALUES.clear()
wh._redact_secrets("")
```

So moving a function out of `bin/k3dm-webhook` **breaks these tests unless the
name is re-exported from the entrypoint**. Every phase must therefore either:

1. re-export the moved names in `bin/k3dm-webhook` (`from webhook.x import _y`), or
2. repoint the test file at the new module in the same commit.

**Prefer (2).** Option (1) keeps the file long and defeats the purpose; it is
acceptable only as a transitional step within a single phase, never as the end
state. A phase that lands (1) permanently has not reduced the surface.

## Extraction order

Ordered by **value if the release stops early**, not by ease and not by size.
Each phase is one commit, independently mergeable, and behaviour-neutral.

### Phase 1 — `webhook/policy.py` + explicit route dispatch (do this first)

The security payoff, and the only phase that is worth doing on its own.

- Move the 149 lines of authz/policy (`_normalize_role`, `_role_allows`,
  `_action_policy`, `_thread_command_min_role`, `_effective_make_role`,
  `_request_role`, `_request_actor`, `_audit_remote_action`, `_rate_limited`)
  into `scripts/lib/webhook/policy.py`.
- Replace the `if self.path == ...` ladder in `do_POST`/`do_GET` with a **route
  table** mapping path → `(handler, min_role, action_name)`, so each route's
  authorization requirement and its handler are declared on **one line, together**.
- `do_POST` becomes: parse, look up route, enforce `min_role`, audit, dispatch.

Acceptance: no route may reach a job-spawning call without passing through the
table's `min_role` check. Assert this structurally — a test that enumerates the
table and fails if any entry is missing `min_role`, so a future route cannot be
added without declaring one.

This is first because it is the reason for the work. If v1.37.0 runs out of
room after Phase 1, the release still delivered the thing that mattered.

### Phase 2 — `webhook/smoke.py` (483 lines)

Pure leaf, zero HTTP coupling, already pinned by 14 pytest cases. Repoint
`test_smoke_logins.py` at the new module in the same commit.

Note the overlap to resolve **later, not here**: `scripts/plugins/smoke.sh` +
`make smoke` landed in v1.36.0 as a 72-line dispatcher. It does **not** duplicate
this logic today. Converging the two is explicitly out of scope — flag it, do not
attempt it.

### Phase 3 — `webhook/agent.py` (450 lines)

`_call_gemini`, `_run_cluster_ask`, `_is_fix_request`, `_fix_mode_enabled`,
`_is_filing_request`, `_sanitize_question`, `_parse_gemini_observations`.

`_fix_mode_enabled` gates whether an AI agent may mutate the cluster. It has no
dedicated test file today. **Add `scripts/tests/bin/webhook_agent.py`** covering
the fix-mode and sanitisation decisions before or with the move — an extraction
that carries an untested security gate across a file boundary is not safe.

### Phase 4 — `webhook/lifecycle.py` + `webhook/status.py` (1233 lines)

Largest and last, because the seams from phases 1–3 make it tractable. Split
long-running orchestration (`_run_cluster`, `_run_cluster_resume`, `_run_upgrade`,
`_run_cleanup`, `_run_make_target`) from reporting (`_run_cluster_status`,
`_format_status_summary_slack`, `_run_hostinger_status`).

### Deferred, not in this release

Slack thread commands (362), failure analysis (153), metrics (100), redaction
(50). Redaction already has its own test file and is the natural Phase 5.

- No `--no-verify`. The pre-commit `_agent_audit` blocks a net decrease in

  suite. A `tail` of the log is not evidence.

## Risks

- **Silent auth regression.** The route-table rewrite is the one phase that can
  change behaviour invisibly. Mitigation: diff the effective `(path, min_role)`
  pairs before and after and assert equality as a test, not by eye.
- **`make test` gives false confidence.** It excludes all 37 Python cases. Any
  agent reporting "tests pass" from `make test` alone has not tested this file.
- **Import cycles.** `policy.py` needs `config`; `lifecycle.py` needs `proc`,
  `render`, `policy`. Keep the dependency direction one-way toward `config`.

# Phase 1b — make the route table authoritative (and retire the fail-open branch)

**Status:** SPEC — ready to implement
**Filed:** 2026-09-24
**Follows:** `b6c8a141` (Phase 1)

## Why

Phase 1 landed the tables but left their `min_role` **declarative only**. Enforcement still runs
through `_action_policy`, so Phase 1 did **not** meet its own acceptance criterion:

> no route may reach a job-spawning call without passing through the table's `min_role` check

Two consequences, both measured on `b6c8a141`:

1. **A future route added to `_POST_ROUTES` without an `_ACTION_POLICY` entry gets no
   authorization at all.** `_action_policy` returns `None`, and line ~3557 is
   `if action_policy:` — so the role check *and* the `_audit_remote_action` write are both
   skipped. The completeness test added in Phase 1 asserts the entry declares a `min_role`, but
   since that field is never read, the test guards a field that does nothing. It is false
   assurance.
2. **The table is misleading as documentation.** `/api/v1/cluster` declares `reader` while
   `up`/`down` require `admin` and `kill` requires `operator`; `/api/v1/make` declares `reader`
   while its real floor comes from `MAKE_TARGETS`. In the component the operator has repeatedly
   named as their top security worry, an authorization table that reads wrong is worse than no
   table.

Nothing is currently reachable at a lower privilege than before — the dynamic resolution still
governs, and the one path that resolves to `None` (`/api/v1/cluster` with an action outside
`kill|up|down`) is rejected by its own handler with a 400. But that is the handler re-validating,
not the authz layer working.

## The design — one effective role, one check, one audit

Do **not** convert the `None` branch to fail-closed as a separate change. Unify instead:

```
effective_min_role = strictest_of(route["min_role"], dynamic_min_role_or_None)
```

then perform exactly **one** role check and exactly **one** audit write against that value. This
retires the fail-open branch by construction rather than by a behaviour change, because a route
with no dynamic policy still has its table floor.

### Why this is behaviour-neutral

Every current route's table floor is **≤** its dynamic requirement, so `strictest_of` returns the
dynamic value wherever one exists, and the floor only ever applies where there is none. Verified
pair by pair on `b6c8a141`:

| Route | Table floor | Dynamic | Effective (unchanged) |
|---|---|---|---|
| `/api/v1/argocd-upgrade` | admin | admin | admin |
| `/api/v1/cve-remediate` | operator | operator | operator |
| `/api/v1/cluster` | reader | admin (up/down), operator (kill), **None** (other) | admin / operator / **reader** |
| `/api/v1/cluster-status` | reader | reader | reader |
| `/api/v1/diagnostics` | reader | reader | reader |
| `/api/v1/hostinger-status` | reader | reader | reader |
| `/api/v1/cluster-refresh` | operator | operator | operator |
| `/api/v1/cluster-resume` | admin | admin | admin |
| `/api/v1/cleanup-stale-sandbox` | admin | admin | admin |
| `/api/v1/make` | reader | `MAKE_TARGETS[target]`, else reader | dynamic |
| `/api/v1/analyze` | operator | operator | operator |
| `/api/v1/ask` | reader | reader | reader |

The `/api/v1/cluster` + unknown-action row is the only one whose gate changes at all, and it
changes from *no check* to *reader*. `reader` is level 1 in `_ROLE_LEVELS`, and `_request_role`
returns `admin` for a direct token and `reader` for a present-but-invalid header — so **every
caller who reaches this code already satisfies `reader`**. No response code changes. The request
still reaches the handler and still gets its 400.

GET routes are unaffected for the same reason: both declare `reader`.

**Keep the floors as they are. Do NOT "correct" `/api/v1/cluster` to `operator`.** `reader` is the
accurate floor — a reader genuinely can reach that handler and receive a 400. Raising it to
`operator` would turn that 400 into a 403, which is a real behaviour change and is out of scope.

## S1 — mark the dynamic routes so the table stops reading wrong

The misleading-documentation problem is not fixed by changing the numbers; it is fixed by saying
which routes resolve per-request. Add a flag and a resolver name:

```python
    "/api/v1/cluster": {"handler": "cluster", "min_role": "reader", "action_name": "cluster",
                        "dynamic": "_action_policy resolves per action: up/down=admin, kill=operator"},
    "/api/v1/make":    {"handler": "make", "min_role": "reader", "action_name": "make",
                        "dynamic": "_action_policy resolves from MAKE_TARGETS[target]['min_role']"},
```

`min_role` now has one documented meaning for every entry: **the floor that applies when no
dynamic policy resolves.** Say so in a comment above `_POST_ROUTES`.

## S2 — single effective-role enforcement

In `policy.py`:

```python
def strictest_role(*roles):
    """Return the highest-privilege requirement among the given roles; None values ignored."""
    present = [_normalize_role(r) for r in roles if r]
    return max(present, key=lambda r: _ROLE_LEVELS[r]) if present else _ROLE_DEFAULT


def effective_policy(route, path, body):
    """Resolve the one (action_name, min_role) pair a request must satisfy."""
    dynamic = _action_policy(path, body)
    if route is None:
        return dynamic
    min_role = strictest_role(route["min_role"], (dynamic or {}).get("min_role"))
    return {"name": (dynamic or {}).get("name") or route["action_name"], "min_role": min_role}
```

`strictest_role()` with no arguments returning `_ROLE_DEFAULT` (`admin`) is deliberate: an empty
requirement set must mean *most restrictive*, never *unchecked*. Note `_normalize_role` maps an
unrecognised string to `admin`, which is the safe direction here — do not change it.

In `bin/k3dm-webhook`'s `do_POST`, replace the `action_policy = _action_policy(...)` /
`if action_policy:` block with:

- resolve `route` first, `404` when it is `None` (keep the existing 404 position and body)
- `policy = effective_policy(route, self.path, body)`
- **unconditionally** check `_role_allows(request_role, policy["min_role"])` → 403 with the
  existing message shape on failure
- **unconditionally** `_audit_remote_action(...)` exactly **once** per request

There must be no surviving `if action_policy:` guard and no path that reaches a handler without
both a check and an audit write. Audit exactly once — a second write is a defect, because the
audit log is append-only and a duplicated line misreports operator activity.

## S3 — the one intended observable change

Requests that previously resolved to `None` were executed **with no audit record**. After this
change they are audited. That is the point, not a side effect. Response codes and bodies are
unchanged for every route. Record it in the CHANGELOG under `### Fixed`, not `### Changed`.
