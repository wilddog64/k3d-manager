## Problem

Every change to a shopping-cart service is all-or-nothing: it is on for every user from the moment
Argo syncs the image. The platform stages rollouts per cluster (`make appsets-reapply`, hub then app
clusters) but has no way to ship code dark, turn a feature on without a deploy, or turn it off again
in seconds. Nor is there any metric that says how a change behaves for the requests that saw it.

## Scope of this slice

Feature flags only, on one service. Out of scope, for later slices of the theme: Argo Rollouts
canaries and automatic rollback, a user feedback endpoint, percentage or per-user targeting, and any
automatic promotion.

## Design

### D1. flagd on every app cluster (k3d-manager)

`services/feature-flags/` (picked up by the existing `services-git` ApplicationSet, which deploys
`services/*` to every app cluster):

- Namespace `feature-flags`; a flagd `Deployment` (1 replica, small requests/limits, non-root,
  read-only root FS) and a `ClusterIP` `Service` on 8013 (gRPC evaluation) and 8014 (metrics).
- Image `ghcr.io/open-feature/flagd` pinned to an exact released tag (pick the newest release at
  implementation time that is at least two weeks old; record it in the CHANGELOG entry).
- flagd reads one file, `flags.flagd.json`, from a ConfigMap generated by kustomize
  (`configMapGenerator`, so a flag change rolls the Deployment). No flagd operator, no CRDs.
- A `NetworkPolicy` allows ingress to 8013 only from namespace `shopping-cart`, and to 8014 only
  from `monitoring`.
- A `ServiceMonitor` for 8014 with the `release` label the app-cluster Prometheus selects
  (read the selector from `scripts/etc/helm/observability/kube-prometheus-stack-acg-values.yaml`; do
  not guess it).

`flags.flagd.json` holds one flag:

```json
{
  "$schema": "https://flagd.dev/schema/v0/flags.json",
  "flags": {
    "basket-cart-summary": {
      "state": "ENABLED",
      "variants": { "on": true, "off": false },
      "defaultVariant": "off"
    }
  }
}
```

A flag change is a reviewed commit to that file; Argo syncs it. Nothing else changes a flag.

### D2. The basket flag (shopping-cart-basket)

- Add the OpenFeature Go SDK and the flagd provider (RPC mode), pinned in `go.mod`.
- Config: `FLAGD_HOST` (default `flagd.feature-flags.svc.cluster.local`), `FLAGD_PORT` (default
  `8013`), in `internal/config/config.go`. If `FLAGD_HOST` is empty, register no provider: every
  evaluation returns its default.
- `GET /api/v1/cart` (`CartHandler.GetCart`): evaluate `basket-cart-summary` (boolean, default
  `false`) per request. When `true`, add `"summary": {"itemCount": <sum of quantities>,
  "distinctItems": <number of lines>}` to the response. When `false` or on any evaluation error,
  the response is byte-for-byte what it is today.
- Metric `basket_flag_evaluations_total{flag, variant, reason}` (Prometheus counter on the existing
  `/metrics`); `variant` is `on`, `off` or `default` (the evaluation fell back), `reason` is
  OpenFeature's reason (`STATIC`, `TARGETING_MATCH`, `ERROR`, …). Request latency for `GET /cart`
  gains a `flag_variant` label on the existing histogram if there is one; otherwise add
  `basket_cart_get_duration_seconds{flag_variant}`.
- Startup never waits on flagd. A missing or unreachable flagd logs one warning and serves defaults.

`services/shopping-cart-basket/kustomization.yaml` (k3d-manager) sets `FLAGD_HOST` and `FLAGD_PORT`
on the Deployment.

### D3. Rollout-health dashboard (k3d-manager)

`scripts/etc/grafana/dashboards/rollout-health.json` (deployed to app clusters by
`grafana-dashboards-acg`), one row:

- flag evaluations per second by flag and variant;
- share of evaluations that fell back to the default (`variant="default"`), with a threshold at 1%;
- `GET /cart` p50/p95 latency and 5xx rate split by `flag_variant`;
- flagd up / restarts.

Panel descriptions say what each one answers and what a fallback means.

### D4. Flag-change record (k3d-manager)

`bin/k3dm-flag set <flag> <variant> --reason "<text>"`:

- edits `defaultVariant` in `services/feature-flags/flags.flagd.json` (refuses an unknown flag or
  variant, and a missing or empty reason);
- writes a command record on the v1.44.2 ledger (`action: flag-set`, `target: <flag>`,
  `origin: shell`, the old and new variant, the reason, and the operator as submitter);
- prints the `git commit` it suggests; it does not commit, push or touch a cluster.

`make flag-set FLAG=… VARIANT=… REASON=…` wraps it.

## Tests

basket (`go test ./...`, in-memory OpenFeature provider; no flagd, no network):

1. Flag `true`: `GET /api/v1/cart` has `summary.itemCount` = sum of quantities and `summary.distinctItems` = line count.
2. Flag `false`: the response body equals today's (golden JSON from the pre-change handler).
3. Provider returns an error: response equals today's; `basket_flag_evaluations_total{variant="default",reason="ERROR"}` increments.
4. `FLAGD_HOST` empty: no provider registered; server starts; evaluations return the default.
5. Each evaluation increments the counter with the right `flag` and `variant`.

k3d-manager:

6. `feature_flags_manifests.bats`: `kustomize build services/feature-flags` succeeds; the image tag is pinned (no `latest`, no floating tag); namespace is `feature-flags`; the NetworkPolicy admits only `shopping-cart` on 8013 and `monitoring` on 8014; the ServiceMonitor's `release` label equals the selector in the ACG Prometheus values; the flag file is valid JSON with `defaultVariant` `off`.
7. Same suite: `kustomize build services/shopping-cart-basket` sets `FLAGD_HOST` and `FLAGD_PORT`.
8. `test_k3dm_flag.py` (temp repo copy, temp ledger): `set basket-cart-summary on --reason x` changes only `defaultVariant` and writes one `flag-set` command with old `off`, new `on`, the reason.
9. Unknown flag, unknown variant, or empty reason: non-zero, file unchanged, no ledger record.
10. Dashboard JSON parses; every panel query names a series from D2 or flagd's own metrics.
