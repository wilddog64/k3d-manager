## Problem

Every change to a shopping-cart service is all-or-nothing: it is on for every user from the moment
Argo syncs the image. The platform stages rollouts per cluster (`make appsets-reapply`, hub then app
clusters) but has no way to ship code dark, turn a feature on without a deploy, or turn it off again
in seconds. Nor is there any metric that says how a change behaves for the requests that saw it.

## Scope of this slice

Feature flags only, on one service. Out of scope, for later slices of the theme: Argo Rollouts
canaries and automatic rollback, a user feedback endpoint, percentage or per-user targeting, and any
automatic promotion.

## Rollout stages

| Stage | Where flags are on | How | Gate |
|---|---|---|---|
| 1 (this plan) | ACG sandbox (`k3d-manager/provider: k3s-aws`) | the `feature-flags` ApplicationSet selects only `k3s-aws` | none: the sandbox is disposable |
| 2 (later) | Hostinger | add `k3s-hostinger` to the set's provider list, after stage 1's E3 has passed on at least one sandbox | explicit operator go (touches Hostinger) |
| 3 (out of scope) | hub | not planned; the hub runs no shopping-cart services | n/a |

Each stage is enabled by one line in the ApplicationSet selector. Stage 2 is a one-line change
with its own commit and reapply, not a new plan.

## Design

### D1. flagd on the sandbox (k3d-manager)

A new ApplicationSet, `scripts/etc/argocd/applicationsets/feature-flags.yaml`, modelled on
`observability-acg.yaml`:

- label `k3dm.k3d.io/rollout-stage: app-cluster` (the reapply refuses a set without it);
- clusters generator: `k3d-manager/role: app-cluster` and `k3d-manager/provider In [k3s-aws]`;
- one Application per cluster, `{{.name}}-feature-flags`, destination `{{.name}}`, source path
  `scripts/etc/feature-flags` at `${K3D_MANAGER_BRANCH}`; automated sync with prune and selfHeal;
  `goTemplateOptions: [missingkey=error]`.

It deliberately does **not** live under `services/`, because `services-git` deploys every
`services/*` directory to every app cluster, Hostinger included.

`scripts/etc/feature-flags/` (kustomize):

- Namespace `feature-flags`; a flagd `Deployment` (1 replica, small requests/limits, non-root,
  read-only root FS) and a `ClusterIP` `Service` on 8013 (gRPC evaluation) and 8014 (metrics).
- Image `ghcr.io/open-feature/flagd` pinned to an exact released tag (pick the newest release at
  implementation time that is at least two weeks old; record it in the CHANGELOG entry).
- flagd reads one file, `flags.flagd.json`, from a ConfigMap generated by kustomize
  (`configMapGenerator`, so a flag change rolls the Deployment). No flagd operator, no CRDs.
- A `NetworkPolicy` allows ingress to 8013 only from namespace `shopping-cart`, and to 8014 only
  from `monitoring`.
- A `ServiceMonitor` for 8014 with the `release` label the app-cluster Prometheus selects
  (read the selector from `scripts/etc/helm/observability/kube-prometheus-stack-acg-values.yaml`; do
  not guess it).
- A ConfigMap `basket-feature-flags` in namespace `shopping-cart` with `FLAGD_HOST=flagd.feature-flags.svc.cluster.local`
  and `FLAGD_PORT=8013`. Its presence is what turns flags on for basket on that cluster (D2).
- The rollout-health dashboard ConfigMap (D3), in namespace `monitoring`, so the dashboard exists
  only where flags do.

`flags.flagd.json` holds one flag:

```json
{
  "$schema": "https://flagd.dev/schema/v0/flags.json",
  "flags": {
    "basket-cart-summary": {
      "state": "ENABLED",
      "variants": { "on": true, "off": false },
      "defaultVariant": "off"
    }
  }
}
```

A flag change is a reviewed commit to that file; Argo syncs it. Nothing else changes a flag.

### D2. The basket flag (shopping-cart-basket)

- Add the OpenFeature Go SDK and the flagd provider (RPC mode), pinned in `go.mod`.
- Config: `FLAGD_HOST` (default empty), `FLAGD_PORT` (default `8013`), in
  `internal/config/config.go`. If `FLAGD_HOST` is empty, register no provider: every evaluation
  returns its default, and the metric records `variant="default"`, `reason="DISABLED"`.
- `GET /api/v1/cart` (`CartHandler.GetCart`): evaluate `basket-cart-summary` (boolean, default
  `false`) per request. When `true`, add `"summary": {"itemCount": <sum of quantities>,
  "distinctItems": <number of lines>}` to the response. When `false` or on any evaluation error,
  the response is byte-for-byte what it is today.
- Metric `basket_flag_evaluations_total{flag, variant, reason}` (Prometheus counter on the existing
  `/metrics`); `variant` is `on`, `off` or `default` (the evaluation fell back), `reason` is
  OpenFeature's reason (`STATIC`, `TARGETING_MATCH`, `ERROR`, …). Request latency for `GET /cart`
  gains a `flag_variant` label on the existing histogram if there is one; otherwise add
  `basket_cart_get_duration_seconds{flag_variant}`.
- Startup never waits on flagd. A missing or unreachable flagd logs one warning and serves defaults.

`services/shopping-cart-basket/kustomization.yaml` (k3d-manager) adds to the basket container
`envFrom: [{configMapRef: {name: basket-feature-flags, optional: true}}]`. On a cluster without the
ConfigMap (Hostinger in stage 1) the env stays empty and basket behaves exactly as today. envFrom is
read at pod start, so enabling a cluster needs one basket restart; the guide says so, and E3 includes it.

### D3. Rollout-health dashboard (k3d-manager)

`scripts/etc/feature-flags/rollout-health-dashboard-configmap.yaml` (a Grafana dashboard
ConfigMap in `monitoring`, same sidecar label as the files in `scripts/etc/grafana/dashboards/`;
deployed by the D1 set, not by `grafana-dashboards-acg`), one row:

- flag evaluations per second by flag and variant;
- share of evaluations that fell back to the default (`variant="default"`), with a threshold at 1%;
- `GET /cart` p50/p95 latency and 5xx rate split by `flag_variant`;
- flagd up / restarts.

Panel descriptions say what each one answers and what a fallback means.

### D4. Flag-change record (k3d-manager)

`bin/k3dm-flag set <flag> <variant> --reason "<text>"`:

- edits `defaultVariant` in `scripts/etc/feature-flags/flags.flagd.json` (refuses an unknown flag or
  variant, and a missing or empty reason);
- writes a command record on the v1.44.2 ledger (`action: flag-set`, `target: <flag>`,
  `origin: shell`, the old and new variant, the reason, and the operator as submitter);
- prints the `git commit` it suggests; it does not commit, push or touch a cluster.

`make flag-set FLAG=… VARIANT=… REASON=…` wraps it.

## Tests

basket (`go test ./...`, in-memory OpenFeature provider; no flagd, no network):

1. Flag `true`: `GET /api/v1/cart` has `summary.itemCount` = sum of quantities and `summary.distinctItems` = line count.
2. Flag `false`: the response body equals today's (golden JSON from the pre-change handler).
3. Provider returns an error: response equals today's; `basket_flag_evaluations_total{variant="default",reason="ERROR"}` increments.
4. `FLAGD_HOST` empty: no provider registered; server starts; the response equals today's; the counter records `variant="default"`, `reason="DISABLED"`.
5. Each evaluation increments the counter with the right `flag` and `variant`.

k3d-manager:

6. `feature_flags_manifests.bats`: the `feature-flags` ApplicationSet selects `k3d-manager/provider In [k3s-aws]` only and carries the rollout-stage label; `kustomize build scripts/etc/feature-flags` succeeds; the image tag is pinned (no `latest`, no floating tag); namespace is `feature-flags`; the NetworkPolicy admits only `shopping-cart` on 8013 and `monitoring` on 8014; the ServiceMonitor's `release` label equals the selector in the ACG Prometheus values; the flag file is valid JSON with `defaultVariant` `off`.
7. Same suite: `kustomize build services/shopping-cart-basket` adds exactly one `envFrom` on `basket-feature-flags` with `optional: true`, sets no `FLAGD_*` env directly, and changes nothing else in the rendered Deployment (diff against the pre-change render).
8. `test_k3dm_flag.py` (temp repo copy, temp ledger): `set basket-cart-summary on --reason x` changes only `defaultVariant` and writes one `flag-set` command with old `off`, new `on`, the reason.
9. Unknown flag, unknown variant, or empty reason: non-zero, file unchanged, no ledger record.
10. Dashboard JSON parses; every panel query names a series from D2 or flagd's own metrics.

## What NOT to Do

- Do NOT create a PR, commit to `main` in either repo, or skip hooks (`--no-verify`).
- Do NOT add Argo Rollouts, percentage or user targeting, a feedback endpoint, or automatic promotion.
- Do NOT use a floating image tag or an unpinned Go module.
- Do NOT add `k3s-hostinger` (or any other provider) to the feature-flags set, put flag manifests under `services/`, or deploy flagd to the hub or to namespace `default`.
- Do NOT run `kubectl`, `make up`, `make refresh` or `make appsets-reapply`, or push to the Pushgateway.
- Do NOT modify files outside the Files list.
