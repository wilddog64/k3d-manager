## Problem

`frontend.3ai-talk.org` runs on Hostinger, but the public path to it goes through the M4:
Cloudflare → cloudflared on the M4 (`scripts/etc/cloudflared/config.yml`, origin `127.0.0.2:80`) →
`kubectl port-forward svc/frontend` on the M4 (`_hostinger_write_frontend_browser_wrapper`) →
the M4's SSH tunnel to Hostinger's API server (`:6443`) → the pod. Any loss of the M4 → Hostinger
path is a public outage while every Hostinger workload is healthy. The M4's port-forward logs show
six such drops between 2026-10-12 and 2026-10-22, the longest about 10 minutes. The M4 sleeping,
rebooting or losing its ISP has the same effect.

## Fix

### F1. In-cluster cloudflared on Hostinger

New directory `scripts/etc/argocd/hostinger-edge/`:

- `namespace.yaml`: namespace `edge` (never `default`).
- `externalsecret.yaml`: `ExternalSecret` `cloudflared-credentials` in `edge`, `ClusterSecretStore`
  `vault-backend`, `refreshInterval: 1h`, key `credentials.json` from Vault KV
  `secret/cloudflared/hostinger` property `credentials_json`. `deletionPolicy: Retain`, so a Vault
  outage (Vault on Hostinger is reached through the M4's `-R 8200` tunnel) never removes the synced
  Secret.
- `configmap.yaml`: `cloudflared` config, locally managed (in git, not the Cloudflare dashboard):
  ```yaml
  tunnel: ${HOSTINGER_EDGE_TUNNEL_ID}
  credentials-file: /etc/cloudflared/creds/credentials.json
  metrics: 0.0.0.0:2000
  no-autoupdate: true
  ingress:
    - hostname: frontend.3ai-talk.org
      service: http://frontend.shopping-cart-apps.svc.cluster.local:80
    - service: http_status:404
  ```
  The tunnel ID is not a secret; commit it once the operator creates the tunnel (see Operator
  steps). Until then the ApplicationSet must not be applied.
- `deployment.yaml`: `cloudflared`, 2 replicas (two connectors, so a pod restart is not an
  outage), image `cloudflare/cloudflared:<pinned tag>` (a pinned release tag, never `latest`; Claude
  confirms the tag exists at review), args `tunnel --config /etc/cloudflared/config/config.yaml run`.
  `runAsNonRoot`, `readOnlyRootFilesystem`, all capabilities dropped,
  `automountServiceAccountToken: false`. Requests `cpu: 20m`, `memory: 64Mi`; limit
  `memory: 128Mi` and no CPU limit (see `reference_alertmanager_cpu_limit_throttles_notifications`).
  Readiness and liveness on `GET /ready` port 2000, `periodSeconds: 10`, `failureThreshold: 3`.
- `networkpolicy.yaml`: egress only to DNS, the frontend Service in `shopping-cart-apps`, and
  TCP/UDP 7844 + TCP 443 to the internet (Cloudflare edge); no ingress except port 2000 from
  `monitoring`.

No ServiceAccount permissions beyond the default; no ClusterRole.

### F2. ApplicationSet

`scripts/etc/argocd/applicationsets/hostinger-edge.yaml`, copied from
`hostinger-cve-inventory-reader.yaml`: list generator `ubuntu-hostinger`, label
`k3dm.k3d.io/rollout-stage: app-cluster`, project `platform`, destination namespace `edge`, path
`scripts/etc/argocd/hostinger-edge`, automated prune + selfHeal, `ServerSideApply=true`. Add
`hostinger-edge.yaml` to the list in `_hostinger_reapply_gitops_applicationsets`.

### F3. Stop serving the frontend from the M4 for Hostinger

- `scripts/etc/cloudflared/origins.tsv`: the `k3s-hostinger` row's origin becomes `in-cluster`.
- `_hub_recovery_render_cloudflared_config` (`scripts/lib/cloudflared_render.sh`): an `in-cluster`
  origin removes that hostname's ingress rule from the rendered M4 config. `k3d` and `k3s-aws`
  rows are unchanged.
- The M4 frontend port-forward (`frontend-browser-http`) stays: it serves local browsing at
  `127.0.0.2`, not the public hostname.

### F4. Docs

- `docs/howto/tunnel.md`: a section on the Hostinger edge: what serves `frontend.3ai-talk.org`, the
  operator steps below, and the rollback.
- `docs/guides/public-endpoint-alerts.md`: `PublicEndpointDown` for the frontend no longer implies
  the M4 path; check `kubectl --context ubuntu-hostinger -n edge get pods` first.

## Operator steps (not Luna; run in order, with Claude reading along)

1. `cloudflared tunnel create k3dm-hostinger-edge` on the M4. Give Claude the tunnel ID (not a
   secret) to commit into `configmap.yaml`.
2. Write the credentials JSON to Vault through stdin, never as an argument:
   `vault kv put secret/cloudflared/hostinger credentials_json=@-` < the credentials file. Confirm
   the Vault policy behind Hostinger's `vault-backend` can read `secret/cloudflared/hostinger`; if
   not, add the path additively (dump the live policy and diff first).
3. `make appsets-reapply` from the v1.43.8 branch (the app-cluster stage applies `hostinger-edge`),
   then confirm the two pods are Ready and `cloudflared_tunnel_ha_connections` ≥ 2 on each.
4. Cut over DNS: `cloudflared tunnel route dns --overwrite-dns k3dm-hostinger-edge
   frontend.3ai-talk.org`. Then re-render the M4 config (`make refresh` or the hub recovery path) so
   the M4 tunnel drops the hostname.

**Rollback:** `cloudflared tunnel route dns --overwrite-dns <M4 tunnel> frontend.3ai-talk.org` and
revert the `origins.tsv` row; the M4 port-forward is still running, so this is immediate.
