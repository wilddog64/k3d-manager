## Context

`bin/k3dm-cloud-request` files a request, prints its id, and with `--wait` / `--wait-final` polls the `cloud-requests` branch for
`responses/<id>.json` (then `responses/<id>.final.json` for `--wait-final`) until one shared deadline from `--timeout` (default 300 s,
`:36`; loop `:97-143`), mapping `status` to an exit code (`ok` 0, `rejected` 3, `error` 4; timeout 5). Some requests now wait up to 30
minutes for an operator decision. Meanwhile the bridge commits `responses/<id>.pending.json`:
`{"schema": 1, "id": "<id>", "action": "<action>", "status": "ok", "http_status": 202, "completed_at": "...", "body": {"status":
"approval-pending", "approval_id": "c1-0123abcd", "expires_at": "2026-11-25T21:30:00Z"}}`. The answer still arrives as
`responses/<id>.json`. The branch is public and attacker-writable, so treat the pending file as untrusted.

## Files

`bin/k3dm-cloud-request`, `scripts/tests/bin/test_cloud_request_wait.py` (new). Nothing else.

## Change

While `responses/<id>.json` is absent, read `responses/<id>.pending.json`. It counts only if it parses, `id` equals the request id,
`action` equals the requested action, `body.status == "approval-pending"`, `body.approval_id` matches `^c[0-9]+-[0-9a-f]{8}$`, and
`body.expires_at` parses with `datetime.fromisoformat` (any offset). When it counts:
- the first time, print one line to **stderr**: `awaiting operator approval (<approval_id>) until <expires_at>`;
- convert the wall-clock expiry to the loop's clock (`time.monotonic()` now + (`expires_at` epoch - `time.time()`)) and set
  `deadline = max(deadline, min(that + 120 s, wait start + 2100 s))`, so a longer `--timeout` is never shortened;
- when `responses/<id>.json` then appears, add the time spent waiting for approval to the deadline before the `--wait-final` phase, so
  the final phase keeps its full `--timeout`.
A pending file that does not count changes nothing. Stdout (the request id line, then the final JSON) and exit codes are unchanged; the
pending file is never printed to stdout.

## Tests (`scripts/tests/bin/test_cloud_request_wait.py`)

Stub `_git` and both clocks (no real git, no sleep); first assert the stubs are the ones in use. Cases: no pending file -> exit 5 at
`--timeout`; pending then final `ok` -> exit 0, one stderr line, stdout is the id line then the final JSON; pending with 20-minute expiry
and `--timeout 300` -> still waiting at 10 minutes; 3-hour expiry -> deadline capped at start + 2100 s; `--timeout 3600` with pending ->
deadline not shortened; `--wait-final` after a 10-minute approval -> final phase still gets its full timeout; pending with the wrong `id`,
wrong `action`, bad `approval_id`, or unparsable `expires_at` -> treated as absent; final `rejected` `denied by the operator` -> exit 3.
