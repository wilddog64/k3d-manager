## Context

`bin/k3dm-cloud-request --wait` (and `--wait-final`) polls the `cloud-requests` branch for `responses/<id>.json` until `--timeout`
(default 300 s, `:36`) and maps its `status` to an exit code (`ok` 0, `rejected` 3, `error` 4; timeout 5). Some requests will now wait
for an operator approval of up to 30 minutes. While waiting, the bridge commits `responses/<id>.pending.json`:
`{"schema": 1, "id": ..., "action": ..., "status": "ok", "http_status": 202, "completed_at": ..., "body": {"status":
"approval-pending", "approval_id": "c1-0123abcd", "expires_at": "2026-11-25T21:30:00Z"}}`. The final answer still arrives as
`responses/<id>.json`.

## Files

`bin/k3dm-cloud-request`, `scripts/tests/bin/test_cloud_request_wait.py` (new). Nothing else.

## Change

In the wait loop (`:110-142`), while `responses/<id>.json` is absent:
- if `responses/<id>.pending.json` exists and parses with `body.status == "approval-pending"` and a valid ISO `expires_at`: the first
  time, print one line to **stderr**: `awaiting operator approval (<approval_id>) until <expires_at>`; and move the deadline to
  `max(deadline, expires_at + 120 s)`, never beyond the wait's start + 35 minutes;
- a missing, unparsable or other-shaped pending file changes nothing (no message, deadline unchanged).
Stdout, exit codes and everything after `responses/<id>.json` appears are unchanged. The pending file is never printed to stdout.

## Tests (`scripts/tests/bin/test_cloud_request_wait.py`)

Stub `_git` and the clock (no real git, no sleep): first assert the stubs are in use. Cases: no pending file -> times out at `--timeout`
(exit 5) as before; pending then final `ok` -> exit 0, one stderr line, stdout only the final JSON; pending with `expires_at` 20 min
ahead and `--timeout 300` -> still waiting at 10 min, not timed out; pending with `expires_at` 3 h ahead -> deadline capped at 35 min;
malformed pending file -> behaves as no pending file; final `rejected` with reason `not approved before the request expired` -> exit 3.
