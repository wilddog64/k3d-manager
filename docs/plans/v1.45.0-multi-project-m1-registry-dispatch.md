## Problem (2026-11-17)

dirused task started with `--repo ../dirused --branch X` gets ledger rows under `v1.44.x`, shows up in k3d-manager's `open`

The parent plan says `--project` reads and gates the spec **in the project repo**. M1 keeps the spec in k3d-manager (same

## Change (`bin/k3dm-codex-dispatch`)

1. **Registry.** New file `scripts/etc/projects.list`, one project per line, `#` comments and blank lines ignored:
   `name|local path|github repo|release scheme|default branch`. Content:
   ```
   k3d-manager|.|wilddog64/k3d-manager|branch|main
   dirused|~/src/gitrepo/personal/dirused|wilddog64/dirused|tag|main
   ```
   `.` means this repo; a leading `~` expands to `$HOME`. `K3DM_PROJECTS_LIST` overrides the file path (tests use it).
   A helper `_dispatch_project_field <name> <field>` returns one field or fails; malformed lines (not 5 fields, name not
   `^[A-Za-z0-9._-]{1,64}$`, scheme not `branch|tag`) make it fail with the line number.
2. **`start --project NAME`.** Unknown name → error naming the known projects.
   - `--project k3d-manager`, or no `--project`: exactly today's behaviour; no `project` file, no `project` ledger key.
   - Any other project: requires `--branch` (same main/master refusal); the task repo is the registry path. If `--repo` is
     also given and resolves to a different toplevel → error. All existing `--repo` checks run unchanged on the registry path.
   - **Version** for scheme `tag`: `--version vX.Y.Z` if given (new start option, validated `^v[0-9]+\.[0-9]+\.[0-9]+$`);
     otherwise the highest `v*` tag on the project's origin (`git ls-remote --tags --refs origin 'v*'`, `sort -V`) with the
     patch number plus one (`v0.0.4` → `v0.0.5`); no tag → `v0.0.1`. `--version` without `--project` (or with
     `k3d-manager`) → error. Task branch, worktree and run dir use this version: `task/v0.0.5/<slug>`,
     `$root/v0.0.5/<slug>`.
   - Write `$run/project` (the name). Spec gates (tracked, unchanged, pushed, spec-intent, `## Files`) are unchanged and still
     run against k3d-manager.
3. **Ledger.** In `_dispatch_ledger_event`, when `$_dispatch_worktree_root/$version/$slug.run/project` exists and is not
   `k3d-manager`, add `project:<name>` to the event (same pattern as `repo-name`). k3d-manager events stay byte-identical
   (no `project` key). Readers treat a missing `project` as `k3d-manager`.
4. **Find an existing task's version.** New helper `_dispatch_resolve_version <slug>`: look for
   `$root/v*/<slug>.run/project` whose content is not `k3d-manager`. Exactly one → that version. More than one → error
   `slug <slug> exists in several projects/versions; pass --version`. None → today's rule (current release branch).
   Use it in verify, land, handoff, resume and abandon (abandon only when `--version` is absent). Where a subcommand has no
   `--version` option, add one to verify, land, handoff and resume (validated as above) that bypasses the lookup.
5. **`status`.** After the current loop (unchanged), also list every task dir whose `.run/project` exists and is not
   `k3d-manager`, in any version dir, with the same block plus a `project: <name>` line after `repo:`. Skip ones already
   printed. Output for k3d-manager tasks is byte-identical to today.
6. **`open`.** Add `--project NAME` (filter; a row without `project` is `k3d-manager`) and `--count`.
   - Rows of other projects get ` [<name>]` appended; k3d-manager rows unchanged.
   - `--count` prints one line per project with open tasks, then a total line:
     `<project> <n>/3` … `all <n>/<ceiling>`. Tasks whose start event has `role == "review"` are not counted (but are still
     listed without `--count`). Ceiling: `K3DM_DISPATCH_WIP_GLOBAL`, default 6. Exit 0. No enforcement in `start` (the WIP
     rule stays a process rule; P0/P1 may exceed).
7. **Usage text.** Add `--project`, `--version` and `open --project/--count` to `_dispatch_usage`.

   branch `task/v0.0.5/<slug>`, run dir under `v0.0.5`, `$run/project` is `dirused`, ledger start row has
   `version == "v0.0.5"` and `project == "dirused"`; `--version v0.1.0` gives `v0.1.0`.
3. `project P3: k3d-manager start is unchanged` — no `--project`, and `--project k3d-manager` → version `v1.44.2`, no
   `project` file, ledger row has no `project` key; `--version` without a non-k3d-manager project exits 2.
4. `project P4: land, abandon and resume find a dirused task from a k3d-manager release branch` — with a dirused task under
   `v0.0.5` and HEAD on `k3d-manager-v1.44.2`, `abandon --slug <slug> --reason x --yes` and `land` (stubbed test command)

5. `project P5: same slug in two versions asks for --version` — tasks `s` under `v0.0.5` (dirused) and `v0.0.6` (dirused) →
   `land --slug s` exits 2 with `pass --version`; `--version v0.0.6` picks that one.
6. `project P6: status lists dirused tasks; k3d-manager status output is unchanged` — capture `status` with only a
   k3d-manager task, add a dirused task, capture again: the first capture is a prefix-identical block of the second, and the

7. `project P7: open filters and tags rows; counts per project without review children` — one k3d-manager task, two dirused
   tasks, one dirused `--role review` child → `open` prints the k3d-manager row exactly as before and dirused rows ending
   ` [dirused]`; `open --project k3d-manager` prints only the k3d row; `open --count` prints `k3d-manager 1/3`,
