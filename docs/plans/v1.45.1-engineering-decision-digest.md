**Approval:** explicit 2026-10-11 "sounds good. go ahead for that"; spec-level approval added at the operator's request ("is it possible to track approval in the spec?")
**Branch:** `k3d-manager-v1.45.1` (cut from `main` after v1.45.0 merges; never `main`)
**Status:** PROPOSED — operator approved the scope 2026-10-11
**Milestone:** v1.45.1 (patch), plan 2 of 5
**Depends on:** nothing in v1.45.1; reads the dispatch ledger from v1.42.x
**Implementer:** Codex · **Verifier:** Claude

## Problem

The operator wants one view that answers:

1. What did I request recently?
2. Which requests became specifications?
3. What did Claude and Codex complete?
4. What changed without my explicit approval?
5. What decisions still require my attention?

Today the answers are scattered or missing:

| Question | Where it lives today | Why that is not enough |
|---|---|---|
| 1 | memory-bank and roadmap prose ("operator, 2026-10-11"), bug-doc Symptom quotes | free text, no consistent field |
| 2 | `docs/plans/`, `docs/bugs/` | nothing links a doc back to the request |
| 3 | git log (`Co-Authored-By`), the dispatch ledger | a bare `codex exec` writes no ledger event |
| 4 | **nowhere** | approvals are given in chat and never recorded |
| 5 | memory-bank prose ("awaiting operator decision", "undecided") | not structured, so nothing can list them |

Question 4 is the one that matters most and the one nothing can answer. The fix records approval
**in the spec** (a header every plan and bug doc carries), lets a commit point at the approved spec
instead of restating approval, and derives the digest from git. No new store: git is the record,
so the digest can be rebuilt for any ref, and Grafana can chart specs by approval state.

## Definitions (the contract every item uses)

**Spec approval header** — every `docs/plans/*.md` and `docs/bugs/*.md` added after this lands
carries, within its first 15 lines, exactly one `**Approval:**` line:

| value | meaning |
|---|---|
| `explicit YYYY-MM-DD "<quote>"` | the operator approved this spec; the quote is the operator's words (1–200 chars, no `"`/newline inside); free text after the closing quote is ignored |
| `standing <rule-id>` | written under a standing rule (e.g. `bug-filing`), not individually approved |
| `pending` | written by an agent and waiting for the operator; counts as an open decision |

**Tracking starts at v1.43.2** (operator, 2026-10-11: "we can start that with next release"). The
collector's `TRACKING_FROM = "v1.43.2"`: specs whose release sorts before it are left out of
`specs`, the spec metrics and the chart entirely (not reported as `unrecorded`), and agent commits
older than the first commit on a `k3d-manager-v1.43.2` branch are left out of
`without_explicit_approval`. From v1.43.2 on, headers are written by hand until this hook lands, so
`unrecorded` inside the tracked range means a real gap.

Moving a spec from `pending` to `explicit` is a one-line edit made when the operator approves, with
the operator's words as the quote. Tracked docs (v1.43.2 and later) without a header are
reported as `unrecorded`; the digest never guesses (no parsing of "operator approved" out of `**Status:**`).

**Agent commit** — a commit whose message has a `Co-Authored-By:` trailer naming `Claude` or
`Codex` (case-insensitive), or whose author email is `noreply@anthropic.com`.

**`Approval:` trailer** — required on every agent commit made after this lands. Exactly one of:

| value | meaning |
|---|---|
| `explicit YYYY-MM-DD` | the operator asked for, or approved, this change; the date is when |
| `spec <path>` | implements that plan/bug doc; valid only if the doc at `HEAD` (or staged in this commit, see item 2) has `**Approval:** explicit` or `standing` — a `pending` spec does not approve its commits |
| `standing <rule-id>` | done under a standing rule listed in `docs/decisions/standing-approvals.md` |
| `none` | the agent acted on its own judgment; the digest lists it under question 4 |

**`Requested-by:` trailer / header** — `operator YYYY-MM-DD "<quote>"`; quote 1–200 characters, no
`"` or newline inside. As a commit trailer it may repeat. As a doc header it is the line
`**Requested-by:** operator YYYY-MM-DD "<quote>"` (free text after the closing quote is allowed and
ignored), at most one per doc, within the first 15 lines.

**Decision line** — anywhere in `docs/bugs/*.md`, `docs/plans/*.md`, `memory-bank/activeContext.md`:

- open: `**Decision needed:** <question> (asked YYYY-MM-DD)`
- closed: the same line rewritten as `**Decided:** YYYY-MM-DD <answer>`

`<question>` is 1–160 characters with no `"`, `\` or newline. A decision is identified by
`(path, question)`; it is open while an open line with that question exists at the ref.

**Window** — `--days N` (default 7, 1–90), measured back from the ref's commit time for commits and
from now for ledger events.

## Fix

### 1. Standing-approval registry: `docs/decisions/standing-approvals.md` (new)

A table `| id | rule | source |`. Seed it with the rules the operator has already granted, each
pointing at the line that grants it:

| id | rule | source |
|---|---|---|
| `feature-branch-commit` | commit and push to a `k3d-manager-v*` feature branch | operator standing instruction (memory-bank) |
| `memory-bank-update` | update `memory-bank/` after every completed action | `CLAUDE.md` Claude Session Rules |
| `bug-filing` | file a bug doc for a defect found in the work | `CLAUDE.md` Docs Conventions |
| `release-split` | split a growing release into a patch release | `CLAUDE.md` release scope limit |
| `codex-dispatch` | dispatch a written spec to Codex | memory: specs go to Codex by default |

Ids match `^[a-z0-9-]{1,40}$`. Only the operator adds a row; the `commit-msg` hook below refuses a
`standing` id that is not in the table **at the commit being made**, so an agent cannot add a row
and use it in the same commit (the hook reads the registry from `HEAD`, not the index).

### 2. `.githooks/commit-msg` (new; `core.hooksPath` is `.githooks`)

- Agent commit with no `Approval:` trailer → refuse with one line naming the three forms.
- `Approval:` malformed, a date that is not a real date, or `standing <id>` not in `HEAD`'s
  registry → refuse.
- `Approval: spec <path>`: the doc must exist at `HEAD` or in the index, and its `**Approval:**` must
  be `explicit` or `standing` **at `HEAD`**. A commit that itself flips the doc from `pending` to
  `explicit` may not use `spec <path>` for that same doc; it uses `explicit <date>` (so an agent
  cannot approve a spec and ride the approval in one commit).
- A malformed `Requested-by:` → refuse.
- Non-agent commits: `Approval:` is optional but validated if present.
- Merge commits and `fixup!`/`squash!` commits are skipped.
- `set -euo pipefail`; parsing with `git interpret-trailers --parse`, so trailers must be in the
  final trailer block, which is where `Co-Authored-By` already sits.

### 3. `.githooks/pre-commit`

For each staged `docs/bugs/*.md` or `docs/plans/*.md`:

- **added**: must carry one well-formed `**Approval:**` line (same style as the Priority check);
- **added or modified**: `**Approval:**`, `**Requested-by:**`, `**Decision needed:**` and
  `**Decided:**` lines, where present, must be well formed. Legacy docs without them stay valid.

### 4. Collector: `scripts/decision-digest.py` (new; Python, stdlib only)

`decision-digest.py [--ref REF] [--days N] [--json|--markdown|--metrics] [--ledger PATH]`

Reads only git (`git log`, `git show <ref>:<path>`, `git ls-tree`) at `REF` (default `HEAD`) and
the dispatch ledger (default `K3DM_WORKTREE_ROOT/ledger.jsonl`, missing = empty). It never runs a
model and never reads anything outside the repo and the ledger.

Output object (`--json`), each list newest first:

- `requested`: one entry per distinct `(date, quote)` from commit `Requested-by:` trailers in the
  window and doc `**Requested-by:**` headers with a date in the window: `date`, `quote`, `source`
  (commit sha or doc path).
- `became_specs`: docs whose header has `Requested-by` in the window: `path`, `kind`
  (`plan`/`bug`), `status` (the doc's `**Status:**` text up to the first ` — `), `date`.
- `completed`: agent commits in the window (`sha`, `subject`, `agent`: `claude`/`codex`/`both`,
  `approval`) and ledger `land` events in the window (`slug`, `version`, `agent: codex`).
- `without_explicit_approval`: agent commits in the window whose approval is `none` (`reason:
  none`) or that have no `Approval:` trailer (`reason: unrecorded`; only commits older than this
  feature's landing can be unrecorded once the hook is in). `standing` commits are **not** here;
  they are counted separately under `standing` by rule id.
- `standing`: `{rule_id: count}` for the window.
- `specs`: every plan and bug doc at `REF` (not windowed): `path`, `kind`, `release` (the
  `vX.Y.Z` prefix of a plan's file name, else the doc's `**Branch:**` version, else `none`),
  `approval` (`explicit`/`standing`/`pending`/`unrecorded`), `approved` date when explicit,
  `status`. Agent commits whose `Approval:` is `spec <path>` are reported under the spec's approval
  kind in `completed`.
- `decisions_open`: every open decision at `REF` regardless of window: `path`, `question`,
  `asked`, `days_open`; oldest first. A spec whose approval is `pending` is also an open decision,
  question `Approve <path>?`, asked = the date of the commit that added the header (from
  `git log --diff-filter=A` on the path, or the first commit that contains `pending`).
- `generated`: ref sha, window days, timestamp.

`--markdown` prints five headed sections in the operator's question order, each with a count and at
most 20 rows plus "… and N more". Empty sections say "none".

`--metrics` prints Prometheus text:

- `k3dm_decision_digest_count{section,window="7d"}` for `requested`, `became_specs`, `completed`,
  `without_explicit_approval`, `decisions_open`; and
  `k3dm_decision_standing_count{rule,window="7d"}`.
- `k3dm_decision_open_info{question,doc,asked} <days_open>`, at most 50 (oldest first), with
  `k3dm_decision_open_truncated` 0/1. `question` and `doc` are the validated strings above; a
  decision that fails validation is skipped and counted in `k3dm_decision_open_skipped`.
- `k3dm_decision_unapproved_info{sha,subject,reason} 1`, at most 50 (newest first), `subject` cut
  to 100 characters with `"`, `\` and newlines removed; `k3dm_decision_unapproved_truncated` 0/1.
- `k3dm_decision_spec_count{release,kind,approval}` — number of specs per release, kind and approval
  state (all states always emitted, zero included, for every release that has a spec).
- `k3dm_decision_spec_info{doc,release,kind,approval,approved} 1`, at most 200 (pending first, then
  newest release first), `k3dm_decision_spec_truncated` 0/1. `doc` is the file stem, validated
  `^[A-Za-z0-9._-]{1,120}$`; failures counted in `k3dm_decision_spec_skipped`.
- `k3dm_decision_digest_timestamp_seconds`.

### 5. Publish: `bin/k3dm-vectordb-metrics`

Next to the bug groups, run `decision-digest.py --metrics --ref <same ref as bug-tally>` and PUT the
text to group `k3dm-decision-digest` with the existing `_push_bug_group(job, payload, method="PUT")`
(PUT so a closed decision disappears). A collector failure logs one line and does not stop the bug
push.

### 6. Dashboard: `scripts/etc/argocd/platform-ops/grafana-dashboard-decision-digest.yaml` (new)

Same ConfigMap shape and labels as `grafana-dashboard-agent-dispatch.yaml`; `uid`
`k3dm-decision-digest`, title `k3dm Decision Digest`.

- Row 1: five stats, one per question, from `k3dm_decision_digest_count{section=...}`; "Without
  explicit approval" red above 0, "Decisions waiting" yellow above 0.
- Row 2: table "Decisions waiting on you" from `k3dm_decision_open_info` (Question, Doc, Asked,
  Days open), sorted by Days open descending.
- Row 3: table "Changed without explicit approval" from `k3dm_decision_unapproved_info` (Commit,
  Subject, Reason), and a bar gauge "Done under standing rules" from `k3dm_decision_standing_count`.
- Row 4: "Spec approval by release" — a stacked bar chart of
  `sum by (release, approval) (k3dm_decision_spec_count)` for the current release and the five
  before it (explicit green, standing blue, pending yellow, unrecorded grey); and a table "Specs
  awaiting approval" from `k3dm_decision_spec_info{approval="pending"}` (Doc linked to the file on
  the release branch, Release, Kind).
- Export age stat: `time() - k3dm_decision_digest_timestamp_seconds`, yellow above 1 day.
- Every description states its limit (e.g. "requests given in chat but never recorded in a commit
  or doc header are not counted").

### 7. `/ask-docs` fast path: `scripts/lib/webhook/decision_digest.py` (new) + `ask_docs.py`

Like `bug_count.match`: `decision_digest.match(question)` returns true for "digest", "what did I
(request|ask for)", "what needs my (attention|decision)", "what (changed|was done) without (my)?
approval". `ask_docs.answer` checks it right after `bug_count.match`; on a match it runs the
collector with `--markdown --days 7` at the webhook's checked-out ref and replies with that text,
no model and no similarity search. A collector error replies with one line and the fallback search
does not run (a wrong digest is worse than none).

## Tests

All tests build a throwaway git repo in a temp dir; none touches this repo's history, the real
ledger, the network or the hub Pushgateway.

**`commit_msg_hook.bats`**

0. `Approval: spec docs/plans/x.md` → accepted when x.md at `HEAD` is `explicit` or `standing`;
   refused when `pending`, unrecorded or missing; refused when this same commit flips x.md from
   `pending` to `explicit`.
1. Agent commit without `Approval:` → refused; with each of the three valid forms → accepted.
2. `Approval: explicit 2026-02-30` → refused (not a real date).
3. `Approval: standing release-split` with the id in `HEAD`'s registry → accepted; with the id only
   in the staged registry → refused.
4. Non-agent commit without `Approval:` → accepted; with a malformed one → refused.
5. `Requested-by: operator 2026-10-11 "a "b" c"` → refused.
6. Merge and `fixup!` commits → skipped.

**`test_decision_digest.py`**

1. A fixture repo with: one `explicit`, one `standing bug-filing`, one `none`, one agent commit with
   no trailer, one operator commit; a plan with `**Requested-by:**`; two decisions, one closed. Assert
   every section's contents and counts exactly, `standing == {"bug-filing": 1}`, and that the
   `explicit` and `standing` commits are absent from `without_explicit_approval`.
2. Window: a commit 8 days old is excluded at `--days 7`, included at `--days 8`; an open decision
   asked 30 days ago is listed regardless of window.
3. A closed decision (`**Decided:**`) is not listed; reopening it (open line again) lists it.
4. Ledger `land` events become `completed` rows with `agent: codex`; a missing ledger is empty, not
   an error.
5. `--metrics`: 51 open decisions → 50 `k3dm_decision_open_info` lines and truncated 1; a question
   containing `"` is skipped and counted; no commit subject in the output contains `"` or `\`.
6. `--ref` reads docs at that ref, not the working tree (an uncommitted decision is not listed).

7. Specs: one plan each `explicit`, `standing`, `pending`, one tracked plan with no header, and one
   `v1.43.1-` plan with no header → `specs` approval values exactly
   `explicit/standing/pending/unrecorded` and the v1.43.1 plan absent; the `pending` one is also in
   `decisions_open`; `k3dm_decision_spec_count` emits zero rows for missing states.
8. `pre-commit`: an added plan without `**Approval:**` is refused; a modified legacy plan without it
   is accepted.

**`decision_digest_dashboard.bats`**: valid ConfigMap JSON; every queried metric appears in
`scripts/decision-digest.py`; panels do not overlap.

**ask-docs**: "what needs my attention" → digest reply, model and retrieval stubs never called;
collector error → one-line reply, retrieval never called; "how many P1 bugs" still goes to
`bug_count`.

**Mutations** (each must turn a test red): let a `pending` spec approve a `spec <path>` commit; let a
commit flip a spec to `explicit` and cite it in the same commit; accept a missing `Approval:` on an
agent commit; read the
registry from the index instead of `HEAD`; count `standing` commits as unapproved; drop the window
filter for decisions (would hide old ones); fall back to similarity search on a collector error.

## Proof it works

1. On the release branch, `make decision-digest DAYS=7` lists this spec under "became
   specifications" with its Requested-by quote, and the commits since the hook landed show their
   approval kind.
2. This spec's own header is `explicit`, so the "Spec approval by release" chart shows v1.45.1 with
   at least one explicit spec, and no release before v1.43.2 appears.
3. After `make appsets-reapply` and one `k3dm-vectordb-metrics` run, the "k3dm Decision Digest"
   dashboard shows the five counts and the open-decision table matches `make decision-digest`.
4. `/ask-docs what needs my attention` in Slack returns the same five sections.

## Known limits

- A request made in chat that never reaches a commit trailer or a doc header is not counted.
  The CLAUDE.md bullet is what closes that gap; nothing can recover it after the fact.
- Releases before v1.43.2 are not tracked at all. No backfill: inventing approvals after the fact would be the thing the digest is
  meant to catch.
- "Explicit" is the agent's own statement. The digest makes the claim visible and auditable against
  the date; it cannot prove the operator said it.

## What NOT to Do

- Do NOT read Claude or Codex session transcripts; they hold credentials-adjacent text and are not
  the record.
- Do NOT call a model anywhere in the collector or the fast path.
- Do NOT let an agent add a registry row and rely on it in the same commit.
- Do NOT backfill `Approval:` onto past commits (no history rewrite).
- Do NOT create a PR, skip hooks (`--no-verify`) or commit to `main`.
- Do NOT push to the hub Pushgateway from a test.
