# v1.40.0 — Cloud-bridge e2e dispatch (scoped runner role)

## What the operator asked for

Expose `make e2e-test`, `make e2e-remote` and `make test` through the cloud bridge so a
cloud session can run them.

## Findings that reshape the request

Read before accepting the request as stated. Three of the premises do not hold.

**1. `make e2e-test` does not exist.** The Makefile's e2e targets are `e2e` (local hub),
`e2e-sandbox` (Tier 2, live ACG), `e2e-remote` (Tier 1, remote runner), `e2e-replay` and
`e2e-runner-health`. The intent is almost certainly `e2e-remote`; `e2e` and `e2e-sandbox`
are the other plausible readings and they differ enormously in blast radius.

**2. `make test` is not in `MAKE_TARGETS` at all**, so it is not exposed to the webhook in
any tier, let alone the bridge. Exposing it means widening the *webhook's* surface first,
not just the bridge allowlist.

More importantly it buys close to nothing. `make test` is `./scripts/k3d-manager test all`
— pure-logic BATS, no cluster. **A cloud session can already run `bats` in its own
sandbox.** Routing it through the bridge spends real security budget to obtain a capability
the session already has, and adds a 15-minute synchronous job to a channel whose whole
value is fast turnaround. Recommendation: **do not expose `make test` or `make test-bin`.**
`test-pytest` and `test-python-unit` are already reader-tier and already reachable; that is
the right precedent and it is already satisfied.

> **Superseded 2026-09-26** by `v1.40.0-cloud-bridge-test-targets.md`: the operator decided the
> offline `test*` family *is* exposed, at reader tier, because only the macOS host exercises the
> BSD userland the tool ships on. That spec owns `make test` / `test-bin`. This spec no longer
> asserts, documents or forbids anything about them — it is scoped to `e2e-remote` alone.

**3. There is no operator credential.** `_resolve_token_role` (`scripts/lib/webhook/auth.py:63`)
compares the presented bearer against exactly two secrets — admin and reader — and returns
`None` otherwise. `e2e-remote`, `e2e-sandbox` and `e2e-replay` are all `min_role: operator`
(`scripts/lib/webhook/make_targets.py:24-26`). The bridge presents the reader token, so the
webhook refuses them today at the authorization layer, independently of the allowlist.

**This is the load-bearing finding.** There is no middle credential to reach for. The only
existing token that clears `operator` is the **admin** token — and handing the bridge admin
would make a branch-driven channel authoritative for `fix-delete-pod`, `fix-force-sync`,
`e2e-runner-unlock`, `cluster-resume`, `cleanup-stale-sandbox` and `argocd-upgrade`. That is
not a narrow widening; it is the whole surface. It is also the opposite of the standing rule
that the admin token stays out of any channel a third party can influence.

## Why the injection surface matters here specifically

The bridge's safety today rests on two *independent* controls:

1. `ACTION_ALLOWLIST` maps action → target **server-side**; nothing on the branch ever
   reaches the `target` field, so branch content never becomes a command.
2. The webhook independently refuses anything above `reader` for the presented token.

Control 1 is preserved by any allowlist addition and is not at risk. Control 2 is what
upgrading the credential destroys. Losing it means the bridge's own allowlist becomes the
*sole* control over a channel whose input derives from PR titles, issue bodies and review
comments — content anyone who can open a PR can influence. A bug in one file would then be
sufficient, where today it is not.

So the design constraint is: **add the capability without collapsing control 2.**

## Approach — a third token bound to a new `cloud-runner` role

Introduce a role that sits beside the existing ladder rather than inside it, granting
exactly an enumerated set of dispatch targets and nothing else.

- New secret `k3dm-webhook-token-cloud-runner`, read from env
  `K3DM_WEBHOOK_TOKEN_CLOUD_RUNNER` then Keychain **only** — no `TOKEN_FILE` fallback, matching
  the reader token's rule.
- `_resolve_token_role` gains a third `compare_digest` arm returning `"cloud-runner"`.
- `cloud-runner` is **not** a rank in `_ROLE_LEVELS`. Ranking it would make it transitively
  grant every target at or below its level, which is exactly the collapse this design avoids.
  It is an explicit capability set: a target is permitted iff it appears in
  `CLOUD_RUNNER_TARGETS`. Everything else fails closed, including reader-tier targets not on
  the list.
- `CLOUD_RUNNER_TARGETS` for this release: **`e2e-remote` only.**

`e2e-sandbox` is excluded: it drives the live ACG sandbox, whose session lifetime is 4h and
whose access is governed by the one-agent-per-sandbox rule. It is not a fit for unattended
dispatch and would need its own decision.

### Runner contention is a real blocker, not a footnote

`e2e-runner-unlock` exists as an **admin** target whose stated purpose is to clear a stale
remote-runner lock. That tells us the runner is a singleton with a lock and that concurrent
dispatch is an already-observed failure mode. The standing rule is one agent per live runner.

A cloud session dispatching `e2e-remote` unattended can therefore collide with the operator's
own run, and the recovery for that collision is an admin-tier unlock — i.e. the failure costs
more than the feature saves. So:

The refusal already exists and is the right place for it. `e2e_runner_dispatch`
(`scripts/plugins/e2e_remote.sh`) claims the runner lock with an atomic remote `mkdir` in
`_e2e_remote_lock_acquire` and, if the lock is held, fails with
`runner <name> is busy (lock held); not dispatching, no local fallback`. So:

- The bridge must **not** add its own check-then-dispatch. A separate "is the lock held?" probe
  followed by a dispatch is a time-of-check/time-of-use race — the lock can be taken between the
  two — and it would need the bridge to reach the runner over SSH, which it has no business
  doing. The dispatcher's atomic acquire is the single control.
- The refusal reaches the session through the normal async path: the dispatch returns 202 and a
  job id, and `job-status` on that job reports `failed` with the busy message in its output.
- **Name the holder in that message.** The lock directory already records it
  (`${E2E_M2_LOCK}/meta` holds `owner=<host> pid=<pid> ts=<epoch>`), but the refusal does not
  print it. Extend the busy branch to read and print `meta`, so a session can tell the operator
  whose run it collided with.
- Nobody on this path waits for, or clears, the lock under any circumstance.

The lock spans the whole run, not one bridge tick, so it also provides single-flight: a second
dispatch while a run is in progress — in the same tick or twenty ticks later — is refused by the
same acquire. A per-tick counter in the bridge would add nothing and would miss the cross-tick
case.

### Async, not synchronous

`e2e-remote` has `timeout: 3600`. That does not touch the bridge's limits: `/api/v1/make`
answers HTTP 202 with a job id before the job runs (the `make` handler in `bin/k3dm-webhook`),
so the bridge's HTTP call returns in seconds. `HTTP_TIMEOUT` bounds only that call and
`REQUEST_TTL_SECONDS` only how long a request may wait on the branch for pickup; neither needs
to change. The session polls the existing `job-status` action with the returned job id.

This is also why **the artifacts spec is a prerequisite, not a sibling.** Dispatching a
3600-second run whose only readback is the last 2000 bytes of output reproduces the exact
limitation that motivated it. Land `v1.40.0-cloud-request-artifacts.md` first.

## Milestones

**M1 — the token and the role.** Add `_get_cloud_runner_token` and the third
`_resolve_token_role` arm. The operator provisions the secret; **no agent creates, reads,
echoes, logs or commits its value.**

**M2 — capability set, not a rank.** Add `CLOUD_RUNNER_TARGETS = {"e2e-remote"}` and enforce
it in `_action_policy`/authorization as a membership test. Assert in code and in a gate that
`cloud-runner` is absent from `_ROLE_LEVELS`.

**M3 — bridge action.** Add `"make-e2e-remote": ("POST", "/api/v1/make", {"RUNNER": RUNNER_RE}, "e2e-remote")`
and have the bridge present the cloud-runner token for it and the reader token for everything
else. `RUNNER_RE` mirrors the webhook's own `RUNNER` pattern — do not loosen it.

**M4 — lock refusal names the holder.** No bridge-side lock check. In the busy branch of
`e2e_runner_dispatch` (`scripts/plugins/e2e_remote.sh`), read `${E2E_M2_LOCK}/meta` and include
it in the refusal message. Never clear the lock.

**M5 — gates.**
1. `cloud-runner` presenting a non-`CLOUD_RUNNER_TARGETS` target is refused — including a
   *reader-tier* target, proving the set is not a rank.
2. The reader token is still refused for `e2e-remote`.
3. The admin token is never read by the bridge on any path.
4. With the lock held (stubbed SSH, no real runner), `e2e_runner_dispatch` fails with the busy
   message, the message contains the holder's `owner=` token, and the lock is still held
   afterwards.
5. The bridge contains no runner-lock probe and no SSH call — a second dispatch while a run is
   in progress is refused by the dispatcher's acquire, not by bridge logic.
6. Every gate above shown capable of failing: mutate, observe red, restore, assert byte
   equality.

**M6 — docs.** `docs/howto/cloud-session-requests.md`: the new action, the lock refusal and
what to do about it (ask the operator — never unlock), and how the refusal arrives (a
`failed` job naming the holder, read via `job-status`). Update the action count. Add the `cloud-runner` token to wherever the reader token's provisioning is
documented.

## What NOT to Do

- Do NOT create a PR, merge, commit to `main`, or use `--no-verify`.
- Do NOT give the bridge the admin token, or add an admin-tier target to any allowlist.
- Do NOT add `cloud-runner` to `_ROLE_LEVELS`.
- Do NOT expose `e2e-sandbox`, `e2e-replay` or `e2e-runner-unlock` through the bridge.
- Do NOT raise `HTTP_TIMEOUT` or `REQUEST_TTL_SECONDS` to accommodate a 3600s run.
- Do NOT clear, override or probe-then-clear the remote-runner lock.
- Do NOT create, read, echo, log or commit any token value, in code, tests, fixtures, commit
  messages or reports.
