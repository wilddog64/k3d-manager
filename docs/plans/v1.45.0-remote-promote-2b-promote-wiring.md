## Problem

With the approval store, evaluation and push moved into the root authority (Parts 2a, 2c, 2d), the user-side scripts only have to hand the
authority an approval id and a resolved commit and report what it says. The v1 draft had them run `consume`, `refuse` and `outcome`
steps, set test variables and mint fixtures with a Python helper; all of that is gone. What remains has two review findings to get right:
`BREAK_GLASS` and `SKIP_CHECK_RUNS` must be impossible on the approval path (from the command line or the environment), and a rerun must work
after the move succeeded.

## Behaviour

1. **Command line.** `bin/k3dm-hub-promote promote REF --approval ID` (exactly four arguments; `--approval` is the third). `ID` must match
   `^p[0-9]+-[0-9a-f]{8}$` (usage error exit 2 otherwise). Any other use of the third and fourth positions keeps today's meaning
   (`BREAK_GLASS`, `SKIP_CHECK_RUNS`, `bin/k3dm-hub-promote:315-316`), so the typed-confirmation path is unchanged. `make hub-promote` forwards
   three positionals (`Makefile:521-522`) and is not edited; the approval path is `bin/k3dm-hub-promote` or `bin/k3dm-hub-deploy`.
2. **No bypass on the approval path.** With `--approval`, a set `BREAK_GLASS` or `SKIP_CHECK_RUNS` (value other than empty or `0`) in the
   environment is refused before anything else, exit 1, message `--approval cannot be combined with BREAK_GLASS or SKIP_CHECK_RUNS`. There is no
   argument form of either on this path. (The authority has no such switch either, Part 2d N7.)
3. **Resolve, then ask.** The script runs the existing `git fetch "$REMOTE" --prune` and `resolve_on_origin` (`bin/k3dm-hub-promote:80`) to get the full sha of
   `REF` (never a short sha, never a name), then calls the client: `"$REPO_ROOT/bin/k3dm-promote-client" promote --id ID --sha <full sha>`. The client path is derived from the script's own location
   (the `REPO_ROOT` line, `bin/k3dm-hub-promote:4`); there is no environment override. No TTY and no typed confirmation is required on this path
   (the authority checked the nonce, the approver and the TOTP code). The script never runs `git push` on this path and never reads a token.
4. **Exit map, one table for both scripts** (Part 2a B.6): client exit 0 prints
   `[hub-promote] moved deploy/hub <old7>..<new7> (<tag>) by approval <id>` when the response `data.outcome` is `moved`, or
   `[hub-promote] deploy/hub already at <new7> by approval <id>` when `already`, and exits 0; client exit 1 prints the response message and exits 1, the
   message saying the approval is kept unless the code is `already_spent`; client exit 2 exits 2; client exit 75 prints
   `[hub-promote] could not decide (<message>); the approval is kept; rerun the same command` and exits 75. Nothing else is mapped; a client exit
   other than 0, 1, 2, 75 is treated as 75.
5. **Rerun after a move (R4).** A rerun with the same approval id after a successful move reaches the authority, which answers `ok`/`already`
   from the remote tag naming the approval (Part 2d C.5), so exit 0 again. The old-equals-new shortcut of `bin/k3dm-hub-promote:325-328` (`deploy/hub is already at ... nothing to promote`) is not taken on
   this path; the authority is always asked, because the shortcut would otherwise skip the approval check.
6. **hub-deploy.** `bin/k3dm-hub-deploy <ref> [--approval <id>]` (usage check `bin/k3dm-hub-deploy:14` becomes one or three arguments, `--approval` second, id regex as above) passes `--approval <id>` to the
   promote call (`:32`) and nothing else changes: the appsets diff and reapply, the `appsets-check platform-ops` loop, the rollout check, and Part 1's launchd step all run after a promote
   that exits 0. The `stop` message (`:9-13`) prints `rerun bin/k3dm-hub-deploy <ref> --approval <id>` when an approval id is in use, because `make hub-deploy` forwards only `REF` (`Makefile:525-527`), and the existing
   `make hub-deploy REF=<ref>` text otherwise. Exit codes, including 75, are the existing `stop` pass-through.
7. **Docs (this part owns the final wording; Part 1 owns the launchd sentence).** `docs/process/rules.md:95` (the enforcement paragraph) gains: promote can also be done with an approval
   from the root promote authority (`bin/k3dm-promote-client`, Part 2c): the nonce, approver and TOTP code are checked by that root process; evaluation and the push run there; the user-side scripts only ask. It states the honest limit: until the GitHub
   ruleset of `docs/howto/promote-authority.md` is on, the authority is a gate on the honest path, not a barrier. `docs/howto/hub-promote.md` gains an "Approved promote" section after "Everyday promote" (`:29-37`): request, approve, then
   `bin/k3dm-hub-deploy <ref> --approval <id>`, what exit 75 means, and that a rerun is safe. `.github/copilot-instructions.md:138` (`deploy/hub` moves only through `bin/k3dm-hub-promote`) becomes: only through `bin/k3dm-hub-promote` or the promote authority,
   and flags a call to the authority that passes `BREAK_GLASS`/`SKIP_CHECK_RUNS` or a client with an environment override; `:42` mentions the authority in one clause. `CLAUDE.md` is not edited.
