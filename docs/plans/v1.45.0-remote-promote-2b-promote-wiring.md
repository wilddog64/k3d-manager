## Problem

The approval store, evaluation and push now live in the root authority (Parts 2a, 2c, 2d). The user-side scripts only:
- hand the authority an approval id and a resolved commit;
- report its answer;
- run the downstream deploy steps on exactly the commit the authority moved.

Round 3 found these problems in v3:
- **A second move could still deploy another sha** (Astra blocker 2). v3 checked `deploy/hub` once after the promote. A move after that
  read was not caught: `platform-ops` fetches the branch again and applies whatever it finds (`Makefile:1393-1398`), and
  `appsets-reapply` applies the invoking checkout's templates (`Makefile:512-514`). Neither received the approved sha.
- **Exit 75 at `read-promoted-ref` was permanent** (Fable M7). Once another approval moved `deploy/hub` on, every rerun saw the same
  mismatch.
- **`old` was dropped** (Fable M6; Astra major). Part 1 seeds its appsets base from `old` on a first run, and the approval path skipped the
  read.
- **Resolution masked errors** (Astra major; Fable minor, probed). Wrapping `resolve_on_origin` (`bin/k3dm-hub-promote:80-91`) in a
  subshell with a local `die` cannot recover statuses it already lost: the `show-ref` calls sit in a conditional, any `rev-parse` failure at
  `:87` becomes "cannot resolve", and a failed `branch -r --contains | sed` at `:88` falls through to the reachability refusal at `:89`.
- **False claims.** "deploy/hub already at" can be false after the branch moved on; "approval is kept" can be false after a lost reply
  that followed a consume (Astra major).
- **Smaller gaps:** the fetch message lacked the id; the validator did not check `code` or the message type; 40 versus 64 hex; a rerun
  with a symbolic REF can resolve another sha; positive controls did not prove the client was reached; the pre-change doc copies had no
  file in `## Files` (Astra and Fable minors).

## Behaviour

1. **Command line.**
   - The approval form is `bin/k3dm-hub-promote promote REF --approval ID`: exactly four arguments, with `--approval` third.
   - `ID` must match `^p[0-9]+-[0-9a-f]{8}$`; otherwise it is a usage error, exit 2.
   - Any other use of the third and fourth positions keeps today's meaning: `BREAK_GLASS` and `SKIP_CHECK_RUNS`
     (`bin/k3dm-hub-promote:315-318`).
   - Today `:315` accepts two to four arguments, and `:317` rejects `--approval` as a `BREAK_GLASS` value with exit 1 (`BREAK_GLASS must be 0
     or 1`). That exit 1 is the pre-fix red for every approval-path test.
   - The usage lines at `:288` and `:315` gain the approval form.
   - `make hub-promote` forwards three positionals (`Makefile:521-522`) and is not edited. The approval path is `bin/k3dm-hub-promote` or
     `bin/k3dm-hub-deploy`.
   - **One sha format (v4).** Everywhere in this part a sha is `^[0-9a-f]{40}([0-9a-f]{24})?$`: 40 or 64 lowercase hex, as Parts 2a and
     2d allow.
2. **No bypass on the approval path.**
   - With `--approval`, the script checks `BREAK_GLASS` and `SKIP_CHECK_RUNS` in the environment. A value other than empty or `0` is
     refused before anything else, with exit 1 and the message `--approval cannot be combined with BREAK_GLASS or SKIP_CHECK_RUNS`.
   - The client is then always started as `env -u BREAK_GLASS -u SKIP_CHECK_RUNS -u SKIP_CHECK_RUNS_REASON -u REF -u MAKEFLAGS -u MFLAGS
     -u MAKELEVEL "$REPO_ROOT/bin/k3dm-promote-client" ...`. That is the pattern of `git_push` at `bin/k3dm-hub-promote:20`, so even an
     empty or `0` value never reaches the client.
   - There is no argument form of either on this path. The authority has no such switch either (Part 2d).
3. **Resolve, then ask.** With `--approval`, the script:
   1. Runs `git fetch "$REMOTE" --prune` (`:322`). A failure is exit 75, with `[hub-promote] could not fetch origin for approval <id>;
      rerun the same command`.
   2. **`approval_resolve REF` (v4, rewritten).** A new function; `resolve_on_origin` is not called on this path and is not changed. Every
      git call has its status checked explicitly (`if out="$(git_cmd ...)"; then ...; else rc=$?; fi`), so neither errexit nor `pipefail`
      decides an outcome, and there is no pipeline. It returns 2 for a deterministic refusal and 75 for anything else, and the caller uses
      `if sha="$(approval_resolve "$ref")"; then :; else rc=$?; fi`.
      1. `git show-ref --verify --quiet refs/heads/<REF>` and `refs/remotes/origin/<REF>`: status 0 is present, 1 is absent, anything else
         is 75.
      2. When both exist: `git rev-parse --verify "<ref>^{commit}"` for each. A failure is 75 (the refs exist). Different values are 2,
         `branch '<REF>' differs: local <a>; origin/<REF> <b>`.
      3. `git rev-parse --verify --quiet "<REF>^{commit}"`: status 0 gives the sha; status 1 is 2, `cannot resolve REF '<REF>' to a
         commit`; any other status is 75. Proof 1 shows 1 for an unknown name and 128 for an unreadable object store.
      4. `git for-each-ref --contains <sha> --format='%(refname)' refs/remotes/origin/`: a non-zero status is 75; status 0 with no line
         other than `refs/remotes/origin/HEAD` is 2, `commit <sha> is not reachable from an origin branch`; otherwise ok.
      5. The sha must match the Behaviour 1 format; otherwise 75.
   3. Does not read `remote_sha` (`:67-78`) and does not take the old-equals-new shortcut (`:325-328`). The authority is always asked
      (Behaviour 5).
   4. Calls the client: `promote --id ID --sha <full sha>`. The client path is `"$REPO_ROOT/bin/k3dm-promote-client"`, with `REPO_ROOT`
      from `:4`; there is no environment override.
   - No TTY and no typed confirmation is required on this path, because the approval was a Worker-signed envelope verified by the
     daemon: signature first, then the nonce, the approver, the check value and the TOTP code (Part 2a G.20, K4). `--approval <id>` only
     promotes an already approved record; this script forwards nothing new and never sees the envelope or its `sig`.
   - The script never runs `git push` and never reads a token on this path. The push itself is the authority's: the branch alone, then
     the witness tag (Part 2d C.13, R4-B1). The reply `{outcome, old, new, tag}` is unchanged.
4. **Validate the reply.** The client's stdout line is parsed by `/usr/bin/python3 -I -c '<inline validator>'` reading stdin. The validator
   takes the requested sha and the client exit as its arguments, uses only `json` and `re`, and does not use `jq`.
   - **Client exit 0.** The line must satisfy all of these, or the script exits 75 with `[hub-promote] the authority's reply for approval
     <id> did not match the request; rerun the same command`:
     - exactly the keys `v`, `result`, `code`, `message` and `data`;
     - `v` is the integer 1 (not a boolean);
     - `result` is `ok` and `code` is `ok`;
     - `message` is a string;
     - `data` is an object with exactly the keys `outcome`, `old`, `new`, `tag`;
     - `data.outcome` in {`moved`, `already`};
     - `data.new` equal to the requested sha;
     - `data.old` in the Behaviour 1 format;
     - `data.tag` matching `^hub-promote/[0-9]{8}T[0-9]{6}Z$`.
   - **Client exit 1.** The line must have the same five keys, `v` 1, `result` `refused`, `code` and `message` strings, and `data`
     exactly `{"approval": "kept"|"final"}` (Part 2a B.5). Otherwise the script exits 75 with the Behaviour 4 message.
5. **Exit map.** One table serves both scripts (Part 2a B.6).

   | client exit | script prints (stderr) | script exit |
   |---|---|---|
   | 0, valid, `moved` | `[hub-promote] approval <id> moved deploy/hub <old7>..<new7> (<tag>)` | 0 |
   | 0, valid, `already` | `[hub-promote] approval <id> had already moved deploy/hub <old7>..<new7> (<tag>)` | 0 |
   | 0, invalid | Behaviour 4 message | 75 |
   | 1, valid, `approval` `kept` | `[hub-promote] refused: <message>; approval <id> is kept` | 1 |
   | 1, valid, `approval` `final` | `[hub-promote] refused: <message>; approval <id> is closed; request a new one` | 1 |
   | 1, invalid | Behaviour 4 message | 75 |
   | 2 | `[hub-promote] refused: <message>` | 2 |
   | 75, or any other exit | `[hub-promote] could not decide for approval <id> (<message or "no reply">); rerun the same command; bin/k3dm-promote-client show --id <id> reports its state` | 75 |

   - The `already` line states what the record or witness says happened; it makes no claim about where `deploy/hub` is now (v4).
   - The 75 line no longer says "kept": after a lost reply the approval may already be consumed (Part 2a B.6).
   - **Machine lines (v4).** The 0 rows print exactly two lines to stdout, in this order, and nothing else goes to stdout:
     `approved-sha <new>` and `approved-old <old>`, both from `data`.
6. **Rerun after a move.** A rerun with the same approval id after a successful move reaches the authority. The authority answers
   `ok`/`already` from the consumed record (Part 2d D.16.2), with no time limit (Part 2a G.22), so the script exits 0 again with the same
   two machine lines.
7. **hub-deploy.**
   - **Usage.** `bin/k3dm-hub-deploy <ref> [--approval <id>]`. The usage check at `bin/k3dm-hub-deploy:14` accepts one or three arguments,
     with `--approval` second and the id regex as above.
   - **Promote call.** It passes `--approval <id>` to the promote call (`:32`) and captures stdout. On exit 0 it requires exactly the two
     machine lines of Behaviour 5 in the Behaviour 1 format, and sets `new` and `promoted_old` from them. A missing or malformed line stops
     at step `promote` with 75.
   - **`old` for Part 1 (v4, Fable M6).** On the approval path the pre-move read at `:29` is skipped. Where Part 1 needs `old` (its first-run
     `appsets <old>` seed, Part 1 Behaviours 4-5), it uses `promoted_old`, which is the exact pre-move commit from the authority's record,
     on a first run and on a rerun alike. On a first run (Part 1 Behaviour 4: no state directory before the script's own `mkdir`) the
     approval path writes nothing before the promote and, right after the promote returns, writes both lines `appsets <promoted_old>`
     and `launchd full` in one atomic write (Part 1 Behaviour 5, v5). Part 1 cannot test this path, because it does not exist before
     this part, so the test is here (E4).
   - **Superseded is final (v4, Fable M7).** After the promote, the re-read at `:39-41` is a check. If `remote_sha` differs from `new`, the
     script prints `hub-deploy: deploy/hub is now <got7>; approval <id> moved it to <new7> and has been superseded; nothing more to deploy
     for it` and exits 1 at step `superseded`. This is final: a rerun gets the same answer. Part 1 leaves both persisted bases unchanged
     (Part 1 Behaviour 14), so the run for the newer commit reconciles from them. Part 1 states the same sentence about the two bases:
     the launchd base is unchanged; the appsets base is as Behaviour 6 left it (v5, Fable M5).
   - **Single-writer assumption and residual (v5, Fable M3).** The superseded logic assumes one writer of `deploy/hub`. Until Part 2e is
     cut over, a CVE pin commit can supersede a run (the in-cluster promoter commits to `deploy/hub` every 15 minutes,
     `scripts/etc/argocd/platform-ops/app-cve-scan-cronjob.yaml:193`). Recover with the manual `make platform-ops` and a rerun of
     `bin/k3dm-hub-deploy` for the current `deploy/hub` sha.
   - **Pinned mutating steps (v4, Astra blocker 2).** On the approval path, every step that applies configuration receives `new` and applies
     exactly that commit:
     - `make platform-ops PLATFORM_OPS_SHA=<new> K3DM_SUPERSEDED_OUT=<path>`: after its existing fetch (`Makefile:1393-1394`), when
       `PLATFORM_OPS_SHA` is set it must match the Behaviour 1 format, `FETCH_HEAD` must equal it (otherwise the recipe goes to the
       superseded exit below, before applying), and it archives `PLATFORM_OPS_SHA` instead of `FETCH_HEAD`. The marker it writes
       (`:1397-1398`) is then that sha, which Part 1's downstream pin (Part 1 Behaviour 13) compares with `new`.
     - `make appsets-reapply APPSETS_SHA=<new> K3DM_SUPERSEDED_OUT=<path>`: when `APPSETS_SHA` is set, the target does the same
       fetch-and-compare, extracts `git archive <APPSETS_SHA>` into a temporary directory (the `platform-ops` pattern at `:1390-1395`), and
       runs `deploy_argocd_applicationsets` from there with the existing `K3D_MANAGER_BRANCH=deploy/hub`.
     - `appsets-check` is read-only and runs unchanged.
     - Without these variables both targets behave exactly as today; the TTY path does not set them.
     - A move after the fetch-and-compare cannot change what is applied, because the archive is of the pinned sha, not of `FETCH_HEAD`
       (which a later fetch moves; Proof 5). Argo CD itself keeps following the branch; that is its design and is not this script's step.
   - **Superseded result through a file (v5, Astra 7).** A recipe `exit 1` makes `make` exit 2 (contract probe, GNU Make 3.81), so the
     exit status cannot tell a pin mismatch from any other recipe failure. Mechanism:
     - Both pinned targets take one more variable `K3DM_SUPERSEDED_OUT=<path>`. On a pin mismatch after the fetch, and when the variable
       is non-empty, the recipe writes the one line `superseded <got> <want>` (the two full shas) to that path, prints its existing
       human line (`[platform-ops] deploy/hub is <got7>, not <want7>; superseded`, and the `[appsets-reapply]` equivalent), and exits
       nonzero before applying anything. With the variable empty or unset, the human line and the nonzero exit are the same.
     - `bin/k3dm-hub-deploy` creates the file with `mktemp` (mode 0600) before each pinned call, passes the path, and after a nonzero
       `make` maps "the file is non-empty and its first word is `superseded`" to the final exit 1 at step `superseded` (printing the
       Behaviour 7 superseded line from the two shas in the file). Any other nonzero `make` keeps its existing step failure through `stop`.
     - The file is removed on every exit path (success, `stop`, `die`, a signal), with an `EXIT` trap.
     - Part 1's own pin check (`deployed-platform-ops` against the promoted sha, Part 1 Behaviour 13) is inside hub-deploy and keeps
       exiting 1 directly; it does not use the file.
   - **ApplicationSets diff base.** Part 1's persisted appsets base (Part 1 Behaviours 5-6) supplies the diff base, so a rerun after a failed
     reapply still reapplies.
   - **Transient reads.** On the approval path, a `remote_sha` failure (`:21-27`) is exit 75 through `stop`. The TTY path is unchanged.
   - **Retry text (v4).** Part 1's `retry_hint` gains the id and the resolved sha. With an approval in use, every retry line (`stop` and
     launchd pending alike) reads `rerun bin/k3dm-hub-deploy <new> --approval <id>`, naming the full approved sha, never the symbolic REF
     that could resolve elsewhere later. Before the promote has answered, `<new>` is not known and the line names the REF as given. Without
     an approval: `rerun make hub-deploy REF=<ref>`. The bin form is needed because `make hub-deploy` forwards only `REF`
     (`Makefile:525-527`).
   - **Exit codes.** `stop` maps exit codes as Part 1 Behaviour 14 defines: 75 passes through only at `run-lock`, `promote`,
     `read-deploy-hub` and `read-promoted-ref`; a child 75 at any other step becomes 1; other codes pass through as today.
8. **Docs.** This part owns the final approval wording; Part 1 owns the launchd sentence.
   - **`docs/process/rules.md`.** The enforcement paragraph at `:95`, pre-Part-1, gains one sentence: promote can also be done with an

## Proof of external behaviour

1. **git resolution statuses** (m4-air, macOS 26.5.2, 2026-11-19 12:15 UTC, git 2.56.1; scratchpad `p1v4/2b/resolve.sh` and
   `resolve.log`): `rev-parse --verify --quiet <name>^{commit}` exits 1 for an unknown name and for an absent 40-hex object, 0 for a
   commit, and 128 with an unreadable object store. `show-ref --verify --quiet` exits 1 for an absent ref. `for-each-ref --contains <c>
   refs/remotes/origin/` exits 0 with the containing refs, 0 with no output when none contains it, and 129 for an unknown commit.
2. **Errexit in a subshell** (Fable round-3 probe 13): a captured-status call (`w || rc=$?`) disables errexit inside, so a failed pipeline
   falls through. Behaviour 3.2 therefore checks every status explicitly.
3. **Stub client.** The stub in the bats tests reproduces the exit map of Part 2a B.6 and the envelope of B.5. It carries a comment that it
   is a stub of the Part 2c client, not a capture.
4. **Validator interpreter.** `/usr/bin/python3` 3.9.6 on the hub (probe, m4-air, 2026-11-18) and `/usr/bin/python3` on the Ubuntu CI
   runner. It uses only `json` and `re`. Part 2c uses the Command Line Tools interpreter for root because `/usr/bin/python3` is the Xcode
   shim (Part 2c A.1). That reason does not apply here: this validator runs as the hub user, whom O2 already treats as an attacker, and it
   only decides what to print. `/usr/bin/python3` is kept because it exists on both the hub and the CI runner.

5. **`FETCH_HEAD` moves on a second fetch; an older object still archives** (m4-air, macOS 26.5.2, 2026-11-19, git 2.56.1; scratchpad
   `p1v5/2b/`, built inline: a local origin with branch `deploy/hub`, a clone, two fetches of `refs/heads/deploy/hub` with a commit
   added to the origin between them): `rev-parse FETCH_HEAD` returned `7f6fa22a...` then `45530a29...`, and `git archive 7f6fa22a...`
   of the first sha still exited 0 after the second fetch. This is what E5 uses to kill the `archive FETCH_HEAD` mutant.
6. **`make` status for a recipe `exit 1`** is 2, from the contract probe (GNU Make 3.81, m4-air, 2026-11-19; scratchpad
   `p1v5/k4/Makefile`). Behaviour 7 therefore does not rely on the recipe's own status.
7. **`deploy_argocd_applicationsets` reads no git state (closed, v5).** `grep -nE '\bgit\b' scripts/plugins/argocd.sh` finds no `git`
   command: the only hits are repository URLs (`:751`, `:969`), the secret name `platform-ops-git-writer` (`:1827-1841`) and a help
   string (`:1631`). The function (`:1310-1377`) calls `_argocd_prepare_applicationsets` (`:1288-1309`, reads `$ARGOCD_CONFIG_DIR`
   which is `$SCRIPT_DIR/etc/argocd`, `:43`), `_argocd_apply_and_confirm_appset_stage` (`:1276-1286`) and helpers that call `kubectl`,
   `jq` and `sed`. `scripts/k3d-manager` has no `git` call. The only `git` in the sourced libraries are `_k3dm_repo_root`
   (`scripts/lib/foundation/scripts/lib/system.sh:8-25`, called by `scripts/plugins/copilot.sh:52`, not by the ApplicationSet path, and
   falling back to `SCRIPT_DIR` when `git` fails, as it does in an archive directory with no `.git`) and `agent_rigor.sh:11-21`
