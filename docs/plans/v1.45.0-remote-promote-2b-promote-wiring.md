## Problem

The approval store, evaluation and push now live in the root authority (Parts 2a, 2c, 2d). The user-side scripts only:
- hand the authority an approval id and a resolved commit;
- report its answer;
- run the downstream deploy steps on the commit the authority moved.

Round 2 found these problems in v2:
- **Transient exit codes.** A transient failure on the user side still exits 1 or 128, which Part 3 would read as a refusal (Fable 19;
  Astra 13).
- **Bypass variables.** Benign `BREAK_GLASS=0` could still reach the client environment.
- **Success not validated.** A success reply was not validated against the requested sha.
- **Wrong approval claim.** "Kept unless already_spent" is wrong for `expired` and `too_many_codes`.
- **Downstream sha.** `hub-deploy` re-read the live ref after the promote, so a second move in between could run the later steps on a
  commit nobody approved (Astra 9).
- **Pre-fix arity.** The definition of done described the old arity wrongly (Astra 15).

## Behaviour

1. **Command line.**
   - The approval form is `bin/k3dm-hub-promote promote REF --approval ID`: exactly four arguments, with `--approval` third.
   - `ID` must match `^p[0-9]+-[0-9a-f]{8}$`; otherwise it is a usage error, exit 2.
   - Any other use of the third and fourth positions keeps today's meaning: `BREAK_GLASS` and `SKIP_CHECK_RUNS`
     (`bin/k3dm-hub-promote:315-318`).
   - Today `:315` accepts two to four arguments, and `:317` rejects `--approval` as a `BREAK_GLASS` value with exit 1 (`BREAK_GLASS must be 0
     or 1`). That exit 1 is the pre-fix red for every approval-path test (Astra 15).
   - The usage line at `:288` and `:315` gains the approval form.
   - `make hub-promote` forwards three positionals (`Makefile:521-522`) and is not edited. The approval path is `bin/k3dm-hub-promote` or
     `bin/k3dm-hub-deploy`.
2. **No bypass on the approval path.**
   - With `--approval`, the script checks `BREAK_GLASS` and `SKIP_CHECK_RUNS` in the environment. A value other than empty or `0` is
     refused before anything else, with exit 1 and the message `--approval cannot be combined with BREAK_GLASS or SKIP_CHECK_RUNS`.
   - The client is then always started as `env -u BREAK_GLASS -u SKIP_CHECK_RUNS -u SKIP_CHECK_RUNS_REASON -u REF -u MAKEFLAGS -u MFLAGS
     -u MAKELEVEL "$REPO_ROOT/bin/k3dm-promote-client" ...`. That is the pattern of `git_push` at `bin/k3dm-hub-promote:20`, so even an
     empty or `0` value never reaches the client (Astra 13).
   - There is no argument form of either on this path. The authority has no such switch either (Part 2d).
3. **Resolve, then ask.** With `--approval`, the script:
   1. Runs `git fetch "$REMOTE" --prune` (`:322`). A failure is exit 75, with `[hub-promote] could not fetch origin; the approval is
      kept; rerun the same command`.
   2. Resolves `REF` with `resolve_on_origin` (`:80-91`) to the full sha. Never a short sha, never a name.
      - Its three refusals are deterministic after a successful fetch and exit 2: `differs` (`:85`), `cannot resolve REF` (`:87`), and
        `not reachable from an origin branch` (`:89`).
      - Any other git failure inside it (`:83-84`, the `branch -r --contains` at `:88`) is exit 75.
      - Approval mode does this through a wrapper, `approval_resolve`, that runs in a subshell with a local `die` of exit 2 for those three
        messages and maps every other non-zero status to 75. The TTY path keeps `die` exit 1.
   3. Does not read `remote_sha` (`:67-78`) and does not take the old-equals-new shortcut (`:325-328`). The authority is always asked
      (Behaviour 5).
   4. Calls the client: `promote --id ID --sha <full sha>`. The client path is `"$REPO_ROOT/bin/k3dm-promote-client"`, with `REPO_ROOT`
      from `:4`; there is no environment override.
   - No TTY and no typed confirmation is required on this path, because the authority checked the nonce, the approver and the TOTP code.
   - The script never runs `git push` and never reads a token on this path.
4. **Validate the reply** (Astra 13; Fable 19). The client's stdout line is parsed by `/usr/bin/python3 -I -c '<inline validator>'`
   reading stdin. The validator takes the requested sha as its only argument, has no other dependency, and does not use `jq`. On client
   exit 0 the line must satisfy all of these, or the script exits 75 with `[hub-promote] the authority's reply did not match the request;
   the approval is kept; rerun the same command`:
   - exactly the keys `v`, `result`, `code`, `message` and `data`;
   - `v` equal to 1;
   - `result` equal to `ok`;
   - `data.outcome` in {`moved`, `already`};
   - `data.new` equal to the requested sha;
   - `data.old` 40 hex;
   - `data.tag` matching `^hub-promote/[0-9]{8}T[0-9]{6}Z$`.

   On a client exit of 1, the validator reads `data.approval`, which is `kept` or `final` (Part 2a B.5).
5. **Exit map.** One table serves both scripts (Part 2a B.6).

   | client exit | script prints | script exit |
   |---|---|---|
   | 0, valid, `moved` | `[hub-promote] moved deploy/hub <old7>..<new7> (<tag>) by approval <id>` | 0 |
   | 0, valid, `already` | `[hub-promote] deploy/hub already at <new7> by approval <id>` | 0 |
   | 0, invalid | Behaviour 4 message | 75 |
   | 1, `data.approval` `kept` | `[hub-promote] refused: <message>; approval <id> is kept` | 1 |
   | 1, `data.approval` `final` | `[hub-promote] refused: <message>; approval <id> is closed; request a new one` | 1 |
   | 1, `data.approval` missing or invalid | Behaviour 4 message | 75 |
   | 2 | `[hub-promote] refused: <message>` | 2 |
   | 75, or any other exit | `[hub-promote] could not decide (<message or "no reply">); approval <id> is kept; rerun the same command` | 75 |

   - After the human line, the 0 rows print exactly one machine line to stdout, `approved-sha <new40>`, and nothing else goes to stdout.
     The human lines go to stderr.
   - The phrase "kept unless already_spent" is gone. The answer always comes from `data.approval` (Fable 19).
6. **Rerun after a move (R4).** A rerun with the same approval id after a successful move reaches the authority. The authority answers
   `ok`/`already` from the record or the witness tag (Part 2d D.15), so the script exits 0 again.
7. **hub-deploy** (Astra 9).
   - **Usage.** `bin/k3dm-hub-deploy <ref> [--approval <id>]`. The usage check at `bin/k3dm-hub-deploy:14` accepts one or three arguments,
     with `--approval` second and the id regex as above.
   - **Promote call.** It passes `--approval <id>` to the promote call (`:32`) and captures stdout. On exit 0 it requires exactly one line
     `approved-sha <40-hex>`, and sets `new` from it. A missing or malformed line stops at step `promote` with 75.
   - **Pin to the approved commit.**
     - On the approval path, the re-read at `:39-41` is kept as a check, not a source. If `remote_sha` differs from the approved `new`,
       the script prints `hub-deploy: deploy/hub moved to <got7> after approval <id> moved it to <new7>` and stops at step
       `read-promoted-ref` with 75.
     - Part 1's downstream pin (Part 1 Behaviour 13) compares the platform-ops marker with the same `new`.
     - Part 1's persisted appsets base (Part 1 Behaviours 5-6) supplies the diff base, so a rerun after a failed reapply still reapplies.
   - **Transient reads.** On the approval path, a `remote_sha` failure (`:21-27`) is exit 75 through `stop`. The pre-move read at `:29` is
     not needed on this path and is skipped; Part 1's state base takes its place. The TTY path is unchanged.
   - **Retry text.** Part 1's `retry_hint` (Part 1 Behaviour 10.6) gains the id. With an approval in use, every retry line, `stop` and
     launchd pending alike, reads `rerun bin/k3dm-hub-deploy <ref> --approval <id>`; otherwise `rerun make hub-deploy REF=<ref>`. The bin
     form is needed because `make hub-deploy` forwards only `REF` (`Makefile:525-527`).
   - **Exit codes.** Exit codes, including 75, pass through `stop` as today.
8. **Docs.** This part owns the final approval wording; Part 1 owns the launchd sentence.
   - **`docs/process/rules.md`.** The enforcement paragraph at `:95`, pre-Part-1, gains one sentence: promote can also be done with an
     approval from the root promote authority (`bin/k3dm-promote-client`, Part 2c). The nonce, approver and TOTP code are checked by that
     root process, evaluation and the push run there, and the user-side scripts only ask. It states the limit honestly: until the GitHub
     ruleset of `docs/howto/promote-authority.md` is on, the authority is a gate on the honest path, not a barrier.
   - **`docs/howto/hub-promote.md`.** It gains an "Approved promote" section after "Everyday promote" (`:24`). The section covers:
     - request, approve, then `bin/k3dm-hub-deploy <ref> --approval <id>`;
     - what exit 75 means;
     - that a rerun is safe;
     - a link to `docs/howto/promote-authority.md`.
   - **`.github/copilot-instructions.md`.**
     - `:138` (`deploy/hub` moves only through `bin/k3dm-hub-promote`) becomes: only through `bin/k3dm-hub-promote` or the promote
       authority. It also flags an authority call that passes `BREAK_GLASS` or `SKIP_CHECK_RUNS`, or a client with an environment override.
     - `:42` mentions the authority in one clause.
   - `CLAUDE.md` is not edited.
