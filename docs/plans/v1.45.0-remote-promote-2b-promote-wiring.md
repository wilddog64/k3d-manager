## Problem

`bin/k3dm-hub-promote promote REF` needs a typed confirmation on a TTY (`bin/k3dm-hub-promote:135`), so nothing can promote from a phone.
Part 2a gives an approval record that proves a human said yes with a code. This part makes the promoter accept that record in place of the
TTY, and only then, and in a way that cannot move `deploy/hub` to anything the human did not approve. The blind review found: the order
(`fetch` before resolve) matters, a transient failure must not burn the approval while a real mismatch must, the containment refusal is a bare
`exit 1`, `check_runs` dies inside a function, the "ahead" check would have refused real history, and "already deployed" was undefined.

## Behaviour

`bin/k3dm-hub-promote promote REF --approval ID` and `bin/k3dm-hub-deploy COMMIT-ISH --approval ID`. Without `--approval` everything is unchanged
(TTY refusal at `:135` stays; no new output).

1. **Argument parsing.** In `main`, `--approval ID` is removed from the positional list before the existing parse (`:315-316`), anywhere after
   `promote`. A second `--approval` or a missing/malformed id (not `^a-[0-9a-f]{16}$`) is `usage` exit 1 (`die`). `rollback` with `--approval` dies
   `rollback does not take --approval` before anything is read. `is-green`, `status`, `is-contained` ignore nothing: `--approval` there is a usage error.
2. **Refuse flag mixes (record kept).** With `--approval`, if `break_glass` or `skip_checks` ends up `1` from **either** source (the positional
   arguments or the `BREAK_GLASS` / `SKIP_CHECK_RUNS` environment variables, `:316`; checked on the raw environment values too, so a positional `0` that overrides
   an environment `1` still refuses), die `--approval cannot be combined with BREAK_GLASS or SKIP_CHECK_RUNS` (exit 1) and do not touch the record. A human who wants break glass uses the TTY.
3. **Read the record.** Run `bin/k3dm-hub-approval show --id ID`; exit non-zero or a state other than `approved` dies with the CLI's message and exit
   1 (or 4 for infrastructure) and does not change the record. Parse `sha7`, `branch`, `channel`. A record whose `expires` has passed dies with the
   `expired` message (the record becomes expired through `show`'s lazy expiry; see 2a item 23).
4. **Fetch first, transient failures keep the record.** Order inside `promote` with `--approval`: (a) step 3; (b) `git_cmd fetch "$REMOTE" --prune` (the existing `:322`); a
   fetch failure exits **75** with `fetch failed; the approval is still valid until <ISO>` and the record stays `approved`; (c) `new="$(resolve_on_origin "$ref")"` (`:323`);
   (d) `old="$(remote_sha 1)"` (`:324`).
5. **Sha binding.** `show` prints only `sha7`, so the early check compares `sha7` with the first seven characters of `new`. A difference runs
   `bin/k3dm-hub-approval refuse --id ID --code sha_mismatch --detail <new7>` and exits 1 with `approval <id> is for <sha7>, not <new7>` (the record is burned). The full-sha comparison is made by `consume --sha "$new"` in item 9.
6. **Already deployed is success, not a refusal.** If `new == old` (existing `:325-328`), print `[hub-promote] deploy/hub is already at <new>; nothing to promote`, leave the record **untouched** (still `approved`, to expire) and exit 0 so `bin/k3dm-hub-deploy` continues to appsets, platform-ops, the rollout check and the Part 1 launchd step.
7. **Containment, refuse and burn.** The existing `:329-343` path stays for the no-approval promote. With `--approval` an uncontained commit list prints
   as now to stderr, runs `refuse --id ID --code not_contained`, and exits 1 (the existing bare `exit 1` at `:341` stays for the TTY path only). Cannot-check conditions (`die "cannot fetch ..."`, `die "cannot check deploy/hub containment ..."`) exit 75 and keep the record.
8. **Newest green commit of the newest release branch.** With `--approval`:
   1. `branch` (from the record, validated by 2a against `^k3d-manager-v[0-9]+\.[0-9]+\.[0-9]+$`) must equal the first line of
      `git for-each-ref --sort=-version:refname 'refs/remotes/origin/k3d-manager-v*' --format='%(refname:short)'` with the `origin/` prefix removed. Otherwise `refuse --code not_newest_branch`, exit 1.
   2. Walk `git rev-list --first-parent --max-count=20 origin/<branch>`, newest first. For each commit run `classify_check_runs` (not `check_runs`, which dies):
      rc 0 means the first green commit; rc 1 (pending or failed) and rc 3 (no check runs) continue to the next commit (the walk `bin/k3dm-repo-sync:89-99` does through `is-green`); rc 2 (lookup failed) exits **75** with the record kept (it never walks past an unknown).
   3. The first green commit must equal `new`. If none of the 20 is green, or the first green commit differs from `new`, run `refuse --code not_newest_green --detail <first-green7|none>` and exit 1 `approval <id> is not for the newest green commit`.
   There is no "ahead" check: of the 14 most recent `hub-promote/*` tags, 3 had `old` that is not an ancestor of `new` (2026-11-19 UTC, m4-air.local); an ancestry rule would have refused real history. Containment (item 7) is the only history rule.
9. **Consume, then move, then outcome.** Immediately before `record_move`, run `bin/k3dm-hub-approval consume --id ID --sha "$new"` (2a item 20: fresh clock read under the lock; expiry, sha, current operator id). A refusal exits 1 with the CLI's message; if the refusal is the `is for <sha7>, not <given7>` one the promote also runs `refuse --id ID --code sha_mismatch`. A busy store (exit 4, `approval store is busy`) exits 75 with the record kept; any other exit 4 passes through as 4. After a successful consume `record_move` runs with two new tag lines `approval: <id>` and `channel: <channel>` appended after `REF:` (the rollback parser reads `action`, `old`, `new` only; `status` and `rollback` ignore the new lines). On success the promote then runs `outcome --id ID --result moved`. If `record_move` dies, an exit handler set just before the call runs `outcome --id ID --result failed --reason push_failed` (or `tag_failed` when the push had succeeded, i.e. the die at `:169` or `:170`) and the promote exits with the same code. The record stays `consumed`; **a failed move after consume is not retried with the same id** (the operator asks again; this closes the replay).
10. **No confirmation prompt, a loud line.** With `--approval`, `show_and_confirm` is not called; instead it prints the same old/new/commit list that it prints now, then `[hub-promote] approval <id> (<channel>) approved this promote`. The TTY refusal at `:135` is not reached.
11. **Environment hygiene.** `git_push` at `:20` adds `-u K3DM_PROMOTE_TEST_ROOT -u K3DM_PROMOTE_TEST_SECURITY -u K3DM_PROMOTE_TEST_NOW` to the `env -u` list so a push hook never sees them.
12. **hub-deploy.** `bin/k3dm-hub-deploy` usage becomes `k3dm-hub-deploy <commit-ish> [--approval <id>]` (`:14` area); the role gate (`:17-19`) still runs first; the promote call (`:32`) becomes `promote "$ref" --approval "$id"` when given. Exit **75** from the promoter stops hub-deploy at step `promote` like any non-zero (existing `stop`, `:9-13`), and the message already tells the operator to rerun with the same REF; for an approval id the rerun passes `--approval` again. A promote that exits 0 because the ref is already deployed continues to the later steps (item 6). `bin/k3dm-hub-deploy` without `--approval` is unchanged.
13. **Test helper.** `scripts/tests/bin/hub_approval_mint.py <store-root> <sha> <branch> <channel> <approver> <state> [<expires-offset>]` (test only, refuses unless
    `K3DM_PROMOTE_TEST_ROOT` has the sentinel) creates a record through `hub_approval.create_record`, drives it to the given state through the library with the stub Keychain and prints `<id>` only (the BATS never needs the nonce).
14. **Copilot instructions.** `.github/copilot-instructions.md:42` and `:138` gain one clause each: `--approval <id>` is the only non-TTY promote path and needs an approved record; a promote without a TTY confirmation or a valid approved record remains a flag. Nothing else in that file changes.
