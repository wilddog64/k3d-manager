# v1.34.0 — Hermes scheduled `make status` sensor, triage, and bounded auto-repair

**Branch:** `k3d-manager-v1.34.0`
**Filed:** 2026-09-16
**Status:** ASSIGNED — Codex, 2026-09-16
**Motivation:** `make status` is the only detector we have for a browser-SSO outage
(`reference_e2e_cannot_detect_browser_sso_outage`), and today it only runs when a human types it.
The 2026-09-15 Keycloak browser-flow regression broke every human login on the platform and was
found by hand, hours in.

## Problem

Three facts, all verified in the code as it stands today:

1. **Nothing schedules `make status`.** Hermes's `_run_cycle` samples six sensors — `eso`,
   `argocd`, `reachability`, `node_pressure`, `kine`, `ci`. None of them runs the status check
   suite.
2. **The closest existing sensor cannot see this class of failure.** `reachability` shells out to
   `bin/public-endpoint-probe`, which scores a host healthy on a 2xx/3xx from `https://<host>/`.
   During the 2026-09-15 outage `keycloak.3ai-talk.org/` returned 200 the entire time — the
   failure only appears when you drive a **PKCE authorization request** and assert a login form
   renders instead of an HTTP 400. That is precisely what `make status`'s SSO login checks do and
   nothing else in the fleet does.
3. **Neither e2e tier covers it either.** Tier 1 runs `OAUTH2_ENABLED=false` with no Keycloak;
   Tier 2 authenticates by **password grant**, which returned 200 throughout the outage. A green
   e2e run is compatible with every human login being down.

So the one real detector runs only on human initiative.

## Design

### Cadence — a slot gate inside the existing poll, not a new launchd agent

`com.k3d-manager.hermes.plist.tmpl` already sets `StartInterval` **300** (5 min). The status run is
gated *inside* `_poll`, exactly as `_schedule_e2e` gates the e2e run.

**Consequence to accept explicitly: 39 is not a multiple of 5.** The gate fires on the first poll
at or after 39 minutes since the last run, so the real cadence is **~40 minutes** (and drifts to
45 whenever a poll is late or skipped). This is the honest behaviour; do not add a second timer to
chase exactly 39. `K3DM_HERMES_STATUS_INTERVAL_MIN` (default `39`) makes it tunable, and
`K3DM_HERMES_STATUS_ENABLED=0` disables it.

Interval state is a single epoch in the Hermes state file (`status_last_run`), not a claims
directory — unlike e2e there is no multi-host race and no long detached child to claim against.

### Cost and blocking

`bin/cluster-status --json` resolves through the webhook's `/api/v1/health` with
`curl --max-time 90`. Worst case it blocks the poll for 90s inside a 300s interval — acceptable, and
the reason the run stays **inline** rather than detached like e2e (which can take 5400s). Give the
subprocess a hard `timeout=120` so a wedged webhook cannot stall Hermes past its next interval.

### Sensor — consume the JSON contract, never scrape the human output

`bin/cluster-status --json` already emits a stable machine contract (`bin/cluster-status-summary`
lines 50-62):

```json
{"overall":"fail|warn|healthy|unknown",
 "provider":"k3s-hostinger","context":"...",
 "errors":[...],"warnings":[...],
 "checks":[{"id":"frontend_sso_login","service":"Frontend SSO login",
            "status":"error","message":"...","http_code":400}],
 "counts":{"services_failed":3,"services_warning":0,"services_healthy":17}}
```

`id` is the service name lowercased with spaces → underscores, so the SSO lines are stable ids:
`frontend_sso_login`, `argocd_sso_login`, `keycloak_admin_login`. Match on `id`, never on `message`
prose.

New `status_checks(run, state, threshold=2)` in `scripts/lib/hermes/sensors.py`, returning the
standard `record(...)`:

| Condition | Status | Notes |
|---|---|---|
| `overall == "healthy"` | `healthy` | clears the debounce |
| `overall == "warn"` | `healthy` | warnings are not pages; carried in `data` |
| `overall == "fail"` | `degraded` after `_debounced(..., threshold=2)` | two consecutive reds ≈ 80 min |
| `overall == "unknown"`, or non-JSON, or timeout | `unknown` | **must not** page — see below |

`data` carries `{"failed_ids": [...], "warned_ids": [...], "counts": {...}}`.

**The `unknown` case is load-bearing.** When the webhook is down, `cluster-status-summary` emits
`overall: "unknown"` with a single `status_source` warning. That is already R1's territory
(`make restart-webhook`, driven by `_unknown_webhook`). Reporting it as `degraded` here would
double-page one fault and could race two repairs against each other. It stays `unknown`.

### Triage — new pure module `scripts/lib/hermes/status_triage.py`

Same shape as `e2e_triage.py`: pure functions, no I/O, `redact()` applied to every string that
reaches a log or Slack. Classification is by check `id`, and the **ordering is the policy**:

| Class | Matches | Simple? | Action |
|---|---|---|---|
| `status-source` | `status_source` | — | defer to R1, emit nothing |
| `sso-auth` | `*_sso_login`, `keycloak_admin_login` | **no** | notify + file bug |
| `edge` | ids whose message carries `HTTP 5xx`/`HTTP 530` | maybe | defer to `reachability`/R2/R3 |
| `credential` | `*_login` not matching `sso-auth` | **no** | notify + file bug |
| `sync` | `eso_*`, `argocd_*` (non-login) | **no** | notify + file bug |
| `data` | `data_layer`, `product_images` | **no** | notify + file bug |
| `service` | everything else | maybe | defer to R2 if a single host |

Group, count, and slug exactly as `e2e_triage.group_slug` does, so bug filenames stay stable and
`e2e_bugs.file_bugs` can be reused unchanged for the filing path.

### "Agent fix if the problem is simple" — what that can and cannot mean today

This is the part of the request that does **not** map cleanly onto the current design, and the spec
says so rather than quietly inventing a new power.

`scripts/lib/hermes/repairs.py` opens with: *"No repair runs outside approve(); the poll cycle only
proposes."* Phase 3 — cooldowns, budgets, durable audit, auto-verification — **is not implemented**.
There is exactly one auto-executing path, `auto_remediate_kine`, and it is opt-in via
`K3DM_HERMES_AUTO_KINE_GUARD=1`, bounded to once per incident, and writes a `repair_audit` entry.

So "agent fix if simple" is delivered as **proposal + one-click Slack approval**, which already
exists (`interactive_blocks` / `post_interactive` / `_drain_approvals`). Concretely:

- **No new repair is added by this spec.** Every class in the table above that is plausibly
  simple — `edge`, `service` — is already covered by R2 (kickstart a port-forward agent) and R3
  (refresh the Hostinger edge). The status sensor's job is to *raise the signal*; the existing
  preconditions decide whether a repair is proposable.
- **`sso-auth` is never auto-repairable and must never become so.** The 2026-09-15 fix was a realm
  authentication-flow repair whose acceptance criteria include surviving a Keycloak restart. That
  is a human decision, in the same category as R6 (restart the control plane), which is
  deliberately proposal-only and `reversible: False`.
- If auto-execution of R2 on a sustained single-service red is wanted later, it is a **separate
  spec** that must mirror `auto_remediate_kine`: its own env flag, once-per-incident guard, and
  `repair_audit` entry. Do not fold it into this change.

### Notification — state-change only, or it becomes noise

Paging every ~40 minutes for a red that a human is already working is how a monitor gets muted.
Reuse `e2e_triage.diff_groups` against the previous run's groups stored in state:

- **new** → Slack post, and file/reopen a bug via `e2e_bugs.file_bugs` (worktree + push path is
  already built and already refuses to file unless the repo is on a release branch).
- **ongoing** → silent, except one daily reminder (first run after local midnight).
- **resolved** → a single "recovered" Slack line.

The Slack text must name the failing check ids and the counts, and must pass through `redact()` —
status messages can contain usernames.

## Blocking dependency — fix the known false red first

`make status CLUSTER_PROVIDER=k3s-hostinger` currently reports:

```
✗ Prometheus: HTTP Error 401: Unauthorized
```

This is a **false** red. `docs/bugs/2026-09-15-prometheus-public-endpoint-unauthenticated.md` added
`bin/prometheus-auth-proxy` in front of the public endpoint; the status probe was never taught to
authenticate, so it now reports the very protection it asked for as a failure, and it counts toward
`Overall: FAIL`.

Turning on a 40-minute schedule while that line is red means **a Slack page and a filed bug on the
first run, and a stale ongoing red forever after**. Land the probe-authentication fix first, or this
sensor ships muted and useless.

## Tests (pytest, stubs only — no live cluster)

- `parse`/`classify`: each id in the table maps to its class; `status_source` classifies to
  `status-source` and produces **no** group.
- `overall: "unknown"` → sensor status `unknown`, never `degraded`.
- `overall: "fail"` once → `healthy` (debounced); twice → `degraded`.
- `overall: "warn"` → `healthy`, with `warned_ids` populated.
- Non-JSON output, empty output, and a subprocess timeout all → `unknown`, no exception.
- Interval gate: not due → runner not called; due → called once and `status_last_run` advanced;
  `K3DM_HERMES_STATUS_ENABLED=0` → never called.
- `diff_groups` drives notification: new → post, ongoing → silent, resolved → post.
- A message containing a bearer token or `password=` is `redact()`ed before it reaches the group.
- Assert meaningful tokens, never whole source lines.

## What NOT to Do

- Do not add a new launchd agent or a second timer — gate inside the existing 300s poll.
- Do not add a new entry to `REPAIRS`, and do not make any repair auto-execute. Proposal +
  approval only; auto-execution is a separate spec with its own env flag and audit entry.
- Do not make `sso-auth` repairable by an agent, ever.
- Do not scrape `make status` human output — consume `--json` only.
- Do not change `bin/cluster-status`, `bin/cluster-status-summary`, or the webhook's health model.
- Do not report `overall: "unknown"` as `degraded` — it is R1's signal, not this sensor's.
- Do not print or log any credential; no base64 comparisons.
- Do not run `kubectl`, `helm`, `launchctl`, or live `curl` from tests.
- Do not edit `scripts/lib/foundation/` or `scripts/lib/acg/`.
- No PR, no merge, no `main` commit, no force-push, no `--no-verify`. No `git add -A`, no
  `git stash`.
