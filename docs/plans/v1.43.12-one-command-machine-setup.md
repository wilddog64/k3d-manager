## Problem

The operator's MacBook Air M5 (32 GB, 1 TB) arrives on Wed 2026-10-28. The agreed layout has three roles:

| Machine | Role | Runs |
|---|---|---|
| M5 Air 32 GB | **hub** | k3d hub cluster, Claude sessions, tmux `work`, webhook, Hermes, port-forward and rotator LaunchAgents, weekly snapshot |
| M4 Air 24 GB | **worker** | Luna (Codex) dispatches, `make test` and pytest, ACG sandbox and Playwright login |
| M2 16 GB | **console** | browsing, Grafana, SSH into the other two, optionally off-hub snapshot copies |

Building a machine today means remembering about 12 `make install-*` targets, 18 LaunchAgent templates,
several setup scripts (`k3dm-webhook-setup`, `k3dm-hermes-setup`, `setup-vault-ca`), the tool versions
CI pins, and which Keychain items each component reads. Nothing writes this down in one place.
v1.43.8 showed the cost: ruff was missing on the Mac, so a lint error passed the local gate and failed
CI.

## Design

One script and one Make entry point, run per role:

    make machine-setup ROLE=hub|worker|console          # install and configure
    make machine-check ROLE=hub|worker|console          # read-only report, exit 1 if anything is missing

`bin/k3dm-machine-setup --role <role> [--check] [--dry-run]` sources lib-foundation like the other
`bin/` scripts, and routes privileged commands through `_run_command`.

### S1. Manifests, not code, say what a role needs

`scripts/etc/machine/` holds plain lists, one item per line, with `#` comments:

- `brew.<role>.list`: formulae and casks. Versions come from what CI pins where CI pins them
  (ruff `0.15.8`, kubeconform, promtool, bats, shellcheck, yamllint).
- `secrets.<role>.list`: Keychain service names (account `k3dm` unless the line says otherwise), each
  with a one-line purpose and the setup command that creates it. The worker list includes
  `gemini-cli-api-key` (query embedding for local `find-similar-docs`, plan 2 D7).
- `agents.<role>.list`: the `make install-*` targets and setup scripts to run, in order.
- `repos.list`: repositories to clone under `~/src/gitrepo/personal/` (k3d-manager, lib-foundation and
  the shopping-cart repos), each with the role(s) that need it.

The initial lists are derived from the code at implementation time: every `security find-generic-password`
service name, every `install-*` target and every LaunchAgent template. A test fails when a new LaunchAgent
template or `install-*` target exists that no role's list mentions (and is not on an explicit
`not-installed` list), so the manifests cannot rot silently.

### S2. Phases, each idempotent

1. **Preflight:** macOS on arm64, Xcode command line tools, Homebrew, `gh auth status`. A missing
   Homebrew prints the official install command and stops; the script does not pipe a remote installer
   into a shell.
2. **Tools:** `brew bundle`-style install of `brew.<role>.list`; pip-only tools (ruff, pytest) into a
   repo-local virtualenv that `make test` and `make lint-python` find.
3. **Repos:** clone what is missing; never touch an existing clone's working tree.
4. **Secrets (presence only):** for each name in `secrets.<role>.list`, check presence with
   `security find-generic-password -s <name> -a <account>` **without `-w`**. Report missing names with
   their setup command. In setup mode, offer to run that setup command; it prompts on the TTY. Values are
   re-entered or rotated on the new machine, never copied from another machine, never read, printed or
   logged by this script. With no TTY, the script does not prompt (a bare `-w` with no TTY stores an
   empty value at rc 0) and reports the item as missing instead.
5. **Agents:** run `agents.<role>.list` in order. Only the hub list installs hub LaunchAgents
   (port-forwards, rotators, webhook, Hermes, snapshot, cleanup). On a new hub, `make embed-cache-restore` runs before the first
   `make index-docs`.
6. **Report:** a table of every item with `ok`, `installed`, `missing` or `skipped (reason)`. The report
   holds no username, home path or secret value. `--check` prints the same table and changes nothing.

### S3. Out of scope

- Moving the hub cluster or its data. That stays the snapshot and restore path, and the operator
  decides when the M5 takes over (likely after the 10-29 drill).
- Changing the current M4 hub. Running `ROLE=worker` on the M4 must not uninstall hub agents while it
  is still the hub; removing them is a separate, explicit operator step documented in the how-to.
- SSH keys and cosign keys. The how-to names them as manual steps; the script only checks that
  `~/.ssh` has a key by file name, never reading it.

## What NOT to Do

- Do not copy, export or read Keychain values, SSH private keys or the cosign key.
- Do not modify existing clones, uninstall agents, or touch the running hub cluster.
- Do not rewrite the `install-*` targets or setup scripts; call them.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
