## Problem

The operator's MacBook Air M5 (32 GB, 1 TB) arrives on Wed 2026-10-28. The agreed layout has three roles:

| Machine | Role | Runs |
|---|---|---|
| M5 Air 32 GB | **hub** | k3d hub cluster, Claude sessions, tmux `work`, webhook, Hermes, port-forward and rotator LaunchAgents, weekly snapshot |
| M4 Air 24 GB | **worker** | Luna (Codex) dispatches, `make test` and pytest, ACG sandbox and Playwright login |
| M2 16 GB | **console** | browsing, Grafana, SSH into the other two, optionally off-hub snapshot copies |

Building a machine today means remembering about 12 `make install-*` targets, 18 LaunchAgent templates,
several setup scripts (`k3dm-webhook-setup`, `k3dm-hermes-setup`, `setup-vault-ca`), the tool versions
CI pins, and which Keychain items each component reads. Nothing writes this down in one place.
v1.43.8 showed the cost: ruff was missing on the Mac, so a lint error passed the local gate and failed
CI.

## Design

One script and one Make entry point, run per role:

    make machine-setup ROLE=hub|worker|console          # install and configure
    make machine-check ROLE=hub|worker|console          # read-only report, exit 1 if anything is missing

`bin/k3dm-machine-setup --role <role> [--check] [--dry-run]` sources lib-foundation like the other
`bin/` scripts, and routes privileged commands through `_run_command`.

### S1. Manifests, not code, say what a role needs

`scripts/etc/machine/` holds plain lists, one item per line, with `#` comments:

- `brew.<role>.list`: formulae and casks. Versions come from what CI pins where CI pins them
  (ruff `0.15.8`, kubeconform, promtool, bats, shellcheck, yamllint).
- `secrets.<role>.list`: Keychain service names (account `k3dm` unless the line says otherwise), each
  with a one-line purpose and the setup command that creates it. The worker list includes
  `gemini-cli-api-key` (query embedding for local `find-similar-docs`, plan 2 D7).
- `agents.<role>.list`: the `make install-*` targets and setup scripts to run, in order.
- `repos.list`: repositories to clone under `~/src/gitrepo/personal/` (k3d-manager, lib-foundation and
  the shopping-cart repos), each with the role(s) that need it.

The initial lists are derived from the code at implementation time: every `security find-generic-password`
service name, every `install-*` target and every LaunchAgent template. A test fails when a new LaunchAgent
template or `install-*` target exists that no role's list mentions (and is not on an explicit
`not-installed` list), so the manifests cannot rot silently.

### S1a. Workstation parity with the M4 (operator, 2026-10-29)

Operator: "ideally, homebrew and necessary development tools like m4, and you, codex, gemini configuration
private repos". Every role that runs agents (hub, worker) gets the M4's development environment, not only
the hub tooling:

- **Tools.** `brew.<role>.list` starts from the M4's `brew leaves` and `brew list --cask` at
  implementation time. The operator then marks each item keep or drop. M4-only items such as VirtualBox
  and Vagrant stay off unless kept. Tools installed outside Homebrew (`k3d` and `istioctl` in
  `~/.local/bin`) are installed at the versions the repo pins. Language toolchains (pyenv, rbenv, Go,
  Node, OpenJDK 21) come from the list. Agent CLIs (Claude Code, Codex, agy/Gemini, Copilot) are
  installed the same way the M4 installed them.
- **Agent configuration.** Cloned from the operator's private repos, only into an absent or empty target:
  `claude-settings` → `~/.claude`, `codex-settings` → `~/.codex`, `gemini-config` → `~/.gemini`, and
  `copilot-config` to the path the M4 uses. Each repo's `.gitignore` already excludes credentials,
  sessions and history (`.credentials.json`, `auth.json`, `oauth_creds.json`, `history.jsonl`,
  `sessions/`). The script never copies those files. It ends with the login steps (`claude` `/login`,
  `codex login`, agy/Gemini auth, `gh auth login`) for the operator to run at the TTY.
- **Shell (operator, 2026-10-29).** `zshdotfiles` is cloned into `~/src/gitrepo/personal/zshdotfiles`, as
  on the M4. Then `~/.zsh` is symlinked to it, and `~/.zshrc` → `~/.zsh/zshrc` and `~/.zshenv` →
  `~/.zsh/zshenv` are linked the same way. An existing regular file in any of those places is moved to
  `<name>.pre-machine-setup`, never deleted.
- **Same `~/src` layout as the M4 (operator, 2026-10-29).** `repos.list` is generated from the M4 at
  implementation time. Each line records the path relative to `~/src`, the remote, the branch, and the
  role(s) that need it. The M4 today has 50 checkouts: `gitrepo/code-review-graph`, and 49 under
  `gitrepo/personal/`, in the subfolders `ansible/`, `python/`, `shopping-carts/` and `articles/tech`.
  Setup reproduces the paths exactly, so the path-keyed Claude memory and the hard-coded sibling paths
  (`../lib-foundation`, `shopping-carts/<repo>`) work unchanged. The generator handles these cases:
  - Second checkouts (`shopping-cart-frontend-tw4` on `chore/tailwind-v4-migration`,
    `shopping-cart-infra-ldap` on `fix/remove-orphan-osixia-ldap`) are cloned on their branch. If the
    branch is merged or deleted upstream, the line is reported and skipped.
  - `tmp-*` scratch checkouts (`tmp-trivy/`) are not copied.
  - Bitbucket remotes (`bde`, `pygit`, `python/dreambox-pythonlib`, three `ansible/` repos) need the
    operator's Bitbucket SSH key. Without it, setup reports them as skipped and continues.
  - `articles/` has no remote. Only its `tech` checkout is cloned.
  - Third-party clones (`code-review-graph`, `smartcd`) come from their upstream remotes.
  - `k3dm-hub-data` is not cloned; the hub reads it through `hub-data-recover`.

  Clones use `gh repo clone` or `git clone` with the operator's own auth.
- **smartcd, direnv and the agent-state backup (operator, 2026-10-29).** On the M4, entering
  `~/src/gitrepo/personal` runs the untracked `.envrc` there through direnv. It calls
  `~/.local/bin/sync-claude`, `sync-gemini`, `sync-codex` and `sync-copilot`, which commit and push
  `~/.claude`, `~/.gemini`, `~/.codex` and `~/.copilot` to `claude-settings`, `gemini-config`,
  `codex-settings` and `copilot-config` ("chore: sync on <date> — <repo>"). That is the backup, and
  setup restores it in this order:
  1. Clone `smartcd` (upstream `cxreg/smartcd`) and install it to `~/.smartcd/lib`. Its config is
     `~/.zsh/smartcd_config`, already tracked in zshdotfiles.
  2. Install `direnv` from the brew list. `~/.zsh/direnvrc` is tracked; link it to
     `~/.config/direnv/direnvrc` if the M4 does (checked at implementation time).
  3. Link `~/.local/bin/sync-*` to `zshdotfiles/scripts/` exactly as on the M4. `sync-claude` and
     `sync-gemini` link to their own scripts; `sync-codex` and `sync-copilot` link to
     `sync-agent-state.sh`.
  4. Clone the four config repos into place (see Agent configuration) **before** the first `cd` into
     `~/src`, so the first sync commits onto a real clone, never an empty directory.
  5. Restore the untracked files the chain depends on: the four smartcd `bash_enter` scripts under
     `~/.smartcd/scripts/` (for `~/src`, `gitrepo/personal`, `k3d-manager` and
     `ansible/provision-win-tomcat`), and the untracked `.envrc` files in `gitrepo/personal`,
     `k3d-manager` and `ansible`. None of them is in a repo today. Before implementation they move into
     a tracked home (zshdotfiles is the natural one), with any secret values replaced by Keychain or
     Vault lookups; the operator reviews each file. Setup links them into place and runs
     `direnv allow` on each. The 17 `.envrc` files already tracked in their repos arrive with the
     clones and still need `direnv allow`.

  **Two machines, one backup repo.** Both Macs would commit and push the same four repos. Before the
  M5 runs its first sync, each sync script must `pull --rebase` before committing, and must stop
  and report on a conflict rather than force-push. Until that holds, only one machine runs the sync,
  and setup tells the operator which one. Each machine's commit subject names its host, so the
  history shows which machine wrote what.
- **Loose files.** `~/src/gitrepo/personal/CLAUDE.md`, `AGENTS.md` and `GEMINI.md` are in no repo, yet
  every agent session there reads them. Before implementation they move into a tracked home: the
  operator's decision, for example `claude-settings` or a small `workspace-config` repo. Setup then links
  them into place. The `lib-acg-final-archive-*.bundle` is an archive, not a working file; it stays on the
  M4 and the operator's backup.

### S2. Phases, each idempotent

1. **Preflight and bootstrap:** macOS on arm64, Xcode command line tools, Homebrew, `gh auth status`.
   **No manual prep (operator, 2026-10-29).** Setting up the M5 by hand took several separate steps,
   each needing a correction: installing the CLT, downloading Homebrew, `gh auth login`,
   `gh auth setup-git`, and cloning the four config repos plus zshdotfiles and k3d-manager. The one
   command does all of them, starting from a Mac that has none of them.
   - **First step without git.** A fresh Mac has no `git` until the CLT are installed, so the entry
     point cannot assume a k3d-manager clone. A small `bin/machine-bootstrap` runs before the clone:
     the operator fetches it as a single file and **reads it before running it**. It is never piped into
     a shell. It installs the CLT and Homebrew, logs in to gh, clones k3d-manager, then hands off to
     `make machine-setup`. The same steps run idempotently from `make machine-setup` on a machine
     that already has the clone.
   - **CLT:** skipped when `xcode-select -p` succeeds. Otherwise the current
     `Command Line Tools for Xcode` label is read from `softwareupdate --list` and installed with
     `softwareupdate --install "<label>"`. The label is not hard-coded, because it changes with every
     Xcode release (26.6 on 2026-10-29).
   - **Homebrew:** skipped when `/opt/homebrew/bin/brew` exists. Otherwise the script downloads
     `https://github.com/Homebrew/brew/releases/latest/download/Homebrew.pkg`. The asset is named
     `Homebrew.pkg`, with no version in the name: a `Homebrew-<version>.pkg` match found nothing on
     2026-10-29. It then checks `pkgutil --check-signature` for a notarized Developer ID Installer
     signature from Homebrew's team ID `927JGANW46`, and runs `installer` through
     `_run_command --require-sudo`. It refuses on any other signer, and never pipes a remote script
     into a shell. The CLT and Homebrew installs share one sudo prompt.
   - **gh:** `brew install gh tmux`. When `gh auth status` fails, the script runs `gh auth login`
     on the TTY, with no TTY it reports instead. It then runs `gh auth setup-git`, so HTTPS clones
     and the sync scripts' pushes can authenticate. A login stored in `~/.config/gh/hosts.yml`
     instead of the Keychain is reported, with the command to move it. That is what happened when
     the M5 logged in over SSH.
   - **Config repos** clone directly as the dot-folders, matching the M4: `claude-settings` →
     `~/.claude`, `codex-settings` → `~/.codex`, `gemini-config` → `~/.gemini`,
     `copilot-config` → `~/.copilot`. An existing folder that is not a clone of the expected
     remote is reported and left alone.
   The console username must match the M4's, so the path-keyed Claude memory directories under
   `~/.claude/projects/` resolve unchanged; a mismatch is reported, not worked around.
2. **Tools:** `brew bundle`-style install of `brew.<role>.list`; pip-only tools (ruff, pytest) into a
   repo-local virtualenv that `make test` and `make lint-python` find.
3. **Repos:** clone what is missing; never touch an existing clone's working tree.
4. **Secrets (presence only):** for each name in `secrets.<role>.list`, check presence with
   `security find-generic-password -s <name> -a <account>` **without `-w`**. Report missing names with
   their setup command. In setup mode, offer to run that setup command; it prompts on the TTY. Values are
   re-entered or rotated on the new machine, never copied from another machine, never read, printed or
   logged by this script. With no TTY, the script does not prompt (a bare `-w` with no TTY stores an
   empty value at rc 0) and reports the item as missing instead.
5. **Agents:** run `agents.<role>.list` in order. Only the hub list installs hub LaunchAgents
   (port-forwards, rotators, webhook, Hermes, snapshot, cleanup). On a new hub, `make embed-cache-restore` runs before the first
   `make index-docs`.
6. **Report:** a table of every item with `ok`, `installed`, `missing` or `skipped (reason)`. The report
   holds no username, home path or secret value. `--check` prints the same table and changes nothing.

### S3. Out of scope

- Moving the hub cluster or its data. That stays the snapshot and restore path, and the operator
  decides when the M5 takes over (likely after the 10-29 drill).
- Changing the current M4 hub. Running `ROLE=worker` on the M4 must not uninstall hub agents while it
  is still the hub; removing them is a separate, explicit operator step documented in the how-to.
- SSH keys and cosign keys. The how-to names them as manual steps; the script only checks that
  `~/.ssh` has a key by file name, never reading it.

## Decisions (operator, 2026-10-29)

- **D1. One tracked home: `zshdotfiles`.** The three untracked `.envrc` files (`gitrepo/personal`,
  `k3d-manager`, `ansible`), the four smartcd `bash_enter` scripts and the loose `CLAUDE.md`,
  `AGENTS.md` and `GEMINI.md` in `~/src/gitrepo/personal` move into `zshdotfiles`. The operator
  moves them and reviews each file, replacing any secret value with a Keychain or Vault lookup;
  Claude does not read them. Setup links them into place from the zshdotfiles clone and runs
  `direnv allow`. `repos.list` and the how-to name the zshdotfiles paths once they exist.
- **D1a. One workspace instruction file, not three (operator, 2026-10-29).** The workspace-level
  `CLAUDE.md`, `AGENTS.md` and `GEMINI.md` are identical today (only the code-review-graph section).
  zshdotfiles keeps one file, `CLAUDE.md`, holding only rules that apply to every repo under
  `~/src/gitrepo/personal`. Setup links it into place and makes `AGENTS.md` and `GEMINI.md` links to the
  same file, so they cannot drift. Repo-specific rules stay in each repo's own agent files. The content
  never lives in k3d-manager: it is public and changes branch constantly, and a link into its working
  tree would make every repo's instructions depend on the checked-out branch. k3d-manager owns only the
  setup that links it.
  The shared file opens with an instruction-precedence preamble (operator, 2026-10-29), in this order:
  security and platform restrictions; the operator's in-session instructions; repository instructions;
  shared defaults; task specs, which narrow and never loosen (an exception goes on the spec's
  `**Approval:**` line). A real conflict the order does not settle means stop and ask. A short
  layer-1 security list follows, then the shared defaults. Claude drafted it; the operator approves the
  text and merges it. Approved 2026-10-29 ("go for that"); zshdotfiles branch `docs/workspace-claude-md`
  `4800546` adds `workspace/CLAUDE.md` (preamble + the code-review-graph section). Merged 2026-10-29 as zshdotfiles PR #2 (`880aa24`).
- **D2. Sync scripts fixed by Claude on a zshdotfiles branch.** `sync-claude`, `sync-gemini` and
  `sync-agent-state.sh` get `pull --rebase` before committing, stop and report on a conflict (never
  force-push), and name the host in the commit subject. The operator reviews and merges. Until it
  merges, only the M4 runs the sync, and setup on the M5 says so.
  Done 2026-10-29: zshdotfiles `fix/sync-two-machines` `f985522` (one file, `scripts/sync-agent-state.sh`;
  `sync-claude` and `sync-gemini` are symlinks to it). Two-clone test: concurrent syncs rebase and push,

## What NOT to Do

- Do not copy, export or read Keychain values, SSH private keys or the cosign key.
- Do not modify existing clones, uninstall agents, or touch the running hub cluster.
- Do not rewrite the `install-*` targets or setup scripts; call them.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
