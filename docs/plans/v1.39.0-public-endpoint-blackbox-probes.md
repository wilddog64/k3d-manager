# v1.39.0 — Blackbox probes over the public hostnames, and a tunnel-down alert

**Status:** spec, not implemented
**Target branch:** `k3d-manager-v1.39.0`
**Carried:** Carried from v1.38.0 unimplemented (scope decision 2026-09-26). v1.38.0 shipped five specs and implemented one; this is one of three carried.
**Motivation:** two silent public outages. Nothing in this repo observes the public path.
**Bug evidence:** `docs/bugs/2026-09-25-frontend-public-url-routes-to-wrong-cluster.md`

---

## The gap, stated precisely

Three independent facts, each verified on 2026-09-25:

1. `make status` produces **no metrics**. There is no Pushgateway writer anywhere in `scripts/` or
   `bin/` — no `push_to_gateway`, no `metrics/job/`, no curl to Pushgateway. Its results live only
   in the operator's terminal, so no rule can fire from them.
2. **No blackbox exporter exists anywhere in the repo** — zero matches for `blackbox`. Prometheus
   scrapes in-cluster targets only, so the edge → tunnel → origin path is entirely unobserved.
3. The rule that would cover the storefront is `ServiceDown`
   (`sum by (namespace)(kube_pod_status_ready{condition="true", namespace=~"shopping-cart.*"}) == 0`).
   It is correctly silent when pods are healthy and only the public route is broken — which is
   exactly what happened.

Alert **delivery** is not the problem: `scripts/etc/prometheus/alertmanager.yaml.tmpl` already routes
`severity = critical` to `sms-critical`. The missing piece is a producer.

## P1 — deploy blackbox-exporter on the hub

Namespace `monitoring`, managed by ArgoCD like the rest of the stack, chart version **pinned**.

Probing from inside the hub is deliberate: the request leaves the network, traverses Cloudflare's
edge and the tunnel, and comes back. That is the path users take and the path nothing currently
tests.

### Two modules, not one

A single module with a naive `valid_status_codes` is the trap here. Four of the seven hosts do not
return 200 when healthy, and one returns 404 while broken — so the status list decides whether this
whole feature works:

```yaml
modules:
  http_public_ui:
    prober: http
    timeout: 10s
    http:
      valid_status_codes: [200, 301, 302]
      valid_http_versions: ["HTTP/1.1", "HTTP/2.0"]
      follow_redirects: false
      preferred_ip_protocol: ip4
      headers:
        User-Agent: "k3dm-blackbox/1.0 (+https://github.com/wilddog64/k3d-manager)"
  http_authenticated:
    prober: http
    timeout: 10s
    http:
      valid_status_codes: [200, 401]
      valid_http_versions: ["HTTP/1.1", "HTTP/2.0"]
      follow_redirects: false
      preferred_ip_protocol: ip4
      headers:
        User-Agent: "k3dm-blackbox/1.0 (+https://github.com/wilddog64/k3d-manager)"
```

`http_public_ui` for argocd, frontend, keycloak, grafana; `http_authenticated` for prometheus,
alertmanager, webhook.

**The `User-Agent` header is required, not cosmetic.** Cloudflare returns 1010 to requests with a
missing or default client UA, which would make every probe fail identically and teach everyone to
ignore the alert. See `reference_cloudflare_1010_ua_block`.

`follow_redirects: false` keeps a 302 to a login page a *success* for the UI hosts rather than
chasing into an auth flow whose status is not ours to assert.

**Accepting 401 has a known blind spot:** an auth proxy that 401s unconditionally — including when
its backend is gone — looks healthy. That is the deliberate trade for not putting credentials in a
probe. Record it in the guide so nobody reads a green probe as "Prometheus is serving data."

## P2 — Probe resources and the scrape config

Use the prometheus-operator `Probe` CRD, one per module, with `staticConfig.targets` built from
`CF_DOMAIN`. Interval 60s.

**The `release` label is load-bearing.** The stack's serviceMonitorSelector /
probeSelector matches on `release`, and a resource without it is silently skipped — no error, no
target, just absence. Confirm the targets actually appear in the TSDB
(`count(probe_success)` equals the number of hostnames), not merely that the object was created.
See `reference_helm_subchart_servicemonitor_no_release_label`.

## P3 — Three alert rules

New file `scripts/etc/prometheus/rules/public-endpoints.yaml`, group `public.endpoints`,
interval 60s.

```yaml
- alert: PublicEndpointDown
  expr: probe_success{job=~".*blackbox.*"} == 0
  for: 5m
  labels:
    severity: critical
    cluster: hub
  annotations:
    summary: "Public endpoint {{ $labels.instance }} is failing its probe"
    description: "{{ $labels.instance }} has failed the blackbox probe for 5 minutes. Last status code: {{ with printf `probe_http_status_code{instance=%q}` $labels.instance | query }}{{ . | first | value }}{{ end }}."

- alert: CloudflareTunnelDown
  expr: sum(probe_success{job=~".*blackbox.*"}) == 0
  for: 3m
  labels:
    severity: critical
    cluster: hub
  annotations:
    summary: "Every public hostname is failing — tunnel or edge is down"
    description: "All blackbox probes are failing simultaneously, which points at the cloudflared tunnel or the Cloudflare edge rather than any one service."

- alert: PublicEndpointProbeAbsent
  expr: absent(probe_success{job=~".*blackbox.*"})
  for: 15m
  labels:
    severity: critical
    cluster: hub
  annotations:
    summary: "The public endpoint probes have stopped reporting"
    description: "No probe_success series for 15 minutes. The exporter, the Probe resource, or the scrape is broken — public availability is currently unmonitored."
```

`PublicEndpointDown` and `CloudflareTunnelDown` will both fire in a full outage. That is intended —
the second names the cause and is the one worth waking up for. Do **not** suppress one with the
other via an inhibit rule in this change; get real firing history first.

`PublicEndpointProbeAbsent` is the rule that makes this trustworthy. Without it, a broken probe is
indistinguishable from healthy silence, which is the exact failure mode this whole spec exists to
fix. Note that it cannot cover the hub itself being down — nothing inside the hub can. Say so in
the guide rather than implying full coverage.

`group_wait` for `sms-critical` is 5m, so expect roughly 8–10 minutes from outage to SMS for a
single endpoint and 8 minutes for a full tunnel outage. Acceptable; do not shorten the global
`group_wait` for this.

## What NOT to Do

- Do NOT put any credential in a probe. The 401 blind spot is accepted, documented, and not to be
  solved by giving the exporter a token.
- Do NOT edit `~/.cloudflared/config.yml` or restart the tunnel as part of this change. It serves 7
  public hostnames and a bad edit takes all of them down; that has already happened once.
- Do NOT fix the `frontend` 404 here. It is a separate decision with its own bug doc, and this
  change needs it broken as a live positive control.
- Do NOT add an inhibit rule between `PublicEndpointDown` and `CloudflareTunnelDown` yet.
- Do NOT route any of these to `platform-warning` to reduce noise. A public endpoint being down is
  the case SMS exists for.
- Do NOT use `latest` for the chart or the image.
