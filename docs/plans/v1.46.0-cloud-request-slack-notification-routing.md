## Problem

A cloud request (`bin/k3dm-cloud-request` → `cloud-requests` branch → `bin/k3dm-cloud-bridge` → local webhook) carries no Slack
context: the bridge builds the webhook body only from allowlisted `args` plus the fixed part (`bin/k3dm-cloud-bridge:338-349`),
so the webhook writes no `channel_id` for the job (`bin/k3dm-webhook:2817-2836`) and `_notify_job` posts to the process-wide
`SLACK_CHANNEL_ID` (`bin/k3dm-webhook:1333-1339`; `scripts/lib/webhook/config.py:38`). A long `make-test-all` cannot report into
the test channel without moving every other notice.

Cloud requests already reach three destinations, not one:

| Destination | Used by | Where |
|---|---|---|
| `SLACK_CHANNEL_ID` (task channel) | `make-*`, `sandbox-up/down` jobs | `bin/k3dm-webhook:1333-1339` |
| `K3DM_STATUS_CHANNEL_ID` | `cluster-status`, `hostinger-status`, `diagnose-*` with no Slack context | `scripts/lib/webhook/status.py:78-89` |
| Keychain `k3dm-slack-webhook` relay | the approval card for gated actions | `bin/k3dm-cloud-bridge:67-70,785` |

## Design (rev 1)

- **Route map.** `alias:CHANNEL_ID[,alias:CHANNEL_ID...]`, read from `K3DM_SLACK_NOTIFICATION_ROUTES` or else Keychain
  `k3dm-slack-notification-routes` (account `k3dm`), the same pattern as the role map (`scripts/lib/webhook/auth.py:113`). One
  loader module, `scripts/lib/webhook/notify_routes.py` (p2a), used by the bridge (alias names only) and the webhook (resolves
  the ID). Limits: alias `^[a-z][a-z0-9-]{0,31}$`, channel ID `^[CG][A-Z0-9]{8,11}$`, at most 8 aliases, raw value at most 512
  bytes, no duplicate alias or channel ID, `default` reserved. Any violation makes the whole map invalid (fail closed).
- **No route = today, byte for byte.** A request without `notify_route` produces the same request JSON, webhook body, job
  files and Slack destination as before. There is no configurable "default".
- **Request field.** Optional top-level `notify_route` (schema stays 1): fields are exactly the six, or the six plus
  `notify_route`. CLI flag `--notify-route ALIAS` (p2c).
- **Routable actions.** Only actions whose messages all go through `_notify_job`: allowlist path `/api/v1/make` or
  `sandbox-up`/`sandbox-down`. Any other action with `notify_route` is rejected with `notification route not supported for this
  action` (status reports would otherwise post nothing: `scripts/lib/webhook/status.py:67-73`).
- **Validation points.** The bridge checks shape, routability and that the alias is configured **before** approval admit (an
  invalid alias posts no card and uses no card slot) and again at execute; a failure is a fixed `invalid notification route`
  rejection, never a fallback. The reason never lists aliases (responses are committed to a branch any session reads).
- **Bridge → webhook.** The bridge adds `notify_route` to the body; it never forwards `channel_id`, `response_url` or
  `thread_ts` from request data. The webhook resolves the alias at job creation, writes `notify_route` and the resolved
  `channel_id` into the 0700 job directory (the route is then fixed for the job, across a map change or restart), and returns
  400 if `notify_route` arrives with any of the three Slack context fields.
- **No spill on failure.** A routed job never posts to `K3DM_SLACK_WEBHOOK_URL` or `SLACK_CHANNEL_ID`; an undelivered message
  is recorded in `delivery.jsonl` with `delivered: false` and a new `notify_route` key (the existing `route` key keeps its
  meaning, `bin/k3dm-webhook:1366-1379`).
- **Approval card.** Shows `Notifications: <alias>` (through `_safe`) when present; the card itself always goes to the fixed
  `k3dm-slack-webhook` destination.
- **Where channel IDs may appear.** Never in a blob committed to `cloud-requests`, in `approvals.json`, or in the bridge's
  webhook response handling; the local job directory and `delivery.jsonl` may hold them (they already do).
- **Label escaping.** For a routed job, the request-derived job label (`scripts/lib/webhook/lifecycle.py:164`) has `&`, `<`, `>`
  escaped so request text cannot form a Slack mention; unrouted jobs are unchanged.

## Decisions (operator, 2026-11-26)

- **D1 — where aliases live:** Keychain item plus env override, shared loader. Operator: "Keychain item (Recommended)".
  (Neon proposed plist-only plus a read-only `GET /api/v1/notification-routes`; not adopted: plist values are dropped by
  `bin/k3dm-webhook-setup:94-97`, which keeps only three keys, the class of `docs/bugs/2026-10-31-hub-migration-drops-webhook-slack-bot-config.md`.)
- **D2 — route trust:** routing allowed for `make-*` and `sandbox-up/down`; recorded **accepted risk**: an ungated action such
  as `make-test-all` can be routed by anyone who can push to `cloud-requests`, without an approval. Mitigations: only
  low-audience channels may be aliased (no incident or announcement channels), label escaping, the card shows the route for
  gated actions. Operator: "Accept, limit aliases (Recommended)".
- **D3 — Slack `/k3dm` may not pick a route; `default` is not configurable.** Both reviewers and Claude agreed; slash commands
  already carry their own channel (`workers/slack-relay/index.js:534-536`), and `parse_make_request` refuses unknown keys
  (`scripts/lib/webhook/make_targets.py:85-87`).
