## 1. Why

On 2026-10-02 the hub had five firing alerts. Claude triaged them by hand in one session:

| Alert | What found the cause | Kind of fix |
|---|---|---|
| `KubeJobFailed` (ldap rotator) | Job conditions, image contents, live CronJob env | Code (`96af55b1`) |
| `KubeHpaMaxedOut` ×2 | HPA min/max/current | Config (`119f8a7b`) |
| `CPUThrottlingHigh` (ArgoCD controller) | Throttle ratio, reconcile counts per app, controller log | Config (`efaf4038`) |
| `PrometheusOutOfOrderTimestamps` | Prometheus log per `scrape_pool`, federate payload | Config (`8b792fcc`) |
| `E2EVerificationFailing` | Existing E2E triage + source reading | Code, three repos |

Two lessons set the scope:

1. **The diagnostics were mechanical; the fixes were not.** Every first step was a fixed read-only query keyed by
   the alert name. A recipe can do that in seconds, every time, at 3 a.m.
2. **No alert was fixable by a runtime action.** All five were defects in git. Restarting, deleting or scaling would
   have cleared a symptom and hidden the defect. So "fix automatically" means **triage and draft automatically, repair
   with approval**, and a code fix still goes spec → Codex → review → PR.

Nothing watches Alertmanager today. Hermes' `alert_delivery` sensor checks that alerts *can* be delivered, not what is
firing. Alerts reach the operator only as e-mail/SMS, with no evidence attached.

## 2. Goal

When an alert fires on a watched cluster, Hermes, within one poll cycle and with no new credentials:

1. **sees it**, from Alertmanager, read-only;
2. **collects evidence** with a per-alert read-only recipe;
3. **finds prior art** (`docs/bugs/` exact slug, then `prior_art` similarity);
4. **reports** it in Slack, by severity (§3.4): `critical` gets its own thread; `warning` and `info` go into one
   daily digest. Every entry carries what fired, the evidence, the likely cause and the matching bug doc;
5. **proposes** an allowlisted repair, only where one exists and its precondition holds, through the existing
   `repairs.propose()` → Slack approval → `repairs.approve()` path;
6. otherwise **drafts a bug doc** in Hermes' own worktree, the way `e2e_bugs.file_bugs` does for E2E failures.

## 3. Design

### 3.1 Ingest — new sensor `alerts`

- Source: `GET /api/v2/alerts?active=true&silenced=false&inhibited=false` through the kube-apiserver service proxy
  (`kubectl --context <ctx> get --raw /api/v1/namespaces/monitoring/services/<alertmanager-svc>:9093/proxy/api/v2/alerts`).
  It uses the kubeconfig Hermes already uses for `node_pressure` and `app_health`. There is no port-forward, no new
  token, and no inbound listener; this is the Phase 1 pull model.
- Clusters: `k3d-k3d-cluster` (hub) and `ubuntu-hostinger`. ACG sandboxes are ephemeral and excluded.
- Ignore `Watchdog` and `InfoInhibitor`, the same exclusion as the Overview's Firing Alerts panel (`665da724`).
- Group key: `alertname` + `cluster` + the alert's identifying labels (`namespace`, plus one of `job_name`, `pod`,
  `horizontalpodautoscaler`, `scrape_pool`). The record carries `startsAt` and the fingerprint.
- Debounce like the other sensors: act only after an alert has been seen for 2 consecutive cycles, so a flap does not
  page Slack.

### 3.2 Recipes — `scripts/lib/hermes/alert_recipes.py`

A table `alertname → recipe`. Each recipe is a pure function: alert labels → a list of **read-only** commands → a
bounded, redacted evidence dict plus a one-line `likely_cause`. A grep invariant in the tests enforces read-only:
`get`, `describe`, `logs`, `top`, and Prometheus `query`/`query_range` only; never `exec` into an app pod, and never
`describe secret` or `-o` on a Secret.

First recipes, from today's alerts:

| Alert | Evidence collected | `likely_cause` classifier |
|---|---|---|
| `KubeJobFailed` | Job conditions, owning CronJob `lastSuccessfulTime`, last pod log tail (if any) | "never succeeded since creation" vs "regressed after N successes" |
| `KubeHpaMaxedOut` | HPA min/max/current, CPU vs target | `min == max` → "pinned HPA, can never clear" |
| `CPUThrottlingHigh` | Throttled ratio 1h, limit/request, 24h CPU avg/max; for `argocd-application-controller`, reconciles per app (10 min) | "limit too low" vs "workload storm" (top-N share above 50%) |
| `PrometheusOutOfOrderTimestamps` | `num_dropped` by `scrape_pool` from the Prometheus log | names the scrape pool |
| `KubePodCrashLooping` | Restart count, last terminated reason, previous-container log tail | OOMKilled / probe / exit code |
| `TargetDown`, `KubeAPIDown` | Target health, last scrape error, scrape duration vs timeout | per `reference_disappeared_from_target_discovery_is_kubeapidown` |
| `E2EVerificationFailing` | none: delegates to `e2e_triage`, reports its result | |
| *(no recipe)* | Alert labels, annotations, 48h firing history (`ALERTS` range query) | "no recipe; manual triage" |

The 48h firing history is collected for every alert, following the rule to deep-dive every reported alert.

### 3.3 Route — repair, bug draft, or report only

- **Repair proposal:** only through `repairs.REPAIRS`. Each recipe may name the repair key it can map to, and the
  repair's own precondition still decides. Example: a `KubeJobFailed` whose CronJob spec changed after the failure
  maps to a new repair, R10 (see decision 3).
- **Bug draft:** if no repair applies and no open bug doc matches, write `docs/bugs/<date>-alert-<slug>.md` in Hermes'
  worktree with evidence, cause and history. If a doc already matches: when it is FIXED or CLOSED, reopen it as a
  recurrence; when it is open, only link it in Slack. Reuse `e2e_bugs.file_bugs`' worktree, branch-guard, reopen and
  commit logic; factor it out rather than copy it.
- **Report only:** a severity below the threshold, or an alert whose recipe classifies it as "expected while X".

### 3.4 Slack

Placement is by the alert's `severity` label (decision 1):

- **`critical`:** one threaded message per new alert group, updated in place while it fires, with a final reply when it
  resolves. Top line: `[FIRING] <alert> on <cluster> — <likely_cause>`. Thread replies hold the evidence, the prior
  art link, and any repair proposal with Approve/Deny buttons.
- **`warning` and `info`:** one daily digest message, one line per alert group (alert, cluster, how long it has fired,
  `likely_cause`, bug doc link), with the evidence in the digest's thread. Use the once-per-period stamp pattern of
  the monthly audit (`audit.py`), keyed by UTC date. A repair proposal for one of these still posts on its own, because
  an approval must be actionable the same day.
- Unlabelled severity is treated as `warning`.

Severity decides only the Slack placement. Recipes, prior-art lookup and bug drafts run for every alert regardless.
All five alerts from 2026-10-02 are `warning` or `info` (`CPUThrottlingHigh` is `info`), so under this rule all five
would land in the digest.

## 4. Non-goals (hard boundaries)

- **No automatic code changes, PRs or merges.** Hermes never edits a file outside `docs/bugs/` in its own worktree,
  and never dispatches Codex. Spec → Codex stays an operator-initiated step.
- **No auto-executed repair.** The `repairs.approve()` invariant is unchanged. The one existing exception
  (`auto_remediate_kine`, default off) is not extended.
- **No new credentials or scopes.** Read-only kubeconfig use only; Alertmanager via the apiserver proxy.
- **No silencing.** Hermes never creates Alertmanager silences or edits alert rules; a noisy rule is a bug draft.
- **No alert storms.** At most N new Slack threads per cycle (default 5); the rest are summarised in one message.

## 6. Definition of done

- Replay test: today's five alerts, as captured `/api/v2/alerts` JSON plus recorded command outputs, produce five
  digest entries with the correct `likely_cause`, one E2E delegation, and four bug-doc matches by slug (linked, not
  refiled). A synthetic `critical` copy of one of them produces a thread instead.
- A live check on the hub: a deliberately failing test Job in a scratch namespace fires `KubeJobFailed`, and Hermes
  posts it within two cycles. The operator runs this.
- `docs/guides/hermes.md` gains an "Alert triage" section: the recipe table, how to add a recipe, and the
  boundaries.
- The roadmap's Hermes Phase 2/3 entry is updated to say what shipped.

## 7. Risks

- **Wrong `likely_cause` misleads.** Mitigation: the evidence is always shown with the classification, and a
  classifier that does not match says "unclassified", never guesses.
- **Bug-doc spam from flapping alerts.** Mitigation: debounce, the exact-slug match, and reopening instead of creating.
- **Evidence leaks a secret.** Mitigation: the read-only invariant forbids Secret reads; log tails pass through the
  existing `_redact_status`-style redaction and are length-capped.

## 8. Decisions (operator, 2026-10-02)

1. **Slack placement by severity:** `critical` → its own thread; `warning` (and `info`) → daily digest. See §3.4.
2. **Bug drafts from Hermes' worktree:** yes, the same model as E2E bugs (committed on the release branch in Hermes'
   worktree and pushed).
3. **R10, delete a failed Job superseded by a newer CronJob spec:** yes, approval-gated, limited to an allowlist of
   namespaces (`identity`, `monitoring`, `cicd`). Ships in v1.43.0 (§5).
4. **Release placement:** fill v1.42.0 to its five-plan cap, overflow to v1.43.0 (§5). Both this and the daily
   verification plan touch the Hermes scheduler and poll loop, so their specs must be written against each other.
