# v1.36.0 — Keycloak admin credential rotator

**Status:** SPEC — ready for implementation
**Branch:** `k3d-manager-v1.36.0`
**Owner:** Codex
**Filed:** 2026-09-21

---

## Why

Grafana, ArgoCD and Prometheus each have a monthly credential rotator. **Keycloak has none**, so
its admin password is the one service credential with no rotation path — and it is the credential
that leaked into a session transcript on 2026-09-21. Rotating it today requires a hand-run
multi-step procedure that is easy to get half-right, and getting it half-right locks the operator
out of the console.

This spec adds `keycloak-credential-rotator` so Keycloak can be rotated the same way as the
others: one job, on a schedule, with a rollback on failure.

### Keycloak is NOT a copy of the Grafana rotator — four verified differences

Do not clone `grafana-credential-rotator.yaml` and swap names. All four of these were verified
against the live hub, and each one breaks a naive copy.

**1. The Kubernetes Secret is a bootstrap-only input.** Keycloak's password reaches the pod as
`KEYCLOAK_ADMIN_PASSWORD` in the `keycloak-secrets` Secret, which the chart consumes to *create*
the admin user on first start. The user then lives in the Postgres database. Updating the Secret
and restarting does **not** change the live password. So unlike Grafana — where the restart is
what applies the change — the authoritative write here is into Keycloak itself, via its Admin
REST API. A rotator that only updates Vault and restarts will report success and change nothing.

**2. The ExternalSecret is ArgoCD-managed with `selfHeal=true`, so the force-sync annotation
trick does not transfer.**

| | ExternalSecret | ArgoCD tracking-id | selfHeal |
|---|---|---|---|
| Grafana | `grafana-admin-credentials` (ns `monitoring`) | **none** — applied directly | n/a |
| Keycloak | `keycloak-secrets` (ns `identity`) | `shopping-cart-identity` | **true**, prune true |

The Grafana job does `kubectl annotate externalsecret … force-sync=$(date +%s)`. On
`keycloak-secrets` that is an out-of-band mutation of an ArgoCD-managed resource and selfHeal
will revert it. **Do not annotate it.** The Secret does not need to update promptly anyway (see
difference 1) — it refreshes on its own `refreshInterval: 15m0s`.

**3. The Vault secret is shared with the database credential.** `secret/keycloak/admin` holds
**both** `admin_password` and `db_password`:

```
keycloak-secrets (ns identity), store vault-kv-store:
  KEYCLOAK_ADMIN_PASSWORD  <- secret/data/keycloak/admin  property admin_password
  KC_DB_PASSWORD           <- secret/data/keycloak/admin  property db_password
  LDAP_BIND_CREDENTIAL     <- secret/data/ldap/openldap-admin  property LDAP_ADMIN_PASSWORD
```

A KV v2 write replaces the whole secret. Writing only `admin_password` **destroys
`db_password`** and breaks Keycloak's database connection on its next restart. The rotator MUST
read the existing secret, change one field, and write both back. `db_password` must never be
rotated by this job — rotating it requires rotating the Postgres user too, which is out of scope.

**4. There are two divergent in-repo notions of this secret's schema, and only one is live.**
`scripts/plugins/keycloak.sh:179` (`_keycloak_seed_vault_admin_secret`) writes a single key
`password`, and `scripts/etc/keycloak/externalsecret-admin.yaml.tmpl` targets a Secret named
`keycloak-admin-secret` reading property `password`. **Neither is what runs.**
`keycloak-admin-secret` does not exist on the live cluster; the deployed ExternalSecret is
`keycloak-secrets`, sourced from the `shopping-cart-infra` repo
(`identity/keycloak/keycloak-secrets-externalsecret.yaml`), and it reads `admin_password`.

**Build the rotator against the live schema (`admin_password` / `db_password`).** Do NOT "fix"
`keycloak.sh` or the template in this spec — that divergence is a separate defect and is out of
scope here (see Non-goals). Just do not let it mislead you.

## Non-goals

- **Do NOT rotate `db_password`.** Read it, preserve it, write it back unchanged.
- **Do NOT touch `secret/keycloak/users/*`.** Those are the *realm SSO* users
  (admin/developer/operator) in the `home` realm, written only by `bin/cluster-up`. This job
  rotates the **master-realm service admin** only.
- **Do NOT reconcile the divergent schema** in `scripts/plugins/keycloak.sh` or
  `scripts/etc/keycloak/externalsecret-admin.yaml.tmpl`. File nothing, change nothing there.
- **Do NOT modify the `shopping-cart-infra` repo.** The rotator is applied directly by
  k3d-manager, exactly as the Grafana and ArgoCD rotators are — it does not go through ArgoCD.
- **Do NOT annotate, patch or otherwise mutate the `keycloak-secrets` ExternalSecret.**
- **Do NOT add `keycloak/users/*` to the Vault seed allowlist** in `scripts/plugins/vault.sh`.
- **Do NOT run the rotator against the live cluster.** Source-only change with stubbed tests.
  The operator triggers the first real run.
- **Do NOT print, log or echo any password**, old or new, at any point.

## M1 — The rotator manifest

Create `scripts/etc/argocd/platform-ops/keycloak-credential-rotator.yaml`, modelled on the
Grafana rotator's structure: ServiceAccount, namespace-scoped Role + RoleBinding, the
notifications ClusterRole/ClusterRoleBinding for the Slack webhook read, and a CronJob.

- Namespace: `identity` (all of SA, Role, RoleBinding, CronJob).
- Name: `keycloak-credential-rotator`.
- Schedule: `0 0 1 * *`, `concurrencyPolicy: Forbid`, `successfulJobsHistoryLimit: 2` — match the
  other two rotators exactly.
- Resources: copy the Grafana job's requests/limits.
- RBAC: the Role needs **no** write access to `keycloak-secrets`. The job does not touch it. Grant
  only what is actually used — if the script reads nothing from the Kubernetes API in `identity`,
  the Role should be empty or omitted, and you should say so in your report rather than granting
  unused verbs. The ClusterRole for reading `platform-ops-notifications` mirrors Grafana's.

### The script body — order matters, and it is not Grafana's order

```
1. Vault login via kubernetes auth, role `keycloak-rotation`, using the pod's SA JWT.
2. Read the WHOLE secret: old_admin="$(… | jq -er '.data.data.admin_password')"
                          old_db="$(…    | jq -er '.data.data.db_password')"
   Fail closed if either is missing or empty — a partial secret must abort before any change.
3. new="$(head -c 24 /dev/urandom | od -An -tx1 | tr -d ' \n')"
4. Obtain an admin token from the MASTER realm using old_admin:
      POST http://keycloak.identity.svc/realms/master/protocol/openid-connect/token
           grant_type=password, client_id=admin-cli, username=$admin_user, password=$old_admin
   Fail closed if no token — nothing has changed yet.
5. Resolve the admin user's id:
      GET /admin/realms/master/users?username=$admin_user&exact=true   -> .[0].id
6. Install the rollback trap NOW, before the first mutation.
7. Reset the password INSIDE Keycloak:
      PUT /admin/realms/master/users/<id>/reset-password
          {"type":"password","value":"<new>","temporary":false}
8. Write Vault, preserving db_password:
      PUT secret/data/keycloak/admin
          {"data":{"admin_password":"<new>","db_password":"<old_db>"}}
9. Verify: obtain a fresh master-realm token using the NEW password. Fail if it does not work.
10. trap - EXIT, then post the value-free Slack notification.
```

**Do NOT force-sync or annotate the ExternalSecret.** It converges within its 15m
`refreshInterval`. Note this in the Slack message wording if you mention propagation at all.

### The rollback trap

Rollback is genuinely different from Grafana's, because Keycloak is mutated before Vault and the
authoritative store is Keycloak's database, not Vault:

- If step 7 (Keycloak reset) failed: nothing changed. Restore is a no-op.
- If step 7 succeeded but 8 or 9 failed: Keycloak holds the new password and Vault holds the old
  one — the operator is locked out. The trap MUST put Keycloak back:
  1. get a token using the **new** password,
  2. `reset-password` back to `old_admin`,
  3. best-effort re-write Vault with `{admin_password: old_admin, db_password: old_db}`.
- Every rollback step is best-effort (`|| true`) so the trap cannot itself abort, exactly as the
  Grafana and ArgoCD jobs do.
- If rollback cannot restore Keycloak, the job must exit non-zero **and** the Slack message must
  say the credential is in an unknown state and name the Vault path — without printing any value.
  A silent failure here is the worst outcome of this whole change.

### Secret hygiene, non-negotiable

- Every step redirects to `>/dev/null`; the job's logs must stay empty on success, like the
  others. Verify by reading the manifest, not by running it.
- No password in any argv: build JSON with `jq -nc --arg` and pass bodies via `--data @-` on
  stdin or `-d "$(jq …)"`; never interpolate a password into a URL or a `-u` flag.
- No `set -x`. Keep `set -eu`.

## M2 — Apply path in the plugin

Add `_keycloak_apply_credential_rotator` to `scripts/plugins/keycloak.sh`, mirroring
`_observability_apply_grafana_rotator` (`scripts/plugins/observability.sh:154`):

```bash
function _keycloak_apply_credential_rotator() {
  local manifest="${SCRIPT_DIR}/etc/argocd/platform-ops/keycloak-credential-rotator.yaml"
  [[ -f "${manifest}" ]] || return 0
  _kubectl apply -f "${manifest}" >/dev/null \
    && _info "[keycloak] monthly credential rotator applied"
  if declare -f _vault_configure_secret_writer_role >/dev/null 2>&1; then
    _vault_configure_secret_writer_role "secrets" "vault" \
      "keycloak-credential-rotator" "identity" "secret" "keycloak/admin" \
      "keycloak-rotation" "keycloak-rotation" \
      || _err "[keycloak] failed to configure Keycloak rotation Vault role"
  fi
}
```

Call it from the existing Keycloak deploy path, at the point where the admin secret and
ExternalSecret are already established. Find that call site by reading the file — do not invent a
new public entrypoint, and do not call it from `observability.sh`.

**Note the `declare -f` guard is copied deliberately**: the dispatcher lazy-loads only the invoked
plugin, so `_vault_configure_secret_writer_role` may genuinely be absent. Keep the guard.

## M3 — Tests

New suite `scripts/tests/plugins/keycloak_credential_rotator.bats`. These are **static manifest
assertions plus a stubbed apply path** — no cluster, no Vault, no curl.

Manifest assertions (parse the YAML with `yq`, which the repo already uses in
`alertmanager_config_secret.bats`):

1. CronJob exists in namespace `identity`, schedule `0 0 1 * *`, `concurrencyPolicy: Forbid`.
2. **`db_password` is preserved** — the script body writes both `admin_password` and
   `db_password` in its Vault PUT. Assert both appear in the payload construction. This is the
   single most important test in the suite: its absence is how the database credential gets
   destroyed.
3. **The ExternalSecret is never mutated** — assert the manifest contains no `annotate`, no
   `patch` and no `force-sync` against `keycloak-secrets`. This pins difference 2 against a later
   "make it consistent with Grafana" edit.
4. **The master realm is used**, not `home` — assert `realms/master` appears and
   `realms/home` does not.
5. **A rollback trap exists** and is installed before the `reset-password` call — assert
   `trap` appears at an earlier line number than the first `reset-password`.
6. **No password in argv** — assert the body contains no `-u ` with an interpolated password and
   no `password=` inside a URL string; token requests must use `--data`/`-d`.
7. **Logs stay silent** — assert every `curl` invocation in the body is redirected to
   `/dev/null` (or its output captured into a variable), i.e. no bare `curl` whose stdout escapes.

Plugin assertions:

8. `_keycloak_apply_credential_rotator` applies the manifest — stub `_kubectl` to log its argv and
   assert the manifest path appears.
9. It configures the Vault role with exactly `keycloak-credential-rotator` / `identity` /
   `secret` / `keycloak/admin` / `keycloak-rotation` — stub
   `_vault_configure_secret_writer_role` to record its arguments.
10. It is a no-op when the manifest file is absent, and does not fail the caller.
11. It survives `_vault_configure_secret_writer_role` being undefined (the `declare -f` guard).

Follow the repo's BATS conventions: no bare `!` at the start of an assertion — use
`run <cmd>` then `[ "$status" -ne 0 ]`. A bare `!` suppresses `set -e` and the assertion can
never fail; two such no-op assertions were found in this repo on 2026-09-21 and
`scripts/tests/lib/bats_negation_lint.bats` now gates them. Do not add a third.

Do not assert against whole lines of the manifest with `grep -F` — assert meaningful tokens.

### Mutation check (mandatory)

A new test passing does not prove it can fail. For tests 2, 3, 4 and 5, temporarily break the
manifest in a scratch copy and show each assertion going red, then restore. Paste the output.
Specifically: drop `db_password` from the Vault payload and show test 2 red — that is the one
that matters.
