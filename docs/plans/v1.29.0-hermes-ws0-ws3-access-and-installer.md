## WS0 — Access model (least-privilege, webhook-authoritative)

### Governing discovery (verified 2026-09-04)

The authoritative webhook payload (`GET /api/v1/health?provider=<p>` → `_smoke_test_services`,
`bin/k3dm-webhook`) **already reports**, as entries in the `services` array:

- `ESO ClusterSecretStore` — `Ready=True` / not.
- `ESO ExternalSecrets` — `{total}/{total} synced`, or a not-synced failure with counts.
- Per-service endpoint health, `Data layer` readiness, and **ArgoCD server** liveness (healthz).

It does **not** expose per-`Application` `Degraded`/`OutOfSync` in the JSON (that lives only in the
Slack digest path). Node/control-plane pressure is likewise reached through the webhook, never a
direct probe (scope §4, constraint 2).

**Consequence for least privilege:** routing the ESO signal (WS1 sensor a) and node pressure
(sensor d) through the webhook means **Hermes needs no direct kube-apiserver credential at all.**
Adding a read-only K8s `Role` for ExternalSecrets would (a) duplicate the authoritative webhook — a
"second health model", forbidden by constraint 2 — and (b) place an extra cluster credential off-hub
for no signal gain. So WS0 deliberately provisions **zero direct K8s RBAC**. This refines the parent
plan / scope §6 wording ("namespaced K8s Role"): the webhook already *is* that read path, held by an
already-existing read-only token.

### The three credentials Hermes holds (all read-only)

1. **Webhook bearer token — EXISTING, reused, no provisioning.**
   Keychain `k3dm-webhook-token` (laptop), port 7443. Read-only by construction: Hermes only issues
   `GET /api/v1/health`. Source for sensors: ESO sync (a), service/endpoint health, node pressure
   (d), ArgoCD-server liveness. On `overall:"unknown"` (webhook down) Hermes reports "status source
   unavailable", never a fabricated verdict (constraint 2).

2. **ArgoCD read-only local account `hermes` — NEW (this doc's manifest change).**
   For sensor (b), per-`Application` `Degraded`/`OutOfSync`, which the webhook JSON omits.
   - `scripts/etc/argocd/values.yaml.tmpl` `configs.cm`: `accounts.hermes: apiKey`
     (apiKey capability only — **no** `login`, so no web password).
   - `configs.rbac.policy.csv` adds:
     ```
     p, role:hermes-readonly, applications, get, */*, allow
     g, hermes, role:hermes-readonly
     ```
     `get` only — **no** `sync`, `update`, `delete`, `override`, `action`, and no `*`.
   - Token minted out-of-band: `argocd account generate-token --account hermes`, stored **off-hub**
     (laptop Keychain, suggested service `k3dm-hermes-argocd-token`), never committed.

3. **GitHub fine-grained read-only PAT — NEW, USER mints (Claude cannot issue tokens).**
   For sensor (e), CI/required-check health.
   - Resource owner: `wilddog64`. Repositories: `k3d-manager` (add `shopping-cart-infra` only if its
     CI is watched).
   - Repository permissions — **Read-only, all of them**: `Actions`, `Checks`, `Commit statuses`,
     `Contents` (metadata read). **No** write permission anywhere; **no** account/org permissions.
   - Store off-hub (laptop Keychain, suggested service `k3dm-hermes-gh-token`), never committed.

### DoD (scope §6 — verified to hold no write verbs)

- [ ] ArgoCD: `argocd account can-i sync applications '*/*'` (as the `hermes` token) → **no**;
      `argocd account can-i get applications '*/*'` → **yes**. `argocd app sync <any>` denied.
- [ ] ArgoCD: `hermes` account has `apiKey` capability only (no `login`) — `argocd account get hermes`.
- [ ] GH token: `gh api -H "Authorization: token <PAT>" repos/wilddog64/k3d-manager` succeeds (read);
      any write (e.g. `PATCH .../branches/main/protection`) is 403/404. No `contents:write`, no admin.
- [ ] K8s: **no** SA/kubeconfig issued to Hermes (by design). Assert the Hermes codebase holds no
      kubeconfig/token path (grep at WS1/WS2 review).
- [ ] Webhook token is GET-only in use — no Hermes call hits a mutating webhook route.

### Live steps (prepare-and-stop — NOT done by this commit)

The manifest change is committed to the branch but **not applied**. To activate on the hub (a live
action; do only on explicit go, and it is a required-on-release reapply per CLAUDE.md):
1. Reapply the ArgoCD helm values (hub) so `argocd-cm`/`argocd-rbac-cm` pick up the `hermes` account +
   policy; confirm with `argocd_check_values_branch` pinned to `k3d-manager-v1.29.0`.
2. `argocd account generate-token --account hermes` → store in laptop Keychain `k3dm-hermes-argocd-token`.
3. User mints the GH fine-grained PAT above → laptop Keychain `k3dm-hermes-gh-token`.
4. Run the DoD checks above and record results in memory-bank.

## WS3 — `_install_hermes_agent` (installer, off-hub)

WS0/WS1/WS2 interfaces are now fixed (commit `4e9d3e6e`): the agent is `bin/k3dm-hermes`
(single-shot — one sense→correlate→report cycle per run, state persisted to
`~/.k3dm/hermes/state.json`), reading three read-only Keychain creds and posting to the
existing Slack relay only on a correlated event. WS3 stands that agent up as a supervised,
bounded, off-hub launchd LaunchAgent.

### Design (mirrors the existing launchd pattern; helper in lib-foundation)

Every launchd agent in this repo (webhook, vault-failover, node-health-watch, rotators)
follows one pattern: a `scripts/etc/launchd/*.plist.tmpl` template rendered by a `bin/` setup
script that `bootout`s then `bootstrap`s the job. WS3 reuses that pattern, but per scope §10
(dated decision 2026-09-04) the **reusable install/uninstall logic lives in lib-foundation**
so the plist-render + launchctl + credential-preflight surface is shared, not copy-pasted.

Split of responsibilities:

- **lib-foundation upstream** (`scripts/lib/system.sh`, edit upstream → PR → tag → subtree pull;
  NEVER edit `scripts/lib/foundation/` directly):
  - `_install_hermes_agent <repo_root>` — mac-only guard (`_is_mac`); **preflight** that the
    three read-only creds and the Slack relay already exist in the login Keychain (services
    `k3dm-webhook-token`, `k3dm-hermes-argocd-token`, `k3dm-hermes-gh-token`, `k3dm-slack-webhook`,
    account `k3dm`) via `_security find-generic-password ... </dev/null` (no `-w`, so no secret is
    read into the process) — **fail fast with a clear message if any is missing; NEVER mint or
    write a credential** (constraint: no new privilege at install time, §6/§10); render
    `scripts/etc/launchd/com.k3d-manager.hermes.plist.tmpl` to
    `~/Library/LaunchAgents/com.k3d-manager.hermes.plist`; `launchctl bootout` (ignore-fail) then
    `launchctl bootstrap gui/$(id -u)`. All launchctl/rm/render go through `_run_command`.
  - `_uninstall_hermes_agent` — `bootout` (ignore-fail) + remove the rendered plist **only**.
    Does NOT delete Keychain creds (they are user-minted, shared, read-only — not owned by the
    agent, unlike the webhook's self-generated token).
  - BATS coverage in lib-foundation: preflight-missing-cred fails; happy path renders the plist
    and issues bootout+bootstrap (launchctl/`_security` stubbed — pure logic, no live launchd).

- **k3d-manager consumer** (lands after the subtree pull; template + entrypoint are consumer data,
  they stay in k3d-manager and are NOT pushed upstream):
  - `scripts/etc/launchd/com.k3d-manager.hermes.plist.tmpl` — Label `com.k3d-manager.hermes`;
    `ProgramArguments` = `/opt/homebrew/bin/python3 {{HERMES_BIN}}`; `EnvironmentVariables` carry
    `K3DM_REPO_ROOT`, `PATH`, and `K3DM_HERMES_JITTER=1`; **`StartInterval` = 300** (bounded 5-min
    poll, not a tight loop) with `RunAtLoad`; **no `KeepAlive`** (single-shot per interval);
    `StandardOutPath`/`StandardErrorPath` → `{{HERMES_LOG}}`
    (`~/Library/Logs/k3dm-hermes.log`). No secrets in the plist (creds are read from Keychain at
    runtime by the agent).
  - `bin/k3dm-hermes-setup` — thin entrypoint mirroring `bin/k3dm-webhook-setup`'s CLI
    (`[--uninstall]`): `set -euo pipefail`, source the foundation lib, resolve `REPO_ROOT`, then
    call `_install_hermes_agent "${REPO_ROOT}"` or `_uninstall_hermes_agent`.
  - `bin/k3dm-hermes` — **minimal** jitter add (constraint 5, bounded polling is "jittered"):
    at the top of `main()`, when `K3DM_HERMES_JITTER` is set, `time.sleep(random.uniform(0, 30))`
    before sensing, so runs do not align to a hard 5-min boundary. Guarded by env so tests /
    manual runs stay instant. This is the only WS1/WS2-file touch WS3 makes.

### Definition of Done

- [ ] lib-foundation: `_install_hermes_agent` + `_uninstall_hermes_agent` in `scripts/lib/system.sh`;
      shellcheck clean; BATS green (preflight-missing + happy-path render/bootstrap, launchctl stubbed).
- [ ] lib-foundation `make credential-test` live gate green before PR (per lib-foundation ACG rule).
- [ ] lib-foundation PR merged (user go) + tagged (next patch, e.g. `v0.4.15`); `git subtree pull`
      into `scripts/lib/foundation/` on `k3d-manager-v1.29.0`.
- [ ] k3d-manager: `com.k3d-manager.hermes.plist.tmpl` (StartInterval, no KeepAlive, no secrets),
      `bin/k3dm-hermes-setup` (install/uninstall), `bin/k3dm-hermes` jitter add.
- [ ] No-mutation proof still holds across the added code:
      `grep -rEn 'apply|patch|delete|sync|restart|generate-token|add-generic-password' bin/k3dm-hermes* scripts/etc/launchd/com.k3d-manager.hermes.plist.tmpl` → no write path
      (install preflight is read-only `find-generic-password`, no `-w`, no `add`/`delete`).
- [ ] No kubeconfig / SA / cluster credential introduced (grep).
- [ ] Off-hub: LaunchAgent is a `gui/<uid>` user agent on the laptop, never in-cluster.

### Live activation steps (prepare-and-stop — NOT done by the WS3 commit)

Requires the WS0 creds to be live in Keychain first (ArgoCD token minted, GH PAT minted — WS0
"Live steps"). Then, on explicit go:
1. `bin/k3dm-hermes-setup` → installs + starts the LaunchAgent.
2. Confirm: `launchctl print gui/$(id -u)/com.k3d-manager.hermes` shows the job; tail
   `~/Library/Logs/k3dm-hermes.log` for a clean single cycle emitting the records JSON.
3. Re-run the WS0 DoD read-only checks post-install (nothing gained a write verb).
4. `bin/k3dm-hermes-setup --uninstall` verified to bootout + remove the plist, leaving creds intact.

### What NOT to do

- Do NOT edit `scripts/lib/foundation/` directly — lib-foundation upstream + subtree pull.
- Do NOT mint, write, or delete any credential at install time — preflight is read-only.
- Do NOT add `KeepAlive` (tight supervision loop) — bounded `StartInterval` poll only.
- Do NOT put any secret in the plist template — creds are read from Keychain at runtime.
- Do NOT create a PR/merge/tag or run the live install without explicit go (prepare-and-stop).
