## Why

Asked for on 2026-09-25: a Claude cloud session can already operate on the k3d-manager repo
through the GitHub connection, but cannot reach anything outside that environment. The ask is to
let it call the k3dm webhook — "generate a special API token, set up network and environment
variables."

## Decision — 2026-09-25: PULL

The operator chose the **pull** model over exposing the endpoint. No public route, no credential in
a third-party secret store, and the cluster-mutation decision never leaves a host under the
operator's control. The push design is retained at the bottom of this doc for the record but is
**not** to be built.

S1/S2 below survive the decision and become *more* load-bearing, not less: the pull executor runs
locally and would otherwise reach the webhook with the admin credential, which would make
"read-only" a convention rather than an enforced property. S1/S2 is what lets it present a
credential that is genuinely incapable of mutation.

## Why S1/S2 are prerequisites — audit finding F4, promoted

This is **not a new finding.** `docs/issues/2026-09-07-webhook-server-security-audit.md` **F4**
already recorded it: "`X-K3DM-Role` is client-asserted (LOW / INVARIANT TO DOCUMENT)", rated LOW
explicitly *because* of the single-admin-token invariant, with the note "revisit if role-scoped
tokens are added."

This spec is that revisit. Adding a second, lower-tier credential is precisely the condition F4
named, and it converts the finding from LOW to blocking — F4's own text anticipates it: "a low-tier
token could send `X-K3DM-Role: admin` and escalate." So S1 cannot ship without S2.


The bearer token **is** an admin credential, and the role a caller gets is **self-asserted in a
header**, not derived from the credential. `scripts/lib/webhook/policy.py:108`:

```python
def _request_role(headers):
    raw = headers.get("X-K3DM-Role")
    if raw is None:
        return _ROLE_DEFAULT  # direct token = admin credential
```

with `_ROLE_DEFAULT = "admin"` (line 30). `bin/k3dm-webhook:1713` `_auth()` compares the presented
bearer against the single `_get_token()` value and returns a boolean — it does not carry any
identity forward. So any holder of `k3dm-webhook-token` who omits `X-K3DM-Role` (or sends
`X-K3DM-Role: admin`) reaches `admin`, which unlocks `cluster-resume`, `cluster-up`,
`cluster-down`, `cleanup-stale-sandbox` and `argocd-upgrade`.

The `_normalize_actor_role` fail-closed-to-reader path (line 103) does **not** protect this: it
normalizes an already-resolved role string, and the direct-token path never routes through a
resolver that could return an unknown value. The `_effective_make_role` capping (line 116) also
short-circuits when the header is absent.

**Consequence:** "issue the cloud session a reader-only token" is not configuration — it requires
a code change. Handing it the existing token is handing it cluster-mutation authority. That is the
whole risk in this request, and it is why S1/S2 below are mandatory before any network work.

## Threat model — why this is stricter than a normal API client

A cloud session's prompt derives from GitHub content: PR titles, issue bodies, review comments.
That content is attacker-influenceable by anyone who can open a PR. The webhook's `agent.py` makes
a role-gated **cluster-mutation decision** and carries an `_INJECTION_RE` prompt-injection filter
precisely because its inputs are not trusted. Exposing a mutation-capable endpoint to a caller
whose instructions come from PR text composes those two surfaces: injection in a PR comment
becomes a path to the cluster.

Therefore the design target is **read-only, allowlisted, and incapable of escalation even if the
sandbox is fully compromised.** The pull model removes the network half of that problem; P2's
validation and S1's credential ceiling carry the rest.

## S1 — bind role to the credential, not to a header (`auth.py`)

Add a second, reader-scoped token and a resolver that reports *which* credential authenticated.
Keep `_get_token()` unchanged so the existing admin path and every current caller keep working.

```python
def _get_reader_token():
    token = os.environ.get("K3DM_WEBHOOK_TOKEN_READER")
    if token:
        return token
    return _keychain_secret("k3dm-webhook-token-reader") or None


def _resolve_token_role(presented):
    """Return the role bound to the presented bearer, or None if it matches no credential.

    Order matters: the admin credential is checked first so that an operator who sets both
    vars to the same value keeps admin rather than being silently downgraded.
    """
    if not presented:
        return None
    admin_token = _get_token()
    if admin_token and hmac.compare_digest(presented, admin_token):
        return "admin"
    reader_token = _get_reader_token()
    if reader_token and hmac.compare_digest(presented, reader_token):
        return "reader"
    return None
```

Both comparisons use `hmac.compare_digest` — never `==`. Compare the **token**, not the whole
`Authorization` header, so a length difference between the two credentials does not leak through
timing on the header prefix.

`_get_reader_token()` reads only env and Keychain. It must **not** fall back to `TOKEN_FILE`:
that file is the admin credential's on-disk fallback, and a shared file would make the two roles
the same secret.

## S2 — make the token role a ceiling the header cannot raise (`policy.py`, `bin/k3dm-webhook`)

`_auth()` becomes role-aware, and `_request_role` takes the credential's role as an upper bound:

```python
def _request_role(headers, token_role=None):
    raw = headers.get("X-K3DM-Role")
    if raw is None:
        role = token_role or _ROLE_DEFAULT
    else:
        raw = raw.strip().lower()
        role = raw if raw in _ROLE_LEVELS else "reader"
    if token_role is not None and _ROLE_LEVELS[role] > _ROLE_LEVELS[token_role]:
        return token_role
    return role
```

`token_role=None` preserves today's behavior exactly, so no existing call site changes meaning.
In `bin/k3dm-webhook`, `_auth()` stores the resolved role on the handler (e.g.
`self._token_role`) and the POST gate passes it through:

```python
        request_role = _request_role(self.headers, getattr(self, "_token_role", None))
```

The same ceiling must be applied to `_effective_make_role` — it calls `_request_role` internally,
so it needs the argument threaded too, or a reader token could reach an `operator` make target.

**Invariant this establishes, to be stated in `.github/copilot-instructions.md`:** a role may only
ever be *narrowed* by a request header; the credential sets the maximum. Any future code that
lets a header raise a role is a privilege-escalation bug.

## S3 — `do_GET` never checks a role at all (found 2026-09-25 while validating this spec)

`bin/k3dm-webhook:2163` `do_GET` calls `self._auth()`, the rate limiter and the path guard, then
serves the matched route. It **never calls `_request_role`** and never compares anything against
`get_route["min_role"]`. That `min_role` key on both `_GET_ROUTES` entries is dead metadata today.

It is not currently exploitable: both GET routes are `reader`, so "no check" and "check for reader"
agree. But it means the reader credential's read-only property on the GET side rests on an
*unenforced* coincidence. The moment anyone adds a GET route above reader, the reader token reaches
it, and nothing in review would flag it because the surrounding code looks role-aware.

Since this spec's whole purpose is to make a lower-tier credential genuinely incapable, close it:

```python
        role = _request_role(self.headers, getattr(self, "_token_role", None))
        if not _role_allows(role, get_route["min_role"]):
            self._json(403, {"error": "forbidden"})
            return
```

placed immediately after `get_route` is resolved and **before** the `/api/v1/health` early returns —
those two branches currently answer ahead of route resolution, so the check has to be reachable for
them too, or `health` stays ungated. Restructure only as far as that requires: resolve the route,
apply the gate, then keep the existing branches in order. The comparison helper is `_role_allows(actual_role, required_role)` at
`scripts/lib/webhook/policy.py:132` — verified present; it is already exported, but confirm it is in
`bin/k3dm-webhook`'s import list from `policy` and add it there if not.

This is a behavior change for any caller that presents a valid token: none today, because every GET
route is reader and `token_role=None` yields `admin`. Assert that in a test rather than reasoning
about it.

## P1 — the channel: a dedicated git branch

The cloud session already has exactly one capability that reaches out of its sandbox: push access
to this repo through the GitHub connection. Use that as the transport and add nothing else.

Branch `cloud-requests`, never merged to `main`, carrying three directories:

```
requests/<utc-iso-compact>-<slug>.json     written by the cloud session
responses/<same-id>.json                   written by the local executor
ledger/processed.txt                       append-only, one request id per line
```

Request schema, all fields required:

```json
{
  "schema": 1,
  "action": "cluster-status",
  "args": {},
  "requested_by": "claude-cloud",
  "requested_at": "2026-09-25T20:14:03Z",
  "expires_at": "2026-09-25T20:44:03Z"
}
```

`schema` is pinned and compared with `==`; an unrecognized value is rejected, never coerced. This
is what stops a future format change from being silently reinterpreted by an old executor.

## P2 — the executor: `bin/k3dm-cloud-bridge`

A new poller on its own launchd agent (60s interval), **not** an addition to Hermes — Hermes'
blast radius should not grow, and its plist already has template drift
(`K3DM_HERMES_AUTO_KINE_GUARD`) that a second consumer would complicate.

Loop, per tick:

1. Operate in a **dedicated bare clone** at `${K3DM_CLOUD_BRIDGE_REPO:-${HOME}/.k3d-manager/cloud-bridge/repo.git}`,
   created with `git clone --bare` on first run. Fetch `cloud-requests` into it and read blobs with
   `git cat-file` / `git show FETCH_HEAD:<path>`.

   **Never operate in the operator's working repo.** A bare clone has no working tree, which makes
   `git checkout` impossible by construction rather than merely forbidden by review — and it also
   keeps the repo's pre-commit hooks out of an unattended commit path, so the bridge never needs
   `--no-verify` (which is forbidden) and can never be blocked by a hook on someone else's staged
   work.
2. Enumerate `requests/` entries whose id is absent from `ledger/processed.txt`.
3. Validate, in this order, rejecting on the first failure: file size under a cap; parses as a JSON
   object; `schema == 1`; `action` present in the allowlist below; every key in `args` present in
   that action's declared parameter set; every value matching an **anchored, metacharacter-free
   `fullmatch`** pattern; `expires_at` parses and is in the future.
4. Execute by issuing an HTTP request to `https://127.0.0.1:7443<path>` with the **reader** bearer
   from S1. Never by building a shell command from request content — `cmd[0]` stays a literal at
   every spawn site, which is the same invariant that makes the four dismissed CodeQL
   `posix_spawn` alerts false positives.
5. Write `responses/<id>.json` and append the id to the ledger, in **one** commit, then push. The
   id is appended whether the request succeeded, was rejected, or expired — so nothing is ever
   retried.

   Build that commit with plumbing only — `git hash-object -w`, `git update-index` against a
   throwaway `GIT_INDEX_FILE`, `git commit-tree`, `git update-ref`, `git push` — since a bare clone
   has no index or worktree to stage into. Push with `--force-with-lease` so a concurrent push from
   the cloud session is a detected conflict retried next tick, never a silent overwrite of a request
   that was never processed.

Action allowlist — reader-only, and this table is the security boundary:

| action | method | webhook path | args |
|---|---|---|---|
| `health` | GET | `/api/v1/health` | none |
| `cluster-status` | **POST** | `/api/v1/cluster-status` | none |
| `hostinger-status` | **POST** | `/api/v1/hostinger-status` | none |
| `job-status` | GET | `/api/v1/status/<job_id>` | `job_id`, `fullmatch` `[0-9a-f]{8,64}` |

**Verified against the code 2026-09-25, and not what the first draft of this doc assumed.**
`_GET_ROUTES` in `bin/k3dm-webhook:1708` holds exactly two entries — `/api/v1/health` and
`/api/v1/status/`. `cluster-status` and `hostinger-status` are in `_POST_ROUTES`, so the bridge must
POST them with an empty JSON body. Hard-code the method per action in the allowlist table; never
derive it from the request file.

`/api/v1/ask` and `/api/v1/analyze` are deliberately excluded despite being `min_role: reader`:
they invoke an AI, and a request file authored from GitHub content is exactly the injection source
`agent.py`'s `_INJECTION_RE` exists to defend against. Adding either later requires its own spec.

## P3 — properties this has to hold, and how each is enforced

| property | mechanism |
|---|---|
| read-only | the P2 allowlist, plus the S1 reader credential as the enforced ceiling |
| no escalation from request content | request values never become argv or shell text; role comes from the credential, never the payload |
| replay-proof | the committed ledger; an id is processed exactly once |
| stale requests inert | `expires_at` checked before execution |
| fails closed | any validation failure writes an error response and consumes the id; no retry path |
| bounded | max requests processed per tick; per-file size cap |
| auditable | execution goes through the webhook, so `_audit_remote_action` records it on the existing path |

**Treat every byte on that branch as hostile.** The cloud session can push arbitrary content there,
and so can anything that compromises the session. That is the entire attack surface — far smaller
than a public endpoint, but it is not zero, and the validation order in P2 step 3 is the control.

## P4 — CI on the branch: already inert, keep it that way

**Checked 2026-09-25: no workflow edit is required.** The repo has exactly two workflows.
`ci.yml` triggers on `pull_request` with `branches: [main]`, so a push to `cloud-requests` does not
start it. `deploy-worker.yml` triggers on `push` but is scoped to `branches: [main]` **and**
`paths: workers/slack-relay/**`. Nothing fires on a request commit.

So P4 is an **invariant to record, not code to write**. Do not add branch filters — they would be
dead config implying a protection that the existing triggers already provide. Instead state in
`.github/copilot-instructions.md` that any new `push`-triggered workflow must be branch-scoped, and
that `cloud-requests` must never be in its trigger set. If a future workflow does trigger on all
branches, the filter becomes real work and belongs in that workflow's own change.

When verifying this claim, count across both `*.yml` and `*.yaml` — a glob matching one extension
has silently skipped workflows in this repo before.

## P5 — cloud-side helper

A small script in the repo the session calls to file a request and poll for its response, so it
does not hand-roll git plumbing each time. It needs no credential beyond the repo access the
session already has, and no environment variables at all — which is the practical payoff of
choosing pull.

## S6 — tests (`scripts/tests/bin/webhook_policy.py`, pure logic)

1. `_resolve_token_role` returns `admin` for the admin token, `reader` for the reader token,
   `None` for an unknown value, `None` for empty.
2. Admin token first: when both credentials hold the same string, the result is `admin`.
3. `_request_role(headers, "reader")` with no header → `reader` (**not** `admin`) — this is the
   regression gate for the defect this spec exists to fix.
4. `_request_role({"X-K3DM-Role": "admin"}, "reader")` → `reader` — the header cannot raise.
5. `_request_role({"X-K3DM-Role": "reader"}, "admin")` → `reader` — narrowing still works.
6. `_request_role(headers)` with `token_role=None` → unchanged behavior on every existing case.
7. `_effective_make_role` with a reader token cannot reach an `operator` target.
8. S3: a GET route whose `min_role` is above the caller's role returns 403; with `token_role=None`
   every existing GET route still returns 200. Add a temporary above-reader entry to a copy of
   `_GET_ROUTES` for the 403 case rather than changing the real table.

**Existing assertions that must stay green — do not "fix" them:**
`scripts/tests/lib/webhook.bats:959-960` asserts `_request_role({}) == "admin"` and
`_request_role({"X-K3DM-Role": "bogus"}) == "reader"`, and
`scripts/tests/bin/webhook_make_targets.py:69-80` pins six `_effective_make_role` results. The
`token_role=None` default exists precisely so these keep passing unchanged. If any of them goes red,
the default was broken — fix the implementation, not the test.

Mutation-check 3 and 4 against pre-change `policy.py`: both must fail there, or they are not
testing the fix.

## Not chosen — the push path (retained for the record)

Had push been chosen it would have required: a cloudflared ingress rule mapping a hostname to
`https://127.0.0.1:7443`; a Cloudflare Access application scoped to the four read-only paths; an
Access **service token** (`CF-Access-Client-Id` / `CF-Access-Client-Secret`) as the scoped,
independently revocable credential; and four values plus a hostname allowlist entry in the cloud
environment settings, including the reader token stored in a third-party secret store.

Why it lost: the sandbox is outbound-only, so push needs a *public* route to a host that also
serves mutation-capable paths, and the session's prompt derives from attacker-influenceable GitHub
content. Pull achieves the same read-only outcome with no public route and no exported credential.

Revisit only if the session must read live cluster state **mid-reasoning** at sub-poll latency.
The 60s tick in P2 is the thing to measure before reopening this.

## P6 — reader-tier `make` targets through the bridge (added 2026-09-26)

### Why this is an increment, not a new feature

`/api/v1/make` already exists (`bin/k3dm-webhook:1704`) and is already governed by a per-target
table in `scripts/lib/webhook/make_targets.py`: each target carries a `min_role`, a required and
optional argument set, and an anchored regex per argument in `_ARG_PATTERNS`. `parse_make_request`
returns argv as `[target, "KEY=value", ...]` with every value `fullmatch`ed. That is already the
shape P3 demands — no request byte becomes a free string in argv.

The table was built for the Slack `/k3dm` path and the bridge was never wired to it. P6 wires it,
for reader targets only. **No new credential, no new role, no new endpoint.** The bridge keeps
presenting the reader bearer from S1, so the S2 ceiling refuses every `operator` and `admin`
target regardless of what the bridge sends. A bug in P6 fails closed.

### The six reachable targets

These are exactly the `min_role: reader` entries in `MAKE_TARGETS`:

| bridge action | make target | args | what you get |
|---|---|---|---|
| `make-fix-list` | `fix-list` | none | the list of fix targets |
| `make-fix-status` | `fix-status` | `NS` | node + pod status for a namespace |
| `make-status-public` | `status-public` | none | probe results for the public Cloudflare hostnames |
| `make-observability-status` | `observability-status` | none | monitoring/trivy-system pods, both clusters |
| `make-vuln-scan` | `vuln-scan` | none | VulnerabilityReport summary |
| `make-e2e-runner-health` | `e2e-runner-health` | none | hub vs remote-runner health |

### One action per target — not one `make` action

The obvious design is a single `make` action taking `target` as an argument. **Do not build that.**
`validate_request` enforces an exact key-set match (`set(allowed) - set(args)` rejects a missing
key). A single `make` action has a per-target variable argument set, which that validator cannot
express, so it would force a change to the security-critical validator itself.

Six flat entries need **zero change to `validate_request`**. The allowlist stays a literal,
readable table — which is what makes it reviewable as a boundary — and each entry has a fixed
required-arg set that the existing code already validates correctly.

### No optional arguments in phase 1

`fix-status` accepts an optional `FIX_CONTEXT` and `e2e-runner-health` an optional `RUNNER`.
Neither is exposed. Supporting them means teaching `validate_request` the difference between
required and optional keys, which is a change to the validator and needs its own mutation tests.
Phase 1 omits them and takes each target's default. If a default turns out useless in practice,
that is a phase-2 decision with its own spec section — not something to add opportunistically.

### Bridge changes — `bin/k3dm-cloud-bridge`

The allowlist tuple grows a fourth element: the static make target, or `None` for the four
existing actions. It is a string, never a callable — nothing in this table may be executable.

```python
NS_RE = re.compile(r"[a-z0-9]([-a-z0-9]{0,61}[a-z0-9])?")
ACTION_ALLOWLIST = {
    "health": ("GET", "/api/v1/health", {}, None),
    "cluster-status": ("POST", "/api/v1/cluster-status", {}, None),
    "hostinger-status": ("POST", "/api/v1/hostinger-status", {}, None),
    "job-status": ("GET", "/api/v1/status/{job_id}", {"job_id": JOB_ID_RE}, None),
    "make-fix-list": ("POST", "/api/v1/make", {}, "fix-list"),
    "make-fix-status": ("POST", "/api/v1/make", {"NS": NS_RE}, "fix-status"),
    "make-status-public": ("POST", "/api/v1/make", {}, "status-public"),
    "make-observability-status": ("POST", "/api/v1/make", {}, "observability-status"),
    "make-vuln-scan": ("POST", "/api/v1/make", {}, "vuln-scan"),
    "make-e2e-runner-health": ("POST", "/api/v1/make", {}, "e2e-runner-health"),
}
```

`validate_request` changes by exactly one line — the unpack becomes a 4-tuple:

```python
    _, _, allowed, _ = ACTION_ALLOWLIST[action]
```

`_call_webhook` learns to send a body:

```python
    method, path_template, _, make_target = ACTION_ALLOWLIST[action]
    path = path_template.format(**request["args"])
    if method == "GET":
        data = b""
    elif make_target is None:
        data = b"{}"
    else:
        data = json.dumps(
            {"target": make_target, "args": request["args"]}, sort_keys=True).encode()
```

Arg keys are the uppercase `_ARG_PATTERNS` names because that is what `parse_make_request`
expects. The request slug `make-fix-status` already satisfies `ID_RE`.

### The drift guard — the reason this stays safe over time

The bridge duplicates `NS_RE` rather than importing `_ARG_PATTERNS`, because a computed boundary
is not a reviewable one. Duplication invites drift, so a test pins them together. Add to
`scripts/tests/bin/test_cloud_bridge.py`:

1. For every `make-*` action, its regex for each declared arg has a `.pattern` **identical** to
   `webhook.make_targets._ARG_PATTERNS[key].pattern`. This fails the moment someone tightens the
   webhook pattern without tightening the bridge.
2. For every `make-*` action, the target is in `MAKE_TARGETS` and its `min_role` is exactly
   `"reader"`. This fails if a target is ever promoted to `operator` upstream.
3. For every `make-*` action, the declared arg set equals that target's `required` set — proving
   no required arg is dropped and no optional arg was quietly added.
4. Every `min_role: reader` target in `MAKE_TARGETS` either has a `make-*` action or is listed in
   an explicit `KNOWN_UNEXPOSED` set in the test. A new reader target upstream then forces a
   deliberate decision instead of silently widening or silently lagging.

### Mutation-checked behavior tests

Each must be shown red against an implementation with that one check removed:

- `make-vuln-scan` with a non-empty `args` is rejected (`unexpected argument`).
- `make-fix-status` with no `NS` is rejected (`missing argument`).
- `make-fix-status` with `NS="identity; rm -rf /"` is rejected (`invalid NS`).
- `make-fix-status` with `NS="Identity"` is rejected — the pattern is lowercase-only.
- An action named `make-sync-apps` is rejected as an unknown action, **not** run as an operator
  target. Assert on the reason string.
- `_call_webhook` for `make-fix-status` produces body bytes
  `{"args": {"NS": "identity"}, "target": "fix-status"}` and for `cluster-status` still `b"{}"`.
  No network: call the body-building path directly or factor it into a helper.

### Out of scope for P6 — do not build

Operator-tier targets. They would turn a push to a git branch into a cluster mutation, and the
branch's authorization boundary today is "anyone who can push to the repo" — the bridge never
inspects who wrote a request and `requested_by` is a self-declared string. That gap is
tolerable while every reachable action is read-only. It is **not** tolerable for a mutation, so
crossing that line requires requester authentication (signed commits or an author allowlist)
designed first, in its own spec, with the operator's explicit decision.

## What NOT to Do

- Do NOT change `_get_token()`, `_ROLE_DEFAULT`, or the meaning of any existing call site.
- Do NOT build any part of the push path — no tunnel ingress, no Access application, no service
  token. The decision is pull.
- Do NOT put either token in a cloud environment or third-party secret store. Pull needs neither.
- Do NOT add `ask`, `analyze`, or any `operator`/`admin` action to the P2 allowlist.
- Do NOT `git checkout` or `git switch` anywhere in the bridge — it runs unattended against the
  operator's working tree.
- Do NOT pass any request field into a shell string, `eval`, or an AI prompt.
- Do NOT merge `cloud-requests` into `main`, and do NOT bootstrap the launchd agent — that is the
  operator's to run.
- Do NOT create a PR, commit to `main`, force-push, or use `--no-verify`.
- Do NOT edit `scripts/lib/foundation/` or `scripts/lib/acg/` (subtrees).
- Do NOT print or echo either token value in code, logs, tests, or commit messages.

## Out of scope

Per-route in-code allowlists bound to a credential; an `operator`-scoped third token; replacing
the static tokens with short-lived ones (`project_webhook_token_rotation` owns that); and any
change to the Slack role-map path.
