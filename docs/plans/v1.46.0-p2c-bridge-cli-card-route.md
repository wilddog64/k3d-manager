## Context

`bin/k3dm-cloud-request` commits a request JSON with exactly six fields to the public `cloud-requests` branch
(`bin/k3dm-cloud-request:118-125`); `bin/k3dm-cloud-bridge` validates it (`validate_request`, `:99-127`; field set `:47`), sends
gated actions (`gated()`, `:58-60`) to Slack approval first (`admit` and `post_interactive`, `:777-785`; card text
`scripts/lib/webhook/cloud_approval.py:157-175`), and runs requests through `_run_request_tail`, which builds the webhook body in
`_request_body` (`:338-349`) and calls `_call_webhook`. Anything on the branch is attacker-writable; responses the bridge commits
are readable by every session.

This child adds one optional top-level field, `notify_route` (a Slack channel alias). p2a provides
`notify_routes.ALIAS_RE`, `route_names()` (names only; reads the env var or the Keychain item when called), `routable(action)`,
`INVALID_REASON = "invalid notification route"`, `UNSUPPORTED_REASON = "notification route not supported for this action"`.
p2b makes the webhook resolve the alias; the bridge never sees channel IDs.

## Behaviour

### 1. `bin/k3dm-cloud-bridge`

1. **Field set.** `validate_request` accepts a request whose keys are exactly `REQUIRED_FIELDS`, or `REQUIRED_FIELDS` plus
   `notify_route`; any other set keeps today's reason `request fields are not exactly the required six`. `schema` stays 1.
2. **Shape and action (pure, in `validate_request`, after the args checks and before expiry).** If `notify_route` is present: not
   a string that fullmatches `ALIAS_RE` → `INVALID_REASON`; `routable(action)` false → `UNSUPPORTED_REASON`.
3. **Configured check (`_check_route(request) -> reason | None`).** Returns `None` when the request has no `notify_route`
   without reading anything; else `INVALID_REASON` unless the alias is in `route_names()`. Called (a) in the claim loop right
   after `validate_request` succeeds and **before** `gated()`/`admit`, so an invalid alias posts no card and uses no card slot;
   (b) at the start of `_run_request_tail`, before any token read or webhook call, for reader and approved requests alike. A
   failure commits the normal `rejected` response with that reason; never a fallback to running without the route.
4. **Body.** `_request_body` adds `"notify_route": <alias>` at the top level of the JSON body when present (make and sandbox
   shapes). It never adds `channel_id`, `response_url` or `thread_ts`. A webhook 400 is reported as `rejected` with the
   webhook's `error` string only when it is one of the two p2a reasons or `notify_route cannot be combined with Slack context`;
   otherwise today's handling.
5. **What is committed.** Responses, final responses and `artifacts/<id>/summary.json` may contain the alias, never a channel
   ID (the bridge has none). `approvals.json` stores the request as today (alias only).

### 2. `scripts/lib/webhook/cloud_approval.py`

`card()`: when `request` has `notify_route`, append ` Notifications go to \`<alias>\`.` (through `_safe`) to the card text, after
the args. The card's destination is unchanged (the bridge still posts it to the `k3dm-slack-webhook` URL).

### 3. `bin/k3dm-cloud-request`

New option `--notify-route ALIAS`: refused by the parser unless it fullmatches `notify_routes.ALIAS_RE`; when given, the
payload gains top-level `"notify_route": ALIAS`; when not, the payload is byte-identical to today. Usage string updated. The
CLI cannot know the configured names (cloud sessions have no Keychain); the bridge decides.

## What NOT to Do

- Do not forward any Slack context field from request data; do not read or hold channel IDs in the bridge.
- Do not change the token choice, the gate, `admit`, expiry or nonce handling from plan 1, except calling `_check_route` before
  `admit` and in the tail.
- Do not touch the webhook, `notify_routes.py`, docs or the relay. Do not commit.
