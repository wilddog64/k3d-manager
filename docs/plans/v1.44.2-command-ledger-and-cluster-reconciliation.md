## Problem

Our "devices" are unreliable by design: ACG sandboxes expire after 4 hours, Hostinger is reached
only through laptop tunnels, the hub lives on a laptop that sleeps, and requests arrive from Slack,
the cloud bridge and the operator's shell. Three defects filed on 2026-10-23 are the classic failures
of command dispatch without a target, an identity or a record of intent:

| Failure | 2026-10-23 instance |
|---|---|
| A command with no explicit target took a default and acted on the wrong device | bare `tunnel_start` repointed Hostinger's tunnels at the `ubuntu` sandbox alias |
| Desired state was last-writer-wins, not keyed per device | one `observability-acg` set moved between Hostinger and the sandbox |
| Old telemetry read as current, or as a bare number | snapshot age `(344 old)`; `make status` UNKNOWN with no reason in a shell without the webhook token |

What the code has today:

- `bin/k3dm-webhook` mints a fresh `uuid4()[:8]` job id at 26 call sites. A retried request (Slack
  retry, a re-filed cloud request, an operator re-run) is a new job; nothing links it to the first.
- `_running_cluster_job` (`bin/k3dm-webhook:603`) turns a `running` job older than
  `_MAX_JOB_AGE_SECS` (3 h) into `failed` as a side effect of a lookup. "The webhook lost track of it"
  and "it failed" are the same state.
- `bin/k3dm-cloud-bridge` `prepare_request` deduplicates request ids, but only within the bridge's
  in-memory `processed` set; the id never reaches the webhook job.
- No single place records, per cluster, what we last asked it to be (provider, tunnel host,
  ApplicationSet branch, observability destination) next to what it last reported and when. Each
  check (status, snapshot, tunnel, appsets-check) reads its own source with its own idea of "stale".

## Design

Read-only first slice. It records and reports; it repairs nothing. Auto-repair is a later plan,
behind its own approval, once the drift report has been trusted for a release.

### D1. Command envelope and ledger

Every webhook job gets a command record, appended to `~/.local/share/k3d-manager/commands.jsonl`
(one JSON object per event, same discipline as the dispatch ledger):

- `command_id` — taken from the request when present (cloud request id, Slack `X-Slack-Retry`
  original id via the event id, or an explicit `command_id` body field from the shell), else minted.
- `job_id` (the existing short id), `action`, `target` (cluster name, required for every action that
  touches a cluster — see D2), `origin` (`slack`, `cloud`, `shell`, `schedule`), `submitter`.
- Events: `accepted`, `started`, `finished` (`outcome`: `succeeded` | `failed`), `lost`, `duplicate`.

A job helper, `_new_command(action, target, origin, command_id=None)`, replaces the 26 inline
`uuid4()` calls. It returns the job id and writes `accepted`.

### D2. Explicit targets and duplicate suppression

- An action that touches a cluster must carry a target cluster. The webhook never fills one from a
  default; a missing target is rejected with a message naming the valid targets (the tunnel lesson,
  generalised). Read-only actions that span all clusters (`cluster-status` with no provider) use the
  target `all`, explicitly.
- A request whose `command_id` matches a command `accepted` within the last 24 h returns the
  existing job (its id, state and thread) and writes a `duplicate` event. It never starts a second
  run. Status actions are exempt (re-asking for status is the point); lifecycle, refresh, dispatch
  and e2e actions are not.

### D3. Leases instead of silent failure

`started` carries a `lease_until` (per action, from a table; default 3 h, matching today's
`_MAX_JOB_AGE_SECS`). The job's runner renews it while the process is alive. A `running` job whose
lease expired and whose process is gone is marked `lost`, not `failed`, by a sweep at webhook
start and on each `_running_cluster_job` call, and the operator gets one Slack notice naming the job.
A `lost` lifecycle job still blocks a new lifecycle job on the same target until the operator clears
it (`make command-clear ID=…`), because "we do not know what happened to the cluster" is not "safe
to start again".

### D4. Per-cluster desired/observed record

`bin/k3dm-cluster-state` (stdlib Python, read-only) builds, for each known cluster (hub,
`ubuntu-hostinger`, any registered sandbox), one record:

- **desired** — from repo and local config: provider, tunnel SSH host (Hostinger), ApplicationSet
  values branch (the release branch), the observability Applications that should target it
  (`<cluster>-<app>` once the 10-23 P2 lands), the last lifecycle command (D1) and its outcome.
- **observed** — each signal with its own timestamp and source: tunnel wrapper host and agent state,
  ApplicationSet `targetRevision` as live, observability Application destinations, ESO store
  readiness, last `make status` result, hub snapshot stamp. A signal that could not be read is
  `unknown` with a reason (e.g. `no webhook token in this shell`), never omitted.
- **freshness** — each signal is `fresh`, `stale` (older than its threshold, shown with its age and
  unit) or `unknown`. Thresholds live in one table in the script.
- **drift** — a list of `{check, desired, observed}` where both are known and differ. Initial checks:
  tunnel host, appset values branch, observability destination, last lifecycle command `lost`.

Output: a table for humans, `--json` for tools. The cloud bridge gets it as one reader-scoped action,
`cluster-state`.

### D5. Status and metrics

- `bin/cluster-status-summary` prints one drift line per cluster from D4 (`drift: none` or the
  checks that differ). Its verdict does not change in this slice.
- Pushed series (hub Pushgateway, existing push path, never from tests):
  `k3dm_cluster_signal_age_seconds{cluster,signal}`, `k3dm_cluster_signal_unknown{cluster,signal}`,
  `k3dm_cluster_drift{cluster,check}` (0/1), `k3dm_command_events_total{action,event}`.
- One Grafana panel row: drift by cluster, stale/unknown signals, lost and duplicate commands. No
  alert rule in this slice.

## Out of scope

- Any automatic repair or re-issue of a command.
- Changing what a status verdict is.
- Ordering or sequence numbers on telemetry (each signal is read fresh from its source; there is no
  stream to reorder yet).
- Agents' own dispatch ledger (`bin/k3dm-codex-dispatch`), which already has its own events.

## Tests

`test_webhook_commands.py` (temp `JOB_DIR` and ledger; no Slack, no subprocess):

1. Each of the 26 job-creation paths goes through `_new_command` (static check: no `uuid.uuid4()` left in `bin/k3dm-webhook`).
2. A lifecycle request without a target is rejected and starts no job.
3. The same `command_id` twice within 24 h: one job, one `duplicate` event, the second response names the first job.
4. A status request repeated with the same `command_id` runs twice.
5. A `running` job with an expired lease and no process becomes `lost`, not `failed`; a new lifecycle job on the same target is refused until `command-clear`.
6. A cloud request id reaches the job's `command_id`.

`test_cluster_state.py` (fixture configs and stubbed readers; no kubectl, no launchctl):

7. Tunnel wrapper host differs from the Hostinger host in config: drift `tunnel_host`.
8. A signal that cannot be read is `unknown` with its reason, and is not counted as drift.
9. A snapshot 200 h old is `stale` with age `200h`.
10. `--json` output has `desired`, `observed`, `freshness`, `drift` per cluster.

`cluster_status_summary.bats`:

11. With a stubbed `k3dm-cluster-state --json` reporting one drift, the summary prints the drift line and the overall verdict is unchanged.
