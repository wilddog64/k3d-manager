## You will see / It failed if

- **You will see:** when the release branch has a CI-green commit that `deploy/hub` lacks, a request filed from a Claude cloud session
  reaches you as a Slack Approve/Deny card; you press Approve, enter the six-digit code from your authenticator, and the hub runs
  `make hub-deploy REF=<sha>` by itself. The result comes back to the same thread. `docs/howto/hub-promote.md` and `CLAUDE.md` name
  `hub-deploy` as the one promote command.
- **It failed if:** anyone but you can approve, an approval works without the authenticator code, an approval works twice or after it
  expires, a commit that is no longer green or no longer the newest green commit is promoted, or a promote runs with `BREAK_GLASS` from
  a remote approval.

## Does Channel A depend on the Hermes reauth weakness? Yes, and it is not load-bearing once TOTP is required

Channel A's Approve press is handled by the same relay path as Hermes repairs: `workers/slack-relay/index.js:247-283`
(`handleInteractivity`). Before it records the approval it requires `reauth:<user>` in KV (`:270`), which `/hermes-auth` writes with a
24-hour TTL (`REAUTH_TTL_SECONDS = 86400`, `:3`; written at `:403`) and which the click never removes. That is exactly the weakness in
`docs/bugs/2026-11-09-hermes-reauth-lasts-24h-and-is-reusable.md` (OPEN, P3, Waiting on dispatch): anyone holding the operator's Slack
session can run `/hermes-auth` and then Approve. For promotes that is why TOTP has to be checked on the hub (Behaviour 3 and 4), not in
the relay: the Slack session alone, even with a fresh reauth, produces an `approval:<id>` KV entry that the hub refuses to act on
without a valid code. So Channel A can ship without that bug being fixed. Two consequences stated plainly: (a) the relay's 24-hour
reauth is not a security control for promote and this plan does not rely on it; (b) when the reauth bug is fixed (10 minutes, one use),
every promote needs `/hermes-auth` first, so the operator does three Slack steps (`/hermes-auth`, Approve, code), which is friction but
not a blocker. The bug fix and Part 3b both edit `workers/slack-relay/index.js`; the one-dispatch-per-file rule means they are
sequenced, not parallel. Channel B (the alert-card button) has no hub-side TOTP-only story because it would carry the same click path
for a standing alert, so it still waits on the bug (see Later).

## Review 2026-11-18

Confirmed, raised by both reviewers unless marked:

1. **Part 1 reinstalls the old template.** The `install-*` targets render from the working tree. `hub-deploy` only moves `origin/deploy/hub`, and the hub checkout follows on the next 5-minute repo-sync. `platform-ops` avoids this by archiving the promoted sha (`Makefile:1392-1396`). E10 stubs `make`, so it cannot catch it.
2. **Part 1 installs agents the hub deliberately skips** (Fable). `not-installed.list:2` keeps `install-token-rotator` off the hub, and `:38-41` covers the dispatch agents. The fix: reinstall only labels whose plist already exists in `~/Library/LaunchAgents`, and use `--diff-filter=AM`.
3. **A failed reinstall disappears on a rerun.** On the rerun `old == new`, so the step is skipped. A launchd failure also stops the run before `appsets-check` and `platform-ops`.
4. **A same-user process can forge an approval.** The store directory, operator id and `security` all come from env or PATH. The record's `state`, `approver` and `totp_counter` are trusted JSON. This is the env-var bypass the v1.44.0 N1 forbade.
5. **Expiry and single use are not enforced at the consume point.** Expiry is checked before up to 20 `gh` calls, and the final consume does not recheck it. A `security` exit other than 0 or 44 has no defined behaviour.
6. **The newest-green walk treats a failed lookup as "not green."** `classify_check_runs` rc 2 (`bin/k3dm-hub-promote:95`) should die, not walk back to an older commit. `branch` is never validated.
7. **The state machine has gaps.** `pending -> refused` is missing, there is no failed-attempt counter, and the check order is unspecified. The steps also resolve REF before the fetch, but the existing code fetches first (`:322-323`). An already-deployed sha exits 0 while E3 expects a refusal.
8. **The ahead check blocks routine promotes, and its test cannot fail** (Fable). Containment refuses "behind" earlier. Two of the last 14 ordinary promotes had old not an ancestor of new.
9. **A verifier cannot work from Acceptance alone.** These are missing: `create` arguments, record fields, refusal strings, exit codes, the Keychain service/account and `K3DM_PROMOTE_OPERATOR_SLACK_ID`. `consume-check` is undefined, and M6 has no evidence. Several mutants are equivalent: `expires <= now` is the same as `now >= expires`.
10. **`## Files` grants both parts' lists to each dispatch** (`bin/k3dm-codex-dispatch:832-835`). Split each part into its own spec, or trim the list before each dispatch.
11. **Part 3 timing breaks the TOTP window.** Hermes polls every 300 s, but a code lives 120 s in KV and ±1 step on the hub. That changes Part 2's `approve` input, so it must be decided before Part 2.
12. **The intent gate refuses the spec.** `spec_intent.py` exits 1 because the line must end at the date. E6-E10 have no approved intent. A paragraph between `## Acceptance` and the fence makes the per-evidence intent check skip silently.
13. **The "corrected" citations are wrong again.** `cloud_actions.py` is 52 lines, so the table is at `:17-52`. The `k3dm-cloud-bridge`, `slack.py`, `test_cloud_bridge.py` and `hub-promote.md` lines are off too. The `slack.py` offsets come from reading concatenated `cat -n` output.

Minor: the external-proof captures were taken on m4-air, not the hub, and none of the captured commits is green (Astra). `totp-setup` prints the otpauth URI into tmux scrollback, which agents capture. There is no global TOTP failure throttle. Part 2 should be split into 2a (library, CLI, pytest) and 2b (promote/deploy wiring, BATS).

## Open questions for the operator

One list for plan 1 (the specs carry none of their own). Each has Claude's recommended answer.

1. **Part 1 checkout wait.** `K3DM_HUB_DEPLOY_CHECKOUT_WAIT` defaults to 330 s (one repo-sync interval plus margin). Recommended: keep 330 s; a shorter wait makes "pending" the normal result.
2. **Part 1 exact-HEAD gate instead of an archive.** Part 1 installs only when the hub checkout is exactly at `$new` with a clean tracked tree, under repo-sync's lock, because installing from a `git archive` bakes a deleted path into the plist (`Makefile:72`). Recommended: accept the exact-HEAD gate.
3. **2a plain checksum, no HMAC.** Under O2 the state lives in a root-only directory; the checksum only detects corruption. Recommended: yes, plain checksum.
4. **2d one atomic push.** Branch and tag in one `git push --atomic` with a lease (proof owed live on GitHub). Recommended: yes; if GitHub refuses the combination, fall back to tag-first with the witness rules, recorded as a spec change.
5. **2d `not_newest_green`.** New policy, not a port: an older green commit cannot be promoted while a newer green exists on the newest release branch, which blocks deliberately holding back. Recommended: keep it for the approval path only (the TTY path is unchanged, so holding back stays possible at home).
6. **Release-branch protection.** Anyone who can push the newest release branch and get CI green supplies a policy-valid commit (R2d-2). Recommended: add a ruleset on `k3d-manager-v*` requiring a PR, after the plan lands; until then it is a named residual.
7. **Reduce the hub's GitHub credentials (O3 "where practical").** Replace the hub's `gh` token with a fine-grained token without Administration and without deploy-key write. Recommended: yes, before the ruleset is enabled; capture its scopes (2c proof owed 4).
8. **TTY promote after the ruleset.** Route the typed-confirmation promote through the authority as channel `cli` (request, approve with the TOTP code at the tty, promote) as a small follow-up spec before enabling the ruleset. Recommended: yes; this plan leaves the TTY path untouched.
9. **Rollback, BREAK_GLASS, SKIP_CHECK_RUNS and bootstrap after the ruleset.** Recommended now: the operator-watched break-glass procedure of 2c H.21 (disable the ruleset from your own device, run the shell command, re-enable).
