## You will see / It failed if

- **You will see:** when the release branch has a CI-green commit that `deploy/hub` lacks, a request filed from a Claude cloud session
  reaches you as a Slack Approve/Deny card; you press Approve, enter the six-digit code from your authenticator, and the hub runs
  `make hub-deploy REF=<sha>` by itself. The result comes back to the same thread. `docs/howto/hub-promote.md` and `CLAUDE.md` name
  `hub-deploy` as the one promote command.
- **It failed if:** anyone but you can approve, an approval works without the authenticator code, an approval works twice or after it
  expires, a commit that is no longer green or no longer the newest green commit is promoted, or a promote runs with `BREAK_GLASS` from
  a remote approval.

### Part 2 — approval record, TOTP, non-TTY promote (one worker)

Terms: **record** = one JSON file per approval; **operator** = the Slack user id in `K3DM_PROMOTE_OPERATOR_SLACK_ID` (one id,
regex `^[UW][A-Z0-9]{2,31}$`, set in the hub environment; the helper refuses when unset or malformed); **dir** =
`${K3DM_PROMOTE_APPROVAL_DIR:-$HOME/.local/share/k3d-manager/promote-approvals}`.

1. **Record.** `scripts/lib/hub_approval.py` writes `<dir>/<id>.json` (mode 0600; dir 0700, created with `umask 077`; the helper
   refuses a dir that is group- or world-accessible):
   `{"schema":1,"id","sha","branch","nonce","channel","requested_by","created","expires","state","approver","approved_at","totp_counter","reason"}`.
   - `id` matches `^p[0-9]+-[0-9a-f]{8}$` (`p<created epoch seconds>-<4 random bytes hex>`; the `p` prefix is deliberately outside the
     existing repair id `^r[0-9]+-[0-9a-f]{8}$` of `scripts/lib/hermes/approvals.py:14` so a repair approval can never be read as a
     promote approval and the reverse).
   - `sha`: 40 to 64 lowercase hex, the full commit id (a branch name or short sha is refused at create).
   - `nonce`: 16 lowercase hex (`secrets.token_hex(8)`), the same shape as `NONCE_RE` (`approvals.py:15`); it ties a Slack click to
     this record and is never printed, logged or passed on an argv.
   - `channel`: `cloud-session` (Part 3a) or `test`; any other value is refused. `requested_by`: free text from the request, at most
     80 printable ASCII characters, informational only (it is not an identity: see Open questions).
   - `created`, `expires`: integer UTC epoch seconds; `expires = created + 900` (15 minutes), fixed, not configurable.
   - `state`: `pending` (at create), `approved` (after Behaviour 3), then exactly one terminal state: `consumed` (promote ran),
     `refused` (a recheck failed at click time), `denied` (operator pressed Deny) or `expired` (set lazily when a read finds
     `now >= expires`). `reason` is the one-line refusal text for a `refused`/`denied`/`expired` record.
2. **Single use and locking.** Every state change is: take an exclusive `fcntl.flock` on `<dir>/.lock` (blocking, bounded by a 10 s
   alarm; a timeout refuses with `approval store is busy`), re-read the record, check the transition is legal (`pending -> approved |
   denied | expired`, `approved -> consumed | refused | expired`; anything else is `approval <id> is not <wanted> (state: <state>)`),
   write `<id>.json.tmp`, `fsync`, `os.replace` over the record, `fsync` the dir, release. A terminal record is kept (not deleted) so
   reuse reports its state; `create` prunes records older than 7 days. Two concurrent `consume` calls: exactly one succeeds (N7).
3. **Approve (the TOTP check).** `bin/k3dm-hub-approval approve --id ID` reads one JSON object from stdin
   `{"nonce","approver","totp"}` (never argv). It refuses unless: the record is `pending` and unexpired; `nonce` equals the record's
   (`hmac.compare_digest`); `approver` equals the operator id; the TOTP code verifies (Behaviour 4). On success it stores
   `approver`, `approved_at`, `totp_counter`, state `approved`, in one locked write. Every refusal leaves the record `pending`
   (a wrong code can be retried within the TTL, at most 5 failed attempts per record, then the record becomes `refused` with reason
   `too many failed codes`). `deny --id ID` (same stdin object without `totp`) moves `pending -> denied` for the operator id only.
4. **TOTP.** RFC 6238: HMAC-SHA1, 6 digits, 30 s step, T0 = 0, accept the current step and one step either side (window +/-1),
   `hmac.compare_digest` per candidate, stdlib only (`hmac`, `hashlib`, `struct`, `base64`). Secret: 20 random bytes, base32, in the
   login Keychain item service `k3dm-promote-totp-secret`, account `k3dm`, read with `security find-generic-password -s
   k3dm-promote-totp-secret -a k3dm -w` (secret on stdout, not argv; missing item is exit 44, captured below). Replay: the highest
   accepted step is kept in `<dir>/totp-state.json` (`{"last_step": n}`) and a code is accepted only when its step is strictly
   greater, updated under the same lock as the approval write, so a code can never approve two records. `bin/k3dm-hub-approval
   totp-setup` (requires a TTY, refuses to overwrite an existing item unless `--rotate`) generates the secret, stores it through
   `security -i` stdin (the pattern at `Makefile:1352`, so it is never on argv), prints the `otpauth://totp/k3dm-promote?secret=...&issuer=k3d-manager`
   URI once to the terminal (not to a file or the log), and writes no other copy. The `approve` output and every log line never
   contain the code, the secret or the nonce.
5. **Non-TTY promote.** `bin/k3dm-hub-promote promote REF --approval ID` (the flag may follow REF or the two positional switches; the
   existing positional `BREAK_GLASS`/`SKIP_CHECK_RUNS` forms of `:314-316` are unchanged). Order, all before any push, each failure
   is `die` (exit 1, `[hub-promote] ERROR: <message>` on stderr), and the order is the contract:
   1. `--approval` with `BREAK_GLASS` positional or env equal to `1`: `--approval cannot be combined with BREAK_GLASS=1`. With
      `SKIP_CHECK_RUNS` equal to `1`: `--approval cannot be combined with SKIP_CHECK_RUNS=1`. Checked before the record is read, so
      the record stays usable.
   2. `ID` not matching the id regex: `approval id is malformed`.
   3. Load the record under the lock; unknown: `approval <id> not found`; `state` other than `approved`: `approval <id> is not
      approved (state: <state>)`; `now >= expires`: mark `expired`, `approval <id> expired at <ISO UTC>`.
   4. `approver` not the operator id: `approval <id> approver is not the operator`. `totp_counter` missing or null: `approval <id>
      has no verified TOTP`.
   5. Resolve `REF` through the existing `resolve_on_origin` (`:80-91`); its full sha must equal the record `sha`:
      `approval <id> is for <record7>, not <ref7>`.
   From here the record is single-shot: any failure below sets state `refused` with the message as `reason` (under the lock) before
   `die`, and nothing retries. A refused id cannot be reused; a new request is needed.
   6. Existing gates, unchanged and in their existing order: `fetch`, `old=remote_sha`, already-promoted exit (`:325-328`, which here
      also marks the record `refused` with `deploy/hub already at <sha7>` and exits 0), containment (`:329-343`), then `check_runs`
      (`:103-111`; the 4 messages there stay).
   7. Newest green: `branch` is the record's release branch; walk `git rev-list --first-parent --max-count=20 origin/<branch>` newest
      first and take the first commit whose `classify_check_runs` (`:93-101`) returns 0; the record sha must equal it, else `<sha7> is
      not the newest green commit of <branch> (newest green is <other7>)`; no green commit in 20: `no green commit found on <branch>
      in the newest 20`. (Superseded pushes show as `cancelled` and so are never green, see Proof, which is why the walk is needed.)
   8. Ahead: `git merge-base --is-ancestor $old $new` must hold and `new != old`: `<sha7> is not ahead of deploy/hub`.
   9. Consume: under the lock, `approved -> consumed`; if another process consumed first, `approval <id> is not approved (state:
      consumed)`. This is the last check before `record_move` (`:142-172`), whose `--force-with-lease` push is the final guard.
   `show_and_confirm` is replaced for this path by one printed line `[hub-promote] approval <id> consumed; approver <operator>; channel
   <channel>` (no TTY read), and the tag message of `record_move` gains `approval: <id>` and `channel: <channel>` lines (not the
   nonce). Without `--approval` the behaviour is byte-for-byte today's, including `confirmation requires a TTY` (`:135`).
6. **`hub-deploy` passthrough.** `bin/k3dm-hub-deploy <commit-ish> [--approval ID]`; with the flag it calls
   `k3dm-hub-promote promote "$ref" --approval "$id"` (`:32`) and everything after the promote step runs as before. The usage
   string and `die` for any other argument list stay. The role gate (`:17-19`) still runs first.
7. **Click-time recheck result.** On any refusal in steps 1-8 `hub-deploy` stops at step `promote` with the promote's exit code (the
   existing `stop`, `:9-13`), so the caller (Part 3a) can post the refusal line.
8. **Operator id and Keychain are not read by tests.** The helper takes the Keychain reader and the clock as injectable functions
   (`security` is found on PATH, so BATS stubs it; pytest passes fakes).
9. **Audit.** `scripts/lib/hub_approval.py` appends one JSON line per event to `<dir>/promote-audit.jsonl` (0600, `O_APPEND`, one
   `write` per line): `{"ts":"<ISO UTC>","event":"<event>","id":"<id>","sha":"<sha7>","channel":"<channel>","actor":"<slack id or
   system>","result":"ok|refused","reason":"<one line>"}`. `event` is one of `create`, `approve`, `deny`, `consume`, `refuse`,
   `expire`, `totp-fail`. The line never contains `nonce`, the TOTP code, the TOTP secret or a token (the writer builds the line from
   a fixed field list; it has no code path that takes the stdin object). A write failure prints a warning to stderr and does not
   change the outcome of the promote (an audit outage must not block or silently allow it; the record file is the source of truth).
10. **No new network.** None of Part 2 talks to Slack, GitHub except through the existing `gh api` calls of `classify_check_runs`
    (`:95`) and `merged_pr_contains` (`:24`), or the cloud branch.

### Does Channel A depend on the Hermes reauth weakness? Yes, and it is not load-bearing once TOTP is required

Channel A's Approve press is handled by the same relay path as Hermes repairs: `workers/slack-relay/index.js:247-283`
(`handleInteractivity`). Before it records the approval it requires `reauth:<user>` in KV (`:270`), which `/hermes-auth` writes with a
24-hour TTL (`REAUTH_TTL_SECONDS = 86400`, `:3`; written at `:403`) and which the click never removes. That is exactly the weakness in
`docs/bugs/2026-11-09-hermes-reauth-lasts-24h-and-is-reusable.md` (OPEN, P3, Waiting on dispatch): anyone holding the operator's Slack
session can run `/hermes-auth` and then Approve. For promotes that is why TOTP has to be checked on the hub (Behaviour 3 and 4), not in
the relay: the Slack session alone, even with a fresh reauth, produces an `approval:<id>` KV entry that the hub refuses to act on
without a valid code. So Channel A can ship without that bug being fixed. Two consequences stated plainly: (a) the relay's 24-hour
reauth is not a security control for promote and this plan does not rely on it; (b) when the reauth bug is fixed (10 minutes, one use),
every promote needs `/hermes-auth` first, so the operator does three Slack steps (`/hermes-auth`, Approve, code), which is friction but
not a blocker. The bug fix and Part 3b both edit `workers/slack-relay/index.js`; the one-dispatch-per-file rule means they are
sequenced, not parallel. Channel B (the alert-card button) has no hub-side TOTP-only story because it would carry the same click path
for a standing alert, so it still waits on the bug (see Later).
