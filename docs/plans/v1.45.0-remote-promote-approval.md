## You will see / It failed if

- **You will see:** when the release branch has a CI-green commit that `deploy/hub` lacks, you approve it from your phone (a Slack
  Approve button, or a request filed from a Claude cloud session) and the hub runs `make hub-deploy REF=<sha>` by itself. The result
  comes back to the same thread. `docs/howto/hub-promote.md` and `CLAUDE.md` name `hub-deploy` as the one promote command.
- **It failed if:** anyone but you can approve, an approval works twice or after it expires, a commit that is no longer green or no
  longer the newest green commit is promoted, or a promote runs with `BREAK_GLASS` from a remote approval.

## Context

`make hub-deploy REF=` (`bin/k3dm-hub-deploy`) already chains hub-promote (all gates), appsets-reapply when ApplicationSets changed,
appsets-check, platform-ops and an exporter rollout check. `bin/k3dm-hub-promote` asks for the typed word `promote` and refuses
without a TTY (`bin/k3dm-hub-promote:112`), so nothing remote can call it today. v1.44.0 plan 3 (`deploy-hub-behind-alert`) already
alerts when deploy/hub is behind, naming the command. Live checks waited days on promotes the operator could run only at home
(v1.43.15: 4+ days against a 2-day median).

## Scope

1. **One promote command (docs half, can land first):** `docs/howto/hub-promote.md` and the `CLAUDE.md`/`AGENTS.md`/`GEMINI.md`
   shared rule teach `make hub-deploy REF=` instead of the three-step path. `hub-deploy` reinstalls a launchd agent whose
   `scripts/etc/launchd/*.plist.tmpl` changed between the old and new deploy/hub.
2. **Approval record:** an approval is `{id, sha, nonce, approver, channel, created, expires}`; single use; expires after 15 minutes;
   the approver must be the operator's Slack user id (Slack channel) or the operator's GitHub login (cloud channel).
3. **Non-TTY promote path:** `k3dm-hub-promote promote REF --approval <id>` replaces the typed confirmation with a check of a
   valid, unused, unexpired approval for exactly that sha, and consumes it. `--approval` together with `BREAK_GLASS=1` is refused.
4. **Click-time recheck:** before running, the sha's CI is green on origin, it is the newest green commit of the release branch,
   and it is ahead of deploy/hub. Any failure refuses and posts the reason; nothing is retried.
5. **Channel A, cloud session:** a new cloud-request action `promote-request <sha>` (`bin/k3dm-cloud-request`) files a request; the
   operator's Slack DM gets Approve/Deny. The cloud session never approves itself.
6. **Channel B, Slack:** the deploy-hub-behind alert card gets an Approve button. It needs the Hermes reauth fix first (10-minute,
   single-use reauth). TOTP as a second factor is decided at spec review (operator decision).
7. **Audit:** every request, approval, refusal and result is one line in the Hermes audit log, with no tokens.
