# v1.33.0 — Hermes Kine circuit breaker

**Status:** approved for the bounded implementation below (2026-09-09)
**Scope:** local hub K3s/Kine only; no ACG/Hostinger mutation; no SQLite writes

## Problem

The hub's embedded K3s Kine SQLite datastore reached 8.3 GiB with more than one
million rows. Slow Kine SQL starved the API server and caused public 502s. The
immediate incident also contained a stale ACG ArgoCD registration pointing at
`host.k3d.internal`, which generated reconciliation retries.

SQLite `VACUUM` does not remove live Kine revision history, and raw age-based
deletion can invalidate Kubernetes resource-version/watch semantics. K3s does
not expose a supported "keep N days" setting for embedded Kine.

## Design

Add a sixth Hermes sensor, `kine`, which uses only read-only local commands:

1. read `state.db` byte size through the k3d server container;
2. inspect recent k3s server logs for `Slow SQL` and `COMPACT` entries;
3. read ArgoCD cluster-registration Secrets and identify the known stale ACG
   endpoint (`host.k3d.internal`).

The sensor is `degraded` after three consecutive samples when either the DB is
at least 8 GiB, or slow SQL occurs without a recent compaction event. Source
failure is `unknown`, never a fabricated degradation.

## Bounded automatic response

When **all** conditions hold—sustained Kine degradation, DB >= 8 GiB, and the
known stale ACG registration is still present—Hermes may run one reversible
circuit breaker per incident, but only when
`K3DM_HERMES_AUTO_KINE_GUARD=1` is explicitly configured:

```text
kubectl --context k3d-k3d-cluster -n cicd \
  scale statefulset/argocd-application-controller --replicas=0
```

This pauses GitOps reconciliation; it does not delete an Application, Secret,
PVC, workload, or Kine row. Hermes records the action, does not repeat it until
the incident resolves, and posts the outcome through its existing Slack path.
Restoring reconciliation remains a deliberate operator action after stale
registration/application cleanup.

## Hard boundaries

- No `sqlite3` write query, `VACUUM`, or file replacement by Hermes.
- No age-based Kine retention policy; five-day retention applies only to
  observability data, not Kubernetes state.
- No action when the registration signature is absent, the probe is unknown, or
  the opt-in is unset.
- Long-term remediation is to remove the churn source and restore healthy Kine
  compaction; if that cannot be achieved, rebuild the hub from GitOps/Vault
  through a separately reviewed offline procedure.

## Acceptance

- Stubbed Hermes tests prove healthy/degraded/unknown datastore verdicts,
  sustained debounce, exact stale-registration guard, opt-in-only execution,
  and one action per incident.
- The probe performs only `docker exec` read, `docker logs`, and `kubectl get`.
- Full Hermes pytest suite, syntax checks, shellcheck, and agent audit pass.
