## Problem

The operator asked for a **verified delivery cost**: the tokens spent to get a spec through a
successful independent verification and, where its Acceptance block requires it, live
verification — not merely through landing.

The **k3dm Agent Dispatch** dashboard stops at landing. Three things are missing:

1. **Verification is not in the ledger.** The ledger (`ledger.jsonl` under
   `K3DM_WORKTREE_ROOT`) records `start`, `resume`, `codex_exit`, `land_refused`, `land` and
   `abandon`. Nothing records whether the independent verifier passed or failed, or when live
   evidence was accepted. Live evidence is in the spec doc itself: a `**Live evidence:**` line
   (parsed by `doc_live_evidence` in `scripts/lib/hermes/prior_art.py`) and a `LIVE-VERIFIED`
   status.
2. **The ledger does not record which spec a task came from.** `start` derives `slug` from the
   spec's basename (`v<version>-` stripped for plans, whole basename for bugs) or takes `--slug`,
   and writes the spec path only to `<run>/spec`, which is deleted with the worktree. A plan slug
   and a bug slug cannot be mapped back to a document reliably.
3. **Only Codex tokens are measured.** `codex_exit.tokens` comes from the `tokens used` line of
   each Codex log. Claude's verification work and a verifier run outside `k3dm-codex-dispatch` are
   not counted. The panel must say "Codex tokens", never "total tokens".

Also unsettled: `resume` reuses the Codex session (`codex exec resume <session_id>`), and
`_task_metrics` takes the token figure from the **last** run. Whether that figure is the session's
cumulative total or the last invocation alone has not been checked. If it is per-invocation, every
per-spec token figure today undercounts specs that were resumed.

## Fix

### 1. Settle what `tokens used` means after a resume

Before any metric change: find a ledger task with more than one run (on 2026-10-18,
`v1.43.0/hub-dr-drill` with 7 and `v1.43.0/hub-data-export-schedule` with 2) and compare the
`tokens` of successive `codex_exit` events, plus the `tokens used` lines in that run's
`codex.log` and `codex-<n>.log` if they still exist. Record the finding in this plan's
**Findings** section. If the figure is per-invocation, `_task_metrics` sums the runs' tokens and the
Per spec table's description changes to match; if it is cumulative, keep the last value.

### 2. `bin/k3dm-codex-dispatch`

- `start` adds `spec` (the repo-relative spec path it already validated) to its ledger event.
  Readers must accept older `start` events without it.
- New subcommand `verify --slug SLUG --result pass|fail [--tokens N] [--verifier NAME]` appends a
  `verify` event for the current release's task. It refuses a slug with no `land` event, a
  `--result` other than `pass`/`fail`, and a non-integer `--tokens`. It writes nothing else and
  needs no network. Claude runs it after the independent verifier reports; `--tokens` is given
  only when the verifier ran as a Codex task (its own `codex_exit` total), and omitted otherwise.
- `usage` lists the new subcommand.

### 3. `bin/k3dm-dispatch-metrics`

For each landed spec, a spec is **delivered** when:

- its latest `verify` event is `pass`, and
- if its spec doc's `## Acceptance` block has any `evidence` item with `kind: live`, the doc's
  `**Status:**` starts with `LIVE-VERIFIED` and it has at least one well-formed
  `**Live evidence:**` line (reuse `doc_live_evidence`; do not write a second parser).

The doc is read from the repo checkout the exporter runs in (`K3DM_REPO_ROOT`, defaulting to the
script's repo), at the `spec` path in the `start` event. With no `spec` field, or a missing file, the
spec is reported as **unknown**, never as delivered or not-delivered.

New series, per window (the window is keyed on the **delivery** time: the later of the `pass` and
the last commit that set `LIVE-VERIFIED`, or the `pass` alone when no live evidence is required):

- `k3dm_dispatch_delivered{window}` — specs delivered in the window.
- `k3dm_dispatch_codex_tokens_per_delivered{window}` — mean Codex tokens per delivered spec,
  including the verifier's `--tokens` when given. Emitted only when at least one spec was delivered.
- `k3dm_dispatch_awaiting_verification` — landed specs with no `pass` yet, or a `pass` but required
  live evidence still missing.
- `k3dm_dispatch_verification_unknown` — landed specs whose doc cannot be found.
- `k3dm_dispatch_rework_landed{cause="review"}` — landed specs with at least one `verify fail`.
  `any` includes it. This closes the gap the v1.43.4 rework bug records.

Existing series keep their names, labels and values.

### 4. Dashboard and guide

- A **Codex tokens per verified spec** stat and an **Awaiting verification** stat. Free space
  starts at `y 22`; place them in one row and keep every existing panel's `gridPos`.
- Panel 13 (**Rework rate**) description: drop the sentence saying the verifier's verdict is not
  recorded and name the `review` cause.
- `docs/guides/grafana-dashboards.md`, dispatch section: define *delivered*, state that the cost
  counts Codex tokens only (implementation runs plus a Codex-run verifier) and excludes Claude's own
  verification, and say how `awaiting` and `unknown` differ.
- The dispatch how-to (or the guide, if there is none) documents `verify` and when Claude runs it.
