## Context

Plan 2 lets a cloud request send its job notices to an approved Slack channel alias:

- Request JSON: optional top-level `notify_route` (schema 1); CLI `bin/k3dm-cloud-request <action> --notify-route ALIAS`.
- Routable actions: those whose allowlist path is `/api/v1/make`, plus `sandbox-up` and `sandbox-down`
  (`scripts/lib/webhook/notify_routes.py` `routable`). Others are rejected with `notification route not supported for this action`.
- Unknown or malformed alias, or no valid map: rejected with `invalid notification route`, before any approval card.
- Map: Keychain item `k3dm-slack-notification-routes` (account `k3dm`) or env `K3DM_SLACK_NOTIFICATION_ROUTES`, format
  `alias:CHANNEL_ID,...`, at most 8 aliases and 512 bytes, `default` reserved; set with
  `make update-webhook-slack-routes K3DM_SLACK_NOTIFICATION_ROUTES=...` (restarts webhook and bridge); doctor key
  `slack_notification_routes`; carried by machine secrets (`scripts/etc/machine/secrets.hub.list`).
- A routed job's notices stay in that channel; if Slack refuses (for example the bot is not in the channel) they are recorded
  `delivered: false` in the job's `delivery.jsonl` and not sent elsewhere. Invite the bot to each aliased channel.
- Approval cards show the alias and still go to the usual approval channel.
- Accepted risk (operator, 2026-11-26): anyone who can push to `cloud-requests` can route an ungated action (for example
  `make-test-all`) without approval, so only low-audience channels may be aliased (no incident or announcement channels).
