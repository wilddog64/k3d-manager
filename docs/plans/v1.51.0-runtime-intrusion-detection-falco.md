## Context / problem

Trivy detects known vulnerabilities in artifacts, while Istio/ztunnel supplies workload identity, encrypted transport and network policy. Neither establishes that unexpected shells, sensitive-file reads or container escape indicators in *running* workloads are detected and delivered as actionable incidents. k3d-manager needs read-only, low-overhead runtime IDS with reproducible detections, alerting and live verification; avoid confusing a scanner finding with evidence of an intrusion.

## Goals and non-goals

- Deploy Falco as the first runtime sensor, via existing Argo CD GitOps, **only on validated supported Linux nodes**.
- Route Falco structured events through Falcosidekick and an existing-compatible metrics/logging pipeline to Prometheus/Grafana and Alertmanager/Slack. Preserve event detail without high-cardinality Prometheus labels.
- Offer Hermes and cloud-bridge **read-only** status/incident diagnostics through the existing role/allowlist architecture, only after a separate security review.
- Provide deterministic, isolated E2E detection tests and independent verification; distinguish sensor readiness, alert transport, acknowledgement and live incident proof.
- No production enforcement, quarantines, pod deletion, node isolation, additional public ingress, credential exfiltration, or auto-remediation.
- No claim of comprehensive NIDS/DPI from ztunnel or Falco. A later Suricata/Tetragon evaluation is out of scope.

## Design decisions

1. **Host prerequisite gate:** Audit kernel/driver mode, supported eBPF or modern eBPF, host mounts, cluster policies and resource headroom before deployment. Falco needs privileged host instrumentation; k3d/OrbStack/macOS VM support is **unverified**, so skip unsupported targets with an explicit status, not a silent green signal. Validate Hostinger capacity separately; trial on a disposable Linux node/ACG when possible.
2. **Deployment:** Pin compatible Helm chart, image digest and ruleset/plugin versions; install via the repository's existing Argo CD AppSet conventions, including rollout-stage metadata and release-branch values. Namespace and service accounts have minimum feasible privileges consistent with the chosen driver; document unavoidable privileged capabilities, security review and compensating controls. No public Service/LoadBalancer.
3. **Detection:** Begin with version-pinned upstream Falco rules for unexpected container shells, sensitive file access, suspicious privilege operations, unexpected binary executions and supported outbound-connection indicators. Avoid claims that every escape, network attack, miner or exfiltration attempt is detected. Document testable rules, severity, exclusions and suppressions by namespace/workload, with expiration and owner.
4. **Event flow:** Falco -> Falcosidekick (or verified equivalent) -> existing alert intake + durable bounded event storage if available. Prometheus exports aggregated counters (cluster, severity, rule ID from finite allowlist, delivery state), sensor/forwarder health, dropped events and timestamp of last event. **Never use pod UID, message body, user-controlled command, IP, file path or event ID as metrics labels.** Detailed events are retained only by an approved existing log backend; if no backend exists, make log retention an explicit prerequisite rather than claiming the metrics are forensic storage.
5. **Alerting:** Alertmanager routes severity-mapped alerts to the existing Slack mechanism, with dedupe/grouping, cooldown, bounded formatting, escaping/untrusted text protection and no sensitive command/output in Slack. State is 'detected', 'notified', 'acknowledged' or 'investigated' only when supported by a traceable event; don't infer resolved from a green dashboard.
6. **ChatOps/Hermes:** Read-only `ids-status`, `ids-recent` and `ids-event` are *proposed* command names, not yet callable. Follow the existing role model; any new cloud-bridge target requires separate min_role, fixed argv, strict validated arguments, response limits, audit log and tests. No automatic destructive dispatch.
7. **Fail-visible:** Missing DaemonSet, disabled probe, unsupported kernel, event loss, webhook failure, stale exporter or no telemetry must display Unknown/No Data or Sensor Unhealthy, **never zero intrusions**.
8. **Security & data:** Apply scoped RBAC, Kubernetes secrets for endpoints, TLS verification, event redaction and retention policy. Threat-model compromised pod, compromised sensor and forged alert input. No external notification endpoints without review.

## Operational requirements

| Item | Requirement |
|---|---|
| Resources | Measure baseline CPU/memory per node and Falco/forwarder usage in isolated test; define per-workload requests/limits from evidence, not invented defaults. |
| Capacity | Hostinger single-node restart risk; avoid scheduling until node headroom and daemon privileges are reviewed. No PVC or permanent new backend without a separate approved spec. |
| Alert quality | Track true positives, false positives, event drops, sensor coverage and detection-to-Slack latency. Set SLO thresholds only after observing a baseline. |
| Deployment | Staged: disposable Linux-node smoke -> local supported-node pilot -> explicitly approved Hostinger rollout. Never deploy automatically merely because the plan doc is filed. |
| Rollback | Git revert pinned deployments/rules; sync AppSets and platform-ops per CLAUDE.md; verify sensor uninstall, daemon privileges and alert routes cleanly removed. Retain recorded incidents per policy. |
| Security | No public ingress, no auto-blocking, no broad cloud-bridge execution permissions. Protect and redact event payloads. |
| Proof | Correlated rule event, metrics increment, visible Grafana panel, Alertmanager/Slack delivery and a traceable incident ID in an authorized live test. |

## Verification

Offline: YAML/Helm rendering, Argo CD policy and permission validation, Falco rule tests and synthetic event transport fixtures. Mutation/negative tests must show failures for disabling the sensor, dropping notification, adding unbounded metric labels, leaking secrets, or permitting destructive cloud requests. Independent verifier writes acceptance tests **only from the Acceptance contract**, not from implementation code.

Live (operator-authorized **disposable Linux** test cluster only): deploy sensor, record health and kernel/driver support; run a deliberately labeled benign shell command in an isolated test pod that matches a pinned Falco rule; capture event with namespace/pod/time/rule, Grafana count delta and Slack notification with matching correlation ID. Repeat with a deliberately failing sink to prove visible delivery failure. Run twice to test deduplication, verify no production traffic impact, and remove test resources. A simulated fixture is *not* live proof. Do not launch exploit payloads or use real secrets.

## Acceptance

```yaml
acceptance:
  must:
    M1: "Supported test Linux node runs version-pinned Falco sensor and exports healthy coverage metrics"
    M2: "A known benign isolated shell test triggers the pinned runtime rule, with traceable event and severity"
    M3: "The same event appears in the intended Grafana view and yields a deduplicated, redacted Slack notification"
    M4: "Sensor absence, unsupported node, dropped event and notification failure appear explicitly as unhealthy or unknown"
    M5: "A GitOps revert removes the sensor and its route without mutating unrelated workloads"
  must_not:
    N1: "Report zero intrusions when telemetry or sensors are absent or stale"
    N2: "Expose payload secrets or untrusted commands in metric labels or Slack message content"
    N3: "Allow automatic quarantine, delete, privilege escalation or non-allowlisted remote execution"
    N4: "Schedule a privileged runtime sensor onto an unvalidated target node"
    N5: "Call a synthetic event fixture live-verified or mark a forwarded event as acknowledged"
  evidence:
    E1: {proves: [M1, M4, N1, N4], kind: offline, how: "render/policy/unit fixtures plus independent negative and mutation tests; then record real compatibility gate"}
    E2: {proves: [M2, M3, N2, N5], kind: live, how: "operator-approved isolated Linux test, correlated Falco event, Grafana sample and Slack delivery with redaction checks"}
    E3: {proves: [M4, N1, N3], kind: offline, how: "independent verifier uses failure-injection and cloud-bridge authorization fixtures; every N case shown red against an intentionally invalid design"}
    E4: {proves: [M5, N4], kind: live, how: "authorized test-node deployment and rollback with namespace/node/DaemonSet and alert-route inventory before and after"}
  interface:
    gitops: "existing Argo CD ApplicationSet and staged deployment flow; exact chart paths to be audited"
    telemetry: "Falco event output, Falcosidekick status, existing Prometheus/Alertmanager/Grafana pipeline"
    chatops: "proposed read-only ids-status, ids-recent, ids-event; not yet implemented"
    e2e: "operator-approved isolated Linux cluster; exact make entry point determined after audit"
```

Every must_not requires a negative test demonstrated red against the pre-change/invalid behavior, plus green after implementation; do not misrepresent a not-yet-installed sensor as a baseline failure of an existing feature.

## Deferred

Tetragon enforcement, Suricata NIDS/DPI, SIEM purchase, automated remediation/quarantine, long-term forensic retention service and cross-cluster incident correlation beyond existing supported telemetry are separate future proposals.

AI triage of Falco findings (read-only, report-only) is the roadmap's v2.6.4 candidate slice; this release only has to leave Falco's events readable through the approved read-only path.
