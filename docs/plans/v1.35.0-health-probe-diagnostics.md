# v1.35.0 — Preserve health-probe diagnostics

**Type:** Observability enhancement
**Status:** Proposed
**Milestone:** v1.35.0
**Owner:** platform / webhook health checks

## Problem

Cluster status can report misleading failures when a probe command returns empty output, malformed
JSON, a timeout, or an authentication/context error. For example, an ESO check currently exposes
`Expecting value: line 1 column 1 (char 0)` instead of the failed `kubectl` command and its exit
evidence. A data-layer probe can similarly turn unreadable readiness output into `not ready`.

This makes a transient Kubernetes-access problem look like an ESO or database outage while HTTP
service checks remain healthy. Operators need enough bounded evidence to distinguish a real resource
failure from a failed diagnostic probe.

## Goals

- Preserve the probe command's exit code, timeout state, and bounded redacted stderr/stdout.
- Distinguish `healthy`, `failed`, `unknown`, and `not_installed` outcomes.
- Replace raw JSON parser exceptions with an actionable, human-readable reason.
- Keep Slack, HTTP, and JSON status representations consistent.
- Prevent credentials, tokens, kubeconfigs, and unbounded command output from escaping.

## Non-goals

- Retrying indefinitely or changing Kubernetes resource state.
- Treating inaccessible diagnostics as proof that the underlying service is unhealthy.
- Exposing full command lines containing secrets or returning complete pod logs.
- Changing the existing HTTP smoke-test success criteria.

## Proposed result contract

Each command-backed probe returns an internal structured result with:

| Field | Meaning |
|---|---|
| `state` | `healthy`, `failed`, `unknown`, or `not_installed` |
| `exit_code` | Integer process exit code, or `null` when not started/timed out |
| `timed_out` | Whether the bounded command deadline expired |
| `stdout_excerpt` | Redacted, normalized excerpt capped at 500 characters |
| `stderr_excerpt` | Redacted, normalized excerpt capped at 500 characters |
| `reason` | Stable category such as `empty_output`, `invalid_json`, `command_failed`, `timeout`, or `context_unusable` |
| `observed_at` | UTC timestamp for correlation, not a high-cardinality metric label |

The status formatter maps these results as follows:

- `healthy`: green check with the resource readiness detail.
- `failed`: red check only when the command completed and established a resource failure.
- `unknown`: warning when the probe could not establish resource state.
- `not_installed`: warning when the CRD/resource type is absent.

For JSON status, the structured evidence is included under a bounded `diagnostic` object. Slack
shows the state, reason, exit code/timeout marker, and one redacted excerpt. Raw parser exception
text is not shown unless it is part of the normalized reason.

## Command handling

1. Execute the existing read-only command with the current timeout and context.
2. Capture stdout and stderr separately, preserving the exit code and timeout state.
3. Classify transport/context failures before attempting JSON parsing.
4. Parse JSON only after a non-empty successful result; classify malformed output as `invalid_json`.
5. Redact registered secrets and common credential/token patterns before truncation.
6. Normalize whitespace and cap each stream independently at 500 characters.
7. Return the structured result to all status consumers.

The probe must continue to use the existing safe process-spawn path and must not interpolate
untrusted resource names into a shell command.

## Metrics and logging

This enhancement does not add resource-name or command-output labels to Prometheus. Optional
bounded counters may record probe outcome by probe family (`eso`, `data_layer`, `service`) and
reason category. Exact excerpts remain response/job evidence only. Debug logs may retain the same
redacted bounded evidence under the existing status-job retention policy.

## Acceptance criteria

- [ ] Empty stdout with non-zero exit reports `unknown`, `command_failed`, and the exit code; it
      does not report `invalid_json`.
- [ ] Empty stdout with zero exit reports `unknown`, `empty_output`, and a bounded diagnostic.
- [ ] Malformed non-empty JSON reports `unknown`, `invalid_json`, and a bounded excerpt.
- [ ] Timeout reports `unknown`, `timeout`, `timed_out=true`, and no fabricated readiness failure.
- [ ] A valid `Ready=True` ESO response remains healthy.
- [ ] A valid `Ready=False` ESO response remains a genuine failed resource check.
- [ ] Data-layer readiness distinguishes command failure from a valid `readyReplicas=0` result.
- [ ] Slack and JSON status expose the same state and reason categories.
- [ ] Secrets and credential-shaped values are redacted in stdout, stderr, Slack, and JSON.
- [ ] Excerpts are bounded and status latency remains within the existing request budget.

## Verification plan

- Add unit tests for command results, classification, redaction, truncation, and JSON parsing.
- Add smoke tests using fake command runners for exit 0/1, empty output, malformed JSON, timeout,
  missing CRD, valid ESO readiness, and valid data-layer readiness.
- Add contract tests proving Slack and JSON render the same diagnostic state.
- Run the offline BATS and Python suites through the tripwire.
- Perform one live Hostinger verification with a healthy ESO/data layer and one controlled
  read-only probe failure; confirm the latter is reported as `unknown` with preserved evidence.

## Rollout and compatibility

The existing top-level health status and HTTP probe fields remain compatible. New diagnostic data
is additive and bounded. The rollout should first land the shared result/classification helper,
then migrate ESO and data-layer probes, followed by Slack/JSON rendering and live verification.
