## Context

`bin/k3dm-cloud-bridge` polls the public `cloud-requests` branch and sends each valid request to the local webhook. Four actions use
the cloud-runner token and today run on push alone: `sandbox-up`, `sandbox-down`, `make-e2e`, `make-e2e-remote` (token choice `:332`).
From now on each waits for an operator Approve on a Slack card. Reader actions must behave exactly as before. Anything on the branch is
attacker-writable.

`scripts/lib/webhook/cloud_approval.py` (landed) provides `load`, `save`, `StoreError`, `admit` (`Pending` or `Refusal`), `remove`,
`card`, `due_for_drain`, `decide` (`Decision.kind`: `execute` with `request` and `expires_at`, `deny` / `expire` with `request_id`,
`drop` with `approval_id`; decided records are removed from the store), `CLOUD_ACTION_ID_RE`. Read it first.

## Change

1. **Single instance.** In `main()`, before the loop, open `STATE_DIR/bridge.lock` and take `fcntl.flock(fd, LOCK_EX | LOCK_NB)`; on
   failure print `k3dm-cloud-bridge: another bridge is running` to stderr and exit 1. Hold it for the process lifetime.
2. **`gated(action) -> bool`**: true exactly for actions whose `ACTION_ALLOWLIST` target is `e2e` or `e2e-remote`, or that are in
   `LIFECYCLE_TIMEOUTS`. Token choice at `:332` becomes `_get_cloud_runner_token() if gated(action) else _get_reader_token()`.
3. **Lazy state and config.** `_approvals_path()` returns `STATE_DIR / "approvals.json"` at call time (tests patch `STATE_DIR` after
   import). Read config (`K3DM_HERMES_APPROVAL_DRAIN_URL`; Keychain `k3dm-hermes-approval-drain-token` and `k3dm-slack-webhook` via the
   existing `webhook.auth` Keychain helper) only when admitting a gated request or when `due_for_drain` is true; never on a tick with
   neither. Never print or log the values. Config is complete only if all three are non-empty and the drain URL starts with `https://`.
4. **Load the store once per tick**, lazily, the first time it is needed. On `StoreError`: log one error line (no content); answer each
   new gated request `rejected` `approval state is unreadable on the bridge`; skip `_recover_orphaned_claims` for this tick; process
   reader requests normally.
5. **New gated request** (claim loop, after `prepare_request` returns no rejection, `:639-643`), instead of `_call_webhook`:
   - config incomplete -> `rejected` `operator approval is not configured on the bridge`;
   - `admit` returns `Refusal` -> `rejected` with its reason;
   - else `save`; then build `card` and `post_interactive` inside one `try` that treats any exception as a failed post. Failed ->
     `remove`, `save`, `rejected` `approval card not delivered; file a new request`. Succeeded -> publish the pending notice (item 7).
   Rejections go through the normal outbox + `_write_commit` path and add the id to `processed`. Each answered or admitted request counts
   toward `MAX_PER_TICK`.
6. **Drain and decide** — every tick, before the `if not changed: return` early exit, if the store loads and `due_for_drain` and config is
   complete: `fetch_approvals(drain_url, token, id_pattern=CLOUD_ACTION_ID_RE)`, `decide(store, items, time.time())`, `save` (records
   the drain time). If `due_for_drain` but config is incomplete, call `decide(store, [], now)` so expiries still happen. Then for each
   decision, one at a time:
   - `drop` -> `delete_approval(..., id_pattern=CLOUD_ACTION_ID_RE)`;
   - `deny` -> `rejected` `denied by the operator`; `expire` -> `rejected` `not approved before the request expired` (both via outbox +
     `_write_commit`, add to `processed`);
   - `execute` -> check `time.time() < decision.expires_at` immediately before the token is read; if not, answer as `expire`. Otherwise
     run the stored request through the shared tail (item 8).
   Decisions count toward `MAX_PER_TICK`, but every decision from one `decide` call is acted on in that tick even past the limit: its
   record was already removed and saved, and there are at most `MAX_PENDING` of them.
7. **Pending notice.** `_write_commit` gains `pending=False`; with `pending=True` it writes `responses/<id>.pending.json` with
   `_response(id, action, "ok", 202, body={"status": "approval-pending", "approval_id": <id>, "expires_at": <ISO Z>})`, does not touch
   `ledger/processed.txt`, and is never stored in the outbox. Each tick, for every record with `notice_published == False`, try it; on
   success set the flag and `save`; on failure retry next tick. Never repost a card.
8. **Shared tail.** Factor what happens after `prepare_request` for a request that is sent (`_call_webhook`, `scrub_credentials` for
   `job-status`, `job_artifacts`, `_watch_entry`, outbox, `_write_commit`, `processed`) into one function used by both the claim loop and
   `execute`. Keep each existing call's arguments exactly as today (tests fake these functions positionally).
9. **Orphan recovery** (`:236-253`): skip ids in the pending store (as it skips `_slow_pending`).
10. **Plist**: add `K3DM_HERMES_APPROVAL_DRAIN_URL` = `https://k3dm-slack-relay.k3dm.workers.dev/hermes/approvals` to the bridge plist
    template's `EnvironmentVariables`. **Makefile** `install-cloud-bridge`: presence-check (no value printed) the Keychain items
    `k3dm-hermes-approval-drain-token` and `k3dm-slack-webhook` with a warning, not a failure, if absent (gated requests are then rejected
    "not configured").

## Tests (extend `scripts/tests/bin/test_cloud_bridge.py`; follow its fixtures)

First, a fixture assertion that `_approvals_path()` is under the tmp `STATE_DIR` and that the real Keychain helper and `post_interactive`
are patched. Fakes: Keychain, `post_interactive`, `fetch_approvals`/`delete_approval` (returning drain items with `decision`), counting
fakes for both token getters and the webhook opener, a controllable clock.

Cover: `gated` true for exactly the four actions; a gated request posts one card, commits `.pending.json` (no nonce), reads no
cloud-runner token, opens no webhook connection; approve runs it once and commits the normal response; deny, expiry, wrong nonce,
unknown id, and the clock passing `expires_at` between `decide` and the token read never run it; exact reason for every rejection; a
second `process_tick` after a successful execute does not run it again; a crash simulated by raising inside the shared tail after `save`
leaves nothing to run on the next tick; restart (fresh module state, same `STATE_DIR`) keeps the record and orphan recovery leaves it;
`StoreError` rejects new gated requests with its reason, skips orphan recovery, and still answers a reader request; a reader request is
answered in the same tick with three records pending; a tick with no pending records and no gated request makes zero Keychain reads; the
lock refuses a second `main()`; a failed pending-notice push is retried next tick without a second card; the nonce never appears in any
committed file, outbox file or captured log (scan them for the nonce); all existing tests pass unchanged.
