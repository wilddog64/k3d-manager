**Approval:** operator asked to write this enhancement spec; no live system changes approved

**Related:** `docs/howto/cloud-session-requests.md`, `docs/architecture/cloud-bridge.md`, `docs/bugs/2026-10-06-cloud-bridge-make-job-status-empty-output.md`, `docs/bugs/2026-10-10-offline-suite-count-floor-stale-and-partial-runs.md`, `docs/bugs/2026-10-15-cluster-up-progress-slack-thread-missing.md`

## Problem / observed need

On 2026-10-20 `OfflineSuiteFailing` and `OfflineSuiteRunIncomplete` fired together for `target=test-all` on `ubuntu-hostinger` (three failed cases; incomplete run). The operator was away from the M4 and could not inspect the original local `k3dm-test-all-*.log`. A cloud agent successfully queued a new `make-test-all` through `cloud-requests`, but that repeats a roughly 15–20-minute test run merely to retrieve evidence that the prior run already produced. Existing `job-status` returns only a bounded tail for an individual webhook job and may not contain earlier failed assertions.

The current `bin/k3dm-test-metrics` already parses failures (up to `MAX_FAILURES=100`), suite/case/name/first reason, stage markers and aggregate counts for Prometheus. Extend that structured parsing **without making Prometheus labels or Git history a raw log store**.

## Outcome / user story

A cloud agent with only the existing reader-scoped bridge can query the **most recent recorded offline test run**, or one recent run by an opaque server-issued ID, and receive: run completion/classification, timestamps, case counts, stage completeness, and sanitized failing-case identifiers/reasons. The operation is fast, bounded, read-only, works while the operator is away, and **never triggers tests**.

## Goals

- Retrieve prior `test-all` result data in seconds without a `make` job or cluster mutation.
- Show `failed` vs `incomplete` distinctly; correlate them to one recorded run, including last successful stage and missing stages.
- Return actionable failing-suite/test names and bounded, redacted diagnostic summaries with clear truncation indicators.
- Retain a small, local, auditable history; do not publish raw stdout/stderr, environment, credentials, tokens, or arbitrary paths on GitHub.
- Preserve the current `make-test-all`, Pushgateway metrics and alerts, and the existing `cloud-requests` six-field JSON contract.

## Non-goals

- Remote execution of tests, retries, test selection, arbitrary filesystem reads or shell commands.
- Returning complete test logs or stack traces through the reader tier.
- Adding an LLM diagnosis step, using Slack as a required transport, or changing alert thresholds.
- Expanding cloud-bridge or webhook authentication privileges.

## Proposed architecture

### A. Capture a structured local result at the existing publish boundary

After each `make test-all` run, extend/reuse `bin/k3dm-test-metrics.parse_log()` to produce a **separate normalized JSON record** while retaining the existing Prometheus payload behavior.

- Write under a fixed owner-controlled path, e.g. `~/.k3dm/test-runs/`; **never** accept a request-supplied path.
- Fields: `schema_version`, opaque `run_id`, `target=test-all`, `started_at`, `finished_at`, `exit_code`, `classification`, `run_complete`, `expected_stages`, `completed_stages`, `missing_stages`, `cases_total`, `cases_failed`, `suites` (bounded aggregate counts), `failures` (bounded list), `truncated`, and `source=local-test-metrics`.
- A failure record contains `suite`, `case`, `name`, and **sanitized bounded** `reason`; no arbitrary raw line fields or paths. Handle BATS TAP `not ok`, pytest and unittest output; if the parser cannot isolate a case, represent `diagnostic_unavailable` rather than inventing one.
- Distinguish an incomplete run with 0 failed cases from a completed green run. A result can be `failed_untriaged` and `run_complete=false` simultaneously.
- Atomic write with restrictive permissions (directory 0700, files 0600, temp file + rename); retain the newest **20** records or 14 days, whichever is smaller, as a configurable bounded policy. Only prune owned record files after validating their location and type.
- The test result's timestamp and run ID must identify the exact run; do not read `latest` from stale Pushgateway metrics. If data predates this implementation, return `not_available` with a clear reason, not guessed failures.
- A crashed/killed run before metrics publication is not automatically observable: document this limit. Consider a future separate in-progress marker, but do not misrepresent an interrupted writer as a finished run.

### B. Read-only local webhook retrieval

Implement one fixed reader endpoint (proposed `GET /api/v1/test-runs`) with **only allowlisted selectors**:

- `target=test-all` and optional `run_id` (opaque ID matching a restrictive regex, selected from the bounded local index).
- Without `run_id`, return the most recent recorded `test-all` result plus the result's age and capture timestamp.
- With `run_id`, return that one retained record. No filename, path, glob, query expression, shell command, or custom target accepted.
- Strict schema checks, read-time redaction, bounded response size (suggest **16 KiB**), bounded failures (at most **20** returned by default with `failures_total` / `truncated`), fixed safe error codes for absent/expired/malformed records; reject symlink traversal and file ownership/permission anomalies.
- Require the existing authenticated **reader** credential. Never let the client supply a webhook URL or exceed the role's permissions.
- Do not log complete result bodies; log request ID, run ID, status, duration and a coarse count only.

### C. Cloud-bridge contract

Add a single allowlisted action `test-run-diagnostics` to `scripts/lib/webhook/cloud_actions.py` (same action table consumed by bridge/helper).

Example cloud request (existing six-field wrapper remains mandatory):

```json
{
  "schema": 1,
  "action": "test-run-diagnostics",
  "args": {},
  "requested_by": "cloud-agent",
  "requested_at": "<generated UTC timestamp>",
  "expires_at": "<generated UTC expiry>"
}
```

Optional `args.run_id` must match the fixed opaque pattern. The bridge maps the action to the fixed reader endpoint and commits only the **scrubbed, bounded structured result** under `responses/<id>.json`. Keep request validation exact; unknown arguments are rejected. No additional keychain token or elevated role is needed.

Document `bin/k3dm-cloud-request --wait test-run-diagnostics`, and how to retrieve a specific `run_id`. If the response is too large, summarize/truncate locally rather than streaming raw logs or silently dropping the record.

### D. Failure semantics and observability

- Differentiate `no_record`, `stale_record`, `corrupt_record`, `redacted`, `truncated`, and `run_incomplete` in a stable structured status field; do not label unavailable evidence as a passed run.
- Report last completed stage and expected-but-missing stages; support the original 2026-10-20 failure class without rerunning tests.
- Do not embed raw failing-case reasons in Prometheus labels beyond existing behavior; evaluate the existing `k3dm_test_failure` label design separately if sensitive content leakage is observed.
- Update `docs/howto/cloud-session-requests.md`, `docs/architecture/cloud-bridge.md`, and relevant test-result operations guidance.

## Implementation and rollout sequence

1. Extract/extend the parser with fixture-driven regressions and explicit redaction tests; validate source log semantics without publishing any data.
2. Persist restricted atomic structured results locally; test retention, concurrent readers and interrupted writers.
3. Add reader endpoint and exact bridge action with negative authorization tests.
4. Validate on the operator's macOS environment and via an operator-approved read-only `cloud-requests` request after a pre-existing test run.
