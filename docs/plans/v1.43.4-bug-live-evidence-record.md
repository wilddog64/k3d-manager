## Problem

A bug doc becomes LIVE-VERIFIED by editing its Status line to free text. Nothing records **which
environment, scenario, test run and commit** produced the proof, and nothing checks that the
proving run actually contained the fix. An old green run can be cited as proof for newer code,
and the Bug Tracking table will show it as live-verified.

The e2e runs already write all four facts (`~/.k3dm/e2e/<run>.json` carries `runner`, `tier`,
`project`, `service`, `run_id`, `commit`). They are just never carried into the bug doc.

## Design

### 1. The `**Live evidence:**` line

A bug doc records each live proof as one header line, any number of them, anywhere in the doc:

```
**Live evidence:** 2026-10-17 · run 1792268856-27928 · env sandbox/local-m4 · scenario stripe/product-catalog · commit 408c2934 · proves E3
```

Fields, in this order, separated by ` · ` (U+00B7 with one space either side; ` | ` also accepted):

| Field | Form | Notes |
|---|---|---|
| date | `YYYY-MM-DD` | required |
| `run <id>` | non-empty token, no spaces | an e2e run ID, or a log path for a non-e2e proof (`run logs/make-down-2026-10-18.log`) |
| `env <value>` | non-empty token, no spaces | e.g. `sandbox/local-m4`, `hub/k3d`, `hostinger` |
| `scenario <value>` | non-empty token, no spaces | e.g. `stripe/product-catalog`, `make-down-keep-hub` |
| `commit <sha>` | 7–40 lowercase hex | the k3d-manager commit checked out when the proof ran |
| `proves <ids>` | comma-separated evidence IDs (`E3` or `E1,E3`) | IDs from the doc's Acceptance block |

A line that does not match this form is **malformed** and counts as absent.

Add `doc_live_evidence(text) -> list[dict]` to `scripts/lib/hermes/prior_art.py`, returning one
dict per well-formed line (`date, run, env, scenario, commit, proves`). Malformed lines are skipped.
Both consumers below import it; no second parser.

### 2. Bug metrics: the `live_evidence` label

In `_bug_status_metrics`, every `k3dm_bug_info` sample gains `live_evidence="<state>"`:

| State | When |
|---|---|
| `-` | status is not fixed, or the doc is not LIVE-VERIFIED |
| `n/a` | LIVE-VERIFIED, release older than v1.43.4 (historic docs predate the rule and must not light up) |
| `missing` | LIVE-VERIFIED, release ≥ v1.43.4, no well-formed `Live evidence` line |
| `unchecked` | well-formed line(s) exist but the fix commit is unknown (`fix_sha` is `-`) |
| `stale` | fix commit known, and **no** well-formed line's commit has the fix commit as an ancestor (or equal), including when the evidence commit does not exist in the repo |
| `ok` | at least one well-formed line's commit contains the fix commit |

Ancestry is `git -C <root> merge-base --is-ancestor <fix_commit> <evidence_commit>` (rc 0 = contains,
rc 1 = does not, anything else = stale). Use the full fix commit from `fixed_in[path]["commit"]`,
not the 8-char label. Timeout 10s per call, as `_verification_commit` does. `_bug_status_metrics`
takes a new optional parameter `evidence_check=None`: a callable `(fix_commit, evidence_commit) ->
bool`. Default is the git call above; tests inject a stub.

**Open for:** a LIVE-VERIFIED row on release ≥ v1.43.4 whose state is `missing` or `stale` keeps
counting days since filed (it is not proven). `ok`, `unchecked` and `n/a` keep today's `-2`. Every
other row's value is unchanged.

### 3. Lint: `scripts/check-bug-evidence.py`

New script. Arguments: bug doc paths. For each path, it fails (exit 1, one line per failure naming
the file) when **the staged/working version's Status is LIVE-VERIFIED and the `HEAD` version's
Status is not** (the commit makes the doc LIVE-VERIFIED), and the doc has no well-formed
`Live evidence` line. A doc already LIVE-VERIFIED at `HEAD`, a new file that is not LIVE-VERIFIED,
and any non-`docs/bugs/` path all pass. A new file that is LIVE-VERIFIED on creation is checked.
Exit 0 when nothing fails. Read the HEAD version with `git show HEAD:<path>` (missing = new file).

Wire it:
- `.githooks/pre-commit`: a new guard block after the doc-link guard, same shape — staged
  `docs/bugs/*.md` only, bypass `K3DM_SKIP_BUG_EVIDENCE=1`, message names the `Live evidence` format
  and `docs/guides/grafana-dashboards.md`.
- `Makefile`: `check-bug-evidence` target running it over every `docs/bugs/*.md`; add to `.PHONY`.

### 4. Dashboard and docs

- `grafana-dashboard-bugs.yaml`: add a **Live evidence** column to the Bug Tracking table, after
  Live-verified, from the `live_evidence` label, with value mappings: `ok` → `✓ current`,
  `stale` → `stale proof` (red), `missing` → `missing` (orange), `unchecked` → `unchecked`,
  `n/a` → `n/a`, `-` → `—`. Do not reorder or remove existing columns.
- `docs/guides/grafana-dashboards.md`: in the Bug Tracking section, document the column, its six
  states, the `Live evidence` line format (copy the table above), and that Open for keeps counting
  for `missing`/`stale`.

## Verification notes (Claude, 2026-10-17)

- Codex gated the `live_evidence` state on the doc being present in `fixed_in`, so a LIVE-VERIFIED
  doc with an unknown fix commit showed `-` and dropped out of tracking (M3/M5). Gate removed; two
  earlier tests that asserted "LIVE-VERIFIED → -2" with no evidence now carry an evidence line,
  because this spec deliberately supersedes that rule for v1.43.4+.
- The "fix commit" from `bug-tally.py` is the first commit that closed the doc's Status, not the
  code fix. A doc closed after its proof (straight to LIVE-VERIFIED) reads as stale. Added an
  optional `**Fix commit:** <sha>` header (`doc_fix_commit`) that overrides the proxy for this check.
- Docs filed before the Acceptance rule have no E-IDs: `proves fix` is accepted for them.
- The guide's Fix commit paragraph had been split by the insertion; restored.
- Codex removed the per-row `fixed_item` assignment in the label loop, so every row's `fix_sha`
  carried the last doc's commit (`cc88386c` on the real tree). Restored; regression test red on `1a965ff8`.
- Backfilled `**Live evidence:**` on the six LIVE-VERIFIED v1.43.4 docs from the runs their Status
  cites; all six scan `ok`.
- Releases are squash-merged, so the tally's commit for a closed-out release is the squash commit
  (`cc88386c` for 447 docs). `**Fix commit:**` keeps the introducing commit; the tally commit stays
  the integration commit. The ancestry check now returns `unchecked`, not `stale`, when git cannot
  resolve either commit (exit 128) — the state every cited branch commit reaches once a
  squash-merged release branch is deleted. The `/post-merge` branch cleanup now pushes
  `archive/<branch>` tags before deleting, so the commits stay resolvable. N5 test red on `7c8e8b49`.
