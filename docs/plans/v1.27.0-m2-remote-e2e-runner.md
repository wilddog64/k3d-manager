# v1.27.0 — M2 remote E2E runner

**Milestone:** v1.27.0 (promoted from v1.26.0 — deferred at the v1.26.0 cut)  
**Status:** Scoped — high-priority reliability work; splits E2E load off the M4 laptop.  
**Plan count:** #2 of the v1.27.0 four (under the maximum of five).  
**Depends on:** `v1.27.0-foundation-managed-vcluster-cli.md` — must land first.  
**Roles:** M4 remains the hub, public edge, and observability source of truth; M2 runs ephemeral E2E compute only.

## Problem

The M4 hosts the k3d hub, Grafana, Prometheus, Keycloak, Cloudflare port-forwards, and normal development work. A vCluster E2E run adds an ephemeral control plane, datastore pods, service pods, Playwright, and image pull/build pressure to the same OrbStack runtime. On 2026-08-19 the M4 was approximately 75% CPU busy with a load average near its ten cores; subsequent OrbStack/kubelet instability interrupted Grafana and Keycloak.

The available M2 (`m2jump` → `m2-air.local`) has eight CPU cores, 16 GiB RAM, low current CPU load, ample disk, and OrbStack installed. It is suitable for one bounded E2E run at a time, but must not become a second hub or receive the M4's administrator kubeconfig.

## Goal

Run `make e2e`-equivalent vCluster/Playwright work on the M2, publish a schema-validated result to the M4 hub, and keep Grafana on the M4 as the single E2E dashboard. An M2 failure must not interrupt M4 public services; an M4 hub failure must prevent result publication without granting the M2 extra cluster authority.

## Locked architecture

```text
M4 operator ──SSH dispatch──> M2 runner cluster ──E2E result JSON──> M4 restricted publisher ──> hub ConfigMap
     │                              │                                      │                         │
     │                              └─ vCluster + Playwright only           └─ schema/authorization    └─ exporter → Prometheus → Grafana
     └─ Grafana, Keycloak, ArgoCD, Cloudflare, hub k3d stay on M4
```

1. **Dedicated M2 cluster.** The M2 owns a distinct k3d cluster/context (for example `k3d-e2e-runner`), a separate kubeconfig, vCluster namespace, report directory, and image cache. It must never use `k3d-k3d-cluster` or the M4 hub kubeconfig.
2. **One run at a time.** The M2 runner uses a host-level lock. A second dispatch returns a clear busy result; it never creates a concurrent vCluster on a 16 GiB host.
3. **Foundation-owned CLI prerequisite.** The `v1.27.0-foundation-managed-vcluster-cli.md` plan is a hard dependency and must land first. The runner calls the foundation contract; no manual `vcluster` install, Homebrew install, or consumer-local binary download is permitted.
4. **No M4 admin credential on M2.** M2 writes its local JSON summary only. A restricted M4-side publisher accepts that JSON through a dedicated SSH key/forced command, validates it, and is the only component that creates the hub `e2e-result` ConfigMap.
5. **Same observability contract.** Published events retain the existing `k3dm.k3d.io/e2e-result=true` label and E2E schema. Add a required `runner` field (`m2` for this runner) and a matching ConfigMap label. Extend the exporter and Grafana dashboard labels/variables so M2 results are visible without mixing them with future runners.
6. **M4 remains low-impact.** Dispatch and publication are bounded control-plane operations. M4 never creates the M2 vCluster, runs Playwright, pulls E2E images, or performs the M2's datastore/service startup.

## Implementation

### 1. M2 runner bootstrap and preflight

Add a k3d-manager-managed M2 bootstrap/health command. It must:

- connect only through the configured `m2jump` SSH host; do not hard-code a LAN IP;
- start OrbStack only when it is stopped, then wait with a bounded timeout for Docker to respond;
- create or reconcile the dedicated M2 runner k3d cluster, never the M4 hub cluster;
- verify the exact vCluster CLI through `foundation_ensure_vcluster_cli`;
- enforce preflight capacity before dispatch: no active lock, Docker responsive, at least 35% CPU idle over two samples, at least 25% memory free, and at least 40 GiB available disk;
- report a structured unavailable/busy/capacity result instead of attempting a run when a gate fails.

M2's 16 GiB RAM is sufficient for one E2E vCluster. Do not schedule image builds, CVE scans, or load tests on the M2 box concurrently in v1.27.0 (the sibling image-signing and adaptive-load-testing scopes run on their own substrates, not on this runner).

### 2. Remote dispatch

Add `make e2e-remote RUNNER=m2 [DIGEST=sha256:…]` on M4. The command:

1. validates `RUNNER` against an allowlist and validates `DIGEST` using the existing E2E digest contract;
2. sends a bounded SSH command to M2 that runs the existing E2E entry point with the M2 runner context and report directory;
3. streams the remote terminal output to the caller and persists a local dispatch transcript;
4. returns the E2E result code unchanged, including capacity/busy failures;
5. does not fall back to running the workload locally on M4.

The local `make e2e` behavior stays unchanged for explicit local development. Documentation must direct routine live validation to `make e2e-remote RUNNER=m2` once the runner is available.

### 3. Restricted result publication

Create an M4-side `e2e-result-publish` command and a dedicated SSH principal for M2. Its forced command accepts one JSON document on stdin and performs all of the following before touching Kubernetes:

- rejects additional SSH commands, shell access, paths, and environment-controlled kubeconfigs;
- validates the exact E2E result schema: run ID, timestamp, tier, service, project, candidate digest, pass/fail, exit code, phase, duration, and `runner=m2`;
- bounds field lengths and rejects unexpected labels/annotations;
- assigns the M4 hub context and `platform-ops` namespace internally;
- creates the ConfigMap and applies the existing retention/pruning policy;
- writes a redacted audit log containing run ID, runner, result, and publisher outcome.

The publisher must be idempotent for a run ID so SSH retries cannot create duplicate observations. It must not accept a kubeconfig, arbitrary manifest, arbitrary kubectl arguments, or an arbitrary namespace from M2.

### 4. E2E result and Grafana provenance

Extend the E2E summary/event contract with `runner`:

- local E2E defaults to `runner=local-m4`;
- M2 E2E sets `runner=m2` at run creation, not through user-provided free text;
- the published ConfigMap includes `k3dm.k3d.io/e2e-runner: m2`;
- `e2e_run_info`, `e2e_last_run_pass`, timestamp, duration, and last-success metrics gain the `runner` label;
- Grafana gets a runner variable with `all`, `local-m4`, and `m2` values; existing panels must continue to show all runners by default;
- alerts include runner in their labels and summaries.

The exporter must remain read-only (`get,list` ConfigMaps only). No RBAC widening is permitted.

### 5. Failure behavior and operations

- If M2 becomes unreachable, return `runner unreachable`; do not start local E2E work on M4.
- If M2 loses capacity or its vCluster fails, write/publish the failed result when possible and preserve its local report/transcript for investigation.
- If M4 publication is unavailable, retain the M2 result under its report directory and mark it `publication_pending`. A bounded, explicit replay command may publish only validated retained results after M4 recovers.
- Never automatically restart OrbStack, delete a cluster, or clear a lock without bounded ownership/age checks.
- M4 status must distinguish hub health from runner availability; an unavailable M2 is a warning unless an E2E run was explicitly requested or an E2E freshness alert is firing.

## Security boundaries

- Use a new dedicated M2 SSH key, not a personal/admin key, with an M4 `authorized_keys` forced command for result publication.
- Limit the M2 key to the publisher command; disable PTY, port forwarding, agent forwarding, and shell access.
- Store no M4 kubeconfig, Vault token, Cloudflare credential, or Keychain secret on M2.
- Verify remote host identity through the existing SSH configuration/known_hosts; do not add `StrictHostKeyChecking=no`.
- Treat runner output and result JSON as untrusted input; redact credentials from retained logs and Grafana labels.

## Tests and gates

### Unit/structural

- BATS: capacity gate, busy lock, SSH target allowlist, digest validation, M2 command construction, no-local-fallback, result-schema rejection, publisher idempotency, and rejection of arbitrary namespaces/manifests/kubeconfigs.
- BATS: event schema preserves legacy local results and emits the new runner label; exporter and Grafana dashboard tests cover the label and default `all` variable.
- shellcheck all changed shell files; Python syntax checks for any publisher helper.
- static disappearance checks ensure the remote runner path does not copy/read M4 kubeconfig, Vault tokens, or Cloudflare credentials.

### Live acceptance

1. Start M2 OrbStack through the managed bootstrap and verify runner preflight passes.
2. Run one intentional failing E2E and one passing E2E from M4 through `make e2e-remote RUNNER=m2`.
3. Confirm M4 public Grafana, Keycloak, and ArgoCD stay healthy throughout both runs.
4. Confirm each result appears once in `platform-ops`, Prometheus exposes runner-labelled metrics, and Grafana displays the correct M2 pass/fail state.
5. Confirm an unavailable M2 produces a warning/clear dispatch failure without creating an M4 vCluster.

## Non-goals

- Do not move the M4 hub, Grafana, Prometheus, Keycloak, ArgoCD, Cloudflare tunnel, or day-to-day development to M2.
- Do not make M2 a second production or public cluster.
- Do not schedule load tests, CVE scans, or concurrent E2E runs on the M2 runner box in v1.27.0.
- Do not bypass the foundation-managed vCluster CLI contract.
- Do not share the M4 administrator kubeconfig with M2.

## Definition of done

- Routine E2E work can run on M2 through a documented M4 dispatch command.
- M4 public services remain healthy while M2 E2E runs execute.
- M2 has no M4 administrator credentials and can publish only validated E2E results.
- Grafana displays runner-labelled E2E results from the M2.
- All focused tests, shellcheck, and the two-run live acceptance gate pass.
