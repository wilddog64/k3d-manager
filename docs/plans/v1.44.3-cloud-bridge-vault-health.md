## Problem

During the 2026-10-20 Hostinger incident, the operator was away from home. A critical frontend blackbox 502 coincided with Hostinger Kubernetes API request timeouts, degraded data workloads, and an ExternalSecret event reporting `ClusterSecretStore "vault-backend" is not ready`. The hub ESO store remained Ready=True. An earlier 2026-10-17 Hostinger incident involved **sealed Vault** and a previously missing unseal watchdog, which was later fixed and live-verified.

Existing cloud actions `hostinger-status`, `diagnose-pods`, `diagnose-describe-pod` and `diagnose-logs` are insufficient to distinguish **Vault sealed** from **Vault unreachable**, **Kubernetes API unreachable**, **ESO store not ready**, or **watchdog failed**. In particular, a `kubectl` timeout is not a valid measurement of Vault's sealed state.

An AI investigator should be able to obtain bounded, read-only, correlated Vault diagnostics for both the local hub and Hostinger without shell access, privileged tokens, cluster mutation, or running an unseal procedure.

## Desired operator workflow

```bash
# PROPOSED, NOT IMPLEMENTED
bin/k3dm-cloud-request --wait vault-status --arg provider=hostinger
bin/k3dm-cloud-request --wait vault-status --arg provider=hub
```

The result should clearly separate **observed state**, **reachability**, **freshness**, and **unknown**. A remote agent can compare hub versus Hostinger and attach sanitized evidence to the P1 incident without claiming recovery.

## Design

### 1. Single fixed reader-scoped action

Extend `scripts/lib/webhook/cloud_actions.py` with exactly one action, `vault-status`, accepting a mandatory `provider` argument with **only** `hub|hostinger`. Never broaden this to arbitrary providers, namespaces, endpoints or pod names from the caller. Map to one fixed, authenticated webhook reader endpoint, e.g. `GET /api/v1/vault-status?provider=hostinger` (exact route subject to current webhook conventions).

Use the existing six-field cloud request envelope; no arbitrary JSON keys:

```json
{
  "schema": 1,
  "action": "vault-status",
  "args": {"provider": "hostinger"},
  "requested_by": "cloud-agent",
  "requested_at": "<generated UTC time>",
  "expires_at": "<generated UTC expiry>"
}
```

Bridge validates provider against the exact action-specific pattern and persists only a bounded, redacted response to `cloud-requests/responses/<request-id>.json`. All secrets stay on the host. No admin/operator permission and no new credential distributed to remote agents.

### 2. Resolve fixed per-provider targets locally

Map each provider to *server-side* contexts and resources. Initial targets, verified against the 2026-10-17 incident record:

- `hostinger`: Kubernetes context `ubuntu-hostinger`, Vault `secrets/vault-0`, unseal watchdog `secrets/vault-unseal-watchdog`, Vault-backed ESO `ClusterSecretStore/vault-backend`.
- `hub`: existing hub kube context, Vault instance and watchdog, discovered through their known deployment configuration rather than assuming Hostinger's names apply.

Do not accept pod name, namespace, context, URL, JWT, Vault token, or cluster override as request arguments. If configured resource names are absent, report `not_installed`/`not_available` rather than silently falling back to another cluster.

### 3. Truthful multi-layer health probe

Collect a short independent result for each layer, with a hard per-probe timeout and an overall bounded timeout:

1. **Kubernetes API reachability:** server-side read-only `/readyz` or equivalent, with connection/timeout/auth errors classified separately. This check establishes **visibility**, not Vault health.
2. **Vault pod state:** observed pod phase, Ready condition and restart count (or `unknown` if API cannot answer). No secret/env/container arguments in output.
3. **Vault seal state:** prefer an established, configured Vault health endpoint, such as `GET /v1/sys/seal-status`, reachable from an authorized local/cluster route **without obtaining root/unseal credentials**. Parse only `initialized` and `sealed`; restrict addresses to configured local paths and prohibit user-supplied URLs, redirects and open SSRF proxies. If the probe fails or cannot reach Vault, use `unknown`, **never** `sealed=true` by inference. Determine and document whether Vault's unauthenticated seal-status endpoint is actually available along the selected transport before implementation.
4. **ESO store state:** read `ClusterSecretStore/vault-backend` conditions and `observedGeneration`, extract only Ready True/False/Unknown, bounded condition reason and age; never return Secret data or sensitive messages.
5. **Unseal watchdog status:** read `CronJob` schedule, suspension, last schedule/success and bounded latest Job state. If Jobs/history are absent or stale, report `unknown`/`not_available`; `CronJob exists` does **not** prove it ran or successfully unsealed Vault.

Each layer gets `state`, `checked_at`, `error_class` (when applicable) and `age_seconds` for cached observations. Independent checks should continue when possible if the Kubernetes API times out; failed API reachability may make pod/store/watchdog unknown without preventing a separately authorized direct seal endpoint check.

### 4. Stable minimal response contract

Illustrative schema (values below are examples, not evidence of current live state):

```json
{
  "schema": 1,
  "provider": "hostinger",
  "checked_at": "2026-10-20T21:45:00Z",
  "kubernetes_api": {"state": "unreachable", "error_class": "timeout"},
  "vault": {
    "reachable": "unknown",
    "initialized": "unknown",
    "sealed": "unknown",
    "pod_ready": "unknown"
  },
  "secret_store": {
    "name": "vault-backend",
    "ready": "unknown",
    "reason": "kubernetes_api_unavailable"
  },
  "unseal_watchdog": {
    "state": "unknown",
    "last_success_at": null
  },
  "overall": "unknown",
  "partial": true
}
```

Separate `reachable` from `sealed`. For `sealed`/boolean-looking fields, use actual JSON booleans **only when measured**; otherwise the explicit string `unknown`. `overall` may be `healthy|degraded|unknown`; never return `healthy` unless observed Vault unsealed and required dependencies are current. Return no more than 8–16 KiB, with predictable truncation and no raw command output.

### 5. Guardrails

- Credential boundary: reader token only, existing webhook role checks and bridge validation unchanged.
- All operations are fixed, bounded, read-only. Forbid `vault operator unseal`, `vault operator init`, `kubectl exec` that could mutate, restarts, Job creation, secret reads and unrestricted shell/HTTP access.
- Treat Vault seal-status response and Kubernetes resource metadata as **untrusted**. Allowlist output fields and enum values; redact at webhook **and** bridge boundaries. Never return Vault tokens, unseal shards, secret paths/values, pod environment, service-account tokens, response headers or arbitrary event messages.
- Restrict egress to configured Vault endpoints; reject redirects and arbitrary hostnames to prevent SSRF.
- Apply independent timeouts, concurrency/rate limits, failure-safe defaults and bounded output.
- A cached `Ready=True` with stale timestamp must not hide a current timeout or be called live-healthy.
- Preserve existing webhook and cloud-request actions, API response contracts and Slack notification routing.

## Implementation / verification plan

1. Confirm existing hub/Hostinger Vault instance addresses, namespaces, safe seal-status transport and webhook architecture. Resolve these via existing server configuration, not client input.
2. Implement pure diagnostic collectors with hard deadlines and strict normalization first; add negative redaction, SSRF, auth and timeout tests, including mutation checks.
3. Register a single fixed reader route and cloud action; preserve the exact request envelope and existing capabilities.
4. Update docs and confirm output does not reveal secrets in example artifacts.
5. Run stubbed regression suite, then request **operator-approved** live hub/Hostinger verification. Capture response IDs, branch SHA, observed states and timestamps. Keep status PROPOSED until implementation; do not claim LIVE-VERIFIED from simulated data.

## What NOT to Do
