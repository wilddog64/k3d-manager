## Why this spec exists

The Tier 2 tracker records P4 as *"Operator's action (Keychain `k3dm-acg-pluralsight`, or one
manual sign-in in `pw-profile`)"*, which reads as though ACG login is an unautomated manual step.
**It is not.** The headless auto-login was built and wired in v1.14.0 / lib-foundation v0.4.1–v0.4.2
and fires on every run. Verified against the live tree on 2026-09-22:

```
make -C scripts/lib/foundation credential-test
  → scripts/lib/acg/bin/acg-credential-test:7-8   source cdp.sh; _browser_launch
     → _browser_launch                            cdp.sh:132 (Chrome already up) AND :163 (fresh launch)
        → _cdp_ensure_acg_session                 cdp.sh:166
           → _secret_load_data k3dm-acg-pluralsight username|password   cdp.sh:184-185
```

`_browser_launch` is called unconditionally at the top of `acg-credential-test`, and it invokes
`_cdp_ensure_acg_session` on **both** branches. There is no missing wiring.

**The actual gap is that the credential store the gate reads does not exist on this machine:**

```
security find-generic-password -s "k3dm-acg-pluralsight"   →   item ABSENT
```

`cdp.sh:184-185` loads both keys with `2>/dev/null || true`, so an absent item yields two empty
strings and the node gate takes its `ACG_LOGIN_NO_CREDS` branch. From a non-TTY caller that
surfaces as `ACG_SESSION_EXPIRED`. **This has been misread as "the session gate is not wired"
for several sessions.** It is not a code defect; it is an unpopulated secret plus a missing
preflight that would have named it.

## Task 0 — decide which path applies (operator, blocking)

`docs/bugs/v1.14.0-bugfix-acg-pluralsight-autologin.md:394` is a hard design constraint:

> **No-MFA only.** The login refuses MFA challenges by design. Never store the company (MFA)
> account in the `k3dm-acg-pluralsight` Keychain item.

So the implementation branches on one fact that only the operator can supply:

| | Condition | Consequence |
|---|---|---|
| **Path A** | The ACG account used for sandboxes has **no MFA** | Populate the Keychain item once. Auto-login becomes fully unattended, including for non-TTY callers (Claude, `codex exec`, the webhook). Tier 2's P4 closes permanently. |
| **Path B** | That account **has MFA** | Auto-login is impossible *by design* — do not try to defeat it. `pw-profile` holds the only session, it must be refreshed by a human whenever it lapses, and P4 can never be "closed", only "currently valid". |

**Do not implement Tasks 1–3 differently per path** — they are correct either way. Path B only
changes the message text in Task 1 and what the Task 3 doc tells the reader to do. Resolve Task 0
before writing the message strings.

Determining this does not require reading any password: sign-in flow alone answers it.

## Task 1 — give `e2e_verify_sandbox` a real preflight (k3d-manager, in-repo)

`scripts/plugins/e2e.sh:294` sets `_E2E_ACTIVE_PHASE="preflight"` and then checks **nothing**. Its
first live action is:

```bash
  _E2E_ACTIVE_PHASE="extending-sandbox"
  acg_extend_playwright "${_ACG_SANDBOX_URL:-}"
```

Consequences today:

1. A missing Keychain item is not detected. The run proceeds into Playwright and dies with
   `Buttons: ["Sign in"]` — a symptom several layers from the cause. The Tier 2 impl spec quotes
   exactly this confusing failure.
2. `_ACG_SANDBOX_URL` defaults to empty, so an unset sandbox URL is also only caught downstream.
3. A report directory and an EXIT trap are already established, so the failure writes a summary
   attributing the failure to `extending-sandbox` rather than to absent credentials.

**Add a preflight helper** `_e2e_sandbox_preflight_auth`, called immediately after
`_E2E_ACTIVE_PHASE="preflight"` and **before** `acg_extend_playwright`. It must fail fast, with an
actionable message, on each of:

- `_ACG_SANDBOX_URL` empty or unset.
- Keychain service `k3dm-acg-pluralsight` absent. **Check existence only** — use
  `security find-generic-password -s <svc>` with **no `-w`**, or the foundation existence helper if
  one exists. Never read the value, never log it. On Path B this check is a warning, not an error,
  because a live `pw-profile` session is legitimate without the item.
- `K3DM_ACG_SKIP_SESSION_CHECK=1` being set. This env var (`cdp.sh:167`) bypasses the session gate
  entirely and would let Tier 2 drive a signed-out browser. Tier 2 must **refuse to run** with it
  set — it is a local debugging escape hatch, never valid for an acceptance run.

The message must name the service, say which of Path A / Path B applies, and — per the standing
rule — **must not be a paste-ready command containing a placeholder password.** Point the reader at
the Task 3 doc instead.

**Rules:**
- `set -euo pipefail` semantics preserved; double-quote every expansion.
- No secret values in any log line, ever — existence booleans only.
- Minimal patch. Do not restructure `e2e_verify_sandbox` beyond inserting the call.

## Task 2 — do NOT edit the auto-login itself here

The login code lives under `scripts/lib/foundation/scripts/lib/acg/` — a **subtree**.
Per the standing rule, `scripts/lib/foundation/` is never edited in k3d-manager; ACG bugs are
fixed upstream in lib-foundation and subtree-pulled.

This spec deliberately requires **no** upstream change: the gate is already correct and already
wired. If implementation uncovers a genuine defect in `cdp.sh` or `acg_session_check.js`, stop and
file it against lib-foundation — do not patch the subtree copy to keep this spec moving.

## What NOT to do

- Do NOT skip pre-commit hooks (`--no-verify`).
- Do NOT edit anything under `scripts/lib/foundation/`.
- Do NOT attempt to automate an MFA challenge, and do not add an MFA-solving path.
- Do NOT store the MFA/company account in `k3dm-acg-pluralsight`.
- Do NOT read, print, echo or test-compare the Pluralsight password; do not base64 it.

- Do NOT loosen or remove the `K3DM_ACG_SKIP_SESSION_CHECK` refusal to make a run go green.
- Do NOT touch the Tier 1 path (`e2e_verify_vcluster`) — it has no Keycloak and no ACG dependency.

## Risks

- **Path B makes this permanently manual.** If the account has MFA, no amount of preflight closes
  P4; the preflight only converts a confusing late failure into an early, accurate one. That is
  still worth doing, but it must not be reported as "Tier 2 unblocked".
- **A green preflight is not a valid session.** Keychain-item existence proves a credential is
  stored, not that it still authenticates — the password may have been rotated upstream. The
  preflight is a fail-fast, not a guarantee; only `_cdp_ensure_acg_session` returning `ACG_SESSION_OK`
  proves the session.
- **This does not move Stripe past 2/4.** P3 (`KeycloakRealmRoleConverter` absent from
  `shopping-cart-payment` `origin/main`) is the cause of the payment→Stripe 403 and is untouched by
  this spec. A PR in `shopping-cart-payment` is **not approved**. Do not "fix" the 403 by loosening
  the harness.
- **`pw-profile` must never be deleted** while diagnosing this. It holds the only artifact of any
  manual sign-in; deleting it discards a working session and, under Path B, cannot be recreated
  without a human.
