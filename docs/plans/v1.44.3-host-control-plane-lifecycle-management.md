## Problem and boundaries

On October 26, 2026, the operator observed Slack/webhook failures and Cloudflare 1033 for the frontend. The Cloudflare dashboard showed the single `k3d-manager` tunnel Down with 0 active replicas across seven configured routes. This identifies a connector availability failure at that observation; it does **not** establish whether its underlying cause was sleep, launchd, process crash, network or a software update. The operator also wants timely detection of critical `cloudflared` security updates and asks who updates Hermes itself.

Hermes cannot be the sole authority for restarting or updating itself, and the webhook cannot be the only recovery channel when webhook/tunnel access fails. Introduce a **minimal, deterministic macOS host-level lifecycle controller**, scheduled and supervised by launchd, with no model calls and no dependency on Hermes, webhook, cloud-bridge, OrbStack, or Hostinger. Git-approved immutable revisions are authoritative for k3d-manager components. The host controller is **not** a second unrestricted AI agent.

This plan coordinates with the independently filed heartbeat/Healthchecks.io P2; it does not replace it. Tailscale remains an operator-only break-glass channel. A powered-off, sleeping, FileVault-locked or disconnected Mac may remain unreachable; do not overclaim recovery.

## Decisions and phased scope

### Phase 1 — Observe, classify and bounded recovery (this plan's first deliverable)

1. Inventory the **actual** installed launchd jobs, binary paths and user/system domains on m4 before changing anything: `com.k3d-manager.hermes`, `com.k3d-manager.webhook`, cloud-bridge and `com.k3d-manager.cloudflare-tunnel` (verify its existence/configuration), plus any Homebrew-managed `cloudflared` service. Avoid duplicate controllers or relying on stale documentation.
2. A small independent launchd-run Bash/Python-stdlib controller records process/launchd health, local functional probe, connector connectivity and the last *observed* successful work. Prefer existing supported health interfaces; do not equate PID, installed binary version, or successful `launchctl` exit with actual health.
3. Distinguish: `healthy`, `degraded`, `down`, `recovering`, `cooldown`, `escalated`, `unknown`. A tunnel Down with 0 replicas is separate from an origin listener failure. The controller must not require contacting the failed webhook in order to report status.
4. Phase 1 recovery: preserve timestamped redacted evidence, apply one allowlisted low-risk launchd restart *only* to a locally proven stopped/unresponsive eligible service, then prove functional recovery. Bound attempts, rate/cooldown, exclusive locks, timeout and backoff; if the cause is ambiguous or persists, alert and stop. Never reboot the Mac, restart OrbStack, unseal/reset Vault, regenerate tokens, alter Git branches or modify Hostinger.
5. Keep alert sending independent, outbound HTTPS via an explicitly configured external heartbeat/notification service, with missing-heartbeat and explicit-failure semantics. Failed sending must not block the local supervisor, and delivery cannot be assumed from a successful local subprocess exit.
6. Do not silently expand the existing v1.46.0 HermesNotRunning webhook handler. That handler may remain an independent advisory/approved routine, but overlapping restart authorities must share a single lock/cooldown or only one may have restart permission.

### Phase 2 — Detect security updates and stage immutable releases (separate authorization gate)

1. Periodically inspect Cloudflare security notices, trusted releases and Homebrew formula data. Record advisory ID, fixed version, installed version, **running executable version**, affected host and classification `routine|security|urgent|unknown`. Never infer a security advisory merely from a semver bump. If Cloudflare/upstream data is unavailable, say `unknown`, not safe/current.
2. For Hermes/webhook/cloud-bridge, track an **approved immutable k3d-manager release commit or signed/tagged artifact**; never auto-deploy a moving feature branch. Identify active revision, staged revision and last-known-good revision. Validate signatures/checksums where supported, dependency/interpreter paths and launchd configuration.
3. Stage a new version into a separate, versioned host path with preflight and offline tests. Before activation, preserve a recoverable previous binary/configuration and rollback commands; prevent concurrent host maintenance with an atomic lock. Do not copy secrets into Git or logs.
4. Upgrade `cloudflared` through its actual installation manager (Homebrew if Homebrew-managed); package update and service restart are separately recorded. Do not run generic install/rotate-token commands or create an additional tunnel/replica accidentally. Retain tunnel identity and routing configuration.
5. Activation is **operator-approved by default** for each host-level update or disruptive restart. Automatic application of urgent security updates requires a later explicit operator-approved policy and demonstrated independent connectivity/rollback tests. An advisory may justify expedited notification but **not** silent loss of the only seven-route connector.
6. Verify post-activation with functional host/endpoint checks and, when available, independent external tunnel connector/route observation. Confirm running version (not merely installed version), Hermes scheduled work/heartbeat, webhook read-only request, bridge freshness and representative published hostname; declare `unknown` when external verification cannot be obtained.
7. On failed activation, perform a bounded rollback to a known-good **compatible** artifact/config and verify; do not roll back to a known vulnerable `cloudflared` version silently. When no safe security/availability trade-off exists, stop and escalate rather than claiming success.
8. Report a structured lifecycle event: host, component, old/new versions/revisions, reason/advisory, timestamps, gate evidence, action, verification, rollback and alert delivery outcome. Secrets and full private command lines are forbidden in event exports.
