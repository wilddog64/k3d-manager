# v1.12.0 — Remote Operator Access for k3d-manager via Slack + Cloudflare

**Status:** Proposed  
**Branch:** `k3d-manager-v1.12.0`  
**Owner:** Codex  
**Scope:** `workers/slack-relay`, `bin/k3dm-webhook`, Cloudflare tunnel wiring, auth/RBAC, audit logging, operator docs

## Goal

Allow remote/mobile/cloud agents to operate `k3d-manager` against:

- local Hub `k3d` on `m4-air.local`
- remote `k3s` providers such as Hostinger and AWS
- shopping-cart apps and supporting infra

without exposing arbitrary shell access to the Mac.

The system should support status, diagnostics, selected repairs, and controlled
cluster operations through Slack-triggered requests routed over Cloudflare to a
Mac-resident control endpoint.

## Problem

The current repo already has:

- Slack as a user-facing trigger surface
- a Cloudflare Worker relay
- a Python webhook on the Mac
- provider-aware `make` / `k3d-manager` operations

but it does **not** yet provide a clear permission model for remote operators
who need to troubleshoot and operate both clusters and shopping-cart apps.

Today the practical gap is not just Slack command coverage. It is the lack of a
repo-scoped execution policy that distinguishes:

- safe read-only diagnostics
- allowed repair/refresh operations
- destructive or lifecycle-changing actions
- code-change workflows versus cluster operations

## Non-Goals

- General remote shell access to `m4-air.local`
- Arbitrary `bash` execution via Slack or Cloudflare
- Direct write access to `main`
- Broad SSH exposure outside Cloudflare Access
- Moving the webhook into a separate repo as part of this feature

## Design Principles

1. Permissions apply to **k3d-manager workflows**, not to the Mac as a whole.
2. Slack remains the operator UI, but authorization lives behind the webhook.
3. Commands must be validated against an allowlist and argument policy.
4. Read-only diagnostics can be broader than mutating or destructive actions.
5. Every action must emit a durable audit record.
6. Code changes remain branch-only and PR-gated.

## Operator Roles

### Reader

Allowed to:

- run `make status CLUSTER_PROVIDER=...`
- inspect ArgoCD app health/sync state
- collect `kubectl get`, `describe`, and `logs` for approved contexts/namespaces
- inspect LaunchAgent and access-layer status
- read shopping-cart app readiness, image, and CVE summaries

Not allowed to:

- mutate cluster state
- restart daemons
- refresh clusters
- update code

### Operator

Includes Reader permissions, plus:

- `make refresh CLUSTER_PROVIDER=...`
- controlled ArgoCD sync / refresh actions
- restart repo-owned LaunchAgents and access-layer components
- selected `kubectl rollout restart` / `annotate` / `delete pod` recovery actions
- reapply observability/access-layer resources

Not allowed to:

- `make up` / `make down`
- arbitrary `kubectl exec`
- arbitrary file edits

### Admin

Includes Operator permissions, plus:

- controlled `make up` / `make down`
- provider lifecycle operations
- credential rotation and access-layer reprovisioning
- explicitly approved destructive recovery actions

## Allowed Tool Families

Expose only brokered/validated commands from the webhook:

- `make`
- `./scripts/k3d-manager`
- `kubectl`
- `argocd`
- `launchctl`
- selected repo helper binaries

### Allowed Command Patterns

- `make status CLUSTER_PROVIDER=<allowed-provider>`
- `make refresh CLUSTER_PROVIDER=<allowed-provider>`
- `kubectl get ...`
- `kubectl describe ...`
- `kubectl logs ...`
- `kubectl rollout restart ...` for approved resource kinds/namespaces
- `argocd app get|sync ...`
- `launchctl print|bootstrap|bootout` for repo-owned labels only

### Disallowed Patterns

- arbitrary shell pipelines
- arbitrary `kubectl exec`
- unrestricted `kubectl apply -f`
- unrestricted local file writes
- direct git pushes to protected branches

## Namespace and Context Guardrails

The broker must validate:

- context
  - `k3d-k3d-cluster`
  - approved app-cluster contexts such as `ubuntu-hostinger`
- namespaces
  - `cicd`
  - `monitoring`
  - `platform-ops`
  - `shopping-cart-apps`
  - `identity`
  - `secrets`
  - other repo-owned namespaces only
- resource kinds allowed per action
- provider token normalization (`hostinger`, `aws`, `gcp`, `az`, `oci`)

## Troubleshooting Coverage

The first implementation should support diagnostics for:

- Hub cluster health
- app-cluster health
- ArgoCD apps and ApplicationSets
- Image Updater status
- ESO / Vault bridge / auth proxy state
- Cloudflare / LaunchAgent access layer
- shopping-cart frontend, basket, order, payment, product-catalog
- data-layer readiness and rollout issues
- Trivy / Prometheus / Grafana / Alertmanager health

## Code-Change Workflow

If a remote diagnosis requires code changes:

1. the operator flow may gather context and identify the likely fix
2. code edits happen on a branch only
3. tests/lint/audit must run
4. merge remains PR-only with human approval

This feature does **not** grant direct “edit and merge to main” capability.

## Proposed Changes

### Change 1 — webhook command broker and RBAC

Add an explicit command registry for remote operator actions with:

- action id
- role requirement
- allowed provider/context set
- argument schema
- read-only vs mutating flag
- confirmation requirement for dangerous operations

### Change 2 — Cloudflare-accessed operator endpoint

Use the existing Cloudflare path as the ingress surface for remote/mobile/cloud
operators, but keep the Mac-side webhook as the only execution endpoint.

The endpoint must require:

- worker/webhook auth
- role-aware authorization
- replay-safe request handling

### Change 3 — audit logging

Persist per-action records including:

- actor
- source command
- role
- provider/context
- exact validated command executed
- start/end timestamps
- exit code
- summary/result path

### Change 4 — troubleshooting command set

Add explicit troubleshooting actions for:

- cluster status
- pod/log inspection
- app sync/health inspection
- selected restart/resync operations
- shopping-cart service diagnostics

### Change 5 — docs and smoke tests

Document the operator model, RBAC surface, and recovery flow.
Add tests that prove:

- unauthorized actions are rejected
- provider/context validation works
- mutating commands require the right role
- allowed diagnostic flows execute

## Acceptance Criteria

- Remote operators can run approved `k3d-manager` diagnostics against both Hub
  and app clusters through Slack + Cloudflare.
- Role-based authorization blocks disallowed actions.
- Mutating and destructive operations are explicitly gated.
- Shopping-cart and infra troubleshooting commands are covered.
- Every execution is auditable.
- No arbitrary shell surface is exposed.

## Delivery Order

1. Define action registry + roles
2. Implement read-only diagnostic commands
3. Implement selected repair/operator commands
4. Add audit logging
5. Document and smoke-test the full path
