## Problem

`deploy/hub` moves only when the operator runs `make hub-promote REF=<sha>` with a CI-green commit. Nothing tells the
operator when such a commit exists. In v1.43.15 Claude watched CI by hand and set a reminder cron at 3:37pm to name the
SHA; the release ran 4+ days against a 2-day median, mostly in live checks waiting on promotes. The operator asked three
times (2026-11-08, 2026-11-10, 2026-11-11) for promotion to tell them when and what to run.

## Goal

The hub sync, which already runs every five minutes on the M5 and fetches `deploy/hub`, also finds the newest commit on
the release branch that `deploy/hub` lacks and whose CI is green, and publishes it. An alert names that SHA and the exact
command. The operator stays the gate: nothing promotes automatically.

## Design

1. **Find the newest promotable commit.** In the hub role of `bin/k3dm-repo-sync`, after the fetch (which, once the
   dependency lands, refreshes both `deploy/hub` and the upstream), list `origin/deploy/hub..<upstream>` newest first and
   take the first commit that is green by **the same rule `hub-promote` uses**. Do not copy that rule: add a read-only
   `bin/k3dm-hub-promote is-green <sha>` (exit 0 green, 3 not green, 2 lookup failed; 1 stays reserved for `die` and usage errors) built on its existing
   `check_runs` (`bin/k3dm-hub-promote:70-72`), and call it. Stop after the first green commit, and check at most 10
   commits per run, so the GitHub API cost stays at a few calls every five minutes.
2. **Publish it** in the same Pushgateway push as the other `k3dm_repo_sync_*` series:
   - `k3dm_repo_sync_promotable{repo="k3d-manager",sha="<7-char>",branch="<upstream branch>"} 1` when one exists;
     no series when none does.
   - `k3dm_repo_sync_promote_backlog_commits{repo="k3d-manager"} <n>` (the count the dependency fixes), and
     `k3dm_repo_sync_promote_lookup_failed{repo="k3d-manager"} 1` when `is-green` returned 2 for the first candidate.
   - the `hub-sync` summary line gains `promotable: <sha7>|none|unknown`.
3. **Alert** in `scripts/etc/prometheus/rules/repo-sync.yaml`, `cluster: hub`, `severity: warning`, through the existing
   route (same as `K3dmDeployPending`):
   - `K3dmPromoteWaiting`: `k3dm_repo_sync_promotable == 1`, `for: 15m`. Summary
     `CI-green {{ $labels.sha }} is waiting to promote`; description `Run: make hub-promote REF={{ $labels.sha }}`
     (this becomes `make hub-deploy` when part 1 lands; that plan updates the string).
   - A newer green commit replaces the series (new `sha` label), so the alert names the newest one and the old one resolves.
4. **Dashboard:** a "deploy/hub behind" stat on k3dm Release Tracking (`grafana-dashboard-bugs.yaml`, uid `k3dm-bugs`)
   showing `k3dm_repo_sync_promote_backlog_commits` and the promotable SHA, with a threshold at 1.

Out of scope: auto-promote, the Slack Promote button and the cloud-session approval (part 3, after part 1 and the Hermes
reauth P2), and the dev-hub gate idea (2026-11-10 row).

## Re-check against the landed code (Claude, 2026-11-12)

Checked after the deploy/hub batch and the promote-backlog fix landed. One clarification for the worker, no scope change:

- `check_runs` (`bin/k3dm-hub-promote:70-78`) calls `die` (exit 1) on all three outcomes: lookup failed, no check runs,
  pending or failed. `is-green` cannot wrap it as it stands, because a lookup failure would read as "not green".
  Split it: a classifier returns 0 green, 1 not green (pending, failed, **or no check runs**), 2 lookup failed, and
  writes no output; `check_runs` calls it and keeps its three existing `die` messages, so promote's output and every
  existing `hub_promote.bats` check-runs test stay unchanged. `is-green <sha>` maps the classifier: 0 green, 3 not green (pending, failed or no check runs), 2 lookup failed. Amended 2026-11-13 (round 2): not-green is exit 3, so a `die` (exit 1) can never read as not-green.
- `bin/k3dm-repo-sync` makes no `gh` call today; this plan adds the first one. That is why the M5 probe below is a gate.
- The rest of the Design matches the code: `promote_backlog` and `promote_backlog_unknown` are already published
  (`bin/k3dm-repo-sync:144,178,199-203,278`), and the hub path fetches `deploy/hub` into `{remote}/deploy/hub` (:154).

## External behaviour (proof before dispatch)

- **GitHub check-runs shape:** `gh api repos/wilddog64/k3d-manager/commits/<sha>/check-runs --jq '.check_runs[]'` gives
  compact JSON lines `{conclusion,name,status}`; captured read-only on the M4 (`m4-air`) on 2026-11-11 by the v1.43.15
  independent verifier (`scratchpad/plan-verify/hub-deploy-ref-and-live-write-guard/tests`). `is-green` reuses the
  existing parser, so no new shape is introduced.
- **Proven 2026-11-12 (the dispatch gate):** on the M5 (`m5-air.local`), run by the operator under a launchd-like
  environment (`env -i HOME="$HOME" PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin`):
  `gh auth status` → logged in to github.com as `wilddog64`, active, token read from `~/.config/gh/hosts.yml` (an OAuth
  `gho_` token in the file, not the Keychain), scopes `admin:public_key, gist, read:org, read:packages, repo, workflow`;
  `gh api repos/wilddog64/k3d-manager/commits/main/check-runs --jq '.total_count'` → `5`. `gh --version` was not
  captured. So the sync job can read check runs with no Keychain and no login shell; the spec needs no token change.

## Acceptance
