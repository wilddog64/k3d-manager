## Problem

Under O2 the operator account, and every process it runs, is an attacker. A TOTP secret, an approval store, a spent-id list or a signing key
that the operator can read or write protects nothing. So the approval authority has to be a different principal: a root-owned process whose
state the operator cannot touch, reached over a socket it can only talk to, and which is the only holder of the credential that moves
`deploy/hub`. This is the same shape as plan 4 Part C's `totpd` (`docs/plans/v1.45.0-web-console-c-totp-gate.md:23`, root-only state, socket owned
by the operator uid with mode 0600, enrol through `_run_command --interactive-sudo`), and it follows the lesson of
`docs/bugs/2026-11-05-sudoers-launchdaemon-plist-rule-is-root-equivalent.md`: root never executes anything the operator can write.

This part is the daemon, the client, install and enrol, and the howto. Evaluation and pushing (git, GitHub) are Part 2d's mover; the wiring
into `bin/k3dm-hub-promote` is Part 2b.

## Behaviour

**A. Principals and paths**

1. Installed, all `root:wheel`, never read from the checkout at run time:
   - `/usr/local/libexec/k3dm-promote/` mode 0755 holding copies of `k3dm-promote-daemon.py` (source `scripts/libexec/k3dm-promote-daemon.py`), `hub_approval.py` (2a) and `promote_mover.py` (2d), each 0644 except the daemon 0755;
   - `/etc/k3dm-promote/promote.conf`, mode 0644 (readable, root-writable only);
   - `/var/db/k3dm-promote/` mode 0700, holding the engine state, `totp.secret`, `deploy_key`, `deploy_key.pub`, `known_hosts`, `readtoken`, `mirror.git/` (all 0600 or 0700);
   - `/var/run/k3dm-promote/` mode 0755 with socket `sock`;
   - `/Library/LaunchDaemons/com.k3d-manager.promote-authority.plist` (rendered from `scripts/etc/launchd-daemons/com.k3d-manager.promote-authority.plist.tmpl`), `root:wheel` 0644, `ProgramArguments` `/usr/bin/python3`, `-I`, `/usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py`, `serve`; `RunAtLoad`, `KeepAlive`; log `/var/log/k3dm-promote.log`.
2. The operator's checkout is only a source. Install copies by `_run_command --interactive-sudo -- install -m <mode> -o root -g wheel <src> <dest>` for each file
   (`scripts/lib/foundation/scripts/lib/system.sh:152` defines `--interactive-sudo`). There is no sudoers rule, no wildcard, no `sudo` literal in
   the new files; a test greps for it. The install prints the SHA-256 of every source before copying and refuses a checkout with tracked
   changes (`git status --porcelain --untracked-files=no`), so the operator sees what becomes root-owned code.

**B. The socket**

3. The daemon sets `umask 0o177`, binds `/var/run/k3dm-promote/sock`, then `chown <operator_uid>:<operator_gid>` and keeps mode 0600 (no window in which another
   user can connect). `operator_uid` and `operator_gid` come from `promote.conf`. The `AF_UNIX` path limit is 103 bytes on macOS; the
   production path is 26 bytes (a longer scratch path failed with `AF_UNIX path too long`, captured 2026-11-18, m4-air).
4. Every accepted connection is checked with `LOCAL_PEERCRED`: `getsockopt(SOL_LOCAL=0, LOCAL_PEERCRED=1, 76)` returns a `struct xucred`
   (`cr_version` 0 at offset 0, `cr_uid` at offset 4, `cr_ngroups` short at offset 8; captured 2026-11-18 on macOS 26.5.2 with
   `/usr/bin/python3 -I`: length 76, version 0, uid equal to the caller, ngroups 16). A uid other than `operator_uid` is closed with no reply. State plainly: this excludes other local users; it cannot tell the operator from an attacker running as the operator, which is
   why every consequential op is gated by the approval and the credential separation below, not by this check.
5. Bounded I/O: one request per connection; the request is one line of at most 4096 bytes; each read has a 5-second timeout and the whole read
   a 10-second budget; a longer line, a non-UTF-8 line, a non-JSON line, or a JSON value that is not an object with exactly the allowed keys
   gets `bad_input` and the connection closes. The `promote` op has a 120-second deadline; on expiry the reply is `unknown`/`deadline`.
   The daemon serves one connection at a time under a store lock.

**C. Protocol (the single contract of Part 2a)**

6. Request: `{"v":1,"op":<op>, ...}`; ops and their exact key sets: `request` (`sha`, `branch`, `channel`, `requested_by`), `show` (`id`),
   `approve` (`id`, `nonce`, `approver`, `totp`), `deny` (`id`, `nonce`, `approver`), `promote` (`id`, `sha`), `status` (none). `consume`,
   `refuse` and `outcome` do not exist on the wire: they are steps inside `promote` (R3). Response and exit map: Part 2a Behaviour B.5 and B.6.
7. `promote` runs the Part 2d mover under the rules in Part 2d and Part 2a (check order, refusals keep the approval, only a verified move
   consumes). The daemon never reads an environment variable (`os.environ` and `os.getenv` do not appear in the daemon source; a test greps).
8. `status` returns `{"daemon":"ok","configured":true|false,"pending":N,"state":"ok"|"lost"}` and nothing secret. `request` returns the id and
   nonce only to the caller that made the request (the socket is one user); the nonce is never logged.

**D. Production configuration (R1)**

9. `serve` loads `/etc/k3dm-promote/promote.conf` and nothing else; there is no flag or variable that selects another file, socket or
   state directory. Keys, all required: `operator_uid` (int), `operator_gid` (int), `operator_ids` (comma list; each `^[A-Z0-9]{2,32}$` or `cli`), `repo_ssh` (must match
   `^git@github\.com:[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+\.git$`), `repo_slug` (`^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`, and equal to the owner/name inside `repo_ssh`). The API
   base is the constant `https://api.github.com`. A `file://` URL, a local path, an `ssh://` form, a different host or any other key makes `serve` exit 78 before it binds.
   The same rule is how the mover is made unable to reach a fake in production: the mover takes its repo URL, API base and ssh command as constructor arguments, and only
   tests (which build the mover directly against a local bare repository) pass anything else (Part 2d).
10. `GH_REPO` is not read by the daemon. The repository is the one value in `promote.conf`, used for both the push and the API reads, so the
    API repo cannot differ from the push remote (Astra).

**E. Enrol (operator, once, and for rotation)**

11. `make promote-authority-enrol` runs `bin/k3dm-promote-authority enrol`, which calls
    `_run_command --interactive-sudo -- /usr/bin/python3 -I /usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py enrol`. In that root process, on `/dev/tty` only (refused without one):
    1. TOTP: refuse when `totp.secret` exists unless `--rotate`; generate 20 random bytes, write `totp.secret` 0600, print the `otpauth://` URI and the base32 secret to the tty only;
    2. deploy key: `ssh-keygen -t ed25519 -N '' -C k3dm-promote -f /var/db/k3dm-promote/deploy_key` (argv holds paths only), print `deploy_key.pub` to the tty for the operator to add to the repository as a deploy key with write access;
    3. read-only token: prompt on the tty with echo off (`termios`) for a fine-grained read-only token, write `readtoken` 0600; the token is never in argv, environment or logs and is sent to curl on stdin (Part 2d);
    4. GitHub host key: `ssh-keyscan -t ed25519 github.com` into `known_hosts`, print its SHA256 fingerprint for the operator to compare with `gh api meta --jq .ssh_key_fingerprints` (proof owed below);
    5. `--reset-state` is the only way past `state_lost` (Part 2a E.11): it moves the old state directory to `state.lost.<UTC>` (kept, 0700) and initialises a new one.
12. Nothing secret appears in argv of any process (the `security -i` stdin precedent is `bin/k3dm-machine-secrets:199`; here there is no Keychain at all). A test runs enrol with a stub `ssh-keygen` and a pty and
    asserts the secrets reach the tty and files only.

**F. The client**

13. `bin/k3dm-promote-client` (Python, `#!/usr/bin/python3 -I`): subcommands `request`, `show`, `approve`, `deny`, `promote`, `status`; `approve` and `deny` read their JSON secrets from stdin, never argv. The socket path is the constant
    `/var/run/k3dm-promote/sock` with no environment override (the module exposes `run(argv, stdin, sock_path)` for tests, called with an explicit path by pytest and by the bats stub). It connects with a 5-second timeout, sends one line, reads at most 65536 bytes to a newline with a total deadline of 150 seconds for `promote` and 15 for the rest (so the daemon's own deadline reply wins), prints the response line to stdout,
    the message to stderr, and exits by the Part 2a B.6 table. A connection failure, timeout, empty reply or non-JSON reply is exit 75.

**G. Install, status, Makefile**

14. `bin/k3dm-promote-authority install|enrol|status|uninstall|print-plan` (bash, `set -euo pipefail`). `print-plan` prints, one per line, every command it would run through `_run_command --interactive-sudo`, with absolute destinations only, and runs nothing. `status` is read-only: it asks the daemon `status` through the client, and prints
    `launchctl print system/com.k3d-manager.promote-authority` state when readable. `uninstall` boots out the daemon and removes the installed files but leaves `/var/db/k3dm-promote` (re-enrol needs `--reset-state`).
15. Makefile targets `promote-authority-install`, `promote-authority-enrol`, `promote-authority-status`, each one line calling the script. `scripts/etc/machine/not-installed.list` gains `install-promote-authority|operator-run: root LaunchDaemon, installed by the operator with sudo, never by machine setup` so setup skips it. `docs/howto/promote-authority.md` covers install, enrol, rotate, the ruleset step, `state_lost` recovery and the residuals below.

**H. The move authority is separate (the O2 core)**

16. The credential that can move `deploy/hub` is the `deploy_key` (write-enabled deploy key) in `/var/db/k3dm-promote`. The operator cannot read it. The GitHub side (an operator step, proof owed, shown in the howto): a ruleset on `refs/heads/deploy/hub` and `refs/tags/hub-promote/*` that blocks update, deletion and non-fast-forward for everyone except a bypass
    actor, with the deploy key as the only bypass actor. **Until that ruleset is on, a same-user attacker can still push `deploy/hub` with the operator's own `gh` token or SSH key; the daemon is then a gate on the honest path and not a barrier.** The howto says so and `status` prints `ruleset: not verified` until the operator confirms it (the daemon cannot read rulesets; it prints the probe command).
17. Honest residuals, stated in the howto and the review ask: (a) a same-user attacker who sniffs one in-flight TOTP code can approve only a policy-valid promote: the newest green commit of the newest release branch, contained in the release, never an arbitrary sha; (b) the control protects the remote ref, not the operator's checkout or the hub's local state; (c) the peer uid check cannot tell the operator from malware running as the operator; (d) root compromise ends it.
18. TTY path: this spec does not change the operator's own typed-confirmation promote in `bin/k3dm-hub-promote`. After the ruleset flip the operator's own push to `deploy/hub` is rejected, so the TTY path must also go through the daemon (channel `cli`, typed word plus TOTP) before the ruleset is enabled; see Open questions.

## Worker definition of done

1. Each must_not test contains its positive control and is shown red against a daemon stub that accepts any uid, reads `os.environ`, and runs an unbounded read.
2. Pytest sockets live under a short `/tmp/k3dm.XXXX` directory (the `AF_UNIX` limit) created with `tempfile.mkdtemp(dir="/tmp")`; fixtures assert the directory and socket mode first.
3. Nothing in the tests calls `sudo`, `launchctl`, `security`, the network, or writes under `/var`, `/etc`, `/usr/local` or `/Library`.
4. `shellcheck` clean on `bin/k3dm-promote-authority`; `make lint-python`, `make test-pytest`, the new bats pass.

## What NOT to do

- No sudoers rule, ever (`docs/bugs/2026-11-05-sudoers-launchdaemon-plist-rule-is-root-equivalent.md`). Install and enrol go through `_run_command --interactive-sudo`.
- Do not run install, enrol, `launchctl` or anything with root during development; the live evidence is the operator's.
- Do not add an environment variable, a flag or a config key that reaches a test fake.
- Do not edit `bin/k3dm-hub-promote` or `bin/k3dm-hub-deploy` (Part 2b).

## Open questions for the operator

1. **Deploy key plus read-only token, or a GitHub App.** The deploy key writes and a fine-grained read-only token reads check-runs and PRs (two credentials, no JWT code); an App would be one credential acting as the ruleset bypass actor but needs JWT signing (openssl) and more code. Recommendation: deploy key plus token, unless proof owed 2 shows deploy keys cannot be bypass actors.
2. **The operator's own typed-confirmation path after the ruleset.** The ruleset blocks the operator's own push. Recommendation: before enabling the ruleset, route the TTY promote through the daemon as channel `cli` (typed word plus TOTP) in a small follow-up to Part 2b; until then leave the ruleset off and accept that the control is a gate, not a barrier.
3. **Ruleset timing.** Recommendation: build and soak the daemon with the ruleset off, run proof owed 2 on a throwaway branch, then enable the real ruleset in the same sitting as the TTY routing.
4. **Install only from a promoted checkout?** The install prints digests and refuses a dirty tree. Recommendation: also require `HEAD == origin/deploy/hub` after the first install so a later reinstall cannot ship unpromoted code; the first install cannot, so it keeps an explicit `--first-install`.
5. **Audit log home.** The engine writes `audit.jsonl` under `/var/db/k3dm-promote` (root-only). Recommendation: expose the last N lines through `status` so the operator can read them without root.
