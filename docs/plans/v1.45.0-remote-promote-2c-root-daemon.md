## Problem

Under O2, a process running as the operator is an attacker at runtime. The approval authority is therefore a different principal: a
root-owned process.
- The operator cannot touch its state.
- The operator can reach it only through a socket.
- It alone holds the credential that moves `deploy/hub`.

This is the shape of plan 4 Part C's `totpd` (`docs/plans/v1.45.0-web-console-c-totp-gate.md:23`), and it follows
`docs/bugs/2026-11-05-sudoers-launchdaemon-plist-rule-is-root-equivalent.md`: root never executes anything the operator can write.

**O3** (umbrella, 2026-11-18): O2 applies at runtime, meaning login, approval and promote. Install, enrol and rotate, and ruleset setup
are one-off steps the operator starts and watches. They are trusted and recorded below as named residuals (R2c-1 to R2c-4). Round 3 still:
- removes admin- or ruleset-capable credentials from what the hub user can read where practical, or names the residual (H.19);
- blocks tag creation under `hub-promote/*` (H.16).

This part is the daemon, the client, install and enrol, and the howto. Evaluation and pushing are Part 2d; the wiring into
`bin/k3dm-hub-promote` is Part 2b.

Round 2 found these problems in v1. Each is fixed below:
- **`/var/run` is cleared at boot** (agreed defect; Fable 7). The daemon now creates its directory at start (B.3).
- **`python3 -I` cannot import the sibling modules** (agreed defect; Fable 9). The daemon inserts its constant directory into the path
  after an ownership check (A.2).
- **CI is Linux Python 3.12 and the hub runs Python 3.9.6** (agreed defect; Fable 8). The peer-credential function is injected, and the
  macOS-only test is skipped elsewhere (B.4, definition of done 3).
- **The 120 s deadline had no mechanism** (agreed defect; Fable 11). It is now a monotonic budget passed into the mover, and the push is
  never aborted (B.5, C.7).
- **Other `deploy/hub` writers were missing** (agreed defect; Fable 5; Astra 2). They are now listed and routed before any ruleset (H.18).
- **Install TOCTOU and ancestor ownership** (Fable 2; Astra 1). Install now uses one root-owned staging copy compared against the
  promoted commit's blob shas, plus an ancestor check (G.15).
- **Enrol:** the seed display rules, host-key activation only after a match, atomic and resumable stages, and credential and state
  lifecycles kept apart (E.11-E.13; Fable 3; Astra 11, 12).
- **Acceptance defects** (Fable 12; Astra 11):
  - the nonce is allowed in the `request` response;
  - each bad input has one behaviour;
  - a privileged test seam;
  - E8 no longer claims N2;
  - a ruleset must;
  - `promote.conf` rendering and `configured: false` behaviour.
- **The ruleset now blocks tag creation**, with probes for a second deploy key and for token edits (Fable 1, 6; Astra 2).

## Behaviour

**A. Principals and paths**

1. **Installed paths.** All are `root:wheel`, and none is read from the checkout at run time:
   - `/usr/local/libexec/k3dm-promote/` (0755) holds `k3dm-promote-daemon.py` (0755, from `scripts/libexec/k3dm-promote-daemon.py`),
     `hub_approval.py` and `promote_mover.py` (0644). Install creates `/usr/local/libexec` (0755) when it is absent; it is absent on
     m4-air.
   - `/etc/k3dm-promote/promote.conf` (0644).
   - `/var/db/k3dm-promote/` (0700), with three separate subtrees:
     - `creds/` (0700): `totp.secret`, `deploy_key`, `deploy_key.pub`, `known_hosts`, `readtoken`, each 0600, plus `ruleset-verified` (0600,
       H.17);
     - `state/` (0700): the Part 2a engine directory;
     - `mirror.git/` (0700): the Part 2d mirror.
   - `/var/run/k3dm-promote/` (0755), created by the daemon at start (B.3), holding the socket `sock`.
   - `/Library/LaunchDaemons/com.k3d-manager.promote-authority.plist` (0644), rendered from
     `scripts/etc/launchd-daemons/com.k3d-manager.promote-authority.plist.tmpl`.
     - `ProgramArguments` are `/usr/bin/python3`, `-I`, `/usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py` and `serve`.
     - `RunAtLoad` and `KeepAlive` are set, and the log is `/var/log/k3dm-promote.log`.
     - `EnvironmentVariables` is absent.
2. **Startup integrity and imports** (agreed defect).
   - The daemon's first statements, before it imports anything outside the standard library, check with `os.lstat` that every one of these
     is owned by uid 0, is not a symlink, and is not group- or other-writable:
     - `/usr`, `/usr/local`, `/usr/local/libexec`, `/usr/local/libexec/k3dm-promote` and the three files in it;
     - `/etc/k3dm-promote` and `promote.conf`;
     - `/var/db/k3dm-promote` and its three subtrees.
   - Any failure exits 78 with the path named.
   - Only then does it run `sys.path.insert(0, LIBEXEC)` with the module constant `LIBEXEC = "/usr/local/libexec/k3dm-promote"`, followed by
     `import hub_approval, promote_mover`.
   - Tests call `bootstrap(root=<fake root>, owner_uid=os.getuid())`, the only seam, and `main()` passes the real `/` and 0.
   - Probe, m4-air, 2026-11-18, `/usr/bin/python3` 3.9.6: with `-I` a sibling import fails with `ModuleNotFoundError`, and after
     `sys.path.insert(0, dir)` it succeeds, with `sys.flags.isolated` equal to 1.

**B. The socket**

3. **Run directory** (agreed defect).
   - At start, the daemon `lstat`s `/var/run/k3dm-promote`.
     - **Absent:** it is created with `mkdir` mode 0755 and `chown` 0:0.
     - **Present** as a directory owned by root, mode 0755: it is used.
     - **Anything else:** it is renamed to `k3dm-promote.bad.<UTC>`, then created afresh.
   - Then it unlinks `sock` if present, sets `umask 0o177`, binds `sock`, and runs `chown(<operator_uid>, <operator_gid>)`, so the mode is
     0600 from the bind onward.
   - `/var/run` is `root:daemon 0775` (m4-air, 2026-11-18) and is cleared at boot.
   - `chown`, `mkdir` and the run-directory path are injected through `serve(..., fs=RealFs())`. Tests pass a recording `FakeFs` rooted in
     a short `/tmp` directory, so they run unprivileged (Astra 11).
   - The macOS `AF_UNIX` path limit is 103 bytes. The production path is 26 bytes.
4. **Peer check.**
   - Every accepted connection is checked by `peer_uid(conn)`. Production uses `LOCAL_PEERCRED`: `getsockopt(0, 1, 76)` returns a
     `struct xucred` (`cr_version` 0 at offset 0, `cr_uid` at offset 4). This was captured on macOS 26.5.2 with `/usr/bin/python3 -I`.
   - `serve(..., peer_uid=local_peercred_uid)` takes the function as a parameter, and tests inject one. The real-socket test is
     `skipif(sys.platform != "darwin")`.
   - A uid other than `operator_uid` is closed with no reply.
   - The check excludes other local users only. It cannot tell the operator from an attacker running as the operator; the approval and the
     credential separation do that.
5. **Bounded I/O.**
   - One request per connection. The request is one line of at most 4096 bytes. Each read has a 5 s timeout, and the whole read has a 10 s
     budget.
   - Every malformed request gets exactly one `bad_input` reply, then the connection closes; this is one behaviour per case (Fable 12).
     The malformed cases are:
     - a line over 4096 bytes;
     - a stall past the budget;
     - non-UTF-8 or non-JSON;
     - not an object;
     - a missing or extra key;
     - an unknown op.
   - Connections are served one at a time.
   - `promote` gets `deadline = monotonic() + 120`, passed to Part 2d's `promote` glue (Part 2d A.5). The push and its observation are not
     cut by it. The longest `promote` call is therefore 120 + 60 + 30 s.

**C. Protocol (the single contract of Part 2a B.5-B.6)**

6. **Request.** The request is `{"v": 1, "op": <op>, ...}`, with these exact key sets:

   | op | keys |
   |---|---|
   | `request` | `sha`, `branch`, `channel`, `requested_by` |
   | `show` | `id` |
   | `approve` | `id`, `nonce`, `approver`, `totp` |
   | `deny` | `id`, `nonce`, `approver` |
   | `promote` | `id`, `sha` |
   | `status` | none |

   `consume`, `refuse`, `outcome` and anything else are unknown ops (`bad_input`).
7. **`promote`** calls `promote_mover.promote(engine, mover, id, sha, deadline)` (Part 2d D.15). The daemon never reads the environment:
   `os.environ` and `os.getenv` are absent from the daemon and client sources, and a test greps for them.
8. **Responses.**
   - The `request` response is the only one that carries the nonce, in `data.nonce`, sent only on the requesting connection (Astra 11;
     Fable 12). The nonce is never logged.
   - `status` returns `{"daemon": "ok", "configured": bool, "pending": N, "state": "ok"|"lost", "ruleset": "verified <date>"|"not
     verified"}`, and nothing secret.
9. **Unconfigured.** While any of `creds/totp.secret`, `creds/deploy_key`, `creds/readtoken` or `creds/known_hosts` is missing,
   `configured` is false. `request`, `approve`, `deny` and `promote` then return `Unknown("unconfigured")` (exit 75, approval kept; Part 2a
   B.5), while `show` and `status` work. Credentials are read from `creds/` on every request, never cached, so rotation needs no reload.

**D. Production configuration (R1)**

10. **Loading `promote.conf`.** `main()` loads `/etc/k3dm-promote/promote.conf` and nothing else; no flag or variable selects another file,
    socket, state directory or credential.
    - Its keys are all required:
      - `operator_uid` and `operator_gid` (int);
      - `operator_ids` (comma list, each `^[A-Z0-9]{2,32}$` or `cli`);
      - `repo_ssh`, which must match `^git@github\.com:[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+\.git$`;
      - `repo_slug`, equal to the owner/name in `repo_ssh`.
    - The API base is the constant `https://api.github.com`.
    - A `file://` URL, a local path, an `ssh://` form, another host, a missing key or an extra key makes `serve` exit 78 before it binds.
    - The production mover is built only from these values and the Part 2d constants. This is where 2d's old N2 now lives (N6 here).
11. **Rendering** (Fable 12). `bin/k3dm-promote-authority install OPERATOR_IDS=<list>` renders `scripts/etc/promote/promote.conf.tmpl`
    into the staging directory (G.15).
    - `operator_uid` and `operator_gid` come from `id -u` and `id -g` of the invoking user. `repo_ssh` and `repo_slug` come from the
      template's fixed values for `wilddog64/k3d-manager`.
    - An `OPERATOR_IDS` value that is missing or invalid refuses before any privileged step.
    - `GH_REPO` is not read.

**E. Enrol and rotation (trusted O3 steps)**

12. **`make promote-authority-enrol`** runs `bin/k3dm-promote-authority enrol`.
    - The script refuses when `TMUX` or `STY` is set, or when stdin is not a tty. It asks for the physical console, outside tmux (R2c-2).
    - It then calls `_run_command --interactive-sudo -- /usr/bin/python3 -I /usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py enrol
      [--rotate totp|deploy-key|token|host-key]`. The root process talks only to `/dev/tty`.
    - Each stage writes `<name>.new` (0600), `fsync`, then `os.replace`. A stage whose file exists is skipped unless `--rotate` names it,
      so an interrupted enrol resumes at the first missing stage (Astra 11). The stages:
      1. **TOTP.** Generate 20 random bytes and print the `otpauth://` URI and the base32 secret. Wait for Enter, clear the screen and
         scrollback (`\033[3J\033[H\033[2J`), then activate `totp.secret`.
      2. **Deploy key.** `ssh-keygen -t ed25519 -N '' -C k3dm-promote -f creds/deploy_key.new` (argv holds paths only). Print the public
         key for the operator to add as a write deploy key. On rotation, print the instruction to delete the old key on GitHub.
      3. **Read token.** Prompt with echo off (`termios`) and write `readtoken`. The token is never in argv, the environment or a log.
      4. **Host key** (Astra 12). Run `ssh-keyscan -t ed25519 github.com` into `known_hosts.new` and print its SHA256 fingerprint. The
         operator compares it with GitHub's published fingerprint on a device of their own and types `yes`. Only then is `known_hosts`
         activated; anything else deletes `.new` and exits 1 (trust on first use, R2c-3).
      5. **First fetch.** `Mover.prime()` (Part 2d A.4), outside any request budget.
13. **Lifecycles are separate** (Astra 11).
    - `--rotate` replaces one credential and never touches `state/` or `mirror.git/`. Pending and approved records stay valid; a rotated TOTP
      secret applies from the next `approve`.
    - `--reset-state` is the only way past `state_lost` (Part 2a E.11). It renames `state/` to `state.lost.<UTC>` (0700) and creates an
      empty `state/`. It never touches `creds/` or the mirror.
    - `uninstall` removes the plist and `/usr/local/libexec/k3dm-promote` and keeps `/var/db/k3dm-promote` and `/etc/k3dm-promote`.
14. **No secret in argv.** No secret appears in the argv of any process. The stdin precedent is `bin/k3dm-machine-secrets:199`; there is no
    Keychain here. A pty test runs enrol with stub `ssh-keygen` and `ssh-keyscan` and asserts that the secrets reach only the tty and the
    files.

**F. The client**

15. **`bin/k3dm-promote-client`** (Python, `#!/usr/bin/python3 -I`, 3.9 syntax).
    - Subcommands: `request --sha S --branch B --channel C --requested-by R`, `show --id I`, `approve` and `deny` (JSON on stdin, never in
      argv), `promote --id I --sha S`, and `status`.
    - The socket path is the constant `/var/run/k3dm-promote/sock`. `run(argv, stdin, sock_path)` is the test seam.
    - It connects with a 5 s timeout, sends one line, and reads at most 65536 bytes up to a newline within 240 s for `promote` and 15 s for
      the rest.
    - **Response validation.** It validates the response strictly: exactly the keys `v`, `result`, `code`, `message` and `data`; `v` equal
      to 1; `result` in the closed set; `data` an object; a code from Part 2a B.5. Anything else is exit 75.
    - **Output.** It prints the response line to stdout and the message to stderr, and exits by Part 2a B.6. A connection failure, timeout,
      empty reply or invalid reply is exit 75. A usage error is exit 2.

**G. Install, status, Makefile**

16. **Install** (Fable 2; Astra 1). This is a trusted O3 step, and its residual is R2c-1.
    - **Command:** `bin/k3dm-promote-authority install OPERATOR_IDS=<list> [INSTALL_REF=<commit>]` (bash, `set -euo pipefail`).
      `INSTALL_REF` defaults to `origin/deploy/hub` after `git fetch origin refs/heads/deploy/hub`. The first install, before any promote
      through the authority, may name another commit.
    - **Steps:**
      1. As the operator: for each of the five sources (daemon, engine, mover, plist template and conf template), the expected blob is
         `git rev-parse <INSTALL_REF>:<path>`. The files are extracted with `git cat-file blob` into a fresh `mktemp -d` directory and
         rendered there (plist and conf).
      2. One privileged copy: `_run_command --interactive-sudo -- /usr/bin/ditto <tmpdir> /var/db/k3dm-promote/staging.<UTC>`. Then
         `chown -R 0:0` and `chmod -R go-w` on the staging directory, both through `_run_command --interactive-sudo`.
      3. Each staged source file is hashed as root, outside any repository: `env -i PATH=/usr/bin:/bin HOME=/var/empty
         GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null /usr/bin/git hash-object --no-filters <staged file>`, run from `/`. Any
         mismatch with the expected blob deletes the staging directory and exits 1. The rendered files are printed in full for the operator
         to read instead.
         - Probe, m4-air, 2026-11-18: this command, run from `/`, printed `586a824e...` for `bin/k3dm-hub-deploy`, equal to `git rev-parse
           HEAD:bin/k3dm-hub-deploy`.
      4. Ancestor check, as root: `/usr/bin/stat -f '%u %Lp'` on every directory in A.2's list that exists, plus `/Library/LaunchDaemons`.
         Any that is not uid 0, or that is group- or other-writable, refuses.
      5. Activation from staging with `install -m <mode> -o root -g wheel`, then `launchctl bootstrap system <plist>`, or `kickstart -k` on
         an upgrade.
    - **Never:** a sudoers rule, a wildcard, or a bare `sudo` (the only form is `_run_command --interactive-sudo`). Root never executes git
      inside the operator's checkout.
    - **`print-plan`** prints every privileged command, with absolute paths, and runs nothing.
17. **`status`** is read-only: the client's `status`, plus `launchctl print system/com.k3d-manager.promote-authority` when readable.
    **`uninstall`** follows E.13.
18. **Makefile and setup.**
    - The Makefile gets three one-line targets: `promote-authority-install`, `promote-authority-enrol` and `promote-authority-status`.
    - `scripts/etc/machine/not-installed.list` gains `promote-authority-install|operator-run: root LaunchDaemon, installed by the operator
      with sudo, never by machine setup`. That is the real target name (Fable 25; Astra 15). Setup discovery only considers `^install-`
      targets (`scripts/tests/bin/machine_setup_acceptance.bats:197` and `:339`), so the line documents intent and changes no test.
    - `docs/howto/promote-authority.md` covers:
      - install, enrol, rotate and reset;
      - the ruleset (H.16);
      - the writer routing (H.18);
      - the credential inventory (H.19);
      - the residuals.

**H. The move authority (the O2 core) and its limits**

19. **The ruleset** (Fable 6; Astra 2; a trusted O3 setup step).
    - The credential that moves `deploy/hub` is `creds/deploy_key`, which the operator cannot read. The howto's ruleset has two rules:
      - a branch rule on `refs/heads/deploy/hub` blocking **creation**, update, deletion and non-fast-forward;
      - a tag rule on `refs/tags/hub-promote/*` blocking **creation**, update and deletion.
    - The only bypass actor is the deploy key. A precondition is that the repository has no other write-enabled deploy key; the howto lists
      them with `gh api repos/<slug>/keys`.
    - Until the ruleset is on, the authority is a gate on the honest path, not a barrier. The howto and `status` say so.
20. **Verification record.**
    - `bin/k3dm-promote-authority ruleset-verified` runs `_run_command --interactive-sudo -- /usr/bin/python3 -I <daemon> mark-ruleset`.
      Within the operator-watched step, it prints the probe results the operator just ran and writes `creds/ruleset-verified` (date, and
      the ruleset id typed on the tty).
    - `status` reports `verified <date>` from that root-only file, and `not verified` otherwise. It is the operator's assertion, recorded
      by root, so a same-user process cannot set it (Fable 12). It is not a live read (R2c-4).
21. **Writers routed before any ruleset** (agreed defect; Fable 5; Astra 2). After the ruleset, `bin/k3dm-hub-promote` cannot push.
    - **TTY promote** (`:314-330`, typed word). Before the ruleset is enabled, it changes to the authority flow: `request` (channel `cli`),
      `approve` with the TOTP code typed on the tty, then `promote`. This is a named follow-up after 2b (umbrella open question Q8); the
      ruleset waits for it.
    - **Rollback** (`:215`, `record_move` at `:284`), **BREAK_GLASS and SKIP_CHECK_RUNS promotes** (`:316`), and **bootstrap** (the first
      `deploy/hub` push) stay in the shell promoter. They become operator-watched break-glass procedures, written in the howto:
      1. Disable the ruleset from the operator's own device in the GitHub web UI.
      2. Run the existing command at the TTY.
      3. Re-enable the ruleset.
      4. Run `make promote-authority-status`.

      While the ruleset is off, the control is a gate. A daemon `rollback` op is umbrella open question Q9.
22. **Credential inventory** (Fable 1; Astra 2; O3 "remove where practical").
    - The howto lists every GitHub credential readable by the hub user: the `gh` token, the SSH push key, and the Hermes and webhook tokens.
      For each, it records whether it has repository Administration write or deploy-key write (proof owed 4).
    - Practical removal: the hub's `gh` token is replaced by a fine-grained token without Administration and without deploy-key write.
      This is umbrella open question Q7, recommended yes.
    - What cannot be removed is a named residual: the SSH push key can push release branches (R2a-2, R2d-2).
23. **Residuals,** in the howto and the review ask:
    - **R2c-1, install (S2).** Install runs operator-writable scripts through sudo. A same-user process present at install time can swap the
      expected blobs or shim `sudo`. Accepted under O3; the operator installs from a session they watch.
    - **R2c-2, enrol (S3).** The TOTP seed is shown on a tty. Mitigations: the physical console, outside tmux, with scrollback cleared.
      Rotate after any suspected same-user compromise. Accepted under O3.
    - **R2c-3, host key on first use.** The fingerprint check is the operator comparing it with GitHub's published value on their own
      device. Accepted under O3.
    - **R2c-4, ruleset (S1).** The ruleset's protection is only as strong as the absence of an admin-capable credential on the hub (H.22).
      Bypass is per actor type; whether it is per key is proof owed 2. `ruleset-verified` is an assertion, not a live read.
    - **R2c-5, socket denial of service** (Fable 11). The server is serial. A same-user process can occupy it for 10 s per connection, or
      for up to 210 s with a `promote`. This is a denial of service, not a promote.
    - **R2c-6, code not bound to the transaction (S4).** See Part 2a R2a-2. The single pending record narrows it.
    - **R2c-7.** The peer uid check cannot tell the operator from same-user malware, the control protects the remote ref and not the hub's
      checkout, and root compromise ends it.

## Proof of external behaviour

Captured on m4-air (macOS 26.5.2), `/usr/bin/python3` 3.9.6, `/usr/bin/git` 2.50.1, 2026-11-18:

- **Peer credentials:** `LOCAL_PEERCRED` layout and the `AF_UNIX` path limit (v1 probe `p1v2/peercred.py`).
- **Sibling imports:** `-I` blocks a sibling import, and `sys.path.insert` restores it.
- **Path ownership:** `/var/run` is `root:daemon 0775`, `/usr/local` is `root:wheel 0755`, and `/usr/local/libexec` is absent.
  `/Library/LaunchDaemons` and `/var/db` are `root:wheel 0755`.
- **Hashing outside a repository:** `git hash-object --no-filters` in a clean environment from `/` equals the commit's blob sha.

Proof owed before dispatch. Each is a read-only capture or an operator probe; none is asserted here.

1. **Socket on the hub.** A root `KeepAlive` daemon that creates `/var/run/k3dm-promote` and `chown`s the socket to uid 501 is connectable
   by uid 501 and not by `nobody`, and survives a reboot. Record the macOS version.
2. **Rulesets.**
   - A ruleset can name a **deploy key** as the bypass actor.
   - The tag rule blocks **creation** under `hub-promote/*` for the operator token and the operator's SSH key.
   - A *second* write deploy key is rejected (or bypass is per type, which makes the H.19 precondition the control).
   - A throwaway branch `deploy/hub-ruleset-probe` covered by an identical ruleset rejects the operator token and accepts the deploy key.
3. **GitHub host key:** `gh api meta --jq .ssh_key_fingerprints` equals the `ssh-keyscan -t ed25519 github.com | ssh-keygen -lf -`
   fingerprint.
4. **Hub credentials.** The scopes of every GitHub credential readable by the hub user (`gh auth status`, fine-grained token permissions).
   Whether each can PATCH or DELETE the ruleset or add a deploy key (capture the HTTP status of a dry-run-safe GET of `rulesets` and
   `keys`, plus the token's documented permissions).
5. **Read token.** A fine-grained token with Actions read and Pull requests read lists check-runs and `commits/<sha>/pulls`.
6. **Root under launchd** (Fable 10). `/usr/bin/python3` and `/usr/bin/git` are Xcode command-line shims. That they run as root under
   launchd with the plist's empty environment, and that `ssh -F /dev/null ... UserKnownHostsFile=` works as root.
7. **Atomic push on GitHub:** Part 2d proof owed 1.

## Worker definition of done

1. **Red first.** Each must_not test contains its positive control. Each is shown red against a stub daemon that accepts any uid, reads
   `os.environ`, does an unbounded read, puts the nonce in every response and installs without comparing. The pre-fix state is "files
   absent".
2. **Test isolation.** Pytest sockets live under a short `tempfile.mkdtemp(dir="/tmp")`. Fixtures assert the directory, the fake root and
   the socket mode first.
3. **CI portability.** Tests run on Linux Python 3.12 (CI) and macOS `/usr/bin/python3` 3.9.6. Only the real `LOCAL_PEERCRED` test is
   `skipif(sys.platform != "darwin")`.
4. **Nothing privileged.** No test calls `sudo`, `launchctl`, `security` or the network, or writes under `/var`, `/etc`, `/usr/local` or
   `/Library`.
5. **Checks.** `shellcheck` is clean on `bin/k3dm-promote-authority`; `make lint-python`, `make test-pytest` and the new bats pass.

## What NOT to do

- No sudoers rule, ever. Install and enrol go through `_run_command --interactive-sudo`.
- Do not run install, enrol, `launchctl` or anything as root during development; the live evidence is the operator's.
- No environment variable, flag or config key that reaches a test fake.
- Do not edit `bin/k3dm-hub-promote` or `bin/k3dm-hub-deploy` (Part 2b, and the TTY follow-up).
- Do not design a separate admin account or a phone confirmation channel (O3).
