## Problem

Under O2, a process running as the operator is an attacker at runtime. The approval authority is therefore a different principal: a
root-owned process.
- The operator cannot touch its state.
- The operator can reach it only through a socket.
- It alone holds the credential that moves `deploy/hub`.

This is the shape of plan 4 Part C's verifier daemon `totpd` (`docs/plans/v1.45.0-web-console-c-totp-gate.md:24`; line 23 is its
forced-command gate, line 22 its interpreter rule), and it follows
`docs/bugs/2026-11-05-sudoers-launchdaemon-plist-rule-is-root-equivalent.md`: root never executes anything the operator can write.

**O3** (umbrella, 2026-11-18): O2 applies at runtime, meaning login, approval and promote. Install, enrol and rotate, and ruleset setup
are one-off steps the operator starts and watches. They are trusted and recorded below as named residuals (H.25). This part still:
- removes admin- or ruleset-capable credentials from what the hub user can read where practical, or names the residual (H.24);
- blocks tag creation under `hub-promote/*` (H.21).

**K2a and K3a** (operator, 2026-11-19): `approve` carries the record's check value next to the TOTP code (Part 2a F.16 and G.20); the
CVE promoter stops writing `deploy/hub` (Part 2e), and the ruleset stays off until that lands.

This part is the daemon, the client, install and enrol, and the howto. Evaluation and pushing are Part 2d; the wiring into
`bin/k3dm-hub-promote` is Part 2b.

Round 3 found these problems in v3. Each is fixed below; the full list is the v4 changes table.
- **B4: the mover could not use the enrolled credentials, and nothing created the state subtrees** (Astra 4; Fable M4). One set of
  path constants is used by enrol and by the mover's construction (C.8); install creates every directory (A.3).
- **B2: a real `deploy/hub` writer was missing** (Astra 5). The CVE promoter is in the writer inventory and the ruleset gate waits for
  Part 2e (H.23).
- **B3: the code was not bound to the record** (both). The wire carries `check` (C.7) and `show` returns it (C.9).
- **Test seams** for enrol, mark-ruleset, reset-state and uninstall (Fable M5; Astra), E.16.
- **Interpreter** `-IS` on the Command Line Tools path, as the cited precedent requires (Astra), A.1.

## Behaviour

**A. Principals and paths**

1. **Installed paths.** All are `root:wheel`, and none is read from the checkout at run time:
   - **Interpreter** `PY = /Library/Developer/CommandLineTools/usr/bin/python3`, always run with `-IS`. This follows
     `docs/plans/v1.45.0-web-console-c-totp-gate.md:22`: `/usr/bin/python3` is the Xcode tool shim (codesign identifier
     `com.apple.dt.xcode_select.tool-shim-public`), which resolves the real tool through an operator-owned lookup cache; `-I` ignores
     `PYTHON*` variables and the user site, and `-S` skips `site`, so no `.pth` file in `/Library/Python/3.9/site-packages` runs.
     Probe below: under `-I` alone `sys.path` still holds two `site-packages` directories; under `-IS` it holds none.
   - **Git** for every root-side git call is `GIT = /Library/Developer/CommandLineTools/usr/bin/git` (a real Mach-O, not the
     `/usr/bin/git` shim). `ssh`, `ssh-keygen`, `ssh-keyscan`, `curl`, `ditto` and `install` are the `/usr/bin` binaries, which are
     Apple-signed tools, not shims (probe).
   - `/usr/local/libexec/k3dm-promote/` (0755) holds `k3dm-promote-daemon.py` (0755, from `scripts/libexec/k3dm-promote-daemon.py`),
     `hub_approval.py` and `promote_mover.py` (0644). Install creates `/usr/local/libexec` (0755) when it is absent; it is absent on
     m4-air.
   - `/etc/k3dm-promote/promote.conf` (0644).
   - `/var/db/k3dm-promote/` (`ROOT`, 0700), with three separate subtrees, each 0700:
     - `creds/`: `totp.secret`, `deploy_key`, `deploy_key.pub`, `known_hosts`, `read_token`, `primed`, each 0600, plus `ruleset-verified`
       (0600, H.22);
     - `state/`: the Part 2a engine directory;
     - `mirror.git/`: the Part 2d mirror.
   - `/var/run/k3dm-promote/` (0755), created by the daemon at start (B.4), holding the socket `sock`.
   - `/Library/LaunchDaemons/com.k3d-manager.promote-authority.plist` (0644), rendered from
     `scripts/etc/launchd-daemons/com.k3d-manager.promote-authority.plist.tmpl`.
     - `ProgramArguments` are `PY`, `-IS`, `/usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py` and `serve`.
     - `RunAtLoad` and `KeepAlive` are set, `Umask` is 63, and the log is `/var/log/k3dm-promote.log`.
     - `EnvironmentVariables` is absent.
2. **Startup integrity and imports.**
   - The daemon's first statements, before it imports anything outside the standard library, check with `os.lstat` that every path in
     this list is owned by uid 0, is not group- or other-writable, and (except the two interpreter symlinks) is not a symlink:
     - the interpreter chain: `PY`, its symlink target `.../Python3.framework/Versions/3.9/bin/python3`, the resolved
       `python3.9`, and every directory from `/Library` down to it;
     - `/usr`, `/usr/local`, `/usr/local/libexec`, `/usr/local/libexec/k3dm-promote` and the three files in it;
     - `/etc/k3dm-promote` and `promote.conf`;
     - `ROOT` and `ROOT/creds`, `ROOT/state`, `ROOT/mirror.git`.
   - Any failure exits 78 with the path named.
   - Only then does it run `sys.path.insert(0, LIBEXEC)` with the module constant `LIBEXEC = "/usr/local/libexec/k3dm-promote"`, followed by
     `import hub_approval, promote_mover`.
   - Tests call `bootstrap(root=<fake root>, owner_uid=os.getuid(), chain=<list>)`; `main()` passes `/`, 0 and the constant chain.
   - The check runs after the interpreter started, so it cannot protect the interpreter's own startup; install checks the same chain
     before activation (G.18 step 4), and an interpreter swapped after that needs root (R2c-7).
3. **Directory creation** (B4; Fable M4). Install (G.18 step 2) creates, as root, before anything is copied: `ROOT` (0700), `ROOT/creds`,
   `ROOT/state`, `ROOT/mirror.git` (each 0700, empty) and `/etc/k3dm-promote` (0755), with `install -d -m <mode> -o root -g wheel`. An
   existing directory with the right owner and mode is kept; any other is refused with its path. So the daemon's first start after install
   passes A.2 and serves `status` and `show` unconfigured (C.10); it never crash-loops on 78. `Mover.prime()` turns the empty
   `mirror.git/` into a bare repository (Part 2d) during enrol (E.13 stage 5). The staging directory is removed after activation and on
   every failure (G.18).

**B. The socket**

4. **Run directory.**
   - At start, the daemon `lstat`s `/var/run/k3dm-promote`.
     - **Absent:** it is created with `mkdir` mode 0755 and `chown` 0:0.
     - **Present** as a directory owned by root, mode 0755: it is used.
     - **Anything else:** it is renamed to `k3dm-promote.bad.<UTC>`, then created afresh.
   - Then it unlinks `sock` if present, sets `umask 0o177`, binds `sock`, and runs `chown(<operator_uid>, <operator_gid>)`, so the mode is
     0600 from the bind onward.
   - `/var/run` is `root:daemon 0775` (m4-air, 2026-11-18) and is cleared at boot.
   - `chown`, `mkdir` and the run-directory path are injected through `serve(..., fs=RealFs())`. Tests pass a recording `FakeFs` rooted in
     a short `/tmp` directory, so they run unprivileged.
   - The macOS `AF_UNIX` path limit is 103 bytes. The production path is 26 bytes.
5. **Peer check.**
   - Every accepted connection is checked by `peer_uid(conn)`. Production uses `LOCAL_PEERCRED`: `getsockopt(0, 1, 76)` returns a
     `struct xucred` (`cr_version` 0 at offset 0, `cr_uid` at offset 4). This was captured on macOS 26.5.2 with `/usr/bin/python3 -I`
     and reproduced by both round-3 reviewers.
   - `serve(..., peer_uid=local_peercred_uid)` takes the function as a parameter, and tests inject one. The real-socket test is
     `skipif(sys.platform != "darwin")`.
   - A uid other than `operator_uid` is closed with no reply.
   - The check excludes other local users only. It cannot tell the operator from an attacker running as the operator; the approval, the
     check value and the credential separation do that.
6. **Bounded I/O and timing.**
   - One request per connection. The request is one line of at most 4096 bytes. Each read has a 5 s timeout, and the whole read has a 10 s
     budget.
   - Every malformed request gets exactly one `bad_input` reply, then the connection closes. The malformed cases are:
     - a line over 4096 bytes;
     - a stall past the budget;
     - non-UTF-8 or non-JSON;
     - not an object;
     - a missing or extra key, or a value of the wrong JSON type;
     - an unknown op.
   - Connections are served one at a time; the listen backlog is 8.
   - **`promote` timing** (replaces v3's "longest call is 120 + 60 + 30 s"). The daemon passes `deadline = monotonic() + 120` to Part 2d's
     `promote` glue. Before the push, every mover call gets `min(default, remaining)` as its timeout, and `CurlApi.get_all` recomputes
     that per page (Part 2d). The push (timeout 60 s) and its observation (timeout 30 s) are exempt from the deadline. So from the return
     of `begin_promote` the mover needs at most 120 + 60 + 30 = 210 s. The engine calls around it each wait at most 5 s for the lock
     (Part 2a A.4), so the expected worst case is about 220 s, and the client waits 240 s. This is not a hard bound: `fsync` latency is
     not bounded. A client that times out exits 75, which means "outcome unknown, retry safe, `show` is authoritative" (Part 2a B.6).
   - **Queueing.** A client whose connection waits behind a running `promote` can time out (15 s) before its request is read; it exits 75
     with the request never started. A client that times out after its request was read gets 75 with the outcome unknown. Part 2a B.6
     covers both: a retry is refused or idempotent.

**C. Protocol (the single contract of Part 2a B.5-B.6)**

7. **Request.** The request is `{"v": 1, "op": <op>, ...}`, with these exact key sets and JSON types (all strings unless noted):

   | op | keys |
   |---|---|
   | `request` | `sha`, `branch`, `channel`, `requested_by` |
   | `show` | `id` |
   | `approve` | `id`, `nonce`, `approver`, `totp`, `check` |
   | `deny` | `id`, `nonce`, `approver` |
   | `promote` | `id`, `sha` |
   | `status` | none |

   - `check` is the record's four-character check value (Part 2a F.16, alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ`, accepted
     case-insensitively by the engine). The daemon passes it to `engine.approve(id, nonce, approver, totp, check)` unchanged; the engine
     owns its validation and the counted `check` refusal.
   - `consume`, `refuse`, `outcome`, `authorize_push`, `commit_moved`, `finish_unmoved`, `note_refusal`, `begin_promote` and anything else
     are unknown ops (`bad_input`). Only the `promote` glue reaches the engine's move calls.
8. **`promote` and the mover wiring** (B4).
   - `promote` calls `promote_mover.promote(engine, mover, id, sha, deadline)` (Part 2d D.16), which takes the branch from the record
     itself; an exception from the glue is the reply. The glue calls `engine.authorize_push(id, sha, attempt)`
     through the mover's `authorize(attempt)` callable.
   - The production mover is built per request, from `promote.conf` (D.11) and these constants only:
     - `Mover(repo_url=<repo_ssh>, repo_slug=<repo_slug>, api=CurlApi(ROOT + "/creds/read_token"), ssh_command=SSH, workdir=ROOT +
       "/mirror.git", clock=hub_approval.SystemClock())`;
     - `SSH = "/usr/bin/ssh -F /dev/null -i /var/db/k3dm-promote/creds/deploy_key -o IdentitiesOnly=yes -o
       UserKnownHostsFile=/var/db/k3dm-promote/creds/known_hosts -o StrictHostKeyChecking=yes -o BatchMode=yes"`.
     - The paths in `SSH` and `CurlApi` are built from the same `CREDS` constants that enrol writes (E.13). A test asserts the two sets are
       identical (B4 was the two disagreeing).
     - Part 2d's mover runs git as `GIT` (A.1), not `/usr/bin/git`; this is a requirement on Part 2d, listed under Contract readers.
   - The daemon never reads the environment: `os.environ` and `os.getenv` are absent from the daemon and client sources, and a test greps
     for them.
9. **Responses.**
   - The `request` response is the only response that carries the nonce, in `data.nonce`, sent only on the requesting connection. The
     nonce is never logged, never audited and never in any other response. It is legitimately present in the `approve` and `deny`
     requests, which the client sends from stdin (F.17).
   - The `request` response carries `data.check`, and the `show` response carries `check` (Part 2a G.18, G.19); Part 3's card shows it.
   - `status` returns exactly `{"daemon": "ok", "configured": bool, "pending": N, "state": "ok"|"lost", "ruleset": "asserted
     YYYY-MM-DD"|"not asserted", "audit": [ ... ]}` and nothing secret (umbrella Q12, yes):
     - `pending` is the number of records whose effective state from `engine.show` is `pending`;
     - `state` is `lost` when any record file exists and any of `serial.json`, `totp-state.json` or `clock-hw.json` is missing (the
       presence half of Part 2a E.12; a corrupt singleton shows as `state_lost` on the next mutating call);
     - `audit` is the last 10 lines of `state/audit.jsonl` (continuing into `audit.1.jsonl` when fewer), each the Part 2a E.14 object with
       `id` replaced by null when that id is currently `pending`. The audit never holds a nonce, code or check value (Part 2a E.14).
10. **Unconfigured.** `configured` is true only when all of `creds/totp.secret`, `creds/deploy_key`, `creds/known_hosts`,
    `creds/read_token` and `creds/primed` exist and pass the A.2 ownership rule. Otherwise the daemon builds `Engine(state_dir,
    SystemClock(), None, operator_ids)` (Part 2a A.2, E step 2): `show` and `status` work, and `request`, `approve`, `deny` and `promote`
    return `unknown`/`unconfigured` (exit 75). `promote` checks `configured` before it builds a mover. Credentials are read from `creds/`
    on every request, never cached, so rotation needs no reload. `totp.secret` holds the base32 text of 20 bytes; a value that does not
    decode to at least 20 bytes counts as missing.

**D. Production configuration (R1)**

11. **Loading `promote.conf`.** `main()` loads `/etc/k3dm-promote/promote.conf` and nothing else; no flag or variable selects another file,
    socket, state directory or credential.
    - **Grammar.** ASCII, LF line endings, at most 4096 bytes. Every line is `key=value` with no spaces around `=`, no quoting and no
      trailing whitespace; no blank lines and no comments. Each key appears exactly once. Any other line, a duplicate, a missing key or an
      extra key makes `serve` exit 78 before it binds.
    - **Keys:**
      - `operator_uid` and `operator_gid`: `^[0-9]{1,10}$`, not 0;
      - `operator_ids`: comma list without spaces, each `^[A-Z0-9]{2,32}$` or `cli`;
      - `repo_ssh`: `^git@github\.com:[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+\.git$`;
      - `repo_slug`: equal to the owner/name in `repo_ssh`.
    - The API base is the constant `https://api.github.com`.
    - A `file://` URL, a local path, an `ssh://` form or another host fails the `repo_ssh` pattern (exit 78).
    - The production mover is built only from these values and the C.8 constants (N6).
12. **Rendering.** `bin/k3dm-promote-authority install OPERATOR_IDS=<list>` renders `scripts/etc/promote/promote.conf.tmpl` into the
    staging directory (G.18).
    - `operator_uid` and `operator_gid` come from `id -u` and `id -g` of the invoking user. `repo_ssh` and `repo_slug` come from the
      template's fixed values for `wilddog64/k3d-manager`.
    - An `OPERATOR_IDS` value that is missing or invalid refuses before any privileged step.
    - `GH_REPO` is not read.
    - The renderer is one pure function, `render(template_text, values) -> text`, in the daemon module. The operator-side step runs it to
      produce the staged files, and root re-runs it from the staged, hash-checked templates as the comparison oracle (G.18 step 3).

**E. Enrol and lifecycles (trusted O3 steps)**

13. **`make promote-authority-enrol`** runs `bin/k3dm-promote-authority enrol`.
    - The script refuses when `TMUX` or `STY` is set, or when stdin is not a tty. It asks for the physical console, outside tmux (R2c-2).
    - It then calls `_run_command --interactive-sudo -- <PY> -IS /usr/local/libexec/k3dm-promote/k3dm-promote-daemon.py enrol
      [--rotate totp|deploy-key|token|host-key]`. The root process talks only to `/dev/tty`.
    - **Leftovers.** At the start of every stage, any `<name>.new` from an interrupted run is deleted unread.
    - Each stage writes `<name>.new` (0600), `fsync`, then `os.replace`, then `fsync` of `creds/`. A stage whose target exists is skipped
      unless `--rotate` names it, so an interrupted enrol resumes at the first missing stage. The stages, in this order:
      1. **TOTP** (target `totp.secret`). Generate 20 random bytes and print the `otpauth://` URI and the base32 secret. Wait for Enter,
         clear the screen and scrollback (`\033[3J\033[H\033[2J`), then activate `totp.secret`.
      2. **Deploy key** (target `deploy_key`). `ssh-keygen -q -t ed25519 -N '' -C k3dm-promote -f creds/deploy_key.new` (argv holds paths
         only). Activate `deploy_key.new` as `deploy_key`, then write `deploy_key.pub` from `ssh-keygen -y -f creds/deploy_key` (the public
         key derived from the active private key; probe: equal to the generated `.pub` in its first two fields), and delete
         `deploy_key.new.pub`. On every enrol run with `deploy_key` present, `deploy_key.pub` is re-derived the same way, so a crash between
         the two replaces can never leave a mismatched pair. Print the public key for the operator to add as a write deploy key; on
         rotation, print the instruction to delete the old key on GitHub.
      3. **Read token** (target `read_token`). Prompt with echo off (`termios`) and write `read_token`. The token is never in argv, the
         environment or a log.
      4. **Host key** (target `known_hosts`). Run `ssh-keyscan -t ed25519 github.com` into `known_hosts.new` and print its SHA256
         fingerprint. The operator compares it with GitHub's published fingerprint on a device of their own and types `yes`. Only then is
         `known_hosts` activated; anything else deletes `.new` and exits 1 (trust on first use, R2c-3).
      5. **First fetch** (target `primed`). Build the production mover exactly as C.8 does and call `Mover.prime()` (Part 2d: `git init
         --bare -q` when `mirror.git` has no `HEAD`, then the first fetch), outside any request budget. On success write `primed` (the UTC
         date and the fetched `deploy/hub` sha). On any failure, print the error, leave `primed` absent and exit 1; `configured` stays
         false (C.10) and a rerun retries stage 5 only.
    - **Rotation and `primed`.** `--rotate deploy-key`, `--rotate token` and `--rotate host-key` delete `primed` first, then run their
      stage and stage 5. `--rotate totp` leaves `primed`.
14. **Lifecycles are separate.**
    - `--rotate` replaces one credential and never touches `state/` or `mirror.git/`. Pending and approved records stay valid; a rotated TOTP
      secret applies from the next `approve`.
    - `--reset-state` is the only way past `state_lost` (Part 2a E.12). It renames `state/` to `state.lost.<UTC>` (0700) and creates an
      empty `state/` (0700). It never touches `creds/` or the mirror. Part 2a R2a-3 states what a reset forgets.
    - `uninstall` runs `launchctl bootout system/com.k3d-manager.promote-authority`, removes the plist and `/usr/local/libexec/k3dm-promote`,
      and keeps `ROOT` and `/etc/k3dm-promote`.
15. **No secret in argv.** No secret appears in the argv of any process. The stdin precedent is `bin/k3dm-machine-secrets:199`
    (`security -i` reads the command from stdin); there is no Keychain here.
16. **Test seams** (Fable M5; Astra). Every root-side lifecycle step is a function in the daemon module that takes its paths and tools as
    parameters, and the `main()` subcommand only binds the constants:
    - `enrol(root, tty_in, tty_out, tools, rotate=None, mover_factory=build_mover)`, where `tools` is `{"ssh_keygen", "ssh_keyscan"}` and
      `mover_factory(root)` returns the mover for stage 5;
    - `reset_state(root, clock)`;
    - `mark_ruleset(root, tty_in, tty_out, probe_file, clock)` (H.22);
    - `probe_deploy_key(root, tty_out, mover_factory)` (H.22);
    - `render(template_text, values)` (D.12).

    Tests call them with a fake root under `tempfile.mkdtemp(dir="/tmp")`, a pty pair and stub tools. The shell steps (install,
    uninstall, print-plan, the enrol wrapper) are tested by copying `bin/k3dm-promote-authority` into a scratch tree whose
    `scripts/lib/system.sh` defines a recording `_run_command` that rewrites the absolute prefixes `/var/db`, `/var/run`, `/etc`,
    `/usr/local` and `/Library/LaunchDaemons` into a fake root and replaces `launchctl` with a recorder. The script resolves its libraries
    relative to its own path, so this needs no variable.

**F. The client**

17. **`bin/k3dm-promote-client`** (Python, first line `#!/Library/Developer/CommandLineTools/usr/bin/python3 -IS`, 3.9 syntax; it runs as
    the operator).
    - **Subcommands:** `request --sha S --branch B --channel C --requested-by R`, `show --id I`, `approve`, `deny`, `promote --id I --sha
      S`, and `status`.
    - **Stdin envelopes.** `approve` reads exactly one JSON object from stdin with the keys `id`, `nonce`, `approver`, `totp`, `check`;
      `deny` reads `id`, `nonce`, `approver`. At most 4096 bytes, one line, all values strings. These fields never appear in argv. A
      missing or extra key, or anything else on stdin, is a usage error.
    - **Socket.** The default is the constant `/var/run/k3dm-promote/sock`. An optional first argument `--socket PATH` selects another
      socket; it is the test and end-to-end harness seam (umbrella E2E). It gives a same-user caller nothing it lacks, because such a
      process can open any socket itself; the controls are the daemon's peer check and the remote ref. Part 2b passes `--socket` only from
      its own test seam. `run(argv, stdin, stdout, stderr)` is the Python test entry.
    - It connects with a 5 s timeout, sends one line, and reads at most 65536 bytes up to a newline within 240 s for `promote` and 15 s for
      the rest.
    - **Response validation.** Exactly the keys `v`, `result`, `code`, `message` and `data`; `v` equal to 1; `message` a string of at most
      1024 characters without a newline; and by `result`:
      - `ok`: `code` equal to `ok` and `data` an object; for `request` exactly `{id, nonce, expires, check}`; for `show` the Part 2a G.19
        key set; for `promote` exactly `{outcome, old, new, tag}` with `outcome` in `moved|already` (Part 2d D.16 reports a consumed record as `already`), `old` and `new` 40 or 64
        lowercase hex, `new` equal to `--sha`, and `tag` matching `^hub-promote/[0-9]{8}T[0-9]{6}Z$`; for `status` the C.9 key set;
      - `refused`: `code` in Part 2a B.5's refusal set and `data` exactly `{"approval": "kept"|"final"}`;
      - `unknown`: `code` in Part 2a B.5's unknown set and `data` exactly `{}`.

      Anything else is a protocol error.
    - **Output.** On every exit except a usage error, stdout holds exactly one line: the daemon's envelope, or for a connection failure,
      timeout or empty reply the synthesized `{"v":1,"result":"unknown","code":"unreachable","message":...,"data":{}}`, and for a reply
      that fails validation the same with `code` `protocol`. The message goes to stderr. Exit codes follow Part 2a B.6: 0 ok, 2 refused

18. **Install.** This is a trusted O3 step, and its residual is R2c-1.
    - **Command:** `bin/k3dm-promote-authority install OPERATOR_IDS=<list> [INSTALL_REF=<commit>]` (bash, `set -euo pipefail`).
      `INSTALL_REF` defaults to `origin/deploy/hub` after `git fetch origin refs/heads/deploy/hub`. The first install, before any promote
      through the authority, may name another commit.
    - **The five sources:** `scripts/libexec/k3dm-promote-daemon.py`, `scripts/lib/hub_approval.py`, `scripts/lib/promote_mover.py`,
      `scripts/etc/launchd-daemons/com.k3d-manager.promote-authority.plist.tmpl` and `scripts/etc/promote/promote.conf.tmpl`.
    - **Steps:**
      1. As the operator: for each source, the expected blob is `git rev-parse <INSTALL_REF>:<path>`. The files are extracted with `git
         cat-file blob` into a fresh `mktemp -d` directory. The plist and conf are rendered there with `render` (D.12) into
         `rendered/`, and the values are written to `values.json` (`operator_uid`, `operator_gid`, `operator_ids`).
      2. Privileged, each through `_run_command --interactive-sudo`: create the A.3 directories; `/usr/bin/ditto <tmpdir>
         /var/db/k3dm-promote/staging.<UTC>`; `chown -R 0:0` and `chmod -R go-w` on the staging directory.
      3. As root, outside any repository: each staged source is hashed with `env -i PATH=/usr/bin:/bin HOME=/var/empty
         GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null <GIT> hash-object --no-filters <staged file>`, run from `/`. Any mismatch with the
         expected blob refuses. Then root runs the staged, hash-checked daemon as `<PY> -IS <staging>/k3dm-promote-daemon.py render-check
         <staging>`, which re-renders both templates from the staged templates and `values.json` and compares them byte for byte with
         `rendered/`; any difference refuses. The rendered files are also printed in full for the operator to read.
         - Probe, m4-air, 2026-11-18 (round 3 reproduced): the hash command, run from `/`, printed `586a824e...` for
           `bin/k3dm-hub-deploy`, equal to `git rev-parse HEAD:bin/k3dm-hub-deploy`.
      4. Ancestor and interpreter check, as root: `/usr/bin/stat -f '%u %Lp'` on every path in A.2's list that exists, plus
         `/Library/LaunchDaemons`. Any that is not uid 0, or that is group- or other-writable, refuses.
      5. Activation from staging with `install -m <mode> -o root -g wheel`, then `launchctl bootstrap system <plist>`, or `kickstart -k` on
         an upgrade.
      6. `rm -rf /var/db/k3dm-promote/staging.<UTC>` (through `_run_command --interactive-sudo`), after activation and also from an `EXIT`
         trap on every refusal or failure after step 2.
    - **Never:** a sudoers rule, a bare `sudo` (the only form is `_run_command --interactive-sudo`), or root running git inside the
      operator's checkout.
    - **`print-plan`** prints every privileged command, with absolute paths, and runs nothing.

**H. The move authority (the O2 core) and its limits**

21. **The ruleset** (a trusted O3 setup step).
    - The credential that moves `deploy/hub` is `creds/deploy_key`, which the operator cannot read. The howto's ruleset has two rules:
      - a branch rule on `refs/heads/deploy/hub` blocking **creation**, update, deletion and non-fast-forward;
      - a tag rule on `refs/tags/hub-promote/*` blocking **creation**, update and deletion.
    - The only bypass actor is the deploy key. A precondition is that the repository has no other write-enabled deploy key; the howto lists
      them with `gh api repos/<slug>/keys`.
    - Until the ruleset is on, the authority is a gate on the honest path, not a barrier. The howto and `status` (`not asserted`) say so.
    - Timing (umbrella Q11, yes): the operator enables it after one week of promotes through the authority, after Q7 and Q8 are done,
      after Part 2e (H.23), and after E9 and E10 pass.
22. **Probes and the verification record** (Astra; Fable minor on the probe source).
    - **Probe ruleset.** The howto sets up a second ruleset identical to H.21 on `refs/heads/deploy/hub-ruleset-probe` and
      `refs/tags/hub-promote-probe/*`, with the same bypass actor. Probes never touch `deploy/hub` or `hub-promote/*` (a probe tag there
      would break `bin/k3dm-hub-promote` rollback, which requires every `hub-promote/*` tag to carry valid old and new shas).
    - **`bin/k3dm-promote-authority probe-deploy-key`** runs `_run_command --interactive-sudo -- <PY> -IS <daemon> probe-deploy-key`. As
      root, with the C.8 `SSH` command, it pushes the current `deploy/hub` sha to `refs/heads/deploy/hub-ruleset-probe` (create), pushes that sha's parent with
      `--force` (non-fast-forward), pushes the sha again (update), deletes the branch, then creates and deletes a lightweight tag
      `refs/tags/hub-promote-probe/<UTC>`, and prints one line per operation with the git exit code. The constant refs are the only refs it
      can touch.
    - **The probe file.** The operator records every probe in a text file using the howto's template, one line per row:
      `<credential>|<ref kind>|<operation>|<expected>|<observed>`, where the credentials are `gh-token`, `ssh-push-key`,
      `cve-write-token`, `deploy-key`; the ref kinds `branch` and `tag`; the operations `create`, `update`, `delete`, `force` (branch only);
      and `expected` is `accepted` for `deploy-key` and `rejected` for the rest. It also holds one line `2e|landed <commit>|live-verified
      YYYY-MM-DD` and one line `inventory|<path of the H.24 inventory section>|YYYY-MM-DD`.
    - **`bin/k3dm-promote-authority ruleset-verified PROBE_FILE=<path>`** runs `_run_command --interactive-sudo -- <PY> -IS <daemon>
      mark-ruleset` with the file on stdin (root never opens an operator path). `mark_ruleset` (E.16) accepts at most 64 KiB of UTF-8,
      requires every one of the 28 credential rows plus the `2e` and `inventory` lines, and refuses (exit 1, nothing written) when a row is
      missing, duplicated, malformed, or has `observed` different from `expected`. It prints the file on the tty, asks for the ruleset id
      and a typed `yes`, then writes `creds/ruleset-verified` as `{"kind": "operator assertion", "asserted_on": "YYYY-MM-DD",
      "ruleset_id": <int>, "probe_sha256": <hex>}`.
    - `status` reports `asserted <date>` from that root-only file, and `not asserted` otherwise. It is the operator's dated assertion,
      recorded by root, so a same-user process cannot set it. It is not a live read of GitHub (R2c-4).
23. **Writers of `deploy/hub` and the activation gate** (B2). After the ruleset, only the deploy key can write `deploy/hub` or create a
    `hub-promote/*` tag. Every current writer is routed first:
    - **TTY promote** (`bin/k3dm-hub-promote:314-351`, typed word at `:349` `show_and_confirm`, push at `:350` `record_move`). It changes to
      the authority flow (`request` with channel `cli`, `approve` with the TOTP code and check value typed at the tty, then `promote`) in a
      follow-up spec after 2b (umbrella Q8, yes). The ruleset waits for it.
    - **Rollback** (`:215`, `record_move` call at `:284`), **BREAK_GLASS and SKIP_CHECK_RUNS promotes** (`:316`), **bootstrap** (the first
      `deploy/hub` push), and the Makefile wrappers `hub-promote` (`Makefile:521-522`) and `hub-rollback` (`:530-531`) stay in the shell
      promoter as operator-watched break-glass procedures (umbrella Q9, yes), written in the howto:
      1. Disable the ruleset from the operator's own device in the GitHub web UI.
      2. Run the existing command at the TTY.
      3. Re-enable the ruleset.
      4. Run `make promote-authority-status`.

      While the ruleset is off, the control is a gate. A daemon `rollback` op is a later spec.
    - **The CVE promoter** (`scripts/etc/argocd/platform-ops/app-cve-scan.sh`): `_app_target_branch` (`:534-537`) reads the
      Application's `targetRevision`, which is `deploy/hub` on the hub, and `_git_persist_promotion` (`:563-614`) commits an image pin
      (`:603-604`) and pushes it to that branch (`:605-606`) with `GIT_WRITE_TOKEN` (`:18`; the CronJob's secret at
      `scripts/etc/argocd/platform-ops/app-cve-scan-cronjob.yaml:108`). Precedent: `docs/bugs/2026-11-10-hub-promote-discards-cve-promoter-commits.md`.
      Under K3a, Part 2e moves these pins to their own branch, read by Argo CD as a second source, and removes this writer's push to
      `deploy/hub`.
    - **Activation gate.** The ruleset is not enabled, and `mark-ruleset` refuses, until Part 2e has landed and its live evidence passed:
      the probe file's `2e` line names the landed commit and date, and the `cve-write-token` rows show that token rejected on
      `deploy/hub-ruleset-probe`. Without Part 2e, enabling the ruleset would break CVE persistence, and giving the CVE token bypass would
      break the sole-mover claim.
24. **Credential inventory** (O3 "remove where practical"; umbrella Q7, yes).
    - The howto lists every GitHub credential readable by the hub user: the `gh` token, the SSH push key, the Hermes and webhook tokens,
      and the CVE promoter's `GIT_WRITE_TOKEN`. For each, it records its documented permissions (permission inventory, E9).
    - The hub's `gh` token is replaced by a fine-grained token without Administration and without deploy-key write, before the ruleset.
    - Operation evidence is separate (E10): the H.22 rows show each credential's real push behaviour; for ruleset and deploy-key edits,
      each non-deploy-key credential attempts to add a deploy key and to change the probe ruleset, and the HTTP status is recorded (a
      `403` or `404` passes; a `2xx` fails and is undone at once). A read-only GET proves nothing about write and is not evidence.
    - What cannot be removed is a named residual: the SSH push key can push release branches (Part 2a R2a-2, Part 2d R2d-2).
25. **Residuals,** in the howto and the review ask:
    - **R2c-1, install (S2).** Install runs operator-writable scripts through sudo. A same-user process present at install time can swap the
      expected blobs or shim `sudo`. Accepted under O3; the operator installs from a session they watch.
    - **R2c-2, enrol (S3).** The TOTP seed is shown on a tty. Mitigations: the physical console, outside tmux, with scrollback cleared.
      Rotate after any suspected same-user compromise. Accepted under O3.
    - **R2c-3, host key on first use.** The fingerprint check is the operator comparing it with GitHub's published value on their own
      device. Accepted under O3.
    - **R2c-4, ruleset (S1).** The ruleset's protection is only as strong as the absence of an admin-capable credential on the hub (H.24).
      Bypass is per actor type; whether it is per key is proof owed 2. `ruleset-verified` is a dated operator assertion, not a live read.
    - **R2c-5, socket denial of service.** The server is serial. A same-user process can occupy it for 10 s per connection, or for about
      220 s with a `promote` (B.6). This is a denial of service, not a promote.
    - **R2c-6, what binds the code to the record (S4).** Runtime, in scope under O3, and fixed by K2a: the operator's typed entry carries
      the record's check value, verified by the engine, and the matched TOTP step must be after the record's creation step (Part 2a F.16,
      G.20 checks 6 and 8). The remaining limit is Part 2a R2a-2; the approver name is asserted (Part 2a R2a-4).
    - **R2c-7.** The peer uid check cannot tell the operator from same-user malware, the control protects the remote ref and not the hub's
      checkout, the startup check cannot protect the interpreter's own startup (A.2), and root compromise ends it.

## Worker definition of done

1. **Red first, per must_not.** This is a new feature: every file is absent before it, so "red on pre-fix code" is an import failure that
   proves nothing. Each must_not test is instead shown red against the mutant named in its text, and each contains its positive control
   showing the fixture reached the operation (the engine call, the subprocess, the write). Report the mutant and the positive control per
   must_not in the hand-off.
2. **Test isolation.** Pytest sockets and fake roots live under a short `tempfile.mkdtemp(dir="/tmp")`. Fixtures assert the directory, the
   fake root and the socket mode first.
3. **CI portability.** Tests run on the CI Linux runner's `python3` and on macOS `/usr/bin/python3` 3.9.6 (the CLT interpreter's version).
   Only the real `LOCAL_PEERCRED` test is `skipif(sys.platform != "darwin")`. The bats suite needs no macOS tool: the recording
   `_run_command` replaces `stat`, `ditto`, `install` and `launchctl`.
4. **Nothing privileged.** No test calls `sudo`, `launchctl`, `security` or the network, or writes under `/var`, `/etc`, `/usr/local` or
   `/Library`.
5. **Checks.** `shellcheck` is clean on `bin/k3dm-promote-authority`; `make lint-python` and `make test-pytest` pass, and the new bats file
   passes under `bats scripts/tests/bin/promote_authority.bats` and in `make test-bin`.

## What NOT to do

- No sudoers rule, ever. Install and enrol go through `_run_command --interactive-sudo`.
- Do not run install, enrol, `launchctl` or anything as root during development; the live evidence is the operator's.
- No environment variable, flag or config key that reaches a test fake. The client's `--socket` is the only selection seam, and it is
  user-side.
- Do not edit `bin/k3dm-hub-promote`, `bin/k3dm-hub-deploy` (Part 2b and the TTY follow-up) or `app-cve-scan.sh` (Part 2e).
- Do not design a separate admin account or a phone confirmation channel (O3).
