## Goal

On 2026-10-31 the operator noticed the M4 was hot and slow. Nothing in Grafana showed it. Claude found it by hand:
load 19–20 on 10 cores, 2.7% idle and 47% sys, swap 33.8 of 34.8 GB used, `fseventsd` holding 37 GB, and
`mediaremoted` stuck at about 100% CPU. The cause turned out to be the old hub's k3d cluster, which was still running.
The fleet Macs need CPU and memory on a dashboard, plus an alert that posts a diagnosis to Slack. The diagnosis
should name the top processes, so the operator does not have to ssh in to find them.

## Observed signals (captured 2026-10-31, read-only)

One ssh call per host gets everything:
`sysctl -n hw.ncpu hw.memsize kern.memorystatus_vm_pressure_level vm.loadavg vm.swapusage; top -l 2 -s 1 -n 5 -o cpu -stats pid,command,cpu,mem`.
Only the second `top` sample is meaningful: the first sample's CPU numbers are averages since boot, and the
parenthesised swap counts in the second sample are deltas over the 1 s interval.

Store these raw outputs verbatim as test fixtures, with host and capture time in a comment.

What they show, which drives the alert design:
- **`PhysMem used` does not work as an alert signal.** The idle M5 hub reports 31 of 32 GiB used, because macOS counts file cache as used.
- **`kern.memorystatus_vm_pressure_level` stayed at 1 (normal)** on the M4 while it was thrashing. It cannot be the only memory signal.
- **Swap-used percentage does not work as an alert signal either.** The M2 is at 88% of swap and 80% idle.
- **The swap-in rate is the signal.** The M4 showed 400 swap-ins in 1 s, while the M2 and M5 showed 0.
- **`%sys` is the other signal.** 33–47% sys on the M4 was memory compression and paging.

## Design

1. **Fleet list in one place.** Move `FLEET` out of `bin/k3dm-disk-metrics` into `scripts/etc/machine/fleet.list`
   (`label|ssh-host|disk-path`). Both producers read that file, and `bin/k3dm-disk-metrics` behaves exactly as before.
   As in the disk producer, the local Mac is `local` and its label comes from `scutil --get LocalHostName` with any
   `-air` suffix removed. The local Mac is never probed over ssh. `K3DM_HOST_TARGETS` (`label=host ...`), when set,
   is used verbatim.
2. **`bin/k3dm-host-metrics` (new, Python, the same shape as `bin/k3dm-disk-metrics`).** For each host, it runs
   the single command above. Remote hosts are reached over ssh with `BatchMode=yes` and `ConnectTimeout=10` and a
   30 s timeout. The local Mac runs the command directly. It pushes to the Pushgateway as job `k3dm-host`, with
   retries like the disk producer. A failure on one host never stops the others or the Hermes tick.
   Gauges, all labelled `host`:
   - `k3dm_host_probe_success`
   - `k3dm_host_cpu_count`
   - `k3dm_host_cpu_user_ratio`, `k3dm_host_cpu_sys_ratio`, `k3dm_host_cpu_idle_ratio` (from the second sample)
   - `k3dm_host_load1`, `k3dm_host_load5`, `k3dm_host_load15`
   - `k3dm_host_memory_total_bytes`, `k3dm_host_memory_wired_bytes`, `k3dm_host_memory_compressor_bytes`,
     `k3dm_host_memory_unused_bytes`
   - `k3dm_host_memory_pressure_level`
   - `k3dm_host_swap_total_bytes`, `k3dm_host_swap_used_bytes`
   - `k3dm_host_swapins_per_second` (the parenthesised delta)
   - `k3dm_host_top_process_cpu_percent{host,rank,command}` and `k3dm_host_top_process_memory_bytes{host,rank,command}`
     for ranks 1–5. `command` is truncated to 32 characters and restricted to `[A-Za-z0-9 ._-]`.

   `top`'s memory column has suffixes `K`, `M`, `G` and an optional trailing `+`/`-`. Parse all of them.
   `--diagnose HOST` prints a human-readable snapshot for one host and pushes nothing. The snapshot is the
   `top -l 2 -s 1 -n 10 -o cpu` second sample, plus the 10 processes with the most memory (`-o mem`), the sysctls
   and `vm.swapusage`.
3. **Hermes** calls the producer every tick (5 minutes) through `_publish_host_metrics()`, built like
   `_publish_disk_metrics()`. The producer has a 120 s timeout and is non-fatal.
4. **Rules: `scripts/etc/prometheus/rules/host-resources.yaml`.** Group `host.resources`, interval 60s, labels
   `severity`, `cluster: hub`.
   - `HostCPUSaturated` (warning): `k3dm_host_cpu_idle_ratio < 0.10 or k3dm_host_load5 / k3dm_host_cpu_count > 1.5`, `for: 15m`.
   - `HostMemoryThrashing` (warning): `k3dm_host_swapins_per_second > 100 or k3dm_host_memory_pressure_level >= 2`, `for: 15m`.
   - `HostResourceMetricsStale` (warning): `k3dm_host_probe_success == 0 or (time() - max(push_time_seconds{job="k3dm-host"}) > 1800)`, `for: 30m`.

   With 5-minute samples, `for: 15m` means at least three bad samples in a row. This catches sustained load, not
   a 30-second burst. Faster sampling is out of scope. The thresholds are a starting point, to be tuned from the
   dashboard after a week.
5. **Slack diagnosis.** Add `HostCPUSaturated|HostMemoryThrashing` to the `k3dm-analyze` matcher in
   `scripts/etc/argocd/platform-ops/alertmanager-config.yaml`; do not add the stale alert. In `bin/k3dm-webhook`
   `_run_analyze`, an alert whose `alertname` starts with `Host` and that has a `host` label gets host diagnostics:
   - It runs `bin/k3dm-host-metrics --diagnose <host>` through `_posix_spawn_capture` with a 60 s timeout. `host`
     must match `^[a-z0-9-]+$` and be a label in the fleet list; otherwise the alert is logged and skipped.
   - It does not gather the Kubernetes diagnostics.
   - It sends a prompt that frames the model as a macOS operations expert and asks for the likely culprit process
     and one safe next step.
   - The Slack message is `🔍 *<alertname>* — \`<host>\``, followed by the analysis. Delivery is unchanged (status
     channel, then the incoming-webhook fallback).
6. **Dashboard: `scripts/etc/argocd/platform-ops/grafana-dashboard-host-resources.yaml`** ("Host Resources").
   It is applied in `deploy_argocd_platform_ops` next to the host-disk dashboard. It has a `host` variable (multi,
   all) and these panels:
   - CPU busy (user + sys, stacked) per host
   - load5 / cores
   - swap-ins per second
   - compressor + wired / total
   - swap used / total
   - memory pressure level
   - a top-5 process table by CPU and by memory
   - probe success
7. **Docs.** Add `docs/guides/grafana-dashboards/k3dm-host-resources.md` and link it from the dashboards index. It
   covers what each panel means, why "memory used" is not shown as a health signal, the alert thresholds, and what
   the Slack diagnosis contains. Also add a CHANGELOG `[Unreleased]` entry.

## What NOT to do

- Do not install node_exporter or any agent on the Macs; probes are read-only ssh/sysctl/top.
- Do not run `sudo`, `fs_usage`, `killall` or anything that changes a host. The diagnosis only reads.
- Do not alert on `PhysMem used` or swap-used percentage alone.
- Do not send host alerts to SMS or e-mail receivers; they go only to `k3dm-analyze` (Slack).
- Do not read or copy ssh private keys, and do not touch `known_hosts` or `authorized_keys`.
- Do not create a PR, skip hooks, commit to `main`, or modify files outside the list above.
