# v1.43.14 — Intent verification: the operator approves plain-language intents before dispatch, and every verification answers them

**Status:** PLANNED — dispatch after `k3d-manager-v1.43.14` is cut from `main` once v1.43.13 merges (v1.43.13 is at its 5-plan cap)
**Approval:** operator, 2026-10-31 — proposed after blind calibration 1 ("or if we can do intent verification in the future release that would help too"); plan go ("go ahead").
**Branch:** `k3d-manager-v1.43.14`
**Depends on:** `docs/plans/v1.43.13-agent-instruction-files-refresh.md` (its shared rules block in `CLAUDE.md`, `AGENTS.md` and `GEMINI.md`, and `make check-agent-docs`, carry the Acceptance rule this plan extends)
**Related:** `docs/calibration/v1.43.12.md` (findings O2 and O4); `docs/howto/blind-review-calibration.md`; `bin/k3dm-codex-dispatch`; `CLAUDE.md` Docs Conventions (Acceptance block, Test controls)

## Goal

Calibration 1 on the v1.43.12 release (2026-10-31) gave two operator findings that this plan answers:

- **O4.** Verification output showed errors that Claude still reported as good. The operator cannot rerun the
  commands and depends on Claude's verdict, so a PASS beside visible errors leaves no shared ground.
- **O2.** "One command builds the M5" turned out to be a project: two-machine environment sync and process
  migration. The size of the work only became clear while doing it.

Both start in the same place. The Acceptance block is written for code (`must`, `must_not`, `evidence`), and
the operator approves a spec without a plain statement of what they will see when it works. Claude then
verifies against the code-level items, and the operator has nothing they can check the verdict against.

The fix has three parts:

1. Each evidence item carries a plain-language **intent**.
2. The operator approves the intents before dispatch.
3. Every verification report answers the intent first, then gives proof and an "Errors seen" list.

## Change

### 1. `intent` on every evidence item

Each `evidence` item in an Acceptance block gains an `intent` field written for the operator, not for a test.
It has two sentences:

- **You will see:** an observable result. This is a dashboard value, a Slack message, a command's last line
  or a count, never a function name.
- **It failed if:** the specific thing that means it did not work.

Example (from the v1.43.12 Hostinger handoff):

```yaml
evidence:
  - id: E2
    proves: [M1, N1]
    kind: live
    intent: >-
      You will see 33 Applications on the M5's ArgoCD and the M4's application controller at 0 replicas.
      It failed if any Hostinger app still names the M4 as its manager, or the M5 shows fewer Applications.
    text: ...
```

An intent that cannot be written in two plain sentences signals that the evidence item, or the plan, is too
big. Claude splits it before asking for approval. This is the early catch for O2.

### 2. `**Intent approved:**` header line

A spec gets `**Intent approved:** operator, <date>` once the operator has read the intents. This is separate
from `**Approval:**`, which approves doing the work at all. Claude asks for it by listing only the intents:
the plain sentences in order, one per evidence item, with no YAML and no code.

### 3. Dispatch refuses a spec without approved intents

`bin/k3dm-codex-dispatch` checks the spec before it builds the prompt, and refuses with a message naming the
missing items when:

- any `evidence` item in the Acceptance block has no `intent`, or
- the header has no `**Intent approved:**` line.

The check applies only to specs whose `**Filed:**` date, or the plan's first-commit date, is on or after this
plan's merge date. Older specs are dispatched as before. The checker is a small Python module
(`scripts/lib/spec_intent.py`) that the dispatcher calls and that `make check-spec-intent SPEC=<path>` runs on
its own.

### 4. Verification report shape

`docs/howto/verification-report.md` sets the shape Claude uses for every live or offline verification it
reports to the operator, including reviews of a dispatched agent's fix:

1. **Intent:** the approved intent sentence, then the answer in plain words: *seen* or *not seen*.
2. **Verdict:** PASS, FAIL or PASS WITH NOTES.
3. **Proof:** the command or make target, its exit code, and the one output line that shows the result.
4. **Errors seen:** every error, warning or non-zero exit in the output, each with a plain reason it does or
   does not change the verdict. If there are none, write "none". An error Claude cannot explain means the
   verdict is not PASS.

A `**Live evidence:**` line in a bug or plan doc links the report.

### 5. Rule text

The `CLAUDE.md` Acceptance paragraph, and the shared rules block that v1.43.13 copies into `AGENTS.md` and
`GEMINI.md`, gain one sentence: every evidence item carries an operator-facing `intent`, and the spec carries
`**Intent approved:**` before dispatch. `make check-agent-docs` keeps the three copies identical.

## Acceptance

```yaml
must:
  - id: M1
    text: a spec filed on or after the merge date whose evidence items all carry intent and whose header has an Intent approved line is dispatched as before
  - id: M2
    text: make check-spec-intent SPEC=<path> exits 0 for such a spec and non-zero, naming each gap, otherwise
  - id: M3
    text: docs/howto/verification-report.md defines the four-part report (intent answered, verdict, proof, errors seen) and the shared rule sentence is identical in CLAUDE.md, AGENTS.md and GEMINI.md
must_not:
  - id: N1
    text: dispatch of a post-merge spec with an evidence item lacking intent is refused, and no agent process starts
  - id: N2
    text: dispatch of a post-merge spec with intents but no Intent approved line is refused
  - id: N3
    text: a spec filed before the merge date is never refused for missing intents (paired with N1, so the refusal is shown to be date-scoped, not universal)
evidence:
  - id: E1
    proves: [M1, M2, N1, N2, N3]
    kind: offline
    intent: >-
      You will see the new tests pass, and the two refusal tests fail when run against today's dispatcher.
      It failed if a spec with a missing intent can still reach an agent, or an old spec is refused.
    text: pytest scripts/tests/bin/test_spec_intent.py with fixture specs in a scratch directory (fixture asserts it is not the real docs/plans first); the dispatcher's agent launch is stubbed and asserted not called for N1/N2; N1 and N2 red on the pre-change dispatcher
  - id: E2
    proves: [M3]
    kind: offline
    intent: >-
      You will see make check-agent-docs pass with the new sentence in all three instruction files.
      It failed if the sentence is in only one file, or the check passes when one copy differs.
    text: make check-agent-docs; Claude reads verification-report.md against this plan
  - id: E3
    proves: [M1]
    kind: live
    intent: >-
      You will see the first v1.43.14-or-later spec ask you to approve its intents as plain sentences before

      It failed if you are asked to approve YAML or code, or a verdict says PASS while its Errors seen list

    text: the operator approves the next spec's intents in chat; Claude records the dispatch and the four-part verification report

  - make check-spec-intent SPEC=<path>
  - bin/k3dm-codex-dispatch (refusal message and exit code)
  - scripts/lib/spec_intent.py check(path) -> list of gaps
```

## What NOT to do

- Do not rewrite existing specs to add intents. They stay valid under the date scope.
- Do not make the intent a test oracle. Tests still come from `must` and `must_not`; the intent is for the
  operator.
- Do not let the checker judge the quality of an intent. It checks presence only. Quality is Claude's
  responsibility when asking for approval.
- Do not route Gemini or any dispatched agent into live verification. E3 is Claude's and the operator's.

## Not in this plan

- Automating the manual steps of the M5 build (operator finding O3). That is a separate plan, not yet written.
- Changing the blind calibration protocol. Calibration continues on the next PRs with instructions unchanged.
