# v2.2 — Agent identity and capability enforcement

**Status:** PROPOSED — 2026-10-27; documentation only; no implementation authorized
**Release:** v2.2 (plan 1 of 5; AI diagnostics and healing gateway policy stage)
**Branch:** k3d-manager-v1.43.9 (spec authored here; implementation after v2.1)
**Priority:** P1 security foundation
**Approval:** documentation requested 2026-10-27; execution, credential changes and rollout require separate operator approval
**Dispatch:** not authorized
**Dependencies:** v2.1 read-only gateway; existing webhook/cloud-bridge RBAC, Agent Dispatch worktree isolation and approval contracts
**Component:** shared deterministic policy contract; dispatch, gateway, webhook and tool adapters

## Problem
Multiple coordinator and worker models use tools with different privilege and identity assumptions. Worktree isolation is not a security boundary; inherited host credentials, tool delegation, and cross-repository operations can exceed task scope. A prompt-only allowlist cannot stop an agent that has direct OS credentials.

## Design
- Define a versioned, closed-schema task capability manifest: task ID, actor/coordinator/worker identities, repository and commit scope, approved filesystem paths, tool verbs, resource targets, expiry, and approval reference.
- The dispatcher and every privileged execution adapter independently check the manifest before tool execution; reject missing/expired/unknown identity, unspecified capability, cross-repo escalation, and self-approved permissions.
- Enforce restrictions using OS/process sandboxing, narrowly scoped tokens, and server-side RBAC. Do not pretend YAML or model instructions enforce permission. Never deliver Vault root, general GitHub push, cloud admin or operator credentials to untrusted workers.
- Separate worker implementation from landing, cluster mutation, secret access and policy change. Preserve existing explicit operator approvals and SHA-bound gates; no silent privilege widening.
- Record bounded, redacted allow/deny audit events (actor, task, policy version, reason, timestamp, tool class), without token, prompt or raw worker transcript.
- Keep dispatch and bridge offline if the authorization store or policy cannot be verified; read-only diagnostics may follow an explicit separate allowlist.
- Support an operator-only emergency mechanism with independently audited expiry, not an LLM-originated override.

## Files
- New versioned capability schema and policy validator in the existing policy/gateway structure (path resolved at implementation).
- Agent Dispatch and gateway/webhook/cloud-bridge enforcement adapters.
- Offline policy fixtures, negative tests and operator runbook.

## Acceptance
1. Luna assigned a Grafana-only change cannot read another agent's credentials, push a repository, change Vault, mutate Kubernetes or spawn a nested worker even if malicious text instructs it to.
2. Direct adapter invocation cannot bypass the dispatcher policy; fail-closed on unknown identity, expired permission or invalid approval.
3. Approved reader task still operates; no change to existing production behavior until explicit deployment approval.
4. Audit reports denied attempts without exfiltrating secrets or full transcripts.
5. macOS and Linux enforcement limitations are documented and live-tested before claiming sandbox isolation.

## Out of scope
New identity provider, replacing Vault, a general autonomous permission manager, automatic authorization by LLM, and rewriting Agent Dispatch.
