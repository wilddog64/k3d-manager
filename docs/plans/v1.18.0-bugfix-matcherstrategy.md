# Bugfix: v1.18.0 — Alertmanager namespace matcher filters cluster-wide CVE alert to cicd-only

**Branch:** `k3d-manager-v1.18.0`
**Files:** `scripts/etc/helm/observability/kube-prometheus-stack-values.yaml`

---

## Problem

The v1.18.0 event-driven CVE auto-patch alert `TrivyCriticalVulnerabilityDetected`
(`sum by (namespace, image_repository)(trivy_image_vulnerabilities{severity="Critical"}) > 0`)
is deliberately **cluster-wide** — Critical CVEs are counted across every namespace. But the
alert never reaches the `k3dm-cve-remediate` / `k3dm-analyze` receivers for any namespace other
than `cicd`, so remediation silently never fires for the majority of workloads.

**Root cause:** the `kube-prometheus-stack` Alertmanager leaves
`spec.alertmanagerConfigMatcherStrategy` unset, so prometheus-operator applies its default
`type: OnNamespace`. That default **injects a `namespace="<AlertmanagerConfig namespace>"`
matcher** onto every route rendered from an `AlertmanagerConfig`. Our config lives in `cicd`, so
the operator injects `namespace="cicd"` onto the top-level route. Live evidence:
`trivy_image_vulnerabilities{severity="Critical"}` spans 8 namespaces (monitoring 18, cicd 8,
identity 7, kube-system 6, secrets 4, platform-ops 3, istio-system 2, trivy-system 2); only the
`cicd` subset survives the injected matcher. The existing ArgoCD alerts were unaffected because
`argocd_app_info` already carries `namespace="cicd"`.

Because `k3dm-analyze` is the **only** `AlertmanagerConfig` in the cluster, the namespace
isolation the default provides is moot — there is nothing to isolate it from. Setting
`type: None` removes the injected matcher so routes match on their own `alertname` /
`remediation` matchers alone.

---

## Reproduction

```
# Decode the running Alertmanager config and inspect the k3dm route:
kubectl -n monitoring get secret alertmanager-kube-prometheus-stack-alertmanager-generated \
  -o jsonpath='{.data.alertmanager\.yaml\.gz}' | base64 -d | gunzip
```

**Actual (default OnNamespace):** the `k3dm-analyze` route carries an extra
`namespace="cicd"` matcher next to the `alertname=~"…"` matcher, so a
`TrivyCriticalVulnerabilityDetected` alert with `namespace="identity"` (etc.) is dropped.

**Expected (after fix):** the top-level `k3dm-analyze` route matches on `alertname` only; the
CVE alert reaches both child routes regardless of workload namespace.

---

## Fix

### Change 1 — `scripts/etc/helm/observability/kube-prometheus-stack-values.yaml`: add matcherStrategy

**Exact old block:**

```yaml
alertmanager:
  enabled: true
  alertmanagerSpec:
    resources:
      requests:
        memory: 32Mi
        cpu: 10m
      limits:
        memory: 64Mi
        cpu: 50m
  configSecret: alertmanager-smtp-secret
```

**Exact new block:**

```yaml
alertmanager:
  enabled: true
  alertmanagerSpec:
    alertmanagerConfigMatcherStrategy:
      type: None
    resources:
      requests:
        memory: 32Mi
        cpu: 10m
      limits:
        memory: 64Mi
        cpu: 50m
  configSecret: alertmanager-smtp-secret
```

## Related operational gap (not part of this file change)

The bearer-token Secret referenced by the AlertmanagerConfig — `k3dm-webhook-token` in `cicd`,
key `token` — must exist or prometheus-operator **rejects the entire `k3dm-analyze`
AlertmanagerConfig** (ArgoCD routes included). It is a manual bootstrap step documented at
`scripts/plugins/argocd.sh:1429` and was absent on the hub cluster (rejected on every reconcile
2026-07-25 → 2026-07-27). It has been recreated. Follow-up: fold this secret into the
cluster-rebuild bootstrap so it does not vanish on the next rebuild.
