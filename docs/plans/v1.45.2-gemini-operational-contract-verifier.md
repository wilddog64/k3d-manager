## Motivation

Several defects escaped green status/tests on 2026-10-15: AWS `cluster-up` reported success while Prometheus port-forward was absent; `cluster-down` could return green without verified CloudFormation deletion; `k3dm help` during `cluster-up` had no visible Slack reply; deployment metrics remained empty after lifecycle jobs; cluster-up progress messages shifted Slack threads. Each is a **cross-component operational contract discrepancy**. Manual detection relies on the operator noticing a contradiction.

Gemini is already used for embeddings and is being considered for independent red-team review, but its additional ability to summarize correlated anomalies has not been fully exploited. Under a fixed subscription/free-tier budget, Gemini must **not** be called for every successful sensor sample.

## Goal

Introduce a low-cost, read-only **operational contract verifier** integrated with existing Hermes/off-hub monitoring. Deterministic code checks expected evidence against observed evidence; **Gemini analyzes only bounded, novel, nonhealthy cases** to propose hypotheses, reproduction steps, and candidate bug reports. This must not become an unsupervised agent that modifies infra, Git, incident severity, or test outcomes.

## Initial contract catalog and evidence

| ID | Trigger and expected evidence | Violation or uncertainty |
|---|---|---|
| `slack-command-response` | Accepted command event has correlated processed result and delivery acknowledgment within configured timeout; help independent of lifecycle jobs | Missing reply / bot API failure / missing event evidence differentiated |
| `lifecycle-terminal` | Started job has terminal result within action-specific deadline | No terminal state / delayed result / stale status |
| `lifecycle-postcondition` | Green `cluster-up` carries readiness check outcomes; `cluster-down` carries stack-delete state and scoped absence verification | Green result without required evidence is **unknown/unverified**, not proven failure |
| `lifecycle-metric` | Completion job ID appears in durable metrics destination within bounded scrape/ingest delay | Missing metrics, unknown datasource or ephemeral-only retention are distinct |
| `slack-thread-integrity` | Posted progress/terminal messages carry expected channel/thread correlation and acknowledged Slack result | Wrong thread, fallback posting or missing acknowledgment |

Implement contracts incrementally, starting with **Slack command-response** using mockable event and delivery boundaries. Do not bulk-rewrite all lifecycle systems in this release. Existing bugs remain canonical implementation work; this enhancement adds detection rather than subsuming their fixes.

## Deterministic verification architecture

1. Extend existing Hermes sensor/record/correlator interfaces where feasible, rather than creating an independent continuously running AI daemon. Read-only, off-hub polling/event reconciliation should survive app-cluster outages.
2. Emit small structured events from approved local webhook paths: `event_id`, `job_id`, `action`, provider, started/completed timestamps, expected `channel_id/thread_ts`, actual Slack API success/failure, metrics publish outcome, and verification evidence references. Do **not** store raw Slack credentials, message payloads, OIDC cookies, or AWS secrets.
3. Keep an append-only or atomic bounded local ledger (SQLite or existing established store, **choose based on source audit**). Use stable event/contract keys, TTL/retention, deduplication, reboot recovery, and concurrency-safe ingestion. Avoid introducing a network database.
4. Contracts return `verified`, `violated`, `unknown` (with missing evidence and source freshness). Missing telemetry cannot be silently counted as zero or failure. Timeouts must account for asynchronous processing, scrape latency and Slack API acknowledgments; avoid false alarms during intentional sandbox shutdown.
5. Correlate by job ID, Slack event/thread IDs, provider and time window. Collect only read-only/bounded evidence from current job files, webhook delivery results, Hermes sensors, dashboard query status where authorized and Git-tracked bug/spec history.
6. Publish bounded contract status and counters to existing Grafana/Alertmanager where appropriate; guard against alert storms. The sensor itself must report when stale/offline and keep a separate `last successful evaluation` indicator.

## Gemini anomaly review — budget and safety contract

- Invoke Gemini **only** for newly detected or materially changed `violated`/`unknown` cases after deterministic deduplication and a configurable debounce. Never invoke for every healthy poll.
- Respect explicit request/token quotas, daily budget, backoff for 429 and model errors, concurrency cap (default one), short context limits and a dry-run mode. Embedding API quota and generative-model quota are **not interchangeable**; validate model availability, API permissions and their actual free-tier limits before implementation.
- Send sanitized structured evidence, not unrestricted shell access, private repo credentials, AWS credentials, personal data, or raw Slack event bodies. Default to local and/or approved Gemini tool adapter; if unavailable, preserve deterministic detections without AI.
- Gemini returns **hypotheses with confidence/uncertainty**, likely violated contract, evidence references, suggested red-green reproduction and triage recommendation. No assertion that a hypothesis is proven. Validate output structure and keep the original deterministic evidence alongside it.
- Read-only vector-search of existing indexed bug/issue/spec docs may help prior-art matching; require provenance (path/ref, source timestamp) and account for incomplete indexing/free-tier exhaustion. Avoid recursive autonomous RAG/embedding calls.
- Gemini cannot autonomously create commits/PRs, file GitHub bugs, edit docs, run destructive `make`, promote releases, close alerts, or trigger cloud operations. Generate a **candidate bug report** for operator/Claude review with explicit approval before writing it.
- Maintain operator-adjustable enablement and quotas. On quota exhaustion, service outage or parse failure, degrade to deterministic alerts with a clear `Gemini analysis unavailable` annotation.

## Verification and rollout

**Phase A:** Trace existing webhook, Hermes, Pushgateway and Slack delivery contracts; identify available evidence and telemetry gaps. Specify schema, retention/PII policy, and trust boundaries.

**Phase B (MVP):** Implement one deterministic `slack-command-response` verifier and mocked integration tests. Prove that a simulated `cluster-up` in progress does not interfere with `k3dm help`, and that dropped outbound Slack delivery is detected even if Slack Events returns HTTP 200.

**Phase C:** Add Gemini bounded analysis and human-review output, with fixtures for malformed model response, 429, no network, duplicated incidents, and malicious text in log evidence.

**Phase D (optional after evaluation):** Extend the same verifier to lifecycle postconditions, metric publication and thread integrity, using existing bug fixes/contracts rather than rebuilding them.

**Acceptance criteria:**
- Offline deterministic test suite reproduces at least one previously silent failure **before** correction and surfaces a `violated` result with correlated evidence; a healthy concurrent scenario remains `verified`.
- Absent credentials, missing permissions and stale instrumentation produce `unknown` with reasons; no false green or false deletion claim.
- Novel anomaly results are deduplicated and Gemini calls stay within configured budget; testable zero calls on healthy polls.
- Alert/candidate-bug artifacts show expected versus actual behavior, source timestamps, links to original logs and redacted data, and explicitly distinguish proven observation from hypothesis.
- No autonomous writes or infrastructure actions; no new paid dependency; feature remains disabled until reviewed and operator-approved.
