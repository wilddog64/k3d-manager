## Goal

On 2026-11-08 three Hermes failures passed every offline test and were found only when the operator pressed a
button: the Slack app had Interactivity off, `/hermes-auth` pointed at the interactivity Request URL instead of the
commands one, and the cards were posted by a different app from the relay's. The first two are Slack app
*settings*. A probe sent straight to the relay skips Slack and cannot see them; only the app manifest can. This plan
adds two sensors that are silent on a healthy stack and degrade within a day of such a setting going wrong.

## Design

Revised 2026-11-13 after the Fable spec review (18 findings; `## Spec review` below).

Constants in `scripts/lib/hermes/sensors.py`: `SLACK_RELAY = "https://k3dm-slack-relay.k3dm.workers.dev"`,
`SLACK_APP_ID = "A0B863SCQUV"` (app `k3d-manager`, whose signing secret the relay verifies; not `k3dm-notices`
A0CFHA9KCNQ), `SLACK_CONFIG_SERVICE = "k3dm-slack-config-token"`, `SLACK_CONFIG_REFRESH_SERVICE =
"k3dm-slack-config-refresh-token"`, `SLACK_RELAY_NAMED_ROUTES = ("/slack/interactivity", "/slack/events",
"/hermes/")` (from `workers/slack-relay/index.js:342-352`; comment: keep in step with the relay),
`SLACK_REQUIRED_COMMANDS = ("/hermes-auth",)`, `HERMES_USER_AGENT = "k3dm-hermes/1"`.

**Common rules for both sensors.**
- Every HTTP call sends `User-Agent: k3dm-hermes/1`. Python's default `Python-urllib/3.x` gets **403** from
  Cloudflare on the relay (capture 3b), and the same rule applies to slack.com. Timeout 10 s for Slack, 5 s for
  the relay (not `_http_json`'s 90 s default, `bin/k3dm-hermes:82`).
- `now` is epoch seconds (float), optional, defaulting to `time.time()`, matching `_poll_cycle`.
- Evidence is one string of at most 200 characters (`records.py:19`), **action first** (the SMS is cut to 140
  characters, `pager.py:37`). Details go in `data`. Evidence and `data` never contain `str(exc)`, `repr` of a request
  or response, or any Slack response field except the `error` code string. Records are printed to the log and
  pushed into a ConfigMap through `kubectl --from-literal` (`bin/k3dm-hermes:508`), so they must hold no secret.

**Sensor `slack_app_config(api, state, store, now=None, may_rotate=False, threshold=1)`.**
`api(method, token, fields)` POSTs a form to `https://slack.com/api/<method>`; for `apps.manifest.export` the token
travels as an `Authorization: Bearer` header, never in the URL. It returns decoded JSON or raises. `store` has
`read(service) -> str`, `write(service, value) -> bool` and `writable(service) -> bool`. The default store is
Keychain-backed:
- read is `_keychain_secret`;
- write feeds `add-generic-password -U -a k3dm -s <service> -X <hex-of-value>` to `security -i` on **stdin** (the
  method at `bin/k3dm-machine-secrets:199`), with stdout and stderr captured and discarded (they can echo the command
  line), then compares a read-back;
- writable rewrites the current value to itself and reads it back;
- write refuses any service other than the two constants.

All of the sensor's state lives in `state["slack_config"]`: `checked_at`, `expires_at`, `rotated_at`,
`needs_regenerate`, `record` (the last healthy or degraded record).

1. **Cadence.** The manifest is read at most every `K3DM_HERMES_SLACK_CONFIG_INTERVAL` seconds (default 3600, floor
   60). Between checks the sensor returns the stored `record` with its original `sampled_at` and `data.cached: true`,
   and leaves the debounce counter alone. **Unknown is never cached**: an unknown result does not advance
   `checked_at`, so the next poll retries. One network blip is therefore one unknown cycle, not twelve.
2. **Rotation**, only when `may_rotate` is true. Only `_poll_cycle` passes it; the approval drain
   (`bin/k3dm-hermes:276`) and CLI `approve` (`:1036`, `:1039`) call `_run_cycle` without it and get the stored
   record or an unknown. The rotation steps, under an exclusive `fcntl.flock` on `~/.k3dm/hermes/slack-config.lock`:
   1. Re-read both items.
   2. If `expires_at` is known and within 3600 s of `now`, rotate before the manifest call. If `expires_at` is
      absent, call the manifest first and rotate only if it returns `token_expired` or `invalid_auth`. This way a
      lost state file cannot cause a rotation every cycle.
   3. Before rotating, `store.writable()` on both items. If it fails (locked keychain, ACL prompt under launchd),
      return unknown `Keychain not writable; unlock the login keychain on the hub` **without** rotating.
   4. Call `api("tooling.tokens.rotate", None, {"refresh_token": <refresh>})`. If it returns `ok: true`, write the
      refresh token, then the access token, read both back, and set `expires_at = exp` and `rotated_at = now`. Then
      call the manifest with the new token.
   5. If Slack **rejects** the rotate, re-read the refresh item. If it differs from the one sent (another process
      rotated first), retry the manifest with the stored access token. Otherwise set `needs_regenerate`.
   6. If a write or read-back fails after a successful rotate, return unknown `Keychain write failed; unlock the
      login keychain on the hub` **without** setting `needs_regenerate`. Capture 4 showed that the previous pair
      stays valid after a rotate, so the next cycle retries with the stored pair. `needs_regenerate` is set only
      when Slack rejects a rotate made with the refresh token currently stored (step 5).
   - `needs_regenerate` returns unknown with evidence `Regenerate Slack config token at api.slack.com/apps and
     re-store both items`. While it is set, no rotate is attempted. The manifest is retried once per interval with
     the stored token, and a success clears the flag. `pager.py:79-82` texts the operator after 6 unknown cycles (30
     min); that is the intended escalation.
3. **Checks on `.manifest`** (paths from capture 1). Each finding goes in `data.findings` as
   `{field, found, expected}`. The evidence names the first finding and the count. The findings:
   - `settings.interactivity.is_enabled` is not `true`;
   - `settings.interactivity.request_url` is not `SLACK_RELAY + "/slack/interactivity"`;
   - a command in `SLACK_REQUIRED_COMMANDS` is missing from `features.slash_commands[].command`;
   - a `features.slash_commands[].url` whose scheme and host are not `SLACK_RELAY`'s, or whose path is a named route
     or lies under one. The test is equality, or a prefix followed by `/` (`/slack/eventsX` is not a match;
     `/hermes/` is a prefix). The bare root, `/slack/command` and `/slack/commands` are healthy today (capture 1) and
     must stay healthy.
   - `data` also carries `commands` (count), `event_url` (recorded, not judged), `token_expires_at` and `rotated_at`
     (which makes E3 visible without reading Keychain).
4. **Status.** Findings feed `_debounced("slack_app_config", True, threshold, state)`, which is `count > threshold`
   (`sensors.py:37`). With threshold 1 and the hourly cadence, the sensor is degraded on the second consecutive real
   check. No findings means healthy and resets the counter. Unknown covers: a missing item, `ok: false` (except
   `token_expired`/`invalid_auth`, which go to the rotation path when `may_rotate` is true), a network error, or a
   manifest without the expected keys. Unknown never moves the counter.
5. **Notification.** The correlator opens an incident only for 2 or more degraded sensors (`correlator.py:18`), and the
   pager pages only on unknown. So a lone degraded `slack_app_config` would reach no one. `bin/k3dm-hermes` gains a
   `_slack_config_notification(state, record, relay)`, called beside `_status_notification` (`:960-963`). It posts
   once through `post_summary` when the sensor turns degraded (`Hermes: Slack app setting wrong — <first finding>`)
   and once when it recovers, tracked in `state["slack_config"]["notified"]`. The incoming webhook does not depend on
   Interactivity, so the post still arrives when the setting it reports is broken.

**Sensor `slack_relay_reachable(probe, state, threshold=2)`.** `probe(url)` sends an unsigned `POST` with an empty
body, `User-Agent: k3dm-hermes/1`, and no `X-Slack-Signature` or `X-Slack-Request-Timestamp`, with a 5 s timeout. It
returns the HTTP status code (mapping `urllib.error.HTTPError` to its code) or raises on a timeout or connection error.
It probes `/slack/interactivity` and `/slack/commands`. If both return `401`, the sensor is healthy, with evidence
`relay deployed and verifying signatures`. Capture 3 showed that 401 proves deployment and the signature check, not
routing; routing is `slack_app_config`'s job. Any other code, a timeout or a connection error on either path is
raw-degraded, with the path and the code or `timeout`. Debounce threshold 2 means degraded on the third consecutive
failing poll. `data` carries the code for each path. There is no unknown state: a failed probe is the signal itself.

Both sensors are wired in `_run_cycle` after `alert_delivery` (`bin/k3dm-hermes:217`). Their transports sit next to
`_http_json` (`:80`). `_run_cycle` gains `may_rotate=False`, and `_poll_cycle` (`:919`) passes `True`. The Grafana
Hermes dashboard lists `hermes_sensor_status` generically
(`scripts/etc/argocd/platform-ops/grafana-dashboard-hermes.yaml:38-56`; series produced at `bin/k3dm-hermes:488-532`),
so it needs no change.

**Out of scope:**
- checking that Hermes posts from the relay's app;
- judging whether Event Subscriptions should go through the relay (capture 1 finding b);
- tidying the 13 non-canonical command URLs.

## What NOT to do

- Do not copy the relay's signing secret to the hub or sign any probe.
- Do not send a real button click, post anything to Slack, or call any Slack method other than
  `apps.manifest.export` and `tooling.tokens.rotate`.
- Do not write any Keychain item other than the two named; do not pass a token as a process argument.
- Do not treat an API error as healthy, and do not demand `/slack/commands` exactly.
- Do not edit `workers/slack-relay/index.js` or the Slack app settings.
