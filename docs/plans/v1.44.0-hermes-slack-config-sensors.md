## Goal

On 2026-11-08 three Hermes failures passed every offline test and were found only when the operator pressed a
button: the Slack app had Interactivity off, `/hermes-auth` pointed at the interactivity Request URL instead of the
commands one, and the cards were posted by a different app from the relay's. The first two are Slack app
*settings*. A probe sent straight to the relay skips Slack and cannot see them; only the app manifest can. This plan
adds two sensors that are silent on a healthy stack and degrade within a day of such a setting going wrong.

## Design

**Sensor `slack_app_config`.** Reads the relay app's manifest with `apps.manifest.export` and checks:

- `settings.interactivity.is_enabled` is true;
- `settings.interactivity.request_url` is `https://k3dm-slack-relay.k3dm.workers.dev/slack/interactivity`;
- every slash command Hermes depends on (`/hermes-auth` at least; the list is a constant in the sensor) has a `url`
  of `https://k3dm-slack-relay.k3dm.workers.dev/slack/commands`.

Degraded names the field that is wrong and what it should be, never a token. Runs at most once an hour (state
timestamp), because the manifest changes rarely. Unknown (not degraded) when the token is missing or the API call
fails, with the Slack error code (`invalid_auth`, `token_expired`…).

**Sensor `slack_relay_reachable`.** An unsigned `POST` to `/slack/interactivity` and to `/slack/commands` on the
relay must answer `401` within 5 s (`index.js:249` and `:378`: `verifySlack` fails with no signature). `401` means
the worker is deployed and routing; `404`, `5xx` or a timeout is degraded. No signing secret is used or stored.

Both follow the existing sensor shape (`record(...)`, `_debounced`, threshold 2) and are wired in `bin/k3dm-hermes`
next to `alert_delivery` (`bin/k3dm-hermes:217`).

**Out of scope:** checking that Hermes posts from the relay's app. The incoming-webhook URL does not carry an app id
the manifest can be matched against; this stays a manual check unless the proof below finds a way.

## External behaviour to prove before dispatch

CLAUDE.md requires proof from the real API before a spec that depends on it is dispatched. Claude captures, with
host, date and token type beside each, and stores the outputs here (token values redacted):

1. A real `apps.manifest.export` response for the relay app (app id from the Slack app config page), showing the
   exact JSON paths of `interactivity.is_enabled`, `interactivity.request_url` and `features.slash_commands[].url`.
   **Captured 2026-11-13 by the operator on m5-air.local (`apps.manifest.export`, app `k3d-manager` A0B863SCQUV,
   config token via stdin header; first try `invalid_auth` until the duplicate token pair was deleted and re-stored):**
   paths confirmed as `.manifest.settings.interactivity.{is_enabled,request_url}` (URL ends `/slack/interactivity`),
   `.manifest.settings.event_subscriptions.request_url` and `.manifest.features.slash_commands[].url`. Findings:
   (a) of 14 command URLs, 12 are the bare relay root, one is `/slack/command` (singular), one `/slack/commands`;
   all work today only because unmatched form POSTs fall through to the command handler (`index.js:346-378`). The
   sensor must therefore not demand `/slack/commands` exactly: it flags a command URL that is off the relay host or
   points at a named non-command route (`/slack/interactivity`, `/slack/events`, `/hermes/...`), which is the
   2026-11-08 `/hermes-auth` failure. (b) Event Subscriptions point at `https://webhook.3ai-talk.org/slack/events`,
   the webhook directly, not the relay; only `docs/plans/v1.6.0-slack-thread-commands.md` names it. Whether that is
   intended is an operator question; the sensor records the URL and reports it, it does not judge it.
2. Whether the config token expires and how it is refreshed (`tooling.tokens.rotate`). If it expires in hours, the
   sensor must rotate it and store the new pair, which makes Hermes a Keychain writer: that is an operator decision
   recorded here before dispatch, and the design above is amended.
   **Answered 2026-11-13 (operator screenshot of api.slack.com/apps, workspace DevOps Automation):** the access token
   shows "Expires in 12 hours" beside a separate refresh token, so the sensor must rotate. Operator decision on
   Hermes as a Keychain writer (limited to `k3dm-slack-config-token` and `k3dm-slack-config-refresh-token`):
   **approved by the operator 2026-11-13** ("go for your recommendation"). The spec must add: rotate writes both items
   (new refresh token first is not enough; a crash between `tooling.tokens.rotate` and the Keychain write must not leave
   a dead refresh token unnoticed, so the sensor reports unknown with a regenerate hint), no other Keychain item is
   written, and `## Contract readers` lists both items' writers. Both items stored on m5-air.local 2026-11-13 via the `security -w` prompt.
3. The unsigned-POST status codes from the live relay for both paths.
   **Captured 2026-11-13T01:26:27Z by Claude from m4-air.local (curl -X POST, no body, -m 5):** `/slack/interactivity`
   401 in 0.13 s, `/slack/commands` 401 in 0.07 s, and a control path `/slack/nope` **also 401**: in
   `workers/slack-relay/index.js:346-378` every POST that matches no named route falls through to the slash-command
   handler, which verifies the signature first. So 401 proves the worker is deployed and checking signatures, **not**
   that a path is routed; the sensor text above ("401 means ... routing; 404 ... degraded") over-claims, since a POST
   never gets 404. Wrong Request URLs are caught by `slack_app_config` (the manifest), not by this sensor. Spec to
   reword `slack_relay_reachable` accordingly and drop the 404 case for POST.

## Operator prerequisite

Create the Slack app configuration token and store it in Keychain through the usual prompt (never in chat or a
command line). Suggested item: `k3dm-slack-config-token` (and `k3dm-slack-config-refresh-token` if item 2 says it
rotates). New Slack config token: operator-approved 2026-11-08 by choosing this design.

## What NOT to do

- Do not copy the relay's signing secret to the hub or sign any probe.
- Do not send a real button click or post anything to Slack from a sensor.
- Do not treat an API error as healthy.
