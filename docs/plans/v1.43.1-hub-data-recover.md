## Why the 5-step runbook is not safe to automate as written

Read-only checks on the live hub, 2026-10-10:
- `deployment/postgres-keycloak` is owned by the ArgoCD Application `shopping-cart-identity`
  (namespace `cicd`, tracking id `shopping-cart-identity:apps/Deployment:identity/postgres-keycloak`).
  Auto-sync would put the replicas back while a claim is being replaced. `statefulset/vault` and
  `statefulset/openldap` are Helm-managed.
- `hub_data_restore` always applies `scripts/etc/dr/postgres-keycloak.yaml`, the **drill's** postgres
  (no password, built for a throwaway cluster). On the real hub that would replace the GitOps
  deployment.
- After `make hub-recover`, the restored Vault still holds the **old** cluster's
  `auth/kubernetes/config` (CA and reviewer JWT), so every ESO login fails. The in-cluster
  `vault-unseal` Secret, the `k3d-manager-vault-unseal` Keychain cache and the `vault-root` Secret
  all belong to the freshly initialised Vault, which no longer exists once its data is replaced.

## B0 — Non-negotiable safeguards (operator review, 2026-10-10)

| # | Safeguard | How This spec meets it |
|---|---|---|
| S1 | Explicit target validation | Context pin (D2) **and** cluster identity: the context's API server must be the local k3d load balancer of `K3DM_HUB_DATA_CLUSTER` (default `k3d-cluster`) — the `k3d-<cluster>-serverlb` container exists on this Mac and publishes the port in the context's `server` URL — and `k3d-<cluster>-server-0` must be running locally. The resolved context, server URL and node list are printed before approval. |
| S2 | Secure key handling | The age identity is read with `read -rs`, held in one shell variable, given to `age` only through a process substitution, and `unset` in the EXIT trap (success and failure). Never Keychain, file, argv, env of child processes, log or `set -x` (`_no_trace`). |
| S3 | Fail-fast and resumable | Every step writes a checkpoint `~/.k3dm/hub-recover/<run_id>/steps.jsonl` (`step`, `started`, `finished`, `rc`). `RESUME=<run_id>` continues from the first unfinished step. **Destructive steps (4 restore claims, 6 re-point Vault) are never repeated automatically:** if one started and did not finish, resume stops and requires `REDO_STEP=<n>` plus the approval again. |
| S4 | Backup validation | `_hub_data_verify_export` (D6: checksums, manifest equals directory, age headers) **plus compatibility:** the export's `inventory.json` gains `format: 2` and `images` (the running image of vault, postgres-keycloak and openldap at export time). Restore refuses when an image's **major** version differs from the target's, or when an expected claim is missing from `pv-pvc.yaml`. An export without `format: 2` is refused unless `K3DM_HUB_DATA_ALLOW_LEGACY_EXPORT=1`. |
| S5 | Data restoration proof | Counts are not proof. The export inventory (the v1.43.0 list-only login, policy widened to **`read` on `secret/metadata/*`**, still no access to secret data) gains `vault_keys`: every KV key path, recursively, with its `current_version`. Keycloak gains `keycloak_usernames_sha256` and LDAP `ldap_dns_sha256` (SHA-256 of the sorted list; no names stored). Verification compares all three exactly. No secret value is read at export or verify. |
| S6 | Production approval | Approval is typed at the TTY, not a make variable: after preflight prints the target (S1), the export, its age, and **live vs export** counts, the operator types the export timestamp. `hub-recover-all` asks once, before the rebuild, and the approval is recorded in the report. |

**One engine for the drill and the restore.** The drill and the real restore must use the same
code: restore (`hub_data_restore`), unseal (`hub_data_unseal_dr`) and **verify**
(`hub_data_verify`, moved from `bin/dr-drill` V1–V5 into `hub_data.sh`, extended with S5 and
V8). `bin/dr-drill` keeps only what is drill-specific: the throwaway cluster, V0 egress, V6
budget, V7 age. A test asserts `bin/dr-drill` defines no `_dr_drill_v1`…`_dr_drill_v5`.

**Stages and orchestrator.** `hub-recover` (rebuild + credentials, existing) and
`hub-data-recover` (data) stay independently runnable and tested; `hub-recover-all` is the
orchestrator. (The name `hub-restore` is taken by the existing Keychain credential restore, so it
is not reused.)

**Auditable report.** `~/.k3dm/hub-recover/<run_id>/report.json`: run id, host, operator
(`id -un`), k3d-manager commit, target (S1), export timestamp and `SHA256SUMS` digest, approval
time, each step with start/finish/rc, every check, and `rto_seconds`. Written on failure too.

## B1 — `hub_data_recover` (M4, Terminal.app, attended)

Steps, each logged as `[hub-recover] Step N/9 — …`; any failure stops, runs the EXIT cleanup and
exits non-zero:

1. **Preflight.** Interactive TTY (`[[ -t 0 ]]`); pinned hub context (D2) reachable; the three
   workloads exist; the chosen export (newest, or `K3DM_HUB_DATA_EXPORT=<ts>`) passes
   `_hub_data_verify_export`. Print the export timestamp and its age, then the S1 target, S4 compatibility and S6 approval. A wrong or empty
   approval exits 2 having changed nothing. Refuse on the M2 unless the context is `k3d-dr-drill`
   (`K3DM_HUB_DATA_RECOVER_ALLOW_DRILL=1`), so This spec can be rehearsed there.
2. **age identity.** Prompt with `read -rs` from the TTY; check it starts with `AGE-SECRET-KEY-1`
   without printing it; keep it in a shell variable only, and `unset` it on EXIT. It never goes to
   the Keychain, a file or argv. `_hub_data_restore_one` uses that variable when it is set, and the
   Keychain otherwise (the drill path is unchanged). This replaces runbook steps 2 and 4 (store the
   key in the M4 Keychain, then delete it).
3. **Pause ArgoCD** for `shopping-cart-identity` with the same mechanism `observability_pause`
   uses (`spec.syncPolicy.automated: null`, and whatever it does for ApplicationSet-generated
   apps). Resume in the EXIT trap, on success and on failure.
4. **Restore the claims** with `HUB_DATA_RESTORE_TARGET=hub`: identical to the drill restore,
   except `_hub_data_apply_keycloak` is **skipped** and the existing postgres-keycloak deployment is
   required instead. A test asserts the drill manifest is never applied in hub mode.
5. **Unseal** with the `k3dm-vault-unseal-dr` shards. Move `_dr_drill_wait_vault` and
   `_dr_drill_unseal` from `bin/dr-drill` into `hub_data.sh` as `_hub_data_wait_vault` and
   `hub_data_unseal_dr` (message prefix as an argument); `bin/dr-drill` calls them. Behaviour and
   messages stay the same; the existing dr_drill.bats tests must pass unchanged apart from the
   function names.
6. **Re-point Vault to the rebuilt cluster**, using a root token from `_hub_data_generate_root`:
   - rewrite `auth/kubernetes/config` exactly as `scripts/plugins/vault.sh` does at enable time
     (`token_reviewer_jwt` from the pod's service-account token, `kubernetes_host`,
     `kubernetes_ca_cert`);
   - replace the `vault-unseal` Secret and the `k3d-manager-vault-unseal` Keychain cache with the
     DR shards, through the existing writers in `vault.sh` (do not invent a new format);
   - store this root token as the `vault-root` Secret and its `k3dm-vault-root-token` Keychain
     mirror through the existing `hub_recovery.sh` mirror code. It is the hub's working root token
     from now on, so it is not revoked.
7. **Refresh dependents:** `rollout restart deployment/keycloak -n identity`, and annotate every
   ExternalSecret with `force-sync=<epoch>`.
8. **Verify on the hub:** V1 unsealed; V2 `hub_data_verify_vault_paths`; V3 Keycloak users and V4
   LDAP entries equal the inventory; V5 placement; **V8** no ExternalSecret reports
   `SecretSyncedError` five minutes after step 7. Print a table of the checks.
9. **Report:** write the B0 auditable report; resume ArgoCD (also done in the EXIT trap).

## B2 — Make targets

```make
## Restore hub data from the newest encrypted export (Terminal.app; approval typed at the prompt)
hub-data-recover:
	@./scripts/k3d-manager hub_data_recover

## Full hub disaster recovery: rebuild, credentials, then data (Terminal.app; approval typed at the prompt)
hub-recover-all:
	@$(MAKE) --no-print-directory hub-recover
	@$(MAKE) --no-print-directory hub-data-recover
```
`hub-recover-all` runs preflight and the S6 approval **before** `hub-recover`, so it never rebuilds
and then refuses.

## What NOT to do

- Do not read, print or generate the unseal shards, the age identity, any deploy key or any token.
- Do not apply `scripts/etc/dr/postgres-keycloak.yaml` to the real hub, ever.
- Do not grant the inventory policy anything beyond `list` on `secret/metadata/` and `read` on
  `secret/metadata/*`.
- Do not run the restore against the live hub; the operator does, in a window they pick.
- Do not create a PR, skip hooks (`--no-verify`), commit to `main`, or touch files not named here.
