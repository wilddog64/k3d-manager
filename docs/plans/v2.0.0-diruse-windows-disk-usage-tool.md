## Goal

**From one Windows node, see and free disk space across many machines**, with nothing installed on
them. One executable measures a local path, a UNC path or a list of them, shows the largest files
first, and helps free space, from a command line or a GUI.

The operator's stated intent (2026-11-06): "run from one node and allow to access multiple machines".
So `/file` is the main mode, not an extra, and every design choice below assumes remote targets first.

## Placement

  public release, so no winget or public packaging. It has no cluster, Bash or ArgoCD surface, so it follows the

## Test environments

| Stage | Where | Proves |
|---|---|---|
| Offline gate | `windows-latest` CI runner, private repo | Builds, unit and black-box tests |
| Daily development | Vagrant + Windows 11 ARM VM, on the M4 | GUI by eye, local paths, `\\localhost\c$` |
| Multi-node | Windows Server x64 on an ACG AWS sandbox: one central node, two or more targets | UNC, admin shares, unreachable nodes, fleet purge, real x64 |

- **Vagrant on the M4, not the M5.** The M5 has the room (32 GiB, 50% free, 800 GB disk; read
  2026-11-06), but it is the hub, and a Windows VM takes memory from its monitoring and public edge.
  The M4 has 24 GiB, 89% free, 161 GB disk and Vagrant already installed, and it is where agents run.
  The VM stays halted when not in use. The operator suggested the M5 as a maybe, so this can be reversed.
- **Vagrant provider: VirtualBox (operator, 2026-11-06).** VirtualBox 7.2 added Windows 11/Arm guests.
  The M4 has VirtualBox 7.2.22, which lists OS type `Windows11_arm64`, and Vagrant 2.4.9, reported to
  support 7.2 (read 2026-11-06). The M5 has neither. Two things
  are unproven:
  - Nothing found confirms Vagrant, VirtualBox and a Windows ARM guest working together end to end,
    and VirtualBox arm64 boxes are scarce. So expect to build a private box from Microsoft's Windows
    11 ARM64 ISO; that also avoids trusting a third-party image. M1 proves this first: boot, WinRM,
    a shared folder and `\\localhost\c$`.
  - The Windows licence for the VM is not settled.
  If VirtualBox fails that check, the fallback is `vagrant_utm`, already installed on the M4, then
  VMware Fusion with `apter-tech/vagrant-windows-11-arm64`.
- **ARM versus x64.** Apple Silicon runs Windows on ARM, where an x64 build runs under emulation.
  Company machines are presumably x64 Windows Server, so the VM is for fast iteration and ACG is the
  evidence that counts.
- **ACG is unconfirmed for Windows.** Pluralsight's docs list t2, t3, t3a and t4g up to medium and
  100 GB volumes, and say nothing about Windows AMIs. t4g is ARM, so use `t3.medium` as the existing
  ACG plugin does. M1's first task is a live probe: launch one Windows Server instance. If it is
  refused, multi-node testing falls back to two local VMs, and this plan comes back to the operator.
- **ACG rules.**
  - One agent per sandbox.
  - A sandbox lasts about 4 hours, so the fleet is rebuilt from a script each time.
  - Port 445 is open only between the nodes through a self-referencing security group, never to the
    internet; RDP only from the operator's IP.
  - Test accounts are throwaway.
- **Workgroup versus domain.** ACG nodes have no domain, and Windows filters local accounts on admin
  shares unless `LocalAccountTokenFilterPolicy` is set on the targets. A company domain account does
  not hit this, so ACG results do not prove domain behaviour. The first company run is its own check.
- **Agents.** They cross-compile on a Mac and cannot run Windows tests in their sandbox, so the CI gate
  must exist before the first feature spec.

## Stack

C# on .NET LTS with WinForms (operator, 2026-11-06), published as one self-contained x64 file.
The executable is large, which matters little for a private tool copied to one central node.

**One executable for both modes** means a console-subsystem build that detaches its console when
`/gui` starts. A GUI-subsystem build could not print to the calling shell.

## Command line

Every switch accepts `/name` and `--name`. The draft's `—` is read as an autocorrected `--`.

| Command | Meaning |
|---|---|
| `diruse -h`, `/help`, `help` | Usage |
| `diruse .` | Measure the current directory |
| `diruse D:\path` | Measure a local path; `D:\` measures the drive |
| `diruse \\node\d$\path` | Measure a UNC path |
| `diruse /file targets.txt` | Measure each target listed, one per line; blank lines and `#` comments are ignored |
| `/file targets.txt /summary` | Used, free and percent per volume, largest first, with no tree walk; takes seconds across a fleet |
| `/top N` | Rows to show; default 50 |
| `/timeout 30m`, `/parallel 4` | Limit per target, and targets scanned at once |
| `/json`, `/csv` | Machine-readable output |
| `/gui` | Open the GUI, on the given targets if any |
| `<target> /purge /top N /plan p.json` | Dry run: list what would be deleted, per node and in total, and save it |
| `/purge-plan p.json /confirm` | Delete exactly what the plan lists; add `/allow-multi` if it spans more than one node |
| `<single target> /purge /top N /confirm` | Shortcut for one target only; refused with `/file` |
| `/purge-list a.log,b.log` or `/purge-list @list.txt` | Build a plan from exactly these paths, then the same two steps |
| `<target> /threshold 85` | One check: exit 2 if the volume is at or above 85% used |
| `/file targets.txt /monitor /threshold 85 /interval 15m` | Repeat across all targets; alert on crossing, and on a node that cannot be reached |
| `/autopurge` | Last milestone only; see "Safety rules" |

**Exit codes:** 0 success, 1 failure, 2 threshold exceeded, 3 partial (some targets or directories
could not be read).

**Output.** A volume line (used, free, total, percent), the largest directories, then the largest
files, each sorted descending, with logical size and size on disk.

## GUI

1. Node list from `/file`: used percent per volume, largest first. A node that cannot be reached is
   shown as such, never left out.
2. Table: node, drive, file path, size, sorted descending. Sortable, filterable by node; multi-select.
3. Pie chart of used and free for the selected volume.
4. Preview pane on click:
   - Text: the first 1 MiB.
   - Images: rendered, with a size cap.
   - Anything else: a hex view.
   - Over SMB it reads only the capped bytes and can be cancelled.
   - Reads use the app's own viewer, never shell preview handlers.
5. Right-click menu:
   - **Delete:** moves to the Recycle Bin on a local path. A remote path has no Recycle Bin, so
     only the permanent action is offered there.
   - **Permanently delete:** also Shift+Delete.
   - **Edit in external editor:** a configured editor, Notepad by default. It never uses the shell's
     `open` verb, which would run a `.bat` or `.exe`.
6. Every delete prompts first, stating the node count, file count and total bytes. On a UNC path the
   prompt says the delete is permanent, which is the normal case for this tool.

## Scan correctness

- **Reparse points:** never followed, because junctions and symlinks create loops and double counts.
- **Unreadable directories:** counted and reported. The total is marked incomplete and the exit code
  is 3, never a silently low number.
- **Long paths:** handled with `\\?\`.
- **Sparse, compressed and hard-linked files:** size on disk comes from the file system. Hard links
  are counted once per volume.
- **Cloud placeholders:** OneDrive-style files are listed but never read, because a preview would
  download them.
- **Multiple targets:** bounded concurrency; one failed target does not stop the rest.
- **Credentials:** the current Windows token only. No password switch, ever. Use `net use` or run as
  another account. `d$` needs admin rights on each target, so the central node holds a powerful
  account; prefer a read-only account and plain shares for scanning, and an admin one only to delete.
- **Slow links:** a full tree walk over SMB can take a long time, so scans show progress, honour
  `/timeout`, and return partial results marked as partial. M1 measures this on ACG.

## Safety rules

Every spec that can delete inherits these as `must_not` items.

| Rule | Why |
|---|---|
| `/purge` refuses to run without a limit (`/top N` or `/min-size`) | The draft set no limit, so "largest files" had no end |
| Never touches `\Windows`, `\Program Files*`, `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`, `System Volume Information`, `$Recycle.Bin`, or a reparse point | The largest file on a Windows machine is often one of these |
| Deletes files only, never directories or a drive root | Bounds the damage of a wrong target |
| Re-checks size and modified time just before deleting; a changed file is skipped and reported | The dry run and the delete are separated in time |
| Any delete spanning more than one node needs a saved plan and `/allow-multi` | One flag must not delete across a fleet |
| Appends every delete to `%ProgramData%\diruse\purge-log.jsonl` on the central node: time, user, node, path, size, plan hash, result | Deletes on an admin share need a record |
| A confirmed delete works from the saved plan and never rescans | A rescan of a remote fleet would pick a different list from the one reviewed |
| One node failing does not stop the others, and the result reports each node | A partial fleet delete must be visible |

**`/autopurge`** is the riskiest feature here. With `/monitor` it deletes unattended, on a loop, and a
single `/confirm` becomes standing permission. On a server the largest files are often live databases,
VHDX images and active logs. So it ships last, and only with all of these required, none defaulted:

- `/purge-root <dir>`: the only tree it may touch.
- `/min-age <days>`: leaves recently written files alone.
- `/max-bytes <n>` per run.
- A stop as soon as usage is back under the threshold.
- A single target. `/autopurge` is refused with `/file`; fleet-wide automatic deletion would need its
  own later decision.

It needs its own operator go after the earlier milestones have seen real use. It may be dropped.

## Changes from the draft

| Draft | Change | Reason |
|---|---|---|
| `diruse .` measures the "drive path" | Measures the current directory | `D:\` already covers a drive |
| `/purge` removes "largest files" | Requires a limit | No limit means no bound |
| `/file-to-purge` takes a comma list or a file | `/purge-list`, with `@file` for a file | A bare argument could be either; one `@file` holds names containing commas |
| `/confirm` on the purge command itself | A saved plan for anything multi-node | A rescan could delete files nobody reviewed |
| `/file` is one option among many | The main mode; adds `/summary`, `/timeout`, `/parallel` and a node list in the GUI | The stated intent is one node reaching many |
| `/autopurge` needs only `/confirm` | Needs root, age and byte limits; ships last | Unattended deletion |
| `/threshold` and `/monitor` name no alert path | Exit code 2, console, Event Log, `/interval` | An alert needs somewhere to go |
| Shift+right-click deletes permanently | A menu item and Shift+Delete | Shift+right-click opens the Windows extended menu; Shift+Delete is the convention |
| Table has drive, path, size | Adds a node column | `/file` mixes machines |
| Preview shows "the file content" | Size caps, own viewer | Large, binary and cloud-placeholder files |
| Not mentioned | `/top`, `/json`, `/csv`, exit codes, audit log | Needed for large drives, scripting and accountability |

  Reconsider only if M1 shows full scans are too slow, since `/summary` and `/monitor` need no tree walk.

## Open before any company use

These do not block development. They block the first run on a company machine.

1. **Company approval.** Check the company's policy on outside software, who owns a tool built
   personally but used at work, and whether security must review it first.
2. **Code signing.** An unsigned tool deleting over admin shares will likely trip SmartScreen and
   endpoint protection. A company code-signing certificate or an allow-list entry is the likely answer.
3. **Accounts.** Which account the central node runs under, and whether scanning and deleting can use
   separate ones.
4. **Separation.** No company hostnames, target lists or data go in the repo, or to agents, or to ACG.
