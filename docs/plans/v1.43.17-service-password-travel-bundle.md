# v1.43.17 — Service passwords while travelling: an age-encrypted bundle only enrolled laptops can open

**Status:** PLANNED — operator asked for the spec 2026-11-07; dispatch when `k3d-manager-v1.43.17` is cut
**Priority:** P2 (after a rotation, a laptop away from home cannot read the new service passwords; SSO still works, so this is break-glass access)
**Approval:** operator 2026-11-07: "is there a secure way to send make show-service-passwords to me if I travel with my labtop and password rotation happened"; on option 2 (encrypted push): "yes, write a spec for option 2"
**Release:** v1.43.17 (branch `k3d-manager-v1.43.17`)
**Depends on:** none. Part of the travel goal (`project_travel_any_machine_goal`), which is otherwise only a design goal.

## Problem

`make show-service-passwords` (`Makefile`) works only on the hub. It reads the Vault root token from
`secrets/vault-root` through the `k3d-k3d-cluster` context and queries Vault at `127.0.0.1:18200`.
The credential rotators (ArgoCD, Grafana, Keycloak, LDAP, Prometheus basic auth) change those
passwords on a schedule. A laptop away from home has no copy of the new values and no way to fetch
them.

The passwords must never travel in plaintext. Slack, email, chat or a page that renders them can all
leak (operator, 2026-11-07: "the exception should not explore on the page ... that's security concern").

## Design

The hub publishes the `show-service-passwords` output **encrypted with `age` for each enrolled
laptop's public key**. Only a laptop holding the matching private key, kept in its Keychain, can
decrypt it. The file can therefore travel over a convenient channel: the delivery folder only ever
holds ciphertext.

### B1 — enrol a laptop (runs on the laptop)

- `make password-bundle-enroll` generates an age identity with `age-keygen`. The identity goes
  straight into the login Keychain as service `k3dm-password-bundle-age`, account `identity`, through
  the existing `_secret_*` helpers. It is never written to a file and never appears in argv.
- It prints only the public key (`age1…`) and the next step to run on the hub.
- If an identity already exists, it refuses unless `FORCE=1`. Replacing an identity makes every
  bundle encrypted for the old key unreadable.

### B2 — recipients (runs on the hub)

- `make password-bundle-add-recipient NAME=<laptop> KEY=<age1…>` and
  `make password-bundle-remove-recipient NAME=<laptop>` maintain
  `$K3DM_PASSWORD_BUNDLE_STATE_DIR/recipients` (default
  `${K3DM_STATE_DIR:-$HOME/.local/share/k3d-manager/state}/password-bundle`, the state root `argocd_upgrade` uses; directory mode 700, file mode 600; one line per laptop: `<name> <age1…>`).
- The name must match `^[a-z0-9-]{1,32}$`. The key must match `^age1[02-9ac-hj-np-z]{58}$` (bech32).
  Anything else is refused before the file is touched.
- Removing a recipient republishes at once (B3 with `FORCE=1`), so the next bundle is not readable
  with the removed key. The how-to states that a removed laptop can still read bundles it already
  downloaded, so passwords should be rotated after losing a laptop.

### B3 — publish (runs on the hub)

`make password-bundle-publish` (and the LaunchAgent in B4):

1. Runs `make -s show-service-passwords` and captures its output **in memory** (a shell variable or a
   pipe; never a temporary file).
2. Refuses to publish, keeping the last bundle, when the target exits nonzero or there are no
   recipients. In both cases it pushes `k3dm_password_bundle_publish_success 0`.
3. Compares a SHA-256 of the output with the hash stored in
   `$K3DM_PASSWORD_BUNDLE_STATE_DIR/last.sha256` (mode 600). If they are equal and `FORCE` is not set,
   it stops there and pushes success with no new bundle.
4. Otherwise it pipes the output to `age -e` with one `-r` per recipient, and writes
   `service-passwords.age` in the delivery folder atomically (a temp file in the same folder, then
   `mv`). The bundle is mode 600. Next to it, it writes `service-passwords.meta` in plain text:
   `generated_at`, `hub_host` and the recipient names. The meta file never holds a hash or any
   secret-derived value.
5. Pushes `k3dm_password_bundle_last_publish_timestamp`, `k3dm_password_bundle_last_change_timestamp`
   and `k3dm_password_bundle_recipients` through the existing Pushgateway path.

The delivery folder is `K3DM_PASSWORD_BUNDLE_DIR`. It defaults to
`~/Library/Mobile Documents/com~apple~CloudDocs/k3dm/password-bundle` (iCloud Drive; both the M5 and
the M4 have it, checked 2026-11-07). The folder must not be inside a git work tree: git history would
keep every old bundle forever. B3 refuses a folder for which `git -C <dir> rev-parse` succeeds.

### B4 — schedule (hub)

A LaunchAgent `com.k3d-manager.password-bundle` runs B3 every 15 minutes. It is installed by
`make password-bundle-install` and removed by `make password-bundle-uninstall`, following the
existing LaunchAgent install helpers. Only a change produces a new bundle, so iCloud syncs only when a
password actually rotated. The rotators stay unchanged: watching the output catches every rotation,
including ones added later.

### B5 — read it (runs on the laptop)

`make password-bundle-show` reads the identity from the Keychain and decrypts the bundle to the
terminal. The identity reaches `age -d -i` through process substitution, the same way as
`_hub_data_restore_one`. The plaintext is never written to disk. It prints `generated_at` from the
meta file first, and warns if that is more than 24 hours old.

### B6 — alert

The alert `PasswordBundleStale` fires when `time() - k3dm_password_bundle_last_publish_timestamp`
exceeds 2 hours, or when `k3dm_password_bundle_publish_success == 0` for 30 minutes. It uses the
existing email route. The alert text names the metric and the make target, never a password.

### Related, not in this plan

Tailscale (operator, 2026-11-07: "probably talescale is another option") would let the laptop run
`ssh <hub> make show-service-passwords` from anywhere: the pull option. It complements this plan but
does not replace it. It needs the hub awake and its home network up, and those are exactly the times
the bundle covers. It is a separate candidate for the travel goal.

## What NOT to Do

- Do not run any target against the hub, the LaunchAgent or the real Keychain. The operator runs the
  E2 and E3 evidence.
- Never write the plaintext output to a file, a log, `/tmp`, a Pushgateway label or the meta file.
  Never put a password, the identity or the hash in argv.
- Do not change `show-service-passwords` or any rotator.
- Do not add Slack, email or webhook delivery of the bundle or its contents.
- Tests use a scratch `HOME`, `K3DM_PASSWORD_BUNDLE_STATE_DIR` and `K3DM_PASSWORD_BUNDLE_DIR`, a stub
  `show-service-passwords`, a stub `security`, and the Pushgateway at `127.0.0.1:9`. A fixture first
  asserts that it points at the scratch paths. The stub `security` output comes from a real
  read-only capture, with the host and date beside it. `age` and `age-keygen` are the real binaries.
- Write the must_not tests first and show them red on the pre-fix tree.
- Do not edit CLAUDE.md, `memory-bank/` or `docs/roadmap.md`. Do not commit to `main`, create a PR or
  skip hooks.
