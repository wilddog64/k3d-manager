# v1.44.0 — Authenticated cloud-request submitters

**Status:** PROPOSED — enhancement specification; no runtime changes
**Owner:** cloud-bridge security and automation maintainers
**Motivation:** The current pull-based bridge treats write access to the `cloud-requests`
branch as sufficient to submit a request. A GitHub connector belonging to an agent can therefore
enqueue any request that passes schema validation, even when that agent was not intentionally
authorized to invoke the cloud bridge.

## Problem statement

The cloud bridge polls an orphan GitHub branch. Any principal able to push to that branch can
create a valid request file. `requested_by` is currently an unsigned descriptive field, so it is
not reliable attribution. The bridge does enforce action and argument allowlists and uses separate
reader/cloud-runner tokens, but those controls authorize the request *after* branch submission;
they do not authenticate which agent submitted it.

The existing branch-write model should remain available during migration, but it must not be the
long-term authorization boundary for privileged cloud actions.

## Goals

- Authenticate the submitter independently of GitHub account or connector write access.
- Bind each request to a named agent identity and a bounded capability set.
- Preserve the current action, argument, expiry, size, token-role, and output-redaction controls.
- Reject forged, modified, replayed, expired, and revoked requests before webhook execution.
- Support key rotation and immediate revocation without rewriting request history.
- Provide useful, non-secret audit metadata for accepted and rejected requests.
- Keep the orphan branch architecture and asynchronous request/response workflow.

## Non-goals

- Treating GitHub commit author, committer, or account name as sufficient authentication.
- Giving agents direct webhook tokens or arbitrary Slack/channel permissions.
- Expanding the set of cloud actions or changing their existing role requirements.
- Making the cloud-request branch private-data storage; requests and responses remain subject to
  the repository's existing read-access and retention model.
- Proving the identity of an agent whose private signing key has been compromised.

## Proposed design

### 1. Signed request envelope

Keep the existing request fields and add a signed authentication envelope. The signed payload must
be canonical JSON with deterministic key ordering and no insignificant whitespace:

```json
{
  "schema": 2,
  "request": {
    "id": "20261007T120000Z-make-test-all",
    "action": "make-test-all",
    "args": {},
    "requested_by": "codex-cloud",
    "requested_at": "2026-10-07T12:00:00Z",
    "expires_at": "2026-10-07T12:30:00Z"
  },
  "auth": {
    "key_id": "codex-cloud-2026-10",
    "signature": "base64url-ed25519-signature"
  }
}
```

The signature covers the complete `request` object, including action, arguments, identity, request
ID, and expiry. The bridge must verify the canonical bytes before parsing or executing the request.
It must not accept a signature over a subset of fields.

Ed25519 is the preferred algorithm: the bridge stores only public verification keys, while each
approved agent holds its private key outside the repository. The algorithm and signature encoding
must be explicit in the contract so an implementation cannot silently downgrade verification.

### 2. Agent registry and capabilities

Maintain a server-side registry mapping `key_id` to:

- public verification key;
- stable agent identity;
- allowed capability class, such as `reader` or `cloud-runner`;
- creation, expiry, and revocation state.

The registry must not live on the writable `cloud-requests` branch. It belongs in the webhook's
operator-controlled configuration or a protected secret/configuration store. A key is authorized
only when its identity, validity window, and capability class are active.

The bridge intersects the agent capability with the existing action allowlist. A signed
`cloud-runner` request still cannot invoke an action outside the cloud-runner allowlist, and a
reader key cannot gain lifecycle or E2E permissions by changing JSON fields.

### 3. Replay and freshness protection

- Require a unique request ID matching the existing format.
- Reject duplicate IDs even if the signature is valid.
- Require `requested_at` within a bounded clock-skew window.
- Require `expires_at` after `requested_at` and no later than the configured maximum TTL.
- Record the authenticated key ID and request ID in the processed ledger.
- Consume IDs for rejected, expired, and invalid-signature requests so they cannot be retried
  indefinitely under the same identifier.

The bridge must use its own clock for expiry and must not trust a client-provided status or result.

### 4. GitHub access reduction

After signed requests are deployed, reduce the cloud-session GitHub token to the minimum branch
write scope needed by the approved submitter mechanism. The bridge's response writer remains a
separate identity from request submitters where practical. Branch write access is treated as a
transport capability, not authorization.

If GitHub Apps are used, record the installation identity for audit only; do not use commit metadata
as a replacement for request signatures. A compromised GitHub token must not be able to forge an
authorized request without also obtaining the corresponding private signing key.

### 5. Migration modes

Provide explicit modes:

- `audit`: accept legacy unsigned requests but log that they are unauthenticated; accept signed
  requests normally;
- `signed-privileged`: require signatures for lifecycle, E2E, and any future mutating action while
  allowing legacy reader requests during migration;
- `required`: require valid signatures for every cloud request.

The mode must be operator-controlled, visible at bridge startup, and included as redacted health
metadata. The final release default should be `required`; legacy fallback must not be indefinite.

## Failure and audit behavior

Return stable rejection reasons such as `missing signature`, `unknown key`, `invalid signature`,
`revoked key`, `capability denied`, `request expired`, and `request replayed`. Do not include public
key material, signature bytes, private paths, or secret configuration in responses.

For every request, record bounded metadata: request ID, action, authenticated key ID or `unknown`,
validation outcome, rejection reason, and timestamp. Store no raw private key and no full request
body in logs beyond the existing sanitized request artifact policy.

## Test plan

Add focused tests for:

1. valid signature over canonical request is accepted;
2. changed action, argument, identity, or expiry invalidates the signature;
3. unknown, revoked, expired, and not-yet-valid keys are rejected;
4. unsigned legacy behavior matches each migration mode;
5. a valid reader signature cannot invoke cloud-runner actions;
6. duplicate request IDs are rejected after success, rejection, and expiry;
7. clock skew and maximum TTL are enforced;
8. malformed encodings, unsupported algorithms, oversized envelopes, and duplicate JSON keys are
   rejected deterministically;
9. request metadata contains key ID and outcome but no signature or secret;
10. response writing and existing action/argument validation remain unchanged.

Mutation checks should prove that removing signature verification, capability intersection,
revocation checks, or replay tracking makes the focused suite fail.

## Rollout and acceptance

1. Generate separate signing keys for the approved local CLI and cloud agents; store private keys
   outside GitHub and publish only public keys to the protected bridge configuration.
2. Deploy `audit` mode and measure legacy versus signed submissions without executing new actions.
3. Move privileged actions to `signed-privileged`; verify unsigned lifecycle/E2E requests are
   rejected before webhook execution.
4. Move all actions to `required`; verify an approved signed `make-test-all` still completes and
   reports its authenticated submitter alias.
5. Revoke one test key and confirm its new request is rejected while previously accepted jobs keep
   their original audit identity.
6. Rotate a key without downtime and verify both the documented overlap window and final revocation.
7. Remove legacy unsigned submission from the helper and update the cloud-request guide.

## Open decisions

- Where should the protected public-key registry live: LaunchAgent configuration, Vault, or a
  dedicated versioned security repository?
- Should the bridge accept one key per named agent, one key per organization, or both with scoped
  capabilities?
- Should signature verification be implemented in the CLI helper, a reusable library, or both?
- What is the approved overlap duration for key rotation and migration from unsigned requests?
