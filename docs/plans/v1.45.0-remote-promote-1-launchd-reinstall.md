## Problem

`make hub-deploy REF=` (`bin/k3dm-hub-deploy`) is the one promote command, but the rules still teach the three-step path. The command
also does not refresh the hub's launchd agents when a plist template changes. After a promote, the hub runs new scripts under old agent
settings until someone remembers to run `make install-<agent>`.

v2 kept a single "last reconciled sha". Round 2 found that v2 could still lose work, in these cases:

1. **First run.** The base falls back to `old` because no marker exists yet. If an install fails, the rerun has `old == new`, so the diff
   is empty and the install is never retried (Astra 7, Fable 16).
2. **Partial success, then a revert.** X installs from B and Y fails. Commit C then reverts X's template to A. The net `A..C` diff omits X,
   but X's plist still carries B (Astra 7).
3. **One failing name pins the base.** Every later run reinstalls every other changed agent too (Fable 18).
4. **HEAD and clean-tree samples are not a binding.** Repo-sync can move the checkout between the sample and the read inside `make` (Astra 8).
5. **The mtime check is too weak.** "mtime at or after start" proves neither a rewrite nor a load (Astra 8, Fable 27).
6. **The platform-ops pin breaks existing tests.** The stub `make` never writes the marker the pin reads (Fable 17).
7. **The PID-directory lock is unsafe.** It races, and PID reuse can block it (Astra 9, Fable 27).
8. **`stat -f %m` is not portable.** It fails where GNU coreutils comes first on `PATH` (probe below).

**This part is an honest-path correctness property, not an O2 control.** The hub user can write `~/Library/LaunchAgents` and the checkout
directly. Nothing here defends against a same-user attacker. The goal is that an honest `hub-deploy` never leaves agents stale and never
forgets a failed reinstall.

## Behaviour

1. **One promote command in the rules.** These places say `make hub-deploy REF=<commit-ish>` instead of the three-step path:
   - `CLAUDE.md:25`;
   - the bullet at `docs/process/rules.md:83-93`, under the heading at `:81`;
   - `:95`, the paragraph after that bullet.

   The bullet lists what the command does: typed confirmation, tag, appsets-reapply only when ApplicationSets changed, `appsets-check`,
   `platform-ops`, rollout check, and launchd reinstall of changed installed agents. The three targets stay documented as the manual
   fallback in `docs/process/rules.md` and `docs/howto/hub-promote.md`. `CLAUDE.md` stays one bullet with one `[more]` link.
   `AGENTS.md` and `GEMINI.md` are not edited, because this is not a shared block; `bin/k3dm-check-agent-docs` must still pass.
2. **Howto.** "Everyday promote" at `docs/howto/hub-promote.md:24-36` gains one sentence: after `platform-ops`, changed launchd agents
   that are already installed on this host are reinstalled from a checkout locked at the promoted commit; one that could not be reinstalled
   is reported pending and retried by the next `bin/k3dm-hub-deploy <ref>` run, including a rerun of the same ref. Add nothing about
   approvals; Parts 2c and 2b own that wording.
3. **Makefile help.** `Makefile:2351` becomes
   `make hub-deploy REF=...    Promote, reconcile and verify the hub (typed confirmation required; reinstalls changed launchd agents)`.
   This is the only Makefile edit in this part.
4. **State file.** The path is `$HOME/.local/share/k3d-manager/hub-deploy/state`.
   - Modes: directory 0700, file 0600.
   - Writes are atomic: write `state.tmp.$$`, then `mv` it into place.
   - The file holds only lines from this grammar:
     - `appsets <40-hex>`: the last sha whose ApplicationSet changes are reconciled.
     - `launchd <40-hex>`: the last sha whose template changes are resolved or recorded as pending.
     - `launchd full`: a full reconcile is owed.
     - `pending <x>`: zero or more lines, `<x>` matching `^[a-z0-9-]+$`.
   - The file is unreadable if any line falls outside the grammar, or if a 40-hex value fails
     `git -C "$REPO_ROOT" cat-file -e "<sha>^{commit}"`. An unreadable file is treated as absent and reported as
     `hub-deploy: state unreadable; full launchd reconcile owed; appsets base <old7>`.
5. **Persist before the move.** After the lock (Behaviour 12) and the `old` read (`bin/k3dm-hub-deploy:29-31`), and before the promote
   call (`:32`), the script fills in missing values:
   - a missing `appsets` value becomes `appsets <old>`;
   - a missing `launchd` value becomes `launchd full`;
   - `pending` lines are kept.

   A failure anywhere later therefore leaves a base that still owes the work.
6. **ApplicationSets diff base.** The diff at `bin/k3dm-hub-deploy:42` uses the state's `appsets` sha instead of `old`. The value moves to
   `appsets <new>` only after the reapply exited 0, or after an empty diff. A failed reapply leaves it unchanged, so a rerun with
   `old == new` reapplies again. Messages and existing exit behaviour are unchanged. Existing `M1`, `M2` and `M4`
   (`scripts/tests/bin/hub_deploy.bats:93-126`) stay green: their fixture HOME has no state, so the base is `old`, as today.
7. **launchd candidates.**
   - With `launchd <sha>`, the candidates are the short names from
     `git -C "$REPO_ROOT" diff --no-renames --name-only --diff-filter=AM "<sha>" "$new" -- scripts/etc/launchd/`, plus every `pending`
     name.
   - With `launchd full`, the candidates are every name in the table below.
   - The diff runs through `_run_command --soft`. A diff error stops at step `launchd-diff` with git's exit code, through `stop`
     (`bin/k3dm-hub-deploy:9`).
   - A pending name whose template no longer exists at `$new` is dropped with `hub-deploy: launchd <x> template removed; dropped`.
8. **Eligibility, per candidate `<x>`.** `<x>` is the part between `com.k3d-manager.` and `.plist.tmpl`.
   1. `webhook-token-rotate`, `dispatch-stall-watch` and `dispatch-metrics` are excluded. The step prints
      `hub-deploy: launchd <x> is excluded from automatic reinstall (scripts/etc/machine/not-installed.list); skipping`, and the name is
      resolved. The token rotator rotates shared secrets, and `not-installed.list:8` says the operator installs it only after cutover, so
      `hub-deploy` never reloads it on its own (Fable 27).
   2. A name with no row in the table prints `hub-deploy: launchd template <x> changed; no install target is wired`, and is resolved.
      In `full` mode only table rows are candidates, so this case cannot arise there.
   3. If `$HOME/Library/LaunchAgents/com.k3d-manager.<x>.plist` is absent, the step prints
      `hub-deploy: launchd <x> is not installed on this host; skipping`, and the name is resolved. In `full` mode absent plists are
      counted silently instead.
   4. Otherwise the agent is installed (Behaviour 10).
9. **Step order.** The launchd step runs after the rollout check (`bin/k3dm-hub-deploy:62-64`) and before the summary (`:66`). It runs only
   after the promote returned 0, the role gate passed and the pin (Behaviour 13) held.
10. **Install under the checkout lock.** This runs only when at least one candidate reached 8.4.
    1. **Take repo-sync's lock.** The step takes repo-sync's own lock, `$HOME/.local/share/k3d-manager/repo-sync/lock`
       (`bin/k3dm-repo-sync:15`, `:17`): `mkdir`, write the script's `$$` to `lock/pid`, then read `lock/pid` back and require it to
       equal `$$`.
       - If the directory already exists and repo-sync's staleness rule does not apply (`:35-52`: mtime older than 180 s, or a dead pid),
         the step waits.
       - While the step holds the lock, repo-sync prints `already running` and exits 0 without touching the checkout (`:339-350`).
    2. **Check the checkout under the lock.** Two conditions must hold: `git -C "$REPO_ROOT" rev-parse HEAD` equals `$new`, and
       `git -C "$REPO_ROOT" status --porcelain --untracked-files=no` prints nothing.
       - If either fails, the step releases the lock, polls every 10 s, and waits at most `K3DM_HUB_DEPLOY_CHECKOUT_WAIT` seconds
         (default 330; bats sets 0). The lock is released between polls because repo-sync must run to catch up.
       - On timeout, every remaining name is pending:
         `hub-deploy: launchd <x>: hub checkout is not at <new7> with a clean tracked tree; pending; rerun bin/k3dm-hub-deploy <ref>`.
    3. **Before each install, still under the lock:**
       1. `touch` the lock directory, so repo-sync's 180 s staleness rule does not fire;
       2. re-read `lock/pid` and require `$$`; if it differs, the name is pending;
       3. require `git -C "$REPO_ROOT" hash-object scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl` to equal
          `git -C "$REPO_ROOT" rev-parse "$new:scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl"`, which binds the template bytes to
          the promoted commit;
       4. record `pre="$(/usr/bin/stat -f '%Fm %i' "$plist")"`.
    4. **Run the target:** `make --no-print-directory -C "$REPO_ROOT" <target>`, through `_run_command --soft`.
    5. **Verified** requires all four:
       1. the target exited 0;
       2. HEAD is still `$new` and the tracked tree is still clean;
       3. `/usr/bin/stat -f '%Fm %i'` of the plist differs from `pre`. This is a fractional mtime plus the inode, compared for
          inequality, so a future-dated or same-second plist cannot pass;
       4. `launchctl print "gui/$(id -u)/com.k3d-manager.<x>"` exits 0, proving the label is loaded. This is a read-only call that
          `bin/launchd-reload:13` already relies on.
    6. **Otherwise pending**, with exactly one reason:
       - `install failed (exit N)`;
       - `checkout moved during install`;
       - `plist not rewritten`;
       - `plist written but not loaded`. This includes `K3DM_AGENT_LOAD=0`, which `Makefile:73-74` honours.

       The message is `hub-deploy: launchd <x> <reason>; pending; rerun bin/k3dm-hub-deploy <ref>`. All retry text comes from one
       function, `retry_hint`, which Part 2b extends with `--approval <id>`.
    7. **Release.** A trap on exit releases the lock, but only while `lock/pid` still equals `$$`. No hand `make install-*` command is
       ever printed.
    8. **`stat` by absolute path.** `/usr/bin/stat` is called by its absolute path, because GNU `stat` rejects `-f %m` (probe below).
11. **Advance per name.** After the loop, one atomic write sets the state to `launchd <new>` plus one `pending <x>` line per name still
    pending.
    - Resolved names leave the pending set.
    - The next run diffs from `new` and also retries the pending names.
    - A name that fails every time stays listed without pinning the others.
12. **One run at a time.** After the role gate (`bin/k3dm-hub-deploy:17-19`), the script runs:

    ```sh
    exec 9>>"$STATE_DIR/run.lock"
    /usr/bin/lockf -s -t 0 9
    ```

    This is a kernel `flock(2)` lock held for the life of the process. There is no stale file, no PID reuse, and no window between taking
    the lock and recording the owner.
    - `lockf` exit 75 (`EX_TEMPFAIL`; probe below): print `hub-deploy: another run is active` and exit 75.
    - Any other non-zero exit: stop at step `run-lock` with that code.
13. **Downstream pin.** After the `platform-ops` step (`bin/k3dm-hub-deploy:56-60`) and before the rollout check, the script compares
    `$HOME/.local/share/k3d-manager/repo-sync/deployed-platform-ops` with `$new`. That file is written at `Makefile:1398`, from the fetch at
    `:1393`.
    - The pin applies on every run, including one with an empty appsets diff.
    - On a mismatch or an unreadable file, the script prints `hub-deploy: platform-ops applied <got7>, expected <new7>` and stops at step
      `platform-ops-pin` with exit 75.
    - The file's second reader, `bin/k3dm-repo-sync:403`, is unchanged.
14. **Exit 75 means one thing.** `hub-deploy` exits 75 only when nothing was refused and the same command can safely be rerun: the run
    lock is held, or a concurrent move broke the pin. Part 2b maps the same code to "approval kept or already consumed; rerun".
15. **Soft otherwise.** A pending reinstall never changes the exit status and never stops an earlier step.
    - The summary line (`bin/k3dm-hub-deploy:66`) gains `; launchd skipped|ran|pending <N>`.
    - When `N > 0`, the script also prints `hub-deploy: launchd pending: <x> <y>` on stderr.
    - The substring `reapply ran; appsets-check ok; platform-ops ok; exporter rolled out` stays intact
      (`scripts/tests/bin/hub_deploy.bats:97`).
16. **Test fixture, same file.** The stub `make` at `scripts/tests/bin/hub_deploy.bats:55-61` behaves like the real `platform-ops`
    (`Makefile:1393-1398`): for target `platform-ops` it writes the `ls-remote` sha of the fixture origin's `refs/heads/deploy/hub` to
    `$HOME/.local/share/k3d-manager/repo-sync/deployed-platform-ops`.
    - Existing `M1`-`M4` and `N1`-`N3` then stay green, including `M3` (`:111-117`), where `deploy/hub` stays at BASE.
    - A stub `launchctl` goes first on `PATH` and answers `print` from a per-label file under the scratch HOME.

## Residuals (named, honest path only)

- **R1-a.** A same-user edit of the checkout between the template-blob check and the read inside `make` can change the render. Helpers
  inside `make` are also read from the worktree, for example `bin/launchd-reload` (`Makefile:770`). The lock stops repo-sync, the only
  automated writer. It does not stop the operator or another same-user process. This is not an O2 control (see Problem).
- **R1-b.** An install that runs longer than 180 s may let repo-sync declare the lock stale and take it. The check after the install then
  reports `checkout moved during install` if the checkout changed.
- **R1-c.** `webhook-log-level` (`Makefile:668`) rewrites the webhook and cloud-bridge plists. If it runs during an install, the mtime check
  passes without the target's bytes. The load check still applies.
- **R1-d.** A failed appsets reapply from before this part existed cannot be recovered, because that history is unknown. After the first
  v3 run, the persisted `appsets` base covers the case.

## Proof of external behaviour

Local read-only probes, m4-air, macOS 26.5.2, `/usr/bin/git` 2.50.1, 2026-11-18 (2026-11-19 04:38 UTC):

- **Rename and delete handling.** `git diff --no-renames --name-only --diff-filter=AM` lists a renamed template as an added name and omits
  a deleted one. This is the same capture v1 recorded.
- **`stat`.** The `stat` on `PATH` is GNU coreutils (`/opt/homebrew/opt/coreutils/libexec/gnubin/stat`), and `stat -f %m` fails there
  with "cannot read file system information". `/usr/bin/stat -f %Fm` printed `1795055042.944412820`, a fractional mtime.
- **`lockf`.** While one shell held the lock, `/usr/bin/lockf -s -t 0 9` on fd 9 in a second shell exited 75. After the first shell
  exited, the lock was free again (rc 0). `/usr/bin/flock` does not exist; `/usr/bin/lockf` and `/usr/bin/shlock` do.
- **`launchctl print`.** Not run here (brief: no launchctl). Its exit code as a load probe is already relied on at `bin/launchd-reload:13`.

Proof owed, none blocking dispatch: confirm on the hub that `/usr/bin/lockf` and `/usr/bin/stat -f '%Fm %i'` behave the same. The hub runs
the same macOS base system, so this is expected.

## What NOT to do

- Do not run `make install-*` from a `git archive` directory. That bakes a deleted path into a plist (`Makefile:72`).
- Do not edit the install targets, `bin/k3dm-repo-sync` or `bin/launchd-reload`.
- Do not print a hand install command. Do not install the three excluded agents.
- Do not edit `AGENTS.md`, `GEMINI.md`, `bin/k3dm-hub-promote` or anything about approvals.
- Do not call bare `stat` or `flock`.
