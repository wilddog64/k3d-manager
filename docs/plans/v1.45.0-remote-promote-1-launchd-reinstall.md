## Problem

`make hub-deploy REF=` is the one promote command (`bin/k3dm-hub-deploy`), but the rules still teach the three-step path, and the command
does not refresh the hub's launchd agents when a plist template changed. After a promote the hub runs new scripts under old agent
settings until someone remembers `make install-<agent>`.

The 2026-11-15 outline said hub-deploy already reinstalls agents; it does not. A first draft of this part (umbrella, 2026-11-18) had
four defects that the blind review confirmed, and this spec fixes each:

1. the `install-*` targets render the plist from the working tree (`$$(pwd)`), and `hub-deploy` only moves `origin/deploy/hub`; the hub
   checkout follows on the next 5-minute repo-sync, so a reinstall straight after the promote installs the old template;
2. it installed agents the hub deliberately skips (`scripts/etc/machine/not-installed.list:2` token rotator, `:38-41` dispatch agents);
3. a failed reinstall vanished on the rerun, because the rerun has `old == new` and an empty diff, and a launchd failure stopped the run
   before `appsets-check` and `platform-ops`;
4. its test stubbed `make`, so it could not tell which bytes were installed.

## Behaviour

1. **One promote command in the rules.** `CLAUDE.md:25` and `docs/process/rules.md:84-86` and `:95` say
   `make hub-deploy REF=<commit-ish>` (typed confirmation, `hub-promote/<UTC>` tag, appsets-reapply only when ApplicationSets changed,
   `appsets-check`, `platform-ops`, exporter rollout, launchd reinstall of changed agents) instead of the three-step path. The three
   individual targets stay documented as the manual fallback, in `docs/process/rules.md` and in `docs/howto/hub-promote.md:38` onward.
   `CLAUDE.md` stays one bullet with one `[more]` link. `AGENTS.md` and `GEMINI.md` are not edited (the promote rule is not in a shared
   block; `bin/k3dm-check-agent-docs`, run by `make test-pytest`, must still pass).
2. **Howto sentence.** `docs/howto/hub-promote.md:32-36` ("Everyday promote") gains one sentence: changed launchd agents that are already
   installed on this host are reinstalled after `platform-ops`; one that could not be reinstalled is listed as pending and retried by
   the next `make hub-deploy` run (also the rerun of the same REF); the printed hand command is the fallback. Nothing about approvals
   (those come in Part 3).
3. **Makefile help.** `Makefile:2351` becomes `make hub-deploy REF=...    Promote, reconcile and verify the hub (typed confirmation required; reinstalls changed launchd agents)`.
   This is the only Makefile edit in the whole plan (Part 2b does not touch the Makefile, so the file has one owner).
4. **The step.** `bin/k3dm-hub-deploy` gains function `launchd_pending_add` and function `launchd_reinstall`, a fixed label-to-target
   table, and a state file. Names, all inside the script:
   - state file `$HOME/.local/share/k3d-manager/hub-deploy/launchd-pending` (directory mode 0700, file mode 0600, one short name per
     line, sorted unique; the pattern of `Makefile:1398` writing under `$(HOME)/.local/share/k3d-manager/repo-sync`);
   - short name `<x>` is the part of the template file name between `com.k3d-manager.` and `.plist.tmpl`; the installed plist is
     `$HOME/Library/LaunchAgents/com.k3d-manager.<x>.plist` (the path every install target writes, e.g. `Makefile:72`).
5. **Record before anything can fail.** Immediately after `new` is read (`bin/k3dm-hub-deploy:39-41`) and before the ApplicationSets
   step, `launchd_pending_add` runs
   `git -C "$REPO_ROOT" diff --no-renames --name-only --diff-filter=AM "$old" "$new" -- scripts/etc/launchd/`
   through `_run_command --soft` and appends each `scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl` as `<x>` to the state file.
   `--diff-filter=AM` skips deleted templates; `--no-renames` makes a renamed template show as an added one (captured below: without
   it the renamed name is missing from the AM list). A diff error stops the run at step `launchd-diff` with the git exit code through
   the existing `stop` (`:9-13`), before anything beyond the promote moved. When `old == new` the diff is empty and nothing is added
   (the pending file may still hold earlier names).
6. **The reinstall, after `platform-ops` and the exporter rollout check, before the summary line.** `launchd_reinstall` reads the state
   file and for each name `<x>`:
   1. no row in the table below: print `hub-deploy: launchd template <x> changed; no install target is wired; reinstall it by hand`
      and drop `<x>` from the file (nothing can ever retry it);
   2. plist `com.k3d-manager.<x>.plist` absent under `$HOME/Library/LaunchAgents`: print
      `hub-deploy: launchd <x> is not installed on this host; skipping` and drop `<x>`. This is what keeps the token rotator, the dispatch
      agents and every other not-installed agent off the hub;
   3. template check: `git -C "$REPO_ROOT" archive "$new" -- scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl | tar -x -C "$tmp"` into
      a `mktemp -d` directory, removed on exit, then `cmp` of that file with the same path in `$REPO_ROOT`. Different bytes (the hub
      checkout has not caught up to `$new`): do not install; keep `<x>` in the file and print
      `hub-deploy: launchd <x>: hub checkout template is not at <new7> yet (repo-sync advances it within 5 minutes); pending; run make hub-deploy REF=<ref> again, or by hand: make install-<target>`;
   4. same bytes: run `make --no-print-directory -C "$REPO_ROOT" <target>` through `_run_command --soft`. Exit 0: drop `<x>`. Non-zero
      `N`: keep `<x>` and print `hub-deploy: launchd <x> install failed (exit N); pending; run by hand: make install-<target>`.
   Why the template is compared instead of rendered from the archive (this departs from the operator's P2 wording "from an archive of
   `$new`"): every install target writes the checkout path into the plist (`$$(pwd)` at `Makefile:72`, `:91`, `:110`, `:148`, `:708`,
   `:720`, `:733`, `:749`; `$(CURDIR)` at `:883`), so running the target from a temporary archive directory would bake a deleted
   directory into a LaunchAgent. Comparing the archived template with the one the target will read proves the installed bytes come from
   `$new` and keeps the runtime path durable. Flagged for confirmation under Open questions.
7. **Soft.** A pending, skipped or failed reinstall never changes the exit status of `hub-deploy` and never stops `appsets-check`,
   `platform-ops` or the rollout check (they ran before). After the loop the script prints the one summary line (`:66`) extended with
   `; launchd <state>` where state is `skipped` (state file empty at the start of the step), `ran` (every listed name resolved, dropped or
   installed) or `pending <N>` (N names remain), and when `pending` it also prints
   `hub-deploy: launchd pending: <x> <y>` to stderr. The existing substring `reapply ran; appsets-check ok; platform-ops ok; exporter rolled out` stays
   intact (`scripts/tests/bin/hub_deploy.bats:97`). When the step had nothing to do it prints
   `launchd templates unchanged between <old7> and <new7>; skipping reinstall`.
8. **Rerun safety.** Because step 5 records before `appsets-reapply`, `platform-ops` or the rollout check can stop the run, the rerun
   (`old == new`, the existing already-current path, `scripts/tests/bin/hub_deploy.bats:111`) still finds the names in the state file and
   does step 6. A failure at `platform-ops` therefore does not lose a changed template.
9. **Role gate and order unchanged.** The role check (`:17-19`) still runs first; the diff, the state write and the reinstall never run
   before the promote step returned 0.
