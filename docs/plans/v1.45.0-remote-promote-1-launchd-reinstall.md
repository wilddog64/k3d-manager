## Problem

`make hub-deploy REF=` (`bin/k3dm-hub-deploy`) is the one promote command, but the rules still teach the three-step path. The command
also does not refresh the hub's launchd agents when a plist template changes. After a promote, the hub runs new scripts under old agent
settings until someone remembers to run `make install-<agent>`.

v3 persisted the bases before the move and kept per-name pending lines. Round 3 found these gaps:

1. **An interrupted loop loses a reinstall** (Astra blocker 6). Durable `launchd A`; at B, X installs; the process dies before the single
   end-of-loop write; C reverts X's template to A. The next diff `A..C` omits X, and its plist still carries B.
2. **The checkout lock ignored repo-sync's configuration** (Astra major). Repo-sync reads `K3DM_REPO_SYNC_STATE_DIR` and
   `K3DM_REPO_SYNC_TIMEOUT` (`bin/k3dm-repo-sync:15`, `:18`), and its staleness window is `2 * TIMEOUT + 60` (`:37`), not a fixed 180 s.
   It treats a missing or unreadable `pid` as stale (`:38-41`). Reading one's own pid back does not prove uninterrupted ownership.
3. **Children inherit the run lock** (Astra major; Fable M8). fd 9 passes to `make`, `kubectl` and their children, so a surviving child
   keeps the `flock` after the shell is killed (probe 4 below).
4. **The load check passes an old job** (Astra major). With `K3DM_AGENT_LOAD=0` a target rewrites the plist and leaves the old label
   loaded (`Makefile:73-74`), so "plist changed" and "`launchctl print` exits 0" both pass.
5. **Unmapped templates were resolved silently** (Astra major). `password-bundle` has an installer under another name
   (`Makefile:2446`), and so do `hub-data-export` (`:218`) and `hub-snapshot` (`:2245`).
6. **Lost state loses the ApplicationSet base** (Astra major). Falling back to `old` skips an earlier failed reapply when `old == new`.
   Duplicate lines passed the grammar; the first-run line had no exact text; E4's 2 s wait could not see a catch-up with 10 s polls; exit
   75 could still come from an earlier step, because `stop` keeps the child's code.
7. **The Linux BATS job breaks** (Astra major). `scripts/tests/bin` runs on Ubuntu (`.github/workflows/ci.yml:149-157`, `make test-shard`, which takes `scripts/tests/bin` at `scripts/ci/test_shard.sh:25`), where
   `/usr/bin/lockf` does not exist and `/usr/bin/stat -f` means something else. `make test-bats` does not exist.
8. **Smaller gaps** (Fable minors): `STATE_DIR` must exist before `exec 9>>`; the pre-change doc copies had no file in `## Files`.

**This part is an honest-path correctness property, not an O2 control.** The hub user can write `~/Library/LaunchAgents` and the checkout
directly. Nothing here defends against a same-user attacker. The goal is that an honest `hub-deploy` never leaves agents stale and never
forgets a failed reinstall.

4. **State file.** `STATE_DIR=$HOME/.local/share/k3d-manager/hub-deploy`; the file is `$STATE_DIR/state`.
   - Right after the role gate, the script runs `umask 077; mkdir -p "$STATE_DIR"` and then `chmod 0700 "$STATE_DIR"`. A failure stops at
     step `state-dir` with exit 1. This precedes the run lock (Behaviour 12), whose file lives there.
   - The file mode is 0600. Writes are atomic: write `state.tmp.$$`, then `mv -f` it into place.
   - **Grammar (v4).** The file holds exactly one `appsets` line, exactly one `launchd` line, and zero or more `pending` lines, in any
     order:
     - `appsets <sha>` or `appsets full` (an ApplicationSet reapply is owed);
     - `launchd <sha>` or `launchd full` (a full launchd reconcile is owed);
     - `pending <x>`, with `<x>` matching `^[a-z0-9-]+$`, each name at most once.

     `<sha>` matches `^[0-9a-f]{40}([0-9a-f]{24})?$`.
   - **Unreadable.** The file is unreadable when a line is outside the grammar, a line kind is missing or repeated, a pending name repeats,
     or a sha fails `git -C "$REPO_ROOT" cat-file -e "<sha>^{commit}"`.
   - **First run versus lost state (v4, defined in v5).**
     - The test runs after the run lock is held (Behaviour 12), so `run.lock` always exists by then. A **first run** is a run where the
       state file is absent and `run.lock` is the only entry in `STATE_DIR` (`ls -A "$STATE_DIR"` prints exactly `run.lock`). A first run
       that stopped early (any stop before its first state write) leaves only `run.lock`, so its rerun is again a first run, not lost
       state. The script prints exactly `hub-deploy: no reconcile state yet; full launchd reconcile owed; appsets base <old7>`, and the missing
       values are `appsets <old>` and `launchd full`.
     - When the file is absent and `STATE_DIR` has any other entry (for example a `state.tmp.<pid>` left by a killed write), or the file
       is present but unreadable, state was **lost**. The script prints exactly
       `hub-deploy: state unreadable; full launchd reconcile and appsets reapply owed`, and the values are `appsets full` and
       `launchd full`. Pending lines of an unreadable file are not trusted; the full launchd reconcile covers them.
   - **Valid provisional state (v5).** The smallest valid file is exactly two lines, one `appsets` line and one `launchd` line, with no
     `pending` line, for example `appsets <sha>` and `launchd full`. Every state write in this script, whatever its reason, writes both base
     lines plus the pending lines in one atomic write. No code path ever writes a one-line state.
   - On the approval path (Part 2b), `<old>` here is the `approved-old` value from the promote. The pre-move read is skipped there, so on
     a first run nothing is written before the promote, and the two provisional lines `appsets <approved-old>` and `launchd full` are
     written in one atomic write right after the promote returns (Behaviour 5). A run that dies between the promote and that write leaves a
     `STATE_DIR` holding only `run.lock`, which the next run treats as a first run; a rerun with the same approval id gets the same
     `approved-old` (Part 2b Behaviour 6), so it seeds the same base. A run killed inside that write leaves `state.tmp.<pid>`, which is
     lost state (`appsets full`, `launchd full`).
5. **Persist before the move.** After the run lock (Behaviour 12) and the `old` read (`bin/k3dm-hub-deploy:29-31`), and before the promote
   call (`:32`), the script writes the Behaviour 4 values that are missing. `pending` lines are kept. A failure anywhere later therefore
   leaves a base that still owes the work. On the approval path, which has no pre-move read, a first run writes nothing before the promote
   and, right after the promote returns and before any later step, one atomic write of both lines `appsets <approved-old>` and
   `launchd full` (Behaviour 4, valid provisional state). The approval path with an existing valid state file writes nothing at this point.
6. **ApplicationSets diff base.** The diff at `bin/k3dm-hub-deploy:42` uses the state's `appsets` sha instead of `old`. With
   `appsets full`, the reapply runs whatever the diff says, and the message says `appsets reapply owed after lost state`. The value moves to
   `appsets <new>` only after the reapply exited 0, or after an empty diff from a sha base. A failed reapply leaves it unchanged, so a rerun
   with `old == new` reapplies again. **Applied base (v5).** The move to `appsets <new>` is its own atomic write (both base lines kept)
   made as soon as the reapply exits 0, before `appsets-check` and `platform-ops`, and a later `superseded` or other stop never undoes it.
   It records what was actually applied: `appsets-reapply` applies `deploy/hub` as of the call (`Makefile:514`), which is `$new` or newer,
   so the recorded `new` is never ahead of the cluster and the next diff can repeat work but never skip it. Without this, a revert commit
   `C` after a superseded run would diff against a base that predates the applied `B` and miss the revert (M15). Messages and existing exit behaviour are otherwise unchanged. Existing `M1`, `M2` and `M4`
   (`scripts/tests/bin/hub_deploy.bats:93-126`) stay green: their fixture `HOME` is scratch with no `STATE_DIR`
   (`hub_deploy.bats:12`), so after the mkdir and run lock `STATE_DIR` holds only `run.lock` and it is a first run and the base is `old`, as today.
7. **launchd candidates.**
   - With `launchd <sha>`, the candidates are the short names from
     `git -C "$REPO_ROOT" diff --no-renames --name-only --diff-filter=AM "<sha>" "$new" -- scripts/etc/launchd/`, plus every `pending`
     name.
   - With `launchd full`, the candidates are every template present at `$new`, listed with

   - The diff runs through `_run_command --soft`. A diff error stops at step `launchd-diff` with git's exit code, through `stop`
     (`bin/k3dm-hub-deploy:9`).
   - A pending name whose template no longer exists at `$new` is dropped with `hub-deploy: launchd <x> template removed; dropped`.
8. **Eligibility, per candidate `<x>`.** `<x>` is the part between `com.k3d-manager.` and `.plist.tmpl`.
   1. `webhook-token-rotate`, `dispatch-stall-watch` and `dispatch-metrics` are excluded. The step prints
      `hub-deploy: launchd <x> is excluded from automatic reinstall (scripts/etc/machine/not-installed.list); skipping`, and the name is
      resolved. The token rotator rotates shared secrets, and `not-installed.list:8` says the operator installs it only after cutover, so
      `hub-deploy` never reloads it on its own.
   2. **Unwired (v4).** A name in the unwired list below, or with no row at all, is not installed. If its plist
      `$HOME/Library/LaunchAgents/com.k3d-manager.<x>.plist` exists, the step prints
      `hub-deploy: launchd <x> changed and is installed, but no installer is wired; reinstall it with its setup command`, counts it as
      `unwired`, and the name is resolved. If the plist is absent, the name is resolved silently. In `full` mode every unwired name with an
      installed plist is reported the same way, so the promise never exceeds the table.
   3. If the plist is absent, the step prints `hub-deploy: launchd <x> is not installed on this host; skipping`, and the name is resolved.
      In `full` mode absent plists are counted silently instead.
   4. **Load disabled (v4, persisted in v5).** If `K3DM_AGENT_LOAD` is `0` in `hub-deploy`'s environment, no target runs and no lock is
      taken; every name that reached here is written as a `pending` line by the journal write of 10.1 and printed with the reason
      `agent load disabled (K3DM_AGENT_LOAD=0)`, so the next run retries it. Otherwise every target runs with `K3DM_AGENT_LOAD` removed from
      its environment (`env -u K3DM_AGENT_LOAD`), so it always reloads.
   5. Otherwise the agent is installed (Behaviour 10).
9. **Step order.** The launchd step runs after the rollout check (`bin/k3dm-hub-deploy:62-64`) and before the summary (`:66`). It runs only
   after the promote returned 0, the role gate passed and the pin (Behaviour 13) held.
10. **Journal, then install under the checkout lock.** 10.1 runs when at least one candidate reached 8.4 (including the load-disabled
    branch); 10.2 to 10.8 run only when, in addition, 8.4 did not disable loading.
    1. **Journal first (v4, Astra blocker 6).** Before taking the checkout lock, and so before any install side effect, one atomic write
       sets the state to `launchd <new>`, the current `appsets` line, and one `pending <x>` line for every name that reached 8.4 plus every
       earlier pending name still a candidate. From here on, a crash at any point leaves each not-yet-verified name pending, and the next run
       retries it whatever the diff says. A name leaves the journal only through the per-name write of 10.6.
    2. **Take repo-sync's lock (v4).** `RS_DIR="${K3DM_REPO_SYNC_STATE_DIR:-$HOME/.local/share/k3d-manager/repo-sync}"` and
       `RS_STALE=$(( 2 * ${K3DM_REPO_SYNC_TIMEOUT:-60} + 60 ))`, read the way `bin/k3dm-repo-sync:15` and `:18` read them. The lock is
       `$RS_DIR/lock` (`:17`).
       - Before the take, `mkdir -p "$RS_DIR"`, as repo-sync does for its own directory (`bin/k3dm-repo-sync:339`, `STATE_DIR.mkdir(parents=True,
         exist_ok=True)`); without it a first deploy on a host whose repo-sync never ran would fail at the lock.
       - Take: `mkdir "$RS_DIR/lock"`, then write `$$` to `lock/pid`, then read it back and require `$$`.
       - If the directory exists, `hub-deploy` never removes it unless the lock's mtime is older than `RS_STALE` seconds, or `lock/pid`
         holds a positive integer whose process does not exist (`kill -0` fails with "no such process"). A missing or unreadable `pid`
         under a fresh mtime is treated as held, never stale: that is repo-sync's own window between `mkdir` and its pid write (`:341`,
         `:352`). This is stricter than repo-sync's rule (`:38-41`), on purpose.
       - While the step holds the lock, repo-sync prints `already running` and exits 0 without touching the checkout (`:348`, `:350`).
    3. **Check the checkout under the lock.** Two conditions must hold: `git -C "$REPO_ROOT" rev-parse HEAD` equals `$new`, and
       `git -C "$REPO_ROOT" status --porcelain --untracked-files=no` prints nothing.
       - If either fails, or the lock is held by another live owner, the step releases any lock it holds and waits. It re-checks at most
         every 10 s, and never later than the deadline: each sleep is `min(10, deadline - now)`, with a final check at the deadline. The
         wait is at most `K3DM_HUB_DEPLOY_CHECKOUT_WAIT` seconds (default 330; bats sets 0 or 2). The lock is released between checks
         because repo-sync must run to catch up.
       - On timeout, every remaining name stays pending:
         `hub-deploy: launchd <x>: hub checkout is not at <new7> with a clean tracked tree; pending; rerun bin/k3dm-hub-deploy <ref>`.
    4. **Before each install, still under the lock:**
       1. `touch` the lock directory, so repo-sync's staleness window restarts;
       2. re-read `lock/pid` and require `$$`; if it differs, the name is pending (`checkout lock lost`);
       3. require `git -C "$REPO_ROOT" hash-object scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl` to equal
          `git -C "$REPO_ROOT" rev-parse "$new:scripts/etc/launchd/com.k3d-manager.<x>.plist.tmpl"`, which binds the template bytes to
          the promoted commit;
       4. record `pre="$(plist_stamp "$plist")"` (Behaviour 17), or `absent`.
    5. **Run the target (v5, Astra 5):** `env -u K3DM_AGENT_LOAD make --no-print-directory -C "$REPO_ROOT" <target>`, through
       `_run_command --soft`, with fd 9 **left open** for this one child. The installer and its own descendants therefore hold the run lock
       for their whole life: if the shell is killed while the installer still has a write or a load outstanding, a retry gets exit 75 until
       the installer has finished (probe 6), and so cannot install the newer template only to have an older installer write over it. Every
       other child (git, the promote, `appsets-reapply`, `appsets-check`, `platform-ops`, `kubectl`, `launchctl`) is started with `9>&-`
       (Behaviour 12). The checkout lock directory left by a killed shell names a dead pid, so the retry that follows the installer's end
       takes it by the dead-pid rule of 10.2.
    6. **Verified** requires all five:
       1. the target exited 0;
       2. `lock/pid` still holds `$$` (v4: ownership checked after the install as well as before);
       3. HEAD is still `$new` and the tracked tree is still clean;
       4. `plist_stamp` of the plist differs from `pre`: a fractional mtime plus the inode, compared for inequality, so a future-dated or
          same-second plist cannot pass;
       5. `launchctl print "gui/$(id -u)/com.k3d-manager.<x>"` exits 0, proving the label is loaded. This is a read-only call that
          `bin/launchd-reload:13` already relies on. Every wired target boots the label out and bootstraps it again when loading is enabled
          (for example `Makefile:76-77`), and `launchctl bootstrap` of a label that is still loaded fails, so with 8.4 in force an exit 0
          plus a loaded label means a fresh load. Residual R1-e names the limit.

       A verified name is removed from the journal at once by one atomic state write (v4), before the next name starts.
    7. **Otherwise pending**, with exactly one reason:
       - `install failed (exit N)`;
       - `checkout lock lost`;
       - `checkout moved during install`;
       - `plist not rewritten`;
       - `plist written but not loaded`.

       The message is `hub-deploy: launchd <x> <reason>; pending; rerun bin/k3dm-hub-deploy <ref>`. All retry text comes from one
       function, `retry_hint`, which Part 2b extends with `--approval <id>` and the full approved sha.
    8. **Release.** A trap on exit releases the checkout lock, but only while `lock/pid` still equals `$$`. No hand `make install-*` command is
       ever printed.
11. **Advance per name.** The journal (10.1) has already moved the base to `launchd <new>`, and each verified name has left it (10.6).
    After the loop the pending set is exactly the names that are not verified, and no further write is needed. A name that fails every time
    stays listed without pinning the others. When no candidate reached 8.4, one atomic write sets `launchd <new>` and keeps the pending
    lines that are still candidates and not resolved.
12. **One run at a time.** After `STATE_DIR` exists (Behaviour 4), the script opens `exec 9>>"$STATE_DIR/run.lock"` and takes a
    non-blocking exclusive lock on fd 9 with the host's tool (Behaviour 17). It is a kernel `flock(2)` lock held for the life of the
    process: no stale file, no PID reuse, and no window between taking the lock and recording the owner.
    - **Unrelated children never hold it (v4, Fable M8; narrowed in v5).** Every child the script starts gets `9>&-`, so a surviving
      unrelated child cannot keep the lock after the shell dies (probe 4). The one exception is the mutating installer of 10.5, which keeps
      fd 9 on purpose so that serialization lasts as long as its writes can (probe 6).
    - Conflict exit 75: print `hub-deploy: another run is active` and exit 75.
    - Any other non-zero exit: stop at step `run-lock` with exit 1.

    - The pin applies on every run, including one with an empty appsets diff.
    - **Superseded (v4).** On a mismatch the script prints
      `hub-deploy: platform-ops applied <got7>, expected <new7>; deploy/hub has moved on; superseded` and stops at step `superseded` with
      exit 1. A rerun of the same ref cannot fix this, so it is not 75 (Fable M7). This check is inside `hub-deploy` and exits 1 directly.
      It does not depend on make's exit status. (Part 2b's pinned `make` targets cannot return 1, because make exits 2 for any failing
      recipe, probe 7; Part 2b owns the `K3DM_SUPERSEDED_OUT` file that tells them apart, 2b Behaviour 7. Part 1 adds no `mktemp` and no

    - **Residual (Fable M3, v5).** Until Part 2e is cut over, a CVE pin commit can supersede a run (the in-cluster promoter commits to
      `deploy/hub` every 15 minutes, `scripts/etc/argocd/platform-ops/app-cve-scan-cronjob.yaml:193`). Recover with the manual
      `make platform-ops` and a rerun of `bin/k3dm-hub-deploy` for the current `deploy/hub` sha.
    - An unreadable or absent file stops at step `platform-ops-pin` with exit 1.
    - The file's second reader, `bin/k3dm-repo-sync:403`, is unchanged.
14. **Exit 75 means one thing (v4).** `hub-deploy` exits 75 only when nothing was refused and the same command can safely be rerun:
    - the run lock is held (Behaviour 12);
    - on the approval path, the promote or a `deploy/hub` read answered 75 (Part 2b Behaviours 5 and 7).

17. **Portable host tools (v4, Astra major).** Both the macOS hub and the Ubuntu CI runner run this script.

## Residuals (named, honest path only)

- **R1-a.** A same-user edit of the checkout between the template-blob check and the read inside `make` can change the render. Helpers
  inside `make` are also read from the worktree, for example `bin/launchd-reload` (`Makefile:770`). The lock stops repo-sync, the only
  automated writer. It does not stop the operator or another same-user process. This is not an O2 control (see Problem).
- **R1-b.** Repo-sync can still take the lock in two cases: an install that runs longer than `RS_STALE`, and repo-sync's own rule that a
  missing `pid` is stale, in the instant between `hub-deploy`'s `mkdir` and its pid write. Ownership is checked before and after every
  install (10.4.2, 10.6.2), and HEAD, the clean tree and the template blob are checked after it, so a takeover is reported as
  `checkout lock lost` or `checkout moved during install`. It is not counted verified.
- **R1-c.** `webhook-log-level` (`Makefile:664`) rewrites the webhook and cloud-bridge plists. If it runs during an install, the stamp check
  passes without the target's bytes. The load check still applies.
- **R1-d.** A failed ApplicationSet reapply from before this part existed, or one followed by deletion of the whole `STATE_DIR`, cannot be
  recovered, because that history is unknown: such a run is treated as a first run with base `old`. Deleting only the state file
  (leaving `run.lock` alone) is also a first run with base `old` (v5 first-run definition, Behaviour 4), so a failed reapply recorded
  in the deleted file is not retried; any other entry left in `STATE_DIR` makes it lost state and forces a reapply. On the approval path,
  a run that died between the promote and its first write and is followed by a different approval seeds from that approval's own
  `approved-old`, so the first approval's appsets change is not diffed; this is accepted.
- **R1-f (Fable M3).** The superseded logic assumes `deploy/hub` has one writer, this script's promote. Until Part 2e is cut over, the
  in-cluster promoter's CVE pin commits can move it (see Behaviour 13), and a run can end `superseded` for a reason no rerun of its own
  ref can fix. Recovery text is in Behaviour 13. A slow or hung installer holds the run lock (10.5) and makes a rerun exit 75 until it
  ends; the operator waits or kills it.
- **R1-e.** A wired target that rewrites the plist, skips its reload and still exits 0 while the old job stays loaded would pass 10.6. The
  only known way to get that is `K3DM_AGENT_LOAD=0`, which 8.4 removes. A target that changes to skip its reload without saying so is
  outside this check.

2. Every must_not test contains its positive control in the same `@test`. Record the red run on the pre-fix base for the three commands
   named at the head of `## Acceptance` (`P1 superseded`, `P1 first run`, `P1 docs`), and the red run for each named mutant of N1-N6, N8,
   N9, M14 and M16 (the verifier applies the mutant to the fixed code and restores it).

   repo, and stub `make` and `launchctl` found first on `PATH`.

   `make test-pytest` (agent-doc drift) passes.

## What NOT to do

- Do not edit the install or schedule targets, `bin/k3dm-repo-sync` or `bin/launchd-reload`.
- Do not print a hand install command. Do not install the three excluded or the five unwired agents.
- Do not edit `AGENTS.md`, `GEMINI.md`, `bin/k3dm-hub-promote` or anything about approvals.
