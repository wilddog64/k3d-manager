## Problem

`make hub-deploy REF=` is the one promote command (`bin/k3dm-hub-deploy`), but the rules still teach the three-step path and the command
does not refresh the hub's launchd agents when a plist template changed. After a promote the hub runs new scripts under old agent
settings until someone remembers `make install-<agent>`.

The v1 draft kept a pending-name list and compared templates against a `git archive`. The re-review found it unsafe or wrong in these ways,
each fixed below:

1. (R6) the pending list is lost whenever the diff is empty or the state file is deleted, and a name resolved against a stale template is
   dropped for good. This version keeps one durable fact, the last sha whose launchd templates were fully reconciled, and diffs from it;
2. (R7) the install targets render from the working tree (`$$(pwd)`, `Makefile:72`), `hub-deploy` only moves `origin/deploy/hub`, and
   `bin/k3dm-repo-sync` can leave the checkout dirty (`:265`) or reset it later, so "the checkout catches up within 5 minutes" is not a
   promise. This version installs only from a checkout whose HEAD is exactly `$new` with a clean tracked tree, checked before and after
   `make`, and waits a bounded time for it;
3. (R7) the old diagnostic printed a hand `make install-*` command that installs whatever the checkout holds. It is gone; only
   `bin/k3dm-hub-deploy <ref>` is printed;
4. (Astra) `install-prometheus-credential-rotator` can exit 0 without installing (prerequisites missing, `scripts/plugins/observability.sh`
   `_observability_install_prometheus_rotator`), so exit 0 is not proof. This version also requires the plist mtime to move;
5. (Fable) the doc test the first draft called E1 could not fail, because `CLAUDE.md:25` already contains `make hub-promote-status`. E1 is
   now a string-presence test with a positive control against the pre-change files.

## Behaviour

1. **One promote command in the rules.** `CLAUDE.md:25` and `docs/process/rules.md:83-94` (the bullet under the heading at `:81`) and
   `:95`, the paragraph after it, say `make hub-deploy REF=<commit-ish>` (typed confirmation, tag, appsets-reapply only when
   ApplicationSets changed, `appsets-check`, `platform-ops`, rollout check, launchd reinstall of changed installed agents) instead of the
   three-step path. The three targets stay documented as the manual fallback in `docs/process/rules.md` and `docs/howto/hub-promote.md`.
   `CLAUDE.md` stays one bullet with one `[more]` link. `AGENTS.md` and `GEMINI.md` are not edited (not a shared block;
   `bin/k3dm-check-agent-docs` must still pass).
2. **Howto.** `docs/howto/hub-promote.md:24-36` ("Everyday promote") gains the launchd sentence: changed launchd agents that are already
   installed on this host are reinstalled after `platform-ops`, from a checkout verified to be at the promoted commit; one that could not
   be reinstalled is reported pending and retried by the next `bin/k3dm-hub-deploy <ref>` run, including a rerun of the same ref. Nothing
   about approvals (Parts 2c and 2b own that wording).
3. **Makefile help.** `Makefile:2351` becomes `make hub-deploy REF=...    Promote, reconcile and verify the hub (typed confirmation required; reinstalls changed launchd agents)`.
   This is the only Makefile edit of this part. (Part 2c adds Makefile targets afterwards; the dispatch order is the sequencing.)
4. **State: one sha.** File `$HOME/.local/share/k3d-manager/hub-deploy/launchd-reconciled`, directory mode 0700, file mode 0600, content
   one full 40-hex sha and a newline, written atomically (write `launchd-reconciled.tmp.$$`, then `mv`). Same directory pattern as
   `Makefile:1398` (`$(HOME)/.local/share/k3d-manager/repo-sync`). It means "every template change up to this commit has been resolved on
   this host".
5. **Diff base.** `base` is the file's sha when it is a valid 40-hex and `git -C "$REPO_ROOT" cat-file -e "$base^{commit}"` succeeds;
   otherwise `base` is `$old` and the step prints `hub-deploy: launchd: no usable reconciled sha; diffing from <old7>`. The diff is
   `git -C "$REPO_ROOT" diff --no-renames --name-only --diff-filter=AM "$base" "$new" -- scripts/etc/launchd/`, through
   `_run_command --soft`. A diff error stops the run at step `launchd-diff` with the git exit code through the existing `stop`
   (`bin/k3dm-hub-deploy:9`). An empty diff and `base == new` prints `launchd templates unchanged between <base7> and <new7>; skipping reinstall`
   and does nothing else.
6. **Eligibility, per changed template short name `<x>`** (the part between `com.k3d-manager.` and `.plist.tmpl`). The step runs after the
   rollout check and before the summary line, never before the promote returned 0, and after the role gate (`bin/k3dm-hub-deploy:17`).
   1. `<x>` is `webhook-token-rotate`, `dispatch-stall-watch` or `dispatch-metrics`: skipped as not installed on the hub, always, even when a
      plist exists (`scripts/etc/machine/not-installed.list:2` and `:38-41`). Resolved.
   2. No row in the table below: print `hub-deploy: launchd template <x> changed; no install target is wired` (this is "no table row"; a
      target may exist elsewhere, e.g. `password-bundle-install` at `Makefile:2446`). Resolved.
   3. Plist `$HOME/Library/LaunchAgents/com.k3d-manager.<x>.plist` absent: print `hub-deploy: launchd <x> is not installed on this host; skipping`. Resolved.
   4. Otherwise install (Behaviour 7). Resolved only when the install is verified.
7. **Install gate (R7).** Before any `make`, the checkout must satisfy all of: `git -C "$REPO_ROOT" rev-parse HEAD` equals `$new`, and
   `git -C "$REPO_ROOT" status --porcelain --untracked-files=no` prints nothing. If not, the step waits, polling every 10 seconds, up to
   `K3DM_HUB_DEPLOY_CHECKOUT_WAIT` seconds (default 330; bats sets 0) for both to hold, then treats every remaining install as pending:
   `hub-deploy: launchd <x>: hub checkout is not at <new7> with a clean tracked tree (repo-sync); pending; rerun bin/k3dm-hub-deploy <ref>`.
   When the gate holds, each install runs `make --no-print-directory -C "$REPO_ROOT" <target>` through `_run_command --soft`, then the gate is
   checked again (HEAD still `$new`, tracked tree still clean); a change during the run is pending (the plist may carry other bytes). The
   install counts as verified only when the target exited 0 and the plist mtime is at or after the step's start time
   (`stat -f %m`, compared to a start epoch taken before the first install). Non-zero `N`: `hub-deploy: launchd <x> install failed (exit N); pending; rerun bin/k3dm-hub-deploy <ref>`.
   No hand `make install-*` command is ever printed.
8. **Advance the sha.** After the loop, `launchd-reconciled` becomes `$new` only if every changed name was resolved. Any pending name
   leaves the file at its old value (or absent), so the next run diffs from the same base and sees the same names again. This is the
   whole of the rerun story: nothing depends on `old == new`.
9. **Downstream pin.** After `platform-ops` succeeded, the step reads `$HOME/.local/share/k3d-manager/repo-sync/deployed-platform-ops`
   (written at `Makefile:1398`) and compares it with `$new`. A mismatch (or an unreadable file) stops at step `platform-ops-pin` with exit 75
   and `hub-deploy: platform-ops applied <got7>, expected <new7>`, before any launchd step. Reason: the launchd step must not run against a
   tree `platform-ops` did not apply.
10. **Soft otherwise.** A pending reinstall never changes the exit status and never stops the earlier steps. The summary line
    (`bin/k3dm-hub-deploy:66`) gains `; launchd skipped|ran|pending <N>` and, when pending, `hub-deploy: launchd pending: <x> <y>` on stderr.
    The substring `reapply ran; appsets-check ok; platform-ops ok; exporter rolled out` stays intact (`scripts/tests/bin/hub_deploy.bats:97`).
11. **One run at a time.** After the role gate, the script takes a lock: `mkdir "$HOME/.local/share/k3d-manager/hub-deploy/lock"` with a
    `pid` file inside; if the directory exists and `kill -0 <pid>` succeeds, exit 75 `hub-deploy: another run is active (pid <p>)`; a stale lock
    (pid gone) is removed and taken; the lock is removed on exit by a trap. This keeps two runs from writing the sha file or installing
    concurrently.

## Worker definition of done

1. Every must has a bats test; every must_not test contains its positive control in the same `@test`, so each is red against the pre-change
   `bin/k3dm-hub-deploy` (which has no launchd step and installs nothing). Show the red run for N1 to N6 before the fix.

3. `make test-bats` for the hub_deploy suite and `make test-pytest` (agent-doc drift) pass.
4. No `sudo`; no new environment variable besides `K3DM_HUB_DEPLOY_CHECKOUT_WAIT`.

## What NOT to do

- Do not run `make install-*` from a `git archive` directory (bakes a deleted path into a plist, `Makefile:72`).
- Do not edit the install targets or pass a runtime-root variable through them.
- Do not print a hand install command. Do not install the three excluded agents.
- Do not edit `AGENTS.md`, `GEMINI.md`, `bin/k3dm-hub-promote` or anything about approvals.
