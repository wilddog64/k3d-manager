# v1.39.0 — Publish `make test` / `make test-all` results to Grafana, with staleness

**Status:** SPEC — ready to implement
**Filed:** 2026-09-24
**Branch:** `k3d-manager-v1.39.0` (created by `/post-merge` from the v1.38.0 merge SHA — do NOT cut it early)

---

## Why

The offline suite is the project's main quality gate — **1,253 BATS cases plus 189 pytest and 28
unittest cases** — and it produces no durable signal. A run's result exists only in the terminal
scrollback of whoever ran it. There is no way to answer "when did the suite last pass?", "is that
suite slower than it was?", or "has anything been red for a week?" without re-running 15 minutes of
tests.

Two concrete losses already happened in this repo for exactly this reason:

1. **`cluster_status_summary.bats` was red on the release branch from 05:08 to 08:30 on 2026-09-24**
   — introduced by `492b3cba`, whose own "make test green" gate did not hold, and found only when a
   later unrelated agent run tripped over it. A recorded per-suite red would have surfaced it in
   minutes rather than hours.
2. **Two separate agent runs reported `make test-all` as a mysterious failure**, because it exits 2
   on this box for an environmental reason (below). A dashboard that distinguishes *cases failed*
   from *exit code* removes that confusion permanently.

The transport already exists and was repaired this release. `_push_metrics`
(`bin/k3dm-webhook:1586`) is the working template, and `_deploy_pushgateway_acg` already installs
the Pushgateway and applies a dashboard ConfigMap to the **app cluster**. This spec reuses both.

### Why Pushgateway and not the exporter path

The e2e, CVE and Hermes dashboards are fed by labelled ConfigMaps read by
`vulnerability-inventory-exporter`. That is wrong for this workload: `make test` runs **on the
laptop**, so the ConfigMap path would need kubectl write access into `platform-ops` on every local
test run, and the exporter is built for in-cluster events. Pushgateway exists precisely for batch
jobs that start, finish and exit with nothing to scrape. Use it.

Metrics land in the **app-cluster** Prometheus. The hub has no Pushgateway by design
(`_provider_supports_pushgateway`), so the dashboard datasource must be the app-cluster one — the
same decision already recorded for the deployment-metrics dashboard.

## The four traps this spec must design around

These are the reason the spec is not simply "push some numbers".

### T1 — `exit_code` is a lying metric on this box

`make test-all` **always** exits 2 here: the `test-pytest` recipe calls `python3`, which is
Homebrew 3.14.7 with no pytest. Measured 2026-09-24: `EXIT=2` with **1237 BATS ok / 0 not ok** and
all four unittest files green.

A panel reading "last run: FAILED" would therefore be permanently red and would train the operator
to ignore it — the same failure mode as Grafana Overview's "Firing Alerts" panel, which queries a
metric this stack never exposes and so reads `No data` forever.

**Therefore: `k3dm_test_cases_failed` is the health signal. The exit code is recorded as
informational only and MUST NOT drive any alert or any red/green panel.** Record which make step
was reached separately, so "died before pytest" is visible without pretending it means failure.

### T2 — Pushgateway has no staleness, and this is the load-bearing risk

Pushgateway holds the last pushed value **forever**, until it is overwritten or deleted. A
dashboard will happily display a green run from three weeks ago as though it were current, and
nothing in the panel will say otherwise.

**A dashboard without an age signal is worse than no dashboard**, because it asserts a freshness it
does not have. There is currently **no** staleness rule for any `k3dm_*` metric — verified against
`scripts/etc/argocd/platform-ops/prometheusrule.yaml`, which has rules for argocd, trivy-operator,
CVE and e2e but none for `k3dm_deployment_*`. That gap was deferred once. It is **not** deferrable
here, so S4 is part of this spec, not a follow-up.

`E2EVerificationStale` (`prometheusrule.yaml:131`) is the shape to copy:
`time() - <metric>_timestamp_seconds > <seconds>`.

### T3 — a failed push is indistinguishable from "no run"

Pushing depends on the `localhost:9091` port-forward LaunchAgent — the component whose service-name
drift silently held the deployment dashboard at zero series for **64 days**. If a push fails, the
last value simply stays, which looks identical to a stale success. This is the same root risk as T2
and is why the age panel and the staleness alert are mandatory rather than nice-to-have.

The pusher must be **non-fatal** (a failed push must never fail a green test run) but must print
its failure loudly, exactly as `_push_metrics` does.

### T4 — local and CI will clobber each other

Pushgateway's grouping key is the URL path, `/metrics/job/<job>/instance/<instance>`. Labels in the
body do **not** separate series with the same grouping key — a later push replaces the group.

So `origin` (local vs ci) must be part of the **URL**, not just a label. Otherwise a green CI run
silently overwrites a red local run and the dashboard lies. Use:

    /metrics/job/k3dm-tests/instance/<target>-<origin>

## S1 — `bin/k3dm-test-metrics` (new)

A standalone script that parses a captured run log and pushes. It takes the log path so it can be
re-run against an old log without re-running the suite.

    bin/k3dm-test-metrics <log-path> --target test|test-all [--origin local|ci] [--exit-code N]

Requirements:

- **Parse BATS TAP**, which is what the suites emit: a `1..<N>` plan line, then `ok <n> <name>` and
  `not ok <n> <name>`. Attribute each case to a suite by tracking the most recent
  `# <path>.bats`-style marker or the `[make] bats <file>` line — **verify which marker the real
  log contains before writing the parser, and quote the line you keyed on in your report.** Do not
  guess the log format; run `make test > /tmp/x.log` once and read it.
- **Parse the unittest blocks** (`Ran N tests in Xs` followed by `OK` or `FAILED`), which is how
  `make test-bin` reports `webhook_make_targets`, `webhook_policy`, `webhook_redaction`,
  `webhook_request_hardening`.
- **Parse the pytest summary** (`N passed`, and `N failed` when present).
- Emit Prometheus text format and POST it with the **same retry-and-healthcheck discipline** as
  `_push_metrics`: check `/-/healthy` first, retry, and on final failure print a clearly-labelled
  non-fatal skip. Never exit non-zero because a push failed.
- Read the endpoint from `K3DM_PUSHGATEWAY_URL`, defaulting to `http://localhost:9091` — the same
  variable `scripts/lib/webhook/config.py:33` already uses. Do NOT introduce a second variable.
- Be importable for tests without side effects (no push at import time).

### Metrics

```
# HELP k3dm_test_suite_cases Test cases by suite and result
# TYPE k3dm_test_suite_cases gauge
k3dm_test_suite_cases{suite="webhook.bats",result="ok"} 64
k3dm_test_suite_cases{suite="webhook.bats",result="not_ok"} 0

# HELP k3dm_test_suite_duration_seconds Wall-clock duration of one suite
# TYPE k3dm_test_suite_duration_seconds gauge
k3dm_test_suite_duration_seconds{suite="webhook.bats"} 12.4

# HELP k3dm_test_cases_total Total cases in the run
# HELP k3dm_test_cases_failed Failed cases in the run — THE health signal
# TYPE k3dm_test_cases_failed gauge
k3dm_test_cases_failed{target="test-all"} 0
k3dm_test_cases_total{target="test-all"} 1470

# HELP k3dm_test_run_duration_seconds Wall-clock duration of the whole run
# HELP k3dm_test_last_timestamp_seconds Unix timestamp of the last completed run
# HELP k3dm_test_last_success_timestamp_seconds Unix timestamp of the last run with zero failures
# HELP k3dm_test_exit_code Make exit code — INFORMATIONAL ONLY, see the staleness note
# HELP k3dm_test_last_step_reached Last make sub-target that ran (1 per step name)
# TYPE k3dm_test_last_step_reached gauge
k3dm_test_last_step_reached{target="test-all",step="test-pytest"} 1
```

`k3dm_test_last_success_timestamp_seconds` is what S4's staleness alert reads. It must be pushed
**only** when the run had zero failed cases, and must be **omitted** (not zeroed) otherwise, so a
failing run cannot reset the clock and a red streak ages visibly.

### Cardinality

Label by **suite file** — a few dozen series. **Never label by test name**: 1,253 series that churn
on every rename, for no analytical gain. Do not add a `commit` or `branch` label either; that is
unbounded over time. If run-to-run correlation is ever wanted, that is a Loki/log concern, not a
metric label.

## S2 — `make test-metrics`

Do **not** change `make test` or `make test-all`. CI runs both, and wrapping either in a pipe would
change exit-status propagation — `cmd | tee` yields tee's status, and this repo has already been
burned by piping a long-running command into `tail`, which buffers all output so the log stays empty
until exit.

Add a separate, opt-in target:

```make
## Run the offline suite, capture the log, and publish results to Pushgateway
test-metrics:
	@set -o pipefail; \
	_log="$${TMPDIR:-/tmp}/k3dm-test-all-$$(date -u +%s).log"; \
	$(MAKE) test-all >"$${_log}" 2>&1; _rc=$$?; \
	./bin/k3dm-test-metrics "$${_log}" --target test-all --exit-code "$${_rc}"; \
	echo "[test-metrics] log: $${_log}"; \
	exit 0
```

`exit 0` is deliberate: the target's job is to publish, and T1 means a non-zero `test-all` exit is
expected on this box. The **failure signal is `k3dm_test_cases_failed`**, which the pusher reports
and the dashboard shows. Print the parsed summary to stdout too, so a human running it sees the
counts without opening Grafana.

Add `test-metrics` to `.PHONY`. Do **not** add it to `/k3dm`'s allowlist in this spec — a 15-minute
Slack job needs its own decision.

**Note for whoever writes this:** `$(MAKE)` inside a recipe is fine, but be aware `make -n` still
*executes* `$(MAKE)` lines in this repo, and a stray `$$(MAKE)` resolves to APFS `/usr/bin/MAKE` and
runs `make help`. Use `$(MAKE)`, single dollar, exactly as written.

## S3 — dashboard: `scripts/etc/grafana/dashboards/k3dm-tests-configmap.yaml` (new)

Copy the structure of `k3dm-deployments-configmap.yaml` exactly: a ConfigMap in namespace
`monitoring` labelled `grafana_dashboard: "1"`, holding one JSON key. Apply it from
`_deploy_pushgateway_acg` (`scripts/plugins/observability.sh:706`) next to the existing dashboard
apply, using the same `--context "${_app_context}"`.

Panels, in this order:

1. **Suite freshness** — `time() - k3dm_test_last_timestamp_seconds`, unit seconds, as the **first
   panel on the dashboard.** Thresholds: green < 24h, amber < 72h, red beyond. This panel exists
   because of T2 and must not be moved below the fold.
2. **Last passing run** — `time() - k3dm_test_last_success_timestamp_seconds`, same treatment.
3. **Failed cases** — `k3dm_test_cases_failed`, stat, red on anything > 0. This is the health
   signal.
4. **Cases by suite** — `k3dm_test_suite_cases{result="not_ok"} > 0`, table, so a red suite is named
   rather than just counted.
5. **Suite duration over time** — `k3dm_test_suite_duration_seconds`, timeseries, to catch a suite
   that is quietly getting slower.
6. **Total cases** — `k3dm_test_cases_total`, timeseries. A sudden **drop** is the interesting
   event: it means tests were deleted, which the `_agent_audit` hook is supposed to block.
7. **Exit code** — `k3dm_test_exit_code`, table, with the panel description stating in words that
   **2 is expected for `test-all` on this box because `test-pytest`'s `python3` has no pytest**, and
   that this panel must not be read as pass/fail. A panel that needs this caveat must carry it.

Set the datasource to the app-cluster Prometheus, matching the deployments dashboard. Do **not**
repoint any existing dashboard's datasource uid.

## S4 — staleness rules (NOT deferrable — see T2)

Add a `k3dm-tests.alerts` group to `scripts/etc/argocd/platform-ops/prometheusrule.yaml`, modelled
on `E2EVerificationStale` at line 131:

```yaml
    - name: k3dm-tests.alerts
      rules:
        - alert: OfflineSuiteFailing
          expr: k3dm_test_cases_failed > 0
          for: 30m
          labels:
            group: k3dm-tests
            severity: warning
          annotations:
            summary: "{{ $value }} offline test case(s) failing for target {{ $labels.target }}"
            description: "The last recorded run of {{ $labels.target }} had failing cases. This is the health signal; the exit code is not."
        - alert: OfflineSuiteStale
          expr: time() - k3dm_test_last_success_timestamp_seconds > 604800
          for: 1h
          labels:
            group: k3dm-tests
            severity: warning
          annotations:
            summary: "no passing offline suite for {{ $labels.target }} in >7d"
            description: "Pushgateway retains the last pushed value indefinitely, so a stale success is indistinguishable from a current one. No zero-failure run has been recorded for over 7 days."
```

**Also close the pre-existing gap in the same commit**, since it is the identical mechanism and this
spec is what makes it load-bearing:

```yaml
        - alert: DeploymentMetricsStale
          expr: time() - k3dm_deployment_last_timestamp_seconds > 1209600
          for: 1h
          labels:
            group: k3dm-tests
            severity: warning
          annotations:
            summary: "no k3dm deployment metric pushed for {{ $labels.action }}/{{ $labels.provider }} in >14d"
            description: "The k3dm Deployment Metrics dashboard held zero series for 64 days because the Pushgateway port-forward was removed on every access-layer refresh. This alert makes that class of silence visible."
```

7d for tests and 14d for deployments are deliberate: the suite is run most days, a cluster
up/down is not. Check `_hostinger_refresh_access_layer`'s cadence before changing them, and **verify
the label names on `k3dm_deployment_last_timestamp_seconds`** against `_push_metrics` before writing
the annotation — it carries `action`, `provider` and `status`.

## Tests — `scripts/tests/bin/test_k3dm_test_metrics.py` (new, pytest)

Parsing is the whole risk; the transport is a copy of working code. Test the parser against
**real captured fixtures**, not hand-written idealised ones.

Capture a genuine log once (`make test > fixture.log`), trim it to a few suites, and commit it as a
fixture under `scripts/tests/fixtures/`. Import the script with the existing `SourceFileLoader`
pattern at `scripts/tests/bin/test_smoke_logins.py:12-16` — do not invent a second mechanism and do
not add an `__init__.py`.

1. **`test_bats_tap_counts_match_the_fixture`** — parsed ok/not_ok per suite equal hand-counted
   values from the committed fixture.
2. **`test_a_red_case_is_attributed_to_the_right_suite`** — a fixture containing one `not ok`
   attributes it to the correct suite file, not to the previous or next one. Off-by-one in
   suite attribution is the likeliest parser bug.
3. **`test_unittest_and_pytest_blocks_are_parsed`** — `Ran 14 tests … OK` and `189 passed` both land
   in the totals; `FAILED (failures=2)` yields 2 failed.
4. **`test_total_equals_sum_of_suites`** — `k3dm_test_cases_total` equals the sum of all
   `k3dm_test_suite_cases`, so a parser that silently drops a suite is caught.
5. **`test_success_timestamp_is_omitted_when_any_case_failed`** — with ≥1 failure the payload
   contains no `k3dm_test_last_success_timestamp_seconds` line at all. Asserting it is *absent*, not
   zero, is the point: a zero would make the staleness alert fire on epoch instead of ageing.
6. **`test_exit_code_2_with_zero_failures_is_not_a_failure`** — the T1 case: `--exit-code 2` plus a
   clean log yields `k3dm_test_cases_failed 0` and still pushes a success timestamp.
7. **`test_origin_is_in_the_grouping_url_not_only_a_label`** — the push URL contains the origin
   (T4). Assert on the URL string.
8. **`test_no_metric_is_labelled_by_test_name`** — scan the payload and fail if any label value
   contains a space or exceeds ~80 chars, i.e. a test title leaked into a label. This is the
   cardinality guard.
9. **`test_push_failure_is_non_fatal`** — with the endpoint unreachable, the script still exits 0
   and prints a skip. Stub the transport at the network boundary only; the payload builder under
   test stays real.
10. **`test_payload_is_valid_prometheus_text_format`** — every non-comment line matches
    `name{labels} value`, each metric has `# HELP` and `# TYPE`, and no `NaN`/`inf` values.

**No test may stub the thing it measures.** `scripts/tests/hermes/test_alert_delivery.py` was 8/8
green while the probe it claimed to cover was never executed, because it injected a stub at the
wrong seam.

## What NOT to do

- Do NOT let the exit code drive any alert, threshold or red/green panel (T1).
- Do NOT omit the staleness rules or the freshness panel; they are the point, not polish (T2).
- Do NOT label any metric by test name, commit or branch (cardinality).

- Do NOT add a Pushgateway to the hub, and do NOT repoint an existing dashboard's datasource uid.
- Do NOT add `test-metrics` to the `/k3dm` allowlist.
- Do NOT touch the live cluster or host: no kubectl, no helm, no launchctl, no restart of the
  webhook, no push to the real Pushgateway.
