# v1.46.0 — Measure full hub recovery time, separately from the data RTO

**Filed:** 2026-10-10, Claude
**Branch:** `k3d-manager-v1.46.0` (do not start until that branch exists; never `main`)
**Status:** QUEUED for v1.46.0. Needs one operator decision (below) before dispatch.
**Origin:** operator, 2026-10-10: "your current 30-minute DR-drill budget measures restoration of
critical data services, not complete recovery of every hub component. That's worth tracking
separately."
**Implementer:** Codex · **Verifier:** Claude

## Problem

The weekly drill's RTO (`rto_seconds`, check V6, budget `DR_DRILL_RTO_BUDGET_S=1800`) is the time
from Phase 2 to verified data. In drill mode `bin/hub-up` stops after Step 4 (Vault, LDAP), and the
drill restores and checks Vault, Keycloak's database and LDAP. It never builds ArgoCD or anything
ArgoCD deploys (monitoring, Alertmanager, ESO, Loki, the Pushgateway, the vector store), and it
never times the M4 host services (the cloudflared tunnel, the webhook, Hermes, the port-forwards).

So "RTO 30 minutes" means "the data services are back in 30 minutes". The time until the hub
works again (alerts sent, apps reconciling, the tunnel serving) is not measured anywhere.

## Design

### D1 — Name the current number for what it is

No behaviour change, only labels:
- the result JSON gains `"rto_scope": "data-services"`;
- `bin/dr-drill-publish` adds the label `scope="data-services"` to `k3dm_dr_drill_rto_seconds`;
- `docs/howto/hub-dr-drill.md`, `docs/architecture/hub-dr-drill.md` and the v1.46.0 dashboard spec's
  RTO panel title say "Data-services RTO".

The dashboard spec (`v1.46.0-dr-drill-dashboard.md`) lands first or in the same branch. Its producer
test (every dashboard series is pushed) keeps passing, because the series name does not change.

### D2 — Full-recovery drill (monthly, attended, separate run)

`make dr-drill-full` on the M2 runs `bin/dr-drill` with `DR_DRILL_FULL=1`:
1. Same Phases 1–4 as the weekly drill, unchanged. If they fail, stop; there is no full result.
2. **Phase 4b, platform:** continue `bin/hub-up` past Step 4 (ArgoCD), then apply the hub
   ApplicationSets for the drill cluster.
3. Record, for each hub Application, the time from Phase 2 start until it is first
   `Synced` + `Healthy`. Stop waiting at `DR_DRILL_FULL_BUDGET_S` (default 7200).
4. Result fields: `full_rto_seconds` (time until the last **required** app is healthy),
   `apps_healthy`, `apps_not_healthy` (names), `rto_scope: "full"`.
5. Teardown as usual.

**Required apps** are listed in `scripts/etc/dr/full-recovery-apps.txt` (one name a line), taken
from the hub's in-cluster Applications on 2026-10-10: `kube-prometheus-stack`, `hub-platform-ops`,
`hub-pushgateway`, `k3d-cluster-eso`, `shopping-cart-identity`. Other in-cluster apps
(`hub-loki`, `hub-grafana-dashboards`, `blackbox-exporter`, `hub-vectordb`, `trivy-operator`, the
rollout demos) are timed but not required.

**Not covered, and said so in the how-to:**
- Apps whose destination is another cluster (`ubuntu-hostinger`, the ACG app cluster). The drill
  cluster has no cluster-registration Secrets, so those generators produce nothing, and it must
  never be given one.
- Services that run on the M4 host, not in the cluster: the cloudflared tunnel, the webhook, Hermes
  and the launchd port-forwards. Their recovery is a manual checklist in the how-to, with a
  "time taken" column the operator fills in at the next real rebuild.

Metrics: `k3dm_dr_drill_full_rto_seconds` and `k3dm_dr_drill_full_apps_not_healthy`, pushed by
`make dr-drill-publish` when the result has `rto_scope: "full"`. A new alert,
`DRFullRecoveryStale`, fires when no full drill has run for 35 days (email only).

### The decision the operator must make: egress

The weekly drill's isolation guarantee (V0: no egress before Vault is unsealed) is load-bearing.
A full rebuild needs egress: ArgoCD pulls git, and nodes pull images. Options:

| Option | What runs | Isolation | Recommendation |
|---|---|---|---|
| **A** | Full run **without restored data**. Phases 2 and 4b only; Vault is fresh, so apps that need real secrets are expected to be unhealthy and are listed. Egress allowed. | Nothing secret is in the cluster, so egress is harmless. | **Recommended.** Full RTO ≈ data RTO (weekly) + platform RTO (this run). The sum is an upper bound, since in a real recovery they overlap. |
| B | Full run with restored data and an egress allowlist (github.com, ghcr.io, docker.io, quay.io). | Restored secrets in a cluster that can reach the internet, limited by a hostname allowlist. NetworkPolicy cannot filter by hostname, so this needs Cilium or an egress proxy. | Not recommended: new component, weaker guarantee. |
| C | No drill. Time the next real hub rebuild on the M4 and record it by hand. | n/a | Fallback only. A real rebuild is rare and unplanned, so this is not a measurement you can schedule. |

With option A, Phase 4b replaces "Phases 1–4" in D2: the full run skips the restore and the V1–V5
checks, and records `data_restored: false`.

## Tests (BATS, stubbed)

1. Weekly run result has `rto_scope: "data-services"`, and publish labels the RTO series with it.
2. `DR_DRILL_FULL=1` (option A): `hub-up` is called without the Step-4 stop, no restore is called,
   and the result has `full_rto_seconds`, `data_restored: false` and `rto_scope: "full"`.
3. An app on the required list that never becomes healthy appears in `apps_not_healthy`, and
   `full_rto_seconds` is the budget, not the time of the last healthy app.
4. An app not on the required list that is unhealthy does not change `full_rto_seconds`.
5. The weekly run never applies ApplicationSets and never relaxes the egress policy (assert on the
   stubbed kubectl log).

Mutations: drop the required-list filter (test 4 red); let the weekly run continue past Step 4
(test 5 red).

## What NOT to do

- Do not change what the weekly drill measures, its budget, or V0.
- Do not allow egress in any run that has restored data (unless the operator picks option B).
- Do not create a PR, skip hooks (`--no-verify`), commit to `main`, or touch files not named here.
