## Problem

Agent Dispatch reports **Time to land** using `land.ts - earliest(start.ts)` in `bin/k3dm-dispatch-metrics`. This is wall-clock turnaround time, not worker execution or active engineering time. GPT-6-Luna can finish worker execution in a few minutes yet take many minutes/hours to land while its coordinator pauses or awaits operator instructions; Claude/Opus generally advances autonomously. A high landing time is therefore not evidence of slow code generation. Live verification takes place *after* the controlled landing step and is not part of this metric.

The exporter already exposes sum-of-worker-run execution time and `land.wait_seconds`, but does not expose the **final worker exit → land** gap as a per-spec/aggregate metric, nor track *explicitly reported* human continuation prompts. Model comparisons are additionally confounded unless actual coordinator and worker identities are known; never infer a model from a default.

The Codex worker does **not** commit or land code. The authorized `--land` workflow executes tests and scope checks, integrates work and emits the authoritative `land` event. This must remain unchanged.

## Design

1. **Preserve and clarify existing elapsed time.** Keep existing `k3dm_dispatch_task_elapsed_seconds` and `k3dm_dispatch_elapsed_minutes_per_landed` definitions and series unchanged. Rename the display to **Dispatch-to-land elapsed (wall clock)**. Document `earliest(start.ts) → land.ts`, including retries, idle time and overnight waits.
2. **Final exit-to-land gap.** Compute `max(0, land.ts - last qualifying codex_exit.ts)`, selecting the latest `codex_exit` for the same task whose timestamp is at/before `land.ts`. Emit `k3dm_dispatch_task_post_exit_land_seconds{window,version,slug[,repo]}` and `k3dm_dispatch_post_exit_land_minutes_per_landed{window}` (mean over eligible landed tasks). Reject invalid/non-finite timestamps; omit missing values, never substitute zero. This measures a *wall-clock gap*, not proven human wait or active review. A resumed task uses its final exit; do not claim the metrics form an additive time breakdown.
3. **Operator intervention signal.** Provide an append-only, explicitly operator-initiated event for a known task, with controlled reasons `continue_prompt`, `clarification`, `correction`, `other`. Exact interface to be designed in implementation (candidate: `bin/k3dm-codex-dispatch intervention --slug SLUG --reason REASON`). Record time/task/reason; refuse unknown tasks, invalid reasons and unauthorized worker self-report. Distinguish *tracking enabled with no interventions* from *historical tracking unknown* by writing an explicit coverage-start marker. Do not mine chat logs or guess how many prompts were sent. These are manual observable events, not a claim that all human effort is measured.
4. **Dashboard.** Add **Final worker exit → land** column to Per spec (N/A if unavailable), corresponding aggregate, and **Human continuation prompts** with tracking coverage denominator and reason breakdown. Preserve existing window/release selectors, existing panels/IDs where possible, 50-task cap, and upcoming `repo` dimension. Tooltips distinguish worker time, final-exit gap, total elapsed, independently verified delivery and post-land live verification.
5. **Evidence, compatibility and safety.** Additive ledger events only, historical events unchanged, no invented model attribution or backfilled interventions. Existing readers must ignore unknown event types. No change to `--land` authorization, tests, commits, no auto-land. Bound metric cardinality and fail closed on invalid input.

## Operational Requirements

No new pod, daemon, credential, or cloud access. CPU cost is bounded by the existing ledger scan and 50-task per-window cap; do not introduce unbounded per-event labels. Rollback is code/dashboard revert only; additive events remain readable/ignorable. Proof: metric values reconcile against known ledger timestamps and an actual operator intervention is shown with correct coverage in Grafana after metrics push.

## Rules

- Edit only the listed files for implementation; do not touch `memory-bank/` or unrelated providers.
- Preserve existing Prometheus series meaning; keep missing data distinct from measured zero.
- Run `shellcheck` on touched shell scripts, BATS suites and pytest metrics tests; record exact outcomes, never claim live verification without it.
- Do not grant dispatched Codex workers commit/land authority or create a PR.

## What NOT to Do

Do not change the dispatch lifecycle or landing gate to shorten recorded time. Do not assume slow landing means slow Codex execution. Do not silently backfill, rewrite or deduce human-intervention records. Do not conflate landed with live-verified.
