## Problem

`bin/k3dm-codex-dispatch` already starts isolated Codex worktrees on task branches, records
task status and supports local verification and landing. However, its `start` operation
is not exposed as a narrowly authorized remote operation. An operator away from the
Mac cannot use Slack to request an approved implementation and collect bounded results
using the existing webhook/cloud-bridge job machinery.

Exposing the entire executable, or adding a generic Make target with arbitrary arguments,
would cross several trust boundaries: `start --network` grants network access,
`resume --prompt-file` reads arbitrary local instructions, `land --test CMD`
executes `bash -c` and fast-forwards the release checkout, and `abandon --yes`
removes task worktrees. In the current implementation `land` is *not* a PR gate.

The operator's intended workflow is autonomous development on a branch,
testing on M2/vCluster by default and on a short-lived, restricted ACG AWS sandbox
only when real AWS verification is necessary, followed by PR/CI and independently
approved integration. The Hub and Hostinger are not disposable test targets.

## Goals and decisions

1. **Admin-only remote start.** A verified Slack user ID explicitly mapped
   to `admin` can request a remote dispatch. Other users, unmapped Slack IDs,
   bearer-only callers and the ordinary cloud-reader/cloud-runner identities
   cannot start work. Claude running locally retains the existing local CLI route;
   do not impersonate a Slack user for Claude.
2. **Narrow operations.** Initial remote surface: `codex-status` (bounded
   read-only) and `codex-start` (approved spec + explicit confirmation).
   No remote `land`, `resume`, `abandon`, arbitrary `--network`,
   arbitrary test command, or `--allow-out-of-scope`.
3. **Cloud-authored spec synchronization.** Before dispatch, fetch the release branch from origin and resolve the exact newly committed `docs/plans/` or `docs/bugs/` document, even when it was created by ChatGPT through GitHub and is absent from the Mac checkout. Never overwrite uncommitted local work or silently move the release branch.
4. **Task isolation.** Preserve dedicated worktree + task branch, pinned
   source spec/ref and scope verification. Codex does not modify the shared
   operator checkout or promote its own changes.
4. **Execution boundary.** Execute agent-controlled code/tests only in an
   isolated execution environment. Default: M2 disposable vCluster for Kubernetes
   integration. Optional: ACG disposable AWS sandbox for EC2/SSM and real-cloud
   E2E. Pure offline tests can run in a constrained local/container sandbox.
   Never give this executor access to Hub or Hostinger credentials/endpoints.
6. **Promotion boundary.** Require reviewed PR and CI for promotion into the
   chosen release branch. Explicit approval is required before PR merge,
   deployment or any operational Hub/Hostinger action. Existing local
   `codex-land` may remain for other workflows, but must be unavailable to
   the remote dispatch route.
7. **Observable and recoverable.** A task has a durable ID, owner, reviewed
   spec identity, start/finish timestamps, state, target environment,
   bounded diagnostics and verification artifacts. Disconnects, ACG expiry,
   cancellation, stale locks and cleanup cannot silently become success.
8. **Reuse first.** Reuse existing webhook job framework, scoped token/role
   policy, Cloudflare Slack relay, vCluster and ACG E2E automation. Do not
   create a second generic remote shell or bypass the bridge's allowlist.

## Existing interfaces and constraints (verified on v1.43.5)

- `scripts/lib/webhook/auth.py` loads `K3DM_SLACK_ROLE_MAP` from env/Keychain
  (`<SlackUserID>:admin|operator|reader`); unmapped IDs resolve to reader.
  `scripts/lib/webhook/policy.py` implements ranked roles and separate
  unranked `cloud-runner` capabilities. Token role alone is not a unique
  Slack-user identity.
- `scripts/lib/webhook/make_targets.py` is the `/k3dm` target catalog;
  `scripts/lib/webhook/cloud_actions.py` is a separate fixed-action allowlist.
  Do not automatically inherit an admin endpoint into cloud-bridge.
- `bin/k3dm-codex-dispatch start --spec PATH [--slug SLUG] [--network]`
  checks a tracked clean spec and a pushed release checkout, creates a
  `task/<version>/<slug>` worktree, then launches Codex.
- Current `start` explicitly fetches `origin/<release>`, then refuses unless local `HEAD` equals the fetched remote ref; cloud-created plans/bugs can therefore be invisible or blocked until a safe sync occurs. A plain `git pull` is not safe while Claude or the operator has uncommitted work.
- Its `land --test CMD|--no-test` can run a caller-chosen shell command and
  fast-forward the operator checkout. It must *not* be routed from Slack/cloud.
- `make e2e` and `make e2e-remote` provide reusable disposable vCluster
  testing; `make e2e-sandbox-provision` can provision ACG before testing.
  Examine current implementation/runner placement before wiring them to tasks.
- ACG's operator-described `cloud_user` is restricted, used here for VM/SSM,
  with rotating session credentials (normally 4 hours, optionally extended
  for another 4). The expiry is an operational limit, not a substitute for
  verifying the current effective IAM policy.

## Proposed implementation

### 1. Remote API and identity gate

Add **distinct** `codex-status` and `codex-start` actions to the existing
webhook/Slack command path. Do not expose the entire dispatcher executable.
For `codex-start`:

- Authenticate Slack's signed request at the ingress/relay boundary, bind the
  validated Slack user ID to the request, and independently verify its identity
  binding at the webhook (e.g., signed trusted identity envelope or a
  server-side verified session). **Do not trust body `slack_user_id` or
  `X-K3DM-Role` alone**, even when accompanied by a shared admin bearer token.
- Require both caller's mapped Slack role = `admin` and a distinct dispatch
  capability approved for that user; ordinary `operator`, `reader`, unknown,
  direct bearer-only and cloud-runner calls are denied and audited.
- Keep the requested spec path under canonical `docs/plans/*.md` or
  `docs/bugs/*.md`; require Git-tracked, clean, pushed and an approved
  immutable revision. Resolve/validate the real path under the repository,
  refuse symlinks, traversal, option injection and unsupported refs.
- Parse the spec's `**Approval:**` metadata for triage, **but do not treat
  an editable approval line as an authentication/authorization decision**.
  Store the operator's approval against `(spec path, approved commit SHA,
  spec blob SHA, requesting Slack user ID, chosen test tier)` in a trusted
  server-side approval record. Reject a changed spec pending reapproval.
- Show a preview of spec, base SHA, intended task branch, allowed test
  environment, expected costs/time, and resource limits before `confirm`.
  Confirm must reference the same approved immutable request, must expire,
  be single-use and be idempotent for duplicate Slack deliveries.
- Keep response formatting bounded and redact credentials, tokens and
  potentially sensitive file/log contents. Log actor and decision, not secrets.

For `codex-status`, permit read-only access under existing reader policy
only after bounding/redacting the result and deciding whether other users
may see task names. Prefer restricting detailed task logs to the task owner
or an admin.

### 2. Remote job orchestration, no shell passthrough

Add a small, fixed-argv dispatch wrapper (exact name decided during implementation)
that calls only the allowed `start` and `status` operations of
`bin/k3dm-codex-dispatch`. Use subprocess argument arrays; do not use shell
string concatenation. A generic `make codex-dispatch ARGS=...` endpoint is
explicitly forbidden.

- Record `request_id`, approved spec identity, task ID, requester, target,
  worker host, PIDs, timestamps and terminal state.
- Enforce one active task per slug, a global bounded concurrency limit, a
  separate lock around Git worktree/branch creation and a finite maximum runtime.
  The existing landing lock is insufficient for remote start coordination.
- Handle interrupted jobs, PID reuse, dispatcher failure, unavailable worker,
  out-of-date release ref and duplicate/replayed requests.
- Treat completed implementation as **awaiting verification**, not landed or
  merged. Return a bounded list of changed files, exit code and artifact IDs.
- Local CLI behavior remains backwards compatible; do not change existing
  `land` into a remote endpoint.

### 2a. Fetch and reconcile cloud-authored specs before dispatch

Support specs/bugs created from GitHub by ChatGPT, Claude cloud sessions, or other authorized cloud writers. A release branch on the Mac can legitimately lag the remote; synchronizing it must not disturb Claude's ongoing work.

- Fetch the **explicit allowlisted release ref** from `origin` using a fixed refspec; verify remote ownership, branch syntax and fetch result. Never execute Git commands supplied by a cloud request or trust a `cloud-requests` data branch as the source of executable specs.
- Resolve the requested `docs/plans/*.md` or `docs/bugs/*.md` path from the **fetched remote commit** and validate the canonical relative path, file mode (regular file, not symlink), content and pinned blob SHA. Allow a newly pushed file missing locally; don't require a preexisting Mac working-tree copy simply to discover it.
- Preferred implementation: create the **isolated task branch/worktree directly from the pinned `origin/<release>` commit**, leaving the operator's checkout untouched. Refactor the existing `start` precondition instead of requiring `HEAD == origin/<release>` for this safe remote mode. A post-fetch force-push or changed spec/blob must cause refusal and a new approval.
- If the operator also requests local release-checkout synchronization, use a **separate, serialized fast-forward-only path**: verify correct checked-out release branch, clean index/worktree and no conflicting active release/landing operation; `git merge --ff-only` the validated fetched ref. If dirty, diverged, detached, unavailable or locked, report `sync_blocked` and preserve all local changes. Never `reset --hard`, auto-stash, rebase, force-pull or auto-commit. Dispatch may still safely use the pinned remote worktree after an explicit policy decision; do not report the operator checkout as synchronized when it is not.
- Bind approval, task base, audit and verification artifacts to `(release ref, fetched commit SHA, spec path, spec blob SHA)`. The task's scope allowlist must be read from that immutable blob, not the mutable worktree document.
- A remote repo update that lands while a dispatch is in progress does not rebase the running agent implicitly. Record `remote_ahead` and require a controlled PR/CI reconciliation during handoff.
- Handle absent specs, fetch failures, non-fast-forward remote rewrite, dirty or diverged checkouts, concurrent Claude changes and stale confirmations with clear non-destructive errors.

### 3. Execution isolation and environment routing

Choose the target from an explicit enum: `offline`, `m2-vcluster`,
`acg-aws`. There is no `hub`, `hostinger` or arbitrary kube-context
selection. The server validates the target, not the agent prompt.

- **Offline:** use disposable container/OS-level isolation and block real
  host-mutating tools. The worktree and per-task state may be mounted/writable,
  but Mac Keychain, Vault materials, kubeconfigs, SSH credentials, Docker
  host socket and hub management endpoints must not be accessible.
- **M2/vCluster (default integration):** create a task-scoped disposable vCluster
  via existing supported provisioning. Give the execution worker only a
  vCluster-specific kubeconfig/service account with least-privilege RBAC,
  CPU/memory/storage quotas, network restrictions and TTL. Limit underlying
  host-cluster permissions and deny access to hub/Hostinger.
- **ACG AWS (explicit opt-in):** route only through existing ACG session
  acquisition/Playwright provisioning and approved E2E paths. Use current
  restricted, expiring ACG credentials; verify effective EC2/SSM permissions,
  disallow cross-account/non-ACG access, and set a session-time budget before
  launching long jobs. Never export the AWS credentials to Git, Slack logs,
  task artifacts, or the general M4 dispatcher.
- Distinguish Codex **code generation** from **execution of generated code**:
  a vCluster kubecontext environment variable alone cannot sandbox shell
  commands running on macOS. Validate the isolation of the actual Codex
  process, its child processes and the test runner before allowing networked
  remote jobs.
- Prevent task payloads from selecting raw executable paths or overriding
  `K3DM_*`, `HOME`, `KUBECONFIG`, AWS auth paths or run directories.

### 4. Validation and evidence

Provide a two-tier gate: offline/unit/BATS/shellcheck as relevant, then
M2/vCluster integration by default, with ACG real-cloud E2E only when
spec-required and explicitly selected. Reuse existing job artifact retention,
test classification and Grafana metrics where applicable.

- Bind evidence to task SHA, spec SHA, environment ID, test command ID
  (from fixed allowlist), start/finish times, exit state and cleanup result.
- Do not call an ACG timeout or session expiry a test failure in the code;
  classify infrastructure expiration separately and retain partial evidence.
- If tests or verification fail, create an actionable result for Claude/the
  operator; do not auto-merge, run `land`, deploy or alter Hub/Hostinger.

### 5. PR handoff and promotion

The remote workflow may generate a **PR candidate** and a structured
verification summary. Only an explicitly approved, narrow GitHub credential
may push task branches/create PRs after review of proposed file changes;
do not grant the Codex execution process a write-capable release token.

- Validate branch target and changed-path scope against the **pinned base
  spec**, verify Git diff and require CI. Detect untracked and binary files.
- PR base is the intended release branch, never `main` by default.
- No automated PR merge, direct release fast-forward, `--no-test`,
  `--allow-out-of-scope` or operational deployment from remote dispatch.
- Claude/operator verification is a distinct state and action. PR approval
  and final promotion remain separate trust decisions.

### 6. Slack and cloud-bridge rollout

Stage A (read-only): bounded `/k3dm codex-status`, regression tests for
authorization, identity, response redaction and role caps.

Stage B (Slack admin): preview + confirm + start of a pinned spec using
the isolated offline/M2 worker. Initially concurrency 1 and no ACG/PR
automation until live E2 evidence is collected.

Stage C (cloud ACG and PR handoff): enable explicit `acg-aws` tier and
optional PR-candidate creation only after the first two stages prove safe.
If future cloud-bridge dispatch is wanted, create **a new scoped capability**
with separate operator approval on the Mac; never widen the existing
reader/cloud-runner credential to general code execution or accept arbitrary
GitHub-branch requests.

Every stage should include rollback that disables its route while leaving
the ordinary local `codex-dispatch` workflow functional.

## Tests (every new negative test must fail on the pre-fix code or deliberate mutation)

1. **Cloud-created spec fetch/sync:** temp origin receives a new tracked plan after the local clone is created; remote dispatch discovers the new file from the explicit fetched release ref, pins the approved commit/blob and starts its worktree while the operator checkout remains unchanged. Separate optional local sync fast-forwards only a clean checkout; dirty, diverged, detached, missing-ref and concurrent-checkout mutations fail closed with no local data loss. Verify stale-approval and remote-force-push refusal.
2. **Identity and authorization:** mapped admin succeeds with valid confirmation;
   mapped operator/reader, unknown ID, direct bearer, forged/mismatched
   identity, invalid/replayed Slack request and cloud-runner fail closed.
3. **Spec integrity:** tracked approved SHA and canonical allowed path succeed;
   edited doc, stale SHA, symlink, traversal, unsupported path, expired approval
   and approval-line-only spoof fail.
4. **Argument safety:** every forbidden subcommand/flag/test command/environment
   override is refused before executing Codex. Recorded argv cannot contain
   `bash -c`, `land`, `--network` or credentials.
5. **Dispatcher jobs:** concurrent duplicate request returns the same durable
   job, not a second worktree; separate jobs respect resource limit; stale PID,
   timeout, crash and cancellation produce accurate terminal states.
6. **Test isolation:** deliberately try to access Hub/Hostinger kubeconfig,
   Keychain/SSH/Vault and API endpoints from the actual executor; all denied.
   Verify M2 worker cannot reach or modify the underlying host cluster beyond
   the vCluster's bounded namespace/capabilities.
7. **ACG session:** simulated expiry/failed renewal blocks or aborts appropriately,
   without leaking secret material; real-cloud E3 only after approval.
8. **PR boundary:** remote route contains no call to `land`, `git merge`,
   release ref push or deployment. Only an approved PR candidate is created.
9. **Regression:** existing `scripts/tests/bin/codex_dispatch.bats`,
   webhook role tests, Slack relay tests and cloud-bridge validation remain green.
10. **Mutation:** weaken user binding, drop spec-SHA match, permit host context,
   allow shell test CMD, skip cleanup, or add implicit merge; each change must
   make an appropriate test fail.

Offline fixtures must not contact real GitHub, Slack, Codex, Kubernetes,
ACG, Vault, Keychain, Pushgateway or the operator's worktrees.

## What NOT to Do

- Do NOT add a generic `execute`, shell, arbitrary Make target or `ARGS` passthrough.
- Do NOT use an ordinary admin bearer token or user-supplied Slack ID alone as remote-dispatch authorization.
- Do NOT grant the cloud-reader/cloud-runner credential general code execution.
- Do NOT expose `land`, `resume`, `abandon`, `--no-test`, `--allow-out-of-scope`, `--network` or raw `--test CMD` remotely.
- Do NOT execute Codex/tests on Hub or Hostinger or give the executor access to their secrets.
- Do NOT assume a vCluster kubeconfig isolates a macOS process or that short-lived ACG credentials allow only EC2/SSM without IAM verification.
- Do NOT use `git reset --hard`, auto-stash, rebase, force-pull or automatic branch switches to synchronize the Mac checkout; never overwrite Claude/operator local edits.
- Do NOT merge to `main`, create an unapproved PR, skip hooks (`--no-verify`), or perform a live cluster change as part of spec filing.
- Do NOT let this proposal automatically authorize implementation or deployment.
