## Problem

A promote needs a human "yes" that a phone can give, without weakening the typed confirmation at the terminal. The umbrella's design was
a JSON file per request plus a TOTP code. The blind review found that file forgeable by any process of the same user (a hand-written
`"approved"` record), the state machine under-specified (what a failed code does, what is checked first, what happens at expiry while a
promote is running), and the acceptance not self-contained. Operator decision P1 (2026-11-18): every record is HMAC-signed with a key held
in the macOS Keychain; the store ignores environment overrides unless an explicit test mode is on. This part is the library, a small CLI
and the pytest suite. It does not touch `bin/k3dm-hub-promote` (Part 2b) and does not talk to Slack (Part 3).

## Behaviour

All paths and names below are exact. "Now" is the wall clock in whole UTC seconds (`int(time.time())`).

**A. Files, names and modes**

1. Library `scripts/lib/hub_approval.py` (no third-party imports; `hashlib`, `hmac`, `json`, `os`, `secrets`, `subprocess`, `time`,
   `fcntl`, `re`, `pwd` only). CLI `bin/k3dm-hub-approval` (Python, executable, imports as in `bin/k3dm-cloud-request:4-15`: `sys.path.insert` of `scripts/lib`, then `import hub_approval`).
2. Store directory `<HOME>/.local/share/k3d-manager/promote-approvals`, mode 0700 (created with 0700; a wider existing mode is tightened
   or refused with `approval store is not private`; the check uses `os.stat` on the directory). Files inside, mode 0600:
   `<id>.json` one record; `totp-state.json`; `promote-audit.jsonl` (append only); `.lock` (the `fcntl.flock` file).
3. `<HOME>` is `pwd.getpwuid(os.getuid()).pw_dir`, never the environment `HOME` (an attacker-set `HOME` must not move the store).

**B. Production mode and test mode (P1)**

4. Production mode (the default) reads **no** environment variable for the store directory, the operator id, the `security` binary
   path, the clock or the TOTP secret. The Keychain tool is always `/usr/bin/security` by absolute path.
5. Test mode is on only when the environment variable `K3DM_PROMOTE_TEST_ROOT` names an existing directory that contains a regular
   file named `.k3dm-promote-test-root`. In test mode: the store directory is `<K3DM_PROMOTE_TEST_ROOT>/store`, the `security` command is
   the executable named by `K3DM_PROMOTE_TEST_SECURITY` (required in test mode), the clock is the integer in
   `K3DM_PROMOTE_TEST_NOW` when set, and every record it writes carries `"test": true`. In production mode a record with `"test": true`
   is refused (`approval <id> is a test record`); in test mode a record without `"test": true` is refused the same way. If
   `K3DM_PROMOTE_TEST_ROOT` is set but the sentinel is missing, every command exits 4 with `test mode requested but the sentinel is missing` (it never falls back silently).
6. Residual risk, stated plainly: the Keychain items are readable by any process running as the same macOS user (the item is not
   restricted to one binary), and the sentinel file is creatable by that user. A same-user attacker who can run `/usr/bin/security`
   can therefore read the HMAC key and forge a record. P1 removes the cheap forgery (editing a JSON file or setting an environment
   variable) and stops a record from a different machine or an older key; it does not stop a same-user attacker with shell access. A
   different principal (a separate macOS user or a signing helper behind a socket) would; that is an open question, not in this part.

**C. Record and integrity**

7. Record `<id>.json`, one JSON object, keys exactly:
   `schema` (1), `id`, `sha` (40 or 64 lowercase hex), `branch` (string matching `^k3d-manager-v[0-9]+\.[0-9]+\.[0-9]+$`),
   `nonce_sha256` (hex of SHA-256 of the nonce; the nonce is never stored), `channel` (`slack` | `cli` | `test`), `requested_by` (string,
   1-64 chars of `[A-Za-z0-9._:@-]`), `created` (int), `expires` (`created + 900`), `state`, `approver` (null or string), `approved_at`
   (null or int), `totp_step` (null or int), `failed_attempts` (int, 0-5), `reason` (null or enumerated refusal code), `outcome` (null |
   `moved` | `failed`), `outcome_reason` (null or enumerated), `test` (bool, only present and true in test mode), `hmac`.
8. `id` is `a-` followed by 16 lowercase hex characters from `secrets.token_hex(8)`; the id regex everywhere is `^a-[0-9a-f]{16}$`. A
   malformed id (or one with `/`, `..` or NUL) is refused with `approval id is malformed` before any path is built.
9. `hmac` is lowercase hex HMAC-SHA256 of the canonical JSON of the record without the `hmac` key
   (`json.dumps(rec_without_hmac, sort_keys=True, separators=(",", ":"), ensure_ascii=True)`), keyed by the bytes of the Keychain item
   service `k3dm-promote-hmac-key`, account `k3dm` (a 64-hex-character string, the key is the 32 decoded bytes). Compared with
   `hmac.compare_digest`. Any record whose `hmac` is missing or wrong, or whose JSON has keys other than the list in item 7, or any value outside the
   shapes above, is refused `approval <id> failed integrity check` (exit 4) and never read further.
10. Every write is: build the full record, sign it, write `<id>.json.tmp` mode 0600, `fsync`, `os.replace`. Every read-modify-write
    holds `fcntl.flock(LOCK_EX | LOCK_NB)` on `.lock` and retries for at most 5 seconds; failing that, `approval store is busy` (exit 4).
11. `totp-state.json` is signed the same way (key `hmac`), keys exactly `schema`, `last_step` (int, 0 when none), `fail_count` (int),
    `window_start` (int), `locked_until` (int, 0 when none), `last_now` (int), `hmac`. Missing or unsigned `totp-state.json` while any
    `<id>.json` holds a non-null `totp_step` refuses with `approval <id> failed integrity check` (fail closed); with no such record it is created as
    `last_step 0`, counters 0.

**D. Keychain reads (P1, fail closed)**

12. The three items, all read with `/usr/bin/security find-generic-password -s <service> -a k3dm -w` (the value arrives on stdout of that call; nothing is put in an argument):

    | service | content | used by |
    |---|---|---|
    | `k3dm-promote-hmac-key` | 64 hex characters | every record and `totp-state.json` signature |
    | `k3dm-promote-totp-secret` | base32 RFC 4648 secret, 32 characters, no padding | `approve` |
    | `k3dm-promote-operator-id` | the approver id, 1-64 chars of `[A-Za-z0-9._:@-]` (for Slack, `U` followed by letters/digits) | `approve`, `deny`, `consume` |

13. Exit code of `security`: 0 means read; 44 means the item does not exist (captured, see Proof); **any other** exit code (locked keychain, user
    denial, missing binary, timeout of 10 seconds) is a refusal `cannot read <service> (security exit N)` (exit 4, `N` is the code or `timeout`, `missing`), never an approval and never a failed-code count.
    Exit 44 gives `TOTP is not set up` (secret item), `approval store is not set up` (HMAC key; exit 4) or `operator id is not configured` (operator item; exit 1).
14. The operator id is read from the Keychain item only; the umbrella's environment variable is not read (decision recorded under Open questions).

**E. State machine and check order**

15. States: `pending`, `approved`, `denied`, `expired`, `refused`, `consumed`. Transitions, nothing else is legal:
    `pending -> approved | denied | expired | refused`; `approved -> consumed | refused | expired`; `consumed` is final except that `outcome` goes
    from null to `moved` or `failed` exactly once. `denied`, `expired`, `refused` are final.
16. `approve` runs these checks in this order and stops at the first failure; the order is part of the contract:
    1. id regex, record read, signature, `test` flag (`approval id is malformed`, `approval <id> not found`, `approval <id> failed integrity check`);
    2. state is `pending` (else `approval <id> is not pending (state: <state>)`);
    3. `now < expires` (else the record becomes `expired` and `approval <id> expired at <ISO UTC>`); expiry compares `now >= expires` as expired, so `expires - 1` is valid, `expires` and `expires + 1` are expired;
    4. clock-rollback guard: `now < totp-state.last_now` refuses `clock moved backwards` (exit 4) and nothing is written; otherwise `last_now` is set to `now` with the write below;
    5. global lock: `now < locked_until` refuses `approvals are locked until <ISO UTC>` (no count, nothing written);
    6. nonce: SHA-256 of the given nonce, `hmac.compare_digest` to `nonce_sha256`; mismatch refuses `nonce does not match` and counts toward the global throttle only;
    7. approver: given `approver` equals the Keychain operator id, else `approver is not the operator`; counts toward the global throttle only;
    8. code: six digits (any other shape is `TOTP code rejected` and counts), RFC 6238 SHA-1, 6 digits, 30-second step, window of steps `t-1`, `t`, `t+1` where `t = now // 30`, accepted only when the matching step is strictly greater than `totp-state.last_step`; a wrong, replayed (step `<= last_step`) or malformed code refuses `TOTP code rejected`, counts toward the global throttle and adds 1 to the record's `failed_attempts`; the fifth failed code sets the record `refused` with reason `too_many_codes` and the message `too many failed codes`.
17. Throttle, global (`totp-state.json`): every counted failure (nonce, approver or code, on any record) adds 1 to `fail_count` after resetting `fail_count` to 0 and `window_start` to `now` when `now - window_start >= 900`; reaching 10 sets `locked_until = now + 900`. A success resets `fail_count` to 0.
18. Success of `approve`: write order is first `totp-state.json` (`last_step` = the matched step, counters cleared, `last_now`), then the record (`approved`, `approver`, `approved_at`, `totp_step`), so a crash between the two writes leaves the code burned and the record still pending (fails closed).
19. `deny` runs checks 1-3, 4-5, 6 and 7 as above (no code), and on success writes `denied` with `approver` and `approved_at`; it needs no TOTP (a denial cannot cause harm) but is subject to the same lock and nonce and approver checks.
20. `consume` (called by the promote, Part 2b) holds the store lock, reads the clock **again**, and requires all of: record valid and signed, state `approved`, `now < expires`, the given `--sha` equals the record `sha` (else `approval <id> is for <sha7>, not <given7>`; the record is not changed), approver equals the **current** Keychain operator id, `totp_step` is an int. Then it writes `consumed` and prints nothing else. Otherwise exit 1 with the matching refusal (`approval <id> is not approved (state: <state>)`, `approval <id> expired at <ISO>` and the record becomes `expired`).
21. `refuse --id ID --code CODE [--detail SHA7]` (called by Part 2b to burn a record whose precondition failed): allowed from `pending` or `approved`; sets `refused`, `reason = CODE`. `CODE` must be one of `sha_mismatch`, `not_contained`, `not_newest_green`, `not_newest_branch`, `too_many_codes`, `operator_refused`, otherwise exit 2. `--detail` must match `^[0-9a-f]{7}$`.
22. `outcome --id ID --result moved|failed [--reason CODE]` is allowed only from `consumed` with `outcome` null and sets it once (second call: `approval <id> outcome already set`, exit 1). `CODE` one of `none`, `push_failed`, `tag_failed`, `appsets_failed`, `platform_ops_failed`.
23. Expiry is evaluated lazily; the `expire` event is written the first time a read finds `now >= expires` on a non-final record, which then becomes `expired`.

**F. Create and the nonce (library only)**

24. `hub_approval.create_record(sha, branch, channel, requested_by)` returns `(id, nonce)`; `nonce` is `secrets.token_hex(16)` (32 hex chars). It validates `sha`, `branch` (the regex in item 7), `channel` and `requested_by`, stores the record `pending` with `failed_attempts` 0. The CLI has **no** `create` subcommand and no command prints a nonce; Part 3's bridge imports the library and puts the nonce only in the Slack button payload.

**G. CLI**

25. `bin/k3dm-hub-approval <subcommand>`; stdout is only what is listed, diagnostics go to stderr. Exit codes: 0 ok; 1 refused; 2 usage; 4 infrastructure (busy, integrity, Keychain, test-mode misconfiguration). Subcommands:
    - `show --id ID` prints one line `id=<id> state=<state> sha7=<7> branch=<branch> channel=<channel> expires=<ISO UTC> approver=<approver|-> outcome=<outcome|->` (it never prints `nonce_sha256`, `hmac` or `totp_step`), exit 0; a record that fails any check of item 16.1 exits as there.
    - `approve --id ID` reads **stdin** one JSON object with exactly the keys `nonce`, `approver`, `totp` (any other key set: `approve input must be exactly nonce, approver, totp`, exit 2; nothing is accepted in arguments or environment). Prints `approved <id>` on success.
    - `deny --id ID` reads stdin exactly `nonce`, `approver`. Prints `denied <id>`.
    - `consume --id ID --sha SHA` prints `consumed <id>`.
    - `refuse --id ID --code CODE [--detail SHA7]` prints `refused <id> <code>`.
    - `outcome --id ID --result moved|failed [--reason CODE]` prints `outcome <id> <result>`.
    - `totp-setup [--rotate] [--operator-id ID]`: refuses with exit 1 `totp-setup must run in a private terminal` when `$TMUX` is set or stdin/stdout is not a TTY. Without `--rotate` it refuses when the secret item exists (`TOTP is already set up; use --rotate`). It generates a 20-byte random secret, base32 without padding, writes it with `/usr/bin/security add-generic-password -U -s k3dm-promote-totp-secret -a k3dm -w <secret>` (the only place a secret is in an argument; it is a one-time local setup the operator runs at a terminal, and the umbrella's Keychain pattern is followed), creates `k3dm-promote-hmac-key` (32 random bytes as 64 hex) when absent, writes `k3dm-promote-operator-id` when `--operator-id` is given, and prints the `otpauth://totp/k3d-manager-promote?secret=<secret>&issuer=k3d-manager&algorithm=SHA1&digits=6&period=30` URI **only to the terminal** (never to a pipe, never to the audit file). Rotate also resets `totp-state.json` `last_step` to 0 and signs it.
26. No subcommand returns the nonce, the TOTP secret or the HMAC key. `--help` text shows only the above.

**H. The Part 3 contract (P3)**

27. Part 3's bridge handles an approve click by writing, on stdin of `bin/k3dm-hub-approval approve --id <id>`, `{"nonce": "<hex>", "approver": "<slack user id>", "totp": "<six digits>"}`. A code is valid for at most about 90 seconds (steps `t-1..t+1`), so Hermes must drain `p` (promote) approval ids as soon as the click arrives and not on its 300-second poll. This part only fixes the stdin contract and states the timing; the Hermes change is Part 3.

**I. Audit**

28. Every create, approve, deny, consume, refuse, expire, TOTP-failure and outcome appends one JSON line to `promote-audit.jsonl`: `ts` (ISO UTC), `event` (`create|approve|deny|consume|refuse|expire|totp-fail|outcome`), `id`, `sha7`, `channel`, `actor` (the given approver or `-`), `result` (`ok|refused`), `reason` (enumerated, never free text, never a nonce, code, secret or key). The write is best effort: a failure to append is an error to stderr, it does not change the decision.

## Worker definition of done

Before the last message the worker does all of these and pastes the evidence.

   - `perl -e 'alarm shift; exec @ARGV' 1800 make test-pytest` (the whole pytest tree stays green)
   - `perl -e 'alarm shift; exec @ARGV' 1800 python3 -m py_compile scripts/lib/hub_approval.py bin/k3dm-hub-approval`
   - `shellcheck` and the awk if-count check do not apply (no shell in this part), say so.
2. Every fixture asserts its target first: the store is under pytest `tmp_path`, the sentinel is there, `K3DM_PROMOTE_TEST_SECURITY` names the stub
   inside `tmp_path`. No test may run `/usr/bin/security`, read the real Keychain or write the real home. A test that proves production-mode behaviour (the absolute path, the passwd home) does it
   by running the library with a patched `subprocess` and `pwd` seam inside a subprocess whose `HOME` is a scratch directory, never a real call.

   whose test stayed green with the guard broken, and show its positive control.
4. The RFC vectors are the proof for TOTP; there is no real-data run on this host (needs the operator's Keychain); say so.
5. List every place the worker chose something the spec did not decide.
6. Hard limits: edit only the paths in `## Files`; do not commit; LF endings; no inline comments in code except the host/date capture comments for fixtures
   the test-controls rule requires; no secret in source or in a fixture except the public RFC secret and clearly fake values; never log a nonce, code or key.

## What NOT to do

- Do not add a `create` subcommand or any way to print a nonce, secret or key.
- Do not read `HOME` or any environment variable in production mode; do not add a second test-mode gate.
- Do not call `security` by name through `PATH`; do not put a secret or code in an argument (except the one-time `totp-setup` add).
- Do not store the nonce, a code or the secret in the record, the audit or the state.
- Do not edit `bin/k3dm-hub-promote`, `bin/k3dm-hub-deploy`, the Makefile or any doc (Parts 1 and 2b own them).
- Do not run `make install-*`, lifecycle targets, the network or the real Keychain.
