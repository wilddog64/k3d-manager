## Problem

Once v1.43.15 lands, the hub runs only what `deploy/hub` holds. A dashboard, ApplicationSet or CRD change
on a release branch can then be checked live only by promoting it to the hub, which is what v1.44.0
exists to avoid. Development needs a live cluster that reads the release branch and cannot change the hub.

| Pods, 7-day peak working set (Prometheus) | 4.38 GiB |
| Sum of pod memory requests / limits | 4.17 GiB / 15.79 GiB |

All k3d nodes share the one VM, and each node advertises the whole VM, so the scheduler sees far more
memory than exists. The limits already add up to the VM. A quota caps the dev hub, but nothing reserves
memory for the hub; hence P0 and D3.

### D1 — `make dev-hub-up`, `dev-hub-down`, `dev-hub-status`

- A vCluster named `dev-hub` in its own host namespace `dev-hub`, created with `vcluster_create` and
  `VCLUSTER_NAMESPACE=dev-hub`. It must never use the shared `vclusters` namespace:
  `_vcluster_reconcile_namespace` deletes every other vCluster there, so the next e2e harness run would
  delete the dev hub as an orphan, and the dev hub's creation would delete an e2e run's cluster.
- A values file `scripts/etc/vcluster/values-dev-hub.yaml`. It syncs only the host Services named in D2
  (`networking.replicateServices.fromHost`), and nothing else from the host.
- `dev-hub-up` is idempotent. It needs the hub role (`bin/k3dm-require-role hub`) and the hub context.
- `dev-hub-down` deletes the vCluster and the `dev-hub` namespace, and nothing else.
- `dev-hub-status` (read-only): vCluster phase, quota use (used/hard for memory and CPU), the branch the
  dev hub's ApplicationSets read, and the dev-hub Grafana URL.

### D2 — what runs inside the dev hub

- **ArgoCD**, at the chart version the hub runs (`ARGOCD_CHART_VERSION`), installed with the same values
  template.
- **ApplicationSets** rendered with `K3D_MANAGER_BRANCH=<release branch>` (`make dev-hub-sync`, defaulting
  to the checked-out release branch). The `app-cluster` stage is not applied: the dev hub never deploys
  to ACG or Hostinger. Each Application's destination is the dev hub's own API server only.
- **Grafana** with the branch's dashboards (the platform-ops dashboard ConfigMaps from the branch tree,
  through a `git archive` of the release branch head on `origin`, not the working tree). Its only
  datasource is the hub Prometheus, replicated into the vCluster from host
  `monitoring/kube-prometheus-stack-prometheus`, read-only (HTTP GET query API).
- **No secrets from the hub.** No Vault access, no ESO SecretStore pointing at the hub Vault, no hub
  kubeconfig, no Pushgateway or remote-write target. Grafana's admin password is generated at `dev-hub-up`
  and stored in the macOS Keychain item `k3dm-dev-hub-grafana-admin`.

### D3 — the hub keeps priority

- Host namespace `dev-hub` gets a ResourceQuota: `limits.memory` 3Gi, `requests.memory` 1536Mi,
  `limits.cpu` 3, `requests.cpu` 1500m, `pods` 40; and a LimitRange with default requests and limits so a
  pod without them is admitted inside the quota.
- A PriorityClass `k3dm-dev-preemptible` (value -100, `preemptionPolicy: Never`, `globalDefault: false`).
  Every pod in host namespace `dev-hub` runs at that class, so a hub pod (priority 0 or higher) preempts it
  when scheduling and the kubelet evicts it first under memory pressure. The worker picks the mechanism
  (vCluster sync patch or an admission policy) and states it in the howto; the test checks the result on
  the rendered manifests.
- Alerts, email only, in the existing platform-ops rules: `DevHubNearQuota` when dev-hub memory working
  set is above 90% of its `limits.memory` hard quota for 10m; `HubVmMemoryLow` when the OrbStack VM's
  available memory is below 3 GiB for 10m (from the node exporter or `container_memory` on the k3d server
  node, whichever the hub already scrapes; the worker states which).

### D4 — how a live check works

1. `make dev-hub-sync` (the release branch must be pushed: the dev hub reads `origin`).
2. The operator checks in the dev-hub Grafana (or ArgoCD UI).
3. When it passes, `make hub-promote REF=<that commit>` (v1.43.15).

## What NOT to Do

- Do not run `dev-hub-up`, `dev-hub-sync` or any `make` target against a cluster; tests use stubs and
  rendered manifests. The operator runs E2.
- Do not change OrbStack settings (P0 is the operator's).
- Do not give the dev hub any hub credential, Vault path, kubeconfig or write endpoint.
- Do not use the `vclusters` namespace or change `_vcluster_reconcile_namespace` behaviour for the e2e
  harness.
- Do not change hub ApplicationSets, charts or dashboards, or `deploy/hub`.
- Do not edit CLAUDE.md, `memory-bank/` or `docs/roadmap.md`. Do not commit to `main`, create a PR or skip
  hooks.
- Stubs for `vcluster`, `kubectl` and `helm` take output from a real read-only capture, with host and date
  in a comment beside it.
- Write the must_not tests first and show them red on the pre-fix tree.
