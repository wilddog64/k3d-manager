## Problem

Once v1.43.15 lands, the hub runs only what `deploy/hub` holds. A dashboard, ApplicationSet or CRD change
on a release branch can then be checked live only by promoting it to the hub, which is what v1.44.0
exists to avoid. Development needs a live cluster that reads the release branch and cannot change the hub.

memory than exists. The limits already add up to the VM. A quota caps the dev hub, but nothing reserves
memory for the hub; hence P0 and D3.

### D1 — `make dev-hub-up`, `dev-hub-down`, `dev-hub-status`

- A vCluster named `dev-hub` in host namespace `dev-hub`, created with `vcluster_create` under
  `VCLUSTER_NAMESPACE=dev-hub VCLUSTER_LOCAL_PORT=11444 VCLUSTER_VALUES_FILE=scripts/etc/vcluster/values-dev-hub.yaml`
  (`VCLUSTER_VERSION` stays 0.32.1). Never the shared `vclusters` namespace: `_vcluster_reconcile_namespace`
  (`vcluster.sh:64–79`) deletes every other vCluster there. Port 11444, not the default 11443, because
  `bin/cluster-preflight:555` uses 11443 and may run on the M5.
- `scripts/plugins/dev_hub.sh` sources `vcluster.sh` the way `_e2e_load_deps` does (`scripts/plugins/e2e.sh:24–37`).
- Kubeconfig: `~/.kube/vclusters/dev-hub.yaml` (written by `_vcluster_export_kubeconfig`). Every in-vCluster
  call uses `kubectl --kubeconfig ~/.kube/vclusters/dev-hub.yaml` / `helm --kubeconfig ...`; every host call uses
  `--context k3d-k3d-cluster -n dev-hub` (or cluster-scoped for the PriorityClass only).
- `dev-hub-up` is idempotent, needs `bin/k3dm-require-role hub`, and applies host objects in this order:
  PriorityClass, namespace, ResourceQuota, LimitRange, then `vcluster_create`, then ArgoCD and Grafana (D2).
- `dev-hub-down` must not call `vcluster_destroy`: that calls `_vcluster_deregister_from_hub`
  (`vcluster.sh:102`, 114–142), which deletes ApplicationSets, Applications and the cluster Secret in hub `cicd`.
  It runs `vcluster delete dev-hub -n dev-hub`, `kubectl --context k3d-k3d-cluster delete namespace dev-hub`,
  `_vcluster_remove_proxy dev-hub`, removes `~/.kube/vclusters/dev-hub.yaml`, and deletes nothing else (the
  PriorityClass stays; it is inert without pods).
- `dev-hub-status` (read-only): vCluster phase, quota used/hard for memory and CPU, the branch the dev hub's
  ApplicationSet reads (`targetRevision`), and the Grafana command and URL (D2).

### D2 — what runs inside the dev hub

- **ArgoCD**: chart `argo/argo-cd` at `ARGOCD_HELM_CHART_VERSION` (10.10.5, same pin as the hub), release
  `argocd` in vCluster namespace `cicd`, with a dedicated `scripts/etc/dev-hub/argocd-values.yaml`. Not the hub
  template: it carries LDAP/Keycloak, the Hermes account, ESO health checks and ServiceMonitors (no
  `monitoring.coreos.com` CRD in the vCluster), and limits that alone exceed the quota. The dev values: dex,
  notifications and all `metrics.serviceMonitor` off; `server.insecure=true`, Service ClusterIP; resources per D3.
- **AppProject** `platform` from `scripts/etc/dev-hub/argocd-project.yaml` (not
  `scripts/etc/argocd/projects/platform.yaml.tmpl`, which names external clusters). Destinations only
  `https://kubernetes.default.svc` with namespaces `monitoring`, `default`, `staging`; source repo only
  `https://github.com/wilddog64/k3d-manager.git`; no cluster-scoped resource whitelist.
- **ApplicationSets**: `make dev-hub-sync [BRANCH=<b>]` (default: current branch; refuses `main` and `deploy/hub`;
  refuses a branch whose head is not on `origin`) renders an allowlist with `envsubst` and
  `K3D_MANAGER_BRANCH=<b>` and applies it with the dev-hub kubeconfig. Allowlist: `grafana-dashboards-hub.yaml`
  only. Not applied, ever: `observability`, `platform-ops`, `vectordb` (they need Vault/ESO, CRDs or more memory
  than the quota), `demo-rollout` (needs the Rollouts CRD; operator may add it later), and every app-cluster
  stage file. `dev-hub-sync` must not call `deploy_argocd_applicationsets`, `_argocd_prepare_applicationsets`,
  `_argocd_set_active_app_cluster` or `_argocd_confirm_applicationset_stage`: they hardcode or use the hub context
  (`argocd.sh:1239,1246,1252`, 1582–1605).
- **Dashboards** arrive through that ApplicationSet: the in-vCluster ArgoCD syncs `grafana-dashboard-*.yaml` and
  `k3dm-tests-configmap.yaml` from `origin` at the branch into vCluster `monitoring` (this replaces the earlier
  `git archive` idea; it reads the pushed branch, never the working tree).
- **Grafana**: chart `grafana/grafana` 8.8.2 (Grafana 11.4.0, the hub's version) from
  `https://grafana.github.io/helm-charts`, release `dev-hub-grafana` in vCluster `monitoring`, values
  `scripts/etc/dev-hub/grafana-values.yaml`: `sidecar.dashboards.enabled: true`, `label: grafana_dashboard`,
  `labelValue: "1"`, `searchNamespace: monitoring`; `sidecar.datasources.enabled: false`; persistence off; one
  datasource, provisioned in values: name `Prometheus`, uid `prometheus`, type `prometheus`, access `proxy`,
  `isDefault: true`, url `http://hub-prometheus.monitoring.svc:9090`. Dashboards load only through the sidecar,
  never a ConfigMap volume. The 6 Loki panels show no data (no Loki datasource, by design); the howto says so.
- **Hub Prometheus**: `networking.replicateServices.fromHost: [{from: monitoring/kube-prometheus-stack-prometheus,
  to: monitoring/hub-prometheus}]`. This creates the cluster-wide read-only services/endpoints ClusterRole above;
  the howto carries the one-line justification CLAUDE.md asks for.
- **Access**: `dev-hub-status` prints `kubectl --kubeconfig ~/.kube/vclusters/dev-hub.yaml -n monitoring
  port-forward svc/dev-hub-grafana 13000:80` and `http://127.0.0.1:13000`; the operator runs it. No ingress,
  no NodePort.
- **No secrets from the hub.** No Vault address or token, no ESO, no hub kubeconfig, no Pushgateway or
  remote-write URL. Grafana's admin password is generated at `dev-hub-up` and stored with
  `security add-generic-password -U -s k3dm-dev-hub-grafana-admin -a k3dm` fed through `security -i` on stdin
  (the pattern at `bin/k3dm-machine-secrets:199`), never in argv; it is passed to helm through a values file in a
  `mktemp` dir removed on exit. Not added to `scripts/etc/machine/secrets.hub.list` (optional, recreated by
  `dev-hub-up`).

### D3 — the hub keeps priority

- `scripts/etc/dev-hub/resourcequota.yaml` (host `dev-hub`): `limits.memory` 3Gi, `requests.memory` 1Gi,
  `limits.cpu` 3, `requests.cpu` 1500m, `pods` 30.
- `scripts/etc/dev-hub/limitrange.yaml`: container default limit 128Mi / 200m, default request 32Mi / 20m.
- Budget (limits / requests), set in `values-dev-hub.yaml`, `argocd-values.yaml`, `grafana-values.yaml`:

| Component | Limit | Request |
|---|---|---|
| vCluster control plane (data on a 2Gi `local-path` PVC, not the Memory emptyDir of `values.yaml`) | 768Mi | 256Mi |
| coredns (synced) | 128Mi | 32Mi |
| ArgoCD controller / repo-server / server / applicationset / redis | 512 / 384 / 256 / 128 / 128Mi | 192 / 96 / 64 / 48 / 32Mi |
| Grafana + dashboard sidecar | 384 + 128Mi | 128 + 32Mi |
| Total | 2816Mi (headroom 256Mi for init containers and one restart) | 880Mi |

- PriorityClass `k3dm-dev-preemptible` (`scripts/etc/dev-hub/priorityclass.yaml`): value -100,
  `preemptionPolicy: Never`, `globalDefault: false`. Mechanism: `values-dev-hub.yaml` sets
  `sync.toHost.pods.priorityClassName: k3dm-dev-preemptible`, `controlPlane.statefulSet.scheduling.priorityClassName:
  k3dm-dev-preemptible`, and leaves `sync.toHost.priorityClasses.enabled` and `sync.fromHost.priorityClasses.enabled`
  false (proof above). What this buys: the scheduler preempts dev-hub pods for a pending hub pod, and kubelet
  eviction ranks them first. It does not protect against the kernel OOM killer (it ignores PriorityClass), and
  kubelet eviction rarely fires because each node advertises the whole VM. The quota and `HubVmMemoryLow` are the
  real guard; the howto says so.
- Alerts, new group `dev-hub.alerts` in `scripts/etc/argocd/platform-ops/prometheusrule.yaml`, labels
  `severity: warning`, `cluster: hub`, `group: dev-hub`:
  - `HubVmMemoryLow`: `min(node_memory_MemAvailable_bytes{job="node-exporter"}) < 3 * 1024 * 1024 * 1024`, `for: 10m`.
  - `DevHubNearQuota`: `sum(container_memory_working_set_bytes{namespace="dev-hub",container!=""}) /
    sum(kube_resourcequota{namespace="dev-hub",resource="limits.memory",type="hard"}) > 0.9`, `for: 10m`.
  - Email only: `severity=warning` routes to `platform-warning` (`scripts/etc/prometheus/alertmanager.yaml.tmpl:14–36`);
    neither name matches the k3dm-analyze regex (`scripts/etc/argocd/platform-ops/alertmanager-config.yaml:11–14`),
    and neither file changes. The rules reach the hub only after `hub-promote` + `make platform-ops`.

### D4 — how a live check works

1. Push the release branch; `make dev-hub-sync` (the dev hub reads `origin`).
2. Run the port-forward `dev-hub-status` prints; check in the dev-hub Grafana.
3. When it passes, `make hub-promote REF=<that commit>` (v1.43.15).

## What NOT to Do

- Do not run `dev-hub-up`, `dev-hub-sync` or any `make` target against a cluster; tests use stubs and
  rendered manifests. The operator runs E2.
- Do not call `vcluster_destroy`, `_vcluster_deregister_from_hub`, `deploy_argocd_applicationsets`,
  `_argocd_prepare_applicationsets`, `_argocd_set_active_app_cluster` or `_argocd_confirm_applicationset_stage`
  from `dev_hub.sh`.
- Do not change OrbStack settings (P0 is the operator's).
- Do not give the dev hub any hub credential, Vault path, kubeconfig or write endpoint.
- Do not use the `vclusters` namespace or change `vcluster.sh`.
- Do not change hub ApplicationSets, charts, dashboards, alert routing or `deploy/hub` (the Trivy line, operator yes
  2026-11-12).
- Do not edit CLAUDE.md, `memory-bank/` or `docs/roadmap.md`. Do not commit to `main`, create a PR or skip
  hooks.
- Stubs for `vcluster`, `kubectl`, `helm` and `security` take output from a real read-only capture, with host and
  date in a comment beside it (the captures above are usable).
- Write the must_not tests first and show them red on the pre-fix tree.
