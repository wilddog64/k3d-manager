# v1.28.0 — Parallel multi-cloud provisioning (concurrent `make up` per provider)

**Status:** queued (design)
**Milestone:** v1.28.0 (after v1.26.0 fleet-lifecycle, v1.27.0 image-signing)
**Scope:** make it safe to run two or more provider bring-ups concurrently from the
same host — e.g. `make up CLUSTER_PROVIDER=k3s-aws` in one terminal and
`make up CLUSTER_PROVIDER=k3s-hostinger` in another — without the local
orchestration layer clobbering itself.

---

## Problem

Today the *remote* provisioners are independent (AWS CloudFormation stack vs. a
Hostinger VPS share nothing), but the **local orchestration layer on the laptop is
single-tenant**. A second concurrent `make up` clobbers the first because both
runs assume sole ownership of a set of **global, non-provider-scoped** resources.

Steady state is already multi-cloud: the ArgoCD hub keys each app cluster by a
distinct cluster-secret name and ApplicationSets fan out across all of them. The
gap is strictly **concurrent provisioning**, not coexistence.

Both `up` paths converge on the same shared plumbing (`Makefile:17-26`):
- `k3s-aws` / `k3s-gcp` → `bin/cluster-up`
- `k3s-hostinger` / `k3s-oci` → `scripts/k3d-manager deploy_cluster`
- **both** then run `make observability` + `make platform-ops`.

### Collision inventory (grounded in current code)

| # | Shared resource | Where | Failure when run concurrently |
|---|---|---|---|
| 1 | `~/.local/share/k3d-manager/active-provider` | single global file, written per run; read by `make status`/`down`/`refresh` and `scripts/lib/webhook/config.py:38` | Last writer wins. After both finish it names one provider, so a later bare `make down`/`make status`/webhook targets the **wrong** cluster. |
| 2 | `_ACG_STATE_DIR="${HOME}/.local/share/k3d-manager"` | `bin/cluster-up:37`; `run/`, `logs/`, `bin/`, `checkpoints/` are global | Fixed pid filenames `run/{vault-pf,frontend-pf,acg-prom-pf}.pid` (`bin/cluster-up:116-117,346`) collide. One run's `_acg_up_cleanup` (`:112-124`) kills the **other** run's port-forwards. Logs interleave. |
| 3 | Fixed local ports | Vault `18200:8200`, Prometheus `19090`, Alertmanager, ArgoCD-browser HTTPS, Keycloak listeners (`Makefile:206-238`, `bin/cluster-up`) | Second run's `port-forward`/listener bind fails (port in use), or both fight over one forward. |
| 4 | Fixed launchd labels | `com.k3d-manager.vault-port-forward`, `com.k3d-manager.cloudflare-tunnel`, `com.k3d-manager.prometheus-port-forward`, alertmanager, argocd/keycloak browser listeners | Both runs `bootout`/`bootstrap` the **same** label → clobber. |
| 5 | Hub bootstrap | both register into the same laptop ArgoCD hub and may bootstrap/refresh its Vault + LDAP + ArgoCD concurrently (`bin/cluster-up` Step 3.6) | Race on hub bring-up (double init, half-applied CRDs). |
| 6 | `~/.kube/config` | both merge contexts into the default kubeconfig | Context **names** differ, but `kubectl config` merges aren't atomic → possible corruption under true concurrency. |

Remote-side collisions are out of scope here: the AWS CloudFormation stack name
`${_ACG_CF_STACK_NAME}` (= `k3d-manager-cluster`) is AWS-only and would only
collide with a **second AWS** run — a separate concern (multi-AWS-sandbox) not
covered by this spec.

---

## Design

Principle: **provider-scope everything the bring-up owns locally, and serialize the
one thing that is legitimately shared (the hub).**

### 1. Provider-scoped state dir
Introduce `_ACG_STATE_DIR="${HOME}/.local/share/k3d-manager/<provider>"` (fall back
to the flat path for the default/local provider to preserve existing behavior).
`run/`, `logs/`, `bin/`, `checkpoints/` become per-provider. Pid files, wrappers,
and TLS material no longer collide.

### 2. `active-provider` becomes a set, not a scalar
Replace the single-value file with a directory of live registrations
(`.../active-providers/<provider>`) or a newline set, written by the registration
helper (single writer preserved). `make status`/`down`/`refresh` and the webhook
resolver consume the set:
- an explicit `CLUSTER_PROVIDER` always wins;
- with no explicit value and **one** live provider, use it (back-compat);
- with **multiple** live, require an explicit `CLUSTER_PROVIDER` and print the set.

### 3. Per-provider local ports + launchd labels
Allocate the browser/port-forward local ports from a per-provider base offset, and
suffix launchd labels with the provider (`com.k3d-manager.<provider>.vault-port-forward`).
Keep the current fixed values for the default/local provider so single-cloud users
see no change.

### 4. Hub-bootstrap lock
Guard the hub bootstrap/refresh (Vault + LDAP + ArgoCD on the laptop) with a
host-level advisory lock (`flock` on `.../hub-bootstrap.lock`). The first run
bootstraps; concurrent runs wait, then observe "already ready" and skip. This is
the one resource that is correctly shared — serialize, don't duplicate.

### 5. Kubeconfig write serialization
Wrap context merges into `~/.kube/config` behind the same host lock (or a dedicated
`kubeconfig.lock`) so concurrent `kubectl config` writes can't interleave. Context
names remain distinct per cluster.

---

## Non-goals

- Concurrent **same-provider** runs (two AWS sandboxes at once) — needs stack-name
  parameterization; separate spec.
- A single command that provisions multiple clouds at once. The model stays
  "one `make up` per provider"; this spec only removes the requirement that they
  not overlap in time.
- Changing the steady-state hub/ApplicationSet fan-out (already multi-cloud).

---

## Phased implementation

1. **Phase 1 — state-dir scoping (`bin/cluster-up`).** Provider-scope `_ACG_STATE_DIR`
   and everything derived from it. BATS: two providers get disjoint run/log dirs; the
   default/local provider keeps the flat path.
2. **Phase 2 — `active-provider` set + resolver.** Update `_acg_resolve_provider`
   (see `scripts/tests/lib/provider_contract.bats`) and `webhook/config.py` to the
   set semantics. BATS: multi-live requires explicit selection; single-live is
   back-compat.
3. **Phase 3 — per-provider ports + launchd labels.** Template the labels/ports by
   provider in the Makefile port-forward targets and the browser listeners.
4. **Phase 4 — hub-bootstrap + kubeconfig locks.** `flock` guards; a stubbed BATS
   proving the second concurrent caller waits and then skips.

---

## Definition of Done

- [ ] Two concurrent `make up` runs (`k3s-aws` + `k3s-hostinger`) complete without
      killing each other's port-forwards, without port-bind failures, and with both
      clusters registered in the hub under distinct names.
- [ ] `make status` / `make down` with an explicit `CLUSTER_PROVIDER` targets the
      right cluster while the other is live; bare invocation with multiple live
      providers refuses and prints the set.
- [ ] Single-cloud users see **no** behavior change (flat paths, fixed ports/labels).
- [ ] `shellcheck -S warning` clean on all changed shell; new BATS for each phase.

---

## Rules

- Preserve back-compat for the default/local provider (flat state dir, fixed
  ports/labels) — gate the scoping on a non-default provider.
- `bin/cluster-up`'s EXIT trap must only reclaim **its own** provider-scoped state.
- No direct `sudo` — route launchd through `_run_command` as today.

## Implementation-ready detail (v1.28.0 session, 2026-09-04)

Recon of the real code corrected three assumptions in the design above and locked
the outstanding decisions. **This addendum is authoritative where it conflicts with
the narrative above.**

### Corrections from recon

1. **Phase 1 is a single-variable change, not ~30 edits.** All state paths in
   `bin/cluster-up` already derive from `${_ACG_STATE_DIR}` (verified: ~30 sites, all
   references). Scoping that one variable scopes everything downstream. No per-site edits.
2. **The webhook consumer is a dead constant.** `scripts/lib/webhook/config.py:38`
   defines `_ACTIVE_PROVIDER_FILE` but **nothing reads it** (grep across all
   `scripts/lib/webhook/*.py`). Collision #1's webhook bite does not exist today.
   Action: leave the constant, or repoint it in a later phase — no behavior change needed now.
3. **The resolver already selects by reachability, not last-writer.**
   `_acg_resolve_provider` (`scripts/lib/provider.sh:121`) probes contexts
   `ubuntu-hostinger → ubuntu-k3s → ubuntu-azure → ubuntu-gcp` and takes the first
   that answers `/readyz`; the `active-provider` file is only a **fallback** when no
   context is reachable and `CLUSTER_PROVIDER` is unset. So collision #1's real bite is
   (a) that offline fallback and (b) `make down`/teardown reading a stale scalar, plus
   `k3s-hostinger.sh:1007` deleting the **whole** marker file (would clear other
   providers under a set).

### Decisions (locked)

- **State-dir scoping (Phase 1):** *All* providers scope to
  `~/.local/share/k3d-manager/<provider>` (uniform, no special-case flat provider).
  A **one-time migration** on first scoped run moves any pre-existing flat state
  (`run/ logs/ bin/ checkpoints/ acg-state.json`) into the subdir named by the legacy
  `active-provider` scalar (its rightful owner), else the current run's provider. The
  same `make up` re-bootstraps launchd forwards under the new path, so the one-time
  orphan closes within the run. *(User decision 2026-09-04: "All scoped, migrate on first run".)*
- **`active-provider` set representation (Phase 2):** a **directory**
  `~/.local/share/k3d-manager/active-providers/` holding one empty marker file per live
  provider. Register = `: > active-providers/<p>` (atomic, no read-modify-write race
  between concurrent runs); de-register = `rm -f active-providers/<p>` (targeted).
- **Resolver stays best-effort; refusal lives in the wrapper.**
  `_acg_resolve_provider` must never hard-fail — argocd.sh, observability.sh,
  shopping_cart.sh call it opportunistically. It gains a set-aware fallback (below).
  The "multiple live → refuse and print the set" behavior belongs to the
  `make down`/`status` layer (out of this phase's low-level scope; tracked for Phase 3).

## Phase 3+4 — implementation-ready detail (2026-09-04)

Recon corrected two more spec assumptions:

1. **Not all fixed ports/forwards are per-provider.** The Vault forward
   (`localhost:18200`) targets `--context k3d-k3d-cluster` — the **shared hub**; hub
   ArgoCD likewise. The ACG Prometheus forward (`localhost:19090`, `cluster-up:1842-1852`)
   targets `--context "${_acg_observability_context}"` — the **app cluster** (per-provider).
   **Only genuinely per-app-cluster forwards get a port offset.** Hub-shared forwards stay
   at their fixed ports — they are created **once** and reused; concurrency-safety for them
   comes from the Phase 4 hub lock, not from offsetting. (The collision inventory item #3
   conflated the two.)
2. **`flock(1)` is not on stock macOS** (util-linux only; host is Darwin). The advisory
   lock is **`mkdir`-based** (atomic create, pid file for stale reclaim), not `flock`.

### Decisions (locked)

- **Hub lock (Phase 4):** `_acg_lock_acquire`/`_acg_lock_release` (mkdir-based, pid stale
  reclaim, bounded wait then proceed-without-lock rather than deadlock) wrap the hub
  verify+bootstrap critical section (`cluster-up:337-375`, Step 3.5+3.6) so concurrent runs
  can't double-create or double-bootstrap the shared hub. Lock dir: `${_ACG_STATE_BASE}/hub-bootstrap.lock`.
- **Per-provider port offset (Phase 3):** `_acg_provider_port_offset <provider>` → small
  deterministic integer, **0 for k3s-aws** (cluster-up's default provider ⇒ single-cloud
  users keep the historical fixed ports unchanged). Applied to the ACG Prometheus forward
  (`$((19090 + offset)):9090`). Pid-file collisions were already fixed by Phase 1's scoped
  state dir.

### Session slice (Phase 3+4)

Ships the two pure-logic helpers (+ BATS), the hub-bootstrap lock wiring, and the ACG
Prometheus per-provider port offset. **Deferred (Phase 3b, tracked):** kubeconfig-merge
lock (app-context fetch, `cluster-up:677+`); the full per-app-cluster launchd-**label**
suffix audit across `observability.sh`/`argocd.sh`/`k3s-hostinger.sh` (must not touch
hub-shared listeners); `make down`/`status` set-aware refuse-when-ambiguous (changes the
Makefile's global `CLUSTER_PROVIDER ?= k3s-aws` defaulting — separable, riskier); the live
two-cloud DoD (needs two real clouds up).

### DoD (Phase 3+4 slice)
