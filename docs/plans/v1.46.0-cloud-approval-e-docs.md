card before the cloud bridge runs them. Read the landed code first: `scripts/lib/webhook/cloud_approval.py`; `gated()`, the approval

## Change

- `docs/howto/cloud-session-requests.md`: a section "Requests that need operator approval": the four actions; what the cloud session
  sees (`responses/<id>.pending.json`, the stderr notice, the longer wait); every rejection reason, verbatim, with what to do:
  `operator approval is not configured on the bridge`, `approval state is unreadable on the bridge`,
  `too many requests awaiting approval; try again later`, `request expires too soon for approval; file it with at least 5 minutes left`,
  `approval card not delivered; file a new request`, `denied by the operator`, `not approved before the request expired`. Add
  `.pending.json` to the response-file list near `:242`; keep the status list (`:263`) and exit codes (`:289`) as they are. Operator
  setup: after the hub promote, `make deploy-worker` (relay) and `make install-cloud-bridge` (plist gains
  `K3DM_HERMES_APPROVAL_DRAIN_URL`; `make restart-cloud-bridge` is not enough because it does not re-render the plist); the Keychain items
  are the ones Hermes already uses.
- `docs/architecture/cloud-bridge.md`: a trust-boundary row "Operator approval" in the table at `:82-92` (gated actions, card, first
  decision wins, drain by prefix, stored request runs, expiry, single bridge); a row "Watch ledger" (entries from the public branch are
  validated); update the sequence diagram so a gated action passes approval before the token read.
- `docs/guides/hermes.md`: the relay accepts three prefixes (`r` Hermes repairs, `d` dispatch-recover, `c` cloud requests); only `c`
  records Deny and only the first decision; each consumer drains and deletes only its own; the relay lists at most 50 items.
- `CHANGELOG.md` `[Unreleased]`: one bullet for the approval gate, one for the two watch-ledger fixes.
