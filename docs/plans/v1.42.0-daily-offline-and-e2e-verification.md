# v1.42.0 — Daily offline suite and Tier 1 E2E verification

## Goal

Run the repository's offline `k3dm-test` suite and Tier 1 vCluster E2E verification once per
day, while keeping them operationally independent. A failure, timeout, or unavailable
environment in one run must not prevent the other run from starting, finishing, publishing
its result, or being triaged.

This plan covers Tier 1 (`make e2e` / `e2e_verify_vcluster`) only. Tier 2
(`make e2e-sandbox`) remains an opt-in ACG/Stripe check and is not silently converted into a
daily unattended job.

## Current facts and constraints

- `make test-metrics` runs `make test-all`, then publishes `k3dm_test_*` metrics. Its wrapper
  intentionally exits zero after publishing so the metric carries the suite result.
- The k3dm-test dashboard records the last result, failed cases, freshness, and exit code.
  `k3dm_test_cases_failed > 0` is the failure signal; exit code is supporting evidence.
- The offline duration metrics are currently not trustworthy: the exporter emits the run
  duration as `0`, and the BATS/Python parsers do not receive the duration markers they expect.
- Tier 1 creates a throwaway vCluster, deploys the self-contained substrate, waits for the
  seed and service rollouts, runs the in-cluster Playwright Job, writes a JSON result, and
  tears the vCluster down. The Playwright portion has previously taken about 12–31 seconds;
  lifecycle work makes the full run several minutes. The E2E Job timeout is 1200 seconds and
  rollout/readiness waits can be 300 seconds.
- Existing E2E result publication and Hermes deterministic E2E triage must remain the source
  of truth for E2E failures. The new offline-suite path must not be made to look like an E2E
  failure.

## Required behavior

### 1. One daily trigger, two independent executions

Add one daily scheduler entrypoint (the existing Hermes scheduling mechanism is the preferred
owner) that starts these as separate bounded jobs:

1. the offline suite through `make test-metrics`; and
2. Tier 1 through `make e2e-remote RUNNER=m2` when the configured remote runner is available,
   otherwise the explicitly configured Tier 1 runner path.

The trigger must not use fail-fast chaining. It must start both jobs even if the first start
fails, and it must wait/collect each job independently. A non-zero result, timeout, or launch
error from one job must not suppress the other job's result. The combined scheduler result is
an envelope containing two distinct statuses, not a replacement status for either job.

The daily run must have an idempotency key such as the UTC date. A retry may repair a missing
publication, but must not launch an unbounded second copy of either job.

### 2. Preserve separate result channels

The offline run publishes only `k3dm_test_*` metrics with a run timestamp, target, origin,
duration, exit code, total cases, failed cases, and a bounded redacted failure summary.

The E2E run publishes its existing JSON/result ConfigMap and E2E metrics unchanged, including
the tier, runner, project, exit code, duration, failure groups, and failure details.

The scheduler publishes a small run-envelope record containing, for each child:

- `started`, `finished`, and `duration_seconds`;
- `status`: `pass`, `fail`, `timeout`, or `unavailable`;
- a redacted reference to the child result; and
- the daily idempotency key.

No dashboard query may combine the two result types into one pass/fail series.

### 3. Measure the actual time

Repair the offline metrics path so duration is measured around the complete `make test-all`
execution and passed to `bin/k3dm-test-metrics`. Parse and publish per-suite duration only
when the suite provides a trustworthy value; otherwise publish an explicit missing/unknown
state instead of `0`.

The daily envelope must measure wall-clock duration for both children, including setup and
teardown. The dashboard should distinguish:

- offline suite runtime;
- E2E test-job runtime; and
- E2E lifecycle runtime.

Do not infer a current failure from an old Pushgateway value. Every daily result needs a
timestamp/run identity, and stale data must be displayed as stale.

### 4. Hermes triage and bug filing

Keep the existing E2E Hermes triage/file-bug path unchanged for E2E results.

Add a separate offline-suite Hermes sensor/triage path that reads the offline metrics and
envelope. It may file a bug only for a newly observed offline failure, repeated failure, or
stale/unavailable run according to explicit debounce rules. Its bug document must identify
`k3dm-test` as the source and include the run ID, target, failed/total counts, exit code,
duration, and redacted failure text.

The two triage paths must have separate deduplication keys and state. An offline failure must
not be filed as an E2E service failure, and an E2E failure must not clear or suppress an
offline incident. Filing remains approval-gated if that is required by the existing Hermes
bug-writing policy; this plan does not add automatic code changes or repairs.

### 5. Alerting and stale-data semantics

Retain independent alerts for:

- offline failed cases;
- offline suite stale/unavailable;
- E2E failed result;
- E2E result stale/unavailable; and
- scheduler child launch/collection failure.

The alert evidence must say which child failed and link to its result. A green offline result
must not mask a failed E2E result, and a green E2E result must not mask stale offline metrics.

## Implementation boundaries

Expected areas are the Hermes scheduler/sensor and triage modules, the offline metrics wrapper
and exporter, the daily-run dashboard/rules, and focused offline tests. Do not alter the live
cluster, ArgoCD applications, Slack routing, or Tier 2 sandbox behavior as part of this plan.

The implementation must use stubs/fixtures for runner, Pushgateway, Prometheus, and result
publication tests. No test may read the host Keychain, require a live cluster, call Stripe, or
make a network request.

## Tests and mutation coverage

The implementation is not complete until these cases are covered:

1. both children are launched when neither has failed;
2. offline launch failure does not prevent E2E launch;
3. E2E launch failure does not prevent offline launch;
4. one child timing out still produces the other child's final result;
5. duplicate daily invocation does not create an unbounded duplicate run;
6. offline failure is published with its own metrics and triage key;
7. E2E failure retains the existing E2E triage classification and key;
8. stale offline data is not treated as a fresh pass or failure;
9. durations are non-zero for controlled sleeps and are preserved independently; and
10. redacted failure text and result links are present without secrets.

At minimum, planned mutations must make the suite red when:

- the second child is launched only after the first succeeds;
- one child result overwrites the other in the envelope;
- the offline result is routed through E2E triage; and
- duration is replaced with the current hardcoded zero.

Each mutation must be restored and the full focused suite rerun green.

## Gates and acceptance

- The existing offline BATS and Python suites remain green.
- Focused tests cover the scheduler, exporter duration, offline triage, and E2E compatibility.
- `shellcheck` is clean for touched shell files.
- `make check-doc-links` is green.
- Dashboard and Prometheus-rule rendering/contract tests are green.
- A dry-run demonstrates that both child commands are scheduled independently and no live
  cluster is contacted.
- One controlled fixture run proves the envelope records distinct pass/fail combinations and
  preserves both child results.
- No Tier 2 sandbox run is required for acceptance.

## Non-goals

- Making either test depend on the other.
- Making the daily run a blocking deployment gate.
- Automatically repairing failed E2E or offline runs.
- Running the ACG/Stripe Tier 2 sandbox unattended every day.
- Replacing the existing E2E triage taxonomy or dashboard result schema.

## Suggested release placement

v1.42.0 is appropriate: this is a cross-cutting observability and scheduled-verification
feature, not a small v1.40.x bug fix. It should be split into implementation commits for the
independent scheduler/envelope, duration correctness, and offline Hermes triage if review finds
the work too large for one change.
