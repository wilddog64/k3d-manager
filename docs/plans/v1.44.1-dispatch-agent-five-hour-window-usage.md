## Problem

Claude and Codex each work inside a rolling 5-hour usage window, plus a weekly one. When an agent
runs out mid-dispatch, the work stalls, and the dashboard cannot show why or how close an agent
is. The operator wants each agent's 5-hour consumption on the agent dispatch dashboard, next to
the dispatch data, so a run that hits the window can be read from the dashboard.

## Sources (read-only; no credential, no API call)

| Agent | Source | Fields |
|---|---|---|
| Codex (Luna) | `${CODEX_HOME:-~/.codex}/sessions/**/rollout-*.jsonl`, each event carrying `rate_limits` | `primary.used_percent` with `window_minutes: 300` (5 h); `secondary` with `10080` (7 d); `resets_at` (epoch s) |
| Claude | the operator's statusline usage cache (`cache_file` under `STATUSLINE_CACHE_DIR` in `~/.claude/statusline.sh`) | `.five_hour.utilization`, `.five_hour.resets_at`, `.seven_day.*` |
| agy (Gemini) | none known | the exporter emits `k3dm_agent_window_source_present{agent="agy"} 0` |

The exporter reads the windows by their `window_minutes` and keys, never by position. It never calls
a usage endpoint, never reads `~/.claude/.credentials*` or the Keychain, and never runs the
statusline script.

## Fix

### F1. Exporter: window gauges

In `bin/k3dm-dispatch-metrics`, a new collector `_agent_window_rollup`:

- `k3dm_agent_window_used_percent{agent, window}`: `agent` is `claude`, `codex` or `agy`;
  `window` is `5h` or `7d`. This is the latest sample per agent and window.
- `k3dm_agent_window_resets_at_seconds{agent, window}`.
- `k3dm_agent_window_sample_age_seconds{agent}`: now minus the sample time. The sample time is the
  rollout event's `timestamp` for Codex and the cache file's mtime for Claude.
- `k3dm_agent_window_source_present{agent}`: 1 or 0.

A stale Claude cache is exported with its age and never presented as current. A source that
is missing or unparsable sets `source_present` to 0 and writes one stderr line. It never fails
the run.

### F2. Exporter: window used per dispatch (Codex)

For each landed dispatch that has a Codex session ID, emit
`k3dm_dispatch_codex_window_used_percent{version, slug}`. This is the rise in
`primary.used_percent` from the session's first rate-limit sample to its last, when both have the
same `resets_at`. When the window reset during the session, the value is the sum over each
`resets_at` segment of last minus first. Label cardinality matches the existing per-spec series.

Claude has no per-dispatch window figure: the cache holds one current value. The Claude column
stays the per-spec cost from the v1.43.8 plan.

### F3. Dashboard

A new row, **Session windows**, at the top of `grafana-dashboard-agent-dispatch.yaml`:

1. A stat per agent: 5 h used %, thresholds 70 (amber) and 90 (red), with reset time and sample
   age in the description. Shows "no source" for agy.
2. A time series of `k3dm_agent_window_used_percent{window="5h"}` by agent.
3. A 7 d used % stat per agent.
4. The Per spec table gains a **Codex 5h %** column from F2.

Each panel description says where the number comes from and that Claude's value is only as fresh as
the statusline's last fetch.

### F4. Docs

`docs/guides/grafana-dashboards/k3dm-agent-dispatch.md`: the new row, the sources, staleness, and why
agy shows no source.

## Tests

`scripts/tests/bin/test_dispatch_metrics.py` (or the existing exporter test file):

1. Codex fixture rollout with three `rate_limits` events: gauges equal the last sample; 5 h and
   7 d come from `window_minutes`, not position (fixture swaps primary and secondary).
2. Codex session crossing a reset: F2 sums segments; never negative.
3. Claude fixture cache: gauges and age from the file mtime; a malformed cache sets
   `source_present` 0 and the run exits 0.
4. No Claude cache, no Codex sessions, agy: `source_present` 0 for each, no other series.
5. Isolation: the test sets `HOME`, `CODEX_HOME` and the statusline cache dir to tmp paths, and the
   Pushgateway URL to `http://127.0.0.1:9`. An autouse fixture fails any open of a path under the
   real home.
6. Dashboard: the row exists; every expr names only metrics the exporter emits, with labels it
   sets (the dashboard-queries-untested check).

Show tests 1 (swapped windows) and 2 (reset) red against a naive implementation in a temp copy.
