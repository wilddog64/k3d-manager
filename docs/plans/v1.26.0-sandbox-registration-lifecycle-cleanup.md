# v1.26.0 — managed sandbox registration lifecycle and stale ArgoCD cleanup

**Status:** queued
**Milestone:** v1.26.0
**Scope:** detect and safely remove ArgoCD registrations and generated Applications for
ephemeral app clusters that have been intentionally destroyed.

## Problem

An expired AWS sandbox left the `ubuntu-k3s` ArgoCD cluster Secret and ten generated Applications
behind. ArgoCD reported them as `Unknown` because the API endpoint was gone. `Unknown` alone is not
safe to use as a deletion signal: a live cluster can be temporarily unreachable.

## Design

### 1. Registration metadata

Every k3d-manager-managed cluster registration must include:

- `k3d-manager/managed: "true"`
- `k3d-manager/provider`
- `k3d-manager/sandbox-id` (when ephemeral)
- `k3d-manager/registered-at`
- `k3d-manager/expires-at` (ephemeral registrations only)

The registration helper remains the single writer for the ArgoCD cluster Secret.

### 2. Explicit teardown

`make down` / provider destroy must call a shared deregistration helper before destroying an
ephemeral cluster. The helper must:

1. mark dependent ApplicationSets as resource-preserving;
2. delete the managed ArgoCD cluster Secret;
3. wait for generated Applications to disappear; and
4. never delete workloads in another cluster.

The operation is idempotent and supports `--dry-run`.

### 3. Stale-registration watchdog

Add a host-side launchd job or hub CronJob that evaluates only registrations with
`k3d-manager/managed=true`. A registration is eligible for cleanup only when all conditions hold:

- `expires-at` is in the past, or the provider reports the sandbox absent;
- the API endpoint has failed continuously for a configurable grace period (default 30 minutes);
- the registration has not been refreshed during that grace period; and
- the cluster is not marked `k3d-manager/retain=true`.

The watchdog must use a bounded retry/backoff, emit a dry-run decision to its log, and preserve
Application resources while removing generated Application objects and the cluster Secret.

### 4. Observability and operator controls

Export `k3dm_argocd_cluster_registration_stale{cluster,provider}` and
`k3dm_argocd_cluster_cleanup_total{cluster,reason}`. Add Grafana panels and a warning alert for
registrations approaching expiry or stale beyond the grace period. Slack notifications must contain
cluster, provider, reason, and age—not credentials or bearer tokens.

Provide:

```text
make cleanup-stale-clusters --dry-run
make cleanup-stale-clusters --confirm
```

`--confirm` is required for deletion outside the normal provider teardown path.

## Safety rules

- Never delete solely because ArgoCD reports `Sync: Unknown`.
- Never touch hostinger/permanent registrations from this cleanup path.
- Never prune application resources as part of registration cleanup.
- Refuse cleanup when metadata is missing or contradictory; report for operator review instead.
- Keep a JSON audit record with decision, endpoint, timestamps, and reason.

## Files expected to change during implementation

The implementation should be limited to the lifecycle owner and its tests, likely:

- `Makefile` (operator targets);
- `scripts/lib/providers/k3s-aws.sh` and shared provider lifecycle helpers;
- ArgoCD registration/ApplicationSet templates;
- launchd/CronJob watchdog manifest and observability rules/dashboard;
- focused BATS coverage under `scripts/tests/`.

The exact file list must be finalized before implementation; no live cluster changes are part of
the source-only task.

## Gates

- BATS covers normal teardown, expired sandbox cleanup, grace-period protection, retain protection,
  dry-run, and idempotent rerun.
- `shellcheck -S warning` is clean for touched shell files.
- YAML and plist parse checks pass.
- A live dry-run proves hostinger/permanent registrations are skipped and a stale managed
  registration is proposed without deletion.
- Confirmed cleanup leaves no generated `Unknown` Applications for a destroyed sandbox and does not
  prune resources in any surviving cluster.
