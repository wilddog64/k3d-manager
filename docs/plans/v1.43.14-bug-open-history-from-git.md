## Problem

The Bugs dashboard panel "Open by priority over time" plots `k3dm_bug_docs{state="open"}` from Prometheus. Hub
Prometheus keeps 3 days (`retention: 3d`, size cap 8GB, the same on the M4 and M5, checked 2026-10-30). A 30-day
range therefore showed an empty chart with a spike at the right edge, which the operator read as data lost in the
M4 → M5 cutover. `ff7d54e7` pinned the panel to 3 days so it no longer misleads, but there is still no 30-day trend.

The counts are not lost: every past inventory is in git. `_bug_metrics` already computes one inventory from a ref
(`_bug_texts(root, ref)` + `doc_meta`). Running the same count at past commits gives the history without longer
retention.

## Fix

### H1 — Exporter (`bin/k3dm-vectordb-metrics`)

Add `_bug_open_history(root, ref, days=30, repo=...)`:
- For each of the last `days` UTC dates D (today included), pick the last commit on `ref` at or before
  `D 23:59:59Z` (`git rev-list -1 --before=<D>T23:59:59Z <ref>`). A date before the ref's first commit has no
  commit and is skipped.
- Count open bugs at that commit with the existing `_bug_texts(root, commit)` and `doc_meta`, using exactly the
  same priority and state rules as `_bug_metrics`. Do not write a second parser.
- Count each distinct commit once and reuse its counts for every date that maps to it.
- Emit `k3dm_bug_open_history{repo,priority,date} <count>`. `date` is `YYYY-MM-DD` (UTC), and `priority` is
  one of `P0 P1 P2 P3 unset`. Emit all five priorities for each date, zeros included, so the stacked bars line up.
- Emit `k3dm_bug_open_history_scan_timestamp_seconds{repo}`.

Publish it with PUT to a new Pushgateway group `k3dm-bug-open-history` (instance = repo), so dates older than 30
days drop out on each push. Do this from `publish_bug_metrics` (k3d-manager, same `ref`) and
`_publish_lib_foundation_bugs` (lib-foundation, `origin/main`). Follow the existing pattern there: it is
non-fatal, so on failure print `bug open history skipped (non-fatal): ...` and push nothing for that group. Never
push a partial set of dates.

The latest scrape holds the whole 30 days, so the panel reads it with an instant query and Prometheus retention
no longer limits it.

### H2 — Dashboard (`scripts/etc/argocd/platform-ops/grafana-dashboard-bugs.yaml`)

Add a panel "Open by priority, last 30 days (from git)" next to the 3-day panel:
- Bar chart, stacked by priority, x-axis `date`. Use an instant query of
  `sum by (date, priority) (k3dm_bug_open_history{repo="$repo"})`, with the transformations Grafana needs to put
  `date` on the x-axis and one series per priority. Keep the existing priority colours.
- Description: counts are open docs per day, read from the last commit of each UTC day on the release ref. This
  is an inventory snapshot, not opened/fixed events: a falling count does not prove a fix. Not limited by
  Prometheus retention.
- Keep the 3-day panel. Do not change its query.

### H3 — Docs

## Review notes (Claude, 2026-11-05)

agy run on `gemini-3.8-flash-high`. This is the first data point on Flash quality for a spec of this size.

- **Exporter.** `_bug_open_history` reuses `_bug_texts` and `doc_meta`, so there is no second parser. Each distinct commit is counted once. Dates before the first commit are skipped. All five priorities are emitted for every date. Both pushes are PUT to `k3dm-bug-open-history`, with instance = repo, and each sits in its own non-fatal `try`. In lib-foundation it runs before the tally, so a tally failure leaves the history pushed. Claude checked that `git rev-list --before=<D>T23:59:59Z` reads the `Z` as UTC, even under `TZ=America/Los_Angeles`.
- **Dashboard.** The new panel (id 18) uses an instant table query with `groupingToMatrix` on date × priority. It uses the same five priority colours as the 3-day panel. The 3-day panel's width went from 24 to 12 so the two sit side by side; its query and `timeFrom` are unchanged.
- **Tests.** E1 pairs N1 and N2 with positive controls (a first-commit date, and a 23:59:58Z commit). E2 only adds the new group to the exact-set push assertions, so every existing push stays asserted.
- **Defect Claude fixed.** `test_dashboard_queries.py::test_every_bug_dashboard_target_matches_producer_series` failed after the land. Its fixture runs the real producers, but it never called `_bug_open_history`, so promtool found no series for the new panel's query. The file is not in the spec's list, and promtool runs in docker, which the agent sandbox blocks. Claude added the producer to the fixture. Mutation check: misspelling the metric name in the panel makes the test fail again.
- **Process slip (Claude).** The land `--test` string ended in `; true`, so it could not fail. Claude reran the same suites unmasked on the landed tree. That run found the defect above. After the fix: pytest 112 passed, 2 skipped; the Bugs, Pushgateway and appsets BATS 98/98.
