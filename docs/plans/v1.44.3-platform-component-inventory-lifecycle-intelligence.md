## Problem

Current CVE scanning and update automation primarily cover container images and specific platform workflows. Component version drift, unsupported releases, high-priority vendor advisories, and the distinction between *installed*, *declared/desired*, and *actually running* versions are not available as one reliable inventory across machines and clusters. Today's cloudflared tunnel outage illustrated the cost of missing lifecycle visibility, but it has **not** been proven to be caused by an outdated binary.

The target is **inventory everything in scope, risk-classify changes, and recommend a safe update path**, not blindly run `brew upgrade` or update every Helm chart automatically. This plan is the discovery/intelligence foundation. Actual automated application policies remain narrow and subject to separate approval and implementation gates.

## Scope and decisions

### D1 — Inventory as an evidence-backed record

Each record must include a stable `component_id`, owner, host/cluster/environment, install manager, authoritative source and source revision, desired/installed/running versions where discoverable, last observed timestamp, observation method, support/advisory status and evidence reference. Report `unknown` for unsupported sources and distinguish `not installed` from `not observed`. Never fabricate a version by substituting the latest release for the running version.

Initial coverage:
- macOS M4 and optional M2 (M5 once provisioned): macOS version, Homebrew packages, OrbStack, Python interpreters, cloudflared, Tailscale where installed, Git tooling and critical launchd-managed k3d-manager components.
- Hub and Hostinger: k3s/k3d where applicable, Helm, Argo CD, Vault, Istio, Keycloak, External Secrets, cert/security controllers, Trivy, Grafana, Prometheus, Alertmanager, Loki and supporting stateful components **only where already discoverable by authorized read-only interfaces**.
- Application workloads: image digest, provenance/signature, deployed image, relevant Trivy vulnerability status and owner; reuse existing inventory where possible.
- ACG ephemeral sandbox: lifecycle-scoped observations tagged with expiration; missing retired sandboxes must not appear as live security failures.

Do not collect private package metadata or credentials outside an explicit allowlist. Avoid querying any outside Mac/cluster that is currently unreachable; classify it as stale/unknown.

### D2 — Advisory and lifecycle intelligence

Use trustworthy version feeds (vendor security advisories, release notes, GitHub security advisories where applicable, OSV and existing Trivy data), with cached timestamp/source and per-component version-matching logic. Separate `security_fix_available`, `routine_update`, `end_of_support`, `unsupported_version`, `incompatible`, and `unknown`. Do not infer CVE applicability from a product name alone; account for package source, image digest, installed distribution and vendor backports. Flag missing or stale advisory sources.

Identify direct and dependent components so suggested updates account for Kubernetes/Istio/ArgoCD compatibility, CRDs, Vault/ESO, Python interpreter changes and macOS/OrbStack constraints. Dependency or support matrices that cannot be confirmed must block automatic promotion, not block visibility.

### D3 — Update policy and authority

- **Observe-only** is the default for all discovered components.
- **Notify/recommend**: emit a proposed version, reason, source, compatibility caveats, owner, risk tier, suggested maintenance window and required verification.
- **Approval-gated**: disruptive host components, Helm controllers, identity/security systems, cluster core and networking must have explicit operator authorization, backups and an environment-specific test/rollback or forward-recovery plan.
- **Automatic** is reserved for a later explicitly approved *allowlist of components and update classes* with preflight, isolation and proven rollback/forward recovery. The approval must cover the exact actor, environment and scope. This spec does not authorize it.
- Security emergencies should shorten triage/notification deadlines, **not** silently bypass compatibility checks, production approval or credentials policy.
- State-bearing components may require forward recovery and schema-aware backups; never assume binary rollback reverses a migration.
- Apply eventual upgrades through the correct authority: host supervisor for macOS tools, GitOps promotion for Kubernetes configuration/images, and approved OS mechanisms for macOS. No second mutation channel that fights Argo CD or host launchd.

### D4 — Output and observability

Publish a versioned, redacted, read-only inventory artifact in an established k3d-manager data location and bounded metrics to the existing observability stack. Dashboard proposal: **Platform Lifecycle** with counts by environment/risk/status, components overdue for urgent action, unsupported versions, stale inventory, approval/verification states and last observation age. Never expose tokens, keychain values, environment variables or arbitrary package output in metrics. Link findings to existing CVE/bug workflows without silently generating duplicates.

Provide a concise operator report with `component | location | desired | installed | running | advisory | proposed action | confidence/freshness`. A missing source must display `unknown` visibly. Keep high-cardinality version strings out of unbounded metric labels.

### D5 — Progressive rollout

Phase A: read-only inventory for M4 and one hub context with fixtures plus stale/source-failure behavior. Phase B: Hostinger and optional M2/M5 with no inbound network requirements and ACG expiration semantics. Phase C: advisory correlation and compatibility matrix with the dashboard and notification report. Prove inventory quality before enabling *any* automated update policy. The host supervisor plan's bounded recovery functionality is separate from platform-wide update execution.

## Definition of Done

- [ ] Inventory schema, source ownership, component allowlist and source freshness semantics reviewed.
- [ ] Exact implementation file list identified and pinned before dispatch.
- [ ] Phase A read-only inventory and isolated tests pass; no service/host mutations.
- [ ] Advisory correlation, update-policy classification and compatibility blockers independently tested.
- [ ] Operator-readable report and dashboard distinguish unknown, stale, vulnerable and current with evidence.
- [ ] Read-only live sampling validated against real approved sources; mark LIVE-VERIFIED only with recorded proof.
- [ ] Future auto-update workflow proposed separately; no silent permission escalation.

## What NOT to Do

- Do not implement or deploy component upgrades merely because this inventory spec is scheduled.
- Do not create a PR, modify main, run live shell commands or inspect private credentials while writing this spec.
- Do not treat every version bump as a security requirement or every advisory as applicable.
