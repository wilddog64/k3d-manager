## Problem

The M4 Air (24 GB) is the hub. Its Kine datastore has stopped compacting twice (2026-09-09 and 2026-10-28). A restart does not fix it and causes a bootstrap crash loop. The M5 Air (32 GB) becomes the hub, and the M4 becomes a worker.

The pieces exist only as separate commands, each with its own preconditions (`make hub-up`, `bin/hub-restore`, `make hub-data-recover`, `make appsets-reapply`, `make platform-ops`, `make observability`). Two hubs serving at once caused a Cloudflare split-brain before. The danger is not the cluster, it is the **single-instance agents**: anything that talks to the outside world or writes shared state must run on exactly one Mac.

State of the M5 on 2026-10-30: `make machine-setup ROLE=hub FROM=m4-air.local SECRETS=skip AGENTS=skip` has run; brew, repos, config and all 17 Keychain records are present; no `com.k3d-manager.*` agent is loaded (12 plists from an earlier run are in `~/Library/LaunchAgents.disabled/`).

## Agent classification (part A)

Two new manifests in `scripts/etc/machine/`, one label per line, `#` comments allowed, format `label|install command|note`:

- **`hub-local.list`** — agents that only reach **this Mac's own cluster** and are safe on both Macs at once: every `*-port-forward` (argocd, frontend, grafana, keycloak, vault, prometheus, pushgateway, hub-pushgateway, hub-loki, alertmanager) and the auth proxies (`alertmanager-auth-proxy`, `prometheus-auth-proxy`). `hub-new` may load these.
- **`hub-singletons.list`** — agents that must run on **exactly one** Mac, in the order they load at cutover, `cloudflare-tunnel` **last**: `vault-failover`, `ssh-tunnel-vault`, `ssh-tunnel`, `cleanup`, `node-health-watch`, `sandbox-reaper`, `acg-watch`, `prometheus-credential-rotator`, `hub-snapshot`, `hub-data-export`, `test-metrics`, `cloud-bridge`, `webhook`, `hermes`, `heartbeat`, `cloudflare-tunnel`. The install command column names the existing Make target or script that writes that agent's plist **without loading it** (see below). Luna finds each one by grepping the repo for the label; a label whose installer cannot be found is reported in the task summary, not guessed.

`webhook-token-rotate` and the `sandbox.*` port-forwards are in neither list: the rotator is in `not-installed.list`; the `sandbox.*` forwards belong to the ACG sandbox lifecycle, which `make up` manages. Add the `sandbox.*` labels to `not-installed.list` with that reason.

**Coverage test.** Every `com.k3d-manager.<label>` that appears in `scripts/etc/launchd/*.plist.tmpl` or as a literal label in `bin/`, `scripts/lib/` or `scripts/plugins/` is in exactly one of `hub-local.list`, `hub-singletons.list` or `not-installed.list`. A new agent added later without a classification turns this test red.

**Write without loading.** Single-instance agents must be installable with the plist written but not bootstrapped, so `hub-new` can prepare them and `hub-cutover` only loads them. Add one environment switch, `K3DM_AGENT_LOAD=0`, honoured by every installer named in `hub-singletons.list`: when set, the installer writes the plist and skips `launchctl bootstrap`/`kickstart`. Default behaviour (unset or `1`) is unchanged. Where an installer is a Make target that calls a shared helper, change the helper once.

## Part A — `make hub-new` (on the M5)

`bin/hub-new` sources lib-foundation like the other `bin/` scripts. It runs these stages in order. Each stage records its result in `~/.local/share/k3d-manager/hub-new/state` (one `stage=pass|fail epoch` line each), so a rerun resumes at the first stage that has not passed; `HUB_NEW_FROM=<stage>` forces a restart from that stage. It stops at the first failure, with the reason and the next safe step.

1. **Preflight (read-only).**
   - arm64; `hw.memsize` ≥ 34359738368; at least 100 GB free on `$HOME`'s volume.
   - `hostname -s` equals `HUB_NEW_HOST` (default `m5-air`) and differs from `HUB_OLD_HOST`'s short name (default `m4-air.local` → `m4-air`).
   - `pmset -g` shows `disablesleep 1`. If not, print `sudo pmset -a disablesleep 1` and stop. Never run sudo.
   - `docker info` succeeds (OrbStack running); `gh auth status` succeeds.
   - No k3d cluster named `${HUB_CLUSTER_NAME:-k3d-cluster}` exists, unless the state file shows `hub-up=pass` (this script created it).
   - **No single-instance agent is loaded on this Mac**: no label from `hub-singletons.list` appears in `launchctl list`. If one does, stop and print the `launchctl bootout` line for it.
2. **Machine setup.** `make machine-setup ROLE=hub FROM=$HUB_OLD_HOST SECRETS=skip AGENTS=skip`. Passes when it exits 0.
3. **Secrets present (read-only).** Every record in `secrets.hub.list` is present in the login Keychain, checked with `security find-generic-password -s … -a …` **without `-w`**. Includes the Vault DR shard records (`k3dm-vault-unseal-dr`). A missing record stops the stage with `make machine-setup ROLE=hub FROM=$HUB_OLD_HOST SECRETS=skip AGENTS=skip` as the next step.
4. **Fresh cluster.** `make hub-up` (the k3d hub-only path, never bare `make up`). Never copies a datastore file.
5. **Credentials and agents.** `HUB_RESTORE_TUNNEL=skip K3DM_AGENT_LOAD=0 bin/hub-restore`. Change `bin/hub-restore`: when `HUB_RESTORE_TUNNEL=skip`, it does not call `_ensure_cloudflare_tunnel_agent`, and its verify step reports the Cloudflare tunnel check as `SKIP` (not `FAIL`). Port-forwards (in `hub-local.list`) load as today.
6. **Prepare single-instance agents.** Run every install command in `hub-singletons.list` with `K3DM_AGENT_LOAD=0`. Passes when each plist exists and **none** is loaded.
7. **Data.** `make hub-data-recover` against the newest export. The operator types the approval at its prompt.
8. **Platform.** `make appsets-reapply` (on the release branch), then `make appsets-check`, `make platform-ops`, `make observability`.
9. **Verify (read-only).** All must pass; then write `hub-new-report.json` (stage results, each check, Kine datastore and WAL sizes, timestamp) and print a table.
   - Every ArgoCD Application in `cicd` is Synced and Healthy; none Degraded or Progressing over 10 minutes.
   - Every ExternalSecret is `SecretSynced` (counts only, never Secret data).
   - Vault is unsealed; the ESO ClusterSecretStore is Ready.
   - The identity Application exists and is Healthy.
   - The system-notice Slack URL key is present in its Secret, checked with `kubectl describe` (key names only).
   - Kine has logged at least 6 consecutive `COMPACT deleted` cycles over at least 30 minutes with no transaction error. If fewer, the check fails with `Kine: N of 6 compaction cycles; rerun make hub-new after HH:MM`, and a rerun repeats only this stage.
   - Still no label from `hub-singletons.list` is loaded.

`hub-new` never connects to `HUB_OLD_HOST` except through machine setup's `FROM=` copy, never stops, unloads or edits anything there, and never loads a single-instance agent.

### Amendment: no manual steps before `hub-new` (Claude, 2026-10-30; operator: "go ahead")

A read-only check of the M5 before the first run found three steps the operator would have done by hand: copy the Cloudflare tunnel credentials and origin cert, export `HOSTINGER_HOST`, and install `k3d`. All three are now part of `make hub-new`; the only step before it is `git pull`.

- **Tunnel files.** `bin/k3dm-machine-setup` reads a new `scripts/etc/machine/files.<role>.list` (paths relative to `HOME`). With `FROM=<host>` it `scp`s each missing file from the old Mac into a `.k3dm-partial` file, saves it with mode 600 in a mode-700 directory, and never overwrites a present file. With no `FROM`, in check mode, or in a dry run, it copies nothing. `files.hub.list` names `.cloudflared/<tunnel-id>.json`, which must match `credentials-file` in `scripts/etc/cloudflared/config.yml` (enforced by a test), and `.cloudflared/cert.pem`. This stays inside N1: it is machine setup's `FROM=` copy. `hub-new`'s `secrets-present` stage, which runs after machine setup and before `hub-up`, refuses if either file is missing.
- **Hostinger target.** `prepare-singletons` sources `scripts/etc/hostinger/vars.sh`, so an unset `HOSTINGER_HOST` uses the tracked default (`srv1754834.hstgr.cloud`, user `ubuntu`), the same target the M4's live tunnels use (checked 2026-10-30). An exported value still overrides it.
- **k3d.** Preflight skips the cluster query when `k3d` is not installed; `hub-up` installs it (`_provider_k3d_install`).

## Part B — `make hub-cutover` and `make hub-cutover-rollback` (on the M5)

`bin/hub-cutover` refuses to run unless `hub-new-report.json` shows a pass less than 24 hours old. It prints the plan (every label it will stop on the M4 and load on the M5), then asks for a typed `cutover` on `/dev/tty`. `DRY_RUN=1` prints the plan and exits 0.

1. **Stop the old hub's single-instance agents**, over SSH to `HUB_OLD_HOST`, in **reverse** `hub-singletons.list` order (`cloudflare-tunnel` first): `launchctl bootout gui/<uid>/<label>` for each one that is loaded. Record the labels it stopped in `~/.local/share/k3d-manager/hub-cutover/stopped-on-old`. Never delete a plist, never touch `hub-local.list` agents or the old cluster.
2. **Confirm the old hub is quiet**: over SSH, no `hub-singletons.list` label is loaded. Otherwise stop, without loading anything on the M5, and print the rollback command.
3. **Load the M5 single-instance agents** in `hub-singletons.list` order (`launchctl bootstrap` of the plists part A wrote), `cloudflare-tunnel` last.
4. **Verify (read-only).** `make webhook-doctor` healthy; the frontend and webhook public hostnames return 200 or the expected auth code; exactly one cloudflared connector per tunnel (`cloudflared tunnel info`); the Hostinger SSH tunnels are up; a Hermes test message is delivered.
5. **Record.** Append the time, old host, new host, the labels moved and the verify result to `hub-cutover-report.json`.

`make hub-cutover-rollback` unloads the M5's `hub-singletons.list` agents (reverse order), then bootstraps on `HUB_OLD_HOST` exactly the labels in `stopped-on-old`, in list order. It also asks for a typed `rollback`.
