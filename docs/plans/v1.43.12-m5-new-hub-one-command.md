## Problem

The M4 Air (24 GB) is the hub. Its Kine datastore has stopped compacting twice (2026-09-09 and 2026-10-28). A restart does not fix it and causes a bootstrap crash loop. The operator has decided not to repair it in place: the M5 Air (32 GB, arrived 2026-10-28) becomes the hub, and the M4 becomes a worker.

The pieces exist, but only as separate commands, each with its own preconditions:

- `make hub-up`: builds a hub-only k3d cluster. Bare `make up` takes the full ACG path, and `CLUSTER_PROVIDER=k3d` is rejected.
- `make hub-restore`: restores Keychain-backed credentials and local agents.
- `make hub-data-recover`: restores data from the newest encrypted export.
- `vault-dr-shards-*`: moves Vault's unseal shards.
- `make appsets-reapply`, `make platform-ops`, `make setup-worker`: deploy the rest.

A new machine also needs everything `machine-setup ROLE=hub` provides. Run by hand, this is a long checklist that is easy to get wrong. Two hubs serving at once caused a Cloudflare split-brain before.

## Design

Two commands, split on purpose. `hub-new` builds and verifies the new hub while the M4 keeps serving. `hub-cutover` moves traffic and agents in one step. The operator runs both on the M5, in a real terminal (Terminal.app or tmux), because the secret prompts need a TTY.

### D1. `make hub-new` (on the M5)

`bin/hub-new` sources lib-foundation like the other `bin/` scripts. Privileged commands go through `_run_command`. It runs these stages in order. Each stage is idempotent and records its result in a state file under `~/.local/share/k3d-manager/hub-new/`, so a rerun resumes at the first stage that has not passed. It stops at the first failure, with the reason and the next safe step.

1. **Preflight (read-only).**
   - The machine is arm64, has at least 32 GB of memory and at least 100 GB of free disk.
   - The hostname matches `HUB_NEW_HOST` (default `m5-air`). It refuses to run on the current hub's host.
   - `pmset -g` shows `disablesleep 1`. If not, it prints `sudo pmset -a disablesleep 1` and stops. It never runs sudo for this itself.
   - The Xcode command line tools, Homebrew and `gh auth status` are ready. A missing one is handed to machine-setup.
   - No k3d hub cluster exists on this machine yet. If one does, it stops, unless the state file shows this script created it.
2. **Machine setup.** Runs `make machine-setup ROLE=hub`. Secrets are entered at the TTY and only their presence is checked. Values are never copied from the M4, never read, and never logged.
3. **Vault unseal shards.** The operator imports them with `make vault-dr-shards-import`, from the export they made on the M4 with `make vault-dr-shards-export`. The stage checks the import by Keychain presence only.
4. **Fresh cluster.** Runs `make hub-up` (the k3d, hub-only path, never bare `make up`). The cluster gets a new, empty Kine datastore. It never copies a datastore file from the M4.
5. **Credentials and agents.** Runs `bin/hub-restore`, with **hub LaunchAgents installed but not loaded**. The webhook, Hermes, port-forwards, cloudflared and snapshot jobs stay unloaded until cutover.
6. **Data.** Runs `make hub-data-recover` against the newest export in `k3dm-hub-data`. The operator types the approval at its prompt.
7. **Platform.** Runs `make appsets-reapply` from the release branch, then `make appsets-check`, `make platform-ops` and `make observability`.
8. **Verify (read-only).** Every check below must pass. Then it writes `hub-new-report.json` and prints a table.
   - Every ArgoCD Application in `cicd` is Synced and Healthy. None is Degraded or stuck Progressing for over 10 minutes.
   - Every ExternalSecret is `SecretSynced`. Only the counts are read, never Secret data.
   - Vault is unsealed. The ESO ClusterSecretStore is Ready.
   - The identity Application exists and is Healthy (bug 2026-10-15).
   - Kine has logged at least 6 consecutive `COMPACT deleted` cycles, over at least 30 minutes, with no transaction error.
   - The report records the datastore size and the WAL size.
   - The system-notice Slack URL is present by name in its Secret. The value is not read.

`hub-new` never stops, unloads or edits anything on the M4. It never touches the Cloudflare tunnel or the Hostinger tunnel.

### D2. `make hub-cutover` (on the M5, after `hub-new` passes)

`bin/hub-cutover` refuses to run unless `hub-new-report.json` shows a pass less than 24 hours old. It prints the plan, then asks for a typed `cutover` at the TTY. With `DRY_RUN=1` it only prints the plan.

1. **Stop the M4 hub agents**, over SSH to `HUB_OLD_HOST` (default `m4-air.local`). It unloads the hub LaunchAgents listed in the `agents.hub.list` manifest from plan 1. It does not delete them. It does not delete the M4 cluster.
2. **Load the M5 hub agents** in a fixed order: port-forwards, then the webhook (`make setup-worker`, which keeps the existing Keychain token), then Hermes, the snapshot and export jobs, and cloudflared last.
3. **Repoint the edge.** The Cloudflare tunnel and the Hostinger tunnel connect from the M5. The M4 connector must already be stopped (step 1), so only one connector serves.
4. **Verify (read-only).**
   - `make webhook-doctor` reports healthy.
   - The frontend and webhook public hostnames return 200 or the expected auth code.
   - The Hostinger tunnel is up.
   - Exactly one cloudflared connector is registered for each tunnel. The connector count is read from `cloudflared tunnel info`.
   - A Hermes digest test message is delivered.
5. **Record.** Appends the cutover time, the old host, the new host and the verification result to `hub-cutover-report.json`.

`make hub-cutover-rollback` reverses the steps: it unloads the M5 hub agents, then reloads the M4 agents over SSH. It works because step 1 only unloads them and never deletes them.

### D3. After cutover (documented, not automated)

The how-to lists the steps that follow cutover:

- Leave the M4 cluster stopped, not deleted, for 7 days as the rollback path.
- Then run `make machine-setup ROLE=worker` on the M4, and remove its hub LaunchAgents as a separate, explicit operator step (plan 1, S3).
- Update the memory and docs that name the M4 as the hub: the `HUB_*` defaults, the SSH config aliases and the `docs/howto` pages.

### D4. Out of scope

- A local LLM (Ollama) on the M5. It is a follow-on plan, after the M5 has run as the hub for a week and its free memory is measured. It runs on the macOS host, not in a container, with a memory cap. See the roadmap note.
- Repairing the M4's Kine datastore.
- Hostinger changes beyond which machine its tunnel connects from.
- Copying secret values between machines.
