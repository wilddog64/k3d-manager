## Context

The current Grafana Bug Tracking dashboard shows bugs filed/open/fixed; it does **not** count feature/enhancement specifications in `docs/plans/`. The v1.45.1 Engineering Decision Digest already plans to expose `k3dm_decision_spec_count{release,kind,approval}`, but approval is **not implementation progress**. The operator wants a separate, accurate spec-work view (and a link to it from Bug Tracking), without conflating defects with engineering work or exceeding the five-spec-per-release rule.

## Objectives / boundaries

- Add a **Spec Tracking / Engineering Work** section to the existing Decision Digest dashboard; Bug Tracking remains about bugs, with a navigation link to the spec view (only if technically supported by its dashboard configuration).
- Display for the current release and nearby releases: planned specs, approved specs, implementation pending/in progress/completed, blocked specs, and remaining capacity under the five-spec rule.
- Make all counts reproducible from Git-tracked documents and existing verified workflow evidence. Reuse the v1.45.1 parser, metric producer, exporter and Grafana dashboard. No database, second collector/service or new dashboard unless an explicit blocker is demonstrated.
- Preserve a strict distinction between operator approval, agent implementation, integration and operational verification. `**Approval:** explicit` does NOT mean implemented, and a green unit test alone does NOT mean operationally verified.
- Respect patch-release splitting: when a release is at its five-plan cap, show capacity 0; never reassign automatically.

## Data contract and status semantics

Release scope is `docs/plans/vX.Y.Z-*.md` matched by exact version segment (not substring; v1.45.1 and v1.45.2 are distinct). Exclude `docs/plans/archive/`, templates, and non-versioned planning references from the five-plan denominator. Avoid double counting multiple links to the same file; Git path is the identity.

Reuse existing `**Approval:** explicit|standing|pending` (plus `unrecorded`). Introduce a separate, machine-readable header for tracked plan docs **on or after v1.45.2**:

```text
**Implementation:** not-started | in-progress | blocked | completed | verified
```

- `not-started`: no implementation work begun.
- `in-progress`: implementation begun, not yet completed.
- `blocked`: agent cannot advance; reason and next action are recorded in spec prose.
- `completed`: implementation integrated into the target release branch with verified CI evidence, but operational acceptance not yet established.
- `verified`: completed plus required acceptance/operational checks and immutable reference(s) have been recorded (spec or referenced trusted evidence).
- `unrecorded`: missing/malformed implementation header; do not infer success from approval, git commits, unchecked checklists or prose. Existing older specs stay unrecorded unless deliberately updated; **no mass backfill**.

A spec may remain `Approval: pending` while work has not started. Approval and implementation are separate dimensions. A stale approval cannot override a blocked state.

For `completed`/`verified`, require an evidence field or link to the authoritative existing CI/merge/release evidence with commit SHA and result; design exact validation using the existing decision digest and v1.47.0 hub-e2e proof when applicable. Failed/missing evidence must not count as verified. Do not fabricate evidence; state `unverified` where appropriate. The lifecycle should be updated by the responsible agent and independently checked by the existing CI/hook policy, not silently inferred or self-approved.

## Verification / acceptance

1. Fixture with 5 uniquely named `v1.45.2` plan docs -> planned 5, slots 0; another v1.45.1 document does not alter v1.45.2.
2. A sixth spec yields an over-limit warning and negative/zero remaining as explicitly documented; no silent reassignment.
3. Approval pending + implementation verified are shown as separate fields (and flagged for review), never counted as approved.
4. `Approval: explicit` with `Implementation: not-started` is approved but **not completed**.
5. A spec marked `verified` without authoritative evidence is flagged invalid/unverified; `completed` without CI/merge evidence is not counted as completed.
6. Missing or malformed status is `unrecorded`; historical specs aren't automatically modified.
7. Archived, duplicate and non-versioned plans never consume capacity; current five-spec rule does not depend on bug counts.
8. Missing metrics show “no data” rather than zero successes, and dashboard displays approval and implementation charts separately.
9. Layout BATS tests detect overlapping panels and broken dashboard references. All new parser/metric tests pass in clean, isolated test environments.
10. No new persistent service, database, Prometheus high-cardinality per-spec labels, branch-protection bypass, or runtime deployments in this task.
11. Mutation tests: treat approval as implementation completion; count a duplicate twice; assign a v1.45.1 plan to v1.45.2; accept a verified state with missing evidence. Each mutation must make a test fail.
