# v1.48.0 — Structured E2E failure evidence

**Status:** PROPOSED — moved from v1.43.0 to v1.47.0, then to v1.48.0 on 2026-10-10 (v1.47.0 is dedicated to the infra e2e); no runtime changes yet
**Owner:** k3d-manager E2E and cloud-bridge maintainers
**Motivation:** The v1.42.0 log-tail fix makes the final Make output visible, but a bounded
tail alone is not sufficient to diagnose many E2E failures after the temporary vCluster is
deleted.

## Operator request

When `make e2e` fails, the cloud requestor should be able to identify what failed without
asking the operator to reconstruct a deleted vCluster. The response should say which E2E run
and step failed, expose the exit status and a redacted error excerpt, and link to durable
artifacts such as the summary JSON, Playwright logs, screenshots, and traces when available.

The existing response remains useful for successful runs: it should continue to return a
bounded tail containing rollout, test-launch, result-publication, and cleanup steps.

## Problem statement

The webhook currently streams Make output to `make.log` and returns only a bounded redacted
tail through `job-status`. That tail can show the last lifecycle steps, but it may omit the
Playwright assertion, expected-versus-actual values, stack trace, pod events, or trace files
needed for root-cause analysis. E2E cleanup also removes the temporary vCluster, so collecting
evidence after the fact is unreliable.

This is an enhancement, not a correction to the v1.42.0 empty-output bug: existing output is
now returned, and this proposal adds structured evidence and durable preservation for E2E.

## Goals

- Preserve E2E evidence before temporary vCluster teardown.
- Return a compact, stable failure summary in the bridge response.
- Include the E2E run ID, job ID, target, exit code, failing step when known, and terminal
  classification.
- Preserve the bounded, redacted response contract; do not return full logs inline.
- Publish durable, branch-addressable artifact links for summary JSON, logs, screenshots, and
  Playwright traces when those files exist.
- Make successful and failed runs distinguishable without treating cleanup warnings as test
  failures.
- Keep the existing cloud-bridge action allowlist, role model, and asynchronous job lifecycle.
- Stay workload-agnostic. Capture keys on the e2e runner Job and the run's namespaces, not on
  `shopping-cart-*` names; `failed_step` comes from the Playwright test title. v1.50.0 points
  e2e at the TwinkleAI app, and this evidence path must work unchanged when it does.

## Non-goals

- Expanding the cloud-bridge action allowlist or granting new roles.
- Returning raw credentials, bearer tokens, URLs with embedded credentials, or unbounded logs.
- Keeping a vCluster alive solely for post-failure inspection.
- Rerunning failed tests automatically.
- Replacing the existing `make.log` tail or the E2E result-event mechanism.
- Claiming HIPAA compliance or changing data-retention policy without a separate security review.

## Proposed design

### 1. Capture before teardown

Extend the E2E runner's result collection so it gathers evidence immediately after the
Playwright Job reaches a terminal state and before vCluster deletion:

- the E2E run summary JSON;
- the Playwright job's pod/container logs;
- the failing test name and assertion details when present;
- screenshots and traces produced by the runner;
- relevant pod events and rollout state for startup, readiness, and timeout failures.

Collection must be best-effort. A missing screenshot or trace must not turn a passing run into
a failure, and an evidence-collection error must be recorded separately from the test result.
The runner must retain the original test exit code.

### 2. Structured summary

Write a bounded scrubbed evidence summary alongside the existing E2E summary and make it
available through the existing cloud artifact flow. The minimum schema is:

```json
{
  "schema": 1,
  "run_id": "1791332445-1095",
  "job_id": "cb9fca49",
  "target": "e2e",
  "status": "failed",
  "exit_code": 1,
  "failure_class": "playwright_assertion",
  "failed_step": "checkout flow",
  "error_excerpt": "redacted bounded text",
  "artifacts": [
    {"kind": "summary", "path": "...", "url": "..."},
    {"kind": "playwright-trace", "path": "...", "url": "..."}
  ]
}
```

Fields that cannot be determined are omitted or set to `null`; the implementation must not
invent a failure reason. `failure_class` should use a finite set such as
`playwright_assertion`, `pod_startup`, `rollout_timeout`, `authentication_or_connectivity`,
`test_timeout`, `cleanup`, `evidence_collection`, or `unknown`.

### 3. Bridge response

Keep `job-status.output` bounded to the existing 2,000-character redacted tail. Add structured
fields or artifact references without embedding large files:

- `run_id` and `exit_code` when known;
- `failure_class` and `failed_step` when known;
- `error_excerpt`, independently bounded and redacted;
- `artifacts`, containing stable references to preserved files.

The response must distinguish the test result from cleanup and evidence-collection status.
For example, a passing E2E run with a failed optional screenshot upload remains `success` while
reporting the upload warning in evidence metadata.

### 4. Retention and redaction

Apply the existing credential scrubber before committing evidence summaries or returning
excerpts. Enforce per-file and total-size caps, reject path traversal, and use the existing
job-ID-safe artifact directory. Retention should reuse the webhook job/artifact cleanup policy;
it must not create an indefinite second log store.

Playwright traces and screenshots may contain application data. Their publication requires an
explicit allowlisted artifact path and should be disabled or reduced to metadata when the
operator has not enabled artifact retention. Do not publish arbitrary pod filesystem paths.

## Milestones

**M1 — evidence contract and fixtures**

- Define the summary schema, failure classes, size limits, artifact naming, and redaction rules.
- Add representative fixtures for assertion, rollout, timeout, connectivity, cleanup, and
  successful runs.

**M2 — runner capture**

- Capture summary, logs, events, screenshots, and traces before vCluster teardown.
- Preserve the original exit status and make collection best-effort.
- Add focused offline tests proving capture occurs before cleanup and missing optional files do
  not fail the run.

**M3 — artifact publication**

- Publish the structured summary and allowlisted supporting artifacts through the existing
  cloud-request artifact mechanism.
- Add path, size, retention, and redaction tests.

**M4 — job-status integration**

- Add structured evidence fields to terminal E2E job responses while preserving the existing
  2,000-character output tail and non-E2E job behavior.
- Add bridge tests for success, assertion failure, timeout, and cleanup-warning responses.

**M5 — live validation and documentation**

- Run one successful and one deliberately diagnosable failed E2E request.
- Confirm the requestor can identify the failing step and retrieve preserved artifacts after
  vCluster deletion.
- Document operator recovery and retention behavior.

## Verification requirements

- Existing E2E BATS suites remain green; test counts do not decrease.
- Python/unit and bridge tests cover every failure class and redaction path.
- ShellCheck and `_agent_audit` pass for touched shell/Python files.
- A mutation removing pre-teardown capture causes a focused test to fail.
- A mutation removing redaction causes a credential fixture to fail.
- A mutation replacing the real exit code with success causes a terminal-status test to fail.
- Live acceptance confirms the final response includes the run ID, status, and useful evidence
  references for both successful and failed runs.

## Open decisions

- Which artifact store and URL format should be canonical for screenshots and Playwright traces?
- Should artifact retention be enabled by default, or opt-in per E2E request?
- What total retention budget is acceptable for the webhook host and cloud-request repository?
- Should Slack expose artifact links automatically, or only the structured diagnosis command?
