## Problem

On 2026-10-25 at approximately 14:56 PDT, Claude Code displayed a five-hour quota limit reached at 100%, with automatic continuation scheduled for the 15:30 PDT reset, while the seven-day quota showed 78% used. The existing dashboards report Claude token volume, token kinds and modeled API-equivalent prices, but do not explicitly capture quota-exhaustion events, associated blocked tasks, reset schedules or actual quota-induced wait time.

Token volume is not equivalent to provider quota consumption. The limit can interrupt a coordinator even when its context window has space remaining. This is an observability enhancement, not a defect in existing token accounting.

## Scope and design

### C1. Provider-neutral availability event schema

Record availability transitions for a provider/model/coordinator with fields such as `provider`, `kind` (`five_hour`, `seven_day`, `unknown`), `state` (`exhausted`, `resume_scheduled`, `resumed`), UTC event time, optional reset time, and an optional dispatch/task correlation ID when evidence exists. Never invent a transition, duration, task attribution, or reset time. Do not export prompts, transcripts, credentials, tokens, or account identifiers as label values. Keep label cardinality bounded.

### C2. Source and detection

Assess machine-readable Claude Code session/usage records and wrapper lifecycle evidence first; document exactly which source can establish each transition. Parse provider CLI limit notices only when a stable, tested source exists; otherwise mark the state unknown. Handle repeated notices, restarts, duplicate events, clock drift, missing reset metadata, and multiple sessions without double-counting. Do not infer an exhausted quota from daily token totals or from a gap in activity.

### C3. Resume and waiting-time attribution

When a reliable exhausted event and a reliable subsequent resume event exist, compute elapsed quota-unavailable time. A scheduled reset alone must not be counted as actual resumption. Separate quota wait from worker execution, verification, human continuation and infrastructure outage latency. Tasks blocked by the event are counted only with explicit task correlation, not by temporal coincidence. Preserve task-scoped release attribution where available.

### C4. Metrics and Grafana

Publish bounded, low-cardinality events/counters and observed wait duration, with a dashboard view for five-hour versus seven-day events, latest known coordinator state, reset time when observed, total confirmed wait time, and correlated tasks. Display **No data/Unknown** when there is insufficient evidence; zero means positively observed zero, not instrumentation absent. Show the collector's last-observed timestamp and data coverage. Use the project's existing offline exporter and dashboard deployment approach; avoid a new always-on polling dependency unless justified.

### C5. Safety and rollout

Telemetry is read-only; no quota bypass, purchased credits, provider switching, retry storms, or automated coordinator failover. Explicitly separate future provider-neutral collection from any later scheduler/failover implementation. On live verification, use non-destructive observations and do not intentionally exhaust an account to manufacture a test event.
