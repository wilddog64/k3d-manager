# v1.44.0 — Bounded read-only index metrics diagnostics

**Status:** PROPOSED — specification only; no runtime capability enabled
**Date:** 2026-10-08
**Milestone:** v1.44.0 candidate, plan 5 of 5 at drafting
**Owner:** cloud-bridge, webhook security and observability maintainers
**Reviewed baseline:** dea9805631bf05460165d10ac0e97481e9d07b2e

## Problem and outcome

The VectorDB Grafana "Index age (last published)" panel showed an overnight gap on October 8.
Its source query is time() - k3dm_vectordb_last_index_timestamp_seconds. A gap is missing usable
samples, not proof that indexing stopped or documents were lost. Index age would ordinarily
continue growing if the index timestamp remained exported and scraped. Current pod health cannot
explain historical absence. Cloud-bridge has no historical Prometheus query action today.

Provide one narrowly scoped, deterministic diagnostic: compare recorded index timestamp
availability with the corresponding Pushgateway scrape and publication evidence over a bounded
window. Return facts, uncertainty and suggested investigation; never change the environment.

The proposal is a fixed diagnostic tool, not a wrapper around Codex CLI, Claude, a shell,
computer control or arbitrary PromQL.

## Scope and proposed contract

Names below are NEW and are not currently supported:

```json
{
  "schema": 1,
  "action": "diagnose-index-metrics",
  "args": {"lookback_hours": "24"},
  "requested_by": "codex-cloud",
  "requested_at": "<UTC timestamp>",
  "expires_at": "<UTC timestamp within the bridge TTL>"
}
```

This illustrates the action within today's envelope; it is not authorization to keep unsigned
submission. In production use the authenticated schema/envelope from the submitter plan.

- Exactly one required argument: lookback_hours, a string enum of 1, 6, 12, 24 or 48.
- Reject additional/missing arguments and non-enumerated forms.
- Compute end=now once on the server and start=end-lookback. The requester cannot select end,
  datasource, URL, host, port, query, metric, label, file path or command.
- Use a fixed webhook diagnostic route under /api/v1, registered in the central route/policy
  table and cloud action allowlist. Its action policy is reader, intersected with the
  authenticated submitter's explicit diagnostic capability and token ceiling.
- Use the existing asynchronous job/status/output/artifact pipeline, with job-status watcher
  support for this action. Do not assume diagnosis jobs already receive automatic final responses.
- A matching local Make entry point may call the same diagnostic implementation with the same
  argument bounds. No new Slack command is required.

## Execution and access boundary

Implement a dedicated Python collector with a small HTTP client and deterministic summarizer.
It must not spawn an agent, general shell, subprocess, kubectl or port-forward. No model may
choose queries or act on results. Data from Prometheus is untrusted input.

Keep the action disabled by default. Activate only after:
1. Security prerequisites are verified and source/deployed versions recorded.
2. Signed submitter verification is enforced for this action, including revocation, freshness,
   replay and capability intersection. During companion migration, unsigned requests to this
   action still fail before collection.
3. The operator explicitly installs its fixed source configuration and enables the capability.

The HTTP client uses only a vetted local/read-only Prometheus query endpoint. Pin the scheme,
numeric loopback address, port and allowed GET paths in operator-owned configuration outside
cloud-requests. Changes require local operator configuration; request JSON cannot alter them.
Disable redirects and ambient HTTP proxy inheritance; reject URL credentials, non-loopback
destinations and configuration resolving to other addresses. An authenticated local proxy may
protect Prometheus, but cannot forward arbitrary routes or writes.

Allow only /api/v1/query_range for predefined templates (and /api/v1/query if explicitly needed);
no admin, delete-series, lifecycle, configuration, remote-read/write, arbitrary search or
datasource proxy endpoints. Give the collector no general administrator or writer credentials.

Prefer a dedicated service identity with only required configuration/output access and bounded
network reach. The webhook passes a validated job to that service, not its entire environment.
If deployed under the operator's account during a prototype, document the missing OS isolation
and keep remote activation disabled. Treat same-port impersonation by another local process as
a residual local compromise risk; local loopback binding is not server authentication.

## Fixed source mapping and queries

The current producer bin/k3dm-vectordb-metrics defaults to
K3DM_VECTORDB_PUSHGATEWAY_URL=http://localhost:19094, with group /metrics/job/k3dm-vectordb.
That is distinct from the Hostinger test Pushgateway commonly forwarded on 9091. Neither
the dashboard's active datasource nor the actual scrape labels have been confirmed live.

At setup, the operator pins a named source alias, its owning Prometheus endpoint, and exact
vetted selectors for the VectorDB and Pushgateway series. Determine actual job/instance and
exported_job labels from the deployment; do not guess that job contains pushgateway. Configured
selectors are reviewed literal definitions, not user-supplied PromQL. No topology discovery or
fallback to another Prometheus is permitted during a request.

The collector may issue at most six fixed query templates:

| Evidence | Fixed metric family | Purpose |
|---|---|---|
| Recorded index timestamp | k3dm_vectordb_last_index_timestamp_seconds | Timestamp updates and availability |
| Recorded successful index | k3dm_vectordb_index_last_success_timestamp_seconds | Distinguish success from other publication |
| Matching Pushgateway scrape | up | Recorded healthy/failed scrape observations |
| Push publication timestamp | push_time_seconds | Successful group publication evidence if exported/scraped |
| Last index result | k3dm_vectordb_index_last_result | Bounded success/noop/paused/failed evidence if available |
| Metric sample timestamp | timestamp(k3dm_vectordb_last_index_timestamp_seconds) | Age of selected samples at evaluation |

All selectors are fixed to the approved source/group. Unknown label values are not copied to
output. Filter last-result labels to the defined enum. Multiple unexpected source series are
ambiguous evidence; do not silently aggregate across instances or choose the newest.

Use at least a 60-second range step, chosen from a pinned source scrape cadence, with no more
than 2,881 evaluation points per series. Prometheus lookback/staleness can repeat a sample across
steps. Distinguish evaluation values from actual selected sample timestamps. Do not interpret
each returned point as a fresh scrape or an individual indexing run.

## Resource and data limits

- One active collector globally; concurrent submissions return a stable busy outcome.
- At most six HTTP queries, 5-second request timeouts, a 60-second total job deadline and no
  automatic retries/resubmission. Operator may request a new job explicitly.
- Enforce configured Prometheus server query timeout/sample/concurrency limits as well as
  client deadlines; a client disconnect alone does not guarantee backend work has stopped.
- At most eight series per query, 2 MiB per HTTP response and 8 MiB total response bytes.
  Reject over-budget responses while reading; request bounded backend result limits where
  supported. Limit JSON nesting, point counts and scalar length; never log raw oversized bodies.
- Clamp range length and step before networking. No streaming of uncapped series/labels.
- Diagnostic JSON plus human-readable summary: at most 32 KiB. Return intervals/counts and
  selected timestamps, not entire histories.
- Use existing private local artifact modes and bounded retention. Cloud-published output has
  its own small budget; retention defaults to 7 days/20 MiB locally, preserving active jobs.
- Allowlist published fields before redaction. Omit hostnames/IPs, raw labels, query strings,
  Prometheus error bodies, internal paths, credentials and environment dumps.
- Audit request ID, authenticated submitter alias, action, source alias, bounded window,
  durations/query counts and outcome. Do not dump request signatures or response contents.

The GitHub request branch is not private incident storage. If a result fails output validation
or redaction, publish only a stable error and collection metadata, never the unsafe payload.

## Evidence semantics and output

Include schema version, request/job IDs, collector version, source alias, UTC window and
resolution, query outcomes, coverage, bounded gap intervals, timestamp advances, limitations
and a deterministic evidence classification. Unknown values stay null.

| Evidence | Classification and wording |
|---|---|
| up=0 observed during absent index values | scrape_failure_observed; matching target reported failed scrapes |
| up=1 observed while index metric absent | index_metric_absent_with_scrape_up; endpoint scraped successfully but series absent |
| up itself absent or history outside retention | inconclusive; no scrape-state evidence for the interval |
| Index timestamp constant with covered samples | index_timestamp_unchanged; no recorded timestamp advance, not proof of process failure |
| Multiple overlapping conditions | mixed; report separate intervals and limitations |
| Query/source unavailable | collection_unavailable; distinguish query failure from legitimate empty data |

Do not infer exact outages from coarse boundaries: give first/last missing evaluation and
resolution/lookback uncertainty. A missing push_time_seconds metric is not proof no pushes
occurred. Changes in a timestamp indicate recorded updates, not necessarily completed
successful index jobs. Neither an index gap nor a successful scrape establishes VectorDB
data loss, health, quota state, port-forward root cause or producer failure.

Separate execution status from diagnosis: collection can succeed with an inconclusive result.
If a required query fails or is truncated, return partial/failed collection honestly.
Preserve the existing body.status/body.exit_code/body.output contract through job-status;
a diagnostic finding itself does not imply process failure. Do not call a partial report a pass.
Optional unavailable evidence is explicit and never silently dropped.

## Verification and acceptance

Use isolated HTTP fixtures and synthetic Prometheus data; no real Slack messages, credential
reads, production failure injection or laptop changes in the default tests.

1. Healthy timestamps, delayed indexing, up=0 gaps, up=1 missing metrics, absent up, quota-like
   result fixtures, duplicate series and retention boundaries yield the documented distinctions.
2. Sparse histories, stale repeated samples and downsampled ranges preserve uncertainty;
   no fabricated exact scrape/index run counts.
3. Invalid/additional args, arbitrary URLs/queries, redirects, proxy inheritance, wrong source,
   overlarge/malformed responses and malicious label strings fail before unsafe work/publication.
4. Unsigned/forged/replayed/revoked/capability-denied requests cannot reach the collector.
   Reader capability cannot request writes or other routes by changing fields.
5. Timeout, busy, byte/sample limits, backend cancellation policy and artifact/redaction failure
   return honest bounded results. No uncapped retry loops.
6. Exercise request -> queued job -> terminal status -> automatic final response; ensure
   body.exit_code and bounded body.output are retained on success and failure.
7. Synthetic secrets/internal identifiers never appear in GitHub artifacts, summaries or audits.
8. Mutations removing source pinning, auth verification, argument bounds or output filtering
   must make corresponding tests fail.
9. Integrate fixtures with [operator acceptance automation](v1.44.0-operator-acceptance-automation.md);
   existing unit/BATS, lint/audit/doc links remain green.

Opt-in live acceptance: operator validates source mapping, enables the signed action, and
submits one bounded 24-hour query. Compare with the same Grafana datasource/window and record
UTC timestamps, revisions and resolution. If October 8 history has expired by implementation,
use a known retained interval; never recreate a production outage for this test.

## Implementation and rollback

1. Define result schema, immutable source configuration, fixed queries and fixture oracles.
2. Build isolated collector, limits, field filtering and local entry point.
3. Integrate authenticated allowlist/route/job watcher behind a disabled feature flag.
4. Verify security gates and one opt-in live comparison; document activation and residual risks.
5. Enable only the approved capability; do not expand to other dashboards without a later spec.

Rollback disables the diagnostic action/capability and stops its dedicated collector only.
Existing webhook/bridge jobs and metrics producers stay operational. No service restarts,
repairs, indexing, dashboard edits or bug filing are side effects of diagnostics.

## Definition of done

The fixed diagnostic distinguishes scrape failures from missing metric evidence within declared
limits, returns honest job/log outcomes, and cannot accept arbitrary execution/network/query
parameters. Signed identity, OS isolation and bounded output are verified before remote enablement.
Documentation names current limitations and shows a single supported request example.
The October 8 gap remains an unconfirmed observation until matching historical evidence is obtained.
