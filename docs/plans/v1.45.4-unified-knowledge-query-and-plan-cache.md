## Problem and operator evidence

On 2026-11-02, Slack `ask-docs how many P3 bugs in current release` used deterministic `bug-tally` and returned one open P3 item, while `ask-docs list all P3 bugs in v1.43.14` fell into semantic excerpt search and incorrectly said the excerpts contained no answer. This illustrates a **routing** problem, not evidence the corpus lacks a matching document. A separate issue is provenance: that first reply pointed to `docs/bugs/2026-11-01-lib-foundation-vcluster-ci-concurrent-staging-race.md`, which must be attributed to its actual repository rather than assumed to be in k3d-manager.

The existing `scripts/lib/webhook/bug_count.py` uses count-word regex and first-priority matching; the v1.45.1 design introduces model translation only when a keyword gate matches. Patching ever more keywords for `list`, `show`, `find`, `compare`, `what remains`, and thread follow-ups does not solve general intent interpretation. In addition, top-k similarity retrieval cannot prove an exhaustive list or count.

The engineering corpus already includes `docs/bugs`, `docs/issues`, `docs/plans`, `docs/retro`, `docs/job-failures` and, once the separately approved v1.45.2 work lands, selected `memory-bank` content. The vector index is a rebuildable cache, not the authority; tracked Git records and their immutable revision are authoritative.

## Goal

One **read-only** /ask-docs query capability understands a user request semantically; selects a validated, bounded plan over all eligible indexed document types; combines structured enumeration, semantic retrieval, evidence joins and release history as needed; and answers from fresh authoritative evidence. A reusable validated plan template can satisfy semantically equivalent future requests without a new planning-model call. Preserve current `/ask-docs` and `find-similar-docs` interfaces and explicit `bug-tally` contract; do not introduce another command family or datastore service.

### Representative questions that must work

- `how many P3 bugs are open in current release` (exact count)
- `list all P3 bugs in v1.43.14` (complete enumerated list, not top-k)
- `show unresolved issues and bugs for this release` (multi-type filter)
- `which approved plans are not implemented` (plans; approval != implementation)
- `find previous incidents similar to this Vault error` (semantic relevance)
- `why did ask-docs fail after migration` (evidence synthesis, may span issues/bugs/plans/retro)
- `which plans are blocked by open bugs` (explicit linked relationships, not guessed links)
- `compare unresolved P2/P3 work across the last two releases` (multi-priority, release comparison)
- `what about P2?` (follow-up in the same thread, preserving explicitly resolved scope)

## Scope and contract

### 1. LLM-first intent planner; no regex vocabulary gate

The model receives the user's bounded, sanitized question; authorized corpus/capability catalog; safe thread context; current source/release facts; and a strict typed schema. It returns a **plan proposal**, never a count or asserted fact. Validation and execution happen in code. Do not gate model planning on `how many`, `bugs`, `list`, a document type, or any other natural-language keyword. Regex may validate machine identifiers and schema fields only.

Suggested closed plan representation (the implementer may refine field names while preserving semantics):

```json
{
  "schema_version": 1,
  "operations": [
    {"kind": "enumerate", "source": "documents",
     "filters": {"document_types": ["bug"], "priority": ["P3"],
                 "state": ["open"], "release": "v1.43.14"},
     "projection": ["path", "title", "status", "source_ref"]}
  ],
  "response_mode": "list",
  "completeness_required": true
}
```

Supported **bounded** operations: `enumerate`, `aggregate`, `semantic_search`, `fetch_evidence`, `join_explicit_relationships`, `compare_releases`. Closed filters: repository, document type, release, priority, status/verification/approval/implementation lifecycle, time range, and exact source identifiers where indexed. Unknown type or operator fails closed with an actionable clarification/error, never silently drops a constraint. Explicit allowlisted join depth, result limits, model calls, cost ceilings and per-operation deadlines. No model-generated SQL, Python, shell, PromQL, Git commands, write tools or network endpoints. Executor templates own the actual SQL/Git calls. Plan schema and worker role are versioned.

The planner may choose multiple operations; executor verifies provenance and returns evidence IDs. The answer model can summarize those results but cannot invent counts, unseen documents, dependency edges or fixes. Distinguish `no matches` from `source incomplete/stale` and `query unsupported`.

### 2. Exact enumeration and source coverage

For questions involving `all`, counts, grouping, comparisons or exact lifecycle filters, use a complete Git-revision-scoped inventory/metadata index or existing authoritative tally, **never** a top-k vector result as the denominator. Define `total`, scanned count, filtered count, source repositories/ref/SHA, ignored/unknown metadata and pagination. Page bounded full listings without silently truncating; display total, shown and continuation. If available indexed metadata cannot prove completeness, return `incomplete` with a reason and evidence rather than an unqualified answer.

A canonical document ID is (repository, path, immutable Git commit); the logical document key is (repository, path) at a requested revision. Normalize parsed lifecycle metadata but retain original text and `unknown` explicitly. Distinguish filed-in, target and fixed-in release; `docs/issues` and `docs/plans` are not inherently bugs. Reuse v1.45.1 bug tally and v1.45.2 index provenance instead of separately redefining either. Cross-repository paths (for example lib-foundation) must never be presented as residing in the k3d-manager checkout.

Semantic `find similar` and diagnostic explanation requests use the existing pgvector/prior-art engine plus keyword/exact-path retrieval where appropriate. A similarity score is relevance evidence, not a lifecycle fact, duplicate confirmation or an authoritative relationship.

### 3. Validated, parameterized query-plan cache

Cache *templates* or safely reusable fully bound plans, **not answers**, in the existing local SQLite infrastructure; use existing pgvector only for optional semantic candidate retrieval. No Redis, new vector service, autonomous migrations of live data or new secrets. Store schema/executor version, template/parameter types, sanitized example intent or embedding reference, allowed source/capabilities, verification history, success/failure counters, last used and optional expiration. Include the authorization policy version/tenant visibility scope in compatibility checks; no cross-role cache leakage.

Lookup order: (a) exact canonical-plan reuse when request and bound parameters genuinely match; (b) semantic candidate retrieval with **independent intent equivalence checks**; (c) planner on miss, ambiguity or validation failure. Similarity threshold is candidate selection only, never execution approval. In particular `open` vs `closed`, `bugs` vs `plans`, `list` vs `count`, `current release` vs a historical version, and `all` vs top-k must not collide. Thread references must be resolved and authorized before cache lookup. Bind placeholders for priority, release, type and state only after checking the new question. Revalidate every hit with current schema, executor allowlist, RBAC and query bounds.

Plans may be marked `candidate`, `verified`, `quarantined` or `retired`; a runtime success alone does not certify that intent was correctly understood. Cache only validated and sufficiently verified templates; quarantine disputed/wrong results and prevent them being promoted automatically. Prefer conservative misses over false-positive reuse. Invalidate on schema/executor/policy incompatibility; data changes invalidate result snapshots, **not necessarily query templates**. Preserve opt-out/kill switch and an uncached baseline for regression comparisons.

### 4. Operational quality, cost and fallback

Return source-linked answers with source revision, last index time/lag, result kind (`complete` / `partial` / `semantic`), and plan origin (`new`, `exact-cache`, `semantic-cache`). Do not display `Sources: none` for results produced from identified documents. On ambiguous user intent, request clarification only if an incorrect execution would materially change the result; otherwise state explicit assumptions. On planner unavailable, a bounded **clearly labeled** semantic evidence fallback may answer exploratory queries, but must never masquerade as complete enumeration or emit an invented exact count.

Privacy-safe telemetry: planning model calls, exact/semantic hits, validation rejects, quarantines, fallback, freshness misses, per-stage latency, input/output planner tokens, estimated cost, evidence coverage and sampled correctness. No raw questions, user identity, source excerpts, auth tokens or arbitrary paths as Prometheus labels. Reuse `ask-docs-quality-observability` as the consumer rather than build a competing dashboard. Dashboard cache-hit savings must be measured against the uncached baseline; do not claim universal improvement.

## Operator console: show-plan and read-only query diagnostics

**Design integration, 2026-11-02 (operator):** reuse the existing console-level `show plan` / diagnostic workflow wherever its actual command or entrypoint can be verified during implementation audit. The current repository search did not establish a unique executable API named `show-plan`; do **not** invent a duplicate console command or claim that a new command already exists. Identify and document the real entrypoint, supported arguments, roles and current output before wiring the new query planner into it. If the existing interface cannot display these fields, extend it compatibly rather than adding a parallel debug subsystem.

The console's read-only **show-plan** view should expose the plan used for a specific ask-docs job/query, without rerunning the planner:
- Plan ID and schema/executor version; normalized intent, operation DAG/sequence, typed filters, repository/document-type scope, output mode and completeness requirement.
- Candidate cache key/ID (opaque), `exact_hit` / `semantic_candidate` / `verified_hit` / `miss` / `rejected` / `quarantined` / `planner_fallback`; distinguish a similar embedding from a safe executable match.
- Bound parameters after thread resolution; explicit current-release resolution, permissions and policy version; indicate missing/ambiguous parameters.
- Execution stage trace (planner → validation → cache verification → inventory/search → evidence → response), elapsed time and bounded token/cost totals per stage, row counts, truncation and completeness.
- Immutable source refs and index freshness/lag; Git authoritative inventory vs vector semantic evidence; cited source IDs; error and fallback reason, including whether validation or corpus coverage failed.
- A sanitized `explain` / dry-run path that validates and displays the proposed plan without fetching live secrets, mutating data or executing cluster/Git write operations. For an existing job ID, read saved structured diagnostics; do not reconstruct by asking the model again.

**Diagnose** should accept a specific query/job identifier and show a compact causal sequence:
1. Why this intent/operation was chosen and why a different candidate was rejected.
2. Whether a plan-cache hit was actually verified or only proposed by vector similarity.
3. Which document sources/ref revisions and completeness guarantees were used.
4. Why two paraphrases differed (operation, constraints, stale source, cache collision, model ambiguity or missing index).
5. Safe next diagnostic action, with no automatic remediation.

Use the existing job/audit storage and console log conventions after inspecting their real schemas. Persist **bounded structured trace fields**, not raw model prompts, raw user questions, full document excerpts or environment/credential contents. Redact user-identifying and token-like data; configure retention and authorizations. Console diagnostics must not grant any operation unavailable to the invoking role; any multi-user access must be separately authenticated and scoped. Correlation IDs connect Slack replies to console traces without exposing private content.

**Specific regression:** reproduce the 2026-11-02 `how many P3 bugs` versus `list all P3 bugs` discrepancy. The show-plan view must reveal `aggregate` versus `enumerate`, the same release and source SHA, and the exact result count versus complete list. For forced semantic false-hit, `diagnose` must identify the rejected plan and reason (e.g., open/closed, list/count conflict) and show a fresh planner invocation, not silently execute it. A cache-hit trace must verify zero planner calls for that job. Exercise an index-stale case and a truncated result case; both must be labeled visibly.

This work is **part of the same v1.45.4 plan**, not a sixth plan, new dashboard, or independent observability service.

## Implementation workstreams (one plan, staged gates)

1. **Inventory and contracts:** audit actual index schema, `prior_art`, `ask_docs.py`, `bug_count.py`, `bug-tally.py`, source-ref handling and current authorization. Define a typed plan schema plus exact Git-backed inventory/provenance interface; map all currently indexed content types (and enabled v1.45.2 additions). Preserve legacy behavior behind a feature flag.
2. **Planner and executor:** implement bounded LLM-first intent proposals, deterministic validation and read-only dispatch over existing search/tally/metadata capabilities, plus explicit unsupported/partial result states. Verify list/count parity at the same immutable revision.
3. **Plan-cache layer:** SQLite template registry, candidate retrieval, intent equivalence verification, typed parameter binding, invalidation/quarantine, policy/version compatibility and safe disabled mode.
4. **Slack/context and answer grounding:** integrate thread context, source links, result completeness and provenance. Keep existing Slack response limits, with complete-list pagination or continuation rather than silent clipping.
5. **Console diagnostics and evidence:** first verify the existing show-plan/diagnostic entrypoints; extend the existing read-only console path to expose plan/cache/trace/source provenance by job ID. Add red-before-green offline tests, mutation/negative tests, a task-specific evaluation set and separately approved read-only live smoke. Record token/latency/completeness tradeoffs before enabling semantic reuse by default.

Do not combine this with automatic incident remediation, AI agents executing GitOps, reindexing all `memory-bank`, or changing the v1.45.1/v1.45.2 ownership of their components.

## Boundaries / rollout

- Cache does not self-authorize or self-learn from untrusted log/document text. Source excerpts are data, never instructions.
- Preserve role-based restrictions at plan time, cache lookup, evidence retrieval and execution; fail closed on any mismatch.
- Query planner and semantic cache features are separately switchable. Canary rollout requires offline gate, independent review and operator-approved live E4.
- Write operations, new ingestion scope, autonomous fixes, generic unrestricted agent tools and a second vector DB are excluded.
- Prior v1.45.1 tests (multi-priority count, date/release filters, thread follow-ups and counted-document sources) remain regression requirements; avoid maintaining two conflicting intent parsers.
- If this one plan proves too large at design audit, split its **implementation** into a follow-on patch release without exceeding the five-plan cap. Keep this spec as the architectural contract and update the roadmap before dispatch.
