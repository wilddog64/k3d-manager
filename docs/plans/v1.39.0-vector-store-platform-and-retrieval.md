## Why this spec exists

### The agent-level defect (the real driver)

`scripts/lib/hermes/e2e_bugs.py:163`:

```python
matches = sorted(bug_dir.glob(f"*-{group['slug']}.md"))
```

Hermes decides **"is this a new bug or a recurrence of one I already filed?"** by globbing an exact
slug. The slug is derived from failure grouping, so a shift in error text produces a different slug,
and Hermes files a **fresh** bug doc for a defect it already has open — then keeps doing so on every
subsequent run. This is an unattended agent whose recall over its own memory is `strcmp`, writing
into a corpus that is already 495 files.

Everything downstream inherits the error: `status` transitions, reopen detection, and the
`ongoing` / `created` / `reopened` outcome reported to Slack.

### The context-budget cost

`MEMORY.md` indexes 165 memory files and is read in full every session. `CLAUDE.md` records the
constraint this collides with: thinking budget capped at 8,192 tokens, manual `/compact` required at
60% utilisation. A hand-maintained linear index *is* a retrieval system; it is just one that cannot
rank, and whose cost grows with the corpus rather than with the query.

### The filing-time gap

The `docs/bugs/` / `docs/issues/` dedup rule in `CLAUDE.md` is exact slug matching over 495 + 373
files. Two filings of one defect in different vocabulary do not collide.

#### Measured on 2026-09-23 — a five-document cluster the gate cannot see

This is no longer hypothetical. One root symptom — istio-cni's CNI directories being wrong for a k3s
substrate, leaving `istio-cni-node` at `0/1` on ubuntu-hostinger — is described across five bug docs
filed over 68 days:

| Filed | Slug |
|---|---|
| 2026-07-17 | `ambient-istio-cni-conf-bin-dir-mismatch` |
| 2026-07-21 | `istio-ambient-cni-dirs-not-substrate-aware` |
| 2026-07-21 | `ambient-cni-vars-missing-from-argocd-vars` |
| 2026-09-23 | `appset-live-overrides-lock-in-stale-cni-dirs` |
| 2026-09-23 | `hostinger-registration-never-sets-provider-label` |

Running the `CLAUDE.md` gate (`ls docs/bugs/*-<slug>.md`) for each returns **exactly one match: the
document itself**. Not one pair collides. The five are causally chained — each fix was correct and
each was defeated by the next link down — so they are not strictly duplicates, which makes them a
**near-duplicate cluster**: precisely the case lexical matching misses and the case an agent most
needs surfaced, since filing #5 without seeing #1–#4 is how the chain stayed invisible for 17 days.

Two of them do share the token `cni`, so a substring or TF-IDF scorer would likely link *some* of
this cluster. That is exactly why WS5 (now `docs/plans/v1.40.0-hermes-prior-art-and-retrieval-eval.md`) keeps the lexical control: this cluster should be scored by
both, and the honest question is not "does semantic beat nothing" but "does it beat `grep`".

#### The gate also fires falsely

Filing #5 above, the dedup check for slug `hostinger-registration-never-sets-provider-label` was run
as a keyword grep and surfaced `2026-06-08-thread-reply-triggers-unknown-command.md` — matched on the
word `unknown`, about a Slack command parser, no relation. So the current practice fails in both
directions: silent on real near-duplicates, noisy on incidental token overlap. A retrieval scorer
that cannot separate these two is not an improvement, and WS5 (v1.40.0) must include this pair as a hard
negative.

### Why a deployed vector store rather than a flat file

On throughput alone a flat file wins: brute-force cosine over ~1,360 documents is microseconds, and
at this scale a vector database is not a performance requirement. Three other reasons carry it:

- **Hermes is a long-lived process** that would query on every alert, from a host outside the hub.
  A store with persistence and concurrent access is a better fit than a file each process reloads.
- **k3d-manager exists to know how to deploy platform components.** A vector store managed by
  ArgoCD, credentialed through ESO and Vault, on the cluster's own storage class, is the repo
  dogfooding its own purpose — the same path Vault, ESO and Istio already take.
- It is a real, inspectable artefact rather than a script-local index.

Deploy it because it is a platform component worth being able to deploy, not because 1,360 rows
need one. Say so honestly in the guide.

## WS1 — pgvector as a platform component

- Own namespace (never `default`), per the security rules. Suggest `vectordb`.
- Deploy through an ApplicationSet under `scripts/etc/argocd/applicationsets/`, following the `eso`
  pattern. **Pin the chart version explicitly** — no floating `latest`.
- Credentials via ESO from Vault. No password in the manifest, in argv, or in git; use
  `${PLACEHOLDER}` substitution only.
- Namespace-scoped Role + RoleBinding. **No `cluster-admin`, no new ClusterRole** without written
  justification.
- PVC on the cluster's `local-path` default. Note in the guide that `local-path` is
  `reclaimPolicy: Delete` — the index is a **rebuildable cache**, not a system of record, and the
  spec must not create the impression it is durable. Losing it costs one re-index.
- **Do not** put this behind the `k3d-manager/role: app-cluster` selector. It is hub platform
  infrastructure — use a hub-scoped Application like `hub-loki` / `hub-platform-ops`. See
  `docs/plans/v1.37.0-deregister-hub-app-cluster-shopping-cart.md` for why that distinction matters.

## WS2 — The indexer

- `scripts/index-docs.py`, stdlib only. `bin/k3dm-hermes` already uses `urllib.request`, so a hosted
  embeddings API over HTTP is the established idiom here — **no `torch`, no
  `sentence-transformers`, no `numpy`.** The repo has zero third-party Python runtime dependencies
  and runs Python 3.14.7, where those wheels are not assured.
- Corpus: `docs/bugs/`, `docs/issues/`, `docs/plans/`, `docs/retro/`, enumerated with `git ls-files`
  (tracked-only, matching `check-doc-links.py` — whose tracked-only behaviour has already surprised
  one session).
- Per document embed the `#` title, the leading prose paragraph and the `##` headings. Bodies are
  largely shell transcripts and add noise.
- Key each row by **content hash**; re-embed only changed documents. A full re-index must be cheap
  enough to be routine.
- API key from env or Keychain, **never argv**. Register any new sensitive flag in
  `_args_have_sensitive_flag` (`scripts/lib/system.sh`).
- Fail closed and legibly when no key is configured: the tool reports that retrieval is unavailable,
  and callers fall back to existing behaviour. It must never block or crash a Hermes run.

## WS3 — Retrieval library and CLI (the by-product)

- `scripts/lib/hermes/prior_art.py` — `search(text, k=5)` returning `(score, path, title)`, so both
  Hermes and the CLI share one implementation.
- `scripts/find-similar-docs.py` + `make find-similar-docs Q="..."`, mirroring `check-doc-links`
  conventions. Advisory, exit 0 always, default 5 results.
- Update the `Docs Conventions` dedup rule in `CLAUDE.md`: exact-slug glob stays as the first pass,

# WS1 implementation decisions (2026-09-26) — read before dispatching

## No Helm chart: plain manifests from git

The WS1 bullet says "Deploy through an ApplicationSet ... **Pin the chart version explicitly**". The
chart is dropped and the **image** is pinned instead. Reasons, in order:

1. **Bitnami is disqualified on evidence, not preference.** `bitnami/postgresql` is the obvious
   chart, and Bitnami's image relocation has already broken this repo once —
   `docs/bugs/v1.23.0-bugfix-bitnami-kubectl-image-removed.md` — with two `bitnamilegacy` pins still
   outstanding and unmirrored (no GHCR push credential yet). Adopting a Bitnami chart for a new
   platform component would knowingly take on a dependency the repo is already trying to shed.
2. **CloudNativePG is disproportionate.** A Postgres *operator* for a single-instance rebuildable
   cache adds a CRD set, a controller and an upgrade surface to avoid writing one StatefulSet.
3. **The repo already has the pattern.** `platform-ops` is a hub-scoped Application reading plain
   manifests from `scripts/etc/argocd/platform-ops` via `path:` + `directory:`. WS1 copies it
   exactly, so there is nothing novel to review.

The supply-chain rule is satisfied the same way either route: a pinned tag, never `latest`. Use
`pgvector/pgvector:pg17`. **Record the resolved digest in the guide** and treat moving the manifest
to a digest pin as a follow-up, not a blocker.

**This supersedes the "chart version pinned" line in the Definition of Done.** Read it as "image tag
pinned, no `latest`".

## Layout — copy `platform-ops`

- `scripts/etc/argocd/vectordb/` — the manifests (Namespace is created by the sync option, not a file).
- `scripts/etc/argocd/applicationsets/vectordb.yaml` — hub-scoped, `path: scripts/etc/argocd/vectordb`,
  `targetRevision: '${K3D_MANAGER_BRANCH}'`, destination namespace `vectordb`.
- **Not** generated by a `role: app-cluster` selector, and not added to `data-git`/`services-git`.

## RBAC — none, deliberately

WS1's bullet asks for "namespace-scoped Role + RoleBinding". A Postgres StatefulSet makes **no
Kubernetes API calls**, so it needs no ServiceAccount permissions at all. Ship it on the namespace
default ServiceAccount with **no Role and no RoleBinding**. An unused Role is not least privilege —
it is a grant nobody audits. The rule that matters is the one that is actually satisfied here: no
`cluster-admin`, no ClusterRole.

## Credentials — ESO, and the Vault secret is NOT Codex's to create

- `ClusterSecretStore` is `vault-backend` (verified live 2026-09-26; 6 of 7 hub ExternalSecrets are
  `SecretSynced/True`).
- Vault key: `vectordb/postgres`, fields `username` and `password`. Follow the shape of the
  `platform-ops` `cosign-public-key` ExternalSecret, whose `remoteRef.key` is `cosign/signing`.
- **The ExternalSecret manifest is in scope. Writing the secret into Vault is not.** Codex must not
  create, generate, invent, echo or log a password, and must not run `vault`. The ExternalSecret will
  sit `SecretSyncedError` until the operator writes the Vault path — that is the expected state on
  delivery, not a bug to chase.

## What is dispatchable, and what is not

**Dispatchable (authoring only):** the ApplicationSet, the manifests, the ExternalSecret, and BATS
coverage. None of it touches a cluster.

**NOT dispatchable — operator steps, in this order, after the manifests merge:**

1. Write `vectordb/postgres` into Vault.
2. Reapply the ApplicationSets so the new set is created.
3. Confirm the Application goes `Synced/Healthy` and the ExternalSecret reaches `SecretSynced/True`.

Codex must do none of these and must not run `deploy_argocd_applicationsets`.

# WS1 addendum (2026-09-26) — seed `vectordb/postgres` in code

**This section supersedes operator step 1 above ("Write `vectordb/postgres` into Vault") and the
"Writing the secret into Vault is not [in scope]" line in *Credentials*.** Those were correct for
the first deployment: the path had to exist before any code existed to create it, and the operator
wrote it by hand on 2026-09-26. A hand-written Vault entry does not survive a hub rebuild, which
makes vectordb the only Postgres in this repo whose credential is not reproducible. That is the
defect this addendum closes.

## The distinction that matters, because the section above says the opposite

*Credentials* forbids Codex to "create, generate, invent, echo or log a password". That prohibition
is about a **password value** passing through an agent, a commit, a log or a terminal. It still
holds in full.

What is in scope here is **code that generates a password at runtime, inside the Vault pod**. Codex
writes the generator; Codex never sees, prints, commits or transmits a value. The distinction is
exactly the one the operator's own one-off write already honoured — the password was produced by
`tr -dc` inside `vault-0` and never reached the host, argv or shell history.

So: **no password literal, placeholder or example value appears anywhere in the diff, the commit
message, the BATS files or the report.** Generating one at runtime in-pod is required; handling one
is still forbidden.

## Where the seed goes, and why there

`argocd.sh` already owns platform-tier bootstrap and already sources the Vault plugin (line 21), so
the Vault helpers resolve without a cross-plugin lazy-load guard. The precedent to mirror is in the
same file, with the rationale stated in its own comment:

```bash
   # Deploy the platform-ops CVE/observability tier (namespace, CronJobs, dashboards).
   # Deployed here so it survives a hub rebuild instead of needing a manual one-shot.
   deploy_argocd_platform_ops || _warn "[argocd] platform-ops deploy reported a problem — CVE scan/dashboards may be incomplete"
```

"So it survives a hub rebuild instead of needing a manual one-shot" is precisely the requirement.
The seed is a sibling of that call.

Do **not** put this in `shopping_cart.sh`. Its `_vault_kv_put` / `_vault_kv_exists` helpers are
sandbox-scoped, and calling them from `argocd.sh` is the cross-plugin lazy-load trap: the call
silently no-ops rather than failing.

## Target 1 — new function in `scripts/plugins/argocd.sh`

Add immediately after `_argocd_seed_vault_admin_secret`:

```bash
function _argocd_seed_vectordb_postgres() {
   local ns="${VAULT_NS_DEFAULT:-vault}"
   local release="${VAULT_RELEASE_DEFAULT:-vault}"
   local pod="${release}-0"
   local secret_path="vectordb/postgres"

   if _vault_exec_stream --no-exit --pod "$pod" "$ns" "$release" -- \
         vault kv get -mount=secret "$secret_path" >/dev/null 2>&1; then
      _info "[argocd] Vault secret secret/${secret_path} already present, not rotating"
      return 0
   fi

   _info "[argocd] Seeding vectordb Postgres credentials in Vault"
   _vault_login "$ns" "$release"

   local rc=0
   _vault_exec_stream --no-exit --pod "$pod" "$ns" "$release" -- \
      sh -c 'P=$(LC_ALL=C tr -dc "A-Za-z0-9" < /dev/urandom | head -c 32); printf "{\"username\":\"postgres\",\"password\":\"%s\"}" "$P" | vault kv put -mount=secret vectordb/postgres -' || rc=$?

   if (( rc != 0 )); then
      _err "[argocd] Failed to seed secret/${secret_path} in Vault (exit ${rc})"
      return "$rc"
   fi

   _info "[argocd] vectordb Postgres credentials seeded"
}
```

Three properties of that body are load-bearing. Do not "clean up" any of them:

**The password is generated inside the pod and piped to `vault kv put ... -` on stdin.** It never
appears in argv, so it cannot reach a `kubectl exec` command string, `ps`, a shell history or a CI
log. CLAUDE.md requires this. Note that the neighbouring
`_argocd_seed_vault_admin_secret` does the opposite — it passes `"${KEY}=${password}"` as an
argument — and is therefore **not** the part of the precedent to copy. Leave that existing function
alone; fixing it is a separate change with its own rotation consequences.

**The existence check must skip, never rotate.** This is a correctness requirement, not tidiness.
The PVC `vectordb-data` persists across redeploys and Postgres initialises its data directory with
the password it first saw. Overwriting the Vault entry would make ESO publish a new password that
the already-initialised database does not accept, turning a working cluster into authentication
failures with no obvious cause. `vault kv get` returning success means stop.

**A missing `-mount=secret` silently targets the wrong path.** The KV v2 mount here is `secret`, and
the ExternalSecret reads `vectordb/postgres` through it. Keep the flag on both the get and the put.

## Target 2 — call site in `deploy_argocd_bootstrap`

In `scripts/plugins/argocd.sh`, after the `deploy_argocd_platform_ops` line and **before** the
AppProject block, so the credential exists before the ApplicationSet creates the ExternalSecret:

```bash
   # Seed the vectordb Postgres credential before the ApplicationSets create its
   # ExternalSecret, so a rebuilt hub does not need a manual Vault write.
   _argocd_seed_vectordb_postgres || _warn "[argocd] vectordb credential seeding reported a problem — the vectordb ExternalSecret may stay SecretSyncedError"
```

`|| _warn` matches the platform-ops line: a Vault that is not yet up must not abort the whole
bootstrap.

## What NOT to change

- **Do not add `vectordb/postgres` to the `_keys` array in `vault_seed_hub_into_context`**
  (`vault.sh:1063`). That function replicates hub secrets *into an app cluster*. vectordb's
  ApplicationSet has a single list element, `- name: hub` — it is a hub-only component, so an app
  cluster has no consumer for the credential. Adding it there would seed secrets nothing reads.
- Do not touch `scripts/etc/ldap/vars.sh`, the ApplicationSet, or any `scripts/etc/argocd/vectordb/`
  manifest. They are already correct and live.
- Do not modify `_argocd_seed_vault_admin_secret`.

## Target 3 — BATS gates

Extend `scripts/tests/plugins/argocd_vectordb.bats` (currently 10 tests, all green). Pure source
greps — no cluster, no mocks. Every gate must be mutation-proved: break the thing it asserts, show
the test goes red, restore. Paste the red output in the report.

1. `_argocd_seed_vectordb_postgres` is defined in `scripts/plugins/argocd.sh`.
2. `deploy_argocd_bootstrap` calls it, and the call appears **before** the `_argocd_deploy_appproject`
   call (assert on line ordering, not mere presence).
3. The function contains an existence check — a `vault kv get` for the path occurring **earlier** in
   the function body than the `vault kv put`.
4. No password reaches argv: within the function body there is no `password=` assignment passed as a
   `vault kv put` argument, and the put ends in a bare `-` operand.
5. The generated value comes from `/dev/urandom` inside the remote `sh -c`.
6. Both the get and the put carry `-mount=secret`.

Assert on meaningful tokens, never whole source lines. `grep -c` exits 1 on zero matches, so for a
must-be-absent assertion use the disappearance form (`[ "$output" = "0" ]` against a counted grep
with `|| true`) rather than a bare negated grep.
