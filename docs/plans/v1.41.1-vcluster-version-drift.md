# v1.41.1: Detect and bump the pinned vCluster version

**Status:** PROPOSED (operator request 2026-10-02: "we should automate this")
**Milestone:** `v1.41.1`
**Owner:** k3d-manager

## Problem

The e2e harness pins vCluster at `0.32.1`, and the latest release is `v0.37.2`. That puts it five
minor versions behind, and nothing reported it: the only signal was vcluster's own
"Run `vcluster upgrade`" warning. That warning names the wrong action, and
`docs/bugs/2026-10-02-vcluster-upgrade-nag-in-harness-output.md` silences it.

The pin is deliberate. `VCLUSTER_VERSION` selects both the SHA-256-checked CLI
(`foundation_ensure_vcluster_cli`, which verifies against the release's `checksums.txt`) and the Helm
chart (`--chart-version`). So upgrading means changing the pin and proving it with a live e2e run.
Upgrading the binary in place does not count.

## Pin locations (all must move together)

| File | Line today |
|---|---|
| `scripts/plugins/vcluster.sh` | `VCLUSTER_VERSION="${VCLUSTER_VERSION:-0.32.1}"` |
| `.github/actions/vcluster-e2e-setup/action.yml` | `vcluster-version` input `default: '0.32.1'` |
| `scripts/tests/plugins/vcluster.bats` | `--chart-version 0.32.1` (2 asserts) and `VCLUSTER_VERSION defaults to 0.32.1` |

## Scope

1. **`make vcluster-version-check`**
   - Reads the pin from `scripts/plugins/vcluster.sh`.
   - Reads the latest release from `gh api repos/loft-sh/vcluster/releases/latest --jq .tag_name`, stripping
     the `v`. Drafts and prereleases are already excluded by `releases/latest`.
   - Prints `pinned`, `latest`, and how many minor versions behind.
   - Exits 0 when current. When behind, it also exits 0, and prints the `make vcluster-bump` command.
   - If `gh` or the network is unavailable, it prints a warning and exits 0. It must never block anything.
2. **`make vcluster-bump VERSION=x.y.z`**
   - Validates `^[0-9]+\.[0-9]+\.[0-9]+$` and confirms the release exists and publishes `checksums.txt`.
   - Rewrites the pin in all three files from the table, and nothing else.
   - Prints the follow-up gates: `bats scripts/tests/plugins/vcluster.bats`, then a live `make e2e`.
   - It does not commit, push, or open a PR.
3. **Drift visibility**
   - A weekly GitHub Actions workflow (`.github/workflows/vcluster-version-drift.yml`, `schedule` +
     `workflow_dispatch`) runs the same check.
   - It writes the result to the job summary, and it is red only when the pin is 3 or more minor versions
     behind.
   - Use `permissions: contents: read` and actions pinned by tag. The workflow opens no PR: a
     `GITHUB_TOKEN` PR would not trigger CI here, and the bump needs a live e2e anyway.
4. **Add the checker to `make help`.**

## Out of scope

- The actual 0.32.1 → 0.37.x bump. That is a separate change, run through `make vcluster-bump`
  plus a live `make e2e`, once this tooling exists. Read the chart's release notes for
  `scripts/etc/vcluster/values.yaml` breaking changes.
- Running `vcluster upgrade` anywhere.

## Tests

`scripts/tests/bin/vcluster_version.bats`, with `gh` stubbed on `PATH` and no network:

1. current pin → "up to date", exit 0;
2. 5 minors behind → prints the bump command, exit 0;
3. `gh` failing → warning, exit 0;
4. `vcluster-bump VERSION=bad` → rejected, files unchanged;
5. `vcluster-bump` on a temp copy of the three files rewrites every pin, and `grep` finds no old version
   left;
6. the workflow has `permissions: contents: read` and no `pull-requests: write`.

Run the touched suites, shellcheck the touched shell, and `make check-doc-links`.

## Completion criteria

- `make vcluster-version-check` shows drift in one command.
- `make vcluster-bump VERSION=0.37.2` leaves a tree where the only remaining gate is a live e2e run.
- The weekly workflow turns drift into a visible red before it reaches five minor versions again.
