## Goal

An OrbStack update stops the VM that runs the hub. On 2026-10-25 it happened without warning at 05:36
PDT, and recovery took about 90 minutes of manual steps:

1. unseal Vault;
2. repair Vault's Kubernetes auth;
3. refill the Pushgateway;
4. fix a node-exporter pod left on its old IP.

Auto-update is now off on both Macs, so updates only happen when someone chooses to. This plan makes
that one decision plus one command:

- **Notice.** Hermes says an update is available and names the next window.
- **Upgrade.** The operator runs `make orbstack-upgrade`. It refuses when the hub is busy, updates
  OrbStack, brings the hub back, and reports what it found.

Hermes never installs the update. The upgrade restarts the whole hub, so the operator starts it. This
replaces phase 2 of the 2026-10-12 bug (an unattended weekly install), which stays out of scope.

## Proposed behavior

### 1. Notice (Hermes)

When the phase 1 metric `k3dm_orbstack_update_available` is 1, Hermes adds one line to its existing
notification path, once per new version. Example: "OrbStack <new> is available (running <old>);
installing it stops the hub. Run `make orbstack-upgrade` in a planned window."

- It never repeats for the same version and never runs `orbctl update`.
- No new channel. Hub notices already go to the operator; do not add SMS.

### 2. `make orbstack-upgrade` → `bin/k3dm-orbstack-upgrade`

The target runs four phases in order. Each phase writes one line to stdout and to a JSON report at
`~/.k3dm/orbstack-upgrade/<UTC timestamp>.json`.

**Preflight.** Refuse, exit 2 and change nothing, when any of these holds:

- `orbctl update --check` says no update is available. `FORCE=1` overrides this check only.
- A Codex dispatch task is running (`bin/k3dm-codex-dispatch status` shows a running state).
- A `cluster-up`, `make up`, `make refresh` or `make platform-ops` process is running.
- The current kube context is not the hub (`k3d-k3d-cluster`).
- The DR unseal copy is not present. Check this by presence only: `security find-generic-password -s
  k3dm-vault-unseal-dr -a secrets/vault:count` with no `-w`. Never read the value.
- The newest hub-data export is older than 24 h. Point the operator at `make hub-data-export`.

When preflight passes, record:

- the vault-0 pod UID;
- the hostNetwork pod IPs;
- the counts of Ready nodes, Valid SecretStores, synced ExternalSecrets and Healthy ArgoCD
  Applications.

**Upgrade.** Ask for a typed `yes` on a TTY; with no TTY, refuse. Then run `orbctl update`. Wait up to
15 min for `docker info` and the hub API to answer, and for every node to be Ready.

**Recover.** Each step runs only when its check says it is needed. Each step is logged as `skipped`,
`done` or `failed`.

1. **Vault sealed.** Wait one watchdog interval (up to 6 min) for `vault-unseal-watchdog` to unseal.
   If Vault is still sealed, run `./scripts/k3d-manager hub_data_unseal_dr`. Never run `deploy_vault`.
2. **vault-0 recreated.** If its pod UID differs from preflight and any SecretStore is not Valid, run
   the Kubernetes auth repoint through a public wrapper. Add `hub_data_repoint_vault` in
   `hub_data.sh`, calling `_hub_data_repoint_vault <context>`.
3. **Host-network drift.** Run `bin/k3dm-hostnet-drift --fix`.
4. **Pushgateway.** Run `make dispatch-metrics`, then `launchctl kickstart -k
   gui/$(id -u)/com.k3d-manager.hermes`, so every pushed job is refilled now rather than at the next
   cycle.
5. **Port-forwards.** For each `com.k3d-manager.*-port-forward` LaunchAgent whose local port does not
   answer, `launchctl kickstart -k` it once.

**Verify.** Compare against the preflight counts:

- nodes Ready;
- Vault unsealed;
- SecretStores Valid;
- ExternalSecrets synced;
- ArgoCD Applications Healthy;
- a `k3dm-release-forecast` series present on the Pushgateway.

Exit 0 only when every count is at least its preflight value. Otherwise exit 1 and name each check
that got worse. Push `k3dm_orbstack_upgrade_last_success` and
`k3dm_orbstack_upgrade_last_timestamp_seconds` (job `k3dm-orbstack-upgrade`). Hermes includes the
result in its next notice.

### 3. Dry run

`DRY_RUN=1 make orbstack-upgrade` runs preflight read-only and prints the plan. It never runs
`orbctl update`, an unseal, a repoint, a kickstart or `--fix`.
