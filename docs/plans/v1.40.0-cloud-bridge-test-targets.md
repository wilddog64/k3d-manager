# v1.40.0 — Expose the offline `test*` targets through the cloud bridge

## Decision

Operator decision, 2026-09-26: the `test*` family is safe to expose. The line to hold is
**create, destroy, or anything that can destroy a service or a cluster** — not "anything that
runs a command."

This supersedes the recommendation in `v1.40.0-cloud-bridge-e2e-dispatch.md` that
`make test` stay unexposed. That recommendation argued low *value*, not risk, and it
under-weighted one real value: **the host is macOS with BSD userland; a cloud sandbox is
Linux.** BSD-vs-GNU divergence in `sed`, `stat`, `grep` and `cat` is a recurring defect class
in this repo, and BATS run on the M4 exercises the platform the tool actually ships on. A
cloud session running `bats` in its own Linux sandbox cannot see those. That is information
only the host can produce, which makes exposure worth its cost.

## Why this needs no new credential

Every target here is offline and non-mutating, so it fits `min_role: reader` — the tier the
bridge's existing token already presents. `test-pytest` and `test-python-unit` are already
reader-tier and already reachable, which is the governing precedent.

So this spec is **independent of** `v1.40.0-cloud-bridge-e2e-dispatch.md` and much smaller:
no third token, no new role, no capability set. The `cloud-runner` design in that spec remains
required for `e2e-remote` alone, because `e2e-remote` really does drive a live cluster.

## Scope — the complete `test*` family

Enumerated from the Makefile, not guessed:

| target | body | status |
|---|---|---|
| `test` | `./scripts/k3d-manager test all` — BATS dispatcher suites | add, reader |
| `test-bin` | `bats scripts/tests/bin` | add, reader |
| `test-python-unit` | stdlib unittest suites | already reader ✅ |
| `test-pytest` | pytest suites | already reader ✅ |
| `test-python` | `test-python-unit test-pytest` | add, reader |
| `test-all` | `test test-bin test-python` | add, reader |

None creates, destroys, or touches a cluster, a container, a volume or a cloud resource. Four
additions; two already exist.

## The one safety claim that is not yet proven

The claim "the BATS suites are offline" is repo *convention* — `CLAUDE.md` states
`scripts/tests/` is "pure logic only — no cluster mocks" — and there is an **open, unfinished
task** to sweep `scripts/tests/` for reachability-dependent live mutation. Convention plus an
unfinished sweep is not evidence.

A scan for mutation verbs finds six files containing them:

```
scripts/tests/plugins/e2e_remote.bats
scripts/tests/plugins/vcluster.bats
scripts/tests/run-cert-rotation-test.sh
scripts/tests/lib/hostinger_pushgateway_port_forward.bats
scripts/tests/lib/provider_contract.bats
scripts/tests/lib/webhook.bats
```

Spot-checking shows each carries stub/mock infrastructure and at least one hit is inside a
comment, so the convention appears to hold. **Appears is not good enough for a target reachable
from a branch anyone can influence.** Finishing the sweep is therefore M1 of this spec, not a
follow-up: it is the evidence the exposure rests on.

The failure mode it guards against is specific and plausible: a suite that stubs `kubectl` only
when a cluster is *unreachable*, and silently exercises the real binary when one is reachable.
On the operator's host a cluster is always reachable. Such a suite is green in CI, green
locally, and mutating.

## Milestones

**M1 — finish the offline sweep (BLOCKING; the rest depends on it).** For every file under
`scripts/tests/` reached by `test`, `test-bin` and `test-python`, establish that no code path
can reach a real cluster, container runtime, cloud API or the host keychain. Specifically:
- Every `kubectl`/`helm`/`k3d`/`docker`/`aws` invocation is stubbed unconditionally, never
  "stubbed only when unreachable."
- No suite consults a real kubecontext, `$KUBECONFIG`, or a live endpoint to decide a branch.
- Record the result in `docs/issues/` with the file list and the method. A file that cannot be
  cleared is excluded from the exposed targets and named in the doc.

**M2 — a gate that keeps it true.** A test asserting that no file under `scripts/tests/`
invokes an unstubbed mutation verb. This is the durable control; M1 without M2 rots on the next
suite anyone adds. Prefer a disappearance gate (known set → 0) over a count.

**M3 — `MAKE_TARGETS` entries.** Add `test`, `test-bin`, `test-python`, `test-all` at
`min_role: reader`, each with an explicit `timeout`. `make test` is ~15 minutes, so:
`test` 1200, `test-bin` 300, `test-python` 900, `test-all` 1800. Do not rely on a default.

**M4 — bridge actions.** Add `make-test`, `make-test-bin`, `make-test-python`, `make-test-all`
to `ACTION_ALLOWLIST`, no args, target hardcoded server-side as with every existing entry.

**M5 — async readback.** `test-all` at 1800s meets `REQUEST_TTL_SECONDS` exactly and exceeds
the 300s default `HTTP_TIMEOUT`. The dispatch must return the webhook job id and the session
must poll `job-status`; do **not** raise `HTTP_TIMEOUT` or `REQUEST_TTL_SECONDS`. A test run
whose readback is the last 2000 bytes of output is nearly useless, so
`v1.40.0-cloud-request-artifacts.md` should land first — that is what turns this from "it went
red" into "this assertion failed."

**M6 — gates.**
1. Each new action resolves to its intended target and to `reader`.
2. A request cannot influence the `target` field (the existing server-side mapping property,
   asserted for the new entries).
3. No create/destroy target is reachable: assert `cluster`, `cluster-up`, `cluster-down`,
   `fix-delete-pod`, `fix-force-sync`, `e2e-runner-unlock`, `cleanup-stale-sandbox` and
   `argocd-upgrade` are all absent from `ACTION_ALLOWLIST`.
4. Each declared timeout is present and non-default.
5. Every gate shown capable of failing: mutate, observe red, restore, assert byte equality.

**M7 — docs.** `docs/howto/cloud-session-requests.md`: the new actions, their runtimes, the
async polling pattern, and the corrected action count. State the boundary in the operator's own
terms — offline test targets yes; create, destroy, or anything that can destroy a service or
cluster, never. Also fix `CLAUDE.md`'s stale "Four read-only actions are available."

## What NOT to Do

- Do NOT create a PR, merge, commit to `main`, or use `--no-verify`.
- Do NOT expose any target that creates or destroys a cluster, service, pod, volume or cloud
  resource — this is the operator's stated boundary and it is the whole point of the allowlist.
- Do NOT expose `e2e`, `e2e-sandbox`, `e2e-remote`, `e2e-replay` or `e2e-runner-unlock` here.
  `e2e-remote` has its own spec and its own credential design.
- Do NOT proceed past M1 if any suite cannot be cleared as offline — exclude it and say so.
- Do NOT raise `HTTP_TIMEOUT` or `REQUEST_TTL_SECONDS`.
- Do NOT give the bridge any credential other than the reader token for these targets.
