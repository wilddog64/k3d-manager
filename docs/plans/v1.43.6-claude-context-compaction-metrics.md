## Problem

Claude Code now compacts the conversation automatically at about 200K tokens. A larger window means
fewer compactions, but each turn reads more context. A smaller window means cheaper turns, but more
compaction summaries and more files re-read afterwards. Caching changes the arithmetic. How subscription
usage counts each token type isn't documented in enough detail to work it out. The only honest answer
is to measure it.

The operator's metrics (2026-10-18):

| Metric | Why it matters |
|---|---|
| Claude usage per verified spec | Overall efficiency |
| Compactions per spec | How often context resets |
| Repository re-reads after compaction | Reconstruction overhead |
| Task-resumption failures | Reliability |
| Corrections caused by missing context | Quality impact |

The first three can be derived from local files. The last two need judgment, so they are tallied by
hand and exported from the tally.

## Findings

These were read from Claude Code's session logs on 2026-10-18:

- Each compaction writes a line with `{"type":"system","subtype":"compact_boundary",…}` and a
  `compactMetadata` object. Its fields are:
  - `trigger`: `"auto"` or `"manual"`;
  - `preTokens` and `postTokens` (integers);
  - `durationMs`.

  The line also carries `timestamp` and `sessionId`. One such line in this repo's session read
  `trigger manual`, `preTokens 113270`, `postTokens 18037` and `durationMs 45152`.
- The line after it is a `user` entry with `"isCompactSummary": true`.
- The session file is continuous across compactions. Entries from before the boundary stay in the same
  file, so a single pass can see what was read on both sides.
- Assistant entries carry `message.usage`. Plan 5 already sums it.
- `Read` tool calls appear as assistant `message.content[]` items with `type: "tool_use"`,
  `name: "Read"` and `input.file_path`.

The files also hold prompts, file contents and tool output. None of these may be read into a metric
beyond the fields named here.

## Fix

### C1. `bin/k3dm-dispatch-metrics`: extend plan 5's Claude scan

In the same pass over each session file, in file order:

- **Compactions:** for every `compact_boundary` line, record its timestamp, `trigger` and `preTokens`.
  A missing or non-integer `preTokens` counts the compaction but adds no tokens.
- **Re-reads after compaction:** keep the set of `Read` `input.file_path` values seen so far in the
  session.
  - A `Read` that comes after at least one boundary, on a path already in the set when the latest
    boundary was crossed, is a **re-read**.
  - Count re-reads and all Reads.
  - Hold the path only in memory and never export it.
- **Verified specs:** run `git log --since=<window start> -p -- docs/bugs docs/plans` in the repo
  root. Count the distinct files where an added line `+**Status:** …` matches `_CLOSED_RE` from
  `scripts/lib/hermes/prior_art.py` (import it; don't copy the regex) and the commit time falls in the
  window. A file counts once per window.

### C2. Manual tally: `docs/metrics/context-window-experiment.md`

New file. It holds a short protocol section and two tables with fixed headers.

The **settings** table records each change to the auto-compaction threshold:

    | date | auto_compact_tokens | note |

The **incidents** table has one row per incident, added by Claude or the operator when it happens:

    | date | kind | spec | note |

`kind` is `resumption-failure` (after a compaction, Claude lost track of the task: redid finished work,
asked for something already given, or acted on a stale state) or `missing-context-correction` (the
operator corrected Claude for something the pre-compaction context held).

The exporter reads this file from the repo root. Rows that don't parse are skipped. It never exports
`spec` or `note`.

### C3. New series

These go on the time windows (1d, 7d, 30d) only.

- `k3dm_claude_compactions{window,trigger}`
- `k3dm_claude_compaction_pre_tokens_sum{window,trigger}`
- `k3dm_claude_reads{window,kind}`, where `kind` is `all` or `reread_after_compaction`
- `k3dm_claude_verified_specs{window}`
- `k3dm_claude_context_incidents{window,kind}`: from C2, by row date
- `k3dm_claude_auto_compact_tokens`: global, no window label. It is the latest settings-table value
  whose date is not in the future. Omit it when the table is empty.

### C4. Dashboard: new row "Claude context and compaction"

Place it below every existing row.

- **Claude cost per verified spec:** a stat of plan 5's Claude API-price cost for `$window`, divided by
  `k3dm_claude_verified_specs{window="$window"}`. It shows "No data" when the count is 0. Unit
  `currencyUSD`.
- **Compactions per verified spec:** a stat of
  `sum(k3dm_claude_compactions{window="$window"}) / k3dm_claude_verified_specs{window="$window"}`.
- **Compactions by trigger:** a bar gauge, split by `trigger`.
- **Re-read share after compaction:** a stat of re-reads ÷ all Reads, unit `percentunit`.
- **Context incidents:** a bar gauge of `k3dm_claude_context_incidents{window="$window"}`, split by
  `kind`.
- **Auto-compact threshold:** a stat of `k3dm_claude_auto_compact_tokens`.

### C5. Guide

Add a paragraph to the **k3dm Agent Dispatch** section of `docs/guides/grafana-dashboards.md`. It should
cover:

- what each panel means;
- that "cost" is at API list prices, not subscription usage;
- that "verified spec" means a doc whose Status moved to a closed state in the window;
- that the incident panels are only as complete as the hand tally in
  `docs/metrics/context-window-experiment.md`.

## Experiment protocol (goes in the C2 file)

1. **Weeks 1–2:** keep the 200K threshold, and record it in the settings table.
2. **Weeks 3–4:** raise the threshold, record the change on the day it is made, and compare the four
   panels over the two 14-day windows.
3. Add each incident row on the day it happens, not from memory at the end.
4. The deciding number is **Claude cost per verified spec**. Compactions and re-reads explain it, and
   incidents set the quality floor.
5. Don't change the threshold more than once per two weeks.
