## Why this spec exists

### The agent-level defect (the real driver)

`scripts/lib/hermes/e2e_bugs.py:163`:

```python
matches = sorted(bug_dir.glob(f"*-{group['slug']}.md"))
```

Hermes decides **"is this a new bug or a recurrence of one I already filed?"** by globbing an exact
slug. The slug is derived from failure grouping, so a shift in error text produces a different slug,
and Hermes files a **fresh** bug doc for a defect it already has open — then keeps doing so on every
subsequent run. This is an unattended agent whose recall over its own memory is `strcmp`, writing
into a corpus that is already 495 files.

Everything downstream inherits the error: `status` transitions, reopen detection, and the
`ongoing` / `created` / `reopened` outcome reported to Slack.

### The context-budget cost

`MEMORY.md` indexes 165 memory files and is read in full every session. `CLAUDE.md` records the
constraint this collides with: thinking budget capped at 8,192 tokens, manual `/compact` required at
60% utilisation. A hand-maintained linear index *is* a retrieval system; it is just one that cannot
rank, and whose cost grows with the corpus rather than with the query.

### The filing-time gap

The `docs/bugs/` / `docs/issues/` dedup rule in `CLAUDE.md` is exact slug matching over 495 + 373
files. Two filings of one defect in different vocabulary do not collide.

#### Measured on 2026-09-23 — a five-document cluster the gate cannot see

This is no longer hypothetical. One root symptom — istio-cni's CNI directories being wrong for a k3s
substrate, leaving `istio-cni-node` at `0/1` on ubuntu-hostinger — is described across five bug docs
filed over 68 days:

| Filed | Slug |
|---|---|
| 2026-07-17 | `ambient-istio-cni-conf-bin-dir-mismatch` |
| 2026-07-21 | `istio-ambient-cni-dirs-not-substrate-aware` |
| 2026-07-21 | `ambient-cni-vars-missing-from-argocd-vars` |
| 2026-09-23 | `appset-live-overrides-lock-in-stale-cni-dirs` |
| 2026-09-23 | `hostinger-registration-never-sets-provider-label` |

Running the `CLAUDE.md` gate (`ls docs/bugs/*-<slug>.md`) for each returns **exactly one match: the
document itself**. Not one pair collides. The five are causally chained — each fix was correct and
each was defeated by the next link down — so they are not strictly duplicates, which makes them a
**near-duplicate cluster**: precisely the case lexical matching misses and the case an agent most
needs surfaced, since filing #5 without seeing #1–#4 is how the chain stayed invisible for 17 days.

Two of them do share the token `cni`, so a substring or TF-IDF scorer would likely link *some* of
this cluster. That is exactly why WS5 keeps the lexical control: this cluster should be scored by
both, and the honest question is not "does semantic beat nothing" but "does it beat `grep`".

#### The gate also fires falsely

Filing #5 above, the dedup check for slug `hostinger-registration-never-sets-provider-label` was run
as a keyword grep and surfaced `2026-06-08-thread-reply-triggers-unknown-command.md` — matched on the
word `unknown`, about a Slack command parser, no relation. So the current practice fails in both
directions: silent on real near-duplicates, noisy on incidental token overlap. A retrieval scorer
that cannot separate these two is not an improvement, and WS5 must include this pair as a hard
negative.

### Why a deployed vector store rather than a flat file

On throughput alone a flat file wins: brute-force cosine over ~1,360 documents is microseconds, and
at this scale a vector database is not a performance requirement. Three other reasons carry it:

- **Hermes is a long-lived process** that would query on every alert, from a host outside the hub.
  A store with persistence and concurrent access is a better fit than a file each process reloads.
- **k3d-manager exists to know how to deploy platform components.** A vector store managed by
  ArgoCD, credentialed through ESO and Vault, on the cluster's own storage class, is the repo
  dogfooding its own purpose — the same path Vault, ESO and Istio already take.
- It is a real, inspectable artefact rather than a script-local index.

Deploy it because it is a platform component worth being able to deploy, not because 1,360 rows
need one. Say so honestly in the guide.

## WS1 — pgvector as a platform component

- Own namespace (never `default`), per the security rules. Suggest `vectordb`.
- Deploy through an ApplicationSet under `scripts/etc/argocd/applicationsets/`, following the `eso`
  pattern. **Pin the chart version explicitly** — no floating `latest`.
- Credentials via ESO from Vault. No password in the manifest, in argv, or in git; use
  `${PLACEHOLDER}` substitution only.
- Namespace-scoped Role + RoleBinding. **No `cluster-admin`, no new ClusterRole** without written
  justification.
- PVC on the cluster's `local-path` default. Note in the guide that `local-path` is
  `reclaimPolicy: Delete` — the index is a **rebuildable cache**, not a system of record, and the
  spec must not create the impression it is durable. Losing it costs one re-index.
- **Do not** put this behind the `k3d-manager/role: app-cluster` selector. It is hub platform
  infrastructure — use a hub-scoped Application like `hub-loki` / `hub-platform-ops`. See
  `docs/plans/v1.37.0-deregister-hub-app-cluster-shopping-cart.md` for why that distinction matters.

## WS2 — The indexer

- `scripts/index-docs.py`, stdlib only. `bin/k3dm-hermes` already uses `urllib.request`, so a hosted
  embeddings API over HTTP is the established idiom here — **no `torch`, no
  `sentence-transformers`, no `numpy`.** The repo has zero third-party Python runtime dependencies
  and runs Python 3.14.7, where those wheels are not assured.
- Corpus: `docs/bugs/`, `docs/issues/`, `docs/plans/`, `docs/retro/`, enumerated with `git ls-files`
  (tracked-only, matching `check-doc-links.py` — whose tracked-only behaviour has already surprised
  one session).
- Per document embed the `#` title, the leading prose paragraph and the `##` headings. Bodies are
  largely shell transcripts and add noise.
- Key each row by **content hash**; re-embed only changed documents. A full re-index must be cheap
  enough to be routine.
- API key from env or Keychain, **never argv**. Register any new sensitive flag in
  `_args_have_sensitive_flag` (`scripts/lib/system.sh`).
- Fail closed and legibly when no key is configured: the tool reports that retrieval is unavailable,
  and callers fall back to existing behaviour. It must never block or crash a Hermes run.

## WS3 — Retrieval library and CLI (the by-product)

- `scripts/lib/hermes/prior_art.py` — `search(text, k=5)` returning `(score, path, title)`, so both
  Hermes and the CLI share one implementation.
- `scripts/find-similar-docs.py` + `make find-similar-docs Q="..."`, mirroring `check-doc-links`
  conventions. Advisory, exit 0 always, default 5 results.
- Update the `Docs Conventions` dedup rule in `CLAUDE.md`: exact-slug glob stays as the first pass,
  similarity search second. A high score means **read that file before filing**, not *do not file*.

## WS4 — Hermes consumes it (strictly additive)

**Hermes' filing decision does not change in this release.** The exact-slug glob at
`e2e_bugs.py:163` stays authoritative for `created` / `reopened` / `ongoing`.

What is added: when Hermes files a **new** bug doc, `_doc()` gains a `## Possible prior art` section
listing the top 3 retrieved documents with scores, or nothing when retrieval is unavailable.

This ordering is deliberate and is not negotiable within this release. An unproven retriever that
can suppress a bug report converts a false positive into a **silently unfiled defect** — the failure
mode is invisible, which is the worst kind. Additive output is reviewable by a human on every run,
and it generates the precision evidence needed to decide whether gating is ever safe.

Letting retrieval influence the filing decision requires its own spec, its own version, and a
measured precision floor. Do not do it here.

**Evidence that this ordering is right, from 2026-09-23.** The `alert_delivery` Hermes sensor was
specced, implemented and merged with 8 green tests, and its probe was inverted: it reported a total
alerting blackout against a healthy cluster (see WS5, "The eval must exercise the real component").
Had that sensor been wired to *act* rather than to report, it would have raised a blackout incident
for a cluster that was fine. An automated component that is confidently wrong on its first live run
is the normal case, not the pathological one — which is the whole argument for additive-only here.
Note also which direction the error took: the probe cried wolf. A retriever wired to suppress
filings fails the other way, silently, and would not have been caught at all.

## WS5 — Evaluation (gates WS4's future, and this release's claims)

- `scripts/tests/fixtures/doc-dedup/pairs.jsonl` — hand-mined duplicate/near-duplicate pairs from the
  existing corpus plus hard negatives (same component, genuinely different defect). Target ≥25
  positives and ≥25 hard negatives. Follow the schema style of
  `scripts/tests/fixtures/e2e-corpus/corpus.jsonl`, the existing precedent.
- Implement a **stdlib TF-IDF cosine scorer as the control** and measure both. If embeddings do not
  beat lexical on this corpus, that is a real finding and the deployed store earns its place on the
  platform-component argument alone — which is a legitimate outcome, but it must be *stated*, not
  quietly skipped.
- `scripts/tests/bin/test_find_similar_docs.py` — pytest, mirroring `test_check_doc_links.py`.
  Report **recall@5** for both scorers with a floor the suite enforces; break it out per directory,
  since `docs/bugs/` and `docs/issues/` dominate and plans/retros differ in register.
- Add the file to the `make test-pytest` target's path list.
- Mine the pairs **before** tuning either scorer, and never add a pair to fix a failing score.
- Record the measured numbers in the retro, not just in a passing test.
- **Seed pairs already mined** (2026-09-23, from the incident in "The filing-time gap"): the five
  istio-cni / CNI-dir documents form one near-duplicate cluster — 10 positive pairs, all of which the
  exact-slug gate provably misses. The pair
  (`2026-09-23-hostinger-registration-never-sets-provider-label`,
  `2026-06-08-thread-reply-triggers-unknown-command`) is a **hard negative**: they share the salient
  token `unknown` and nothing else. Include both; they are real, dated, and were not constructed to
  make a scorer look good.

### The eval must exercise the real component, not a stub

A defect on 2026-09-23 is the reason this subsection exists, and WS5 must not repeat it.
`scripts/tests/hermes/test_alert_delivery.py` had **8 green cases** covering the `alert_delivery`
sensor. The probe it consumes, `bin/k3dm-alert-delivery-status`, read the generated Alertmanager
Secret under the key `alertmanager.yaml`. That key does not exist — the Prometheus Operator emits
only `alertmanager.yaml.gz`, base64 **and** gzipped. The missing key produced `b64decode("") → b"" →
yaml.safe_load → None`, which collapsed to `root_receiver_is_null: true, child_routes: 0`: the probe
reported a **total alerting blackout against a healthy cluster with five working routes**.

All 8 tests stayed green, because they inject a stubbed `run` and the probe script never executes.
They proved the sensor's parsing of a hypothetical payload, not the probe's ability to produce one.
The suite measured the half of the seam that could not fail.

Binding consequences for WS5:

- The retrieval eval must run the **real indexer and the real scorer over real files on disk**. A
  test that feeds hand-written vectors or a stubbed embedding call measures the ranking arithmetic,
  which is not where this class of bug lives. Stub the hosted embeddings **network call** only, and
  when stubbed, assert against a **recorded real response**, not a synthesized one.
- At least one case must execute `bin/find-similar-docs` end to end as a subprocess against the real
  `docs/` tree, the way `test_check_doc_links.py` exercises its script.
- Every scorer assertion must be **mutation-proved**: break the scorer, confirm the recall floor goes
  red. A recall number that cannot fall is not a gate. This is the standing
  "a new test passing is not evidence it can fail" rule, and it applies to metrics too.
- Prefer a failure mode that is loud over one that is plausible. The blackout bug was survivable
  precisely because its wrong answer looked like a legitimate answer; a retriever returning zero
  results must be distinguishable from one that errored.

## WS6 — Documentation (same release, not deferred)

This release introduces a **new major technology** (a vector store) and changes what an autonomous
agent writes. The standing rules apply in full: every feature is documented in the same release, and
each major technology gets a guide. CHANGELOG, the releases table, memory-bank and this spec do
**not** satisfy either rule.

Named deliverables — a reader must be able to operate this without reading the spec:

- **`docs/guides/vector-store.md`** (new; satisfies "guide per major tech"). Must cover: what is
  deployed and into which namespace; how credentials reach it via ESO from Vault; that the index is a
  **rebuildable cache** on `local-path` with `reclaimPolicy: Delete`, not a system of record; how to
  re-index and what an incremental run costs; how to verify it is healthy; how to recover after a
  cluster rebuild; and — stated plainly — **why a vector store was deployed at a scale that does not
  require one**, so a future reader does not mistake it for a performance decision.
- **`docs/guides/hermes.md`** (existing; update). What `## Possible prior art` is, that it is
  advisory output only, and that Hermes' new-vs-recurrence decision is still the exact-slug glob —
  so nobody reads a prior-art list as evidence the filing logic consulted it.
- **`docs/architecture/hermes-phase2-repair-scope.md`** (existing; update). Where retrieval sits in
  the sensor → correlate → propose chain, and the explicit boundary that it does not influence
  filing or repair decisions in this release.
- **`docs/howto/find-prior-art.md`** (new). The filing-time workflow: exact-slug glob first,
  `make find-similar-docs Q="..."` second, how to read a score, and that a high score means *read
  that file*, not *do not file*.
- **`docs/api/functions.md`** (existing; update). Any new public function, with source file and line.
- **`README.md`** (existing; update). The new `make` target in the appropriate section, and the
  How-To entry for `docs/howto/find-prior-art.md` under its component group.
- **`make help`** — `find-similar-docs` with its `Q=` argument.
- **`CLAUDE.md`** — the `Docs Conventions` dedup rule (also listed in WS3).

Write the guide from the deployed system, not from this spec: if a command in the guide has not been
run against the real component, it does not go in.

## Intended second consumer — Slack Q&A over the corpus (NOT this release)

Operator direction 2026-09-23: the Slack bot should consume this. It is the right second consumer
and it is deliberately **out of scope for v1.38.0**.

Why it is the right one:

- It proves WS3's `search()` is a shared library rather than a Hermes-private helper. A retrieval
  layer with exactly one caller has not been shown to be reusable; two callers is the cheapest
  possible proof, and Slack is a caller with a different query distribution (human, conversational,
  vocabulary-mismatched) than Hermes (machine, slug-derived). That difference is the whole point of
  semantic retrieval, so it is also the better source of precision evidence for the WS4 gating
  decision.
- The failure mode is benign. A Slack answer is read-only, advisory, and has a human reading it in
  the same second. Compare WS4, where a wrong suppression is silent. Shipping the forgiving consumer
  first and the unforgiving one later is the correct order.
- The transport already exists: `k3dm-slack-relay` (Cloudflare Worker), with
  `scripts/tests/plugins/slack_slash_commands.bats` and `slack_relay_ack.bats` already covering the
  slash-command and ack paths. This is a new handler, not new infrastructure.

Why not in v1.38.0:

- v1.38.0 already carries six workstreams, one of which (WS1) is a live deploy needing the operator's
  go. The spec's own Risks section says to split WS1 from WS2-WS5 rather than breach the 5-plan-doc
  cap; adding a seventh workstream argues the other way.
- It needs answers the release does not have yet. WS5 has not run, so the measured recall is unknown.
  Building a user-facing Q&A surface on an unmeasured retriever repeats the mistake WS4 exists to
  avoid — and this time the wrong answers would be read by a person who did not write the query
  expecting to audit it.
- Auth is unsolved for this shape. The existing relay handles slash commands with a static token;
  a Q&A bot reading the full docs corpus needs a decision about who may ask and what is returnable,
  which is a spec of its own, not a paragraph in this one.

Sequencing: land v1.38.0, run WS5, publish the measured recall@5 for both scorers, then spec the
Slack consumer in v1.39.0 with the measurement in hand — spec filed as `docs/plans/v1.39.0-slack-corpus-qa.md`. If WS5 shows embeddings do not beat the
lexical control, the Slack bot should use the control — and that finding is exactly why WS5 comes
first.

## What NOT to do

- Do **not** let retrieval gate, suppress or redirect Hermes' filing decision in this release.
- Do **not** add `torch`, `sentence-transformers`, `numpy`, or any third-party Python runtime
  dependency.
- Do **not** deploy the store via an app-cluster-selected ApplicationSet.
- Do **not** grant `cluster-admin` or add a ClusterRole without written justification.
- Do **not** float the chart version.
- Do **not** put the API key in argv, a manifest, or a commit.
- Do **not** index the out-of-repo `~/.claude/.../memory/` files here; mixing an out-of-tree path
  into a `git ls-files` corpus invites the tracked-vs-untracked confusion `check-doc-links` already
  produced. It gets its own task once the in-repo path is proven.
- Do **not** make the similarity check blocking, in the pre-commit hook or anywhere else.
- Do **not** tune either scorer before `pairs.jsonl` exists.
- Do **not** create a PR, merge, commit to `main`, force-push, or use `--no-verify`.

## Risks

- **Scope.** Six workstreams spanning a deployed service, an indexer, a library, an agent change and
  an eval harness is a large release. If it grows further, the split is clean: **WS1 alone** is a
  platform-component release, **WS2–WS5** the retrieval release — each carrying its own share of WS6. Take that split rather than
  breaching the 5-plan-doc cap or shipping a half-integrated store.
- **An unmeasured retriever looks like it works.** Plausible-looking top-5 results are the most
  likely way this ships broken. WS5 is the control, not paperwork.
- **Hand-mining pairs is the bulk of the effort.** Reading enough of 868 bug and issue docs to label
  25 genuine duplicates cannot be skipped without making the evaluation meaningless.
- **`local-path` is `reclaimPolicy: Delete`.** A rebuild loses the index. Acceptable only because it
  is a cache; the guide must say so, or a future session will treat it as durable.
- **Egress and cost.** Embedding ~1,360 documents is cents, but it is an outbound dependency in a
  repo that otherwise runs offline. Incremental indexing keeps steady-state calls near zero.
- **Corpus skew.** Bugs and issues dominate; plans and retros differ in register and may score worse.
  Report recall per directory.
