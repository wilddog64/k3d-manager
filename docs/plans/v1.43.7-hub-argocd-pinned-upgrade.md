## Problem

Claude read the hub on 2026-10-18:

- The hub ArgoCD release `argocd` in namespace `cicd` runs chart `argo-cd-10.10.5` (app `v3.5.5`).
- Its Helm history has one revision: `Install complete` on 2026-10-15. That is the hub rebuild.
- 10.10.5 is the newest chart in `argo/argo-cd` today, so nothing needs patching right now.

The real gap is process:

1. **The chart isn't pinned.** `scripts/etc/argocd/vars.sh` sets `ARGOCD_HELM_CHART_VERSION=""  # Empty = latest`.
   - This breaks the CLAUDE.md rule that every Helm install pins its chart version.
   - The hub's ArgoCD version changes silently whenever the hub is rebuilt, and nobody reviews the change.
2. **An in-place upgrade has never been a planned, routine step.** The only attempt on record failed:
   `docs/bugs/2026-09-13-hub-argocd-foreign-chart-ownership-blocks-helm-upgrade.md`. Patches arrive only
   through rebuilds.
3. **There's no before/after check.** Nothing records whether every Application was still Synced and Healthy
   after a change, and nothing says how to roll back.

## Fix

### C1. Pin the chart

In `scripts/etc/argocd/vars.sh`, set `ARGOCD_HELM_CHART_VERSION="10.10.5"` and change the comment to:
`# pinned; bump via docs/howto/hub-argocd-upgrade.md`. `deploy_argocd` already passes `--version` when this is
set (`_argocd_helm_deploy_release`), so no other change is needed for fresh installs.

### C2. `argocd_upgrade` (public function in `scripts/plugins/argocd.sh`)

Usage: `argocd_upgrade [--to <chart-version>] [--dry-run]`. Default target: `ARGOCD_HELM_CHART_VERSION`.

1. **Preflight.** Any failure here stops the upgrade with a non-zero exit, before anything changes.
   - The hub context is reachable.
   - `helm status argocd -n cicd` shows `deployed`.
   - The target version exists in `argo/argo-cd`. Run `helm repo update argo` first.
   - The target is newer than the deployed chart. Equal means print `already at <v>` and exit 0. Older is
     refused unless `--allow-downgrade` is given.
   - Record a snapshot to `${K3DM_STATE_DIR}/argocd-upgrade/<UTC stamp>/`:
     - `before.json`: every Application's name, sync status and health status;
     - the deployed chart version and Helm revision.
2. **Dry run.** With `--dry-run`, print the snapshot summary and the exact `helm upgrade` command, then stop.
   It must not call `helm upgrade` or `kubectl apply`.
3. **Upgrade.** Call `_argocd_helm_deploy_release` with the target version, the same path `deploy_argocd` uses,
   so the values stay identical. Do not use `--reuse-values`.
4. **Postcheck.**
   - Wait up to `ARGOCD_UPGRADE_SETTLE_SECONDS` (default 600) for the `argocd-*` Deployments and the
     StatefulSet to finish rolling out.
   - Then wait for every Application that was `Synced`/`Healthy` before to be so again.
   - Write `after.json`.
   - Print the Applications whose status got worse, if any.
   - Exit 0 only when none got worse.
5. **Rollback hint.** If the postcheck fails, print `helm rollback argocd <previous revision> -n cicd` (from the
   snapshot) and the snapshot directory. Never roll back automatically.

Never read or print Secret data. In particular, `argocd-secret` must stay untouched, so API tokens survive the
upgrade. A rebuild regenerates it; an upgrade must not.

### C3. Make target

Add `make argocd-upgrade`, taking `TO=<version>` and `DRY_RUN=1`, which calls `argocd_upgrade`. Add it to the
README make-target list.

### C4. How-to

Create `docs/howto/hub-argocd-upgrade.md`. It covers:

- checking for a newer chart, and reading its release notes for breaking changes;
- bumping the pin on the release branch;
- running `make argocd-upgrade DRY_RUN=1`, then `make argocd-upgrade` in the operator's tmux;
- reading the result, and rolling back.

It also states that a minor or major chart bump needs its own plan, while a patch bump (`10.10.x`) is routine.
