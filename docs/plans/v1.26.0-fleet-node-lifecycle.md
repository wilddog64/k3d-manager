# v1.26.0 — Count-agnostic fleet node lifecycle (Lambda portfolio proof)

**Milestone:** v1.26.0
**Status:** Scoped — ready for implementation.
**Plan count:** #4 of the v1.26.0 maximum of five.
**Repos:** `lib-foundation` (lib-acg module, upstream-first) + `k3d-manager` (provider + app-cluster join).
**Driver:** close the résumé-vs-code gap for fleet lifecycle automation (Lambda Bellevue target). The
node *count* is not the point — the count-agnostic *pattern* is, proven at ACG's 5-node cap but
written for N.

## Problem

The résumé claims: *"CloudFormation provisions EC2 fleets, configures nodes over SSH, installs the
runtime, validates readiness, registers healthy nodes."* The code is **two hardcoded agents, joined
serially**, with the count baked into three separate places that must be kept in sync by hand:

1. **CFN template** — `scripts/etc/acg-cluster.yaml` (and its vendored twin
   `scripts/lib/foundation/scripts/lib/acg/etc/acg-cluster.yaml`) declares a static
   `ServerInstance` + `Agent1Instance` + `Agent2Instance`, with outputs `Agent1PublicIP` and
   `Agent2PublicIP` only.
2. **Agent-IP discovery** — the vendored `scripts/lib/foundation/scripts/lib/acg/acg.sh` (lines
   ~151–157) reads exactly three outputs: `server_ip`, `agent1_ip`, `agent2_ip`. Adding an agent
   silently drops off the end.
3. **Join + readiness** — `scripts/lib/providers/k3s-aws.sh:236` hardcodes
   `UBUNTU_K3S_AGENT_HOSTS="ubuntu-1,ubuntu-2"`, and `:245` hardcodes `total_nodes=3`. The actual
   per-agent join loop is `scripts/plugins/shopping_cart.sh:deploy_app_cluster()` (consumes
   `UBUNTU_K3S_AGENT_HOSTS` at lines ~1215 and ~1286), joined **serially**.

### Prior art — why the last attempt was reverted

`ACG_AGENT_COUNT` existed once and was **deliberately removed** in v1.0.1 (see
`docs/retro/2026-03-31-v1.0.1-retrospective.md` and
`docs/issues/archive/2026-03-31-copilot-pr58-review-findings.md`). Copilot found it inconsistent: the
env var drove `total_nodes` while the CFN template and `UBUNTU_K3S_AGENT_HOSTS` stayed hardcoded at
two agents, so the knob and the reality could disagree. The fix at the time was to hardcode
`total_nodes=3` and let "the CloudFormation template drive node count; bash reflects the template, not
vice versa." The stale help text at `k3s-aws.sh:188` (`ACG_AGENT_COUNT  Number of agent nodes`) is a
leftover from that removal — it documents a knob that is no longer wired.

**This plan does not re-introduce the old bug.** The old design had two sources of truth (the var and
the template) that drifted. The new design has **one** source of truth: `ACG_AGENT_COUNT` *generates*
the template, so the template, the discovery loop, and the readiness gate are all derived from the
same number and cannot drift.

## Goal

Make the fleet lifecycle count-agnostic end to end, driven by a single knob `ACG_AGENT_COUNT` (default
`2`, preserving today's behavior). One value must drive: how many agent instances CloudFormation
creates, how many agent IPs discovery reads, how many hosts the join targets, and how many nodes the
readiness gate expects. Provisioning of the agents must run in parallel with a per-node readiness gate,
and the whole flow must be idempotent on re-run.

## The count-agnostic pattern — six properties (each an interview talking point)

1. **Templated N agents.** The CFN template is *generated* — `Agent${i}Instance` +
   `Agent${i}PublicIP` in a loop, driven by `ACG_AGENT_COUNT`. ACG blocks Auto Scaling Groups, so
   generate N discrete instances, not an ASG.
2. **Dynamic discovery.** Agent-IP resolution queries **all** `Agent*PublicIP` stack outputs; no
   hardcoded `Agent1`/`Agent2` names.
3. **Parallel provisioning.** Configure/join all agents concurrently (background jobs + `wait`), not
   serially — O(1) wall-clock instead of O(N).
4. **Per-node readiness gate.** Each node is validated individually (SSH reachable → runtime installed
   → node reports `Ready`); failures are collected and reported, not fatal on the first bad node
   ("one bad node doesn't sink the fleet").
5. **Idempotent re-run.** Re-running converges: already-joined nodes are skipped, no duplicate joins,
   no duplicate SSH aliases.
6. **Single knob.** `ACG_AGENT_COUNT=N` drives the generated template, the discovery loop, the join
   host list, and the expected-node count together.

## Scope split (upstream-first)

### Part A — `wilddog64/lib-foundation` (lib-acg module) — **do first, release, subtree-pull**

Per the lib-acg subtree discipline (never edit `scripts/lib/foundation/scripts/lib/acg/` directly),
these land upstream in the `lib-foundation` clone, ship as a `lib-foundation` release, and flow into
k3d-manager via subtree pull.

1. **Generated CFN template.** Replace the static two-agent `etc/acg-cluster.yaml` with a generator
   that emits `Server` + N × `Agent${i}Instance` and N × `Agent${i}PublicIP` outputs for
   `ACG_AGENT_COUNT` (default 2). Options, decided during implementation: (a) a small emitter
   function in `acg.sh` that writes the rendered template to a temp file before
   `aws cloudformation deploy`, keeping a 2-agent template checked in as the documented default; or
   (b) a base template plus a generated agents fragment. Either way the rendered template is the only
   thing `deploy` sees, and its agent count equals `ACG_AGENT_COUNT`.
2. **Dynamic agent-IP discovery.** In `acg.sh`, replace the hardcoded `agent1_ip`/`agent2_ip`
   `describe-stacks` reads (~lines 151–157) with a loop that collects **every** `Agent*PublicIP`
   output into an ordered list (`agent_ips[]`), regardless of count.
3. **BATS** in the lib-foundation lib-acg suite using stubbed `aws`:
   - generator emits exactly `ACG_AGENT_COUNT` agent resources + matching outputs;
   - discovery collects N IPs from N outputs, and 2 IPs when unset (default);
   - malformed/zero counts fail before any `aws` call, with no writes;
   - no hardcoded `Agent1`/`Agent2` string survives (disappearance check).
4. **Release** the lib-foundation change (its own `feat/vX.Y.Z` → PR → stamp → tag), record the SHA.

### Part B — `wilddog64/k3d-manager` — **after the subtree pull**

1. **Subtree pull** the released lib-foundation change into `scripts/lib/foundation`; record the
   upstream SHA in the merge commit.
2. **Regenerate** `scripts/etc/acg-cluster.yaml` to match the upstream default (2 agents) so the
   checked-in k3d-manager copy and the upstream copy do not drift; the active template path is still
   the exported `ACG_CLUSTER_TEMPLATE` (`scripts/plugins/acg.sh:14`).
3. **`scripts/lib/providers/k3s-aws.sh`:**
   - derive `UBUNTU_K3S_AGENT_HOSTS` from `ACG_AGENT_COUNT` (e.g. `ubuntu-1,…,ubuntu-N`) instead of
     the hardcoded `ubuntu-1,ubuntu-2` at line 236;
   - set `total_nodes=$((1 + ACG_AGENT_COUNT))` instead of the hardcoded `3` at line 245;
   - update the stale help text at line 188 to describe the now-wired knob (default 2).
4. **`scripts/plugins/shopping_cart.sh:deploy_app_cluster()`** — make the agent join:
   - **parallel** across `UBUNTU_K3S_AGENT_HOSTS` (background jobs + `wait`), replacing the serial
     loop;
   - **per-node readiness**: each node's SSH → runtime → `Ready` checked individually; collect
     failures into a list and report them all, rather than aborting on the first;
   - **idempotent**: skip a node already `Ready`/already joined; never create a duplicate SSH alias
     or re-run a completed join.
5. The `Agent*PublicIP` → SSH-alias (`ubuntu-1`…`ubuntu-N`) wiring must be traced and generalized to N
   during implementation (the write site is downstream of discovery; confirm where the alias file is
   authored and make it count-driven).

## Non-goals

- **Do not** generalize the `k3s-oci` single-agent join — the AWS path is the résumé story; OCI is a
  follow-on and OCI itself is de-scoped (see `project_oci_descoped`).
- **Do not** introduce an Auto Scaling Group — ACG blocks ASGs; N discrete instances is the design.
- **Do not** raise ACG usage beyond its 5-node sandbox cap in this release; the code is written for N
  and *demonstrated* at ≤5.
- **Do not** add HPA in this plan. Workload autoscaling onto the fleet
  (`resources.requests.cpu` + HorizontalPodAutoscaler on frontend/basket/order/payment/product-catalog,
  conservative bounds per the hostinger 2-CPU constraint) is a **secondary, deferred** note, not part
  of this DoD.
- **Do not** change credential/CDP/sandbox-lifecycle behavior in `acg.sh`.

## Verification ladder

Four rungs, cheapest first. BATS alone only proves the *shape* of generation and control-flow; the
"count-agnostic" claim is only true once N real nodes join and go `Ready`. Each rung maps to a real
entrypoint (verified 2026-08-20).

### Rung 0 — offline (no AWS): render + BATS

- **Template render check.** Render the generated template at `ACG_AGENT_COUNT=4`; assert it declares
  exactly 4 `Agent{1..4}Instance` resources and 4 `Agent{1..4}PublicIP` outputs, plus one `Server`.
  Assert `ACG_AGENT_COUNT` unset renders exactly 2 agents (behavior preserved).
- **lib-foundation lib-acg BATS** (stubbed `aws`): generator emits exactly `ACG_AGENT_COUNT` agents +
  matching outputs; dynamic discovery collects N IPs from N `Agent*PublicIP` outputs and 2 when unset;
  malformed/zero counts fail before any `aws` call; no `Agent1`/`Agent2` literal survives.
- **k3d-manager BATS** (stubbed `aws`/`ssh`/`kubectl`): `ACG_AGENT_COUNT` unset → 2 agents /
  `total_nodes=3` / hosts `ubuntu-1,ubuntu-2`; `ACG_AGENT_COUNT=4` → 4 agents / `total_nodes=5` /
  hosts `ubuntu-1,…,ubuntu-4`; parallel-join fan-out spawns N background jobs and `wait`s; a per-node
  failure is collected and reported, not fatal on the first; idempotent re-run adds no duplicate
  host/join/SSH-alias.
- `shellcheck` (default severity — lib-foundation CI catches `info`) clean on `acg.sh`;
  `shellcheck` clean on `k3s-aws.sh` and `shopping_cart.sh`.
- Static disappearance checks: no `ubuntu-1,ubuntu-2` and no `total_nodes=3` literal remains in
  `k3s-aws.sh`; no `agent1_ip`/`agent2_ip` literal remains in the vendored `acg.sh`.
- `_agent_audit` passes.

### Rung 1 — CFN static validation (ACG creds, zero instances)

- `aws cloudformation validate-template` on the rendered `ACG_AGENT_COUNT=4` template returns success —
  proving the generated N-agent YAML is a *deployable* CloudFormation template, not just well-formed text.

### Rung 2 — CFN change-set / dry provision (ACG creds, zero instances)

- `create-change-set --no-execute` (or `acg_provision` dry-run) against the generated template shows a
  plan that would create exactly 5 instances (1 server + 4 agents). No instances are created.

### Rung 3 — real fleet, no app stack (live sandbox, serialized to ONE agent)

The proof rung, and the DoD's live acceptance. This uses **`deploy_cluster`, not `make up`** — the
provider deploy stops at node-join + label + readiness and returns *before* the Istio/Vault/ArgoCD/app
stack is layered on, so it exercises exactly cluster-creation + node-joining without paying for the
whole stack.

- **At the ACG ceiling:** `ACG_AGENT_COUNT=4 deploy_cluster` (server + 4 agents = **5 nodes = the ACG
  5-node cap**). If your ACG plan actually admits a 6th instance, bump to `ACG_AGENT_COUNT=5` for a
  6-node run; the code is count-agnostic either way.
- Confirm all four agents join **in parallel**, all five nodes reach `Ready`
  (`kubectl --context ubuntu-k3s get nodes` = 5 Ready), and a **re-run is a no-op** (idempotent).
- Retain the provisioning log as evidence; tear down with `make down`.

### Each rung is a Makefile target

The ladder ships as first-class `make` targets (provider-aware, `k3s-aws` only), so the gates are
repeatable and discoverable via `make help`, not ad-hoc commands. All take an optional
`ACG_AGENT_COUNT=N` (default 2):

| Target | Rung | Does | Runs |
|---|---|---|---|
| `make fleet-render` | 0 | Render the generated CFN template to stdout + assert agent/output count | offline — Codex + Claude |
| `make fleet-validate` | 1 | `aws cloudformation validate-template` on the rendered template | live — Claude |
| `make fleet-plan` | 2 | `create-change-set --no-execute`; print planned instance count (no create) | live — Claude |
| `make fleet-up` | 3 | `deploy_cluster --confirm` — node-join only, **not** the full `make up` stack | live — Claude, serialized |

Teardown stays `make down`. `make fleet-up` is the node-join-only entrypoint that stops before the
Istio/Vault/ArgoCD/app stack.

## Division of labor — Codex vs Claude (live-sandbox rule)

Per `feedback_serialize_live_sandbox_access`, only ONE agent may touch a live ACG sandbox at a time,
and any `make up/down` / `deploy_cluster` re-provisions and would destroy an in-flight cluster.

- **Codex owns:** all implementation (Part A upstream in the lib-foundation clone, Part B in
  k3d-manager after the subtree pull), Rung 0 in full (offline render + stubbed BATS + shellcheck +
  disappearance checks + `_agent_audit`). Codex must **not** run `make up`, `make down`,
  `deploy_cluster`, `acg_provision`, `validate-template`, `create-change-set`, or `make credential-test`
  — anything that touches the shared ACG sandbox or its CDP browser session.
- **Claude owns:** Rungs 1–3 (everything touching real AWS / the live sandbox), run serialized in a
  single session, and captures the evidence.

## Definition of done

- `ACG_AGENT_COUNT=N` is the single knob that drives the CFN template, agent-IP discovery, the join
  host list, and the readiness gate — with no second source of truth that can drift (the v1.0.1
  regression does not recur).
- Agents provision in parallel with a per-node readiness gate that collects rather than aborts.
- Re-runs converge idempotently.
- Default (`ACG_AGENT_COUNT` unset) reproduces today's two-agent, three-node behavior exactly.
- lib-foundation change released + subtree-pulled; both repos' focused BATS + shellcheck gates pass;
  one live acceptance run at the ACG ceiling (`ACG_AGENT_COUNT=4` → 5 nodes) recorded — run by Claude,
  serialized, via `deploy_cluster` (not `make up`).
