## Goal

Claude runs on the M4 and pushes every commit from there. Nothing updates the other checkouts, so the M5 hub
serves stale answers. On 2026-10-31 the M5's k3d-manager checkout sat at `087b87fc` while `origin` was at
`85d5e7bb`; the Slack `ask-docs` bot answered "v1.43.13: 0 P2 bug docs" when two existed, because it counts
`docs/bugs/` at the checkout's HEAD. The same day the M5's dotfiles checkout was behind and missing a PATH fix.
The bug count itself was fixed in v1.43.13 (`e2b62aa2`, it now reads the fetched upstream ref), but webhook code,
`docs/` read by ask-docs, and the other checkouts still wait for a manual pull.

Each machine should pull for itself. The hub makes only outbound calls (no new inbound endpoint), local work is
never overwritten, and a sync that stops working is noticed.

## Change

1. **`bin/k3dm-repo-sync`** (new, `set -euo pipefail`). For each repository listed for this machine's role (see 3),
   when the checkout exists:
   - Skip, with a logged reason, when: HEAD is detached; a rebase, merge, cherry-pick or bisect is in progress; the
     branch has no upstream; or local commits are not on the upstream (`ahead` > 0, including diverged).
   - Otherwise `git fetch` the upstream branch only, then `git merge --ff-only` to it. Untracked files and local
     edits are left alone; when git refuses the fast-forward because it would overwrite local changes, record
     `blocked` and change nothing.
   - Never `reset`, `rebase`, `stash`, `checkout`, `clean`, switch branch, or pass `--autostash`.
   - Run non-interactively: `GIT_TERMINAL_PROMPT=0`, `GIT_SSH_COMMAND` with `BatchMode=yes` and
     `ConnectTimeout=10`, and a total time limit per repository (default 60 s). An auth or network failure is a
     recorded `fetch_failed`, never a prompt or a hang.
   - One run at a time (a lock directory under `~/.local/share/k3d-manager/repo-sync/`; a second run exits 0 with
     `already running`).
   - Writes `~/.local/share/k3d-manager/repo-sync/state.json`: per repository the path, branch, result
     (`updated`, `current`, `skipped:<reason>`, `blocked`, `fetch_failed`), behind count before and after, old and
     new HEAD, and the run time. One summary line per repository goes to the log.
   - When an update in the k3d-manager checkout changes `scripts/lib/webhook/` or any `bin/k3dm-webhook*`, the run
     logs `webhook code changed; restart pending` and sets `webhook_restart_pending: true` in the state. It never
     restarts the webhook.
   - `--remote HOST` runs the same command on HOST over SSH (`BatchMode=yes`) and prints its summary; this is the
     post-push nudge (see 5). `--check` prints what it would do without fetching or merging.
2. **Metrics (hub only).** After each run on the `hub` role, push one Pushgateway group (`job=k3dm_repo_sync`,
   `instance=<short hostname>`) through the existing Pushgateway helper:
   `k3dm_repo_sync_behind_commits{repo}`, `k3dm_repo_sync_last_success_timestamp_seconds{repo}`,
   `k3dm_repo_sync_result{repo,result}` (1 for the current result) and `k3dm_repo_sync_webhook_restart_pending`.
   A Pushgateway failure is logged and does not fail the run.
3. **Which repositories.** Reuse `scripts/etc/machine/repos.list`: every row whose roles include this machine's role
   and whose remote is not `SKIP:`. The branch column is not enforced; the sync follows whatever branch is checked
   out. The k3d-manager checkout itself is always included.
4. **Install.** `scripts/etc/launchd/com.k3d-manager.repo-sync.plist.tmpl` (`StartInterval` 300, `RunAtLoad`), a
   Makefile `install-repo-sync` / `uninstall-repo-sync` pair modelled on the existing heartbeat install, and an
   `install-repo-sync` line in `agents.hub.list`, `agents.console.list` and `agents.worker.list`.
5. **Post-push nudge.** `make hub-sync` runs `bin/k3dm-repo-sync --remote "$K3DM_HUB_HOST"` (default the hub host in
   `scripts/etc/hostinger/vars.sh` or the fleet config, whichever already names the M5). The push line that
   `codex-land` prints becomes `git push ... && make hub-sync`. A failed nudge prints one warning and exits 0;
   the timer catches up.
6. **Alert.** `K3dmRepoSyncStale`: on the hub, the k3d-manager repository's last success is older than 60 minutes
   for 10 minutes, or its result is `blocked` or `fetch_failed` for 30 minutes. Severity `warning`, routed like the
   other hub warnings (Slack/email, not SMS). The annotation names the repository and the result, never a URL with
   credentials.
8. **Deploy-pending report.** A pulled commit is not live until its deploy step runs. On the `hub` role, after each run,
   the sync works out which deploy steps are pending and records them; it never runs them.
   - `scripts/etc/machine/deploy-paths.tsv` (new) maps path prefixes to a step: `scripts/etc/argocd/platform-ops/` →
     `platform-ops`; `scripts/lib/webhook/` and `bin/k3dm-webhook` → `webhook-restart` (replaces the hard-coded check
     in 1; `webhook_restart_pending` stays in the state, derived from this list).
   - `platform-ops` is pending when a mapped file changed between the commit of the last successful
     `make platform-ops` and HEAD. On success, the `platform-ops` Makefile target writes that commit to
     `~/.local/share/k3d-manager/repo-sync/deployed-platform-ops`. With no marker, the step is `unknown`, not pending.
   - `appsets-reapply` is pending when the checkout is on a release branch and any hub Application reads another
     branch. Reuse the read-only query behind `make appsets-check`; do not write a second one. When the cluster
     cannot be reached, record `unknown`; the run still succeeds.
   - State: `deploy_pending` lists `{step, since_commit, paths (at most 5)}`; `deploy_unknown` lists steps that could
     not be decided.
   - Metric: `k3dm_repo_sync_deploy_pending{step}` (1 pending, 0 not, absent when unknown), in the same Pushgateway
     group.
   - Alert: `K3dmDeployPending`, any step pending for 30 minutes. Severity `warning`, routed like the other hub
     warnings. The annotation names the step and the command to run (`make platform-ops`, `make appsets-reapply`,
     restart the webhook). Same rule file as 6.
9. **The nudge reports the hub.** `make hub-sync` prints one line after the remote run, from the hub's state:
   `hub <host>: <branch> at <short sha> (<result>); deploy pending: <steps or none>`. `codex-land`'s printed push line
   already runs it (5), so after a push Claude can say "the M5 is at X; run `make platform-ops`" without anyone
   checking first. When SSH fails, it prints the warning from 5 and exits 0.
10. **Docs.** `docs/howto/checkout-auto-sync.md`: what it does, what it never does, how to read the state file, how
   to pause it (`make uninstall-repo-sync`), and that a webhook restart is still manual.

## Amendment 2026-11-08 — the hub follows `deploy/hub`

Written before `v1.43.15-hub-deploy-ref-and-live-write-guard` landed. That plan makes `deploy/hub` the only ref the
hub reads, and `make platform-ops` applies the `deploy/hub` tree. Three parts of this plan assumed the hub follows the
release branch:

- **A1 — what the hub's checkout follows (item 1, item 3).** The webhook and Hermes run from the M5's k3d-manager
  checkout, outside ArgoCD. Fast-forwarding it to the release branch would land unpromoted code on the running hub.
  On the `hub` role, the k3d-manager checkout fast-forwards to `origin/deploy/hub` instead of its upstream (fetch
  `deploy/hub` only). When `deploy/hub` is not a fast-forward of HEAD (after a rollback, or once a squash-merged
  `main` commit is promoted), the checkout is left alone and the result is `skipped:not-ff-to-deploy-hub`; the
  operator moves it by hand. Other repositories, and every other role, are unchanged.
- **A2 — platform-ops pending (item 8).** The marker records the SHA `make platform-ops` applied (H3 prints it), not
  the checkout HEAD. Pending means a mapped path changed between the marker SHA and `origin/deploy/hub`.
- **A3 — appsets-reapply pending (item 8).** Pending when any hub Application does not read `deploy/hub`, from the
  query behind `make appsets-check` (whose default is now `deploy/hub`). The release-branch condition is removed.
- **A4 — promote backlog (report only, items 8 and 9).** The state records how many commits the checkout's
  upstream branch is ahead of `deploy/hub`, as `make hub-promote-status` counts them, and `make hub-sync` prints it.
  No alert: promoting is the operator's decision. The sync never moves `deploy/hub` (N8).

Files: no new file; `bin/k3dm-repo-sync`, `Makefile` (`platform-ops` writes the applied SHA) and
`scripts/tests/bin/repo_sync.bats` carry the change.

## What NOT to do

- Do not add an inbound trigger (GitHub webhook, HTTP endpoint) on the hub.
- Do not restart the webhook or any LaunchAgent from the sync.
- Do not run a deploy step from the sync, and do not add a second ApplicationSet query beside `make appsets-check`'s.
- Do not switch branches to match `repos.list`.
- Do not move `deploy/hub` or run `make hub-promote` / `make hub-rollback` from the sync.
- Tests never touch real checkouts, the real `~/Library/LaunchAgents`, the real Pushgateway or the real hub.

## Not in this plan

- Automatic webhook restarts after a code change (revisit once the restart-pending metric shows how often it happens).
- Running a deploy step from the sync or from a LaunchAgent (for `make platform-ops`, which reads the login Keychain);
  revisit once `K3dmDeployPending` shows how often a deploy waits.
- Linux (systemd timer) install for the `control` role on Linux; follows `v1.43.15-control-node-linux`.
