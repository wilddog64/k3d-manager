## Operator observation

On 2026-10-15 a new P2 bug document was committed to `k3d-manager-v1.43.2` (`d1c09401`). Grafana initially showed `noop`, 8.50 hours since last successful index, zero embedded/cache/pruned/backlog and `not paused`. A later screenshot showed `success`, 2.61 minutes since last success, around two seconds of run duration, no quota pause and zero backlog. This is **not proven to be a malfunction**: short *execution duration* and larger *age since last successful index* are different measurements. A successful indexer invocation does not by itself prove the particular Git commit was indexed or is retrievable. The dashboard currently makes that distinction difficult.

## Goal

Provide unambiguous answer to:
1. When did Hermes **last attempt** indexing, and what was its result?
2. When did the most recent **successful index operation** finish, and how long did it take?
3. **Which exact Git source/ref and immutable commit SHA** was processed and committed to the vector store?
4. Does the processed SHA match the **currently fetched source SHA**, and is new work pending?
5. Did the cycle actually embed/cache/prune any documents, or finish successfully with zero document changes?

## Scope

- Extend the existing VectorDB indexing dashboard, not a new dashboard or service.
- Add **Last attempt (UTC)**, **Last successful index (UTC)**, and **Last indexed Git commit (short SHA + full SHA in metadata/detail)**. Retain existing last run result, index-age, runtime duration, API/cache/pruned counts, backlog and quota panels, with explanatory descriptions.
- Also show **source ref** (e.g. `origin/k3d-manager-v1.43.2`), **fetched/head commit** and whether it matches the indexed commit. The tracking ref is selected by `K3DM_INDEX_REF` or the checkout's upstream; display the actual resolved ref, not a guessed branch or `main`.
- Define precise semantics for `noop` (unchanged fingerprint, no indexing work), `success` (index-docs returned successfully), `paused`, `failed`, and successful **zero-write** runs. Do not label `noop` as new indexing success.
- Show short, actionable text: `up-to-date`, `pending`, `unknown`, or `failed`. Never show `up-to-date` solely because backlog is zero; only assert it when source SHA and indexed SHA are both known and match, with successful durable index result.
- Prefer fixed-label numeric gauges for timestamps/duration and existing bounded status/result metrics. For SHA/ref metadata, use a bounded info-style metric with exactly one active series or existing local state/status endpoint; avoid per-commit accumulating time series and unbounded labels. Document chosen retention behavior.
- Record a successfully **committed** indexed ref/SHA atomically with durable indexing completion, not on mere fetch/start. Ensure interrupted/partial/index-paused runs do not falsely advance the indexed SHA. For partial batch writes, represent pending/unknown as appropriate.
- Keep the current Git fetch/corpus fingerprint/noop optimization; this enhancement is observability only, not a request to change synchronization policy, indexing quota, or RAG retrieval.

## Implementation guidance

Study `bin/k3dm-hermes` (`_index_ref`, `_refresh_index`, `_push_index_metrics`) and `scripts/index-docs.py` to find the true durable commit boundary and decide how to persist/prove it. Reuse the existing Pushgateway and Prometheus dashboard pipeline. Add a low-cardinality result contract rather than arbitrary Git state encoded as many metric labels. At each tick, distinguish selected/ref-resolved SHA, fetched SHA, and last successfully committed indexed SHA; document what a forced/noop run means.

### Acceptance tests

1. New tracked document on the configured branch, successful fetch + index: dashboard advances indexed SHA only after successful commit; source/indexed SHAs match.
2. New commit fetched, indexing paused/failed: fetched SHA moves; indexed SHA does not; status shows pending/failed, not fresh.
3. Fingerprint unchanged: `noop` updates last-attempt time but not last-success time, without implying missing work.
4. Full successful run with zero changed documents: valid success; zero written; provenance preserved or advanced only if its index contract is satisfied.
5. Partial `--limit 100` processing with outstanding docs: last fully indexed commit must not be incorrectly advanced; backlog/pending visible.
6. Git fetch failure, wrong tracking ref, unavailable vector DB or malformed state: report unknown/error without falsely green status.
7. Grafana presentation differentiates *duration* (seconds) from *age* (elapsed since completion), includes readable UTC timestamps, and does not display stale metadata as fresh.
8. Unit/BATS tests for the exporter, metrics shape, SHA transition and dashboard contracts; no real secrets, no production mutation; full `test-all` gate.

## Out of scope

No new arbitrary shell/cloud-bridge privileges; no forced reindex on every tick; no index-persistence redesign; no changes to existing v1.44.0 historical diagnostic bridge action. Spec-only until independently approved for implementation.
