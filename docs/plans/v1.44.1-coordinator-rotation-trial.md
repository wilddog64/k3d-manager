## Problem

Claude is the coordinator today: it triages, writes specs, dispatches, reviews, lands, and runs
read-only live checks. The operator wants each agent to take that lead role in turn (Claude, Codex,
agy/Argon), and to compare how each one performs.

The question started from an observation on 2026-10-24: Claude's own bug sweep (reading docs and
running read-only checks, no dispatch) seemed to use the weekly quota slowly. Nothing measures that
today. The dashboard counts dispatches, not the coordinator's own work, and it doesn't split quota
use by kind of activity.

## Design

- **The trial.** One coordinator per period, a week by default, set by the operator. The other
  agents keep their worker roles.
- **The rules are the same for every coordinator.** `CLAUDE.md`, `AGENTS.md` and `GEMINI.md` already
  carry the session rules; this plan adds a short "When you are the coordinator" section to
  `AGENTS.md` and `GEMINI.md` that points at the CLAUDE.md rules, and changes nothing else.
- **Limit for the agy coordinator.** Live verification stays with the operator or Claude, as it does
  today, so the operator runs every live check during the agy coordinator's period. The ledger records
  each such handoff, because it is part of the cost of that coordinator.
- **What gets recorded.** The coordinator wraps each block of its own work in an activity record
  from `bin/k3dm-coord`.

## Fix

### F1. `bin/k3dm-coord`: an activity ledger

- `bin/k3dm-coord begin --agent claude|codex|agy --activity <kind> [--ref <doc or slug>]` prints an
  activity ID. `bin/k3dm-coord end <id> [--outcome done|abandoned|handed-off]` closes it.
- `<kind>` is one of `bug-sweep`, `triage`, `spec-write`, `dispatch`, `review`, `land`, `live-check`,
  `release`, `other`. Anything else is refused.
- On both `begin` and `end`, the tool samples that agent's window sources (the 5-hour and 7-day used
  percent, and `resets_at`) with the same reader as the window plan. It then appends one JSON line
  to the dispatch ledger directory as `coord_begin` or `coord_end`.
- A missing source writes the record with null windows, not zero.
- `bin/k3dm-coord rotate --agent <name>` records which agent is coordinating from now on.
  `bin/k3dm-coord current` prints it.
- Make targets: `coord-begin`, `coord-end`, `coord-rotate`, `coord-current`.

### F2. The exporter

New series in `bin/k3dm-dispatch-metrics`:

- `k3dm_coord_activity_seconds_total{agent, activity}`
- `k3dm_coord_activity_count{agent, activity, outcome}`
- `k3dm_coord_weekly_used_percent_total{agent, activity}`: the 7-day used percent at `end` minus at `begin`.
- `k3dm_coord_window_used_percent_total{agent, activity}`: the same for the 5-hour window.
- `k3dm_coord_unmeasured_count{agent, activity}`: activities with no usable window delta.
- `k3dm_coord_current{agent}`: 1 for the current coordinator, 0 for the others.

Rules for the window deltas:

- **Window reset:** a delta is counted only when `begin` and `end` share the same `resets_at`.
  Across a reset the activity counts as unmeasured, never as a negative or a guessed value.
- **Overlap:** when two activities of the same agent overlap in time, both count as unmeasured for
  quota, because the delta can't be split. Their time is still counted.
- **Outcomes per coordinator period:** specs landed, bugs closed, rework rounds per landed spec,
  live checks handed to the operator, and defects found later. A "defect found later" is a bug doc
  whose `**Related:**` names a spec landed in that period.

### F3. Dashboard row "Coordinator"

On the agent dispatch dashboard:

1. A stat per agent: weekly percent used per hour of coordinator activity, split by activity kind.
2. A table with one row per agent per period: hours, specs landed, bugs closed, rework rounds per
   spec, live checks handed off, defects found later, and the weekly percent used.
3. A bar chart: weekly percent used per activity kind, by agent. This chart answers whether a bug
   sweep is cheaper than review-and-land, and for which agent.
4. The current coordinator.

Each panel's description says that the percent numbers are relative to each agent's own plan. They
compare how an agent spends its budget, not raw cost across vendors.

## Vendor-neutral coordinator versus worker attribution — 2026-10-27

**Operator request:** compare Sol 6.1 coordinating Luna with Opus 4.8 coordinating Sonnet/Haiku. Extend this existing v1.44.1 plan 5/5, not a separate plan.

- The coordinator and worker are **separate actor roles**, each with provider, runtime and verified effective model. A shared vendor CLI does not imply that coordinator and worker used the same model. Track primary coordinator, acting coordinator on handoff, worker, land actor, run ancestry and immutable task version in the existing ledger.
- Persist measured usage at actor/activity boundaries when supported, with source ID and sample age. Explicitly preserve unknown if there is no reliable model attribution, quota source, or cost breakdown; never charge worker tokens to the coordinator, or infer an Opus/Haiku run from task naming.
- Outcome comparisons group by coordinator–worker pair, task complexity bands, release window, test evidence status, first-pass acceptance, rework, verified landing and elapsed time. Report denominators and selection bias; do not rank teams on tiny or mixed samples. Human continuation prompts and unobserved work must be distinguished.
- On handoff and quota exhaustion, persist an operator-readable checkpoint and remaining task authorization; a fresh model must not inherit widened privileges or restart a worker run simply because the prior coordinator stopped.
- Test fixtures: Sol → Luna, Opus → Sonnet, Opus → Haiku, unknown model, mixed-coordinator release, failed/missing usage source, handoff and simultaneous workers. Verify model attribution, no double-counting and explicit unknowns.
- **Acceptance addition:** Dashboard can distinguish coordinator versus worker contributions and show verified results and measurable costs for each pairing; it must never imply the entire current release was produced by one coordinator. Preserve old records and dashboard compatibility.


## Quota-aware coordinator handoff and worker reservation — 2026-10-27

**Operator request:** Coordinate Claude Opus and GPT-6.1 Sol coverage across independent provider resets while Luna workers share Codex capacity with a Sol coordinator. This amends the existing plan 5/5, not a new feature slot. Switching is operator-controlled in this release; Hermes only advises.

### F5. Shared quota-pool admission and reservations
- Model each quota pool independently from individual agent/model identity. `claude-cli` Opus coordinator generally draws on the Claude subscription pool; Sol running through Codex and Luna workers may share the **same Codex pool**. This mapping must be explicitly operator-configured or verified, never deduced solely from model name.
- Before start/resume/rotation, calculate an advisory availability decision for coordinator **and** intended worker using only approved read-only usage sources: available / low / exhausted / unknown / stale. Unknown is not 0 and is not permission to claim continuity.
- Support operator-configured *advisory* Codex worker reserve and low-watermark thresholds. A Sol coordinator must not silently consume capacity explicitly reserved for Luna. No undocumented vendor throttle, reset-time assumptions or external rate-limit API calls.
- Keep time-window (5h) and weekly (7d, where available) constraints independent, including reset timestamps and cache freshness. Do not assume both vendors reset together or that one reset restores the other.
- Do not automatically reroute to other models or charge one runtime's costs to another.

### F6. Durable, idempotent operator-controlled handoff
- A handoff checkpoint captures: originating coordinator and acting coordinator, quota source/freshness and reason; release/ref/SHA; task and run IDs; active worker and worktree ownership; latest event/exit state; last independently verified tests; pending reviews, approvals, risks and actionable next step.
- On rotation, record a durable append-only handoff event with an idempotency key and ownership epoch. Use a lock/fencing contract to prevent two coordinators from owning a task concurrently. A missing or incomplete checkpoint fails closed for new task mutation; existing workers are not killed or re-dispatched.
- `coord rotate` should preview status and checkpoint, require explicit operator confirmation, then change the acting coordinator; the coordinator CLI cannot grant permissions or approvals. Resume/reconcile only after checking the current ledger, worktree, process and landed SHA; avoid duplicate workers and double-counted outcomes.
- At usage exhaustion, persist a pause reason and next reset if **observed**; if not available, record unknown. Never promise an automatic restart, and never imply a fresh coordinator inherits the previous coordinator's credentials.
- Ensure this is an additive extension to v1.44.1's existing rotation and identity work. Production-enforced cross-host task fencing and automated failover remain deferred until v2.2 policy governance and tested coordination primitives.

### F7. Dashboard and E2E acceptance additions
- Show coordinator/worker pool, freshness, handoff reason, pending-review count, reserved worker capacity warning and resume/paused state; distinguish advisory from enforced decisions.
- Test sequences: Opus→Luna for several days, Claude weekly exhaustion, operator handoff to Sol→Luna, Codex 5h exhaustion before weekly, Codex pool shared by Sol/Luna, operator return to Opus when its weekly reset is observed, unknown/missing sources, repeated rotation and interrupted coordinator process.
- Negative assertions: no duplicate Luna worker; no two active owners; no task/approval loss; no invented reset time; no unauthorized model auto-switch; no silent bypass of worker reserve; no live credentials or full worker transcripts in dashboard.
- Document a rollback path to manual coordinator selection and existing dispatch behavior. An independent live exercise requires operator approval and a reconciled run ledger before marking the feature live-verified.
