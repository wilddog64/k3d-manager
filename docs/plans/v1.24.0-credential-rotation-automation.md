# v1.24.0 (E) — Recurring credential-rotation automation: ArgoCD / Prometheus / Alertmanager

**Branch:** `k3d-manager-v1.24.0`
**Type:** design + implementation spec (design-led; the credential-application step differs per service)

---

## Problem

Recurring, unattended credential rotation exists for only **two** platform services — LDAP and Grafana
(both have monthly Vault-sourced rotator CronJobs). **ArgoCD, Prometheus, and Alertmanager admin/basic-auth
credentials were rotated once by hand** and have no automation. This is the last un-built slice of
workstream E.

**Goal:** each of the three services gets a monthly Vault-sourced rotator that mirrors the proven
Grafana pattern (`scripts/etc/argocd/platform-ops/grafana-credential-rotator.yaml`): Vault k8s-auth
login → read old → generate new → write Vault → force-sync ESO → apply to the consumer → Slack notify,
with a `trap`-based restore-on-failure.

---

## The proven pattern (reference: `grafana-credential-rotator.yaml`)

```
CronJob (0 0 1 * *, Forbid, alpine/k8s:1.31.4, runAsUser 65534)
  → Vault k8s login  (role: <service>-rotation)
  → read old = secret/data/<path>.password
  → new = head -c 24 /dev/urandom | od -An -tx1
  → trap restore EXIT   (write old back + force-sync ESO)
  → write Vault new
  → kubectl annotate externalsecret <es> force-sync=$(date +%s)
  → <SERVICE-SPECIFIC APPLICATION STEP>          ← the part that differs
  → Slack notify via platform-ops-notifications (value-free message)
  → trap - EXIT
```

The **only** part that differs per service is the application step. Grafana's is plaintext
(`grafana cli admin reset-admin-password --password-from-stdin`). The three new services need a
**hashed** credential written into a consumer secret — that is the design work.

## Per-service analysis

| Service | Namespace | Consumer secret (confirm live) | Application mechanism | Complication |
|---------|-----------|-------------------------------|-----------------------|--------------|
| **ArgoCD admin** | `cicd` | `argocd-secret` keys `admin.password` (bcrypt) + `admin.passwordMtime` | patch `argocd-secret` with `bcrypt(new)` + RFC3339 mtime, OR `argocd account update-password` via CLI | bcrypt hashing inside an `alpine/k8s` job (no htpasswd guarantee); ESO template must emit bcrypt or the job hashes and patches directly |
| **Prometheus** basic-auth | `monitoring` | web-config basic_auth secret behind the auth proxy (`alertmanager_auth_proxy.bats` sibling) | patch htpasswd (bcrypt) secret, restart proxy/prometheus | shared auth-proxy pattern with Alertmanager — likely one credential, confirm |
| **Alertmanager** basic-auth | `monitoring` | web-config basic_auth secret | patch htpasswd (bcrypt) secret, restart proxy/alertmanager | may share the Prometheus proxy credential — if so, ONE rotator not two |

## Design decisions (resolve before implementing)

1. **One rotator per service vs a parameterized template.** Recommend **one manifest file per service**
   (`argocd-credential-rotator.yaml`, `observability-basicauth-rotator.yaml`) — matches the existing
   one-file-per-rotator convention and keeps per-service RBAC least-privilege. If Prometheus and
   Alertmanager share a single basic-auth credential, they share **one** rotator.
2. **Hashing inside the job.** `alpine/k8s:1.31.4` has no guaranteed `htpasswd`/`bcrypt` binary (same
   class of gap that broke the Grafana rotator on `openssl`). Decide: (a) add a tiny hashing step the
   image can run (python `bcrypt` is not present either), or (b) use each app's own CLI
   (`argocd account bcrypt` / prometheus web-config tooling) via `kubectl exec` into the running pod,
   mirroring how Grafana used `grafana cli`. **Recommend (b)** — reuse the app's own hasher, no new deps.
3. **ESO vs direct patch.** Grafana round-trips through ESO force-sync. For bcrypt-in-secret consumers,
   decide whether ESO templates the hash or the job patches the consumer secret directly after writing
   plaintext to Vault. Keep Vault as the source of truth for the **plaintext**; the consumer secret holds
   the hash.
4. **Vault k8s-auth roles + policies.** Each rotator needs its own role (`argocd-rotation`,
   `observability-rotation`) bound to its ServiceAccount, with a policy granting `read`+`write` on ONLY
   that service's KV path (least privilege — CLAUDE.md OWASP A01).

## Rules

- Least privilege: each rotator's Vault policy and k8s Role scoped to ONLY its own path/secret (`resourceNames`).
- Pin `alpine/k8s:1.31.4` (no floating `latest`); `runAsNonRoot`/`runAsUser: 65534`; `concurrencyPolicy: Forbid`; `ttlSecondsAfterFinished`.
- No plaintext credential in Slack messages (value-free notify, as Grafana does).
- No secrets in `kubectl exec` command strings that appear in logs — pass via stdin (as Grafana does).
- `shellcheck -S warning` clean on `vault.sh`/`observability.sh` hunks; `bats` green.

## What NOT to Do

- Do NOT re-implement the Grafana rotator — it shipped in v1.23.0; SKIP it entirely.
- Do NOT grant a rotator `cluster-admin` or a broad Vault policy — one path each.
- Do NOT add a new hashing dependency to the job image if the app's own CLI can hash (decision 2b).
- Do NOT create a PR; do NOT `--no-verify`; do NOT commit to `main`.
