## Problem

The PR Checks dashboard intentionally lists only currently open pull requests. A successful merge or close removes the row on the next successful Hermes poll. This correctly reflects Open PRs, but leaves no history of a Dependabot PR failing CI, a Copilot repair, a successful rerun and merge. Operators mistakenly look at the unrelated Current CVE Remediation Status panel, whose `state=applied` means verified deployment and has no necessary relationship to GitHub PR merge events. This is missing visibility, **not** a defect in the existing open-PR behavior.

## Design

1. Reuse the existing Hermes GitHub read token, repository allowlist, five-minute poll, exporter and Grafana `k3dm-pr-checks` dashboard. No new service, credential, scheduler, SIEM or default auto-merge.
2. Collect **recent merged** and **closed without merge** PRs for allowed repositories with a configurable default lookback of 30 days. Track `repo` + `pr_number` + immutable head SHA, opened/closed/merged timestamps (UTC), final known checks and evidence refresh timestamp. Distinguish authoritative GitHub merge/closed facts from last-observed CI state. CI passed earlier does not imply the latest merge commit was independently tested.
3. Preserve existing open-PR counters, queries and table exactly. Add separate **Recently Merged PRs** and **Closed Without Merge** tables, plus optional recent-merge totals. Merged entries must never inflate `Open PRs`, `Failing` or `Running`.
4. Persist a bounded, deduplicated PR lifecycle cache across successive polls, with idempotent upserts keyed by repo + PR + head revision / event type where needed. Avoid changing history due to polling windows. Explicit retention and pruning, corrupt-cache handling and no guessed completion state.
5. Record check-run status for the relevant head SHA when available and the last successful GitHub read timestamp. Missing, timed-out, inaccessible or stale GitHub results show **unknown/stale**, not `success`; an unsuccessful poll retains the last proven state with its age rather than falsely marking a PR merged.
6. Do not infer that Copilot performed a repair merely from commit authorship or a comment; display `repair actor` only when a reliable GitHub event or explicitly linked audit record proves it. Likewise, do not equate CVE auto-patch `applied` with a PR merge.
7. Scope is the current supported repository allowlist. Avoid excessive GitHub API requests: pagination bounds, conditional requests when supported, per-poll deadline and rate-limit handling. Bounded labels in Prometheus; full per-PR detail in the existing bounded table data path or durable local records, never arbitrary PR title/SHAs as new metric labels.

## Tests

1. A PR transitions open/failing → new head/success → merged; open count falls, one merged history row appears with correct repo/PR/SHA and merge time.
2. A PR closed without merging appears only in the closed-without-merge table.
3. Duplicate polling emits one history row; PR numbers in different repos remain distinct.
4. GitHub read failure preserves a marked-stale last observation and does not fabricate new merges or green checks.
5. A PR whose checks were successful on an earlier head but failed/unknown on the latest head is not shown as verified green.
6. A merged Dependabot Java image PR repaired by Copilot is displayable as merged with final observed CI; Copilot attribution stays unknown unless independently evidenced.
7. CVE remediation records never appear as PR history merely because they have `applied` state.
8. Retention expiry and malformed cache behave deterministically; API budget and credential redaction tests pass.
9. Existing open-PR dashboard queries and alert values remain unchanged.
