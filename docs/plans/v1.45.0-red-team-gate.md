## Why

Each v1.45.0 spec was reviewed against its own Acceptance. Nobody has attacked the release as a whole: what an attacker
with one foothold (a console session, write access to a branch, a local unprivileged process, a leaked bundle) can chain
into across features. The new surfaces share one host (the hub, m5-air), so the seams between them are the risk.

## Threat model (starting points, not limits)

Attackers: (1) a holder of a valid console login without the TOTP factor; (2) a console user past the gate (the forced
command is the only shell they should get); (3) an unprivileged local process on the hub; (4) someone with push access to
a non-protected branch or the `cloud-requests` / `cve-pins/hub` branch; (5) someone holding a copied travel bundle;
(6) anyone reading CI logs, launchd logs, shell history or process lists.

Questions each reviewer must answer for every surface: input validation and injection (shell, argv, path, YAML/envsubst);
TOCTOU and symlink races on files a root process reads or writes; approval forgery, replay, expiry and binding to the exact
ref/SHA; privilege of each process (root only where needed, file modes, socket permissions); secrets in argv, env dumps,
logs, temp files, crash output; TOTP brute force, replay window, clock skew, lockout, secret storage; forced-command escape;
crypto choices (algorithms, randomness, key handling); fail-open versus fail-closed on errors; and cross-surface chains.

## Rules of engagement

- Offline and read-only. Reviewers read code and may write proof-of-concept tests that run only under a scratch HOME and
  temp dirs they create and assert first (`docs/process/rules.md#test-controls`). No `sudo`, no launchctl, no network, no
  install targets, no hub, Cloudflare, GitHub or cluster access. A finding that needs live proof is written as a proposed
  probe for the operator.
- Never read, print or copy a real secret, Keychain value or `~/.codex/auth.json`; use fixtures.
- PoC files stay in the reviewer's scratch dir and are not committed; Claude moves any accepted PoC into a fix spec's test.
- Fable and Astra work independently from this spec and the code; neither sees the other's report.

## Output

Each reviewer writes one report: commit reviewed, then findings ranked by severity, each with surface, file:line,
attacker (from the threat model), preconditions, concrete steps, impact, a PoC or why none is possible offline, and a
suggested fix. Also a short "attacked and held" list, so coverage is visible.

Claude adjudicates: reproduces each claimed finding (offline PoC or code reading), marks it confirmed, plausible or
rejected with a reason, merges duplicates across the two reports, and maps each confirmed finding to a priority:
P0/P1 are fixed before the release PR (bug doc + dispatch at once); P2/P3 are captured as `docs/bugs/` docs per the
capture-first rule. The merged report is committed as `docs/issues/2026-11-XX-v1.45.0-red-team.md` with no secret values
and no working exploit against the live hub beyond what the fix spec needs.
