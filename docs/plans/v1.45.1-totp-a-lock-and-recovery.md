## Problem

`totpd` locks for a flat 300 s after five failures and then resets (`k3dm-console-totpd.py:744-748`, `:794`), so a
certificate holder gets about 1,440 guesses a day at 3 in 10^6 each, and nothing is logged. There is no way to clear a
lock except waiting, and no way back in without the authenticator. The operator travels with an iPad only, so the way
back in must work from the console, without root on the hub.

## Behaviour

Parent **B1–B5 and B8**, in full. Summary for the worker; the parent's text wins where they differ.

1. **Escalating lock (B1).** `LOCK_SECONDS = [300, 1800, 14400, 86400]`. Five consecutive failures raise `lock_level`
   by one (cap 4) and lock for `LOCK_SECONDS[level-1]`; the fifth failure replies `NO`, attempts while locked reply
   `WAIT <remaining>`. On expiry `failures` resets to 0 and `lock_level` is kept. Level 4 repeats 24 h locks; it is never
   permanent and there is no `LOCKED` reply (operator Q3).
2. **Decay (B1, operator Q4).** With no active lock and `lock_level > 0`, the level drops by one per full 86400 s since
   the last lock expired, anchored on `locked_until` (kept on disk after expiry while `lock_level > 0`). Applied at the
   next VERIFY and at daemon start. At level 0 write the 5-key form with `locked_until: 0` and log
   `totp-unlock source=decay`.
3. **Clock (B2).** The running daemon enforces the lock against `monotonic()` with `lock_deadline_mono`, set once per
   lock (at imposition, or at start as `monotonic() + clamp(locked_until - clock(), 0, LOCK_SECONDS[level-1])`), rebuilt
   only when `locked_until` on disk changes.
4. **State (B3).** `load_state` accepts the v1.45.0 5-key set or the 5 keys plus `lock_level` (int 1–4 when present);
   anything else is state-unavailable, as today. Writers add `lock_level` only when non-zero.
5. **Unlock (B4).** Admin `UNLOCK` (peer uid 0) → `UNLOCKED` and a 5-key reset commit, or `NOT_ENROLLED` /
   `UNAVAILABLE`. `totpctl unlock` prints `unlocked`.
6. **Recovery codes (B8).**
   - Pending set of 10 codes (`os.urandom(10)` → 16 base32 characters, shown `XXXX-XXXX-XXXX-XXXX`) made at
     `ENROLL_BEGIN`, `ROTATE_BEGIN` and `RECOVERY_BEGIN`, held beside the pending secret with the same 300 s window.
     `RECOVERY_GET <i>` (0–9) → `CODE <grouped>` | `UNAVAILABLE`.
   - `<state_dir>/recovery.json`, root 0600, `{"v": 1, "codes": [{"s": <32 hex>, "h": <64 hex sha256(salt || code)>}]}`,
     0–10 entries, written with `commit_state`'s atomic pattern (generalise `commit_state` to take a file name, or add a
     sibling; keep its pre-/post-rename error split). Enrol/rotate commit `recovery.json` first, then `state.json`.
   - `load_recovery`: symlink, non-regular, wrong owner, mode ≠ 0600, format deviation or > 10 entries → recovery
     unavailable, logged `totp-recovery-damaged`; missing → 0 codes. Never makes TOTP login unavailable.
   - Gate: buffer cap 7 → 20 (`k3dm-console-gate.py:327-328`); accept 6 digits, or 16 `[A-Z2-7]` after uppercasing and
     removing hyphens, sent as `VERIFY XXXX-XXXX-XXXX-XXXX`; anything else stays the local "Invalid code". Regex `:157`
     and branches `:338-352` unchanged.
   - totpd VERIFY accepts exactly `[0-9]{6}` or `[A-Z2-7]{4}(-[A-Z2-7]{4}){3}`.
   - One recovery-format attempt per 60 s against `monotonic()` (`recovery_next_mono`), locked or not; inside the window
     → `WAIT <remaining>`, not evaluated.
   - Compare with every remaining entry via `hmac.compare_digest`, no early exit. Valid: burn (commit `recovery.json`
     without the entry) before the reply, then commit the 5-key reset and reply `OK`; `last_counter` unchanged. Burn
     fails pre-rename → `UNAVAILABLE`, code still valid. Reset fails pre-rename after the burn → `UNAVAILABLE`, code
     spent. Post-rename failures keep today's fatal exit.
   - Wrong code: not locked → counts as a failure, `NO`; locked → `NO`, lock unchanged. No codes left or recovery
     unavailable → handled as a wrong code. TOTP input while locked → `WAIT <n>`.
   - Admin `RECOVERY_STATUS` → `RECOVERY <n>` | `NOT_ENROLLED` | `UNAVAILABLE`; `RECOVERY_BEGIN` → `RECOVERY_PENDING` |
     `NOT_ENROLLED` | `REFUSED`; `RECOVERY_COMMIT` → `OK` | `UNAVAILABLE` (replaces the whole set). All peer uid 0.
   - totpctl: `recovery-status` prints `recovery codes left: <n>`; `recovery-regen` fetches the ten codes, prints them
     on `/dev/tty`, asks the operator to type `yes`, then commits (otherwise sends `ABORT`); `enroll` / `rotate` print the
     ten codes on `/dev/tty` after the secret and before asking for the code. No code on stdout, in argv or in env; the
     existing scrollback clear (`k3dm-console-totpctl.py:141`) covers them.
7. **Log lines (B5).** `<UTC ISO-8601> event=<name> key=value ...`, bare names kept: `totp-failure`, `totp-lock`,
   `totp-locked-reply` (first per lock), `totp-unlock source=<admin|success|recovery|enrol|rotate|decay>`,
   `totp-recovery-used remaining=<n>`, `totp-recovery-low remaining=<n>` (n ≤ 2), `totp-recovery-failure`,
   `totp-recovery-rate-limited` (first per window), `totp-recovery-regen count=<n>`, `totp-recovery-damaged`. No line
   carries a code, secret, counter, salt or hash. Logging stays best-effort and never changes a reply.

## Why one child, not two

Three source files plus the test file is over the usual three-file split. A1 (lock, decay, unlock) and A2 (recovery)
would both change `totpd.py` (state handling, VERIFY branch, admin verbs), `totpctl.py` and
`test_web_console_totp.py`; under one-dispatch-per-file they run in sequence anyway, and A2 rebases onto A1's state and
commit changes. One child and one review pass is cheaper and safer (parent Routing; operator confirms with the intent
approval).
