## Problem

`totpd` locks for a flat 300 s after five failures and then resets (`k3dm-console-totpd.py:744-748`, `:794`), so a
certificate holder gets about 1,440 guesses a day at 3 in 10^6 each, and nothing is logged. There is no way to clear a
lock except waiting.

## Behaviour

Parent **B1–B5**, in full. Summary for the worker; the parent's text wins where they differ. B8 (recovery codes) is
part A2: do not start it here.

1. **Escalating lock (B1).** `LOCK_SECONDS = [300, 1800, 14400, 86400]`. Five consecutive failures raise `lock_level`
   by one (cap 4) and lock for `LOCK_SECONDS[level-1]`; the fifth failure replies `NO`, attempts while locked reply
   `WAIT <remaining>`. Level 4 repeats 24 h locks; it is never permanent and there is no `LOCKED` reply (operator Q3).
2. **Expiry reset (B1, rev 4).** The reset after a lock (today `:744-746`, triggered by `locked_until > 0`) fires only
   when `failures >= 5` and the lock has expired. It sets `failures` to 0 and keeps `locked_until` and `lock_level`.
3. **Decay (B1, operator Q4).** With no active lock and `lock_level > 0`, the level drops by one per full 86400 s since
   the last lock expired, anchored on `locked_until` (kept on disk after expiry while `lock_level > 0`). Applied at the
   next VERIFY and at daemon start. At level 0 write the 5-key form with `locked_until: 0` and log
   `totp-unlock source=decay`.
4. **Clock (B2).** The running daemon enforces the lock against `monotonic()` with `lock_deadline_mono`, set once per
   lock (at imposition, or at start as `monotonic() + clamp(locked_until - clock(), 0, LOCK_SECONDS[level-1])`), rebuilt
   only when `locked_until` on disk changes.
5. **State (B3, rev 4).** `load_state` accepts the v1.45.0 5-key set or the 5 keys plus `lock_level`, where
   `type(lock_level) is int and 0 <= lock_level <= 4` (an explicit 0 loads; `true` is refused). A 5-key state reads as
   level 0 when `locked_until` is 0 and as level 1 when `locked_until > 0`: an active v1.45.0 lock is clamped to 300 s and
   the next lock is 1800 s. Anything else is state-unavailable, as today. Writers add `lock_level` only when non-zero.
6. **Unlock (B4).** Admin `UNLOCK` (peer uid 0) → `UNLOCKED` and a 5-key reset commit, or `NOT_ENROLLED` /
   `UNAVAILABLE`. `totpctl unlock` prints `unlocked`; the usage line (`totpctl.py:36`) gains `unlock`. A correct code,
   enrol and rotate also reset `failures`, `locked_until` and `lock_level` to 0.
7. **Log lines (B5).** `<UTC ISO-8601> event=<name> key=value ...`, bare names kept: `totp-failure failures=<n>
   lock_level=<l>`, `totp-lock lock_level=<l> seconds=<s>`, `totp-locked-reply lock_level=<l>` (first refused attempt
   per lock only), `totp-unlock source=<admin|success|enrol|rotate|decay>`. A2 adds `source=recovery` and the recovery
   events. No line carries a code, secret or counter value. Logging stays best-effort and never changes a reply.
8. **Gate untouched.** The gate's existing WAIT branch (`k3dm-console-gate.py:346-350`) already shows "Too many attempts;
   try again later"; E6 checks it as a positive control only.
