# v1.41.1: Scheduled baseline load test, and a stress-test gate for major releases

**Status:** PROPOSED (operator decision 2026-10-02)
**Milestone:** `v1.41.1`
**Depends on:** `docs/plans/v1.41.1-loadtest-credentials-and-preflight.md` (Vault credentials,
`loadtest_preflight`, `make loadtest`). Build that first.

## Decision

The operator asked for a stress test about every 12 hours. We agreed to split it in two:

1. **Every 12h: a light baseline**, not the full 6-stage stress. It keeps the Checkout Load Test dashboard
   filled with trend data, so a latency, error-rate or idempotency regression shows as a step change. It
   must not push `ubuntu-hostinger` to its limit twice a day. That box has had two CPU-oversubscription 502
   incidents (`docs/bugs/2026-07-22-hostinger-trivy-cpu-oversubscription-502.md`,
   `docs/bugs/2026-08-23-hostinger-trivy-scanjob-cpu-request-unschedulable.md`).
2. **Full stress for every major release, run before the release PR or while it is open.** Its result is
   a gate for that PR. Outside of a major release, the full stress test stays manual
   (`make loadtest CONFIRM=1`).

Scheduling generates checkout traffic without anyone typing `--confirm` each time. That is an
explicit change to the "not automatic" stance in the credentials plan, made by the operator here. The
consent is recorded once: the operator installs the schedule. Each run does not ask again.

## Scope

### 1. Baseline profile

- Add `LOADTEST_PROFILE=baseline|stress` to `loadtest_run`; `stress` is the default and is today's behaviour.
- `baseline` runs one stage: about 5–10 VUs for about 5 minutes. Put the values in `scripts/etc/loadtest/`,
  not inline.
- The `run_id` is prefixed `baseline-` or `stress-` so the dashboard selector separates them.
- Every order or payment the run creates carries the `run_id`. A post-run cleanup step deletes that
  run's orders. If the order service has no way to do that, report it as a blocker. Do not leave test
  orders behind.

### 2. Skip conditions (baseline only; each logs a reason and exits 0)

- an e2e harness run is active (the `make e2e` lock or a live `e2e-*` vCluster);
- another load test is running (a lock file under `LOADTEST_RESULT_DIR`);
- hostinger CPU is above a threshold (reuse `LOADTEST_PROMQL_CPU`);
- `loadtest_preflight` fails. In that case also post one alert-free note, so a credential that stays broken
  is not silent forever.

### 3. Schedule

- A launchd agent on the operator's Mac, which hosts the hub. Model it on the node-health watch install
  targets.
- Targets: `make install-loadtest-baseline` / `make uninstall-loadtest-baseline`.
- It runs every 12h. A run missed while the laptop sleeps is skipped, not caught up later.
- Results go to Prometheus through remote write, as now. Write a one-line summary to the existing results
  directory.

### 4. Major-release stress gate

- **Trigger:** a major release, meaning `vN.0.0` or a release the plan marks as major. When the
  release PR is prepared, the operator runs `make loadtest CONFIRM=1 LOADTEST_PROFILE=stress`, either
  before opening the PR or while it is open.
- **Record:** paste the `run_id`, stage reached, p95/p99 and error rate into the release PR body.
  `make loadtest` prints a ready-to-paste block. Add this to the `/create-pr` checklist and to
  `docs/howto/` release steps as a required item for major releases.
- **Fail:** a stress run that breaches a stage gate blocks the PR until it is explained or fixed.
- This stays operator-run, not CI. The traffic goes to the live environment, and CI holds no
  credentials for it.

## Out of scope

- Running the full stress test on a schedule.
- Any new cluster, environment, or credential.

## Tests

- `LOADTEST_PROFILE=baseline` renders a single stage. Unknown profiles are rejected.
- Each skip condition is stubbed and makes the run skip with its reason and exit 0, before any token is
  minted.
- `make -n install-loadtest-baseline` renders a launchd plist with a 12h `StartInterval` and no secret
  in it.
- The release checklist contains the major-release stress step.

## Completion criteria

- Within 12h of install, the dashboard's `run_id` selector lists a `baseline-` run, and its panels show data.
- A major-release PR template asks for, and gets, a `stress-` run summary.
- No run leaves test orders behind, and none starts while e2e or another load test is running.
