# v1.39.0 — vectordb health in Hermes and Grafana

**Target branch:** `k3d-manager-v1.39.0`
**Status:** SPEC. Requested by the operator on 2026-09-26, after WS2/WS3 landed.
**Scope:** a Hermes sensor for the vector store, and the metrics a Grafana panel needs.

## Why

WS1 cost a day of live debugging that no dashboard would have shortened, because nothing watched
the component. The observed failure chain was: Vault path absent → `vectordb-postgres`
`SecretSyncedError` → `pod/vectordb-0` `CreateContainerConfigError`. Every link was visible to
`kubectl` and invisible to everything else.

There is a second failure mode that has not happened yet and is quieter: the index silently stops
being refreshed. `make find-similar-docs` keeps returning plausible results from a stale index, so
the dedup check degrades into confidently recommending the wrong prior art. Nothing about that is
visible from pod health.

## H1 — Hermes sensor `vectordb`

Add to `scripts/lib/hermes/sensors.py`, following the injected-callable shape of `argocd` and
`kine`:

```python
def vectordb(run, state, threshold=2, max_index_age_seconds=7 * 86400):
```

Returns `record("vectordb", status, detail)` with `healthy` / `degraded` / `unknown`. Four checks,
in the order the failure chain actually propagates, so the detail names the cause and not the
symptom:

1. `vectordb-postgres` ExternalSecret `SecretSynced` condition — **first**, because it is upstream
   of the pod. When it is not `True`, the detail must say so and must NOT also report the pod as the
   problem.
2. `pod/vectordb-0` ready.
3. Store reachable: one `SELECT count(*)` through the existing `prior_art.run_sql` path.
4. Index freshness: `max(indexed_at)` older than `max_index_age_seconds` → `degraded`.

Rules:

- `unknown`, never `degraded`, when the source itself is unavailable — matching `eso` and `argocd`.
  A missing kube context is not a store outage.
- Debounce through `_debounced` at `threshold`, as every other flapping-prone sensor does.
- The sensor must never raise. A bare `except Exception` returning `unknown` is the established
  contract here.
- It must not import a third-party module and must not read the database password.

## H2 — metrics for Grafana

New `bin/k3dm-vectordb-metrics`, publishing to Pushgateway (`K3DM_PUSHGATEWAY_URL`, default
`http://localhost:9091`) in the idiom `bin/cluster-up` already uses:

```
k3dm_vectordb_rows                          gauge  rows in doc_embeddings
k3dm_vectordb_corpus_docs                   gauge  tracked docs on disk
k3dm_vectordb_drift_docs                    gauge  corpus_docs - rows
k3dm_vectordb_last_index_timestamp_seconds  gauge  max(indexed_at)
k3dm_vectordb_reachable                     gauge  1/0
k3dm_vectordb_external_secret_synced        gauge  1/0
```

**The staleness trap is load-bearing here and is designed around, not documented around.**
Pushgateway has no staleness: if the publisher stops, every gauge above keeps its last value
forever, so `k3dm_vectordb_reachable == 1` would assert a healthy store indefinitely after the
publisher dies. Therefore:

- `k3dm_vectordb_last_index_timestamp_seconds` is the **only** series an alert may be built on,
  because it is the only one whose stale value is itself the alarm: `time() - <ts>` grows without
  bound once publishing stops. Alerting on `reachable == 0` is forbidden — it cannot fire.
- Every other gauge is for a panel, not a rule. The dashboard must label them "last published"
  rather than implying "now".

Alert rule, in a new file under the observability rules path:

```
k3dm_vectordb_last_index_timestamp_seconds is absent for 1h        -> VectorDBMetricsStale
time() - k3dm_vectordb_last_index_timestamp_seconds > 7*86400      -> VectorDBIndexStale
```

## H3 — dashboard

`scripts/etc/grafana/dashboards/k3dm-vectordb-configmap.yaml`, following
`k3dm-deployments-configmap.yaml` including its `release` label. Panels: rows vs corpus docs, drift,
index age, and a reachability/sync stat row.

**The subchart trap applies.** A ServiceMonitor or dashboard ConfigMap that does not carry the
`release` label the stack selects on is silently skipped — already observed with the Grafana
subchart's own ServiceMonitor, where 0 of 1740 series appeared. Confirm the dashboard is loaded in
Grafana itself, not by the ConfigMap existing.

## Tests

`scripts/tests/hermes/` for the sensor, pytest. Stub only the injected `run`.

**The half-a-seam trap is explicitly in scope.** The `app-health-delta` suite kept 8 tests green
while the probe never executed, because the tests injected a stubbed `run` and asserted the parsing
of a hypothetical payload. So, in addition to the parsing cases:

- one test must assert the **real argv** the sensor would invoke, so a renamed resource or a wrong
  namespace fails a test rather than silently returning `unknown` forever;
- `unknown` must be distinguished from `degraded` by a test, since conflating them is how a
  monitoring gap reads as health;
- every assertion must be mutation-proved: break the check, confirm the specific test goes red.

## What NOT to do

- Do NOT read or print the vectordb Postgres password. The sensor reaches the store through
  `prior_art.run_sql`, which keeps the credential inside the pod.
- Do NOT put the embeddings API key anywhere in a metric label, a dashboard, or a log line.
- Do NOT add a `reclaimPolicy: Retain` or a new StorageClass to make the index durable — it is a
  rebuildable cache by design, and that change is separately unapproved.
- Do NOT hand-patch the live ApplicationSet or Application to add the dashboard; ArgoCD self-heal
  reverts out-of-band patches.
- Do NOT alert on row count dropping to zero as a store failure — a deliberate re-index truncates
  nothing, but a corpus prune legitimately lowers it.
