# v1.27.0 — Adaptive checkout load testing

**Milestone:** v1.27.0, alongside image signing and attestation
**Status:** SCOPED — planning only; implementation starts after v1.26.0 is complete
**Scope:** API-level checkout load, Grafana/Prometheus telemetry, and a small browser-validation cohort

## Goal

Measure the checkout system's safe sustained concurrency without requiring thousands of browser
instances. The test must exercise the real order orchestrator and Stripe **test mode**, detect the
first capacity boundary, and leave an auditable result in Grafana.

## Safety boundaries

- Use only Stripe `sk_test_...` credentials and Stripe test PaymentMethods. Never accept or emit
  live card data or `sk_live_...` keys.
- Run the generator outside the hub when possible; generator CPU and memory must not consume the
  capacity being measured.
- Use unique test users, carts, orders, and idempotency keys. A rerun must not double-charge or
  reuse an order unintentionally.
- Start with 100 concurrent checkouts and ramp through 250, 500, 1,000, 2,500, and 5,000 only
  while stop conditions remain clear. Ten thousand is out of scope for the first implementation.
- Stop the run when any hard threshold persists for two observation intervals: control-plane/API
  errors, checkout error rate above 2%, p95 latency above 2 seconds, database pool exhaustion,
  Stripe rate limiting, CPU above 80%, memory pressure, or node eviction risk.
- Keep the test opt-in and impossible to trigger from an unauthenticated Slack command.

## Implementation

### 1. Load generator

Add a k6 or Go-based runner (prefer k6 unless an existing Go harness is required) that:

1. Authenticates test principals, creates isolated carts, and adds deterministic products.
2. Calls the order checkout API with a Stripe test PaymentMethod and unique idempotency key.
3. Records success, decline, HTTP failures, latency, order state, payment state, and cart state.
4. Supports fixed stages and an adaptive controller. The controller increases concurrency only
   when the health gates are green and backs off on saturation or error signals.
5. Emits a run ID, stage, target concurrency, actual throughput, and final pass/fail summary.

The runner must not drive 5,000 browser sessions. Add a separate 20–100 session Playwright smoke
cohort to verify the browser-to-API path while the API runner supplies concurrency.

### 2. Metrics and Grafana

Expose or publish Prometheus metrics with a run ID and bounded labels:

- `checkout_load_requests_total{stage,result}`
- `checkout_load_latency_seconds{stage}` (histogram)
- `checkout_load_concurrency{stage}`
- `checkout_load_orders_total{state}`
- `checkout_load_payments_total{state,gateway}`
- `checkout_load_idempotency_failures_total`
- `checkout_load_run_info{run_id,stage,target_concurrency}`

Capture existing service, database, queue, node, and Stripe-client metrics alongside them. Add a
Grafana dashboard for throughput, p50/p95/p99 latency, errors, resource saturation, and the safe
maximum concurrency. Add alerts only for an active run and stale-run detection; do not page on
historical test data.

### 3. Adaptive control and acceptance

The controller polls Prometheus at a fixed interval, applies the stop conditions above, and writes
one immutable JSON summary per stage. Acceptance requires:

- no duplicate order or payment for a request;
- expected Stripe test-mode success and decline behavior;
- no unexplained 5xx responses;
- control-plane health remains green;
- a repeat run at the discovered safe concurrency produces equivalent results.

The first release must produce a capacity report, not promise a universal 5,000-request limit.
Capacity is specific to the node size, replica count, database limits, and Stripe test account.

## Out of scope

- Live Stripe charges or production card data.
- Ten thousand real browser sessions.
- Automatic cluster scaling or changing production resource limits during a run.
- Admission/promotion policy changes; those remain in the image-signing plan.

## Definition of done

- Staged 100→5,000 API test can be started with an explicit confirmation flag.
- Adaptive increase/backoff and hard stop conditions have unit tests.
- Stripe test-mode happy/declined and idempotency cases pass.
- Prometheus metrics and Grafana dashboard render a completed run.
- A 500-concurrency run passes on the M4 baseline, or the report records the measured bottleneck.
- A higher-capacity host is used before claiming 2,500 or 5,000 concurrency support.
