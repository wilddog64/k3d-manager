# v1.20.0 - Command Wrapper Rigor Migration

**Branch:** `k3d-manager-v1.20.0`
**Goal:** make the host-side command-wrapper convention enforceable, then
incrementally migrate the current raw-command baseline without changing
runtime behavior.

## Evidence and Scope

The parser-derived baseline is documented in
`docs/issues/2026-07-30-command-wrapper-rigor-coverage-gap.md`:

- 410 raw host-manager calls: `kubectl`=311, `curl`=73, `ssh`=15,
  `docker`=6, `k3d`=4, `helm`=1.
- `scripts/plugins/shopping_cart.sh`=66 raw `kubectl` calls,
  `bin/cluster-up`=65, `bin/cluster-status`=29, and
  `scripts/lib/providers/k3s-hostinger.sh`=24.
- 47 additional calls are in tests, self-contained container scripts, or
  standalone scripts. They are explicit-exception candidates, not host-wrapper
  migration targets.

`scripts/lib/agent_rigor.sh` and
`scripts/lib/foundation/scripts/lib/agent_rigor.sh` have diverged. The latter
is vendored from lib-foundation, but the former is a k3d-manager-owned copy.
Therefore an upstream release does not automatically enforce the rule here.

## Decisions

1. **Host Bash rule:** direct `kubectl`, `curl`, `helm`, and `k3d` calls must
   use `_kubectl`, `_curl`, `_helm`, or `_k3d`; direct `docker`, `ssh`, and
   `wget` calls must use `_run_command -- <tool> ...` unless an approved
   file-and-context exception applies.
2. **Execution-context exceptions:** BATS fixtures, CronJob/container scripts,
   remote shell payloads, and Python subprocesses must use their own tested
   adapter or be explicitly allowlisted. They must not be mechanically changed
   to host helpers that are unavailable in that process.
3. **Detection mechanism:** use `shfmt --to-json` to inspect shell
   `CallExpr` nodes. Do not use grep as the enforcement mechanism: it cannot
   distinguish commands from heredocs, quoted text, or documentation.
4. **Enforcement rollout:** reject only newly introduced violations at first.
   The existing 410-call baseline is reduced batch by batch; CI must not be
   made permanently red by historical debt.
5. **Live verification:** the ACG AWS sandbox is the acceptance environment
   for behavior-changing batches, not a substitute for BATS or static checks.

## Change 1 - Upstream lib-foundation contract

In lib-foundation:

1. Add a parser-backed command-wrapper audit helper used by `_agent_audit`.
   It receives staged files and a declarative command/context configuration;
   it reports file, line, command, and required wrapper.
2. Keep the generic policy in the library. Do not embed k3d-manager file paths
   or application-specific exceptions upstream.
3. Add BATS coverage using temporary git repositories with staged fixtures:
   raw `kubectl`/`curl`/`helm`/`k3d`/`docker`/`ssh`/`wget` fail; dedicated
   wrappers and `_run_command --` pass; pipelines, conditionals, command
   substitutions, and multiline calls are recognized; heredocs and quoted
   text do not false-positive; configured exceptions pass.
4. Add `shfmt` as an explicit development/CI prerequisite, pin its version or
   verify a compatible major version, and fail clearly when unavailable.
5. Release the upstream change only after `bats scripts/tests/lib/agent_rigor.bats`,
   the relevant system tests, shellcheck, and the new parser fixtures pass.

**Upstream test value:** this isolates the parser and staged-diff contract in
small disposable repositories. It proves detection independently from a live
cluster and prevents downstream migrations from weakening the gate.

## Change 2 - Downstream adoption and policy

In k3d-manager:

1. Bring the upstream helper and its tests into the local
   `scripts/lib/agent_rigor.sh` deliberately; do not assume the foundation
   subtree pull updates this file. Add a parity check or document the intended
   downstream delta so the two copies do not silently diverge again.
2. Add a k3d-manager policy/allowlist that limits enforcement to host-side
   files and records each approved non-host context with a reason and owner.
3. Add a repository scanner command that produces the same parser-derived
   baseline locally and in CI. Its required result is no new violations;
   its informational result is the remaining baseline by file and tool.
4. Extend `scripts/tests/lib/agent_rigor.bats` with k3d-manager policy cases;
   keep the existing bare-sudo and credential checks intact.

## Change 3 - Migration Batches

Each batch is one focused PR or a small coordinated set. A batch must preserve
arguments, redirections, pipelines, `--context`, namespace flags, and existing
`set -e` behavior. Do not combine wrapper conversion with unrelated refactors.

1. **Batch A - deployment path:** `scripts/plugins/shopping_cart.sh` and the
   k3s-AWS-specific caller paths. Migrate direct Kubernetes operations to
   `_kubectl` and direct HTTP/download operations to `_curl` or
   `_run_command`. Add/extend focused shopping-cart and k3s-AWS BATS tests.
2. **Batch B - lifecycle binaries:** `bin/cluster-up`, `bin/cluster-status`,
   `bin/cluster-refresh`, `bin/cluster-down`, and their existing BATS suites.
   These are high-volume and live-critical; migrate one binary per PR where
   practical.
3. **Batch C - provider paths:** k3s-hostinger, k3s-gcp, k3s-az, k3s-oci,
   and k3s-aws. Preserve their explicit kubeconfig/context selection and test
   provider contracts before any live provider action.
4. **Batch D - plugin paths:** ArgoCD, Vault, Jenkins, Copilot, and
   observability. Validate credential and port-forward handling explicitly.
5. **Batch E - residual tools and exceptions:** remove stale allowlist entries,
   document intentional adapters, and tighten the audit from no-new-violations
   to zero host-manager baseline for the managed command set.

## Required Gate Per Batch

1. Parser scan: the migrated file has no unallowlisted host-side raw call for
   the managed command set; total baseline does not increase.
2. `shellcheck` and `bash -n` for every touched shell source.
3. Focused BATS suite for the modified file, the agent-rigor suite, then
   `./scripts/k3d-manager test all` before a live acceptance run.
4. `_agent_audit` on the real staged diff and a review of its parser output.
5. No new `if`-count allowlist entry unless a separate issue explains a
   legacy exception.

## ACG AWS Sandbox Acceptance

Run this only after the static and BATS gates pass and only with valid ACG
credentials. It is a controlled live test, not an unattended CI job.

1. Start or verify the sandbox:
   ```bash
   ./scripts/k3d-manager acg_status
   ```
   If absent, obtain credentials through the existing secure flow, set a
   restrictive `ACG_ALLOWED_CIDR`, then run
   `./scripts/k3d-manager acg_provision --confirm`.
2. For a fresh acceptance environment, deploy the AWS app cluster using the
   existing supported path:
   ```bash
   CLUSTER_PROVIDER=k3s-aws make up
   ```
3. Verify the application cluster and platform behavior:
   ```bash
   ./scripts/k3d-manager acg_status
   kubectl --context ubuntu-k3s get nodes
   CLUSTER_PROVIDER=k3s-aws make status
   ```
   Confirm the expected nodes are Ready, the shopping-cart workload is
   healthy, and no wrapper conversion changed context or namespace handling.
4. Exercise the batch-specific action once more where safe (for example,
   `make status` after Batch B, or the targeted deployment/status flow after
   Batch A). Capture command output and the remaining parser baseline.
5. Teardown only after evidence is captured and with explicit operator intent:
   ```bash
   ./scripts/k3d-manager acg_teardown --confirm
   ```
   Do not run teardown automatically and do not expose broad SSH or Kubernetes
   ingress while testing.

## Definition of Done

- [ ] lib-foundation has a released, parser-backed staged-diff wrapper audit
      with representative BATS coverage.
- [ ] k3d-manager has adopted the contract with an explicit policy/exception
      file and no hidden divergence from the upstream implementation.
- [ ] Every migration batch has focused BATS, shellcheck, syntax, and audit
      evidence; the host-manager baseline reaches zero for the managed tools.
- [ ] At least Batch A, Batch B, and the final batch have passed fresh or
      controlled ACG AWS sandbox acceptance.
- [ ] The final exception list contains only intentional non-host execution
      contexts, each with a documented reason.

## Non-Goals

- Do not wrap commands inside Python with Bash helpers; retain the webhook's
  timeout-aware subprocess adapter.
- Do not rewrite CronJob/container scripts to source host-only `system.sh`.
- Do not change command arguments, privilege semantics, contexts, namespaces,
  or timeouts as part of a wrapper-only migration.
- Do not enable a global zero-baseline CI failure before the migration batches
  have reduced the historical host-manager baseline.
