# Proposal — E2E preflight uses current release branch HEAD (local and remote)

**Filed:** 2026-10-13, operator request
**Branch:** `k3d-manager-v1.48.1` (triage 2026-10-15, operator-approved placement; renamed from `e2e-current-release-head-sync.md`)
**Status:** PROPOSED — spec only; not implemented or live-verified
**Scope:** Existing `make e2e` and `make e2e-remote` entrypoints, including cloud-bridge dispatched variants
**Priority:** Release verification correctness; no extra cloud action requested

## Operator intent

When a cloud agent commits and pushes a fix to the **current release branch**, an existing cloud-bridge `make-e2e` or `make-e2e-remote` request should automatically test that branch's current remote HEAD, without a manual local `git pull`. This applies to k3d-manager and the required shopping-cart application/test repositories. **Never default or fall back to `main`.**

The bridge already exposes only fixed E2E actions. Do **not** add unrestricted `git pull`, arbitrary repository, branch, SHA, shell, or URL parameters to the bridge. The trusted E2E runner owns synchronization.

## Existing behavior and the gap

- `scripts/lib/webhook/cloud_actions.py` allowlists `make-e2e` and `make-e2e-remote`; its action arguments do not select arbitrary refs.
- `docs/bugs/2026-09-15-e2e-m2-runner-checkout-drift.md` was fixed: `scripts/plugins/e2e_remote.sh` sends the M4 checkout's **local HEAD SHA** to an E2E-owned M2 clone and forces that clone to the SHA. That prevents M2 checkout drift, but does **not** prove M4 HEAD matches the latest **remote HEAD of the active release branch**.
- The local `make e2e` and the remote path must share one revision-resolution contract, without expanding authorization.
- Shopping-cart repositories and the Playwright image may independently lag even if k3d-manager source is current. Inspect the existing image build/pin and deployment paths before coding; a source fetch alone is not proof that those commits were deployed.

## Functional requirements

1. **Discover release branch from trusted configuration.** Resolve the **current** release branch (`k3d-manager-vX.Y.Z`) from the runner's approved release configuration/checked-out release branch. Explicitly reject detached HEAD without a trusted release ref, conflicting configured refs, non-release branches, or a missing origin branch. No implicit `main`, `master`, or default-branch fallback. Never treat untrusted cloud request content as a ref.
2. **Fetch and pin once per run.** Immediately before either E2E operation, `git fetch` the approved remote ref, resolve `refs/remotes/origin/<release-branch>` to a full SHA, and pin that SHA as the run's k3d-manager revision. If fetch fails, abort rather than silently using local/stale refs. If the release branch advances during the run, continue at the pinned SHA and report it (a later run tests the newer HEAD).
3. **Isolate checkout.** Run from an E2E-owned clean clone/worktree at the pinned SHA; never `git pull`, reset, clean, checkout, or rebase the operator's development tree, Claude/Codex worktrees, or the bridge's orphan `cloud-requests` bare clone. Concurrent runs must not share mutable checkout state. Cleanup only runner-owned paths.
4. **Remote path.** M4 chooses and records the authoritative release ref and fetched SHA; the M2 runner fetches/verifies the **same** SHA into its existing E2E-owned checkout before execution. Fail closed if M2 cannot resolve it; do not substitute M2's current branch HEAD. Preserve existing remote-runner locking and return/diagnostic behavior.
5. **Shopping-cart inputs.** Inventory the shopping-cart repos actually needed by the current Tier 1 test/deploy pipeline (source, manifests and Playwright tests). Define a trusted repo-to-ref mapping in version-controlled runner configuration; **do not assume** those repos use `k3d-manager-vX.Y.Z` branches. Resolve each approved branch's latest remote SHA once and record it. No arbitrary URL or branch input in cloud requests, and no implicit `main` fallback for an unknown mapping. If a repo is consumed as a pinned immutable artifact rather than source, record that artifact's digest and its build provenance instead of gratuitously pulling the repo.
6. **Actually test the candidate.** Confirm the application/test image(s) deployed into disposable vCluster correspond to the resolved source revisions (build/publish or choose an existing immutable, attestable image); capture image digests. Never report a successful candidate verification while silently running an older image. If the harness cannot yet build/publish candidate images, explicitly fail with `candidate-not-deployed` or report that image/source freshness is **unverified**, not a green verification of the new fix. Do not mutate persistent hub/Hostinger/ACG workloads as part of the sync.
7. **Results and evidence.** Every result records `release_ref`, `k3d_manager_sha`, per-repo `{repo,ref,sha}`, the test-suite SHA, deployed image digests, run mode (`e2e` or `e2e-remote`), and freshness/provenance verification status. Make these visible in E2E logs and existing status/result artifacts; retain bounded/sanitized output in cloud-bridge responses. A PASS means the stated revision and images were tested, not merely that an old deployment passed.
8. **Failure behavior.** Fail closed on missing ref, bad Git remote, auth/rate-limit/network fetch failure, missing SHA, unsafe checkout, invalid mapping, lock contention, or candidate-image mismatch. Never run against stale inputs under a nominal PASS. Preserve current scoped webhook role, action/argument allowlist, timeouts, E2E locks, and operator approval boundaries.
9. **Scope of tests.** Keep existing E2E test tiers and auth mode unchanged unless separately specified. Tier 1 with OAuth disabled does **not** prove a live Keycloak redirect/login fix; that requires an appropriately configured OIDC test, not just fresh source.

## Design sketch

```text
Cloud agent fixes bug -> push to CURRENT release branch
  -> existing cloud-bridge make-e2e / make-e2e-remote
  -> trusted runner preflight:
       approved release ref -> origin/ref fetch -> pin SHA
       approved app/test repo mappings -> fetch/pin or verify immutable image provenance
       E2E-owned isolated checkouts (no developer-tree writes)
  -> prepare/deploy candidate images -> verify deployed digests
  -> run vCluster E2E -> result: PASS/FAIL + exact refs/SHAs/digests
```

Implement preflight in shared E2E code called by the two entrypoints, not in `bin/k3dm-cloud-bridge`. Reuse M2 SHA pinning, not replace it. Check existing `scripts/plugins/e2e.sh`, `scripts/plugins/e2e_remote.sh`, `docs/guides/vcluster-e2e-harness.md`, and `scripts/etc/e2e/` before settling the implementation files and artifact path.

## Acceptance tests / Definition of Done

- [ ] Active release branch behind `origin`: cloud-requested local E2E tests latest **origin release SHA**, even if the operator's checkout is behind; operator tree remains untouched.
- [ ] Same scenario with remote E2E: M2 uses the exact M4-pinned SHA, not an older M4/M2 checkout.
- [ ] Current branch absent, detached without trusted ref, wrong branch, or fetch failed: explicit preflight failure; no `main` fallback, stale PASS, cluster side effects, or silent retry.
- [ ] Shopping-cart repo on a separately named approved branch: correct SHA; unconfigured repo/ref rejected.
- [ ] Push changed app code: test either deploys matching new image digest or **does not claim** to have verified the fix.
- [ ] Changed Playwright test code is included from its expected SHA, not a stale image.
- [ ] Race: branch advances after pinning; complete on pinned SHA and report it.
- [ ] Concurrent/locked runner and dirty operator checkout remain intact.
- [ ] Stubbed BATS/pytest cover Git fetch/ref validation, malformed mapping, candidate image provenance, remote pinning, failure modes and output contract, with regression tests that fail on old behavior.
- [ ] Manual live check through both existing cloud-bridge actions (only when operator-approved), inspect recorded SHAs/digests and compare to origin and deployed workloads.
- [ ] Update E2E how-to, architecture, and release evidence; independently verify PASS has meaningful revision provenance.

## Operational Requirements

- **Security:** No new cloud-bridge verb, credentials, arbitrary Git command or branch override; fixed approved remotes/refs and bounded outputs. No developer worktree modifications.
- **Availability:** Run only in disposable E2E resources; no persistent application rollout or hub changes.
- **Resource budget:** Reuse existing runner capacity, locks and timeouts. Document storage bounds and cleanup for isolated checkouts/images.
- **Rollback:** Disable auto-sync preflight using an operator-only rollback to prior E2E runner revision; report old behavior as unverified against latest origin until fixed, not as release-verified.
- **Observability:** E2E logs/results include ref, source SHA and image digest; raise a visible freshness/provenance failure rather than a misleading green status.

## What NOT to do

- Do not grant cloud agents general `git pull`, checkout, branch, URL, Make target or shell execution.
- Do not synchronize against `main` by default.
- Do not force-reset active operator or agent checkouts.
- Do not equate freshly fetched Git docs with freshly deployed test images.
- Do not change release-promotion gates, cluster lifecycle permissions, or Keycloak testing scope as a side effect.
