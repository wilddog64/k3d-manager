## Safety rules for every capture

- Isolation. No capture touches the production console: not the labels `com.k3d-manager.web-console-sshd` or `com.k3d-manager.web-console-totp`, not `/etc/k3dm-web-console`, not `/Library/PrivilegedHelperTools/k3dm-web-console`, not `/var/db/k3dm-web-console` or `/var/db/k3dm-web-console-run`, not port 42722.
- Capture authority (one rule; replaces v2's conflicting lines, Astra 16). Against Cloudflare and GitHub: `GET` only (`curl` GET, `gh api` GET); no `POST`, `PUT`, `PATCH`, `DELETE`. The throwaway Access app, policy and tunnel of C5 and C9 are created and deleted by the operator in the dashboard, never by a capture command. Throwaway connector (Fable B1): the throwaway tunnel is a remotely managed tunnel (created in the dashboard, its public hostname and service set there, `config_src` `cloudflare`); `cloudflared tunnel create` and `cloudflared tunnel login` are forbidden (the first is a `POST` and both write under `~/.cloudflared`). The operator saves the connector token from the dashboard into `<scratch (1)>/tunnel-token` (`0600`) without displaying it and runs the connector in the foreground from a plain terminal, with `cloudflared tunnel --no-autoupdate run --token-file <scratch (1)>/tunnel-token`; never `--token <value>`, so the token is in no argv (`cloudflared tunnel run --help`, 2026.11.1, m4-air, 2026-11-19, lists `--token-file value` "Filepath at which to read the tunnel token" with `$TUNNEL_TOKEN_FILE`, next to `--token` with `$TUNNEL_TOKEN`; the help text was read, no tunnel was run). The connector is stopped with Ctrl-C and the token file is removed with the scratch directory; the tunnel is deleted in the dashboard at the end of the session. A local config file is used only by the offline `ingress` commands of C8. On the Macs, a capture may write only in two places and only by the operator, or by Claude with the operator's go for an unprivileged step: (1) the unprivileged scratch directory `/private/tmp/k3dm-captures-<date>/` (operator-owned, `0700`, files `0600`) for foreground scratch sshd runs, filtered output and scratch scripts; (2) the root scratch directory `/private/var/db/k3dm-capture-<date>/` (created `root:wheel 0755` by the operator with `sudo`; `/private/var/db` is `root:wheel 0755`, probe on `m4-air` 2026-11-18) for every file a root-run capture executes or reads (scratch plist, config, host key, CA key, scripts, sockets), so a root job never runs a file the operator's user can write (Astra 16). The only launchd job a capture may load is `com.k3d-manager.capture-sshd` (and, for C12, `com.k3d-manager.capture-totpd` and `com.k3d-manager.capture-idle`), each from a plist in directory (2), bootstrapped and booted out by the operator. No `make install-*`, no part A or part C artifact. Both directories are removed with `rm -r` (the root one with `sudo`) at the end of each capture session, and the removal is recorded.
- Scratch sshd. A capture that needs an sshd runs a foreground `sshd -D -e -f <dir>/sshd_config -h <dir>/host_key` on port 42723, bound to 127.0.0.1, with every file (config, host key, CA public key, `ForceCommand` test script, `AuthorizedPrincipalsFile`, log, `PidFile none`) in directory (1). `sshd` as non-root cannot switch users, so these runs authenticate the operator's own account only, which is all those captures need. A foreground process is not proof of root-job behaviour: anything about a LaunchDaemon (bootout, `launchctl print`, process tree under launchd) uses the scratch label from directory (2) (Astra 16). A capture that substitutes a different forced command edits only its scratch config. Port 42723 has one owner at a time (Fable B5): the foreground scratch sshd (C4, C5, C7, C8) and the scratch LaunchDaemon (C6, C9, C11-C17) are never up together; the operator stops one (Ctrl-C, or `launchctl bootout`) and confirms with `netstat -anv -p tcp` that no `127.0.0.1.42723` LISTEN row remains before starting the other, and the throwaway tunnel's service stays `ssh://127.0.0.1:42723` for both.
- The Cloudflare token is read from the Keychain by the shell and passed to `curl` through a config file on stdin (`curl --config -` with `header = "Authorization: Bearer ..."`), never as an argument, never echoed, never in shell history. Presence is checked by name only: `security find-generic-password -s <item> >/dev/null` (the exit code, never `-w` output on a terminal).
- Scope for the capture token: a read-only API token created for this capture (permissions below), stored as `k3dm-cloudflare-access-capture-token`, deleted afterwards. It is not `k3dm-cloudflare-api-token` and not the future setup token.
- Do not run any capture inside tmux or any session an agent reads, when the output contains an account id, a team name or a policy body. Save to a file with mode 600 under `/private/tmp/k3dm-captures-<date>/`, filter, then show the filtered file.
- Filters ("FILTER" below): `jq` allow-list projections that keep field names and shapes, and replace every value of `id`, `uid`, `account_id`, `zone_id`, `tunnel_id`, `aud`, `email`, `domain`, `name` (when it holds a hostname or person) with `<redacted:field>`. Never keep a token, a certificate body, a private key, an `AUD` tag or a team name. Scan the filtered file with `grep -Ei 'bearer|eyJ|BEGIN|ssh-(rsa|ed25519)|@[a-z0-9.-]+\.[a-z]{2,}'` before it is shown or committed; any hit blocks the capture.
- Each capture records host, date, tool versions (`cloudflared --version`, `/usr/sbin/sshd -V`, which prints `OpenSSH_10.2p1, LibreSSL 3.3.6` on m4-air, macOS 26.5.2, probe 2026-11-19 (Astra round 3), `ssh -V`, `sw_vers -productVersion`) in a header comment.

### C4. Certificate principal mapping

- Order: runs after C5, on C5's throwaway app, tunnel and foreground scratch sshd, with two supervised logins of its own (C5 needs only C1-C3; v3 had C4 and C5 each waiting on the other, Astra round 3).
- Commands. Login 1, inspect before the principal match (Astra 10: under the default rule a certificate whose principal is not the login name is refused before any forced command runs, so the default mapping cannot be the first step): the scratch sshd sets `ExposeAuthInfo yes` (`sshd_config(5)`: writes the authentication methods and public credentials used to a file named by `SSH_USER_AUTH`; local man page, OpenSSH_10.2p1, m4-air, 2026-11-19) and `AuthorizedPrincipalsCommand <root scratch (2)>/principals-any %t %k` with `AuthorizedPrincipalsCommandUser` the operator. `%k` is "the base64-encoded key or certificate for authentication" and `AuthorizedPrincipalsCommand` accepts `%k` and `%t` (`sshd_config(5)` TOKENS, same man page); the program "must be owned by root, not writable by group or others" (same page), so it is a `root:wheel 0755` script in directory (2). It feeds `<type> <base64>` to `ssh-keygen -L -f -`, writes the filtered lines described below to a `0600` file in directory (1), and prints the certificate's own principals on stdout, one per line, so sshd accepts the certificate whatever its principal is. Whether a foreground sshd that is not root runs this command is not known; if it refuses, login 1 is made on the scratch LaunchDaemon of C6 instead (root, same port, the foreground sshd stopped first) and that is recorded. With that permissive scratch mapping the login is accepted, and as a second view its scratch `ForceCommand` reads the file named by `$SSH_USER_AUTH`, takes the line that starts with `publickey `, strips that prefix (Fable B3) and feeds the rest to `ssh-keygen -L -f -`, printing only the `Principals:`, `Valid:`, `Key ID:` and `Signing CA:` key type lines, with every principal and key id replaced by its length and its equality (yes or no) with the local login. Login 2, the default mapping tested on its own: the same scratch sshd without `AuthorizedPrincipalsCommand` and without an `AuthorizedPrincipalsFile`; record whether the login is accepted and the sshd `LogLevel VERBOSE` line either way. The scratch sshd's `Accepted publickey ... ID ... (serial ...) CA ...` line is kept as a cross-check only: it names the key id and CA, not the principal list or validity, so it is not the proof (Astra round 3). sshd itself creates and removes the `SSH_USER_AUTH` file, at `/tmp/sshauth.XXXXXXXXXXXXXXX` outside the scratch directory (`strings /usr/libexec/sshd-session`, m4-air, 2026-11-19); the capture never copies it or the certificate anywhere, and only the filtered lines above are written to the scratch directory (Fable B3).
- Proves: which string Cloudflare puts in the certificate principal (the part of the GitHub email before the `@`, an Access-derived name, or the local login), whether there is more than one principal, and the certificate validity period; and, from login 2 by direct observation, whether `AllowUsers` plus the default "principal must equal the login name" works or an `AuthorizedPrincipalsFile` mapping is needed. If login 1 itself is refused, the certificate was not inspected and C4 is void, not a result. If the principal is not the local login, part A is re-specified and re-reviewed before part B (part A header), never a worker choice. Feeds: sshd principal configuration, N3 and the lost-device story.

### C8. Origin JWT validation and the tunnel

Feeds: ingress template, the `check` tunnel item, the one-connector-per-tunnel assumption that `bin/hub-cutover` (D2 isolates the console from it) relies on.
