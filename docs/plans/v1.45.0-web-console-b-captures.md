## Why captures first

`docs/process/rules.md` (prove external behaviour before dispatch) says a fix that depends on how an outside tool behaves carries proof from the deployed version. Part B depends on the Cloudflare Access API, browser-rendered SSH, the short-lived certificate principal mapping, and `sshd` under a LaunchDaemon. None is proven. The review (blocker 8) and Astra's finding 5 say the same. Each capture below names what it proves and the decision it feeds. Captured output is redacted by the filters named, saved as a dated file under `docs/captures/` only after the operator reads it, and then embedded in the part B spec as fixtures.

## Safety rules for every capture

- Isolation. No capture touches the production console: not the labels `com.k3d-manager.web-console-sshd` or `com.k3d-manager.web-console-totp`, not `/etc/k3dm-web-console`, not `/Library/PrivilegedHelperTools/k3dm-web-console`, not `/var/db/k3dm-web-console` or `/var/db/k3dm-web-console-run`, not port 42722.
- Capture authority (one rule; replaces v2's conflicting lines, Astra 16). Against Cloudflare and GitHub: `GET` only (`curl` GET, `gh api` GET); no `POST`, `PUT`, `PATCH`, `DELETE`. The throwaway Access app, policy and tunnel of C5 and C9 are created and deleted by the operator in the dashboard, never by a capture command. On the Macs, a capture may write only in two places and only by the operator, or by Claude with the operator's go for an unprivileged step: (1) the unprivileged scratch directory `/private/tmp/k3dm-captures-<date>/` (operator-owned, `0700`, files `0600`) for foreground scratch sshd runs, filtered output and scratch scripts; (2) the root scratch directory `/private/var/db/k3dm-capture-<date>/` (created `root:wheel 0755` by the operator with `sudo`; `/private/var/db` is `root:wheel 0755`, probe on `m4-air` 2026-11-18) for every file a root-run capture executes or reads (scratch plist, config, host key, CA key, scripts, sockets), so a root job never runs a file the operator's user can write (Astra 16). The only launchd job a capture may load is `com.k3d-manager.capture-sshd` (and `com.k3d-manager.capture-totpd` for C12), each from a plist in directory (2), bootstrapped and booted out by the operator. No `make install-*`, no part A or part C artifact. Both directories are removed with `rm -r` (the root one with `sudo`) at the end of each capture session, and the removal is recorded.
- Scratch sshd. A capture that needs an sshd runs a foreground `sshd -D -e -f <dir>/sshd_config -h <dir>/host_key` on port 42723, bound to 127.0.0.1, with every file (config, host key, CA public key, `ForceCommand` test script, `AuthorizedPrincipalsFile`, log, `PidFile none`) in directory (1). `sshd` as non-root cannot switch users, so these runs authenticate the operator's own account only, which is all those captures need. A foreground process is not proof of root-job behaviour: anything about a LaunchDaemon (bootout, `launchctl print`, process tree under launchd) uses the scratch label from directory (2) (Astra 16). A capture that substitutes a different forced command edits only its scratch config.
- The Cloudflare token is read from the Keychain by the shell and passed to `curl` through a config file on stdin (`curl --config -` with `header = "Authorization: Bearer ..."`), never as an argument, never echoed, never in shell history. Presence is checked by name only: `security find-generic-password -s <item> >/dev/null` (the exit code, never `-w` output on a terminal).
- Scope for the capture token: a read-only API token created for this capture (permissions below), stored as `k3dm-cloudflare-access-capture-token`, deleted afterwards. It is not `k3dm-cloudflare-api-token` and not the future setup token.
- Do not run any capture inside tmux or any session an agent reads, when the output contains an account id, a team name or a policy body. Save to a file with mode 600 under `/private/tmp/k3dm-captures-<date>/`, filter, then show the filtered file.
- Filters ("FILTER" below): `jq` allow-list projections that keep field names and shapes, and replace every value of `id`, `uid`, `account_id`, `zone_id`, `tunnel_id`, `aud`, `email`, `domain`, `name` (when it holds a hostname or person) with `<redacted:field>`. Never keep a token, a certificate body, a private key, an `AUD` tag or a team name. Scan the filtered file with `grep -Ei 'bearer|eyJ|BEGIN|ssh-(rsa|ed25519)|@[a-z0-9.-]+\.[a-z]{2,}'` before it is shown or committed; any hit blocks the capture.
- Each capture records host, date, tool versions (`cloudflared --version`, `sshd -V` is not available, so `ssh -V`, `sw_vers -productVersion`) in a header comment.

## Required API token permissions (to confirm in C1)

The capture token needs read access only: Account, Access: Apps and Policies, Read; Account, Access: Certificates, Read; Account, Cloudflare Tunnel, Read; Account, Access: Organizations, Identity Providers, and Groups, Read; Zone, DNS, Read for the one zone. Part C1 records which of these the endpoints actually demand (an HTTP 403 with `code` 10000 names a missing permission). The setup token of part B is derived from that list, narrowed further: Access Apps and Policies Edit, Access Certificates Edit, Cloudflare Tunnel Edit, DNS Edit for the one zone, and no other permission.

### C5. Browser-rendered SSH with a ForceCommand and a PTY

## Part B outline (spec after the captures)

1. **Per-machine tunnel, independent of the hub (D2).** Tunnel named `k3dm-console-<host>`; config `~/.cloudflared/console-<host>.yml`; credentials file restored from its own Keychain item `k3dm-console-<host>-credentials` (name by capture C8); launchd label `com.k3d-manager.console-tunnel`, recommended as a root LaunchDaemon with its config and credentials in root-owned paths (umbrella open question 9: under O2 at runtime, a user LaunchAgent's config and credentials are operator-writable, so a same-user process could repoint the console route; a user agent also needs a GUI login); ingress exactly `ssh://127.0.0.1:<port>` for the one hostname and a final `http_status:404`; `originRequest.access.required: true` with the app's `teamName` and `audTag` (C8). No edit to `scripts/etc/cloudflared/config.yml`, `bin/cluster-up`, `bin/cluster-down`, `bin/hub-cutover`, `hub-singletons.list`, `bin/public-endpoint-probe`, `bin/k3dm-cloudflare-posture`, `scripts/lib/hermes/sensors.py` (C10). Part A's `check --cloudflared-config` reads the console config.
2. **Access app and policy.** Created through the API using the schema of C1: one app per machine, one allow rule for the operator's GitHub login method and email, no Bypass, `Everyone`, service-token or other identity provider, session duration 6 hours, short-lived certificates on. `setup` verifies the app and policy shape before it makes the origin routable (ingress and DNS last) and fails closed on a partial setup. `--dry-run` prints the plan with no write.
3. **Origin JWT validation** as in item 1, and the certificate CA (C3) installed through part A's `--ca-file`, with a drift check.
4. **Revoke order** (fail closed, each step idempotent, safe to repeat, each continuing when an earlier one finds nothing to do), refined by C9: first cut the route (stop the console tunnel job and remove its ingress), so no connection reaches `127.0.0.1:<port>` while the sshd is down and a same-user process could bind it (Fable A13, residual R-PORT-GAP in part A); then part A `revoke` (not `uninstall`, which part A refuses while part C is installed; `revoke` boots out the job, moves the plist aside and ends console sessions, Astra 7); then revoke Access sessions and disable or delete the app (per C2); last remove the DNS record. A repeated revoke after any partial run completes the remaining steps. A remote path for a lost laptop (the dashboard steps, off the device) is part of the how-to; the local cleanup runs when the laptop returns. `check` after revoke exits with a distinct status for intentionally revoked versus broken.
5. **Idempotence and secrets.** A dedicated Access setup token item `k3dm-cloudflare-access-token`, read by name only, passed to `curl` through stdin config, never in argv, logs or `check` output; setup refuses to run when the token's verified permissions exceed the C1 list. O3: `setup` is a one-off step the operator starts and watches, so it is trusted; the edit-capable setup token is not kept where the operator's user (and so the hub user's runtime processes) can read it: the how-to has the operator create it for the setup run and delete it afterwards, and `check` uses a read-only token. Residual **R-SETUP (O3, accepted):** during the setup run a same-user process could read the setup token from the login Keychain or alter the setup script, as R-INSTALL in part A.
6. **Machine lists.** The console-tunnel LaunchAgent and the install target go in `not-installed.list` (operator-run), never an agents or secrets list, like parts A and C.
7. **Evidence.** Offline: fixtures built from C1-C3 and C8 captures (host, date, version in a comment) for schema, policy-shape refusals, idempotence, dry-run, redaction. Live (operator): login from mobile data, a different GitHub account denied, `check` green on both Macs, a revoke drill with an already-open browser session and a fresh connection, repeated after a connector restart, the other Mac and the hub services unaffected.
8. **Order of work.** C11, C12, C14 and C16 need only the scratch daemons and gate the dispatch of parts A and C (they close A P1, P2, P4 and C P4, P6, P7, P9-P11); C13 needs part A's library at its landed commit, so it runs after A lands and before A is installed. C1-C4 and C8 can be captured in parallel; C5-C7, C9 and C15 need the throwaway app and tunnel. None needs part A or part C installed. The part B spec is written after C1-C16 are embedded and goes to blind review before dispatch.
