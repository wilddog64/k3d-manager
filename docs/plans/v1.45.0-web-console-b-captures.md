## Why captures first

`docs/process/rules.md` (prove external behaviour before dispatch) says a fix that depends on how an outside tool behaves carries proof from the deployed version. Part B depends on the Cloudflare Access API, browser-rendered SSH, the short-lived certificate principal mapping, and `sshd` under a LaunchDaemon. None is proven. The review (blocker 8) and Astra's finding 5 say the same. Each capture below names what it proves and the decision it feeds. Captured output is redacted by the filters named, saved as a dated file under `docs/captures/` only after the operator reads it, and then embedded in the part B spec as fixtures.

## Safety rules for every capture

- Read-only: only `GET` against the Cloudflare API, only `gh api` GET, only read commands on the Macs. No `POST`, `PUT`, `PATCH`, `DELETE`, no `launchctl bootstrap`, no `make install-*`.
- The Cloudflare token is read from the Keychain by the shell and passed to `curl` through a config file on stdin (`curl --config -` with `header = "Authorization: Bearer ..."`), never as an argument, never echoed, never in shell history. Presence is checked by name only: `security find-generic-password -s <item> >/dev/null` (the exit code, never `-w` output on a terminal).
- Scope for the capture token: a read-only API token created for this capture (permissions below), stored as `k3dm-cloudflare-access-capture-token`, deleted afterwards. It is not `k3dm-cloudflare-api-token` and not the future setup token.
- Do not run any capture inside tmux or any session an agent reads, when the output contains an account id, a team name or a policy body. Save to a file with mode 600 under `/private/tmp/k3dm-captures-<date>/`, filter, then show the filtered file.
- Filters ("FILTER" below): `jq` allow-list projections that keep field names and shapes, and replace every value of `id`, `uid`, `account_id`, `zone_id`, `tunnel_id`, `aud`, `email`, `domain`, `name` (when it holds a hostname or person) with `<redacted:field>`. Never keep a token, a certificate body, a private key, an `AUD` tag or a team name. Scan the filtered file with `grep -Ei 'bearer|eyJ|BEGIN|ssh-(rsa|ed25519)|@[a-z0-9.-]+\.[a-z]{2,}'` before it is shown or committed; any hit blocks the capture.
- Each capture records host, date, tool versions (`cloudflared --version`, `sshd -V` is not available, so `ssh -V`, `sw_vers -productVersion`) in a header comment.

## Required API token permissions (to confirm in C1)

The capture token needs read access only: Account, Access: Apps and Policies, Read; Account, Access: Certificates, Read; Account, Cloudflare Tunnel, Read; Account, Access: Organizations, Identity Providers, and Groups, Read; Zone, DNS, Read for the one zone. Part C1 records which of these the endpoints actually demand (an HTTP 403 with `code` 10000 names a missing permission). The setup token of part B is derived from that list, narrowed further: Access Apps and Policies Edit, Access Certificates Edit, Cloudflare Tunnel Edit, DNS Edit for the one zone, and no other permission.

## Captures

Placeholders: `${ACCOUNT_ID}`, `${APP_ID}` are read from earlier captures or the dashboard by the operator and never written into the repo. The API base is `https://api.cloudflare.com/client/v4`.

### C1. Access applications, policies and session settings

- Commands (GET): `/accounts/${ACCOUNT_ID}/access/apps`; `/accounts/${ACCOUNT_ID}/access/apps/${APP_ID}` for any existing self-hosted app; `/accounts/${ACCOUNT_ID}/access/apps/${APP_ID}/policies`; `/accounts/${ACCOUNT_ID}/access/identity_providers`; `/accounts/${ACCOUNT_ID}/access/organizations`.
- FILTER: keep `type`, `session_duration`, `allowed_idps`, `auto_redirect_to_identity`, `enable_binding_cookie`, `policies[].decision`, `policies[].include[].*` key names, `policies[].exclude`, `policies[].require`, `domain_type`; redact every identifier, hostname, email and team name.
- Proves: the app `type` value for a browser-rendered SSH app (`ssh` versus `self_hosted`) and its schema; where `session_duration` lives and its accepted format (so the 6-hour value is expressible); the exact `include` rule keys that mean "this GitHub login method and this email" (`login_method` plus `email`, or `github-organization`), which decides how part B writes "exactly one allow rule" and how `check` tells a bypass or `Everyone` rule from it; whether policies are app-scoped or account-reusable (inherited policies are how an extra allow could arrive); whether `allowed_idps` can pin the single GitHub provider. Feeds: Behaviour of `setup`, `check` policy-shape item, N3.
- Needs the operator to have at least one Access app to read; if none exists, C1 is blocked and the schema is captured from the API reference at the dated page version instead and the live proof moves to C9 (a throwaway app created by the operator in the dashboard, then deleted).

### C2. Can an app be disabled, or only deleted

- Commands: read the OpenAPI schema for the app object from the dated Cloudflare API reference page (no auth) and look for any `enabled` or `status` field on `PUT /access/apps/{id}`; in the dashboard (operator, no API) check whether a self-hosted app has a disable switch; on the throwaway app of C9, GET after a dashboard disable.
- Proves: whether "revoke disables the Access app" (umbrella S5) is expressible at all; if only delete exists, the revoke order and the `check` state for "intentionally revoked" change (the app is absent, not disabled), and re-creation has a new AUD tag that the origin JWT validation must pick up. Feeds: revoke design, `check` exit-status mapping.

### C3. Short-lived certificate CA

- Commands: `/accounts/${ACCOUNT_ID}/access/apps/${APP_ID}/ca` (GET); `/accounts/${ACCOUNT_ID}/access/gateway_ca` (GET, if the account uses Gateway).
- FILTER: keep the key names and the type of `public_key`; replace the key body with `<redacted:public_key length=N>`; never save the full key into the capture file shown to the agent. The operator saves the real public key for the throwaway test (C6) in a mode 600 file.
- Proves: whether the CA is per app or per account, whether its public key is stable across reads and when it rotates (a rotation would invalidate the installed `access_ca.pub`, so `check` needs a drift item and `setup` a re-fetch), and the key's algorithm. Feeds: how part A's `--ca-file` is populated, drift detection, rotation procedure.

### C4. Certificate principal mapping

- Commands: on the machine, from a throwaway browser-rendered SSH login (C5) the operator runs `ssh-keygen -L -f` on the presented certificate if obtainable, or reads the part A sshd's `LogLevel VERBOSE` log lines (`Accepted publickey ... ID ... (serial ...) CA ...`) which name the principal and key id, filtered to remove the user name and key ids.
- Proves: which string Cloudflare puts in the certificate principal (the part of the GitHub email before the `@`, an Access-derived name, or the local login), and therefore whether `AllowUsers` plus the default "principal must equal the login name" works or part B must add an `AuthorizedPrincipalsFile` mapping the operator's principal to the local account. Also the certificate validity period. Feeds: sshd principal configuration (a part A follow-up if needed), N3 and the lost-device story.

### C5. Browser-rendered SSH with a ForceCommand and a PTY

- Method: operator, from a browser on mobile data, against a throwaway Access SSH app and a throwaway tunnel that targets part A's daemon after part A is installed with the stub `ForceCommand` replaced for the test by a script that prints `pty=<yes|no>`, the value of `$SSH_ORIGINAL_COMMAND`, `TERM`, then reads one line and echoes its length, then reads raw bytes for Ctrl-C, Ctrl-Z and Ctrl-backslash and prints their codes.
- Proves: the browser terminal allocates a PTY and delivers the control characters as input rather than to the browser (feeds the TOTP gate's INT/TSTP/QUIT handling and the whole of part C), what `TERM` is, what environment arrives, whether the Access-rendered page needs `PermitTTY`, that `ForceCommand` runs, and what the browser shows on a non-zero exit. Also whether the page reconnects automatically after an idle drop (feeds the 120-second idle layer and `ClientAliveInterval`).
- Cannot be done offline. Needs part A installed on one machine and C1-C4 done.

### C6. `sshd -T` on each Mac, and the console config under a LaunchDaemon

- Commands, read-only, on the M5 and the M4: `sshd -G` (effective system config, unprivileged); `sudo sshd -T` (effective system config including host keys; operator types the password); `ssh -V`; `launchctl print system/com.openssh.sshd | head -20`; `netstat -anv -p tcp | grep LISTEN` filtered to the `sshd` rows; `systemsetup -getremotelogin` under sudo.
- FILTER: drop `allowusers`, `authorizedkeysfile` values that contain paths with the login name, and `hostkey` paths; keep the rest.
- Already proven locally on the M4 on 2026-11-18 (OpenSSH_10.2p1, macOS 26.5.2): `sshd -G` shows `passwordauthentication yes`, `kbdinteractiveauthentication yes`, `usepam yes`, `authenticationmethods any`, and Remote Login is on (`*.22` listening). The capture adds the M5 and the root-only `-T` view, and settles whether D1's "system sshd has password auth off" is already true on either Mac (it is not on the M4), which decides whether part A's `check` item C8 is a hard failure at first run.
- Live under a LaunchDaemon (after part A install on one machine, operator-run): `sudo launchctl print system/com.k3d-manager.web-console-sshd`; `sudo lsof -nP -p <pid> -a -i`; `ls -le /etc/k3dm-web-console`; the daemon's log lines for `UsePAM no` (accepted or warned), host key load, and what happens to `sshd-session` children on `launchctl bootout`. Proves: host key permission handling by `sshd -D -f` as root under launchd, `UsePAM no` on macOS 26, session cleanup on bootout (part A proof owed; feeds revoke order).

### C7. Keychain and secret readability from an SSH session

- Commands, from a console login on a machine with part A installed and the throwaway ForceCommand of C5 replaced by a shell for one supervised test, run as the operator, outputs reduced to exit codes: `security find-generic-password -s k3dm-cloudflare-api-token >/dev/null; echo $?` (never `-w`); `security show-keychain-info ~/Library/Keychains/login.keychain-db`; `ls -l /var/db/k3dm-web-console` (part C paths, expected denied); `launchctl print gui/$(id -u) | head -3`.
- Proves: whether a login that comes in over SSH can read the login Keychain (it is usually locked in an SSH session, which `docs/howto/machine-setup.md` already notes) and so whether the Keychain is any barrier against an agent running as the operator; and that a root-only secret directory is denied to the operator. Feeds: N6 honesty (what "no agent" can mean once same-user programs run inside `work`), part C's secret placement. Mark the output filtered to exit codes; do not run `-w` or `dump-keychain` at all.

### C8. Origin JWT validation and the tunnel

- Commands: `cloudflared --version`; read the `cloudflared` release notes at the installed tag for `originRequest.access` (`required`, `teamName`, `audTag`); on a throwaway tunnel run `cloudflared tunnel ingress validate` and `cloudflared tunnel --config <scratch> ingress rule ssh://127.0.0.1:42722` (read-only commands) for the console ingress; read the tunnel's API object (`GET /accounts/${ACCOUNT_ID}/cfd_tunnel/${TUNNEL_ID}`, FILTER to keep `status`, `connections[].*` key names, `config_src`).
- Proves: that `originRequest.access.required: true` makes cloudflared reject requests without a valid Access JWT for that AUD (so a request that bypasses Access at the edge still fails), whether a `ssh://` ingress honours it, the schema for `config_src` local versus remote, and how many connectors a tunnel shows. Feeds: ingress template, the `check` tunnel item, the one-connector-per-tunnel assumption that `bin/hub-cutover` (D2 isolates the console from it) relies on.

### C9. Throwaway end-to-end and revoke ordering

- Method: operator creates, by hand in the dashboard, a throwaway Access SSH app and policy (one GitHub-login allow rule, 6-hour session) for a throwaway hostname, a throwaway tunnel, and the part A daemon. Capture: login works with the right identity; a second GitHub account is denied at Access; with the daemon stopped the browser shows an error and no listener remains; after deleting (or disabling, per C2) the app, a previously open browser session ends or persists (time it) and a fresh connection is refused; after removing the ingress and DNS record, name resolution and routing fail; Access session revocation in the dashboard (`Revoke existing sessions`) versus an open SSH session.
- Proves: the revoke order in the outline below, and how long an established session survives each step. Feeds: revoke design, the lost-laptop and lost-phone steps in the how-to, E-items for live revoke drills.

### C10. Existing readers and writers of the hub tunnel (local, no operator action)

Local greps confirm that part B's per-machine tunnel must stay out of the hub tunnel's paths (D2). Citations from `grep -n` on each file, run 2026-11-18:

- `bin/cluster-up:1844` and `:1845` set `~/.cloudflared/config.yml` and `scripts/etc/cloudflared/config.yml`; `bin/cluster-up:1873-1875` re-render the live config from the repo on every run. A console ingress placed in either file would be erased or restored by it.
- `Makefile:1005` (`cloudflared-backup`), `:1021` (`cloudflared-config`), `:1024-1025` (live and source config) read the same files.
- `bin/public-endpoint-probe:110-115` enumerates every `hostname:` of the config it is given (default the repo config, `:60`) and `scripts/lib/hermes/sensors.py:537` runs that probe for Hermes. A console hostname in the repo config would be probed and reported.
- `bin/k3dm-cloudflare-posture:16` hard-codes the seven public hostnames (`HOSTS`), iterated at `:282`; the console hostname is not in it and must not be added.
- `bin/cluster-down:343` and `:355` name the hub tunnel's LaunchAgent and legacy LaunchDaemon plists; teardown boots out the hub tunnel only.
- `bin/hub-cutover:220-222` requires exactly one connector for tunnel `k3d-manager`; `scripts/etc/machine/hub-singletons.list:16` lists `cloudflare-tunnel` as the last singleton.
- `scripts/etc/cloudflared-config.yml.tmpl:1-14` is a second tunnel-config template (the hub's, with `${CLOUDFLARE_TUNNEL_ID}`); `scripts/etc/cloudflared/config.yml` ends with `http_status:404` at `:19`.

A dedicated console tunnel therefore needs its own config path (for example `~/.cloudflared/console.yml`), its own LaunchAgent label, its own credentials item, and none of the files above. This is the D2 design check and needs no capture from the operator.

## Part B outline (spec after the captures)

1. **Per-machine tunnel, independent of the hub (D2).** Tunnel named `k3dm-console-<host>`; config `~/.cloudflared/console-<host>.yml`; credentials file restored from its own Keychain item `k3dm-console-<host>-credentials` (name by capture C8); LaunchAgent label `com.k3d-manager.console-tunnel` (a user agent; the console works only while the operator is logged in, or a LaunchDaemon variant if C7/C8 show a reason, an open decision); ingress exactly `ssh://127.0.0.1:<port>` for the one hostname and a final `http_status:404`; `originRequest.access.required: true` with the app's `teamName` and `audTag` (C8). No edit to `scripts/etc/cloudflared/config.yml`, `bin/cluster-up`, `bin/cluster-down`, `bin/hub-cutover`, `hub-singletons.list`, `bin/public-endpoint-probe`, `bin/k3dm-cloudflare-posture`, `scripts/lib/hermes/sensors.py` (C10). Part A's `check --cloudflared-config` reads the console config.
2. **Access app and policy.** Created through the API using the schema of C1: one app per machine, one allow rule for the operator's GitHub login method and email, no Bypass, `Everyone`, service-token or other identity provider, session duration 6 hours, short-lived certificates on. `setup` verifies the app and policy shape before it makes the origin routable (ingress and DNS last) and fails closed on a partial setup. `--dry-run` prints the plan with no write.
3. **Origin JWT validation** as in item 1, and the certificate CA (C3) installed through part A's `--ca-file`, with a drift check.
4. **Revoke order** (fail closed, each step idempotent, safe to repeat), refined by C9: stop the console sshd and end its sessions first (part A `uninstall`, which also ends `sshd-session` children); then revoke Access sessions and disable or delete the app (per C2); then remove the ingress and stop the console tunnel; last remove the DNS record. A remote path for a lost laptop (the dashboard steps, off the device) is part of the how-to; the local cleanup runs when the laptop returns. `check` after revoke exits with a distinct status for intentionally revoked versus broken.
5. **Idempotence and secrets.** A dedicated Access token item `k3dm-cloudflare-access-token`, read by name only, passed to `curl` through stdin config, never in argv, logs or `check` output; setup refuses to run when the token's verified permissions exceed the C1 list.
6. **Machine lists.** The console-tunnel LaunchAgent and the install target go in `not-installed.list` (operator-run), never an agents or secrets list, like parts A and C.
7. **Evidence.** Offline: fixtures built from C1-C3 and C8 captures (host, date, version in a comment) for schema, policy-shape refusals, idempotence, dry-run, redaction. Live (operator): login from mobile data, a different GitHub account denied, `check` green on both Macs, a revoke drill with an already-open browser session and a fresh connection, repeated after a connector restart, the other Mac and the hub services unaffected.
8. **Order of work.** Parts A and C land first (offline, operator installs); C1-C4 and C8 can be captured in parallel with them; C5-C7 and C9 need part A installed; the part B spec is written after all ten captures are embedded and goes to blind review before dispatch.
