## Problem

The operator asked for the ETA to v1.50.0, the milestone where the platform proofs switch from
shopping-cart to the TwinkleAI app. Claude answered by hand on 2026-10-17:

- 12 releases remain;
- recent releases come about every 2.4 days, so cadence alone gives ~Nov 14–21;
- that estimate is honest only up to v1.48.x, because v1.49.0 cannot start until TwinkleAI app M1,
  in another repo, is near done.

None of this is recorded anywhere a dashboard can read:

- the shipped dates are in git tags;
- the remaining releases are in roadmap prose. v1.49.0 and v1.50.0 are table rows, not headings;
- the external block is in a sentence.

Each answer is redone by hand and goes stale as soon as a release splits into a patch. v1.43 alone
grew from one release to six.

## Requirements (operator's 2026-10-17 rules from plan 1, applied here)

1. **The inventory is explicit and authoritative.** The remaining releases come from one
   checked-in file, not from scraping roadmap prose. A drift test keeps that file and the roadmap
   in step.
2. **A forecast is not a fact.** A shipped date (a tag) and a forecast date are different series
   with different labels, and are never shown in the same column.
3. **Don't infer from missing information.**
   - A milestone that waits on outside work shows `blocked`, and every milestone after it
     shows `after_blocked`; neither gets a date.
   - With fewer than 6 shipped releases in the window, the cadence is `insufficient` and nothing
     gets a date.
   - A forecast is always a range, never one date.

## Decisions

- **New data file `docs/release-milestones.json`** is the ordered list of releases not yet shipped,
  up to and including the target. Claude maintains it with the roadmap, in the same commit as any
  release split or re-plan. JSON because the scanner is stdlib-only (no `yaml`).
- **A milestone is shipped when tag `v<version>` exists.** It stays in the file until the next edit
  that removes it, and the scanner marks it `shipped` from the tag, so a stale entry is harmless.
- **Cadence** = gaps between consecutive `v1.*` / `v2.*` release tags, using the tag dates
  (`%(creatordate:unix)`, annotated tags). Use the last **12** gaps; minors and patches count
  equally, because the remaining list also mixes both. Same-day releases give a gap of 0, which is
  real and is kept. Publish the 25th, 50th and 75th percentiles.
- **Forecast for the k-th unshipped, unblocked milestone in file order (k = 1, 2, …):**
  `low = last_tag + k·p25`, `mid = last_tag + k·p50`, `high = last_tag + k·p75`, in unix seconds.
  If a bound lands in the past (the release is overdue), clamp it to scan time and set
  `overdue="true"`.
- **Blocking.** A milestone can carry `"blocked_by": "<text>"` and `"blocked_done": false`. That
  milestone is `blocked`. Every later milestone is `after_blocked`, because the order is a chain.
  Neither gets a forecast. Once `blocked_done` becomes `true`, forecasting continues past it.
- **Target.** Exactly one milestone has `"target": true`. It drives the headline tiles. The
  drift test enforces "exactly one".

## Fix

### 1. `bin/k3dm-vectordb-metrics` — release forecast

Add these functions:

- `_release_tags(root)` → `[(version, unix_ts)]`, sorted by version, from
  `git for-each-ref --format='%(refname:short) %(creatordate:unix)' refs/tags/v*`. Keep only names
  that fully match `v\d+\.\d+\.\d+`.
- `_load_milestones(root, ref=None)` → the parsed JSON. With `ref`, read it through `git show
  <ref>:docs/release-milestones.json`; otherwise from the tree. Raise `ValueError` on a missing
  version, a non-`vX.Y.Z` version, a duplicate, or a target count other than 1.
- `_cadence(tags, window=12)` → `{"p25", "p50", "p75", "gaps", "last_ts"}`, or `None` if fewer than
  6 gaps. Use nearest-rank percentiles on the sorted gaps; no numpy.
- `_forecast(milestones, tags, cadence, now)` → one dict per milestone, with `state` one of
  `shipped | forecast | blocked | after_blocked | insufficient`, the bounds where the state is
  `forecast`, and `overdue`.
- `_forecast_metrics(root, ref=None, now=None, repo="k3d-manager")` → this text:

```
k3dm_release_shipped_timestamp_seconds{repo="k3d-manager",version="v1.43.3"} 1792108800
k3dm_release_cadence_seconds{repo="k3d-manager",quantile="0.25"} …
k3dm_release_cadence_seconds{repo="k3d-manager",quantile="0.5"} …
k3dm_release_cadence_seconds{repo="k3d-manager",quantile="0.75"} …
k3dm_release_cadence_window_gaps{repo="k3d-manager"} 12
k3dm_release_milestone_info{repo="k3d-manager",version="v1.49.0",release_order="<_release_order>",position="11",kind="minor",state="blocked",blocked_by="TwinkleAI app M1 near done (app repo)",target="false",current="false"} 1
k3dm_release_milestone_forecast_seconds{repo="k3d-manager",version="v1.44.0",bound="low"} …
k3dm_release_milestone_forecast_seconds{repo="k3d-manager",version="v1.44.0",bound="mid"} …
k3dm_release_milestone_forecast_seconds{repo="k3d-manager",version="v1.44.0",bound="high"} …
k3dm_release_milestones_remaining{repo="k3d-manager"} 12
k3dm_release_forecast_scan_timestamp_seconds{repo="k3d-manager"} <now>
```

- **Shipped timestamps:** emit only the last 20 tags, to bound cardinality.
- **Cadence:** with `None`, emit `k3dm_release_cadence_window_gaps` with the real count, and no
  quantile lines.
- **`state` label values:** `shipped`, `forecast`, `blocked`, `after_blocked`, `insufficient`.
- **`current="true"`** marks the milestone equal to `_current_release(root, ref)`.
- **`overdue="true"`** goes on `k3dm_release_milestone_info` when any bound was clamped.
- **`blocked_by`:** sanitize like the bug title helper (no `"`, `\` or newlines), cap at 80 chars,
  and use an empty string if absent.
- **`k3dm_release_milestones_remaining`** counts the not-shipped milestones up to and including the
  target.

In `publish_bug_metrics`, after the plan push from plan 1, inside its own `try`, call
`_push_bug_group("k3dm-release-forecast", _forecast_metrics(root, ref), method="PUT")`. On any
exception, including a `ValueError` from a malformed file, print `release forecast skipped
(non-fatal): …` to stderr. Nothing else changes.

### 3. `scripts/etc/argocd/platform-ops/grafana-dashboard-bugs.yaml` — "Release forecast" row

Add a row titled `Release forecast` directly below plan 1's
"Release plans" section. Shift nothing.

**Tiles** (`h` 4):

| Title | Expr | Display |
|---|---|---|
| Releases to target | `k3dm_release_milestones_remaining{repo="k3d-manager"}` | number |
| Median days per release | `k3dm_release_cadence_seconds{repo="k3d-manager",quantile="0.5"} / 86400` | 1 decimal; `noValue`: `insufficient history` |
| Target forecast (earliest) | `min(k3dm_release_milestone_forecast_seconds{bound="low"} * on(version) group_left k3dm_release_milestone_info{target="true"}) * 1000` | unit `dateTimeAsIso`; `noValue`: `no date — see table` |
| Target forecast (latest) | same with `bound="high"` and `max` | same |
| Target state | `k3dm_release_milestone_info{target="true"}` with the `state` label as display text | value mappings: `blocked` / `after_blocked` orange `blocked upstream`, `insufficient` yellow, `forecast` green, `shipped` blue |

**Table** `Remaining releases` (`w` 24): instant queries joined by `version`.

- **Queries:**
  - A: `k3dm_release_milestone_info{repo="k3d-manager",state!="shipped"}`;
  - B/C/D: the three forecast bounds;
  - E: `sum by (release) (label_replace(k3dm_plan_release_docs{repo="k3d-manager"}, "version", "$1", "release", "(.*)"))`,
    which is the plan count per release from plan 1.
- **Transformations:** `merge`, then `organize`.
- **Columns:** Position, Version, Kind, State, Blocked by, Plans, Earliest, Expected, Latest.
  Earliest, Expected and Latest show the forecast bounds as `dateTimeAsIso`, multiplied by 1000.
- **Empty values:** an empty forecast cell shows `-`, never a date. Plans shows `0` when the release
  has no plan docs yet. That is a fact from `docs/plans/`, not a guess.
- **Sort:** by Position ascending.
- **Header:** the column header for the dates reads `Forecast — earliest/expected/latest`, so a
  forecast is never mistaken for a ship date.

## Tests (each new one must fail against the pre-change code; show it on a temp copy)

No live Pushgateway (the `_no_live_pushgateway` fixture). Use `tmp_path` git repos with tags created
at chosen dates (`GIT_COMMITTER_DATE` on `git tag -a`), and fixed `now`.

1. `_cadence`:
   - 13 tags give 12 gaps; check p25/p50/p75 against hand-computed nearest-rank values;
   - two same-day tags give a 0 gap that is kept;
   - 6 tags (5 gaps) → `None`;
   - non-semver tags (`v1.2`, `lib-v0.5.2`) are ignored.
2. `_forecast`, with milestones A, B, blocked C and target D:
   - A gets k=1 bounds and B gets k=2 bounds, exactly;
   - C → `blocked`, D → `after_blocked`, and neither has bounds;
   - with C `blocked_done: true`, C gets k=3 bounds and D gets k=4 bounds; assert those exact values;
   - a milestone whose tag exists → `shipped`, and it does not consume a k;
   - a bound in the past is clamped to `now` and sets `overdue`.
3. `_forecast` with `cadence=None` → every unshipped milestone is `insufficient`, with no bounds.
4. `_load_milestones` raises on: a duplicate version, zero targets, two targets, and version `1.44`.
5. `publish_bug_metrics` with `_push_bug_group` stubbed:
   - pushes `k3dm-release-forecast` with `PUT`;
   - a malformed milestones file → the other groups are still pushed, and stderr contains
     `release forecast skipped (non-fatal)`;
   - the emitted text has no `k3dm_release_milestone_forecast_seconds` line for a `blocked` or
     `after_blocked` version.
6. `test_release_milestones_drift.py`, against the **real** `docs/release-milestones.json` and
   `docs/roadmap.md` (read-only, no network). This is the drift guard for Requirement 1:
   - the file loads (exactly one target);
   - every listed version appears somewhere in `docs/roadmap.md`;
   - every `### Candidate milestone — vX.Y.Z` heading whose version has no git tag and is ≤ the
     target appears in the file;
   - file order is ascending by version.
7. `grafana_dashboard_bugs.bats`:
   - no forecast panel is titled or column-headed with `ship` or `release date` (case-insensitive),
     so a forecast is never labelled as a fact;
   - the target tiles have a `noValue` text;
   - the table's forecast columns have an empty-value mapping to `-`;
   - new panels' `gridPos.y` ≥ plan 1's section bottom, and no overlaps.

### Mutations (Claude, at verification)

- Forecast `after_blocked` milestones (ignore the chain) → tests 2 and 5 fail.
- Let a shipped milestone consume a k → test 2 fails.
- Drop the `< 6 gaps` guard → test 3 fails.
- Add a roadmap heading `### Candidate milestone — v1.46.1 (patch)` without updating the JSON →

## Operational Requirements

- No new schedule. It runs with the existing Hermes-driven scan on the laptop. The scan needs the
  repo's tags locally, which a normal `git fetch --tags` gives.
- The dashboard deploys via `hub-grafana-dashboards` from the release branch. `make appsets-reapply`
  is part of the release.
- **Maintenance rule** (added to `docs/roadmap.md`): a release split, a new patch or a dropped
  milestone updates `docs/release-milestones.json` in the same commit. If a blocker is lifted,
  set `blocked_done: true`, then delete the field after that release ships.
- Cardinality: about 20 shipped series, 3 cadence series, under 20 milestone-info series, and
  under 60 forecast series.

## What NOT to Do

- Do not parse roadmap prose for dates, durations or blockers. The JSON is the only input besides
  tags.
- Do not show a single forecast date anywhere; always low/mid/high.
- Do not forecast past a blocked milestone, and do not default a missing cadence to a guess.
- Do not count lib-foundation or shopping-cart tags.
