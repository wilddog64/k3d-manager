## Diagnosis (read-only, Claude, 2026-11-23, kept `dr-drill` cluster on m2-air)

- The export holds only three PVC tarballs plus `inventory.json` (`hub_data_export`, `scripts/plugins/hub_data.sh:400-439`;
  claims at `:32`). There is no `openldap-admin` Secret to restore, so option (a) cannot be done literally.
- `openldap-admin` is an ExternalSecret from Vault `ldap/openldap-admin` (`scripts/etc/ldap/eso.yaml:27-43`,
  `refreshInterval: 1h`, `creationPolicy: Owner`). The Vault PVC *is* restored, so the restored Vault already holds the
  backup's password.
- Timeline on the kept cluster: the Secret was created and last refreshed at 13:30:16Z, from the drill's fresh Vault,
  seeded with a random password by `deploy_ldap` (`scripts/plugins/ldap.sh:1133`). `vault-0` and `openldap-0` started at
  13:47:59Z, after the restore. Since then the ExternalSecret has been `SecretSyncedError` ("could not get secret data
  from provider"), and SecretStore `vault-kv-store` has been `InvalidProviderConfig: unable to create client`.
- Probable cause (the pre-dispatch probe below must prove it): the restored Vault's `auth/kubernetes/config` names the
  real hub's API server and CA, so ESO's Kubernetes-auth login (role `eso-ldap-directory`, SA `eso-ldap-sa`) fails.
  The Secret keeps the fresh password, and the pod's `LDAP_ADMIN_PASSWORD` does not match the restored `cn=ldap-admin`
  entry, giving `Invalid credentials (49)`. The fresh drill Vault got the same host-plus-CA write (`vault.sh:2305-2307`),
  and ESO synced with it.
- `hub_recover` rewrites this config in step 6 (`_hub_data_repoint_vault`, `hub_data.sh:1211`). The drill must **not**
  reuse that function. After the auth write it also:
  - applies a `vault-root` Secret holding the root token (`:889`);
  - syncs Keychain item `k3dm-vault-root-token` (`:890`, `hub_recovery.sh:51-78`).

  The drill's credential allowlist only permits that item in `restore` scope (`scripts/etc/dr/credential-allowlist.tsv:10-11`),
  so the shim refuses it, and `_err` exits the drill.

## Behaviour

1. New `_hub_data_drill_ldap_resync <context>` in `scripts/plugins/hub_data.sh`, next to `_hub_data_refresh_dependents`.
   - Declare it with a subshell body `( … )`.
   - Every `_kubectl` call starts with `--no-exit`. Without it, a failing call ends in `_err` and `exit 1`
     (`system.sh:117-131`), which is the defect 2 mechanism.
   - It never calls `_err`. On the first failing step it prints one line,
     `ERROR: [dr-drill] LDAP admin re-sync failed at <step>`, to stderr and returns 1.

   Steps:
   1. **auth:**
      - `token="$(_hub_data_generate_root secrets vault)"`.
      - Run the same `vault write auth/kubernetes/config kubernetes_host=… kubernetes_ca_cert=@…` as `:855`, through
        `_no_trace _vault_exec_stream --no-exit --stdin`, with the token on stdin.
      - Then `_hub_data_vault_revoke "$token" secrets vault`, run on success and on failure.
      - No `vault-root` Secret, no Keychain access, no `vault-unseal` Secret.
   2. **mark:** read `.status.refreshTime` of ExternalSecret `${LDAP_ADMIN_SECRET_NAME:-openldap-admin}` in `identity`.
      An empty value is allowed.
   3. **sync:**
      - Annotate SecretStore `${LDAP_ESO_SECRETSTORE:-vault-kv-store}` in `identity` with `force-sync=$(date +%s)`.
      - Annotate every ExternalSecret in `identity` (`--all -n identity`) with the same annotation, so V8's
        all-ExternalSecrets check (`:1025`) also sees fresh data.
      - Use `--overwrite` on both.
   4. **wait:** poll every `${K3DM_HUB_DATA_ESO_POLL_S:-5}`s, up to `${K3DM_HUB_DATA_ESO_WAIT_S:-300}`s, until both hold:
      - the ExternalSecret's `refreshTime` differs from the step 2 value;
      - its `Ready` condition is `True`.

      A plain `kubectl wait --for=condition=Ready` is not enough: it can pass on the stale 13:30 `Ready`.
   5. **restart:** `rollout restart statefulset/openldap`, then `rollout status statefulset/openldap --timeout=300s`.
2. `bin/dr-drill:282`: when `hub_data_unseal_dr` succeeds, call `_hub_data_drill_ldap_resync "$DR_DRILL_CONTEXT"`
   before the V1 check.
   - On failure, `_dr_drill_set failed ldap_resync`, then run V1–V5 as today. V4 reports `false` with its own reason.
   - Never return or exit: phases 5 and 6 always run.
3. `_hub_data_refresh_dependents` is unchanged, including its message at `:813`, which test K2 (`hub_data.bats:764`)
   asserts.
4. Bash 3.2, every expansion quoted, no `eval`, no new global trap.

**Probe result (m2-air, operator at the keyboard in Terminal.app, `~/k3dm-v4-probe.sh`, 2026-11-25T13:51:23Z, m2 checkout
`c007e754`, kept `dr-drill` cluster from the 2026-11-24 E7 run; output `~/k3dm-v4-probe-20261125T055123.txt`): PASS.**
- Before: ExternalSecret `openldap-admin` Ready=False `SecretSyncedError` (refresh 04:03:51Z); SecretStore Ready=False
  `InvalidProviderConfig`; `ldap-admin` bind rc 49.
- Step 1: `auth/kubernetes/config` write rc 0; restored role `eso-ldap-directory`: bound SA `["eso-ldap-sa"]`, namespaces
  `["identity"]`, audience `null`, policies `cosign-verify`, `eso-apps`, `eso-ldap-directory`; root token revoke rc 0.
- The SecretStore turned `Valid` within seconds of the auth write (event `Normal Valid store validated`). This confirms the
  diagnosis.
- **Ordering finding (new in rev 3):** the script annotated the SecretStore and the ExternalSecret together. The ExternalSecret
  reconciled while the store was still invalid (`UpdateFailed … SecretStore "vault-kv-store" is not ready`) and then sat on
  error backoff (`refreshInterval` 1h). At about +55 s Claude re-annotated the ExternalSecret over SSH (`kubectl annotate
  … force-sync`, approved probe scope); it was `SecretSynced` 6 s later. The script then logged `resync: READY after 62s`
  (refreshTime 04:03:51Z → 13:52:26Z). Without the manual re-annotate the 300 s wait would most likely have timed out.
  Hence M1's order and N5: wait for the store to be Ready, then force-sync the ExternalSecrets.
- Step 5: `rollout restart statefulset/openldap` complete in 33 s. Step 6: `ldap-admin` bind rc 0 (PASS).
- Time budget: auth write to bind PASS about 2 min with the correct order; well inside V6's 1800 s.
