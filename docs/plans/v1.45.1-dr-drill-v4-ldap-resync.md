## Diagnosis (read-only, Claude, 2026-11-24, kept `dr-drill` cluster on m2-air)

- The export holds only three PVC tarballs plus `inventory.json` (`hub_data_export`, `scripts/plugins/hub_data.sh:400-439`;
  claims at `:32`). There is no `openldap-admin` Secret to restore, so option (a) cannot be done literally.
- `openldap-admin` is an ExternalSecret from Vault `ldap/openldap-admin` (`scripts/etc/ldap/eso.yaml:27-43`,
  `refreshInterval: 1h`, `creationPolicy: Owner`). The Vault PVC *is* restored, so the restored Vault already holds the
  backup's password.
- Timeline on the kept cluster: the Secret was created and last refreshed at 13:30:16Z, from the drill's fresh Vault,
  seeded with a random password by `deploy_ldap` (`scripts/plugins/ldap.sh:1133`). `vault-0` and `openldap-0` started at
  13:47:59Z, after the restore. Since then the ExternalSecret has been `SecretSyncedError` ("could not get secret data
  from provider"), and SecretStore `vault-kv-store` has been `InvalidProviderConfig: unable to create client`.
- Cause: the restored Vault's `auth/kubernetes/config` still names the real hub's API server and CA, so ESO's
  Kubernetes-auth login (role `eso-ldap-directory`, SA `eso-ldap-sa`) fails. The Secret keeps the fresh password, and
  the pod's `LDAP_ADMIN_PASSWORD` does not match the restored `cn=ldap-admin` entry, giving `Invalid credentials (49)`.
- `hub_recover` fixes this as step 6 (`_hub_data_repoint_vault`, `hub_data.sh:1211`). The drill never calls it:
  `bin/dr-drill:282` unseals and goes straight to V1–V5. Step 7 (`_hub_data_refresh_dependents`, `:810-828`) skips drill
  targets entirely; the message at `:813` says "no Keycloak or ESO", but the drill does run ESO.

## Behaviour

1. New `_hub_data_drill_ldap_resync <context>` in `scripts/plugins/hub_data.sh`. Put it next to
   `_hub_data_refresh_dependents`. It runs these steps in order and returns non-zero at the first failure:
   1. `_hub_data_repoint_vault "$context"`. For a drill context, this already skips the Keychain cache and the
      `vault-unseal` Secret (`:865-868`).
   2. `_kubectl --context "$context" -n identity annotate externalsecret "${LDAP_ADMIN_SECRET_NAME:-openldap-admin}" "force-sync=$(date +%s)" --overwrite`
   3. `_kubectl --context "$context" -n identity wait externalsecret "${LDAP_ADMIN_SECRET_NAME:-openldap-admin}" --for=condition=Ready --timeout="${K3DM_HUB_DATA_ESO_WAIT_S:-180}s"`
   4. `_kubectl --context "$context" -n identity rollout restart statefulset/openldap`
   5. `_kubectl --context "$context" -n identity rollout status statefulset/openldap --timeout=300s`

   On failure it prints one `ERROR: [dr-drill] LDAP admin re-sync failed at <step>` line to stderr and returns 1. Use
   `printf ... >&2; return 1`, not `_err`, which exits (defect 2).
2. `bin/dr-drill:282`: when `hub_data_unseal_dr` succeeds, call `_hub_data_drill_ldap_resync "$DR_DRILL_CONTEXT"`
   before the V1 check.
   - On failure, record `_dr_drill_set failed ldap_resync`, then run V1–V5 as today. V4 then reports `false` with its
     own reason.
   - Never return or exit: phases 5 (report) and 6 (teardown) always run.
3. `_hub_data_refresh_dependents` keeps its behaviour. Change only the message at `:813`, to
   `[hub-recover] drill target: no Keycloak, Grafana or ArgoCD to refresh; skipping`.
4. Bash 3.2, every expansion quoted, no `eval`, no new global trap.
