# v1.43.7 — Attribute agent and coordinator models in dispatch telemetry

**Status:** PROPOSED — specification only; not dispatched
**Release:** v1.43.7 (plan 2 of 5)
**Branch:** `k3d-manager-v1.43.7` (cut from `main` after v1.43.6 merges)
**Depends on:** `docs/plans/v1.43.7-codex-dispatch-cross-repo.md`; preserve its repo-aware task lifecycle and ledger compatibility.
**Approval:** Operator requested this plan on 2026-10-21; no approval to change or select runtime models.
**Component:** `bin/k3dm-codex-dispatch`, `bin/k3dm-dispatch-metrics`, `scripts/etc/argocd/platform-ops/grafana-dashboard-agent-dispatch.yaml`, related tests and Grafana guide.

## Problem

The Agent Dispatch dashboard currently exposes a Claude-edit indicator, but it does not identify
which vendor/model performed the dispatched implementation or which vendor/model served as the
primary coordinator for the task. This makes task history hard to interpret when work uses models
from more than one vendor, and it hides the coordinator model from the same operational view.

Model attribution must distinguish the implementation agent from the coordinator. A task may have
multiple implementation attempts or resumes, and the selected model may not be verifiable from the
current configuration. Historical and incomplete records must remain honest rather than assigning
the current default retroactively.

## Scope / contracts

1. **Vendor-neutral identity.** Represent an agent identity as separate `vendor` and `model` values.
   Do not encode vendor assumptions into metric names or assume every future worker is Codex. Keep
   the current Claude-edit measure as an intervention signal; it is not a substitute for the
   coordinator identity or worker identity.
2. **Worker identity per execution.** Record the worker vendor/model for each task execution attempt
   (initial run and resume), along with identity source/status: explicitly selected, runtime-reported,
   inherited/unverified, or unknown. If multiple attempts use different identities, retain each
   attempt and show the task's set/sequence; do not silently collapse it to the latest value.
3. **Primary coordinator identity.** Record the primary coordinator vendor/model separately from
   worker identity. The coordinator is the agent responsible for directing/verifying the dispatched
   task (currently often Claude); capture the actual reported or explicitly declared identity and
   provenance. Do not infer a model name from the vendor name, account settings, or today's default.
   If unavailable, record/display `unknown` or `N/A`.
4. **Ledger compatibility and privacy.** Extend `ledger.jsonl` with optional, backward-compatible
   identity metadata. Old events without identity remain readable and render as unknown. Store only
   bounded vendor/model identifiers, role, attempt/session correlation needed for the task, and
   provenance. Never store prompts, credentials, raw transcripts, account identifiers, or full model
   responses in ledger-derived metrics.
5. **Dashboard.** Add worker vendor/model and primary coordinator vendor/model to the per-task view,
   retaining existing panels and Claude-edit data. Clearly distinguish unknown/unreported from a
   measured empty value. Do not expose session IDs or task-specific high-cardinality values as
   Prometheus labels. Any model grouping must use a bounded allowlist/normalization policy.
6. **Source of truth.** Prefer runtime-reported identity where the CLI/API provides a documented,
   machine-readable field. Otherwise retain the explicitly selected identity with its provenance;
   inherited defaults without verifiable evidence remain unverified. Do not read or rewrite user
   model configuration to manufacture attribution.
7. **No model routing change.** This plan adds attribution only. It does not add model flags, change
   defaults, recommend or automatically select models, switch a model on resume, benchmark models,
   or alter permission/sandbox behavior. Later model-routing work (including the broader proposal in
   `v1.45.1-codex-model-routing-and-efficiency.md`) must treat this plan's identity contract as its
   prerequisite and must not duplicate its telemetry implementation.
8. **Cross-repo compatibility.** For tasks using the v1.43.7 `--repo` flow, worker and coordinator
   identity must follow the task regardless of work repository. Preserve bounded repo labels and the
   existing aggregate-series contract from the cross-repo plan.

## Acceptance

- A task record can show distinct worker and primary coordinator vendor/model values.
- Worker identities are associated with each execution attempt; resuming does not overwrite prior
  identity evidence or imply a model switch.
- A model selected by configuration but not verified by the runtime is visibly marked unverified,
  not reported as an observed effective model.
- Missing identity in old or partial ledger events renders `unknown`/`N/A`; it never inherits the
  current machine's configured model.
- A worker and coordinator from different vendors render correctly; tests use fixtures and make no
  real model/API calls.
- Metrics have bounded labels, contain no prompts/secrets/session IDs, and preserve current aggregate
  series and dashboard panels.
- Existing Claude-edit data remains available and is labeled as intervention, not coordinator model
  attribution.
- Tasks in another repository retain their identity metadata through status/resume/land and display
  alongside the repo recorded by the cross-repo dispatcher.
- Dispatch execution argv, default model behavior, approvals, sandbox/scope rules, and landing gates
  are unchanged.
- Focused tests, applicable regression suite, ShellCheck (for touched shell), `_agent_checkpoint`,
  `_agent_lint`, and `_agent_audit` pass; results are recorded before landing.

## Non-goals

Model selection/routing, automatic escalation, model quality ranking, token/cost attribution not
reliably supplied by the relevant runtime, coordinator workload/resource accounting, changes to
Claude's review policy, and a generalized multi-agent scheduler.
