# Plan: v1.16.0 — multiple simultaneously-active app-clusters

**Branch:** `k3d-manager-v1.16.0`
**Type:** architecture change (phased)
**Primary files (Phase 1):** `scripts/plugins/argocd.sh`, `scripts/lib/providers/k3s-hostinger.sh`, `scripts/tests/lib/provider_contract.bats`

---

## Problem

`make status CLUSTER_PROVIDER=k3s-aws` (the `ubuntu-k3s` sandbox) reports the data layer,
Pushgateway, and ESO ClusterSecretStore as `⚪ not deployed`. This is **correct and by design**:
the platform enforces a **single active app-cluster**. Only one ArgoCD destination cluster at a
time carries the `k3d-manager/role=app-cluster` label, and the `eso` + `data-git` ApplicationSets
select on that label — so the full app stack follows whichever single cluster holds it. Hostinger
holds it now, which is why `ubuntu-k3s` is ambient-mesh-only.

The goal of this plan is to allow **both** `ubuntu-hostinger` and `ubuntu-k3s` (and any future
app-cluster) to be fully deployed at the same time, so `make status` is green on both.

---

## Current architecture (as investigated 2026-07-18)

Ground truth mapped on the live hub (`k3d-k3d-cluster`) and in the code:

1. **Exclusive-label switch — in TWO functions.** Both label the target cluster
   `k3d-manager/role=app-cluster` and **strip that label from every other cluster secret**:
   - `_argocd_set_active_app_cluster` — `scripts/plugins/argocd.sh:1207-1225` (called by
     `register_app_cluster` at `argocd.sh:1308`, and at `argocd.sh:1167`).
   - `_hostinger_set_active_app_cluster` — `scripts/lib/providers/k3s-hostinger.sh:174-193`.
   Verified: `cluster-ubuntu-hostinger` secret HAS `k3d-manager/role=app-cluster` + `environment: dev`;
   `cluster-ubuntu-k3s` HAS NEITHER.

2. **`eso` ApplicationSet** (`scripts/etc/argocd/applicationsets/eso.yaml`) — cluster generator
   `selector: matchLabels: k3d-manager/role: app-cluster`; app name `'{{.name}}-eso'`
   (**collision-free** — fans out per cluster with no rename). Installs the `external-secrets`
   **controller chart + CRDs only.**

3. **`vault-backend` ClusterSecretStore is NOT GitOps-managed.** On hostinger the CSS object has
   **no `argocd.argoproj.io/tracking-id`** — it is created **imperatively** by a k3d-manager plugin
   (`scripts/plugins/eso.sh`, per kube-context), not by the `eso` ApplicationSet. So a fanned-out
   controller alone will NOT create the CSS; the imperative per-context step must also run against
   `ubuntu-k3s`. (Relates to the "App-cluster Vault auth portability" project — kubecontext-keyed,
   Vault endpoint is the open seam.)

4. **`data-git` ApplicationSet** (`scripts/etc/argocd/applicationsets/data-git.yaml`) — cluster
   generator, `destination.name: '{{.name}}'` (already per-cluster) BUT
   `metadata.name: data-layer` is **hardcoded** → multi-cluster **name collision** (only one
   `data-layer` app can exist in `cicd`). Additionally, the k3s-aws path deploys the data layer
   **imperatively** via `bin/cluster-up` (Step 10b, lines 725-790+): it `kubectl apply`s a
   **separate manual** Application from `../shopping-carts/shopping-cart-infra/argocd/applications/data-layer.yaml`
   and hardcodes the app name `data-layer` in ~15 places. So the two clusters use **two different
   data-layer deploy mechanisms** and both assume the name `data-layer`.

5. **`observability-acg` ApplicationSet** (`scripts/etc/argocd/applicationsets/observability-acg.yaml`) —
   a **single-`${APP_CLUSTER_NAME}`** `list` generator (charts: kube-prometheus-stack incl.
   Pushgateway, loki, trivy-operator). `destination.name: ${APP_CLUSTER_NAME}` and
   `externalLabels.cluster` are substituted at apply time → points at exactly one cluster
   (currently `ubuntu-hostinger`). Applied via `make observability-acg` → `deploy_observability_acg`.

**Consequence:** `make up CLUSTER_PROVIDER=k3s-aws` (bin/cluster-up) makes `ubuntu-k3s` the sole
app-cluster — it would **strip hostinger's label and re-home ESO/data-layer off hostinger**,
breaking it. The two are mutually exclusive as full app-clusters today.

---

## Target architecture

Move from "single active app-cluster" to "**every registered app-cluster is fully deployed**":

- Labeling becomes **additive** — registering/activating a cluster labels it without stripping the
  role from other clusters. The old exclusive behavior stays available behind an opt-in env flag
  `K3DM_EXCLUSIVE_APP_CLUSTER=true` (default `false`).
- Label-gated ApplicationSets (`eso`, `data-git`) then fan out to **all** labeled clusters.
- Per-cluster imperative steps (`vault-backend` CSS via `eso.sh`; data layer) are made
  context-aware so they run for each app-cluster.
- `observability-acg` is converted from a single-`${APP_CLUSTER_NAME}` list to a per-cluster
  fan-out (matrix generator: clusters × charts).

Because the blast radius spans provider code, ApplicationSets, `bin/cluster-up`, and a second repo
(`shopping-cart-infra`), this is delivered in **phases**, each independently verifiable by Claude
against the live hub + both clusters **before** the next phase starts.

---

## Phase 1 — additive app-cluster labeling (IMPLEMENT NOW)

This is the only phase Codex implements in this task. It is self-contained, low-risk (additive;
old behavior preserved behind a flag), and is the foundation the later phases build on. It makes
the `eso` **controller** fan out to every labeled cluster; it does **not** by itself turn any `⚪`
green (the CSS/data/monitoring pieces are Phases 2–4) — its success criterion is
"both clusters carry the label, hostinger is unharmed, and the `eso` ApplicationSet generates a
`ubuntu-k3s-eso` app."

### Change 1 — `scripts/plugins/argocd.sh`: `_argocd_set_active_app_cluster` additive by default

**Exact old block (lines 1207-1225):**

```bash
function _argocd_set_active_app_cluster() {
   local _active="${1:-}"
   if [[ -z "${_active}" ]]; then
      _err "[argocd] _argocd_set_active_app_cluster: active cluster name required"
      return 1
   fi
   local _ns="${ARGOCD_NAMESPACE:-cicd}"
   local _s _cname
   while IFS= read -r _s; do
      [[ -z "${_s}" ]] && continue
      _cname="$(_kubectl get "${_s}" -n "${_ns}" -o jsonpath='{.metadata.labels.argocd\.argoproj\.io/cluster-name}' 2>/dev/null)"
      if [[ "${_cname}" == "${_active}" ]]; then
         _kubectl label "${_s}" -n "${_ns}" k3d-manager/role=app-cluster --overwrite >/dev/null 2>&1 || true
      else
         _kubectl label "${_s}" -n "${_ns}" k3d-manager/role- >/dev/null 2>&1 || true
      fi
   done < <(_kubectl get secrets -n "${_ns}" -l argocd.argoproj.io/secret-type=cluster -o name 2>/dev/null)
   _info "[argocd] app-cluster role label set on '${_active}' (cleared from others)"
}
```

**Exact new block:**

```bash
function _argocd_set_active_app_cluster() {
   local _active="${1:-}"
   if [[ -z "${_active}" ]]; then
      _err "[argocd] _argocd_set_active_app_cluster: active cluster name required"
      return 1
   fi
   local _ns="${ARGOCD_NAMESPACE:-cicd}"
   local _exclusive="${K3DM_EXCLUSIVE_APP_CLUSTER:-false}"
   local _s _cname
   while IFS= read -r _s; do
      [[ -z "${_s}" ]] && continue
      _cname="$(_kubectl get "${_s}" -n "${_ns}" -o jsonpath='{.metadata.labels.argocd\.argoproj\.io/cluster-name}' 2>/dev/null)"
      if [[ "${_cname}" == "${_active}" ]]; then
         _kubectl label "${_s}" -n "${_ns}" k3d-manager/role=app-cluster --overwrite >/dev/null 2>&1 || true
      elif [[ "${_exclusive}" == "true" ]]; then
         _kubectl label "${_s}" -n "${_ns}" k3d-manager/role- >/dev/null 2>&1 || true
      fi
   done < <(_kubectl get secrets -n "${_ns}" -l argocd.argoproj.io/secret-type=cluster -o name 2>/dev/null)
   if [[ "${_exclusive}" == "true" ]]; then
      _info "[argocd] app-cluster role label set on '${_active}' (exclusive: cleared from others)"
   else
      _info "[argocd] app-cluster role label set on '${_active}' (additive: other app-clusters keep their role)"
   fi
}
```

- Fix `data-git.yaml`: `metadata.name: data-layer` → `metadata.name: '{{.name}}-data-layer'`
  (collision-free multi-cluster fan-out; destination is already `'{{.name}}'`).
- Reconcile `bin/cluster-up` Step 10b (lines 725-790+): it hardcodes the app name `data-layer` in

  either (a) let `data-git` own the data layer for all clusters and drop the manual apply, updating
  every `data-layer` reference to `${cluster}-data-layer`; or (b) keep the manual apply for

  the renamed one → a brief re-sync of hostinger's running StatefulSets. Plan a maintenance window
  / verify PVC retention (the ApplicationSet already sets `persistentVolumeClaimRetentionPolicy`
