## Context / Problem

On 2026-10-26 the operator reported the m4 webhook unresponsive while away from home. Cloud-bridge depends on the webhook, so its normal GitHub-mediated request path can fail at the same time. Hostinger cannot initiate a connection to m4/m2 today. Healthchecks.io provides independent detection but not an interactive repair channel. We need a **human-only, independently authenticated, private break-glass path** to diagnose and, with explicit operator action, run the existing `make restart-webhook` target even when webhook, Hermes, cloud-bridge or Hostinger is unavailable.

Tailscale adds an explicitly restricted inbound path over the tailnet; it is not accurate to call this "outbound-only access" merely because peers create outbound coordination connections. No home-router public port forwarding or exposure of services to the public internet is intended. This is a deliberate, documented exception to the previous no-inbound-home-control architecture.

## Decision / Scope

- **Phase 1:** install and enroll the operator's personal trusted remote device and m4 in a personal tailnet; add m2 after m4 security and post-reboot behavior pass.
- Default transport: **Tailscale networking + macOS built-in Remote Login (OpenSSH) with key-based authentication**. The ordinary macOS Tailscale GUI does *not* provide Tailscale SSH server; do not enable or claim native Tailscale SSH unless adopting and validating the open-source `tailscaled` variant. This spec does not require that variant.
- Restrict access with tailnet **grants**, scoped to the operator identity/device(s) and m4/m2 on `tcp:22` only. Verify the effective tailnet policy and run negative-access tests; do not rely on the permissive default policy. Hostinger is **not enrolled** in Phase 1 and cannot initiate SSH into either Mac.
- No subnet-router advertisement, exit node, public Funnel, Serve for management APIs, broad LAN access, unattended AI SSH keys, cloud agent identities, or credentials stored in GitHub.
- The operator retains human approval and existing local authorization boundaries. Existing cloud-bridge reader actions, Slack flows, branch/PR controls and Kubernetes contexts remain unchanged.

## Target topology

```text
Trusted remote device -- Tailscale encrypted tailnet -- m4:22 (macOS Remote Login)
                                                   \-- m2:22 (Phase 2)
Healthchecks.io <-- outbound host heartbeats (separate P2 enhancement)
Hostinger: not a tailnet peer, no inbound route to m4/m2
```

Note: Tailscale reachability and SSH access are two separate controls. The path still depends on m4 having power, a network connection, Tailscale connectivity, a running SSH service and an accessible login session/user configuration. Reboot-before-login and FileVault behavior must be tested on the actual Macs; don't promise unattended reachability.

## Functional design

### D1. Operator enrollment and least privilege

1. Document signing in with MFA, verifying the operator's trusted remote device, enrolling m4, then checking Tailscale IP/MagicDNS and connectivity.
2. Draft a *deny-by-default* tailnet grant allowing only an explicitly named operator principal or operator-owned device set to connect to m4 `tcp:22`. Add m2 only after independent testing. Use illustrative identity placeholders, not real email addresses or tokens.
3. Disable/override any existing catch-all tailnet permit rules when testing effective policy; adding a narrow grant is not sufficient if a broader grant still applies.
4. Turn on macOS Remote Login only after consent, restrict authorized local macOS users, require public-key authentication, verify host-key fingerprints out of band and ensure private SSH keys are never committed or shared with agents.
5. Host-side SSH hardening must not break established local SSH workflows. Prefer a dedicated low-privilege operator account if practical; privilege escalation remains explicit, audited and restricted to existing operator permissions.
6. Treat work-issued devices/accounts as outside scope unless employer policy permits installing/using a personal tailnet.

### D2. Failure isolation and minimal recovery

Operator sequence, not agent automation:

1. Healthchecks.io alerts that m4/webhook is missing or explicitly failed; alert alone does not prove the host is down.
2. From an enrolled, authorized remote device, establish tailnet connectivity to m4. If it fails, report `tailnet_unreachable`, do not assume power failure. Confirm local login/Remote Login after a Mac reboot.
3. SSH into the permitted local account; collect timestamp, launchd service state, process/listener health and redacted webhook logs as instructed in the October 26 incident bug.
4. If local functional webhook probe fails and a controlled restart is warranted, operator runs `make restart-webhook` **once**. This target also restarts cloud-bridge; verify the exact checked-out Makefile first.
5. Verify local authenticated webhook health and independent end-to-end Slack/cloud-bridge read-only request; capture job result and reply delivery. Do not treat successful SSH or a loaded process as proof of recovery.
6. If recovery fails, preserve sanitized evidence, stop restart attempts, and continue manual investigation; no reboot, cluster mutation, Keychain changes or new privileged routes in this scope.

### D3. Threat model and fallback

- Loss of operator device: revoke node and SSH credentials promptly; test that its old identity cannot reconnect.
- Compromised tailnet identity: enforce MFA, grants and device approvals where supported; remove broad grants and protect node enrollment keys.
- macOS login/session/boot state: record realistic post-reboot behavior for the specific client installation type; do not promise remote unlocking of FileVault.
- Tailscale control-plane/DERP or local ISP failure: SSH may be unavailable. Healthchecks.io remains an independent alert channel; the local launchd service may still self-recover.
- A malicious or compromised AI agent must not gain SSH or tailnet management credentials. No automated repair via this new path.
- Hostinger availability is independent and not required for this operator connection.

## Verification

**Offline E1 — contract and guardrails.** Run the repo test suite for the new policy/runbook fixtures (no real SSH), and check that the proposed grants are restricted to explicit principals/destinations and port 22, with no `*` all-port, Hostinger access, subnet routes or Funnel. Test rejection of an unauthorized principal and an unauthorized destination/port. Never perform tests against a live third-party account in CI.

**Operator live E2 — m4.** With consent and an enrolled device, from a separate network verify approved `ssh` over the Tailscale address, host identity verification, read-only `launchctl print`/log access, and one *safe functional health request*. Refuse a restart as a demonstration when the webhook is already healthy. If a real failure exists, recovery is separately logged under the incident bug.

**Operator live E3 — negative and availability.** Check policy denial for a non-operator identity and an unintended port; verify loss/revocation blocks access, m4 reboot/sleep and FileVault behavior, and that Hostinger is neither enrolled nor able to reach m4 via this tailnet. Repeat for m2 only when explicitly approved.

## What NOT to Do

- Do not create a PR merely to file this spec, commit it to `main`, or prematurely dispatch it to agents.
- Do not silently enable macOS Remote Login, change firewall rules, enroll Tailnet nodes or provision keys.
- Never offer Tailscale as a method for recovering an m4 that has no power/network/usable OS login.
- Do not use a shared or work laptop as an operator device without checking policy.
