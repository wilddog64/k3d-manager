## Goal

Machine setup has only run on Apple-silicon Macs. `bin/k3dm-machine-setup` fails its preflight unless
`uname -s` is `Darwin` and `uname -m` is `arm64`, and it assumes Homebrew, the macOS Keychain and launchd.
Running the `control` role on Linux tests what the one-command setup assumes about the OS. The first Linux
machine is the Hostinger VPS.

Facts read on 2026-10-31, read-only, from `ubuntu@srv1754834.hstgr.cloud`: Ubuntu 24.04.4 LTS, `x86_64`, 4 CPUs,
15 GB of memory (9 GB available), 156 GB of free disk. It has `git` and `python3`, but no `make`, `zsh` or `brew`.
The `ubuntu` user is in `sudo`. The VPS runs the live k3s cluster that serves the shopping cart.

`k3d-manager` and `lib-foundation` are public repos, so a Linux control node needs **no credentials**.

## Scope: a control node that holds no secrets

On Linux, `control` installs the tools and the two repos, and runs the offline work: `make test`, bats,
pytest, shellcheck and the docs checks. It holds no GitHub write key, no hub SSH key and no secrets.
It does not run hub work and does not use `cloud-requests`. Hostinger is reachable from the internet, so a
break-in there must not reach the hub or the repos.

## Changes

1. **Platform detection** in `bin/k3dm-machine-setup`: `platform=darwin|linux` from `uname -s`.
   - On Linux only `--role control` is accepted. Any other role exits 2 with
     `role <r> is macOS-only; use --role control on Linux`.
   - The `arm64` check applies to Darwin only. Linux accepts `x86_64` and `aarch64`.
   - The script must still run on bash 3.2 on macOS and bash 5 on Ubuntu.
2. **Packages: Homebrew on Linux**, so a Linux control node runs the same tool versions as the Macs (Ubuntu's
   `shellcheck`, `bats` and `yq` are older, and a different shellcheck gives different warnings).
   - Setup reads the `formula:` entries of `brew.control.list` and skips `cask:` entries on Linux,
     reporting each as `cask:<name> skipped (linux)`. A formula that has no Linux build is listed in a new
     `scripts/etc/machine/brew.control.linux-skip.list`, with the reason in a comment.
   - Homebrew's prefix on Linux is `/home/linuxbrew/.linuxbrew`. **Setup never runs `sudo`.** Before the
     first run the operator installs Homebrew's documented Linux prerequisites (`build-essential procps curl file
     git`) and creates the prefix owned by the setup user. If either is missing, setup prints the exact
     commands to run, as one block, and exits non-zero without changing anything.
   - With the prefix present and writable, setup installs Homebrew with `NONINTERACTIVE=1`, using the same
     signed installer path as on macOS, and runs `brew shellenv` for its own PATH. It does not edit any shell
     startup file on Linux. The how-to gives the one line the user adds.
   - The Python tools go into the user venv the same way as on macOS (`ensure_python_tools`).
3. **Steps skipped on Linux**, each reported as one line `<item> skipped (linux)`:
   - Homebrew;
   - the Keychain and `secrets.*.list` (a Linux control node has none);
   - LaunchAgents and `agents.*.list`;
   - `FROM=` file copy;
   - `ensure_operator_include`;
   - shell links and the four agent-settings repos;
   - smartcd.
4. **Repos:** only the `repos.list` rows whose roles include `control` are cloned (k3d-manager and
   lib-foundation, from v1.43.13), over HTTPS. That is correct here: there is no key, and setup does not
   switch remotes on Linux.
5. **Account.** The how-to tells the operator to create a dedicated user with no sudo, `k3dm-control`, and
   run setup as that user, after installing the packages as `ubuntu`. Setup refuses to run as root on
   Linux (`id -u` = 0 → exit 2).
6. **Make:** `make machine-setup ROLE=control` and `make machine-check ROLE=control` work on Linux.
   GNU make 4 and BSD-style flags must both work; no macOS-only `sed -i ''`, `stat -f` or `date -j` in any
   path the control role runs.
7. **Tests:** run `make test` on the Linux control node itself. Fix only failures caused by the OS (`stat -f`,
   `date -j`, `security`, `launchctl`, `pmset`): mark them `skip "macOS-only"` behind a single helper,
   `require_macos` in `scripts/tests/test_helpers.bash`. Do not change what a test asserts on macOS.
   List every test skipped on Linux in the how-to.
8. **Docs:** `docs/howto/machine-setup.md` gets a "Linux control node" section: the steps, the
   dedicated user, the root commands for Homebrew's prefix, the Vagrant test VM, what is skipped and why it holds no secrets. A `CHANGELOG.md` entry.

## Rollout order

1. **A Vagrant VM on the M4 first.** The M4 is idle now that its k3d cluster is stopped. It has Vagrant and
   VirtualBox, whose current releases run arm64 guests on Apple silicon. A new
   `scripts/etc/machine/vagrant/control-linux/Vagrantfile` uses the `virtualbox` provider with an arm64 Ubuntu
   24.04 box (for example `bento/ubuntu-24.04`; pin the box version). Its `ansible_local` provisioner runs the
   `provision-homebrew` role (see below) with `provision_homebrew_scope: prereqs`, which does **only** the
   operator's root steps: install the prerequisites, create the `k3dm-control` user without sudo, and create
   the Homebrew prefix owned by that user. Setup then runs as that user via
   `vagrant ssh -c 'sudo -iu k3dm-control ...'`. Run `vagrant destroy -f` afterwards. The VM is arm64 and
   Hostinger is x86_64: the VM proves the OS path, and Hostinger proves x86_64.
2. **Then Hostinger**, with the operator's dispatch go, as `k3dm-control`. The operator runs the same role
   with `provision_homebrew_scope: prereqs` once as `ubuntu` (`--become`), so Hostinger gets the root steps
   the VM proved, not commands typed by hand. Claude runs the checks and records them.

## Root steps: the `provision-homebrew` role (separate repo, separate PR)

`wilddog64/provision-homebrew` (private Ansible role, `master`) already installs Homebrew on Linux, but only
on RedHat: `tasks/main.yml` includes `install-{{ ansible_os_family }}-packages.yml`, and only the `RedHat`
file exists. Changes, in a PR to that repo on its own branch:

1. **`tasks/install-Debian-packages.yml`** (new), the Debian twin of `install-RedHat-packages.yml`: create
   `{{ homebrew_user }}` with no extra groups, and `apt` (with `update_cache`) Homebrew's documented
   prerequisites `build-essential procps curl file git`, plus `zsh`.
2. **`provision_homebrew_scope`** in `defaults/main.yml`, `full` (today's behaviour, unchanged) or `prereqs`.
   With `prereqs`, `tasks/main.yml` runs the OS-family packages task and a new `tasks/create-brew-prefix.yml`
   (create `/home/linuxbrew/.linuxbrew`, owned by `{{ homebrew_user }}`, mode 0755), and nothing else: no
   sudoers line, no Homebrew install, no `/etc/profile` or `/etc/zshrc` edits, no repos, no dotfiles.
3. **`tests/playbook-prereqs.yml`** (new): `homebrew_user: k3dm-control`, `provision_homebrew_scope: prereqs`.
4. README: the two scopes and the Debian support.
5. **CI gate** (operator, 2026-10-31: "setup a CI on provision-homebrew so we can gate our change"). The
   dead `.travis.yml` (python 2.7, syntax check only) is replaced by `.github/workflows/ci.yml`, on
   GitHub-hosted `ubuntu-24.04` runners, `permissions: contents: read`, actions pinned to a version tag:
   - `lint`: `yamllint`, `ansible-lint`, and `ansible-playbook --syntax-check` on both test playbooks.
   - `prereqs` (matrix `ubuntu:24.04`, `rockylinux:9` containers): run `tests/playbook-prereqs.yml` with a
     local connection, run it again and fail unless `changed=0`, then assert: the user exists and is in no
     `sudo`/`wheel` group, the prefix is owned by it with mode 0755, `brew` is not installed, and
     `/etc/sudoers`, `/etc/profile` and `/etc/zshrc` have the checksums taken before the first run.
   - The workflow is a required check on `master`, so a role change merges only when it is green.

   A self-hosted runner on the M2 is not used: the M2 is the operator terminal and the e2e runner, and the
   prereqs scope needs no VM, so containers cover it. The VM-level gate is the Vagrant run on the **M4**
   (Claude's development machine; the M5 is the hub and stays untouched), in the style of the remote e2e
   run: `make vm-test` in the role repo boots a pinned `bento/ubuntu-24.04` VirtualBox VM, runs the role
   through `ansible_local`, repeats the same assertions, and destroys the VM. Claude runs it before asking
   for the role PR's merge and pastes the output into the PR.

Known faults in `full` scope, not fixed here and never run by this plan: a `NOPASSWD:ALL` sudoers line, an
unpinned installer from `install/master`, an `args.creates` path (`/linuxbrew/...`) that never matches,
system-wide profile edits, `remote_user: root`, and a hard-coded `homebrew` user in the RedHat file.

## What NOT to do

- Do not run `sudo` from setup on Linux, and do not change anything owned by root.
- On Hostinger, do not touch k3s, `/etc/rancher`, systemd units, the firewall, or any user but `k3dm-control`.
- Do not put any key, token or Keychain item on a Linux control node.
- Do not change macOS behaviour: every existing role and test on the M4 gives the same result.
- Do not install Homebrew anywhere but `/home/linuxbrew/.linuxbrew`, and do not use apt for a tool that `brew.control.list` names.
- The Vagrantfile's provisioner does nothing setup itself is meant to do; it only stands in for the operator's root steps.
