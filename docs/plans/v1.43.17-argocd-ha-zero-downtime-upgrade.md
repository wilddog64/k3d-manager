# v1.43.17 — ArgoCD HA: CVE upgrades without ArgoCD downtime, rehearsed in the dev hub

**Status:** PLANNED — operator dispatch go 2026-11-07; dispatch when `k3d-manager-v1.43.17` is cut
**Priority:** P2 (an ArgoCD CVE patch today restarts single-replica pods, so the ArgoCD UI, API and sync go down during the rollout)
**Approval:** operator 2026-11-07: "by doing this, do we have room to support argocd no downtime upgrade (for cve patch)"; "go ahead"
**Release:** v1.43.17 (branch `k3d-manager-v1.43.17`)
**Depends on:** [`v1.43.16-dev-hub-vcluster`](v1.43.16-dev-hub-vcluster.md) (D3 rehearsal target) and its operator prerequisite P0 (OrbStack 24 GB).
**Supersedes (ArgoCD part only):** [`v1.28.0-platform-zero-downtime-rollouts`](v1.28.0-platform-zero-downtime-rollouts.md), parked until the hub left the M4 Air. The M5 is that hardware. The rest of the v1.28.0 tier (Istio, Grafana, Loki, ESO, exporters) stays queued.

## Problem

All seven ArgoCD components on the hub run one replica, with no PodDisruptionBudget (measured 2026-11-07,
namespace `cicd`). `argocd_upgrade` (`scripts/plugins/argocd.sh`) snapshots Applications, upgrades the
chart and checks that healthy Applications stayed healthy, but nothing keeps `argocd-server` or
`argocd-repo-server` serving while their pods are replaced, and nothing measures whether they did.

The apps ArgoCD manages keep running through an ArgoCD upgrade either way. What goes down is the ArgoCD
UI and API, and syncing.

## Measured (read-only, hub, 2026-11-07)

ArgoCD 7-day peak working set 1.44 GiB; application-controller 934 MiB, every other component under
100 MiB. Estimated cost of this plan: about 0.5 GiB more requests, plus about 0.3 GiB of surge during a
rollout.

## Design

### A1 — replicas, disruption budgets, rollout strategy

In `scripts/etc/argocd/vars.sh` and `scripts/etc/argocd/values.yaml.tmpl`:

| Component | Replicas | PDB | Strategy |
|---|---|---|---|
| `argocd-server` | 2 (`ARGOCD_SERVER_REPLICAS`) | `minAvailable: 1` | `maxUnavailable: 0`, `maxSurge: 1` |
| `argocd-repo-server` | 2 (`ARGOCD_REPO_SERVER_REPLICAS`) | `minAvailable: 1` | same |
| `argocd-applicationset-controller` | 2 (`ARGOCD_APPLICATIONSET_REPLICAS`, leader election on) | `minAvailable: 1` | same |
| `argocd-application-controller` | 1 (StatefulSet; a restart pauses reconciliation, no app impact) | none | unchanged |
| `argocd-redis` | 1 (a cache; it refills after a restart) | none | unchanged |
| `argocd-notifications-controller`, `argocd-dex-server` | 1 | none | unchanged |

- Readiness probes stay at the chart defaults or longer; no probe with a 1 s period or timeout (the
  2026-09 CPU-starvation kill loop).
- Requests and limits are unchanged per pod.
- Replica and PDB values are variables, so the existing single-replica path (`=1`, no PDB) still renders
  for clusters that set them.

### A2 — measure availability during `argocd_upgrade`

- During the rollout, `argocd_upgrade` probes `argocd-server` `/healthz` through its Service every 2 s,
  and runs `argocd app list` (or the equivalent API GET) every 10 s. Each probe's time and result go to
  `$snapshot/availability.tsv`.
- The upgrade fails its postcheck if any `/healthz` probe fails, and prints the failure count and window.
  `--allow-downtime` turns that into a warning (for single-replica clusters).
- The result is pushed as `k3dm_argocd_upgrade_probe_failures` and `k3dm_argocd_upgrade_duration_seconds`
  through the existing Pushgateway path, so the CVE dashboard can show the last upgrade.

### A3 — rehearse in the dev hub first

- `argocd_upgrade --context dev-hub --to <version>` runs the same upgrade, probes and postcheck against
  the dev hub's ArgoCD. The current hub-only context check accepts exactly two contexts: the hub, or the
  dev-hub vCluster context written by `dev-hub-up`.
- An upgrade against the hub refuses unless a passing rehearsal for the same target version exists in
  `$K3DM_STATE_DIR/argocd-upgrade/` from the last 7 days (`availability.tsv` with no failure and a
  passing postcheck). `--no-rehearsal` overrides it and is recorded in the snapshot metadata.
- `make argocd-upgrade-rehearse TO=<version>` and `make argocd-upgrade TO=<version>` wrap them.

## What NOT to Do

- Do not run `argocd_upgrade`, `helm upgrade` or any `make` target against a cluster. The operator runs
  E2 and E3.
- Do not change the ArgoCD chart version, the application-controller, Redis, Dex or notifications.
- Do not add probes with a 1 s period or timeout.
- Do not change other platform components from the v1.28.0 plan.
- Do not edit CLAUDE.md, `memory-bank/` or `docs/roadmap.md`. Do not commit to `main`, create a PR or skip
  hooks.
- Stubs for `helm`, `kubectl` and `curl` take output from a real read-only capture, with host and date in
  a comment beside it.
- Write the must_not tests first and show them red on the pre-fix tree.
