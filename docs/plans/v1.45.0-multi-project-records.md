**First project:** dirused (wilddog64/dirused)

## Problem (2026-11-16)

- dirused bugs live in k3d-manager `docs/dirused/bugs/`, which bug-tally does not scan (moved there on purpose so they stop blocking k3d-manager releases).
  So no dashboard shows dirused bugs at all.
- dirused fix commits read `unchecked` on the Bugs dashboard: ancestry is checked in the k3d-manager repo.
- `bin/k3dm-codex-dispatch start` requires the spec tracked in k3d-manager and versions every ledger row by the k3d-manager release branch,
  so a dirused dispatch is recorded under `v1.44.1` and counts toward k3d-manager WIP (e.g. `dirused-m1c-a-summary-all`, 2026-11-16).
- dirused has no release view, progress file or grooming of its own.

## Decision

Same process for every project: bug docs with Priority, specs with Acceptance and intent, verification that fails before the fix and passes after, live checks, release tags.
Each project keeps its records in its own repo. k3d-manager is the platform: the tooling, the ledger, the dashboards and one roll-up view.

## Milestones (operator-approved 2026-11-17)

Each milestone is its own dispatch, in this order:

- **M1 — registry and dispatch:** scope items 1 and 3. Fixes the most concrete harm first: a dirused dispatch counted toward k3d-manager WIP and versioned as a k3d-manager release.
- **M2 — metrics:** scope item 4. dirused bugs reach bug-tally and the vectordb metrics; fix-commit ancestry is checked in the bug's own repo.
- **M3 — dashboards:** scope item 5.
- **M4 — records migration and grooming:** scope items 2 and 6.

## Constraints (operator-approved 2026-11-17)

- **Back-compat ledger:** existing ledger rows have no `project` field. Every reader treats a missing `project` as `k3d-manager`; no existing dashboard panel or `codex-dispatch` command changes its output for k3d-manager rows.
- **wilddog64/dirused is public:** before M4 moves any record there, scan every file to be moved for hostnames, `servers.list` contents, VM names, IPs and credentials, and redact or keep in k3d-manager whatever is private. Acceptance carries this as a `must_not`: no private host detail lands in the public repo.

## Scope

1. **Project registry** `scripts/etc/projects.list`: `name|local path|github repo|release scheme|default branch`. k3d-manager is an entry too.
2. **Records in the project repo:** `docs/bugs/`, `docs/plans/`, `docs/ideas.md`, `memory-bank/progress.md`, `CHANGELOG.md`, its own tags (dirused `v0.x`).
   Migrate `docs/dirused/bugs/`, `docs/dirused/ideas.md` and the `docs/plans/dirused-*` specs into wilddog64/dirused, with links back.
3. **Dispatch:** `codex-dispatch start --project <name>` reads and gates the spec (spec-intent, Acceptance) in the project repo; ledger rows carry `project`;
   the version is the project's open release, not k3d-manager's; WIP limits are counted per project (3 each) plus a global ceiling.
4. **Bug and plan metrics:** `scripts/bug-tally.py` and `bin/k3dm-vectordb-metrics` scan each registered repo; fix-commit ancestry is checked in the bug's own repo
   (`_bug_status_metrics` already takes `repo=`), so dirused fixes stop reading `unchecked`.
5. **Dashboards:** a `project` variable on the Bugs, Plans and Agent Dispatch dashboards (default: all); a Projects overview panel with open bugs by priority,
   open dispatches, latest release and the next step for each project.
6. **Grooming:** `/release-groom <project>`; Sunday grooming walks every project; triage maps a bug to that project's patch release.

## Contract readers (to complete by grep before dispatch)

Ledger row shape (`project`, `version`): `bin/k3dm-codex-dispatch` (start, land, status, verify, mark), `bin/k3dm-dispatch-metrics`, `bin/k3dm-dispatch-stall-watch`,
the Agent Dispatch dashboard JSON. Spec location: `bin/k3dm-codex-dispatch` start (spec must be tracked in k3d-manager), `scripts/lib/spec_intent.py`.
Bug scan roots: `scripts/bug-tally.py`, `bin/k3dm-vectordb-metrics`, the Bugs dashboard JSON, `/release-groom`, `/sprint-plan`.

## Decided questions (operator-approved 2026-11-17)

- **Hub promote for dirused:** none. dirused does not run on Kubernetes; a GitHub release (tag + release.yml) is its release.
- **Ledger:** one shared `ledger.jsonl` with a `project` field, not one per project. It keeps cost and WIP views simple and leaves existing readers working.
- **Dashboards read other repos from local clones on the M5,** kept fresh by the existing repo-sync, not through the GitHub API (no token, no rate limit). Because a clone can lag, the dashboards show each project clone's last fetch time.
