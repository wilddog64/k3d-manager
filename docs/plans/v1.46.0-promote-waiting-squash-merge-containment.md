## Problem

`bin/k3dm-repo-sync` publishes `k3dm_repo_sync_promotable{sha,branch} 1` for the newest CI-green commit in
`<remote>/deploy/hub..<upstream>` (`find_promotable`, `bin/k3dm-repo-sync:83-99`; called at `:466-470`), and
`K3dmPromoteWaiting` fires after 15 min (`scripts/etc/prometheus/rules/repo-sync.yaml:31-33`). Release branches are
squash-merged into `main`, and `deploy/hub` moves to the squash commit, so the release branch's own commits are never
ancestors of `deploy/hub`. The range never empties: the newest green commit on the dead branch stays "promotable" and
the alert fires until someone moves the hub checkout to the next release branch. `carry_forward_promotable`
(`:102-117`) re-carries the same sha through unknown cycles by the same ancestry test (`:111-115`). Seen 2026-11-17
(`sha=1c12925`, content shipped in squash `666b27b7`).

## Proven facts

- Ancestry is the only containment test today (`:85` `rev-list deploy/hub..upstream`; `:112` `merge-base
  --is-ancestor`). `bin/k3dm-hub-promote:39-48` solves the same blind spot for promote with the GitHub API
  (`merged_pr_contains`); repo-sync should not add a network dependency.
- `git merge-tree --write-tree <a> <b>` (git ≥ 2.38) performs a real three-way merge without touching the index or
  worktree; it exits 0 on a clean merge and prints the result tree id on the first line, exits 1 on conflicts, other
  codes on error. Hub git: `git version 2.56.1` (m5-air, 2026-11-27, Claude over ssh); m4: 2.56.1.
- If merging commit C into `deploy/hub` yields exactly `deploy/hub^{tree}`, every change C carries (relative to their
  merge base) is already in `deploy/hub` — which is the squash case.

## Behaviour

1. Add `content_contained(remote, sha) -> bool | None` in `bin/k3dm-repo-sync`:
   `git merge-tree --write-tree --no-messages <remote>/deploy/hub <sha>`; return True only when the exit is 0 and the
   first stdout line equals `git rev-parse <remote>/deploy/hub^{tree}`; False on exit 1 (conflict) or a different
   tree; None on any other exit, a timeout or `OSError`. Use the existing `git()` helper (same timeout handling).
2. `find_promotable` (`:83-99`): for each candidate, call `content_contained` **before** `is-green`. True → skip the
   candidate (it neither counts as checked nor stops the loop). False or None → evaluate as today (None is
   conservative: a check we could not do never hides an alert). The 10-candidate window and the return tuple are
   unchanged.
3. `carry_forward_promotable` (`:102-117`): do not carry a sha for which `content_contained` returns True.
4. `promote_backlog` (`:461-463`) and its metric keep their ancestry meaning (commit count); no change.
5. Log one line per run when at least one candidate was skipped:
   `promotable: skipped <n> candidate(s) already in deploy/hub by content`.

## Test design

Use the suite's existing fixture (`scripts/tests/bin/repo_sync_promote_backlog.bats:1-78`: origin repo, hub clone,
stubbed `bin/k3dm-hub-promote is-green`). New cases build a release branch with 2 commits off `deploy/hub`, then
create a squash commit on `deploy/hub` with the release tip's exact tree (`git commit-tree <tip>^{tree} -p
<deploy/hub>`), push it, and run hub repo-sync with `is-green` stubbed green for every sha.

- **S1 (bug):** squash case → no `k3dm_repo_sync_promotable` series; the skip log line appears.
- **S2 (positive control):** S1 plus one new commit on the release branch after the squash, touching a file → that
  commit is published as promotable.
- **S3 (conflict):** a release commit whose change conflicts with a later `deploy/hub` change → still promotable.
- **S4 (carry-forward):** previous state `promotable_sha` = a contained sha and a lookup-failure cycle (as E5 `:162`)
  → not carried; positive control: an uncontained sha is still carried (existing E5 stays green).
- **S5 (error):** `git merge-tree` made to fail (a `git` wrapper on PATH that exits 128 only for `merge-tree`) →
  candidate evaluated as today.
