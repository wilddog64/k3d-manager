## Problem

`bin/k3dm-repo-sync` publishes `k3dm_repo_sync_promotable{sha,branch} 1` for the newest CI-green commit in
`<remote>/deploy/hub..<upstream>` (`find_promotable`, `bin/k3dm-repo-sync:83-99`; called at `:466-470`), and
`K3dmPromoteWaiting` fires after 15 min (`scripts/etc/prometheus/rules/repo-sync.yaml:31-33`). Release branches are
squash-merged into `main` and `deploy/hub` moves to the squash commit, so the branch's own commits are never ancestors
of `deploy/hub`: the range never empties, the newest green commit on the dead branch stays "promotable", and the alert
fires until someone switches the hub checkout to the next release branch. `carry_forward_promotable` (`:102-117`)
re-carries the same sha through unknown cycles by the same ancestry test (`:111-115`). Seen 2026-11-17 (`sha=1c12925`,
content shipped in squash `666b27b7`).

## Proven facts (read-only; cite these, do not re-derive)

- Ancestry is the only containment test today: `:85` (`rev-list deploy/hub..upstream`) and `:111-112`
  (`merge-base --is-ancestor`); `:259` is the checkout fast-forward test and is out of scope. `bin/k3dm-hub-promote:39-48`
  solves the same blind spot for promote with the GitHub API; repo-sync must not add a network dependency.
- **Only the tip is contained after a real squash** (Fable, replay on this repo, git 2.56.1, m4, 2026-11-27): of the 10
  newest commits of `19d396ed..origin/k3d-manager-v1.45.1` (291 in range) against squash `19d396ed`, only tip `05510385`
  merges to the squash tree; the other 9 conflict in `memory-bank/activeContext.md` / `CHANGELOG.md`. v1.45.0 the same
  (tip `a219635f`, 744 in range). Intermediate commits and the squash both extend the same lines from the fork point.
- **Merge-tree containment is lost once `deploy/hub` moves past the squash** (same replay): each old tip merges cleanly
  only into the squash commit itself; from the next `deploy/hub` commit on (post-merge docs, 3 minutes later) it
  conflicts. The incident tip `1c12925` conflicts with today's `origin/deploy/hub` `1c74deb3`.
- **Exact tree identity survives later commits**: a squash made from the release tip with no other change has
  `squash^{tree} == tip^{tree}`; that equality is permanent and needs no object writes.
- `git merge-tree --write-tree <a> <b>` (git ≥ 2.38) merges without touching index or worktree but **does write new
  loose objects** into the object database (Fable: 10 → 11 objects in a test); exit 0 clean (first stdout line = result
  tree), exit 1 conflict **or** unresolvable rev, other codes on error. `--merge-base=<c>` needs git ≥ 2.40.
- **Post-squash revert hole** (Fable, throwaway repos): a commit on the dead branch that returns a shipped change to its
  fork-point state merges to the squash tree ("contained") although it carries real work. A second merge with
  `--merge-base=<sha>^` (the commit's own delta only) differs from the hub tree for the revert and equals it for a
  squashed tip.
- Versions: hub m5-air and m4 `git version 2.56.1` (Claude, 2026-11-27). CI runs on `ubuntu-24.04`
  (`.github/workflows/ci.yml:105`; Neon: ships git 2.43.0); `scripts/tests/bin/hub_promote.bats:1138` already runs
  `merge-tree --write-tree` in CI.
- `git()` (`:34-35`) wraps every call in `bash` + `source system.sh` with `timeout=10` and `text=True` (`:24-31`);
  `--remote` gives the whole hub run `TIMEOUT + 15` = 75 s (`:312-313`); repo-sync runs every 300 s
  (`scripts/etc/launchd/com.k3d-manager.repo-sync.plist.tmpl:13`). `--check` sets `K3DM_REPO_SYNC_CHECK=1` (`:357`) and
  marks the backlog unknown (`:212-225`), which reaches `carry_forward_promotable` (`:472-474`).
- `make hub-sync` runs `bin/k3dm-repo-sync >/dev/null && bin/k3dm-repo-sync --hub-summary` over ssh (`:312`) and must
  print exactly one line (`scripts/tests/bin/repo_sync.bats:622-630`); repo-sync's own status lines go to stdout
  (e.g. `:401`).

## Behaviour

1. **`content_contained(remote, sha, ctx) -> True | False | None`** in `bin/k3dm-repo-sync`. `ctx` is computed once per
   run: `hub_tree` = `git rev-parse <remote>/deploy/hub^{tree}` (must exit 0 and be a hex OID, else every call returns
   None) and `shipped_trees` = the set of `%T` from `git log --first-parent --max-count=50 --format=%T
   <remote>/deploy/hub`. Steps, in order:
   - **A (read-only):** `git rev-parse <sha>^{tree}` is in `shipped_trees` → True.
   - **B (writes objects; skipped when `K3DM_REPO_SYNC_CHECK=1` → return None):** `git merge-tree --write-tree
     --no-messages <remote>/deploy/hub <sha>` exits 0 with a non-empty first line equal to `hub_tree`, **and** the
     tip-delta guard `git merge-tree --write-tree --no-messages --merge-base=<sha>^ <remote>/deploy/hub <sha>` also
     exits 0 and equals `hub_tree` → True. `<sha>` with no parent → None. Exit 1 or a different tree → False.
   - Every git call here uses `timeout=CONTAIN_TIMEOUT` (`K3DM_REPO_SYNC_CONTAIN_TIMEOUT`, default 5). Catch
     `OSError`, `subprocess.TimeoutExpired` and `UnicodeDecodeError` → None. A per-run budget of 20 s (monotonic) and the
     first `TimeoutExpired` both disable further containment for the run (later calls return None). Containment never
     raises into the caller, so it can never set `promote_lookup_failed`.
2. **Sticky record.** New state key `promote_contained = {"sha": <full sha>, "branch": <upstream branch>,
   "deploy_hub": <full deploy/hub sha when recorded>}`. The state dict is rebuilt every run (`:372-374`), so copy the
   previous record forward explicitly, and only while still valid: same branch as `state["upstream_branch"]`, the
   recorded `deploy_hub` is an ancestor of (or equal to) the current `<remote>/deploy/hub` (a rollback invalidates it),
   and the recorded sha is an ancestor of `upstream_ref`. Otherwise drop it.
3. **`find_promotable`** (`:83-99`):
   - Range: `rev-list --max-count=10 <upstream_ref> --not <remote>/deploy/hub [<contained sha>]` (the record excludes
     the contained commit and all its ancestors). Empty range → `(None, False, False)`.
   - Walk newest first. For each candidate call `content_contained` first. **True → record it (Behaviour 2) and stop:
     return `(None, False, False)`** — never promote a contained commit or any ancestor of it; newer candidates were
     already evaluated as today. False/None → `is-green` exactly as today.
   - The return tuple and the unknown rule at `:99` are otherwise unchanged.
4. **`carry_forward_promotable`** (`:102-117`): after the existing ancestry checks pass, decline to carry when (a) a valid
   record exists and the prior sha is an ancestor of or equal to its sha, or (b) `content_contained(prior sha)` is True,
   or (c) `upstream_ref` is set and `content_contained(upstream tip)` is True (record it). Short-circuit (a) → (b) → (c).
5. **Log** on stdout only (never stderr), and only when a new record is created or its sha changes:
   `promotable: <sha7> on <branch> already in deploy/hub by content; ignoring it and older commits`.
6. `promote_backlog` (`:461-463`) keeps its ancestry meaning; after a squash it stays > 0 beside `promotable: none`
   until the hub checkout switches branch (documented, intentional).

Fixture: `scripts/tests/bin/repo_sync_promote_backlog.bats:4-77`. The upstream "release branch" is `main`; `deploy/hub`
is a separate ref; the real `bin/k3dm-hub-promote` is copied (`:70`) and `gh` is stubbed (`:43-50`). Add one line to
the `gh` stub: `GH_GREEN_ALL=1` answers success for every sha (existing behaviour unchanged when unset). Squash =
in `$SCRATCH/seed`: `git commit-tree <tip>^{tree} -p origin/deploy/hub -m squash` then push that sha to
`refs/heads/deploy/hub`. "Same file" = each release commit appends a line to `change`.

- **S1 (bug, tip-first stop):** 3 commits on `main` to `change`; `GH_GREEN_ALL=1`; squash the tip; run → no
  `k3dm_repo_sync_promotable{` in `$CURL_BODY`; `--hub-summary` says `promotable: none`; stdout has the log line once;
  a second run → still none and no log line.
- **S1b (window):** as S1 with 12 commits → `promotable: none`, not `unknown`.
- **S2 (sticky):** before the squash, push one unrelated commit (`other` file) to `deploy/hub`, so the squash tree ≠ the
  tip tree (Step A fails, Step B contains). Run → none and `promote_contained` recorded. Then push one more `deploy/hub`
  commit appending to `change` (overlapping hunk). Run → still none.
- **S2r (rollback invalidates):** after S2, force-push `deploy/hub` back to before the recorded `deploy_hub` → the
  record is dropped from `state.json`.
- **S3 (positive control):** after S1, push a new commit `N` changing `change` → `N` is published.
- **S4 (conflict):** an unshipped commit conflicting with a later `deploy/hub` change → published.
- **S5 (post-squash revert):** after S2, push `R` that reverts the last shipped change on `main` → `R` is published.
- **S6 (carry-forward; Fable shape):** run 1 publishes tip `T` (`GH_GREEN_SHA=T`); then squash `T` onto `deploy/hub`
  and push a new uncontained commit `N` to `main` with `GH_FAIL_SHA=N` → run 2: `promote_lookup_failed 1` (proves the
  carry path ran) and **no** promotable series. Positive control: same without the squash → `T` is carried.
- **S7 (error):** on the S2 fixture install, after setup, a `git` wrapper first on `PATH` that exits 128 when its
  arguments contain ` merge-tree ` (note `git()` passes `-C <path>` first) and records each hit → the tip is published
  as today, the wrapper was hit, `promote_lookup_failed 0`.
- **S8 (timeout):** `K3DM_REPO_SYNC_CONTAIN_TIMEOUT=1` and a wrapper that sleeps 3 s on ` merge-tree ` → published as
  today, `promote_lookup_failed 0`.
- **S9 (`--check`):** with a wrapper recording ` merge-tree ` calls, run `--check` with a prior `promotable_sha` →
  zero `merge-tree` calls.
