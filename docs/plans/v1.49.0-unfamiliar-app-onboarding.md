# v1.49.0 — Unfamiliar-app onboarding: can the platform run an app it has never seen?

**Filed:** 2026-10-11, Claude
**Status:** PROPOSED (operator, 2026-10-11: "sounds like a fun thing to try"). Not ready for Codex.
Scope it into implementation specs only after v1.47.0 ships; see **Timing**.
**Implementer:** Codex (generator, tests) · **Operator:** Bolt account, app repo, live runs · **Verifier:** Claude

## Why

Today the only proof that k3d-manager can operate an application is shopping-cart, and shopping-cart
was built alongside the platform. It fits the platform by construction. The v1.49.0 onboarding of
the TwinkleAI app (`docs/roadmap.md`, v2.0.0 track) has the same weakness: we will write it knowing
what the platform expects.

The honest test is a stranger: an app generated by a different AI tool (Bolt.new), exported to
GitHub, and handed to the platform cold. The question is not "can we deploy it" (we can, by hand).
It is **how many manual interventions it takes**, and which of them the platform can absorb.

## Targets

| Metric | Target | Notes |
|---|---|---|
| Manual interventions | **0**, long-term | Phase 0 measures the real number; each later phase must lower it |
| Deployment success | **100%** for supported app templates | an unsupported app must be refused with a reason, not half-deployed |
| Verification | **E2E: functional + operational** | the app works, and the platform can see it fail |

"Supported app template" is a named, tested shape, not "anything Bolt emits". Initial set:

1. Node/Next.js full-stack, optional Postgres
2. Static Vite front end + Node API, optional Postgres

Anything else is detected and refused at the start with `unsupported template: <reason>`.

## The pipeline under test

```
Bolt.new                        generate the real-estate application
   │
GitHub repository               unmodified source and dependency manifests (pinned SHA)
   │
AI onboarding agent             analyze application      detect dependencies
(Experiment B only;             generate deployment      generate test contracts
 skipped in A)                  configure secrets        configure observability
   │
k3d-manager → vCluster          build → deploy → scan → test → observe
   │
Evidence-based promotion gate   promote only after security and e2e checks pass
```

1. Bolt generates the app. Ask for a **self-contained backend** (Node API + Postgres). An app whose
   data lives in Supabase or Bolt's hosting leaves nothing to run but a static site. **A partial
   app is a valid input** (operator, 2026-10-11): Bolt's free tier caps at 300k tokens a day, and
   the experiment measures how much of an unfamiliar codebase the platform and agents can carry,
   not whether Bolt can finish one. The minimum per test: nothing for the code review and for
   Experiment A; for B, it builds and its server starts (one page and one API route answering); for
   generated e2e, a few real behaviours (a listing page, one API call, one DB read/write if there is
   a DB). If Phase I does not build, B records the agents' repairs as interventions.
2. Export the source to its own GitHub repo (operator; never into k3d-manager).

   **Pinned input (operator, 2026-10-12):** `wilddog64/twinkleai-real-estate-lab` at `56dab41`, as
   pushed. Bolt spent the day's 300k tokens on the export, so it stays partial; do not ask for more.
   Known at pin time:
   - Next.js 13.5 with a Netlify config, and two pages (listings, property detail).
   - No API routes and no database: data comes from `lib/demo-data.ts`. `@supabase/supabase-js`
     is a dependency but no code uses it.
   - The UI component push stops at `form`. `components/ui/form.tsx` imports
     `components/ui/label`, which is missing, so `next build` fails as pushed. That is a gap for A
     and an intervention for B, not a reason to re-export.
   - **Target (operator, 2026-10-12):** the question is "how easily does this deploy to the ACG AWS
     sandbox on the k3s infrastructure". Use the ACG k3s app cluster for the live run, not a
     Tier 1 vCluster (step 4 and phase 0b).
3. Claude analyses the repo and produces the deployment specs (step 3 output below).
4. k3d-manager deploys it into a Tier 1 vCluster.
5. Automated e2e, vulnerability scans and operational checks.
6. Promotion through the GitOps workflow. The v1.47.0 promotion gate applies unchanged; it is never
   weakened for this app.

## The five challenges

Each is a place where a generated app and the platform disagree. Each manual fix found in Phase 0
is logged against one of them.

### 1. Build — make it a signed image

Bolt does not write a Dockerfile, health endpoints or a non-root runtime. The platform supplies a
per-template Dockerfile (multi-stage, non-root, pinned base), builds in CI, and signs with cosign so
Kyverno admits it. Supply-chain rules from `CLAUDE.md` hold: pinned base tags, pinned Actions.

### 2. Config and secrets

Generated apps put keys in `.env` or inline. Step 3 lists every config read (`process.env.*`,
`import.meta.env.*`) and classifies each as plain config or secret. Secrets go to Vault and reach the
pod through an ExternalSecret; the generated repo must contain no secret value. A key found inline
in source is a **stop**, recorded as an intervention, not silently moved.

### 3. Deploy — GitOps and isolation

Own namespace (never `default`), Helm chart or kustomize generated from the template, an
ApplicationSet entry carrying `k3dm.k3d.io/rollout-stage`, small requests with memory limits,
NetworkPolicy default-deny plus the edges the template declares. Postgres, when present, is
included in the hub-data DR inventory.

### 4. Verification — functional and security

- Functional: the app has no test suite that fits the harness. Step 3 writes a minimal e2e contract
  (load the main page, one API round trip, one DB write/read) in the existing e2e format.
- Security: Trivy image scan with the existing critical/high thresholds; Kyverno admission.

### 5. Observability onboarding

Can k3d-manager configure health monitoring, metrics, logs and alerts for an app it does not know?
Split what the platform can do with **no app cooperation** from what needs the app's help, and
detect which case applies instead of assuming.

| Signal | Without app cooperation (always) | With app cooperation (detected) |
|---|---|---|
| Health | blackbox HTTP probe on the service; liveness/readiness on the port | readiness on `/healthz` or `/api/health` if it exists |
| Metrics | Istio RED metrics (rate, errors, duration) per service; cAdvisor CPU/memory; kube-state restarts | a ServiceMonitor when `/metrics` answers in Prometheus format |
| Logs | Loki by namespace/pod labels | parsed fields when the logs are JSON |
| Alerts | default rules per app: CrashLoop, ready replicas < desired, 5xx ratio, p95 latency, probe down | app-specific rules only from a declared file |
| Dashboard | generated Grafana dashboard from the template, RED + resources + probe | app panels from its own metrics |

Alerts follow the existing routing: email for sandbox, SMS only for hub and Hostinger
(`feedback_sandbox_alerts_email_only`).

**Operational verification** is the part that proves observability is real, not configured-looking:

- every generated dashboard panel has a producer with data (an empty panel is a missing producer, not
  a pass; see `docs/guides/grafana-dashboards.md`);
- fault injection: scale the app to zero, and the probe-down alert must fire and resolve; return 500s
  from a test route, and the 5xx alert must fire;
- the run records each check true/false, like the DR drill's V-checks.

## Step 3 output — what Claude produces

From the app repo, read-only:

- `onboarding/report.md`: detected template (or refusal), services, ports, config reads with the
  secret/plain classification, external dependencies, data stores, and a list of gaps.
- A PR to the **app repo** with the Dockerfile and health endpoint if absent, and the e2e contract.
- A PR to the **GitOps/k3d-manager side** with the chart values, ApplicationSet entry,
  ExternalSecret, NetworkPolicy, probes, ServiceMonitor (when detected), alert rules and dashboard.

Neither PR is auto-merged. The promotion gate decides.

## Intervention log

Every manual step between "export to GitHub" and "green e2e plus operational checks" is one line in
`onboarding/interventions.tsv`:

`timestamp  challenge(1-5)  what  why the platform could not do it  fix-class(platform|template|app|refuse)`

The count is the headline number. Each line ends as one of: a platform feature (generator, default
rule), a template change, a documented requirement on apps, or a refusal rule.

## Effort metrics — how much human help the agents need

Zero manual interventions is not success on its own: agents that reach a green deploy after hours
of retries have moved the cost, not removed it. Each run records, per experiment and per challenge:

| Metric | Why it matters |
|---|---|
| Human interventions (count, and minutes of human time per step) | agent autonomy |
| Agent repair attempts (per step: an agent re-running after its own failure) | remediation efficiency |
| Failed deployment attempts | how often the platform rejected the generated config |
| Time to first successful deployment, and total onboarding duration | onboarding speed |
| Time per pipeline step (analyze, generate, build, deploy, scan, test, observe) | where the time goes |
| Lines and files changed in the app repo and on the GitOps side | remediation scope (not difficulty) |
| First-pass e2e success rate (generated tests green on the first run) | generated test and app quality |
| Time to first green e2e (functional and operational) | the end-to-end number |
| Regression count (a repair that breaks a check that was passing) | whether repairs break behaviour |
| Manual configuration and secrets (each value a human had to supply) | what the platform cannot automate |
| AI tokens and cost, per agent and per step; Bolt tokens and plan tier for generation | the price of autonomy |

**Retry budget.** Each pipeline step gets a budget of agent attempts and wall time, fixed before
the run (start at 3 attempts and 30 minutes per step; Phase 0 calibrates). An exceeded budget
stops the step and counts as one intervention, even if a human then only says "continue". So
zero interventions reached through unbounded retries is not a pass.

Recorded in `onboarding/metrics.tsv` next to `interventions.tsv`, one row per step:
`experiment  step  challenge  start  end  attempts  human_minutes  tokens  cost_usd  files  lines  result`.

## Two experiments, same input

Both run against the **same Bolt export, pinned to one commit SHA**, so the difference between them
is attributable to the onboarding, not to a different app.

**Experiment A — unmodified Bolt output.** Give k3d-manager the repository exactly as Bolt produced
it, with no edits by a human or an agent, and record what happens. The expected result is a refusal
or a failure. That is the useful output: A measures what the platform can do **on its own**, and its
refusal report is the list of gaps, each tagged with one of the five challenges. A refusal with a
clear reason counts as correct behaviour. A half-deployed app, or a confusing error, counts as a
platform defect.

**Experiment B — AI-assisted onboarding.** Claude and Codex inspect the same repository, identify
its dependencies, generate the Dockerfile and manifests, wire Vault/ESO, and configure the e2e
contract and observability (step 3, then implementation). Every human action is an intervention,
including a prompt to an agent that corrects its own wrong output. B shows how far the agents close
A's gaps, and at what cost.

Recorded for both: interventions (by challenge), wall time, agent tokens and cost (B), deployment
result, and each functional and operational check true/false. **A's gap list minus B's remaining
interventions is what the agents actually contributed**; what remains after B is the platform's
backlog. Over the phases, the work should move from B into the platform, so that A's refusal list
shrinks and the target of 0 interventions becomes reachable without an agent in the loop.

## Phases

| Phase | What | Exit |
|---|---|---|
| 0a — analysis (any time, no cluster) | Bolt Phase I pushed and pinned; Claude's read-only step 3 report: template match or refusal, services, config/secret reads, dependencies, code-quality notes, gap list by challenge; a drafted e2e contract against the real routes | the gap list and e2e draft; input to v2.0 scoping |
| 0b — baseline deploy (after v1.47.0) | Experiment A, then Experiment B into a vCluster, same pinned SHA; every step logged with the effort metrics | A's refusal list, B's honest intervention count and effort numbers, the five challenges confirmed or corrected |
| 1 — generator | `make app-onboard REPO=<url>` produces step 3's report and both PRs for the two templates; BATS-stubbed | Phase 0 app re-onboarded with fewer interventions |
| 2 — observability | the challenge-5 defaults and the fault-injection checks | all operational checks true for the Phase 0 app |
| 3 — second app | a different Bolt app of the other template, run cold | count compared with Phase 0; target trend toward 0 |

TwinkleAI's v1.49.0 onboarding then runs through the same generator, so it becomes the third data
point rather than a hand-built special case.

## Open questions

1. Which Bolt prompt reliably yields a self-contained backend? Phase 0 records the prompt used.
2. Where does the generated chart live: the app repo, or k3d-manager's ApplicationSet values? Decide
   in Phase 1, the same way for TwinkleAI.
3. If Bolt generates a **real-estate** app, how does it relate to the TwinkleAI app (own repo,
   Codex-built from the operator's plan, M1–M4)? Options: (a) the Bolt app is a throwaway probe that
   only shares the domain; (b) Bolt seeds TwinkleAI M1 and the Codex plan continues from it. (a)
   keeps the experiment clean, because the A/B result is not tangled with the app's own roadmap.
   Recommendation: (a), firmly. The operator's Bolt project is `twinkleai-real-estate-lab`
   (2026-10-11); the name is fine, but it lives in its own repo, holds no LLM or TwinkleAI keys,
   is pinned once for the A/B, and is never promoted into TwinkleAI's codebase.
4. Is Istio sidecar injection on for the app namespace by default? Challenge 5's "no cooperation"
   RED metrics depend on it.

## What NOT to do

- Do not let generated config weaken an existing guard (promotion gate, Kyverno, NetworkPolicy,
  pinned images) to make an app pass. A refusal is a valid outcome.
- No secret value in either generated PR or in the intervention log.
- Do not commit the Bolt app into k3d-manager; it lives in its own repo.
- Do not deploy anything before v1.47.0 ships.
