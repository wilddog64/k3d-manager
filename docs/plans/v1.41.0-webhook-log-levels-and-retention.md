# v1.41.0 — Webhook log levels, make-job logs, log retention, and failed-job notes

**Branch:** `k3d-manager-v1.41.0`
**Status:** DONE — M1 `3f7cf103`, M2 `73d0ef56`, M3 `dc5211de`, M4 `f1d0ec5d`, follow-up `cd20fc1b` (Claude-verified 2026-10-03)
**Requested by:** CK, 2026-09-28 ("we need log levels … and a retention policy to keep disk space lean")
**Related:** `docs/bugs/2026-09-28-make-jobs-never-write-output-file.md`,
`docs/plans/v1.40.0-cloud-request-artifacts.md`

## Problem

A live cloud request on 2026-09-28 showed how little the M4 keeps:

- **No log levels.** `bin/k3dm-webhook` writes with 17 bare `print()` calls and
  `bin/k3dm-cloud-bridge` with one. There is no way to turn detail up while debugging or down
  when things are quiet. The per-request line is switched off entirely
  (`log_message(self, *_)` is a no-op), so `~/Library/Logs/k3dm-webhook.log` does not show which
  requests arrived.
- **No make-job log.** `_run_make_target` (`scripts/lib/webhook/lifecycle.py:82`) captures the
  full output in memory, posts the last 40 lines to Slack, and drops it. The job folder holds
  only `status`.
- **No retention.** Nothing prunes `~/.local/share/k3d-manager/webhook-jobs/`. `_running_cluster_job`
  (`bin/k3dm-webhook:538`) walks and stats every job folder on each cluster request, so the cost
  grows with history. The twelve `~/Library/Logs/k3dm-*.log` files written by launchd agents are
  never rotated.

## Approach

Three milestones, each shippable alone. All of it runs on the M4. Nothing here changes what the
bridge returns to a cloud session.

### M1 — log levels

New module `scripts/lib/webhook/log.py` on stdlib `logging` only:

- `get_logger(name)` returns a logger writing one line per record to stderr, formatted
  `2026-09-28T13:14:32Z LEVEL name message`, in UTC.
- The level comes from `K3DM_LOG_LEVEL`: `error`, `warn`, `info` (default) or `debug`,
  case-insensitive. An unknown value falls back to `info` and logs one `warn` saying so. It never
  crashes the webhook.
- Levels mean:
  - `error`: a request or job failed in a way the operator must act on.
  - `warn`: degraded but continuing (a Slack post failed, a stale job was marked failed).
  - `info`: one line per HTTP request (method, path, status code, role, duration in ms), and
    one line per job start and end (job id, action or make target, final status, rc).
  - `debug`: adds the job's argv (after `_args_have_sensitive_flag`-style masking), the
    bridge's per-tick summary, and timings of subprocess calls.
- **Never logged at any level:** request bodies, headers, bearer tokens, Keychain values,
  Slack `response_url`, or make output. The request line logs the route template
  (`/api/v1/status/{job_id}`), not the raw path with the id, when the route is known.

Convert every `print()` in `bin/k3dm-webhook`, `bin/k3dm-cloud-bridge` and
`scripts/lib/webhook/auth.py` to the logger at the level that matches its meaning. Replace the
no-op `log_message` with the `info` request line. Add `K3DM_LOG_LEVEL` to the webhook and
cloud-bridge launchd templates (default `info`) and a `make webhook-log-level LEVEL=debug`
helper that rewrites the plist value and restarts the agent.

Hermes and the shell plugins are out of scope for M1. They can adopt the module later.

### M2 — make-job log on the M4 only

Close the local half of `docs/bugs/2026-09-28-make-jobs-never-write-output-file.md`: in
`_run_make_target`, write the full output to `JOB_DIR/<job_id>/make.log`, capped at the last
1 MiB, before `status` is written.

It is named `make.log`, not `output`, on purpose. The `job-status` handler returns `output`, and
the bridge commits whatever `job-status` returns to the `cloud-requests` branch permanently.
Publishing make output to cloud sessions stays with the artifacts spec's redaction filter. That
spec, not this one, decides when `output` is written for make jobs.

While the job runs, post progress to the job's Slack thread every 120 seconds, the same way
cluster lifecycle jobs already do (`_post_progress` in `_run_cluster`,
`scripts/lib/webhook/lifecycle.py:171`): elapsed minutes plus the last lines of `make.log`.
This means `make.log` is written as the job runs (spawn to a file, as `_run_cluster` does with
`_posix_spawn_job`), not after it ends. Cancel the timer when the job finishes. Make jobs have
never had this; they were added in v1.34.0 with a single end-of-job post.

Add `make job-log ID=<job_id>` to print `make.log` for a job (operator-only, not in
`MAKE_TARGETS`, not reachable from Slack or the bridge).

### M3 — retention

Extend `bin/k3dm-cleanup`, which already runs daily at 03:00 through
`com.k3d-manager.cleanup` and already follows the `K3DM_*_RETENTION_DAYS` pattern:

- **Job folders:** delete folders under `JOB_DIR` whose `status` is not `running` or `queued`
  and whose mtime is older than `K3DM_JOB_RETENTION_DAYS` (default 14). Separately, keep at most
  `K3DM_JOB_RETENTION_MAX` (default 500) finished folders, oldest first out. Never touch a
  `running` or `queued` folder, whatever its age.
- **launchd logs:** for each `~/Library/Logs/k3dm-*.log` over `K3DM_LOG_MAX_MB` (default 10),
  copy it to `<name>.1.gz` (shifting `.1.gz` to `.2.gz` and so on), then truncate the original in
  place. Keep `K3DM_LOG_KEEP` (default 5) generations. Truncate rather than move, because launchd
  holds the file open in append mode and a moved file would keep receiving writes.
- Print one summary line per category (`k3dm-cleanup: pruned 37 job folders, rotated 2 logs,
  freed 48 MiB`) so the cleanup log itself shows what retention did.

No `newsyslog` config: it needs root under `/etc/newsyslog.d`, and the cleanup agent already
runs as the user.

### M4 — failed-job notes in the prior-art index

CK, 2026-09-28: raw logs stay out of the vector store (noisy, high churn, can carry secrets, and
M3 deletes them), but a short redacted note per **failed** job is worth indexing, so
`find-similar-docs` can answer "has this target failed like this before, and what fixed it?".

The index only reads files tracked in git (`iter_corpus` runs `git ls-files` over
`CORPUS_GLOBS`, `scripts/lib/hermes/prior_art.py:31`), so a note must be committed to be found.
The webhook must not commit to the repo, so this is split into a write step and a harvest step.

**Write (webhook, automatic).** When a make job or cluster job ends `failed`, write
`JOB_DIR/<job_id>/failure.md`:

```markdown
# Job failure: make <target> (<job_id>)

**Date:** <UTC date>  **Target:** <make target or cluster action>  **Result:** failed (rc N) | timed out after Ns
**Signature:** <target>: <error line>

## Error

<error line>

## Fix

(unknown — fill in when resolved)
```

The error line is the last line of the job's log matching `error|fail|fatal|traceback|exception`
(case-insensitive), or the last non-empty line if none match, capped at 300 characters. It goes
through the redaction filter from `v1.40.0-cloud-request-artifacts.md` M2 before it is written.
If that filter has not landed, M4 is blocked. Do not ship an unredacted note, because the note is
headed for git.

**Harvest (operator, on demand).** `make harvest-job-failures` walks `JOB_DIR` for
`failure.md` files not yet harvested and copies each to
`docs/job-failures/<date>-<target>-<job_id>.md`. Dedup works like the repo's bug-filing rule: if
a file with the same **Signature** already exists, append a `- <date> (<job_id>)` line under a
`## Recurrences` heading instead of creating a second file. It prints what it added and changed
and stops. The operator (or a Claude session) fills in `## Fix` and commits. Mark harvested
folders with an empty `harvested` file so reruns are no-ops.

Add `"docs/job-failures/*.md"` to `CORPUS_GLOBS`. Notes are small and live in git, so M3's
retention does not apply to them. A folder whose `failure.md` was never harvested is still
pruned after 14 days, and the harvest target's output says how many notes are waiting.

## Tests

- **M1** (`scripts/tests/bin/test_webhook_log.py`): each of the four levels filters as specified;
  an unknown `K3DM_LOG_LEVEL` falls back to `info` with one warning; the request line for a
  request carrying `Authorization: Bearer <x>` and a JSON body contains neither `<x>` nor the
  body; the route template replaces the job id. A grep gate:
  `command grep -c 'print(' bin/k3dm-webhook bin/k3dm-cloud-bridge` returns `0` for both.
- **M2**: a stubbed make job leaves its output in `make.log` and not in `output`; `job-status`
  for that job still returns `"output": ""`; output over 1 MiB keeps the tail.
- **M3** (BATS against a temp `JOB_DIR` and temp logs dir): old finished folders go; a 30-day-old
  `running` folder stays; the count cap removes the oldest first; an 11 MiB log becomes
  `.1.gz` plus an empty original with the same inode; `.6.gz` never exists with the default keep.
- **M4**: a failed stubbed job writes `failure.md` with the matched error line; a successful job
  writes none; a synthetic token in the log comes out `[REDACTED]` in the note; harvesting twice
  adds one file, not two; a second failure with the same signature appends a recurrence line
  instead of a new file; `iter_corpus` picks up a tracked `docs/job-failures/*.md`.
- **Mutations:** drop the `running` guard and the stale-running test fails; write `output`
  instead of `make.log` and the M2 `job-status` test fails; skip the redaction call and the M4
  token test fails; remove the header masking and the
  M1 token test fails.

## Out of scope

- Publishing make output to cloud sessions (the artifacts spec and its redaction filter own it).
- Growth of the `cloud-requests` branch itself. It is an orphan branch of small JSON files. If it
  needs pruning, that is its own spec, because it rewrites a shared branch.
- Hermes, shell plugins, and Kubernetes pod logs.
- Shipping logs anywhere (Loki, Grafana). This is local hygiene only.

## Defaults chosen without asking (change any of them here before implementation)

`info` level by default; job folders kept 14 days, at most 500; launchd logs rotated at 10 MiB,
5 generations kept; `make.log` capped at 1 MiB.
