## Why rev 1 was replaced

Rev 1 proposed Ed25519 request signing with a key per agent. A cloud session holds no credential by policy
(`docs/howto/cloud-session-requests.md`, "The short version"), so a cloud agent's key would sit next to its GitHub token and a stolen
session would get both. The operator chose an approval gate (2026-11-25).

A GitHub ruleset limiting who can push `cloud-requests` was dropped: `git log origin/cloud-requests -200` (2026-11-25, M4) shows every
commit authored as the operator (`chengkai liang` 118, `chengkai` 58, `t` 24; none signed), so a ruleset cannot tell sessions apart.

## Threat model

- **Attacker:** anyone who can push `cloud-requests` (a cloud session, a leaked token with repo write, a misbehaving agent). The repo is
  public; everything on the branch, including `ledger/` and `responses/`, is public and attacker-writable.
- **Asset:** the cloud-runner set, which today runs on push alone: `sandbox-up`, `sandbox-down` (provider fixed to `aws`; cost money),
  `make-e2e`, `make-e2e-remote` (`scripts/lib/webhook/cloud_actions.py:21-22,38-39`; token choice `bin/k3dm-cloud-bridge:332`).
- **Goals:** (1) no cloud-runner request reaches the webhook, or reads the cloud-runner token, without an operator Approve on a card
  showing that exact request, before it expires; (2) each approval runs its request at most once; (3) a pusher cannot stop the bridge
  answering reader requests, and cannot keep the operator from approving a real request for longer than one Deny press per slot.
- **Not in scope:** the webhook's own auth; Slack account takeover (the relay requires the approver allowlist and a fresh
  `/hermes-auth` per press, `workers/slack-relay/index.js:267-275`); a second bridge on another host (only the hub runs one).

## Design

1. **One bridge.** At startup the bridge takes an exclusive `fcntl.flock` on `STATE_DIR/bridge.lock` for its lifetime; a second instance
   exits 1 with one stderr line (precedent `bin/k3dm-dispatch-recover:155-161`).
2. **Gate.** One predicate `gated(action)`: true exactly for actions using the cloud-runner token. The token choice at `:332` calls it.
   A gated request that passes `prepare_request` is not sent; it becomes a pending approval.
3. **Pending approval.** Stored in `STATE_DIR/approvals.json` (0600, atomic replace; path resolved at call time). Record: request id,
   approval id `c1-<8 hex>`, 16-hex nonce, the validated request as parsed, `created_at`, `expires_at` (request's `expires_at`, any
   offset, normalised to epoch; at most now + 30 min), and `notice_published`. Admission refuses a request with under 5 minutes left,
   more than 3 pending, or more than 10 cards in a rolling hour.
4. **Card.** `interactive_blocks` + `post_interactive` (`scripts/lib/hermes/approvals.py:62`, `scripts/lib/hermes/slack.py:47`) to the
   relay URL in Keychain `k3dm-slack-webhook`. Shows request id, action, arguments, a fixed blast-radius line per action, expiry, and
   `requested_by` (only if it matches `^[A-Za-z0-9._@:-]{1,64}$`, else `(invalid)`, always in a code span) labelled not verified.
5. **Relay.** For `c` ids only, the relay records both decisions (`decision: approve|deny`), keeps the first decision for an id, and
   returns `decision` in the drain listing. `r` and `d` behave exactly as today.
6. **Drain and decide.** While any record is pending, at most once per 30 s, the bridge drains `^c[0-9]+-[0-9a-f]{8}$` approvals
   (`fetch_approvals`/`delete_approval`, `approvals.py:26,47`; drain URL `K3DM_HERMES_APPROVAL_DRAIN_URL`, token Keychain
   `k3dm-hermes-approval-drain-token`). For each decision in turn: remove the record and save the store, then act. Approve with matching
   nonce: recheck `time.time() < expires_at` immediately before reading the token; run the **stored** request through the existing path.
   Deny with matching nonce: reject `denied by the operator`. Wrong nonce or unknown id: delete the approval, keep the record. Past expiry:
   reject `not approved before the request expired`. Hermes (`r`) and dispatch-recover (`d`) filter by their own prefixes.
7. **Responses.** While pending, the bridge commits `responses/<id>.pending.json` (status `ok`, body `{"status": "approval-pending",
   "approval_id", "expires_at"}`; never the nonce), retried each tick until `notice_published`, never through the outbox, never
   recording the id as processed, never reposting the card. The final answer is the normal `responses/<id>.json` via the outbox.
   Status values stay `ok`, `rejected`, `error`.
8. **Fail closed.** Missing drain URL, drain token or relay URL, or an unreadable store: a gated request is rejected at once; on an
   unreadable store, orphan recovery is skipped for that tick. Reader requests are never rejected for approval reasons.
9. **Watch ledger (b1).** `_read_watching` validates every field; a bad line is skipped, not fatal. The lifecycle watch timeout is chosen
   explicitly. Watched terminal output gets the same `scrub_credentials` pass as direct `job-status`.

## Contract between the children

| Name | Owner | Readers |
|---|---|---|
| `scripts/lib/webhook/cloud_approval.py` API (child a spec) | a | b |
| Drain item shape: `action_id`, `approved_by`, `approved_at`, `nonce`, `decision` (`approve`/`deny`; missing means `approve`) | c | a, b |
| `responses/<id>.pending.json` shape (design 7) | b | d, e |
| Approval id `^c[0-9]+-[0-9a-f]{8}$`, nonce `^[0-9a-f]{16}$` | a | b, c |
| Rejection reasons (below) | b | d, e |
| `K3DM_HERMES_APPROVAL_DRAIN_URL` in the bridge plist | b | e |

Rejection reasons (exact `reason` text): `operator approval is not configured on the bridge`, `approval state is unreadable on the bridge`,
`too many requests awaiting approval; try again later`, `request expires too soon for approval; file it with at least 5 minutes left`,
`approval card not delivered; file a new request`, `denied by the operator`, `not approved before the request expired`.

## Residuals

- R1: the relay lists at most 50 KV items (`index.js:222`); stale `r`/`d` items could hide a `c` decision until they expire (1 h).
- R2: the card's confirm title from `interactive_blocks` reads "Approve repair?" (`approvals.py:75`); changing it touches a file shared
  with Hermes and dispatch-recover.
- R3: KV has no compare-and-set: two presses within milliseconds could both be stored; the bridge treats any Deny for an id as winning.
- R4: a pusher can still hold the 3 slots; the operator frees each with one Deny press. `requested_by` stays unverified.
