## Problem

The Plans table shows each plan's Order and its declared `**Depends on:**` plans. It does not show
how the release will actually run:

1. **Which plans can run together.** On v1.43.8 as first filed, release duration, Slack routing
   and the snapshot schedule shared no files and could be dispatched at once, while Claude
   cost-by-reference had to wait for release duration. The table shows Order 1–5, which reads as a
   sequence.
2. **Timing constraints.** Plan 5 (Hostinger edge) should run only after the 2026-10-29 hub
   rebuild. That is a window, not a plan, so it cannot go in `Depends on`, and today it lives only
   in the roadmap prose.
3. **Missing dependencies.** Until 2026-10-25, the release-duration and Claude cost-by-reference plans both listed
   `bin/k3dm-dispatch-metrics` and the Agent Dispatch dashboard in `**Component:**` with no
   `Depends on` between them. Nothing flagged it; Claude found it by reading the specs.
4. **Dependencies are not actionable.** The Plan cell links to its spec; the Depends on cell links
   nowhere, and nothing says *why* a plan cannot be dispatched yet.
5. **Approval is ambiguous.** `_plan_approval` returns `explicit` for every `**Approval:**` line
   that does not start with "pending". "Approved to file spec — dispatch not yet approved" therefore
   shows `explicit`, which reads as authorisation to execute.

## Scope and design

### W1. Wave column, derived from dependencies

- For each plan, Wave = 1 when it has no `Depends on` plan in the same release. Otherwise Wave = 1
  plus the highest Wave among its same-release dependencies. Dependencies on other releases do not
  change the Wave; they stay in Depends on.
- A dependency cycle within a release shows Wave `cycle` for every plan in it.
- Plans not yet assigned a plan order (no `**Release:** … (plan N of …)`) keep the current
  behaviour and show `-`.

### W2. Optional `**Wave:**` header for timing constraints

- Format: `**Wave:** <n> — <reason>`, for example
  `**Wave:** 3 — after the 2026-10-29 hub rebuild`.
- A declared Wave may only move a plan **later** than its derived Wave. If it is lower, the table
  shows the derived Wave and the Wave note says `declared <n> < required <m>`.
- The reason is shown in a **Wave note** column. It is sanitised like the title (quotes,
  backslashes and control characters removed) and capped at 80 characters.

### W3. Undeclared overlap column

- Each plan's files are the backticked paths on its `**Component:**` line (the body is not read; it
  mentions files for context, which would be noise). A path ending in `/` matches every path under
  it.
- Two plans in the same release **overlap** when they share a file and neither depends on the
  other, directly or through other plans.
- An **Overlaps** column lists them as `plan <n>: <file>`, at most three, then `+<k> more`. Empty
  shows `-`.
- A per-release count, `k3dm_plan_undeclared_overlaps{repo,release}`, backs a small stat beside the
  Plans table so a nonzero count is visible without scrolling.

### W5. Two approvals: spec and dispatch

- The Approval column is replaced by two columns:
  - **Spec approval** (from `**Approval:**`): `approved`, `pending`, `none`, or `n/a` before
    v1.43.2. Same rule as today, renamed from `explicit` to `approved`.
  - **Dispatch** (from a new `**Dispatch:**` header): `go`, `needed`, `not required` or `unknown`.
    Format: `**Dispatch:** go 2026-10-24 — operator, "<quote>"`, `**Dispatch:** needed — <why>` or
    `**Dispatch:** not required — <why>`.
- The legacy prose inside `**Approval:**` ("dispatch not yet approved", "**Dispatch go**") is
  **not** parsed. A plan with no `**Dispatch:**` header shows `unknown`, never `go`.
- Before dispatch, Claude adds `**Dispatch:**` headers by hand to every plan in the open releases
  (v1.43.8 to v1.43.10) from their existing approval prose, quoting the operator. Closed releases are
  not backfilled.

### W6. Actionable dependencies and a Blocked by column

- The Depends on cell links to the dependency's spec on the scanned branch. When a plan has several
  dependencies, the cell lists all of them and links to the first. A Grafana cell has one link
  target, and a fake per-dependency menu would show empty entries.
- A **Blocked by** column applies to plans whose execution is `proposed` or `ready`. It lists the
  first applicable reasons in this order:
  1. `branch not cut` — no `k3d-manager-v<release>` ref exists locally or on `origin`;
  2. `plan <n> not landed` — a same-release dependency whose execution is not `implemented`
     (cross-release dependencies use the stem);
  3. `dispatch go needed` — Dispatch is `needed`;
  4. `wave note` — a `**Wave:**` header is present (its reason is in Wave note; the scan cannot
     judge a date window, so it says so rather than guessing).
- A plan with no reason shows `ready to dispatch`. A plan with Dispatch `unknown` shows
  `dispatch approval unknown`, never `ready to dispatch`.

### W7. Docs

- `docs/guides/grafana-dashboards.md` explains Wave, Wave note and Overlaps, and how to clear an
  overlap: add `Depends on`, or accept it by listing the overlap in the plan's body (it stays
  flagged, by design).
- The plan-filing guidance says to keep `**Component:**` complete, because overlap detection reads
  only that line.

## What NOT to Do

- Do not read plan bodies for file paths; only the `**Component:**` line.
- Do not infer dependencies from overlaps; overlaps are shown, never turned into Depends on.
- Do not change Order, Depends on's text or Execution's meaning.
- Do not parse dispatch approval from `**Approval:**` prose.
- Do not mark anything ready to dispatch on missing data.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
