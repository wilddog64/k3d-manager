## Problem and evidence

Cloudflare analytics reports 7,360 historical HTTP 502 responses and high-volume 302 redirects across seven public hostnames. Cloudflare's assistant attributes them broadly to edge/tunnel/origin connectivity, but aggregates alone do **not** establish the 502 hostname distribution, origin versus edge response, root cause, duration, or overlap with prior incidents. Country attribution and the claim that all 302s are Keycloak redirects are hypotheses, not observed causes.

The 2026-10-20 incident already demonstrates a useful diagnostic pattern: frontend returned five consecutive 502s while six other public endpoints passed; Hostinger Kubernetes API requests timed out from M4; the initial cloud diagnostic incorrectly reported success despite kubectl failure. Later recovery did not prove the precise failed network segment. The existing v1.43.10 edge plan removes the M4 dependency for the Hostinger frontend but must not be conflated with diagnosis of every historical 502.

Current monitoring has important blind spots: hub-hosted probes cannot detect their own hub's outage, authenticated probes may accept 401 without verifying backend functionality, and healthy 302 responses may conceal redirect loops. Evidence can disappear during self-recovery.

They cannot both be treated as the same complete error population. Query provenance, time range, sampling/extrapolation, status filters, hostnames, and edge-vs-origin definitions must be reconciled. Do not calculate a 502 rate or infer attack/availability severity from either number until scope is established. If the source cannot reconcile them, label the totals contradictory and preserve both as unverified operator-provided summaries.

**Correlation caveat:** the Oct 22 502 date aligns with an independently documented M4/Hostinger tunnel interruption, but same-day matching is not same-minute proof. Existing incident notes describe port-forward drops and a healthy Hostinger uplink; no claim of an ArgoCD deployment failure or compromised laptop is supported by these counts.

**Deployment-aware diagnostics:** the primary public `cloudflared` connector is a macOS launchd process on M4, **not** a `cloudflared` pod in the hub Kubernetes cluster. A generic `kubectl logs -l app=cloudflared` command would be inappropriate until the separately planned Hostinger in-cluster edge exists. Use the configured launchd unit and its timestamped logs; identify the live topology before selecting commands.

**Five historical replay fixtures:** create separate UTC-window fixtures for Oct 1 (530), Oct 5 (530), Oct 18 (500), Oct 21 (524) and Oct 22 (502), carrying source provenance and intentional unknown fields. The Oct 22 replay additionally correlates the known tunnel/port-forward incident. Include a contradictory-summary fixture with both 7,360 and 160, and a negative fixture where the 502 peak does *not* align with a Kubernetes deployment. Pass means reporting hypotheses with coverage and contradictions, not claiming that a particular error proves a pod restart, connector crash, attack, or specific root cause.

**Collection checklist:** before adding new probes, request the smallest permitted Cloudflare aggregation by UTC hour, hostname, edge status, origin status and sample class; compare Prometheus `probe_http_status_code`/`probe_success` and their sample timestamps, M4 launchd/cloudflared/SSH/port-forward records, Alertmanager firing times, Hostinger API availability, and ArgoCD deployment history. Record which sources lack historical retention. Preserve raw event timestamps without rounding them to days for causal claims.

## Goals

1. Build reproducible, **read-only**, time-correlated investigations triggered by public endpoint alerts or operator requests.
2. Separate observed facts, candidate failure domains, contradictory evidence, unknowns, and confidence; never assert a root cause from status code alone.
3. Capture a durable, bounded evidence bundle while incidents are active and allow historical replay when retained data exists.
4. Reuse Hermes, existing blackbox metrics and cloud-bridge read-only diagnostics rather than replacing the current alerting stack.
5. Surface diagnostic timelines and telemetry coverage in Grafana, with links to a safely redacted investigation report.
6. Keep remediation outside the first implementation. No repair action is authorized by this spec.

## Architecture

### A1. Event and evidence contract

Normalize `incident_id`, `start/end UTC`, `hostname`, `http_status`, `edge_status`, `origin_status` (when supported), `source`, `observed_at`, `ingested_at`, `freshness`, `collection_result` and `evidence_ref`. Use window boundaries and UTC everywhere; preserve original time zone/offset in provenance. Unknown must be `unknown`, not zero.

Record the source's retention, sampling, aggregation and completeness. Cloudflare Ray IDs may be retained only in a bounded, access-controlled incident artifact if permitted, never as Prometheus labels. No raw cookies, authorization headers, user IPs, URLs with secrets or request bodies.

### A2. Supported collection

- **External edge:** establish first whether the account permits an official, documented Cloudflare analytics/API query for errors by hostname, time bucket and edge/origin status. Minimum privileges; avoid browser scraping or undocumented endpoints. If unavailable, explicitly record `unsupported` and allow operator-provided aggregate snapshots with limited evidentiary weight.
- **Public path:** existing Prometheus blackbox series (`probe_success`, `probe_http_status_code`) plus per-endpoint probe freshness, one-time on-demand read-only requests within strict timeout and rate caps.
- **Tunnel/M4 path:** cloudflared connectivity and connector restart logs where collected; M4-to-Hostinger API/port-forward failures, process liveness and connection-state facts. Do not assume a healthy M4 if its sensor stops reporting.
- **Origin:** Hostinger node/Kubernetes API reachability, service endpoints, pod readiness/restart events, Istio gateway/proxy status and permitted error aggregates; distinguish command transport failure from a successful diagnosis.
- **Independent vantage:** where feasible, use an outside-hub probe. Failure of the hub-hosted blackbox alone is not an external outage verdict.

All probes and queries must have allowlisted actions, bounded time windows, safe output lengths, rate limits and timeouts. Reuse credential-bound cloud-bridge reader permissions; never broaden role ceilings or provide a generic command-execution escape hatch.

### A3. Correlation and hypothesis engine

Use deterministic classification before any LLM summary. Rule examples:
- Seven hosts fail together and tunnel connector reports disconnected: candidate shared tunnel / ingress failure.
- Frontend fails while six hosts pass, with M4 API timeouts: candidate frontend-specific M4-to-Hostinger path failure.
- Edge healthy and origin explicitly returns 502: candidate origin-side gateway/app failure.
- Pods ready while public status fails: route/network failure plausible, not proven.
- Missing probe samples: monitoring coverage failure, not a passing probe.
- Repeated redirects: flag possible loop, require bounded redirect-chain evidence before labeling auth normal.

Report candidate causes ranked as `supported`, `possible`, `contradicted`, or `insufficient evidence`, together with source evidence and missing checks. Do not fabricate numeric confidence scores. Separate correlation from causation; no definitive cause without discriminator evidence. LLM narrative is optional, clearly secondary, and grounded in collected records.

### A4. Trigger, retention and interfaces

Hermes starts a bounded investigation on `PublicEndpointDown`, `CloudflareTunnelDown`, or explicit operator request. Deduplicate repeated alerts per incident/window and avoid recursive triggers. Collect one small immediate bundle, then optionally bounded follow-up checks while incident persists; enforce a collection budget and cooldown. On failure, persist partial findings and error statuses without disrupting Hermes or Alertmanager.

Use the existing incident/ledger conventions; generate a machine-readable JSON artifact and a short Markdown report. Redact and cap output, with a retention policy and file permissions reviewed before implementation. Store low-cardinality counts, age and status in Prometheus; keep host/time-series detail in existing blackbox metrics, not in unbounded labels. Link Grafana panels for affected endpoints, evidence freshness, observed failure domain and incident timeline. Preserve existing dashboards/alerts.

### A5. Dependencies and release boundary

This enhancement **complements**, not replaces, the v1.43.10 Hostinger public-path redesign. Validate correlation rules against the Oct 20 incident before and after any edge migration; a network topology change updates route facts, not historical evidence. Reuse existing diagnostic result-classification fixes. Confirm current repository interfaces and live deployment before writing code; do not assume the Cloudflare account supplies full historical HTTP request logs.
