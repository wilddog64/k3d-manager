**Status:** QUEUED for v1.37.0. Do not implement during v1.36.0.
**Filed:** 2026-09-22
**Target:** `scripts/plugins/ldap.sh`, `Makefile`, `docs/howto/rotate-service-credentials.md`

> Requested as "v1.34.0". That milestone is **shipped** (tag `v1.34.0` exists) and already at
> the 5-plan-doc cap, so a spec filed there could never be implemented. Retargeted to v1.37.0,
> which had 1 plan doc. This makes 2.

## Why

On 2026-09-22 `make show-service-passwords` reported all three realm SSO users
(admin/developer/operator) as unavailable. The accounts were fine — `ldapsearch` on
`ou=users,dc=home,dc=org` returned all three with working passwords. What was missing was the
**Vault plaintext copy** at `secret/keycloak/users/*`.

Cause: `bin/cluster-up` Step 10d.5 (`:1018-1072`) is the **only** writer of that plaintext. The
hub was rebuilt with `make up`, which does not run `bin/cluster-up`, while OpenLDAP's
`local-path` PV survived. So the LDAP entries persisted and the Vault records did not.

This was repaired by hand (see `memory-bank/progress.md`, 2026-09-22), but the repair required
writing a throwaway script that duplicated Step 10d.5's logic, because **there is no reachable
entry point** for it. The defect is not the missing records — it is that the only way to restore
them is a 14-step cluster bootstrap or a hand-rolled script.

`docs/howto/rotate-service-credentials.md:151-155` already documents the trap
("written only by `bin/cluster-up` … so a hub rebuild never restores it") and offers no remedy.
This release supplies the remedy.

**It will recur.** Every future `make up` hub rebuild reproduces the same split state.

## Requirements

### 1. `ldap_reseed_realm_users` — new public function in `scripts/plugins/ldap.sh`

Reseed the three realm SSO users' passwords into **both** LDAP and Vault.

Home is `ldap.sh`, not `keycloak.sh`, because the mutation is `ldappasswd` against the OpenLDAP
pod and `ldap.sh` already owns the pod-lookup and `ldappasswd` idioms (`_ldap_sync_admin_password`,
`:836`). See the lazy-load constraint below — this choice is load-bearing, not cosmetic.

Behaviour per user, and this split is the point of the feature:

| Vault record | Action | Rotates? |
|---|---|---|
| **present** | re-apply Vault's existing value to LDAP | **No** — repairs drift, saved logins survive |
| **absent** | generate, write to Vault, apply to LDAP | **Yes** — unavoidable; LDAP stores only hashes |

The non-rotating branch is the valuable half and must not be skipped as an optimisation. It
mirrors the Prometheus recovery precedent (`observability.sh:264-340`, which logs
`recovered … not rotating`). Log the two cases distinctly so the operator can tell from the
output whether anything rotated. When it does rotate, say so loudly — anything holding the old
`developer`/`operator` password breaks.

Every user must be verified with `ldapwhoami` after the change. A set that cannot be verified is
a failure, not a warning: count failures, report which users, and return non-zero — matching
Step 10d.5, which refuses to write its checkpoint on any verification failure.

### 2. `make reseed-realm-sso-users` — the reachable entry point

A Makefile target invoking the function through `./scripts/k3d-manager`. This is what the
operator runs after a hub rebuild, and what `make show-service-passwords` points at when records
are absent.

Update the hint added in `80970c04` (`Makefile:572`) to name this target instead of
`bin/cluster-up Step 10d.5`, once the target exists.

### 3. `bin/cluster-up` Step 10d.5 delegates to the function

Step 10d.5 must call `ldap_reseed_realm_users` rather than keeping its own copy. Two
implementations of a credential-seeding path is how they drift. Behaviour of `bin/cluster-up`
must not change: same users, same Vault path, same reuse-if-present semantics, same
checkpoint (`step-10d5-ldap-passwords`), same hard failure on unverified users.

This is the step that makes the release worth doing rather than adding a fourth copy of the
logic. If it is dropped, the feature is a convenience wrapper, not a fix.

## Constraints discovered — read before implementing

### The two Vault conventions do NOT agree

There are two paths for what sounds like the same thing:

| Reader | Vault path | Namespace |
|---|---|---|
| `ldap.sh:787 ldap_get_user_password` | `secret/ldap/users/<user>` | `vault` |
| `bin/get-keycloak-password:17,62` | `secret/keycloak/users/<user>` | `secrets` |

The realm SSO users live at **`secret/keycloak/users/*` in namespace `secrets`** — that is what
`bin/get-keycloak-password`, `Makefile:567-569` and Step 10d.5 all use.

**Do not wire the new function to `ldap_get_user_password`.** It reads a different path in a
different namespace and will silently return nothing, which looks exactly like "record absent"
and would make the tool report success while reseeding from a path nobody writes. Unifying the
two conventions is **out of scope** — flag it, do not attempt it.

### Cross-plugin calls silently no-op

The dispatcher lazy-loads only the invoked plugin. A function in `ldap.sh` calling a helper
defined in `keycloak.sh` or `shopping_cart.sh` is a silent no-op, not an error. Step 10d.5's
`_vault_kv_put`/`_vault_kv_exists`/`_vault_kv_get_field` are defined **only** in
`scripts/plugins/shopping_cart.sh:645,666,680` and additionally depend on the globals
`_vault_root_token` and `_vault_local_port`, which `bin/cluster-up:381` sets and a plugin
invocation does not.

So `ldap_reseed_realm_users` must do its own Vault KV access rather than reach for those
helpers. `bin/restore-hub-ghcr-pat:33,57` and `bin/rotate-ghcr-pat:32,46` are the precedent for
resolving the token and port locally. A `declare -f` guard around a cross-plugin helper is a
smell, not a fix.

### Secret hygiene — the stdin idiom is mandatory

Pass the new password to `ldappasswd` on **stdin**, as Step 10d.5 does:

```bash
printf '%s\n%s\n' "${_pass}" "${_pass}" | _kubectl exec -i -n identity "${_pod}" -- \
  sh -ceu 'ldappasswd -x -H ldap://localhost:1389 \
    -D "cn=ldap-admin,dc=home,dc=org" -w "$LDAP_ADMIN_PASSWORD" \
    -S "uid=$1,ou=users,dc=home,dc=org"' sh "${_user}"
```

The single quotes are **required**: `$LDAP_ADMIN_PASSWORD` and `$1` must expand inside the pod.
Double-quoting them interpolates host values and bakes the LDAP admin password into the
`kubectl exec` command string that reaches logs — a direct CLAUDE.md violation.

Note `_ldap_sync_admin_password` (`:836`) passes secrets via `env ADMIN_PASS=…` on the exec
line. Do **not** copy that shape; it is wrapped in `_no_trace` but the value still appears in
process arguments. Use stdin.

Write the Vault token to a `chmod 600` header file and pass it with `curl --config`, never
`-H` on the command line. Never log a password. Verify presence by length or exit status.

### `shellcheck` needs `-S error` for this pattern

Plain `shellcheck` emits info-level **SC2016** on the deliberate single-quoted pod scripts and
exits non-zero, which silently short-circuits an `&&` gate chain. During the manual repair this
caused the reset to not run at all while appearing to have been linted. Gate with
`shellcheck -S error`. Do not "fix" SC2016 by double-quoting — see above.

## Out of scope — requires the operator's explicit word

- **Adding `keycloak/users/*` to the 14-key hub seed allowlist.** This is the other candidate
  durable fix and would make a rebuild restore the records without a reseed. Changing the
  allowlist is NOT approved. Do not touch it; do not propose it inside the implementation.
- **Wiring the reseed into `make up` automatically.** The target is operator-invoked in this
  release. Auto-reseeding on every `make up` would silently rotate live passwords.
- Unifying `secret/ldap/users/*` with `secret/keycloak/users/*`.
- `secret/keycloak/admin` (the Keycloak **service** admin) — different secret, seeded on the hub,
  in the allowlist. A blank there is a real fault and must keep its bare `N/A`.
- The `keycloak-credential-rotator` CronJob. It writes `secret/keycloak/admin` only and is not
  implicated. Its BusyBox `base64 --decode` defect is already filed as M4 in
  `docs/bugs/2026-09-22-ci-red-prometheus-reseed-and-rotator-base64.md`.

## Tests

New suite `scripts/tests/plugins/ldap_reseed_realm_users.bats`. Pure logic with stubbed
`_kubectl`/`curl` — no live cluster. Required cases:

1. All three users are attempted (`admin`, `developer`, `operator`).
2. Vault record **present** → LDAP is updated and **no new password is generated**. Assert the
   non-rotating path by stubbing Vault to return a known value and asserting that value reaches
   `ldappasswd` stdin.
3. Vault record **absent** → a password is generated and written to Vault before LDAP.
4. `ldapwhoami` failure → non-zero exit, and the failing username appears in the output.
5. No password appears in any recorded `kubectl exec` **argv** — assert against a captured
   command log. This is the regression guard for the secret-hygiene rule.
6. The Vault token is never passed via `-H` on a `curl` argv.
7. The Vault path used is `keycloak/users/<user>`, not `ldap/users/<user>` — the guard against
   the convention trap above.

Mutation-check cases 2 and 5 against the pre-fix tree: a case that cannot fail is not a test.
Per the `_agent_audit` guard, a net decrease in `@test` blocks is blocked; if delegating Step
10d.5 legitimately removes a case, replace it with an inverse guard, never `--no-verify`.

Run **`make test-all`**, not `make test`. Report `ok`/`not ok` counts. A `tail` of the log is not
evidence — capture full output and count with `grep -cE '^ok '` / `grep -c 'not ok'`.

- Minimal patches, no unsolicited refactors, no inline comments in shell blocks.
- LF only. Public function: no underscore prefix. Private helpers: `_ldap_` prefix.
- Do NOT edit `scripts/lib/foundation/` or `scripts/lib/acg/`.
- Branch: `k3d-manager-v1.37.0`. Do NOT commit to `main`. Do NOT create a PR.

## Risks

- **Silent wrong-path reseed.** Wiring to `ldap/users/*` instead of `keycloak/users/*` yields a
  tool that reports success while `make show-service-passwords` still shows nothing. Test case 7
  is the guard; it is not optional.
- **Unintended rotation.** If the present/absent detection treats a Vault read error as
  "absent", the tool rotates live passwords on a transient Vault outage. Distinguish "Vault
  unreachable" from "record absent" and refuse to generate on the former — this is exactly the
  M1 defect already filed against the Prometheus reseed in
  `docs/bugs/2026-09-22-ci-red-prometheus-reseed-and-rotator-base64.md`. Do not repeat it here.
- **Step 10d.5 regression.** Delegation touches the cluster bootstrap. It is behaviour-neutral
  by requirement; prove it by diffing the effective users, path and checkpoint, not by eye.
