## Goal

The operator wants to travel with the M2 and keep developing k3d-manager on it. Machine setup has three
roles today:

| Role | What it installs |
|---|---|
| `hub` | everything, including OrbStack, the webhook, port-forwards, Hermes and the cloud bridge |
| `worker` | 86 brew packages including OrbStack and the ACG/Playwright tools, `install-sudoers` |
| `console` | 6 brew packages, no secrets, no agents (browser, dashboards, ssh) |

None fits a laptop that develops the repo but runs no cluster. Add a fourth role, `control`:

- **Runs locally:** git, tests (`make test`, bats, pytest), shellcheck, docs, bug filing,
  `make find-similar-docs`, Codex dispatch, and cloud requests (a push to `cloud-requests`).
- **Runs on the hub over ssh:** everything that needs the cluster or the hub's Keychain
  (`make up`, `make platform-ops`, `make appsets-reapply`, kubectl against the hub).
- **Never installs:** OrbStack, any hub LaunchAgent, the webhook, the cloud bridge, ACG or Playwright
  tooling, hub or ACG secrets.

The M2 moves from `console` to `control`. Its GitHub Actions runner stays as it is; machine setup does
not manage it.

## Changes

1. **Manifests** in `scripts/etc/machine/`:
   - `brew.control.list`: `brew.console.list`'s entries plus the CLI tools the repo's own targets need:
     `bats-core`, `shellcheck`, `yq`, `ripgrep`, `git-extras`, `kubernetes-cli`, `python@3` (or the
     formula name `brew.worker.list` already uses), `dtach`, `socat`. No casks other than console's.
     No `cask:orbstack`.
   - `secrets.control.list`: `gemini-cli-api-key|k3dm|Local find-similar-docs query embedding|…` only.
   - `agents.control.list`: `smartcd-install` only.
   - `repos.list`: add `control` to the roles column of the k3d-manager and lib-foundation rows only.
2. **Role validation:** accept `control` everywhere `hub|worker|console` is accepted:
   `bin/k3dm-machine-setup` (usage line and `case`), `bin/k3dm-machine-secrets` (usage and both `case`
   lines), and the `Makefile` help and `Set ROLE=` messages.
3. **Docs:** `docs/howto/machine-setup.md` gets a `control` row in its role table and a short section
   "Working away from home": which work runs locally, which runs on the hub over ssh, and that hub work
   needs a network path to the hub (see Open decisions).
4. **Tests:** `scripts/tests/bin/machine_setup.bats` and `machine_secrets.bats` cover the new role.

## What NOT to do

- Do not change the `hub`, `worker` or `console` manifests or their behaviour.
- Do not install, remove or reconfigure the GitHub Actions runner, OrbStack, or any LaunchAgent.
- Do not run `make machine-setup` for real, ssh anywhere, or touch a real keychain in tests.
- Do not add a network path to the hub (VPN, tunnel, port exposure); that is an open decision.
- Do not create a PR, commit to `main`, or skip hooks with `--no-verify`.
- Write the must_not tests first and show them red on the pre-fix code.

## Open decisions (operator)

- **D1 — reaching the hub while travelling.** `m5-air.local` resolves only on the home LAN. Away from
  home the M2 can develop and push, but cannot run hub work until there is a remote path (for example
  Tailscale, or the queued Cloudflare Access work). Not in this plan.
- **D2 — e2e while the M2 is away.** The M2 is also the remote e2e runner. While it travels,
  `make e2e-remote RUNNER=m2` reports the runner unavailable (no local fallback, by design) and
  `stage2` jobs queue. Options: accept that, or move the runner role to another Mac later.
