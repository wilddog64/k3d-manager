# v1.40.0 — Cloud-request diagnostic artifacts

**Status:** IMPLEMENTED by Claude 2026-10-01 (commit SHA in memory-bank). M2.2's job launch now lives in
`scripts/lib/webhook/lifecycle.py::_run_make_target` (moved out of `bin/k3dm-webhook` since this was
written); `bin/k3dm-webhook` records the make `target` in the job dir for `summary.json`. M7 was already
true: `CLAUDE.md` points at the howto's table instead of stating a count.

## Problem

A cloud session today learns *that* a job failed, not *why*. The bridge's `job-status`
action returns the webhook's status plus the **last 2000 bytes** of
`${K3DM_JOB_DIR}/<job_id>/output`. For a failing pytest or e2e run that tail is almost
always the summary line and the shell epilogue — the assertion, the diff of expected vs
actual, and the failing test's own stderr have already scrolled past it. The session then
guesses, or asks the operator to paste the log, which defeats the point of the channel.

The full output already exists on the host. It is simply never published.

## Approach

Publish per-job diagnostic artifacts to the `cloud-requests` branch alongside the existing
response JSON, using the same detached-index commit the bridge already performs.

```
requests/<id>.json          unchanged — the session writes these
responses/<id>.json         unchanged shape + a new "artifacts" array
artifacts/<id>/summary.json new — structured outcome
artifacts/<id>/junit.xml    new — when the job produced one
artifacts/<id>/output.log   new — PHASE 2 ONLY, redacted (see below)
ledger/processed.txt        unchanged
```

### When artifacts can exist — the job is async

Every `make-*` action, and `cluster-status`/`hostinger-status`, is **asynchronous**: the
webhook answers the dispatch with HTTP 202 and `{"job_id": ..., "status": "queued"}`, and the
job runs after the bridge has already written the response. Verified live 2026-09-28:
`20260928T001624Z-cluster-status` came back `http_status: 202`, `body.status: "queued"`.
At dispatch time there is no outcome, no finish time and no report to publish.

So artifacts are written on the **`job-status` response that first observes a terminal job
state** (`success` or `failed`, read from `${K3DM_JOB_DIR}/<job_id>/status`), not on the
dispatch response. A `job-status` that sees `queued` or `running` publishes nothing new and
omits `artifacts`. A later `job-status` for an already-published job re-lists the existing
paths rather than writing them again.

Artifacts are keyed by the **`job-status` request id** that observed completion. That is the
id the session holds when it reads the result, and the ledger already records it;
`summary.json` carries the `job_id` so the dispatch can be correlated.

`responses/<id>.json` gains one optional field; every existing consumer keeps working. The
existing fields are unchanged — `status` stays `ok` / `rejected` / `error` (the transport
outcome), and `http_status` keeps its name. The job's own outcome lives in `summary.json`:

```json
{
  "schema": 1,
  "id": "20260926T000900Z-job-status",
  "action": "job-status",
  "status": "ok",
  "http_status": 200,
  "completed_at": "2026-09-26T00:09:41Z",
  "body": {"job_id": "d4d6c8be", "status": "failed", "output": "..."},
  "artifacts": [
    "artifacts/20260926T000900Z-job-status/summary.json",
    "artifacts/20260926T000900Z-job-status/junit.xml"
  ]
}
```

Do **not** introduce a new `status` value such as `failed` at the response level:
`bin/k3dm-cloud-request` maps any status other than `ok`/`rejected`/`error` to exit 4, so a
new value would read as a transport error to every existing session.

### Phasing — structured first, raw logs second

**M1–M5 (this release): `summary.json` + `junit.xml` only.**
Both are bounded and field-structured, and carry the diagnostic payload that matters: the
failing test id, the assertion message, the file and line. `summary.json` is built only from
fields the bridge controls, so it carries no free text.

`junit.xml` is **not** inherently safe. A pytest `<failure>` element carries the assertion
message and traceback, and pytest's assertion rewriting prints the compared *values* — a test
that compares a token, a URL or an environment value puts it in the report. With
`junit_logging` enabled it also embeds captured stdout/stderr. So this release publishes
`junit.xml` only after: pytest is run with `-o junit_logging=no`, and the report passes the
redaction filter defined in M2 below. The same filter is what the later `output.log` phase
reuses.

**M6+ (a later release, its own spec): `output.log`, behind a redaction filter.**
Raw job output is the highest-leak artifact in the repo — test runs routinely echo
environment, cluster endpoints and bearer tokens. A `cloud-requests` commit is permanent
and readable by anyone who can read the repo, so the raw log is not publishable until a
redaction filter exists and is itself gated by tests (a fixture containing a synthetic
token must come out redacted, asserted by a BATS/pytest gate that fails on the unredacted
form). That filter must reuse the sensitive-token vocabulary already in
`_args_have_sensitive_flag` (`scripts/lib/system.sh`) rather than introducing a second,
drifting list. **Do not implement `output.log` in this release.**

### Retention

Artifacts committed to a branch grow without bound. `cloud-requests` is never merged to
`main`, so history there is disposable. Prune on write: when the bridge commits artifacts
for a new request, drop `artifacts/` trees whose request id is older than
`K3DM_CLOUD_ARTIFACT_KEEP` (default 50) entries in the ledger. Pruning is a tree
operation in the same detached-index commit — no rewrite, no force-push.

## Milestones

**M1 — `summary.json` writer.** A helper in `bin/k3dm-cloud-bridge`, called only from the
`job-status` path when the job's status is terminal, that renders
`{request_id, job_id, job_status, http_status, target, finished_at}`. `job_status` is the
webhook's terminal value (`success`/`failed`); `finished_at` is the mtime of the job's
`status` file; `target` is the make target when the job's metadata records it, else omitted.
There is **no `exit_code`**: the webhook records only the status word, not the process exit
code. Do not invent one; if a later release makes the webhook persist `rc`, add the field then.
No new webhook call — the bridge already holds the `/api/v1/status/` body and runs on the
same host as `${K3DM_JOB_DIR}`.

**M2 — produce, filter and capture `junit.xml`.** No target writes a JUnit report today, so
this milestone creates one:
1. `Makefile` `test-pytest`: when `K3DM_JUNIT_XML` is set, append
   `--junitxml "$$K3DM_JUNIT_XML" -o junit_logging=no` to the pytest invocation. Unset, the
   recipe is byte-for-byte unchanged in behaviour.
2. `bin/k3dm-webhook`: for make jobs, export `K3DM_JUNIT_XML=${K3DM_JOB_DIR}/<job_id>/junit.xml`
   into the job's environment. Nothing else about job launch changes.
3. A redaction filter in `bin/k3dm-cloud-bridge` applied to the report before it is hashed.
   It replaces credential shapes (`Bearer <value>`, `sk_test_`/`sk_live_` prefixes, and the
   `--password`/`--token`/`--username` values that `_args_have_sensitive_flag` in
   `scripts/lib/system.sh` already names) with `***REDACTED***`. Do not define the patterns here:
   import `scrub_credentials` from `scripts/lib/webhook/redact.py`, created by
   `docs/bugs/2026-09-28-diagnostics-logs-output-unredacted-for-unregistered-secrets.md`,
   so there is one vocabulary and one marker. The later `output.log` phase imports the same module.
4. The bridge copies the filtered report into the artifact tree. If the job produced no
   report, omit the entry — a missing report is not an error and must not fail the response
   commit.

**M3 — commit path.** Extend `_write_commit` to add each artifact blob with the same
`hash-object -w` + `update-index --add` pattern, and populate `artifacts` in the response
JSON. The response and its artifacts must land in **one** commit — a session that sees the
`artifacts` array must find every path in it readable at that same ref.

**M4 — retention.** Implement the keep-window prune described above, with
`K3DM_CLOUD_ARTIFACT_KEEP` defaulting to 50.

**M5 — gates.** Add to the bridge test suite:
1. A response with no artifacts still validates against the existing consumer path
   (the field is optional).
2. Every path listed in `artifacts` exists in the same commit.
3. `summary.json` parses and carries `job_id` and `job_status`; a `job-status` that sees
   `queued` or `running` writes no artifacts and omits the field.
4. The prune keeps exactly `K3DM_CLOUD_ARTIFACT_KEEP` artifact trees and removes the
   oldest beyond it.
5. **No credential shape reaches an artifact** — a synthetic `Bearer`-prefixed token and a
   synthetic `sk_test_` string planted in a captured report must not appear in any
   committed blob. This gate must be shown to fail with the M2 filter bypassed.
6. The response-level `status` is only ever `ok`, `rejected` or `error`, and the field is
   still named `http_status`.
7. `output.log` is **not** written by this release — assert its absence, so M6 has to
   arrive with its redaction filter rather than sneaking in.

**M6 — docs.** Update `docs/howto/cloud-session-requests.md`: document the `artifacts`
field, that it appears on the `job-status` response that first sees the job finish, the
artifact tree layout, the redaction of `junit.xml`, the retention window, and state plainly
that raw job output is deliberately not published yet and why. Per the doc-every-feature rule this is
not optional and does not count as satisfied by the CHANGELOG.

**M7 — correct the stale action count.** `CLAUDE.md` still says "Four read-only actions are
available" in the **No network path out of a cloud session** rule. The bridge allowlist
carries **thirteen** (`ACTION_ALLOWLIST` in `bin/k3dm-cloud-bridge`, counted 2026-09-28).
Fix the number — or better, stop stating a count and point at the howto's table, so the next
added action cannot make it stale again.

## What NOT to Do

- Do NOT create a PR.
- Do NOT merge, and do NOT commit to `main`.
- Do NOT use `--no-verify`.
- Do NOT modify files outside those named above (`bin/k3dm-cloud-bridge`, the
  `test-pytest` recipe in `Makefile`, the make-job launch in `bin/k3dm-webhook`, the bridge
  tests, `docs/howto/cloud-session-requests.md`, `CLAUDE.md`, memory-bank).
- Do NOT add an action to `ACTION_ALLOWLIST`. This spec publishes more detail about the
  thirteen existing actions; it does not widen what a cloud session may invoke.
- Do NOT write `artifacts/<id>/output.log`, or any other free-text log capture, in this
  release.
- Do NOT create, echo, log or commit any real credential value — including in a test
  fixture. The M5 gate uses synthetic strings only.
- Do NOT place a credential of any kind on the `cloud-requests` branch.
