# v1.40.0 — Cloud-request diagnostic artifacts

## Problem

A cloud session today learns *that* a job failed, not *why*. The bridge's `job-status`
action returns the webhook's status plus the **last 2000 bytes** of
`${K3DM_JOB_DIR}/<job_id>/output`. For a failing pytest or e2e run that tail is almost
always the summary line and the shell epilogue — the assertion, the diff of expected vs
actual, and the failing test's own stderr have already scrolled past it. The session then
guesses, or asks the operator to paste the log, which defeats the point of the channel.

The full output already exists on the host. It is simply never published.

## Approach

Publish per-job diagnostic artifacts to the `cloud-requests` branch alongside the existing
response JSON, using the same detached-index commit the bridge already performs.

```
requests/<id>.json          unchanged — the session writes these
responses/<id>.json         unchanged shape + a new "artifacts" array
artifacts/<id>/summary.json new — structured outcome
artifacts/<id>/junit.xml    new — when the target produced one
artifacts/<id>/output.log   new — PHASE 2 ONLY, redacted (see below)
ledger/processed.txt        unchanged
```

`responses/<id>.json` gains one optional field; every existing consumer keeps working:

```json
{
  "schema": 1,
  "action": "make-test-pytest",
  "status": "failed",
  "http": 200,
  "artifacts": [
    "artifacts/20260926T000251Z-make-test-pytest/summary.json",
    "artifacts/20260926T000251Z-make-test-pytest/junit.xml"
  ]
}
```

Artifacts are keyed by **request id**, not webhook job id. The request id is what the
session holds and what the ledger records; the job id is an implementation detail of the
webhook and is not always present (`health` has none).

### Phasing — structured first, raw logs second

**M1–M5 (this release): `summary.json` + `junit.xml` only.**
Both are bounded, field-structured, and carry the diagnostic payload that matters: the
failing test id, the assertion message, the file and line. Neither is a free-text dump of
whatever the process decided to print, so neither is a plausible carrier for a token,
a kubeconfig fragment or a host address.

**M6+ (a later release, its own spec): `output.log`, behind a redaction filter.**
Raw job output is the highest-leak artifact in the repo — test runs routinely echo
environment, cluster endpoints and bearer tokens. A `cloud-requests` commit is permanent
and readable by anyone who can read the repo, so the raw log is not publishable until a
redaction filter exists and is itself gated by tests (a fixture containing a synthetic
token must come out redacted, asserted by a BATS/pytest gate that fails on the unredacted
form). That filter must reuse the sensitive-token vocabulary already in
`_args_have_sensitive_flag` (`scripts/lib/system.sh`) rather than introducing a second,
drifting list. **Do not implement `output.log` in this release.**

### Retention

Artifacts committed to a branch grow without bound. `cloud-requests` is never merged to
`main`, so history there is disposable. Prune on write: when the bridge commits artifacts
for a new request, drop `artifacts/` trees whose request id is older than
`K3DM_CLOUD_ARTIFACT_KEEP` (default 50) entries in the ledger. Pruning is a tree
operation in the same detached-index commit — no rewrite, no force-push.

## Milestones

**M1 — `summary.json` writer.** A helper in `bin/k3dm-cloud-bridge` that renders
`{request_id, action, status, http, exit_code, target, started_at, finished_at}` from the
data the bridge already holds after `_call_webhook`. No new webhook call.

**M2 — `junit.xml` capture.** When the resolved make target produced a JUnit report, copy
it into the artifact tree. Locate it from the target's known report path; if absent, omit
the entry — a missing report is not an error and must not fail the response commit.

**M3 — commit path.** Extend the existing `hash-object -w` + `update-index --add` block to
add each artifact blob, and populate `artifacts` in the response JSON. The response and
its artifacts must land in **one** commit — a session that sees the `artifacts` array must
find every path in it readable at that same ref.

**M4 — retention.** Implement the keep-window prune described above, with
`K3DM_CLOUD_ARTIFACT_KEEP` defaulting to 50.

**M5 — gates.** Add to the bridge test suite:
1. A response with no artifacts still validates against the existing consumer path
   (the field is optional).
2. Every path listed in `artifacts` exists in the same commit.
3. `summary.json` parses and carries `status` and `exit_code`.
4. The prune keeps exactly `K3DM_CLOUD_ARTIFACT_KEEP` artifact trees and removes the
   oldest beyond it.
5. **No credential shape reaches an artifact** — a synthetic `Bearer`-prefixed token and a
   synthetic `sk_test_` string planted in a captured report must not appear in any
   committed blob. This gate must be shown to fail against a build without the filter.
6. `output.log` is **not** written by this release — assert its absence, so M6 has to
   arrive with its redaction filter rather than sneaking in.

**M6 — docs.** Update `docs/howto/cloud-session-requests.md`: document the `artifacts`
field, the artifact tree layout, the retention window, and state plainly that raw job
output is deliberately not published yet and why. Per the doc-every-feature rule this is
not optional and does not count as satisfied by the CHANGELOG.

**M7 — correct the stale action count.** `CLAUDE.md` still says "Four read-only actions are
available" in the **No network path out of a cloud session** rule. The bridge allowlist has
carried **twelve** since the reader-tier make targets landed. Fix the number.

## What NOT to Do

- Do NOT create a PR.
- Do NOT merge, and do NOT commit to `main`.
- Do NOT use `--no-verify`.
- Do NOT modify files outside those named above.
- Do NOT add an action to `ACTION_ALLOWLIST`. This spec publishes more detail about the
  twelve existing actions; it does not widen what a cloud session may invoke.
- Do NOT write `artifacts/<id>/output.log`, or any other free-text log capture, in this
  release.
- Do NOT create, echo, log or commit any real credential value — including in a test
  fixture. The M5 gate uses synthetic strings only.
- Do NOT place a credential of any kind on the `cloud-requests` branch.
