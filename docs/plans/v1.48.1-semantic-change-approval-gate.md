# v1.48.1 — Semantic Change Approval Gate

**Status:** Proposed; implementation not authorized
**Priority:** P2 enhancement
**Approval:** pending
**Release:** v1.48.1
**Dependencies:** v1.45.1 engineering decision digest, existing PR/CI gates, v1.47.0 hub-e2e promotion gate, planned release evidence records.

## Context and intent

Claude/Codex implement most changes while the operator validates system behavior instead of reviewing every line. Add *risk-based semantic approval* at the PR/merge boundary: routine changes retain automation while sensitive changes require independently enforced evidence and human approval. This is not a replacement for Git, a parallel workflow engine or the future v2.x operational policy gateway.

## Critical rules

1. Follow `docs/plans/task-spec-template.md`. Before implementation, break down this feature spec into precise file-level change checklists; do not edit files outside approved scope.
2. Pre-commit is **advisory** for risk classification. Authoritative decisions belong in trusted CI and GitHub protected merge rules. `--no-verify` must not bypass enforcement.
3. A deterministic ruleset establishes the *minimum* risk. AI may explain or escalate risk; it cannot lower it, attest its own success, grant approval or override a required check.
4. UNKNOWN, policy parser errors, classifier timeout, absent checks, incomplete reports or ambiguous effects are blocked, not auto-approved.
5. Validate the entire PR diff from trusted target branch to exact merge candidate/head SHA, including deletes, renames, mode changes, workflow changes and dependency files. New pushes invalidate stale evidence/approval.
6. PR-controlled code/policy/workflows must never run as the trusted approval authority. Use protected-base policy or a pinned trusted workflow. Changes to the policy/gate itself are HIGH.
7. Preserve existing CI, CodeQL, Copilot, `_agent_audit`, agent reviews, release-branch discipline and the v1.47.0 exact-ref hub promotion gate.
8. Do not send raw secrets or sensitive diffs to LLMs, logs, Slack or metrics. No destructive cluster or cloud authorization changes in this release.

## Proposed policy matrix

| Classification | Typical change | Merge requirements |
|---|---|---|
| LOW | Proven docs/comments/format-only; no executable or semantic configuration change | Existing CI checks; eligible for current auto-merge |
| MEDIUM | Ordinary application or test code, observability/config changes | Existing CI, relevant focused tests and independent agent review; current auto-merge only if all checks pass |
| HIGH | Vault/Keycloak/LDAP, IAM/RBAC, bridge/webhook allowlists, cloud credentials, CI/security/policy files, DR/delete/reset, supply-chain/admission, sensitive deployment controls | Existing CI + targeted negative/security tests + explicit operator approval bound to current SHA; no unapproved auto-merge |
| UNKNOWN | Unrecognized path, mixed ambiguous change, unavailable classifier/evidence | Block pending operator triage |

Highest risk in mixed changes wins. Path rules alone are insufficient: analyze content/semantics, including scripts in docs, generated files, renames, new executable entrypoints and indirect authorization changes. Record which rule triggered each escalation. Prefer conservative classification.

## Architecture and interfaces

**Local fast feedback:** extend existing hooks / agent audit with risk *hints*, preserving quick format, lint and secret checks. No local approval authority.

**Authoritative PR gate:** a trusted CI job obtains base/head SHA from GitHub, classifies full diff, verifies targeted tests and operator approval, emits a signed-or-CI-attested versioned JSON report, and publishes a *required* check. Bind all artifacts and approvals to evaluated SHA and trusted policy digest. Check for self-modification and protect the gate itself. Validate branch protection/ruleset capabilities in the actual repo before asserting enforcement.

**Existing integrations:** respect auto-merge and CI rather than replacing them; join v1.45.1 `Approval: explicit|standing|pending` and commit trailers as provenance, *not* sufficient approval for HIGH. Add classified risk and gate evidence to the planned release-evidence record and read-only decision digest. Do not create another database. An explicit authenticated operator identity and current-commit acknowledgement are required for HIGH. Slack may collect authenticated approval via the existing webhook; GitHub Actions independently verifies the durable approval record and all other gates. Slack messages or comments alone are never proof of approval.

**Make is the operator interface:**

```bash
make change-risk                    # local advisory
make change-verify PR=123           # trusted CI evaluation
make change-approval-status PR=123  # read-only reasons/evidence
```

Example report:

```yaml
schema_version: 1
pr: 123
base_sha: "<sha>"
head_sha: "<sha>"
policy_digest: "<digest>"
risk: HIGH
components: [cloud-bridge, webhook]
reasons: ["authorization allowlist changed"]
required_checks: [ci, security-negative-tests, operator-approval]
approval: pending
merge_gate: blocked
```

Make reports understandable for humans and consumable by existing dashboards, with bounded labels (no PR/SHA labels in Prometheus time series).

## Slack and optional SMS approval workflow (operator request, 2026-10-14)

**GitHub Mobile is the preferred approval interface for PRs eligible for native GitHub review approval. Slack remains the primary notification channel and an authenticated alternate approval interface**, reusing k3d-manager's existing Slack ChatOps, signed interactive request verification, webhook and current notification routing. **SMS is optional notification-only in v1.48.1** (a PR link or secure sign-in link, never approving by unverified SMS reply); do not require a new paid provider or introduce SMS as a blocking dependency. SMS-based approval itself is a separately scoped follow-on unless an adequately authenticated scheme is designed and approved.

### GitHub Mobile approval (preferred when eligible)

1. Include a deep link to the exact pull request in Slack notifications; the operator opens it in the GitHub mobile app, reads the risk/intent summary and checks evidence, then uses GitHub's native **Review changes → Approve** when available.
2. The trusted CI gate retrieves reviews from GitHub's API and verifies the reviewer against an allowlisted operator GitHub identity, the review decision, the applicable current PR head/merge candidate, policy digest, and current required checks. A generic PR comment, reaction, label, approval of an earlier commit, or an agent-provided status cannot satisfy approval.
3. Native PR approvals are not valid for PRs authored by the same GitHub identity. Do **not** treat a GitHub Mobile review by the PR author as an exception. Such PRs must use the separately authenticated Slack decision path and independent required CI attestation, if branch-protection/ruleset capabilities actually enforce it. Otherwise the gate remains blocked. Another genuinely independent authorized reviewer/bot identity strategy may be considered, but never impersonate or bypass GitHub controls.
4. Both GitHub Mobile and Slack decisions normalize to the same auditable, SHA-bound approval state; no duplicate approvals required. Deny/Delay via Slack continue to block until an explicit new decision cycle. New commits, policy changes, dismissal or revocation invalidate approval as applicable.
5. For GitHub Mobile tests, verify authorized non-author approval, incorrect reviewer, self-authored PR, stale review after new commits, dismissed approval, pending tests and unavailable GitHub API. Mobile approval does not bypass any targeted security tests or the v1.47.0 infrastructure promotion gate.

1. On HIGH risk, GitHub Actions leaves the required gate pending/blocked and sends one deduplicated Slack interactive notification: PR link, base/head SHA short form, risk reasons, affected components, test results/evidence links and expiration. Do not include secrets, raw diff, tokens or sensitive arguments.
2. The operator can choose **Approve / Deny / Delay**. Interactive actions must arrive at the existing webhook over HTTPS with validated Slack signing secret, timestamp/replay protection, expected team and exact allowlisted Slack user ID. Map that account to the authorized operator using trusted configuration **outside PR-controlled content**. Slack display name, channel membership, message authorship and user-typed `approve` text alone are insufficient.
3. Include an opaque one-time request ID bound server-side to repository, PR, base SHA, head SHA, risk/policy digest, operator, expiration and action; store decisions in a durable, append-only/auditable existing ledger or protected GitHub record (no new database). Atomically consume IDs; reject duplicate, modified, replayed, expired and out-of-order actions. Do not trust request IDs, SHAs or role assertions supplied from Slack payload without server-side lookup.
4. **Approve:** save the authenticated decision and cause the trusted GitHub Actions gate to re-evaluate the exact PR head SHA, policy digest, required tests and current permission state. Approval does not directly merge, skip CI, modify branch rules or execute destructive operations. A new commit or changed policy invalidates the prior approval. **Deny:** record rejection and keep merge blocked until an explicitly new approval cycle is created by the operator. **Delay:** record deferral, leave blocked, and optionally send one bounded reminder (no approval implied).
5. Protect the webhook endpoint with least privilege, idempotent state handling, failure-safe persistence and audit events (who, action, when, PR/head, reason, gate result). If Slack, webhook, approval ledger or GitHub APIs are unavailable, gate remains blocked, never silently grants permission. Any break-glass fallback must use an independent operator-authenticated path and a documented audit record.
6. For PRs authored under the operator's GitHub account, native GitHub self-approval is insufficient. Verify actual GitHub ruleset capabilities and use the trusted CI external approval attestation only if the protected required check can enforce it; otherwise keep the system advisory/blocked rather than promise enforced self-approval.
7. SMS alert, if configured, is notification-only: brief change ID and deep link to authenticated GitHub/Slack approval. Do not place approval tokens or secrets in texts; disable without affecting Slack/CI gating. Rate-limit notifications and do not expose PR contents in SMS.

**Required acceptance scenarios:** authorized Slack Approve/Deny/Delay; unknown Slack actor/team; invalid signature, stale timestamp and replay; duplicate clicks; SHA changed between send and click; policy changed; expired request; forged action payload; concurrent actions; Slack delivery failure; ledger outage; GitHub check failure; operator-authored PR; SMS unavailable. Prove that all negative cases block, DENY/DELAY never grant approval, and APPROVE alone cannot bypass required CI.

## Acceptance criteria / tests

1. Comments-only change is LOW only after verifying no semantic execution/config effect.
2. Ordinary code change is MEDIUM and runs relevant tests and independent review.
3. Any edit to cloud-bridge authorization, Vault/IAM, `DELETE_HUB`, deployment safeguards, PR gates or their policy is HIGH, regardless of agent claims.
4. Mixed-risk changes, renames, deletions, generated files and executable workflow edits use highest relevant risk.
5. A hostile PR changes the classifier/workflow to report LOW: base-trusted evaluation still blocks without operator approval.
6. Unknown path, missing/failed checks, classifier outage or invalid evidence yields BLOCKED/UNKNOWN.
7. A new commit invalidates stale classification/test/approval; forged trailers, labels/comments and `--no-verify` do not pass.
8. Insufficient GitHub branch-rule capabilities are shown as **NOT ENFORCED**; never report PASS until demonstrated with a blocked test PR.
9. Pre-deployment v1.47.0 promotion and runtime destructive-action authorization remain separate mandatory gates.
10. Verify native GitHub Mobile approval by authorized non-author reviewers, self-authored PR rejection, and stale/dismissed reviews; ensure alternate Slack attestation is enforceable through required checks.
11. Verify signed Slack actions, exact allowlisted operator identity, Approve/Deny/Delay, replay resistance, stale SHA, fail-closed outages and self-authored PR handling. SMS may notify but cannot itself authorize.
12. Shadow-test representative historical PRs; track false negatives, false blocks and added CI time. Obtain separate operator signoff before enforcement.
