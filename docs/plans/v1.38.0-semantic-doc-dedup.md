# v1.38.0 — Semantic dedup and retrieval over the doc corpus

**Target branch:** `k3d-manager-v1.38.0`
**Status:** QUEUED for v1.38.0. No live cluster interaction; repo-only.

---

## Why this spec exists

`CLAUDE.md` mandates a dedup check before filing into `docs/bugs/` or `docs/issues/`:

```bash
ls docs/bugs/*-<slug>.md 2>/dev/null
```

That is **exact slug matching**. It finds a duplicate only when the filer independently invents the
same words as the previous filer. The corpus it searches:

| Directory | Files |
|---|---|
| `docs/bugs/` | 495 |
| `docs/issues/` | 373 |
| `docs/plans/` | 250 |
| `docs/retro/` | 78 |
| `~/.claude/.../memory/` | 165 |

A bug filed as `argocd-pvc-immutable-replace.md` and the same defect refiled as
`keycloak-postgres-volumename-blanked.md` share almost no slug tokens and every substantive term.
The current gate cannot see that. `MEMORY.md` is the same problem solved by hand: a linearly-read,
hand-maintained index over 165 files that grows without bound.

This is the one capability gap in the repo's agent tooling. Code already has semantic search via the
`code-review-graph` MCP (`semantic_search_nodes`); documentation never got it.

## What this is NOT

**No vector database.** At ~1,360 documents, a brute-force cosine scan over an on-disk matrix is
microseconds of arithmetic. Introducing Qdrant/Chroma/pgvector here would add a service, a schema,
and a failure mode to replace a `for` loop. A flat file **is** the correct index at this scale.
Revisit only if the corpus passes ~10^5 documents, which it will not.

**No `torch` / `sentence-transformers` in Phase 1.** The repo has **zero third-party Python runtime
dependencies** — `scripts/check-doc-links.py` imports only `re`, `subprocess`, `sys`, `pathlib`, and
no `requirements.txt` or `pyproject.toml` exists. Adding ~2GB of ML wheels, on Python **3.14.7**
where their availability is not assured, to close a dedup gap would be the largest dependency
decision in the repo's history taken as a side effect. Phase 2 addresses embeddings deliberately and
by a route that avoids the wheel problem entirely.

## Phase 1 — Lexical baseline, stdlib only (this release)

### Task 1 — `scripts/find-similar-docs.py`

Pure stdlib (`re`, `math`, `collections`, `pathlib`, `argparse`, `json`). Mirror the structure and
CLI conventions of `scripts/check-doc-links.py`.

- Corpus: `docs/bugs/`, `docs/issues/`, `docs/plans/`, `docs/retro/`. Tracked files only, via
  `git ls-files` — matching `check-doc-links.py`, whose tracked-only behaviour has already surprised
  one session (an untracked doc left the count unchanged).
- Per document extract: the `#` title, the leading prose paragraph, and all `##` headings. Body
  beyond that is mostly shell transcripts and adds noise.
- Tokenize: lowercase, split on non-alphanumerics, drop a small English stopword list **plus** a
  repo-specific one (`k3d`, `manager`, `cluster`, `docs`, `spec`, `fix`, `bug`) — terms present in
  nearly every document carry no discriminating signal.
- Score with TF-IDF cosine. IDF computed over the corpus itself.
- Two modes:
  - `--query "<free text>"` — rank the corpus against ad-hoc text. This is the filing-time gate.
  - `--file <path>` — rank against an existing document, for auditing what is already duplicated.
- Output: top N (default 5) as `score<TAB>path<TAB>title`, `--json` for machine use. Exit 0 always;
  this **advises**, it does not block. A dedup gate that blocks on a fuzzy score will be bypassed
  within a week and is worse than no gate.

### Task 2 — `make find-similar-docs`

```make
find-similar-docs:
	@python3 scripts/find-similar-docs.py --query "$(Q)"
```

Follow the `check-doc-links` target's style. Document `Q=` in `make help`.

### Task 3 — Wire into the dedup rule

Update the `Docs Conventions` section of `CLAUDE.md`: the `ls docs/bugs/*-<slug>.md` check stays as
the exact-match first pass, with the similarity scan as the second. State plainly that a high score
means *read the file before filing*, not *do not file*.

### Task 4 — Evaluation set and harness (the point of the exercise)

A retrieval system whose accuracy is never measured is a guess. Build the labelled set **before**
tuning anything:

- `scripts/tests/fixtures/doc-dedup/pairs.jsonl` — known duplicate/near-duplicate document pairs
  mined from the existing corpus by hand, plus hard negatives (same component, genuinely different
  defect). Target ≥25 positive pairs and ≥25 hard negatives. Follow the schema style of
  `scripts/tests/fixtures/e2e-corpus/corpus.jsonl`, which is the existing precedent.
- `scripts/tests/bin/test_find_similar_docs.py` — pytest, mirroring
  `scripts/tests/bin/test_check_doc_links.py`. Assert tokenizer and TF-IDF behaviour on fixtures,
  and report **recall@5** over `pairs.jsonl` with a floor the suite enforces.
- Record the measured recall@5 in the spec's completion note and in the retro. That number is the
  input to the Phase 2 decision.
- Add the new file to the `make test-pytest` target's path list.

Per the standing rule: confirm each new assertion can actually fail before claiming coverage.

## Phase 2 — Embeddings, only if Phase 1 measurably falls short (deferred, not this release)

Do not start this until Phase 1's recall@5 is measured. If lexical recall is high, the corpus
vocabulary is shared enough that embeddings buy little, and the dependency is unjustified.

If it does fall short, the route is a **hosted embeddings API, not local wheels**: ~1,360 documents
embedded once costs cents, needs no `torch`, and reaches the repo through `urllib` in the stdlib.

- Cache vectors to a gitignored on-disk file keyed by content hash; re-embed only changed documents.
- Keep brute-force cosine. Still no vector database.
- Keep the lexical scorer as a working fallback when no API key is configured — the tool must not
  become unusable offline.
- API key via env or Keychain, never argv, per the repo's secret-hygiene rules. Register any new
  sensitive flag in `_args_have_sensitive_flag` (`scripts/lib/system.sh`).
- Re-measure recall@5 on the **same** `pairs.jsonl`. Adopt only on a real improvement.

Phase 2 needs its own spec and its own version. Do not implement it here.

## What NOT to do

- Do **not** add a vector database.
- Do **not** add `torch`, `sentence-transformers`, `numpy`, or any third-party runtime dependency in
  Phase 1.
- Do **not** make the similarity check blocking, in the pre-commit hook or anywhere else.
- Do **not** tune the scorer before the labelled set exists — that is fitting to intuition.
- Do **not** index `scripts/lib/foundation/` or `scripts/lib/acg/` docs; they are upstream subtrees.
- Do **not** index the `memory/` directory in Phase 1. It lives outside the repo, under
  `~/.claude/projects/`, and mixing an out-of-tree path into a `git ls-files` corpus invites exactly
  the tracked-vs-untracked confusion `check-doc-links` already produced. Handle it in its own task
  once the in-repo tool is proven.
- Do **not** create a PR, merge, commit to `main`, force-push, or use `--no-verify`.

## Risks

- **Fitting to the labelled set.** 50 hand-mined pairs is small; recall@5 on it is a signal, not a
  guarantee. Mine the pairs before writing the scorer, and do not add pairs to fix a failing score.
- **Advisory tools get ignored.** If the output is noisy it will be skipped regardless of
  correctness. Keep the default to 5 results and make titles readable.
- **Hand-mining duplicates is the real cost.** Reading enough of 868 bug and issue docs to label 25
  genuine duplicate pairs is the bulk of the work, and it cannot be skipped without making the
  evaluation meaningless.
- **Corpus skew.** `docs/bugs/` and `docs/issues/` dominate; plans and retros differ in register and
  may score poorly. Report recall per directory, not only in aggregate.
