## Problem

The `shopping-cart-e2e-tests` acceptance suite is **disabled**, and both reasons in its own workflow are
the *same* root cause — **no reachable services**:

- `# schedule disabled — re-enable once ImagePullBackOff resolved and app cluster healthy` (it was
  pinned to the live Hostinger app cluster, which was unhealthy — and prod is the wrong acceptance
  target anyway).
- `# push/pull_request disabled — api-tests and flow-tests require live services at localhost:8083
  (basket), :8000 (catalog), :8080 (order) which do not exist in GitHub Actions CI`.

Consequences that ripple across two releases:
- **CVE loop (v1.26.0):** promotion is gated on Trivy-clean only; nothing runs the acceptance contract
  against a bumped image, so runtime/behavioral regressions (a Tomcat/JVM default, a Go stdlib
  TLS/HTTP change) can auto-promote. No substrate = no functional gate to add.
- **Stripe/Go acceptance (v1.25.0 G):** the live Stripe E2E is stuck at **2/4** with no repeatable
  place to run the full authenticated checkout flow.

**Key enabler discovered:** the suite is **substrate-agnostic**. It consumes only `BASKET_URL`,
`PRODUCT_CATALOG_URL`, `ORDER_URL`, and `OAUTH2_ENABLED`. Anything that hands e2e those four inputs can
run it unchanged. We have two throwaway substrates; use them **tiered**, not either/or.

## Design — two verification tiers

```
 Tier 1 — vCluster (per-candidate, FAST, blocking)        Tier 2 — ACG AWS sandbox (periodic, FULL-STACK)
 ┌───────────────────────────────────────────┐           ┌──────────────────────────────────────────────┐
 │ vcluster_create → deploy basket/catalog/    │           │ acg sandbox up → deploy FULL stack (Istio,     │
 │ order (+ optional CANDIDATE digest)          │           │ Vault, ESO, ArgoCD, shopping-cart)             │
 │ playwright --project=api,flow                │           │ playwright api,flow + Stripe live E2E          │
 │ OAUTH2_ENABLED=false                         │           │ OAUTH2_ENABLED=true (real Keycloak OIDC + TLS) │
 │ trap → vcluster_destroy (always)             │           │ bounded by 4h(+4h) sandbox lifetime            │
 └───────────────────────────────────────────┘           └──────────────────────────────────────────────┘
   Catches: app-logic regressions                            Catches: mesh/ingress/TLS/OIDC-topology regressions
   Cheap, always available, no live-cluster dep              Real ingress; flaky creds → NOT a per-candidate gate
```

**Why both, not one:** vCluster is fast/cheap/always-available but nested — it can't reproduce Istio
ambient mesh, real ingress TLS, or the OIDC issuer (`reference_local_go_and_oauth_testing` issuer trap),
so it can pass while the real topology fails. The ACG sandbox reproduces all of that on real EC2 k3s,
but its 4h(+4h) lifetime and browser-automation credential fragility (the ACG stale-tab / CDP-login
failure modes) make it too slow/flaky to block every candidate. → vCluster is the **blocking
per-candidate gate**; ACG is the **periodic full-stack gate**. Sandbox access is available until ~2027,
so Tier 2 is a viable resource now.

## Part 1 — Make the e2e suite callable (`shopping-cart-e2e-tests`)

- Add a **`workflow_call`** trigger alongside the existing `workflow_dispatch`, with inputs for the four
  knobs (`basket_url`, `product_catalog_url`, `order_url`, `oauth2_enabled`) mapped onto the env the
  jobs already read. This lets k3d-manager (or the infra reusable workflow) invoke e2e with substrate
  URLs — no test code changes.
- **Do NOT** unconditionally re-enable `push`/`schedule` — they stay gated on substrate availability
  (Tier 2 schedule is opt-in; see Part 3).
- Keep `OAUTH2_ENABLED` env-driven (already is) so Tier 1 runs `false` and Tier 2 runs `true`.

---

## Part 2 — Tier 1 harness: vCluster per-candidate (k3d-manager)

**New plugin `scripts/plugins/e2e.sh`** (public `e2e_verify_vcluster`; private `_e2e_*`). Reuses the
existing `vcluster_create` / `vcluster_use` / `vcluster_destroy` primitives and the prior-art two-job
structure from `docs/plans/archive/v0.9.2-vcluster-e2e-workflow.md`.

`e2e_verify_vcluster [candidate_digest]`:
1. `vcluster_create` a uniquely-named ephemeral vCluster; `trap 'vcluster_destroy …' EXIT` (always tear
   down — even on failure).
2. Deploy the e2e-required services into it — basket, product-catalog, order — plus seed data
   (`deploy_shopping_cart_data`) and the GHCR pull secret (`shopping_cart_provision_ghcr_pull_secret`).
   **Optionally pin the CANDIDATE image digest** so the run verifies the *bumped* image, not `latest`.
3. Resolve the three service URLs (in-vCluster ClusterIP DNS if the Playwright runner runs in-cluster,
   else `kubectl port-forward` to localhost — decide per Open Question 1).
4. Run `npx playwright test --project=api --project=flow` with `OAUTH2_ENABLED=false` and the resolved
   URLs. Collect `playwright-report/` + `test-results/` as artifacts.
5. **Exit 0 only if all pass** (gate-consumable contract — v1.26.0 depends on this).

Rules: `set -euo pipefail`, `_kubectl`/`_run_command` only, no bare `sudo`, unique vCluster name per run,
least-privilege RBAC (reuse `scripts/etc/vcluster/argocd-manager-rbac.yaml`). BATS: creates + destroys
the vCluster, sets exactly the three URLs + `OAUTH2_ENABLED=false`, tears down on failure.

## Part 3 — Tier 2 harness: ACG sandbox full-stack (k3d-manager)

`e2e_verify_sandbox` (public, in `e2e.sh`): against an ACG AWS sandbox context (assume up, or bring up
via the ACG lifecycle), deploy the **full** k3d-manager stack (Istio ingress, Vault, ESO, ArgoCD,
shopping-cart), then run e2e with `OAUTH2_ENABLED=true` against **real ingress + real Keycloak OIDC** —
including the **Stripe live E2E** (Part 4).

- **Do NOT tear down the sandbox** — it self-expires (4h + 4h); Tier 2 is best-effort/opt-in, invoked
  manually or on an opt-in schedule while a sandbox is alive. Never a blocking per-candidate gate.
- Handle the OIDC issuer-mismatch trap: fetch the JWT **in-cluster** so the issuer matches
  (`reference_local_go_and_oauth_testing`).
- Reuse existing ACG lifetime handling; dead `ubuntu-*` contexts are normal, not drift
  (`reference_acg_sandbox_lifetime`).

## Part 5 — Promotion-gate seam (FORWARD to v1.26.0 — not built here)

This spec **stands up the harness**; wiring it into the CVE loop is v1.26.0:
- The promoter dispatching `e2e_verify_vcluster` against a candidate and **waiting for
  `conclusion=success`** before pinning (reuses the existing `wget → actions/workflows/dispatches`
  mechanism in `app-cve-scan.sh`).
- An **e2e-passed `cosign attest`** predicate bound to the candidate digest, so the v1.26.0 verify gate
  becomes *authentic + CVE-clean + e2e-accepted* in one check.

To keep that seam clean, **`e2e_verify_vcluster` MUST exit non-zero on any failure** and emit a
machine-readable summary (JSON) alongside the human report.

## Observability — surface e2e runs in Grafana (reuse the CVE-loop pattern)

e2e runs are **batch jobs that exit**, so they can't be scraped directly — the same shape as the CVE
scan / promoter / rotator CronJobs. Those already reach Grafana via a proven seam: a long-lived
exporter reads durable ConfigMap **events** and turns them into Prometheus gauges. Reuse it — **no new
component**, and the harness's existing JSON summary *is* the event payload.

**What the stack has today (verified):** Prometheus + **Pushgateway** (`_deploy_pushgateway_acg` →
`prometheus-community/prometheus-pushgateway` in `monitoring`, deployed *for* batch-job metrics) + Loki.
**No trace backend** (no Tempo/Jaeger/OTel) — true request-level span tracing is out of scope here
(see forward note below).

**The existing seam:** `vulnerability-inventory-exporter.yaml` lists ConfigMaps in `platform-ops`
labeled `k3dm.k3d.io/cve-remediation-event=true` and emits `cve_remediation_state` /
`cve_remediation_*_timestamp_seconds` / `cve_remediation_event_info`; a ServiceMonitor scrapes it every
1m; `grafana-dashboard-cve-autopatch.yaml` renders it.

### Path A (RECOMMENDED) — event ConfigMap → exporter → Prometheus → Grafana

1. On each run, the harness writes a durable ConfigMap in `platform-ops` labeled
   **`k3dm.k3d.io/e2e-result=true`** whose data is the **same JSON summary** it already emits for the
   v1.26.0 gate. Schema (flat, string values — exporter reads them as metric labels):
   ```json
   {
     "run_id": "<uuid>", "tier": "vcluster|sandbox", "service": "order|basket|...|all",
     "candidate_digest": "sha256:…", "project": "api|flow|stripe",
     "passed": "true|false", "total": "N", "failed": "N",
     "duration_seconds": "N", "timestamp": "<unix>", "commit": "<gitsha>"
   }
   ```
2. **Extend the existing exporter** (or add a sibling block mirroring it) to also list
   `k3dm.k3d.io/e2e-result=true` ConfigMaps and emit:
   - `e2e_run_state{tier,service,project,candidate_digest,run_id} 1` (info/state gauge, like
     `cve_remediation_state`)
   - `e2e_pass_total{tier,service,project}` / `e2e_fail_total{…}` (counters)
   - `e2e_duration_seconds{tier,service,project}` (gauge)
   - `e2e_last_success_timestamp_seconds{tier,service,project}` (freshness → alert on staleness)
3. **Dashboard:** add an **E2E row** to `grafana-dashboard-cve-autopatch.yaml` (or a sibling dashboard
   CM): pass/fail by service+tier, last-success age, duration trend, and a table of recent runs from
   `e2e_run_state` labels. **Deploy the dashboard/rule/exporter via `argocd.sh`** (platform-ops path),
   **not** the dashboards-only ArgoCD app — same rule as the CVE work
   (`reference_trivy_vs_remediation_image_repository_label_mismatch`).
4. **Alerting (optional):** a Prometheus rule on `e2e_fail_total` increase or `e2e_last_success_*`
   staleness, routed like the other platform-ops alerts.

> **Label-shape caution:** if any e2e panel/rule joins against `cve_remediation_*` or Trivy series by
> `image_repository`/digest, mind the normalization traps already burned once — Trivy inventory is bare
> `org/repo` while remediation state is `ghcr.io/`-qualified
> (`reference_trivy_vs_remediation_image_repository_label_mismatch`), and multi-arch pods report a
> different OCI index digest than the deploy-pinned spec digest
> (`reference_containerd_index_digest_aliasing_verifier`). Match on `run_id`/`candidate_digest` as
> emitted, don't re-derive.

### Path B (complement) — Loki for per-run drill-down

Ship the raw Playwright output (failed spec, assertion, stack) to Loki as structured lines carrying the
same `run_id`/`tier`/`service`. Grafana Explore / a logs panel gives click-through from a red panel to
the exact failure. Best for detail; Path A owns trend + alerting.

### Not in scope — distributed tracing (forward theme)

A Tempo/Jaeger waterfall of the checkout request across basket→order→payment (e.g. tracing a Tier-2
Stripe run) needs a **trace backend that is not deployed** (Tempo + OTel collector; Istio can emit
spans but has nowhere to send them). That is a **separate net-new observability milestone**, not part of
this harness — noted here so the boundary is explicit. Candidate forward theme: "request-level tracing
(Tempo + Istio telemetry)."

## Open questions (resolve during implementation)

1. **Runner placement / URL resolution.** Run the Playwright container **inside** the vCluster namespace
   (ClusterIP DNS, no port-forward) vs on the host with `kubectl port-forward` of the three services.
   In-cluster is cleaner; prior art (v0.9.2) used a job structure — reuse it. Decide before handoff.
2. **Data seeding determinism.** e2e needs product-catalog seed data; confirm `deploy_shopping_cart_data`
   is idempotent and sufficient for the api/flow assertions.
3. **Keycloak for Tier 1 flow-tests.** Confirm the `flow` project passes with `OAUTH2_ENABLED=false`; if
   any flow assertion requires a token, add a minimal dev Keycloak to Tier 1 or scope those cases to
   Tier 2 only.
4. **Actions vs local for Tier 1.** GH Actions needs a k3s/k3d-in-Actions host for the vCluster (prior
   art did this); the local entrypoint runs on the hub. Support both; default the CVE-gate path
   (v1.26.0) to whichever the promoter can reach.

## Rules (CLAUDE.md)

- **Never point e2e at the live Hostinger prod cluster** — ephemeral substrates only.
- **Always tear down the vCluster** (`trap … EXIT`); never leak running vClusters.
- **Secrets** — Stripe test keys + GHCR PAT from Vault/Keychain, never in argv/logs (A02); reuse the
  existing `shopping_cart_resolve_ghcr_pat` + Stripe Keychain backup.
- **Least privilege** — reuse the vCluster manager RBAC; no `cluster-admin`; namespace-scoped.
- **Pin** the Playwright/node versions, all GitHub Actions (`@vN`), and any image tags (A08).
- `shellcheck -S warning` clean on `e2e.sh`; BATS green.

## What NOT to do

- Do NOT run e2e against live Hostinger prod — ephemeral substrates only.
- Do NOT leave vClusters running — always `vcluster_destroy` via trap.
- Do NOT make the ACG sandbox a blocking per-candidate gate — 4h(+4h) lifetime + fragile creds; periodic
  / opt-in only.
- Do NOT build the promoter dispatch-and-wait or the e2e cosign attestation here — that is v1.26.0. Only
  guarantee the exit-code + JSON-summary contract so v1.26.0 can consume it.

- Do NOT deploy the E2E dashboard/exporter/rule via the dashboards-only ArgoCD app — use the
  `argocd.sh` platform-ops path (same rule as the CVE work).

- Do NOT put Stripe keys / GHCR PAT in argv or logs; no `cluster-admin`; no `--no-verify`; no commit to
  `main`.
