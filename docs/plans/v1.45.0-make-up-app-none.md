## Why

Today `make up` always builds k3s plus the hub, Vault, ESO, ArgoCD, observability and shopping-cart. A lab that is not shopping-cart (the dirused Windows rehearsal, a future project) only needs machines. With `make up APP=none`, the same command gets the ACG sandbox and launches empty nodes, then stops. Later, the app plug-in plan lets each `APP=<name>` say whether it needs Kubernetes at all.

## Behaviour

### 1. Interface and the Makefile

- `make up APP=none` builds bare nodes. `make up` (APP not given on the command line) and `make up APP=shopping-cart` behave exactly as today.
- New script `bin/k3dm-up-app-check` (`set -euo pipefail`, under 40 lines). It is called as the **first** line of the `up:` recipe with `"$(CLUSTER_PROVIDER)" "$(origin APP)" "$(APP)"`.
  - It only looks at APP when `$(origin APP)` is `command line`. A stray exported `APP` in the environment is ignored.
  - Allowed command-line values: `shopping-cart` and `none`. Anything else exits 2 with `APP must be 'shopping-cart' or 'none'`.
  - `none` with any provider other than `k3s-aws` exits 2 with `APP=none is supported on k3s-aws only`.
  - Otherwise it prints the value to pass as `K3DM_APP`: the command-line value, or nothing.
- The cluster-up branch of `up:` (`Makefile:177`) passes `K3DM_APP` from that output. When the output is empty, any `K3DM_APP` already in the environment is left as it is.
- Do **not** add a top-level `APP ?=`, `APP :=` or `APP =`. `APP` is the required argument of `fix-restart`, `fix-delete-pod`, `fix-sync` and `fix-force-sync` (`Makefile:1464-1484`).
- `make help` for `up` mentions `APP=none`.

### 2. `bin/cluster-up` under none

- `_acg_resolve_app` runs after argument parsing and after the `--trust-vault-ca` early exit (`bin/cluster-up:460` and the code that acts on it), and before the checkpoint clear (`:489-491`).
  - `K3DM_APP` empty or `shopping-cart` → shopping-cart; `none` → none; anything else → `_err "K3DM_APP must be 'shopping-cart' or 'none'"`.
  - `none` with a provider other than `k3s-aws` → `_err`. This repeats the Makefile check for Slack and direct callers.
- **Stored app.** The resolved app is written to `${_ACG_STATE_DIR}/app` after the checkpoint clear, before Step 0.
  - With `K3DM_RESUME=1` and `K3DM_APP` empty, the stored value is used. The Slack/webhook resume (`scripts/lib/webhook/lifecycle.py:363-365`) never passes APP.
  - When both are set and they differ → `_err` naming both.
  - A fresh run (not a resume) overwrites the file.
- Under none, these run unchanged and in order:
  - the sandbox sign-in prompt;
  - the checkpoint clear;
  - Step 0, `known_hosts` prune;
  - Step 1, credentials.
- **Step 2 under none** calls the new provider function `k3s_aws_provision_nodes --confirm` instead of `deploy_cluster`, and writes its own checkpoint `step-2-nodes`, not `step-2-cluster`. A later shopping-cart resume must not skip the k3s install.
- After Step 2, under none, `bin/cluster-up` runs **Step 12** (the TTL watcher, `acg_watch_start`). Then it prints a summary, one line per node:
  - role, as `server` / `agent<N>`: they are only names, since no k3s is installed;
  - public IP;
  - the SSH command, using `UBUNTU_K3S_SSH_KEY` and the default user.

  Then it exits 0. Nothing else runs: no Docker or OrbStack check, tunnel, hub, Vault, ArgoCD, ESO, Keycloak, observability or shopping-cart.
- Log line under none, printed once, right after resolution: `[acg-up] APP=none — bare nodes only: no k3s, hub, Vault, ArgoCD or apps`.

### 3. `k3s_aws_provision_nodes` (in `scripts/lib/providers/k3s-aws.sh`)

- Does the same pre-flight TTL extend and the same CloudFormation create/reuse/recreate handling as `deploy_cluster` (`k3s-aws.sh:213-237` region). Extract that block into a private helper `_k3s_aws_ensure_stack` that both functions call, with no change in `deploy_cluster`'s behaviour or log lines.
- Does **not** call `deploy_app_cluster`, wait for k8s nodes, label nodes or merge a kubeconfig.
- Honours the existing `ACG_AGENT_COUNT` (total nodes = 1 + count; validated as today). The cap, `NODE_COUNT` and `OS` are the follow-on plan.
- If the stack already existed and was healthy, print `_warn "[k3s-aws] reusing existing stack — nodes may still run k3s from an earlier make up; run make down first for clean nodes"`.
- Waits for the instances to be reachable on SSH, the same way the current code does before the k3s install, so the summary's SSH commands work. If the existing code has no such wait, use `aws ec2 wait instance-status-ok` on the stack's instances, and say which in the report.
- Has a `-h|--help` text in the same style as `deploy_cluster`.

### 4. Other commands on a stored none

- `make down`: no code change. Stack teardown works as today. Hub deregistration finds nothing to remove; if the hub is not running, it only warns, which is the existing behaviour at `bin/cluster-down:161-166`. E2 confirms this.
- `make refresh` (`bin/cluster-refresh`): when `${_ACG_STATE_DIR}/app` reads `none`, exit 2 at the top with `refresh does not apply to APP=none (no k3s); use make up APP=none`. This is the only change to that file.

### 5. Docs

The README section that documents `make up` gets one paragraph covering:
- what APP=none gives you (bare nodes, SSH, the TTL watcher) and what it skips;
- that it is k3s-aws only;
- the follow-on `OS`/`NODE_COUNT` plan;
- the Known limits.

### Known limits (record, do not fix)

- Fresh Slack `/acg-up` runs always build shopping-cart. Only resume honours the stored app.
- The nodes use the existing Ubuntu AMI and instance types. Windows nodes come in the follow-on plan.
- `make down` may print the existing hub-deregister warning when the hub is not running.

## Contract readers

- `K3DM_APP`: new.
  - Written by: Makefile `up:`, through `bin/k3dm-up-app-check`.
  - Read by: `bin/cluster-up`.
  - Not passed by `lifecycle.py:363-365`; resume uses the stored app.
- `${_ACG_STATE_DIR}/app`: new.
  - Written by: `bin/cluster-up`.
  - Read by: `bin/cluster-up` (resume) and `bin/cluster-refresh`.
- Checkpoint `step-2-nodes`: new.
  - Written and read only by `bin/cluster-up`.
  - The existing `step-2-cluster` is unchanged.
- Make `APP`: the existing readers are `Makefile:1464-1484`. They are unaffected, because there is no top-level default.
- `deploy_cluster` (k3s-aws): its stack block is moved into `_k3s_aws_ensure_stack`.
  - Callers: `bin/cluster-up:576`, `Makefile:344`.
  - Behaviour and log lines are unchanged; the existing provider bats tests stay green unedited.
- `bin/cluster-up --trust-vault-ca` (callers: `Makefile:168`, `lifecycle.py:363`): unaffected, because resolution runs after that early exit.

## What NOT to Do

- Do not change any behaviour when APP is not given or is `shopping-cart`: no step reordering, no renamed log lines.
- Do not edit:
  - `shopping_cart.sh`, `argocd.sh` or the ApplicationSets;
  - `bin/cluster-down` or `lifecycle.py`;
  - `scripts/etc/acg-cluster.yaml`;
  - lib-foundation (`scripts/lib/foundation/`).
- Do not run `make up`, `make down`, `make refresh`, `make -n <lifecycle target>`, `bin/cluster-up` unstubbed, or any `aws` command.
- Test the Makefile wiring through `bin/k3dm-up-app-check`, plus a structural check that the `up:` recipe's first line calls it.
- Do not push, open a PR or skip hooks. Leave the changes uncommitted.
