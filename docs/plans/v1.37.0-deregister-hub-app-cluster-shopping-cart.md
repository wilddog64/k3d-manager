# v1.37.0 — Stop the hub syncing shopping-cart, without breaking the hub's ESO

**Target branch:** `k3d-manager-v1.37.0`
**Status:** **EXECUTED 2026-09-23.** Selectors applied, ApplicationSets reapplied, all seven
shopping-cart Applications gone, option **3a** taken (both namespaces deleted). `ubuntu-k3s-eso` and
`ubuntu-k3s-grafana-dashboards` survived Synced/Healthy with 23 ESO CRDs, 3 Deployments and
`ClusterSecretStore/vault-backend` intact. Remaining: nothing. See the completion note at the end.

**Supersedes the de-registration approach.** An earlier revision of this spec proposed deleting
`Secret cicd/ubuntu-k3s-app-cluster`. That was withdrawn on 2026-09-23 after its own Task 0 proved
it would destroy the hub's External Secrets Operator — see
[Why the first approach was withdrawn](#why-the-first-approach-was-withdrawn). **Do not reinstate
it.** History is in git (`d6297a2c`) and in the `memory-bank/activeContext.md` abort entry.

---

## The goal

Operator decision (2026-09-23): **the hub should not run the shopping-cart data layer or the payment
stack.** Tier 1 (ephemeral vCluster) and Tier 2 (ACG sandbox) each carry their own substrate under
`scripts/etc/e2e/` — `postgres.yaml`, `redis.yaml`, `payment.yaml`, `basket.yaml`, `order.yaml`,
`product-catalog.yaml` and a digest-pinned `kustomization.yaml`. That substrate is independent of
`shopping-cart-infra`'s `data-layer`, so removing hub-side shopping-cart syncing cannot affect
either tier. Verified, not assumed.

The hub **must keep** its ESO install and its three ACG Grafana dashboards, which today are
generated by the same cluster registration.

## Why the first approach was withdrawn

`Secret cicd/ubuntu-k3s-app-cluster` registers cluster `ubuntu-k3s` at
`server=https://kubernetes.default.svc` — the hub itself. It is the **only** Secret carrying
`k3d-manager/role: app-cluster`, and **four** ApplicationSets select on that label:

| AppSet | Generates on the hub | `preserveResourcesOnDeletion` | Deletion finalizer |
|---|---|---|---|
| `eso` | `ubuntu-k3s-eso` — **the hub's entire ESO install** | unset (prunes) | present |
| `grafana-dashboards-acg` | `ubuntu-k3s-grafana-dashboards` — 3 `monitoring` ConfigMaps | unset (prunes) | present |
| `data-git` | `ubuntu-k3s-data-layer` | unset (prunes) | present |
| `services-git` | `ubuntu-k3s-shopping-cart-*` (6) | `true` (preserves) | absent |

`ubuntu-k3s-eso` owns 3 Deployments, **21 CRDs**, 5 ClusterRoles, 2 ValidatingWebhookConfigurations
and the ServiceAccounts in `secrets`, and it carries `resources-finalizer.argocd.argoproj.io`.
Deleting the registration would cascade: the `externalsecrets.external-secrets.io` and
`clustersecretstores.external-secrets.io` CRDs go, removing **all 22 ExternalSecret CRs
cluster-wide** and `ClusterSecretStore/vault-backend`; ESO sets `ownerReferences` on the Secrets it
creates (verified on `monitoring/grafana-admin-credentials` and `identity/keycloak-secrets`), so GC
then deletes `grafana-admin-credentials`, `keycloak-secrets`, `keycloak-client-secrets`,
`ldap-secrets`, `openldap-admin`, `ghcr-pull-secret` and every postgres / redis / rabbitmq / minio
credential. The three ACG dashboard ConfigMaps (`checkout-loadtest-dashboard`,
`k3dm-deployment-metrics`, `trivy-security-dashboard`) are **not** duplicated by
`hub-grafana-dashboards`, which carries a different four.

**The registration is load-bearing, not merely bogus.** `register_app_cluster`
(`scripts/plugins/argocd.sh`) has an explicit `_in_cluster` branch that emits `config: {}` for a
self-registration, and `_argocd_set_active_app_cluster` moves the `role: app-cluster` label onto
whichever cluster is currently active. Hub-as-app-cluster is a **designed single-cluster mode**, not
an accident. What changed is the operator's intent, not the correctness of the code.

**`ubuntu-k3s` is a role alias, not a place.** The name predates this from the ACG sandbox era, and
Tier 2 still self-registers the same name inside a sandbox's own ArgoCD
(`scripts/plugins/e2e.sh:122-138`) — correct *there*, because in a sandbox the app cluster genuinely
is in-cluster. There is no `ubuntu-k3s` kubecontext on the workstation; only `k3d-k3d-cluster` and
`ubuntu-hostinger`.

## Approach: an opt-in shopping-cart label

Add a second, explicit label requirement to **`data-git` and `services-git` only**. `eso` and
`grafana-dashboards-acg` keep their current selector, so the hub keeps ESO and its dashboards.

Default is **absent = no shopping-cart**, so the hub stops generating shopping-cart Applications the
moment the AppSets are reapplied, with no change to the registration Secret and no deletion cascade.

Rejected alternatives:

- **`k3d-manager/managed: "true"` as the discriminator.** `_managed` defaults to `false` and
  `"true"` additionally demands provider + sandbox-id + expires-at + release metadata
  (`argocd.sh:1447-1455`). It means "metadata-complete ephemeral registration", not "runs
  shopping-cart", and would silently exclude a long-lived hostinger app cluster.
- **Selecting on the server field.** ArgoCD cluster generators match labels only; `server` is not
  selectable.
- **A live `kubectl patch` of the selector.** Reverted by selfHeal and again by the release-time
  AppSet reapply. `scripts/etc/argocd/applicationsets/` is the only durable write point.

## Task 2 — Emit the label from `register_app_cluster`

In `scripts/plugins/argocd.sh`, alongside the existing `_managed` handling, add an opt-in variable
defaulting to `false`, and write it into the Secret's label block next to `k3d-manager/managed`:

```yaml
    k3d-manager/shopping-cart: "${_shopping_cart}"
```

Requirements:

- Default `false` — `ARGOCD_APP_CLUSTER_SHOPPING_CART:-false`.
- Accept only `true` / `false`; reject anything else with `_err` and a non-zero return, matching the
  existing validation style.
- Document the variable in the `register_app_cluster` help text, which already lists
  `ARGOCD_APP_CLUSTER_*` variables.
- Do **not** change `_argocd_set_active_app_cluster`. The `role` label stays a pointer to the active
  app cluster; this new label is orthogonal.

## Task 4 — Leave `shopping-cart-identity` alone

It is **excluded** from the `services-git` git generator, has no `ownerReferences`, and targets
namespace `identity` directly. Independent lifecycle, independent defect:

```
PersistentVolumeClaim "postgres-keycloak-pvc" is invalid:
  spec is immutable after creation except resources.requests and volumeAttributesClassName
  - VolumeName:       "pvc-e32941a3-014a-4149-b102-6d478871be37"
  + VolumeName:       ""
  - StorageClassName: &"local-path"
  + StorageClassName: nil
```

ArgoCD is trying to `replace` a bound PVC with a spec that blanks `volumeName` and
`storageClassName`. Fix is `ignoreDifferences` on those two fields plus
`RespectIgnoreDifferences=true` — **file separately as a `docs/bugs/` spec; out of scope here.**
Most likely also why `keycloak-realm-reconcile` is `Failed 0/1`.

## What this also closes

`ubuntu-k3s-data-layer` has been failing its sync atomically:

```
SyncError: namespaces "shopping-cart-payment" not found (retried 5 times)
```

`CreateNamespace=true` creates only the app's *destination* namespace (`shopping-cart-data`), while
its manifests span four (`secrets`, `shopping-cart-apps`, `shopping-cart-data`,
`shopping-cart-payment`). ArgoCD does not create non-destination namespaces, so the sync fails as a
unit and **all seven StatefulSets are never created** — hence Services-only in `shopping-cart-data`,
and three `shopping-cart-apps` pods in `CrashLoopBackOff` on
`postgresql-orders...: no such host`. Not generating the Application at all removes the failure
along with its cause.

## Risks

- **`preserveResourcesOnDeletion: true` makes Task 3 look incomplete.** The `services-git`
  Applications vanish and the pods keep running. Documented behaviour.
- **`data-git` prunes and holds the resources finalizer.** Today that is only Services; if
  StatefulSets appear before execution, Task 0 must stop the work.
- **Reapplying the AppSets is what activates the change.** Until then the config is inert in git —
  the same trap that froze `trivy-operator` for two releases.
- **A future `register_app_cluster` run re-registers the hub without the new label**, which is the
  desired outcome, but a run with `ARGOCD_APP_CLUSTER_SHOPPING_CART=true` against the hub would
  restore the old behaviour. The guide section must say so.
- **`scripts/etc/argocd/cluster-secret.yaml.tmpl` is orphaned** — nothing references it, and it
  writes only `role: app-cluster`. It is stale relative to the inline heredoc in
  `register_app_cluster`. Do not edit or rely on it here; note it for a follow-up.
- **Does not fix Tier 2 Stripe.** Stripe stays capped at 2/4 because P3
  (`KeycloakRealmRoleConverter` absent from `shopping-cart-payment` `origin/main`) is untouched and a
  PR there is not approved.
- **Does not fix the ACG Keychain gap.** See
  [v1.37.0-acg-autologin-enablement-for-tier2.md](v1.37.0-acg-autologin-enablement-for-tier2.md).
