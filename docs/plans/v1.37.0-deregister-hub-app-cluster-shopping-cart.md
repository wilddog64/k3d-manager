# v1.37.0 — De-register the hub's self-referential app-cluster and stop syncing shopping-cart onto the hub

**Target branch:** `k3d-manager-v1.37.0`
**Status:** **TASK 1 WITHDRAWN — DO NOT EXECUTE.** Task 0 ran on 2026-09-23 and proved the
premise below is wrong. Two more ApplicationSets (`eso`, `grafana-dashboards-acg`) select the same
`k3d-manager/role: app-cluster` label, and `ubuntu-k3s-eso` is **the hub's entire External Secrets
Operator install** — 3 Deployments, 21 CRDs, 5 ClusterRoles — carrying
`resources-finalizer.argocd.argoproj.io`. Deleting the registration Secret would remove the ESO
CRDs, which deletes all 22 ExternalSecret CRs cluster-wide and, via `ownerReferences`, the Secrets
they produce (`grafana-admin-credentials`, `keycloak-secrets`, `ldap-secrets`, `ghcr-pull-secret`,
every postgres / redis / rabbitmq / minio credential). The registration is load-bearing.

See `memory-bank/activeContext.md` (2026-09-23 abort entry) for the full evidence. The operator
decision — no shopping-cart on the hub — stands; the delivery mechanism must change to narrowing
the `data-git` and `services-git` selectors in `scripts/etc/argocd/applicationsets/` so they stop
matching the hub, while `eso` and `grafana-dashboards-acg` keep matching. A superseding spec is
required before any live mutation.

---

## Why this spec exists

The hub's ArgoCD carries a cluster registration that points at the hub itself:

```
Secret cicd/ubuntu-k3s-app-cluster   (created 2026-09-21T00:26:24Z)
  name:   ubuntu-k3s
  server: https://kubernetes.default.svc      <-- in-cluster = the hub
  labels: k3d-manager/role: app-cluster
          k3d-manager/provider: k3d
          k3d-manager/managed: false
          k3d-manager/release: unknown
```

Two ApplicationSets select on exactly that label:

| AppSet | Generator | `preserveResourcesOnDeletion` |
|---|---|---|
| `data-git` | `clusters` selector `k3d-manager/role: app-cluster` | **unset** (resources ARE pruned) |
| `services-git` | `matrix` of a `git` directories generator (`services/*`, excluding `services/shopping-cart-identity`) × the same `clusters` selector | **`true`** (resources SURVIVE) |

Because the only cluster bearing `role: app-cluster` is the hub's own self-registration, both
AppSets generate hub-targeted Applications: `ubuntu-k3s-data-layer`, and
`ubuntu-k3s-shopping-cart-{basket,order,product-catalog,frontend,payment,namespace}`.

**The name is misleading and has misled at least one session.** `ubuntu-k3s` originates from the
ACG AWS sandbox era, and Tier 2 still legitimately self-registers that same name inside a sandbox's
own ArgoCD (`scripts/plugins/e2e.sh:122-138`) — correct *there*, because in a sandbox the app
cluster genuinely is in-cluster. The registration described above is a **different** Secret, in a
different namespace, on the hub. There is no `ubuntu-k3s` kubecontext on the workstation; only
`k3d-k3d-cluster` and `ubuntu-hostinger` exist.

`managed: false` and `release: unknown` are not values the normal release path writes.

### Decision (operator, 2026-09-23)

**The hub should not run the shopping-cart data layer or the payment stack at all.** Tier 1
(ephemeral vCluster) and Tier 2 (ACG sandbox) each carry their **own** substrate under
`scripts/etc/e2e/` — `postgres.yaml`, `redis.yaml`, `payment.yaml`, `basket.yaml`, `order.yaml`,
`product-catalog.yaml`, plus a digest-pinned `kustomization.yaml`. That substrate is entirely
independent of `shopping-cart-infra`'s `data-layer` path, so removing the hub's shopping-cart
syncing **cannot** affect either tier. This was verified before the decision, not assumed.

### What this closes

`ubuntu-k3s-data-layer` currently fails its sync atomically:

```
SyncError: namespaces "shopping-cart-payment" not found (retried 5 times)
```

`CreateNamespace=true` creates only the app's *destination* namespace (`shopping-cart-data`), while
the app's manifests span four namespaces (`secrets`, `shopping-cart-apps`, `shopping-cart-data`,
`shopping-cart-payment`). ArgoCD does not create non-destination namespaces. Because the sync
fails as a unit, **all seven StatefulSets are never created** — hence an empty `shopping-cart-data`
holding only Services, and three `shopping-cart-apps` pods in `CrashLoopBackOff` on
`postgresql-orders...: no such host`.

Creating the missing namespace would have "fixed" the symptom by deepening the misconfiguration.
This spec removes the cause instead.

## Task 1 — Delete the registration Secret FIRST (ordering is load-bearing)

```bash
kubectl --context k3d-k3d-cluster -n cicd delete secret ubuntu-k3s-app-cluster
```

**Deleting the generated Applications first does not work** — both AppSets immediately regenerate
them from the still-present cluster registration. The registration Secret is the generator input,
so it goes first. This is the same ordering trap recorded for previous AppSet cleanups.

Then confirm the AppSets have stopped generating:

```bash
kubectl --context k3d-k3d-cluster -n cicd get applications.argoproj.io \
  | grep -c '^ubuntu-k3s-'      # expect 0
```

Allow a reconcile interval before concluding it failed.

## Task 2 — Clean up what `preserveResourcesOnDeletion: true` leaves behind

`services-git` sets `preserveResourcesOnDeletion: true`, so removing its generated Applications
**leaves the deployed workloads running**. After Task 1 the `shopping-cart-apps` Deployments will
still exist, now unmanaged by any Application.

Decide with the operator, then execute exactly one:

- **2a — remove them**: delete the `shopping-cart-apps` and `shopping-cart-data` namespaces. This
  also clears the three `CrashLoopBackOff` pods and the orphaned Services.
- **2b — leave them**: keep the namespaces as an unmanaged local demo. Record this explicitly in
  `memory-bank/activeContext.md`, because unmanaged workloads with no owning Application are
  exactly what future sessions misread as a sync failure.

**Do NOT delete the `secrets` namespace** — it is shared (it holds `vault-root` and
`vault-seed-backup`), not a shopping-cart namespace.

## Task 3 — Leave `shopping-cart-identity` alone

`shopping-cart-identity` is **excluded** from the `services-git` git generator
(`exclude: true, path: services/shopping-cart-identity`), has no `ownerReferences`, and targets
namespace `identity` on `https://kubernetes.default.svc` directly. It has an independent lifecycle
and an independent, unrelated defect:

```
PersistentVolumeClaim "postgres-keycloak-pvc" is invalid:
  spec is immutable after creation except resources.requests and volumeAttributesClassName
  - VolumeName:       "pvc-e32941a3-014a-4149-b102-6d478871be37"
  + VolumeName:       ""
  - StorageClassName: &"local-path"
  + StorageClassName: nil
```

ArgoCD is attempting to `replace` a bound PVC with a spec that blanks `volumeName` and
`storageClassName`. The fix is `ignoreDifferences` on those two fields plus
`RespectIgnoreDifferences=true` — **file that separately as a `docs/bugs/` spec; it is out of scope
here.** This is also the most likely reason `keycloak-realm-reconcile` has been `Failed 0/1`.

## What NOT to do

- Do **not** create the `shopping-cart-payment` namespace on the hub. That treats the symptom and
  entrenches the misconfiguration this spec removes.
- Do **not** delete the generated Applications before the registration Secret — they regenerate.
- Do **not** touch `scripts/etc/e2e/`. Its `payment.yaml` and `postgres.yaml` are the Tier 1 / Tier 2
  substrate and must keep working; they are unrelated to `shopping-cart-infra`'s `data-layer`.
- Do **not** modify the Tier 2 in-sandbox registration at `scripts/plugins/e2e.sh:122-138`. Its
  `server: https://kubernetes.default.svc` is correct in a sandbox.
- Do **not** delete the `secrets` namespace.
- Do **not** prune anything in the `shopping-cart-infra` repo — not approved, and not needed here.
- Do **not** open a PR in `shopping-cart-payment` — not approved.
- Do **not** create a PR, merge, commit to `main`, force-push, or use `--no-verify`.
- Do **not** edit the upstream subtrees.

## Risks

- **`preserveResourcesOnDeletion: true` makes Task 1 look incomplete.** The Applications vanish and
  the pods keep running. That is the documented behaviour, not a failed deletion.
- **`data-git` has no `syncPolicy`, so its resources ARE pruned.** Today that is only Services in
  `shopping-cart-data`, but re-verify in Task 0 — if StatefulSets have since come up, deleting the
  registration destroys their PVCs.
- **Reapplying the AppSets before Task 1 silently undoes it.** Ordering is not cosmetic.
- **This does not fix Tier 2 Stripe.** Stripe stays capped at 2/4 because P3
  (`KeycloakRealmRoleConverter` absent from `shopping-cart-payment` `origin/main`) is untouched and
  a PR there is not approved.
- **This does not fix the ACG Keychain gap.** See
  [v1.37.0-acg-autologin-enablement-for-tier2.md](v1.37.0-acg-autologin-enablement-for-tier2.md).
