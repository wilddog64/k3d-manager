# v1.44.0 — Cloud-request Slack notification routing

**Status:** PROPOSED — enhancement specification; no runtime changes
**Owner:** cloud-bridge and webhook maintainers
**Motivation:** Cloud requests currently notify one webhook-configured Slack channel. Operators
need approved cloud jobs, such as long-running `make-test-all` requests, to reach the channel
responsible for test results without redirecting every webhook notification.

## Problem statement

The webhook uses one `SLACK_CHANNEL_ID` for bot notifications. A cloud request submitted from
the CLI has no originating Slack channel or `response_url`, so its lifecycle messages all go to
that single configured channel. Temporarily changing the environment variable is global, requires
a service restart, and can misroute unrelated status, alert, or job messages.

## Goals

- Route notifications for an individual cloud request to an approved Slack channel alias.
- Preserve the current default channel when no route is supplied.
- Keep routing deterministic across queued, running, progress, success, and failure messages.
- Prevent request data from selecting arbitrary Slack channels.
- Keep the existing response, artifact, redaction, role, and cloud-request trust boundaries.
- Make the selected route visible in safe job metadata without exposing channel secrets.

## Non-goals

- Accepting arbitrary Slack channel IDs, channel names, webhooks, or response URLs from a request.
- Allowing a cloud request to change its execution role or action permissions.
- Replacing Slack `response_url` handling for commands submitted directly in Slack.
- Supporting multiple notification destinations in the first version.
- Changing the existing one-channel behavior for webhook-originated notifications that do not opt
  into routing.

## Proposed design

### 1. Alias configuration

Add a server-side allowlist, supplied through the webhook LaunchAgent environment or its existing
secret/configuration mechanism:

```text
K3DM_SLACK_NOTIFICATION_ROUTES=default:C012OPS,testing:C034TEST,incidents:C056INCIDENTS
```

The parser must reject duplicate aliases, empty aliases, malformed channel IDs, and duplicate
channel IDs unless an explicit policy permits aliases to share a channel. Channel IDs remain
configuration values; they must never be printed in normal job output.

`default` resolves to the current `SLACK_CHANNEL_ID`. If the route map is absent or invalid, the
service must fail closed to the existing default channel and emit a redacted configuration warning
at startup. It must not silently route to a request-provided destination.

### 2. Request contract

Add an optional `notify_route` field to cloud-request actions that produce asynchronous jobs:

```json
{
  "action": "make-test-all",
  "notify_route": "testing"
}
```

The bridge validates the field against the configured alias set before accepting the request. An
unknown alias is rejected with a stable client error that lists allowed aliases only when policy
allows that information; otherwise it reports `invalid notification route`.

The accepted job record stores only the validated alias, not a raw channel ID. Existing requests
without the field use `default` and remain wire-compatible.

### 3. Notification delivery

Resolve the alias once when the job is accepted and pass the resolved, server-side route through
the job lifecycle. The notifier should use the selected channel for:

- job-started messages;
- periodic progress messages;
- terminal success or failure messages;
- failure-analysis and cleanup follow-ups belonging to that job.

The route must remain fixed if configuration changes while a job is running. If the selected
channel is unavailable, preserve the existing fallback behavior and record a bounded delivery
warning; never retry by posting to an arbitrary channel.

Direct Slack commands continue using their existing channel/thread context. This feature applies
only to cloud-request jobs that explicitly select an approved route.

### 4. Safe observability

Expose `notify_route` in the job summary and terminal response as the alias only. Do not expose the
channel ID, bot token, webhook URL, or configuration string. Add a low-cardinality metric or log
field only if it uses the bounded alias set; do not label metrics with user-controlled values.

## Security and privacy requirements

- Route aliases are server-controlled and deny-by-default.
- Validate the request before queueing or executing the job.
- Store aliases, never raw channel IDs, in job state and cloud-request artifacts.
- Reuse existing request authentication, action allowlists, role checks, Slack URL allowlists,
  redaction, and bounded-output limits.
- Do not use a Slack channel name lookup at job runtime; channel names are mutable and introduce
  an unnecessary API dependency.
- Configuration changes require the normal webhook restart/reload procedure and must not alter
  already accepted jobs.

## Test plan

Add focused tests for:

1. missing `notify_route` selects `default`;
2. a valid alias is persisted and delivered to its configured channel;
3. an unknown alias is rejected before a job starts;
4. malformed, duplicate, empty, and oversized route configuration fails closed;
5. the raw channel ID is absent from job output, summaries, and artifacts;
6. queued, progress, success, failure, analysis, and cleanup notifications retain one route;
7. a route-map change does not move an already accepted job;
8. delivery failure does not redirect to another channel;
9. existing Slack `response_url` and thread behavior is unchanged;
10. cloud-request actions without notifications preserve current behavior.

Mutation checks should prove that removing validation, storing the raw channel ID, or falling back
to the default channel after a selected-route delivery failure makes the focused tests fail.

## Rollout and acceptance

1. Add the route configuration with only `default` enabled; verify no behavior change.
2. Add a `testing` alias and submit one `make-test-all` request using it.
3. Confirm start, progress, terminal status, and any failure analysis appear only in the testing
   channel, with the existing bounded output and thread behavior.
4. Submit a request without `notify_route` and confirm it still reaches the default channel.
5. Submit an unknown alias and confirm HTTP/client rejection with no job created.
6. Restart the webhook after configuration changes and verify the bridge remains compatible.
7. Update the cloud-request guide with the alias contract, examples, failure behavior, and the
   restart requirement.

## Open decisions

- Should route aliases be configured in the webhook LaunchAgent plist, Vault, or both with a
  documented precedence order?
- Should operators be allowed to select a route from Slack `/k3dm` commands, or only from the
  CLI/cloud-request API?
- Should the default alias be configurable independently from `SLACK_CHANNEL_ID`, or should it
  always remain the existing channel for backward compatibility?
