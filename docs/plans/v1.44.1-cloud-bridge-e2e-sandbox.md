# v1.44.1 — Cloud-bridge Tier 2 dispatch: `make-e2e-sandbox` under the `cloud-runner` role

**Status:** PLANNED — blocked on v1.44.0 (`v1.44.0-cloud-request-submitter-authentication.md`)
**Approval:** approved — operator, 2026-10-17: "go ahead to write that spec as you suggested" (the design below: expose `e2e-sandbox`, not `e2e-sandbox-provision`; cloud-runner only; single-flight; Slack notice; fail closed on an expired ACG session)
**Branch:** `k3d-manager-v1.44.1`, cut from `main` after v1.44.0 merges

## What the operator asked for

A cloud Claude session should be able to debug the live sandbox path itself: bring the ACG
sandbox up, run Tier 2 against it, and read the result. Today it can do the first step
(`sandbox-up`, `cluster-up@aws`) and Tier 1 (`make-e2e`, `make-e2e-remote`), but not Tier 2.
The operator also asked whether a self-hosted runner would be better. It would not: it puts the
cloud agent on the operator's network with a shell, Keychain and kubeconfig, which is the
access the bridge exists to withhold.

## This reverses an explicit v1.41.0 decision

`v1.41.0-cloud-bridge-e2e-dispatch.md` excluded `e2e-sandbox` ("not a fit for unattended
dispatch and would need its own decision") and gate M5.7 asserts `cloud-runner` is refused for
it. `scripts/tests/bin/test_cloud_bridge.py` lists it in `NEVER_EXPOSED`. This spec is that
decision. The reasons it was excluded are each answered below rather than waived:

| v1.41.0 concern | Answer here |
|---|---|
| One agent per live sandbox | M2: an atomic sandbox lock held for the whole Tier 2 run, on every entry path (tmux, Slack, bridge), naming its holder on refusal |
| 4h ACG session lifetime, interactive login | Unchanged fail-closed preflight (`ACG_SESSION_EXPIRED`); N4 forbids any login path from the bridge |
| Unattended, branch-driven input | Prerequisite: v1.44.0 submitter authentication. No args at all (N2), so request content can choose nothing |

## Scope

- **In:** `e2e-sandbox` (Tier 2 against an existing sandbox).
- **Out:** `e2e-sandbox-provision` stays in `NEVER_EXPOSED`. Provisioning is already reachable as a
  separate, separately bounded step (`sandbox-up`). Chaining two narrow actions is safer than one
  action that both creates infrastructure and runs payments tests.
- **Out:** `e2e-replay`, `e2e-runner-unlock`, `cleanup-stale-sandbox`, `sync-apps` — unchanged.

## Threat model in one paragraph

The cloud session reads repo content, issues and PR text, so it can be prompt-injected. The
worst a bridge request can then do is limited to what the action does with no arguments. For
`e2e-sandbox` that is: run Tier 2 (Stripe **test** mode, synthetic orders) against the sandbox,
for up to 3600 s, using the operator's Keychain-held ACG session and the existing Vault reverse
bridge. The costs to contain are (a) colliding with the operator's own sandbox run or lifecycle
job, (b) secrets in the job output read back through `job-status`, and (c) a run the operator
does not know about. M2–M5 contain each.

## Milestones

**M1 — allow the action.**
- `scripts/lib/webhook/cloud_actions.py` `ACTION_ALLOWLIST`: add
  `"make-e2e-sandbox": ("POST", "/api/v1/make", {}, "e2e-sandbox")`. No args — not even `DIGEST`.
- `scripts/lib/webhook/policy.py`: `CLOUD_RUNNER_TARGETS = {"e2e-remote", "e2e", "e2e-sandbox"}`.
  `cloud-runner` stays out of `_ROLE_LEVELS`.
- `bin/k3dm-cloud-bridge` token selection (the `target in ("e2e-remote", "e2e")` test near line
  213): include `"e2e-sandbox"` so the bridge presents the cloud-runner token, never admin.
- `scripts/tests/bin/test_cloud_bridge.py` `NEVER_EXPOSED`: remove `e2e-sandbox` only.

**M2 — single-flight sandbox lock (all entry paths).**
`e2e_verify_sandbox` (`scripts/plugins/e2e.sh`) has no lock today, so the operator's tmux run, a
Slack `/k3dm e2e-sandbox` and a bridge request can overlap on one sandbox. Add an atomic
`mkdir` lock (same pattern as `_e2e_remote_lock_acquire`) taken before the first sandbox-touching
phase and released by an EXIT/INT/TERM trap. It writes `meta` with `owner=<host> pid=<pid>
ts=<epoch> via=<tmux|slack|bridge>` (`via` from an env var the webhook sets; unset → `tmux`).
On contention it fails before any sandbox or AWS call with
`[e2e] sandbox busy (lock held: <meta>); not running` and leaves the lock untouched. A lock whose
`pid` is not alive on this host is reported as stale in the message but **not** cleared —
clearing stays a human action. Applies equally to `e2e-sandbox-provision`.

**M3 — no lifecycle overlap from the bridge.**
In `bin/k3dm-webhook`, a `cloud-runner` request is refused with HTTP 409 when:
- it is `make` `e2e-sandbox` and `_running_cluster_job()` returns a job; or
- it is the `/api/v1/cluster` route (`sandbox-up`/`sandbox-down`) and a make job with target
  `e2e-sandbox` or `e2e-sandbox-provision` is `running` in `JOB_DIR`.
The message names the other job id and action. Operator and admin paths are unchanged.

**M4 — pattern redaction on cloud-runner job output.**
`_redact_secrets` only knows values the webhook process registered; Tier 2 reads its Stripe key
and Keycloak passwords in a child process. For jobs started by `cloud-runner`, apply an
additional precompiled `re.sub` before output is written to `JOB_DIR/<id>/output` and before
`job-status` returns it, covering at least: `sk_(test|live)_[A-Za-z0-9]+`,
`rk_(test|live)_[A-Za-z0-9]+`, `whsec_[A-Za-z0-9]+`, `hvs\.[A-Za-z0-9_-]+`, and
`(?i)(password|client_secret)["'=: ]+\S+` → `***REDACTED***`. Use `re.sub` with a compiled
pattern (see `reference_codeql_str_replace_redaction_trips_cleartext_storage`), not `str.replace`.

**M5 — operator notice.**
When the webhook accepts a `cloud-runner` `e2e-sandbox` request, post one message to
`SLACK_CHANNEL_ID` (or the v1.44.0-approved alias when that request names one):
`☁️ cloud request started make e2e-sandbox — job <id>, requested_by <verified submitter>`, and a
second on completion with the terminal status. Never include output in either message.

**M6 — docs.**
- `docs/howto/cloud-session-requests.md`: the new action in the table; the chain
  `sandbox-up` → `job-status` → `make-e2e-sandbox` → `job-status`; the busy refusal and what to do
  (ask the operator, never unlock); the expired-session refusal (`ACG_SESSION_EXPIRED` — ask the
  operator to sign in from a terminal); update the action count and the "remain refused" sentence.
- `docs/howto/slack-slash-commands.md`: the sandbox lock and its refusal message.
- `docs/architecture/cloud-bridge.md`: `e2e-sandbox` in the cloud-runner capability set.
- `CHANGELOG.md` under `[Unreleased]`.

## Before You Start

- Read `memory-bank/activeContext.md`, then this spec, `v1.41.0-cloud-bridge-e2e-dispatch.md`
  and `v1.44.0-cloud-request-submitter-authentication.md` (must already be merged).
- Read the targets: `scripts/lib/webhook/cloud_actions.py`, `scripts/lib/webhook/policy.py`,
  `bin/k3dm-cloud-bridge`, `bin/k3dm-webhook` (`_running_cluster_job`, the `make` and `cluster`
  handlers, `_redact_secrets`, `_notify_job`), `scripts/plugins/e2e.sh` (`e2e_verify_sandbox`),
  `scripts/plugins/e2e_remote.sh` (`_e2e_remote_lock_acquire`, as the lock pattern).
- Branch: `k3d-manager-v1.44.1`. `git pull origin k3d-manager-v1.44.1`.

## Rules

- Webhook tests must override `K3DM_JOB_DIR` and `K3DM_RUN_DIR` (see `project_webhook_smoke_gate`).
- No test touches AWS, ACG, a cluster, Slack, or a Pushgateway.
- `shellcheck -S warning` clean on changed shell files; `make test-pytest` and the touched BATS
  suites green; every `must_not` shown red against the pre-fix tree in a temp worktree.
- After merge: `make restart-webhook` (operator) so the running webhook and bridge load the change.

## What NOT to Do

- Do NOT expose `e2e-sandbox-provision` or add any arg to `make-e2e-sandbox`.
- Do NOT add `cloud-runner` to `_ROLE_LEVELS`, or hand the bridge the admin token.
- Do NOT clear a sandbox lock anywhere in code.
- Do NOT create a PR, skip hooks (`--no-verify`), commit to `main`, or touch files outside the targets.
