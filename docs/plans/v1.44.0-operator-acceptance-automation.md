# v1.44.0 — Automated operator acceptance and evidence reporting

**Status:** PROPOSED — no runtime changes
**Milestone:** v1.44.0 candidate, plan 3 of 5 at drafting
**Owner:** testing, cloud-bridge, webhook, and observability maintainers

## Problem

Manual operator testing found failures across cloud job submission, log retrieval, metric
publication, Grafana state transitions, Slack cleanup help, and document indexing. Source
assertions and a passing terminal suite did not prove that cloud/Slack users received the same
result or that dashboards remained correct after failure and recovery.

Turn those checks into repeatable acceptance scenarios with explicit oracles and evidence.
First deliver one pilot for k3dm Tests; reuse its harness for other dashboards later.
This plan defines the acceptance harness, not a fleet-wide dashboard rewrite.

## Deliverables

- A scenario runner with machine-readable JSON, JUnit, and a readable Markdown report.
- An isolated k3dm Tests acceptance profile with pinned Prometheus/Pushgateway/Grafana and
  Playwright versions, the real exporter/dashboard, deterministic fixtures, and command stubs.
- A bounded opt-in live profile validating supported cloud requests and Grafana retrieval.
- Redacted failure evidence and a deterministic deduplicated bug-draft workflow.
- Make entry points and docs for local use, CI, and optional scheduled invocation.

Proposed interface (names are new, not currently available):

```text
make test-operator-acceptance
make test-operator-acceptance-live PROFILE=k3dm-tests
make operator-acceptance-report RUN=<local-run-directory>
```

The default is offline/isolated and requires no production credentials. Include its meaningful
checks in test-all/CI only when dependencies are installed by the pinned setup; missing required
dependencies must not produce a passing zero-test run. Live execution is separate and serialized.
Do not add a cloud action as part of this plan.

## Scenario contract and runner

Each scenario declares a stable ID, fixture revision, required capabilities, tested source SHA,
expected states, assertions, deadline, evidence budget, and teardown. Record deployed dashboard
and service revisions when obtainable; an unknown revision is explicit. Do not treat testing a
different deployed revision as proof that the source revision passed.

Fixtures specify expected case totals; do not hardcode today's total across future revisions.
Keep operator-visible outcomes separate from assertion results: an intentionally failing test
job can make the acceptance scenario pass if it returns the expected failure evidence.

Avoid arbitrary shell strings in scenario configuration. Use fixed adapters and validated
arguments. A runner operation has a deadline and limited retry budget. Read retries are allowed;
never resubmit a mutating job because its response is temporarily missing. Record each phase
(submission, acceptance, execution, response publication, scrape, render, index, retrieval).

## Required pilot scenarios

| Scenario | Required assertions |
|---|---|
| Successful and intentionally failed cloud-style jobs | Stable request/job correlation; queued/running/terminal transitions; exact original exit code; correct terminal classification |
| Bounded output retrieval | Failed case/context plus final log tail survive truncation; passing output remains useful; synthetic secrets are redacted in every exposed artifact |
| Metric publication | Actual fixture totals/failures match published metrics; publication failure is distinct from test failure |
| Pass -> fail -> fail -> pass | Last-run advances each time; last-success remains at prior success across failures/restart; current failures match latest run and clear after recovery |
| Dashboard rendering | Playwright verifies semantic panel titles, units, classification, row fields, current/history distinction, and empty-state explanations; screenshot alone is insufficient |
| Historical failures | Failed cases remain discoverable within selected range after recovery; outside-range rows excluded; repeated scrapes deduplicated; no invented exact run times |
| Stale/no-data/unavailable source | Distinguish recorded stale values, no recorded runs, and failed datasource queries without presenting false health |
| Multiple targets/origins | Aggregation follows documented scope; one target's success must not be misrepresented as another target's success |
| Cleanup help and results | Bare command previews; confirm/apply agree with help; local-only scope; stubs cover absent/removed/failed resources and terminal status |
| File -> fetch -> index -> search | Publication verified first; exact canary document identity returned after indexing deadline; top-k absence alone is not proof of missing ingestion |

Known bugs are input requirements, not automatically fixed by the harness:
[k3dm Tests history](../bugs/2026-10-07-k3dm-tests-failure-history-missing.md),
[last-success retention](../bugs/2026-10-07-test-metrics-last-success-lost-on-failure.md), and
[cleanup reporting](../bugs/2026-10-07-slack-stale-sandbox-cleanup-misleading-reporting.md).
If fixes are pending, report known failing contracts linked to those bugs; do not silently weaken
assertions to make the harness green.

## Isolation and live boundary

The isolated profile uses disposable services, unique fixed-bounded test groupings, deterministic
clock values for metric logic, and a controllable scrape clock for historical assertions. Avoid
wall-clock sleeps for offline age tests. Test genuine Pushgateway PUT replacement and Prometheus
scrapes, not only a mock that duplicates exporter assumptions.

Render the repository dashboard in disposable Grafana. Use stable panel UIDs/IDs and visible
semantic fields rather than fragile CSS coordinates or exact pixel comparison. Verify queries
and transformed rows in addition to screenshots.

Slack adapters use captured contract fixtures or a local fake transport by default. They assert
the outbound notification and request body without messaging real users. Actual Slack delivery
is a separately configured opt-in test destination.

Cleanup apply/error cases always use disposable command stubs. No live cleanup, sandbox up/down,
or resource deletion is part of the default or live acceptance profile. Block ambient CONFIRM,
provider, context, and notification environment values from changing test semantics.

Live mode requires an explicitly configured environment/destination and executes only existing
authorized allowlisted operations. Use test-python-unit as a small bridge smoke by default;
test-all is separately selected and serialized. Do not inject failure into production metrics,
rewrite live dashboard configuration, restart services, or rerun expensive suites automatically.

For live indexing verification, use a designated test-doc prefix/branch in an approved indexed
corpus and publish only a non-secret canary. A signed job/request ID is evidence metadata, not a
Prometheus label. Observe the index checkpoint/backlog when available and retry retrieval with a
bounded schedule aligned to the configured indexing interval (default about five minutes).
Default indexing deadline: 15 minutes, configurable for backlog/quota conditions. Report which
stage failed; a quota pause or unknown checkpoint must not be labeled a confirmed indexer defect.
Canary pruning/retention must operate only in the designated test prefix, never remove real docs.

## Reporting and classification

Use separate scenario outcome and cause fields:

- outcome: passed, failed, skipped, inconclusive;
- cause: product_contract, environment_dependency, harness_error, unknown.

An assertion mismatch with healthy prerequisites is a product-contract finding.
It is not automatically a confirmed production defect. Record reproducibility (single observation,
reproduced isolated, or reproduced live) and whether failure was intentionally injected.
Missing prerequisites are skipped/inconclusive environment results and cannot make a required
release gate green. A harness exception is its own error with diagnostic evidence.

Each report contains scenario/assertion IDs, tested/deployed revisions, timestamps, phase timings,
expected/actual values, original exit code, job/request IDs, redacted excerpts, and artifact links.
Unknown cause/values remain null. Preserve the first failure and cleanup warnings separately.

## Evidence, retention, and bug drafting

Store JSON/JUnit/Markdown, screenshots, and Playwright traces under a private run directory;
directories 0700, files 0600. Default retention: 14 days / 500 MiB, configurable. Never prune
the active run. Collection/pruning failure must not overwrite original scenario results.

Redact before publication. Browser traces/screenshots may contain credentials; default to an
isolated identity and safe fixtures. Unsafe artifacts stay private or are omitted with an explicit
evidence warning. Never publish full environment dumps, Slack response URLs, or tokens.

A finding fingerprint uses stable scenario/assertion and component identifiers, not volatile job
IDs or timestamps. Check existing fingerprints and repository bug paths before vector similarity.
Similarity provides candidates for review; it must not alone merge unrelated reports.

Default output is a bug draft with reproduction, expected/actual, evidence, known/unknown cause,
and proposed acceptance criteria. Existing matched bugs get a proposed evidence update.
Do not automatically reopen fixed bugs or call intentional fixture failures new bugs.
An opt-in filing mode may publish drafts only to an explicitly configured authorized branch;
idempotent writes and lease checks are mandatory. Never auto-fix, deploy, or send Slack messages
as a side effect of running the acceptance suite. Any optional notifications need an explicit
destination and delivery configuration.

## Implementation sequence and release gates

1. Define adapters, fixture/oracle schema, report contract, and dependency checks.
2. Add the isolated exporter -> Pushgateway -> Prometheus -> Grafana pilot and transition cases.
3. Add job/log, fake Slack cleanup, and isolated ingestion/search adapters.
4. Add opt-in live bridge/Grafana/index-canary verification and evidence collection.
5. Add deduplicated bug drafting and document operation/retention.

Required acceptance:

- A known passing fixture yields a complete passing report with nonzero assertion count.
- Deliberately break output selection, last-success retention, failure clearing, dashboard query,
  help alias, and index retrieval in isolation: the corresponding assertion must fail with evidence.
- Injected suite failure with expected reporting passes its acceptance scenario.
- Missing dependency, wrong deployed revision, redaction failure, timeout, and harness exception
  produce honest distinct outcomes; no vacuous success.
- Repeated runs produce one draft per stable finding and preserve previous evidence.
- Default execution cannot reach production cleanup tools or real Slack endpoints.
- One authorized live canary confirms request -> terminal response -> metrics -> rendered panel,
  and one document canary confirms publication -> index -> exact retrieval.
- Existing unit/BATS tests, repository lint/audit/doc-link gates remain green.

No runtime implementation is included in this specification commit.
