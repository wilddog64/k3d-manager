# v1.36.0 — Hub snapshot capture, M2 offload, and retention

**Status:** ASSIGNED (Codex, 2026-09-22)
**Branch:** `k3d-manager-v1.36.0`

## Objective

Capture hub state on the way down so a rebuild comes back with data instead of an
empty Prometheus and an empty Loki.

**The restore half already exists.** `scripts/plugins/hub_recovery.sh` implements
`hub_recovery_plan`, `hub_recovery_validate`, `hub_recovery_targets`,
`hub_recovery_restore` and `hub_recovery_reconcile`, and they were executed
successfully on 2026-09-11 (`docs/plans/v1.33.0-hub-local-path-restore.md`).

What is missing is the **capture** side. Today a capture is a manual procedure.
This task adds a capture that emits **exactly the directory layout
`hub_recovery_restore` already consumes**, offloads it to the M2 box, and prunes
old snapshots.

Do not write a new restore path. Do not modify the existing restore functions
beyond the one additive change in "Loki" below.

## Measured facts (2026-09-22, hub `k3d-k3d-cluster`)

Sizes are real, measured from the k3d nodes' `local-path` trees:

| Claim | On-disk | PVC |
|---|---|---|
| `monitoring/prometheus-…-prometheus-0` | **2.0G** | 25Gi |
| `identity/postgres-keycloak-pvc` | 67M | — |
| `monitoring/storage-loki-0` | **46M** | 10Gi |
| `secrets/data-vault-0` | 23M | 1Gi |

**≈ 2.15G per snapshot**, dominated by Prometheus.

Disk free: **M4 163Gi**, **M2 (`m2jump`, `m2-air.local`) 382Gi**. M2 is the store.

### The retention ceiling — read this before implementing

Hub Prometheus runs with:

```
--storage.tsdb.retention.time=3d
--storage.tsdb.retention.size=8GB
```

Prometheus prunes out-of-retention blocks **on startup**. Restoring a TSDB
snapshot older than 3 days therefore restores blocks that Prometheus immediately
deletes — the feature silently does nothing.

**Consequence:** this feature preserves history across a down/up cycle *within the
3d window*. It does not give long-term history. If long-term history is the goal,
the answer is raising `retention.time` or adding remote-write — not snapshots.
State this limitation in the how-to; do not paper over it.

Because retention is 3d, a **snapshot retention of 3 kept snapshots** is the
default. More than that stores blocks Prometheus will refuse to load.

`enableAdminAPI` is `false`, so the `/api/v1/admin/tsdb/snapshot` endpoint is not
available. That is fine and **no CR change is wanted**: capture happens during
`make down`, when the workloads are being torn down anyway, so a cold copy is
consistent by construction. Do not enable the admin API.

## Output contract

`hub_snapshot_capture` MUST emit the layout `_hub_recovery_validate_files` and
`_hub_recovery_claim_tree` already require:

```
<snapshot-root>/<UTC-timestamp>/
  server-db/state.db
  server-token
  pv-pvc.yaml
  node-server-0-storage/pvc-<uid>_<ns>_<claim>/
  node-agent-0-storage/pvc-<uid>_<ns>_<claim>/
  node-agent-1-storage/…
  node-agent-2-storage/…
  MANIFEST.tsv
  SHA256SUMS
```

`node-*-storage` directory names and the `pvc-<uid>_<ns>_<claim>` tree names must
match `_hub_recovery_records` / `_hub_recovery_claim_tree` exactly, or restore
will reject the snapshot. A capture that restore cannot read is a failed capture.

## Loki — the one additive change

`_hub_recovery_records` in `hub_recovery.sh` does not list Loki. Add it so Loki is
both captured and restorable. Append one line to the heredoc, changing nothing
else:

```
agent-1|monitoring|storage-loki-0|node-agent-1-storage
```

Vault KV needs **no** separate export: `secrets/data-vault-0` is Vault's file
backend and already contains the KV data. Do not add a `vault kv get` export loop,
and do not touch the 14-key Vault allowlist.

## Node placement must be derived, not hardcoded

`_hub_recovery_records` hardcodes a logical node per claim, which was correct for
the 2026-09-11 capture. It is **not** reliable in general: `local-path` pins a
volume to whichever node the pod was scheduled on, and placement changes across
rebuilds. Measured today, Prometheus is on `agent-1` while the record says
`agent-0`.

Capture must therefore resolve each claim's real node from the live cluster and
write it into `MANIFEST.tsv`, using the record's `storage_dir` only as the output
directory name:

```bash
function _hub_snapshot_claim_node() {
  local _ns="$1" _claim="$2" _pv
  _pv="$(_kubectl -n "$_ns" get pvc "$_claim" -o jsonpath='{.spec.volumeName}')" || return 1
  [[ -n "$_pv" ]] || { echo "No bound PV for ${_ns}/${_claim}" >&2; return 1; }
  _kubectl get pv "$_pv" \
    -o jsonpath='{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}'
}
```

If a claim resolves to zero or more than one node, fail closed and name the claim.

## Required behaviour

1. **Fail closed on integrity.** Write `SHA256SUMS` over every captured file and
   verify it after the M2 transfer. A checksum mismatch is a hard failure — the
   snapshot directory must then be marked `.INCOMPLETE` and never pruned over a
   good one.
2. **Never delete the only good snapshot.** `hub_snapshot_prune` keeps the newest
   `K3DM_SNAPSHOT_KEEP` (default **3**) *verified* snapshots. `.INCOMPLETE`
   snapshots are pruned first and never counted toward the keep count. If pruning
   would leave zero verified snapshots, refuse and say so.
3. ~~**Preflight free space.**~~ **REMOVED 2026-09-22.** As implemented the check
   ran *after* the full local capture, so it could not "refuse before copying
   anything" as written — it only guarded the M2 transfer, which `rsync` already
   fails on when the destination is full. Dropped rather than moved: it bought no
   safety the transfer did not already provide.
4. **M2 transfer reuses the existing runner seam.** The SSH host alias is already
   defined: `E2E_M2_SSH_HOST` (default `m2jump`) in
   `scripts/plugins/e2e_remote.sh:18`. Introduce
   `K3DM_SNAPSHOT_HOST="${K3DM_SNAPSHOT_HOST:-${E2E_M2_SSH_HOST:-m2jump}}"` and
   `K3DM_SNAPSHOT_DIR` (default `~/k3dm-snapshots` on the remote). Do not invent a
   second SSH configuration mechanism.
5. **Bounded SSH.** Every ssh call uses `-o BatchMode=yes -o ConnectTimeout=10`.
   An unreachable M2 is a clear error naming the host, not a hang.
6. **Local staging is cleaned up** on success and on failure, via `trap`. A 2.15G
   leak on the M4 is a real cost.
7. `hub_snapshot_list` prints timestamp, size, verified/incomplete, per snapshot.
8. **Secrets.** `server-token` and the Vault tree are sensitive. Never print their
   contents, never pass them as command arguments, and create the staging
   directory `0700` before writing anything into it.

**Fully offline.** Stub `_kubectl`, `ssh`, `rsync`/`scp`, `docker` and `sha256sum`
on `PATH`. No live cluster, no real SSH, no real M2. A test that reaches the
network is a failed test.

Required cases:

1. Capture emits the exact restore layout — assert `server-db/state.db`,
   `server-token`, `pv-pvc.yaml` and one `pvc-*_<ns>_<claim>` tree per record all
   exist under the timestamp directory.
2. The emitted tree names satisfy `_hub_recovery_claim_tree` — source
   `hub_recovery.sh` in the test and call it against the captured directory. This
   is the contract test; without it the two halves can drift apart silently.
3. Node placement is derived from the PV, not the record — stub the PV to report
   `agent-1` for Prometheus while the record says `agent-0`, and assert
   `MANIFEST.tsv` records `agent-1`.
4. A claim resolving to no bound PV fails closed and names the claim.
5. Checksum mismatch after transfer → non-zero exit, directory marked
   `.INCOMPLETE`.
6. ~~Insufficient free space~~ — **REPLACED 2026-09-22** when the preflight was
   removed (see Requirement 3). The case is now the inverse guard: a successful
   capture must issue **no** remote `df`, so restoring the preflight fails the
   suite. Case count stays 14.
7. Prune keeps exactly `K3DM_SNAPSHOT_KEEP` verified snapshots and deletes older
   ones.
8. Prune deletes `.INCOMPLETE` snapshots first and never counts them.
9. Prune refuses when it would leave zero verified snapshots.
10. Unreachable M2 → clear error naming the host; exit non-zero; no partial
    directory left on the remote stub.
11. Staging directory is removed on the failure path (assert it is gone after a
    forced mid-capture failure).
12. Staging directory is created `0700` — assert with `stat -c '%a'`.
13. Loki record present: assert `_hub_recovery_records` yields a
    `monitoring|storage-loki-0` row.
