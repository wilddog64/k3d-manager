# v1.46.0 — HermesNotRunning: the webhook diagnoses Hermes and restarts it once

**Filed:** 2026-10-09, Claude
**Branch:** `k3d-manager-v1.46.0` (do not start until that branch exists; never `main`)
**Status:** QUEUED for v1.46.0. Dispatch to Codex when the branch opens.
**Origin:** operator, 2026-10-09, after the Hermes outage
(`docs/bugs/2026-10-09-launchd-agents-hardcode-homebrew-python3-hermes-down.md`): "HermesNotRunning
fires, Alertmanager can route the incident to an independent webhook". The operator chose a fixed
recovery routine over an AI diagnosis and over a cloud agent. A cloud session has no network path to
the M4.
**Implementer:** Codex · **Verifier:** Claude · **Restart after landing:** operator runs
`make restart-webhook`, then `make platform-ops`

## Problem

Hermes is the platform's self-repair loop, so it cannot repair itself. When it stops,
`HermesNotRunning` emails the operator. After that, everything is manual:
1. read `launchctl print`;
2. work out the exit code;
3. find the cause;
4. restart Hermes.

On 2026-10-09, Hermes was down for hours with exit 78 (`EX_CONFIG`). A Homebrew upgrade had removed
the interpreter named in its plist. The cause took one `launchctl print` to find.

## Approach

Alertmanager already sends ArgoCD and Trivy alerts to the k3dm webhook (AlertmanagerConfig
`k3dm-analyze`). The webhook runs as a separate LaunchAgent (`com.k3d-manager.webhook`), so it is
still up when Hermes is down.

Add a route for `HermesNotRunning` to a new handler that runs a **fixed** recovery routine. It
calls no model. It does not guess: each check below either acts once or reports why not, then posts
the result to Slack.

| # | Check | Outcome | Action |
|---|---|---|---|
| 1 | `launchctl print gui/<uid>/com.k3d-manager.hermes` exits non-zero | `not_loaded` | none. Report: the LaunchAgent is not loaded; reinstall per `docs/guides/hermes.md` "Install and uninstall" |
| 2 | `ProgramArguments[0]` in `~/Library/LaunchAgents/com.k3d-manager.hermes.plist` is missing or not executable | `interpreter_missing` | none. Report the path and `brew install <formula>`, where the formula is the `opt/<formula>/` segment of the path; if there is none, report the path only. Never kickstart: launchd would exit 78 again |
| 3 | `state = running` in the `launchctl print` output | `running` | none. Report: a cycle is in progress; if the alert persists, check `~/Library/Logs/k3dm-hermes.log` for a hang |
| 4 | a kickstart happened less than 1 h ago (cooldown file mtime) | `cooldown` | none. Report the time of the last kickstart |
| 5 | otherwise | `kickstarted` | `launchctl kickstart gui/<uid>/com.k3d-manager.hermes`, **without `-k`**, then touch the cooldown file. Report the last exit code from check 1, plus the kickstart exit code. When the last exit code was 0, add: Hermes itself exits cleanly, so check the heartbeat push to the hub Pushgateway (`localhost:19094`) |

The checks run in that order, and the first match wins.

Why no `-k`: the only state it would act on is `running` (check 3). A slow or hung cycle is
reported, not killed. Kill-and-restart has a cost the operator should decide on.

Why a cooldown: `HermesNotRunning` repeats while it fires. One kickstart per hour gives a failing
cause one retry, and a second alert is then visibly a repeat.

## Design

### 1. `bin/k3dm-webhook`

Add the route:

```python
    "/api/v1/hermes-recover": {"handler": "hermes_recover", "min_role": "operator", "action_name": "hermes-recover"},
```

Add constants beside the CVE cooldown ones (`_CVE_COOLDOWN_DIR`, about line 324):

```python
_HERMES_LABEL = "com.k3d-manager.hermes"
_HERMES_PLIST = Path.home() / "Library" / "LaunchAgents" / f"{_HERMES_LABEL}.plist"
_HERMES_RECOVER_COOLDOWN_FILE = Path.home() / ".k3dm" / "cooldowns" / "hermes-recover"
_HERMES_RECOVER_COOLDOWN_SECS = 60 * 60
```

**Handler.** Model it on `analyze`: create a job dir, start a daemon thread on
`_run_hermes_recover(job_id, body)`, and return `202 {"job_id", "status": "queued"}`. The thread acts
only when the payload contains an alert with `status == "firing"` and
`labels.alertname == "HermesNotRunning"`. For any other payload it writes job status `success`
with the output `no firing HermesNotRunning alert`, and does nothing else.

**`_hermes_recover_diagnose(now=None)`** returns
`{"outcome": <one of the five above>, "detail": <str>, "last_exit": <int|None>, "argv": <list|None>}`.
It holds the decision table and runs no kickstart, so tests can drive it directly.
- **Label and plist path:** the label is the constant. The plist path is the constant, overridable
  only by the env var `K3DM_HERMES_PLIST`, for tests.
- **Nothing from the alert payload reaches a command or a path.**
- **Reading the plist:** use `plistlib` (stdlib). A plist that cannot be read counts as
  `interpreter_missing`, with the detail `plist unreadable: <path>`.
- **Parsing `launchctl print`:** match `^\s*state = (\S+)` and `^\s*last exit code = (-?\d+)`. A
  missing `last exit code` gives `None`.
- **Running commands:** call `launchctl` through `_spawn_capture_text`, the same helper as
  `_active_cve_scan_job`, with a 10 s timeout.

**`_run_hermes_recover(job_id, body)`**:
- calls the diagnosis;
- on `kickstarted`, runs the kickstart and touches the cooldown file, even when the kickstart fails,
  so a failing kickstart is not retried on every repeat;
- writes job `status` and `output`;
- posts one Slack message through `_notify_job(job_id, text)`.

The message starts with `HermesNotRunning: <outcome>`, followed by the detail. It never includes
environment values or plist contents beyond `ProgramArguments[0]`.

### 2. `scripts/etc/argocd/platform-ops/alertmanager-config.yaml`

Add a **second document** to the file, separated by `---`. Do not add the alert to the
`k3dm-analyze` matcher list: an AI diagnosis is the option the operator did not choose.
`deploy_argocd_platform_ops` already applies this whole file.

```yaml
---
apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: k3dm-hermes-recover
  namespace: cicd
  labels:
    release: kube-prometheus-stack
spec:
  route:
    receiver: k3dm-hermes-recover
    matchers:
      - name: alertname
        value: HermesNotRunning
        matchType: "="
    groupBy: ["alertname"]
    groupWait: 30s
    groupInterval: 5m
    repeatInterval: 1h
  receivers:
    - name: k3dm-hermes-recover
      webhookConfigs:
        - url: "https://webhook.3ai-talk.org/api/v1/hermes-recover"
          sendResolved: false
          httpConfig:
            authorization:
              type: Bearer
              credentials:
                name: k3dm-webhook-token
                key: token
```

`alertmanagerConfigMatcherStrategy` is `None` on the hub
(`scripts/etc/helm/observability/kube-prometheus-stack-values.yaml`), so no `namespace` matcher is
injected. That matters because the alert has no `namespace` label. The operator also chains
AlertmanagerConfig routes with `continue: true`, so the `platform-warning` email still goes out.
Prove both from the generated config in step 2 of the live check. Do not assume them.

## Out of scope

- **The hub or the M4 being down.** Alertmanager runs on the same laptop. When the laptop sleeps or
  the hub stops, Hermes, the alert and this route all go silent together. That needs a check that
  runs off the laptop (a dead-man's switch). It is a separate theme.
- **Webhook independence from Homebrew Python.** The webhook runs on the same pinned interpreter
  (`625b44a7`). If that interpreter is gone, the webhook is down too, and this route cannot run. The
  email is then the only signal.
- **Killing a hung cycle (`-k`).** This is reported only. It is the operator's decision.
