## Problem

Cloudflare Access and GitHub 2FA decide who may open the console. They do not decide that the person at the browser right now is the operator: an unattended or borrowed browser session, or a stolen Access session within its 6 hours, would reach a shell. The operator chose a TOTP code at every login (D3) and after 2 idle minutes. Part A's sshd runs a `ForceCommand`; this part replaces its refusing stub with the gate. The runtime claim (K1 = a, umbrella decision 14) has two halves. (1) A remote party who has passed Access and holds the certificate but not the operator's current TOTP code gets no shell and no tmux client. (2) A hostile process running as the operator, outside the gate, cannot run code before the gate, read the secret, submit a code or reach the lockout by connecting to the verifier, or keep a tmux client after the gate exits. It is not claimed that the operator's own terminal is private from such a process: the gate's tty is an operator-owned `0620` pty that a same-user process can read from or write to, a fake prompt can collect a code, a program running as the operator can inject wrong codes into a live genuine gate, where they count as failures and can reach the lockout (operator decision after round 4, residual R-TTY), and a same-user `SIGSTOP` freezes the gate's idle timer (residuals R-TTY, R-SUSPEND, R-ACTIVITY). It can always deny service (it can `kill -9` the gate, which runs as the operator); that is not claimed against either.

- **State directory** `/var/db/k3dm-web-console` (`root:wheel`, `0700`). One file `state.json` (`0600`) holds `secret` (base32, 160 bits from `os.urandom(20)`), `last_counter`, `failures`, `locked_until` and `enrolled`. The daemon is the only writer. A commit: open `state.json.tmp` with `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW` mode `0600`, write, `fsync`, `rename` over `state.json`, `fsync` the directory. At start the daemon removes a leftover `state.json.tmp` unread. A crash leaves the old or the new `state.json`, never a mix. A commit can fail in two places, and the two are different outcomes on both sockets (Astra 6). **Before the rename** (the open, write or `fsync` of the temp file, or the `rename` itself, fails): the disk still holds the old state; the daemon removes the temp file, leaves its in-memory state unchanged, replies `UNAVAILABLE`, logs `commit-failed` and keeps serving; on the admin socket a pending secret stays pending. **After the rename** (the directory `fsync` fails): the disk may hold the new state and the daemon cannot tell; it replies `UNAVAILABLE` to that one request, logs `commit-fsync-failed`, closes both listening sockets and every other connection without a reply, serves no further request and exits 1; a pending secret goes with the process. launchd starts it again (`KeepAlive`, after `ThrottleInterval`; proof owed P13) and the new daemon reads whatever `state.json` the disk holds. So no request is answered from a state that may be older than the disk: no accepted counter is accepted twice and no counted failure is lost. An invalid config is a third, separate case (1.8). The login Keychain is not used.

1. **Verifier protocol (`totp.sock`).**
   1. **Peer identity at accept, before any byte is read (Fable C3, C4; Astra 4).** The daemon reads the peer with `getsockopt(SOL_LOCAL=0, LOCAL_PEERCRED=1, 76)` (xucred: version, uid; `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man4/unix.4:156`) and `LOCAL_PEERPID=2`. It admits the connection only when all hold, in this order, cheapest first:
      - (a) the peer uid equals `uid` from `totp.conf`;
      - (b) the console listener is genuine: exactly one `127.0.0.1.<console_port>` LISTEN row in `/usr/sbin/netstat -anv -p tcp`, its pid has uid 0 (`/bin/ps -o uid= -p`) and equals the `pid =` of `/bin/launchctl print system/com.k3d-manager.web-console-sshd` (part A's C3 rule); the result, success or failure, is cached for 1 s, and checks that find the cache cold share one in-flight lookup (the first starts it; the others wait for its result inside their own 2 s budget and never start a second), so a burst of peers, concurrent or not, costs at most one set of these subprocesses per second (Astra 7);
      - (c) the peer is a gate itself, decided by its chain position: the peer's parent is a process with the operator uid whose command starts `sshd-session: ` and does not end ` [priv]`; that process's parent has uid 0 and a command that starts `sshd-session: ` and ends ` [priv]`; that process's parent is the listener pid from (b) (the exact shape is capture P4; expected: listener, `sshd-session: <login> [priv]` uid 0, `sshd-session: <login>@<tty>` operator uid, peer). The chain position is the control: only sshd creates a process at that position, and sshd runs nothing there but the `ForceCommand`. In addition the peer's `ps -o comm=` must equal `PYAPP` exactly and its `ps -o args=` must equal `PYAPP -IS /Library/PrivilegedHelperTools/k3dm-web-console/forced-command` exactly; these two are hygiene (they reject a wrong install or a stray process early) and are not relied on, because a same-user process can make a child with the same `comm` and `args` (Fable C-M1). A tmux client (the gate's child, whose parent is the gate), a tmux server (ppid 1), anything in a pane (a descendant of the tmux server) and a gate-identical child of the gate all fail the chain position, so a replaced `tmux` cannot submit codes (Fable C5);
      - (d) the peer's `lstart` is the same before and after the `ps` reads (pid reuse).
      The `ps` and `netstat` texts are parsed by one parser function that tests feed with raw captured text (E2). Each subprocess has a 1 s timeout and an accept's subprocesses together have a 2 s budget; any failure, timeout or ambiguity rejects. A rejected connection, including one rejected because (b) fails, is closed at once with no read and no reply, and changes no state. An outside process therefore cannot, by connecting to the verifier, submit a code, learn whether one is right, or reach the lockout (wrong codes injected into a live genuine gate are R-TTY). The decision is one function, `admit(...)`, of the daemon module; the part A job label of (b), the `forced-command` path and `PYAPP` of (c) (so the expected `comm` and `args`) are its parameters, which production `main()` fixes to the constants above (Behaviour 11; R4-B3), so part B C12 runs the same function with its scratch label and scratch entry path.
   2. **Admission.** A `selectors` loop with nonblocking sockets; listen backlog 16. Rule (a) runs on accept with no subprocess; a peer that fails (a) is closed at once. At most 4 identity checks ((b) to (d)) are pending at a time, each in a worker with the 2 s budget; a peer that arrives while 4 are pending is closed at once with no reply, whoever it is. A check that finishes frees its pending slot at that moment: a rejected peer is closed and holds nothing afterwards, however long its owner keeps its end open. At most 4 admitted connections at a time (a peer admitted while 4 are held is closed); each admitted connection has a 5 s deadline for one request line of at most 32 bytes, after which it is closed and its slot is free. Verification and state commits are serialised inside the loop. What this guarantees, and what E2 tests at observable states (Astra 7): rejected peers keep no pending and no admitted slot once their checks finish; an arrival during four pending checks is refused; service resumes as soon as a slot is free; only genuine gates pass (c), so only gates can hold admitted slots. What it does not guarantee: that a gate is served while a same-user process keeps the four pending slots busy with a stream of new connections. That gate is closed with no reply, prints `console login unavailable` and exits 1, nothing is counted, and the operator connects again (R-DENIAL). The loop reports `accepted`, `check-started`, `check-finished`, `admitted` and `closed <reason>` to an event hook that is a `run()` parameter (production: none), which is how tests wait for a state instead of sleeping.
   3. **Framing.** The only request is `VERIFY <6 ASCII digits>\n`. A longer line, a timeout, a non-ASCII byte, a missing newline, another verb or a payload that is not exactly six digits is a wire rejection: the connection is closed with no reply and nothing is counted. (The gate sends only six digits; its own local check counts a malformed line as a wrong code without contacting the daemon.)
   4. **Algorithm:** RFC 6238, HMAC-SHA1, 30 s step, 6 digits, accepted counters `now//30` plus -1, 0, +1 (fixed). Every candidate is compared with `hmac.compare_digest`, with no early exit between candidates.
   5. **Replies:** `OK`, `NO`, `WAIT <seconds>`, `UNAVAILABLE`.
   6. **Replay:** a code is accepted only when its counter is greater than `last_counter`; on acceptance `last_counter` and `failures: 0` are committed before `OK` is sent. A `NO` commits the incremented `failures` (and `locked_until` on the 5th) before `NO` is sent. If a commit fails before its `rename`, the reply is `UNAVAILABLE`, the in-memory state does not advance and the daemon keeps serving; a failure after the `rename` follows the state-directory rule (one `UNAVAILABLE`, no further request served, exit 1). A reused code gets `NO` and counts as a failure, also after a daemon restart.
   7. **Lockout (exact rule).** `failures` counts consecutive `NO` replies. The 5th commits `locked_until = now + 300`. While `now < locked_until` every well-formed request gets `WAIT <remaining>` with no verification and no increment. At the first request with `now >= locked_until` the daemon commits `failures = 0`, `locked_until = 0`, then verifies normally (a wrong code then leaves `failures = 1`). A success sets `failures = 0`. State survives a restart. Guess rate for a gate: at most 5 guesses per about 300 s, under 1,440 per day, against 3 valid codes in 10^6 (about 0.43 percent per day of sustained guessing, only through a real gate, so only past Access and the certificate).
   8. **Unavailable, three separate cases (Astra 6).** (i) State: not enrolled; `state.json` missing, unreadable or malformed; an unreadable clock; a commit that failed before its `rename`: reply `UNAVAILABLE` to the admitted peer, log the event, keep serving. (ii) A commit whose directory `fsync` failed after the `rename`: one `UNAVAILABLE`, then no further request and exit 1 (state-directory rule). (iii) Config: an unreadable or invalid `totp.conf` means no configured uid, so rule (a) cannot pass: every `totp.sock` peer is closed with no reply (never `UNAVAILABLE`), the gate (which reads the same config) prints `console login unavailable`, and on `admin.sock` `STATUS` and every other verb answer `UNAVAILABLE`. A listener check (b) that fails closes the peer with no reply (1.1). The daemon never repairs or rewrites a malformed state file.
   9. **Clock:** if the wall clock moves backward past `last_counter`, valid codes are refused until it catches up (fails closed).
2. **Admin protocol (`admin.sock`, root only).** The daemon admits only a peer whose `LOCAL_PEERCRED` uid is 0. Verbs, one line each, bounded as above:
   - `STATUS` → `ENROLLED`, `NOT_ENROLLED` (no `state.json`) or `UNAVAILABLE` (present but unreadable or malformed, or the config is invalid).
   - `ENROLL_BEGIN` → `ENROLLED` (refused) when enrolled; `UNAVAILABLE` (refused) when damaged; otherwise a secret in memory only, expiry 300 s, one pending secret at a time, reply `SECRET <base32>`.
   - `ENROLL_COMMIT <code>` → verifies against the pending secret; on success one commit writes `secret`, `last_counter` (the matched counter), `failures` 0, `locked_until` 0, `enrolled` true, reply `OK`. A commit failure before the `rename` is `UNAVAILABLE` and the pending secret stays (the operator may type the next code). A failure after the `rename` is `UNAVAILABLE`, the daemon exits (state-directory rule) and the pending secret is gone with it: `totpctl` prints `commit not confirmed; run web-console-totp-status` on `/dev/tty` and exits 1, and the how-to says that `enrolled` then means the secret just shown is the one on disk and `not enrolled` means enrol again.
   - `ROTATE_BEGIN` (refused unless enrolled and undamaged; the current secret stays valid), `ROTATE_COMMIT <code>` (one commit replaces `secret` and `last_counter` and writes `failures` 0 and `locked_until` 0, so a rotation at the machine also ends a lockout: the recovery R-TTY names), `ABORT`. A `ROTATE_COMMIT` commit failure follows the same two rules as `ENROLL_COMMIT`; after a not-confirmed commit the how-to tells the operator to try a login: the new secret's code works when the disk took the new state, the old one's otherwise.
   - A wrong commit code leaves the pending secret for the rest of its 300 s and counts toward a separate in-memory limit of 5, after which the pending secret is dropped. The pending secret is never on disk; a secret reaches disk only inside the commit of `ENROLL_COMMIT` or `ROTATE_COMMIT`, as `state.json.tmp` then `state.json` in the `0700` directory.
   - Repair of a damaged state is `uninstall --purge-secret`, then install and enrol again (the how-to says so).
3. **Gate flow** (`forced-command`, a pty proxy). Exit codes: 0 only when the tmux client the gate started ends by the operator's own detach or exit; 1 for every other end.
   1. Before anything else: `SIGPIPE` ignored; `SIGHUP` and `SIGTERM` raise a handler that ends the connection with exit 1 after the cleanup below; `SIGINT`, `SIGTSTP`, `SIGQUIT` ignored; `umask 077`. `SSH_ORIGINAL_COMMAND` is never read. tmux runs with an environment rebuilt from `PATH=/usr/bin:/bin:/usr/sbin:/sbin:<dirname of tmux>`, `HOME`, `USER`, `LOGNAME`, `TERM`, `LANG` only (so `TMUX_TMPDIR` is dropped; the how-to says a non-default `TMUX_TMPDIR` would give the console a different, empty server). The run is inside `try`/`finally` that restores the terminal (`termios.tcsetattr` with `TCSANOW`, 3.6) and ends the child.
   2. Require stdin to be a tty; otherwise print `console: an interactive terminal is required` to stderr, exit 1. Load and validate `totp.conf`; failure is `console login unavailable`, exit 1.
   3. Clear the screen (`ESC[H ESC[2J ESC[3J`), prompt `Code: ` with the terminal in non-canonical mode, `ECHO` and `ISIG` off (restored in the `finally`), reading one byte at a time with a monotonic deadline, so Ctrl-C, Ctrl-Z, Ctrl-\ and Ctrl-D arrive as data: each discards the typed line and re-prompts; a read of zero bytes is a disconnect and exits 1. A line that is not exactly 6 digits counts as a wrong code locally. Wrong code: print `Invalid code`, sleep 2 s, re-prompt. `WAIT n`: print `Too many attempts; try again later`, sleep 2 s, re-prompt. A `WAIT` reply, a local wrong code and a `NO` each count as one failed prompt. After 10 failed prompts in one prompt episode, or 60 s without a byte at the prompt, exit 1. The failed-prompt counter starts at 0 at each prompt episode: the first prompt of the connection and each re-prompt after an idle end.
   4. **Verifier I/O, bounded.** Connect within 3 s, reply within 5 s, one line of at most 32 bytes. After connect, the gate reads the server's `LOCAL_PEERCRED` and requires uid 0. Daemon unreachable, a reply other than the four, a server uid other than 0, a socket error or a timeout, or `UNAVAILABLE`: print `console login unavailable`, exit 1. The verifier socket is non-inheritable (Python's default, PEP 446) and is closed before step 5. A failure never falls through to attaching.
   5. **On `OK`:** `tmux has-session -t =work` (exact; plain `-t work` prefix-matches `work-console`, probed), each tmux control command run with a 5 s timeout (killed and exit 1 on expiry). When it fails, `tmux new-session -d -s work`; a `duplicate session: work` error counts as success when `has-session -t =work` then passes, otherwise exit 1. Then the gate makes the outer terminal raw and starts, on a new pty it owns (`pty.fork()`), the child `tmux attach-session -E -t =work` (no `-d`, so a local client is not detached; with `-E` the session environment is unchanged by the attach, probed; without `-E` the attach marks `DISPLAY` and `SSH_AUTH_SOCK` removed in the session environment; the global environment is unchanged either way, probed). The gate never creates a grouped session and never names `work-console`.
   6. **Relay and idle layer (Astra 8).** Both fds nonblocking; one `select` loop whose timeout is the smallest of 1 s, the time to the idle deadline and, while an incomplete `ESC` sequence is held, the time to its 100 ms release deadline (Astra 9: with a 1 s timeout and no other I/O a held prefix would be released late); a 64 KiB buffer per direction; when a buffer is full the gate stops reading that direction's source (backpressure) but keeps running the loop, so the idle deadline (`time.monotonic`) is evaluated even when the outer terminal does not drain. It propagates window-size changes (`TIOCSWINSZ` on `SIGWINCH`). Activity is a byte from the outer tty that is not part of a terminal reply sequence: cursor position reports (`ESC [ <n> ; <n> R`), device attributes (`ESC [ ? ... c`, `ESC [ > ... c`), mode reports (`ESC [ ? ... $ y`), focus events (`ESC [ I`, `ESC [ O`), OSC replies (`ESC ] ... BEL` or `ESC ] ... ESC \`) DCS replies (`ESC P ... ESC \`), device status reports (`ESC [ 0 n`, `ESC [ 3 n`) and window reports (`ESC [ 8 ; <rows> ; <cols> t`, `ESC [ 4 ; <h> ; <w> t`) are relayed but do not reset the idle timer (umbrella decision 8). A sequence that starts with `ESC` and is not yet complete is held for at most 64 bytes or 100 ms; when it completes as a reply it is relayed without counting, and when the limit passes or it cannot be a reply it is relayed and counts as activity. Pane output never counts. When `now - last_activity > idle_seconds`: `SIGTERM` the child, wait up to 2 s, `SIGKILL`, reap, then discard both relay buffers and every outer-tty byte that arrived up to this point, including bytes typed while the gate was waiting for the child to end (`termios.tcflush(TCIFLUSH)` on the outer tty, called after the reap; Fable C2), restore the terminal with `termios.tcsetattr(fd, termios.TCSANOW, saved)` (never `TCSADRAIN` or `TCSAFLUSH`, which wait for output that a stuck outer terminal never drains; probe below, Fable C3), then go back to 3.3: the screen clear and `Code: ` prompt are written with a 2 s deadline; when the write cannot complete in 2 s (the outer terminal does not drain) the gate exits 1. The tmux server, session and panes keep running (probed).
   7. **Fail-closed cleanup.** The gate holds the only master of the child's pty. On any exit path (`SIGHUP`, `SIGTERM`, an exception, a relay error, disconnect) the `finally` restores the terminal with `TCSANOW`, sends `SIGTERM` to the child, waits up to 2 s, sends `SIGKILL`, closes the master and exits 1; if the reap function (a `run()` parameter; production a bounded `os.waitpid(pid, os.WNOHANG)` loop) does not report the child gone within a further 2 s the gate closes the master and calls `os._exit(1)`. When the gate is killed with `SIGKILL` the kernel closes the master and the tmux client receives `SIGHUP` and exits (probed with a prototype). No `list-clients` polling or tty-name matching exists.
   8. When the child ends and the gate did not end it: exit 0 if the child exited 0, else 1. The gate never `exec`s a shell, never starts `$SHELL`, and has no code path that runs an interactive shell.
   9. **Failure classes kept separate** (Astra 8): before attach (verifier, config, tmux control command) → exit 1, no client ever started; after attach (relay error, signal, disconnect) → cleanup above, exit 1; at re-authentication after idle (the client is already gone) → the 3.4 rules, exit 1.

## What NOT to do

- Do not use tmux `lock-after-time`, `lock-command`, `lock-server`, grouped sessions, `list-clients` polling or any `set-option` in the gate.
- Do not store the TOTP secret in the Keychain, the checkout, `$HOME`, an environment variable, an argument, a temporary file outside the commit, or any log, and do not print it to stdout or stderr.
- Do not add a shell, `$SHELL`, `exec sh` or any fallback path on error; every error ends the connection.
- Do not name `/usr/bin/python3` or `/usr/bin/env` in a shebang or `ProgramArguments`.
- Do not read any path, socket or executable from the environment in a root-owned artifact.
- Do not run any test against the operator's real tmux server, real `/etc`, `/var` or `/Library`.
- Do not build a separate admin account, a root-owned installer verifier or a phone confirmation (O3).
- Do not add Cloudflare code, change part A's sshd settings, or put the console in an agents or secrets list.
- Do not commit, push, dispatch, or skip pre-commit hooks.
