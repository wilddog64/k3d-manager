**Risk:** critical. This part is the second factor in front of an interactive shell on the operator's Mac, and adds a second root LaunchDaemon. Dispatch needs the operator's go. The operator runs every live step; the worker runs none.
**Depends on:** part A ([`v1.45.0-web-console-a-console-sshd.md`](v1.45.0-web-console-a-console-sshd.md)) lands first (default, open question 4): its `ForceCommand` path, directories, `forced-command.stub`, lock, `scripts/lib/web_console_common.sh` and `_wc_priv` model. Independent of part B.
**Operator decisions applied:** D3 (TOTP at every login through a root-owned gate, loop until a valid code, never exit into a shell, rate-limit, replay state root-owned, idle layer fails closed), D4 (this is part C), O2 (a process running as the operator is an adversary).
**Deviation to confirm (open question 1):** D3 says the idle lock sets tmux lock options globally. All the tmux 3.8 bypasses Fable proved (per-client lock, Ctrl-C at the prompt, non-zero `lock-command`, `lock-after-time` not following a session switch) live inside tmux's lock. This spec uses no tmux locking: the gate owns the pty of the tmux client (a pty proxy), so the idle layer is the gate ending its own client and asking for a code again. It sets no tmux option, so the operator's local clients are untouched by construction.

## Problem

Cloudflare Access and GitHub 2FA decide who may open the console. They do not decide that the person at the browser right now is the operator: an unattended or borrowed browser session, or a stolen Access session within its 6 hours, would reach a shell. The operator chose a TOTP code at every login (D3) and after 2 idle minutes. Part A's sshd runs a `ForceCommand`; this part replaces its refusing stub with the gate. Under O2 the gate, the verifier, the secret and the state must also survive a hostile process running as the operator: it must not run code before the gate, read the secret, guess codes against the verifier, lock the operator out, or keep a tmux client after the gate dies.

## Behaviour

Components, all root-owned, none inside the checkout, `$HOME` or a Homebrew prefix. Paths below are constants; no root-owned artifact reads a path from the environment (the importable modules take every path as a parameter and only `main()` binds the constants; a source scan allows `os.environ` reads of `HOME`, `USER`, `LOGNAME`, `TERM` and `LANG` only, in the gate only):

- Gate `/Library/PrivilegedHelperTools/k3dm-web-console/forced-command` (`root:wheel`, `0755`), source `scripts/libexec/k3dm-console-gate.py`, first line `#!/usr/bin/python3 -I` (Apple's 3.9.6 on the M4; no syntax newer than 3.9; `-I` ignores `PYTHON*` and the user site, probed). Runs as the operator user because sshd drops privileges before `ForceCommand`. It is reached through the trusted entry of part A (1.6: `SetEnv ZDOTDIR` to a root-owned empty directory, so no operator-writable zsh startup file runs first).
- Verifier daemon `/Library/PrivilegedHelperTools/k3dm-web-console/totpd`, source `scripts/libexec/k3dm-console-totpd.py`, and root admin client `totpctl`, source `scripts/libexec/k3dm-console-totpctl.py` (`root:wheel`, `0755`, same shebang). `totpd` runs under the LaunchDaemon `com.k3d-manager.web-console-totp` (`/Library/LaunchDaemons/com.k3d-manager.web-console-totp.plist`, `root:wheel`, `0644`; `ProgramArguments` `/usr/bin/python3`, `-I`, the `totpd` path; no `ProcessType`, no placeholder).
- Config `/etc/k3dm-web-console/totp.conf` (`root:wheel`, `0644`), strict `key=value` lines and no others: `uid=<operator uid>`, `tmux=<absolute path>`, `idle_seconds=120` (accepted 5-600), `console_port=<the port part A rendered>`. The gate and the daemon refuse a config that is not `root:wheel`, is group or other writable, has an unknown key, or has a value outside its range.
- State directory `/var/db/k3dm-web-console` (`root:wheel`, `0700`; `/var/db` is `root:wheel 0755`; the earlier `/var/run` socket directory is dropped because `/var/run` is `root:daemon 0775`, group-writable). One file `state.json` (`0600`) holds `secret` (base32, 160 bits from `os.urandom(20)`), `last_counter`, `failures`, `locked_until` and `enrolled`. The daemon is the only writer. Every change is one commit: write `state.json.tmp` in the same directory, `fsync` it, `rename` it over `state.json`, `fsync` the directory. A crash leaves the old file or the new file, never a mix, and there is no second file whose agreement could be lost. The login Keychain is not used (every process of the operator's user can read it).
- Sockets in `/var/db/k3dm-web-console/run` (`root:wheel`, `0755`, recreated by the daemon at every start: stale sockets are unlinked by name, the directory is checked to be a real directory owned by root, never a symlink): `totp.sock` (`root:wheel`, `0666`, reachable by any uid because authority comes from the peer checks below, not from the file mode) and `admin.sock` (`root:wheel`, `0600`).
- Log `/var/log/k3dm-web-console-totp.log` (`root:wheel`, `0600`): event names and counters only; never a code, a secret or a login name.
- Lock: the same `/var/db/k3dm-web-console.lock` directory as part A. Install, uninstall and part A's install serialize on it (exit 7 when a live holder has it).

1. **Verifier protocol (`totp.sock`).** One request line `VERIFY <6 digits>\n`, at most 32 bytes, read within a 5 s per-connection deadline; a longer line, a timeout or a bad byte closes the connection with no reply and counts nothing. One reply line: `OK`, `NO`, `WAIT <seconds>` or `UNAVAILABLE`. Requests are handled one at a time.
   1. Peer authority, before any verification (W8, O2). The daemon reads the peer with `getsockopt(SOL_LOCAL=0, LOCAL_PEERCRED=1, 76)` (xucred: version, uid) and `LOCAL_PEERPID=2` (probed on macOS 26.5.2: both work on server and client ends and matched uid and pid). It accepts only when the peer uid equals `uid` from `totp.conf` and the peer pid's parent chain (`/bin/ps -axo pid=,ppid=`, at most 16 hops, re-read after the request line to catch pid reuse) reaches the console sshd listener pid, which the daemon takes from `netstat -anv -p tcp` as the one `sshd` process with a LISTEN row `127.0.0.1.<console_port>` (zero or several rows, or a non-`sshd` owner, is `UNAVAILABLE`). A same-user process outside the console's sshd tree gets `UNAVAILABLE`: it cannot guess codes, cannot lock the operator out, and changes no state. The gate checks the other direction: after `connect` it reads `LOCAL_PEERCRED` of the server and requires uid 0, else `console login unavailable`.
   2. Algorithm: RFC 6238, HMAC-SHA1, 30 s step, 6 digits, accepted counters `now//30` plus -1, 0, +1 (fixed; not configurable). Every candidate is compared with `hmac.compare_digest` (no early exit between candidates). The request must match `^[0-9]{6}$`; anything else is a failure.
   3. Replay: a code is accepted only when its counter is greater than `last_counter`; on acceptance `last_counter` is committed (one commit, including `failures: 0`) before `OK` is sent. A reused code gets `NO` and counts as a failure.
   4. Lockout (exact rule). `failures` counts consecutive failed requests that reached verification. The 5th consecutive failure commits `locked_until = now + 300`. While `now < locked_until` every request, valid or not, gets `WAIT <remaining>` with no verification and no increment. At the first request with `now >= locked_until` the daemon commits `failures = 0` and `locked_until = 0`, then verifies normally. A success sets `failures = 0`. State survives a restart. Guess rate: at most 5 guesses per about 300 s, so under 1,440 per day, against 3 valid codes in 10^6 (about 0.43 percent per day of sustained guessing, and only for a process already inside the console sshd tree, i.e. past Access and the certificate).
   5. Not enrolled, a missing, unreadable or malformed `state.json`, an unreadable config or a clock that cannot be read: reply `UNAVAILABLE` and log the event; the gate treats it as login unavailable. The daemon never repairs a bad state file.
   6. Clock note: if the wall clock moves backward past `last_counter`, valid codes are refused until it catches up (fails closed).
2. **Admin protocol (`admin.sock`, root only; W5).** The daemon accepts only a peer whose `LOCAL_PEERCRED` uid is 0. Verbs, each one line, bounded as above: `STATUS` (reply `ENROLLED` or `NOT_ENROLLED`), `ENROLL_BEGIN` (refused with `ENROLLED` when enrolled; otherwise the daemon makes a secret in memory only, expiry 300 s, one pending secret at a time, and replies `SECRET <base32>`), `ENROLL_COMMIT <code>` (verifies against the pending secret; on success one commit writes `secret`, `last_counter` = the matched counter, `failures` 0, `locked_until` 0, `enrolled` true and replies `OK`), `ROTATE_BEGIN` (refused unless enrolled; pending secret as above; the current secret stays valid), `ROTATE_COMMIT <code>` (verifies against the pending secret; one commit replaces `secret` and `last_counter`; the old secret is gone after that commit and valid until it), `ABORT`. A wrong commit code leaves the pending secret for the rest of its 300 s and counts toward a separate in-memory limit of 5 wrong commit codes, after which the pending secret is dropped. The pending secret is never written to disk, so a killed first enrolment leaves no `state.json` (or `enrolled` false and no secret) and a killed rotation leaves the old secret. The admin client `totpctl` (root, run through `_wc_priv`) is the only caller; it prints the secret to `/dev/tty` only.
3. **Gate flow** (`forced-command`, a pty proxy). Exit codes: 0 only when the tmux client the gate started ends by the operator's own detach or exit; 1 for every other end.
   1. Before anything else: `SIGPIPE` ignored; `SIGHUP` and `SIGTERM` raise a handler that ends the connection with exit 1 after the cleanup below; `SIGINT`, `SIGTSTP`, `SIGQUIT` ignored. `umask 077`. `SSH_ORIGINAL_COMMAND` is never read. Run tmux with an environment rebuilt from `PATH=/usr/bin:/bin:/usr/sbin:/sbin:<dirname of tmux>`, `HOME`, `USER`, `LOGNAME`, `TERM`, `LANG` only. The whole run is inside `try`/`finally` that restores the terminal and ends the child (below).
   2. Require stdin to be a tty (`os.isatty(0)`); otherwise print `console: an interactive terminal is required` to stderr, exit 1. Load and validate `totp.conf` (above); failure is `console login unavailable`, exit 1.
   3. Prompt `Code: ` with the terminal in non-canonical mode, `ECHO` and `ISIG` off (restored in the `finally`), reading one byte at a time, so Ctrl-C, Ctrl-Z, Ctrl-\ and Ctrl-D arrive as data: each discards the typed line and re-prompts (never ends the gate); a read of zero bytes is a disconnect and exits 1. A line that is not exactly 6 digits counts as a wrong code without calling the verifier. Wrong code: print `Invalid code`, sleep 2 s, re-prompt. `WAIT n`: print `Too many attempts; try again later`, sleep 2 s, re-prompt. After 10 failed prompts in one connection, or 60 s without a byte at the prompt, exit 1.
   4. Bounded verifier I/O: `connect` within 3 s, the reply within 5 s, one reply line of at most 32 bytes. Daemon unreachable, a reply other than `OK`, `NO`, `WAIT n` or `UNAVAILABLE`, a server uid other than 0, a socket error or timeout: print `console login unavailable`, exit 1. `UNAVAILABLE` prints the same. A failure never falls through to attaching.
   5. On `OK`: `tmux has-session -t =work` (exact match; plain `-t work` prefix-matches `work-console`, probed); when it fails, `tmux new-session -d -s work`, and a `duplicate session: work` error (exit 1 from a concurrent first login) counts as success when `tmux has-session -t =work` then passes, otherwise exit 1. The gate then makes the outer terminal raw and starts, on a new pty it owns (`pty.fork()`), the child `tmux attach-session -E -t =work` (no `-d`, so a local client at home is not detached; `-E` means the client's environment is not merged into the server's `update-environment`, probed: without `-E` an attach from a minimal environment marked `SSH_AUTH_SOCK` and `DISPLAY` removed from the server environment, with `-E` `show-environment` was identical before and after). The gate never creates a grouped session and never names `work-console`.
   6. Relay and idle layer: the gate copies bytes between its own tty and the child's pty master, propagates window-size changes (`TIOCSWINSZ` on `SIGWINCH`) and records the time of the last byte read from the outer tty (only the operator's input counts as activity; pane output does not). When `now - last_input > idle_seconds`, it sends `SIGTERM` to the child, waits up to 2 s, sends `SIGKILL`, reaps it, restores the terminal and goes back to 3.3 (prompt again, then attach again). The tmux server, session and panes keep running (probed: a killed client leaves the session and pane alive).
   7. Fail-closed cleanup (W4, O2). The gate holds the only master of the child's pty. On any exit path (`SIGHUP`, `SIGTERM`, an exception, a relay error, disconnect) the `finally` sends `SIGTERM` to the child, waits up to 2 s, sends `SIGKILL`, closes the master and exits 1; if the child cannot be reaped within a further 2 s the gate closes the master and calls `os._exit(1)` anyway. When the gate itself is killed with `SIGKILL` the kernel closes the master and the tmux client receives `SIGHUP` and exits (probed 2026-11-18 with a prototype: after `kill -9` of the proxy `tmux list-clients` was empty and the session and pane survived). So there is no state in which a client stays attached without a live gate, and no `list-clients` polling or tty-name matching exists to be wrong.
   8. When the child ends and the gate did not end it: exit 0 if the child exited 0, else 1. The gate never `exec`s a shell, never starts `$SHELL`, and has no code path that runs an interactive shell.
4. **tmux is not modified.** The gate runs no `set-option`, `set-hook`, `source-file`, `new-session -t`, `list-clients`, `detach-client` or `lock-*` command. The only tmux commands it runs are `has-session -t =work`, `new-session -d -s work` and `attach-session -E -t =work`. Tests compare the tmux global and per-session environment (`show-environment -g`, `show-environment -t =work`) and options (`show-options -g`, `-s`, `-w`, and each session's) before and after a login, an idle cycle and a reconnect.
5. **Enrolment** (`bin/k3dm-web-console-totp enroll`, operator, at the machine).
   1. The wrapper refuses with exit 2 and `web-console-totp: refusing to show a secret here: <reason>` when `$TMUX`, `$TMUX_PANE` or `$STY` is set, stdin or stdout is not a tty, `/dev/tty` cannot be opened, `$SSH_CONNECTION` or `$SSH_TTY` is set, or the effective uid is 0. These refusals prevent accidents; they cannot stop an adversary running as the operator, who can open a pty of their own (open question 9).
   2. It runs `_wc_priv /usr/bin/python3 -I /Library/PrivilegedHelperTools/k3dm-web-console/totpctl enroll`. In that root process: `ENROLL_BEGIN`, open `/dev/tty` itself (proof owed P6: `/dev/tty` works in a `sudo`-run process) and print the base32 secret and the `otpauth://totp/` URI to it only; neither goes to stdout, stderr, argv, the environment or any log. `enrolled` stays false and nothing is on disk.
   3. It asks on `/dev/tty` for one current code (`ENROLL_COMMIT`); on success it prints `enrolled`, then clears the screen and scrollback (`ESC[3J ESC[H ESC[2J`). No valid code within the 300 s expiry, or any error, leaves nothing behind (the pending secret was only ever in daemon memory).
   4. `rotate` is the same flow with `ROTATE_BEGIN` and `ROTATE_COMMIT` after `--interactive-sudo` (the operator's password is the recovery factor for a lost phone). `status` runs `STATUS` and prints `enrolled` or `not enrolled`, never a secret. Each Mac has its own secret, enrolled under a different account label (`k3dm-console-<hostname>`); nothing copies it and it is in no `secrets.*.list`.
6. **Install** (`bin/k3dm-web-console-totp install`, same generation staging as part A 1.7, through `scripts/lib/web_console_common.sh`): refuse with exit 2 when part A is not installed (no A plist, no `forced-command.stub`); take the lock (exit 7); validate the trust chain for the helper directory, `/etc/k3dm-web-console`, `/Library/LaunchDaemons`, `/var/db` and `/var/db/k3dm-web-console` before any privileged write (exit 8); read the sources from the `HEAD` blobs and refuse a working tree that differs (exit 9); stream every file to root through `tee` into a root-created `.stage.XXXXXXXX` directory and re-hash it as root (exit 8 on mismatch); validate in the stage (`/usr/bin/python3 -I -c 'import ast,sys; ast.parse(open(sys.argv[1]).read())'` on each Python file, `plutil -lint` on the plist, the `totp.conf` rules above); copy the installed generation to `.prev`; move `totpd`, `totpctl`, `totp.conf` and (last of these) the plist into place, create `/var/db/k3dm-web-console` (`0700`); `launchctl bootout` (soft) and `bootstrap`; wait up to 10 s for `totpctl status` to answer; only then move the staged gate over `forced-command` (never before the daemon answers). A failed step after the first move restores the whole previous generation (including the stub as `forced-command`) and exits 5. `tmux` is `command -v tmux` as the operator; the run prints the resolved path and refuses a path outside `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, `/bin`, `/opt/local/bin` unless `--tmux PATH` is given; the path must be absolute and executable. Without `enrolled`, install still places the files and prints `not enrolled: logins stay refused`. The tmux binary lives in an operator-writable prefix; it runs only after the code was accepted, as the operator, so a replaced tmux gives no privilege the operator process did not already have (stated in the how-to).
7. **Uninstall** (`uninstall [--purge-secret]`): lock; `launchctl bootout` the daemon; remove the plist, `totpd`, `totpctl`, `totp.conf` and the run directory; restore `forced-command` from `forced-command.stub` (staged then `mv`); with the flag remove `/var/db/k3dm-web-console`. Sessions already attached continue; new logins meet the stub.
8. **Makefile.** `install-web-console-totp`, `uninstall-web-console-totp` (`PURGE_SECRET=1` adds `--purge-secret`, passed by environment, expanded by the shell), `web-console-totp-enroll`, `web-console-totp-status`, added to `.PHONY` (`Makefile:163`) and the help text. `scripts/etc/machine/not-installed.list` gains `install-web-console-totp|not installed by setup: operator-run once with a password and an authenticator app (docs/plans/v1.45.0-web-console-c-totp-gate.md)` and `web-console-totp|system LaunchDaemon installed once by make install-web-console-totp`. No agents list, no secrets list, no hub list. Tests do not run `make -n` on these targets.
9. **Honest residuals, in the how-to, each separate.** (a) An already-authenticated operator inside the console is trusted: the idle layer protects an unattended screen, not the person who logged in; they can run anything in their shell. (b) A hostile program that can type into the same tmux pane or send terminal query replies keeps the session "active". (c) A same-user process outside the console cannot read the secret (root-only), cannot guess codes and cannot lock the operator out (peer ancestry), but it can run `enroll` or `rotate` if it holds a live `sudo` ticket on the operator's tty or the operator's password (open questions 6 and 9). (d) The installer and sources are operator-writable until the hash-compare of part A open question 5 is done.
10. **Test overrides.** None in a root-owned artifact. The gate and daemon modules are importable (`importlib` from the file path) and expose `run(...)` taking every path, the clock, the tmux argv prefix (production `[tmux]`; tests `[tmux, "-S", <scratch socket>]`), the peer-lookup function and the idle/prompt limits as parameters; `main()` takes none and binds the constants. ## Proof of external behaviour

Local read-only probes, 2026-11-18, `m4-air`, macOS 26.5.2, OpenSSH_10.2p1, tmux 3.8, `/usr/bin/python3` 3.9.6, private tmux socket by relative path under the scratchpad (the full path exceeds the 104-byte socket limit):

- `tmux has-session -t work` succeeds when only `work-console` exists (prefix match); `-t =work` is exact and returns 1 when `work` is absent. A second `new-session -d -s work` fails with `duplicate session: work`, exit 1.
- `tmux attach-session -E`: with it, `show-environment` is identical before and after an attach from a minimal environment; without it, the attach marks `SSH_AUTH_SOCK` and `DISPLAY` as removed (`-SSH_AUTH_SOCK`).

- Unix sockets on Darwin (python): `getsockopt(SOL_LOCAL=0, LOCAL_PEERCRED=1, 76)` returns (xucred version 0, uid) and `LOCAL_PEERPID=2` returns the pid, on both server and client ends; uid and pid matched the test process (uid 501).
