**Deviation (umbrella decision 1, recorded):** D3 says the idle lock sets tmux lock options globally. Every tmux 3.8 bypass Fable proved (per-client lock, Ctrl-C at the prompt, non-zero `lock-command`, `lock-after-time` not following a session switch) lives inside tmux's lock. This spec uses no tmux locking: the gate owns the pty of the tmux client (a pty proxy), so the idle layer is the gate ending its own client and asking for a code again. It sets no tmux option, so the operator's local clients are untouched by construction.

## Problem

Cloudflare Access and GitHub 2FA decide who may open the console. They do not decide that the person at the browser right now is the operator: an unattended or borrowed browser session, or a stolen Access session within its 6 hours, would reach a shell. The operator chose a TOTP code at every login (D3) and after 2 idle minutes. Part A's sshd runs a `ForceCommand`; this part replaces its refusing stub with the gate. The runtime claim (K1 = a, umbrella decision 14) has two halves. (1) A remote party who has passed Access and holds the certificate but not the operator's current TOTP code gets no shell and no tmux client. (2) A hostile process running as the operator, outside the gate, cannot run code before the gate, read the secret, submit a code to the verifier, put the verifier into the lockout state, or keep a tmux client after the gate exits. It is not claimed that the operator's own terminal is private from such a process: the gate's tty is an operator-owned `0620` pty that a same-user process can read from or write to, a fake prompt can collect a code, and a same-user `SIGSTOP` freezes the gate's idle timer (residuals R-TTY, R-SUSPEND, R-ACTIVITY). It can always deny service (it can `kill -9` the gate, which runs as the operator); that is not claimed against either.

## Behaviour

Components, all root-owned, none inside the checkout, `$HOME` or a Homebrew prefix. Paths below are constants; no root-owned artifact reads a path from the environment (the importable modules take every path as a parameter and only `main()` binds the constants; a source scan allows `os.environ` reads of `HOME`, `USER`, `LOGNAME`, `TERM` and `LANG` only, in the gate only).

Install runs part A's `_wc_trust_chain` on `PY` (every symlink hop owned by uid 0 in a trusted directory, final target a trusted regular file; probe: the hops are `root:wheel` symlinks ending at `.../Python3.framework/Versions/3.9/bin/python3.9`, Mach-O, 3.9.6, `root:wheel 0755`) and `_wc_trust_check` on the two files that actually run: the app executable `PYAPP=/Library/Developer/CommandLineTools/Library/Frameworks/Python3.framework/Versions/3.9/Resources/Python.app/Contents/MacOS/Python` and the framework library `.../Python3.framework/Versions/3.9/Python3` (both `root:wheel 0755`, probe 2026-11-19); a chain through `/Applications` (`root:admin 0775`) fails. - **Verifier daemon** `/Library/PrivilegedHelperTools/k3dm-web-console/totpd`, source `scripts/libexec/k3dm-console-totpd.py`, and root admin client `totpctl`, source `scripts/libexec/k3dm-console-totpctl.py` (`root:wheel`, `0755`, same first line). `totpd` runs under the LaunchDaemon `com.k3d-manager.web-console-totp` (`/Library/LaunchDaemons/com.k3d-manager.web-console-totp.plist`, `root:wheel`, `0644`; `ProgramArguments` `PY`, `-IS`, the `totpd` path; `Umask` 63; `StandardErrorPath` the log; no `ProcessType`, no placeholder).
- **Config** `/etc/k3dm-web-console/totp.conf` (`root:wheel`, `0644`), strict `key=value` lines and no others: `uid=<operator uid>`, `tmux=<absolute path>`, `idle_seconds=120` (accepted 5-600), `console_port=<n>`. Install takes `console_port` from the installed `/etc/k3dm-web-console/sshd_config` first line (`^ListenAddress 127\.0\.0\.1:([0-9]+)$`; no match is exit 2), never from the environment; part A refuses a port change while this file exists. The gate and the daemon refuse a config that is not `root:wheel`, is group or other writable, has an unknown key, or has a value outside its range.
- **State directory** `/var/db/k3dm-web-console` (`root:wheel`, `0700`). One file `state.json` (`0600`) holds `secret` (base32, 160 bits from `os.urandom(20)`), `last_counter`, `failures`, `locked_until` and `enrolled`. The daemon is the only writer. A commit: open `state.json.tmp` with `O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW` mode `0600`, write, `fsync`, `rename` over `state.json`, `fsync` the directory. At start the daemon removes a leftover `state.json.tmp` unread. A crash leaves the old or the new `state.json`, never a mix. When the `rename` succeeded but the directory `fsync` fails, the disk may hold the new state: the daemon adopts the new state in memory, replies `UNAVAILABLE`, logs `commit-fsync-failed`, and exits 1 after the reply; launchd restarts it and the new daemon reads whatever `state.json` the disk holds. Each request is answered from the state the disk held at its commit, so no accepted counter is accepted twice and no counted failure is lost. The same rule covers the enrolment and rotation commits (the pending secret is dropped). The login Keychain is not used.
- **Run directory** `/var/db/k3dm-web-console-run` (`root:wheel`, `0755`), a sibling of the state directory, not inside it: the operator needs search permission on every path component to reach the socket (`connect(2)` `EACCES`, `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man2/connect.2:190-191`; Fable C1, Astra 3). Created by install; at every start the daemon checks it is a real directory (not a symlink), owner 0, mode `0755`, no ACL (`/bin/ls -lde <dir>` shows no `+` after the mode; Python 3.9 on macOS has no `os.listxattr`, probe 2026-11-19) (else it exits and launchd's `ThrottleInterval` retries), and unlinks `totp.sock` and `admin.sock` by name before binding. `totp.sock` is `0666` (authority comes from the peer checks, not the mode); `admin.sock` is `0600`.
- **Log** `/var/log/k3dm-web-console-totp.log` (`root:wheel`, `0600`, pre-created by install; plist `Umask` 63): event names and counters only; never a code, a secret or a login name.
- **Shared with part A:** the lock `/var/db/k3dm-web-console.lock`, the journal `/var/db/k3dm-web-console.txn`, the manifest `/etc/k3dm-web-console/manifest` (this part writes its own `C` rows), and the library.

1. **Verifier protocol (`totp.sock`).**
   1. **Peer identity at accept, before any byte is read (Fable C3, C4; Astra 4).** The daemon reads the peer with `getsockopt(SOL_LOCAL=0, LOCAL_PEERCRED=1, 76)` (xucred: version, uid; `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/share/man/man4/unix.4:156`) and `LOCAL_PEERPID=2`. It admits the connection only when all hold, in this order, cheapest first:
      - (a) the peer uid equals `uid` from `totp.conf`;
      - (b) the console listener is genuine: exactly one `127.0.0.1.<console_port>` LISTEN row in `/usr/sbin/netstat -anv -p tcp`, its pid has uid 0 (`/bin/ps -o uid= -p`) and equals the `pid =` of `/bin/launchctl print system/com.k3d-manager.web-console-sshd` (part A's C3 rule); the result, success or failure, is cached for 1 s, so a burst of peers costs at most one set of these subprocesses per second;
      - (c) the peer is a gate itself, decided by its chain position: the peer's parent is a process with the operator uid whose command starts `sshd-session: ` and does not end ` [priv]`; that process's parent has uid 0 and a command that starts `sshd-session: ` and ends ` [priv]`; that process's parent is the listener pid from (b) (the exact shape is capture P4; expected: listener, `sshd-session: <login> [priv]` uid 0, `sshd-session: <login>@<tty>` operator uid, peer). The chain position is the control: only sshd creates a process at that position, and sshd runs nothing there but the `ForceCommand`. In addition the peer's `ps -o comm=` must equal `PYAPP` exactly and its `ps -o args=` must equal `PYAPP -IS /Library/PrivilegedHelperTools/k3dm-web-console/forced-command` exactly; these two are hygiene (they reject a wrong install or a stray process early) and are not relied on, because a same-user process can make a child with the same `comm` and `args` (Fable C-M1). A tmux client (the gate's child, whose parent is the gate), a tmux server (ppid 1), anything in a pane (a descendant of the tmux server) and a gate-identical child of the gate all fail the chain position, so a replaced `tmux` cannot submit codes (Fable C5);
      - (d) the peer's `lstart` is the same before and after the `ps` reads (pid reuse).
      The `ps` and `netstat` texts are parsed by one parser function that tests feed with raw captured text (E2). Each subprocess has a 1 s timeout and an accept's subprocesses together have a 2 s budget; any failure, timeout or ambiguity rejects. A rejected connection, including one rejected because (b) fails, is closed at once with no read and no reply, and changes no state. An outside process therefore cannot submit a code, learn whether one is right, or reach the lockout.
   2. **Admission.** A `selectors` loop with nonblocking sockets; listen backlog 16. Rule (a) runs on accept with no subprocess; a peer that fails (a) is closed at once. At most 4 identity checks ((b) to (d)) are pending at a time, each in a worker with the 2 s budget; a peer that arrives while 4 are pending is closed. At most 4 admitted connections at a time (a fifth admitted peer is closed); each admitted connection has a 5 s deadline for one request line of at most 32 bytes. Verification and state commits are serialised inside the loop. Because only genuine gates pass (c), the only parties that can fill the admitted slots are gates; a same-user process can fill the pending-check slots (R-DENIAL). Test: 20 stalled outside connections held open, then a gate-shaped peer still gets its reply within the gate's 5 s deadline; 4 stalled admitted gate-shaped peers plus a fifth admitted peer, which is closed; when the first stalled peer's 5 s deadline frees a slot, a genuine peer is served.
   3. **Framing.** The only request is `VERIFY <6 ASCII digits>\n`. A longer line, a timeout, a non-ASCII byte, a missing newline, another verb or a payload that is not exactly six digits is a wire rejection: the connection is closed with no reply and nothing is counted. (The gate sends only six digits; its own local check counts a malformed line as a wrong code without contacting the daemon.)
   4. **Algorithm:** RFC 6238, HMAC-SHA1, 30 s step, 6 digits, accepted counters `now//30` plus -1, 0, +1 (fixed). Every candidate is compared with `hmac.compare_digest`, with no early exit between candidates.
   5. **Replies:** `OK`, `NO`, `WAIT <seconds>`, `UNAVAILABLE`.
   6. **Replay:** a code is accepted only when its counter is greater than `last_counter`; on acceptance `last_counter` and `failures: 0` are committed before `OK` is sent. A `NO` commits the incremented `failures` (and `locked_until` on the 5th) before `NO` is sent. If a commit fails before its `rename`, the reply is `UNAVAILABLE` and the in-memory state does not advance. A reused code gets `NO` and counts as a failure, also after a daemon restart.
   7. **Lockout (exact rule).** `failures` counts consecutive `NO` replies. The 5th commits `locked_until = now + 300`. While `now < locked_until` every well-formed request gets `WAIT <remaining>` with no verification and no increment. At the first request with `now >= locked_until` the daemon commits `failures = 0`, `locked_until = 0`, then verifies normally (a wrong code then leaves `failures = 1`). A success sets `failures = 0`. State survives a restart. Guess rate for a gate: at most 5 guesses per about 300 s, under 1,440 per day, against 3 valid codes in 10^6 (about 0.43 percent per day of sustained guessing, only through a real gate, so only past Access and the certificate).
   8. **Unavailable:** not enrolled; `state.json` missing, unreadable or malformed; an unreadable clock; a failed commit: reply `UNAVAILABLE` to the admitted peer and log the event. An unreadable or invalid config means no configured uid, so rule (a) cannot pass: every peer is closed with no reply, and the gate (which reads the same config) prints `console login unavailable`. A listener check (b) that fails closes the peer with no reply (1.1). The daemon never repairs or rewrites a malformed state file.
   9. **Clock:** if the wall clock moves backward past `last_counter`, valid codes are refused until it catches up (fails closed).
2. **Admin protocol (`admin.sock`, root only).** The daemon admits only a peer whose `LOCAL_PEERCRED` uid is 0. Verbs, one line each, bounded as above:
   - `STATUS` → `ENROLLED`, `NOT_ENROLLED` (no `state.json`) or `UNAVAILABLE` (present but unreadable or malformed, or the config is invalid).
   - `ENROLL_BEGIN` → `ENROLLED` (refused) when enrolled; `UNAVAILABLE` (refused) when damaged; otherwise a secret in memory only, expiry 300 s, one pending secret at a time, reply `SECRET <base32>`.
   - `ENROLL_COMMIT <code>` → verifies against the pending secret; on success one commit writes `secret`, `last_counter` (the matched counter), `failures` 0, `locked_until` 0, `enrolled` true, reply `OK`; commit failure is `UNAVAILABLE` and the pending secret stays.
   - `ROTATE_BEGIN` (refused unless enrolled and undamaged; the current secret stays valid), `ROTATE_COMMIT <code>` (one commit replaces `secret` and `last_counter`), `ABORT`.
   - A wrong commit code leaves the pending secret for the rest of its 300 s and counts toward a separate in-memory limit of 5, after which the pending secret is dropped. The pending secret is never on disk; a secret reaches disk only inside the commit of `ENROLL_COMMIT` or `ROTATE_COMMIT`, as `state.json.tmp` then `state.json` in the `0700` directory.
   - Repair of a damaged state is `uninstall --purge-secret`, then install and enrol again (the how-to says so).
3. **Gate flow** (`forced-command`, a pty proxy). Exit codes: 0 only when the tmux client the gate started ends by the operator's own detach or exit; 1 for every other end.
   1. Before anything else: `SIGPIPE` ignored; `SIGHUP` and `SIGTERM` raise a handler that ends the connection with exit 1 after the cleanup below; `SIGINT`, `SIGTSTP`, `SIGQUIT` ignored; `umask 077`. `SSH_ORIGINAL_COMMAND` is never read. tmux runs with an environment rebuilt from `PATH=/usr/bin:/bin:/usr/sbin:/sbin:<dirname of tmux>`, `HOME`, `USER`, `LOGNAME`, `TERM`, `LANG` only (so `TMUX_TMPDIR` is dropped; the how-to says a non-default `TMUX_TMPDIR` would give the console a different, empty server). The run is inside `try`/`finally` that restores the terminal and ends the child.
   2. Require stdin to be a tty; otherwise print `console: an interactive terminal is required` to stderr, exit 1. Load and validate `totp.conf`; failure is `console login unavailable`, exit 1.
   3. Clear the screen (`ESC[H ESC[2J ESC[3J`), prompt `Code: ` with the terminal in non-canonical mode, `ECHO` and `ISIG` off (restored in the `finally`), reading one byte at a time with a monotonic deadline, so Ctrl-C, Ctrl-Z, Ctrl-\ and Ctrl-D arrive as data: each discards the typed line and re-prompts; a read of zero bytes is a disconnect and exits 1. A line that is not exactly 6 digits counts as a wrong code locally. Wrong code: print `Invalid code`, sleep 2 s, re-prompt. `WAIT n`: print `Too many attempts; try again later`, sleep 2 s, re-prompt. A `WAIT` reply, a local wrong code and a `NO` each count as one failed prompt. After 10 failed prompts in one prompt episode, or 60 s without a byte at the prompt, exit 1. The failed-prompt counter starts at 0 at each prompt episode: the first prompt of the connection and each re-prompt after an idle end.
   4. **Verifier I/O, bounded.** Connect within 3 s, reply within 5 s, one line of at most 32 bytes. After connect, the gate reads the server's `LOCAL_PEERCRED` and requires uid 0. Daemon unreachable, a reply other than the four, a server uid other than 0, a socket error or a timeout, or `UNAVAILABLE`: print `console login unavailable`, exit 1. The verifier socket is non-inheritable (Python's default, PEP 446) and is closed before step 5. A failure never falls through to attaching.
   5. **On `OK`:** `tmux has-session -t =work` (exact; plain `-t work` prefix-matches `work-console`, probed), each tmux control command run with a 5 s timeout (killed and exit 1 on expiry). When it fails, `tmux new-session -d -s work`; a `duplicate session: work` error counts as success when `has-session -t =work` then passes, otherwise exit 1. Then the gate makes the outer terminal raw and starts, on a new pty it owns (`pty.fork()`), the child `tmux attach-session -E -t =work` (no `-d`, so a local client is not detached; with `-E` the session environment is unchanged by the attach, probed; without `-E` the attach marks `DISPLAY` and `SSH_AUTH_SOCK` removed in the session environment; the global environment is unchanged either way, probed). The gate never creates a grouped session and never names `work-console`.
   6. **Relay and idle layer (Astra 8).** Both fds nonblocking; one `select` loop whose timeout is the smaller of 1 s and the time to the idle deadline; a 64 KiB buffer per direction; when a buffer is full the gate stops reading that direction's source (backpressure) but keeps running the loop, so the idle deadline (`time.monotonic`) is evaluated even when the outer terminal does not drain. It propagates window-size changes (`TIOCSWINSZ` on `SIGWINCH`). Activity is a byte from the outer tty that is not part of a terminal reply sequence: cursor position reports (`ESC [ <n> ; <n> R`), device attributes (`ESC [ ? ... c`, `ESC [ > ... c`), mode reports (`ESC [ ? ... $ y`), focus events (`ESC [ I`, `ESC [ O`), OSC replies (`ESC ] ... BEL` or `ESC ] ... ESC \`) DCS replies (`ESC P ... ESC \`), device status reports (`ESC [ 0 n`, `ESC [ 3 n`) and window reports (`ESC [ 8 ; <rows> ; <cols> t`, `ESC [ 4 ; <h> ; <w> t`) are relayed but do not reset the idle timer (umbrella decision 8). A sequence that starts with `ESC` and is not yet complete is held for at most 64 bytes or 100 ms; when it completes as a reply it is relayed without counting, and when the limit passes or it cannot be a reply it is relayed and counts as activity. Pane output never counts. When `now - last_activity > idle_seconds`: `SIGTERM` the child, wait up to 2 s, `SIGKILL`, reap, discard both relay buffers and any outer-tty bytes already read (`termios.tcflush(TCIFLUSH)` on the outer tty), restore the terminal, then go back to 3.3: the screen clear and `Code: ` prompt are written with a 2 s deadline; when the write cannot complete in 2 s (the outer terminal does not drain) the gate exits 1. The tmux server, session and panes keep running (probed).
   7. **Fail-closed cleanup.** The gate holds the only master of the child's pty. On any exit path (`SIGHUP`, `SIGTERM`, an exception, a relay error, disconnect) the `finally` sends `SIGTERM` to the child, waits up to 2 s, sends `SIGKILL`, closes the master and exits 1; if the child cannot be reaped within a further 2 s the gate closes the master and calls `os._exit(1)`. When the gate is killed with `SIGKILL` the kernel closes the master and the tmux client receives `SIGHUP` and exits (probed with a prototype). No `list-clients` polling or tty-name matching exists.
   8. When the child ends and the gate did not end it: exit 0 if the child exited 0, else 1. The gate never `exec`s a shell, never starts `$SHELL`, and has no code path that runs an interactive shell.
   9. **Failure classes kept separate** (Astra 8): before attach (verifier, config, tmux control command) → exit 1, no client ever started; after attach (relay error, signal, disconnect) → cleanup above, exit 1; at re-authentication after idle (the client is already gone) → the 3.4 rules, exit 1.
4. **tmux is not modified.** The gate runs no `set-option`, `set-hook`, `source-file`, `new-session -t`, `list-clients`, `detach-client` or `lock-*` command. The only tmux commands it runs are `has-session -t =work`, `new-session -d -s work` and `attach-session -E -t =work`.
5. **Enrolment** (`bin/k3dm-web-console-totp enroll`, operator, at the machine; trusted step under O3, residual R-ENROL).
   1. The wrapper refuses with exit 2 and `web-console-totp: refusing to show a secret here: <reason>` when `$TMUX`, `$TMUX_PANE` or `$STY` is set, stdin or stdout is not a tty, `/dev/tty` cannot be opened, `$SSH_CONNECTION` or `$SSH_TTY` is set, or the effective uid is 0. These refusals prevent accidents only.
   2. It runs `_wc_priv_open`, then `_wc_priv /Library/Developer/CommandLineTools/usr/bin/python3 -IS /Library/PrivilegedHelperTools/k3dm-web-console/totpctl enroll` (code checked). In that root process: `ENROLL_BEGIN`, open `/dev/tty` itself (proof owed P6) and print the base32 secret and the `otpauth://totp/` URI to it only; neither goes to stdout, stderr, argv, the environment or any log.
   3. It asks on `/dev/tty` for one current code (`ENROLL_COMMIT`); on success it prints `enrolled` and clears the screen and scrollback (`ESC[3J ESC[H ESC[2J`). No valid code within 300 s, or any error before the commit's `rename`, leaves nothing on disk (the post-rename fsync case of the state commit is covered by its rule above).
   4. `rotate` is the same flow with `ROTATE_BEGIN` and `ROTATE_COMMIT` (the operator's password is the recovery factor for a lost phone). `status` runs `STATUS` and prints `enrolled`, `not enrolled` or `state damaged`, never a secret. `totpctl status --wire` (root, used by install) prints the daemon's wire word unchanged: `ENROLLED`, `NOT_ENROLLED` or `UNAVAILABLE`. Each Mac has its own secret under the account label `k3dm-console-<hostname>`; nothing copies it and it is in no `secrets.*.list`.
6. **Install** (`bin/k3dm-web-console-totp install [--tmux PATH] [--dry-run]`, operator, watched; through the library, same transaction as part A).
   1. Refusals (exit 2): part A not installed (no A manifest rows or no `forced-command.stub`); the `sshd_config` first line does not parse; `PY` missing or not executable.
   2. Sources unchanged from `HEAD` (exit 9): this script, the three Python files, the plist template, `scripts/lib/web_console_common.sh`, both `system.sh` copies, `scripts/lib/agent_rigor.sh`. Installed bytes are the `HEAD` blobs (R-INSTALL).
   3. `tmux` is `--tmux PATH` when given (absolute and executable, else exit 2); otherwise the first executable of `/opt/homebrew/bin/tmux`, `/usr/local/bin/tmux`, `/opt/local/bin/tmux`, `/usr/bin/tmux`, in that order; none is exit 2 (`web-console-totp: tmux not found; give --tmux PATH`). The operator's `PATH` and `command -v` are not used. The run prints the chosen path. (Probe: tmux exists only at `/opt/homebrew/bin/tmux` on m4-air.)
   4. `_wc_priv_open` (exit 10). `_wc_trust_check` on the helper directory, `/etc/k3dm-web-console`, `/Library/LaunchDaemons`, `/private/var/db`, `/private/var/log`, the state and run directories when they exist, `_wc_trust_chain` on `PY` and `_wc_trust_check` on `PYAPP` and the framework `Python3` library (exit 8); `_wc_dest_check` on every destination file, the log and the plist (exit 8).

## What NOT to do

- Do not use tmux `lock-after-time`, `lock-command`, `lock-server`, grouped sessions, `list-clients` polling or any `set-option` in the gate.
- Do not store the TOTP secret in the Keychain, the checkout, `$HOME`, an environment variable, an argument, a temporary file outside the commit, or any log, and do not print it to stdout or stderr.
- Do not add a shell, `$SHELL`, `exec sh` or any fallback path on error; every error ends the connection.
- Do not name `/usr/bin/python3` or `/usr/bin/env` in a shebang or `ProgramArguments`.
- Do not read any path, socket or executable from the environment in a root-owned artifact.
- Do not run any test against the operator's real tmux server, real `/etc`, `/var` or `/Library`.
- Do not build a separate admin account, a root-owned installer verifier or a phone confirmation (O3).
- Do not add Cloudflare code, change part A's sshd settings, or put the console in an agents or secrets list.
- Do not commit, push, dispatch, or skip pre-commit hooks.
