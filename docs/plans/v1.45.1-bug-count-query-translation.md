## Problem

Bug-count questions in Slack (`/ask-docs …` and `codex|claude|gemini how many bugs …`) are routed by
hand-written regex in `scripts/lib/webhook/bug_count.py`. It understands a literal version,
`last N releases`, `this release`, `P0`–`P3` and open/fixed. Any other phrasing — "bugs we closed
since August", "P1s fixed between the 1.40 and 1.42 releases", "how many outstanding high-priority
bugs" — misses the regex and falls through to similarity search, which answers a count question
with five loosely related documents.

A formal grammar (yacc/lex) does not fix this: Slack questions are free English, and a grammar is a
larger regex. The fix keeps the regex as the fast path and, on a miss, asks the model for one thing
only: a small query object. The code validates it against a closed schema and `bug-tally` computes
the numbers. The model never sees a bug doc and never produces a number, so it cannot invent a
count; at worst it misreads the question, and the reply states what was counted so the reader can
see that.

## Definitions (the contract every item uses)

**Query object** — a JSON object with exactly these keys; all are required, `null` where unused:

| key | allowed values |
|---|---|
| `releases` | `"*"`, `"vX.Y.Z"`, `"last:N"` with N 1–10, or `"range:vA.B.C..vX.Y.Z"` (inclusive, A.B.C ≤ X.Y.Z) |
| `priority` | `null`, `"P0"`, `"P1"`, `"P2"`, `"P3"`, or `"P0-P1"` (urgent = P0 and P1 together) |
| `state` | `null`, `"open"`, `"closed"` |
| `filed_since` | `null` or `YYYY-MM-DD` |
| `filed_until` | `null` or `YYYY-MM-DD`, not before `filed_since` |

Anything else — an extra or missing key, a wrong type, N outside 1–10, an unknown priority, an
invalid date, text around the object other than one optional ```` ```json ```` fence, more than
400 characters — is **invalid**. Invalid means: fall back to similarity search, exactly as today.

**Routing source** — `regex` (the existing `match()` hit), `model` (a valid query object), or
`none` (fall back to search).

## Fix

### 1. `CountQuery` grows to the query object; one validator

`scripts/lib/webhook/bug_count.py`:

- `CountQuery` becomes `(release, priority, state, filed_since, filed_until)`; `match()` fills the
  two new fields with `None`. The existing `last:N` / `vX.Y.Z` / `*` values are unchanged; add
  `range:` and `P0-P1` handling to `_select` and `counts_of`.
- `parse_query(text) -> CountQuery | None` implements the Definitions table exactly. It is pure,
  does no I/O, and returns `None` for every invalid case.

### 2. Translation on a regex miss

`bug_count.resolve(question, *, model) -> tuple[CountQuery, str] | None`:

1. `match(question)` hit → `(query, "regex")`; the model is not called.
2. Gate: the question must contain `_BUG_RE` **and** one of
   `how many|count|number of|tally|total|breakdown|per release|since|between|stats`. Gate miss →
   `None`; the model is not called.
3. `K3DM_BUG_QUERY_MODEL=0` → `None` (kill switch, default on).
4. Otherwise call `model(prompt)` once. The prompt is a fixed module constant: the Definitions
   table, eight worked examples (question → object), the current date, the current release (from
   `_current_release`), and the instruction to reply with the object only. The question is passed
   through `agent._sanitize_question` first and placed last, inside a delimited block.
5. `parse_query(output)` valid → `(query, "model")`; otherwise `None`. A model exception or
   timeout → `None`.

`scripts/lib/webhook/ask_docs.py` `answer()` and `scripts/lib/webhook/agent.py`
`_run_cluster_ask()` both call `resolve()` in place of `match()`; there is no other routing.
`ask_docs` passes its `model` argument; `agent` passes `_call_gemini`.

### 3. Filed-date filter in the tally

`scripts/bug-tally.py` gains `--filed-since` and `--filed-until` (ISO dates). Before counting, a doc
is dropped when its Filed date (from `doc_lifecycle`, v1.44.0: the `**Filed:**` line, else the file
name date) is outside the range. A doc with neither is dropped from a date-filtered count and
reported in a new JSON field `undated` (count) so the reply can say so. Without the flags the
output is byte-identical to today's.

`bug_count.reply()` passes the flags when the query sets them.

### 4. The reply says what it counted

Every count reply starts with one line:

- regex: `Counted: <description>.`
- model: `Counted: <description> — interpreted from your question; rephrase if that is not what you meant.`

`<description>` is built from the query object by code (never by the model), e.g.
`P1, closed, last 2 releases (v1.43.0, v1.42.0), filed since 2026-08-01`. When the date filter
dropped undated docs: `N docs have no Filed date and are not counted.`

The `agent.py` prefix `📊 Counted, not asked (<agent> was not consulted)` stays for `regex`; for
`model` it becomes `📊 Counted (<agent> interpreted the question; the numbers come from the tally)`.

### 5. Logging

Log one line per count question: routing source and, for an invalid model reply, the first failed
rule (`extra key`, `bad releases`, …). Never log the question text or the model output — the
corpus guide promises the question is never logged.

### 6. Docs

- `docs/guides/slack-corpus-qa.md` "Count questions": the regex table stays; add the model path,
  the `Counted:` line, the kill switch, and that a misread is visible and harmless.
- `CHANGELOG.md` `[Unreleased]`.

## Operational Requirements

| Item | Requirement |
|---|---|
| Resources | No new workload. One AI CLI call (the existing `_call_gemini` path and budget) per count question that misses the regex and passes the gate. |
| Capacity | No new metric series, PVCs or log volume beyond one log line per count question. |
| Rollback | `K3DM_BUG_QUERY_MODEL=0` in the webhook environment, then `make restart-webhook`: back to regex-or-search with no code change. A revert of the commits removes the bug-tally flags; nothing persists. |
| Proof it works | In `SLACK_CHANNEL_ID`: `/ask-docs how many bugs did we close since 2026-09-01` replies with `Counted: closed, all releases, filed since 2026-09-01 — interpreted…` and per-release counts; `/ask-docs how many P1 bugs from last two releases` still replies `Counted: P1, last 2 releases…` with no model call (webhook log shows source `regex`). |

## Tests (each shown failing against the pre-change code, on a temp copy)

`test_bug_count.py`:

1. `parse_query` accepts: each `releases` form, `P0-P1`, both dates, a fenced object.
2. `parse_query` rejects, one parametrized case each: extra key, missing key, `last:0`, `last:11`,
   `v1.2`, `range` with A > B, `P4`, `"high"`, `2026-13-01`, `until < since`, prose before the
   object, two objects, 401 characters, non-JSON.
3. `resolve` with a regex hit never calls the model (model stub fails the test if called).
4. `resolve` on a gate miss ("what is the oldest open bug about vault") never calls the model.
5. `resolve` with `K3DM_BUG_QUERY_MODEL=0` never calls the model.
6. Model returns a valid object → source `model`; returns prose, raises, or times out → `None`.
7. The prompt contains the sanitized question exactly once, after the delimiter, and the current
   release.
8. Reply's first line is the code-built `Counted:` description for both sources; the model text
   never appears in the reply.
9. `ask_docs.answer` and `agent._run_cluster_ask` route through `resolve` (stub it; assert both
   call it and fall back to search / the agent on `None`).

`test_bug_tally.py`:

10. With a fixture repo of three docs (Filed in range, Filed out of range, no date): the filter
    counts one, reports `undated: 1`; without flags the JSON equals the pre-change output.

**Mutation checks (paste output):** skip validation (`parse_query` returns any parsed dict) →
test 2 fails; call the model before `match()` → test 3 fails; drop the date filter → test 10

## What NOT to Do

- Do NOT create a PR, commit to `main`, or use `--no-verify`.
- Do NOT let the model see bug docs, tally output or counts, or produce any text that reaches the
  reply.
- Do NOT accept a partially valid object, repair one, or guess missing keys.
- Do NOT call the model when the regex matches or the gate misses.
- Do NOT log the question or the model output.
- Do NOT add the count path to the cloud bridge allowlist; `/api/v1/ask` stays excluded.
- Do NOT change the existing regex phrasings' answers beyond the new first line.
- Do NOT run `make test` or `make e2e`; the live eval is Claude's.
