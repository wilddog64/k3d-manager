# v1.25.0 — concise, color-coded `make status` output contract

**Target branch:** `v1.25.0`
**Status:** SCOPED — implementation not started. Plan doc **#4** for v1.25.0.
**Primary files:** `Makefile`, `bin/cluster-status`, focused status tests under `scripts/tests/`.

## Problem

`make status` currently prints full node/pod lists, every ArgoCD application, Trivy details, and
service probes in one stream. The actionable failures are buried in diagnostic output, and the same
stream is difficult to consume from Slack or scripts. The default report must be service-oriented:
for example, report `shopping-cart-order` as failed with its health/HTTP return code, without dumping
the underlying pod list.

## Goals

- Make the default status report short and scan-friendly, with failures first.
- Use color consistently: red means fatal/error, yellow means warning/degraded, and green means
  healthy/passing.
- Preserve a detailed troubleshooting mode and provide a stable machine-readable mode.
- Return meaningful exit codes so CI, Slack command wrappers, and shell scripts can detect failure.
- Never leak credentials, tokens, response bodies, or ANSI escape sequences into JSON.
- Report failed or degraded services, not individual pods, in the default mode. Pod-level detail is
  reserved for `make status-full`.

## CLI and Make targets

Implement these targets without changing the underlying read-only probes:

```text
make status                 # concise human summary (default)
make status SERVICE=<name>  # focused detail for one service
make status-full            # current detailed diagnostic report
make status-json            # stable JSON summary for automation/Slack
```

`bin/cluster-status` must accept equivalent `--summary`, `--full`, and `--json` flags. The Makefile
targets set the mode explicitly rather than relying on an interactive shell. Existing provider and
context variables (`CLUSTER_PROVIDER`, `APP_CONTEXT`, and `INFRA_CONTEXT`) continue to work.

`SERVICE=<name>` selects one allowlisted service, such as `shopping-cart-order`, `grafana`, or
`argocd`. Focused mode prints only that service's status, health/HTTP return code, readiness, recent
failure reason, rollout age when available, and a safe remediation hint. It must not print unrelated
pods, applications, credentials, or full cluster tables. An unknown service exits with code `3` and
prints the accepted service names. The equivalent binary form is
`bin/cluster-status --service <name> [--json]`.

## Summary output

The concise report has a fixed order:

1. Header with provider/context and `Overall: HEALTHY|WARN|FAIL`.
2. `FAILED SERVICES`/`ERRORS` section, if any, with service name, health result/HTTP return code, readiness, and a
   short reason or remediation hint.
3. `WARNINGS`, if any, for non-fatal service drift or stale checks.
4. Compact green health lines for passing services and aggregate checks; do not print healthy pods.
7. A final hint: `Details: make status-full` and, when relevant, a targeted remediation command.

Example:

```text
Cluster: ubuntu-hostinger (k3s-hostinger)
Overall: FAIL (2 errors, 1 warning)

ERRORS
  ✗ shopping-cart-order: health HTTP 503; readiness 0/1; reason Degraded
      hint: kubectl describe deployment/shopping-cart-order -n shopping-cart-apps
  ✗ ArgoCD login: HTTP 401

WARNINGS
  ! 3 ArgoCD applications: OutOfSync

HEALTH
  ✓ Nodes: 1/1 ready
  ✓ shopping-cart-frontend: HTTP 200
  ✓ shopping-cart-payment: HTTP 200
  ✓ Prometheus: healthy
  ✓ Grafana: healthy
  ✓ Latest CVE scan: passed (5 services)

Details: make status-full
```

The exact service list may vary by provider, but labels and severity semantics must remain stable.
Failures must be listed before healthy checks so a captured/truncated report still contains the key
diagnostic information. A failed service line must include the service identifier and the best
available health return code (`HTTP nnn`, Kubernetes readiness `ready/desired`, or `unknown` when the
probe itself was unreachable). Healthy services may be summarized or listed as one-line checks; their
pods must never be emitted by default.

Focused output example:

```text
Service: shopping-cart-order
Status: FAIL
  health: HTTP 503
  readiness: 0/1
  reason: Degraded
  hint: make status-full SERVICE=shopping-cart-order
Exit code: 1
```

## Color contract

Use ANSI colors only when output is a TTY and color is enabled:

| Severity | Color | Meaning |
|---|---|---|
| fatal/error | red (`31`) | probe failed, authentication failed, unreachable backend, degraded required service |
| warning | yellow (`33`) | non-fatal drift, stale data, available patch, partial readiness |
| healthy | green (`32`) | probe passed, resource ready, service reachable |

Rules:

- `NO_COLOR=1` disables color.
- `STATUS_COLOR=always` forces color for human output; `STATUS_COLOR=never` disables it.
- JSON mode never contains ANSI escapes, regardless of environment.
- Full mode uses the same severity colors for its summary lines but may retain uncolored raw command
  tables so pasted diagnostics remain readable.
- Color helpers must quote values and must not alter exit status or parseable text.

## JSON contract

`make status-json` emits one JSON object on stdout and diagnostics only on stderr. The top-level shape
is stable:

```json
{
  "overall": "fail",
  "provider": "k3s-hostinger",
  "context": "ubuntu-hostinger",
  "errors": [{"id": "shopping_cart_order", "service": "shopping-cart-order", "status": "error", "http_code": 503, "ready": "0/1", "reason": "Degraded", "hint": "make status-full"}, {"id": "argocd_login", "service": "argocd", "status": "error", "http_code": 401, "hint": "make show-service-passwords"}],
  "warnings": [],
  "checks": [{"id": "grafana", "service": "grafana", "status": "healthy", "http_code": 200}],
  "counts": {"nodes_ready": 1, "nodes_total": 1, "argocd_synced": 28, "argocd_out_of_sync": 3}
}
```

IDs, status values (`healthy`, `warning`, `error`, `unknown`), and top-level keys are versioned
contract fields. Service error/check objects use `service`, optional numeric `http_code`, optional
`ready` (`ready/desired`), `reason`, and `hint`. Do not include pod logs, complete ArgoCD objects,
passwords, or arbitrary API payloads.

## Exit status

- `0`: all required checks healthy; warnings may be present.
- `1`: one or more fatal/error checks.
- `2`: status collection could not reach the selected cluster or provider control plane.
- `3`: invalid CLI/mode/JSON configuration.

Individual probe failures must be recorded rather than causing `set -e` to terminate collection early;
the report should include all available failures in one run.

## Slack integration

`/cluster-status` should consume JSON or the concise summary and render only the header, error/warning
lines, and compact health counts. Slack payloads must not contain ANSI codes. A terminal copy may retain
colors, but Slack uses emoji/severity fields (`:x:`, `:warning:`, `:white_check_mark:`) instead.

## Tests and gates

- BATS tests cover color enabled/disabled, `NO_COLOR`, forced color, non-TTY output, JSON without ANSI,
  summary ordering (errors before warnings before health), provider-unreachable exit `2`, and healthy
  exit `0`. Focused mode tests known services, failed-service return codes, unknown-service exit `3`,
  and verifies unrelated pod/application output is absent.
- JSON fixtures validate the schema and stable IDs; malformed probe output must become an `unknown`
  check rather than invalid JSON.
- `shellcheck -S warning bin/cluster-status` and all touched shell files are clean.
- `git diff --check` passes; `_agent_audit` passes.
- Existing detailed status behavior remains available through `make status-full`.

## Definition of done

An operator can run `make status` and immediately see red failed services (including health/HTTP return
codes), yellow warnings, and green health checks without scrolling through pod dumps. They can run
`make status SERVICE=shopping-cart-order` for one service's actionable details. `make status-full`
remains the troubleshooting escape hatch, and `make status-json` can be safely captured by Slack/CI with
deterministic statuses, exit codes, and no secrets or terminal escape sequences.
