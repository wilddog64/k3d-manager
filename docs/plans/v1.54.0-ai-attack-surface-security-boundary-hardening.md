## Problem

AI-assisted adversaries can rapidly iterate against exposed interfaces, automate credential discovery, place malicious instructions in logs/Slack/Git/RAG material, and attempt to turn a lower-trust observation into a privileged tool action. Existing cloud-bridge limits, tests, CVE scans and agent instructions are useful but are not a complete authorization or containment boundary. This plan hardens currently exposed seams without waiting for the larger v2.2 multi-agent gateway.

## Scope and sequencing

1. **Inventory and threat model first (no mutation):** enumerate actual public Cloudflare routes, webhook and bridge ingress, authentication and replay checks, tool allowlists, fixed argument schemas, reader/writer roles, LaunchAgent credentials, GitHub Actions token scopes, Vault access, Mac-to-Hostinger paths, ACG temporary trust, and external watchdog dependencies. Mark verified vs assumed; do not claim compromise from 502/alert spikes.
2. **Deterministic per-tool authorization:** preserve existing read-only diagnostics; require verified caller identity, exact allowlisted verb and target, bounded argv and output, expiry/nonce/replay handling, fail-closed policy loading, and denial audit. Direct tool invocation must not bypass the check. Header-role capping already exists and fails closed (`scripts/lib/webhook/policy.py:118-140`, `auth.py:131-137`): preserve and test it rather than rebuild. Failed authentication gets its own per-source limit and counter: `docs/bugs/2026-11-10-webhook-failed-auth-attempts-unthrottled-and-uncounted.md` (filed separately so it does not wait for this plan). Replay and expiry apply where a request carries them (Slack signatures, `auth.py:100`; bridge `expires_at`); bearer tokens are static, so for them the control is rotation and failed-attempt detection, not nonces. Separate read-only, reversible maintenance, deployment and destructive actions. Do not grant arbitrary shell or wildcard `kubectl`/cloud access.
3. **Untrusted-input boundary:** treat external logs, GitHub issues and files, Slack text, Cloudflare responses, vector chunks, webhook results and agent summaries as data, never executable instructions or approval. Attach immutable source/revision, timestamp, trust category, evidence links and freshness to RAG and incident findings. Sanitization and model-side warnings are defense in depth; tools must refuse unauthorized actions regardless of prompt content.
4. **Privileged change protection:** deny autonomous changes to security policy, bridge/webhook allowlists, secrets, service accounts, admission policy, CI gates, signing configuration and DR destruction until the v1.59.0 SHA-bound operator approval gate is verifiably enforced. Validate the present protection before claiming that a GitHub check is required.
5. **Host and network containment audit:** map which workloads can reach Vault, Argo CD, bridge, hub and other namespaces. Propose staged default-deny Kubernetes ingress/egress policies with audited legitimate flows and safe rollback; never apply a policy that could sever control or emergency access based on AI recommendation alone. Coordinate Mac endpoint controls with the v1.53.0 workstation proposal.
6. **Independent failure detection:** verify off-host heartbeat/blackbox coverage and alert delivery using existing v1.55.0 Hostinger watchdog plan. That plan probes reachability only (`docs/plans/v1.55.0-hostinger-offsite-hub-watch.md:51-71`); it does not carry hub-originated alerts or logs, so item 8 must build the off-host path, not assume it. An attacker or outage on the M5 must not silence all evidence; keep any off-host service read-only and independently credentialed. Validate backup immutability / independently protected copy with existing DR plans.
7. **No autonomous containment in this slice:** publish an evidence-backed containment runbook and approval matrix. Preauthorized reversible isolation is only a later separately reviewed design; no auto-quarantine, auto-delete, token rotation or unrestricted host shell.

8. **Edge intrusion detection (operator, 2026-11-10: "can we then detect any abnormal actions from internet?"; placed here, "go ahead to do that").** Falco (v1.62.0) sees an attacker only once inside a pod; nothing watches who tries to get in. Deterministic rules, no ML (one legitimate identity), report only: no rule blocks a source or revokes a session by itself, so a forged event cannot lock the operator out.
   - **Signals that exist today (spec these first):** webhook 401/403 per `client=` from the access log (`bin/k3dm-webhook:2882-2894`) and the failed-auth counter from the bug in item 2; Slack bad-signature 401s; cloud-bridge rejected requests (the `reason` it commits); login failures on **all seven** public hostnames in `scripts/etc/cloudflared/config.yml` (argocd, frontend, keycloak, prometheus, alertmanager, grafana, webhook): Keycloak, ArgoCD and Grafana login events and the Prometheus/Alertmanager basic-auth 401s, not only the webhook and bridge.
   - **Signals that wait on Cloudflare Access being deployed:** Access denials, an identity outside the allow-list, a new device or country, unusual hours, impossible travel. No Access application exists today (no setup code in `bin/`, `scripts/` or the Makefile; `docs/plans/v1.43.11-web-console-ssh-behind-cloudflare-access.md` is proposed; `docs/plans/v1.38.0-cloud-session-endpoint-access.md:607` forbids one). Spec these rules only after an Access plan lands, with captured proof of the log fields, retention and pull method on the account's plan (host, date).
   - **Alerts and evidence leave the hub.** Rules evaluated on the hub can be muted by an attacker on the M5, and the webhook log is stderr on the M5 (`scripts/lib/webhook/log.py:28`). Ship the webhook and auth logs off-host (append-only, as in the web console audit part of `docs/ideas.md`), evaluate the edge rules there, and alert through a receiver the hub cannot reconfigure. Silence is a finding too: no log lines from a hub that is reachable.
   - **Tuning, not false comfort.** The operator roams (three Macs, ACG and cloud sessions), so "new IP" style rules start as a daily digest, not a page, until a baseline exists; a silent source shows `unknown`, never a green zero. Rate-limit the alerts themselves so a flood cannot become an SMS or attention DoS.
   - **Spoofable source identity.** The webhook binds 127.0.0.1 and takes the source from `CF-Connecting-IP`, which any local process can set; per-source rules are trusted only for tunnel traffic, and that Cloudflare overwrites a client-supplied header must be proven, not assumed.
9. **`cloud-requests` is a trust boundary.** `bin/k3dm-cloud-bridge` fetches `refs/heads/cloud-requests` and runs each valid request; `validate_request` (`:74-104`) checks schema, action, args and expiry, not who wrote the commit. Anyone who can push to the branch (any repo-write token on the three Macs, a cloud agent, a leaked PAT) gets hub-run actions from `scripts/lib/webhook/cloud_actions.py`, including AWS sandbox lifecycle. Add a GitHub ruleset limiting who may push to the branch, a commit-author or signature check in the bridge that fails closed, and an audit line per accepted and rejected request. List readers and writers (writer `bin/k3dm-cloud-request`; reader the bridge) before dispatch.

## Deliverables

- Security trust-boundary inventory with verified endpoints, privileges, credential locations by *type only* (never values), and residual unknowns.
- Authorization matrix and fixed tool-schema / replay-negative-test specification for cloud-bridge and Slack/webhook paths.
- Adversarial regression fixtures covering prompt injection in logs, RAG chunks and Slack; forged tool results; replayed approvals; cross-agent permission escalation; stolen read-only token; failed policy store; CI self-modification; and fake-green test evidence.
- Proposed network-policy matrix and safe rollback prerequisites; evidence-only GitHub Actions privilege review.
- Read-only Security Effectiveness dashboard contract: denied action count, source freshness, test attack detection numerator/denominator, time-to-detect, alert transport and containment verification (if implemented later), with unknown states rather than fabricated zeros.
- `cloud-requests` push protection and bridge author check (item 9), with a test that a request committed by a disallowed author is rejected and audited.
- Edge detection rule set (item 8): each rule's source, threshold, alert text and an injected-event fixture that fires it, plus a paired benign fixture (the operator's normal login) that does not.
- Incident runbook describing isolate / preserve evidence / rotate compromised credentials / trusted rebuild / independent recovery verification, requiring appropriate human authorization.

## Verification / acceptance

- [ ] Every exposed interface and reachable credential-bearing trust boundary has an evidence-backed inventory, owner and unknowns.
- [ ] Crafted logs, docs, Slack messages and tool results cannot cause an unauthorized bridge/tool action in isolated negative fixtures; no model output itself satisfies identity or approval.
- [ ] A read-only identity cannot invoke a write/destructive tool even through direct adapter calls or replay; all denials are auditable without secrets.
- [ ] Each edge rule fires on its injected fixture (webhook 401 burst, Slack bad signature, bridge rejection, login failures on each public hostname; Access-based rules only once Access exists) and stays silent on the operator's normal use; rules run and alert off-hub; a silent source shows unknown; no rule changes access by itself.
- [ ] A `cloud-requests` commit from a disallowed author is never executed and is audited.
- [ ] Security policy outage produces a visible refusal and does not silently grant access.
- [ ] Existing approved diagnostics still work and normal CI remains green.
- [ ] In disposable isolated tests, forged green evidence, stale/duplicate incidents and absent sensor/alert paths cannot be counted as verified success.
- [ ] Live behavior, external watchdog, rollback and real deployment coverage are explicitly **not verified** until separately approved E2 evidence exists.
