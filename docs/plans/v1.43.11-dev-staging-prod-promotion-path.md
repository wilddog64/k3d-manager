## Problem

Production is Hostinger: the `ubuntu-hostinger` app cluster serving `frontend.3ai-talk.org`. It
receives changes with no step in between.

| Change | How it reaches Hostinger today |
|---|---|
| App code | `services/<svc>/kustomization.yaml` pulls `k8s/base?ref=main` from each app repo. A merge to an app repo's `main` reaches every app cluster, Hostinger included, on the next ArgoCD sync |
| Platform config | ApplicationSets use matrix generators: (git source) × (every `role: app-cluster`). A release-branch commit reaches Hostinger as soon as the sets are reapplied |
| CVE fixes | The auto-patch promoter pins a clean image by digest, and ArgoCD deploys it everywhere |
| Fixes by hand | Debugging happens on Hostinger directly (SSH, `kubectl` against prod) |

The ACG sandbox and per-PR vClusters test changes, but nothing requires a change to pass them before
it reaches production.

## Design

### Environments

| Env | Cluster | Lifetime | Gets |
|---|---|---|---|
| **dev** | Per-PR vCluster (Tier 1), plus an optional local app cluster on the M4 | ephemeral | any branch, any time |
| **staging** | A **persistent** app cluster built like Hostinger: k3s (not k3d), the same k3s version, Istio ambient with the k3s CNI paths, Cloudflare tunnel ingress to a `staging.` hostname | persistent, rebuildable | what is proposed for production |
| **prod** | Hostinger | persistent | only what staging verified, through `make promote` |

The ACG sandbox stays the cloud e2e (Tier 2) and can be registered as `dev` or `staging` per run.

Each cluster's ArgoCD registration Secret gets `k3dm.k3d.io/env: dev|staging|prod`. The existing
`role: app-cluster` label stays as is, because four ApplicationSets select on it
(`reference_hub_app_cluster_registration_is_load_bearing_for_eso`).

### D1. Where staging runs — DECIDED 2026-10-25: k3s VM in OrbStack on the M5 hub (operator: "go as you suggested")

**Recommended:** a k3s Linux VM in OrbStack on the **M5 hub**, about 6–8 GB.
- Pros:
  - It is always where the hub is, so ArgoCD reaches it without the LAN or the other laptop.
  - It travels with the hub.
  - The M5 has room for it (32 GB, with a 12 GB hub reserve).
- Con: the hub and staging share the machine, so a staging load test competes with the hub.

**Alternative A:** the same VM on the M4. This keeps load off the hub, but staging becomes unreachable
whenever the M4 is away or asleep, so promotions would stall.

**Alternative B:** a second small VPS. This is the closest to production, but it costs money and is a
second public host.

### D1a. Staging sizing, isolation and parity

Review note, 2026-10-25: the M5 also hosts the hub, observability, Vault and local validation.
Staging must have a resource reservation and must not compete with critical hub services. Running
k3s with the same Istio version is a start, but it does not prove parity.

**Isolation: a hard cap, not a share.**
- OrbStack machines and the OrbStack Docker engine (where the k3d hub runs) share one VM, so an
  OrbStack machine gives no hard reservation. Phase 1 must prove which mechanism it uses before
  building on it. In order of preference:
  - **(a)** a separate VM with fixed memory and vCPUs, for example Lima on Apple Virtualization.
    This is a hard isolation boundary, and it is the default unless (b) is proven.
  - **(b)** an OrbStack machine with the cgroup limit `MemoryMax` and `CPUQuota` on `k3s.service`.
    This is acceptable only if the live check shows staging is OOM-limited inside its cap while the
    hub stays unaffected.
- **Budget on the 32 GB M5** (a starting point, to be replaced by measurement):

  | Consumer | Budget |
  |---|---|
  | macOS and apps | ~6 GB |
  | Hub VM (cluster, observability, Vault) | sized from 7 days of measured hub peak working set + 25% |
  | Staging | hard cap 6 GB, 3 vCPUs |
  | Free headroom | ≥ 4 GB, or the hub's reserve from `hosts.conf` (12 GB, plan 2 D2b), whichever is larger |

  If the measured hub peak does not leave room for this, staging goes to Alternative A (the M4)
  instead of shrinking the hub. That is an operator decision, with the numbers attached.
- **Inside staging:** k3s `--kube-reserved` and `--system-reserved`, and the same requests and limits
  as the prod manifests, so an over-requesting change fails on staging the way it would on
  Hostinger.
- **Hub priority:** the hub's critical workloads (Vault, ESO, ArgoCD, Prometheus, Alertmanager) keep
  their requests and get a PriorityClass. A host memory-pressure alert pauses staging first
  (`make staging-pause` scales the staging workloads to 0). Staging never pauses the hub.
- **Watched:** staging's memory and CPU against its cap, and the hub's working set, both go to the
  existing dashboards. An alert fires when staging is above 90% of its cap or host free memory is
  below the headroom.

**Parity: configuration-equivalent where it matters, and the gaps written down.**
- **Parity manifest:** `make env-parity` reads the same fields from staging and from Hostinger
  (read-only) and prints the differences:
  - OS release, kernel, **CPU architecture**, k3s version and flags;
  - Istio version and profile (ambient), CNI paths, Gateway API CRD version;
  - StorageClass, Kyverno version and policy mode, NetworkPolicies;
  - ESO and Vault auth method, cert-manager and issuers;
  - per-service requests and limits, replicas, `maxSurge`;
  - the ingress path (Cloudflare tunnel → Gateway).
  Every difference must be in the **declared-divergence list** in `docs/architecture/promotion-path.md`,
  or the check fails. Phase 2 makes a clean parity check a promotion gate.
- **Known divergences to declare** (each with its mitigation):
  - **CPU architecture:** the M5 is arm64. Hostinger is expected to be amd64; phase 1 checks this
    and records it. With a multi-arch index, staging runs the arm64 image, so the amd64 image that
    prod runs is never exercised on staging. Mitigation: the phase 2 image gates (cosign, Trivy)
    check the amd64 platform digest explicitly. Before prod, an amd64 smoke runs on the ACG sandbox
    (x86) for changes that touch images, so ACG Tier 2 becomes the arch-parity gate for those.
  - Node size and count, data volume, and the external hostname.
  - Payment: Stripe test mode on staging.
- **Own credentials and state, never shared with production:**
  - its own Cloudflare tunnel and credentials, and its own `staging.` hostname;
  - its own Vault paths (a `staging/` prefix) with their own policies;
  - Stripe test keys; synthetic seed data;
  - production data is never copied to staging.
  `staging-up` refuses to start if any production credential name or path appears in staging's
  configuration.

### D2. Environment refs replace release-branch tracking — DECIDED 2026-10-25: per-environment git branches (operator: "let's do per-environment git branch")

Each environment reads a git ref of its own:

- **dev:** the working branch or PR head, as today.
- **staging:** branch `deploy/staging` in k3d-manager, fast-forwarded by `make promote TO=staging`
  (by default, to the current release branch tip).
- **prod:** branch `deploy/prod`, fast-forwarded **only** by `make promote TO=prod`, and only to a
  commit that `deploy/staging` already passed.

The ApplicationSets select the revision by the cluster's `env` label. This **supersedes** the
2026-07-24 decision (values follow the release branch, so every release needs
`make appsets-reapply`):

- Applying the sets once makes them stable.
- A release becomes "promote to staging, verify, promote to prod".
- The CLAUDE.md release rule is rewritten in phase 2, not before.
- Until phase 2 lands, prod keeps today's behaviour.

`deploy/staging` and `deploy/prod` are protected. Only the promote flow moves them: no direct push,
no force push, fast-forward only.

### How changes move: environment pointers, not git flow

Nobody merges into `deploy/staging` or `deploy/prod`. They are pointers that only `make promote`
moves. Day-to-day git does not change:

    feature work → k3d-manager-vX.Y.Z (release branch) → PR → squash-merge to main
                                 │                                  │
                  promote TO=staging REF=<branch>       promote TO=staging (default: main)
                    (optional pre-merge soak)                        │
                                                       gates pass → promote TO=prod

- **No develop branch, no back-merges, no merge commits on environment branches.** Fixes always go
  through `main`, so the environments cannot drift apart.
- **`deploy/prod` only fast-forwards, and only along `main`.** Each commit it gets is one that staging
  ran.
- **`deploy/staging` may run a release-branch tip before the merge** (`REF=<branch>`), so a release
  can soak on staging while its PR is under review. Because a squash merge creates a new commit, the
  tool moves `deploy/staging` without requiring a fast-forward. Every move is recorded in the ledger,
  and the history is never deleted (each move is a new commit on `deploy/staging` whose tree is the
  target's tree).
- **Tree equality is what lets a commit into prod.** The ledger records the tree hash staging ran.
  After the squash merge, the `main` commit's tree equals the release tip's tree, so
  `promote TO=prod` accepts that `main` commit without another soak. A `main` commit whose tree
  staging never ran is refused.
- **Hotfix:** fix branch → PR → `main` → staging (Critical fast-lane soak) → prod. It is the same path,
  only faster.
- **App repos** keep merging to their own `main`. Their commits and image digests reach staging and
  prod only through the lock (next section).

### Pinned app versions per environment

App repo bases at `ref=main` are replaced with a **promotion lock**, `deploy/<env>.lock.yaml`. For
each service it holds the app repo commit and the image **digest**, and it has a single
k3d-manager commit at the top.

- Kustomize overlays (`services/overlays/<env>/`) render the base at the locked ref and pin the
  image by digest.
- `make promote` copies staging's lock to prod unchanged. Production therefore runs byte-for-byte
  what staging ran.
- Dev keeps `ref=main` and floating tags, so app work stays fast.

### Gates before production

`make promote TO=prod` refuses unless every gate passes on the exact commit and lock being promoted:

1. Every staging Application is Synced and Healthy.
2. The e2e suite is green against staging: the existing e2e harness, pointed at the staging hostname.
3. The image gates pass:
   - cosign verify passes for every locked digest;
   - Trivy shows no **new** Critical compared with the current production lock.
4. Staging has **soaked** for at least `PROMOTE_SOAK_MIN` (default 30) with no firing staging alert.
5. **D3, operator approval — DECIDED 2026-10-25: both ways** (operator: "we can do both. it just
   convenient to have an alternative way to approve a promotion").
   - **(a) Terminal:** the operator runs `make promote TO=prod` themselves.
   - **(b) Slack:** `make promote TO=prod --request` posts the promotion plan to the status channel,
     with Approve and Deny buttons. It reuses the v1.33.0 Hermes Slack approval in
     `workers/slack-relay`: the approver allowlist, the `/hermes-auth` re-auth that lasts 24 hours,
     and the PULL model.
     - The hub-side promoter polls for the decision. Nothing on the hub listens for Slack.
     - An approval is **bound to the exact plan**: a hash over the target commit, its tree, the lock
       digest and the gate results.
     - It is **single-use** and **expires after 30 minutes**.
     - At execution the promoter **re-runs every gate**. If anything changed, the approval is void.
     - Only Slack user IDs on the allowlist can approve, and only after a current `/hermes-auth`.
     - The requester's identity is recorded. An agent may request, but its request still needs the
       operator's click.
   - Claude and the agents may run `make promote --plan` and `--request`. They never run the real
     promotion, and they cannot approve.
   - **One decision per request; the first one wins, and the other path is voided** (operator,
     2026-10-25: "if we approve from one the other should automatically void").
     - Every prod promotion has a single **promotion request** (id, plan hash, state
       `pending → approved|denied|void → executed`). The hub's promotion ledger is the source of truth.
     - **Approving** takes the git lock ref `refs/k3dm/locks/promote-prod` with an atomic
       compare-and-swap (see "Atomic claims and interrupted promotions" below).
       - When **terminal** approval wins, the pending Slack request is marked `void`. The hub pushes the
         void to the relay KV, and the Slack message is edited to "Approved in terminal at <time> — this
         request is void". A later click on it does nothing and replies that the request is void.
       - When **Slack** approval wins, a `make promote` for the same request reports "approved in Slack
         at <time>" and does not run a second promotion. A `make promote` for a different plan hash
         first voids the Slack request, then proceeds as its own request.
     - **Deny** from either path voids the request on both.
     - **A new request** for prod voids any older pending request.
     - At most one prod promotion runs at a time. A second approval can never run a second promotion,
       even if the void message has not reached Slack yet: the lock ref and the plan hash refuse it.
   - **Phase 2 acceptance must include:** (i) terminal-then-Slack and Slack-then-terminal races each
     produce exactly one execution, with the other path reported void; (ii) Deny on one path voids the
     other; (iii) a new request voids older pending ones; (iv) a click on a void Slack request changes
     nothing. Each case must be shown red against a version without the lock.

Every promotion is recorded as an append-only promotion ledger event (who, from, to, commits, lock
digest, gate results). Grafana shows what is running in each environment and how long the gap is.

### Atomic claims and interrupted promotions

Review note, 2026-10-25: a git lock serializes only if every claim is an atomic compare-and-swap,
and an interrupted deployment must be reconciled against the actual production state before any
other operation.

**Every lock and pointer update is a compare-and-swap.**
- A plain `git push` is **not** a lock: it rejects only non-fast-forward pushes. A second claim
  whose commit descends from the holder's commit is accepted, and both claims win.
- **Claim** with `git push --force-with-lease=refs/k3dm/locks/promote-prod: origin <claim>:refs/k3dm/locks/promote-prod`.
  The empty expected value means "succeed only if the ref does not exist". The server checks the
  old value and updates the ref in one step.
- **Release** and **every hand-off** use `--force-with-lease=<ref>:<oid the caller read>`.
- `deploy/prod` and `deploy/staging` move the same way, with the expected old tip, never with a
  bare push or `--force`. When the lock ref and `deploy/prod` move together, the push uses
  `--atomic`, so either both refs change or neither does.
- The claim commit is the **fencing token**. It records the request id, plan hash, approver, path
  (terminal or Slack), host and time. Every later step checks that the lock still holds its own
  claim oid before acting. A holder that lost the lock stops.
- **The Slack path never claims in the relay.** Cloudflare KV is eventually consistent and cannot
  arbitrate a race. A Slack click only records intent. The hub poller then claims with the same git
  CAS, and the terminal path does the same. Git is the only arbiter.
- **Locks have no time-based expiry.** A lock is never stolen because it is old. It is released only
  by its holder or by reconciliation (below).

**The promotion is journaled ahead of each step** in the ledger, in this order:
`claimed → pointer-moved → syncing → verified → executed`, or `failed`. Each state is written
before the action it names.

**Reconcile before any new operation.** `make promote`, `--request` and `promote-rollback` refuse
to start while `promote-prod` is held or the ledger has a promotion without `executed` or `failed`.
They point to `make promote-reconcile ENV=prod`, which is read-only until the operator confirms its
proposed action:

1. **Read the actual production state.** For each prod Application: the synced revision, sync and
   health status, any running operation, and the image digests of the **running pods**. The
   `deploy/prod` tip and the git config alone are not enough.
2. **Classify** against the interrupted promotion's from and to states:

| Actual state | Meaning | Proposed action |
|---|---|---|
| All Applications at the target revision, Healthy, pods on the target digests | finished, but not recorded | record `executed`, release the lock |
| `deploy/prod` still at the previous tip, and every Application and pod on the previous state | never started | record `failed`, release the lock |
| `deploy/prod` moved, Applications still syncing | in progress | wait, and re-check; nothing else may run |
| Mixed: some Applications or pods on the target and some on the previous state, Degraded, or a failed sync | partial | stop. The operator chooses roll forward (re-sync the target) or `promote-rollback`. Both run through the normal gates and CAS |
| Live state matches neither the previous nor the target state | drift | stop, alert, and require break-glass investigation. No automatic action |

3. **Record and release.** The decision goes in the ledger, and the lock is released with CAS
   against the interrupted claim's oid.

**Phase 2 acceptance must also include:**
- (v) Two claims racing, where the second claim's commit descends from the first, produce exactly one
  winner. Shown red with a plain push.
- (vi) A holder that lost the lock stops before moving `deploy/prod`.
- (vii) Each reconcile class is detected from stubbed live state, including a mixed state where
  `deploy/prod` moved but pods still run the previous digests.
- (viii) No operation starts while a promotion is unreconciled.
- (ix) A lock is never released or stolen by age.

### Rollback

`make promote-rollback ENV=prod` fast-forwards `deploy/prod` to a **new** commit that restores the
previous ledger entry's tree and lock. History is never rewritten. The rollback skips the soak gate
but still requires the cosign check.

### No direct work on Hostinger

- **Prod ArgoCD Applications** run with `selfHeal: true` and `prune: true`, so an out-of-band
  `kubectl` change reverts. The AppProject for prod denies sources other than `deploy/prod`.
- **Agents and Claude** get a **read-only** kubeconfig for prod (a namespace-scoped `view` Role, not
  `cluster-admin`). The operator keeps a separate **break-glass** kubeconfig.
  - Its use is logged and alerts the status Slack channel.
  - Any break-glass change must be followed by a git change promoted normally, or self-heal reverts it.
- **Debugging happens on staging.** The how-to says so, and the hub's existing Hostinger helpers are
  re-pointed at staging where they mutate.

### CVE promoter

The auto-patch promoter pins its fix into **staging's** lock and opens the normal promotion.

- **Critical fast lane:** if a Critical CVE has an exploit-known flag, the soak gate shortens to
  10 minutes. The e2e gate stays.
- Prod never receives an image that did not run on staging.

## What NOT to Do

- Do not change anything Hostinger runs in phase 1.
- Do not relabel or remove `role: app-cluster`, and do not deregister clusters.
- Do not give agents write access to prod, and do not let agents run `make promote`.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
