## Problem

Production is Hostinger: the `ubuntu-hostinger` app cluster serving `frontend.3ai-talk.org`. It
receives changes with no step in between.

| Change | How it reaches Hostinger today |
|---|---|
| App code | `services/<svc>/kustomization.yaml` pulls `k8s/base?ref=main` from each app repo. A merge to an app repo's `main` reaches every app cluster, Hostinger included, on the next ArgoCD sync |
| Platform config | ApplicationSets use matrix generators: (git source) × (every `role: app-cluster`). A release-branch commit reaches Hostinger as soon as the sets are reapplied |
| CVE fixes | The auto-patch promoter pins a clean image by digest, and ArgoCD deploys it everywhere |
| Fixes by hand | Debugging happens on Hostinger directly (SSH, `kubectl` against prod) |

The ACG sandbox and per-PR vClusters test changes, but nothing requires a change to pass them before
it reaches production.

## Design

### Environments

| Env | Cluster | Lifetime | Gets |
|---|---|---|---|
| **dev** | Per-PR vCluster (Tier 1), plus an optional local app cluster on the M4 | ephemeral | any branch, any time |
| **staging** | A **persistent** app cluster built like Hostinger: k3s (not k3d), the same k3s version, Istio ambient with the k3s CNI paths, Cloudflare tunnel ingress to a `staging.` hostname | persistent, rebuildable | what is proposed for production |
| **prod** | Hostinger | persistent | only what staging verified, through `make promote` |

The ACG sandbox stays the cloud e2e (Tier 2) and can be registered as `dev` or `staging` per run.

Each cluster's ArgoCD registration Secret gets `k3dm.k3d.io/env: dev|staging|prod`. The existing
`role: app-cluster` label stays as is, because four ApplicationSets select on it
(`reference_hub_app_cluster_registration_is_load_bearing_for_eso`).

### D1. Where staging runs — DECIDED 2026-10-25: k3s VM in OrbStack on the M5 hub (operator: "go as you suggested")

**Recommended:** a k3s Linux VM in OrbStack on the **M5 hub**, about 6–8 GB.
- Pros:
  - It is always where the hub is, so ArgoCD reaches it without the LAN or the other laptop.
  - It travels with the hub.
  - The M5 has room for it (32 GB, with a 12 GB hub reserve).
- Con: the hub and staging share the machine, so a staging load test competes with the hub.

**Alternative A:** the same VM on the M4. This keeps load off the hub, but staging becomes unreachable
whenever the M4 is away or asleep, so promotions would stall.

**Alternative B:** a second small VPS. This is the closest to production, but it costs money and is a
second public host.

### D2. Environment refs replace release-branch tracking — DECIDED 2026-10-25: per-environment git branches (operator: "let's do per-environment git branch")

Each environment reads a git ref of its own:

- **dev:** the working branch or PR head, as today.
- **staging:** branch `deploy/staging` in k3d-manager, fast-forwarded by `make promote TO=staging`
  (by default, to the current release branch tip).
- **prod:** branch `deploy/prod`, fast-forwarded **only** by `make promote TO=prod`, and only to a
  commit that `deploy/staging` already passed.

The ApplicationSets select the revision by the cluster's `env` label. This **supersedes** the
2026-07-24 decision (values follow the release branch, so every release needs
`make appsets-reapply`):

- Applying the sets once makes them stable.
- A release becomes "promote to staging, verify, promote to prod".
- The CLAUDE.md release rule is rewritten in phase 2, not before.
- Until phase 2 lands, prod keeps today's behaviour.

`deploy/staging` and `deploy/prod` are protected. Only the promote flow moves them: no direct push,
no force push, fast-forward only.

### How changes move: environment pointers, not git flow

Nobody merges into `deploy/staging` or `deploy/prod`. They are pointers that only `make promote`
moves. Day-to-day git does not change:

    feature work → k3d-manager-vX.Y.Z (release branch) → PR → squash-merge to main
                                 │                                  │
                  promote TO=staging REF=<branch>       promote TO=staging (default: main)
                    (optional pre-merge soak)                        │
                                                       gates pass → promote TO=prod

- **No develop branch, no back-merges, no merge commits on environment branches.** Fixes always go
  through `main`, so the environments cannot drift apart.
- **`deploy/prod` only fast-forwards, and only along `main`.** Each commit it gets is one that staging
  ran.
- **`deploy/staging` may run a release-branch tip before the merge** (`REF=<branch>`), so a release
  can soak on staging while its PR is under review. Because a squash merge creates a new commit, the
  tool moves `deploy/staging` without requiring a fast-forward. Every move is recorded in the ledger,
  and the history is never deleted (each move is a new commit on `deploy/staging` whose tree is the
  target's tree).
- **Tree equality is what lets a commit into prod.** The ledger records the tree hash staging ran.
  After the squash merge, the `main` commit's tree equals the release tip's tree, so
  `promote TO=prod` accepts that `main` commit without another soak. A `main` commit whose tree
  staging never ran is refused.
- **Hotfix:** fix branch → PR → `main` → staging (Critical fast-lane soak) → prod. It is the same path,
  only faster.
- **App repos** keep merging to their own `main`. Their commits and image digests reach staging and
  prod only through the lock (next section).

### Pinned app versions per environment

App repo bases at `ref=main` are replaced with a **promotion lock**, `deploy/<env>.lock.yaml`. For
each service it holds the app repo commit and the image **digest**, and it has a single
k3d-manager commit at the top.

- Kustomize overlays (`services/overlays/<env>/`) render the base at the locked ref and pin the
  image by digest.
- `make promote` copies staging's lock to prod unchanged. Production therefore runs byte-for-byte
  what staging ran.
- Dev keeps `ref=main` and floating tags, so app work stays fast.

### Gates before production

`make promote TO=prod` refuses unless every gate passes on the exact commit and lock being promoted:

1. Every staging Application is Synced and Healthy.
2. The e2e suite is green against staging: the existing e2e harness, pointed at the staging hostname.
3. The image gates pass:
   - cosign verify passes for every locked digest;
   - Trivy shows no **new** Critical compared with the current production lock.
4. Staging has **soaked** for at least `PROMOTE_SOAK_MIN` (default 30) with no firing staging alert.
5. **D3, operator approval — DECIDED 2026-10-25: both ways** (operator: "we can do both. it just
   convenient to have an alternative way to approve a promotion").
   - **(a) Terminal:** the operator runs `make promote TO=prod` themselves.
   - **(b) Slack:** `make promote TO=prod --request` posts the promotion plan to the status channel,
     with Approve and Deny buttons. It reuses the v1.33.0 Hermes Slack approval in
     `workers/slack-relay`: the approver allowlist, the `/hermes-auth` re-auth that lasts 24 hours,
     and the PULL model.
     - The hub-side promoter polls for the decision. Nothing on the hub listens for Slack.
     - An approval is **bound to the exact plan**: a hash over the target commit, its tree, the lock
       digest and the gate results.
     - It is **single-use** and **expires after 30 minutes**.
     - At execution the promoter **re-runs every gate**. If anything changed, the approval is void.
     - Only Slack user IDs on the allowlist can approve, and only after a current `/hermes-auth`.
     - The requester's identity is recorded. An agent may request, but its request still needs the
       operator's click.
   - Claude and the agents may run `make promote --plan` and `--request`. They never run the real
     promotion, and they cannot approve.

Every promotion is recorded as an append-only promotion ledger event (who, from, to, commits, lock
digest, gate results). Grafana shows what is running in each environment and how long the gap is.

### Rollback

`make promote-rollback ENV=prod` fast-forwards `deploy/prod` to a **new** commit that restores the
previous ledger entry's tree and lock. History is never rewritten. The rollback skips the soak gate
but still requires the cosign check.

### No direct work on Hostinger

- **Prod ArgoCD Applications** run with `selfHeal: true` and `prune: true`, so an out-of-band
  `kubectl` change reverts. The AppProject for prod denies sources other than `deploy/prod`.
- **Agents and Claude** get a **read-only** kubeconfig for prod (a namespace-scoped `view` Role, not
  `cluster-admin`). The operator keeps a separate **break-glass** kubeconfig.
  - Its use is logged and alerts the status Slack channel.
  - Any break-glass change must be followed by a git change promoted normally, or self-heal reverts it.
- **Debugging happens on staging.** The how-to says so, and the hub's existing Hostinger helpers are
  re-pointed at staging where they mutate.

### CVE promoter

The auto-patch promoter pins its fix into **staging's** lock and opens the normal promotion.

- **Critical fast lane:** if a Critical CVE has an exploit-known flag, the soak gate shortens to
  10 minutes. The e2e gate stays.
- Prod never receives an image that did not run on staging.

## What NOT to Do

- Do not change anything Hostinger runs in phase 1.
- Do not relabel or remove `role: app-cluster`, and do not deregister clusters.
- Do not give agents write access to prod, and do not let agents run `make promote`.
- Do not create a PR, commit to `main`, or skip pre-commit hooks.
