## Behaviour

### 1. Runner and report (`scripts/lib/acceptance/runner.py`, `bin/k3dm-operator-acceptance`)

- A scenario is a Python object with: `id` (`^[a-z0-9][a-z0-9-]{2,63}$`), `fixture_revision`, `requires`
  (capabilities, for example `promtool`), `deadline_s`, and a `run(ctx)` returning a list of assertion results.
- Each scenario result has `outcome` ∈ {`passed`, `failed`, `skipped`, `inconclusive`, `known_failing`} and `cause` ∈
  {`product_contract`, `environment_dependency`, `harness_error`, `unknown`}; a `known_failing` result carries the
  linked bug path. A missing required capability gives `inconclusive` / `environment_dependency`; an exception inside
  the harness gives `inconclusive` / `harness_error`; neither is ever `passed`.
- The run passes only when every scenario is `passed` or `known_failing`, at least one assertion ran, and the number
  of scenarios collected equals the number registered. Zero scenarios or zero assertions is a failure.
- Output under a run directory `$K3DM_ACCEPTANCE_RUN_ROOT/<UTC timestamp>-<8 hex>/` (default root
  `$HOME/.local/state/k3d-manager/acceptance`), created `0700`, files `0600`: `report.json` (schema version 1:
  `schema`, `source_sha`, `started`, `finished`, `scenarios[]` with id, outcome, cause, assertions[], linked_bug),
  `junit.xml`, `report.md`.
- Retention: on each run, delete run directories older than `K3DM_ACCEPTANCE_RETENTION_DAYS` (default 14) and then the
  oldest until the root is under `K3DM_ACCEPTANCE_MAX_MB` (default 500). Only directories matching the run-name pattern
  directly under the root are ever deleted.
- Redaction: every string written to the run directory passes `webhook.redact.scrub_credentials` plus two added
  patterns local to the harness: `https://hooks\.slack\.com/\S+` and `xox[abpors]-[A-Za-z0-9-]+`.
- `bin/k3dm-operator-acceptance [--scenario ID]... [--run-root PATH]` runs the registered offline scenarios; exit 0 on
  pass, 1 on any `failed` or `inconclusive`, 2 on usage error. No shell strings anywhere: every subprocess is a fixed
  argv list with `shell=False`.

### 2. Isolation guard (`scripts/lib/acceptance/guard.py`)

Applied by the runner before any scenario:

- Builds the child environment from an allowlist only (`PATH`, `HOME`, `LANG`, `TMPDIR`, plus variables a scenario sets
  explicitly). `CONFIRM`, `CLUSTER_PROVIDER`, `ACG_KUBE_CONTEXT`, `SLACK_*`, `K3DM_SLACK_*`, `VAULT_*`, `GITHUB_*`,
  `K3DM_PUSHGATEWAY_URL` from the parent are never passed through.
- `HOME` is a scratch directory under the run directory; the guard asserts it is not the real home before use.
- `PATH` starts with a stub directory holding `launchctl`, `kubectl`, `security`, `docker`, `git` and `curl` stubs that
  append their argv to `stub.log` and exit 0 (`git` exits 1 on `push`).
- A URL the harness hands to any child must be `http://127.0.0.1:<port>` with a port the harness bound itself; the
  guard refuses (cause `harness_error`, run fails) any URL whose port is 9091, 19094 or 7443, or whose host is not
  loopback.
- `subprocess` calls in the harness go through one helper that applies the environment above; the pytest wrapper also
  runs under `scripts/tests/tripwire.sh` via `make test-pytest`.

### 3. Fake Pushgateway (`scripts/lib/acceptance/fake_pushgateway.py`)

In-process HTTP server on `127.0.0.1`, port 0. Implements `GET /-/healthy`, and `PUT`/`POST`/`DELETE` on
`/metrics/job/<job>/instance/<instance>`: `PUT` replaces the whole group, as the real Pushgateway does. Records every
request. Can be told to fail health or PUT (for the publication-failure scenario).

### 4. Scenarios (`scripts/lib/acceptance/scenarios/`)

| Id | What it drives | Oracle (expected) |
|---|---|---|
| `metrics-totals` | real `bin/k3dm-test-metrics` (subprocess, `K3DM_PUSHGATEWAY_URL` = the fake) on a fixture log | pushed `k3dm_test_cases_total` / `k3dm_test_cases_failed` equal the fixture's declared totals |
| `metrics-pass-fail-fail-pass` | four exporter runs with fixture logs and `--exit-code`; between runs the fake's stored groups are turned into series at t0..t3 | last-run advances four times; last-success stays at t0 through both failures and moves to t3; `k3dm_test_failure` absent at t3 (regression oracle for the 2026-10-07 last-success and history bugs) |
| `metrics-publication-failure` | exporter against the fake with PUT failing | stdout contains `metrics push skipped`; the exit code is 0 today → `known_failing`, linked to `docs/bugs/2026-11-26-test-metrics-exporter-exits-zero-when-push-fails.md` |
| `panels-promql` (requires `promtool`) | every `expr` in `scripts/etc/grafana/dashboards/k3dm-tests-configmap.yaml` (panels 1-9; `$__range` replaced by `6h`), evaluated with `promtool test rules` over the series from `metrics-pass-fail-fail-pass` | panel 3 shows the latest failed count; panel 4 table rows only for the latest run; panel 8 (`max_over_time(k3dm_test_failure[...])`) still lists the t1/t2 failures at t3; panel 9 classification matches `run_classification`; per-panel empty state with no series is "no data" except panel 9's `noValue` |
| `panels-multi-target` (requires `promtool`) | series for a fresh `test` success and a stale `test-all` | panels 1-2 report the fresh `test` time today (max across targets) → `known_failing`, linked to `docs/bugs/2026-11-26-k3dm-tests-summary-panels-max-across-targets-hide-stale-test-all.md` |
| `job-output` | `webhook.job_output.read_job_output` on scratch job directories, and the `/api/v1/status` payload built by loading `bin/k3dm-webhook` as in `test_webhook_stale_cleanup.py` with `JOB_DIR` set to the scratch directory | a job with `exit_code` 7 reports `exit_code` 7, `status` failed, `result_classification` `failed_untriaged`; the bounded output keeps the failing case and the final tail; a planted canary secret is absent |
| `cleanup-preview` | real `bin/cleanup-stale-sandbox` with the stub `PATH`, scratch `HOME`, `CLUSTER_PROVIDER=k3s-aws` set explicitly, no argument | `stub.log` has no `bootout` and no `delete-context`; no file under the scratch `HOME` removed |
| `cleanup-ambient-confirm` | same, with `CONFIRM=1` passed deliberately | `stub.log` shows `bootout` → `known_failing`, linked to `docs/bugs/2026-11-26-stale-sandbox-cleanup-inherits-ambient-confirm.md` (this is also the guard's positive control: without the allowlist the hazard is real) |
| `cleanup-vocabulary` | the webhook thread parser (`cleanup-stale-sandbox apply`) loaded as above with `_notify_job` captured | reply says `apply` is not accepted, while `workers/slack-relay/index.js` accepts it → `known_failing`, linked to `docs/bugs/2026-11-26-cleanup-stale-sandbox-apply-accepted-by-slash-command-refused-in-thread.md` |

"Restart" in the pass/fail sequence means an exporter re-run. A Pushgateway restart is out of scope (the hub
Pushgateway has no persistence; parent § Adjudication F-M4).

The exporter's timestamps are fixed by calling `build_payload` / `build_success_marker` with an explicit `now` where a
scenario needs exact times (no new CLI flag); `metrics-totals` and `metrics-publication-failure` run the real CLI.

### 5. Entry points

- `scripts/tests/bin/test_operator_acceptance.py`: runs every scenario through the runner into `tmp_path`, asserts the
  report, and skips (with reason "promtool not found") only the scenarios that report `inconclusive` because promtool
  is absent. Budget: 30 s wall time on the M4. Collected by `make test-pytest`, so it runs in `test-all` and CI.
- `make test-operator-acceptance`: runs `bin/k3dm-operator-acceptance` under `scripts/tests/tripwire.sh` and prints the
  run directory.

## What NOT to Do

- Do not edit the exporter, dashboard, alert rules, webhook, bridge, relay or cleanup script, even where a scenario is
  `known_failing`. Do not weaken an oracle to turn a `known_failing` green; never report `known_failing` as `passed`.
- No containers, no Playwright, no network beyond the harness's own `127.0.0.1` port-0 listener.
- No shell strings (`shell=True`, `bash -c` with built strings, `os.system`).
- Do not delete anything outside the acceptance run root.
