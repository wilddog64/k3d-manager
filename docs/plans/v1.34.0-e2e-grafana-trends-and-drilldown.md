# Plan: E2E Grafana trends and failure drill-down

## Goal

Make E2E failures actionable from Grafana by showing trends, owning services,
root-cause categories, and individual failing tests without exposing scrape
metadata or requiring an operator to inspect local M2 files.

## Current state

The E2E dashboard already exposes run status, grouped failures, and test-level
details. The result pipeline emits `e2e_failure_group_info` and
`e2e_failure_info`, while the run record retains the consolidated execution
scope (`api+flows`). Failure records now identify `basket`, `order`, `payment`,
`product-catalog`, or `cross-service` ownership.

## Scope

The Recent runs table labels distinguish the E2E runner source revision (`Runner commit`) from the application image being exercised (`Application image digest`) and the test grouping (`Test suite`).

### How to read a Recent runs row

The identifiers describe different parts of the test execution; they are not
alternative names for one application commit:

| Dashboard field | Meaning | Example interpretation |
| --- | --- | --- |
| `Runner commit` | The `k3d-manager` revision that dispatched and recorded the E2E run. | Changing this means the test harness or exporter changed. |
| `Application image digest` | The immutable image digest deployed for the application under test. | Changing this means the tested app build changed. |
| `Service under test` | The owning shopping-cart service associated with the run or failure. | `product-catalog` identifies the app, not the runner repository. |
| `Test suite` | The logical E2E project/scope. | `api+flows` means the API/flow suite; it is not a service name. |
| `Run ID` | The unique execution identifier emitted by the runner. | Use it to correlate run, group, and detail rows. |

For M2, the runner checks out the selected `Runner commit` before executing the
suite. Tier 1 currently exercises API/flow behavior without browser OAuth2;
Tier 2 will add the browser/SSO coverage. The dashboard therefore lets an
operator answer both “which harness ran?” and “which application build failed?”
without inferring either from a generic `Commit` or `Project` label.

Prometheus adds its scrape-target `service` label to exporter metrics. Grafana
must therefore use `exported_service` for failure charts and legends; otherwise
the legend incorrectly reads `vulnerability-inventory-exporter` instead of the
owning application (for example `basket` or `payment`).

Update `scripts/etc/argocd/platform-ops/grafana-dashboard-e2e.yaml` with:

1. **Failure trend:** time series of failed tests by owning `service`.
2. **Failure cause distribution:** stacked bar/time series grouped by
   `service` and `kind` (`contract-drift`, `assertion`, `timeout`,
   `service-unreachable`).
3. **Failure rate:** failed tests divided by total tests per run.
4. **Top failing specs:** table or bar chart grouped by `service`, `file`, and
   failure count.
5. **Existing tables:** retain grouped and test-level tables, hiding scrape
   labels (`container`, `endpoint`, `namespace`, `pod`) and execution metadata
   (`project`) from the failure views.

## Metrics and queries

Use bounded labels only:

```promql
sum by (service) (e2e_failure_group_info)
sum by (service, kind) (e2e_failure_group_info)
sum by (service, file) (e2e_failure_info)
```

Failure text remains in the detail table. Do not chart raw `error` or `title`
labels in time-series panels; they create unnecessary Prometheus cardinality.

For failure rate, add a run-level numeric metric if the existing label-only
`e2e_run_info` cannot be safely used:

```text
e2e_run_failed_tests{run_id,service,runner,tier}
e2e_run_total_tests{run_id,service,runner,tier}
```

The metric must preserve zero-valued successful runs so the rate does not look
like missing data.

## Data and ownership rules

- `service` means the owning application or cross-service test category.
- `runner` distinguishes M2 from future GitHub Actions results.
- `tier` distinguishes Tier 1 API/flow tests from future Tier 2 OAuth2/browser
  tests.
- `project=api+flows` remains available in Recent runs but is hidden from
  failure tables.
- Prometheus scrape labels must be excluded from all user-facing failure panels.

## Acceptance criteria

- A failed run produces visible service-level trend points for every owning
  service represented by the run.
- Cause distribution distinguishes contract drift, assertion, timeout, and
  unreachable-service failures.
- Top failing specs identify the owning service and spec file.
- Failure details remain available as a table with redacted errors.
- Successful runs contribute zero failed tests rather than disappearing.
- Grafana panels render with no `container`, `endpoint`, `namespace`, `pod`, or
  `project` columns in failure views.
- Existing E2E exporter, BATS, shellcheck, and `_agent_audit` gates remain green.

## Out of scope

- Enabling OAuth2 or implementing Tier 2 browser SSO tests.
- Automatic code repair by Hermes.
- Publishing raw Playwright traces or unredacted response bodies.
- Replacing Prometheus with Loki/object storage; that can be a later detail
  retention improvement if label cardinality becomes a problem.
