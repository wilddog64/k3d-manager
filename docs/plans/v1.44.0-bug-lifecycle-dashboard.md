## Goal

Show how many repository bugs are open and fixed, what changed over time, and which reports
need attention. Provide links to the evidence so one maintainer can follow progress without
manually counting Markdown files.

Companion: [operator acceptance automation](v1.44.0-operator-acceptance-automation.md).
The harness may draft/file findings; this dashboard measures canonical repository bug records,
not test failures, issue notes, GitHub issues, or vector search similarity.

## Source of truth and normalization

Scan tracked Markdown under `docs/bugs/` at a configured branch/commit. Record the fetched SHA
and scan completion timestamp. Read docs from fetched git objects; do not require changing the
operator's worktree or silently default to a different branch. Never use an LLM to decide status.

Define a deterministic parser for the existing status formats (bold Status fields, status headings,
and documented fixed-on-branch prose). Support an explicit normalized metadata schema for future
reports: stable bug ID, status, filed date, component, severity, release and resolved date.
Audit actual repository formats before implementation and add representative fixtures.

Canonical states: open, in_progress, fixed, deferred, wont_fix, unknown. Missing, ambiguous or
contradictory status becomes unknown with a validation finding; never silently infer fixed from
a commit, file name, index success, or prose mentioning a proposed fix.
Fixed means the bug record claims a fix; live verification is a separate optional field.
Dates not explicitly recorded remain unknown. Renames preserve identity via stable ID or tracked
rename mapping. Cross-linked reports are not automatically duplicates. Duplicate/superseded records
need an explicit canonical ID; count the canonical bug once and expose excluded duplicate totals.

Exclude archived reports from default active counts; expose archive scope separately. Do not count
docs/issues evidence notes as bugs. Define whether legacy fixed records outside archive count in
the default inventory, and label the scope visibly. Initial default: all canonical non-archived
bug records, including legacy fixed records.

## Export and dashboard

Export bounded aggregate gauges, using a consistent `k3dm_bug_` prefix:

- current canonical count by status;
- counts by controlled component, severity and release buckets;
- unknown/invalid metadata and explicit duplicate/archive totals;
- last successful scan timestamp and scan success state.

Metric names and bucket allowlists finalized during implementation. No bug ID, path, title,
commit SHA, timestamp or user identity as a Prometheus label. Preserve last successful inventory
on fetch/parse/export failure while marking it stale/failed; do not emit false zero counts.
Publish the complete successful snapshot atomically and remove obsolete series.

Dashboard panels: Open bugs, In progress, Fixed bugs, Unknown status, scan freshness and
current counts by component/severity/release. Use zero for a successfully scanned empty set;
distinguish it from no data, stale inventory and unavailable datasource.

Inventory tables need a declared Grafana-compatible structured data source (for example a bounded
read-only JSON endpoint with a pinned datasource plugin). Select the integration and document its
deployment requirements during implementation; Prometheus aggregate gauges cannot supply titles
and links. Rows show title, state, severity, component, release, known dates, verification state,
and a GitHub link pinned to the scanned revision. Keep the structured snapshot free of secrets.

## History semantics

Daily count trends show inventory snapshots, not the number of transitions. A reduction in open
count does not prove a fix: a report can be archived, duplicated, removed, deferred or reopened.
Label charts accordingly.

For opened/fixed/reopened activity, maintain an idempotent transition ledger derived from git
history or successive durable snapshots. Bootstrap current inventory without inventing historical
events. Expose known coverage start and completeness. Count a fixed transition only on entry to
fixed; reopen separately. Git observation time is not an authoritative resolution date.
Same commit rescans and file renames must not create duplicate activity.

## Operation and acceptance

Use an existing repository indexing/fetch checkpoint if reliable, or a bounded scheduled scanner;
VectorDB is optional and never the counting authority. Default scan interval five minutes,
configurable. Read-only repository access; no bug status edits, auto-closing, fixes or Slack posts.
Document retention/storage for the ledger and structured snapshot.

Required tests use a fixture repository containing status variants, unknown/contradictory fields,
fixed/unverified bugs, duplicates, archives, evidence notes, rename, reopen, removal and failed fetch.
Assert exact inventory totals, transition deduplication, preserved last-good snapshot, visible
staleness and honest history coverage. Test Prometheus series replacement and actual Grafana
rendering/links with the acceptance harness; no screenshot-only or vacuous checks.

Implementation delivers parser/exporter, durable snapshot/ledger, datasource contract, dashboard
provisioning, operational docs and focused regression tests. Verify one authorized live scan
against a manual canonical count before release. This specification creates no dashboard yet.
