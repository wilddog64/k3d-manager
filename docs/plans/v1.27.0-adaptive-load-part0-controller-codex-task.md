## Deliverables (exactly these — nothing outside them)

### 1. `scripts/plugins/loadtest.sh`

Header `#!/usr/bin/env bash` + `set -euo pipefail`. Public functions no underscore; private
`_loadtest_` prefix. Use `_info`/`_warn`/`_err` for logging. **This slice contains ONLY the
decision core, the stage ladder, the JSON summary writer, and an opt-in guard** — NO live calls.

Configurable via env (with these defaults):
- `LOADTEST_STAGES="100 250 500 1000 2500 5000"` — the ramp ladder (space-separated). 5000 is the
  hard cap for this release; never step beyond the last stage.
- `LOADTEST_MAX_ERROR_RATE="2"` — percent; breach when checkout error rate **>** 2.
- `LOADTEST_MAX_P95_SECONDS="2"` — breach when p95 latency **>** 2s.
- `LOADTEST_MAX_CPU_PCT="80"` — breach when CPU **>** 80%.
- `LOADTEST_BREACH_INTERVALS="2"` — a hard threshold must persist this many **consecutive**
  observation intervals before STOP (hysteresis, per parent "persists for two observation intervals").

**Functions:**

- `_loadtest_evaluate_gates` — inputs are metric values passed as named args or env (choose one
  style and keep it consistent; document it). Given a snapshot (error_rate, p95_seconds, cpu_pct,
  and boolean flags: `stripe_rate_limited`, `db_pool_exhausted`, `control_plane_error`,
  `node_eviction_risk`, `memory_pressure`), echo a newline/space-separated list of the breached
  threshold names (empty output = all green). Return 0 always; the caller inspects the list.
- `_loadtest_decide` — the core state machine. Inputs: current stage index, the breach list from
  `_loadtest_evaluate_gates`, and a running `consecutive_breach_count`. Output one decision token on
  stdout — exactly one of: `increase`, `hold`, `stop` — with these rules:
  - all gates green → `increase` (move to next stage; if already at the last stage, `hold`).
  - one or more gates breached but `consecutive_breach_count + 1 < LOADTEST_BREACH_INTERVALS` →
    `hold` (this is the first breach interval; do not stop yet — hysteresis).
  - gates breached and `consecutive_breach_count + 1 >= LOADTEST_BREACH_INTERVALS` → `stop`.
  Also echo the updated consecutive-breach count (reset to 0 when green) on a second line or via a
  documented global — pick one and test it.
- `_loadtest_next_stage` — given a current stage index, echo the next concurrency value from
  `LOADTEST_STAGES`, or the same (last) value when already at the ceiling. Never exceed the ladder.
- `_loadtest_write_stage_summary` — write ONE immutable JSON object for a stage to a caller-supplied
  path (fail, do not overwrite, if the file already exists — "immutable per stage"). Fields:
  `run_id`, `stage`, `target_concurrency`, `actual_throughput`, `decision`, `breaches` (array).
  Build JSON safely (`jq -n` with `--arg`/`--argjson`, never string interpolation of untrusted data).
- `loadtest_run` (public) — the opt-in entry. It MUST refuse to do anything unless an explicit
  confirmation is given (`--confirm` flag OR `LOADTEST_CONFIRM=1`); without it, print a clear
  refusal to stderr and `return 1` (parent safety: "impossible to trigger from an unauthenticated
  Slack command"). In THIS slice, after the guard passes, `loadtest_run` only needs to validate
  inputs, initialize a run id, and log that the live generator/poller is not yet wired (Slice F).
  Do NOT call k6, kubectl, curl, Prometheus, or Stripe. Leave a clearly-named seam
  (e.g. a `_loadtest_fetch_metrics` stub that Slice F overrides) so the live slice can plug in.
- `loadtest_status` (public, optional but preferred) — print the configured ladder + thresholds so
  an operator can see what a run would enforce, without running anything.

If `loadtest_run` adds any flag carrying secrets (it should NOT need to — Stripe keys come from
Vault/ESO in Slice F), register it in `_args_have_sensitive_flag` in `scripts/lib/system.sh`.

### 2. `scripts/tests/plugins/loadtest.bats` — unit tests (deterministic)

Assert, at minimum:
- **increase when green** — empty breach list → `_loadtest_decide` yields `increase` and resets the
  consecutive count to 0.
- **hold on first breach (hysteresis)** — a breach with `consecutive_breach_count=0` and
  `LOADTEST_BREACH_INTERVALS=2` → `hold`, count becomes 1 (NOT `stop`).
- **stop on second consecutive breach** — same breach with `consecutive_breach_count=1` → `stop`.
- **each stop condition trips `_loadtest_evaluate_gates`** — error_rate `2.5` (>2), p95 `2.1` (>2),
  cpu `81` (>80), and each boolean flag (`stripe_rate_limited`, `db_pool_exhausted`,
  `control_plane_error`, `node_eviction_risk`, `memory_pressure`) each individually appears in the
  breach list; a fully-green snapshot yields an empty list.
- **boundary is strict `>`** — error_rate exactly `2`, p95 exactly `2`, cpu exactly `80` are NOT
  breaches (green).
- **stage ladder** — `_loadtest_next_stage` walks 100→250→500→1000→2500→5000 and **caps** at 5000
  (never returns a 7th value).
- **confirmation gate** — `loadtest_run` with neither `--confirm` nor `LOADTEST_CONFIRM=1` returns
  non-zero and prints a refusal; with the flag it returns 0 (and makes no live call).
- **immutable summary** — `_loadtest_write_stage_summary` writes valid JSON with the required fields
  (parse with `jq -e`), and a second write to the same path fails rather than overwriting.

Mock any external command the plugin might reference (`jq` is real and allowed; do NOT mock it).
No real kubectl/curl/k6/Stripe calls anywhere.
