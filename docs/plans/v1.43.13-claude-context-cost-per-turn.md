## Problem

Over 30 days (Agent Cost dashboard, window `30d`, 2026-10-30), Claude cost $960 at API prices:

| Kind | Cost | Share |
|---|---|---|
| Cache reads | $435.62 | 45% |
| Cache writes | $321.39 | 33% |
| Output | $203.21 | 21% |
| Input | $0.14 | 0% |

So 78% of the cost is re-reading and rebuilding context, not producing work. The dashboard shows totals, but
not the two things that decide them: how big the context is on each turn, and how often the whole cache is
rebuilt.

## Findings (Claude, 2026-10-30, from the M4's session logs)

The figures were measured offline from `~/.claude/projects/-Users-cliang-src-gitrepo-personal-k3d-manager/**/*.jsonl`.
The context size is the sum of `input_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`
for each unique assistant `message.id`.

| Period | Agent | Turns | Mean | p50 | p90 | Max |
|---|---|---|---|---|---|---|
| 10-18..10-21 (200K setting) | main | 1,554 | 130,716 | 130,993 | 159,650 | 167,355 |
| 10-22..10-30 (400K setting) | main | 7,290 | 130,062 | 130,301 | 159,760 | 168,120 |
| 10-22..10-30 | subagent | 72 | 87,983 | 90,128 | 126,143 | 135,623 |
| before 10-18 | main | 7,874 | 137,733 | 126,165 | 203,184 | 388,911 |

1. **The 400K trial was inert.** In both periods the main session's context never went above about 168K tokens,
   and the distribution is the same. The live hub agrees: 90 auto compactions in 7 days, averaging 168K
   tokens before compacting (`k3dm_claude_compaction_pre_tokens_sum / k3dm_claude_compactions`). Setting
   `autoCompactWindow: 400000` in `.claude/settings.json` did not move the point where compaction happens.
   The dashboard's "Auto-compact threshold 400K" stat reports the settings table, not what actually happens.
   So the v1.43.6 experiment compared two identical periods.
2. **The floor is most of the context.** Right after a compaction, a main turn already carries about 95–100K
   tokens (p5 95,199, p10 100,311 in the 400K period): the system prompt, tool definitions, both CLAUDE.md
   files, MEMORY.md (209 lines, 25.8KB, already over its own load limit) and the compaction summary. Working
   context only spans about 95K to 168K. Lowering the floor reduces the cost of every turn. Moving the ceiling
   does little.
3. **Whole-cache rebuilds are a large share of the write cost.** In the 400K period, 126 main turns each wrote
   more than 50K tokens of cache, about $0.80 each at the 1h write rate. These happen after a compaction and
   after an idle gap longer than the 1-hour cache TTL.

## Fix

### C1 — Exporter metrics (`bin/k3dm-dispatch-metrics`)

Extend the existing Claude record scan. Records already carry `cache_5m`, `cache_1h`, `cache_read` and
`input`. Add a boolean `subagent` (true when the file path contains `/subagents/`) and the session file key.
Context size is `input + cache_read + cache_5m + cache_1h`.

- `k3dm_claude_context_tokens{window,agent,quantile}`: `agent` is `main` or `subagent`; `quantile` is `0.5`
  or `0.9`. Nearest-rank on the sorted per-turn context sizes for turns in the window. A window with no turns
  emits nothing for that agent.
- `k3dm_claude_context_tokens_sum{window,agent}` and `k3dm_claude_context_turns{window,agent}`.
- `k3dm_claude_turns_per_active_day{window,agent}`: `context_turns` divided by the number of distinct UTC
  dates in the window that have at least one turn for that agent. It is emitted only when that number is
  above 0. Active days, not calendar days, so idle days do not dilute it.
- `k3dm_claude_context_floor_tokens{window}`: the median context size of the **first main turn after each
  `compact_boundary`** in the window. The v1.43.6 scan already finds the boundaries.
- `k3dm_claude_context_ceiling_tokens{window}`: the largest main-turn context in the window, so the dashboard
  can show it next to `k3dm_claude_auto_compact_tokens`.
- `k3dm_claude_cache_rebuilds{window,cause}`: main turns whose `cache_5m + cache_1h` is more than 50,000.
  - `cause="compaction"` when the turn is the first turn after a `compact_boundary` in the same session file;
  - `cause="idle"` when more than 3,600 s passed since the previous turn in the same session file;
  - `cause="other"` otherwise.
- `k3dm_claude_cache_rebuild_cost_usd{window,cause}`: the write cost of those turns at the existing
  `claude_models` rates in `scripts/etc/agent/codex-model-prices.json`. It is 0 for an unpriced model.

Release windows use the same rule as the existing release-window Claude series, if there is one. Otherwise,
emit only the time windows and say so in the guide.

### C2 — Dashboard (`scripts/etc/argocd/platform-ops/grafana-dashboard-agent-cost.yaml`)

Add a row "Claude context per turn" with five panels:
1. Context per turn: p50 and p90 for main and subagent (bar gauge).
2. Post-compaction floor next to the observed ceiling and the configured threshold. One stat panel with three
   values; the configured value is labelled "configured" and the ceiling "observed".
3. Cache rebuilds by cause: count and cost.
4. Mean context per turn: `sum / turns`.
5. Turns: `k3dm_claude_turns_per_active_day` for main and subagent, plus turns per verified spec, which is
   main `k3dm_claude_context_turns` divided by `sum(k3dm_claude_verified_specs{level=~"live|verified"})`. With no
   verified spec in the window, the expression must show no value, not `+Inf`; guard it with `> 0` on the
   denominator. The point of this panel: daily tokens are roughly turns × context, so turn count is a
   separate lever from context size (Opus 5.5 all-time: 3.4B cache read against 18.9M output, about 180 tokens
   re-read per token written).

Every panel description says which window variable it follows, as the existing panels do.
