# Multi-App-Cluster — Phase 3: data-git name-collision fix

**Branch:** `k3d-manager-v1.16.0`
**Depends on:** Phase 1 (additive labeling — DONE, `2fa78e35`, live-verified 2026-07-18)
**Files (Codex scope):** `scripts/etc/argocd/applicationsets/data-git.yaml` (one line)

> This is the **third** implementable slice of `docs/plans/v1.16.0-multi-app-cluster.md`.
> Phase 1 made app-cluster labeling additive. Phase 3 removes the one remaining hard
> blocker to labeling **two** clusters at once: the `data-git` ApplicationSet renders a
> hardcoded Application name, so two matched clusters collide on the name `data-layer`.

---

## Problem (empirically confirmed live, 2026-07-18)

With both `cluster-ubuntu-hostinger` and `cluster-ubuntu-k3s` carrying
`k3d-manager/role=app-cluster`, the `data-git` ApplicationSet matched two clusters and
tried to render **two** Applications both named `data-layer`:

```
kubectl get applicationset data-git -n cicd -o jsonpath='{.status.conditions[*]}'
→ ErrorOccurred=True   ApplicationSet data-git contains applications with duplicate name: data-layer
→ ResourcesUpToDate=False
```

It was **non-destructive** (every syncPolicy is `prune: false`, so the existing
`data-layer` app stayed `Synced/Healthy` on `ubuntu-hostinger` and the error auto-cleared
when the second label was removed) — but it blocks a **permanent** two-cluster topology.

**Root cause:** `scripts/etc/argocd/applicationsets/data-git.yaml` line 20 hardcodes
`metadata.name: data-layer`. The cluster generator fans out per matched cluster, but the
Application name is constant → duplicate name whenever more than one cluster matches.

Contrast `eso.yaml`, which is already collision-free because it templates the name as
`'{{.name}}-eso'`. Phase 3 applies the same pattern to `data-git`.

---

## Fix

### Change 1 — `scripts/etc/argocd/applicationsets/data-git.yaml`: per-cluster Application name

**Exact old block (line 20):**

```yaml
      name: data-layer
```

**Exact new block:**

```yaml
      name: '{{.name}}-data-layer'
```

Nothing else in the file changes. In particular **do NOT** touch:
- `path: data-layer` (line 32) — the source path in the shopping-cart-infra repo is unchanged.
- `app-type: data` labels — unrelated.
- the selector `k3d-manager/role: app-cluster` — Phase 1 already made labeling additive; the
  selector stays as-is.

After the change, a matched cluster named `ubuntu-hostinger` yields Application
`ubuntu-hostinger-data-layer`; `ubuntu-k3s` yields `ubuntu-k3s-data-layer`. No collision.

`goTemplate: true` + `goTemplateOptions: [missingkey=error]` are already set (lines 15–17),
so `{{.name}}` resolves exactly as it does today for `destination.name` on line 27.

## Claude-only: live migration (NOT Codex — sequenced for when permanent 2-cluster is wanted)

Committing the rename is inert until the ApplicationSet is re-applied to the hub. When it is
re-applied, `data-git` will want to **delete** the current `data-layer` Application and create
`ubuntu-hostinger-data-layer`. The current `data-layer` app carries
`resources-finalizer.argocd.argoproj.io`, so a naive delete would **cascade-delete hostinger's
live postgres** (data loss). Claude performs this finalizer-safe rename, verified against a
live hub, only when a second cluster is actually going permanent:

1. Snapshot: `kubectl --context k3d-k3d-cluster get application data-layer -n cicd -o yaml`
   and record postgres pod ages in `shopping-cart-data` on `ubuntu-hostinger`.
2. Remove the finalizer from the live app so its deletion will NOT cascade to resources:
   `kubectl --context k3d-k3d-cluster patch application data-layer -n cicd --type merge -p '{"metadata":{"finalizers":null}}'`
3. Re-apply the renamed ApplicationSet to the hub (`make sync-apps` / argocd-registration).
   `data-git` deletes `data-layer` (object only, no cascade) and creates
   `ubuntu-hostinger-data-layer`, which `selfHeal`-syncs and **adopts** the existing postgres
   resources via server-side apply (identical manifests → no StatefulSet recreation).
4. Verify: `ubuntu-hostinger-data-layer` `Synced/Healthy`; postgres pods **same age** as the
   snapshot (never restarted); no `data-layer` app remains; `prune: false` held throughout.
