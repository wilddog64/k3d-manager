# v1.38.0 — A vector store as a platform component, and Hermes prior-art retrieval

**Target branch:** `k3d-manager-v1.38.0`
**Status:** QUEUED for v1.38.0. WS1 deploys to a live cluster and needs the operator's go.

Supersedes the CLI-first framing of `v1.38.0-semantic-doc-dedup.md` (renamed to this file).
Filing-time dedup is still delivered, but as a by-product of WS3 rather than the headline.

---

## Why this spec exists

### The agent-level defect (the real driver)

`scripts/lib/hermes/e2e_bugs.py:163`:

```python
matches = sorted(bug_dir.glob(f"*-{group['slug']}.md"))
```

Hermes decides **"is this a new bug or a recurrence of one I already filed?"** by globbing an exact
slug. The slug is derived from failure grouping, so a shift in error text produces a different slug,
and Hermes files a **fresh** bug doc for a defect it already has open — then keeps doing so on every
subsequent run. This is an unattended agent whose recall over its own memory is `strcmp`, writing
into a corpus that is already 495 files.

Everything downstream inherits the error: `status` transitions, reopen detection, and the
`ongoing` / `created` / `reopened` outcome reported to Slack.

### The context-budget cost

`MEMORY.md` indexes 165 memory files and is read in full every session. `CLAUDE.md` records the
constraint this collides with: thinking budget capped at 8,192 tokens, manual `/compact` required at
60% utilisation. A hand-maintained linear index *is* a retrieval system; it is just one that cannot
rank, and whose cost grows with the corpus rather than with the query.

### The filing-time gap

The `docs/bugs/` / `docs/issues/` dedup rule in `CLAUDE.md` is exact slug matching over 495 + 373
files. Two filings of one defect in different vocabulary do not collide.

### Why a deployed vector store rather than a flat file

On throughput alone a flat file wins: brute-force cosine over ~1,360 documents is microseconds, and
at this scale a vector database is not a performance requirement. Three other reasons carry it:

- **Hermes is a long-lived process** that would query on every alert, from a host outside the hub.
  A store with persistence and concurrent access is a better fit than a file each process reloads.
- **k3d-manager exists to know how to deploy platform components.** A vector store managed by
  ArgoCD, credentialed through ESO and Vault, on the cluster's own storage class, is the repo
  dogfooding its own purpose — the same path Vault, ESO and Istio already take.
- It is a real, inspectable artefact rather than a script-local index.

Deploy it because it is a platform component worth being able to deploy, not because 1,360 rows
need one. Say so honestly in the guide.

## WS1 — pgvector as a platform component

- Own namespace (never `default`), per the security rules. Suggest `vectordb`.
- Deploy through an ApplicationSet under `scripts/etc/argocd/applicationsets/`, following the `eso`
  pattern. **Pin the chart version explicitly** — no floating `latest`.
- Credentials via ESO from Vault. No password in the manifest, in argv, or in git; use
  `${PLACEHOLDER}` substitution only.
- Namespace-scoped Role + RoleBinding. **No `cluster-admin`, no new ClusterRole** without written
  justification.
- PVC on the cluster's `local-path` default. Note in the guide that `local-path` is
  `reclaimPolicy: Delete` — the index is a **rebuildable cache**, not a system of record, and the
  spec must not create the impression it is durable. Losing it costs one re-index.
- **Do not** put this behind the `k3d-manager/role: app-cluster` selector. It is hub platform
  infrastructure — use a hub-scoped Application like `hub-loki` / `hub-platform-ops`. See
  `docs/plans/v1.37.0-deregister-hub-app-cluster-shopping-cart.md` for why that distinction matters.

## WS2 — The indexer

- `scripts/index-docs.py`, stdlib only. `bin/k3dm-hermes` already uses `urllib.request`, so a hosted
  embeddings API over HTTP is the established idiom here — **no `torch`, no
  `sentence-transformers`, no `numpy`.** The repo has zero third-party Python runtime dependencies
  and runs Python 3.14.7, where those wheels are not assured.
- Corpus: `docs/bugs/`, `docs/issues/`, `docs/plans/`, `docs/retro/`, enumerated with `git ls-files`
  (tracked-only, matching `check-doc-links.py` — whose tracked-only behaviour has already surprised
  one session).
- Per document embed the `#` title, the leading prose paragraph and the `##` headings. Bodies are
  largely shell transcripts and add noise.
- Key each row by **content hash**; re-embed only changed documents. A full re-index must be cheap
  enough to be routine.
- API key from env or Keychain, **never argv**. Register any new sensitive flag in
  `_args_have_sensitive_flag` (`scripts/lib/system.sh`).
- Fail closed and legibly when no key is configured: the tool reports that retrieval is unavailable,
  and callers fall back to existing behaviour. It must never block or crash a Hermes run.

## WS3 — Retrieval library and CLI (the by-product)

- `scripts/lib/hermes/prior_art.py` — `search(text, k=5)` returning `(score, path, title)`, so both
  Hermes and the CLI share one implementation.
- `scripts/find-similar-docs.py` + `make find-similar-docs Q="..."`, mirroring `check-doc-links`
  conventions. Advisory, exit 0 always, default 5 results.
- Update the `Docs Conventions` dedup rule in `CLAUDE.md`: exact-slug glob stays as the first pass,
  similarity search second. A high score means **read that file before filing**, not *do not file*.

## WS4 — Hermes consumes it (strictly additive)

**Hermes' filing decision does not change in this release.** The exact-slug glob at
`e2e_bugs.py:163` stays authoritative for `created` / `reopened` / `ongoing`.

What is added: when Hermes files a **new** bug doc, `_doc()` gains a `## Possible prior art` section
listing the top 3 retrieved documents with scores, or nothing when retrieval is unavailable.

This ordering is deliberate and is not negotiable within this release. An unproven retriever that
can suppress a bug report converts a false positive into a **silently unfiled defect** — the failure
mode is invisible, which is the worst kind. Additive output is reviewable by a human on every run,
and it generates the precision evidence needed to decide whether gating is ever safe.

Letting retrieval influence the filing decision requires its own spec, its own version, and a
measured precision floor. Do not do it here.

## WS5 — Evaluation (gates WS4's future, and this release's claims)

- `scripts/tests/fixtures/doc-dedup/pairs.jsonl` — hand-mined duplicate/near-duplicate pairs from the
  existing corpus plus hard negatives (same component, genuinely different defect). Target ≥25
  positives and ≥25 hard negatives. Follow the schema style of
  `scripts/tests/fixtures/e2e-corpus/corpus.jsonl`, the existing precedent.
- Implement a **stdlib TF-IDF cosine scorer as the control** and measure both. If embeddings do not
  beat lexical on this corpus, that is a real finding and the deployed store earns its place on the
  platform-component argument alone — which is a legitimate outcome, but it must be *stated*, not
  quietly skipped.
- `scripts/tests/bin/test_find_similar_docs.py` — pytest, mirroring `test_check_doc_links.py`.
  Report **recall@5** for both scorers with a floor the suite enforces; break it out per directory,
  since `docs/bugs/` and `docs/issues/` dominate and plans/retros differ in register.
- Add the file to the `make test-pytest` target's path list.
- Mine the pairs **before** tuning either scorer, and never add a pair to fix a failing score.
- Record the measured numbers in the retro, not just in a passing test.

## What NOT to do

- Do **not** let retrieval gate, suppress or redirect Hermes' filing decision in this release.
- Do **not** add `torch`, `sentence-transformers`, `numpy`, or any third-party Python runtime
  dependency.
- Do **not** deploy the store via an app-cluster-selected ApplicationSet.
- Do **not** grant `cluster-admin` or add a ClusterRole without written justification.
- Do **not** float the chart version.
- Do **not** put the API key in argv, a manifest, or a commit.
- Do **not** index the out-of-repo `~/.claude/.../memory/` files here; mixing an out-of-tree path
  into a `git ls-files` corpus invites the tracked-vs-untracked confusion `check-doc-links` already
  produced. It gets its own task once the in-repo path is proven.
- Do **not** make the similarity check blocking, in the pre-commit hook or anywhere else.
- Do **not** tune either scorer before `pairs.jsonl` exists.
- Do **not** create a PR, merge, commit to `main`, force-push, or use `--no-verify`.

## Risks

- **Scope.** Five workstreams spanning a deployed service, an indexer, a library, an agent change and
  an eval harness is a large release. If it grows further, the split is clean: **WS1 alone** is a
  platform-component release, **WS2–WS5** the retrieval release. Take that split rather than
  breaching the 5-plan-doc cap or shipping a half-integrated store.
- **An unmeasured retriever looks like it works.** Plausible-looking top-5 results are the most
  likely way this ships broken. WS5 is the control, not paperwork.
- **Hand-mining pairs is the bulk of the effort.** Reading enough of 868 bug and issue docs to label
  25 genuine duplicates cannot be skipped without making the evaluation meaningless.
- **`local-path` is `reclaimPolicy: Delete`.** A rebuild loses the index. Acceptable only because it
  is a cache; the guide must say so, or a future session will treat it as durable.
- **Egress and cost.** Embedding ~1,360 documents is cents, but it is an outbound dependency in a
  repo that otherwise runs offline. Incremental indexing keeps steady-state calls near zero.
- **Corpus skew.** Bugs and issues dominate; plans and retros differ in register and may score worse.
  Report recall per directory.
