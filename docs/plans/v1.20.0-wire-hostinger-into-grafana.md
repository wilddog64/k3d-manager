# v1.20.0 — Wire hostinger observability into the hub Grafana

**Branch (k3d-manager):** `k3d-manager-v1.20.0` (new milestone — observability theme, distinct from
v1.19.0 Dependabot). Cut from `k3d-manager-v1.19.0` tip `e16e8bac` (docs stacked; v1.19.0 PRs to main
independently).
**Goal (this spec):** the hub Grafana can query **hostinger's** Prometheus and Loki as datasources,
so shopping-cart **pod health** (already scraped by hostinger kube-state-metrics) and **app logs**
(already collected by hostinger promtail) are visible from the laptop Grafana.
**Explicit non-goal (separate follow-up spec):** app-level metrics (HTTP/JVM/custom) — hostinger does
not scrape the apps yet (no ServiceMonitor, no named metrics port). Tracked separately in a future
`docs/plans/v1.20.x-shopping-cart-servicemonitors.md`.

**Decisions locked (2026-07-28):**
- Reachability = **cloudflared + Cloudflare Access** (not laptop port-forward).
- Scope = **datasources + Loki now**; app metrics = separate spec.
- Tunnel scope = **observability-only dedicated tunnel**. The frontend stays on `bb7ece59` for now;
  the full split-brain migration (`docs/bugs/2026-07-26-hostinger-cloudflared-stray-connector-split-brain.md`)
  is a **separate PR**, not bundled here.
- Interim laptop port-forward stopgap = **declined**.

## Evidence (verified live 2026-07-28)

- Hub Grafana/Prometheus/Loki run on `k3d-k3d-cluster`; shopping-cart apps run on `ubuntu-hostinger`.
- Hostinger's own Prometheus tracks `kube_pod_status_ready{namespace=~"shopping-cart.*"}` (apps=12,
  data=21, payment=3); job label is exactly `kube-state-metrics`.
- Hostinger has NO ServiceMonitor for the apps → `up{namespace=~"shopping-cart.*"}` = 0 (app metrics
  absent everywhere — the follow-up spec's problem).
- Hostinger cloudflared runs **on the host**, not in-cluster (only `ztunnel` is cloudflared-adjacent),
  so it reaches services via `localhost:<port>`.
- Hostinger monitoring services: `prometheus-operated` (headless, :9090), `loki-gateway` (:80).
- The hub's existing `federate-acg` job federates the hub *from itself* (port-forward `--context
  k3d-k3d-cluster`), mislabeled `cluster=acg` — a separate pre-existing bug, out of scope here.

## Architecture

```
Hub Grafana (laptop)
  ─ datasource hostinger-prometheus ─┐   CF-Access-Client-Id/Secret (service token)
  ─ datasource hostinger-loki       ─┤
                                     ▼
        https://prometheus-hostinger.3ai-talk.org  (Cloudflare Access app)
        https://loki-hostinger.3ai-talk.org        (Cloudflare Access app)
                                     ▼
              cloudflared on hostinger  (NEW dedicated tunnel: hostinger-obs)
                 ├─ prometheus-hostinger → http://localhost:29090
                 └─ loki-hostinger       → http://localhost:23100
                                     ▼
        host port-forwards on hostinger (systemd):
          29090 → svc/prometheus-operated:9090 -n monitoring
          23100 → svc/loki-gateway:80          -n monitoring
```

## Change 1 — hostinger host: expose Prometheus + Loki to cloudflared

On the hostinger VPS, add two long-lived systemd units (mirror the laptop launchd port-forward
pattern), using the in-cluster kubeconfig/context on the VPS:

- `k3dm-hostinger-prometheus-pf`: `kubectl port-forward svc/prometheus-operated 29090:9090 -n monitoring`
- `k3dm-hostinger-loki-pf`: `kubectl port-forward svc/loki-gateway 23100:80 -n monitoring`

(Alternative: NodePort Services — rejected; port-forward matches existing infra, no manifest churn.)

## Change 2 — dedicated hostinger cloudflared tunnel (observability only)

- Create a NEW named tunnel `hostinger-obs` (distinct ID from `bb7ece59`).
- Add a hostinger-scoped cloudflared config (new rendered config on the VPS; do NOT touch the laptop
  `scripts/etc/cloudflared/config.yml`):
  ```yaml
  tunnel: <hostinger-obs-id>
  credentials-file: <path>/<hostinger-obs-id>.json
  ingress:
    - hostname: prometheus-hostinger.3ai-talk.org
      service: http://localhost:29090
    - hostname: loki-hostinger.3ai-talk.org
      service: http://localhost:23100
    - service: http_status:404
  ```
- DNS: `cloudflared tunnel route dns hostinger-obs prometheus-hostinger.3ai-talk.org` (and loki).

## Change 3 — Cloudflare Access (service-token auth)

- Two self-hosted Access applications: `prometheus-hostinger.3ai-talk.org`,
  `loki-hostinger.3ai-talk.org`.
- One service token `grafana-hub`; each app's policy = allow that service token (Non-Identity).
- Store `CF-Access-Client-Id` / `CF-Access-Client-Secret` in Vault
  (`secret/data/cloudflare/grafana-access`); sync to `monitoring` via ESO as Secret
  `grafana-hostinger-access`.

## Change 4 — hub Grafana datasources (kube-prometheus-stack values)

Add under `grafana.additionalDataSources` in
`scripts/etc/helm/observability/kube-prometheus-stack-values.yaml` (alongside `acg-prometheus` / `Loki`):

```yaml
    - name: hostinger-prometheus
      type: prometheus
      uid: hostinger-prom
      url: https://prometheus-hostinger.3ai-talk.org
      access: proxy
      jsonData:
        timeInterval: 30s
        httpHeaderName1: CF-Access-Client-Id
        httpHeaderName2: CF-Access-Client-Secret
      secureJsonData:
        httpHeaderValue1: ${CF_ACCESS_CLIENT_ID}
        httpHeaderValue2: ${CF_ACCESS_CLIENT_SECRET}
    - name: hostinger-loki
      type: loki
      uid: hostinger-loki
      url: https://loki-hostinger.3ai-talk.org
      access: proxy
      jsonData:
        httpHeaderName1: CF-Access-Client-Id
        httpHeaderName2: CF-Access-Client-Secret
      secureJsonData:
        httpHeaderValue1: ${CF_ACCESS_CLIENT_ID}
        httpHeaderValue2: ${CF_ACCESS_CLIENT_SECRET}
```

Inject `CF_ACCESS_CLIENT_ID/SECRET` into the Grafana pod from the ESO Secret via
`grafana.envValueFrom` (or `extraSecretMounts` + `$__file{}`). NEVER hardcode the token in values.

## Change 5 — reapply the observability ApplicationSet

Per the release rule, the appset `$values` ref freezes to the branch it was last applied from. After
merge, **reapply the observability appset for both hub and acg variants**, confirm with
`argocd_check_values_branch`, and rollout-restart Grafana if datasource provisioning does not hot-reload.

## Definition of Done

- [ ] `prometheus-hostinger` / `loki-hostinger` resolve via the dedicated tunnel; curl with the
      service-token headers → 200 + PromQL/Loki JSON; unauthenticated → 403.
- [ ] Hub Grafana → Explore → `hostinger-prometheus`:
      `kube_pod_status_ready{namespace="shopping-cart-apps"}` returns the app pods.
- [ ] Hub Grafana → Explore → `hostinger-loki`: `{namespace="shopping-cart-apps"}` streams app logs.
- [ ] No secret in git; observability appset reapplied (hub + acg); `argocd_check_values_branch` clean.
- [ ] memory-bank updated with the rollout.

## What NOT to Do

- Do NOT put a new hostname on the shared `bb7ece59` tunnel (split-brain → flaky 404s).
- Do NOT expose Prometheus/Loki publicly without Access.
- Do NOT hardcode the CF Access token in the values file or any committed manifest.
- Do NOT claim app-level metrics work — that needs the separate ServiceMonitor spec.
- Do NOT commit to `main` — work on `k3d-manager-v1.20.0`.
