# v1.46.0 — Hostinger watches the hub from outside: email at 10 minutes, SMS at 30

**Filed:** 2026-10-09, Claude
**Branch:** `k3d-manager-v1.46.0` (do not start until that branch exists; never `main`)
**Status:** QUEUED for v1.46.0. Dispatch to Codex when the branch opens.
**Origin:** operator, 2026-10-09. The companion spec is
`v1.46.0-hermes-not-running-recovery.md`. Its "out of scope" names the gap this spec closes:
everything that watches the hub runs on the M4. The operator asked for the check to come from
Hostinger, and approved the warning at 10 minutes and the critical at 30.

The operator then added four review points, all adopted here:
1. Do not rely on federation alone. Add a blackbox probe of a public endpoint, so there are two
   independent signals.
2. Name the alert for what Hostinger can observe. It cannot tell an M4 power failure from a tunnel
   outage, so the alert is `HubExternallyUnreachable`, not "hub down".
3. Fire the Hermes alert only while the hub is reachable. Make sure no grouping or inhibition rule
   can suppress the 30-minute SMS.
4. Keep the credential in a Hostinger-managed Secret, never in git, and federate only the series the
   watchdog needs.
**Implementer:** Codex · **Verifier:** Claude · **Apply after landing:** operator runs
`make hub-watch`

## Problem

The hub's Prometheus, Alertmanager, Hermes and the webhook all run on the M4. Each of these
silences every one of them at once, and nothing reports it:
- a reboot;
- a power loss;
- an OrbStack crash;
- a stopped hub cluster;
- a dead Cloudflare tunnel.

Sleep is already disabled (`sudo pmset -a disablesleep 1`, 2026-10-09). That removes one cause, not
the gap.

Hostinger (`ubuntu-hostinger`, `srv1754834`) is a separate machine. It runs its own
kube-prometheus-stack, with release `acg-kube-prometheus-stack`, Prometheus and Alertmanager in
`monitoring`. Its Alertmanager uses the same `alertmanager.yaml.tmpl` as the hub, with receivers
`sms-critical` and `platform-warning`.

The hub Prometheus is public at `https://prometheus.3ai-talk.org`. The path is the Cloudflare tunnel
to the basic-auth proxy (`bin/prometheus-auth-proxy`, `com.k3d-manager.prometheus-auth-proxy`) and
then to the hub Prometheus.

## Approach

Hostinger gets **two independent signals**:

| Signal | Job | What it reads | Depends on |
|---|---|---|---|
| **probe** | `hub-probe` | a blackbox `http_2xx` probe of `https://argocd.3ai-talk.org/healthz`. This was verified 2026-10-09 to return 200 with no login | M4 up, Cloudflare tunnel, ArgoCD's port-forward. **Not** the hub Prometheus |
| **federate** | `hub-federate` | `/federate` on `https://prometheus.3ai-talk.org` with basic auth, one series only: `k3dm_hermes_last_tick_timestamp_seconds` | M4 up, tunnel, auth proxy, hub Prometheus |

The two signals combine like this:

| probe | federate | Meaning | Alert |
|---|---|---|---|
| fail | fail | Nothing on the M4 is reachable from outside: M4 off, OrbStack or hub down, or the tunnel or Cloudflare down. Hostinger cannot tell which | `HubExternallyUnreachable` |
| ok | fail | The hub answers, but its Prometheus path does not: the auth proxy, the hub Prometheus, or the credential | `HubPrometheusUnreachable` |
| fail | ok | ArgoCD's port-forward alone is down | none here. The hub's own alerts cover ArgoCD |
| ok | ok | healthy. Evaluate the Hermes heartbeat | `HubHermesNotRunningOffsite` when stale |

**Rules**, all on Hostinger, all labelled `cluster: hub`:

| Alert | Expression | `for` | Severity | Goes to |
|---|---|---|---|---|
| `HubExternallyUnreachable` | `probe_success{job="hub-probe"} == 0 and on() up{job="hub-federate"} == 0` | 10m | warning | `platform-warning` (email) |
| `HubExternallyUnreachable` | same expression | 30m | critical | `sms-critical` (SMS) |
| `HubPrometheusUnreachable` | `up{job="hub-federate"} == 0 and on() probe_success{job="hub-probe"} == 1` | 15m | warning | email |
| `HubHermesNotRunningOffsite` | `(time() - k3dm_hermes_last_tick_timestamp_seconds > 1800) and on() up{job="hub-federate"} == 1` | 15m | warning | email. The hub is reachable, so this means Hermes is down while hub alerting is broken or delayed |
| `HubWatchMissing` | `absent(up{job="hub-federate"}) or absent(probe_success{job="hub-probe"})` | 30m | warning | email. A watch job is not loaded, for example its Secret is missing and the operator dropped the scrape |

**Why `cluster: hub` matters:**
- **SMS routing.** Hostinger's Alertmanager uses the same template as the hub. It routes
  `severity=critical, cluster=~"acg|ubuntu-k3s"` to email, and any other `critical` to
  `sms-critical`. With `cluster: hub`, the critical `HubExternallyUnreachable` takes the SMS route.
- **External labels.** Prometheus adds its external label `cluster: ubuntu-k3s` only when the alert
  does not already have one.

**Suppression (review point 3).**
- **Inhibition:** the template's only inhibit rule is `ServiceDown` → `PodCrashLooping|HighErrorRate|TargetDown`,
  so nothing inhibits a `Hub*` alert today. Test 7 locks that in.
- **Grouping:** the warning and the critical go to different routes, so they never share a group.
  The critical gets its own `group_wait` of 5 minutes.

**Timing.** Expect the email about 20 minutes after the outage starts (10m `for` plus 10m
`group_wait`), and the SMS about 35 minutes after (30m plus 5m).

**Planned M4 downtime:** `make hub-watch-silence HOURS=n` adds a maintenance silence on Hostinger
first.

## Design

### 1. `scripts/etc/prometheus/hub-watch/scrapeconfig.yaml` (new)

Two ScrapeConfig documents. The ScrapeConfig CRD is installed on Hostinger, and Prometheus selects
`release: acg-kube-prometheus-stack` for both ScrapeConfigs and rules.

Using the CRD keeps this out of `kube-prometheus-stack-acg-values.yaml`, which **ACG sandboxes
share**. A sandbox must never watch the hub. ACG alerts are email-only, and the watch belongs to the
permanent host.

```yaml
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: hub-federate
  namespace: monitoring
  labels:
    release: acg-kube-prometheus-stack
spec:
  jobName: hub-federate
  scheme: HTTPS
  metricsPath: /federate
  scrapeInterval: 60s
  scrapeTimeout: 20s
  honorLabels: true
  params:
    "match[]":
      - '{__name__="k3dm_hermes_last_tick_timestamp_seconds"}'
  basicAuth:
    username:
      name: hub-prometheus-basic-auth
      key: user
    password:
      name: hub-prometheus-basic-auth
      key: password
  staticConfigs:
    - targets: ["prometheus.3ai-talk.org"]
      labels:
        watched: hub
---
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: hub-probe
  namespace: monitoring
  labels:
    release: acg-kube-prometheus-stack
spec:
  jobName: hub-probe
  metricsPath: /probe
  scrapeInterval: 60s
  scrapeTimeout: 20s
  params:
    module: ["http_2xx"]
  staticConfigs:
    - targets: ["https://argocd.3ai-talk.org/healthz"]
      labels:
        watched: hub
  relabelings:
    - sourceLabels: [__address__]
      targetLabel: __param_target
    - sourceLabels: [__param_target]
      targetLabel: instance
    - targetLabel: __address__
      replacement: prometheus-blackbox-exporter.monitoring:9115
```

**Federate selection (review point 4).** `match[]` names exactly one series. Never widen it to a
regex or a job selector. Test 6 locks it to that single matcher.

### 1b. Blackbox exporter on Hostinger

There is none today. `deploy_hub_watch` installs it the way `_deploy_pushgateway_acg` installs the
Pushgateway:
- `helm upgrade --install prometheus-blackbox-exporter prometheus-community/prometheus-blackbox-exporter`,
  in namespace `monitoring`, on `ubuntu-hostinger` only;
- `--version` pinned explicitly. Pick the newest chart release that is at least two weeks old from
  `helm search repo prometheus-community/prometheus-blackbox-exporter --versions`, and record the
  version in your report;
- `--wait --timeout 120s`. The chart's default `http_2xx` module is enough.

If helm is missing or the install fails, print one error and return 1. Do not apply the
ScrapeConfigs half-done.

### 2. `scripts/etc/prometheus/hub-watch/rules.yaml` (new)

One PrometheusRule named `hub-watch` in `monitoring`, labelled `release: acg-kube-prometheus-stack`,
with group `hub-watch.alerts` and the five rules in the Approach table.

Each annotation `description` says what is known and what to check. Never claim the machine is
down.
- **`HubExternallyUnreachable`:**
  - Say: "Neither the ArgoCD health URL nor the hub Prometheus is reachable from Hostinger. This
    can be the M4, OrbStack or the hub cluster, or the Cloudflare tunnel, and Hostinger cannot tell
    which."
  - Then the checks: whether the M4 is up, the `cloudflared` LaunchAgent, and
    `kubectl --context k3d-k3d-cluster get nodes`.
  - Planned downtime needs `make hub-watch-silence`.
- **`HubPrometheusUnreachable`:** `launchctl print gui/$UID/com.k3d-manager.prometheus-auth-proxy`,
  the hub Prometheus pod, and whether the proxy credential was rotated without `make hub-watch`.
- **`HubWatchMissing`:** `make hub-watch`.
- **`HubHermesNotRunningOffsite`:** `docs/guides/hermes.md`.

### 3. `scripts/plugins/observability.sh`

**`function deploy_hub_watch()`** is public, takes `-h`/`--help`, and uses the context
`${HUB_WATCH_CONTEXT:-ubuntu-hostinger}`.
1. **Seed the Secret** `monitoring/hub-prometheus-basic-auth`, with keys `user` and `password`.
   - The source is the local file `_observability_prometheus_auth_file` (keys
     `PROMETHEUS_BASIC_AUTH_USER` and `PROMETHEUS_BASIC_AUTH_PASSWORD`), the same file the proxy
     refresh reads.
   - Hostinger's ESO store reads **Hostinger's own** Vault, which does not hold the hub credential.
     That is why this is a direct Secret and not an ExternalSecret.
   - Build the manifest in a `mktemp` file with mode 600 and apply it with `--dry-run=client -o yaml
     | _kubectl apply -f -`, the pattern `alertmanager-smtp-secret` uses. **The password must never
     appear in argv, stdout or the log.** Remove the temp file on every path.
   - If the file or either key is missing, print one error naming the file and return 1. Do not
     apply the ScrapeConfig: without its Secret, the operator drops it silently, which is exactly
     what `HubWatchMissing` catches.
2. Install the blackbox exporter (Design §1b).
3. Apply `scrapeconfig.yaml` and `rules.yaml` to the context.
4. Print one line:
   `[observability] hub watch applied on <ctx>: probe + federate every 60s; email 10m, SMS 30m`.

**Wiring:**
- **In `deploy_observability_acg`:** call `deploy_hub_watch` only when the resolved app context is
  `ubuntu-hostinger`. On any other context, print
  `[observability] hub watch skipped on <ctx> (Hostinger only)`.
- **In `_observability_refresh_prometheus_auth_proxy`:** after a successful refresh that **changed**
  the credential, re-seed the Secret when `ubuntu-hostinger` is reachable. Only re-seed the Secret;
  leave the ScrapeConfig and rules alone. A rotation must not leave Hostinger with the old password,
  because the federate scrape would then fail with 401. The probe still passes, so that shows up as
`HubPrometheusUnreachable` (email), not as an SMS, and the Hermes heartbeat goes unwatched. If Hostinger is unreachable,
  warn and continue, and print the `make hub-watch` command.

**`function hub_watch_silence()`** takes `HOURS` (default 8, integer 1–72, refuse anything else).
- It runs `amtool silence add 'alertname=~"Hub.*"' --duration=<H>h --author=k3dm --comment="planned hub downtime"`
  inside the Hostinger Alertmanager pod, through
  `kubectl exec ... -c alertmanager -- amtool --alertmanager.url=http://localhost:9093 ...`.
- It prints the silence ID.

**`function hub_watch_unsilence()`** expires every active silence whose matcher is
`alertname=~"Hub.*"`, using `amtool silence query -q` then `amtool silence expire`.

### 4. `Makefile`

```make
## Apply the Hostinger offsite hub watch (scrape + rules + basic-auth Secret)
hub-watch:
	./scripts/k3d-manager deploy_hub_watch --confirm

## Silence the hub-watch alerts on Hostinger before planned M4 downtime (HOURS=8)
hub-watch-silence:
	HOURS="$(HOURS)" ./scripts/k3d-manager hub_watch_silence

## Expire the hub-watch silences on Hostinger
hub-watch-unsilence:
	./scripts/k3d-manager hub_watch_unsilence
```

Add the targets to `.PHONY` if the Makefile keeps that list.

## Tests (`scripts/tests/plugins/hub_watch.bats`)

Stub `kubectl` and `helm` through PATH, logging argv and stdin to files. Point the auth file at a `BATS_TMPDIR`
fixture. No test may reach a cluster or the network.

1. `deploy_hub_watch`, run with a fixture file:
   - applies a Secret with `user` and `password`;

   - applies the ScrapeConfigs and the rules, **in that order** (Secret first, then helm);
   - every call carries `--context ubuntu-hostinger`.
2. **Secret hygiene:** a sentinel password never appears in kubectl argv, stdout or stderr, and no

5. **Rules file:** parse it with `yq`, or `python3 -c 'import yaml'` if `yq` is absent. Check:
   - the alert names `HubExternallyUnreachable` (twice), `HubPrometheusUnreachable`,
     `HubHermesNotRunningOffsite` and `HubWatchMissing`;
   - the critical `HubExternallyUnreachable` has `for: 30m`, and the warning has `for: 10m`;
   - both `HubExternallyUnreachable` expressions require **both** `probe_success{job="hub-probe"} == 0`
     and `up{job="hub-federate"} == 0`;

   - every rule has `cluster: hub`;
   - the label `release: acg-kube-prometheus-stack` is present.
6. **ScrapeConfigs:**
   - `hub-federate`:
     - targets `prometheus.3ai-talk.org`;
     - uses basic auth from Secret `hub-prometheus-basic-auth`;
     - has exactly one `match[]`, equal to `{__name__="k3dm_hermes_last_tick_timestamp_seconds"}`.
   - `hub-probe`:
     - targets `https://argocd.3ai-talk.org/healthz` with module `http_2xx`;
     - rewrites the address to the blackbox exporter.
   - Both carry the `release` label.
   - The file has no Secret and no credential value.
7. **Routing and suppression.** Render `scripts/etc/prometheus/alertmanager.yaml.tmpl` with dummy
   values. With a small Python matcher over the parsed routes (first match wins, no `continue`),
   check:
   - `{alertname: HubExternallyUnreachable, severity: critical, cluster: hub}` routes to
     `sms-critical`;
   - the same alert with `severity: warning` routes to `platform-warning`;
   - no `inhibit_rules` entry has a target matcher that matches either of those label sets.
8. `hub_watch_silence`:
   - `HOURS=0`, `HOURS=73` and `HOURS=x` are refused;
   - `HOURS=8` runs `amtool silence add` with `--duration=8h` and the `Hub.*` matcher, inside the
     Alertmanager pod, on `ubuntu-hostinger`.
9. **Rotation re-seed.** `_observability_refresh_prometheus_auth_proxy`:
   - when the credential changed, the Hostinger Secret is re-applied;
   - when it did not change, it is not;
   - when Hostinger is unreachable, it warns and returns success.
10. `kube-prometheus-stack-acg-values.yaml` has no `hub-federate` job. This guards against moving
    the watch into the shared values.

## Out of scope

- **Hostinger itself going down.** The hub already watches Hostinger, and Hostinger now watches the
  hub. If both go down at once, nothing alerts. That case needs a third party, such as an external
  uptime service, and is not planned.
- **Cloudflare false pages.** A Cloudflare outage makes the hub unreachable from Hostinger while the
  M4 is fine. The 30-minute delay before the SMS keeps short blips out; a long outage pages, and
  that is acceptable.
- **A least-privilege credential for the scrape.** The scrape requests one series, but the proxy's
  single basic-auth user it reuses can read all of the hub's Prometheus API. A dedicated user on the
  proxy, limited to `/federate` with that one `match[]`, would close this. It is a follow-up and
  needs a `bin/prometheus-auth-proxy` change.
- **Telling an M4 failure from a tunnel failure.** Hostinger cannot see past Cloudflare. The alert
  name and its description say so, and the hub's own data after recovery is where to look.
