**Component:** `bin/k3dm-vectordb-metrics`, `bin/k3dm-codex-dispatch`, `bin/k3dm-dispatch-metrics`,

## Problem

The operator asked "do we have a dashboard to track each release's specs execution condition?" Today:

- **k3dm Bug Tracking** covers `docs/bugs/` per release, and nothing reads `docs/plans/`.
- **k3dm Agent Dispatch** has a Per spec table (Release, Spec, Codex tokens, time, runs), but no state
  column. It only sees specs sent through `bin/k3dm-codex-dispatch`, so a spec Claude implements
  directly, or one not yet started, never appears. Its "Spec" is the dispatch `--slug`, not the plan
  file, so it cannot be matched to a plan.

So nothing answers "which of this release's plans are proposed, ready, being implemented, landed or
live-verified, and is any of them stuck in dispatch?" The release cap (max 5 plan docs, CLAUDE.md) is
also checked by hand.

## Requirements (operator, 2026-10-17)

1. **Include every planned specification.** `docs/plans/` is the authoritative inventory. The
   dispatch ledger is never the source of the row list, because it omits Claude-implemented and
   not-yet-started work.
2. **Keep execution state separate from verification state.** Landed means the code was integrated.
   It does not mean the spec passed e2e or was live-verified, the same distinction the bug tracking
   already draws.
3. **Don't infer completion from missing information.** A plan with no dispatch record could be not
   started, implemented directly by Claude, or simply uninstrumented. Where the evidence is
   insufficient the dashboard shows `unknown` / `no record`, never "not started" or "done".

## Decisions

- **Extend the Bug Tracking dashboard, not a new one.** The plan rows reuse its `$repo` and
  `$release` variables, so a release is chosen once for bugs and plans.
- **Scope: k3d-manager only.** `repo="k3d-manager"` on every new series; the lib-foundation
  bug scan is untouched. On `$repo=lib-foundation` the new panels show no data.
- **A plan belongs to the release in its filename.** `docs/plans/v<X.Y.Z>-<slug>.md` → release
  `v<X.Y.Z>`. Any other name (no version prefix: roadmaps, evaluations, unversioned plans) is not
  emitted and is counted in `k3dm_plan_info_skipped`.
- **Two independent axes, both read only from the plan doc's Status value** (the text
  `_status_value` returns). They are matched case-insensitively on the leading word(s), and the first
  matching row wins. They are separate labels, `execution` and `verification`, and no panel merges them.

  | Doc Status starts with | `execution` | `verification` |
  |---|---|---|
  | `LIVE-VERIFIED` | `implemented` | `live_verified` |
  | `VERIFIED` | `implemented` | `verified` |
  | `IMPLEMENTED`, `DONE`, `LANDED`, `MERGED`, `SHIPPED` | `implemented` | `unknown` |
  | `IN PROGRESS`, `IN-PROGRESS`, `DISPATCHED`, `PENDING CODEX` | `in_progress` | `n/a` |
  | `READY`, `APPROVED` | `ready` | `n/a` |
  | `PROPOSED`, `SPEC`, `DRAFT`, `PLAN`, `PLANNED`, `SCOPED`, `QUEUED` | `proposed` | `n/a` |
  | `DEFERRED`, `MOVED`, `SPLIT` | `deferred` | `n/a` |
  | `SUPERSEDED`, `CANCELLED`, `CANCELED`, `DROPPED`, `WITHDRAWN` | `cancelled` | `n/a` |
  | anything else, or no Status line | `unknown` | `unknown` |

  - `implemented` + `verification="unknown"` is deliberate. "IMPLEMENTED" says the code is in. It
    says nothing about e2e or live proof, so the dashboard must not show it as verified, and must
    not show it as failed either. Words later in the Status ("live proof pending", "Claude-verified:
    pytest …") are **not** parsed for verification: unit-test verification is not e2e/live
    verification, and free text is not reliable evidence.
  - `n/a` means verification does not apply yet (nothing is implemented). It is not a claim about
    quality.
  - A Status written later as "IMPLEMENTED BY …" or "QUEUED FOR …" still maps by its first word.
- **Approval** comes from the `**Approval:**` line (required on every v1.43.2+ plan):
  - no line → `none`;
  - value starting with `pending` (case-insensitive) → `pending`;
  - otherwise → `explicit`.

  Plans in releases below v1.43.2 get `approval="n/a"`, because the header did not exist yet.
- **Dispatch state comes from the ledger, joined on the plan file stem.** The ledger's `start`
  event gains a `spec` field (the repo-relative spec path). `bin/k3dm-dispatch-metrics` emits one
  series per plan stem for its **latest** dispatch (largest `start` ts), so the dashboard join is
  one-to-one. Ledger tasks without `spec` (everything before this change) emit nothing.

  | Latest event of that task | `dispatch_state` |
  |---|---|
  | `start` or `resume` after the last `codex_exit` | `running` |
  | `codex_exit` with `exit` ≠ 0, no later launch | `codex_failed` |
  | `codex_exit` with `exit` 0, no later launch, no `land` | `awaiting_land` |
  | `land_refused` after the last `codex_exit`, no `land` | `refused` |
  | `land` | `landed` |
  | `abandon` | `abandoned` |

  **A plan with no dispatch series shows `no record`**, never "not started". It may be unstarted,
  Claude-implemented, or dispatched before the ledger recorded `spec` (every dispatch before v1.43.5).
  Dispatch `landed` is an execution fact only. It does not move `verification`.
- **Disagreement is surfaced, not resolved.** If the ledger says `landed` while the doc's
  `execution` is `proposed`, `ready` or `in_progress`, the row is flagged `status lags dispatch`.
  The doc was not updated after landing; the dashboard does not "correct" it either way.

- **A bug spec dispatched with the wrapper** (`docs/bugs/…`) gets a dispatch series too, but no
  plan row exists to join it to, so it is invisible on the new panels. That is intended: bugs have
  their own section.

## Fix

### 1. `bin/k3dm-vectordb-metrics` — plan scan

Add `_plan_texts(root, ref=None)`, the same shape as `_bug_texts` but over `docs/plans` (top level
only, `*.md`). With `ref` it reads through one `git cat-file --batch`; without it reads the working tree.

Add `_plan_state(status_value)` (returns `(execution, verification)`), `_plan_approval(text, release)` and
`_plan_metrics(root, ref=None, texts=None, repo="k3d-manager")`. The last returns this text:

```
k3dm_plan_info{repo="k3d-manager",release="v1.43.5",release_order="<_release_order(release)>",plan="v1.43.5-release-plan-tracking",title="<H1 without the 'vX.Y.Z — ' prefix>",execution="proposed",verification="n/a",approval="explicit"} 1
k3dm_plan_release_docs{repo="k3d-manager",release="v1.43.5",release_order="…",execution="proposed",verification="n/a"} 1
k3dm_plan_info_skipped{repo="k3d-manager"} <n>
k3dm_plan_docs_scan_timestamp_seconds{repo="k3d-manager"} <time.time()>
```

- `title` is sanitized exactly like the bug title (strip `` ` `` and `*`, collapse `"`, `\`, tabs and
  newlines to a space, collapse whitespace, cap 120 chars with `…`). Also drop a leading
  `v<X.Y.Z>` plus any `—`, `–`, `-` or `:` separator. With no H1, use the slug with `-` → space.
- `k3dm_plan_release_docs` is emitted for every (release, execution, verification) triple with a count > 0.
- `release_order` uses the existing `_release_order`, so the dashboard's `$release` variable (which
  holds release_order values) filters plans and bugs the same way.

In `publish_bug_metrics`, after the bug groups, inside its own `try`:
`_push_bug_group("k3dm-plan-docs", _plan_metrics(root, ref), method="PUT")`. A failure prints
`plan metrics skipped (non-fatal): …` to stderr and changes nothing else. PUT replaces the group,
so a renamed or deleted plan disappears on the next scan.

### 2. `bin/k3dm-codex-dispatch` — record the spec

The `start` ledger event (line ~278) adds the spec path:

```bash
  _dispatch_ledger_event_best_effort start "$version" "$slug" --argjson network "$network" --arg spec "$spec" \
    '.["network"]=$network | .["spec"]=$spec'
```

`_dispatch_ledger_event` already passes every argument before the final filter on to `jq`, so it
needs no change. `$spec` is the path already validated as tracked and unchanged.

### 3. `bin/k3dm-dispatch-metrics` — per-plan dispatch state

Add `_dispatch_state(task_events)`, implementing the table above, and add this to `render` after the
existing running/awaiting lines:

```
k3dm_dispatch_plan_state{plan="<spec stem>",version="<version>",slug="<slug>",dispatch_state="<state>"} 1
```

- One line per plan stem, taken from the task whose `start` event has the largest `ts` among the
  tasks whose `start` carries that `spec`.
- The stem is `Path(spec).name` without `.md`. Emit the line only if the stem matches
  `^v\d+\.\d+\.\d+-[a-z0-9][a-z0-9-]*$` (plan files). Count any other `spec` in
  `k3dm_dispatch_plan_state_skipped`.
- Not windowed. The existing `k3dm_dispatch_running` / `k3dm_dispatch_awaiting_land` stay as they are.

### 4. `scripts/etc/argocd/platform-ops/grafana-dashboard-bugs.yaml` — "Release plans" section

Add a collapsed-false row titled `Release plans — $release` below every existing panel (current
bottom is `y` = 40; start at `y` 40 and shift nothing). It holds two stat tiles and one table.

**Tiles**, each `h` 4 and `w` 4. Every expr is `sum(k3dm_plan_release_docs{repo="$repo",release_order=~"$release",<matcher>}) or vector(0)`:

| Title | `<matcher>` | Thresholds |
|---|---|---|
| Plans in release | (none) | green; red at `6` (the 5-plan cap) |
| Not yet implemented | `execution=~"proposed\|ready\|in_progress"` | none |
| Implemented, verification unknown | `execution="implemented",verification="unknown"` | yellow at `1` |
| Live-verified | `verification="live_verified"` | green |
| Status unknown | `execution="unknown"` | yellow at `1` |
| Status lags dispatch | `count((k3dm_plan_info{repo="$repo",release_order=~"$release",execution=~"proposed\|ready\|in_progress"} * on(plan) group_left k3dm_dispatch_plan_state{dispatch_state="landed"})) or vector(0)` (full expr, not the template) | yellow at `1` |

There is deliberately **no** "Not started" tile (Requirement 3).

**Table** `Plans` (`w` 24, `h` 9), one instant query, format table:

```
(
  k3dm_plan_info{repo="$repo",release_order=~"$release"}
    * on(plan) group_left(dispatch_state, slug)
  k3dm_dispatch_plan_state
)
or on(plan)
k3dm_plan_info{repo="$repo",release_order=~"$release"}
```

`or on(plan)`, not a bare `or`: the joined side carries `dispatch_state` and `slug`, so a bare `or`
finds no matching label set and returns every dispatched plan a second time as "no record".

Use an `organize` transformation. Show `release` → Release, `plan` → Plan, `title` → Title,
`execution` → Execution, `verification` → Verification, `approval` → Approval,
`dispatch_state` → Dispatch and `slug` → Dispatch task. Hide
`Time`, `Value`, `repo`, `release_order`, `__name__`, `job`, `instance` and `version`. Sort by
`plan` ascending.

Value mappings:

- **Execution:** `in_progress` → `in progress`, `unknown` → `? unknown` (yellow).
- **Verification:** `live_verified` → `✓ live`, `verified` → `✓ verified`, `unknown` → `? unknown`
  (yellow), `n/a` → `-`.
- **Dispatch:** empty → `no record` (grey, **not** `not started`), `codex_failed` → `codex failed`
  (red), `refused` → `land refused` (red), `awaiting_land` → `awaiting land` (yellow),
  `landed` → `landed (code in)`.

Add a cell-colour override on Execution: yellow when the row's Dispatch is `landed` and Execution is
`proposed`, `ready` or `in_progress` (`status lags dispatch`). If a field-based override cannot express
it, use a second hidden query plus a `Join by field` on `plan`, but never a merged state label.

## Rules

- Never commit to `main`; no PR, no merge, no `--no-verify`.
- Do not push to a real Pushgateway and do not read `~/.local/share/k3d-manager/worktrees/ledger.jsonl`.
- Do not change existing metric names, labels or panels; only add.
- Gates (paste the output): the pytest, bats and shellcheck commands in Definition of Done.

## What NOT to Do

- Do not parse plan files for anything except the H1, `**Status:**` and `**Approval:**`.
- Do not combine `execution`, `verification` and `dispatch_state` into one label or column, and do not
  derive any of them from another.
- Do not scan lib-foundation plans.
- Do not change the Agent Dispatch dashboard.
- Do not make the scanner or the dispatch wrapper fail on a plan or ledger parse error. Skip, count
  and carry on.
