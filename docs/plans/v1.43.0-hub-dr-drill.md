# v1.43.0 — Weekly hub disaster-recovery drill

**Status:** PLAN — written 2026-10-03; design decisions from the operator are recorded in §2. Resolve the live checks in §7 before dispatching to Codex.
**Branch:** `k3d-manager-v1.43.0` (not yet created)
**Release count:** 1 of 5 for v1.43.0

## 1. Goal

On 2026-10-03 the hub was deleted by a sandbox teardown. Recovery took hours. The gaps were only found under pressure:

- the Keycloak stack and its Vault paths existed only on the sandbox path;
- the embeddings key's Vault copy was gone;
- a root-owned logs folder silently stopped the Grafana port-forward;
- every ArgoCD API token was invalidated;
- a full VectorDB re-index took 40+ minutes.

The guards against a repeat landed in v1.41.0:

- `make down` keeps the hub unless `DELETE_HUB=1` (`435c95a1`);
- `hub-up` refuses a non-hub context (`ed22bda9`);
- one-command `make hub-recover` (`fb71deb4`).

This plan adds **proof, every week, that hub data comes back quickly and completely.** The operator's requirement: *"we are not necessarily snapshot image but we need to be able to restore data quickly without issue."*

## 2. Design decisions (operator, 2026-10-03)

| # | Decision | Consequence |
|---|---|---|
| 1 | **Vault unseal shards are kept in Apple Keychain** | No k3s datastore (`state.db`) in the backup. The restored Vault is unsealed with the original shards. The data export holds no Kubernetes Secrets. |
| 2 | **Restored data must land on the right node** | Each claim is pre-bound to its logical node before its workload starts. A node mismatch is a hard stop. |
| 3 | **Data is stored in a private git repo and restored from there** | Off-machine, and independent of the M2↔M4 local network. Every file is `age`-encrypted before commit. History is bounded. |
| 4 | **The drill runs from the M2** | The drill hub, its kube context and its ports exist only on the M2. Nothing on the M4 is touched except a read-only export. |
| 5 | **Rules live in GitHub** | PrometheusRules stay in git (GitOps). An independent staleness check runs as a scheduled workflow in the data repo, so it works even when the M4 is down. |
| 6 | **The drill hub runs on the M2, not as a second hub on the M4** | Removes the memory question on the 24 GB M4. The M2's capacity is measured on the first run (§7 L4). |

## 3. What exists today (measured, not assumed)

- **The Keychain path** (`make hub-up` + `bin/hub-restore`) restores credentials and local agents only. It brings back no user data: Keycloak users, LDAP entries and Vault KV that isn't mirrored in Keychain are regenerated, not restored. That regeneration is the 2026-09-29 credential-drift class.
- **The data path:**
  - `hub_snapshot_capture` (v1.36.0) captures to the M2 over SSH (`m2jump`);
  - `hub_recovery_restore` (v1.33.0, executed 2026-09-11) restores from it;
  - capture was never scheduled, so no snapshot existed on 2026-10-03;
  - the restore needs `server-db/state.db`, which contains every Secret in plaintext;
  - both legs depend on the local network.
- **Reusable pieces:**
  - `_hub_snapshot_claim_pv`/`_node`/`_path`/`_copy`;
  - `hub_recovery_targets <context>`;
  - `_hub_recovery_restore_one` (a tar stream into the target node);
  - `_hub_recovery_logical_node`, which matches by suffix, so a cluster named `dr-drill` resolves.
- **Vault shards in Keychain:**
  - `vault.sh` already stores them under service `k3d-manager-vault-unseal`, keyed `<cluster>:shard<N>` and `<cluster>:count`, through `_secret_store_data` / `_secret_load_data`;
  - but `_vault_clear_cached_shards` (`vault.sh:473`) deletes them after a successful unseal, so they are not a durable copy.
- **The cluster template** `scripts/etc/cluster.yaml.tmpl` sets `switchCurrentContext: true`. That is harmless on the M2, because the drill kubeconfig is a dedicated file there (D4).

## 4. Design

### D1 — Durable unseal shards in Keychain (M4 and M2)

- **New Keychain service `k3dm-vault-unseal-dr`,** account `<cluster>`, holding the shard count and the shards. It is separate from the transient `k3d-manager-vault-unseal` cache. It is never cleared by an unseal.
- **`vault_dr_shards_save`** (new public function in `scripts/plugins/vault.sh`). It runs at Vault init and on demand. It reads the shards from the `vault-unseal` Secret through the existing `_vault_collect_unseal_shards_from_secret`, and writes them with `_secret_store_data`. The values travel through the existing helpers' stdin path only; they never appear in argv or logs. Operator-run, in Terminal.app.
- **The M2 copy is a one-time operator step:** `make vault-dr-shards-export` on the M4 piped to `make vault-dr-shards-import` on the M2, over the operator's own SSH session, or typed by hand. Document it; never automate the transfer.
- **Restored-Vault root access:** the drill never stores or reuses a root token. It uses the shards to run `vault operator generate-root`, which gives a short-lived token. It uses that token for `kv list` only, then revokes it (`vault token revoke -self`).

### D2 — Encrypted data export to a private git repo (`hub_data_export`, runs on the M4)

- **The repo** is `wilddog64/k3dm-hub-data` (private; the operator creates it). Branch `snapshots`, one directory per export, `<UTC-ts>/`.
- **Contents of each export:**
  - one `age`-encrypted tarball per critical claim: Vault, postgres-keycloak and the 3 LDAP claims;
  - `pv-pvc.yaml`, PVC metadata only: name, namespace, size, storageClass, accessModes and the logical node;
  - `SHA256SUMS` over the **encrypted** files;
  - `inventory.json`, holding the real hub's **counts and path names** for verification: the Vault KV path list, the Keycloak realm user count, and the LDAP entry count.
  - No `state.db`. No Kubernetes Secret object. No plaintext value.
- **Encryption:**
  - `age` to a recipient public key committed in k3d-manager (`scripts/etc/dr/age-recipient.txt`);
  - the matching identity (private key) is in Keychain service `k3dm-hub-data-age` on the M2, plus the operator's offline copy;
  - **the M4 holds only the public key**, so the capture side cannot decrypt anything.
- **Repo access:**
  - the M4 pushes with a write deploy key scoped to `k3dm-hub-data` only;
  - the M2 pulls with a read-only deploy key;
  - the private keys live in each machine's ssh config. The operator installs them; Claude never reads them.
- **Retention:** keep the newest `K3DM_HUB_DATA_KEEP` exports (default 4, about one month).
  - Pruning rewrites the `snapshots` branch to an orphan commit holding only the kept directories, then force-pushes. Force-pushing is allowed only on this data repo's `snapshots` branch.
  - `git count-objects -vH` should stay under 1 GB.
  - Any file at or over 95 MB is split (`split -b 90m`) before commit, because GitHub's hard limit is 100 MB.
- **Reuse** the `_hub_snapshot_claim_*` and `_hub_snapshot_copy` helpers. **Do not change** `hub_snapshot_capture` or the M2 SSH store; that legacy full-capture path stays as it is.

### D3 — Right-node restore (`hub_data_restore`, runs on the M2)

1. **Decrypt and verify:**
   - `git clone --depth 1` the data repo into a `mktemp -d` stage with mode 700;
   - verify `SHA256SUMS`;
   - decrypt with the Keychain identity, streamed `security … -w | age -d -i -`, so the identity never touches disk.
2. **Pre-bind each claim:**
   - before the owning workload exists, create each PVC from `pv-pvc.yaml` with annotation `volume.kubernetes.io/selected-node: k3d-${DR_DRILL_CLUSTER}-<logical-node>`;
   - the StatefulSet and Deployment then adopt the existing PVC by name, and `local-path` provisions on the annotated node.
   - Confirm that `local-path` honours this annotation in our version (§7 L2).
3. **Gate:** `hub_recovery_targets k3d-${DR_DRILL_CLUSTER}` must map every claim to the same logical node as in `pv-pvc.yaml`. Any mismatch stops the restore before any data is copied.
4. **Copy:** scale the consumers to 0, run `_hub_recovery_restore_one` per claim, then scale back up.
   - Add a thin wrapper that requires only `pv-pvc.yaml`, the claim trees and `SHA256SUMS`.
   - Do not touch `hub_recovery_restore` or `_hub_recovery_validate_files`, which still require `state.db` for the legacy path.
5. **Unseal** with the Keychain `k3dm-vault-unseal-dr` shards (D1).

### D4 — `make dr-drill` → `bin/dr-drill` (runs on the M2)

The capture runs on the M4 as `make hub-data-export`, weekly and attended, before the drill. The drill consumes the newest export.

Phases are logged as `[dr-drill] Phase N/6 — …` and timed:

1. **Preflight.** Exit 2 when any of these fails:
   - an interactive TTY with Keychain access;
   - `hostname` is the M2 (refuse on the M4, unless `DR_DRILL_ALLOW_HOST=1`);
   - a newest export exists and is ≤ 26 h old;
   - no leftover `k3d-${DR_DRILL_CLUSTER}` cluster;
   - free Docker disk ≥ 10 GB.
2. **Build the drill hub:**
   - `KUBECONFIG=~/.k3dm/dr-drill/kubeconfig HUB_CLUSTER_NAME=${DR_DRILL_CLUSTER:-dr-drill} bin/hub-up`;
   - the drill kubeconfig is a dedicated file, so the M2's own default kubeconfig is never touched;
   - `hub-up`'s current-context guard passes naturally inside that file.
3. **Restore:** D3.
4. **Verify:** D5.
5. **Report:**
   - write `~/.k3dm/dr-drill/<ts>.json` and a summary table;
   - commit `results/<ts>.json` to the data repo with the M2 read key. A results write needs a key: use a second deploy key on the M2 with write access scoped to the data repo, and accept the risk; or the operator pushes it. Decide in §7 L5.
   - Push metrics (D6).
6. **Teardown, always,** from an `EXIT` trap:
   - `k3d cluster delete ${DR_DRILL_CLUSTER}`, behind an exact-name guard that refuses `k3d-cluster`;
   - `rm -rf` the stage and the drill kubeconfig.

   `DR_DRILL_KEEP=1` keeps the cluster and prints the delete command.

### D5 — Verify checklist (counts and path names only, never values)

| # | Check |
|---|---|
| V1 | Vault `Sealed false` after unsealing with the Keychain shards |
| V2 | `vault kv list` over the inventory paths, using a generate-root token that is revoked afterwards. Every path in `inventory.json` is present. A path on the real hub but not in the committed allowlist is **UNLISTED**: a warning, not a failure. |
| V3 | Keycloak realm user count = `inventory.json` |
| V4 | LDAP entry count under the base DN = `inventory.json` |
| V5 | vault-0, postgres-keycloak and openldap-0 are Ready within 300 s, each on its expected logical node |
| V6 | RTO (Phases 2–4) ≤ `DR_DRILL_RTO_BUDGET_S` (default 1800) |
| V7 | RPO: export age at restore ≤ 26 h |

Never use `-o jsonpath` on a Secret, `kv get`, or any printed value. Use `kubectl describe secret` where a Secret must be checked, because a failing template dumps raw data.

### D6 — Rules and alerts, kept in GitHub

- **Metrics:** push to the hub Pushgateway as job `k3dm_dr_drill`, with `last_run_timestamp_seconds`, `success`, `rto_seconds`, `rpo_seconds` and `check_ok{check}`.
  - The M2 reaches the Pushgateway only over the local network. When that push fails, the result still lands in the data repo, and the M4 side republishes it on its next `hub-data-export`.
- **PrometheusRules in git, synced by ArgoCD:** `DRDrillFailed` and `DRDrillStale` (`> 8*86400`), warning, email only. Put them in the same file and AppSet as the existing Pushgateway-job rules (§7 L6).
- **Independent check in GitHub:** `.github/workflows/drill-freshness.yml` in `k3dm-hub-data`.
  - It runs daily on schedule with `permissions: contents: read`, actions pinned by tag.
  - It fails when the newest `results/*.json` is older than 8 days or reports `success: false`.
  - GitHub's failed-workflow email is the alert. It needs no M4, no Vault and no secret.

### D7 — Cadence and the real-hub drill

- **Weekly, attended:** `make hub-data-export` on the M4, then `make dr-drill` on the M2. About 30 minutes. Nothing runs unattended; that would need looser Keychain access, which is refused.
- **Also export automatically before any `DELETE_HUB=1` teardown.** `bin/cluster-down` refuses `DELETE_HUB=1` unless an export ≤ 24 h old exists, or `DR_SKIP_EXPORT_CHECK=1` is set.
- **Quarterly real-hub drill (manual runbook):** `make hub-recover` on the M4, then `hub_data_restore` into the real hub. This is the only test of the tunnel, port-forwards, launchd agents and cluster registrations.

## 5. Gates (offline; stubs only — Codex never runs k3d, docker, kubectl, ssh, git push, security or age for real)

1. **Phase order.** The call log shows phases 1–6 in order. Teardown runs when Phase 4 fails.
2. **Name and host guards.** `DR_DRILL_CLUSTER=k3d-cluster` gives exit 2 with no `k3d` call. A stub `hostname` returning the M4 gives exit 2.
3. **Isolation.** Every `kubectl` call carries the drill kubeconfig/context. There is no `config use-context`. A deny-list grep finds no `hub-restore`, `hub_recovery_reconcile`, `install-*-port-forward`, `launchctl` or cloudflared in `bin/dr-drill`.
4. **Node gate.** A stub targets output that puts Vault on `agent-1` (expected `server-0`) aborts before any `_hub_recovery_restore_one` call.
5. **Export contents.** The stub export dir has no `state.db` and no `kind: Secret`. Every claim file ends in `.age`. `SHA256SUMS` covers only encrypted files. No file is over 95 MB after the split.
6. **No plaintext.** A stub shard and identity sentinel string never appears in argv logs, stdout, stderr or the stage. `security -w` output is piped, never assigned to a variable that is echoed.
7. **Root token lifetime.** The call log shows `generate-root` before `kv list`, and `token revoke -self` after it, including on the failure path.
8. **Freshness workflow.** `actionlint` is clean. The script part, run against fixture `results/` (fresh, 9 days old, `success: false`), gives exit codes 0, 1 and 1.
9. **`DELETE_HUB` export guard.** `bin/cluster-down` with `DELETE_HUB=1` and no recent export gives exit 2 and no `k3d cluster delete`.
10. **Mutations.** For each, snapshot with `cp`, mutate, show the test red, restore from the snapshot, confirm with `cmp`:
    - (a) remove the name guard → gate 2 red;
    - (b) drop the `EXIT` trap → gate 1 red;
    - (c) skip the node gate → gate 4 red;
    - (d) drop the `age` encryption on one claim → gate 5 red.
11. **Other checks:** shellcheck clean; `make check-doc-links` passes; the diff touches only the D1–D8 files.

**The first live drill is run by Claude and the operator, never Gemini,** with `DR_DRILL_KEEP=1`. Record the measured RTO/RPO in the how-to.

## 6. What NOT to do

- No change to `hub_recovery_restore`, `_hub_recovery_validate_files`, `_hub_recovery_records` or `hub_snapshot_capture`. Wrap them; don't fork them.
- No plaintext data, `state.db` or Kubernetes Secret in git. No `age` identity on the M4. No root token stored anywhere.
- No unattended run. No new Keychain ACL widening, and no `security set-generic-password-partition-list`.
- No force-push anywhere except `k3dm-hub-data`'s `snapshots` branch.
- No PR, no commit to `main`, no `--no-verify`. No edits to `scripts/lib/foundation/` or `scripts/lib/acg/`.

## 7. Live checks — Claude resolves these, read-only, before dispatch

- **L1 — Shard source.** Confirm the hub's `vault-unseal` Secret still holds the shard data, by key **names** only through `kubectl describe secret`. Confirm Vault's key-share and threshold count.
- **L2 — `selected-node`.** Confirm the hub's `local-path` provisioner version honours a pre-set `volume.kubernetes.io/selected-node` annotation, and check how the 2026-09-11 restore satisfied the node match.
- **L3 — M2 readiness.** Docker, k3d and `age` are installed on the M2, and the repo is checked out there. Check its RAM and free disk. The M2 is already the e2e runner (`E2E_M2_SSH_HOST`).
- **L4 — M2 capacity.** On the first run, measure memory with the drill hub up. If it's tight, use a 1-server + 2-agent drill hub, and update the node map in D3 to match.
- **L5 — Results write path.** Choose between an M2 deploy key with write access to `k3dm-hub-data` only, or the operator pushing the result. The operator decides.
- **L6 — Rules home.** Find the file and AppSet that hold the existing Pushgateway-job PrometheusRules (for example, the `k3dm_test_*` rules).
