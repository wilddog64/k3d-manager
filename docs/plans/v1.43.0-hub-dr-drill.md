# v1.43.0 — Weekly hub disaster-recovery drill

**Status:** PLAN — written 2026-10-03; resolve the open questions (§6) before dispatching to Codex
**Branch:** `k3d-manager-v1.43.0` (not yet created)
**Release count:** 1 of 5 for v1.43.0

## 1. Goal

On 2026-10-03 the hub was deleted by a sandbox teardown. Recovery took hours. The gaps were only found under pressure:

- the Keycloak stack and its Vault paths existed only on the sandbox path;
- the embeddings key's Vault copy was gone;
- a root-owned logs folder silently stopped the Grafana port-forward;
- every ArgoCD API token was invalidated;
- a full VectorDB re-index took 40+ minutes.

The guards against a repeat landed in v1.41.0:

- `make down` keeps the hub unless `DELETE_HUB=1` (`435c95a1`);
- `hub-up` refuses a non-hub context (`ed22bda9`);
- one-command `make hub-recover` (`fb71deb4`).

This plan adds the missing piece: **proof, every week, that hub data comes back quickly and completely.** The operator's requirement (2026-10-03): *"we are not necessarily snapshot image but we need to be able to restore data quickly without issue."*

The deliverable is a planned, repeatable drill. It restores the hub's **data** into a throwaway drill hub, verifies it, measures how long that took and how much was lost, records the result as metrics, and tears the drill hub down. **The real hub is never touched** except by a read-only capture.

## 2. What exists today (measured, not assumed)

### Two restore paths

| Path | Pieces | Restores | Gap |
|---|---|---|---|
| **A. Credentials** | `make hub-up` + `bin/hub-restore` | Keychain-backed items: Alertmanager SMTP, signing key, `platform-ops` Secrets, tunnel config, local agents | No user data. Keycloak users, LDAP entries and any Vault KV not mirrored in Keychain are regenerated, not restored. That regeneration is the 2026-09-29 credential-drift class. |
| **B. Data** | `hub_snapshot_capture` (v1.36.0) → M2 store; `hub_recovery_targets` + `hub_recovery_restore … --confirm` (v1.33.0, executed 2026-09-11) | The 8 local-path claims in `_hub_recovery_records`: Vault, postgres-keycloak, the 3 LDAP claims, trivy, Prometheus, Loki | Never scheduled; no snapshot existed on 2026-10-03. The restore is a multi-step manual procedure (`docs/plans/v1.33.0-hub-local-path-restore.md`). |

### Facts the design depends on

- `make snapshot` → `hub_snapshot_capture`:
  - it is read-only against the hub (`docker cp` of node trees plus `kubectl get`);
  - it rsyncs to `K3DM_SNAPSHOT_HOST` (default `m2jump`) over SSH and verifies `SHA256SUMS`;
  - a snapshot is about 2.15 GB, mostly Prometheus.
- `hub_recovery_targets <context>` and `hub_recovery_restore <dir> <targets.tsv> --confirm` already take a context and arbitrary node hostnames. `_hub_recovery_logical_node` matches by suffix (`*-agent-0`), so a cluster named `dr-drill` resolves.
- The snapshot's `server-db/state.db` is the k3s datastore. It contains every Secret in plaintext, including `vault-unseal` and `vault-root`, so **the M2 snapshot store is secret material.**
- `scripts/etc/cluster.yaml.tmpl` sets `switchCurrentContext: true`, and the loadbalancer binds `HTTP_PORT`/`HTTPS_PORT` (defaults 8089/8443). A second k3d cluster on the M4 must override both, or it takes the operator's context and collides on ports.
- Single-instance resources the drill must never touch:
  - LaunchAgents keyed by fixed labels: `vault-port-forward` (`:18200`), `grafana-port-forward` (`:3001`), `hub-pushgateway-port-forward`, `cloudflare-tunnel`;
  - the three root browser LaunchDaemons;
  - the Cloudflare tunnel;
  - ArgoCD cluster registrations for `ubuntu-k3s` and `ubuntu-hostinger`. Two ArgoCDs managing one cluster is a split-brain.

## 3. Design

### D1 — `make dr-drill` → `bin/dr-drill` (new, `set -euo pipefail`)

Phases, each logged as `[dr-drill] Phase N/7 — …` and timed:

1. **Preflight.** Exit 2 when any of these fails:
   - an interactive TTY;
   - the M2 snapshot host is reachable (`_hub_snapshot_ssh true`);
   - no leftover `k3d-${DR_DRILL_CLUSTER}` cluster exists;
   - free Docker disk ≥ 10 GB;
   - the real hub context `k3d-k3d-cluster` answers.

   Record the operator's current kube context, to restore in Phase 7.
2. **Capture.** Run `hub_snapshot_capture` against the real hub. This is the weekly snapshot, so the drill also fixes "never scheduled". Record the snapshot timestamp as the RPO anchor.
3. **Build the drill hub.**
   - Run `HUB_CLUSTER_NAME=${DR_DRILL_CLUSTER:-dr-drill} bin/hub-up` with `HTTP_PORT`/`HTTPS_PORT` overridden (defaults 18089/18443).
   - Make sure context switching is off for this create (see §6 Q4), so the operator's current context is never changed.
   - `hub-up`'s current-context guard must accept the drill context **only** when `DR_DRILL=1`; the default behaviour stays unchanged.
4. **Restore data.**
   - Copy the snapshot from M2 to a `mktemp -d` stage with mode 700. Verify `SHA256SUMS`.
   - Run `hub_recovery_targets k3d-${DR_DRILL_CLUSTER}` and write the targets file into the stage.
   - Scale the stateful consumers to 0, run `hub_recovery_restore <stage> <targets> --confirm`, then scale back up.
   - **Critical claims only:** Vault, postgres-keycloak and the 3 LDAP claims. Skip trivy, Prometheus and Loki in the drill; they are history or cache and would double the M4's memory load. Implement the skip as a drill-only filter on the claim list, not as a change to `_hub_recovery_records`.
   - Unseal Vault per §6 Q1.
5. **Verify.** Run the checklist in D3 and record PASS/FAIL per item.
6. **Report.**
   - Write `~/.k3dm/dr-drill/<ts>.json` and a human summary table containing: per-phase seconds, total RTO, snapshot age at restore (RPO), and pass/fail per check.
   - Push the metrics in D4.
7. **Teardown, always,** from an `EXIT` trap:
   - `k3d cluster delete ${DR_DRILL_CLUSTER}`, scoped by an exact name equality check. It must refuse `k3d-cluster`; there is a test for this.
   - `rm -rf` the stage.
   - Restore the operator's original kube context, and remove the drill kubeconfig entries.

   `DR_DRILL_KEEP=1` skips the delete, for debugging a failure. It prints the exact delete command instead.

### D2 — Isolation guards (each one is a test)

- **The drill cluster name must differ from the real hub.** `DR_DRILL_CLUSTER` equal to `k3d-cluster`, or empty, makes the drill exit 2 before Phase 1.
- **No singletons.** The drill never calls `bin/hub-restore`, `hub_recovery_reconcile`, `install-*-port-forward`, `launchctl`, the cloudflared helpers or ArgoCD cluster registration. Enforce this with a deny-list grep test over `bin/dr-drill`.
- **The drill never changes the operator's current context.** A stub test asserts the drill makes no `config use-context` call that isn't the final restore of the original context.
- **The only write to the real hub's context is none.** Every `kubectl` call in Phases 3–5 carries `--context k3d-${DR_DRILL_CLUSTER}`.

### D3 — Verify checklist (the drill's acceptance contract)

| # | Check | How |
|---|---|---|
| V1 | Vault unsealed and serving | `vault status` in the drill pod: `Sealed false` |
| V2 | Vault KV restored | Path **list** only (`vault kv list`), never values. Every path in a committed inventory `scripts/etc/dr-drill/vault-paths.txt` exists. Diff against the real hub's list, captured in Phase 2. |
| V3 | Keycloak data restored | the realm exists; the user **count** for the realm equals the real hub's count from Phase 2 |
| V4 | LDAP data restored | entry **count** under the base DN equals the real hub's count |
| V5 | Stateful pods healthy | vault-0, postgres-keycloak, openldap-0 are Ready within 300 s |
| V6 | RTO within budget | total for Phases 3–5 ≤ `DR_DRILL_RTO_BUDGET_S` (default 1800) |
| V7 | RPO | snapshot age at restore ≤ 1 h, which shows Phase 2 ran this drill |

Rules for the checks:
- Comparisons use counts and path names only. No Secret value, KV value, password or token is read, printed or logged. Use `kubectl describe secret`, never `-o jsonpath` on a Secret, because a failing template dumps raw data.
- V2's inventory file is the explicit list of what the hub must hold. A path that exists on the real hub but is missing from the inventory is reported as **UNLISTED**: a warning that the inventory is stale, not a failure.

### D4 — Metrics and alerts

- Push to the hub Pushgateway, job `k3dm_dr_drill`:
  - `k3dm_dr_drill_last_run_timestamp_seconds`;
  - `k3dm_dr_drill_success` (0/1);
  - `k3dm_dr_drill_rto_seconds`;
  - `k3dm_dr_drill_rpo_seconds`;
  - `k3dm_dr_drill_check_ok{check="V1".."V7"}`.
- PrometheusRules in the existing hub rules location (resolve the file per §6 Q5):
  - `DRDrillFailed`: `k3dm_dr_drill_success == 0`, warning;
  - `DRDrillStale`: `time() - k3dm_dr_drill_last_run_timestamp_seconds > 8*86400`, warning, email only.
- A Grafana row on an existing ops dashboard: last result, RTO trend, RPO, and the per-check table.

### D5 — Cadence and the real-hub drill

- **Weekly, operator-attended.** It needs a TTY and the M2 reachable, and takes about 30 minutes. `DRDrillStale` is the reminder; nothing runs unattended, because unattended runs would mean loosening Keychain access, which is refused.
- **Quarterly real-hub drill (manual runbook, no automation):**
  - `make hub-recover` against the real hub at an operator-chosen time, followed by the data restore from the latest snapshot.
  - This is the only exercise of the singletons D2 excludes: port-forwards, tunnel, launchd agents and registrations.
  - The runbook lives in the doc in D6.

## 4. Gates (offline; stubs only — Codex never runs k3d, docker, kubectl or ssh for real)

1. **Phase order.** With stub `k3d`, `kubectl`, `docker`, `ssh`, `rsync` and dispatcher on `PATH`, plus a temp `HOME`, the call log shows phases 1–7 in order. Teardown runs even when Phase 5 fails.
2. **Name guard.** `DR_DRILL_CLUSTER=k3d-cluster` gives exit 2, and the log has no `k3d cluster` call.
3. **Context.** No `config use-context` call except the final restore of the original context. Every Phase 3–5 `kubectl` call carries `--context k3d-dr-drill`.
4. **Deny-list.** `bin/dr-drill` contains none of the singleton calls in D2.
5. **Claim filter.** The restore call covers exactly the 5 critical claims. `_hub_recovery_records` is byte-identical to before.
6. **No values.** The stub `kubectl`/`vault` calls never include `-o jsonpath` on a Secret or `kv get`. The output contains no stubbed secret sentinel string.
7. **Report.** A run with V3 failing writes JSON with `success: 0` and `V3: FAIL`, and pushes `k3dm_dr_drill_success 0`.
8. **Mutations.** For each, snapshot with `cp`, mutate, show the test red, restore from the snapshot, confirm with `cmp`:
   - (a) remove the name guard → gate 2 red;
   - (b) drop the `EXIT` trap → gate 1 red;
   - (c) drop `--context` from one Phase 4 call → gate 3 red.
9. **Other checks:** shellcheck clean; `make check-doc-links` passes; `git diff --stat` shows only the D1–D6 files.

**First live drill: Claude and the operator, never Gemini.** Run with `DR_DRILL_KEEP=1` so a failure can be inspected. Record the measured RTO/RPO in the how-to.

## 5. What NOT to do

- No change to `hub_recovery_restore`, `_hub_recovery_records` or `hub_snapshot_capture` logic. Wrap them; don't fork them.
- No unattended or cron run. No new Keychain ACL, and no `security set-generic-password-partition-list`.
- No public or remote exposure of the drill hub. The kube API stays on `127.0.0.1`.
- No PR, no commit to `main`, no `--no-verify`. No edits to `scripts/lib/foundation/` or `scripts/lib/acg/`.

## 6. Open questions — Claude resolves these, read-only and live, before dispatch

- **Q1 — Unseal source for a restored Vault.**
  - The drill hub's fresh `deploy_vault` creates new unseal keys. The restored `data-vault-0` needs the **old** ones.
  - `vault.sh` caches shards in Keychain (`k3d-manager-vault-unseal`) but clears them after a successful unseal (`vault.sh:473`).
  - The snapshot's `state.db` holds the old `vault-unseal` Secret.
  - Decide how the drill gets the old shards without printing them. Options: export `vault-unseal` and `vault-root` from the real hub into the stage in Phase 2, through a pipe into a `kubectl apply` on the drill context only; or restore `state.db` per the v1.33.0 kine procedure.
  - This decides whether Phase 4 is a PVC-only restore or a datastore restore.
- **Q2 — Node affinity.**
  - `hub_recovery_targets` requires each claim's new PV to sit on the same logical node as in the snapshot. `local-path` binds on first schedule, so the drill hub may place Vault on a different agent.
  - Check how the 2026-09-11 restore met this, then pin the drill's stateful workloads (nodeSelector by logical node) or pre-create PVs.
- **Q3 — Snapshot store during a local network outage.**
  - The store is the M2 over SSH (`m2jump`), so during an M2↔M4 local-network outage, capture and restore both fail.
  - Decide whether that is acceptable (the drill simply reports preflight FAIL) or whether to add a second, encrypted store. The plaintext Secrets in `state.db` rule out any unencrypted cloud store.
- **Q4 — Context switch.** Confirm how to make `deploy_cluster --provider k3d` skip `switchCurrentContext` for the drill only: an env override in the template, or `k3d --kubeconfig-switch-context=false` passthrough. Keep the real hub's default.
- **Q5 — Rules home.** Find where hub PrometheusRules for Pushgateway jobs live today, for example the `k3dm_test_*` rules, and use the same file.
- **Q6 — Memory.** Measure M4 memory with both clusters up (hub plus a 4-node drill hub with 3 claims' workloads). If it's tight, make the drill hub 1 server + 2 agents, and adjust Q2 to match.
