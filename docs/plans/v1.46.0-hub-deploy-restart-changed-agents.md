## Problem

`make hub-deploy REF=<sha>` (`bin/k3dm-hub-deploy`) moves `deploy/hub`, catches the hub checkout up, reapplies
appsets and platform-ops, and reinstalls only launchd agents whose `scripts/etc/launchd/com.k3d-manager.*.plist.tmpl`
changed (`bin/k3dm-hub-deploy` ~215-300). The webhook (`com.k3d-manager.webhook`, `KeepAlive`, Python
`bin/k3dm-webhook`) and the cloud bridge (`com.k3d-manager.cloud-bridge`, `KeepAlive`, Python `bin/k3dm-cloud-bridge`)
load their code once at start, so a promote that changes their code reports success while the hub keeps serving the
old code. Seen 2026-11-22 (`/hostinger-status` still listed) and 2026-11-27 (unrouted-notices fix `35d42bc8` not live
until `make restart-webhook`).

## Behaviour

1. **Detect.** After the checkout step, hub-deploy computes `git diff --name-only <last-restarted> <new>` and decides
   whether the webhook/bridge code changed. Watched paths (conservative; over-restart is cheap): `bin/k3dm-webhook`,
   `bin/k3dm-cloud-bridge`, and `scripts/lib/**/*.py`. `<last-restarted>` is a new state field (`agents`) next to the
   existing `appsets`/`launchd` fields; a missing field means `full` (restart).
2. **Never kill a running job.** Before restarting, hub-deploy checks the webhook job directory
   (`${K3DM_JOB_DIR:-~/.local/share/k3d-manager/webhook-jobs}`) for any job whose `status` file is `running` and whose
   directory is younger than the webhook's own stale limit (3 h, `_MAX_JOB_AGE_SECS`). If one is running it does not
   restart; it prints `hub-deploy: webhook restart pending: job <id> running; rerun make hub-deploy REF=<sha> (or make
   restart-webhook) after it finishes`, leaves `agents` at the old value so the next hub-deploy retries, and exits with
   the existing pending/retry convention (not success-silent).
3. **Restart** by the same mechanism as `make restart-webhook` (bootout + bootstrap with its retry loop; then
   `restart-cloud-bridge`). Do not duplicate the loop: call the make target or factor it into one shared script.
4. **Self-protection.** If hub-deploy is itself running under the webhook (an ancestor process is the webhook's PID,
   e.g. a future remote-promote path), it must not restart the webhook in-process; it records the restart as pending
   with the reason `deploy runs under the webhook` and prints the operator command.
5. **Confirm.** After the restart, hub-deploy waits (bounded, ≤ 30 s) until `launchctl print` shows a PID whose start
   time is after the restart began and `GET http://127.0.0.1:<port>/api/v1/health` answers; it prints
   `hub-deploy: restarted webhook (pid <n>) and cloud-bridge (pid <m>) for <old7>..<new7>`. On timeout it stops with a
   named step (`agent-restart`) and the rerun hint; `agents` is not advanced.
6. **Docs-only diffs restart nothing** and print `agents unchanged`.

## Contract readers

- repo-sync state directory (`$K3DM_REPO_SYNC_STATE_DIR`, default `~/.local/share/k3d-manager/repo-sync`): new field
  `agents`. Writers: `bin/k3dm-hub-deploy` `write_state`. Readers: `bin/k3dm-hub-deploy`, `bin/k3dm-hub-promote`
  (status output — verify by grep whether it parses the state file), `make hub-promote-status`.
- Webhook job directory `status` files: read-only new reader (hub-deploy). Writers: `bin/k3dm-webhook:542`,
  `scripts/lib/webhook/lifecycle.py:195,252,598`.
- `make restart-webhook` (`Makefile:695`): new caller (hub-deploy).

## What NOT to Do

- Do not restart any other agent (port-forwards, auth proxies, web-console, node-health-watch) in this change.
- Do not restart when a job is running; never `kill` job processes.
- No real `launchctl`, `git push`, network or Keychain in tests; stub them (fixtures assert the stubs are first on PATH).
