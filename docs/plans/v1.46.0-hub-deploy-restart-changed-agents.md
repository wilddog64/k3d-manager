## Problem

`make hub-deploy REF=<sha>` (`Makefile:546` → `bin/k3dm-hub-deploy`) moves `deploy/hub`, catches the hub checkout up,
reapplies appsets and platform-ops, and reinstalls only launchd agents whose
`scripts/etc/launchd/com.k3d-manager.*.plist.tmpl` changed (`bin/k3dm-hub-deploy:216-300`). The webhook
(`com.k3d-manager.webhook`, `KeepAlive`, `bin/k3dm-webhook`) and the cloud bridge (`com.k3d-manager.cloud-bridge`,
`KeepAlive`, `bin/k3dm-cloud-bridge`) import their Python once at start, so a promote that changes their code reports
success while the hub keeps serving the old code. Seen 2026-11-22 and 2026-11-27 (`35d42bc8` not live until
`make restart-webhook`).

## Proven facts (read-only captures; cite these, do not re-derive)

- **Hub webhook startup is sub-second.** m5 (`m5-air.local`), 2026-11-27, Claude over ssh: `launchctl print
  gui/<uid>/com.k3d-manager.webhook` → `pid = 2505`, `ps -o lstart=` → `Thu Nov 26 19:51:32 2026` (03:51:32Z);
  `~/Library/Logs/k3dm-webhook.log:5264` → `2026-11-27T03:51:32Z INFO webhook listening on 127.0.0.1:7443` (same
  second). Earlier restarts logged the same line (`:4593` 00:17:29Z, `:4693` 01:02:55Z). Cloud bridge `pid = 2511`.
- **`launchctl print` shows `pid = <n>` and no start time** (`bin/k3dm-webhook-doctor:98`); it also prints the job's
  environment, including `K3DM_WEBHOOK_PORT => <n>` when set (`bin/k3dm-webhook-doctor:83-91`). Default port 7443
  (`scripts/lib/webhook/config.py:14`).
- **An unauthenticated `GET /api/v1/health` answers 401 without running anything**: `do_GET` calls `self._auth()`
  before routing (`bin/k3dm-webhook:2967-2970`). The authenticated form runs the full smoke test
  (`scripts/lib/webhook/smoke.py:566-741`, 3 retries × 10 s) and needs a Keychain token — never use it here.
- **Active jobs are `queued` or `running`.** `ask`, `cluster-refresh` and `cluster-diagnostics` stay `queued` for their
  whole run (up to 400 s; `scripts/lib/webhook/agent.py:364,624`, `lifecycle.py:534-580`, `status.py:457-558`); make
  jobs start `queued` (`bin/k3dm-webhook:2888`). `bin/k3dm-hub-sync:27-39` already refuses on a `queued`/`running`
  status file whose mtime is under 10800 s old — reuse that rule exactly.
- **On startup the webhook marks leftover `running` jobs `failed` and posts an orphan notice**
  (`_clear_stale_jobs`, `bin/k3dm-webhook:1767-1792`); it does not clear `queued`.
- **The only caller of `bin/k3dm-hub-deploy` is `make hub-deploy`** (`Makefile:546`, operator); no webhook or bridge
  path runs it (`hub-deploy` is not in `scripts/lib/webhook/make_targets.py` `MAKE_TARGETS` nor in
  `bin/k3dm-cloud-bridge:26` `ACTION_ALLOWLIST`). `make hub-rollback` runs only `bin/k3dm-hub-promote rollback`.

## Behaviour

1. **State field.** Add an optional `agents <sha>` line to `$HOME/.local/share/k3d-manager/hub-deploy/state`
   (`STATE_DIR`, `bin/k3dm-hub-deploy:33`). Internal variable `agents`, empty meaning "full restart owed".
   - `valid_state` (`:61-82`) accepts at most one `agents` line whose value is a commit sha that `git cat-file -e`
     resolves; a duplicate, `full`, or unresolvable value fails `valid_state` as any malformed line does today. A file
     with no `agents` line stays valid and sets `agents=''`.
   - `write_state` (`:54-60`) writes the `agents` line **only when `agents` is non-empty**, after the `launchd` line and
     before `pending` lines. So every existing reset path (`:92-97`, `:138-141`) and the first-run `--approval` file
     asserted at `scripts/tests/bin/hub_deploy.bats:912` stay byte-for-byte as today, and lost state means a restart.
2. **Where it runs.** A new `agent-restart` block after the launchd loop (after `:300`) and before the summary
   (`:301-305`), in whichever copy reaches that point (the promoted copy after the stage2 handoff at `:176-182`).
3. **Decide** (first match wins; each sets a short result word used in the summary):
   - **not installed** — `$HOME/Library/LaunchAgents/com.k3d-manager.webhook.plist` absent: no restart, print
     `hub-deploy: agents: webhook not installed on this host; skipping`, set `agents=$new`. (Every existing test runs
     without that plist, so the existing suite takes this branch.)
   - **unchanged** — `agents` non-empty and `git diff --quiet --no-renames "$agents" "$new" -- bin/k3dm-webhook
     bin/k3dm-cloud-bridge scripts/lib/webhook/ scripts/lib/hermes/` exits 0: print `agents unchanged between <a7> and
     <n7>`, set `agents=$new`. Exit 1 means changed; any other exit → `stop agent-diff <code>`. Empty `agents` means
     changed (`full`).
   - **deferred: agent load disabled** — `K3DM_AGENT_LOAD=0`.
   - **deferred: checkout** — one `take_lock && checkout_ok` attempt fails (reason `hub checkout is not at <n7> with a
     clean tracked tree`). On success the repo-sync lock is held through the restart and confirmation, then released.
   - **deferred: active job** — checked **last, immediately before the restart**: any
     `${K3DM_JOB_DIR:-$HOME/.local/share/k3d-manager/webhook-jobs}/*/status` whose trimmed content is `queued` or
     `running` and whose mtime is ≥ now − 10800 (same rule and `stat -f %m` / `stat -c %Y` fallback as
     `bin/k3dm-hub-sync:27-39`). Reason `webhook job <id> is <state>`.
   - otherwise **restart**.
4. **Restart.** Record `old_w` / `old_b`: the numeric `pid` from `launchctl print gui/<uid>/com.k3d-manager.webhook`
   and `…cloud-bridge` (empty if not loaded or the bridge plist is absent). Run
   `_run_command --soft -- env -u K3DM_AGENT_LOAD make --no-print-directory -C "$REPO_ROOT" restart-webhook 9>&-`
   exactly once. That target already does the role check, bootout, a 5-try bootstrap and `restart-cloud-bridge`
   (`Makefile:695-712`); do not call `restart-cloud-bridge` separately and do not edit the `Makefile`.
5. **Confirm**, bounded by `K3DM_HUB_DEPLOY_AGENT_WAIT` seconds (default 30), polling once a second:
   - the webhook `pid` is numeric and differs from `old_w`;
   - if the bridge plist exists, the bridge `pid` is numeric and differs from `old_b`;
   - `curl -sS -o /dev/null -w '%{http_code}' --max-time 2 "http://127.0.0.1:<port>/api/v1/health"` prints `401` or
     `200`, where `<port>` is `K3DM_WEBHOOK_PORT => <n>` from the webhook's `launchctl print` (validated 1–65535),
     else `${K3DM_WEBHOOK_PORT:-7443}`. No token, no `Authorization` header, no `?quick` needed.
   On success print `hub-deploy: restarted webhook (pid <n>) and cloud-bridge (pid <m>) for <a7|full>..<n7>` (drop the
   bridge part when its plist is absent) and set `agents=$new`, `write_state`.
6. **Failure.** If `make restart-webhook` exits non-zero or confirmation times out: do not advance `agents`; print
   `hub-deploy: webhook is <loaded (pid <n>)|not loaded>; restore it with make restart-webhook on the hub`, then
   `stop agent-restart 1` (its existing rerun hint covers `--approval`).
7. **Deferred exit.** For any deferred case: do not advance `agents`, do not call `make`, print the normal summary line,
   then on stderr `hub-deploy: agents pending: <reason>; rerun make hub-deploy REF=<ref> after it clears (or make
   restart-webhook)` — using `bin/k3dm-hub-deploy <new> --approval <id>` when `approval_id` is set — and **exit 3**.
   Exit 3 is new and means "deployed, but the webhook still runs older code". Exit 75 stays reserved (`:11`).
8. **Summary.** Append `; agents <restarted|unchanged|not installed|pending>` to the existing summary line (`:303`);
   every current assertion on that line is a substring match (`hub_deploy.bats:243,314,436`) and stays green.

## What NOT to Do

- Do not edit the `Makefile`, `bin/k3dm-webhook`, `bin/k3dm-cloud-bridge` or `bin/k3dm-hub-sync`.
- Do not restart any other agent. `com.k3d-manager.hermes` is excluded on purpose: it is `StartInterval` 300
  (`scripts/etc/launchd/com.k3d-manager.hermes.plist.tmpl:32-33`) and loads new code on its next run.
- No ancestor/self-protection check (no webhook path can run hub-deploy today; captured in `docs/ideas.md`).
- Never `kill` job processes; never read a Keychain item or send an `Authorization` header.
- Do not change existing assertions in `hub_deploy.bats`, `restart_webhook.bats`, `test_restart_cloud_bridge.py` or
  `require_role.bats`.
- Tests: no real `launchctl`, `curl`, `make`, network, port 7443 or real job dir. Extend the suite's `launchctl` stub
  (`hub_deploy.bats:154`) so `print gui/<uid>/com.k3d-manager.{webhook,cloud-bridge}` emits `pid = <n>` (and
  optionally `K3DM_WEBHOOK_PORT => <n>`) from fixture files, shaped from the m5 capture above (put host and date in a
  comment); add a `curl` stub that records its arguments and prints a fixture code; teach the `make` stub
  `restart-webhook` (record the call, check `-e /dev/fd/9` is false and the repo-sync lock is held, bump fixture pids).
  Setup sets `K3DM_JOB_DIR` to a temp dir and `K3DM_HUB_DEPLOY_AGENT_WAIT=0`/small, and asserts the stubs are first on
  `PATH` and that `K3DM_JOB_DIR` is under `$BATS_TEST_TMPDIR`.

**Accepted residual risks (in writing):** a job submitted in the second between the active-job check and `bootout` is
lost, and the webhook's startup sweep reports it; a bridge request mid-call when `restart-cloud-bridge` kills the
bridge becomes "bridge restarted before the request completed" via `_recover_orphaned_claims`
(`bin/k3dm-cloud-bridge:273-290`); an orphaned `queued` file from a crashed webhook defers restarts for up to 3 h —
override with `make restart-webhook`. hub-deploy refuses to restart under a fresh active job, so it does not depend on
whether `bootout` kills `setsid` job children.
