No new runtime dependency: stdlib `urllib`/`json`/`subprocess` only (same posture as the webhook). Do NOT add `requests`/third-party HTTP libs.

- **Modules:** `scripts/lib/hermes/` — `sensors.py` (WS1), `correlator.py` + `slack.py` (WS2), `records.py` (the normalized record type + status enum). Keep each importable and side-effect-free at module load so tests can stub inputs.
- **Tests:** `scripts/tests/hermes/` — pytest, stubbed inputs only (no live cluster, no network). Mirror the existing "pure logic, no cluster mocks" rule: sensors take an injected fetch callable so tests feed canned JSON.

## Credential access (read-only, off-hub — from WS0)

All three come from laptop Keychain at runtime; NEVER read into argv, NEVER logged, NEVER committed:

- **Webhook bearer** — `security find-generic-password -a k3dm -s k3dm-webhook-token -w` → `Authorization: Bearer` on `GET https://<webhook-host>:7443/api/v1/health?provider=<p>`. GET-only.
- **ArgoCD hermes token** — `security find-generic-password -a k3dm -s k3dm-hermes-argocd-token -w` → `ARGOCD_AUTH_TOKEN` env for `argocd app list -o json --grpc-web` (server `argocd.3ai-talk.org`). get-only (WS0-verified: sync/delete denied server-side).
- **GitHub PAT** — `security find-generic-password -a k3dm -s k3dm-hermes-gh-token -w` → `Authorization: token` on `api.github.com` Actions read endpoints. Read-only.

Load each once per cycle via a single `_keychain_secret(service)` helper that shells `security ... -w` through `subprocess` (no secret in argv of the agent's own commands; `security` reads the item by name). If a secret is absent, the dependent sensor emits `unknown` with `evidence="credential unavailable: <service>"` — never crash the whole cycle.

## WS1 — Sensor set

### Normalized record (records.py)

Every sensor returns exactly this shape (constraint: uniform so the correlator is source-agnostic):

```python
{
  "sensor":     "eso" | "argocd" | "reachability" | "node_pressure" | "ci",
  "status":     "healthy" | "degraded" | "unknown",
  "evidence":   "<short human string — the specific failing entity + detail>",
  "sampled_at": "<UTC ISO-8601, e.g. 2026-09-05T12:34:56Z>",
}
```

- `status` is a 3-value enum. `unknown` is mandatory whenever the authoritative source is unavailable (webhook down / `ok: null` / credential missing / API 5xx) — Hermes reports "status source unavailable", never a fabricated `healthy`/`degraded` (scope constraint 2).
- `evidence` names the specific entity (e.g. `ESO ExternalSecrets 3/7 synced`, `shopping-cart-order Degraded/OutOfSync`, `edge-down 0/4 hosts healthy`), truncated to ≤200 chars.

### Sustained-signal debounce (all sensors)

A single flap must NOT flip a sensor to `degraded`. Each sensor keeps a rolling window of its last `N` raw samples (persisted to a small on-disk state file under the agent's run dir, e.g. `~/.k3dm/hermes/state.json`) and only emits `degraded` when the degraded condition holds for **> threshold consecutive cycles**:

- (a) ESO: `> 2` cycles (matches scope §3 "SecretSyncedError sustained > 2 cycles").
- (b) ArgoCD: `> N` cycles, default `N=3` (config).
- (c) reachability: the probe already samples internally; treat one `--json` run as one sample and require `> 2` cycles for `edge-down` (a `single-service` verdict is `degraded` immediately only if it persists `> 2` cycles too — no instant page).
- (d) node/data-layer: `> 2` cycles.
- (e) CI: a failing required check is `degraded` after `> 1` cycle (CI failures are already durable, not flappy); a check stuck `in_progress` beyond a config age is `degraded`.

Thresholds are config with the defaults above. The window state file holds only counts/booleans + timestamps — NO secrets.

### Sensor (a) — ESO sync

- Source: `GET /api/v1/health?provider=<p>` (webhook, bearer). Parse `services[]` for `name in {"ESO ClusterSecretStore","ESO ExternalSecrets"}`.
- Map: entry `ok is True` → healthy; `ok is False` → degraded candidate (evidence = the entry `detail`, e.g. `3/7 synced` or the error); `ok is None` → unknown (not installed / probe indeterminate).
- Debounce > 2 cycles for degraded.

### Sensor (b) — ArgoCD app health

- Source: `argocd app list -o json --grpc-web` with `ARGOCD_AUTH_TOKEN`/`ARGOCD_SERVER` env (hermes token).
- Per app read `.status.health.status` and `.status.sync.status`. `Degraded` (health) or `OutOfSync` (sync) sustained `> N` cycles → degraded; evidence lists the offending `project/app` names (cap the list length in evidence).
- On non-zero exit / empty / auth failure → unknown. NEVER call any mutating verb (WS0 already denies them server-side; the code must also hold no `sync`/`delete`/`patch`/`app set` path — grep-checked in DoD).

### Sensor (c) — public reachability

- Source: wrap the shipped `bin/public-endpoint-probe --json` (do NOT reimplement — parent plan §"Do not reimplement it"). Parse `verdict`.
- Map: `ok` → healthy; `single-service` → degraded (sustained > 2); `edge-down` → degraded (sustained > 2, higher severity in evidence). Probe exit 3 (usage/config) → unknown.

### Sensor (d) — node / data-layer pressure

- Source: same `/api/v1/health` payload. Read the `"Data layer"` entry and the **aggregate** of `ok is False` service entries (the 2026-09-02/03 signature manifested as multiple service failures under node CPU pressure, not a literal node metric — webhook is authoritative, NO direct node probe per scope §4/constraint 2).
- Map: `"Data layer" ok is False` OR (≥ config-threshold services `ok is False` simultaneously) sustained > 2 cycles → degraded; evidence names the failing set. `all_ok is True` → healthy. Payload unreachable / `ok: null` across the board → unknown.

### Sensor (e) — CI health

- Source: GitHub Actions read API (gh PAT). For each watched repo (`wilddog64/k3d-manager`; add `shopping-cart-infra` only if configured), read the latest run(s) on the default branch and required check-run conclusions via `GET /repos/{o}/{r}/commits/{sha}/check-runs` (or `/actions/runs`). Read-only.
- Map: a required check `conclusion in {failure,timed_out,cancelled}` → degraded (> 1 cycle); `status=in_progress` older than config age → degraded (stuck); all required checks `success` → healthy. API 403/5xx / rate-limited → unknown.

## WS2 — Correlator + Slack summary

### Correlator (correlator.py)

- Input: the list of sensor records from one cycle (source-agnostic).
- **Fire condition (deterministic, in code — NOT an LLM decision):** emit ONE summary ONLY on **sustained multi-signal** degradation — `≥ 2` sensors `degraded` within the same correlation window (config `correlation_window`, default 3 cycles). A single degraded sensor, however severe, does NOT fire (Phase-1 is advisory, not a per-flap pager).
- **Incident signature:** include the correlated shape in the summary, e.g. `eso degraded + node_pressure degraded + reachability edge-down` → the 2026-09-02/03 signature. The summary lists each contributing sensor's `evidence` + `sampled_at`.
- `unknown` sensors are reported as "source unavailable" in the summary context but do NOT count toward the multi-signal threshold (an unknown is not a degraded — constraint 2).
- De-dupe: once fired for an active correlated incident, do not re-fire every cycle; emit a single "resolved" note when the multi-signal condition clears. Track active-incident state in the same state file (no secrets).

### Slack (slack.py)

- Reuse the EXISTING relay path (webhook Slack integration / `make update-webhook-slack*` config). Read-only POST of a summary message to the ops channel. NO command surface, NO interactive actions (Phase-1 advisory).
- The Slack webhook/signing config comes from the existing Keychain entries (`k3dm-slack-webhook`, `k3dm-slack-signing-secret`) — reuse, do not mint new.

### LLM routing (constraint 4)

- Deterministic correlation stays in code. Call an LLM ONLY when the multi-signal threshold trips, to phrase the human summary / suggest a likely root cause from the evidence.
- **Default provider: non-Claude** (config; e.g. the existing Gemini path used by the webhook analyze route). **Claude is verify-only**, never the default author.
- **Per-day budget:** hard cap on LLM calls/day (config, default small e.g. 10), enforced in code with a persisted counter in the state file. When the budget is exhausted, fall back to the deterministic template summary (no LLM) — Hermes still fires, just without LLM phrasing.

### WS2 DoD

- [ ] Correlator emits a summary on a SIMULATED multi-signal incident (≥2 degraded in-window) and stays SILENT on single-sensor flaps — both unit-tested.
- [ ] `unknown` does not count toward the threshold — tested (2 unknown + 0 degraded → silent).
- [ ] De-dupe + resolved-note tested (fire once, silent while active, one resolved note on clear).
- [ ] LLM budget enforced: call count capped per day, budget-exhausted falls back to deterministic summary — tested with a stubbed LLM callable (no real LLM call in tests).
- [ ] `grep` proves NO mutation path in the correlator/slack modules (same grep as WS1 DoD, extended to `scripts/lib/hermes/correlator.py scripts/lib/hermes/slack.py`) → 0 matches.
- [ ] Slack post path is POST to the relay only; no other outbound mutation. The GitHub PAT and ArgoCD token are never used for writes (already denied, plus grep-clean).
- [ ] `python3 -m py_compile` clean; pytest green.
