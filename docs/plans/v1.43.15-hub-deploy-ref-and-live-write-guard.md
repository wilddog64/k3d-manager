## Problem

A release branch is not isolated from the running hub:

1. **ApplicationSets read the release branch.** `make appsets-reapply` renders every ApplicationSet with
   `K3D_MANAGER_BRANCH=<release branch>` (`Makefile` `appsets-reapply`; `scripts/plugins/argocd.sh`
   around line 1289). The CLAUDE.md release rule reapplies them during development so live checks see a
   fix, so every push to the branch syncs to the hub. The 2026-11-07 Bugs-dashboard crash (fixed in
   `73120c90`) reached the live hub this way.
2. **`make platform-ops` applies the working tree.** `deploy_argocd_platform_ops` runs
   `_kubectl apply -f "${_dir}/…"` on files in the checkout, so uncommitted edits go live.
3. **Nothing records what the hub runs.** There is no ref or log that says which commit the hub was given,
   so there is nothing to roll back to.

## Design

### H1 — `deploy/hub` is the only ref the hub reads

- A branch `deploy/hub` on `origin`. It is never committed to; it only moves to an existing commit.
- `make appsets-reapply` always renders ApplicationSets with `K3D_MANAGER_BRANCH=deploy/hub`, for both the
  `hub` and `app-cluster` stages. `BRANCH=` and the release-branch check are removed from this target.
  `APPSETS_STAGE=hub` staging is unchanged.
- `make appsets-check` checks against `deploy/hub` by default.
- **Bootstrap (no live change):** the first `hub-promote` points `deploy/hub` at the commit the hub reads
  today, which is the head of the branch `make appsets-check` reports. Only then are the sets reapplied with
  `deploy/hub`, so the content the hub reads does not change on the switch.

### H2 — `make hub-promote` and `make hub-rollback`

New script `bin/k3dm-hub-promote` (Bash, sources lib-foundation like the other `bin/` scripts), with
Makefile targets:

- `make hub-promote REF=<commit-ish>`:
  1. Resolve `REF` to a full SHA, and require that the SHA is on `origin` (reachable from a remote branch).
  2. Require the GitHub check runs for that SHA to be complete with no failure (`gh api`). With no check runs
     for the SHA, refuse.
  3. Print the old and new `deploy/hub` SHAs and the commit subjects between them (at most 30), and require
     the operator to type `promote` on a TTY. No TTY means refuse.
  4. Push `deploy/hub` to the SHA with `--force-with-lease=deploy/hub:<old sha>`, and push an annotated tag
     `hub-promote/<UTC yyyymmddThhmmssZ>` at the SHA whose message records the old SHA, the new SHA and `REF`.
  5. Print the next steps: `make appsets-check`, then `make platform-ops`.
- `make hub-rollback`: undo the newest promotion still in effect, with the same confirmation and tag
  recording (the message says rollback). Repeated rollbacks keep stepping back; they never move forward.
  Rebuild a stack by replaying the `hub-promote/*` tags oldest to newest: a promote (including break-glass)
  pushes its `new` SHA, and a rollback pops one entry. The top must equal the current `deploy/hub` SHA, or
  refuse (it moved outside this tool). The target is the entry under the top. With fewer than two entries,
  refuse: there is nothing earlier to return to. Example: promote A, B, C, then rollback → B,
  rollback → A, rollback → refused; promote A, B, C, rollback → B, promote D, rollback → B (not C).
- `make hub-promote-status` (read-only): the current `deploy/hub` SHA, its last three `hub-promote/*` tags,
  and how many commits the current release branch is ahead of it.

### H3 — `make platform-ops` applies only what `deploy/hub` holds

- `make platform-ops` fetches `origin deploy/hub`, extracts that tree with `git archive` into a fresh
  `mktemp -d` directory, and runs `scripts/k3d-manager deploy_argocd_platform_ops --confirm` **from the
  extracted tree**. It never reads files from the working checkout. It prints the SHA it applied.
- The temporary tree is removed on exit, including on failure.

### H4 — break glass

A real outage may need a fix before CI finishes. `make hub-promote REF=… BREAK_GLASS=1` skips step 2 (the
check-run gate) only. Everything else (on `origin`, TTY confirmation, tag) still applies, and the tag message
says `break-glass`. There is no way to apply the working tree to the hub.

### Process change (Claude, after H1–H3 land; not dispatched)

- CLAUDE.md: replace the "reapply the ApplicationSets when a release branch is cut …" and "run
  `make platform-ops` on every release" rules. The new rule: a live check during development needs
  `make hub-promote REF=<release branch head>` by the operator, then `make platform-ops`; a bad promote is
  undone with `make hub-rollback`. Release close-out promotes the merged `main` commit.
- `docs/roadmap.md`: record that the 2026-07-24 release-branch tracking decision is superseded.
- The follow-up is [`v1.44.0-dev-hub-vcluster`](v1.44.0-dev-hub-vcluster.md): a dev-hub vCluster that
  reads the release branch, so most live checks no longer need a promote.

## What NOT to Do

- Do not run `hub-promote`, `hub-rollback`, `appsets-reapply` or `platform-ops` for real, and do not push
  `deploy/hub` or any `hub-promote/*` tag. The operator does the bootstrap.
- Do not change any ApplicationSet manifest, chart value or dashboard, or the Hostinger promotion plan's refs.
- Do not let any code path apply files from the working checkout to the hub.
- Do not use `git push --force`; only `--force-with-lease` with the expected old SHA.
- Do not edit CLAUDE.md, `memory-bank/` or `docs/roadmap.md` (Claude's follow-ups).
- Do not create a PR, commit to `main`, or skip hooks.
- Stubs for `git ls-remote`, `gh api …/check-runs` and `kubectl` take their output from a real read-only
  capture, with host and date in a comment beside it.
- Write the must_not tests first and show them red on the pre-fix tree.
