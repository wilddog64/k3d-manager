# v1.48.1 — Separate cluster provisioning from application deployment

**Filed:** 2026-11-02 (operator request)
**Status:** PROPOSED — implementation requires operator approval
**Milestone:** v1.48.1 (plan 4 of 5); prerequisite to v1.49.0 app onboarding and v1.50.0
**Component:** Makefile; bin/cluster-up; bin/acg-up (if present); scripts/plugins/shopping_cart.sh; Argo CD ApplicationSets; application deployment manifests
**Depends on:** Existing cluster-registration and provider lifecycle contracts; preserve v1.47.0 promotion gate
**Related issue:** [2026-04-27 k3d-manager shopping-cart tight coupling](../issues/2026-04-27-k3d-manager-shopping-cart-tight-coupling.md)

## Intent

Infrastructure provisioning is provider-specific, but application selection must be independent of the provider. Today the ACG up path hard-couples shopping-cart setup (including the historical Step 10b data bootstrap). Make the same cluster capable of running any **supported, explicitly declared** application without modifying the cluster lifecycle.

The operator's desired interface is `make acg-up CLUSTER_PROVIDER=k3s-aws APP=shopping-cart` (and `APP=<another-app>`). The existing Makefile exposes `make up CLUSTER_PROVIDER=...`, so first reconcile the actual supported target/CLI and retain working aliases; do not invent or silently rename commands. `APP` is optional: omission means **platform/cluster-only**, not an implicit shopping-cart deployment.

## Contract

- `CLUSTER_PROVIDER` identifies the provisioning substrate, not the workload.
- `APP` identifies an application profile, not a namespace, arbitrary script, or remote shell command.
- `make up CLUSTER_PROVIDER=k3s-aws` provisions the cluster and shared platform only.
- `make up CLUSTER_PROVIDER=k3s-aws APP=shopping-cart` provisions/reuses the cluster, then deploys the declared shopping-cart profile.
- Support the requested `make acg-up ... APP=...` form through a documented compatibility target/alias if that is how the public command is currently exposed; no break in existing operator flows.
- `make app-deploy CLUSTER_PROVIDER=k3s-aws APP=shopping-cart` deploys/reconciles only the app onto an existing, identified cluster.
- `make app-down CLUSTER_PROVIDER=k3s-aws APP=shopping-cart` disables/removes that app's owned resources under an explicit, tested retention policy; never destroy the cluster, shared ESO/CRDs, Vault, Argo CD, monitoring or unrelated apps. Require explicit confirmation for PVC/database deletion.
- Invalid/missing profiles fail closed before mutation, listing supported profiles; avoid any application-specific branching in provider libraries.

## Target layering

1. **Provider lifecycle** — cloud credentials, VM/cluster creation, kubeconfig, tunnel, readiness, idempotent cleanup and TTL; no shopping-cart knowledge.
2. **Platform layer** — Argo CD, Vault/ESO, Istio, monitoring, network and registration; retain the existing security baseline.
3. **Application registry** — a validated, versioned `apps/<name>.yaml` (proposed path/schema) holding pinned GitOps repo/revision, components, namespaces, prerequisites, health/e2e contract, and data-retention policy. Profiles may live with the app's infra repo; k3d-manager owns only the validated interface and references.
4. **App reconciliation** — profile-driven Argo CD Application/ApplicationSet selection and sync, with provenance and explicit status; no `kubectl apply` of application manifests outside GitOps.
5. **Evidence** — report provider, cluster identity, APP, profile revision, deployment status, readiness, E2E/security outcomes, duration and human interventions in existing dashboards/ledgers where practical.

## Migration constraints

- Preserve today's shopping-cart functioning as baseline until profile-based provisioning is verified end to end.
- Preserve k3d-manager hub/spoke ApplicationSet behavior. Today `data-git` and `services-git` opt in using `k3d-manager/shopping-cart=true`. Introduce validated app selectors without changing platform-level `k3d-manager/role=app-cluster` registration semantics. An application opt-out must not remove the cluster registration or platform CRDs.
- Migrate shopping-cart app-specific overlays and data bootstrap toward `shopping-cart-infra`; first inventory the current references, repo contents and runtime dependency paths. Do not delete `services/` or `shopping_cart.sh` until GitOps equivalence and rollback are demonstrated.
- Preserve Vault/ESO secret handling, Kyverno image admission, Istio, network policies, CVE gate, E2E and the v1.47.0 promotion gate. Unknown applications are not automatically trusted; unsupported profiles are rejected.
- App-specific alert/dashboard/test configuration belongs to the profile or its GitOps repo, while the shared observability stack remains provider infrastructure.
- Avoid renaming or implicitly re-pointing Hostinger or ACG registered clusters; an ephemeral ACG sandbox must not accidentally become a permanent hub app-cluster registration.

## Phased execution

**Phase 0 — inventory and baseline.** Trace the real `make up` → `bin/cluster-up` → ACG path, shopping-cart calls, ApplicationSets, secrets, teardown, and current tests. Capture fresh sandbox provisioning and app health proof before making changes; establish safe cleanup guards.

**Phase 1 — interface and registry.** Implement `APP` validation and reusable profile contract, separate cluster-only and app-deploy commands, retain compatibility alias, and add mocked provider tests; `APP` must never be interpolated into executable shell.

**Phase 2 — shopping-cart migration.** Implement the shopping-cart profile and migrate bootstrap/manifests incrementally using GitOps. Verify fresh and preexisting ACG clusters, idempotent re-run, E2E, alert/observability panels, and no unexpected resource pruning.

**Phase 3 — app independence proof.** Deploy a second minimal test application on the same supported substrate without editing provider code. Verify app isolation, independent removal with PVC preservation, and platform health. Record interventions.

**Phase 4 — release and downstream handoff.** Update docs, help output, CI/e2e flows, migration instructions, and rollback; publish a reusable contract for v1.49.0 unfamiliar-app onboarding and eventual v1.50.0 workload changes.

## Acceptance criteria

- [ ] With `APP` omitted, a clean `k3s-aws` cluster reaches platform readiness with **no shopping-cart data or service deployment**.
- [ ] `APP=shopping-cart` deploys via the profile and GitOps; expected services, secrets and E2E pass.
- [ ] A second profile deploys without provider/lifecycle edits; two apps remain isolated.
- [ ] Re-running provisioning/deployment is idempotent; invalid APP fails before cloud or cluster mutation.
- [ ] `app-down` removes only intended app-owned resources, preserves data by default, and cannot delete shared ESO, CRDs or cluster registration.
- [ ] Sandbox expiry and `make down` remain provider-owned; cluster teardown requires explicit provider and retains existing billable-resource verification.
- [ ] Both automated tests and a live ACG E2E run demonstrate app-agnostic behavior, security gates and observability data producers.
- [ ] Docs/roadmap and old coupling issue cross-reference the new plan, with any unresolved issue explicitly tracked.

## Non-goals

No generic auto-generation for every arbitrary repo in this release; that's v1.49.0 onboarding. No replacement of Prometheus/Grafana/Hermes. No weakening of app verification to make a second profile pass. No immediate deletion of shopping-cart or its historical workload.
