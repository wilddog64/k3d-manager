## Goal

The Release stat already shows the current scanned release (e.g. `v1.43.5`), driven by
`k3dm_bug_current_release_info{repo="$repo"}`. The "Release (filed in)" dropdown
has a persisted static `current` selection (previously `v1.43.4`); it does not
follow a new release automatically. The operator has to adjust it manually.

Default to **Auto (current release)** while preserving deliberate **Manual**
historical-release selection. When Hermes advances to `v1.43.6`, filtered bug
tables/stats should follow that current release without a dashboard JSON edit or
operator action. Existing historical filtering and "All" remain available.

## Proposed behavior

1. Add a `Release mode` selector: `Auto (current)` (default) and `Manual`.
   When Auto, the current-release *metric*, not a static dashboard selection,
   determines the effective release for all currently release-filtered panels.
2. Retain `Release (filed in)` dropdown to choose one/multiple releases and
   `All` **only in Manual mode**. Grafana may not support dynamically hiding
   a dashboard variable; if not, leave the dropdown visible and clearly label
   it `Manual releases (ignored in Auto)`. Selection must remain intact when
   switching Auto -> Manual -> Auto -> Manual.
3. Release card and Auto filtering must use the same
   `k3dm_bug_current_release_info{repo="$repo"}` source. After Hermes publishes
   the next release, Auto follows it without redeploy or manual filter changes.
4. Respect `$repo` and the existing release attribution ("filed in").
   The current-release metric is currently emitted for k3d-manager; if the
   chosen repo lacks one, **do not silently use another repo's current release,
   choose an arbitrary latest release, or show an unfiltered All view**. Show
   an informative unavailable/current-release-missing state or require Manual.
5. When Manual, preserve the current release regex semantics, multi-select, All,
   filtering, chronological release labels, and all existing panel scoping.
   Panels intentionally not release-filtered remain unaffected in both modes.
6. Keep link navigation changes scoped to the separate P2 bug, avoiding
   overlapping edits when both are assigned concurrently.

## Implementation guidance

Use PromQL-based dynamic release selection, not a saved release variable `current`
hardcoded at each version. A viable design is an Auto arm joined on
`(repo, release)` with `k3dm_bug_current_release_info`, combined with a
Manual arm using `release=~"$release"`. Gate arms with a mode selector so
only the chosen one contributes. Example *conceptual* expression for a table
series, where `$release_mode` is a validated custom numeric selector with
`auto=1` / `manual=0`:

```promql
(
  (k3dm_bug_info{repo="$repo",live_verified=~"$verified"}
    and on(repo,release) k3dm_bug_current_release_info{repo="$repo"})
  and on() (vector($release_mode) == 1)
)
or
(
  k3dm_bug_info{repo="$repo",release=~"$release",live_verified=~"$verified"}
  and on() (vector($release_mode) == 0)
)
```

This is a design sketch, not implementation-ready syntax: validate Grafana's
PromQL interpolation and Grafana/Prometheus binary matching, check numeric
selector substitutions, and avoid zero-valued phantom rows. For aggregates,
use a semantically equivalent filter on the underlying metric, then aggregate;
do not add series values from both modes or double-count. If there is a simpler
Grafana-supported implementation, document why it is safer.

Apply the selected-release behavior consistently to **every panel currently
filtered by `$release`**, including status and verified summaries and the
Bugs table, not just the table. Do not change panels which deliberately use
current release or all releases independently.
