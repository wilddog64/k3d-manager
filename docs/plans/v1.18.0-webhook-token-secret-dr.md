# v1.18.0 — Disaster recovery: auto-sync k3dm-webhook-token Secret from Keychain

**Branch:** `k3d-manager-v1.18.0`
**Files:** `scripts/plugins/argocd.sh`

---

## Problem

The `k3dm-analyze` AlertmanagerConfig references a bearer-token Secret `k3dm-webhook-token`
(namespace `cicd`, key `token`). prometheus-operator **rejects the entire AlertmanagerConfig**
(ArgoCD + CVE routes alike) if that Secret is missing — silently, on every reconcile. The
Secret's canonical source of truth is the macOS Keychain (`service=k3dm-webhook-token`,
`account=k3dm`, created/rotated by `bin/k3dm-webhook-setup` and `bin/rotate-webhook-token`), but
nothing projects the Keychain value into the cluster. So every cluster rebuild loses the Secret
and the alert→webhook pipeline goes dead until someone runs the undocumented-in-practice manual
step (`kubectl create secret generic k3dm-webhook-token --from-literal=token=<token> -n cicd`).
This actually happened: the Secret was absent hub-side from 2026-07-25 to 2026-07-27.

**Root cause:** a required Secret has a durable source (Keychain) but no automated projection
into the cluster; it lives only as a manual `_info` instruction at the end of
`deploy_argocd_platform_ops`.

---

## Fix

Bake the Keychain→cluster projection into the platform-ops deploy path, and expose it as a
standalone recovery entrypoint. Token is read into a shell local and delivered to `kubectl` via
**stdin** (`--from-file=token=/dev/stdin`), never as an argv literal; the whole apply pipeline is
wrapped in `_no_trace` so an active `set -x` cannot echo the token. Idempotent via
`--dry-run=client -o yaml | _kubectl apply -f -` (same pattern the function already uses for
ConfigMaps).

### Change 1 — `scripts/plugins/argocd.sh`: add the sync helper + public entrypoint

Add these two functions immediately **before** `function deploy_argocd_platform_ops() {`
(currently line 1346):

**Exact new block:**

```bash
function _argocd_apply_token_secret() {
   local _token="${1:?token required}"
   local _ns="${2:?namespace required}"
   local _name="${3:?secret name required}"
   printf '%s' "${_token}" \
      | _kubectl -n "${_ns}" create secret generic "${_name}" \
           --from-file=token=/dev/stdin --dry-run=client -o yaml \
      | _kubectl apply -f -
}

function argocd_sync_webhook_token_secret() {
   local _ns="${1:-cicd}"
   local _service="k3dm-webhook-token"
   local _account="k3dm"
   local _token=""

   if _is_mac; then
      # shellcheck disable=SC2016
      _token=$(_no_trace bash -c 'security find-generic-password -s "$1" -a "$2" -w' _ "${_service}" "${_account}" 2>/dev/null || true)
   fi

   if [[ -z "${_token}" ]]; then
      _warn "[argocd] ${_service} not found in Keychain (${_service}/${_account}) — run bin/k3dm-webhook-setup to create it, then re-run; skipping cluster Secret sync"
      return 0
   fi

   _info "[argocd] Syncing ${_service} Secret into namespace ${_ns} from Keychain..."
   _no_trace _argocd_apply_token_secret "${_token}" "${_ns}" "${_service}"
}
```

## Out of scope (future extension, note only)

`oci-kubeconfig` (a file path), `platform-ops-app-rebuild` (a GitHub token), and the
`platform-ops-notifications` slack URL have no durable local source today, so they stay manual.
If/when a Keychain (or Vault) source is defined for them, the same `_argocd_apply_token_secret`
pattern extends to cover them. Also consider adding the Keychain→Secret sync to the cluster
bootstrap/`cluster-up` path so it runs on every fresh cluster, not only on `deploy_argocd_platform_ops`.
