## Problem

`90d8942a` taught `bin/k3dm-node-health-watch` to restart a node that is **Ready** while its kubelet
tunnel returns fast 502s (`proxy error from … while dialing <ip>:10250, code 502`). Two things are
already verified:
- Every path passes under stubs (11/11 BATS).
- The classifier recognizes the real error text.

What has **not** been observed is the full loop on a real cluster: six `tunnel` ticks, then a
`docker restart`, then recovery. The fault comes from a host sleep or wake. It has happened about
30 times since 2026-10-05, but never on demand. Until it happens, the P1 fix has never run end to end.

Inducing it on the hub is out of the question. agent-0 carries argocd-server and 12 other pods, and
the drill ends in a `docker restart`.

## Approach

A new script creates a **throwaway** one-server, one-agent k3d cluster:
1. It confirms the agent is healthy.
2. It injects a fault that reproduces the watchdog's evidence: the node stays `Ready`, and
   `/api/v1/nodes/<agent>/proxy/healthz` fails fast with the tunnel 502.
3. It runs the real watchdog against the drill cluster, with an isolated log and state.
4. It asserts the expected log sequence, then deletes the cluster.

**The fault.** Inside the agent container's network namespace, reject TCP to the agent's own
InternalIP on port 10250:

```bash
iptables -I OUTPUT 1 -p tcp -d "<agent InternalIP>" --dport 10250 -j REJECT --reject-with tcp-reset
```

The API server reaches the kubelet only through the agent's tunnel. The tunnel's far end, the k3s
agent process, then dials `<InternalIP>:10250` locally, and that dial is what this rule refuses.
- Kubelet heartbeats go outward to the server on 6443 and are untouched, so the node stays `Ready`.
- Other nodes' scrapes of 10250 arrive on INPUT, not OUTPUT. A one-agent drill has none anyway.

**What is not reproduced.** The real incident breaks the tunnel itself. The drill breaks the dial at
the tunnel's far end. The watchdog cannot tell the two apart, because it classifies only on Ready
plus the healthz error text, and the **fidelity gate** below proves that this evidence is identical.
If the gate fails, the drill reports INCONCLUSIVE. It never reports PASS from an unfaithful fault.

**Recovery clears the fault.** `docker restart` recreates the container's network namespace, so
the rule is gone after the watchdog acts. If the rule were to survive, the watchdog would log
`did not recover within 100s` and the drill would FAIL. That outcome is informative, not a bug in
the drill.

## Items

### 1. `bin/k3dm-drill-node-tunnel` (new, `set -euo pipefail`, sources lib-foundation like other `bin/` scripts)

**Fixed identity. Nothing here is configurable toward the hub:**

```bash
drill_cluster="k3dm-drill-tunnel"
drill_context="k3d-${drill_cluster}"
drill_agent="k3d-${drill_cluster}-agent-0"
drill_image="rancher/k3s:v1.32.0-k3s1"   # same pin as scripts/etc/cluster.yaml.tmpl
```

The cluster name is a literal. There is no `CLUSTER`, `NAME` or `CONTEXT` override. The only knobs
are `KEEP=1`, which skips deletion at the end, and `K3DM_DRILL_TIMEOUT` (default `600` seconds for
the whole drill).

**Isolation:**
- Create a temp dir with `mktemp -d`, holding `kubeconfig`, `watch.log`, `watch.state` and
  `drill.log`. Export `KUBECONFIG=<tmp>/kubeconfig` for the whole script, so `~/.kube/config` and
  the operator's current context are never read or written.
- `k3d cluster create` runs with `--kubeconfig-update-default=false --kubeconfig-switch-context=false`.
  The script then writes the kubeconfig with `k3d kubeconfig get "$drill_cluster" > "$KUBECONFIG"`.
- Every `kubectl` call passes `--context "$drill_context"`.

**Guard (`_drill_guard <container>`):** before **every** `docker exec`, `docker restart` or
`docker inspect`, assert both of these, and abort with exit 2 otherwise:
- `docker inspect -f '{{ index .Config.Labels "k3d.cluster" }}' <container>` equals `$drill_cluster`.
- The name starts with `k3d-${drill_cluster}-`.

**Pre-flight (exit 2 on failure):**
- `k3d`, `kubectl` and `docker` are on PATH.
- `k3d cluster list -o json` does not already contain `$drill_cluster`. If it does, print
  `stale drill cluster exists; delete it with: k3d cluster delete k3dm-drill-tunnel` and exit 2.
  Do not delete it automatically.

**Cleanup trap (EXIT):**
- Kill the watchdog child if it is running.
- Unless `KEEP=1`, run `k3d cluster delete "$drill_cluster"`, using the literal variable and nothing
  else.
- Print the temp dir path, which is always kept, so the logs survive.

**Phases.** Log each to `drill.log` and stdout as `[drill] <phase>: …`:

1. **create:**
   ```bash
   k3d cluster create k3dm-drill-tunnel --image rancher/k3s:v1.32.0-k3s1 --servers 1 --agents 1 \
     --no-lb --k3s-arg '--disable=traefik@server:0' --k3s-arg '--disable=metrics-server@server:0' \
     --kubeconfig-update-default=false --kubeconfig-switch-context=false --wait --timeout 180s
   ```
2. **baseline:** within 120s, the agent node is `Ready` and its proxy healthz returns `ok` on 3
   consecutive 5s samples. Otherwise the result is INCONCLUSIVE ("drill cluster never healthy").
3. **negative control:** start the watchdog (see item 1a) for 3 ticks against the healthy cluster.
   `watch.log` must stay empty, because a healthy tick logs nothing. If any line appears, FAIL.
   Then stop the watchdog and remove `watch.state`.
4. **inject:**
   - Read the agent InternalIP:
     `kubectl get node "$drill_agent" -o jsonpath='{.status.addresses[?(@.type=="InternalIP")].address}'`.
   - Run `docker exec "$drill_agent" iptables -V`. If that fails, the result is INCONCLUSIVE ("no
     iptables in agent image"). Do not pull a helper image.
   - Insert the rule shown in **Approach**.
5. **fidelity gate:** within 60s, get 3 consecutive 5s samples where **both** of these hold:
   - Ready is `True`.
   - The `kubectl get --raw /api/v1/nodes/$drill_agent/proxy/healthz --request-timeout=15s` output
     (stdout and stderr) matches the watchdog's own regex,
     `proxy error from .* while dialing .*:10250, code 502`.

   Read the regex from `bin/k3dm-node-health-watch` with `grep -o` on the `_healthz_state` line. Do
   not keep a second copy, so the drill cannot drift from the watchdog. If the gate is not met, the
   result is INCONCLUSIVE ("injected fault does not reproduce the tunnel signature"), with the last
   healthz output (first 300 chars) printed.
6. **drill:** record `docker inspect -f '{{.State.StartedAt}}' "$drill_agent"`, then start the
   watchdog. Wait, up to the remaining timeout, for `watch.log` to contain these, in order:
   - `kubelet tunnel dead (1/6)` … `(6/6)`
   - `restarting k3d-k3dm-drill-tunnel-agent-0`
   - `k3d-k3dm-drill-tunnel-agent-0 recovered`
7. **assert:**
   - The six counts appeared in order.
   - Exactly one `restarting` line.
   - `StartedAt` changed.
   - Healthz is `ok` again on 3 consecutive samples.
   - No line contains `slow/unreachable` or `NotReady` between `(1/6)` and `restarting`.

   Every assertion passes → PASS. A timeout or a failed assertion → FAIL, printing the last 20 lines
   of `watch.log`.

**1a. Running the watchdog:** start the real script as a background child (no copy, and no sourcing
into the drill's own shell), with the environment below, then capture its PID.

| Variable | Value | Why |
|---|---|---|
| `K3DM_NODE_RECOVERY_ENABLED` | `1` | otherwise `_recover` only logs |
| `K3DM_NODE_RECOVERY_CONTEXT` | `$drill_context` | |
| `K3DM_NODE_RECOVERY_NODE` | `$drill_agent` | |
| `K3DM_NODE_RECOVERY_INTERVAL` | `10` | the drill takes about 1 minute instead of 3. The threshold under test stays at the default |
| `K3DM_NODE_RECOVERY_LOG` / `_STATE` | the temp dir | the launchd watchdog's log and cooldown state are never touched |
| `K3DM_HOSTNET_DRIFT_BIN` | `/usr/bin/true` | the drift fixer reconciles hub host-network IPs and must not run here |
| `KUBECONFIG` | the temp kubeconfig | |

Leave `K3DM_NODE_TUNNEL_THRESHOLD` **unset**, because the drill proves the shipped default of 6.

**Result line (last stdout line) and exit code:**

| Result | Exit | Meaning |
|---|---|---|
| `DRILL PASS` | 0 | full loop observed |
| `DRILL FAIL: <reason>` | 1 | watchdog misbehaved |
| `DRILL INCONCLUSIVE: <reason>` | 3 | the drill could not stage the fault faithfully. Says nothing about the watchdog |
| `DRILL REFUSED: <reason>` | 2 | pre-flight or guard |

**The launchd watchdog is unaffected.** The production watchdog keeps watching the hub with its own
context, log and state. The drill cluster's context exists only in the temp kubeconfig, so the two
cannot see each other's targets.

### 3. `scripts/tests/bin/drill_node_tunnel.bats` (fully stubbed)

Stub `k3d`, `kubectl`, `docker` and the watchdog. The watchdog is pointed at a stub via
`K3DM_DRILL_WATCH_BIN`, a test-only override read only when `BATS_TEST_TMPDIR` is set. Document
that in the script header. The stubs record argv to call files.

1. **Hub is unreachable by construction:** across a full PASS run, every `docker` call's container
   argument starts with `k3d-k3dm-drill-tunnel-`, every `kubectl` call carries
   `--context k3d-k3dm-drill-tunnel`, and no call mentions `k3d-k3d-cluster`.
2. **Guard refuses a foreign container:** when the `docker inspect` label stub returns `k3d-cluster`,
   the script exits 2 with `DRILL REFUSED`, and no `exec` or `restart` call was recorded.
3. **Stale cluster refused:** `k3d cluster list` already lists `k3dm-drill-tunnel` → exit 2, and
   `cluster delete` is **not** called.
4. **Fidelity gate:** healthz stub returns `context deadline exceeded` after the injection → exit 3
   `INCONCLUSIVE`, and the watchdog stub is never started for phase 6.
5. **PASS path:** the watchdog stub writes the full expected sequence and the `StartedAt` stub
   changes → exit 0, `DRILL PASS`.
6. **FAIL path:** the watchdog stub writes `(1/6)` … `(6/6)` and then `slow/unreachable` with no
   restart → exit 1, `DRILL FAIL`.
7. **Negative control:** the watchdog stub writes a line during phase 3 → exit 1.
8. **Cleanup:** after a FAIL, `k3d cluster delete k3dm-drill-tunnel` is called exactly once. With
   `KEEP=1` it is not called.
9. **Isolation:** `KUBECONFIG` seen by the stubs is under the temp dir, never `$HOME/.kube/config`.
   The watchdog env has `K3DM_HOSTNET_DRIFT_BIN=/usr/bin/true` and no `K3DM_NODE_TUNNEL_THRESHOLD`.
10. **Regex single-sourced:** the regex the drill passes to its matcher equals the one `grep -o`
    finds in `bin/k3dm-node-health-watch`.

**Mutation check (paste in the report):**
- With `_drill_guard` reduced to `return 0`, test 2 fails.
- With the regex hard-coded to a different string, test 10 fails.

## What NOT to Do

- Do NOT run `make drill-node-tunnel`, `k3d cluster create` or any real `docker`/`kubectl`.
  Tests are fully stubbed, and the operator runs the drill.
- Do NOT add a cluster-name, context or node override, and do NOT point anything at
  `k3d-k3d-cluster`.
- Do NOT inject faults on the hub, or call the launchd watchdog's log or state paths.
- Do NOT change `bin/k3dm-node-health-watch`, its threshold, cooldown or regex.
- Do NOT pull or pin a helper image. If the agent image lacks iptables, the result is INCONCLUSIVE.
- Do NOT create a PR or merge. Do NOT use `--no-verify`. Do NOT modify files outside the table.
- Do NOT update memory-bank.
