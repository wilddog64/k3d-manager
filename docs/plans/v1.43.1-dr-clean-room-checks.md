# v1.43.1 — DR clean-room checks: credential allowlist and target isolation

**Filed:** 2026-10-10, Claude
**Branch:** `k3d-manager-v1.43.1` (never `main`)
**Status:** READY. Dispatch after `v1.43.1-hub-data-recover.md` lands (both touch `bin/dr-drill`).
**Origin:** operator-forwarded review, 2026-10-10: a drill should prove recovery "without relying on
the production cluster's state", and making production credentials unavailable "can reveal hidden
dependencies". Decision (Claude, operator agreed): keep the drill on the M2, the second machine; do
not move it to the M4, which shares Docker, the filesystem and the Keychain with production.
**Implementer:** Codex · **Operator:** one audit-mode drill · **Verifier:** Claude

## What already holds

The M2 drill restores only from the encrypted export, runs in its own `dr-drill` k3d cluster with
its own kubeconfig, proves default-deny egress (V0) before unsealing, and checks the data against the
export inventory. Two things are asserted nowhere:

1. **Which credentials the run reads.** `hub-up` in drill mode, `vault.sh` and the restore all read
   the Keychain through different paths (`_secret_load_data`, `security` directly). A hidden
   dependency on something other than the two authorised recovery inputs would pass silently on the
   M2 and fail on a fresh machine.
2. **That every destructive call targets the drill.** The M2 also runs a cluster named
   `k3d-cluster`, the production hub's name. Only naming conventions keep the drill off it.

## C1 — Credential allowlist (audit, then enforce)

- `bin/dr-drill` and `hub_data_recover` put a `security` shim first on `PATH` for the whole run
  (child processes included) and define a `security` shell function for the current shell. The
  shim records the **service name and account** of every `find-generic-password` /
  `add-generic-password` / `delete-generic-password` call to `<run_dir>/credentials.tsv`
  (`op`, `service`, `account`) and then calls the real `/usr/bin/security` with the same
  arguments. It never records `-w` values or stdin.
- Allowlist `scripts/etc/dr/credential-allowlist.tsv` (`op`, `service`, `account` pattern):
  - drill: `find k3dm-hub-data-age identity`, `find k3dm-vault-unseal-dr secrets/vault:*`, plus
    whatever the drill's own throwaway Vault writes and reads for **its own** cluster (account
    patterns scoped to `dr-drill`);
  - real restore (`hub_data_recover`): the same two inputs plus the B1 step 6 writes.
- `DR_DRILL_CREDENTIAL_POLICY=audit|enforce`, default **`audit`** in this release:
  - `audit`: the result JSON gains `credentials_read` (service/account pairs, no values) and
    `credentials_unexpected` (pairs not on the allowlist). Nothing fails.
  - `enforce`: a call not on the allowlist exits 44 from the shim before reaching `security`, and
    the result records check **V9** false.
- **Flip to enforce:** after one audit drill, Claude reads `credentials_unexpected`, decides with the
  operator which entries are legitimate (add them to the allowlist) and which are hidden
  dependencies (file a bug for each), then changes the default to `enforce` in a follow-up commit.

## C2 — Target isolation guard

New `_dr_drill_assert_target`, called before Phase 3 (restore) and before Phase 6 (teardown):
- `KUBECONFIG` is exactly `~/.k3dm/dr-drill/kubeconfig`, it holds exactly one context, and that
  context is `k3d-dr-drill`;
- the context's server port is the published port of the local `k3d-dr-drill-serverlb` container;
- `DR_DRILL_CLUSTER` is `dr-drill`, and is not the name of any other running k3d cluster;
- every `docker exec` target in the restore starts with `k3d-dr-drill-` (assert in
  `_hub_data_restore_one` when `HUB_DATA_RESTORE_TARGET` is not `hub`);
- teardown deletes only `dr-drill`, by literal name.

A failure prints `[dr-drill] refusing: target is not the drill cluster (<reason>)` and stops before
the destructive step.

## Tests (BATS, stubbed)

1. Audit mode: a stubbed run that reads an extra Keychain item records it in
   `credentials_unexpected` and still succeeds.
2. Enforce mode: the same read exits 44 in the shim, never reaches the real `security` stub, and
   V9 is false.
3. The shim's log never contains a value passed with `-w` or on stdin.
4. C2: a kubeconfig with a second context, a server port that is not the serverlb's, a
   `DR_DRILL_CLUSTER=k3d-cluster`, and a docker target outside `k3d-dr-drill-` each stop before
   the restore with the refusal message, and no `docker exec`, `kubectl delete` or `k3d cluster
   delete` is called.
5. Teardown never deletes anything but `dr-drill`.

Mutations: let the enforce shim pass unknown items (2 red); drop the serverlb port check (4 red).

## What NOT to do

- Do not log, print or store any Keychain value; record names only.
- Do not change, lock, move or delete any Keychain, item or search list.
- Do not start in `enforce` before an audit run has been reviewed.
- Do not create a PR, skip hooks (`--no-verify`), commit to `main`, or touch files not named here.
