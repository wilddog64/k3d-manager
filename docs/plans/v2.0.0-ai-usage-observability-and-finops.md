**Components (proposed):** Hermes collector/adapter, existing dispatch ledger and metrics exporter, Prometheus/Pushgateway, a Grafana AI Usage & FinOps dashboard, tests and a guide; exact code paths to be confirmed at implementation time

## Problem

The operator can see ChatGPT/Codex usage breakdowns by model, chat, plugin, feature, and period, including lifetime tokens and relative usage. Grafana does not reproduce these provider-side views or correlate agent consumption with dispatch, verified outcomes, regression/rework and release. Existing per-task cost dashboards may already expose some Codex token data; this proposal must **reuse** them, not double count.

The screenshots from 2026-10-28 include examples of **relative usage units**, lifetime tokens, and per-chat **weekly %** and **5-hour %**. They also show delayed or missing daily reporting and an estimated per-chat 5-hour figure over 100%, which is not a live remaining-quota value. These quantities are not interchangeable with token counts, dollar bills or the CLI's remaining quota.

## Goals / non-goals

1. Show *observable* model/vendor consumption and quota headroom, with source, unit, scope, timestamp, and coverage prominently visible.
2. Correlate consumption by dispatch job/spec/release with **independently verified** delivery, rework, and intervention signals already tracked elsewhere.
3. Use a vendor-neutral data contract and adapters for Codex, Claude and Gemini only where a supported, permitted data source is available.
4. Detect stale/missing telemetry rather than interpreting gaps as zero usage.
5. Do **not** scrape authenticated ChatGPT website pages, reverse-engineer private endpoints, request subscription secrets, equate ChatGPT subscription quota with API spend, or claim that all screenshot figures are programmatically collectible.

## Design

### D1. Inventory sources before coding

Produce a source/capability matrix for each provider and each metric, with documented source, API/CLI version, permission requirements, refresh interval, supported/unsupported status, and validation sample.

Source tiers:
- **Measured locally**: opt-in CLI/OTel or structured run-usage events, dispatch ledger, CI outcomes. Prefer documented interfaces and stable schemas.
- **Provider reported**: official documented usage/billing endpoints where available and authorized; keep API-organization usage/billing separate from consumer subscription allowances.
- **Operator supplied**: manually entered snapshot (optional, separately marked), e.g. ChatGPT screen percentages. Never silently parse screenshot text or treat snapshots as continuous telemetry.
- **Unavailable**: explicit `unknown` with source/coverage reason.

A provider API's existence is not proof it exposes ChatGPT Plus/Codex plan quota or chat/plugin counts. Do not assume Codex's OpenTelemetry fields contain all UI metrics. Confirm actual event payload and opt-in behavior before using it.

### D2. Canonical records and joins

Define versioned records with `provider`, `model`, `source_kind`, `metric_name`, `unit`, `period_start/end`, `observed_at`, `collected_at`, `run_id` and `task_id` if grounded, `value` (nullable), `coverage_status`, and source version. Use stable opaque task IDs from the existing dispatch ledger for joins. Record the attribution method and forbid attribution inferred solely from similar timestamps or chat titles.

Keep tokens (input/output/cache), relative usage units, quota used/remaining percent, billable API dollars, API-equivalent estimates and subscription fixed fees as different types. A percent consumed across an entire chat is not a sum of current-window quota percentages. Never sum overlapping windows or multiple telemetry sources for the same event. Track attempted/failed/retried work separately from landed and live-verified work.

### D3. Collector and storage

Prefer existing Hermes scheduling and exporter conventions; run a bounded read-only collection pass with timeouts and backoff. Preserve raw minimal structured snapshots locally with bounded retention for reconciliation, and export low-cardinality aggregates to Prometheus/Pushgateway using the project's existing conventions. Long-lived per-run detail belongs in existing ledger/artifact storage, not unbounded Prometheus labels.

Do not place user identifiers, conversation names, prompts, home directories, tokens, email addresses, session transcript content, Git SHAs, or high-cardinality task IDs in Prometheus labels. Apply file permission and secret-redaction policy. Disable network collection by default unless a provider-supported source and operator consent are confirmed. Collection failure must not block dispatch, Hermes health, or releases.

### D4. Proposed metrics and dashboard

Exact names follow repository metric naming conventions at implementation; candidate series:

| Candidate metric | Semantics |
|---|---|
| `k3dm_ai_usage_tokens_total{provider,model,direction,source}` | Cumulative tokens from attributable non-overlapping events, only where measured |
| `k3dm_ai_usage_api_cost_usd_total{provider,source}` | Actual documented billable API usage; **not** ChatGPT subscription spend |
| `k3dm_ai_usage_quota_remaining_ratio{provider,window,source}` | Timestamped point-in-time remaining allowance where supported, not inferred |
| `k3dm_ai_usage_last_success_timestamp_seconds{provider,source}` | Last good collector observation |
| `k3dm_ai_usage_collection_status{provider,source}` | 1 fresh, 0 unavailable/error; separate stale threshold |
| `k3dm_ai_dispatch_usage_coverage_ratio{provider}` | Measured attributed dispatches / eligible dispatches |

Dashboard sections:
1. **Availability & coverage:** source status, age, unsupported/unknown counters; prominent last-updated timestamp.
2. **Quota capacity:** provider/window remaining if supported, with reset time only when supplied by source.
3. **Consumption:** tokens and actual API spending by vendor/model, with explicit unit and collection scope.
4. **Per-task / release efficiency:** reuse dispatch/spec metrics to show verified outcomes, retries, review failures, human interventions, and measured consumption; unmeasured tasks stay `unknown`, not zero.
5. **Cost quality:** distinguish subscription flat fee (manual fixed budget), real API invoice, and illustrative API-equivalent costs; do not create a synthetic blended spend figure.

No global productivity score. Compare only like-for-like tasks by complexity, verification level and coverage, as proposed in the existing dispatch quality roadmap.

### D5. Alerts

Warn when collector data is stale for more than twice its expected interval, a source transitions from reporting to missing, or supported quota falls below a configurable threshold. Never alert on `0` usage when the data source is absent. Deduplicate alerts and include a safe diagnostic command and source name, not raw payloads.

### D6. Phased delivery

- **Phase 0, evidence:** source/capability matrix, opt-in/security review, sample fixtures, mapping to existing AI cost/release dashboards.
- **Phase 1, Codex:** one supported local event source, offline replay and reconciliation with a small sample of dispatch runs; publish freshness and token counts only where proven.
- **Phase 2, vendor adapters:** Claude/Gemini only after documenting stable supported data; unsupported fields remain absent/unknown.
- **Phase 3, outcomes:** join with existing dispatch ledger, spec and release verification, and dashboard; no new task-outcome accounting invented here.
- **Phase 4, optional quota snapshots:** official quota sources or explicitly manual operator-entered snapshots, visibly marked as snapshots and not billed cost.

## What NOT to Do

- Do not write deployment code or run live probes merely because this proposal exists.
- Do not alter subscription settings, credentials, billing, login sessions or browser cookies.
- Do not conflate local Codex/Claude/Gemini CLI workloads with ChatGPT web/app activity.
- Do not create a PR, commit to `main`, or bypass existing release gate and hooks.
- Do not promise comprehensive vendor usage measurement without a supported source.
