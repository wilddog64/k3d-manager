# v1.18.0 — Dependabot security updates for the shopping-cart repos (close the first-mile CVE gap)

**Coordinating repo:** `k3d-manager` (spec only — no k3d-manager code changes)
**Target repos (all `wilddog64`):**
`shopping-cart-basket`, `shopping-cart-frontend`, `shopping-cart-order`,
`shopping-cart-payment`, `shopping-cart-product-catalog`
**Branch (all work repos):** `feat/dependabot-security-updates` (create from `origin/main`)

---

## Problem

The event-driven CVE auto-patch loop (k3d-manager v1.18.0) is the **last mile**:
`TrivyCriticalVulnerabilityDetected` → webhook `/api/v1/cve-remediate` → `cve-auto-*` Job →
`app-cve-scan.sh` promotes an already-clean `sha-*` image, or dispatches a CI rebuild.

That closes CVEs only when a **fixed image already exists** or a **plain rebuild** picks up a
patched base layer. It does **nothing** for the class of vuln that matters most here:

- **App-dependency CVEs** — a vulnerable Go module (`go.mod`/`go.sum`), Maven jar (`pom.xml`),
  npm package (`package.json`), or Python dep (`pyproject.toml`). These pin **exact versions**.
  Rebuilding from the same `main` recompiles the identical dependency graph → identical vuln →
  Trivy still flags it → no clean candidate → no promotion → the job re-runs and re-notifies forever.

The fix for that class is a **source commit that bumps the version** — which nothing in the
auto-patch system produces, by design. The **first mile** — "produce a fixed image" — is missing.

**Root cause of the gap:** no dependency-update automation on the app repos. Dependabot is the
piece that opens the version-bump PR; once merged, CI builds a clean `sha-*` image and the existing
auto-patch promotes it. This spec adds Dependabot to all five repos so app-dep CVEs self-heal
end-to-end.

---

## Fix

Add `.github/dependabot.yml` to each repo. Every file declares three ecosystems:

1. The repo's **app ecosystem** (`gomod` / `npm` / `maven` / `pip`) — the actual dep CVEs.
2. `docker` — base-image `FROM` bumps (complements the rebuild path).
3. `github-actions` — keeps workflow action pins current (aligns with the supply-chain rule that
   actions must pin to a version tag).

Dependabot **security updates** (enabled as a repo setting, Change 6 below) open a PR the moment a
dependency is flagged by a GitHub advisory — regardless of the weekly `schedule`. The weekly
version-update schedule plus `groups` (minor+patch grouped, majors separate) keeps routine noise low.

`open-pull-requests-limit: 10` on the app ecosystem so a burst of advisories isn't throttled to the
default 5. Weekly interval; default branch (`main`) is the target — exactly what CI builds.

### Change 1 — `shopping-cart-basket`: new `.github/dependabot.yml`

**Exact new file:**

```yaml
version: 2
updates:
  - package-ecosystem: "gomod"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 10
    groups:
      go-minor-patch:
        update-types:
          - "minor"
          - "patch"
  - package-ecosystem: "docker"
    directory: "/"
    schedule:
      interval: "weekly"
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
```

### Change 6 — enable Dependabot alerts + security updates (Claude-owned, NOT Codex)

The `dependabot.yml` files enable scheduled **version** updates. **Security** updates (immediate
PRs for advisory-flagged deps — the actual CVE closer) are a per-repo GitHub setting. Claude runs
these idempotent API calls (they are settings toggles, not source edits) — do NOT hand to Codex:

```bash
for r in basket frontend order payment product-catalog; do
  gh api -X PUT "repos/wilddog64/shopping-cart-$r/vulnerability-alerts"     # Dependabot alerts
  gh api -X PUT "repos/wilddog64/shopping-cart-$r/automated-security-fixes" # security updates
done
```

If a repo is private and dependency graph is off, `vulnerability-alerts` PUT will need the
dependency graph enabled first (`security_and_analysis.dependency_graph`). Verify per repo.
