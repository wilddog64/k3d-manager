## Problem

The first live drill passed on 2026-10-10 (run `20261010T182508Z`, data-services RTO 499 s).
Two gaps remain:

1. **RPO is the export cadence.** `make hub-data-export` is manual and attended, so a hub loss can
   lose up to a week of Vault, Keycloak and LDAP changes. The export is attended only because
   `_hub_data_inventory` generates a Vault **root token** from the Keychain unseal shards
   (`_hub_data_generate_root`), and it needs that token for one call: `vault kv list secret/`.
2. **No retention.** Every export (about 120 MB, encrypted, does not compress) stays on the
   `snapshots` branch forever. `K3DM_HUB_DATA_KEEP` exists in `hub_data.sh` but nothing reads it.
   GitHub already warned about a 68 MB file.

## Pipeline (operator, 2026-10-10)

Each step gates the next; a failure stops the run, alerts, and leaves the previous good state alone.

| # | Step | Deliverable |
|---|---|---|
| 1 | Scheduled export (launchd on the M4) | D4 |
| 2 | Least-privilege Vault authentication | D1 (plus D2 context pin) |
| 3 | Encrypted export + integrity verification | D6 |
| 4 | Upload to durable backup storage | the existing push to the private `k3dm-hub-data` repo; copies outside GitHub are `v1.46.0-hub-data-backup-integrity.md` D5 |
| 5 | Verify the remote copy before marking successful | D7 |
| 6 | Retention cleanup with verified-backup protection | D3 |

Signing the manifest (authenticity, not just integrity) stays in v1.46.0 D2.

## Design

### D1 — Inventory via a list-only Vault login (no shards, no root token)

- **New public function `hub_data_export_setup`** (attended, operator runs once on the M4; also
  safe to rerun). Uses the existing admin path (`_vault_login`, as `_vault_set_eso_reader` does in
  `scripts/plugins/vault.sh`) to create, idempotently:
  - ServiceAccount `hub-data-export` in namespace `secrets` (`kubectl create sa --dry-run=client -o
    yaml | kubectl apply -f -`). No RBAC is bound to it.
  - Vault policy `hub-data-inventory`, exactly:
    ```hcl
    path "secret/metadata/" { capabilities = ["list"] }
    ```
  - Vault role `auth/kubernetes/role/hub-data-inventory`:
    `bound_service_account_names=hub-data-export bound_service_account_namespaces=secrets
    policies=hub-data-inventory ttl=5m`.
  - Then **self-tests** with D1's login path and fails unless the listing is non-empty.
- **New helper `_hub_data_inventory_token`** replaces `_hub_data_generate_root` in
  `_hub_data_inventory` only:
  1. `_kubectl -n secrets create token hub-data-export --duration=10m` (captured, never echoed);
  2. sent on **stdin** to the Vault pod:
     `vault write -field=token auth/kubernetes/login role=hub-data-inventory jwt=-`
     (`vault write key=-` reads stdin; see `reference_vault_operator_unseal_has_no_stdin_dash`);
  3. an empty result fails with
     `[hub-data] Vault login as hub-data-export failed; run make hub-data-export-setup`.
  The existing `_hub_data_vault_kv_list`, `_hub_data_kv_names` and revoke-on-EXIT logic are kept
  unchanged; only the token source changes.
- `_hub_data_generate_root` stays: `hub_data_verify_vault_paths` (drill V2, M2, attended) still
  uses it against the throwaway drill Vault. The **export** no longer reads
  `k3dm-vault-unseal-dr` at all. Test 2 asserts it.
- Neither token ever appears in argv, a log or `set -x` output (`_no_trace` where the existing
  code uses it).

### D2 — Pin the hub context

The export must never run against whatever context is current (an ACG sandbox context is often
current). `hub_data_export` writes a 0600 kubeconfig for `K3DM_HUB_DATA_CONTEXT` (default
`k3d-k3d-cluster`) with `kubectl config view --minify --flatten --context …` into its stage
directory, exports `KUBECONFIG` to it for the rest of the run, and fails with
`[hub-data] hub context <ctx> not found` if the context is missing. Same pattern as
`scripts/plugins/hub_recovery.sh:90`. Applies to the manual and the scheduled run.

### D3 — Retention: `hub_data_prune`

New public function, also called at the end of every `hub_data_export`, **only after D7 has
verified the new export's remote copy**. If D7 fails, nothing is pruned.

- **Keep set** = the union of:
  - exports whose directory timestamp (`snapshots/YYYYMMDDTHHMMSSZ`) is younger than
    `K3DM_HUB_DATA_RETAIN_DAYS` days (default `5`), measured from now (UTC);
  - the newest export, whatever its age;
  - the `export` named by the **newest** `results/*.json` on the `results` branch whose
    `success` is `true`. Pruning must never remove the last export a drill proved good.
- **Verified-backup protection:** prune also refuses (non-zero, nothing pushed) unless every
  export in the keep set passes D6's manifest check in the clone. It never prunes down to a keep
  set it has not checked.
- **Fail closed:** if the `results` branch cannot be fetched or parsed, prune nothing and return
  non-zero (`[hub-data] cannot read drill results; nothing pruned`). Fetch it explicitly with
  `git fetch origin +refs/heads/results:refs/remotes/origin/results` (a bare
  `git fetch origin results` only writes `FETCH_HEAD`).
- **Nothing to prune:** exit 0, no push.
- **Rewrite, do not delete-commit** (deleting in a normal commit leaves every blob in history, so
  the repo never shrinks): in the clone, `git rm -r -q --cached` the pruned directories, then
  `tree=$(git write-tree)`, `new=$(git commit-tree "$tree" -m "prune: keep <list>")` (no parent),
  then `git push --force-with-lease=snapshots:<sha of origin/snapshots before> origin
  "${new}:refs/heads/snapshots"`. No other ref is ever force-pushed. Files outside the pruned
  directories survive.
- `K3DM_HUB_DATA_PRUNE_DRY_RUN=1` prints `keep:` and `prune:` lines and pushes nothing.
- Remove the unused `K3DM_HUB_DATA_KEEP`.
- `make hub-data-prune` (runs it alone; `DRY_RUN=1` maps to the dry-run variable).
- If the prune fails after a successful export push, `hub_data_export` returns non-zero with
  `[hub-data] export <ts> pushed; prune failed`.

### D4 — Scheduled run: `hub_data_export_scheduled` + launchd

- **New public function `hub_data_export_scheduled`:**
  - lock: `mkdir "${K3DM_HUB_DATA_DIR}/export.lock"`; if it exists, log
    `[hub-data] another export is running` and exit 0 without metrics; remove on EXIT. The manual
    `hub_data_export` takes the same lock.
  - `GIT_SSH_COMMAND='ssh -o BatchMode=yes -o ConnectTimeout=15'` so a key that needs a passphrase
    fails fast instead of hanging.
  - runs `hub_data_export` (export → D6 → push → D7 → D3), then pushes metrics (below), then exits with the export's
    status.
- **Metrics** to `K3DM_HUB_DATA_PUSHGATEWAY_URL` (default
  `http://localhost:19094/metrics/job/k3dm-hub-data-export`) with `curl --fail --data-binary`
  using **POST** (`-X POST`), so a failed run does not erase the last-success series:
  - always: `k3dm_hub_data_export_last_run_timestamp_seconds`,
    `k3dm_hub_data_export_last_run_success` (1/0);
  - on success only (D7 verified and D3 succeeded):
    `k3dm_hub_data_export_last_success_timestamp_seconds`, `k3dm_hub_data_export_exports_kept`,
    `k3dm_hub_data_export_bytes` (size of the new export directory).
  A metrics-push failure is logged and does not change the exit code.
- **launchd template** `scripts/etc/launchd/com.k3d-manager.hub-data-export.plist.tmpl`, modelled on
  `com.k3d-manager.prometheus-credential-rotator.plist.tmpl`: `ProgramArguments` =
  `{{K3D_MANAGER_PATH}} hub_data_export_scheduled`; `StartCalendarInterval` Hour 3, Minute 30
  (launchd runs a missed slot on wake, so a sleeping laptop exports when it wakes);
  `RunAtLoad` false; `EnvironmentVariables` HOME and the same PATH;
  log `{{HOME}}/Library/Logs/k3dm-hub-data-export.log`.
- **Install / remove:** `hub_data_export_schedule` and `hub_data_export_unschedule` (render with
  `sed` as `_observability_install_prometheus_rotator` does; `launchctl bootout` then
  `bootstrap gui/$(id -u)`). Make targets `hub-data-export-schedule`,
  `hub-data-export-unschedule`, `hub-data-export-setup`, `hub-data-prune`. The operator runs
  them; Claude and Codex never run them live.

### D6 — Integrity before upload (pulled forward from v1.46.0 D1)

- `_hub_data_encrypted_checksum` lists **every** file in the export directory except
  `SHA256SUMS` itself: `*.age`, `*.age.part-*`, `pv-pvc.yaml` and `inventory.json`.
- **New helper `_hub_data_verify_export <dir>`:** every `SHA256SUMS` line verifies, and the set of
  files in the directory equals the set in the manifest. An extra or missing file fails with
  `[hub-data] export <ts> does not match its manifest: <file>`.
- Each `*.age` (after re-joining parts in a temp file, then deleting it) passes `age`'s header
  check without decrypting: the first line is `age-encryption.org/v1`. The M4 has no identity and
  must not need one.
- `hub_data_export` runs it before `git commit`; a failure pushes nothing.
- `hub_data_restore` uses the same helper before decrypting (replaces today's manifest-only loop,
  `hub_data.sh` restore checksum step), so a `.age` missing from the manifest is refused.

### D7 — Verify the remote copy before marking success

After `git push origin snapshots`:
1. `git ls-remote origin refs/heads/snapshots` must equal the commit just pushed (git object ids
   are content hashes, so equality proves GitHub holds exactly that tree);
2. a **fresh** clone in a separate stage directory,
   `git clone --depth 1 --filter=blob:none --no-checkout --branch snapshots`, then
   `git checkout <sha> -- snapshots/<ts>`, fetches only the new export's blobs, and
   `_hub_data_verify_export` passes on it. This proves the copy can be downloaded and is intact,
   not just that a ref moved.

A failure returns non-zero with `[hub-data] export <ts> pushed but the remote copy did not
verify: <reason>`; no success metric is written and nothing is pruned.

### D5 — Alerts

Add to `scripts/etc/argocd/platform-ops/prometheusrule.yaml`, group `dr.alerts`, labels
`{group: dr, severity: warning}` (email only, like `DRDrillFailed`):
- `HubDataExportFailed`: `k3dm_hub_data_export_last_run_success == 0`, `for: 10m`.
- `HubDataExportStale`: `time() - k3dm_hub_data_export_last_success_timestamp_seconds > 129600`
  (36 h), `for: 30m`.
- `HubDataExportNeverRan`: `absent(k3dm_hub_data_export_last_success_timestamp_seconds)`,
  `for: 48h`.

## Part B — One-command restore (`make hub-data-recover`, `make hub-recover-all`)

**Added:** 2026-10-10, operator: "should be implemented in this release." Part B is dispatched
**after Part A lands**, as its own Codex task. It reuses Part A's D2 (context pin) and D6
(`_hub_data_verify_export`).

### Why the 5-step runbook is not safe to automate as written

Read-only checks on the live hub, 2026-10-10:
- `deployment/postgres-keycloak` is owned by the ArgoCD Application `shopping-cart-identity`
  (namespace `cicd`, tracking id `shopping-cart-identity:apps/Deployment:identity/postgres-keycloak`).
  Auto-sync would put the replicas back while a claim is being replaced. `statefulset/vault` and
  `statefulset/openldap` are Helm-managed.
- `hub_data_restore` always applies `scripts/etc/dr/postgres-keycloak.yaml`, the **drill's** postgres
  (no password, built for a throwaway cluster). On the real hub that would replace the GitOps
  deployment.
- After `make hub-recover`, the restored Vault still holds the **old** cluster's
  `auth/kubernetes/config` (CA and reviewer JWT), so every ESO login fails. The in-cluster
  `vault-unseal` Secret, the `k3d-manager-vault-unseal` Keychain cache and the `vault-root` Secret
  all belong to the freshly initialised Vault, which no longer exists once its data is replaced.

### B0 — Non-negotiable safeguards (operator review, 2026-10-10)

| # | Safeguard | How Part B meets it |
|---|---|---|
| S1 | Explicit target validation | Context pin (D2) **and** cluster identity: the context's API server must be the local k3d load balancer of `K3DM_HUB_DATA_CLUSTER` (default `k3d-cluster`) — the `k3d-<cluster>-serverlb` container exists on this Mac and publishes the port in the context's `server` URL — and `k3d-<cluster>-server-0` must be running locally. The resolved context, server URL and node list are printed before approval. |
| S2 | Secure key handling | The age identity is read with `read -rs`, held in one shell variable, given to `age` only through a process substitution, and `unset` in the EXIT trap (success and failure). Never Keychain, file, argv, env of child processes, log or `set -x` (`_no_trace`). |
| S3 | Fail-fast and resumable | Every step writes a checkpoint `~/.k3dm/hub-recover/<run_id>/steps.jsonl` (`step`, `started`, `finished`, `rc`). `RESUME=<run_id>` continues from the first unfinished step. **Destructive steps (4 restore claims, 6 re-point Vault) are never repeated automatically:** if one started and did not finish, resume stops and requires `REDO_STEP=<n>` plus the approval again. |
| S4 | Backup validation | `_hub_data_verify_export` (D6: checksums, manifest equals directory, age headers) **plus compatibility:** the export's `inventory.json` gains `format: 2` and `images` (the running image of vault, postgres-keycloak and openldap at export time). Restore refuses when an image's **major** version differs from the target's, or when an expected claim is missing from `pv-pvc.yaml`. An export without `format: 2` is refused unless `K3DM_HUB_DATA_ALLOW_LEGACY_EXPORT=1`. |
| S5 | Data restoration proof | Counts are not proof. The export inventory (Part A's list-only login, policy widened to **`read` on `secret/metadata/*`**, still no access to secret data) gains `vault_keys`: every KV key path, recursively, with its `current_version`. Keycloak gains `keycloak_usernames_sha256` and LDAP `ldap_dns_sha256` (SHA-256 of the sorted list; no names stored). Verification compares all three exactly. No secret value is read at export or verify. |
| S6 | Production approval | Approval is typed at the TTY, not a make variable: after preflight prints the target (S1), the export, its age, and **live vs export** counts, the operator types the export timestamp. `hub-recover-all` asks once, before the rebuild, and the approval is recorded in the report. |

**One engine for the drill and the restore.** The drill and the real restore must use the same
code: restore (`hub_data_restore`), unseal (`hub_data_unseal_dr`) and **verify**
(`hub_data_verify`, moved from `bin/dr-drill` V1–V5 into `hub_data.sh`, extended with S5 and
V8). `bin/dr-drill` keeps only what is drill-specific: the throwaway cluster, V0 egress, V6
budget, V7 age. A test asserts `bin/dr-drill` defines no `_dr_drill_v1`…`_dr_drill_v5`.

**Stages and orchestrator.** `hub-recover` (rebuild + credentials, existing) and
`hub-data-recover` (data) stay independently runnable and tested; `hub-recover-all` is the
orchestrator. (The name `hub-restore` is taken by the existing Keychain credential restore, so it
is not reused.)

**Auditable report.** `~/.k3dm/hub-recover/<run_id>/report.json`: run id, host, operator
(`id -un`), k3d-manager commit, target (S1), export timestamp and `SHA256SUMS` digest, approval
time, each step with start/finish/rc, every check, and `rto_seconds`. Written on failure too.

### B1 — `hub_data_recover` (M4, Terminal.app, attended)

Steps, each logged as `[hub-recover] Step N/9 — …`; any failure stops, runs the EXIT cleanup and
exits non-zero:

1. **Preflight.** Interactive TTY (`[[ -t 0 ]]`); pinned hub context (D2) reachable; the three
   workloads exist; the chosen export (newest, or `K3DM_HUB_DATA_EXPORT=<ts>`) passes
   `_hub_data_verify_export`. Print the export timestamp and its age, then the S1 target, S4 compatibility and S6 approval. A wrong or empty
   approval exits 2 having changed nothing. Refuse on the M2 unless the context is `k3d-dr-drill`
   (`K3DM_HUB_DATA_RECOVER_ALLOW_DRILL=1`), so Part B can be rehearsed there.
2. **age identity.** Prompt with `read -rs` from the TTY; check it starts with `AGE-SECRET-KEY-1`
   without printing it; keep it in a shell variable only, and `unset` it on EXIT. It never goes to
   the Keychain, a file or argv. `_hub_data_restore_one` uses that variable when it is set, and the
   Keychain otherwise (the drill path is unchanged). This replaces runbook steps 2 and 4 (store the
   key in the M4 Keychain, then delete it).
3. **Pause ArgoCD** for `shopping-cart-identity` with the same mechanism `observability_pause`
   uses (`spec.syncPolicy.automated: null`, and whatever it does for ApplicationSet-generated
   apps). Resume in the EXIT trap, on success and on failure.
4. **Restore the claims** with `HUB_DATA_RESTORE_TARGET=hub`: identical to the drill restore,
   except `_hub_data_apply_keycloak` is **skipped** and the existing postgres-keycloak deployment is
   required instead. A test asserts the drill manifest is never applied in hub mode.
5. **Unseal** with the `k3dm-vault-unseal-dr` shards. Move `_dr_drill_wait_vault` and
   `_dr_drill_unseal` from `bin/dr-drill` into `hub_data.sh` as `_hub_data_wait_vault` and
   `hub_data_unseal_dr` (message prefix as an argument); `bin/dr-drill` calls them. Behaviour and
   messages stay the same; the existing dr_drill.bats tests must pass unchanged apart from the
   function names.
6. **Re-point Vault to the rebuilt cluster**, using a root token from `_hub_data_generate_root`:
   - rewrite `auth/kubernetes/config` exactly as `scripts/plugins/vault.sh` does at enable time
     (`token_reviewer_jwt` from the pod's service-account token, `kubernetes_host`,
     `kubernetes_ca_cert`);
   - replace the `vault-unseal` Secret and the `k3d-manager-vault-unseal` Keychain cache with the
     DR shards, through the existing writers in `vault.sh` (do not invent a new format);
   - store this root token as the `vault-root` Secret and its `k3dm-vault-root-token` Keychain
     mirror through the existing `hub_recovery.sh` mirror code. It is the hub's working root token
     from now on, so it is not revoked.
7. **Refresh dependents:** `rollout restart deployment/keycloak -n identity`, and annotate every
   ExternalSecret with `force-sync=<epoch>`.
8. **Verify on the hub:** V1 unsealed; V2 `hub_data_verify_vault_paths`; V3 Keycloak users and V4
   LDAP entries equal the inventory; V5 placement; **V8** no ExternalSecret reports
   `SecretSyncedError` five minutes after step 7. Print a table of the checks.
9. **Report:** write the B0 auditable report; resume ArgoCD (also done in the EXIT trap).
