## Problem

While travelling, the operator may have only the iPad Air with them. After a rotation, the new service passwords reach
the M4 as an `age` bundle that only the M4's Keychain identity can open (`make password-bundle-show`). The iPad cannot
hold that identity: iPadOS has no `age` or Keychain integration in this project, and a copy of the key on a device that
is easier to lose than a laptop widens the blast radius. The iPad needs a way to **see** the passwords without holding
anything that can decrypt them.

## Correction to the roadmap entry

The roadmap paragraph (2026-11-21) says "an iOS SSH client". v1.45.0 part B makes the console a **browser-rendered SSH**
app behind Cloudflare Access with short-lived certificates (part B outline item 2, capture C5). Safari on the iPad is
the client: no SSH app, no SSH key, no `cloudflared` on the iPad. A native iOS SSH client cannot present an Access
short-lived certificate without `cloudflared`, which has no iPadOS build. Using one would need a second, key-based
login path into the console, which v1.45.0 forbids. Native clients are a non-goal (What NOT to Do). The roadmap line is
corrected in the same commit as this spec.

## How it works (no new login path)

1. Safari on the iPad opens the M4's console hostname (part B, placeholder only in the repo). Cloudflare Access asks for
   the operator's GitHub login. Access issues a short-lived certificate, and the browser terminal opens.
2. The part C gate asks for the TOTP code from the operator's phone, then attaches to tmux `work` (part C 3.5).
3. In a `work` pane, the operator runs `make console-show-passwords`. It decrypts the bundle on the M4 and shows the
   passwords in a pager on the terminal's alternate screen. On `q`, or after the display timeout, the screen clears
   and nothing is left in tmux scrollback except one status line (exit code, reason, bundle age), which is also
   appended to a status log with no secrets. `make console-show-passwords CHECK=1` runs every step without showing
   anything: the pre-travel check, and what Claude runs (with the operator's go) when something fails.

Everything that can decrypt stays on the M4. Losing the iPad exposes at most an Access session (6 hours, part B), and
using that session still needs the TOTP.

## Behaviour

1. **`bin/k3dm-console-show-passwords`** (new, `set -euo pipefail`, `set +x` before any secret is handled):
   1. Source: `--source bundle` (default; runs `./scripts/k3d-manager password_bundle_show`) or `--source hub` (runs
      `make -s show-service-passwords`, for the M5 console). Any other value: exit 2, usage on stderr.
   2. Refuses (exit 3, one stderr line, nothing decrypted) unless stdout is a terminal and `$TMUX` is set: the
      scrollback hygiene below assumes a tmux pane.
   3. Keychain precheck (bundle source only): `security show-keychain-info` with no `-w`, exit code only. On a
      non-zero code: exit 4 and one stderr line: the login Keychain is not available in this tmux server (typically
      a server the console gate started, part B C16: rc=36). It names the two ways out (attach to a server started
      at the desk, or run `security unlock-keychain` yourself). It never runs `unlock-keychain` and never reads a
      password (decision D2).
   4. The source's stdout goes straight into `less` through a pipe: no temp file, no variable holding the plaintext.
      The `less` environment is `LESSSECURE=1`, `LESSHISTFILE=-`, `LESS` unset so `less` uses the alternate screen (no `-X`), and
      prompt text `service passwords: q to close`. The source's stderr (the bundle age warning) goes to the pane
      before the pager starts, so the warning stays visible and holds no secret.
   5. Display timeout: `K3DM_CONSOLE_PASSWORDS_TIMEOUT` seconds (default 120, integer 10-900, otherwise exit 2).
      When it expires, `less` and the source are killed and the script exits 5 with `display timed out`.
   6. On every exit after the pager has started (q, timeout, INT, TERM, HUP, source failure), the script runs
      `tmux clear-history -t "$TMUX_PANE"` and clears the visible screen. This happens in an `EXIT` trap that also
      kills any child left over.
   7. Exit code: 0 when the pager closed with `q` and the source exited 0. Otherwise the source's code (1 on a
      missing or unreadable bundle) or one of 2-5 above. Nothing secret appears on stderr on any path.
   8. **Status line (rev 1.1).** On every exit, including the early exits 2-4, the script prints one line to stderr,
      after the clear-history and screen clear of 1.6 so the line survives them:
      `console-show-passwords: exit <code> <reason> (source=<s>, mode=<show|check>, generated_at=<ts|->, age=<hours|->h)`.
      `reason` is one of `closed`, `timeout`, `signal`, `source-failed`, `bad-argument`, `not-tty`, `not-tmux`,
      `keychain-unavailable`, `log-unsafe`, `check-ok`. For the bundle source, `generated_at` and `age` come from
      `service-passwords.meta` (non-secret; the same awk read `password_bundle_show` does), never from the decrypted
      stream. For the hub source both are `-`. This line is what Claude reads with `capture-pane` when debugging.
   9. **Status log (rev 1.1).** The same fields are appended as one line per run, with an ISO-8601 UTC timestamp, to
      `${K3DM_STATE_DIR:-$HOME/.local/share/k3d-manager/state}/console-show-passwords.log`. The directory is created
      `0700` and the file `0600` if absent; they are refused (exit 2, reason `log-unsafe`, status line
      still printed, nothing decrypted) when the file is a symlink or not owned by the user. The log keeps its last 500
      lines. Only the allow-listed fields of 1.8 (plus `pager_started=yes|no` and, in check mode, `lines=<n>`) are
      written; no text from the source's stdout or stderr ever reaches the log.
   10. **`--check` (rev 1.1).** `--check` (Makefile `CHECK=1`) runs every step of a show except the display: the tty and
       tmux checks (same codes 3), the Keychain precheck (4, bundle only), the meta read (bundle age), and the source
       with its stdout piped to `wc -l` only. It never starts `less`, never runs clear-history (nothing was shown),
       prints the 1.8 status line with reason `check-ok` or the failing reason, appends the log line with
       `lines=<n>`, and exits 0 only if every step passed and `n` > 0. It is the pre-travel check and the debug tool:
       with the operator's go, Claude may send it into an idle pane and read the status line.
2. **`Makefile`**: target `console-show-passwords` with optional `SOURCE=bundle|hub`, calls the script; added to
   `.PHONY` and to `make help` under the password-bundle group.
3. **`docs/howto/web-console-sshd.md`**: new section "From an iPad". It covers Safari only; opening the console
   hostname; the GitHub login; the TOTP; running `make console-show-passwords CHECK=1` before travel and `make console-show-passwords`; `q` to close; how to read
   the status line and the log, and how to hand them to Claude; the Keychain message and
   what to do about it; and keeping the iPad from caching anything (close the Safari tab after use, do not add the
   console to the Home Screen as a web app, and close the pager before switching apps so the app switcher snapshot
   does not hold the passwords; residual R-SNAPSHOT). It also says what to do when the iPad is lost: run part B
   revoke for the M4 console and end the Access session in the Cloudflare dashboard. No password rotation is needed,
   because the iPad never held a decryptable copy.
4. **`docs/howto/service-password-travel-bundle.md`**: one paragraph pointing to that section for iPad-only travel.
5. **`docs/roadmap.md`**: the v1.46.0 plan 6 paragraph says "Safari (browser-rendered SSH)" instead of "an iOS SSH
   client" and links this file.
6. **`CHANGELOG.md`**: one line under the v1.46.0 Added section.

## Decisions (operator, before dispatch; recommended first)

- **D1. Where the passwords are shown:** operator chose (a) with the rev 1.1 debug aids (2026-11-21). (a, recommended) a pager on the alternate screen with a timeout, scrollback
  cleared on exit; (b) plain output in the pane, as `make password-bundle-show` does today. Under (b) the plaintext
  stays in `work`'s 50000-line history, where an agent reading the pane would see it, and agents in this project do
  read `work` panes with `tmux capture-pane`.
- **D2. Locked Keychain:** (a, recommended) explain and stop; the operator decides whether to type the macOS login
  password into `security unlock-keychain` over the browser terminal (R-TTY of part C applies to that password);
  (b) the script runs `security unlock-keychain` itself. (b) puts a password prompt inside a tool and is not
  recommended.
- **D3. M5 hub source:** (a, recommended) include `--source hub` now (a few lines, same hygiene); (b) M4 bundle only.

## Proof of external behaviour (owed before dispatch)

- **P1.** In a tmux server started by the console gate (part C installed, or the part B scratch label), with the M4
  enrolled: `make password-bundle-show >/dev/null 2>&1; echo $?`, run by the operator, exit code only. C16 recorded
  `show-keychain-info` rc=36 next to an attribute-only lookup rc=0, but no `-w` read was run. P1 settles whether the
  bundle can be opened from a gate-started server, which decides whether the precheck in Behaviour 1.3 may block.
  If P1 is 0, the precheck becomes a warning (spec rev).
- **P2.** iPad Safari on the browser-rendered terminal (after part B C5 on the iPad, not a desktop browser):
  whether `less` draws on the alternate screen and returns to the prior screen on `q`, whether `q` reaches `less`
  from the on-screen and the Magic Keyboard, and whether Ctrl-C reaches the pty (part B C5 proves this for one
  browser; P2 repeats it on iPadOS Safari).
- **P3.** tmux 3.8 on the M4: `alternate-screen` is `on` (read 2026-11-21 on the M4: `on`, `history-limit` 50000),
  and text drawn on the alternate screen is absent from `capture-pane -S -` after `less` exits. A scratch tmux
  server (`-L k3dm-p3`) with a non-secret marker string, no real passwords.
- **P4.** `tmux clear-history -t <pane>` run from inside that same pane empties `capture-pane -p -S -` for that pane
  (scratch server, marker string).

Every capture records host, date, `tmux -V`, `less --version` (M4 2026-11-21: less 668), `sw_vers` and the iPadOS
version, and is saved under `docs/captures/` after the operator reads it.

## Residuals (accepted, stated in the how-to)

- **R-VIEW.** While the pager is open, a process running as the operator can `capture-pane` the visible screen.
  This is the same K1 = a boundary as part C: same-user secrecy is not claimed. The timeout bounds how long the
  screen is exposed.
- **R-SNAPSHOT.** iPadOS keeps an app switcher snapshot of Safari. The how-to says to close the pager before leaving
  Safari. The project cannot enforce it.
- **R-TTY** (part C) applies to a Keychain password the operator chooses to type under D2 (a).

## What NOT to Do

- No `age` identity, SSH key, Access service token or password copy on the iPad. No new login path into the console,
  no key-based or native-client access, no change to part A, B or C files.
- No temp file, log line, Pushgateway metric, Slack message or variable holding plaintext. The status line and status
  log carry only the allow-listed fields of Behaviour 1.8 and 1.9. Never `set -x` in the
  script.
- Never run `security unlock-keychain`, `find-generic-password -w` or `dump-keychain` in the script.
- Tests never call the real `age`, `security`, `tmux` or `make show-service-passwords`. They use stubs on `PATH`
  built from the P3/P4 captures and a scratch `HOME`. Fixtures assert the stub path before each case.
