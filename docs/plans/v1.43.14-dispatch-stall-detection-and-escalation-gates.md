## Problem and motivating incident

The v1.43.14 headless macOS Vault CA trust bug (`docs/bugs/2026-11-02-acg-up-stalls-at-system-keychain-trust.md`) consumed repeated Terra dispatch runs over roughly two days. The operator had to intervene to demand phase A diagnosis, phase B bounded containment, phase C privileged boundary review, objective tests and independent evidence. Phase A remained root-cause-inconclusive and Phase B passed offline tests but was not landed or live-verified at the time of this request. The system did not autonomously recognize diminishing returns, demand a revised plan or route a high-risk scope expansion to review.

Dispatch currently records attempts, resumes, interventions, verification evidence, and change-size metrics, but they do not form an **enforced task-level decision state machine**. Repeated execution without new evidence should not silently consume the next run. An AI worker's statements about progress or completion must not grant exemption.

## Goals

1. Automatically distinguish **productive continuation** from repeated **rework without new independently checkable evidence**.
2. Require an explicit, measurable acceptance contract before a new implementation task launches.
3. Detect changes beyond originally approved file/path and privilege scope and require a scope review before further implementation or landing.
4. Prevent tests-only success from becoming `LIVE-VERIFIED` unless real deployment behavior is supported by separate live evidence.
5. Escalate repeated failed attempts or repeated design revisions to an independent architectural reviewer, with an operator decision only where actually needed.
6. Surface elapsed time, run count, rework, escalation, gate reasons, and human interventions in existing dashboards to measure autonomy, not merely token expenditure.

## Ownership and enforcement

The **coordinator/dispatcher** owns task state and policy enforcement; workers cannot self-authorize exceptions. Source-of-truth inputs are the existing append-only ledger, task spec at pinned revision, Git diff, independent test/verification artifacts, explicit approvals, and recorded human interventions. Read-only advice is allowed while a gate is blocked. Reuse existing task directories and SHA-bound evidence. Avoid a second ledger or new paid service.

Policy is deterministic and versioned. LLMs may suggest hypotheses, acceptance criteria and reviewers, but cannot assert that a gate passed, grant elevated permissions, dismiss a recorded failure or mark live verification.

## Mandatory gates

### G0 — Acceptance contract before implementation

- For newly dispatched implementation tasks, require a stable task/spec identifier and pinned spec SHA, approved file/path scope, goals, explicit positive acceptance cases, negative/regression cases, verification commands, objective evidence artifacts, and live-evidence requirements (or an explicit `not applicable` with reason).
- Fail closed for new implementation dispatch if the contract is absent or unparseable. Existing running tasks are grandfathered until their **next resume**, where an operator-approved migration/legacy policy is required. Do not retroactively rewrite old ledger entries.
- A coordinator can prepare a draft plan without permission to implement. For diagnosis-only tasks, use a typed `diagnostic` contract with hypotheses, evidence requests and defined exit conditions (including `inconclusive`), not fabricated fix acceptance.

### G1 — Repeated unsuccessful attempts without new evidence

- Default threshold: **two consecutive unsuccessful implementation attempts** on the same task at the same approved spec baseline, without independently checkable new evidence. Trigger a `STALLED_REPLAN_REQUIRED` gate **before launching a third attempt**.
- Qualifying unsuccessful attempt: failed verification/landing, non-zero worker exit, or a documented objective correction/rework when the next run would repeat the same unresolved issue. A routine `continue_prompt`, quota continuation, model switch, or normal checkpoint is **not automatically a failure**.
- New evidence is a persisted, timestamped artifact tied to task/run and code or environment revision: a distinct falsifiable finding, captured process observation, independently executed diagnostic, reproducible failing case, acceptance result, or reviewed narrowed hypothesis. Reworded summaries, token usage, more tests without a demonstrated gap, self-reported progress, or another model repeating the same assertion do **not** reset the counter.
- Gate requires a revised hypothesis and diagnostic/implementation plan that cites previous attempts, the genuinely new evidence (if any), failed assumptions, changed strategy, bounded next experiment, explicit stop condition, and independent reviewer endorsement. If evidence is absent, the plan must say so and choose a discriminating diagnostic before further patching.
- Preserve historical attempt count and rationale after the gate is cleared; resetting thresholds by renaming the slug, changing model, or creating a worktree is forbidden. Associate aliases with stable canonical task identity.

### G2 — File/scope expansion

- At dispatch snapshot the approved file/path set and risk class. Before `resume`, `land`, and any privileged action, compute actual affected paths using a Git-aware full diff including renames, additions, deletions, generated files, submodules and changed external repositories. Measure against pinned spec scope, not the worker's newly edited spec.
- Any new path outside scope pauses the mutating operation with `SCOPE_REVIEW_REQUIRED`. Any change to sudoers, credentials, Vault, IAM/RBAC, approvals, CI gates, security policy, root LaunchDaemons, executable installation, destructive operations, or privileged tool contracts additionally requires a **high-risk approval** regardless of path count.
- The scope reviewer must record which files are indispensable, why, intended security/compatibility effects and paired negative/positive tests. Approve a narrowly revised spec as a new SHA-bound baseline or split unrelated work into another spec. **No automatic approval** simply because an agent says the change is necessary.
- Distinguish observed committed/uncommitted task-tree changes, approved revisions and landed changes. Diff failure or unknown external-repo scope is `UNKNOWN_BLOCKED`, not `in scope`.
- This is a scope gate, **not** a replacement for the future v1.48.1 semantic change approval gate. Use the existing operator approval path for high-risk changes; do not claim branch protections enforce approvals if they do not.

### G3 — Verification truthfulness

- Preserve distinct states: `IMPLEMENTED`, `OFFLINE_TESTED`, `INDEPENDENT_VERIFIED`, `LANDED`, `DEPLOYED`, `LIVE_VERIFIED`. These are not interchangeable, and a later state requires its own source evidence.
- A passing BATS/pytest/shellcheck result or an agent's text report may satisfy only the matching offline gate. `LIVE_VERIFIED` requires a separately captured live test against the intended environment, exact deployed artifact/revision, timestamp, observed expected behavior and immutable evidence reference, with explicit coverage limitations.
- If live work is not authorized, record `LIVE_PENDING`. Do not block an explicitly offline-only authorized landing solely because live verification is pending, but never label it live-verified.
- Reuse existing `verify --evidence` validation and the existing bug/dispatch status fields; no worker-authored plain-language claim can promote status. Reject absent/mismatched source SHA, missing captured output, stale or fabricated pass evidence, and misleading coverage.

### G4 — Independent architectural escalation

- Repeated design changes after a stall gate, two rejected revised plans, or a high-risk scope expansion without a documented boundary decision creates `ARCH_REVIEW_REQUIRED`. An independent reviewer must not be the same worker or a copy of its self-review; record reviewer identity, model/vendor when known, evidence seen, recommendations, unresolved risks, and a bounded decision.
- Reviewer may return `narrow_fix`, `diagnose_first`, `separate_security_spec`, `change_architecture`, or `operator_decision_required`. Escalation is not permission to increase privileges or spend unlimited tokens.
- Deduplicate repeated escalation notices in the existing Slack task thread; send a concise reason and links, with operator approval only for risk, scope, architecture or deployment decisions. Reviewer unavailability blocks further mutating work but permits read-only diagnostics under existing policy.

- Add a read-only `dispatch gate-status --slug SLUG` view: current state, attempt streak, evidence SHA/paths, blocking reasons, approved scope/spec SHA and next required action.
- Proposed `dispatch replan --slug SLUG --plan FILE --evidence FILE` records a reviewed revision; `dispatch scope-review --slug SLUG --decision approve|split|deny --evidence FILE` requires authenticated coordinator/operator authorization appropriate to risk. Names are provisional; inspect existing CLI before choosing them.
- Add append-only typed events `attempt_assessed`, `stall_gate`, `replan_reviewed`, `scope_gate`, `architecture_review` and `gate_cleared`, keyed by canonical task, run, baseline SHA, assessor and supporting evidence digest. Existing `start/resume/codex_exit/verify/land/intervention` events remain authoritative and compatible.
- Protect transitions from concurrent resumes by an atomic task lock. If evidence integrity, event ordering, or lock state is unknown, block mutations visibly, without deleting worktrees or abandoning tasks.

## Acceptance contract

**must**
1. A task with two consecutive qualifying failed/rework runs and no new evidence is blocked before a third launch; a reviewed replan with a discriminating diagnostic clears only the appropriate gate.
2. Two legitimate progress/quota-continuation resumes with verifiable new evidence are not falsely labeled stalled.
3. Unapproved changes to any originally unlisted file or privilege boundary cannot be resumed into further implementation or landed, including direct adapter calls and rename/cross-repo cases.
4. A reviewed narrow scope revision is bound to a fresh spec SHA and preserves the original scope/attempt ledger.
5. Offline independent PASS cannot yield LIVE_VERIFIED; missing or stale live artifacts remain LIVE_PENDING/UNKNOWN.
6. Repeated rejected replans trigger independent architecture review; agent self-approval and reviewer-identity spoofing are refused.
7. Metrics and UI reconstruct the causal sequence and clearly distinguish rework, useful investigation, idle wait and human approvals.
8. Existing authorized tasks can continue after successful gate completion; no code loss, auto-abandon, or automatic production action.
9. An emergency operator bypass, if proposed, requires independently authenticated, expiring, reasoned, auditable approval and cannot grant unauthorized privileged actions. No silent env-var bypass.

**must_not**
1. No double counting automatic retries or routine resumes as failed outcomes.
2. No reset of attempt streak by task alias, worktree recreation or model/vendor switch.
3. No trusted verification from unverified worker claims, edited artifact timestamps or tests that merely assert the presence of a code string.
4. No implicit release approval, merge, privilege escalation, deletion, or automatic escalation to a more expensive model.
5. No release slot exemption for unrelated features: this is a one-time P0 exception specifically approved for v1.43.14.

**evidence**
- E1: controlled dispatch-ledger fixtures: two failures, third run denied, reviewed replan admitted, preserved attempts and receipts.
- E2: clean progress/resume and quota-window fixtures plus task alias, concurrent resume and missing/corrupt evidence cases.
- E3: scope drift fixtures including renamed file, protected sudoers file, cross-repo modification and approved SHA-bound scope revision; rejected operations show zero mutation.
- E4: offline test PASS versus missing/mismatched live artifact, signed/captured verification provenance, and dashboard UNKNOWN/coverage tests.
- E5: independent red-on-pre-fix / green-on-fixed verification, focused BATS/pytest, ShellCheck for touched shell, diff check, staged agent audit, and operator-reviewed live dashboard evidence when separately approved.
