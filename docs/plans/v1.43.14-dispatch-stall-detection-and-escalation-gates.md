## Problem and motivating incident

The v1.43.14 headless macOS Vault CA trust bug (`docs/bugs/2026-11-02-acg-up-stalls-at-system-keychain-trust.md`) consumed repeated Terra dispatch runs over roughly two days. The operator had to intervene to demand phase A diagnosis, phase B bounded containment, phase C privileged boundary review, objective tests and independent evidence. Phase A remained root-cause-inconclusive and Phase B passed offline tests but was not landed or live-verified at the time of this request. The system did not autonomously recognize diminishing returns, demand a revised plan or route a high-risk scope expansion to review.

Dispatch currently records attempts, resumes, interventions, verification evidence, and change-size metrics, but they do not form an **enforced task-level decision state machine**. Repeated execution without new evidence should not silently consume the next run. An AI worker's statements about progress or completion must not grant exemption.

## Goals

1. Automatically distinguish **productive continuation** from repeated **rework without new independently checkable evidence**.
2. Require an explicit, measurable acceptance contract before a new implementation task launches.
3. Detect changes beyond originally approved file/path and privilege scope and require a scope review before further implementation or landing.
4. Prevent tests-only success from becoming `LIVE-VERIFIED` unless real deployment behavior is supported by separate live evidence.
5. Escalate repeated failed attempts or repeated design revisions to an independent architectural reviewer, with an operator decision only where actually needed.
6. Surface elapsed time, run count, rework, escalation, gate reasons, and human interventions in existing dashboards to measure autonomy, not merely token expenditure.

## Ownership and enforcement

The **coordinator/dispatcher** owns task state and policy enforcement; workers cannot self-authorize exceptions. Source-of-truth inputs are the existing append-only ledger, task spec at pinned revision, Git diff, independent test/verification artifacts, explicit approvals, and recorded human interventions. Read-only advice is allowed while a gate is blocked. Reuse existing task directories and SHA-bound evidence. Avoid a second ledger or new paid service.

Policy is deterministic and versioned. LLMs may suggest hypotheses, acceptance criteria and reviewers, but cannot assert that a gate passed, grant elevated permissions, dismiss a recorded failure or mark live verification.

## Mandatory gates

### G0 — Acceptance contract before implementation

- For newly dispatched implementation tasks, require a stable task/spec identifier and pinned spec SHA, approved file/path scope, goals, explicit positive acceptance cases, negative/regression cases, verification commands, objective evidence artifacts, and live-evidence requirements (or an explicit `not applicable` with reason).
- Fail closed for new implementation dispatch if the contract is absent or unparseable. Existing running tasks are grandfathered until their **next resume**, where an operator-approved migration/legacy policy is required. Do not retroactively rewrite old ledger entries.
- A coordinator can prepare a draft plan without permission to implement. For diagnosis-only tasks, use a typed `diagnostic` contract with hypotheses, evidence requests and defined exit conditions (including `inconclusive`), not fabricated fix acceptance.

### G1 — Repeated unsuccessful attempts without new evidence

- Default threshold: **two consecutive unsuccessful implementation attempts** on the same task at the same approved spec baseline, without independently checkable new evidence. Trigger a `STALLED_REPLAN_REQUIRED` gate **before launching a third attempt**.
- Qualifying unsuccessful attempt: failed verification/landing, non-zero worker exit, or a documented objective correction/rework when the next run would repeat the same unresolved issue. A routine `continue_prompt`, quota continuation, model switch, or normal checkpoint is **not automatically a failure**.
- New evidence is a persisted, timestamped artifact tied to task/run and code or environment revision: a distinct falsifiable finding, captured process observation, independently executed diagnostic, reproducible failing case, acceptance result, or reviewed narrowed hypothesis. Reworded summaries, token usage, more tests without a demonstrated gap, self-reported progress, or another model repeating the same assertion do **not** reset the counter.
- Gate requires a revised hypothesis and diagnostic/implementation plan that cites previous attempts, the genuinely new evidence (if any), failed assumptions, changed strategy, bounded next experiment, explicit stop condition, and independent reviewer endorsement. If evidence is absent, the plan must say so and choose a discriminating diagnostic before further patching.
- Preserve historical attempt count and rationale after the gate is cleared; resetting thresholds by renaming the slug, changing model, or creating a worktree is forbidden. Associate aliases with stable canonical task identity.

### G2 — File/scope expansion

- At dispatch snapshot the approved file/path set and risk class. Before `resume`, `land`, and any privileged action, compute actual affected paths using a Git-aware full diff including renames, additions, deletions, generated files, submodules and changed external repositories. Measure against pinned spec scope, not the worker's newly edited spec.
- Any new path outside scope pauses the mutating operation with `SCOPE_REVIEW_REQUIRED`. Any change to sudoers, credentials, Vault, IAM/RBAC, approvals, CI gates, security policy, root LaunchDaemons, executable installation, destructive operations, or privileged tool contracts additionally requires a **high-risk approval** regardless of path count.
- The scope reviewer must record which files are indispensable, why, intended security/compatibility effects and paired negative/positive tests. Approve a narrowly revised spec as a new SHA-bound baseline or split unrelated work into another spec. **No automatic approval** simply because an agent says the change is necessary.
- Distinguish observed committed/uncommitted task-tree changes, approved revisions and landed changes. Diff failure or unknown external-repo scope is `UNKNOWN_BLOCKED`, not `in scope`.
- This is a scope gate, **not** a replacement for the future v1.59.0 semantic change approval gate. Use the existing operator approval path for high-risk changes; do not claim branch protections enforce approvals if they do not.

### G3 — Verification truthfulness

- Preserve distinct states: `IMPLEMENTED`, `OFFLINE_TESTED`, `INDEPENDENT_VERIFIED`, `LANDED`, `DEPLOYED`, `LIVE_VERIFIED`. These are not interchangeable, and a later state requires its own source evidence.
- A passing BATS/pytest/shellcheck result or an agent's text report may satisfy only the matching offline gate. `LIVE_VERIFIED` requires a separately captured live test against the intended environment, exact deployed artifact/revision, timestamp, observed expected behavior and immutable evidence reference, with explicit coverage limitations.
- If live work is not authorized, record `LIVE_PENDING`. Do not block an explicitly offline-only authorized landing solely because live verification is pending, but never label it live-verified.
- Reuse existing `verify --evidence` validation and the existing bug/dispatch status fields; no worker-authored plain-language claim can promote status. Reject absent/mismatched source SHA, missing captured output, stale or fabricated pass evidence, and misleading coverage.

### G4 — Independent architectural escalation

- Repeated design changes after a stall gate, two rejected revised plans, or a high-risk scope expansion without a documented boundary decision creates `ARCH_REVIEW_REQUIRED`. An independent reviewer must not be the same worker or a copy of its self-review; record reviewer identity, model/vendor when known, evidence seen, recommendations, unresolved risks, and a bounded decision.
- Reviewer may return `narrow_fix`, `diagnose_first`, `separate_security_spec`, `change_architecture`, or `operator_decision_required`. Escalation is not permission to increase privileges or spend unlimited tokens.
- Deduplicate repeated escalation notices in the existing Slack task thread; send a concise reason and links, with operator approval only for risk, scope, architecture or deployment decisions. Reviewer unavailability blocks further mutating work but permits read-only diagnostics under existing policy.

- Treat verified provider quota exhaustion and scheduled reset separately from worker exit failure, correction rework, verification refusal, idle time, and human-driven continuation. An interrupted run is `QUOTA_PAUSED` only with provider-reported quota evidence and time; unavailable provider data is `QUOTA_UNKNOWN`, not assumed exhaustion.

### Derivation rules (fixed; both halves implement them independently)

**Reading the ledger.** A valid line is a JSON object with a numeric `ts`; anything else adds 1 to `bad_lines` and is otherwise skipped. **Line order is the order of events.** The ledger is append-only and timestamps have one-second resolution, so `ts` never breaks a tie and lines are never sorted. `--as-of TS` keeps the valid lines with `ts` at or before TS, in line order. `bad_lines` always counts the whole file.

**Tasks.** A task is a `(version, slug)` pair with at least one `start`, so coverage markers, combines and rows such as `release_merged` are never tasks. A command given `--version V` uses that pair. Otherwise it finds the slug in the ledger: one version resolves, none or several exit 2. No S1 command needs a release branch to resolve a task.

**Attempts.** A `start` after an earlier `start` of the same task begins a new attempt (the real ledger has two tasks restarted after `abandon`). Runs, unsuccessful runs, the streak, the ladder, stall state and open gates read only the lines from the task's last `start` onward. `human_interventions`, `parent` and `role` read all of the task's lines.

**Run numbers.** The latest run is set by the lifecycle events of the current attempt. `start`: its `run`, otherwise 1. `resume`: its `run`, otherwise its `n`, otherwise latest + 1. `codex_exit` and `agent_exit` are both exit events: the exit belongs to its `run`, otherwise to the latest run. For a run with several exits the last line sets its exit status. A `verify`, `land_refused` or `intervention` has no run number and belongs to the run that is latest at its line. `runs` is the number of distinct runs from `start` and `resume`.

**Ladder.** Each rung is `done`, `pending` or `unknown`. No rung implies another.

- `implemented`: `done` when the latest run's exit status is 0, otherwise `pending`.
- `offline_tested`, `deployed`, `live_verified`: `done` with a matching `state_mark` in the attempt. Otherwise `unknown` for a task outside coverage, and `pending` for the rest.
- `independently_verified`: read the last `verify` line. `done` for result `pass` with an `evidence_sha256`, `unknown` for `pass` with no digest, otherwise `pending`.
- `landed`: `done` with a `land` in the attempt, otherwise `pending`.

**Coverage.** A task is outside coverage when its first `start` line comes before the first `gate_coverage_start` line, or when the ledger as read has no such line. Line order decides an equal timestamp. Coverage affects only the three rungs with no historical source (`offline_tested`, `deployed`, `live_verified`); `implemented`, `independently_verified` and `landed` follow their own rules at any age, so an old task with no land shows `landed` `pending`.

**Unsuccessful runs.** A run is charged at the first line that gives any of these signals: an exit event with non-zero status; a `resume` with reason `correction` arriving while it is the latest run; a `verify` with result `fail` while it is the latest run; a `land_refused` with reason `tests` or `fast-gate` while it is the latest run. An `intervention` event never counts by itself, and `land_refused` with reason `rebase`, `scope` or `target_diverged` never counts.

The last `attempt_assessed` line naming a run overrides this, wherever it falls: `failed` and `rework` make the run unsuccessful, charged at the assessment's line; `progress` and `quota` make it not unsuccessful; `unknown` leaves the derived answer. An assessment naming a run the attempt does not have is ignored. `unsuccessful` lists the charged runs ascending, each once.

**Streak.** The number of unsuccessful runs that satisfy both conditions:

1. Its run number is above P, the highest run whose last assessment is `progress` with a non-null `new_evidence_sha256` (0 when none). Late assessments apply, since the evidence belongs to the run it names.
2. Its charge line comes after the last `gate_cleared` line with gate `stall` (a clear wipes charges already made, so a correction arriving after a clear counts).

Nothing else resets it: not a resume reason, not a model or agent change, not a rejected replan. `stall_gate` and `replan_reviewed` are recorded and counted but change no derived state.

**Stall state.** `closed` when the attempt has a `land` or `abandon`; `open` when the streak is 2 or more; otherwise `clear`. In S1 `open` is advisory.

**Open gates.** `open_scope` lists the attempt's `scope_gate` lines after its last `gate_cleared` with gate `scope`; `open_architecture` lists its `architecture_review` lines after its last `gate_cleared` with gate `arch`.

**Parent and role.** The last `start` or `link` line of the task with a `parent` sets both; a later one reassigns the task, and it stops being a part of the old parent.

**Next action.** The first that applies: attempt has `abandon` → `none`; stall `open` → `stall_review`; any open gate → `clear_gate`; not landed and the latest run has no exit → `wait_for_run`; not landed and its exit is non-zero → `resume_or_abandon`; not landed → `land`; `independently_verified` `pending` → `verify`; `deployed` `pending` → `deploy`; `live_verified` `pending` → `live_verify`; otherwise `none`. `unknown` rungs and `offline_tested` never drive it.

**`gate-status --json` output (exact keys).** `version`, `slug`, `as_of` (null or integer), `advisory` (always true), `ladder` (the six rungs), `stall`, `streak`, `unsuccessful`, `runs`, `human_interventions`, `open_scope` (objects: `ts`, `paths`, `risk`), `open_architecture` (objects: `ts`, `decision`, `reviewer`), `parent`, `role`, `bad_lines`, `next_action`.

### Dispatcher half

Every new command accepts `--version V` where it takes `--slug`. Every refusal exits 2 and writes nothing. Writing commands schedule metrics as existing commands do; `gate-status` never does.

- `gate-status --slug SLUG [--version V] [--json] [--as-of TS]`: read-only. Prints the fields above, and in human output a line stating the result is advisory and self-reported. Takes no lock, makes no network call, needs no release branch, and creates nothing, including a missing ledger or run directory. An unresolved slug, or a task with no `start` at or before `--as-of`, exits 2. A corrupt line is counted, not fatal.
- `mark --slug S --state STATE --sha SHA --evidence FILE --by NAME`: appends `state_mark`. Refuses if the SHA is not a commit in the task's repo; and for `deployed` and `live_verified`, if the file's `key: value` header lacks `artifact`, `environment`, `command`, or `rc: 0`, or has no `---` line followed by output. The header format matches `verify --evidence`.
- `gate-record --slug S --event EVENT ...` takes exactly these flags per event, all required unless marked:

| `--event` | Flags |
|---|---|
| `attempt_assessed` | `--run N --outcome O --assessor NAME --baseline-sha SHA`, optional `--new-evidence FILE` |
| `stall_gate` | `--runs 1,2 --reason TEXT --assessor NAME --baseline-sha SHA` |
| `replan_reviewed` | `--decision D --reviewer NAME --plan FILE --baseline-sha SHA` |
| `scope_gate` | `--paths a,b --risk R --assessor NAME --baseline-sha SHA` |
| `architecture_review` | `--decision D --reviewer NAME --evidence FILE --baseline-sha SHA` |
| `gate_cleared` | `--gate G --by NAME --evidence FILE` |

  `gate-record` validates, refusing on any failure: unknown events and enum values; a flag missing or not listed for the event; a `--run` or `--runs` entry that is not a run of the task; a `--baseline-sha` that is not a full 40-hex commit in the task's repo; a `reviewer` equal to `worker_identity.model` on any `start` or `resume` of the task, or to its `agent`, compared exactly; and a `gate_cleared` for a gate that is not open (stall state not `open`, or an empty open list). Every assessment without `--new-evidence` records both fields null.

- **Evidence files**, for every flag above that takes a file: a regular, non-empty, readable file, otherwise refused. Repeated events are appended, never deduplicated: the rules above define which one counts.
- **Task's repo:** the `repo` file in the task's run directory, otherwise `K3DM_REPO_ROOT`'s repo.
- **Parent names** on `start`, `link` and `combine` must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`, otherwise refused.
- `gate-coverage-start`: appends `gate_coverage_start` once; a second call changes nothing and exits 0.
- `start` gains `--parent P --role R`; `make codex-dispatch` passes `PARENT=` and `ROLE=`. `link --slug S --parent P --role R` appends its event. `combine --parent P --parts a,b --conflicts N --result pass|fail --evidence FILE --by NAME` appends its event, and refuses a part that is not a task of the version or whose current parent is not P. Repeated combines are allowed; the last one counts.
- New commands in the usage text and `docs/howto/codex-dispatch.md`, including the "What S1 proves" limits.

Worked example, for a task whose worker was `gpt-6-luna`:

`bin/k3dm-codex-dispatch gate-record --slug fix-x --event attempt_assessed --run 2 --outcome progress --new-evidence /path/ev.log --assessor claude --baseline-sha <40-hex>`

`bin/k3dm-codex-dispatch gate-record --slug fix-x --event replan_reviewed --decision approved --reviewer gpt-6-terra --plan /path/plan.md --baseline-sha <40-hex>`

### Metrics half

Series, all computed from the ledger with the rules above. Tasks are the tasks defined above, so coverage markers, combines and slugs with no `start` never count. Gate series cover the 10 versions with the newest ledger lines. For each such version the ladder, stalled, live-pending and gate-event series are always present, at 0 when nothing matches; every rung and status combination and all six gate events are emitted, so 0 is never confused with an absent series.

- `k3dm_dispatch_ladder_tasks{version,rung,status}`
- `k3dm_dispatch_stalled_tasks{version}`: tasks with stall state `open`
- `k3dm_dispatch_live_pending_tasks{version}`: tasks with `landed` `done` and `live_verified` `pending`
- `k3dm_dispatch_gate_events{version,event}`: the six gate events only
- `k3dm_dispatch_split_parent_info{version,parent,combine}` with value 1; `combine` is the last combine's `pass` or `fail`, or `pending` when there is none
- `k3dm_dispatch_split_parent_parts{version,parent,role}`: current members by role, all three roles always present, 0 when none
- `k3dm_dispatch_split_parent_conflicts{version,parent}`: from the last combine; absent until a `combine`
- `k3dm_dispatch_split_parent_elapsed_seconds{version,parent}`: earliest `start` of any current member to the last `combine`, floored at 0; absent until a `combine`, and absent when the parent has no members
- `k3dm_dispatch_split_parents_dropped{version}`: parents not exported, always present for a covered version

**Split parents.** A parent exists when a current member or a combine names it, so a combine with no members still gets a row, with zero parts. A member linked after the combine counts in parts and elapsed, and does not change the recorded result.

**Bounded labels.** `rung`, `status`, `combine`, `role` and `event` take only the values above; an unknown value in the ledger is dropped, not exported. There is no new slug label. `parent` is the one free-form label and it is bounded twice: a value that fails the parent pattern is never exported, and at most the 20 parents with the newest ledger lines are exported across all versions. Both kinds of omission add to `split_parents_dropped`.

**Existing series do not move.** New events and fields change no existing series. Coverage markers, combines and gate events must stay out of the exporter's existing `(version, slug)` grouping.

Agent Dispatch gains four panels: **Stalled tasks**, **Live verification pending**, **Verification ladder** (unknown shown separately, never as zero), and **Split work**, a table with one row per parent: parts by role, conflicts, combine result, elapsed. Every panel query matches a produced series. Each panel description says the data is self-reported and advisory.
