# v1.13.0 — Modularize `k3dm-webhook` In-Repo Before Any Extraction

**Status:** Design approved (v1.12.0); implementation deferred to v1.13.0  
**Branch:** `k3d-manager-v1.13.0` (implementation)  
**Owner:** Codex  
**Scope:** `bin/k3dm-webhook`, new Python support modules, webhook tests, docs

## Goal

Reduce the complexity and change risk of `bin/k3dm-webhook` by splitting it
into clear internal modules while keeping the feature inside this repo.

The immediate objective is maintainability, testability, and safer future work
for Slack commands, cluster operations, diagnostics, and failure analysis.

## Problem

`bin/k3dm-webhook` has accumulated too many responsibilities:

- HTTP ingress and routing
- Slack event handling
- bearer/signature validation
- background job lifecycle
- command parsing and dispatch
- provider-aware cluster execution
- failure analysis
- response formatting
- state-dir and orphan cleanup

That produces a single-file hotspot where small feature work can destabilize
unrelated paths.

## Decision

Do **not** move the whole webhook into:

- a separate repo, or
- `lib-foundation`

yet.

First modularize in-place. Only after the boundaries are stable should we
consider extracting generic helpers. The webhook’s command semantics and cluster
behavior are currently too `k3d-manager`-specific for `lib-foundation`.

## Non-Goals

- Rewriting the webhook in another language
- Changing the external Slack/Worker contract in this refactor
- Extracting provider logic out of `k3d-manager`
- Moving command semantics into `lib-foundation` now

## Target Structure

Keep `bin/k3dm-webhook` as a thin entrypoint that imports from a new internal
package under the repo, for example:

- `scripts/lib/webhook/server.py`
- `scripts/lib/webhook/auth.py`
- `scripts/lib/webhook/routes.py`
- `scripts/lib/webhook/commands.py`
- `scripts/lib/webhook/jobs.py`
- `scripts/lib/webhook/dispatch.py`
- `scripts/lib/webhook/diagnostics.py`
- `scripts/lib/webhook/render.py`
- `scripts/lib/webhook/config.py`

The exact directory name can vary, but the split should follow responsibility,
not arbitrary file count.

## Module Responsibilities

### `server.py`

- HTTP server bootstrap
- request/response lifecycle
- startup/shutdown hooks

### `auth.py`

- bearer token validation
- Slack signature validation
- any future role/identity helpers

### `routes.py`

- route registration
- request body normalization
- path-to-handler mapping

### `commands.py`

- command registry
- argument parsing
- command metadata used by dispatch/RBAC

### `jobs.py`

- background execution
- job state directories
- status/result files
- orphan detection and cleanup

### `dispatch.py`

- map commands to repo workflows
- provider-aware execution seams
- subprocess invocation wrappers

### `diagnostics.py`

- failure analysis
- cluster observations
- product-image health probing
- status helpers reused by commands

### `render.py`

- Slack response formatting
- thread updates
- error/result rendering

### `config.py`

- constants
- env var parsing
- filesystem paths
- timeouts / defaults

## Why Not `lib-foundation` Yet

`lib-foundation` should only receive code that is both:

1. genuinely generic, and
2. already stable at the seam.

Today the webhook is still tightly bound to:

- this repo’s provider model
- shopping-cart diagnostics
- Slack command semantics
- cluster lifecycle commands
- repo-specific LaunchAgent and Cloudflare behavior

Those are not appropriate `lib-foundation` exports yet.

## Candidates for Later Extraction

After in-repo modularization, some pieces may be generic enough to move:

- HTTP bearer/signature auth helpers
- job-state directory primitives
- retry/backoff utilities
- subprocess execution wrappers
- command-registry scaffolding

Only extract those if another repo demonstrably needs them.

## Proposed Changes

### Change 1 — create internal Python module layout

Introduce the new module package and keep the current CLI entrypoint as a thin
shim that imports and runs the server.

### Change 2 — move pure helpers first

Start by extracting low-risk pure logic:

- config/path helpers
- auth helpers
- render helpers
- command metadata

This reduces merge risk before moving execution-heavy logic.

### Change 3 — isolate job runner and dispatch seams

Move background job handling and command execution into their own modules with
stable function boundaries. This is the key seam for future operator RBAC.

### Change 4 — isolate diagnostics/failure analysis

Failure-analysis code should be separated from HTTP routing so it can evolve
without destabilizing Slack ingress behavior.

### Change 5 — strengthen tests around seams

Add or update tests so they target modules directly where possible, while still
keeping end-to-end webhook tests for the integrated flow.

## Suggested Delivery Phases

### Phase 1 — thin entrypoint + config/auth/render split

Low-risk decomposition with no command-behavior changes.

### Phase 2 — command registry + dispatch split

Move command parsing and execution mapping out of the main file.

### Phase 3 — jobs/state management split

Isolate background execution, job files, and orphan cleanup.

### Phase 4 — diagnostics/failure analysis split

Move cluster observation and AI-analysis helpers into dedicated modules.

### Phase 5 — evaluate generic extraction candidates

Only after the above is stable, review whether any pieces belong in
`lib-foundation`.

## File Targets

Expected areas:

- `bin/k3dm-webhook`
- new `scripts/lib/webhook/*.py` modules
- `scripts/tests/lib/webhook.bats`
- any new Python-focused webhook unit tests if introduced
- docs describing the module boundaries

## Acceptance Criteria

- `bin/k3dm-webhook` becomes a thin entrypoint instead of the main logic blob.
- Core responsibilities are split into explicit internal modules.
- Existing Slack/webhook behavior is preserved.
- Tests cover the new seams and existing integration behavior.
- No extraction to `lib-foundation` occurs until generic boundaries are proven.
