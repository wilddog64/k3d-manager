## Problem

The hub data export runs daily and unattended (`v1.43.0-hub-data-export-schedule.md`), but the
drill that proves the export restores is still two manual steps: `make dr-drill` on the M2, then
`make dr-drill-publish` on the M4 (`docs/howto/hub-dr-drill.md`, "Weekly run"). If the operator
forgets, the only signal is `DRDrillStale` after 8 days, and the data repo's freshness workflow
fails at the same point.

v1.43.0 ruled out an unattended drill (`v1.43.0-hub-dr-drill.md`, "No unattended run of the
drill") for two reasons that v1.43.1 has since removed:

- the Keychain guard only audited; it now defaults to `enforce`, so an off-list `security` call
  exits 44 (`scripts/etc/dr/security-shim`);
- the drill overwrote the host's Vault unseal cache; it now uses `k3dm-vault-unseal-drill` and
  purges it at teardown.

Three things still block a schedule:

1. `_dr_drill_preflight` in `bin/dr-drill` refuses without a TTY (`interactive TTY required`).
2. Every Keychain read the drill makes (`credential-allowlist.tsv`, scope `drill`) needs the
   login keychain unlocked in a GUI session. From ssh or a daemon it fails with
   `User interaction is not allowed`.
3. Publishing runs on the M4 and is manual. `bin/dr-drill-publish` also exits 1 when the newest
   result is already published, so it cannot simply be rerun on a timer.

## Decisions

| # | Decision |
|---|---|
| D1 | **M2 runs a GUI LaunchAgent**, `com.k3d-manager.dr-drill`, bootstrapped into `gui/$(id -u)` with `LimitLoadToSessionType` `Aqua`, weekly on **Sunday 05:00 local**. The M4 export runs at 03:30, so the newest export is about 1.5 h old (V7 needs ≤ 26 h). launchd runs a slot missed during sleep on wake. |
| D2 | **Unattended mode is explicit.** `DR_DRILL_UNATTENDED=1` (set only by the plist) replaces the TTY check. In that mode the drill refuses unless the credential policy is `enforce` (it refuses `audit` and any unknown value) and refuses if another drill holds the lock (D5). An attended `make dr-drill` is unchanged. |
| D3 | **No Keychain ACL widening.** Unattended preflight probes the login keychain with `security show-keychain-info` (through the shim; add the allowlist row) and refuses with `login keychain locked` if it fails. It never prompts, never calls `set-generic-password-partition-list`, and never unlocks the keychain. The items the drill reads were created by `security`, which can read them without a prompt while the keychain is unlocked. |
| D4 | **A refusal is a result.** When unattended preflight refuses, the drill still writes `~/.k3dm/dr-drill/<ts>.json` with `success: false`, `rto_seconds: 0`, `rpo_seconds: 0`, empty `checks` and `refused: "<reason>"`. Publishing then fires `DRDrillFailed` the same day instead of waiting 8 days for `DRDrillStale`. Attended refusals keep today's behaviour (no result file). |
| D5 | **One drill at a time.** `bin/dr-drill` takes `~/.k3dm/dr-drill/drill.lock` (mkdir lock, removed by the EXIT trap; a lock older than 6 h with no live PID is reclaimed). An attended run during a scheduled one refuses, and the reverse. |
| D6 | **The M4 pulls; the M2 never pushes.** A second LaunchAgent on the M4, `com.k3d-manager.dr-drill-publish`, runs `bin/dr-drill-publish` **daily at 09:00**. The data repo write key stays on the M4 only. A daily pull also catches a Sunday run delayed by sleep. |
| D7 | **Publish is idempotent.** When `results/<stamp>.json` already exists and is byte-identical, `bin/dr-drill-publish` prints `already published: <stamp>`, still pushes the metrics and exits 0. A different file with the same stamp still exits 1 (it is never overwritten). |
| D8 | **Alerts unchanged.** `DRDrillFailed` and `DRDrillStale` (email, `platform-warning`) cover failure and silence. No SMS. |

## Changes

### 1. `bin/dr-drill`

- In `_dr_drill_preflight`: when `DR_DRILL_UNATTENDED=1`, skip the TTY check and instead:
  - refuse unless `${DR_DRILL_CREDENTIAL_POLICY:-enforce}` is `enforce`;
  - run the keychain probe from D3 after the guard is installed;
  - on any refusal, write the D4 result before exiting.
- Add the D5 lock before the leftover-cluster check.
- Log to `~/.k3dm/dr-drill/run.log` (append, one header line per run with the timestamp and
  `unattended=0|1`). Never log a `security` argument other than what the shim already redacts.

### 2. `scripts/etc/dr/credential-allowlist.tsv`

- One row: `drill	show-keychain-info	-	-` (or the shim's existing form for a call with no
  service or account; read the shim before choosing). No other new rows.

### 3. `bin/dr-drill-publish`

- D7: replace the `result already exists` exit with a `cmp` against the clone's file.
- Accept the D4 refusal result. The `jq -e` check gains an optional string `refused`, and the
  check-count rule allows empty `checks` only when `refused` is present.

### 4. Schedules

- `scripts/etc/launchd/com.k3d-manager.dr-drill.plist.tmpl`: `StartCalendarInterval`
  `{Weekday 0, Hour 5, Minute 0}`, `LimitLoadToSessionType` `Aqua`,
  `EnvironmentVariables` `DR_DRILL_UNATTENDED=1`, program `/usr/bin/caffeinate -i
  {{K3D_MANAGER_REPO}}/bin/dr-drill` (idle sleep only; lid-closed sleep still stops it, which D6
  absorbs), `StandardOutPath`/`StandardErrorPath` under `{{HOME}}/.k3dm/dr-drill/`.
- `scripts/etc/launchd/com.k3d-manager.dr-drill-publish.plist.tmpl`: daily `{Hour 9, Minute 0}`,
  runs `{{K3D_MANAGER_REPO}}/bin/dr-drill-publish`, logs under `{{HOME}}/.k3dm/dr-drill/`.
- `scripts/plugins/hub_data.sh`: `dr_drill_schedule`, `dr_drill_unschedule`,
  `dr_drill_publish_schedule` and `dr_drill_publish_unschedule`, in the same shape as
  `hub_data_export_schedule` / `hub_data_export_unschedule` (render with `sed`, `bootout` then
  `bootstrap` into `gui/$(id -u)`; no-op off macOS).
- `Makefile`: targets `dr-drill-schedule`, `dr-drill-unschedule` (M2) and
  `dr-drill-publish-schedule`, `dr-drill-publish-unschedule` (M4), added to `.PHONY`.

### 5. Docs

- `docs/howto/hub-dr-drill.md`: a "Weekly schedule" section covering:
  - install on each machine;
  - what has to be true on Sunday morning (the M2 logged in with the screen locked, not logged
    out; lid open or on power);
  - how a refusal appears (`DRDrillFailed`, a `refused` field in the result);
  - how to run one now (`launchctl kickstart gui/$(id -u)/com.k3d-manager.dr-drill`);
  - the attended run, which stays available.
- `docs/architecture/hub-dr-drill.md`: the sequence gains the two agents and the pull model; the
  "no unattended run" constraint is replaced with D2–D3.
- `CHANGELOG.md` `[Unreleased]`.

## Tests

Use the existing stubs (`DR_DRILL_TEST_TTY`, stubbed `k3d`/`docker`/`security`). Nothing may call
the real `security`, `launchctl` or the data repo.

`dr_drill.bats`:
- unattended with no TTY and policy `enforce` passes the TTY gate;
- unattended with policy `audit` refuses and writes a result with `success: false` and a
  `refused` field naming the policy;
- unattended with a failing keychain probe refuses with `login keychain locked` and writes the
  result;
- attended with no TTY still refuses and writes **no** result file;
- a held lock refuses a second run; a stale lock (dead PID, older than 6 h) is reclaimed.

`dr_drill_publish.bats`:
- an identical published result exits 0, prints `already published`, still pushes metrics (to the
  stub);
- a different file under the same stamp exits 1;
- a refusal result is accepted and pushes `k3dm_dr_drill_success 0`.

`hub_data.bats`:
- both rendered plists pass `plutil -lint` when available, contain no `{{`, set
  `DR_DRILL_UNATTENDED=1` (drill only) and `LimitLoadToSessionType` `Aqua`.

Mutations, each of which must turn a test red:
- drop the policy check;
- write the refusal result in attended mode too;
- make publish overwrite a different same-stamp file;
- drop the lock.

## Proof it works

1. On the M2 from Terminal.app: run `make dr-drill-schedule`, then
   `launchctl kickstart gui/$(id -u)/com.k3d-manager.dr-drill` with the screen **locked**. A result
   JSON appears with `success: true` and `credentials_unexpected: []`.
2. On the M4: `make dr-drill-publish-schedule` and a kickstart publish it. A second kickstart
   prints `already published` and exits 0.
3. With the M2 logged out (the keychain is locked), a kickstart writes a `refused` result. After
   publishing, `DRDrillFailed` fires by email. Delete that result from the data repo afterwards
   only if the operator says so.
4. The first Sunday after install: a new result is published by Monday 09:00 with no operator
   action.

## What NOT to Do

- Do NOT widen a Keychain ACL, add `-T` apps, call `set-generic-password-partition-list` or unlock
  the keychain from a script.
- Do NOT let the M2 push to the data repo or hold its write key.
- Do NOT allow any policy other than `enforce` in unattended mode.
- Do NOT run the drill as a LaunchDaemon or over ssh; it must stay in the GUI session.
- Do NOT change `DRDrillFailed`/`DRDrillStale` or route them to SMS.
- Do NOT remove the attended `make dr-drill` path.
- Do NOT create a PR, skip hooks (`--no-verify`) or commit to `main`.
