## Problem and evidence

The count-intent fix recognizes `how many P1 open for v1.43.5`, but a live
request still hit the 30-second tally timeout after the webhook was reloaded.
The existing P2 remains open. The verification record includes a 43.471-second
baseline and a 37.997-second candidate under background load. Other attempted
history optimizations either remained too slow or changed attribution in a
rename fixture. A warm local run alone does not establish live reliability.

## Review finding 2026-10-29 — the measured cost is scheduling, not the tally

Claude measured the same command the webhook runs
(`bug-tally.py --json --counts-only --ref HEAD`) on the M4, in the live repo:

| Scheduling | Wall time |
|---|---|
| normal (interactive shell) | 1.8 s, 0.85 s |
| `taskpolicy -b` (background), sample 1 | 13.0 s |
| `taskpolicy -b` (background), sample 2 | 58.6 s |
| `taskpolicy -d throttle` (I/O throttled) | 130.6 s |

The tally code and inputs are unchanged across those rows. Only the scheduling class differs. The 58.6 s sample exceeds the 30 s deadline, matching the live failure. The earlier 43.5/38.0 s Luna figures were also "background-priority" runs. The warm 1.8 s / 0.6 s figures were not.

The webhook LaunchAgent (`scripts/etc/launchd/com.k3d-manager.webhook.plist.tmpl`) sets no `ProcessType`. `launchd.plist(5)` says: "If left unspecified, the system will apply light resource limits to the job, throttling its CPU usage and I/O bandwidth." The tally's Git children inherit that throttle.

Profiling also shows the per-commit `git tag --contains` in `_release_of_commit` is cheap here: 0.02 s each, 94 add-commits, 149 tags. The `-G Status:` history walk is 0.8 s. Neither is the 30 s problem at normal priority.

**Consequence for this plan:** the snapshot/index design below stays as a fallback, but it is not the first step. It adds invalidation, concurrency and rollout risk to solve a cost that mostly disappears at normal priority.

### Phase 0 (do first): run the webhook at interactive priority, then measure

1. Add `<key>ProcessType</key><string>Interactive</string>` to the webhook plist template only. No other LaunchAgent changes; Hermes, exporters and port-forwards stay throttled by design.
2. The operator re-runs `make restart-webhook` (or the setup that renders the plist), then `launchctl print` shows the new class.
3. Measure the live count path at least 20 times over a day that includes ordinary background load. Proceed to the snapshot design only if p95 exceeds 3 s or any request exceeds the 30 s deadline.

Do not raise the 30 s deadline. Do not add `taskpolicy` wrappers inside the tally: a child cannot escape its parent's clamp, and that would hide the cause.

## Proposal for review (fallback if Phase 0 is insufficient)

Evaluate a validated, immutable snapshot or index derived from the existing
authoritative bug tally so that an interactive count can read precomputed
results instead of traversing Git history on every request. Compare this with
other designs before selecting one. This is a candidate architecture, not a
decision to deploy a cache or scheduler. Preserve the existing tally's release,
priority, open/fixed, rename and branch-fallback semantics, including its
handling of missing priorities. The model must not supply the numbers.

The design review must resolve:

1. Snapshot identity and freshness: include repository identity, all relevant
   commit and tag references, branch/fallback context and tally algorithm or
   schema version. Handle moved or deleted tags and branches. Pin inputs for a
   computation and detect changes during construction; do not serve an answer
   as current if the snapshot cannot be validated against the requested state.
2. Construction and operation: specify when and where rebuilding happens, how
   concurrent readers/builders coordinate, atomic publication, ownership and
   permissions, bounded retention, recovery after interruption, and rollback.
   Consider existing tally producers without assuming they can safely be reused.
3. First request and failure: explicitly define cold start, cache miss, stale
   data, rebuild failure and unavailable Git history. Return an honest,
   actionable unavailable/pending result when a current count cannot be proven;
   never invent zero, silently use stale data, or substitute document search.
   A cold build may exceed the interactive deadline; do not promise otherwise.
4. Compatibility: preserve the normal full tally CLI and its consumers,
   including `fixed_in`; keep generic document questions and Slack thread
   routing outside this change. The later query-translation proposal must use
   the same validated tally rather than infer counts from model summaries.
5. Deployment and verification: identify the owner, build trigger and resource
   cost on the actual webhook host, and provide a reversible rollout and live
   verification procedure. Any new service or scheduled job needs explicit
   evaluation and approval before rollout.

Model-summary latency is a separate concern; summarization cannot establish an
authoritative count and is not part of this proposal. Do not treat increasing
the timeout alone as the solution.

## Proposed acceptance criteria

- Compare snapshot results against the existing full tally on representative
  historical releases and fixtures, including positive and zero counts,
  missing priorities, branch fallback, renames, divergent history, and moved,
  deleted and recreated refs. Test ref changes during construction and ensure
  concurrent readers never see a partial snapshot.
- Test cold start, invalidation, failed/interrupted builds, restart, concurrent
  requests and rollback. Failure must be explicit and must not return stale
  results as current. Preserve existing full CLI output and unrelated routing.
- Proposed review targets, not an agreed service level: at least 20 measured
  warm requests on the webhook host, with local count lookup p95 ≤ 3 seconds
  and p99 ≤ 5 seconds; record workload, inputs and individual timings. Confirm
  a warm end-to-end Slack count completes inside the existing 30-second limit.
- Independently compare the exact reported Slack question with the authoritative
  tally at the same pinned refs, including a zero result and its source evidence.
  Record the result and timing; mark the existing P2 live-verified only after
  its actual acceptance requirements pass.

## Evaluation decisions

Choose the implementation approach, snapshot storage and invalidation model;
decide whether cold requests wait or report pending; agree on performance
targets, operational ownership and rollout. Review those decisions with the
operator before dispatch. Potential implementation areas include
`scripts/bug-tally.py`, `scripts/lib/webhook/bug_count.py` and their focused
tests; final file scope depends on the selected design.
