## Problem

The v1.43.0 export (`make hub-data-export`, `scripts/plugins/hub_data.sh`) pushes age-encrypted
claims to `wilddog64/k3dm-hub-data`. What protects it today, checked 2026-10-10:

| Need | Today | Gap |
|---|---|---|
| Corruption check | `SHA256SUMS` over `*.age`, checked at restore (`hub_data.sh:247`) | `pv-pvc.yaml` and `inventory.json` are not covered, yet `pv-pvc.yaml` is applied to the cluster. A `.age` file missing from `SHA256SUMS` is decrypted unchecked, because the loop walks the manifest, not the directory. |
| Malicious change | none | Nothing is signed. The age public key is in git, so anyone who can push can write a new export and a matching `SHA256SUMS`. |
| Deletion / force-push | none | `main`, `snapshots` and `results` have no branch protection and no ruleset. |
| Retention | none | The v1.43.0 plan (D2) specifies `K3DM_HUB_DATA_KEEP` (default 4); it was never built. |
| A copy outside GitHub | none | GitHub is the only off-machine copy. |

One export is about 120 MB (`identity-postgres-keycloak-pvc` 71 MB, `secrets-data-vault-0` 50 MB),
and encrypted data does not compress. Pruning with normal commits would grow the repo by about
120 MB a week of history, which passes GitHub's 1 GB guidance in about two months. So `snapshots`
keeps the planned force-push prune, and protection against deleting or rewriting it comes from the
signature and from copies outside GitHub, not from a ruleset.

## What this guards against, and what it does not

- **Guards:** a stolen GitHub session or token, a stolen `m4-write` deploy key, a mistaken
  force-push or branch delete, silent corruption, and pruning that removes the last good export.
- **Does not guard:** a compromised M4. It holds both the write key and the signing key. The
  external-disk copy (D5) is the answer to that, because it is offline.

## Deliverables

### D1 — A complete manifest

`_hub_data_encrypted_checksum` lists **every** file in the export directory except `SHA256SUMS`
and its signature: `*.age`, `*.age.part-*`, `pv-pvc.yaml` and `inventory.json`.

At restore, before anything is decrypted:
- every manifest line must verify (as today);
- the set of files in the directory must equal the set in the manifest. An extra or a missing file
  fails with `[hub-data] export <ts> does not match its manifest: <file>`.

### D2 — Signed manifest

- **Sign (M4, in `hub_data_export`, after D1):**
  `ssh-keygen -Y sign -f "$K3DM_HUB_DATA_SIGN_KEY" -n k3dm-hub-data SHA256SUMS` writes
  `SHA256SUMS.sig`. The default `K3DM_HUB_DATA_SIGN_KEY` is `~/.k3dm/keys/hub-data-sign`.
  If the key is missing, the export fails before it pushes. There is no unsigned mode.
- **Pin (git):** `scripts/etc/dr/hub-data-allowed-signers`, one line in `allowed_signers` format,
  principal `k3dm-hub-data`. The operator commits the public key; it is not a secret.
- **Verify (M2, in `hub_data_restore`, before D1's checks):**
  `ssh-keygen -Y verify -f scripts/etc/dr/hub-data-allowed-signers -I k3dm-hub-data -n k3dm-hub-data -s SHA256SUMS.sig < SHA256SUMS`.
  A failure stops the restore with `[hub-data] export <ts> signature does not verify`.
  The allowed-signers file is read from the k3d-manager checkout, never from the data repo.
- The signing key is never passed as an argument value that holds key material; `-f` takes a path.

### D3 — Retention (the v1.43.0 D2 design, now built)

`hub_data_prune`, called at the end of `hub_data_export`:
- keeps the newest `K3DM_HUB_DATA_KEEP` exports (default 4);
- **always** keeps the newest export named by a passing result on the `results` branch, even if
  that makes it keep `KEEP + 1`. Pruning must never remove the last export a drill proved good;
- rewrites `snapshots` to one orphan commit holding only the kept directories, then
  `git push --force-with-lease` to `snapshots` only. Every other branch is pushed without force;
- refuses (non-zero exit, nothing pushed) when it would keep fewer than 2 exports, or when any kept
  export fails D1 or D2 checks;
- prints `git count-objects -vH` size after the push.

### D4 — Data repo rulesets (operator applies; the spec supplies the JSON)

`scripts/etc/dr/hub-data-ruleset.json`, applied by the operator with
`gh api repos/wilddog64/k3dm-hub-data/rulesets -X POST --input scripts/etc/dr/hub-data-ruleset.json`:

| Branch | Deletion | Force-push |
|---|---|---|
| `main` | blocked | blocked |
| `results` | blocked | blocked |
| `snapshots` | blocked | allowed (D3 prune) |

No bypass actors. A `make hub-data-protection-check` target reads
`repos/wilddog64/k3dm-hub-data/rules/branches/<b>` for all three and fails when a rule is missing.
It is read-only.

### D5 — Copies outside GitHub

- **M2 local copy (automatic):** after a drill restore verifies D1 and D2, `bin/dr-drill` copies the
  encrypted export directory (still encrypted) to `~/.k3dm/dr-drill/exports/<ts>/`, mode 700,
  keeping the newest `DR_DRILL_KEEP_EXPORTS` (default 4). A GitHub-side deletion or rewrite then
  cannot remove what the M2 already verified.
- **External disk (attended, monthly):** `make hub-data-offline-copy DEST=/Volumes/<disk>` on the M2
  copies the newest verified local export there and verifies it in place (D1 + D2). The disk is
  unplugged afterwards; that is what makes it offline.
- **WORM storage (S3 Object Lock or similar):** out of scope. It needs a paid cloud account. Listed
  under open decisions.

### D6 — Scheduled integrity check

The data repo's `drill-freshness` workflow gains a step that, for **every** export on `snapshots`
(not only the newest), checks D1 and D2. It needs no decryption key. The allowed-signers file is
copied into the data repo's `main` as `.github/hub-data-allowed-signers` by the operator, so the
workflow does not read k3d-manager. A failure fails the workflow, and GitHub emails.

## What NOT to do

- Do not read, print or generate the operator's signing key, the age identity or any deploy key.
- Do not add an unsigned or skip-verify mode.
- Do not force-push any data repo branch except `snapshots`.
- Do not apply the ruleset; the operator does.
- Do not create a PR, skip hooks (`--no-verify`), commit to `main`, or touch files not named here.
