## Decision

One dashboard, rolling 30 days, instead of a separate monitoring system:

| Headline | Target | Definition |
|---|---|---|
| Availability | ≥ 99.5% | 1 − (minutes of SEV1 + SEV2 incidents in the window ÷ window minutes) |
| Deployment success | ≥ 95% | successful webhook deployment jobs ÷ all finished jobs |
| DR drill pass rate | 100% | passing drill results ÷ drill results |
| Automation success | ≥ 90% | Codex dispatches landed ÷ land attempts |
| Security SLA | ≥ 95% | from the v1.45.0 CVE remediation data: critical/high CVEs fixed inside the patch window ÷ due |
| Detection coverage | ≥ 95% | incidents detected by `alert`, `sensor` or `test` ÷ all classified incidents |

Plus a weekly history of the rates (last 4 ISO weeks), a severity row, and the human-effort trend.

### Why the windows are not PromQL

Hub Prometheus keeps 3 days (`retention: 3d`). The deployment, DR and dispatch producers push the
**last** value to the Pushgateway, so even with retention a gauge average is time-weighted, not per
run: one failed drill that stands for a week counts as a week of failure. Raising retention to 35 days
was rejected: the hub runs on a 24 GB laptop.

So the rates are computed from **durable per-run records** by one aggregator, which pushes the
finished ratios. Prometheus only has to hold the latest value.

## Changes

### 1. Deployment ledger — `bin/k3dm-webhook`

Webhook jobs are pruned after 7 days (`_JOB_RETENTION_SECS`). In `_push_metrics`, also append one
line to `${K3DM_LEDGER_DIR:-$HOME/.k3dm/ledger}/deployments.jsonl`:

```json
{"ts": 1760269000, "action": "...", "provider": "...", "status": "success|failed", "duration_secs": 412}
```

Best effort: a write error logs one line and never fails the job. No arguments, env or output in
the record. Create the directory `0700`, the file `0600`.

### 2. Aggregator — new `bin/k3dm-quality-metrics` (Python 3, stdlib)

Inputs (each optional; a missing source → that measure is absent, not 0):

| Measure | Source |
|---|---|
| `deployment` | `deployments.jsonl` above |
| `dr_drill` | drill result JSONs (`run_timestamp`, `success`) in the local hub-data checkout `${K3DM_HUB_DATA_DIR}`; read-only, never `git pull` or write |
| `automation` | the dispatch `ledger.jsonl` read by `bin/k3dm-dispatch-metrics` (reuse its `read_ledger`) |
| `availability`, `detection` | bug docs, via the parsing added in `v1.48.0-incident-severity-records.md` (import it; do not re-parse) |
| `security_sla` | the v1.45.0 CVE remediation record if it exists at build time; otherwise absent and the panel says why |

Output, `PUT` to `${K3DM_QUALITY_PUSHGATEWAY_URL:-http://localhost:19094}/metrics/job/k3dm-quality`
with the same retry and non-fatal skip as `bin/k3dm-disk-metrics`:

```
k3dm_quality_ratio{measure="deployment",window="30d"} 0.97
k3dm_quality_runs{measure="deployment",window="30d"} 34
k3dm_quality_weekly_ratio{measure="deployment",week="2026-W41"} 0.95
k3dm_quality_target{measure="deployment"} 0.95
k3dm_quality_source_ok{measure="security_sla"} 0
```

- A measure with zero runs in a window emits `runs 0` and no `ratio` (the panel shows "no runs",
  not 100% or 0%).
- `--dry-run` prints the body and pushes nothing. `--now` injects the clock for tests.

### 3. `bin/k3dm-hermes`

`_publish_quality_metrics(state, now)` next to `_publish_disk_metrics`, same try/except shape, at most
hourly via `state["quality_last_run"]` (same pattern as the OrbStack metrics).

### 4. Dashboard — new `scripts/etc/argocd/platform-ops/grafana-dashboard-operational-quality.yaml`

ConfigMap shaped like `grafana-dashboard-bugs.yaml`; uid `k3dm-operational-quality`; title
"k3dm Operational Quality".

- **Row 1 — six stats** (two rows of three), each `k3dm_quality_ratio{measure=…,window="30d"}` as a
  percentage, the target in the panel description and as a threshold (red below target, green at or
  above). Each description says what is counted and where it comes from; a measure whose source is
  missing shows "no data" and the description says which release supplies it.
- **Row 2 — Operational quality history**: time series of `k3dm_quality_weekly_ratio` for
  deployment, automation and DR, x-axis by week label (bar chart or table is fine if a time series
  cannot plot labels; say which in the PR).
- **Row 3 — Severity**: per level, the series from the severity spec (SEV1 count + mean recovery,
  SEV2 count + mean duration, SEV3 count + recurred, SEV4 backlog + median resolution).
- **Row 4 — Human effort per verified release**: placeholder panel reading
  `k3dm_release_human_effort_total`; filled by `v1.48.0-human-effort-per-release.md`.
- No alert rules in this spec.

### 5. Docs

- `docs/guides/grafana-dashboards.md`: a k3dm Operational Quality section — every headline, its

## Tests

Python, temp dirs, injected `now`, `--dry-run` only, autouse fixture setting
`K3DM_QUALITY_PUSHGATEWAY_URL` to `http://127.0.0.1:9`.

1. 19 success + 1 failed deployment in 30 days, plus 5 older → ratio `0.95`, runs `20`.
2. One failed drill among four → `dr_drill` ratio `0.75`, regardless of how long ago it ran inside
   the window (proves per-run, not time-weighted).
3. No deployment records → no `ratio` line, `runs 0`.
4. Missing `K3DM_HUB_DATA_DIR` → no `dr_drill` series, exit 0.
5. Weekly buckets: records in two ISO weeks → two `week=` series with the right ratios.
6. Availability: one SEV2 of 72 minutes in a 30-day window → `1 − 72/43200`.
7. Detection: 3 incidents detected by alert/sensor, 1 by human → `0.75`; unclassified docs excluded.
8. Webhook: `_push_metrics` appends exactly one ledger line with the five keys and no other; a
   read-only ledger dir does not fail the job.
9. Hermes: quality step skipped at 10 minutes, runs at 61.
10. Dashboard JSON parses; uid `k3dm-operational-quality`; six stat panels whose exprs reference
    `k3dm_quality_ratio` and each `measure`.

Mutations (each must turn a test red; restore with `cmp`): average a time-weighted gauge instead of
counting runs (test 2); emit ratio `1` when runs is 0 (test 3); drop the 30-day filter (test 1).

Gates: `pytest` on the three test files, `make test-pytest`, `make test` (per-suite counts),
`make validate-manifests`, `shellcheck` on any shell touched.

## Proof it works

After landing, the operator applies the dashboard and restarts Hermes. Within an hour the dashboard
shows deployment and automation ratios from real records, DR drill from the hub-data checkout, and
availability / detection from the classified bug docs. Measures without a source show "no data" with
a description naming the release that supplies it.
