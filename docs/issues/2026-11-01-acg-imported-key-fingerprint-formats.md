# Imported ACG key fingerprint mismatch

Copilot PR #73 finding: the duplicate-key check used SSH wire-format MD5 for every key. EC2 documents SHA-256 for imported Ed25519 keys, including the default key generated by k3d-manager machine setup. The EC2 user guide documents MD5 of DER public keys for imported RSA keys; its API reference instead describes RFC 4716 MD5. The real AWS value for the operator's account has not been captured, so the RSA result remains a live-verification item.

- User guide: https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/verify-keys.html
- API reference: https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_DescribeKeyPairs.html
- PR comment: https://github.com/wilddog64/lib-foundation/pull/73#discussion_r4436749114

The focused tests generate disposable keys in a BATS scratch HOME and stub EC2; they made no AWS calls. Before the fix, against merged `bb7f1f28`, actual output was:

```text
1..2
not ok 1 acg provisioning accepts matching imported Ed25519 fingerprint and rejects mismatch
# (in test file /private/tmp/k3dm-lib-key-before/scripts/tests/lib/acg.bats, line 642)
#   `[ "$status" -eq 0 ]' failed
not ok 2 acg provisioning accepts matching imported RSA fingerprint and rejects mismatch
# (in test file /private/tmp/k3dm-lib-key-before/scripts/tests/lib/acg.bats, line 652)
#   `[ "$status" -eq 0 ]' failed
```

The implementation selects SHA-256 for Ed25519 and the user-guide DER MD5 algorithm for RSA; unknown and malformed keys fail closed. Follow-up: compare both algorithms against a read-only `describe-key-pairs` capture from the operator's sandbox before claiming live verification. Retain the existing fail-closed mismatch behavior.

AWS notes that fingerprint padding may be present. A focused Ed25519 test with a trailing `=` initially failed:

```text
1..1
not ok 1 acg provisioning accepts matching imported Ed25519 fingerprint and rejects mismatch
# (in test file scripts/tests/lib/acg.bats, line 645)
#   `[ "$status" -eq 0 ]' failed
```

After normalizing trailing `=` only for SHA-256 fingerprints, the same case passed. A fingerprint containing non-padding text after `=` still fails closed. The final clean-environment ACG suite passed 37/37; the earlier clean-environment system/core/agent-rigor/ACG run passed 154/154.

Live verification on `m5-air`, 2026-11-03, captured the EC2 `DescribeKeyPairs` fingerprint for the matching imported Ed25519 key as `DWj8LMmMqaZ9O3vJ8oG6xflnl5I/W5HmeoHVYWcR83A=`. AWS returns bare Base64 SHA-256 with one trailing padding character and no `SHA256:` prefix. The local `ssh-keygen -E sha256 -lf` output includes `SHA256:` and omits that padding, so the duplicate-key comparison removes the optional prefix and exactly one trailing `=` for a 43-character local digest. Extra trailing text and mismatched digests remain errors.
