No later successful cycle appeared in the bounded 120,000-line Docker log window. The independently sampled last-compaction metric agrees with the 17:45:03Z success. The alert was firing, while `/readyz` and all four node readiness checks passed. These establish a stalled retention loop alongside a ready API; they do not establish database integrity or a control-plane outage. The log search was bounded and case-sensitive, so “no later success” is limited to that captured window. Push age and Hermes heartbeat were about 10 and 8 minutes at sampling; the direct logs corroborate the fault despite that telemetry staleness. The empty direct `sensor_up` vector is not evidence that the sensor was down because Kine metrics are sent through Pushgateway. The 24-hour database delta was zero but interval coverage was not checked; it is not a growth forecast. Neither API readiness nor a temporarily recovered compactor would establish a permanent fix.

The September recurrence history contains an earlier mistaken restart recommendation and documents bootstrap crash loops after a K3s restart. Current runbook and canonical bug explicitly prohibit restarting K3s as this incident’s remedy. Do not use that historical recommendation.

## Recovery path audit

The current target is `make hub-recover-all` in the [Makefile](../../Makefile), whose actual recipe calls `hub_data_recover_preflight`, `bin/hub-restore --preflight-only`, teardown, `hub-recover`, then `hub_data_recover` with the saved run ID. Its important effects and gates are:

1. `hub_data_recover_preflight` creates a per-run directory, shallow-clones the private `snapshots` branch, selects the newest export by default (or the explicitly selected export), validates its manifest and compatibility, checks whether the local cluster exists, validates the live cluster target when present, records target metadata, and asks the operator to type the selected export timestamp. This is not a read-only preflight: it writes local run state, accesses the private Git remote, and inspects the live target. Do not run it as a casual readiness check. Approval is an exact export timestamp, not a substitute for reviewing the concrete recovery scope and evidence.
2. `_hub_data_verify_export` checks `SHA256SUMS`, file membership, hashes, and age-file headers; `_hub_data_check_compatibility` checks inventory format, required claims, and image major versions. These checks do not prove that the export is recent enough for the current recovery objective or that the encrypted archives can be decrypted and restored. The export freshness, provenance, successful decryption/restore evidence, and required age identity must be reviewed explicitly. The preflight’s target counts can report live Vault paths as unavailable pending Vault login.
3. `bin/hub-restore --preflight-only` requires an interactive TTY and a usable Keychain session unless the bypass variable is set. It exits after those checks; it does not prove every credential needed by the later restore is present. The actual restore runs credential, Vault, observability, reconcile, optional hidden embeddings-key, platform-ops, and local-agent steps. It can write Vault state, create or bootstrap LaunchAgents, and restart a running Grafana port-forward agent. It can skip an unavailable signing-key backup and an embeddings key, so those outcomes need explicit acceptance.
4. `hub_data_recover_teardown` deletes the local hub when present using `bin/cluster-down --confirm --delete-hub`, then explicitly removes remaining containers labeled for that cluster plus its exact network and images volume. This is destructive. The test `recover teardown: present removes only exact k3d leftovers` in `scripts/tests/plugins/hub_data.bats` stubs cluster-down and Docker, supplies both images and recovery-server-data volume names, and asserts that the explicit cleanup never removes `k3d-k3d-cluster-recovery-server-data`. That establishes the scope of this helper's explicit cleanup only. It does not establish how the real `k3d cluster delete` handles all node/data volumes, or prove that any particular volume survives the complete operation. The recipe has no automatic rollback to the deleted cluster if teardown, rebuild, or restore fails. The operator must have an agreed recovery/rollback path and preserve the recorded run ID and evidence.
5. `hub-recover` runs the hub-up path and Keychain-backed restore. `hub_data_recover` then revalidates the export and target, reads the age identity from the terminal, pauses ArgoCD automation, restores claims, unseals/repoints Vault, refreshes dependent services, and performs inventory/service checks. Its exit trap attempts to resume recorded ArgoCD automation and writes a report, but this does not recreate the pre-rebuild cluster or undo partial restored state.

The nested cluster-down snapshot guard is an additional prerequisite, not proof that the selected export will restore. In [hub_snapshot_guard_delete](../../scripts/plugins/hub_snapshot.sh), it first clones the remote export repository into temporary local state and accepts a newest export timestamp age of at most 24 hours; otherwise it checks the M2 snapshot path and its configured age limit. This entails Git/filesystem activity and potentially SSH checks. It is separate from validating the exact selected encrypted export, decryptability, and an operator-accepted recovery point. An approximately 11-hour local marker alone does not demonstrate this guard passed. The recovery wrapper does not pass `--discard-hub-data`; keep that protection intact.

### Confirmed runbook defects and minimal proposed documentation correction

The linked runbook's current text is internally inconsistent and stale. Its section “Data is not restored — DR drill (planned, v1.43.0)” says “None of it is built yet,” although the current Make recipe and `hub_data_recover` implement encrypted export restoration of Vault, Keycloak Postgres, and LDAP claims. The narrower statement that `make hub-recover` restores credentials/local agents remains relevant: that target does not itself call `hub_data_recover`. The complete `hub-recover-all` flow does. Implementation availability does not establish the present export's restore viability or this incident's recovery success.

The runbook's older teardown examples use `make down CLUSTER_PROVIDER=k3d` without explicit hub-deletion flags. Current Make defaults are `KEEP_LOCAL=1`, `DELETE_HUB=0`, with `DELETE_HUB=1` or `KEEP_LOCAL=0` translated into `--delete-hub`. Explicit `KEEP_LOCAL=1 DELETE_HUB=1` is rejected. However, current `bin/cluster-down` also sets `_keep_hub=0` for provider `k3d` even without `--delete-hub`; the test `acg-down k3d provider deletes the local hub by implication` records that exception. Therefore the historical command must not be described as harmless or as preserving the hub. A separately approved manual teardown example should express intent explicitly as `make down CLUSTER_PROVIDER=k3d DELETE_HUB=1`, retain the snapshot guard, and never add `DISCARD_HUB_DATA=1` as a convenience bypass. This is a proposed documentation correction, not a command to execute in this task or a replacement for the approved recovery flow.

The runbook also claims `make up CLUSTER_PROVIDER=k3d` fails because `bin/cluster-up` rejects that provider. Current Make instead routes it to [bin/hub-up](../../bin/hub-up). That script skips cluster creation when the hub already exists, then deploys services. Thus `make up`, `make hub-up`, or `make hub-recover` alone does not establish a fresh datastore or compaction recovery. The teardown phase in `hub-recover-all` is material. Bare `make up` still defaults to the remote provider and should not be offered as the hub-only operation. See [hub-up tests](../../scripts/tests/bin/hub_up.bats) and [cluster-down/Make flag tests](../../scripts/tests/bin/cluster_down.bats); these were inspected, not run.

### End-to-end dry-run audit

`DRY_RUN=1 make hub-recover-all` is **not a safe preview** and is not proposed for execution. The Make recipe has no dry-run branch: it creates directories/files and invokes preflight, Keychain checking, teardown, rebuild, and restore. `hub_data_recover_preflight` uses raw filesystem operations and `git clone` and asks for typed approval regardless of `DRY_RUN`. `hub_data_recover_teardown` has no dry-run guard around its raw `docker rm -f`, `docker network rm`, or `docker volume rm` calls. If nested cluster-down honors dry-run and leaves an existing hub in place, teardown normally refuses at its subsequent existence check; that conditional refusal does not make the whole target safe. With an absent hub, the helper can proceed into leftover cleanup. The restore path also contains raw decryption/Docker extraction and filesystem operations without an enclosing dry-run guard. The dispatcher's deployment argument guard applies to `deploy_*`, not these `hub_data_*` functions. Some nested helpers support dry-run, but their behavior does not cover this orchestration. This conclusion comes from static inspection of Make, `scripts/k3d-manager`, `hub_data.sh`, and `bin/cluster-down`; no preview or real Make target was run.
