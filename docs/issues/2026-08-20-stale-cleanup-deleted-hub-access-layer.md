# Stale cleanup teardown deleted the local Hub access layer

## What was tested

Ran `make down CLUSTER_PROVIDER=k3s-aws CLEANUP_STALE=1` during the sandbox teardown investigation,
then checked the local cluster, kubeconfig, launchd agents, listeners, and access-layer logs.

## Actual evidence

`k3d cluster list` returned no clusters, and `kubectl config get-contexts -o name` retained only
`ubuntu-hostinger`; `k3d-k3d-cluster` was absent.

Grafana's launchd log repeatedly reported:

```text
error: context "k3d-k3d-cluster" does not exist
```

The ArgoCD port-forward log ended with:

```text
/Users/cliang/.local/share/k3d-manager/bin/argocd-port-forward.sh: line 161: 83132 Killed: 9
```

The ArgoCD HTTPS wrapper repeatedly reported:

```text
socat[...] E SSL_CTX_use_certificate_file(): error:80000002:system library::No such file or directory
```

The Cloudflare tunnel log reported:

```text
Unable to reach the origin service ... dial tcp [::1]:8080: connect: connection refused
```

## Root cause

`make down` invokes `bin/cluster-down` before `cleanup-stale-resources`. Unless `KEEP_LOCAL=1` is
passed, `bin/cluster-down` deletes the local Hub cluster. The cleanup command then runs against the
missing `k3d-k3d-cluster` context. The stale cleanup matcher was not responsible for deleting the
Hub; it only removes expired managed app-cluster registrations and their generated Applications.

## Fix

When `CLEANUP_STALE=1`, the Makefile now passes `--keep-hub` automatically. `bin/cluster-down`
also leaves the Hub-dependent port-forward, HTTPS listener, and Cloudflare tunnel in place. This
preserves the Hub and its ArgoCD/Grafana access layer while still tearing down the AWS sandbox and
running guarded stale-resource cleanup. A full local-Hub teardown remains available without
`CLEANUP_STALE=1`.

## Hostinger-only recovery verification

The local Hub was recreated without provisioning AWS. The existing Hostinger VPS was verified with
`hostname && sudo systemctl is-active k3s` (`srv1754834`, `active`). The Hostinger refresh then
re-registered `ubuntu-hostinger`, reapplied its ArgoCD ApplicationSets, and restored the access layer.

Final endpoint checks returned:

```text
HTTP/2 200       https://argocd.3ai-talk.org
HTTP/2 302       https://grafana.3ai-talk.org
grafana_local=200
```

The recreated Hub required a new Grafana admin credential because the previous local Vault data was
lost with the deleted Hub. ArgoCD's initial admin credential was also regenerated by the fresh
installation; `make show-service-passwords` reads the current credentials.

The Hostinger frontend rollout remained a separate failure (`frontend` 0/1 with an older pod in
`CrashLoopBackOff`), but it did not block ArgoCD or Grafana recovery.
